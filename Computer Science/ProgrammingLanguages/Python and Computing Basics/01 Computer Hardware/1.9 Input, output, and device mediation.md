# 1.9 Input, output, and device mediation

An external device does not generally expose its raw physical behaviour directly to each running program. A **device controller** manages lower-level interaction with a device, while software called a **device driver** presents operations suitable for the operating system. The operating system is introduced in Chapter 2; for now it is enough to flag it as privileged coordinating software that mediates shared hardware.

The CPU can interact with devices through mechanisms including **memory-mapped I/O**, in which selected addresses designate device registers rather than ordinary memory, and explicit I/O instructions on architectures that provide them. A device may signal the processor using an **interrupt**, an event that causes control to enter a designated handler. Without interrupts, the processor might need to **poll** repeatedly by asking whether the device is ready. Polling can be appropriate under some timing constraints, but it consumes processing attention when used indiscriminately.

For substantial transfers, **direct memory access** (**DMA**) permits a controller to transfer blocks between a device and main memory with limited per-byte CPU involvement. The CPU configures the transfer, continues other work where possible, and later learns that the operation completed or failed. This already anticipates a principle that recurs in concurrency: initiating work and completing work are different events.

### Worked example 1.8 — Why pressing a key is not a character appearing instantly

When a user presses a key, a chain of representations and decisions occurs:

1. Physical switches or sensors in the keyboard change state.
2. Keyboard electronics encode an event identifying a key position and whether it was pressed or released.
3. A communication interface conveys the event to the computer.
4. A controller and driver make the event available to privileged system software.
5. Input rules combine the event with keyboard layout, modifier state, and composition rules.
6. An application receives a higher-level event or text unit.
7. The application decides whether and where to display anything.
8. Rendering software produces pixel data; display hardware turns that data into light.

The character is not stored inside the physical key. A key position, a layout convention, current modifier state, software policy, and an encoding collectively determine the eventual text. This is why changing a keyboard layout can change the resulting character without changing the keyboard’s switches.
