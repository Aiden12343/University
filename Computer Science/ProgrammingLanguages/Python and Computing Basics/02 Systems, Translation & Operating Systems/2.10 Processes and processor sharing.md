# 2.10 Processes and processor sharing

A **program** in the executable-file sense is a passive representation. A **process** is a running execution environment containing program state: an address space, one or more threads of execution, access rights, open-resource references, and operating-system bookkeeping. Launching the same executable twice ordinarily creates two processes with distinct protected state.

A **thread** is an execution sequence within a process. Threads in one process commonly share the process’s memory and resources while retaining separate call stacks and scheduling state. Full concurrency is treated in Chapter 14; here the term is introduced because process execution requires at least one thread.

The **scheduler** is the operating-system component that decides which runnable thread receives a processor and when. A **context switch** saves enough execution state from one thread and restores another so that each can continue as though its instruction sequence had merely paused. Sharing one CPU core among many runnable threads creates concurrent progress through time even when only one instruction stream executes on that core at an instant.

A process may occupy states such as:

- **running:** currently assigned to a processor;
- **runnable:** able to proceed but awaiting processor time;
- **blocked** or **waiting:** unable to proceed until an event, such as I/O completion;
- **terminated:** finished and awaiting or having completed system cleanup.

### Worked example 2.9 — Scheduling around I/O

Process A runs, requests data not currently available, and blocks. Leaving the CPU idle until storage responds would waste an available resource. The scheduler selects runnable Process B. When the device completes A’s transfer, an interrupt lets the kernel mark A runnable. At a later scheduling decision, A resumes from the state saved at its context switch.

The overlap is not evidence that A’s user-space instructions executed while it was blocked. The device and Process B made progress while A awaited an event. This distinction becomes central when choosing between threads, processes, and asynchronous I/O.

The OS also supplies **process isolation**: one process ordinarily cannot name or modify arbitrary memory belonging to another. “Ordinarily” acknowledges explicit sharing mechanisms, debugging authority, kernel vulnerabilities, and configured permissions. Isolation is a controlled default, not an absolute law immune to privileged mediation.
