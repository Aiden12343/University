# 2.12 Filesystems and persistent names

A storage device exposes blocks or another low-level transfer interface; applications need durable named information with organisation, metadata, and controlled access. A **filesystem** is the operating-system data structure and rule set that organises persistent data into files, directories, names, metadata, and allocation structures.

A **file** is an OS-managed resource presenting stored data, commonly as a sequence of bytes, together with metadata. A **directory** associates names with filesystem entries. A **path** is a structured location description interpreted according to a platform’s path rules. The path is not the file. It may fail to resolve, may designate a directory or special object, and may later designate a different entry if the namespace changes.

Opening a file normally resolves a path and produces a process-local handle. On POSIX-style systems, an integer **file descriptor** commonly indexes the process’s table of open resources. The handle refers to an open-file state that may include a current offset and access mode. Renaming or removing a directory entry need not instantly invalidate every existing open handle; pathname association and open object lifetime are separable.

Filesystems must cope with partial writes, concurrent access, device failure, and sudden power loss. A **journal** or other consistency mechanism records enough intent or metadata to recover a valid structural state after interruption. Valid structure does not guarantee that the most recent application-level operation committed all intended semantic changes. Applications requiring atomic groups of updates need suitable filesystem operations, transaction mechanisms, or higher-level storage systems.

### Worked example 2.11 — Path, entry, open handle, and content

An application opens `/reports/current.txt`. At that moment the directory path resolves to file object F, and the process receives handle 7. Another process renames the entry to `/reports/archive.txt` and creates a new file G at `/reports/current.txt`.

- The string `/reports/current.txt` is unchanged.
- A new resolution of that path reaches G.
- Existing handle 7 may continue to refer to F.
- F’s content and G’s content may differ.

Therefore a path string is not a permanent identity, and an open handle is not merely a cached spelling of a path. This distinction explains otherwise surprising behaviour in log rotation, temporary files, deployment replacement, and concurrent editors.
