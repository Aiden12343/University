# 2.13 Kernel authority and the user-space boundary

Processor hardware provides **privilege levels** that restrict sensitive instructions and memory regions. Kernel code runs with authority to configure page tables, schedule execution, handle interrupts, and control devices. User-space code runs with reduced authority. A transition into the kernel does not automatically make a request legitimate: the kernel must treat user-supplied addresses, sizes, flags, and identifiers as untrusted inputs and validate them.

Protection is relational. A process may have authority to read one file but not another, bind one network port but not a privileged port, or signal a child process but not an unrelated system service. The OS associates resources and operations with credentials and policies.

The boundary also provides failure containment. A calculation defect in one ordinary process should not overwrite kernel memory or another process’s state. It may still consume resources, corrupt files it is allowed to modify, or exploit a vulnerability. Isolation reduces the authority and blast radius of defects; it does not prove application correctness.

### Worked example 2.12 — A system call as checked delegation

Suppose a user-space process requests: “write 4,096 bytes beginning at my virtual address X to open file descriptor 5.” The kernel must establish at least:

1. descriptor 5 exists in this process and permits writing;
2. the requested address range is mapped and readable by this process;
3. the size arithmetic does not overflow an address or implementation limit;
4. the underlying filesystem and device can accept some or all of the transfer;
5. quota, storage capacity, and policy allow the operation;
6. a result reports the actual number written or a specific failure.

This is delegated authority under validation. The process does not gain raw device control merely because it requested output.

### 2.13.1 Privilege is enforced by processor state

Processor architectures supply privileged execution modes and access checks. A current privilege field influences whether an instruction can modify page-table roots, disable interrupts, configure devices, or access protected memory. The kernel arranges that ordinary process code executes in an unprivileged mode.

User code cannot enter privilege by branching to an arbitrary kernel address. Memory permissions prevent executing or reading kernel mappings, and the processor changes privilege only through defined events such as a system-call instruction, interrupt, or exception. An entry mechanism selects a kernel-controlled target and saves return state.

The kernel must distrust the request even though control arrived through a legitimate gate. A pointer remains an address in the caller’s context; the pointed bytes can be invalid or can change concurrently. Kernels use checked copy routines, pinning, locks, or repeated validation under rules appropriate to the operation.

Returning to user mode restores permitted processor state while preventing the caller from choosing privileged flags or addresses. A defect in this validation can become a privilege-escalation vulnerability.

### 2.13.2 System calls

A **system call** is a controlled request from user space for a kernel service. Typical categories include:

- create, replace, and terminate processes or threads;
- map and protect memory;
- open, read, write, and query files;
- create sockets and communicate;
- wait for events;
- obtain clocks and random data;
- change credentials under policy;
- control devices through driver interfaces.

A library function is not necessarily a system call. Python <code>len</code> ordinarily operates entirely in the runtime. A C library <code>printf</code> formats into buffers and eventually may invoke a write system call. A single high-level file read can use several calls; several high-level writes can be combined into one.

System calls commonly report a successful result or an error code. Language runtimes translate errors into return conventions or exceptions. Short reads and writes can be successful: the returned count states actual transfer. Correct code loops when its protocol requires an exact amount.

### Worked example 2.13.1 — Partial progress is not failure

A process asks to write 8,192 bytes to a non-blocking pipe. Its kernel buffer has room for 3,000 bytes. The system can:

- accept 3,000 and return 3,000;
- reject temporarily with a would-block error under specific conditions;
- be interrupted before progress;
- fail because the peer is gone.

Returning 3,000 is successful partial progress. Repeating the original 8,192 bytes would duplicate the prefix. The caller must continue from byte 3,000.

### 2.13.3 Traps, faults, and interrupts

An **exception** at processor level is a control transfer caused by executing state. Terminology differs, but useful categories are:

- **trap:** intentional or reported after an instruction, such as a system call or breakpoint;
- **fault:** detected condition for which handling may repair state and retry, such as a missing virtual-memory page;
- **abort:** severe condition without reliable restart;
- **interrupt:** asynchronous request from a device, timer, or another processor.

The processor uses a vector or table to select an entry point, saves architectural context, and changes privilege. The handler identifies cause and either resolves, signals a process, reschedules, or stops the system.

A page fault is not necessarily an error. It can implement demand paging or copy-on-write. An invalid permission fault becomes a process signal or exception. The identical hardware event class can therefore support ordinary operation and error reporting depending on mapping state.

### 2.13.4 Process identity and process control state

A process is represented in the kernel by control data sometimes called a process control block or task structure. It includes or references:

- process identifier;
- execution contexts for threads;
- virtual address space;
- open handles;
- credentials;
- current and parent relationships;
- signal dispositions;
- accounting and limits;
- scheduling state;
- current directory and namespace context.

The process identifier is a temporary name. After a process terminates and its status is collected, the number can be reused. Retaining a numeric identifier indefinitely and later signalling it can target a different process. Safer interfaces use handle-like process references or validate identity and lifetime.

A process can terminate while some resources outlive it: files persist; child processes can continue; kernel objects remain while other handles refer to them; shared memory survives under its lifetime rule. Process lifetime is not universal resource lifetime.

### 2.13.5 States and queues

A simplified process/thread state model contains:

- **running:** currently executing on a logical processor;
- **runnable:** eligible but waiting for processor time;
- **blocked:** waiting for an event;
- **stopped:** suspended by control;
- **terminated:** execution finished, with status possibly awaiting collection.

The scheduler maintains run queues. An I/O wait places a thread on an event wait structure; device completion makes it runnable. A timer interrupt can pre-empt a running thread and return it to a run queue.

“Sleeping” often means blocked, not consuming instruction cycles. Busy waiting repeatedly tests a condition and does consume cycles. A short spin can avoid a context switch if an event is imminent; long or contended waits should block under an appropriate primitive.

### 2.13.6 Context switches

A **context switch** changes the processor from one execution context to another. The kernel preserves required registers, stack pointer, program counter, and scheduling state; it selects and restores another context; it may change address-space translation.

Costs include:

- kernel entry and scheduler work;
- saving and restoring registers;
- disturbed caches, TLBs, and predictors;
- migration to another core;
- lost pipeline work;
- accounting and security mitigations.

Not every system call causes a process switch. The kernel can handle a quick request and return to the same thread. Not every thread switch changes address space: threads in one process share it. Timing depends on architecture, kernel, workload, and cache state.

### 2.13.7 Scheduling policy

A **scheduler** chooses runnable work for processors. Goals can include:

- interactive response;
- throughput;
- fairness;
- deadlines;
- energy efficiency;
- priority and isolation;
- processor affinity and cache locality.

These goals conflict. Giving an interactive task immediate service can delay batch throughput. Strict priority can starve lower-priority work. Moving tasks balances load but discards cache locality.

**Pre-emption** allows the system to suspend a running task without voluntary yield. A **time slice** is a policy interval of processor use before reconsideration, not necessarily a fixed universal quantum. Modern general-purpose schedulers use dynamic accounting rather than one simple round-robin queue.

Real-time scheduling distinguishes:

- **hard real time:** missing a deadline is unacceptable system failure;
- **soft real time:** misses degrade quality but can be tolerated;
- **best effort:** no bounded deadline guarantee.

Fast average execution does not establish a worst-case deadline.

### Worked example 2.13.2 — Round-robin schedule

Three runnable tasks arrive at time zero:

| Task | CPU work required |
|:---|---:|
| A | 5 ms |
| B | 3 ms |
| C | 7 ms |

With a 2-millisecond round-robin quantum and zero switching cost, execution slices are:

\[
A_2,B_2,C_2,A_2,B_1,C_2,A_1,C_2,C_1.
\]

B completes at 9 ms, A at 12 ms, and C at 15 ms. With a 0.2-ms cost per switch, completion times grow and the proportion spent switching increases as quantum shrinks. The example is a policy model; actual kernels account for blocking, priorities, multicore placement, and variable cost.

### 2.13.8 Processes and threads

A **thread** is an execution sequence with registers and stack scheduled within a process resource context. Threads in one process commonly share:

- virtual address mappings;
- global objects and heap;
- open-file table or references;
- process credentials;
- executable code.

Each thread has its own:

- program counter and registers;
- stack;
- scheduling state;
- thread-local storage;
- signal mask or equivalent details under platform rules.

Sharing makes communication inexpensive and races possible. A wild native pointer in one thread can corrupt the entire process. Separate processes strengthen address-space isolation but require explicit inter-process communication.

The Python thread object, kernel thread, and CPython interpreter execution permission are distinct. Conventional CPython’s GIL constrains simultaneous bytecode execution within an interpreter while threads still overlap I/O and native code can release the lock. Chapter 14 formalises this.

### 2.13.9 Process creation models

On POSIX-style systems, <code>fork</code> creates a child process initially resembling the caller. It receives a logically copied address space, commonly implemented through copy-on-write, and inherited open descriptors. Only the calling thread appears in the child after forking a multithreaded process, so locks held by vanished threads can remain in unusable states.

<code>exec</code> replaces the current process image with a new executable while retaining selected process identity and open descriptors according to flags. It does not create a process by itself. A shell commonly forks, then the child execs the requested program.

Windows and portable high-level APIs commonly create a new process and load a program in one operation. Python’s <code>subprocess</code> abstracts platform differences while preserving important handle, environment, quoting, and security choices.

### Worked example 2.13.3 — Open descriptor inheritance

A parent opens a log file and starts a child without closing or marking the descriptor non-inheritable under the platform rule. The child retains a reference. The parent closes its copy and attempts log rotation, but the open kernel object remains because the child still holds it.

This is not a filesystem leak caused by the pathname. It is reference lifetime across process creation. Close-on-exec/inheritance controls and explicit child-handle lists reduce accidental authority.

### 2.13.10 Process termination and zombies

Termination records an exit status and releases most process resources. A parent can wait to collect the status. On POSIX-style systems, a terminated child whose status has not been collected occupies a small **zombie** process record. It executes no instructions and holds no ordinary address space, but its process-table entry remains.

If the parent terminates, an ancestor service such as an init process adopts or reaps children under system rules. Long-running supervisors must collect child statuses.

Forced termination bypasses application cleanup. Temporary files, partial external effects, and leased work require recovery protocols. Operating-system reclamation closes process handles and memory, but cannot undo a completed bank transfer or repair a half-written application-level format.

### 2.13.11 Signals

A **signal** on POSIX-style systems is an asynchronous process/thread notification carrying a small kind identifier and limited information. Default actions include ignore, terminate, stop, or dump core. A process can install handlers for selected signals.

Signals coalesce or queue according to kind and implementation; they are not a general reliable message queue. Handler context interrupts ordinary execution. Only async-signal-safe operations are permitted in low-level native handlers. Python defers ordinary signal-handler execution to safe interpreter points in the main thread under CPython rules, which changes but does not erase timing constraints.

Common operational uses:

- request graceful termination;
- notify configuration reload;
- reap child status;
- stop/continue a process;
- report terminal interrupt.

An uncatchable forced-kill signal exists on POSIX systems so the kernel can terminate a process that refuses cooperation. It prevents cleanup by design.

### 2.13.12 Inter-process communication

**Inter-process communication**, or IPC, includes:

- anonymous and named pipes;
- local or network sockets;
- shared memory;
- message queues;
- signals;
- files and databases;
- platform-specific remote-procedure facilities.

Each mechanism chooses representation, message boundaries, buffering, identity, blocking, failure, and lifetime. Shared memory transfers no bytes after mapping but requires synchronisation and safe structure layout. A pipe supplies a byte stream and kernel buffering. A message queue preserves message units under size and delivery rules.

A **remote procedure call**, or RPC, makes communication resemble a function call. The resemblance is incomplete: a remote call can time out after the server acts, the network can partition, serialization can fail, and versions can differ. Callers need deadlines, idempotency, and protocol evolution.

### 2.13.13 User and group credentials

Operating systems associate processes with security credentials. POSIX-style credentials include real, effective, and saved user/group identifiers plus supplementary groups and capabilities on some systems. Windows uses access tokens containing user, group, privilege, and restriction information.

The effective identity commonly governs access checks. A set-user-ID executable historically changes effective identity under strict rules; it expands attack consequence and should minimise parsing and authority. Fine-grained capabilities can split root-like privileges, but granting one powerful capability still requires analysis.

The kernel checks credentials against object policy—mode bits, access-control lists, mandatory security labels, namespaces, or other mechanisms. Administrator authority can bypass many checks, so routine services should not run with it.

### 2.13.14 Namespaces and containers

An operating-system **namespace** supplies a process with a particular view of names such as process identifiers, mounts, hostnames, users, or network interfaces. Namespaces support containers but do not create a separate kernel.

A process can see itself as PID 1 inside a PID namespace while having another host PID. A mount namespace can give it a different root filesystem view. A user namespace can map internal identifiers to less privileged host identifiers.

Isolation composes namespaces with cgroups, permissions, capabilities, seccomp-like system-call filtering, and security modules. A privileged container or mounted host control socket can effectively grant host authority. Chapter 20 develops operational use.

### 2.13.15 Pages, frames, and translation

Virtual memory divides a process address space into fixed-size **virtual pages** and physical memory into equal-size **page frames** under a base page size. A page table maps virtual page numbers to physical frame numbers plus permissions and status.

If page size is \(2^{12}=4096\) bytes, the low 12 address bits are the offset within a page. The remaining high bits form the virtual page number. Translation replaces or transforms the page-number portion while preserving offset.

### Worked example 2.13.4 — Translate one address

Let a 16-bit virtual address use 4-KiB pages. Virtual address <code>0x3A7C</code> divides into:

- virtual page number: high hexadecimal digit 3;
- offset: low three digits <code>A7C</code>, because three hexadecimal digits contain 12 bits.

Suppose page-table entry 3 maps to physical frame <code>0x19</code>. The physical address is

<code>0x19A7C</code>.

Permissions can independently allow user read, write, and execute. A write to a read-only mapping faults even though translation exists.

### 2.13.16 Multi-level page tables

A flat table with an entry for every possible virtual page can be enormous even when most address ranges are unused. A **multi-level page table** divides virtual page-number bits into indexes. Upper entries allocate or point to lower tables only for populated regions.

For a conceptual 32-bit address, 4-KiB pages leave 20 page-number bits. Split into ten-bit level-one and ten-bit level-two indexes:

- level one has up to \(2^{10}=1024\) entries;
- each present entry points to one of up to 1024 level-two entries;
- each final entry maps a frame.

Walking the table can require several memory accesses. TLBs cache results. Page-table pages themselves occupy memory and must be protected from user modification.

Larger modern addresses use more levels. Huge pages map larger aligned regions with fewer TLB entries at the cost of internal waste and coarse allocation.

### 2.13.17 Demand paging

**Demand paging** creates a mapping or loads backing content only when a page is first accessed. An executable’s code and data can be mapped from its file without reading all bytes at startup. The first access faults; the kernel allocates a frame, reads or initialises content, updates the page table, and retries the instruction.

A **minor page fault** can be resolved without storage I/O, for example by mapping an already cached page or allocating zero-filled memory. A **major page fault** requires slower backing I/O under common terminology. Exact counters are platform-specific.

Demand paging reduces startup and physical use when mapped pages remain untouched. It introduces latency at first access and can produce fault storms. Real-time systems can prefault and lock selected memory where permissions allow.

### 2.13.18 Copy-on-write

**Copy-on-write**, or COW, initially shares one physical page between mappings while marking it non-writable. When a participant writes, the processor faults; the kernel allocates a private frame, copies content, updates that mapping writable, and retries.

Fork can therefore create a logical address-space copy without copying every page immediately. Pages remain shared until written. A child that immediately execs a new program avoids most copying.

COW cost depends on write pattern. A large parent followed by a child modifying every page eventually copies all. Native memory allocators and garbage collectors writing bookkeeping can break sharing even when application-level values appear unchanged.

File mappings can also be private COW or shared. A private mapping’s writes affect its private pages and not the underlying file under the mapping contract; a shared mapping can propagate changes.

### 2.13.19 Zero pages and lazy allocation

Operating systems can map a shared read-only **zero page** for newly requested anonymous memory. Reads return zeros. First write faults and allocates a private zero-initialised frame. This avoids allocating physical memory for untouched zero regions.

Requesting a large virtual region therefore need not immediately consume equal physical memory. Some systems overcommit promises beyond physical plus backing capacity, expecting not all pages to be used. Later allocation can fail or trigger process termination when commitments are realised.

Memory accounting must distinguish:

- virtual address size;
- resident physical pages;
- private versus shared pages;
- file-backed versus anonymous;
- allocator-reserved but reusable memory;
- swapped or compressed pages.

One “memory usage” number cannot express all.

### 2.13.20 Page replacement and thrashing

When physical frames are scarce, the kernel can evict clean file-backed pages and reload them later, write dirty pages to backing storage, compress memory, or terminate processes under policy. A **page-replacement algorithm** chooses candidates using recency, activity, priority, and cost approximations.

True least-recently-used replacement would require expensive exact ordering. Kernels approximate through access bits, lists, generations, or sampling.

**Thrashing** occurs when active working sets exceed available memory and execution spends much of its time moving pages rather than performing useful computation. CPU utilisation can fall while storage activity rises. Adding more runnable processes can worsen throughput.

A **working set** is the set of pages actively needed over a chosen interval. It changes over time. Capacity planning requires peak concurrent working sets plus kernel and cache needs.

### 2.13.21 Memory-mapped files

A **memory mapping** associates a file region or anonymous object with virtual addresses. Loads and stores then trigger page-cache and filesystem mechanisms. Benefits include:

- demand loading;
- shared pages across processes;
- random access without explicit seek/read at each step;
- kernel-managed caching.

Risks include:

- faults at arbitrary instructions;
- file truncation causing access errors;
- durability separate from memory visibility;
- alignment and offset constraints;
- concurrent update protocols;
- address-space consumption;
- inability to report every I/O error at a convenient call.

Mapping a file does not make its on-disk format equal to native object memory. Endianness, alignment, pointer values, versioning, and crash consistency remain.

### 2.13.22 Stack and heap at the process level

A process address space commonly contains mapped executable code, read-only data, writable data, dynamic libraries, heap-like allocator regions, thread stacks, shared mappings, and kernel-reserved areas. Exact placement varies and is randomised.

The **heap** in operating-system discussion is not necessarily one contiguous structure. Language allocators request virtual memory through system interfaces and subdivide it. Freed Python objects can return storage to an allocator pool without returning pages to the kernel.

Each thread stack has a reservation, committed pages, and guard region under platform rules. Recursive growth can encounter the guard. Python frames are implementation objects and native stack use; they are not identical to one contiguous stack of source-level variables.

### 2.13.23 Directory entries and file identities

A directory maps a component name to an underlying filesystem object identifier. On Unix-like filesystems, an **inode** is a persistent metadata object containing type, permissions, ownership, timestamps, link count, and data-block mapping, but not usually the filename. Directory entries associate names with inode numbers.

A **hard link** is an additional directory entry naming the same file object. Both names have equal status. Removing one decrements link count; content persists while another link or open reference remains.

A **symbolic link** is a separate filesystem object containing a path-like target. Resolution follows that target, which can be relative to the link’s containing directory. It can dangle and can cross filesystems.

On other systems, equivalent concepts and terminology differ. Python <code>pathlib</code> abstracts many path operations but cannot erase semantic differences.

### Worked example 2.13.5 — Links and open lifetime

Directory contains:

\[
\text{alpha}\rightarrow F,\qquad
\text{beta}\rightarrow F.
\]

A process opens alpha and receives handle H. Then both alpha and beta entries are removed.

- New path resolution finds neither name.
- Link count becomes zero.
- H still refers to F, so content remains allocated.
- When H and every other open reference close, filesystem can reclaim F.

This permits safe temporary files created then unlinked while open on supporting systems. Windows sharing and deletion semantics differ.

### 2.13.24 Path resolution

Path resolution starts at a root or current directory and processes components. For each component the kernel:

1. checks that the current object is a directory;
2. checks search/traversal permission;
3. finds the named entry;
4. follows a symbolic link under limits and flags;
5. handles <code>.</code>, parent components, mount points, and namespace rules;
6. arrives at or creates the final component under operation-specific policy.

Read permission on a directory governs listing names under one common model; execute/search permission governs traversal. A process can access a known filename without listing the directory if permissions allow, or list names without opening their files.

Race-free high-assurance operations use directory handles and relative open calls rather than validating a pathname and resolving it again. The name-to-object mapping can change between check and use.

### 2.13.25 Mounts

A **mount** attaches a filesystem or filesystem view at a directory in one namespace. After mounting, path traversal through that point enters the mounted root; the covered directory’s prior contents remain present but hidden from that namespace until unmounted.

Filesystems can represent:

- local storage;
- memory;
- remote network service;
- pseudo-files exposing kernel information;
- union/overlay layers;
- encrypted views.

The file interface therefore does not imply a rotating disk. Network filesystems have caching, identity, failure, and consistency semantics unlike local storage. A path operation can block on a network.

### 2.13.26 Open-file descriptions and offsets

On POSIX-style systems, a file descriptor refers through a process table to an **open-file description** containing current offset and status flags, which refers to a filesystem object. Duplicated descriptors can share one description and therefore one offset.

After fork, parent and child descriptors can refer to the same open description. Concurrent reads then advance a shared offset under kernel rules. Opening the same path separately creates separate descriptions and offsets.

An append flag asks the kernel to place each write at the current end atomically relative to supported concurrent writes. Seeking to end and then writing in two calls races with another writer.

### 2.13.27 Buffering and the page cache

Data can reside in:

- application objects;
- language I/O buffers;
- C library buffers;
- kernel page cache;
- filesystem journal or log;
- device-controller cache;
- storage medium.

A successful buffered Python <code>write</code> can mean characters entered a user-space buffer. <code>flush</code> sends them toward the operating system. A successful kernel write can mean bytes entered kernel cache. <code>fsync</code> or platform equivalents request persistence according to filesystem/device guarantees. Each boundary has distinct errors.

Read caching means later reads can avoid device access. The page cache unifies explicit reads and memory mappings on many systems. Memory reported as cache can be reclaimable and useful, not “wasted.”

### 2.13.28 Atomicity and durability

**Atomicity** concerns whether observers see an operation as indivisible. **Durability** concerns survival after specified failures. They are independent.

Renaming a file within one filesystem can be atomic for namespace observers: they see old name mapping or new mapping, not a half name. If newly written file data or directory metadata have not reached durable media, power failure can still lose the update.

A robust replace protocol can:

1. write a temporary file in the target directory;
2. flush language buffers;
3. request file durability;
4. atomically rename over the destination;
5. request directory-metadata durability.

Exact guarantees and required calls vary by filesystem, mount options, operating system, device cache, and failure model. An application must name whether it protects against process crash, kernel crash, power loss, or device failure.

### 2.13.29 Journaling and copy-on-write filesystems

A **journaling filesystem** records selected updates in a log before applying them to main structures. After interruption, recovery replays committed journal records or discards incomplete transactions, restoring structural consistency. Data journaling, ordered-data modes, and metadata-only journaling provide different content guarantees.

A **copy-on-write filesystem** writes modified blocks to new locations and atomically advances roots or metadata references, enabling snapshots and checksums. It still needs ordering, allocation, garbage collection, and failure recovery.

Filesystem atomic transactions usually do not group arbitrary application changes across several files into one semantic commit. Databases build higher-level logging, locking, and recovery protocols for that purpose.

### 2.13.30 File locking

File locks can be **advisory**, requiring cooperating processes to request and honour them, or **mandatory** under limited platform configurations. Locks can apply to whole files or byte ranges and can be associated with processes, descriptors, or open descriptions.

Closing descriptors, forking, duplicating, and accessing through another path can have surprising effects depending on lock type. Network filesystems add server leases and partition failure. A lock does not validate file content or make multi-file operations transactional.

Atomic creation with exclusive flags is often simpler for one-owner claims. A lock file protocol must handle stale owners, identifier reuse, clocks, and crash recovery; the existence of a file alone does not prove a live lock holder.

### 2.13.31 Device drivers

A **device driver** translates operating-system operations into device-specific protocol while handling interrupts, DMA, errors, power, and concurrency. It runs with substantial authority, commonly in the kernel, though user-space drivers exist.

A block-storage driver exposes addressed blocks and queues; a filesystem builds names and files above it. A network driver exposes packets; sockets and transport protocols build streams or datagrams. A graphics driver manages command submission, memory mappings, scheduling, and display.

Drivers validate requests from user space and devices. A device can DMA malformed data or report impossible lengths because of defect or attack. Kernel-resident driver errors can compromise the whole system, motivating small interfaces, isolation, memory-safe implementations, and input validation.

### 2.13.32 Bootstrapping an operating system

At power-on or reset, the processor begins at an architecture-defined state and address. Firmware initialises enough hardware to locate a boot target. A bootloader loads an operating-system kernel and configuration into memory and transfers control.

The kernel then:

1. establishes early memory mappings;
2. discovers processors and devices;
3. initialises allocators, interrupt controllers, timers, and schedulers;
4. loads or mounts a root filesystem;
5. starts the first user-space process or service manager;
6. user-space services initialise devices, networking, login, and applications.

Each step depends on a smaller earlier environment. This is **bootstrapping**: constructing a richer system using a constrained initial mechanism. Secure boot adds a chain of signature verification from firmware trust anchors to later components. It establishes approved origin under key policy, not absence of defects.
