# 2.8 Just-in-time compilation

**Just-in-time compilation** (**JIT compilation**) translates code during execution, often after observing which paths and types are common. A **hot path** is a region executed frequently enough to justify additional optimisation effort. A JIT may initially interpret code, collect execution information, compile specialised native code for hot paths, and return to a more general mode if an assumption ceases to hold.

**Specialisation** creates code optimised for established conditions. Suppose a dynamic-language addition site repeatedly receives two machine-sized integers. A JIT can generate a fast path that checks those conditions and performs direct integer addition. If a later call supplies a different kind of value, a **guard** fails. The runtime may choose a general operation or **deoptimise**, reconstructing a less specialised execution state.

### Worked example 2.7 — Why a JIT needs guards

Consider the source-level operation `a + b`. The language may permit integers, floating-point numbers, text-like values, or user-defined objects with custom addition behaviour. A compiled integer addition is correct only under the assumption that both operands currently have the required integer representation and that overflow or other language conditions are handled correctly.

A specialised path therefore has the logical form:

```text
if operands satisfy assumptions:
    use specialised integer operation
else:
    use the general language operation
```

The guard is part of correctness, not incidental overhead. Without it, a performance assumption would silently redefine the program’s semantics.

JIT systems trade startup time and memory for possible later speed. A short-lived command may finish before compilation cost is repaid. A long-running service with stable hot paths may benefit. Assertions about JIT performance must therefore name workload, warm-up, runtime, inputs, and measurement method.

> **Common misconception — “Compiled means fast; interpreted means slow.”**  
> Translation strategy is only one variable. Algorithmic complexity, data layout, runtime specialisation, library implementation, I/O, caching, processor behaviour, and workload shape can dominate. “Compiled” also fails to state target, timing, or optimisation quality.

### 2.8.1 A translation pipeline is a sequence of proof obligations

Each translation stage changes representation while preserving specified meaning. Let source program \(S\) denote behaviour under source-language rules, and generated program \(T\) denote behaviour under target rules. Compiler correctness asks, under stated assumptions, that observable permitted behaviour of \(T\) correspond to that of \(S\).

The statement is not simply “outputs match.” Programs can:

- terminate or run indefinitely;
- read input and write output;
- mutate persistent state;
- raise or signal faults;
- interact concurrently;
- depend on undefined or implementation-defined behaviour;
- expose time and resource consumption where those are observable.

A compiler can exploit source-language undefined behaviour because the specification imposes no required outcome for the invalid program. Python defines many operations more completely than C but still leaves implementation and environment freedoms. An optimiser must know which effects Python exposes.

Compilation errors are classified by stage:

- invalid character or unterminated literal: lexical;
- token sequence violates grammar: syntactic;
- unresolved declaration or invalid type relation in a statically checked language: semantic;
- unrepresentable target relocation: linking;
- missing dynamic library: loading;
- input-dependent division by zero: runtime.

These categories aid diagnosis but can overlap in implementation.

### 2.8.2 Tokens and lexemes

A **lexeme** is the concrete character sequence matched as one token occurrence. A **token** is its grammatical category and associated value. In

<code>total = price + 20</code>

the lexemes are <code>total</code>, <code>=</code>, <code>price</code>, <code>+</code>, and <code>20</code>, ignoring spacing under the language’s rules. Categories can be identifier, assignment delimiter, identifier, addition operator, and integer literal.

Lexical rules resolve boundaries. Does <code>12.5</code> form one floating literal or three tokens? Does <code>elsewhere</code> begin with keyword <code>else</code>, or is it one identifier? A maximal-munch rule commonly chooses the longest token permitted at a position, subject to exceptions.

Comments and whitespace can be discarded, retained for diagnostics, or participate in grammar. Python indentation produces structural tokens; C-like languages use braces and treat much whitespace as separation. A tokenizer therefore implements language-specific representation, not a universal word splitter.

Source encodings convert file bytes to characters before or during lexical analysis. Invalid encoding, newline conventions, Unicode identifiers, and visually confusable characters belong to the source boundary.

### Worked example 2.8.1 — Token boundary changes meaning

Compare:

1. <code>value - -1</code>
2. <code>value -- 1</code>

In Python, the first tokenises as identifier, subtraction, unary minus, integer literal and is valid. The second tokenises as identifier, subtraction, unary minus, integer literal as well because Python has no decrement token; spacing does not create <code>--</code> as one operator. In a language defining <code>--</code>, maximal matching can produce a decrement token and another meaning.

The characters alone do not determine tokens without a lexical specification.

### 2.8.3 Grammars and parse trees

A **grammar** is a formal set of rules defining which token sequences have syntactic structure. A **nonterminal** names a syntactic category; a **terminal** is a token used directly. A production

\[
\textit{sum}\rightarrow
\textit{sum}\ +\ \textit{product}
\mid
\textit{product}
\]

states that a sum can consist of a sum, plus token, and product, or simply a product. The vertical bar means alternative.

A **parse tree** records every grammatical derivation. An abstract syntax tree omits punctuation and intermediate nodes unnecessary for later meaning. For <code>2 + 3 * 4</code>, precedence rules form addition whose right child is multiplication, producing \(2+(3\times4)\), not \((2+3)\times4\).

An **ambiguous grammar** permits more than one parse tree for the same token sequence. Language grammar or disambiguation rules must choose. Operator precedence and associativity are grammar properties, not beliefs held by the arithmetic unit.

Parser strategies include recursive descent, precedence climbing, LR families, and parser combinators. Selection affects implementation and diagnostics, not accepted language when correctly implemented.

### 2.8.4 Semantic analysis

Parsing establishes syntactic shape, not complete validity. **Semantic analysis** checks contextual rules and annotates structure. Possible tasks include:

- name binding and scope;
- type checking or inference;
- declaration-before-use rules;
- access control;
- control-flow validity;
- constant-expression requirements;
- function call arity;
- pattern exhaustiveness.

In Python, many type and attribute questions remain dynamic, but the compiler still classifies name scopes, rejects <code>return</code> outside a function, and establishes closure information. Chapter 15 inspects those exact CPython structures.

A **symbol table** records information associated with declared or bound names. The “symbol” is compiler metadata, distinct from a runtime object. One source name can correspond to different bindings in nested scopes; source position and scope identify it.

### 2.8.5 Intermediate representations

An **intermediate representation**, or IR, expresses program operations in a form suited to analysis and transformation. Compilers commonly use several:

- syntax tree retaining high-level constructs;
- control-flow graph of basic blocks;
- three-address instructions with simple operands;
- static single assignment form;
- machine-independent lower-level operations;
- target-specific instructions before final encoding.

A **basic block** is a maximal straight-line instruction sequence entered at its beginning and exited at its end without internal branches. A **control-flow graph** has basic blocks as vertices and possible transfers as directed edges.

**Static single assignment**, or SSA, gives each represented variable version one definition. When control paths merge, a conceptual phi operation selects the version corresponding to the incoming path.

Source:

~~~text
if condition:
    x = 10
else:
    x = 20
print(x)
~~~

SSA-like form:

~~~text
if condition goto then else goto otherwise
then:      x1 = 10; goto merge
otherwise: x2 = 20; goto merge
merge:     x3 = phi(x1, x2); print x3
~~~

SSA makes definition-use relationships explicit, supporting constant propagation, dead-code analysis, and register allocation. The phi is an IR device, not necessarily a machine instruction.

### 2.8.6 Optimisation and observability

**Constant folding** evaluates an expression at translation time when its value and effects are established. **Constant propagation** substitutes known values through uses. **Dead-code elimination** removes computations proven unable to affect required behaviour. **Common-subexpression elimination** reuses an earlier result when operands and relevant state are unchanged.

Every transformation has a precondition. Replacing two calls <code>f(x) + f(x)</code> with one doubled result is invalid if <code>f</code> has side effects, reads changing state, can raise on a different call, or returns a fresh object whose identity is observed.

Loop transformations—unrolling, vectorisation, invariant-code motion—change operation order and timing. Floating-point results can change because addition is not associative. Languages and compiler flags define which reorderings are permitted.

An optimiser can remove an apparently unused memory write in ordinary code. A write to a device register, shared atomic, or volatile-qualified object under another language’s rules can be observable and must be preserved accordingly.

### Worked example 2.8.2 — Dead under one contract, live under another

~~~text
x = expensive()
x = 5
use(x)
~~~

If <code>expensive()</code> is pure, guaranteed terminating, and its result unused, the first assignment can be removed. If it writes a log, consumes input, raises an exception, acquires a lock, or fails to terminate, removal changes observable behaviour. “The value is overwritten” proves only that the produced value is dead, not that the computation is effect-free.

### 2.8.7 Assembly is not a portable universal language

Assembly syntax is defined by an assembler and target ecosystem. The same ISA can have several syntaxes. x86 operands can be written source-first or destination-first by different conventions. Register prefixes, immediate markers, instruction suffixes, directives, and comment symbols vary.

An **assembler directive** instructs the assembler rather than the CPU. Directives select sections, align data, define symbols, reserve storage, or emit constants. They do not necessarily produce an instruction.

A **label** binds a symbolic name to a location or value during assembly. A forward branch can name a label whose address is not yet known. A two-pass assembler can first determine locations and symbols, then encode instructions and references. Modern assemblers use richer internal passes but the principle remains.

### 2.8.8 Sections, symbols, and object files

A translated unit is commonly stored as an **object file** containing:

- machine-code sections;
- read-only constants;
- initialised writable data;
- description of zero-initialised storage;
- symbol definitions and references;
- relocations;
- debugging and exception metadata;
- platform-specific headers.

A **section** groups bytes with related purpose and permissions. A **symbol** associates a name with a defined or required entity such as function or object. A symbol table can distinguish local and externally visible names, binding strength, type, and section.

Zero-initialised global storage need not occupy an equal run of zero bytes in the file. The object records required size; the loader arranges zeroed memory. Persistent representation and runtime memory layout are different.

ELF, PE/COFF, and Mach-O are major executable/object families on different platforms. Their exact headers, relocations, symbol rules, and dynamic-loading mechanisms differ.

### 2.8.9 Relocation

A **relocation** is a request to adjust encoded data when final addresses or offsets become known. Suppose an instruction must call function <code>render</code>, but its final address depends on where object files and libraries are placed. The assembler emits a placeholder and relocation describing:

- location to patch;
- referenced symbol;
- relocation kind;
- addend or related arithmetic.

The linker assigns sections and symbols, computes the required value, checks representable range, and patches the field. Position-relative calls encode target minus next-instruction address; absolute references encode an address or address-derived value.

Position-independent code computes through relative addressing or tables so it can be loaded at different addresses with fewer runtime modifications. This supports shared libraries and address-space randomisation.

### Worked example 2.8.3 — Relative branch relocation

A branch instruction at final address 100 encodes a displacement relative to the next instruction at 104. Target symbol resolves to 140. The displacement is

\[
140-104=36.
\]

If the field is a signed eight-bit byte displacement, 36 fits. If target resolves to 500, displacement 396 does not fit and the linker must reject, relax to a larger instruction when supported, or use a trampoline.

### 2.8.10 Static and dynamic linking

**Static linking** copies or incorporates required library code into an executable artifact under the platform model. Benefits include self-contained deployment and fixed library selection; costs can include larger files, duplicated code in memory/storage, and rebuild requirements for library fixes.

**Dynamic linking** resolves references to shared libraries at load time or during execution. Several processes can map shared read-only code pages. Libraries can be updated independently, but binary compatibility and dependency resolution become runtime concerns.

A **soname** or platform-equivalent identity expresses an ABI compatibility family. Semantic package version and shared-library ABI version solve related but different problems. Replacing a library file without compatible symbol versions, calling conventions, structures, and semantics can break a program even when function names remain.

**Lazy binding** can postpone resolution of a dynamic function until first call. It reduces startup work but moves a possible failure or attack surface into execution. Immediate binding detects missing symbols earlier and can support stronger relocation protection.

### 2.8.11 Application binary interfaces

An **application binary interface**, or ABI, defines binary-level agreements among separately compiled code and the operating environment:

- instruction set and extensions;
- register use;
- stack alignment and frame conventions;
- argument and return placement;
- which registers a caller or callee preserves;
- data type sizes and alignments;
- object-file and dynamic-link formats;
- system-call convention;
- exception and name-mangling rules.

A source-level function

~~~text
long add(long left, long right)
~~~

does not state whether arguments arrive in registers or on a stack, how wide <code>long</code> is, or where the return appears. The ABI answers for one platform.

An ABI can preserve binary compatibility across source/compiler versions. Changing field order in a public C structure can break compiled clients even if source recompiles. Python wheels containing native extensions use platform and ABI compatibility tags because pure Python portability does not make embedded machine code portable.

### 2.8.12 Calling conventions and stack frames

A **calling convention** is the ABI subset governing function calls. A caller places arguments, a return address, and possibly stack space according to the convention; control transfers; a callee preserves required registers and returns a result.

A native **stack frame** can contain saved registers, local storage, outgoing arguments, alignment, and bookkeeping. Optimisation can omit or rearrange a conventional frame, keep locals in registers, inline the call, or eliminate it. Debuggers reconstruct calls using symbols and unwind metadata; a simple linked list of frames is not guaranteed.

A stack grows within mapped memory and has finite capacity. Deep recursion or large local allocations can cross a guard page and fault. Stack overflow at native level can corrupt memory in unsafe environments or be caught by runtime protections; Python recursion adds interpreter-managed frames and enforces a recursion limit partly to protect native resources.

### 2.8.13 Loading an executable

To start an executable, operating-system machinery commonly:

1. resolves and opens the executable under permissions;
2. validates its format and target architecture;
3. creates a process/address-space context;
4. maps executable sections with permissions;
5. maps a stack and initial process data;
6. arranges arguments, environment, and auxiliary information;
7. maps or invokes the dynamic loader when required;
8. resolves libraries and relocations;
9. initialises runtime facilities;
10. transfers control to an entry point.

The source-language <code>main</code> function may not be the executable entry point. Runtime startup code initialises libraries, constructors, thread state, and arguments before calling it; after return it performs termination procedures.

Address-space layout randomisation varies mapping locations to impede attacks relying on known addresses. Position-independent executables support this. Randomisation is defence in depth, not memory safety.

### 2.8.14 Runtime systems

A **runtime system** supplies services required by compiled or interpreted language semantics: memory allocation, object representation, garbage collection, exception propagation, dynamic dispatch, thread coordination, module loading, and I/O adapters.

Ahead-of-time native compilation does not eliminate runtime behaviour. A C executable links startup and standard libraries. A Go executable includes scheduler and garbage collector. A Java runtime loads bytecode and manages a virtual machine. CPython itself is the runtime implementing Python.

The boundary between compiler and runtime is an engineering choice. Bounds checks can be emitted inline or call a helper. Generic functions can be specialised at compilation or use runtime dictionaries. Exceptions can use tables, setjmp-like mechanisms, or explicit result values while preserving source semantics.

### 2.8.15 Dynamic loading and plugins

A process can load a library during execution and resolve named symbols. Plugin systems use this to extend behaviour without relinking the host. The host and plugin need an ABI or higher-level protocol plus version negotiation, ownership rules, threading expectations, and failure isolation.

Loading native code grants it the process’s memory and authority. A plugin is not data. Signature verification can establish an approved publisher and bytes but cannot sandbox behaviour. Run untrusted extensions in a separate restricted process and communicate through a narrow protocol.

Python imports are a higher-level dynamic loading system. Importing a module executes its top-level code. Native extension modules additionally cross the ABI and C API boundary described in Chapters 10 and 15.
