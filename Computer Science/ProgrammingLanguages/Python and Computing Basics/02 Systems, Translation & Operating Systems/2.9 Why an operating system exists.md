# 2.9 Why an operating system exists

A bare machine presents processors, addressable memory, interrupts, timers, and device interfaces. Allowing every application unrestricted access creates immediate conflicts. Two programs may choose the same memory. One may overwrite another’s instructions. Several may attempt to control one storage device concurrently. A defective or hostile program may read private data or refuse to release the processor.

An **operating system** (**OS**) is system software that manages hardware resources, establishes protected execution environments, and supplies common abstractions and services to programs. Its purposes can be grouped as:

- **Abstraction:** present interfaces such as processes, files, sockets, and virtual memory instead of raw device protocols.
- **Multiplexing:** share finite resources among competing activities across time or space.
- **Protection:** restrict what one execution context may read, modify, or control.
- **Coordination:** impose protocols for concurrent access, completion, failure, and accounting.
- **Persistence:** organise durable data and mediate storage devices.

The **kernel** is the privileged core of an operating system. It executes with hardware authority unavailable to ordinary application code and controls mechanisms such as scheduling, virtual-memory mappings, interrupt handling, and device access. **User space** is the less privileged execution domain in which ordinary applications and many system services run. The boundary is enforced by processor privilege mechanisms and memory protection, not by a convention that applications politely observe.

A **system call** is a controlled request from a user-space program for a kernel service. The request crosses the privilege boundary through an architecture-defined mechanism. The kernel validates arguments and authority, performs or initiates the operation, and returns a result or failure indication. Library functions may wrap system calls, but not every library call enters the kernel: many operate entirely on user-space data.

### Worked example 2.8 — Why a file read crosses layers

An application requests 100 bytes from an already opened file.

1. Application code calls a language or runtime I/O function.
2. Buffered runtime code may satisfy the request from data already held in user space. If so, no new system call is necessary.
3. Otherwise, the runtime requests a kernel read through a system-call interface.
4. The kernel validates the file descriptor, permissions, memory destination, and current file state.
5. Filesystem code identifies the required stored region.
6. If the data is already in a kernel cache, it can be copied or mapped from memory. Otherwise a device operation is initiated and the requesting thread may wait.
7. A storage controller may transfer data using DMA and later signal completion through an interrupt.
8. The kernel reports the number of bytes actually made available or a failure.
9. Runtime buffering and decoding may transform bytes before the application receives a result.

The high-level request remains simple because every layer publishes a narrower contract. It would be inaccurate to say that the Python function “talks directly to the disk”, that every read reaches physical hardware, or that requesting 100 bytes guarantees receipt of exactly 100 in every I/O interface.
