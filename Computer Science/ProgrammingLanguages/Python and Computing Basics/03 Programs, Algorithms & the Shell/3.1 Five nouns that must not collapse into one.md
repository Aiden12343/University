# 3.1 Five nouns that must not collapse into one

Programming discussions often use *problem*, *specification*, *algorithm*, *program*, and *execution* as if they named the same thing. They do not.

A **computational problem** is a family of questions described by admissible inputs and required answers. A **problem instance** is one particular admissible input. A **specification** states the relationship that required outputs and effects must bear to admissible inputs and relevant initial state. An **algorithm** is a finite, unambiguous general method intended to satisfy that specification. A **program** is an expression of one or more algorithms and associated data in a form that a computational system can process. An **execution** is one concrete history produced when a program runs under particular inputs, state, implementation, and environment.

For the problem “find a maximum element of a non-empty finite sequence of comparable numbers”:

- `[8, 3, 11, 5]` is an instance;
- “return an element from the input that is no smaller than every input element” is a specification;
- “retain the greatest element seen while scanning once from left to right” is an algorithm;
- source code expressing the scan is a program component;
- the particular sequence of retained values 8, 8, 11, 11 is part of one execution trace.

One successful execution does not establish algorithmic correctness. It shows that one program, run once under one set of conditions, produced one observation. Nor does a correct algorithm establish that the specification captures the user’s real need. A perfectly implemented maximum finder is wrong for a user who needed the second-largest distinct value. Correctness is always correctness *with respect to a specification*.

### Worked example 3.1 — Make a vague request testable

The request “sort these records properly” is not a specification. It omits the ordering key, direction, treatment of equal keys, admitted record structure, and response to malformed data. A stronger contract might be:

> Input is a finite sequence of records, each containing a text surname, text given name, and integer identifier. Return a new sequence containing the same records ordered first by case-folded surname, then by case-folded given name, then by ascending identifier. Preserve input order among records whose three keys compare equal. Reject a record missing any required field without returning a partial result. Do not modify the input sequence or its records.

This statement supplies:

- the input domain;
- the output relationship;
- a stability requirement for ties;
- invalid-input behaviour;
- a mutation constraint.

It still depends on a later definition of Unicode case folding and a precise record representation. Those dependencies would be named at the interface where the specification becomes executable. Precision does not mean forcing every fact into one sentence; it means exposing every assumption at an owned boundary.

> **Common misconception — “The code is the specification.”**  
> Code states what one program does under its language and environment. A specification states what it is required to do and can therefore judge alternative programs, including a defective current one.
