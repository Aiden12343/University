# 3.10 Standard streams, redirection, and pipelines

A newly launched command-line process conventionally receives three standard streams:

- **standard input** (`stdin`) supplies ordinary input;
- **standard output** (`stdout`) carries normal produced data;
- **standard error** (`stderr`) carries diagnostics.

A **stream** is an ordered flow of data available over time. A stream does not necessarily provide all content in one operation and does not imply persistent storage. At the OS boundary these streams are byte-oriented; language runtimes may add text encoding and buffering.

Separating normal output from diagnostics permits composition. A shell can redirect stdout to a file while leaving errors visible. A **pipeline** connects one process’s stdout to another process’s stdin. The first program need not know whether a human, file, or later process receives its output.

POSIX-shell examples, explicitly scoped to that shell family:

```sh
python3 report.py > report.txt
python3 report.py 2> errors.txt
python3 produce.py | python3 consume.py
```

The first redirects stdout, the second redirects stderr, and the third forms a pipeline. PowerShell also supports pipelines and redirection but transports richer objects in some intra-PowerShell contexts and has version-specific stream semantics; commands must not be copied between shells under an assumption of identical grammar.

### Worked example 3.9 — Why diagnostics do not belong on stdout

Suppose `produce.py` is specified to write one integer per line to stdout. `sum.py` reads integers from stdin. If `produce.py` writes `warning: skipped malformed row` to stdout, the downstream parser receives text outside the data contract and may fail or, worse, mis-handle it. Writing the warning to stderr preserves stdout as the promised data channel.

This is an interface theorem: composability requires each channel to retain one stated role. A message being useful to a human does not license placing it in the data stream.
