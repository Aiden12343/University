# 3.11 Exit status and completion contracts

When a process terminates, it supplies an **exit status**, a small integer interpreted by the parent environment. By widespread convention, zero denotes successful completion and non-zero denotes some form of failure. The precise meanings of non-zero values belong to the program and platform contract.

Exit status is not the same as printed output. A program may print an error yet mistakenly return zero; automation can then treat failure as success. It may return non-zero without printing a useful diagnostic. A robust command-line interface aligns three elements:

1. stdout contains only promised normal results;
2. stderr contains actionable diagnostics;
3. exit status truthfully classifies completion.

Shells can use the status to decide subsequent control flow. A build system, continuous-integration service, or wrapper script cannot reliably infer success by reading arbitrary prose. Machine-readable status is therefore part of the interface.

### Worked example 3.10 — Specify a text-counting command

Command shape:

```text
textcount INPUT_PATH
```

Contract:

- exactly one path argument is required;
- on success, stdout contains `LINES=<n>` followed by a newline;
- ordinary diagnostics never appear on stdout;
- missing input, inaccessible file, or invalid text produces a concise stderr message and non-zero status;
- zero status means the complete result was emitted;
- partial output is not emitted before input validation completes.

This contract makes the program usable by both people and other programs. A test can separately capture output, error, and status rather than search one merged transcript.
