# 3.12 The shell is a programming language

A shell offers variables, expansions, conditional execution, repetition, functions, pipelines, and process coordination. It is therefore a programming language, not merely a launcher. Its special strength is composing external commands and streams; its special risks include complex quoting, implicit string conversion, platform differences, and unintended interpretation of untrusted text.

Never construct a shell command by concatenating untrusted input and then asking a shell to interpret the result. The shell grammar may transform data into operators, substitutions, redirections, or additional commands. Prefer process-launch interfaces that pass an explicit argument sequence without a shell when shell syntax is not required. This security rule will be derived in depth in the cybersecurity branch.

### Worked example 3.11 — Data is not source

Suppose a program needs to invoke a converter with an input filename. The conceptual interface should be:

```text
program = "converter"
arguments = ["--input", user_supplied_path]
```

The launch mechanism receives the program and argument boundaries separately. By contrast, concatenating `"converter --input " + user_supplied_path` and asking a shell to parse it turns the supplied characters into shell source. Quoting attempts are shell-specific and easy to make incomplete. The safe abstraction preserves the distinction between syntax owned by the application and data owned by the user.

### 3.12.1 Terminal, console, shell, and command are four entities

A **console** historically denotes a privileged physical or logical terminal associated with system control. A terminal emulator is an application implementing a text terminal protocol inside a graphical or remote environment. A **pseudo-terminal** is a paired operating-system device: one end behaves like a terminal for a child process, while a controller such as a terminal emulator or remote-login server uses the other.

The shell reads bytes or characters through the terminal interface, parses its own language, and starts commands. A command may itself be:

- a shell syntax form;
- a shell built-in executed inside the current shell;
- a shell function;
- an alias expanded during parsing;
- an external executable run in another process.

Changing directory is commonly a built-in because an external child cannot change its parent shell’s current directory. The child could change its own directory and terminate; the shell would remain where it was.

### 3.12.2 Terminal line discipline

In canonical terminal mode, a kernel **line discipline** can process editing characters and deliver input after a line terminator. It can interpret interrupt and end-of-file control characters. In raw mode, applications receive input with less preprocessing and implement interactive editing themselves.

Terminal output contains characters and control sequences. ANSI/ECMA-48-derived escape sequences can move a cursor, select colours, or clear regions. Display width is not equal to Unicode code-point count: combining marks, wide characters, emoji sequences, and tabs complicate columns.

Programs should detect or be told when output is a terminal before emitting interactive formatting. Redirected output is data for another consumer; colour-control bytes can corrupt it. Accessibility and non-colour indicators remain necessary.

### 3.12.3 Shell parsing is staged

A POSIX-like shell performs several conceptual transformations, with exact order defined by its specification:

1. read input and recognise operators/words;
2. parse shell grammar;
3. perform expansions such as parameter, command, arithmetic, and pathname expansion;
4. remove quote syntax;
5. apply redirections;
6. resolve and execute commands.

This is a conceptual model; aliases and here-documents have special timing. The important fact is that a visually typed line is not passed unchanged to a program.

**Quoting** marks characters so selected shell interpretation is suppressed. In common POSIX shells:

- single quotes preserve enclosed characters literally, with no single quote inside that quoted region;
- double quotes preserve spaces while still permitting selected parameter and command expansion;
- backslash quotes one following character under context rules.

These rules are not PowerShell rules and not Windows process command-line rules.

### Worked example 3.12.1 — One visible line, three arguments

~~~sh
tool "North report.txt" '$HOME' "$HOME"
~~~

Under a typical POSIX shell:

1. command name is <code>tool</code>;
2. first argument is <code>North report.txt</code>;
3. second is literal <code>$HOME</code>;
4. third is the value of shell parameter <code>HOME</code>.

Quote characters themselves are removed. If the home value contains spaces, double quotes keep it one argument. Leaving it unquoted can trigger field splitting and pathname expansion.

### 3.12.4 Arguments are a sequence, not one universal string

At a POSIX program boundary, an argument vector is conventionally a sequence of null-terminated byte strings plus a count. An argument cannot contain a null byte. The program receives boundaries already determined by the shell or process launcher.

On Windows, the low-level process-creation interface supplies a command-line string; each runtime applies a parsing convention to construct language-level arguments. Quoting rules can differ among target runtimes. Python’s process library implements conventions for argument sequences on supported platforms, but exact child parsing belongs to the child executable.

This explains why printing an argument list and copying its visual representation is unreliable. A string representation with brackets and quotes is data describing arguments, not the argument vector itself.

### 3.12.5 Parameter expansion and absent values

A shell parameter maps a name to string-like state under shell rules. Expansion substitutes its value. An unset parameter and a parameter set to an empty string can be distinct.

~~~sh
name="May results"
tool --name "$name"
~~~

Quoting the expansion preserves it as one argument. Without quotes, field splitting can form two arguments and pathname expansion can treat wildcard characters as patterns.

Shells provide operators for default, alternate, assignment, or error when variables are unset or empty. Scripts should validate required parameters explicitly. A misspelled unset variable becoming empty can turn a specific path into a broad directory.

Environment variables are exported parameters inherited by children. Changing a shell-local variable does not necessarily export it. A child’s environment modification does not propagate back to its parent.

### 3.12.6 Command substitution

**Command substitution** executes a nested command and inserts its captured standard output into shell processing. In POSIX-like shells:

~~~sh
count="$(count-records input.txt)"
~~~

The substitution generally removes trailing newline characters. The result remains text and can contain embedded newlines. Quoting preserves it as one field under ordinary rules.

Using command substitution to obtain filenames is unsafe when names can contain newlines or other separators. Structured machine interfaces should use null-delimited records, dedicated file descriptors, JSON with a parser, or direct APIs as appropriate.

Nested command failure does not always make the containing assignment fail under every shell construct. Scripts must understand status propagation.

### 3.12.7 Pathname expansion

Unquoted wildcard patterns such as <code>*.txt</code> can be expanded by the shell into matching pathnames before command execution. The target program does not receive the pattern unless no-match policy leaves it or quoting suppresses expansion.

Filenames can begin with hyphen. A command can mistake such a filename for an option. Use an option terminator <code>--</code> where the program supports it or prefix a relative path with <code>./</code>.

Glob expansion can produce many arguments and exceed process argument-size limits. It can also change between inspection and use. Programs processing large or adversarial directories should enumerate through filesystem APIs and define ordering, errors, and race handling.

### 3.12.8 Redirection order

Redirections are processed in written order in common POSIX shells. File descriptors can be opened, duplicated, and closed.

~~~sh
command >combined.txt 2>&1
~~~

First stdout is opened on <code>combined.txt</code>. Then stderr is duplicated to the current stdout, so both refer to the file.

~~~sh
command 2>&1 >output.txt
~~~

First stderr is duplicated to the shell’s current stdout, perhaps the terminal. Then stdout moves to <code>output.txt</code>. Stderr remains on the original destination. The lines are not equivalent.

Redirection failure can prevent command execution. Truncating an output file commonly occurs before the program starts. Redirecting input and output to the same file can therefore erase input before it is read.

### 3.12.9 Here-documents and here-strings

A **here-document** supplies a block of shell source text as command input until a delimiter. Whether parameter and command expansions occur depends on delimiter quoting.

~~~sh
tool <<'END_INPUT'
literal $HOME
second line
END_INPUT
~~~

Quoting the delimiter in a POSIX-like shell suppresses the selected expansions in the body. A **here-string** in shells that support it supplies one expanded string, commonly with a terminating newline.

These mechanisms are convenient for fixed trusted data. They are not a safe way to interpolate untrusted values into another language such as SQL. The receiving language still parses its content.

### 3.12.10 Pipelines create concurrent processes

In

~~~sh
producer | transformer | consumer
~~~

the shell creates pipes and ordinarily starts all commands so they can run concurrently. If the consumer stops reading, writes can block when pipe buffers fill. If the consumer exits, an upstream write can receive a broken-pipe signal or error.

Pipeline exit status differs by shell policy. A POSIX shell ordinarily reports the last command’s status; optional <code>pipefail</code>-like modes report failure from another component according to shell rules. Without such handling, an upstream failure can be masked by a consumer that successfully processes empty input.

A pipeline transports bytes, not records. Newline-delimited text fails for fields containing newlines unless the format escapes them. Binary formats need framing.

### 3.12.11 Conditional command lists

POSIX-like shells commonly provide:

~~~sh
first && second
first || recovery
~~~

With AND-list syntax, <code>second</code> runs only if <code>first</code> returns success status. With OR-list syntax, <code>recovery</code> runs only if <code>first</code> returns failure.

This is status-based control flow. It does not inspect printed words “success” or “error.” A command that prints an error and exits zero misleads the shell.

Negation operators invert status, not output. Parentheses or braces group commands under shell-specific subshell and current-shell semantics. Grouping can determine whether variable and directory changes persist.

### 3.12.12 Background jobs and job control

An interactive shell can start a pipeline as a **background job**, retain job state, and return a prompt. Job control uses process groups and a controlling terminal so terminal-generated signals reach the foreground group.

Suspending a foreground program does not terminate it. The shell can resume it in foreground or background. A background process attempting terminal input can be stopped under line-discipline policy.

Closing a terminal can send a hangup signal to associated jobs. Reliable services should be launched under a service manager, not kept alive through fragile terminal detachment tricks.

### 3.12.13 Shell scripts and failure discipline

A shell script begins with a declared interpreter mechanism on Unix-like executable files, commonly a shebang:

~~~sh
#!/bin/sh
~~~

This asks the kernel/launcher to run a particular interpreter path under platform rules. <code>/bin/sh</code> denotes the system’s POSIX-style shell, not necessarily Bash. Using Bash-only arrays or condition syntax while declaring <code>sh</code> is a portability defect.

Robust scripts:

- validate argument count and forms;
- quote expansions;
- use explicit paths and working directories;
- avoid parsing human-formatted output;
- check every material status;
- use temporary files securely;
- arrange cleanup with traps while recognising forced termination;
- avoid storing secrets in traces and arguments;
- constrain wildcards and destructive targets;
- document supported shell.

Automatic “exit on error” modes have exceptions and version-specific subtleties around conditions, pipelines, substitutions, and functions. They assist but do not replace explicit control-flow understanding.

### 3.12.14 PowerShell is not a POSIX shell with different punctuation

PowerShell pipelines commonly pass .NET objects between PowerShell commands rather than only byte text. Formatting occurs when objects reach a display/output boundary. External native commands still communicate through process streams and argument conventions.

PowerShell has its own quoting, variable, error, provider, path, and stream semantics. A non-terminating error can be written while a pipeline continues unless error policy changes. Its success indicator, automatic variables, and native exit code require separate handling.

Documentation must label examples. “Run this in a terminal” is incomplete when the terminal can host Bash, Z shell, PowerShell, Command Prompt, or another interpreter.

### 3.12.15 Shell use versus a general-purpose language

Shells excel at short orchestration of established commands and streams. Complexity grows rapidly when a task needs:

- nested structured data;
- substantial arithmetic;
- portable path semantics;
- precise exception handling;
- concurrency control;
- unit-testable transformations;
- security-sensitive parsing.

At that point Python can express the logic with argument sequences and library APIs while still invoking external programs where appropriate. The correct choice minimises boundary ambiguity, not line count.

Shell and Python compose: a shell establishes an environment and launches a Python module; Python implements validated data logic and returns a truthful status. Each owns the part its semantics express clearly.
