# 3.6 The limits of algorithmic decision

Turing-complete systems encounter **undecidable problems**: questions for which no algorithm can produce a correct yes-or-no answer for every admitted input. The classical example is the **halting problem**: determine, from an arbitrary program and input, whether that execution will eventually stop.

An informal contradiction demonstrates the boundary. Assume a perfect procedure `halts(program, input)` exists. Construct a new program `opposite(candidate)` that loops forever if `halts(candidate, candidate)` says the candidate stops, and stops immediately if it says the candidate loops. Ask what `opposite(opposite)` does. If the predictor says it stops, its definition makes it loop. If the predictor says it loops, its definition makes it stop. The assumed universal predictor cannot exist.

This result does not prohibit useful termination analysis. Compilers, type systems, linters, and proof tools can establish termination or non-termination for restricted programs and conditions. The impossibility concerns one algorithm that decides the question correctly for every arbitrary program and input.

It also clarifies the limits of testing. No finite test suite can generally establish every semantic property of every arbitrary program. Engineering uses layered evidence—specifications, proofs over tractable components, static checks, tests, reviews, runtime validation, and operational monitoring—because no single universal oracle exists.

> **Common misconception — “Turing-complete means capable of solving any problem.”**  
> It means capable of expressing any Turing-computable procedure, given unbounded abstract resources. Some problems are not computable; many computable instances are practically infeasible; expressibility alone says nothing about correctness.
