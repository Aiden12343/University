# 3.7 Interfaces and contracts

An **interface** is a boundary through which components exchange values, effects, or requests under defined rules. A **contract** states obligations at that boundary. Contracts can include accepted forms, returned values, mutations, errors, ordering, timing, resource ownership, and concurrency guarantees.

A useful contract distinguishes:

- **syntax:** which forms can be presented;
- **semantics:** what valid forms mean;
- **preconditions:** what the caller must establish;
- **postconditions:** what successful completion establishes;
- **effects:** what external or shared state may change;
- **failure modes:** how inability to fulfil the request appears;
- **resource bounds:** relevant limits on time, memory, or external use.

The need for contracts follows from composition. If component A uses component B, A cannot re-derive B’s entire implementation on every call. It relies on an abstraction boundary. B, in turn, is free to change its internal method while preserving the published behaviour.

### Worked example 3.6 — Contract for parsing a whole number

Weak statement: “convert text to a number.”

Stronger contract:

- Input is a finite sequence of Unicode characters.
- Leading and trailing whitespace are permitted and ignored.
- An optional leading `+` or `-` is permitted.
- At least one ASCII decimal digit must remain.
- Internal whitespace and non-digits are rejected.
- On success, return the corresponding mathematical integer.
- On rejection, report an invalid-input failure; do not return a partial prefix.
- The input text is not modified.

Under this contract, `"  -42 "` succeeds with negative forty-two; `"12x"` fails rather than producing twelve; `""` fails; `"+"` fails because no digit follows. Whether non-ASCII decimal characters are admitted has been answered explicitly by saying ASCII digits. A different valid contract could make a different choice.

### 3.7.1 Domains, relations, and functions

A **set** is a collection considered by membership rather than position or repetition. Writing \(x\in A\) means \(x\) is a member of set \(A\). A **domain** is a set of admitted inputs or values under discussion.

A **relation** between sets \(A\) and \(B\) is a set of ordered pairs \((a,b)\) with \(a\in A\) and \(b\in B\). A **function** is a relation assigning each admitted input exactly one output. A mathematical function is not a Python function object; it is an abstract input–output relation with uniqueness.

A specification is often a relation rather than a function. Sorting a sequence of records with equal keys can permit several valid orders unless stability is required. A nondeterministic concurrent service can permit several event orders. An implementation is correct when its actual outcomes remain within the permitted relation.

A **partial function** is undefined for some possible inputs. Division as a function on pairs of integers is undefined when the divisor is zero unless the codomain includes an error outcome. A program interface can totalise the operation by returning either a quotient or a structured failure.

### Worked example 3.7.1 — Specification permits several outputs

Problem: choose one maximum-valued record from a non-empty sequence. If three records tie for maximum, the specification “return a maximum record” permits any of them. An implementation returning the first is correct; one returning the last is also correct.

Add “return the earliest maximum in input order.” The relation becomes a function for a fixed input sequence. This refinement reduces implementation freedom and makes tie behaviour testable.

### 3.7.2 Determinism and nondeterminism

A system is **deterministic** relative to a state model when the same complete state and input select one next state or outcome. A system is **nondeterministic** when several next steps or outcomes are permitted.

Nondeterminism can be:

- a mathematical abstraction allowing several choices;
- environmental variation from scheduling, input arrival, or hardware;
- intentional randomisation;
- underspecification leaving implementations freedom.

A deterministic program can produce different results when the “same input” description omits time, file state, random-generator state, process schedule, or library version. Reproducibility requires identifying complete relevant state, not merely one function argument.

A nondeterministic specification can still be rigorous. It states the set of permitted outcomes and forbidden behaviours. Concurrency correctness often proves every possible interleaving under assumptions preserves an invariant.

### 3.7.3 Randomised algorithms

A **randomised algorithm** uses random or pseudorandom choices as part of its method. Its correctness and cost can be probabilistic.

A **Las Vegas algorithm** always returns a correct result when it terminates, while runtime varies randomly. A **Monte Carlo algorithm** has bounded runtime under a rule but permits a small probability of incorrect or approximate result. Terminology is conventional and not related to geography in the computation.

Randomisation can:

- avoid adversarial worst cases;
- sample a large population;
- break symmetry among concurrent actors;
- construct probabilistic data structures;
- approximate otherwise expensive quantities.

Probability claims require a source model. A deterministic pseudorandom generator with a fixed seed produces a repeatable sequence; security requires unpredictability against an adversary, while simulation requires statistical properties and reproducibility.

### 3.7.4 Heuristics and approximation

A **heuristic** is a method intended to produce useful results without a universal correctness or optimality guarantee for the full problem. An **approximation algorithm** has a proved bound relating its result to an optimum under a formal problem.

These are not synonyms for defective algorithms. Some optimisation problems are computationally intractable at useful scale under current knowledge. A heuristic can be the rational engineering choice when its limitations are measured. An approximation guarantee provides stronger knowledge than typical observed quality.

For a minimisation problem, an algorithm with approximation ratio 2 guarantees its cost is at most twice the optimal cost for admitted instances. It need not know the optimum to prove the relation.

A timeout followed by the best result found so far creates an **anytime algorithm** when quality can improve with more time and a valid current result is available at interruption.

### 3.7.5 Specification refinement

A high-level requirement is refined into contracts at component boundaries. Refinement adds detail while preserving the parent obligation.

High level: “Store the submitted report durably.”

Questions required for refinement:

- Which submission counts as accepted?
- Against which failures must it survive: process crash, host crash, power loss, disk loss, regional loss?
- By what deadline must acknowledgement occur?
- Can duplicate submissions occur?
- How is report identity established?
- Which confidentiality and retention policies apply?
- What does recovery return after partial failure?

“Write the file” is not a refinement until its filesystem calls and durability guarantees satisfy the stated failure model. A database commit can be a refinement under one system architecture; replicated quorum storage under another.

A **trace refinement** proof relates concrete implementation histories to abstract permitted histories. Internal steps can be hidden; every visible concrete effect must correspond to an abstract effect in order.

### 3.7.6 Safety and liveness properties

A **safety property** states that something bad never happens. Examples:

- two processes never own one exclusive lock simultaneously;
- a balance never becomes negative;
- an unauthorised user never reads a report.

A finite bad prefix can demonstrate a safety violation: once the unauthorised read occurs, extending history cannot undo that it occurred.

A **liveness property** states that something good eventually happens:

- every accepted job eventually completes or reports permanent failure;
- a runnable task eventually receives processor time;
- a lock request eventually succeeds under fair competition.

Testing can readily expose a safety counterexample but cannot establish unbounded eventuality by waiting a finite time. Liveness proofs require progress assumptions about scheduling, failures, and resources.

Some properties combine both. “Every request receives exactly one correct response within two seconds” contains safety (no wrong or duplicate response) and bounded liveness (response by deadline).

### 3.7.7 Preconditions as allocation of responsibility

A precondition does more than restrict mathematics; it allocates responsibility to the caller. If a sorting function requires comparable elements, a caller violating that requirement cannot demand a sorted result under the contract. Robust public interfaces commonly validate untrusted inputs rather than rely on invisible preconditions.

Internal helper functions can use stronger preconditions established by callers to avoid repeated work. Proof proceeds compositionally:

1. caller establishes helper precondition;
2. helper guarantees postcondition;
3. caller uses that postcondition to establish its own.

An **assertion** is a proposition checked or assumed at a program point. Assertions documenting internal invariants are different from input validation that must remain active in production. A runtime mode that removes assertions cannot be allowed to remove security or correctness checks at an untrusted boundary.

### 3.7.8 Finite-state computational models

A deterministic finite automaton, or **DFA**, consists of:

- a finite set of states;
- an input alphabet;
- one transition for each state and input symbol;
- a start state;
- a set of accepting states.

It reads a finite symbol sequence one symbol at a time. Acceptance depends on final state. It has no unbounded memory beyond its finite state.

Example: accept binary strings containing an even number of 1 bits. States Even and Odd record parity. Reading 0 leaves state unchanged; reading 1 switches state. Start and accepting state is Even.

| State | input 0 | input 1 | accepting |
|:---|:---|:---|:---:|
| Even | Even | Odd | yes |
| Odd | Odd | Even | no |

No matter how long the input, two states suffice because exact count is unnecessary; only parity matters.

A finite automaton cannot recognise arbitrary balanced parentheses because it would need an unbounded count of unmatched opens. Adding a stack creates a pushdown automaton capable of nested structure. Adding Turing-machine-like writable unbounded storage produces general computability. Computational models are classified by memory and transition power.

### 3.7.9 Turing-machine mechanics in detail

A Turing machine can be specified as a finite transition function. For each current control state and scanned tape symbol, the rule selects:

- symbol to write;
- movement one cell left or right, or sometimes stay;
- next state.

A halting state has no continuation or an explicit halt action. Input occupies a finite initial region; all other cells contain blank symbols.

The tape is unbounded in the model but each individual step touches one cell. It is not infinite physical hardware available instantly. The abstraction asks which functions are computable without imposing one fixed memory bound across all input sizes.

Different variations—several tapes, larger alphabets, movement conventions—compute the same class of functions because each can simulate the others with finite encoding overhead. They can differ greatly in efficiency.

### 3.7.10 Universal computation

A **universal Turing machine** receives an encoding of another machine \(M\) and input \(x\), then simulates \(M\) on \(x\). Program and data occupy one representation: part describes transition rules, part initial state.

This formalises the stored-program insight. A general-purpose interpreter is a practical analogue: CPython consumes a Python program representation and input, then implements its operations. CPython is not literally a simple Turing machine, and finite hardware imposes limits, but universality explains how one fixed machine can enact arbitrarily many algorithms through stored descriptions.

An encoding must be effectively decodable. A sequence can represent states, symbols, and transitions with delimiters or lengths. The universal machine parses this data and updates its own simulation state. No mystical transfer of “meaning” occurs.

### 3.7.11 The Church–Turing thesis

The **Church–Turing thesis** proposes that every effectively calculable function—every method a human or mechanical procedure could carry out by definite finite rules—is computable by a Turing machine. It is a thesis connecting an informal concept, effective calculation, to a formal model; it is not a mathematical theorem proved from the informal side.

Several independently developed models—lambda calculus, recursive functions, register machines, Turing machines—identify the same computable class, supporting the thesis. Physical theories such as quantum computation can change efficiency for some problems without currently establishing computation of non-Turing-computable functions under accepted models.

Turing-completeness is therefore a low threshold for general-purpose expressiveness. Most modern languages cross it. The difficult questions become correctness, complexity, type and effect discipline, parallelism, resource bounds, and human comprehensibility.

### 3.7.12 A more explicit halting contradiction

Assume procedure \(H(P,I)\) returns true exactly when encoded program \(P\) halts on input \(I\), and false otherwise.

Construct program \(D(X)\):

~~~text
if H(X, X) is true:
    loop forever
else:
    halt
~~~

Now evaluate \(D(D)\).

- If \(H(D,D)\) returns true, definition of \(D\) loops, making the answer false.
- If \(H(D,D)\) returns false, definition of \(D\) halts, making the answer true.

Both possibilities contradict perfection of \(H\). Therefore no such total correct procedure exists for all encoded programs and inputs.

The contradiction depends on self-application through encoding and negation of predicted behaviour. It does not say humans can never recognise an individual infinite loop. It says no algorithm decides all cases.

### 3.7.13 Rice’s theorem, informally flagged

**Forward reference — formal language theory is not yet established.** A minimal useful statement is: every nontrivial semantic property of the partial function computed by an arbitrary program is undecidable in general. “Nontrivial” means some programs have the property and some do not. This result is called Rice’s theorem.

Examples of general semantic questions include whether an arbitrary program ever produces output 7, computes the same function as another arbitrary program, or accepts every input. Static-analysis tools answer conservative approximations or restricted cases. They can report “unknown,” reject some safe programs, or require proofs/annotations.

Syntactic properties remain decidable by parsing finite text: whether source contains a token or conforms to a grammar. Semantic properties connect text to unbounded execution and encounter the limit.

### 3.7.14 Feasibility beyond computability

A computable problem can remain infeasible. If an algorithm takes \(2^n\) steps, increasing input by one can double work. At one billion steps per second, \(2^{100}\) steps exceed practical timescales. More hardware changes the constant, not exponential growth.

Complexity theory classifies resource requirements as input grows. Chapter 13 introduces asymptotic notation, but the present distinction is essential:

- **computable:** some terminating algorithm exists;
- **tractable under a model:** an algorithm uses acceptable resources as size grows;
- **practical:** this implementation meets actual time, memory, energy, cost, and reliability constraints for relevant inputs.

An \(O(n^3)\) method can be practical for \(n=20\); an \(O(n)\) method can be impractical if each step contacts a distant service. Mathematical and engineering cost models complement rather than replace one another.
