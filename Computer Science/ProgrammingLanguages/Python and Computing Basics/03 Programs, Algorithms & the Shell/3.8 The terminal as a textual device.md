# 3.8 The terminal as a textual device

A programmer needs a direct, inspectable means of requesting program execution and observing results. A **terminal** is a text-oriented input/output interface. Historically the word referred to physical devices connected to a remote computer; contemporary terminal applications emulate that interaction in a window or screen session.

A terminal is not itself normally the program that interprets commands. It displays output and conveys input to a **shell**. A shell is a program that reads command language, performs expansions and redirections, locates requested programs or built-in operations, launches or coordinates them, and reports completion.

A **command line** is one textual command submission to a shell. A **prompt** is text displayed to indicate readiness for input. The prompt characters are not generally part of the command. Documentation often shows `$` for a POSIX-style shell prompt or `>`/`PS>` for Windows PowerShell; typing the illustrative prompt itself can therefore be an error.

Commands are parsed by the shell’s language before a target program receives arguments. Spaces, quotation marks, wildcard characters, variable markers, pipes, and redirection operators may have shell-specific meanings. The same visible command text can be interpreted differently by Bash, PowerShell, `cmd.exe`, or another shell. Instructions must name the shell they target.

### Worked example 3.7 — Command, arguments, and process

Consider this POSIX-shell command:

```sh
python3 report.py "May results.csv"
```

The shell parses three words because quotation marks group the space-containing filename:

1. `python3` — the command name to locate;
2. `report.py` — first argument;
3. `May results.csv` — second argument.

The quote characters control shell parsing and are not ordinarily included in the argument value. The shell locates an executable associated with `python3`, asks the operating system to create a process, and supplies the argument sequence. Python then decides how to interpret `report.py` and the remaining argument. A failure can belong to different owners:

- the shell cannot locate `python3`;
- the OS denies execution;
- Python cannot open `report.py`;
- the script rejects or cannot open `May results.csv`;
- execution begins and later fails.

“The command does not work” erases the evidence needed to distinguish them.
