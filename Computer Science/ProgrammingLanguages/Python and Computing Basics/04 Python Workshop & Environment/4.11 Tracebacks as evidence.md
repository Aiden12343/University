# 4.11 Tracebacks as evidence

An **exception** is an object signalling that normal execution cannot continue as requested. When an exception propagates without being handled, Python prints a **traceback**, a report of active calls leading to the failure, followed by the exception type and message.

Read a traceback from the final line upwards:

1. identify the exception type;
2. read its message as evidence, not as an infallible diagnosis;
3. inspect the final frame belonging to project code;
4. trace callers only as needed to learn how invalid state arrived;
5. reproduce the smallest failing input before editing.

### Worked example 4.8 — Preserve unexpected failures

The first program catches `OSError` and `UnicodeError` because inability to open/read a path and inability to decode promised UTF-8 are anticipated interface failures. It does not catch `Exception` indiscriminately. If `count_lines` contains a programming defect such as a misspelled method, suppressing its traceback and presenting it as “could not read file” would destroy diagnostic evidence and lie about the failure class.

Expected operational failures can receive concise user-facing treatment. Unexpected defects should ordinarily retain a traceback during development and testing. Error handling is classification, not concealment.

### 4.11.1 Traceback anatomy

A traceback consists of **frames**. A frame records one active execution context, including a code location, namespace references, and instruction position. Printed tracebacks commonly list the path, source line number, function name, and source excerpt for each relevant frame, followed by the exception type and message.

Consider:

~~~python
def parse_count(text: str) -> int:
    return int(text)


def load_count() -> int:
    return parse_count("three")


print(load_count())
~~~

The conversion <code>int("three")</code> cannot interpret the text as a decimal integer and raises <code>ValueError</code>. The traceback connects:

1. the module-level call to <code>load_count</code>;
2. the call from <code>load_count</code> to <code>parse_count</code>;
3. the failing conversion inside <code>parse_count</code>.

The last project-owned frame is usually nearest to the immediate failure, but the earliest incorrect decision can be in a caller that supplied invalid data. Debugging follows data and obligations through frames rather than editing the last line mechanically.

### 4.11.2 Exception type, message, cause, and context

The exception type classifies failure under Python’s exception hierarchy. The message carries instance-specific detail and may vary by platform or version. An exception can also record a **cause** or **context** when one failure arises while handling another.

This wrapper preserves the abstraction boundary:

~~~python
from pathlib import Path


class ConfigurationError(Exception):
    pass


def read_port(path: Path) -> int:
    try:
        text = path.read_text(encoding="utf-8").strip()
        return int(text)
    except (OSError, UnicodeError, ValueError) as error:
        raise ConfigurationError(f"invalid port file: {path}") from error
~~~

The syntax <code>raise ... from error</code> establishes explicit exception chaining. A caller can handle <code>ConfigurationError</code> at the configuration boundary while the traceback retains the original filesystem, decoding, or conversion failure as its cause. Exception classes and handling semantics are fully developed in Chapter 6.

The path inserted into the message is external data. In security-sensitive logs it may require bounded, escaped representation. Exception preservation does not excuse uncontrolled disclosure.

### 4.11.3 Syntax and indentation diagnostics have a different time

A <code>SyntaxError</code> can occur while Python parses source before it begins ordinary execution of that code unit. No earlier statement in the same uncompiled file should be assumed to have executed. Interactive environments can compile one submitted unit at a time, so earlier successful submissions remain in that process.

An <code>IndentationError</code> is a subclass of <code>SyntaxError</code> concerned with invalid indentation structure. A <code>TabError</code> reports inconsistent tab/space use under the lexical rules. These classifications are more informative than the generic phrase “the program crashed”.

The caret or highlighted span in a syntax diagnostic marks where the parser detected impossibility, which can be later than the actual omission. A missing closing delimiter on one line may make a later token appear invalid. Inspect the surrounding construct and delimiter balance.

### 4.11.4 Tracebacks can contain sensitive state

Tracebacks reveal source paths, module names, function names, source excerpts, and exception messages. Enhanced diagnostic tools may additionally capture local variable values. This is useful development evidence and a potential production disclosure.

Use different presentation policies:

- development and controlled tests retain full tracebacks;
- command-line tools may show concise expected operational errors and reserve tracebacks for a debug mode;
- network services log an internal correlation identifier and avoid returning implementation traces to untrusted clients;
- logs apply access control, retention, and secret-redaction policy.

Do not solve disclosure by catching every exception and doing nothing. Preserve the diagnostic internally, classify the public response, and terminate with truthful status.

### 4.11.5 Minimal reproduction

A **minimal reproduction** is the smallest self-contained construction known to exhibit a defect. Producing one tests assumptions:

1. copy, do not edit away, the original evidence;
2. record executable, version, arguments, CWD, and input;
3. remove unrelated modules or data one element at a time;
4. confirm the failure after every removal;
5. stop when another removal changes the failure;
6. express expected and observed behaviour exactly.

A minimal reproduction that no longer fails is not evidence that the original defect disappeared; it shows that a removed condition mattered or that the experiment was not faithful. Conversely, if a five-line reproduction fails in a fresh environment, theories about the larger application become less plausible.

### Worked example 4.8A — Classify three failures

Prepare three files.

File A:

~~~python
print("unterminated)
~~~

File B:

~~~python
from pathlib import Path

print(Path("absent-file").read_text(encoding="utf-8"))
~~~

File C:

~~~python
def square(number: int) -> int:
    return number + number


print(square(5))
~~~

A should fail during parsing with a syntax-class diagnostic. B should parse and begin execution, then fail while opening an absent path, ordinarily with a subclass of <code>OSError</code>. C completes successfully at the process level but prints 10 rather than the mathematically specified square 25; this is a logic defect and may have no traceback.

The trio proves why “run it and fix errors” is not a complete verification method. Syntax diagnostics address source form, runtime exceptions address particular failed operations, and an oracle is required to expose plausible but wrong output.

> **Common misconception — “No traceback means no error.”**  
> A program can return an incorrect value, corrupt a file, leak information, hang, or violate performance requirements while raising no exception. Tracebacks are one evidence class.
