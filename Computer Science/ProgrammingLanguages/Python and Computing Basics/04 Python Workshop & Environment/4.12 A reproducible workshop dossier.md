# 4.12 A reproducible workshop dossier

For every exercise project, retain:

- project tree;
- interpreter executable, implementation, and version;
- operating-system and shell lane;
- environment-creation command;
- installation command;
- launch command and required CWD;
- exact input fixtures;
- expected stdout, stderr, status, and file effects;
- one fresh-process transcript;
- dependency declaration and lock policy;
- known platform qualifications.

This dossier turns setup from folklore into evidence. When two learners see different results, the comparison begins with recorded variables rather than reinstalling blindly.

### 4.12.1 The environment manifest

Create a machine-readable probe and a human-readable interpretation. A minimal probe can emit JSON, whose formal serialisation rules are deferred to Chapter 11:

~~~python
from __future__ import annotations

import json
import os
import platform
import sys
from pathlib import Path

manifest = {
    "implementation": sys.implementation.name,
    "python_version": platform.python_version(),
    "executable": sys.executable,
    "platform": platform.platform(),
    "machine": platform.machine(),
    "cwd": str(Path.cwd()),
    "utf8_mode": sys.flags.utf8_mode,
    "selected_mode": os.environ.get("TEXT_CENSUS_MODE"),
}

print(json.dumps(manifest, indent=2, sort_keys=True))
~~~

The program deliberately reads only one project-specific environment variable. <code>sort_keys=True</code> gives stable key order for easier comparison. Paths and platform strings can contain machine-specific or identifying information, so decide whether a shared dossier should retain, redact, or relativise them.

A manifest is not self-interpreting. If two manifests differ in executable path but use byte-identical builds and equivalent dependencies, the path difference may be irrelevant to a semantic claim. If they differ in Python minor version while a syntax feature changed, it may be decisive. The dossier pairs observations with a claim-specific analysis.

### 4.12.2 The command transcript

A reproducible transcript records:

- shell or launcher language;
- exact command and its reference directory;
- standard-input source;
- standard-output bytes or decoded text;
- standard-error bytes or decoded text;
- exit status;
- files created, modified, or removed;
- start conditions that can affect the result.

Copying a terminal screenshot is inferior to capturing the channels separately because wrapping, colour, prompts, and interleaving can obscure boundaries. For a POSIX-style shell, one can redirect streams to separate files and capture status using the shell’s documented syntax; PowerShell requires its own corresponding mechanism. The manuscript does not pretend one transcript command is portable across shell languages.

Where exact bytes matter, store fixture and output hashes in addition to rendered text. Text display can normalise newlines or replace undecodable bytes. Where semantic records matter, parse them and compare their structure rather than relying only on screen appearance.

### 4.12.3 The clean-room handoff test

The strongest introductory test is a handoff to a new environment whose operator possesses only:

1. the project artefact;
2. the README and declared configuration;
3. access to admitted dependency sources;
4. an operating environment within the support contract.

The operator must not depend on the author’s shell history, global packages, editor state, home-directory layout, or verbal correction. Every question asked during reconstruction identifies a missing contract. Record and repair the documentation, then repeat from a newly constructed environment rather than continuing from the patched one.

This test integrates the first four chapters. Hardware and operating-system conditions delimit the machine. Processes and the shell determine launch. The program and data establish the computation. The Python workshop supplies a reproducible language implementation and dependency boundary.

### 4.12.4 Workshop acceptance criteria

The workshop is accepted only when all of the following are evidenced:

1. An accountable Python 3.12-or-later interpreter is selected by an explicit command.
2. The running process reports the expected implementation, version, and executable.
3. The project source, environment directory, fixtures, and generated artefacts occupy documented roles.
4. A clean virtual environment can be reconstructed without using global project packages.
5. Direct dependencies and their purpose are declared; the resolution or locking policy is named.
6. The installed project imports from the intended location.
7. The documented module invocation succeeds from outside the repository root.
8. Success and two defined failure classes produce the specified streams and statuses.
9. Unexpected defects retain diagnostic evidence during development.
10. A second clean reconstruction reproduces the admitted observations.

These criteria do not certify the program as secure or correct. They establish that subsequent semantic experiments occur in a controlled workshop rather than an undocumented accumulation of state.
