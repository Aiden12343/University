# 4.2 Obtain Python from an accountable source

Software installation changes a machine and crosses a trust boundary. The executable will be permitted to read source, process data, install packages, and in some contexts execute with the user’s authority. Obtain the interpreter from the official Python distribution channel for the platform, an accountable operating-system package repository, or an organisation-managed source. Do not choose an arbitrary download mirror merely because its page appears first in a search result.

Installation has three distinct stages:

1. **Acquisition:** obtain a distribution package and, where supported, verify its origin or integrity.
2. **Placement:** install or unpack executable files and the standard library.
3. **Resolution:** configure or discover the command by which a shell selects the intended executable.

Completing placement does not guarantee resolution. A machine may contain several Python installations. The command `python`, `python3`, a versioned command, a launcher, an absolute executable path, or an activated virtual environment may each select differently.

### 4.2.1 Windows execution lane

On Windows, use the currently supported official Python installation mechanism and its documented launcher commands. During installation, read rather than reflexively accept options concerning command aliases and path registration. After installation, open a fresh PowerShell session so that it inherits the updated environment.

Use commands appropriate to the installed mechanism to list or select runtimes, then ask the selected runtime to identify itself. Common installations support one or more of:

```powershell
python --version
py --version
python -c "import sys; print(sys.executable); print(sys.version)"
```

Do not assume every Windows installation provides every command. A failure to resolve `python` is a shell-resolution fact, not proof that no Python files were installed. Conversely, a successful `python --version` does not prove it selected the newly installed version.

### 4.2.2 POSIX-style execution lane

On Linux and macOS, a system may already use a Python interpreter for operating-system tools. Replacing or modifying that system-managed interpreter can damage package-management assumptions. Use the platform’s supported package mechanism, an official installer, or an accountable version manager without overwriting system components casually.

Typical diagnostic commands include:

```sh
python3 --version
command -v python3
python3 -c 'import sys; print(sys.executable); print(sys.version)'
```

`command -v` is a POSIX-shell-oriented resolution check. Other shells provide their own mechanisms. The executable path printed by `sys.executable` is evidence from the running interpreter itself and therefore stronger than a guess based on command spelling.

### 4.2.3 Interpreter architecture, build, and provenance

Two executables bearing the same Python language version need not be interchangeable. A build is also characterised by its implementation, processor architecture, operating-system interface, compilation options, bundled cryptographic and database libraries, and origin. A 64-bit CPython build and a 32-bit CPython build may admit the same source while differing in addressable memory, binary-extension compatibility, and native integer widths exposed through interfaces. A debug build may maintain additional checks. A vendor build may carry patches absent from the upstream release.

The **processor architecture** of an executable identifies the machine-instruction family for which its native code was produced, such as x86-64 or AArch64. This is distinct from the operating system’s architecture and from the architecture of any particular extension module. A process can load native extension code only when the relevant executable format, processor architecture, operating-system application binary interface, and Python extension interface are mutually compatible.

The following diagnostic program records more than the short version string:

~~~python
import platform
import struct
import sys
import sysconfig

print("implementation:", sys.implementation.name)
print("version:", sys.version)
print("executable:", sys.executable)
print("pointer bits:", struct.calcsize("P") * 8)
print("machine:", platform.machine())
print("platform tag:", sysconfig.get_platform())
print("cache tag:", sys.implementation.cache_tag)
~~~

The expression <code>struct.calcsize("P")</code> reports the size, in bytes, of a native pointer representation used by the running build; multiplying by eight converts bytes to bits. The result characterises this process, not every program on the operating system. <code>sysconfig.get_platform()</code> produces a platform descriptor used by build and installation machinery. <code>cache_tag</code> helps distinguish implementation-specific bytecode caches; bytecode is formally treated in Chapter 15.

**Provenance** is an account of where an artefact came from and which transformations produced it. For a workshop interpreter, provenance may include an upstream installer signature, operating-system repository, organisation-managed image, or version-manager recipe. A version number without provenance is insufficient evidence of authenticity. Conversely, authentic origin does not prove that every third-party package later installed into the environment is trustworthy.

> **Common misconception — “The same version number means the same runtime.”**  
> The language version constrains semantics, but build architecture, implementation, vendor patches, linked libraries, and platform ABI can still differ. Record the dimensions that can affect the claim under investigation.

### 4.2.4 Command resolution and the search path

When a shell receives an unqualified command name, it applies its command-resolution rules. Those rules may consult aliases, functions, built-ins, remembered locations, executable suffix conventions, application aliases, and a **search path**. A search path is an ordered collection of directories considered when resolving an unqualified program name. On many systems it is supplied through the environment variable conventionally named <code>PATH</code>.

The order is semantically important. Suppose the search path is:

~~~text
/project/.venv/bin
/usr/local/bin
/usr/bin
~~~

and each directory contains an executable called <code>python</code>. A rule that selects the first matching executable chooses the project environment’s copy. Reversing the first two entries can choose a different process without changing the command text. Activation commonly works by placing an environment-specific directory early in this ordered search.

Shells can cache earlier resolutions. Therefore changing <code>PATH</code> does not, in every shell, guarantee that a repeated command is immediately resolved afresh. Consult the shell’s command-inspection and cache-reset operations when the reported executable contradicts the visible path. The language-neutral diagnostic sequence is:

1. ask the shell how it resolves the command;
2. invoke the command;
3. ask the running Python process for <code>sys.executable</code>;
4. compare the two observations;
5. use an absolute executable path if ambiguity remains.

An **absolute path** begins at a filesystem root or other platform-defined anchor and does not depend on the current working directory. It can remove search-path ambiguity, although symbolic links, launch shims, containers, and executable replacement mean that it is not an eternal identity. Reproducibility requires enough environmental description to interpret the path.

On POSIX-oriented shells, a command such as <code>type -a python3</code> or <code>command -V python3</code> may expose resolution; PowerShell provides commands such as <code>Get-Command python -All</code>. These are examples rather than cross-platform promises. The shell’s own documentation governs its resolution language.

### Worked example 4.1 — Establish interpreter identity

Run the following using the command selected for the workshop:

```python
import platform
import sys

print(sys.executable)
print(sys.version)
print(sys.implementation.name)
print(platform.platform())
```

Line by line:

1. `import platform` requests the standard-library module containing platform-reporting operations.
2. `import sys` requests the module exposing interpreter and process state.
3. `sys.executable` reports the executable path associated with this running process.
4. `sys.version` reports implementation version and build information.
5. `sys.implementation.name` identifies the implementation, commonly `cpython`.
6. `platform.platform()` constructs an environment description.

The precise output is an **experimental observation**. It must not be copied into a universal rule. Record it in an environment note associated with the project.

> **Common misconception — “Python 3 is one program on the machine.”**  
> Several implementations, minor versions, architectures, and environment-specific executables may coexist. A command name is resolved by a shell; ask the launched process which executable and version it is.
