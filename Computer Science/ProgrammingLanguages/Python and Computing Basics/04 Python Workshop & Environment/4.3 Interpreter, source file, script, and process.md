# 4.3 Interpreter, source file, script, and process

An **interpreter session** is one running Python process accepting Python input. A **source file** is persistent text containing Python source. A **script** is a source file intended to be executed as an entry program. The file does not execute itself; a Python implementation reads it as input under a launch request.

Suppose `temperature.py` contains:

```python
celsius = 21
fahrenheit = celsius * 9 / 5 + 32
print(fahrenheit)
```

Running

```text
python temperature.py
```

asks the shell to locate the `python` command and supply `temperature.py` as an argument. The selected Python process opens the file, decodes its source text, compiles it according to Python’s rules, and executes the resulting code in a newly created top-level module namespace. A later chapter gives the exact object and namespace model.

The process’s current working directory normally begins as the shell’s current directory, not automatically as the directory containing `temperature.py`. Relative paths used by the script are consequently resolved under a process condition not visible in the source line itself.

### Worked example 4.2 — Inspect script and process locations

Save:

```python
from pathlib import Path

print("working directory:", Path.cwd())
print("source file:", Path(__file__).resolve())
```

Run it first from its own directory and then, using a path to the script, from its parent directory. `Path.cwd()` can change while the resolved `__file__` path continues to identify the same source file. The experiment defeats the false rule “the current directory is where the script lives”.

`pathlib.Path` is a standard-library type for path manipulation. This is a minimal forward definition; its full filesystem semantics appear in Chapter 11.

### 4.3.1 The launch contract

A Python launch is a process-creation request with several independent inputs. At minimum it selects:

- an interpreter executable;
- an interpreter mode and options;
- a source origin, such as a file, module, command string, or interactive stream;
- an argument sequence;
- a current working directory;
- an environment mapping;
- inherited or redirected standard streams;
- operating-system credentials and resource limits.

Treating only the source filename as “the command” suppresses most of this contract. The following invocations are not equivalent:

~~~text
python report.py records.csv
python -O report.py records.csv
python -m reporting records.csv
python -c "print('report')" records.csv
~~~

The first requests a source file. The second additionally requests an implementation option conventionally called optimisation mode; code must not depend on implementation assertions for essential validation because this mode can remove them. The third asks Python’s module-location machinery to find an entry module. The fourth supplies source text directly as a command string. Each form determines the first element and interpretation of the process argument list differently.

Python exposes its received argument sequence through <code>sys.argv</code>. Despite the name “argument vector”, it is a Python list of text strings. Under a script-file launch, element zero ordinarily identifies the script and later elements contain user arguments. Details can differ for <code>-m</code>, <code>-c</code>, interactive operation, embedded runtimes, or platform launchers. A program should document the launch forms it admits rather than generalise from one observation.

### Worked example 4.2A — Observe the launch state

Create <code>launch_probe.py</code>:

~~~python
from __future__ import annotations

import os
import sys
from pathlib import Path

print("executable:", sys.executable)
print("arguments:", repr(sys.argv))
print("working directory:", Path.cwd())
print("process identifier:", os.getpid())
print("stdin interactive:", sys.stdin.isatty())
print("stdout interactive:", sys.stdout.isatty())
~~~

Run it first without user arguments, then with two:

~~~text
python launch_probe.py alpha "two words"
~~~

The quotation marks are shell syntax used to preserve <code>two words</code> as one argument; they ordinarily do not appear in the resulting element of <code>sys.argv</code>. <code>repr</code> requests an unambiguous debugging representation and is formally derived in Chapter 5. <code>os.getpid()</code> reports the process identifier on supported systems. <code>isatty()</code> asks whether a stream appears connected to a terminal-like device. Redirecting stdout to a file commonly changes its result:

~~~text
python launch_probe.py > observation.txt
~~~

The exact observations are environmental. The conceptual result is that identical source can execute under a materially different launch contract.

### 4.3.2 Environment mappings are inherited inputs

A process environment is conventionally a mapping from text names to text values supplied when a process begins. A child process usually inherits a copy derived from its parent, subject to explicit changes by the launcher. Later mutation in the parent does not retroactively rewrite the already-created child’s environment.

Python exposes this mapping through <code>os.environ</code>. Reading a deliberately project-specific value is straightforward:

~~~python
import os

mode = os.environ.get("TEXT_CENSUS_MODE", "strict")
print(mode)
~~~

The call requests the value named <code>TEXT_CENSUS_MODE</code> and uses <code>"strict"</code> when the name is absent. Absence and the present-but-empty string are different states. Environment-derived configuration is external input and must be validated. It is also a poor location for durable project explanation: a new shell or another machine may not contain it.

Secrets are sometimes delivered through the environment because this avoids placing them directly in source. That choice does not make them invisible. Child processes may inherit them; diagnostics may print them; crash reports and process-inspection facilities may expose them; shell histories may retain the commands used to set them. A workshop probe must never dump the entire environment indiscriminately. Inspect only deliberately non-secret names.

### 4.3.3 Process termination and interpreter shutdown

A Python process can finish because top-level execution reaches its end, because <code>SystemExit</code> requests termination, because an unhandled exception reaches the interpreter boundary, or because an external event terminates the process. These paths need not perform identical cleanup and do not produce identical statuses.

Ordinary successful completion conventionally yields status zero. <code>raise SystemExit(3)</code> requests status three. An unhandled exception ordinarily emits a traceback on standard error and yields a non-zero status chosen by the implementation and platform conventions. A forceful operating-system termination may prevent Python-level finalisation entirely.

Buffered output complicates the model. A call to <code>print</code> can transfer characters into a user-space buffer rather than immediately into durable storage. Normal shutdown commonly flushes such buffers; abrupt termination may not. A status therefore classifies process termination but does not by itself prove that every external effect reached stable storage. Chapter 11 develops buffering, context management, and durability.

> **Common misconception — “Calling the interpreter with the same file repeats the same experiment.”**  
> Repetition also requires control of arguments, CWD, environment, streams, executable identity, inputs, and relevant external state. Source equality is only one condition.
