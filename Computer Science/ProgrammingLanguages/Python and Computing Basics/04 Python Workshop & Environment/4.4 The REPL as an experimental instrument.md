# 4.4 The REPL as an experimental instrument

**REPL** abbreviates *read–evaluate–print loop*. An interactive Python session reads a submitted construct, evaluates or executes it, prints the representation of an unassigned expression result, and waits for more input. Start it by launching Python without a script argument, using the platform’s selected command.

The REPL is well suited to small, reversible questions:

- What value and type does this expression produce?
- Does this syntax parse?
- How does a particular operation behave on a boundary input?
- Which executable and version are active?
- What does a standard-library function document or return?

It is poorly suited to retaining a multi-file program, proving fresh-process reproducibility, or preserving a complete history unless that history is deliberately saved. Its namespace accumulates state. A later expression can succeed because an earlier unrecorded input created a name. Restarting the interpreter removes that hidden dependence.

### Worked example 4.3 — Expose accumulated state

In one REPL session enter:

```python
rate = 1.2
amount = 50
amount * rate
```

The final expression produces `60.0`. Now exit and start a fresh session, then enter only:

```python
amount * rate
```

The expression fails because neither name is bound in the new top-level namespace. The first session did not make those bindings part of Python globally; it changed one process’s state.

The primary prompt is commonly `>>>`. A continuation prompt, commonly `...`, indicates that Python is waiting for completion of a compound or delimited construct. These prompts are interface output and should not be copied into a source file.

Use `exit()` or the platform’s end-of-input action to leave. Abruptly closing a terminal usually terminates the process but may hide cleanup or diagnostics. The controlled action makes intent explicit.

> **Common misconception — “If it worked in the REPL, the program is saved.”**  
> A REPL execution proves behaviour in one stateful process. Durable source must be stored in a file, and reproducibility requires a fresh process executing that source under recorded conditions.

### 4.4.1 Expression display is not ordinary output

At the interactive prompt, entering an expression causes the REPL’s display mechanism to show a representation of the resulting value. In a script, evaluating an expression by itself ordinarily produces no visible output. This difference belongs to the interactive interface, not to arithmetic.

Compare the interactive submission:

~~~python
2 + 3
~~~

which commonly displays <code>5</code>, with a source file containing only the same line. Executing the file calculates the value and then discards the unused result. To make output part of a program’s observable contract, request it explicitly:

~~~python
print(2 + 3)
~~~

The REPL normally uses a representation intended to help a programmer distinguish values, while <code>print</code> requests a human-oriented string conversion. For a text value, the former commonly shows quotation marks and escape notation whereas the latter emits the text itself. The precise <code>repr</code> and <code>str</code> protocols are derived in Chapters 5 and 9.

### Worked example 4.3A — Separate evaluation from display

At a fresh REPL:

~~~python
word = "line\nbreak"
word
print(word)
result = 6 * 7
result
~~~

The assignment lines do not display assigned values as expression results. Submitting <code>word</code> displays a representation in which the embedded newline is visible as escape notation. <code>print(word)</code> emits two output lines. The final <code>result</code> displays <code>42</code>. Four events have occurred: binding, retrieval, representational display, and explicit output. Collapsing them into “Python prints things” produces later confusion about scripts, notebooks, logging, and tests.

Many standard REPLs bind the name <code>_</code> to a recently displayed result. This is an interactive convenience, not a sound program dependency. It can be shadowed, altered by tooling, or absent in non-standard interactive environments. Durable source should bind meaningful names explicitly.

### 4.4.2 Interactive help and introspection

**Introspection** is programmatic examination of program objects and runtime state. Python offers several interactive aids:

~~~python
help(str)
dir(str)
type("sample")
~~~

<code>help</code> renders available documentation. <code>dir</code> returns a practical list of names associated with an object or scope; it is an exploratory aid, not a complete semantic specification. <code>type</code> reports an object’s runtime class. Results can identify where to look, but the language reference and relevant library contract remain authoritative.

Do not paste unknown object representations or exception messages into a shell as commands. The Python REPL parses Python source; the shell parses shell source. The two languages may use similar punctuation with different meanings and different security consequences.

### 4.4.3 The experimental method for REPL questions

A disciplined micro-experiment has five parts:

1. **Question:** state one semantic uncertainty.
2. **Prediction:** record the expected result before execution.
3. **Minimal construction:** remove unrelated state.
4. **Observation:** capture value, type, exception, output, and version as relevant.
5. **Interpretation:** distinguish what the observation establishes from what remains unproved.

Suppose the question is whether division of two integers produces an integer:

~~~python
value = 7 / 2
print(value)
print(type(value))
~~~

Under the Python version used here, the observation is <code>3.5</code> and the runtime type is <code>float</code>. One case suggests the rule but does not define it; the language reference supplies the general contract, including operand categories and exceptional cases. A second experiment with <code>6 / 2</code> is valuable because an integral-looking result is still represented as <code>6.0</code>. Chapter 5 establishes the numeric model.

Restart the REPL when the question concerns initial state, imports, startup cost, or name existence. Use a script in a fresh process when the question concerns reproducibility, standard streams, exit status, command arguments, or import side effects. The instrument must match the property under study.

> **Common misconception — “The REPL is less real than script execution.”**  
> Both execute Python in a process. They differ in source delivery, display hooks, namespace lifetime, and launch state. An observation is valid only for the conditions it actually tests.
