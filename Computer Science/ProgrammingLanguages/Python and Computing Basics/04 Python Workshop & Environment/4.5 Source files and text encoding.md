# 4.5 Source files and text encoding

Python source is text. Text must be represented as bytes when stored in an ordinary file, requiring a **character encoding**. Python 3 source uses UTF-8 by default. **UTF-8** is a variable-width encoding of Unicode code points. An editor must write valid source bytes; the interpreter must decode them under the applicable rule.

Use an editor that can display line numbers, preserve plain text, select UTF-8, and show exact file extensions. A word processor is unsuitable because its document format contains structure beyond plain source text and may substitute typographic quotation marks.

A source filename conventionally ends in `.py`. The suffix helps tools and people identify intended use but does not make arbitrary contents valid Python. A file named `report.py.txt` may appear as `report.py` when a file browser hides known extensions; show full names when diagnosing launch failures.

### Worked example 4.4 — Create and run a durable first script

Create `hello.py` containing exactly:

```python
message = "Hello, computation."
print(message)
```

From the directory containing it, run the selected interpreter with `hello.py` as the script argument. Then close the terminal, open a fresh one, return to the directory, and repeat from the saved file. The second success tests durable source and launch instructions rather than residual REPL state.

Change the source to contain an opening quotation mark without its closing mate. The interpreter should report a syntax error. Restore the closing quotation mark and rerun. The exercise distinguishes edit-time text, parse-time validity, and execution.

### 4.5.1 Bytes, code points, glyphs, and source decoding

Four levels must be separated:

1. a **byte** is an eight-bit storage unit;
2. a **code point** is an abstract numbered element of a character repertoire such as Unicode;
3. an **encoding** maps code points to and from byte sequences;
4. a **glyph** is a visual shape used to render text.

One visible glyph can arise from several code points; one code point can be rendered with different glyphs; and one code point can occupy several UTF-8 bytes. Consequently “character” is too ambiguous for exact claims about storage, indexing, visual width, or user-perceived symbols.

Python must decode source bytes before it can recognise identifiers, keywords, indentation, string literals, or comments. If the byte sequence is invalid under the declared source encoding, source decoding fails before ordinary program execution. If it decodes to typographic quotation marks rather than the ASCII quotation marks admitted as string delimiters, decoding can succeed while parsing fails.

A source-encoding declaration can appear in a specially positioned comment for compatibility with non-UTF-8 files, but new projects should ordinarily standardise on UTF-8. An encoding declaration cannot make arbitrary bytes meaningful; it changes the decoding rule. Mixed encodings within one file are not supported by such a declaration.

### 4.5.2 Newlines and logical lines

Editors and operating systems have historically represented line endings with different byte sequences. Python’s source reader ordinarily recognises common line-ending conventions and treats them as line boundaries. Version-control and formatting tools can normalise them. This convenience does not imply that all external data readers, binary comparisons, or cryptographic hashes ignore line-ending differences.

A **physical line** is a line as represented in the source text. A **logical line** is a unit considered by Python’s tokeniser after rules for explicit or implicit continuation. Delimiters such as parentheses permit one logical expression to span several physical lines:

~~~python
total = (
    19
    + 23
)
~~~

The outer parentheses keep the logical expression open. This form is generally preferable to a trailing backslash because it tolerates comments and is less vulnerable to invisible whitespace after a continuation marker. The meaning of the expression is developed in Chapter 5; here the point is that source layout participates in tokenisation.

Blank logical lines and comments do not execute as operations, though comments can carry documentation and tool directives. A comment begins with <code>#</code> outside a string literal and continues to the physical line’s end. It does not provide a general mechanism for disabling arbitrary fragments: a <code>#</code> inside a string is data, and commenting only one line of a compound construct may leave invalid structure.

### 4.5.3 Indentation is grammatical structure

Python uses indentation to delimit suites of statements. Indentation is therefore not merely presentation. At a given structural level, statements must align according to the tokeniser’s indentation rules.

~~~python
temperature = 18

if temperature < 20:
    message = "cold"
    print(message)
~~~

The two indented statements belong to the conditional suite. Moving <code>print(message)</code> to the left margin changes when it executes; moving it by an inconsistent amount can produce an indentation error. The colon marks the beginning of a suite-bearing construct, and indentation marks the suite’s extent.

Use spaces consistently and configure the editor to reveal indentation. A tab is a distinct control code whose visual width depends on display settings. Python defines how tabs expand for indentation analysis, but mixing tabs and spaces can create code that appears aligned in one editor and is rejected or behaves differently than expected. PEP 8 recommends four spaces per indentation level for ordinary Python code.

Indentation within parentheses is often stylistic rather than suite-delimiting, yet clarity still matters:

~~~python
result = combine(
    first_value,
    second_value,
)
~~~

The trailing comma makes later line additions mechanically cleaner and is accepted in many delimited sequences. Function calls are introduced in Chapter 5 and derived in Chapter 8.

### 4.5.4 Filesystem names are not Python identifiers

A source file’s path is interpreted by the filesystem and launcher; names inside Python source are interpreted by Python’s lexical grammar. The rules differ. A path may contain spaces or punctuation that cannot occur in an ordinary Python identifier. A Python package intended for conventional import should use names compatible with Python identifiers, commonly lower-case letters, digits after the first position, and underscores.

Case sensitivity is also layered. Python identifiers are case-sensitive: <code>rate</code> and <code>Rate</code> are different names. Filesystem path comparison depends on the mounted filesystem and operating environment. A module import that succeeds despite a case mismatch on one machine can fail on another. Portable projects keep the spelling and case of import references identical to their source paths.

> **Common misconception — “Text that looks identical is necessarily the same source.”**  
> Different Unicode code points, line endings, indentation characters, and normalisation forms can render similarly. Diagnose with byte-aware and code-point-aware tools when visual inspection conflicts with parser evidence.
