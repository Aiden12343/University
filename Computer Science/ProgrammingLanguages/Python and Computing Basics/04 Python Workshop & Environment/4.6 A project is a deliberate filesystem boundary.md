# 4.6 A project is a deliberate filesystem boundary

A **project directory** is the chosen root containing one coherent body of source, tests, documentation, configuration, and project-owned data. It establishes relative relationships. It should not be confused with an operating-system installation directory, a general downloads folder, or the virtual environment itself.

For the first projects, use this structure:

```text
text-census/
    README.md
    pyproject.toml
    src/
        text_census/
            __init__.py
            __main__.py
    tests/
        test_core.py
    data/
        sample.txt
    .venv/
```

The structure anticipates concepts developed later:

- `README.md` documents purpose, environment, and commands.
- `pyproject.toml` holds standard project and tool configuration.
- `src/` separates importable source from repository-root conveniences.
- `text_census/` is the package directory.
- `tests/` contains executable verification.
- `data/` holds controlled sample input, not generated output.
- `.venv/` contains the local virtual environment and is ordinarily excluded from version control.

This is not the only valid Python layout. It is selected because each role has a visible owner and because the `src` layout helps expose accidental imports from the working tree. Layout choices are engineering contracts, not incantations.

A **README** is a durable explanatory document for users and contributors. At minimum it should state the supported Python version, environment construction, installation command, execution command, test command, input/output contract, and relevant platform qualification.

### 4.6.1 The project root as a reference frame

A project root is a chosen reference frame, not an inherent filesystem property. Tools infer it by explicit arguments or by searching for markers such as <code>pyproject.toml</code>, a version-control directory, or tool-specific configuration. Two tools can infer different roots if invoked from different directories or configured with different markers.

Paths in documentation must state their reference frame. “Run <code>python tool.py</code>” is incomplete if <code>tool.py</code> exists only relative to an unstated CWD. A more defensible instruction is “from the project root, run the environment interpreter with <code>-m text_census</code>”. The phrase “project root” is then grounded by the documented tree.

Code should not repair ambiguous invocation by changing the process working directory silently. Doing so alters a global process property and can surprise libraries, tests, threads, and later path operations. Derive project-owned resource paths from an explicit configuration value, an installed-resource facility, or a known module location according to the deployment contract. Accept user-supplied paths relative to a documented CWD unless the interface says otherwise.

### 4.6.2 Source, generated state, and local state

The project tree contains categories with different lifetimes:

| Category | Examples | Ordinary policy |
|:---|:---|:---|
| Authored source | <code>src/</code>, tests, documentation | review and version |
| Declarative configuration | <code>pyproject.toml</code>, tool settings | review and version |
| Controlled fixtures | small test inputs with known provenance | review and version |
| Reconstructible environment | <code>.venv/</code> | exclude; recreate |
| Derived caches | bytecode and tool caches | exclude; recreate |
| Build artefacts | wheels, source archives, coverage reports | regenerate or publish through an artefact channel |
| Secrets | tokens, private keys, credentials | keep outside ordinary source history |
| User data | real inputs and outputs | govern by the application’s data policy |

The verbs “exclude” and “ignore” require a named mechanism. A version-control ignore rule prevents ordinary untracked-file selection; it does not delete a file, remove a secret already committed, prevent every tool from reading it, or create access control. Chapter 12 develops version control.

Generated files should have a clear producer and disposal rule. If deleting an unexplained file may destroy irreplaceable work, the project boundary is already poorly specified. Conversely, committing every cache obscures meaningful review and produces platform-specific churn.

### 4.6.3 Why the source layout is an error detector

With importable code placed directly at the repository root, Python launched from that root may import the working files simply because the empty path entry denotes the CWD. Tests can pass even though the distribution was never installed correctly or omitted package data. Under a <code>src/</code> layout, importable code is one level removed. Installing the project into the environment becomes the intended bridge.

This layout does not magically guarantee correct packaging. A misconfigured editable installation can still mask omissions, and a test runner can still alter the import path. Its value is epistemic: it removes one accidental success route and makes the installed-project assumption easier to test.

Use two complementary checks:

1. during development, install the project in editable mode and test rapid source changes;
2. before distribution, build the actual artefact, install it into a clean environment, and test that installed artefact away from the source tree.

The second check detects files that exist in the working directory but were not included in the distribution. Packaging mechanics are treated fully in Chapter 10.

### 4.6.4 Naming the project at different layers

One project can have several names:

- repository or directory name: <code>text-census</code>;
- distribution name in project metadata: <code>text-census</code>;
- import package name: <code>text_census</code>;
- command name exposed to users: <code>text-census</code>;
- human title: “Text Census”.

Hyphens are not admitted in ordinary Python identifiers, so the import package uses an underscore. Packaging name comparison applies normalisation rules that are not identical to Python identifier comparison. A README should show each relevant spelling rather than imply one universal project name.

### Worked example 4.4A — Construct a root-invariant test

Create an empty temporary directory outside the project. From that directory, invoke the project environment’s Python executable explicitly:

~~~text
/absolute/path/to/project/.venv/bin/python -m text_census /absolute/path/to/input.txt
~~~

Use the Windows executable path form on Windows. This test removes the repository root from the role of CWD while retaining the installed project and explicit input. If import succeeds only from the source root, the project may be relying on working-directory path injection rather than its installation contract. If data lookup fails, determine whether the input path was user-relative or incorrectly assumed project-relative.

> **Common misconception — “A tidy directory tree is merely aesthetic.”**  
> Layout determines path reference frames, import opportunities, distribution inclusion, review scope, and the boundary between authored and reconstructed state.
