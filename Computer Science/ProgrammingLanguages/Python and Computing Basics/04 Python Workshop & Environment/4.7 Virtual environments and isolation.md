# 4.7 Virtual environments and isolation

Installing every project’s packages into one interpreter-wide location creates conflicts. Project A may require one version of a library while Project B requires another. Experiments can silently alter later executions. Removing one project can damage another. A **virtual environment** is an isolated Python execution context with its own interpreter entry points and package installation location, while usually reusing or referring to parts of a base Python installation.

Create one in the project root using the selected base interpreter:

```text
python -m venv .venv
```

The `-m` option asks Python to locate and execute a module as a script; `venv` is the standard-library environment-creation module. `.venv` is the destination directory. Use the command spelling that selects the intended base interpreter on the current platform.

Creation and activation are distinct. **Activation** modifies the current shell environment so unqualified commands such as `python` and `pip` preferentially resolve to the environment. Activation does not create the environment, permanently change the machine, or affect already running unrelated shells.

Common activation commands are shell-specific:

```powershell
# PowerShell
.\.venv\Scripts\Activate.ps1
```

```sh
# POSIX-style shells
. .venv/bin/activate
```

After activation, verify rather than trust the prompt decoration:

```python
import sys
print(sys.executable)
print(sys.prefix)
print(sys.base_prefix)
```

Within an ordinary virtual environment, `sys.prefix` identifies the environment while `sys.base_prefix` identifies the base installation. Exact paths are environmental observations.

An environment can be used without activation by invoking its Python executable explicitly. This is often preferable in automation because the selected executable is visible in the command. Activation is shell convenience, not a prerequisite of isolation.

### Worked example 4.5 — Prove environment separation

1. Ask the base interpreter for `sys.executable` and the location of installed packages.
2. Create `.venv`.
3. Invoke `.venv`’s interpreter explicitly and report the same fields.
4. Install a small, accountable demonstration package into `.venv` only if the exercise environment permits external installation.
5. Show that the environment interpreter can import it while the base interpreter cannot, unless the base independently contains it.

The conclusion must be conditional on the observation. If both can import the package, inspect their reported module paths; do not declare isolation broken without identifying the two installations.

> **Common misconception — “A virtual environment is a virtual machine.”**  
> A Python virtual environment isolates interpreter entry points and installed distributions. It does not emulate hardware, provide an operating-system kernel, or create a security boundary against hostile code.

### 4.7.1 Environment anatomy

A virtual environment ordinarily contains:

- a configuration file identifying its base installation and creation properties;
- an executable or executable link by which the environment’s Python is launched;
- shell-specific activation scripts;
- a site-packages directory for environment-installed distributions;
- package metadata recording installed projects and files.

The exact directory names differ across operating systems and implementations. Programs should use interpreter and packaging interfaces rather than construct site-packages paths from remembered strings.

The environment’s Python adjusts its import configuration so environment-installed distributions are visible. It normally still uses the base installation’s standard library. Isolation therefore means neither a complete copy nor independence from the base interpreter. If the base installation is removed, relocated, or upgraded incompatibly, the environment may cease to function.

The environment configuration file is informative but not a complete lock. It does not record every package source, build tool, native library, environment variable, or external service. Recreate the environment from project declarations and compare the result; do not treat the directory as the declaration.

### 4.7.2 Creation is parameterised

Environment creation has inputs beyond the destination path:

- the exact base interpreter;
- whether existing destination contents are admitted;
- whether package-installation tooling is bootstrapped;
- whether system site-packages are visible;
- whether executable copies or links are preferred;
- implementation- and platform-specific options.

The ordinary command

~~~text
python -m venv .venv
~~~

inherits defaults. Defaults are still parameters; they are merely implicit ones. For an introductory isolated project, system site-packages should ordinarily remain unavailable, because inherited packages reintroduce invisible global state. If a specialised scientific or managed environment intentionally exposes them, the exception belongs in the dossier.

Do not create an environment over an unrelated non-empty directory. Do not point the destination at the project root. The destination is reconstructible local state, and its removal policy must have an exact narrow target.

### 4.7.3 Activation is a reversible shell transformation

Activation scripts commonly:

1. preserve an earlier command-search path;
2. prepend the environment’s executable directory;
3. set an environment marker such as <code>VIRTUAL_ENV</code>;
4. optionally modify the prompt;
5. define a deactivation operation.

These are shell-process mutations. Opening a second terminal creates a different shell state. Running an activation script as a separate child process rather than sourcing it in a POSIX shell cannot modify the parent’s environment, which is why the dot or <code>source</code> operation matters there. PowerShell applies its own script execution semantics.

Prompt decoration is weak evidence. It can be disabled or forged, and command aliases can still interfere. Verify with the running interpreter:

~~~python
import sys

print(sys.executable)
print(sys.prefix)
print(sys.base_prefix)
print(sys.prefix != sys.base_prefix)
~~~

The final Boolean is a useful observation for ordinary CPython virtual environments, not a language-wide proof of isolation. Environment managers other than <code>venv</code> may establish different relationships.

### 4.7.4 Never infer the installer from a bare command

After activation, the command <code>pip</code> often resolves correctly, but <code>python -m pip</code> expresses the interpreter-installer relationship in one invocation. The interpreter locates its <code>pip</code> module and runs it. This form prevents a common split in which <code>python</code> selects one environment while <code>pip</code> names an executable belonging to another.

When diagnosing installation, record all three:

~~~text
python -c "import sys; print(sys.executable)"
python -m pip --version
python -m pip show PROJECT_NAME
~~~

The <code>pip --version</code> output reports both its version and an installation path. <code>show</code> reports distribution metadata, including its location when available. An import probe can then report the loaded module’s origin:

~~~python
import importlib.util

specification = importlib.util.find_spec("example_name")
print(specification)
print(None if specification is None else specification.origin)
~~~

The module <code>importlib</code> supports import machinery. This is a flagged forward use; Chapter 10 explains finders, specifications, loaders, and module origins.

### 4.7.5 Environment lifecycle

Treat a virtual environment as a cache derived from declared inputs:

1. choose and record the base interpreter;
2. create a new environment;
3. update build/install tooling only according to project policy;
4. install the project and declared dependency groups;
5. run verification;
6. discard and recreate when the declaration changes materially or the environment becomes suspect.

In-place package upgrades can leave a state that no fresh resolver would choose, particularly after removals, changed extras, or platform transitions. Periodic clean reconstruction tests the actual onboarding path.

Moving or copying an environment directory is unreliable because scripts and configuration can contain absolute paths and native artefacts can be platform-specific. If reconstruction is unexpectedly expensive, solve that with accountable package caches and documented build artefacts rather than promoting an opaque directory to source of truth.

### Worked example 4.5A — Isolation matrix

Create environments <code>.venv-a</code> and <code>.venv-b</code> from the same recorded base interpreter. For each, record:

| Probe | Base | Environment A | Environment B |
|:---|:---|:---|:---|
| <code>sys.executable</code> | observed path | observed path | observed path |
| <code>sys.prefix</code> | value | value | value |
| <code>sys.base_prefix</code> | value | value | value |
| installer location | value | value | value |
| demonstration distribution | absent/present | absent/present | absent/present |

Install the demonstration distribution only in A. Re-run every probe using absolute executable paths rather than activation. The expected pattern is presence in A and absence elsewhere, but record deviations and inspect origins. This experiment tests package visibility; it does not test security isolation, filesystem isolation, or network isolation.

> **Common misconception — “Deleting and recreating an environment loses the project.”**  
> It loses anything stored only in reconstructible environment state. Authored source, configuration, and dependency declarations belong outside it. If deletion destroys authored work, the project boundary is defective.
