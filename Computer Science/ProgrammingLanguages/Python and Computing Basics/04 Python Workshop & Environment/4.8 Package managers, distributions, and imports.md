# 4.8 Package managers, distributions, and imports

A **package manager** automates acquisition, installation, removal, and inspection of distributed software under a dependency model. `pip` is the standard Python package installer. Use it through the selected interpreter:

```text
python -m pip --version
python -m pip install PACKAGE_NAME
```

This form binds `pip` to the same interpreter named by `python`, reducing ambiguity when several installations exist. It does not make the package trustworthy or compatible; it makes interpreter selection explicit.

Three uses of “package” must be distinguished:

1. An **import package** is a Python module capable of containing submodules.
2. A **distribution package** is an installable project archive or installed metadata unit managed by packaging tools.
3. An operating-system package is an item managed by a system package manager.

A distribution named `beautifulsoup4`, for example, can provide an import package with a different name. Installation success does not imply that the distribution name is a valid import statement.

A **dependency** is an external project required for a project’s operation, build, testing, or development. A **transitive dependency** is required by another dependency rather than selected directly by the project. Every dependency expands the project’s compatibility, security, licensing, and reproducibility obligations.

### Worked example 4.6 — Inspect rather than guess

Inside the project environment:

```text
python -m pip --version
python -m pip list
python -m pip show pip
```

The first output should identify the `pip` installation associated with the environment. `list` reports installed distributions. `show` reports metadata for one distribution. These are package-manager observations; they do not enumerate Python’s standard library, whose modules are supplied with the implementation rather than installed as ordinary project distributions.

Do not install a distribution merely to obtain a name that already belongs to the standard library. A malicious or unrelated project can occupy a public package index under a tempting name. Consult the Python standard-library index and the intended project’s authoritative documentation.

### 4.8.1 Projects, releases, distributions, and artefacts

A **project** is the maintained body of software and metadata. A **release** is a project version made available under a release process. A **distribution** is an installable representation of that release. A release can publish several **distribution artefacts**, commonly a source distribution and one or more wheels.

A **source distribution**, often called an sdist, is an archive containing source and build metadata from which an installer can request a build. A **wheel** is a built-distribution format intended for installation without rebuilding the project in the target environment. A wheel may be:

- **pure Python**, containing no platform-specific native code;
- **platform-specific**, constrained by Python implementation, ABI, operating system, and processor tags.

“Built” does not necessarily mean “one native executable”. A wheel is a specified archive layout containing files and metadata. Installation usually places those files in environment locations and records what was installed.

When no compatible wheel is available, an installer may attempt to build from source. That operation can require compilers, headers, native libraries, network-independent build dependencies, and a supported build backend. Thus the same high-level install request can retrieve a wheel on one platform and execute a native build on another. Reproducibility records artefact identity, not just project name.

### 4.8.2 Indexes are catalogues, not authorities

A **package index** is a service exposing distribution metadata and artefacts for discovery and download. Public availability does not constitute endorsement, authorship verification, security review, or compatibility proof. Names can be confusingly similar; projects can change maintainers; releases can be compromised; dependency accounts can be attacked.

Before adopting a third-party dependency:

1. establish the intended project’s authoritative identity and documentation;
2. inspect ownership and release provenance where available;
3. verify the exact distribution name;
4. read supported Python and platform constraints;
5. inspect licence obligations;
6. examine dependency scope and maintenance evidence;
7. select a version under a documented update policy;
8. retain hashes or signed provenance when the workflow supports them;
9. test the resolved artefacts in isolation.

This procedure does not prove absence of malicious code. It converts an unexamined network execution path into an auditable decision.

An installer may consult more than one index or direct link source. Dependency confusion can occur when an internal project name is also resolvable from a public source and the selection policy admits the unintended artefact. Repository configuration and credentials therefore belong to the threat model. Do not place private index credentials directly in committed configuration or command transcripts.

### 4.8.3 Metadata constrains candidate selection

Distribution metadata can state:

- project name and version;
- required Python versions;
- dependencies and conditional dependencies;
- optional dependency groups, commonly called extras;
- build-system requirements;
- licence and descriptive metadata;
- entry points through which commands or plugins are exposed.

A **requirement** identifies a project plus constraints and optional conditions. Consider:

~~~text
example-lib>=2.1,<3 ; python_version >= "3.12"
~~~

This requirement admits releases at least 2.1 but below 3 only when the environment marker condition holds. The punctuation belongs to packaging requirement syntax, not to Python expressions. A requirement describes an admissible set; it does not say which candidate was selected in a particular installation.

An **extra** names an optional feature set published by a distribution:

~~~text
example-lib[plot]
~~~

It can add dependencies associated with plotting support. An extra is not necessarily a separate import package and does not remove the need to import the chosen runtime modules explicitly.

### 4.8.4 Resolution is a constraint problem

Suppose application A requires:

~~~text
alpha>=2,<4
beta>=5
~~~

and candidate <code>beta==5.3</code> requires <code>alpha>=3.5</code>. The intersection for <code>alpha</code> is:

\[
[2,4) \cap [3.5,\infty) = [3.5,4).
\]

A resolver seeks a set of concrete releases whose metadata satisfies all applicable constraints for the target environment. If another dependency requires <code>alpha<3</code>, the intersection is empty and the dependency set is inconsistent.

The practical problem is more complicated because candidate metadata can introduce further dependencies, versions can be excluded by Python or platform compatibility, artefacts can be absent, and builds can fail. A resolver’s success proves that it found a metadata-consistent candidate set under its inputs. It does not prove behavioural compatibility, security, or correctness.

Installing requirements one command at a time can produce a different result from resolving them together. The later command may upgrade or downgrade a shared dependency, or the installer may preserve an already installed version that satisfies only part of the intended combined policy. Declare the complete direct requirement set and reconstruct it in a clean environment.

### Worked example 4.6A — Solve a dependency intersection by hand

Let:

- project P require <code>gamma>=1.4,<3</code>;
- project Q require <code>gamma!=2.0,>=1.8</code>;
- Python 3.12 compatibility exclude every <code>gamma</code> release below 2.1;
- available candidates be 1.9, 2.0, 2.1, 2.4, and 3.0.

P admits 1.4 through versions below 3. Q admits versions at least 1.8 except 2.0. The Python constraint leaves 2.1, 2.4, and 3.0. Intersecting with P excludes 3.0. Therefore 2.1 and 2.4 remain. A policy such as “select the newest admissible non-yanked release” could choose 2.4, but that policy is an additional resolver rule, not a consequence of the logical constraints alone.

If only a source distribution exists for 2.4 and the target lacks a required native compiler, metadata resolution can succeed while installation fails. Candidate satisfiability and artefact installability are separate obligations.

### 4.8.5 Build isolation

Modern Python builds are mediated by a **build frontend** and a **build backend**. The frontend orchestrates the request; the backend implements project-specific build hooks declared in <code>pyproject.toml</code>. Under build isolation, the frontend creates a temporary environment for declared build requirements rather than letting the project build against arbitrary packages from the user’s development environment.

This division solves a bootstrapping problem: an installer needs to know what build machinery to provide before it can execute the project’s build. It also exposes undeclared build dependencies. A build that succeeds only because an unrelated package happens to be globally installed is not reproducible.

Build isolation is not a security sandbox. The build backend and build-time code execute with process authority sufficient to read source and create artefacts, and may have broader access depending on the environment. Building an untrusted source distribution is code execution. Prefer accountable provenance and inspect workflow boundaries.

### 4.8.6 Installation records and import origins

An installed distribution normally includes metadata with its project name, version, requirements, entry points, and file records. Python’s <code>importlib.metadata</code> module can inspect installed distribution metadata:

~~~python
from importlib.metadata import PackageNotFoundError, version

try:
    installed_version = version("text-census")
except PackageNotFoundError:
    installed_version = None

print(installed_version)
~~~

This looks up a distribution name. It does not import the project’s runtime package. Conversely:

~~~python
import text_census

print(text_census.__file__)
~~~

imports the module and observes an origin attribute when one exists. The two checks answer different questions: “Which distribution metadata is installed?” and “Which module object was loaded from where?” Namespace packages and non-filesystem loaders complicate the latter; Chapter 10 provides the full import model.

### 4.8.7 Removal and environment consistency

Removing a distribution deletes files recorded as belonging to it, subject to installer behaviour. It does not necessarily restore overwritten shared files, remove unrecorded generated state, or uninstall dependencies that became unused. Automatic removal of every transitive dependency would risk deleting a distribution still needed directly or by another project.

After experimental installs and removals, a clean rebuild is stronger evidence than a sequence of repair commands. Use environment consistency checks supplied by the package manager, but recognise their scope: metadata agreement does not exercise imports, native loading, or application behaviour.

> **Common misconception — “Installation and import are inverse operations.”**  
> An installer manages distributions and files; the import system resolves module names at runtime. One distribution can expose several import packages, several distributions can participate in one namespace, and an import can resolve from the working directory without any distribution installation.
