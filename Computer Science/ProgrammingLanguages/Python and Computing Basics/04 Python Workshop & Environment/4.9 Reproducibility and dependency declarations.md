# 4.9 Reproducibility and dependency declarations

An environment directory is normally not a portable deliverable. It can contain absolute paths, platform-specific executables, and installed binaries. Reproducibility comes from recording requirements and reconstruction steps.

`pyproject.toml` is the standard project configuration file used by modern Python packaging. A minimal distributable project may declare:

```toml
[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[project]
name = "text-census"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = []
```

TOML is a configuration language. The brackets introduce tables; quoted text represents strings; square brackets on the right delimit a list. Full packaging semantics appear in Chapter 10. Here the file establishes an explicit Python constraint and records that the first project has no third-party runtime dependencies.

A version constraint such as `>=3.12` states an admitted range but does not guarantee the project was tested against every future Python version. A **lock file** records a more exact dependency solution for reproducible application environments. The Python ecosystem has multiple tools and evolving standards for locking; the chosen tool and file must be named in the project instructions rather than replaced by a generic claim that one command works everywhere.

Reproducibility has levels:

| Level | Evidence |
|:---|:---|
| Source reproducibility | same durable source and inputs can be obtained |
| Environment reproducibility | interpreter and dependency constraints can be reconstructed |
| Build reproducibility | equivalent build inputs produce equivalent artefacts under stated conditions |
| Behavioural reproducibility | specified observations recur on admitted platforms |
| Bit-for-bit reproducibility | artefact bytes are identical, including controlled metadata |

Do not claim the strongest level when only a fresh local run has been repeated.

### 4.9.1 Direct intent and resolved state

Dependency records serve two different purposes:

- an **intent declaration** states the direct compatibility ranges the project claims to support;
- a **resolution record** states a concrete dependency solution selected for a target or family of targets.

For a reusable library, excessively narrow exact pins in published runtime requirements can make it impossible for an application to combine libraries that could otherwise coexist. The library should declare tested compatibility bounds. For an application deployment, a lock or constraints mechanism can choose exact versions and artefacts so reconstruction does not silently select a newer transitive release.

These goals are complementary rather than contradictory. The library answers “what may work under the compatibility contract?” The deployment answers “what exact set did we choose and verify here?”

### 4.9.2 Upper bounds, lower bounds, and evidence

A lower bound such as <code>>=2.0</code> claims that the project does not support earlier versions. Its justification might be a used API introduced in 2.0. An upper bound such as <code><3</code> claims that 3.0 and later are not admitted. It might reflect known incompatibility or a policy that major versions require renewed testing.

Bounds should correspond to evidence and policy:

- a lower bound copied from the newest local environment can exclude working users needlessly;
- no upper bound can admit a future incompatible release never tested;
- an exact pin can prevent security updates or compatible resolution;
- a broad range without a test matrix can overstate support.

Version numbering alone does not guarantee compatibility. Semantic Versioning is a release-policy convention adopted by some projects; Python packaging compares version identifiers but cannot prove that a release obeys semantic compatibility.

### 4.9.3 Requirements files, constraints, and project metadata

Several superficially similar files have different roles. A project’s <code>[project.dependencies]</code> metadata describes runtime requirements of the distribution. A requirements file is installer input listing what should be installed for an environment. A constraints file limits versions considered for otherwise requested requirements but does not necessarily request those projects by itself. Tool-specific lock files record a solved environment under that tool’s semantics.

Do not infer semantics solely from a filename such as <code>requirements.txt</code>. Record the consuming tool and exact command. The same textual requirement can behave differently when index configuration, pre-release policy, upgrade policy, target platform, or already-installed state changes.

A project may define dependency groups for roles such as test, documentation, linting, or development. Production runtime should not acquire every development tool merely because one undifferentiated file lists them all. Separation narrows deployed attack surface and clarifies which dependencies are necessary for which claim.

### 4.9.4 Hashes and artefact identity

A cryptographic hash maps an artefact’s byte sequence to a fixed-size digest. Under appropriate algorithms and verification, a recorded hash can detect that retrieved bytes differ from the selected bytes. It does not establish that the selected bytes were benign, correctly built, or associated with the intended author.

Hash-checked installation changes the claim from “install some artefact satisfying this name and version” towards “install one of these specifically admitted byte sequences”. Platform-specific environments may require several admitted wheel hashes. Source builds add another layer: identical source bytes do not automatically yield identical built wheels unless the build process is reproducible and its toolchain is controlled.

Never use obsolete collision-broken hash algorithms as a security identity merely because a tool displays them. Follow the package ecosystem’s current secure-hash guidance and retain the mechanism’s algorithm name with the digest.

### 4.9.5 Reproducibility matrix

“Reproducible” is incomplete without a target dimension. Construct a matrix:

| Dimension | Controlled value | Permitted variation | Verification |
|:---|:---|:---|:---|
| Source | commit or archive identity | none for the run | digest or version-control identifier |
| Python | implementation and version | declared minor/micro policy | runtime probe |
| Platform | OS, architecture, ABI | named support set | clean environment matrix |
| Direct dependencies | declared ranges | according to policy | metadata inspection |
| Resolution | lock and artefact hashes | target-specific selections | reconstruction |
| Inputs | fixture bytes and arguments | none unless parametrised | digests and transcript |
| Environment | admitted variables and locale | documented values | launch wrapper or record |
| External services | protocol and fixture state | controlled simulation or recorded version | integration test |
| Output | semantic or byte-level oracle | documented nondeterminism only | comparison |

The “permitted variation” column is important. Exact timestamp bytes cannot be reproduced if current time is intentionally part of output, but a semantic property may be reproducible: the timestamp has an admitted format and falls within the execution interval. Reproducibility does not require pretending that nondeterministic inputs do not exist; it requires specifying and controlling or abstracting them.

### 4.9.6 A reconstruction experiment

A valid reconstruction test starts outside the existing environment:

1. obtain the recorded source identity;
2. select an admitted base interpreter independently;
3. create a new empty virtual environment;
4. install from the declared sources under the recorded index and hash policy;
5. verify installed metadata and artefact origins;
6. execute tests from a CWD that does not create accidental imports;
7. run the documented user command on exact fixtures;
8. compare streams, status, and effects with the oracle;
9. record deviations without repairing the environment invisibly.

If the reconstruction requires an undeclared operating-system library, compiler, database, locale, or environment variable, that dependency belongs in the environment specification. Python package declarations cannot express every system prerequisite; documentation and deployment configuration complete the contract.

### Worked example 4.6B — Separate a range from a lock

Assume <code>text-census</code> directly uses a hypothetical library <code>line-rules</code> and has verified versions 2.1 through 2.4, with a known incompatible API planned for 3. Its project intent can state:

~~~toml
[project]
dependencies = [
    "line-rules>=2.1,<3",
]
~~~

A deployment resolution for one platform might select <code>line-rules==2.4.1</code> plus exact transitive versions and wheel hashes in a tool-specific lock. The project metadata communicates compatibility to downstream resolvers; the lock communicates the tested deployment choice. Updating 2.4.1 to 2.4.2 is then a deliberate resolution change followed by verification, not an incidental consequence of rebuilding next month.

### 4.9.7 Offline and archival reconstruction

A lock that names artefacts on a network service depends on that service retaining them and on future access policy. Long-lived research or regulated work may also archive the admitted artefacts, licences, provenance attestations, build instructions, and necessary system packages in an accountable repository. This is an **artefact mirror** or controlled wheelhouse, not a reason to copy opaque environment directories.

Offline reconstruction distinguishes two questions:

- Can the environment be recreated without discovering new candidates?
- Are all selected bytes and build prerequisites actually retained?

A dependency list alone answers neither. Archival completeness should be tested by denying external retrieval during reconstruction and observing every missing input.

> **Common misconception — “Pinning versions makes an environment reproducible.”**  
> A version can have several platform artefacts, a source build can depend on undeclared native state, and an index can change availability. Exact resolution is necessary for some reproducibility claims but not sufficient by itself.
