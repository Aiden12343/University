# 5.1 Source form and program meaning

**Syntax** is the set of forms admitted by a language. **Semantics** is the meaning assigned to admitted forms. A character sequence can fail syntactically, in which case no ordinary execution of that source construct begins; or it can be valid syntax whose evaluation later fails because the requested operation is not defined for the current state.

Consider:

```python
total = 4 + 5
```

The characters are decoded source text. Lexical rules classify `total` as an identifier, `=` as an assignment token, `4` and `5` as integer literals, and `+` as an operator. Grammar rules organise the tokens into an assignment statement whose right side is an addition expression. Semantic rules require the expression to be evaluated first and the resulting object to be bound to the name `total` in a target namespace.

Change the line to:

```python
total = 4 +
```

The parser cannot form the required complete expression, so a `SyntaxError` is reported. Change it instead to:

```python
total = 4 + "5"
```

The syntax is valid. Execution obtains an integer object and a string object, then requests addition. Their types do not supply a compatible operation for this pairing, so execution raises `TypeError`. Syntax admitted the request; semantics rejected the particular operation.

A **literal** is source syntax denoting construction or retrieval of a value, such as `42`, `3.5`, `"text"`, `[1, 2]`, or `None`. An **identifier** is a source name obeying Python’s lexical rules and not serving as a reserved keyword in that position. A **keyword** is a word reserved by the grammar, such as `if`, `for`, `def`, and `return`. A **soft keyword** has special meaning only in specified grammatical contexts; elsewhere the same text may be an identifier. Language documentation, not typography, determines the category.

Python uses indentation as part of the grammar for compound statements. A **suite** is a group of statements controlled by a clause such as `if`, `for`, `while`, `def`, or `class`. After a header ending in a colon, an indented suite marks the nested body:

```python
temperature = 18

if temperature < 20:
    message = "cool"
else:
    message = "warm"

print(message)
```

The blank lines do not create or end scope. The indentation groups assignment to `message` under the selected clause. `print(message)` is aligned with the `if` and therefore follows the whole conditional.

> **Common misconception — “Indentation is only Python style.”**  
> Consistent indentation is a style concern everywhere, but in Python the indentation structure also supplies syntax. Moving a statement across an indentation boundary can change control flow or make the program invalid.

### 5.1.1 From source bytes to executable meaning

The path from a source file to execution has conceptually distinct transformations:

1. bytes are decoded into Unicode source text;
2. physical lines are normalised and combined into logical lines;
3. lexical analysis recognises tokens such as names, numbers, delimiters, and operators;
4. parsing organises tokens according to grammar;
5. compilation constructs executable code for the implementation;
6. evaluation and statement execution act on runtime objects and namespaces.

These stages are a semantic model, not a promise that every implementation stores a separate artefact after every step. CPython, for example, constructs an abstract syntax representation and bytecode, but another implementation can realise the same language by different machinery.

A **token** is a classified source unit consumed by the parser. Whitespace can separate tokens without itself becoming an ordinary token; at logical line beginnings, indentation changes generate structural indentation tokens. Comments are discarded by ordinary parsing after their lexical role is recognised, though tools may retain them by reading source independently.

Consider:

~~~python
area = width * height  # rectangle
~~~

The significant token sequence includes the name <code>area</code>, assignment operator, names <code>width</code> and <code>height</code>, multiplication operator, and logical newline. The comment supplies no runtime multiplication operand. Renaming <code>area</code> changes a binding target. Replacing <code>*</code> with <code>+</code> changes the requested operation. Removing the right operand makes the grammar incomplete.

### 5.1.2 Names and keywords

Python identifiers are formed under Unicode-aware lexical rules. A name must not begin with a decimal digit, and its code points must satisfy identifier categories and normalisation rules. The test methods <code>str.isidentifier()</code> and the module <code>keyword</code> can help inspect a candidate:

~~~python
import keyword

for candidate in ["total", "total_2", "2total", "class", "résumé"]:
    print(
        candidate,
        candidate.isidentifier(),
        keyword.iskeyword(candidate),
    )
~~~

A string can satisfy the identifier shape while being unavailable as an ordinary name because it is a keyword. Soft keywords require context-sensitive analysis beyond <code>iskeyword</code>. A name can be lexically valid and still be a poor public identifier because it resembles another script, uses invisible code points, or violates a project’s interoperability policy.

Names are case-sensitive and Unicode-aware, but identifiers that appear visually identical can be constructed from different code points or normalisation forms. Python applies a specified normalisation in identifier processing; external tools, filenames, and user data may apply other policies. Security-sensitive source review should make confusable characters visible rather than relying on eyesight alone.

### 5.1.3 Delimiters and grouping

Parentheses, brackets, and braces can have several grammatical roles:

- grouping an expression;
- forming a call or generator expression;
- forming a list, tuple, dictionary, or set display;
- selecting an item or slice;
- defining a comprehension;
- marking parameters, annotations, or patterns in later constructs.

Punctuation acquires meaning from grammatical context. The empty parentheses in <code>function()</code> request a call with no explicit arguments; the parentheses in <code>(value)</code> merely group and do not construct a one-element tuple. A comma constructs the tuple structure:

~~~python
grouped = (42)
singleton = (42,)

print(type(grouped))
print(type(singleton))
~~~

The first object is an integer; the second is a tuple. Parentheses make the comma-containing form unambiguous and readable, but the comma is the decisive tuple syntax.

Balanced delimiters also permit implicit physical-line continuation:

~~~python
total = (
    first
    + second
    + third
)
~~~

Indentation inside the open parentheses is not a new statement suite. It communicates visual structure while the delimiters keep one logical line open.

### 5.1.4 Literal syntax and runtime objects

A literal is source notation interpreted during compilation and execution to yield an object. The spelling is not the object itself. The source characters <code>42</code> are text in a file; evaluating the integer literal produces an integer object whose value is forty-two.

Different literal spellings can denote equal values:

~~~python
decimal = 255
binary = 0b1111_1111
octal = 0o377
hexadecimal = 0xFF

print(decimal == binary == octal == hexadecimal)
~~~

All four denote the same integer value. Prefixes select a source radix, and underscores can separate digits for readability under lexical placement rules. Those underscores and prefixes do not become properties of the resulting integer. Formatting the object later requires a separate representation choice.

Adjacent string literals are concatenated during compilation:

~~~python
message = (
    "one logical "
    "string"
)
~~~

This is distinct from adding two arbitrary string-valued expressions at runtime. It is useful for source layout, but accidental missing commas between string literals in a list can silently merge intended elements:

~~~python
labels = [
    "north",
    "south"
    "east",
]
~~~

The list contains two strings, <code>"north"</code> and <code>"southeast"</code>. The syntax is valid, so only an expected-length or value oracle exposes the defect.

### 5.1.5 Parsing does not establish name existence

The parser recognises identifiers structurally without consulting the eventual runtime namespace. Therefore:

~~~python
result = width * height
~~~

can compile even if neither <code>width</code> nor <code>height</code> will be bound when execution reaches the line. Name resolution is a runtime semantic operation. If lookup fails, Python raises <code>NameError</code>; in certain local-scope situations it raises the more specific <code>UnboundLocalError</code>, introduced with scope in Chapter 8.

Conversely, a name cannot repair invalid syntax. Binding a name called <code>otherwise</code> does not allow it to replace the keyword <code>else</code> in an <code>if</code> statement. Grammar is determined before such lookup.

### Worked example 5.1A — Classify failures by stage

Examine four files:

~~~python

~~~

A file containing invalid UTF-8 can fail during source decoding. B decodes but has an unclosed delimiter and fails parsing. C can compile, but name lookup fails during execution. D resolves both literals but the requested type pairing does not define addition, so the operation fails. “Python error” loses the phase information that identifies the violated contract.

> **Common misconception — “Valid-looking source has one all-purpose validation step.”**  
> Decoding, tokenisation, parsing, name lookup, operation dispatch, and domain validation answer different questions. Passing an earlier boundary says nothing universal about later ones.
