# 5.11 Strings, Unicode, and textual value

A `str` object is an immutable sequence of Unicode code points under Python’s language model. **Unicode** is a standard assigning numbers called **code points** to textual elements. A code point is not necessarily a user-perceived character, a glyph, or one byte.

A **glyph** is a rendered visual form. A **grapheme cluster** is a sequence of code points that users may perceive as one character. Python’s ordinary `len(str)` counts code points in the string, not grapheme clusters and not encoded bytes.

```python
text = "A£🙂"
print(len(text))
print(len(text.encode("utf-8")))
```

The string contains three code points. Its UTF-8 representation uses more than three bytes because `£` and the emoji require multiple bytes. Encoding maps text to bytes; decoding maps bytes to text under a named encoding.

String literals support escape sequences. `"\n"` contains one newline code point, not a backslash followed by `n`. A raw string literal such as `r"C:\new"` suppresses most escape processing, but raw strings still follow source grammar and cannot end with an odd number of backslashes. Rawness is a literal-syntax property, not a distinct runtime string type.

Strings are immutable. Methods such as `upper`, `replace`, and `strip` return new strings; they do not modify the receiver.

### Worked example 5.8 — Trace text transformation

```python
source = "  Ada Lovelace\n"
cleaned = source.strip()
upper = cleaned.upper()

print(repr(source))
print(repr(cleaned))
print(repr(upper))
```

`repr` produces a diagnostic representation that makes surrounding spaces and newline escapes visible. `source` remains unchanged; `cleaned` lacks surrounding whitespace; `upper` contains the uppercase transformation. Unicode casing can change length and is not a universal identity normalisation. Case-insensitive comparison often calls for `casefold`, while canonical-equivalence questions require Unicode normalisation under a domain-specific policy.

> **Common misconception — “One displayed character is one string element and one byte.”**  
> Python string indexing selects code points. A perceived character can contain several code points, and each code point can require one to four UTF-8 bytes.

### 5.11.1 Source spelling and runtime text

A string literal has two interpretive layers. First, the source file is decoded. Second, literal escape syntax is interpreted. These spellings can denote the same runtime string:

~~~python
literal_character = "é"
unicode_escape = "\u00e9"
named_escape = "\N{LATIN SMALL LETTER E WITH ACUTE}"

print(literal_character == unicode_escape == named_escape)
~~~

The source bytes differ while the resulting one-code-point strings compare equal. Escape notation is useful when a character is invisible, unavailable on an input device, or needs exact review. Literal characters are often more readable for natural-language text. Adopt a source policy without confusing it with runtime value.

Quotation styles also do not survive:

~~~python
single = 'text'
double = "text"
triple = """text"""
print(single == double == triple)
~~~

All values are equal. Triple-quoted literals admit physical newlines and are used for docstrings, but indentation contained inside them becomes string content unless processed deliberately.

### 5.11.2 Escape processing and raw literals

Common escapes include newline <code>\n</code>, tab <code>\t</code>, backslash <code>\\</code>, and quotation marks. A raw literal suppresses most backslash escape interpretation:

~~~python
ordinary = "C:\\new\\test"
raw = r"C:\new\test"
print(ordinary == raw)
~~~

Raw notation is a source convenience, not a different runtime type. It does not make a string safe for regular expressions, shells, SQL, URLs, or Windows path semantics. Each consumer has its own grammar after Python has produced the string.

A raw literal cannot end with an odd number of backslashes because the final backslash would escape the source closing quote under lexical rules. Compose the value or use an ordinary escape when needed.

### 5.11.3 Indexing is by code point

For a Python <code>str</code>, indexing returns a one-code-point string:

~~~python
text = "A🙂B"
print(text[0])
print(text[1])
print(text[-1])
~~~

Negative indices count from the end. Slicing selects a code-point interval:

~~~python
print(text[1:3])
print(text[::-1])
~~~

Reversing by code point can break user-perceived grapheme clusters and can reorder combining marks away from their base characters. It is a sequence operation, not a linguistically correct reversal for every writing system.

### 5.11.4 Canonical equivalence and normalisation

Unicode can encode visually equivalent text using different code-point sequences. The character “é” may be one precomposed code point or the sequence Latin small e followed by a combining acute accent:

~~~python
import unicodedata

precomposed = "\u00e9"
decomposed = "e\u0301"

print(precomposed == decomposed)
print(len(precomposed), len(decomposed))
print(
    unicodedata.normalize("NFC", precomposed)
    == unicodedata.normalize("NFC", decomposed)
)
~~~

Ordinary string equality compares code-point sequences, so the first comparison is false. Normalisation form NFC produces canonically composed equivalents for this case.

Normalisation is not a universal preparatory step. Identifiers, cryptographic strings, filesystem paths, user-visible names, and protocol fields have different specifications. Applying compatibility normalisation can erase distinctions such as typographic forms; failing to normalise can create duplicate-looking records. State the domain policy and retain original text when auditability requires it.

### 5.11.5 Case conversion is not simple character substitution

Unicode case operations can change length:

~~~python
word = "straße"
print(word.upper())
print(word.casefold())
~~~

Uppercasing can produce <code>STRASSE</code>; case folding produces a form intended for aggressive caseless matching. Even case folding does not solve locale-specific collation, spoofing, whitespace, punctuation, or canonical equivalence automatically.

Do not use <code>lower()</code> as a universal key normaliser. For protocol identifiers, follow the protocol’s ASCII or Unicode rule. For human names, preserving spelling is usually more important than forcing equality. For natural-language sorting, use a locale-aware collation facility with a declared locale and version.

### 5.11.6 Whitespace is a set of code points and policies

Methods such as <code>strip</code>, <code>split</code>, and <code>isspace</code> apply documented Unicode-aware definitions. “Whitespace” is not necessarily the ASCII space alone. Calling <code>strip()</code> without an argument removes a class of leading and trailing whitespace; calling <code>strip("ab")</code> removes any run of the listed characters from both ends, not the exact substring <code>"ab"</code>.

~~~python
print("abbaVALUEba".strip("ab"))
~~~

The result is <code>VALUE</code>. For an exact prefix or suffix, use <code>removeprefix</code> or <code>removesuffix</code>:

~~~python
print("prefix:value".removeprefix("prefix:"))
~~~

Input cleaning is information transformation. Removing all surrounding whitespace can destroy significant data in passwords, fixed-width formats, or user-authored prose. Specify which characters and positions are ignorable.

### 5.11.7 Splitting and joining

With no explicit separator, <code>split()</code> groups runs of whitespace and discards leading and trailing runs. With an explicit separator, adjacent separators produce empty fields:

~~~python
print("  a  b ".split())
print("a,,b,".split(","))
~~~

The results are <code>["a", "b"]</code> and <code>["a", "", "b", ""]</code>. Choosing the wrong mode changes the data grammar.

Joining places one separator between an iterable of strings:

~~~python
fields = ["Ada", "", "Lovelace"]
record = ",".join(fields)
print(record)
~~~

The empty field is preserved between two commas. Joining arbitrary data by calling <code>str</code> does not create a safe CSV format because quoting, separators, embedded newlines, and dialect rules matter. Use the <code>csv</code> module in Chapter 11.

### 5.11.8 Search, prefix, and replacement contracts

The membership expression:

~~~python
"cat" in "concatenate"
~~~

tests code-point substring occurrence and returns true. It does not recognise words, grapheme boundaries, or linguistic equivalence.

<code>find</code> returns an index or -1; <code>index</code> returns an index or raises <code>ValueError</code>. Select according to whether absence is ordinary data or a violated precondition:

~~~python
position = text.find(marker)
if position == -1:
    handle_absence()
~~~

<code>replace(old, new)</code> returns a new string and, unless a count is supplied, replaces all non-overlapping occurrences under its literal substring contract. Regular-expression matching is a separate language with separate escaping and complexity hazards.

### 5.11.9 Formatting is a data boundary

Formatted string literals evaluate embedded Python expressions and apply formatting specifications:

~~~python
name = "Ada"
count = 7
message = f"{name} processed {count:04d} records"
print(message)
~~~

The integer format <code>04d</code> requests at least four decimal digits padded with zeros. Formatting produces text; it does not mutate <code>count</code>.

Do not construct source code, shell commands, SQL, HTML, or regular expressions merely by interpolating untrusted text. Each destination language requires structural parameterisation or context-specific escaping. An f-string guarantees Python string construction, not safety in the next interpreter.

Use <code>repr</code>-style conversion for diagnostics when boundaries and escapes matter:

~~~python
user_text = "first\nsecond"
print(f"received={user_text!r}")
~~~

The result exposes the embedded newline rather than allowing it to forge a second diagnostic line. For sensitive data, representation must also be redacted and bounded.

### Worked example 5.8A — Define a username normalisation function

Suppose a closed application specifies usernames as:

- Unicode text;
- surrounding Unicode whitespace ignored;
- canonical equivalence collapsed with NFC;
- case distinctions ignored through case folding;
- resulting text non-empty;
- at most 32 code points after transformation.

An implementation is:

~~~python
import unicodedata


def normalise_username(source: str) -> str:
    stripped = source.strip()
    normalised = unicodedata.normalize("NFC", stripped)
    folded = normalised.casefold()

    if not folded:
        raise ValueError("username is empty")
    if len(folded) > 32:
        raise ValueError("username exceeds 32 code points")

    return folded
~~~

Each line corresponds to a stated policy. This function is not universally correct for names: case folding may merge identifiers that another system distinguishes; code-point length differs from display width; spoofing remains possible; and storage may need the original spelling. Precision comes from binding implementation to a narrow specification.

> **Common misconception — “Unicode support means text can be compared, sliced, and displayed like ASCII with more symbols.”**  
> Unicode separates code points, grapheme clusters, normalisation, casing, collation, encoding, and rendering. Each operation needs the appropriate layer.
