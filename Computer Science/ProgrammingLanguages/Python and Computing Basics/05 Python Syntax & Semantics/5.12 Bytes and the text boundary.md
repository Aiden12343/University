# 5.12 Bytes and the text boundary

A `bytes` object is an immutable sequence of integers from 0 through 255. A `bytearray` is a mutable byte sequence. Bytes represent binary data; they do not intrinsically contain text.

```python
encoded = "café".encode("utf-8")
decoded = encoded.decode("utf-8")

print(encoded)
print(decoded)
```

The encoding operation crosses from Unicode text to a specified byte representation. Decoding with a different encoding can fail or silently produce different text. The encoding name is therefore part of the data contract.

A bytes literal such as `b"ABC"` directly admits ASCII-range literal characters and escape forms. `bytes[0]` returns the integer value of the first byte, whereas slicing returns another bytes object:

```python
data = b"ABC"
print(data[0])
print(data[:1])
```

Output:

```text
65
b'A'
```

Indexing answers “which byte value occupies this position?” Slicing answers “which byte subsequence occupies this interval?” These are intentionally different result types.

### 5.12.1 Bytes display is diagnostic notation

When Python displays:

~~~python
data = b"A\x00\xff"
print(data)
~~~

the representation <code>b'A\x00\xff'</code> is Python-oriented notation for three byte values 65, 0, and 255. It is not proof that the external data contains the literal characters backslash, <code>x</code>, and hexadecimal digits. Printable ASCII-range bytes are rendered as characters for convenience; others commonly use escapes.

Use <code>data.hex()</code> for an exact hexadecimal string:

~~~python
encoded = data.hex()
restored = bytes.fromhex(encoded)
print(encoded)
print(restored == data)
~~~

Hexadecimal doubles the raw byte count in text form but is useful in protocols and diagnostics. It is an encoding, not encryption.

### 5.12.2 Bytearray mutation

A <code>bytearray</code> permits in-place byte edits:

~~~python
buffer = bytearray(b"ABC")
buffer[1] = 120
buffer.extend(b"YZ")
print(buffer)
~~~

The result represents <code>AxCYZ</code>. An indexed assignment requires an integer from 0 through 255; slice assignment accepts a bytes-like iterable and can change length. Converting with <code>bytes(buffer)</code> creates an immutable bytes value suitable for stable sharing or hashing.

Use mutable byte buffers for incremental I/O, binary protocol construction, and in-place transformations. Do not decode and re-encode arbitrary binary data merely to edit it; not every byte sequence is valid text, and text transformations can change byte length.

### 5.12.3 Encoding and decoding are partial functions

An encoder can fail when the chosen encoding cannot represent a code point:

~~~python
text = "cost £5"
# text.encode("ascii") raises UnicodeEncodeError.
~~~

A decoder can fail when bytes are not a valid sequence:

~~~python
data = b"\xff"
# data.decode("utf-8") raises UnicodeDecodeError.
~~~

Error policies such as <code>"ignore"</code>, <code>"replace"</code>, or specialised round-trip handlers change semantics. Ignoring invalid bytes discards information and can merge distinct inputs. Replacement preserves position approximately but loses original bytes. Use strict errors by default at accountable boundaries, and select another policy only when the data contract specifies how loss is handled.

### Worked example 5.8B — Round-trip conditions

~~~python
source = "café"
encoded = source.encode("utf-8")
restored = encoded.decode("utf-8")

print(restored == source)
~~~

The round trip succeeds because the same encoding is used and every source code point is representable. In general, for an admitted text (t) and lossless encoding (E),

\[
\operatorname{decode}_E(\operatorname{encode}_E(t)) = t.
\]

The reverse direction for arbitrary bytes is defined only for byte sequences valid under the decoder, and Unicode normalisation or lossy error handlers can alter stronger byte-preservation claims.

### 5.12.4 Byte order

Multi-byte numeric fields require an order. **Big-endian** representation places the most significant byte first; **little-endian** places the least significant byte first.

~~~python
value = 0x1234

big = value.to_bytes(2, byteorder="big")
little = value.to_bytes(2, byteorder="little")

print(big.hex())
print(little.hex())
print(int.from_bytes(big, byteorder="big"))
~~~

The two hex strings are <code>1234</code> and <code>3412</code>. Decoding with the wrong byte order produces a different integer without necessarily raising. Width, signedness, and byte order are inseparable parts of a binary-field contract.

### 5.12.5 Binary structure and the struct module

The <code>struct</code> module packs and unpacks fixed-layout binary records under a format string:

~~~python
import struct

packet = struct.pack(">HI", 7, 1_000)
kind, length = struct.unpack(">HI", packet)

print(packet.hex())
print(kind, length)
~~~

The leading <code>&gt;</code> requests big-endian standard sizes; <code>H</code> requests an unsigned two-byte integer and <code>I</code> an unsigned four-byte integer. The resulting packet has six bytes. Range violations or wrong packet length raise errors rather than inventing missing data.

Binary parsers must validate lengths before allocation and interpretation. A length field from untrusted input is a claim, not permission to allocate that many bytes. Chapter 11 develops streamed I/O and serialisation safety.

### 5.12.6 Memoryview and the buffer protocol

Copying a large byte sequence merely to inspect a subrange can be expensive. A <code>memoryview</code> exposes the **buffer protocol**, permitting byte-oriented or typed access to another object’s memory without necessarily copying:

~~~python
payload = bytearray(b"header:body")
view = memoryview(payload)
body = view[7:]

body[0] = ord("B")
print(payload)
~~~

The view and slice refer to the original mutable buffer; changing the first body byte changes <code>payload</code>. This is deliberate shared-memory aliasing. The exporter can restrict resizing while views exist because moving the underlying memory would invalidate them.

Release long-lived views when their purpose ends. Zero-copy interfaces reduce allocation but increase lifetime and mutation coupling.

### 5.12.7 Text mode is a transformation layer

Opening a file in text mode commonly composes:

- a byte-oriented operating-system stream;
- buffering;
- a decoder or encoder;
- newline translation;
- a text interface returning or accepting <code>str</code>.

Binary mode exposes bytes and suppresses text decoding. Therefore a text position or character count does not necessarily equal a byte offset. Seeking by arbitrary text-character indices is not generally valid for variable-width encodings.

Choose text mode when the file format defines text with a known encoding and newline policy. Choose binary mode for compressed data, images, cryptographic material, executable formats, and any protocol defined in bytes. File APIs are developed in Chapter 11.

### 5.12.8 Boundary-first design

Decode bytes once at an input boundary, operate on text internally, and encode once at an output boundary when the domain is textual. Carrying a mixture of <code>str</code> and <code>bytes</code> deep into application logic forces every operation to guess the layer.

For a network protocol whose headers are ASCII-compatible bytes and body is UTF-8 text:

1. parse byte delimiters and declared lengths at the protocol layer;
2. validate the declared text encoding;
3. decode the body strictly;
4. apply Unicode-domain logic;
5. encode under the response protocol.

Never call <code>str(byte_value)</code> as a decoding substitute. It produces a diagnostic representation such as <code>"b'ABC'"</code>, not the decoded text <code>"ABC"</code>.

> **Common misconception — “Bytes are strings before Unicode.”**  
> Bytes are numeric octets. Text arises only through an encoding contract; binary formats may have no textual interpretation at all.
