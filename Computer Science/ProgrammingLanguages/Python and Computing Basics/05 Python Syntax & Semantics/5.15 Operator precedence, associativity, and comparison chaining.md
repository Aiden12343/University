# 5.15 Operator precedence, associativity, and comparison chaining

**Precedence** determines grouping among different operator classes when parentheses do not. **Associativity** determines grouping among operators of equal precedence where the grammar permits a chain. These rules do not generally determine operand evaluation direction.

Exponentiation groups rightward:

```python
print(2**3**2)      # 2 ** (3 ** 2) = 512
print((2**3)**2)    # 64
```

Most arithmetic binary operators group leftward:

```python
print(20 - 5 - 3)      # (20 - 5) - 3 = 12
print(20 - (5 - 3))    # 18
```

Comparisons can be chained:

```python
lower < value <= upper
```

This means both `lower < value` and `value <= upper`, with `value` evaluated once under the language’s chaining semantics. It is not grouped as `(lower < value) <= upper`, which would compare a Boolean result against `upper`.

Use parentheses to expose intended grouping when a reader would otherwise consult a precedence table. Parentheses are semantic punctuation, not an admission of ignorance.

### 5.15.1 Precedence is a grammar of grouping

An expression containing several operators must be parsed into a tree. **Operator precedence** determines which operator occupies which position in that tree when punctuation does not state grouping explicitly. It does not instruct the processor to “do the highest-precedence operation first” as a free-standing scheduling rule.

For:

~~~python
result = left() + middle() * right()
~~~

the expression tree is equivalent in grouping to:

~~~python
result = left() + (middle() * right())
~~~

Yet evaluation begins by evaluating the left operand of the outer addition, so <code>left()</code> is called before <code>middle()</code>. Precedence determines that the multiplication result becomes the right operand of addition; Python’s evaluation-order rules determine when operand expressions are evaluated.

This distinction becomes essential whenever an operand can print, mutate, raise, consume input, or otherwise affect state. A memorised slogan about multiplication happening “first” predicts the wrong trace.

### 5.15.2 A useful precedence ladder

From tighter binding towards looser binding, the principal expression families are:

1. displays and parenthesised forms;
2. attribute access, subscription, slicing, and calls;
3. <code>await</code> expressions in asynchronous functions;
4. exponentiation;
5. unary plus, unary minus, and bitwise complement;
6. multiplication, matrix multiplication, division, floor division, and modulo;
7. addition and subtraction;
8. shifts;
9. bitwise AND, then XOR, then OR;
10. comparisons, membership tests, and identity tests;
11. Boolean <code>not</code>;
12. Boolean <code>and</code>;
13. Boolean <code>or</code>;
14. conditional expressions;
15. lambda expressions;
16. assignment expressions, subject to their grammatical restrictions.

This is a reading aid, not a substitute for the normative language grammar. Constructs such as <code>yield</code> have context-specific grammar, and delimiters can make a form unambiguous without participating as an ordinary operator.

Parenthesise when the intended grouping is not immediately apparent:

~~~python
mask = (flags & REQUIRED) == REQUIRED
eligible = admitted and (score >= threshold)
~~~

The first parentheses make clear that the bitwise result is compared. In the second, the parentheses are redundant under the grammar but can expose the predicate as a unit. Redundant punctuation becomes harmful only when it obscures rather than reveals structure.

### 5.15.3 Exponentiation and unary negation are asymmetric

Exponentiation binds less tightly than a unary operator on its right, but more tightly than a unary operator on its left. Therefore:

~~~python
print(-2**2)
print((-2) ** 2)
print(2**-2)
~~~

The first is grouped as <code>-(2 ** 2)</code> and produces -4. The second explicitly uses negative two as the base and produces 4. The third is admitted as <code>2 ** (-2)</code> and produces 0.25.

Mathematical notation also conventionally interprets (-2^2) as (-(2^2)), but source code must be judged by the programming-language grammar rather than typographic expectation. Parentheses should state a negative base explicitly.

Exponentiation groups to the right:

~~~python
print(2 ** 3 ** 2)
~~~

This means <code>2 ** (3 ** 2)</code>, producing 512, not <code>(2 ** 3) ** 2</code>, which produces 64. Right-associative grouping does not reverse the general left-to-right evaluation of operand expressions.

### 5.15.4 Comparison chains are a distinct construct

The expression:

~~~python
lower < value <= upper
~~~

is semantically related to:

~~~python
lower < value and value <= upper
~~~

but the middle expression in the chain is evaluated only once. The chain is not grouped as:

~~~python
(lower < value) <= upper
~~~

That mistaken grouping would compare a Boolean with <code>upper</code> and lose the original middle value.

### Worked example 5.10B — Observe one middle evaluation

~~~python
def observe(label: str, value: int) -> int:
    print(label)
    return value


result = observe("lower", 1) < observe("middle", 5) < observe("upper", 9)
print(result)
~~~

The three calls occur once each from left to right. If the first comparison is false, Python does not evaluate the remaining comparison operands needed only by the abandoned suffix:

~~~python
result = observe("lower", 10) < observe("middle", 5) < observe("upper", 9)
~~~

This calls <code>lower</code> and <code>middle</code>; it does not call <code>upper</code>. A comparison chain therefore combines single evaluation of shared operands with short-circuit selection.

Chains need not all use the same comparison operator:

~~~python
if start <= position < end:
    ...
~~~

This expresses a half-open interval. A chain such as <code>a == b is c</code> is grammatically admitted but can be semantically obscure; write separate named propositions when relations have different conceptual roles.

### 5.15.5 Membership and identity are comparisons

The operations <code>in</code>, <code>not in</code>, <code>is</code>, and <code>is not</code> occupy the comparison level. Thus:

~~~python
candidate in admitted and candidate is not None
~~~

groups as two comparisons joined by Boolean <code>and</code>. The order is inefficient or invalid if <code>admitted</code> cannot handle <code>None</code> and the candidate might be absent. State the guard first:

~~~python
candidate is not None and candidate in admitted
~~~

The phrase <code>not in</code> is one comparison operator, as is <code>is not</code>. It should not be mentally parsed as applying Boolean <code>not</code> to an already completed expression.

### 5.15.6 Boolean precedence does not remove truth protocols

Boolean <code>not</code> binds more tightly than <code>and</code>, which binds more tightly than <code>or</code>:

~~~python
not first or second and third
~~~

groups as:

~~~python
(not first) or (second and third)
~~~

The <code>not</code> operation returns a Boolean. The <code>and</code> and <code>or</code> operations return selected operands. As a result, the overall expression can return <code>True</code>, <code>False</code>, <code>second</code>, or <code>third</code>-derived objects depending on the path. Grouping alone does not imply a Boolean result type.

For predicates intended to return <code>bool</code>, make the final proposition explicit or convert deliberately. Do not use <code>bool</code> merely to conceal a poorly specified multi-type result.

### 5.15.7 Conditional expressions are lazy and right-associative

A conditional expression has the form:

~~~python
result_when_true if condition else result_when_false
~~~

Python evaluates the condition first and exactly one result expression:

~~~python
label = "even" if number % 2 == 0 else "odd"
~~~

This is value-producing expression syntax, distinct from the statement form:

~~~python
if number % 2 == 0:
    label = "even"
else:
    label = "odd"
~~~

The expression is suitable when both branches produce one conceptually parallel value. Use a statement when branches require several effects, explanations, or distinct control paths.

Conditional expressions group from right to left:

~~~python
result = a if first else b if second else c
~~~

This means:

~~~python
result = a if first else (b if second else c)
~~~

Nested conditional expressions become difficult to scan rapidly. Parentheses or a statement should expose intended nesting.

### 5.15.8 Assignment-expression precedence

The assignment expression has deliberately low precedence and additional parenthesisation requirements. Consider:

~~~python
if (length := len(values)) > 10:
    print(length)
~~~

The parentheses state that the result of <code>len(values)</code> is bound to <code>length</code>, after which the value is compared with 10. Without a careful reading, one might intend to bind the Boolean comparison result instead.

This distinction can be demonstrated outside a restricted condition context:

~~~python
comparison = (length := len(values)) > 10
~~~

After execution, <code>length</code> is an integer and <code>comparison</code> is a Boolean. A different parenthesisation:

~~~python
comparison = (is_long := len(values) > 10)
~~~

binds the Boolean to <code>is_long</code>. Both can be valid; naming and punctuation must reveal which value is retained.

### 5.15.9 Parse-tree inspection

The standard-library module <code>ast</code> exposes an abstract syntax tree for valid source. This is a flagged forward tool: Chapter 15 explains the compilation pipeline, while the present use only inspects grouping.

~~~python
import ast

tree = ast.parse(
    "result = left + middle * right",
    mode="exec",
)
print(ast.dump(tree, indent=2))
~~~

The tree places multiplication inside the right operand of addition. Change the source to <code>(left + middle) * right</code> and compare the structure. An AST omits some surface punctuation because it records abstract grammatical meaning rather than reproducing source typography exactly.

Do not use <code>ast.parse</code> as permission to execute untrusted source. Parsing can establish grammatical form, and tree analysis can impose a restricted policy, but safe evaluation requires a threat model and far more than deleting one node type.

### 5.15.10 Parentheses as executable documentation

Good parentheses:

- disambiguate a negative exponentiation base;
- expose bit-mask grouping;
- make a compound predicate’s conceptual units visible;
- show which value an assignment expression retains;
- delimit a multi-line expression;
- prevent a future local edit from changing adjacent grouping accidentally.

Bad parentheses can conceal a tuple comma, create visual noise around every atom, or suggest a call where none occurs. The criterion is not minimum punctuation. It is minimum interpretive uncertainty under the exact grammar.

> **Common misconception — “Precedence tells Python which operation runs first.”**  
> Precedence determines the expression tree. Evaluation-order, short-circuit, call, and protocol rules determine the temporal execution trace.
