# 5.16 Calls, argument evaluation, and side effects

A **callable** is an object that supports the call operation. A **function call** expression evaluates the callable expression, evaluates argument expressions in order, binds arguments to parameters according to the callable’s signature, then transfers control to the callable.

A **side effect** is an observable state change beyond producing the expression’s value: mutating an object, rebinding non-local state, writing a file, displaying output, sending a network request, or consuming input. The term does not imply harm. It distinguishes state interaction from value production.

### Worked example 5.11 — Argument expressions run before the body

```python
def mark(label: str) -> str:
    print("evaluate", label)
    return label


def combine(left: str, right: str) -> str:
    print("enter combine")
    return left + right


print(combine(mark("A"), mark("B")))
```

Output:

```text
evaluate A
evaluate B
enter combine
AB
```

The callable `combine` is evaluated, then the two argument expressions execute from left to right, then the function body begins with its parameters bound. A failure in `mark("A")` would prevent evaluation of the later argument and prevent entry into `combine`.

Function mechanics and scope are developed in Chapter 8. The present rule is sufficient to trace expressions without treating calls as timeless substitutions.

### 5.16.1 The callable expression is evaluated first

In:

~~~python
provider().operation(argument())
~~~

Python must first evaluate <code>provider()</code>, then obtain its <code>operation</code> attribute, then evaluate the argument expression, and finally invoke the resulting callable. Attribute retrieval itself can execute user-defined descriptor code. A failure at any earlier step prevents later steps.

### Worked example 5.11A — Trace callable acquisition

~~~python
class Service:
    def execute(self, value: int) -> int:
        print("inside execute")
        return value * 2


def make_service() -> Service:
    print("make service")
    return Service()


def make_argument() -> int:
    print("make argument")
    return 21


result = make_service().execute(make_argument())
print(result)
~~~

The output order is:

~~~text
make service
make argument
inside execute
42
~~~

The method model is formally derived in Chapter 9. Minimally, retrieving <code>execute</code> from the instance yields a callable associated with that instance. The trace separates receiver creation, attribute retrieval, argument creation, body execution, and returned value.

### 5.16.2 Argument expressions are evaluated before parameter binding completes

**Arguments** are the expressions and values supplied by the caller. **Parameters** are the names and rules declared by the callable. The call:

~~~python
result = transform(source(), scale=read_scale())
~~~

evaluates <code>source()</code> and <code>read_scale()</code> before the body of <code>transform</code> begins. It then binds the produced values to parameters according to the signature.

The values are not copied by a universal call mechanism. Parameter names become new bindings to the supplied objects. If a mutable argument is changed through the parameter, the caller can observe that same object. If the parameter is rebound, the caller’s name is unaffected.

### 5.16.3 Positional and keyword association

A **positional argument** is associated according to position. A **keyword argument** explicitly names a parameter:

~~~python
def power(base: int, exponent: int) -> int:
    return base**exponent


print(power(2, 5))
print(power(base=2, exponent=5))
print(power(2, exponent=5))
~~~

All three calls produce 32. Once an ordinary keyword argument has appeared, a later ordinary positional argument is not admitted:

~~~python
# power(base=2, 5) is invalid syntax.
~~~

A parameter already filled positionally cannot be supplied again by keyword:

~~~python
# power(2, base=3) raises TypeError.
~~~

Signature binding rejects the duplicate rather than guessing which value should win.

### 5.16.4 Positional-only and keyword-only parameters

A slash in a function signature marks parameters before it as positional-only. An asterisk can mark following parameters as keyword-only:

~~~python
def convert(
    source: str,
    /,
    encoding: str,
    *,
    errors: str = "strict",
) -> bytes:
    return source.encode(encoding, errors)
~~~

Admitted calls include:

~~~python
convert("café", "utf-8")
convert("café", encoding="utf-8")
convert("café", "utf-8", errors="strict")
~~~

The caller cannot supply <code>source=</code>, and <code>errors</code> cannot be supplied as an ordinary third positional argument.

Positional-only parameters permit implementation names to change without breaking callers and allow a keyword mapping to contain the same textual key for a variadic interface. Keyword-only parameters make policy arguments visible at call sites and prevent accidental swapping of several Booleans or similar values.

### 5.16.5 Starred positional expansion

Within a call, a single-starred argument expands an iterable into positional argument values:

~~~python
coordinates = (3, 4)
distance = hypot(*coordinates)
~~~

This is conceptually a call with two positional arguments, not one tuple argument. The callable must be bound before expansion, and the iterable is consumed as part of preparing the call.

Multiple starred segments are admitted:

~~~python
values = [1, 2]
more = (3, 4)
result = combine(0, *values, *more, 5)
~~~

Argument order follows the constructed positional sequence. Expansion can raise if an operand is not iterable or if the resulting count violates the signature. A one-pass generator is consumed by the call and cannot be assumed reusable.

### 5.16.6 Double-starred keyword expansion

A double-starred argument expands a mapping into keyword arguments:

~~~python
options = {
    "encoding": "utf-8",
    "errors": "strict",
}

encoded = convert("café", **options)
~~~

Keys must be strings for ordinary Python calls. Duplicate names across explicit and expanded keyword sources raise <code>TypeError</code>; unlike a dictionary display, later call values do not silently replace an earlier argument:

~~~python
# convert("café", encoding="utf-8", **{"encoding": "ascii"})
~~~

This rejection protects the one-value-per-parameter binding contract.

### 5.16.7 Expansion order and partial effects

Argument expressions and expansions occur in source evaluation order under the call semantics, but all can perform effects before signature binding reports an eventual duplicate or arity error.

~~~python
def observe(label: str, value: object) -> object:
    print(label)
    return value


def target(first: object) -> None:
    print("body")


target(
    observe("positional", 1),
    first=observe("keyword", 2),
)
~~~

Both <code>observe</code> calls can execute before the duplicate binding is rejected; <code>target</code>’s body does not begin. A call that fails to bind is not necessarily effect-free.

Validate and construct complex argument collections before initiating irreversible external actions. Function-call syntax is not a transaction.

### 5.16.8 Default values belong to the function object

Default argument expressions are evaluated when the <code>def</code> statement executes, not each time the resulting function is called. The resulting objects are retained by the function object.

~~~python
def append_record(
    record: str,
    records: list[str] = [],
) -> list[str]:
    records.append(record)
    return records


print(append_record("A"))
print(append_record("B"))
~~~

The second result ordinarily contains both A and B because both omitted-argument calls use the same default list. This is not a random cache; it follows the definition-time evaluation rule.

Use <code>None</code> or a private sentinel when each call needs new state:

~~~python
def append_record(
    record: str,
    records: list[str] | None = None,
) -> list[str]:
    actual_records = [] if records is None else records
    actual_records.append(record)
    return actual_records
~~~

If an explicit <code>None</code> is a legitimate distinct argument, use a unique sentinel instead. Chapter 8 develops defaults, signatures, and annotations completely.

### 5.16.9 Intentional shared defaults

The rule is not “mutable defaults are forbidden”. A retained mutable default can deliberately provide shared state:

~~~python
def allocate_identifier(
    counters: dict[str, int] = {},
) -> int:
    previous = counters.get("next", 0)
    counters["next"] = previous + 1
    return previous
~~~

This is still usually a poor interface: state is hidden in function metadata, difficult to reset, and unsafe under concurrent access. A named object or class makes ownership explicit. Nevertheless, the semantics are lawful. The misconception lies in accidental rather than intentional persistence.

### 5.16.10 Return, exception, and non-returning calls

A successful ordinary call can:

- execute an explicit <code>return expression</code>;
- reach the function body’s end and return <code>None</code>;
- suspend if it belongs to a generator or coroutine protocol;
- never terminate;
- terminate the process;
- raise an exception instead of producing an ordinary result.

The expression surrounding a call receives a value only on an ordinary returning path. In:

~~~python
result = first() + second()
~~~

if <code>first()</code> raises, <code>second()</code> is not called and <code>result</code> is not rebound by this statement. A pre-existing <code>result</code> binding remains unless other effects changed it.

### 5.16.11 Call depth and the call stack

Ordinary function invocation creates an execution frame and nests control until return or exception unwinding. Repeated nested calls consume finite interpreter and native resources. Python deliberately limits recursion depth to avoid uncontrolled exhaustion; it does not promise tail-call elimination.

A call expression that appears visually small can therefore initiate an arbitrarily deep computation:

~~~python
result = solve(problem)
~~~

Complexity belongs to the callable’s contract and input size, not to source-line length. Chapter 8 derives frames, recursion, closures, and the call stack; Chapter 13 analyses resource growth.

### 5.16.12 Pure and impure call interfaces

A **pure function**, under a practical programming definition, returns results determined only by explicit inputs and produces no observable external effects. Pure calls are easier to reorder, cache, test, and reason about. Python does not enforce purity.

~~~python
def rectangle_area(width: int, height: int) -> int:
    return width * height
~~~

By contrast:

~~~python
def read_rectangle_area() -> int:
    width = int(input("width: "))
    height = int(input("height: "))
    print("measured")
    return width * height
~~~

depends on input streams and emits output. Separating interaction from calculation creates a pure core:

~~~python
def rectangle_area(width: int, height: int) -> int:
    return width * height


def main() -> None:
    width = int(input("width: "))
    height = int(input("height: "))
    print(rectangle_area(width, height))
~~~

Purity is not moral superiority; interaction is necessary. It is a localisation strategy for effects.

> **Common misconception — “Python passes mutable objects by reference and immutable objects by value.”**  
> Calls bind parameters to argument objects under one mechanism. Observable differences arise because some objects support mutation and others do not; parameter rebinding remains local in either case.
