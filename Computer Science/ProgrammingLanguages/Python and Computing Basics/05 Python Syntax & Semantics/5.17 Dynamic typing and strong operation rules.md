# 5.17 Dynamic typing and strong operation rules

Python is **dynamically typed**: type information belongs to runtime objects, and ordinary name bindings do not impose a permanently fixed runtime type. Python is also commonly described as **strongly typed**, an informal term meaning that operations generally do not silently reinterpret unrelated values merely to proceed. The term has no single formal definition across language theory, so precise claims should name the actual conversion or rejection rule.

```python
print(3 + 4.5)       # int and float participate in a defined numeric conversion
# print(3 + "4")     # TypeError: no implicit number/text addition
```

The first operation converts within Python’s numeric interoperability rules. The second refuses to guess whether the intent was numeric conversion, textual formatting, or an error. Explicit conversion states the boundary:

```python
numeric = 3 + int("4")
textual = str(3) + "4"
print(numeric, textual)
```

Output:

```text
7 34
```

Type annotations do not change this fundamental runtime model. They publish intended relationships for people and tools; enforcement requires static analysis, runtime validation code, or a framework with such behaviour. Chapter 12 develops this distinction.

### 5.17.1 Dynamic typing locates checks at runtime

In Python, evaluating an operation obtains actual runtime objects and asks whether their types support the operation. The source can therefore be compiled without proving every future operand pairing.

~~~python
def combine(left, right):
    return left + right
~~~

This function can add integers, concatenate strings, concatenate lists, or invoke a user-defined addition protocol:

~~~python
print(combine(2, 3))
print(combine("py", "thon"))
print(combine([1], [2]))
~~~

The call <code>combine(2, "3")</code> reaches the same body but fails because the runtime types do not define the requested pairing. Dynamic typing enables one definition to operate polymorphically while moving some incompatibility detection to executed paths.

### 5.17.2 Dynamic does not mean untyped

Every Python object has a type. Dynamic typing means that ordinary execution tracks those types at runtime and that a name can be rebound to objects of different types. It does not mean values are typeless or that every operation is admitted.

~~~python
quantity = 3
print(type(quantity))

quantity = "three"
print(type(quantity))
~~~

The binding changed; neither object changed type. Type errors occur when an executed operation cannot satisfy its runtime protocol, not when a name is rebound merely because an earlier object had another type.

### 5.17.3 Implicit conversion is local and specified

Python defines selected implicit conversions. Mixed built-in numeric arithmetic can widen to a common numeric type:

~~~python
result = 3 + 0.5
print(result)
print(type(result))
~~~

The integer participates in floating arithmetic and the result is a float. This does not establish a general “automatic conversion” principle:

~~~python
# 3 + "0.5" raises TypeError.
~~~

The language refuses to guess whether the desired outcome is numeric 3.5, textual <code>"30.5"</code>, or rejection. Explicitly parse or format at the boundary.

Implicit truth testing is another protocol, but it does not convert the retained operands of <code>and</code> and <code>or</code> into Boolean objects. Every conversion rule must be named precisely.

### 5.17.4 Construction, parsing, and coercion are distinct intentions

The expression <code>int(value)</code> can perform several roles depending on type:

- return an integer unchanged;
- convert a compatible numeric value under a defined truncation rule;
- parse a textual integer representation;
- invoke a user-defined integer-conversion protocol.

These meanings have different failure and information-loss properties:

~~~python
print(int(3))
print(int(3.9))
print(int("-17"))
~~~

The float conversion truncates towards zero; it does not round to nearest. Parsing text applies an integer grammar. A function parameter accepting all such sources has a wider contract than one accepting an already validated integer.

Prefer boundary-specific names:

~~~python
def parse_count(text: str) -> int:
    count = int(text)
    if count < 0:
        raise ValueError("count must be non-negative")
    return count
~~~

The function first parses representation and then validates domain. <code>int</code> alone proves neither non-negativity nor suitability as a count.

### 5.17.5 Nominal and structural compatibility

**Nominal typing** relates values through explicitly named classes and inheritance. **Structural typing** relates them through supported operations regardless of declared ancestry.

At runtime, <code>isinstance(value, SomeClass)</code> ordinarily asks a nominal question, although metaclasses and registered abstract base classes can customise it. “Can this object be iterated to produce text?” is a structural question.

Python programming often follows **duck typing**: use an object according to the operations required, and reject it when the protocol cannot be satisfied. The name comes from identifying something by behaviour rather than pedigree.

Duck typing does not mean “call arbitrary methods and hope”. A protocol has obligations:

- required operations;
- accepted argument and result meanings;
- state transitions;
- exception behaviour;
- complexity or lifetime requirements where relevant.

A class with a method of the right spelling but incompatible semantics does not satisfy the protocol in any useful engineering sense.

### 5.17.6 Conversion can destroy distinctions

Converting early can merge inputs that the domain needs to distinguish:

~~~python
print(bool(0))
print(bool(None))
print(bool(""))
~~~

All produce false. Converting text to float can merge decimal spellings and lose exact digits. Converting a datetime to an unqualified string can lose timezone or precision. Converting a list to a set loses multiplicity and order.

Apply the principle:

> Preserve distinctions until the specification authorises their collapse.

Normalisation is correct only when the collapsed values are equivalent for the intended operation.

### 5.17.7 Runtime validation is not static analysis

Runtime validation examines actual values on executed paths:

~~~python
def withdraw(balance: int, amount: int) -> int:
    if amount < 0:
        raise ValueError("amount must be non-negative")
    if amount > balance:
        raise ValueError("insufficient balance")
    return balance - amount
~~~

Static analysis examines source-level type claims without executing every path. A type checker can flag a call supplying text where an integer is expected, but it ordinarily cannot infer from <code>int</code> alone that <code>amount</code> is non-negative or no greater than <code>balance</code>. Runtime domain checks remain necessary.

Type annotations create a **gradually typed** development mode: code can carry partial static type information while Python execution remains dynamic. Chapter 12 develops annotations, type variables, protocols, narrowing, and checker limitations.

### 5.17.8 Type narrowing

After a runtime test, subsequent code can operate under a narrower set of possibilities:

~~~python
def render(value: int | None) -> str:
    if value is None:
        return "missing"
    return f"{value:,}"
~~~

The second return is reached only when <code>value</code> is not <code>None</code>. A static type checker can use this control-flow fact to narrow <code>int | None</code> to <code>int</code>.

Narrowing must follow a reliable predicate. A truth test would also exclude zero and would not express the intended type relation:

~~~python
if value:
    ...
~~~

This branch narrows by truthiness, not merely by non-<code>None</code> type.

### 5.17.9 Boolean is an integer subclass

Nominal relationships sometimes admit values a domain wishes to reject:

~~~python
print(isinstance(True, int))
~~~

The result is true. An interface accepting a physical count may nevertheless reject Boolean inputs:

~~~python
def require_count(value: object) -> int:
    if isinstance(value, bool) or not isinstance(value, int):
        raise TypeError("count must be an integer, not Boolean")
    if value < 0:
        raise ValueError("count must be non-negative")
    return value
~~~

The first condition handles the more specific subclass before the general integer class. Whether this rejection is appropriate depends on the API: summing predicates intentionally uses Boolean arithmetic, while reading inventory quantity ordinarily should not interpret <code>True</code> as one item.

### 5.17.10 Exact type checks are restrictive

The test:

~~~python
type(value) is int
~~~

accepts exactly the built-in integer type and rejects subclasses. This can be appropriate at low-level serialisation boundaries requiring exact representation, but it defeats polymorphism when subclasses preserve the intended interface.

Prefer:

~~~python
isinstance(value, int)
~~~

for nominal subtype admission, or validate the actual protocol and domain. Neither test alone proves that a very large integer satisfies a database field’s fixed range.

### Worked example 5.11B — A layered quantity boundary

Suppose command input supplies a quantity as text, the domain requires a non-negative integer no larger than one million, and Boolean values are irrelevant because the source is text:

~~~python
MAXIMUM_QUANTITY = 1_000_000


def parse_quantity(source: str) -> int:
    try:
        value = int(source, 10)
    except ValueError as error:
        raise ValueError("quantity must be decimal integer text") from error

    if not 0 <= value <= MAXIMUM_QUANTITY:
        raise ValueError(
            f"quantity must be between 0 and {MAXIMUM_QUANTITY}"
        )

    return value
~~~

The interface separates:

1. source type: already decoded text;
2. lexical representation: decimal integer grammar;
3. mathematical domain: closed interval;
4. returned runtime type: integer;
5. failure category: invalid value with preserved cause.

No phrase such as “strong typing” can replace these explicit obligations.

### 5.17.11 Why “strongly typed” needs qualification

Language comparisons use “strong” and “weak” typing inconsistently. Possible dimensions include:

- whether unrelated types are implicitly coerced;
- whether memory can be reinterpreted without checks;
- whether operations preserve abstraction boundaries;
- whether type errors are detected statically or dynamically;
- whether programmers can bypass the type system.

Python strongly rejects many unrelated operations while permitting extensive protocol customisation, implicit numeric conversion, truth conversion, and explicit reflective access. A rigorous explanation states the exact rule instead of treating “strongly typed” as a binary scientific classification.

> **Common misconception — “Dynamic typing postpones all errors until production.”**  
> It locates many checks on executed operations. Tests, static analysis, contracts, controlled inputs, and design can expose them earlier; unexecuted paths remain a verification obligation.
