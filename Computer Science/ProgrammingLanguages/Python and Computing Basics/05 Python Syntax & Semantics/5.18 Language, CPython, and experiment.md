# 5.18 Language, CPython, and experiment

Claims about Python must be assigned to their owner.

| Claim | Classification |
|:---|:---|
| Assignment binds after evaluating the right side | Python language semantics |
| `is` tests object identity | Python language semantics |
| Lists are mutable and strings immutable | Python language/data-model contract |
| Ordinary CPython objects have reference-count-related headers | CPython implementation detail |
| A selected small integer literal shares identity in one session | experiment, possibly explained by CPython reuse |
| `sys.getsizeof` reports a particular number | implementation- and build-specific experiment |
| A `float` operation produces one observed last digit | language numeric behaviour constrained by platform representation and one experiment |

The classification protects portability and explanation. A CPython experiment can be valuable without being promoted into a language law. A language guarantee can be used without knowing the object’s byte layout.

### 5.18.1 Four levels of claim

Every technical assertion in this work belongs to at least one level:

1. **Language claim:** required by the Python language reference or language-level specification.
2. **Implementation claim:** documented or evidenced behaviour of CPython or another named implementation and version.
3. **Environment claim:** a fact supplied by the operating system, build, locale, filesystem, or launch context.
4. **Experimental observation:** a result obtained under recorded conditions.

Consider:

~~~python
first = 256
second = 256
print(first is second)
~~~

The language claim is that <code>is</code> tests identity. The observed result may be true in a particular compiled code unit because CPython reused one constant object. It does not follow that every equal integer 256 is identical or that another construction path must reuse it.

### 5.18.2 Normative and descriptive sources

A **normative source** defines obligations for conforming systems. A **descriptive source** explains, records, or teaches behaviour without necessarily defining the contract.

For Python:

- the language reference is primary for syntax and execution semantics;
- the library reference defines standard-library interfaces;
- Python Enhancement Proposals document design decisions and selected specifications, but status and scope matter;
- CPython documentation and source define or evidence implementation behaviour;
- a textbook supplies models, derivations, and pedagogy;
- an experiment supplies observations for one recorded configuration.

When sources disagree, first ask whether they address the same Python version, implementation, domain, and claim type. An implementation optimisation can coexist with a language permission to behave differently.

### 5.18.3 Experiments can test, not legislate

An experiment should record:

~~~python
import platform
import sys

print(sys.implementation.name)
print(platform.python_version())
print(sys.executable)
~~~

Then isolate the disputed operation. Repetition across values and fresh processes can identify a pattern. Source and documentation can explain that pattern. None of these steps promotes an accidental regularity into a portable guarantee.

For example, <code>sys.getsizeof(value)</code> reports an implementation-specific shallow size measure for supported objects. It usually excludes separately allocated referents. Comparing two results can illuminate representation, but it does not yield the total memory cost of an application or a language-mandated object size.

### 5.18.4 Constant folding

An implementation can evaluate selected constant expressions while compiling:

~~~python
def value() -> int:
    return 20 + 22
~~~

CPython may place 42 directly in the code object’s constant table rather than execute an addition instruction. The function’s language-level result remains 42. Source-level reasoning must not require that an addition opcode occur.

Optimisation is constrained by observable semantics. An implementation cannot generally replace arbitrary user-defined addition with a precomputed result because operator dispatch can have effects. Even apparently constant expressions can be limited by compiler resource safeguards.

The standard modules <code>dis</code> and <code>ast</code> can inspect a CPython bytecode representation and abstract syntax tree:

~~~python
import ast
import dis

source = "result = 20 + 22"
print(ast.dump(ast.parse(source), indent=2))
dis.dis(compile(source, "<example>", "exec"))
~~~

This is a flagged forward experiment. Chapter 15 explains code objects and bytecode, and all opcode observations must be labelled with the exact CPython version.

### 5.18.5 Object reuse and interning

**Interning** is an implementation technique that reuses one immutable object for equal values in selected circumstances. CPython interns selected strings and retains a range of commonly used integer objects, but construction route, compilation unit, and version affect observations.

~~~python
first = "".join(["iden", "tifier"])
second = "identifier"

print(first == second)
print(first is second)
~~~

Equality is the stable assertion. Identity may differ. The <code>sys.intern</code> function provides an explicit CPython-supported string-interning interface for specialised uses, but it still should not replace equality in application logic.

### 5.18.6 Reference counts are implementation evidence

CPython’s <code>sys.getrefcount</code> can expose a reference-count-related observation:

~~~python
import sys

value = []
print(sys.getrefcount(value))
~~~

The act of passing <code>value</code> into <code>getrefcount</code> itself creates a temporary reference relevant to the result. CPython versions can also use immortal objects or internal reference mechanisms that complicate naive counts. The value is not a language property and should not drive application logic.

Use weak references, explicit ownership, context managers, and profiling tools for supported lifecycle questions. Do not poll reference counts to decide whether mutating an object is safe.

### 5.18.7 Hash and address observations

The following quantities have narrow contracts:

- <code>id(obj)</code>: identity-associated integer unique among simultaneously live objects under the implementation;
- <code>hash(obj)</code>: process-use hash obeying equality compatibility for hashable values;
- <code>repr(obj)</code>: type-defined diagnostic representation;
- <code>hex(id(obj))</code>: hexadecimal formatting of the identity integer.

On CPython, <code>id</code> is commonly the object’s address, but source must not dereference it or assume permanence. Hashes may be randomised. Representations may include addresses. None is a durable domain identifier.

### 5.18.8 Version-sensitive truth

A claim can be correct for Python 3.12 and false for another release because grammar, standard-library contracts, deprecations, and implementation strategies evolve. Record:

- major and minor language version;
- implementation name;
- micro release when a defect or security patch matters;
- feature flags or build mode;
- relevant platform;
- documentation version.

Avoid vague temporal words such as “currently” in durable reference prose. Attach the claim to a version range or a dated normative source.

### Worked example 5.11C — Classify an identity experiment

~~~python
def make_integer() -> int:
    return int("1000")


left = make_integer()
right = make_integer()

print(left == right)
print(left is right)
print(id(left), id(right))
~~~

The language guarantees equal integer values from successful decimal parsing and defines the identity test. A particular run commonly observes distinct identities, but an implementation is not required to construct separate immutable integer objects. The printed identity integers are process-local observations. The experiment therefore supports value semantics while refusing to legislate allocation.

### 5.18.9 The portability ledger

For each nontrivial example, a **portability ledger** can contain:

| Claim | Owner | Required evidence |
|:---|:---|:---|
| right side evaluated before name binding | language | language reference |
| list augmented assignment ordinarily mutates | built-in data model | language/library documentation and test |
| one bytecode opcode appears | CPython version | disassembly under recorded build |
| source path is case-sensitive | filesystem environment | mount/platform observation |
| object occupies 88 shallow bytes | implementation/build experiment | recorded size probe |
| result satisfies domain invariant | application specification | proof, tests, or both |

This ledger prevents a precise implementation lesson from contaminating a portable interface and prevents a portable language claim from being dismissed merely because its mechanism differs across runtimes.

> **Common misconception — “If the official CPython interpreter does it, Python guarantees it.”**  
> CPython is the reference implementation, but the language deliberately permits implementation variation. Contract ownership must be checked, not inferred from popularity.
