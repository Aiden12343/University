# 5.3 Objects: identity, type, and value

Every datum manipulated directly by a Python program is represented as an **object**. An object has three fundamental properties:

1. **Identity** distinguishes that object from every other object during its lifetime.
2. **Type** determines the object’s supported operations and participates in its representation and behaviour.
3. **Value** is the object’s abstract content or state under its type’s semantics.

Identity never changes during the object’s lifetime. An object’s type also does not change. Its value may or may not be permitted to change. An object whose value can change while identity remains the same is **mutable**. An object whose value cannot change after creation is **immutable**.

Python’s built-in `id()` returns an integer that is unique among simultaneously existing objects for the duration relevant to the implementation’s contract. In CPython it is commonly related to a memory address, but portable Python reasoning must not depend on that representation. After an object’s lifetime ends, a later object may receive the same `id()` result. Identity is not a permanent serial number.

The operator `is` tests identity: whether two expressions produce the same object. The operator `==` tests value equality according to the operands’ types. Equality can invoke user-defined code; identity does not ask the object to define equivalence.

### Worked example 5.2 — Equal is not identical

```python
left = [1, 2]
right = [1, 2]
alias = left

print(left == right)
print(left is right)
print(left is alias)
```

Output:

```text
True
False
True
```

`left` and `right` refer to distinct list objects whose element sequences compare equal. `alias` is bound from the object produced by evaluating `left`, so both `left` and `alias` designate the same list.

Do not infer a general rule from experiments involving small integers or short strings. Implementations may reuse immutable objects. CPython, for example, caches or interns selected objects as an implementation optimisation. Whether two equal literals happen to share identity is usually not a language guarantee. Use `==` for value comparison and reserve `is` for identity contracts, most commonly comparison with the singleton `None`.

> **Common misconception — “Everything is an object means everything is mutable.”**  
> Objecthood supplies identity, type, and value. Mutability is a separate type property. Integers, strings, tuples, and frozensets are immutable; lists, dictionaries, and sets are mutable.

### 5.3.1 Type is itself represented by objects

Python’s object model is reflexive: classes are objects, and the usual type of a class object is the metaclass <code>type</code>. The built-in class <code>int</code> is therefore both a callable used to construct or convert integer objects and an object that can be bound, passed, and inspected.

~~~python
number = 42
number_class = type(number)

print(number_class is int)
print(type(int))
print(isinstance(number, int))
~~~

For ordinary CPython, these expressions display <code>True</code>, <code>&lt;class 'type'&gt;</code>, and <code>True</code>. <code>isinstance</code> asks whether an object belongs to a class or its admitted subclass relationship. It is generally more appropriate for polymorphic interface checks than exact equality of <code>type(value)</code> with a class.

Classes, inheritance, and metaclasses are formally constructed in Chapter 9. The minimal present model is that a type object owns or mediates the operations available for its instances.

### 5.3.2 Behaviour belongs to protocols, not merely printed type names

A **protocol** is a set of operations and behavioural obligations that objects can support. Iterability, callability, context management, hashing, and numeric conversion are protocols. Two unrelated classes can support the same protocol without sharing one concrete representation.

The expression:

~~~python
len(value)
~~~

does not require <code>value</code> to be a list. It requests the length protocol, which strings, tuples, dictionaries, sets, ranges, and user-defined objects can support. This is **polymorphism**: one operation works through a common behavioural contract over different types.

Runtime type names are therefore diagnostic but not a complete design. A function needing “an iterable of text strings” should depend on that behaviour rather than insist on one particular list representation, unless mutation, indexing, or exact list identity is part of its contract.

### 5.3.3 Value can include state beyond visible representation

The displayed representation of an object need not reveal its entire abstract state. Two objects can display alike but differ in identity, hidden metadata, open-resource position, timezone interpretation, comparison policy, or attached behaviour. Conversely, one mutable object can display differently at two times while retaining identity.

For built-in immutable scalar objects, it is often convenient to discuss value as a stable mathematical or textual content. For a file object, value-like state includes current position, buffering and open/closed status, while the external file can also change independently. For a function object, behaviour depends on code, defaults, closure references, and globals. The object model is general enough to represent both data records and active capabilities.

### 5.3.4 Identity is temporal

The relation <code>a is b</code> asks whether the two evaluated operands designate one object at that moment. Identity is not equality of source spelling:

~~~python
first = [1]
second = first
third = [1]

print(first is second)
print(first is third)
~~~

The first relation is true because assignment propagated the reference. The second is false because a separate list display constructed a separate mutable object.

Identity is also not a stable cross-process concept. Serialising an object and reading it into another process ordinarily creates a new object even when value is preserved. Numeric addresses can vary between executions. Persistent domain identity—such as an account identifier—must be represented explicitly as data rather than inferred from Python object identity.

### 5.3.5 Immutability and object reuse

Because an immutable object cannot reveal value-changing mutation, an implementation can sometimes reuse one object for equal values. It can cache small integers, intern selected strings, or return an existing immutable object from an operation. Portable source must remain correct whether reuse occurs or not.

~~~python
first = tuple([1, 2])
second = tuple([1, 2])

print(first == second)
print(first is second)
~~~

Value equality is the intended assertion. The identity result is not the contract. Even <code>tuple(existing_tuple)</code> is permitted to return the same immutable tuple because no new identity is usually promised.

Use identity when identity itself is semantic: testing <code>None</code>, a deliberately unique sentinel, or whether two aliases share mutable state. Never infer value equality merely from different identities; never infer distinct domain entities merely from separate Python objects.

### Worked example 5.2A — Three kinds of sameness

Suppose a domain record carries an explicit identifier:

~~~python
record_a = {"account_id": "A-17", "balance": 20}
record_b = {"account_id": "A-17", "balance": 20}
alias = record_a
~~~

Then:

- <code>record_a is alias</code> expresses Python object identity;
- <code>record_a == record_b</code> expresses dictionary value equality;
- equality of the <code>account_id</code> fields expresses intended domain identity under a stated application rule.

These relations happen to be mutually compatible in the initial state, but they can diverge. Mutating one balance breaks whole-record equality while domain identity remains. Copying a record breaks object identity while domain identity remains. Reusing the same object for corrupted account data preserves object identity while violating domain validity.

> **Common misconception — “Identity, equality, and domain identity are three tests for the same fact.”**  
> They belong to different models: runtime object continuity, type-defined value comparison, and application-defined entity correspondence.
