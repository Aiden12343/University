# 5.4 Names and bindings, not variable boxes

A **namespace** is a mapping from names to objects. A **binding** is an association between a name and an object in a namespace. Assignment evaluates its right-hand expression, then performs binding operations described by its target form.

The familiar word **variable** is acceptable if defined carefully: in Python, a variable is a name that can be bound and rebound. It is not a typed container into which object contents are copied. Type belongs to the object. A later assignment can bind the same name to an object of another type.

```python
quantity = 12
quantity = "twelve"
```

The first assignment binds `quantity` to an integer object. The second evaluates the string literal and rebinds the same name to a string object. It does not mutate the integer 12 into text and does not change any other name that still refers to the integer.

### Worked example 5.3 — Rebinding versus mutation

```python
first = [10, 20]
second = first

first.append(30)
print(first)
print(second)

first = [99]
print(first)
print(second)
```

Output:

```text
[10, 20, 30]
[10, 20, 30]
[99]
[10, 20, 30]
```

Initial state:

- one list object (L_1=[10,20]) exists;
- `first` is bound to (L_1);
- evaluating `first` for the second assignment produces (L_1), so `second` is also bound to (L_1).

`first.append(30)` asks (L_1) to mutate. Both names still designate it, so both observations expose the changed value. `first = [99]` constructs another list (L_2) and rebinds only `first`. `second` remains bound to (L_1). Rebinding changes a namespace association; mutation changes an object.

The box metaphor fails here. If `first` and `second` were independent boxes each containing a copied list, mutation through one would not appear through the other. If they were two labels affixed to one object, the trace follows directly.

An **alias** is another reference or access path to the same object. **Aliasing** makes mutation non-local: an operation through one name can be observed through another. This is not inherently a defect. Shared mutable state is useful, but its ownership and permitted mutation require a contract.

### 5.4.1 Lookup is not binding

Evaluating a name expression requests lookup under the active scope rules. Assigning to a name creates, replaces, or deletes a binding in a namespace determined by the statement and scope. The same spelling can therefore denote different objects in different namespaces.

~~~python
rate = 2


def calculate() -> int:
    rate = 3
    return rate * 10


print(calculate())
print(rate)
~~~

The function body’s <code>rate</code> is local under rules formalised in Chapter 8. Calling the function returns 30; the module-level <code>rate</code> remains bound to 2. Indentation does not itself create this function scope—the function definition does.

### 5.4.2 Rebinding has no backward effect

Once an expression has obtained an object, rebinding the source name does not rewrite previous references:

~~~python
original = "first"
saved = original
original = "second"

print(saved)
print(original)
~~~

<code>saved</code> remains bound to the first string object. The later assignment changes only the <code>original</code> binding. This explains parameter passing as well: binding a parameter gives the called frame another reference to the argument object. Rebinding that parameter does not rebind the caller’s name.

### 5.4.3 Multiple names can encode one state accidentally

Aliasing becomes dangerous when two names suggest independent ownership:

~~~python
pending = []
completed = pending
~~~

The names describe distinct conceptual collections, but the assignment creates one list with two aliases. Appending a completed item also makes it appear pending. The defect is not “Python passed by reference”; it is an object-graph construction inconsistent with the domain model. Construct two lists:

~~~python
pending: list[str] = []
completed: list[str] = []
~~~

Annotations communicate intended element types; they do not change the two-object fact established by two list displays.

### 5.4.4 Naming is part of specification

A name should reveal the role of its current referent, not merely its broad representation. <code>seconds_since_start</code> carries unit and origin that <code>time</code> suppresses. <code>customer_by_id</code> communicates a mapping direction that <code>data</code> does not.

Names cannot enforce invariants. A name <code>positive_count</code> can still be bound to -1. Yet precise naming makes contradictions visible during review and reduces the number of facts held outside source.

Avoid encoding a type that can become false after a routine refactor, such as <code>names_list</code> when the contract merely needs an iterable. Encode representation in a name only when representation matters to the reasoning.

### 5.4.5 Constants are conventions over bindings

Python does not create immutable name bindings merely because a name uses capitals:

~~~python
SECONDS_PER_MINUTE = 60
SECONDS_PER_MINUTE = 61
~~~

Both assignments are executable. Upper-case spelling is a convention announcing that ordinary code should treat the binding as a module-level constant. Static analysis can flag rebinding, and <code>typing.Final</code> can publish intent later, but runtime immutability still belongs to objects and enforcement mechanisms.

A constant binding can refer to a mutable object:

~~~python
DEFAULT_LABELS = ["draft", "final"]
DEFAULT_LABELS.append("archived")
~~~

The name was not rebound, yet the list changed. A constant policy must state whether it forbids rebinding, mutation, or both. Prefer immutable value graphs for shared constants when feasible.

### 5.4.6 Names can become unbound

Using <code>del</code> on a name removes its binding from the relevant namespace:

~~~python
status = "ready"
del status
# Evaluating status here raises NameError.
~~~

An unbound name is not bound to <code>None</code>. These states are distinguishable:

- unbound: lookup fails;
- bound to <code>None</code>: lookup succeeds and returns the singleton;
- bound to an empty value: lookup succeeds and returns that value.

Conflating them obscures interface conditions. Use <code>None</code> or a sentinel when absence is a legitimate value state; do not rely on catching <code>NameError</code> as ordinary data flow.

> **Common misconception — “A name has one global meaning throughout a program.”**  
> Meaning depends on namespace, scope, execution time, and rebinding. Documentation can assign a role, while the runtime resolves each lookup in a particular context.
