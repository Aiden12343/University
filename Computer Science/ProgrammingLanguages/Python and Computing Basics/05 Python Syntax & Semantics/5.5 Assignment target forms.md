# 5.5 Assignment target forms

The left side of assignment is a target, not an unevaluated value expression in every detail. A simple name target changes a namespace. An attribute target requests attribute assignment on an object. A subscription target requests item assignment. Unpacking targets distribute elements across nested targets.

```python
name = "Ada"                 # name binding
record.title = "Engineer"    # attribute assignment
scores[0] = 98               # item assignment
left, right = right, left     # iterable unpacking
```

In the final line, the entire right side is evaluated before target bindings occur. Python constructs or otherwise obtains a two-element intermediate result, then binds `left` from the first element and `right` from the second. This permits swapping without a manually named temporary variable.

### Worked example 5.4 — Unpacking is structural

```python
point = (3, 8)
x, y = point
print(x, y)

head, *middle, tail = [1, 2, 3, 4, 5]
print(head, middle, tail)
```

Output:

```text
3 8
1 [2, 3, 4] 5
```

The first target pattern requires exactly two produced elements. The starred target in the second pattern absorbs zero or more middle elements into a new list. Unpacking depends on iteration, formalised in Chapter 6. It does not require that the source be a tuple.

Augmented assignment, such as `target += value`, has semantics beyond textual replacement with `target = target + value`. The target is evaluated once, and the object may support an in-place operation. For mutable objects, identity may be preserved; for immutable objects, a new result is ordinarily bound.

```python
numbers = [1, 2]
alias = numbers
numbers += [3]
print(numbers is alias, alias)

text = "py"
old_text = text
text += "thon"
print(text is old_text, old_text, text)
```

The list operation mutates and ordinarily preserves identity; the string operation cannot mutate the string and binds `text` to a new string value. The exact dispatch uses special methods introduced in Chapter 9.

### 5.5.1 Name targets and chained assignment

Chained assignment propagates one evaluated object:

~~~python
row_a = row_b = []
row_a.append("x")
print(row_b)
~~~

The result shows <code>["x"]</code> through both names. If independent lists are intended, use independent construction:

~~~python
row_a = []
row_b = []
~~~

Chaining immutable values is usually less hazardous because mutation cannot reveal sharing, but it still means one evaluation:

~~~python
timestamp_a = timestamp_b = read_clock()
~~~

Both names designate the same sampled result rather than two clock readings. Whether that is correct depends on the specification.

### 5.5.2 Attribute targets

In:

~~~python
receiver.attribute = value_expression
~~~

Python evaluates the right side and the receiver according to the assignment semantics, then requests attribute assignment. The target name <code>attribute</code> is not looked up as an ordinary variable. The receiver’s type can validate, transform, record, or reject the assignment through the data model.

Properties and descriptors, introduced in Chapter 9, mean that apparent field assignment can execute arbitrary Python code:

~~~python
account.balance = new_balance
~~~

This could check currency, acquire a lock, update a database proxy, or raise an exception. A dot is interface syntax, not proof of a passive memory slot.

### 5.5.3 Subscription and slice targets

A **subscription** selects by key:

~~~python
sequence[index] = replacement
mapping[key] = value
~~~

The receiver and subscript expressions are evaluated, and the object’s item-assignment protocol is invoked. For a list, an integer index selects a position; for a dictionary, a hashable key selects an association. The same syntax relies on different type contracts.

A slice target can replace a region:

~~~python
values = [0, 1, 2, 3, 4]
values[1:4] = [10, 20]
print(values)
~~~

The list becomes <code>[0, 10, 20, 4]</code>. Ordinary slice assignment can change length. Extended slices with a non-unit step impose different size requirements. These are list semantics, not universal properties of subscription syntax.

Strings and tuples reject item assignment because they are immutable. The failure occurs after target evaluation identifies the object and requests an unsupported operation.

### 5.5.4 Unpacking consumes an iterable

Unpacking does not index the source by requirement. It requests iteration and consumes values to match the target pattern:

~~~python
first, second, third = generate_three()
~~~

If the iterable yields fewer or more than three elements, assignment raises <code>ValueError</code>. With one starred target:

~~~python
head, *body, tail = iterable
~~~

the head and tail each require one item; the starred target receives a newly constructed list of remaining middle items. There can be at most one starred target in the same unpacking level.

An iterable can perform effects or raise while it is consumed. Target binding begins only after enough source material has been obtained for the unpacking operation under the language’s semantics, but nested or exotic target assignments can still have partial effects after consumption.

### Worked example 5.4A — Unpacking a one-pass source

~~~python
def source():
    print("yield A")
    yield "A"
    print("yield B")
    yield "B"
    print("source complete")


left, right = source()
print(left, right)
~~~

Generators are formalised in Chapter 6. Minimally, the call creates a one-pass iterable whose body advances at each requested value. Unpacking must check that a third value does not exist, so it resumes the source through <code>source complete</code> before committing the successful result. The printed trace demonstrates that “take two items” is incomplete; exact unpacking must also establish exhaustion.

### 5.5.5 Augmented assignment is target-sensitive

For a subscription target:

~~~python
records[index] += increment
~~~

Python evaluates the container and index once, retrieves the current item, requests an in-place or ordinary addition operation, and assigns the result back to the selected item. Even if the retrieved object mutates itself in place, the final item-assignment step still occurs under the data model.

This can surprise with a mutable object nested inside an immutable tuple:

~~~python
container = ([1, 2],)
# container[0] += [3]
~~~

The list’s in-place addition can mutate it to <code>[1, 2, 3]</code>, after which assignment back to <code>container[0]</code> fails because tuples do not support item assignment. The expression raises, yet mutation has occurred. Exceptions do not imply atomic rollback.

This is a canonical demonstration of why augmented assignment is not mere textual abbreviation. It combines retrieval, operation dispatch, and target storage, each with possible effects.

### 5.5.6 Annotated assignment

An annotated assignment publishes intended type information:

~~~python
total: int = 0
label: str
~~~

The first both records annotation metadata under context-specific rules and binds <code>total</code>. The second can record an annotation without binding <code>label</code> to a runtime value at module or class scope. Evaluating <code>label</code> before a later assignment can therefore still fail.

Annotations may be stored or evaluated according to the Python version and annotation features in force. This work uses them primarily as static contracts after Chapter 12; do not depend on incidental runtime annotation representation before that model is introduced.

> **Common misconception — “If assignment raises, nothing changed.”**  
> Right-side evaluation, iterable consumption, target-object lookup, in-place mutation, and earlier target stores may already have occurred. Atomicity requires an explicit design.
