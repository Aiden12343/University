# 5.6 References, reachability, and lifetime

A **reference** is an implementation-supported relationship by which one part of program state designates an object. Names hold bindings to objects; collection elements, attributes, frames, and implementation internals can also retain references. Python source does not expose raw memory addresses as ordinary references.

An object is **reachable** when a chain of live references from active program roots can designate it. When no usable reference remains, the object is unreachable by the program. Its resources may then be reclaimed under implementation rules.

CPython predominantly uses **reference counting**: it maintains counts related to strong references and normally deallocates an object when its count reaches zero. Reference cycles require an additional cyclic garbage collector. These are CPython implementation facts, not Python-language promises of immediate finalisation. Code must not depend on a particular collection moment for correctness; resource lifetimes are managed explicitly with context managers in Chapter 11.

### Worked example 5.5 — Losing a binding does not necessarily destroy an object

```python
primary = {"status": "open"}
secondary = primary

del primary
print(secondary["status"])
```

`del primary` removes the binding named `primary` from its namespace. The dictionary remains reachable through `secondary`, so its lifetime continues. The `del` statement applied to a name does not mean “destroy whichever object this name mentioned”. Other target forms of `del` request deletion of an attribute or item and have their own semantics.

If `secondary` is also deleted and no other references exist, the dictionary becomes unreachable. Portable code may say it is eligible for collection. It should not infer a universal exact instant at which memory is returned to the operating system.

> **Common misconception — “`del x` deletes the object.”**  
> With a name target, it deletes one binding. The object survives while reachable through any other reference. With an item or attribute target, `del` invokes that target’s deletion semantics.

### 5.6.1 Object graphs

An **object graph** models objects as nodes and references as directed edges. Namespaces, containers, attributes, active frames, and implementation machinery provide roots or edges. The graph exposes structure that a line-by-line box metaphor hides.

For:

~~~python
shared = {"count": 0}
left = [shared]
right = {"state": shared}
~~~

there are three container objects. The list and outer dictionary each reference the same inner dictionary. Mutating:

~~~python
left[0]["count"] = 1
~~~

is observable through <code>right["state"]</code>. No information travelled from <code>left</code> to <code>right</code> at mutation time; both paths already converged on one node.

### 5.6.2 Strong and weak references

An ordinary reference that keeps an object reachable is called a **strong reference**. Python’s <code>weakref</code> facility can create a **weak reference** that observes an object without by itself extending the object’s lifetime, for types that support it.

~~~python
import weakref


class Record:
    pass


record = Record()
observer = weakref.ref(record)

print(observer() is record)
del record
print(observer())
~~~

In ordinary CPython execution without other strong references, the second call commonly returns <code>None</code>. The portable contract is that a weak reference yields the object while it is alive and <code>None</code> after it has been finalised; code must still account for the object disappearing between observations in concurrent or callback-rich contexts.

Weak references support caches, registries, and observer structures whose bookkeeping should not own the observed object. They are not a substitute for explicit resource lifecycle or a way to inspect arbitrary built-in objects; support is type-dependent.

### 5.6.3 Reachability is not ownership

Python references do not carry a built-in universal ownership label. An application must decide which component is responsible for mutation, validation, closure, and retention. A borrowed reference can still be strong; a logically owning component can store no direct reference if an external system owns the resource.

An **ownership policy** states:

- who may mutate an object;
- whether aliases can escape;
- who closes external resources;
- how long references may be retained;
- whether callers receive a live view, immutable view, shallow copy, or deep independent value.

Returning an internal list directly grants callers a mutation route:

~~~python
def labels(self) -> list[str]:
    return self._labels
~~~

Returning a tuple snapshot narrows that route:

~~~python
def labels(self) -> tuple[str, ...]:
    return tuple(self._labels)
~~~

The snapshot prevents structural mutation through the returned object, though any mutable element objects remain shared. Ownership contracts must specify graph depth.

### 5.6.4 Cycles and collection

A reference cycle occurs when following edges can return to an earlier object:

~~~python
cycle: list[object] = []
cycle.append(cycle)
~~~

Deleting the name <code>cycle</code> removes the external binding but the list still refers to itself. Reference counting alone cannot reduce its count to zero. CPython’s cyclic collector can detect selected unreachable cycles and reclaim them under its policies.

Cycle collection is not a deterministic resource-management interface. The collector may run later, be disabled, or interact with finalisers and extension objects. Files, locks, transactions, and sockets require explicit lifetime boundaries, usually a context manager.

### 5.6.5 Finalisation is not destruction semantics

Some objects participate in finalisation callbacks when becoming unreachable. Depending on cycles, interpreter shutdown, resurrection, and implementation policy, timing and ordering can be subtle. An object can even make itself reachable again during a finaliser, a phenomenon called **resurrection**.

Application correctness must not require a particular finaliser order among unrelated objects. At interpreter shutdown, module globals can already be partly cleared when finalisation code runs. Explicit <code>close</code> operations and <code>with</code> statements provide lexical, testable boundaries; finalisation is a fallback, not the principal commit mechanism.

### Worked example 5.5A — Separate liveness from external-resource state

~~~python
path = "observation.txt"
handle = open(path, "w", encoding="utf-8")
alias = handle
handle.write("record")
del handle
print(alias.closed)
alias.close()
print(alias.closed)
~~~

Deleting one name leaves the file object reachable through <code>alias</code>; the resource remains open. Calling <code>close</code> changes its resource state even while the Python object remains reachable. Object liveness and external-resource openness are different dimensions.

This example uses file I/O before Chapter 11. The minimal contract is that <code>open</code> returns a stream object, <code>write</code> submits text, and <code>close</code> ends use and flushes relevant buffers. Production code uses a context manager so exceptions cannot bypass closure.

> **Common misconception — “Garbage collection manages every resource.”**  
> Collection concerns unreachable Python objects. External resources have protocol-defined release obligations and may remain scarce or semantically active until explicitly closed.
