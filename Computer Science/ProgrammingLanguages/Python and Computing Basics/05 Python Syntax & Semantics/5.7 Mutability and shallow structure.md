# 5.7 Mutability and shallow structure

Mutability belongs to an object’s type. A list can change which objects occupy its positions. A tuple cannot change its positions after construction. This does not mean that every object reachable *through* a tuple is immutable.

```python
record = ([1, 2], "fixed")
record[0].append(3)
print(record)
```

Output:

```text
([1, 2, 3], 'fixed')
```

The tuple still contains the same two references. The list object reached through its first position changed. “The tuple is immutable” means its own structural value cannot be reassigned; it does not recursively freeze its object graph.

A **shallow copy** creates a new outer container whose contained references initially designate the same element objects. A **deep copy** recursively attempts to copy a reachable object graph according to type-specific and library rules. Deep copying is not universally meaningful: files, locks, sockets, modules, shared identities, cycles, and deliberately unique resources resist the simplistic idea of duplicating everything.

### Worked example 5.6 — Trace a shallow copy

```python
original = [[1, 2], [3, 4]]
copied = original.copy()

copied.append([5, 6])
copied[0].append(99)

print(original)
print(copied)
```

Output:

```text
[[1, 2, 99], [3, 4]]
[[1, 2, 99], [3, 4], [5, 6]]
```

`original` and `copied` are distinct outer lists. Appending a third inner list changes only `copied`. Their original first elements are the same inner list object, so mutation through `copied[0]` appears through `original[0]`.

The right question is not “did I copy the value?” but “which levels of identity and sharing must be preserved or separated?”

### 5.7.1 Mutability is operation-relative

Calling a type mutable is shorthand for saying that some admitted operation can change an instance’s value while retaining identity. It does not mean every operation mutates or that every apparent method call changes state.

List method <code>append</code> mutates and conventionally returns <code>None</code>:

~~~python
values = [3, 1, 2]
result = values.append(4)
print(values)
print(result)
~~~

The separate return value discourages accidental chaining and distinguishes effect from transformed value. By contrast, <code>sorted(values)</code> constructs a new list while leaving <code>values</code> unchanged, whereas <code>values.sort()</code> reorders the existing list and returns <code>None</code>.

Names such as “sort” do not universally decide mutation; consult each interface contract.

### 5.7.2 Structural and transitive immutability

An object is **shallowly immutable** when its immediate structure cannot change. A value graph is **transitively immutable** when no object reachable as part of the represented value can change through any admitted route relevant to the model.

A tuple of integers is transitively immutable under ordinary integer semantics. A tuple containing a list is only shallowly immutable. A <code>frozenset</code> can contain only hashable members, which excludes ordinary lists and dictionaries, but a user-defined hashable object could expose mutable state if it violates or carefully narrows equality semantics.

Transitive immutability is useful for:

- safe sharing across components;
- stable hashing;
- reasoning about concurrency;
- cache keys;
- reproducible snapshots.

It is a graph property plus a behavioural contract, not something inferred solely from the outer class name.

### 5.7.3 Copy depth is a policy

Suppose:

~~~python
source = {
    "labels": ["new", "review"],
    "owner": {"name": "Ada"},
}
~~~

Possible copy policies include:

1. reuse the same outer mapping;
2. copy only the outer mapping;
3. copy the mapping and label list but share the owner;
4. recursively copy all ordinary containers;
5. construct new domain objects while preserving selected shared identities;
6. serialise and reconstruct only admitted fields.

There is no context-free “true copy”. The correct policy follows from which subsequent mutations must be isolated and which identities must remain common.

The <code>copy</code> module supplies <code>copy.copy</code> and <code>copy.deepcopy</code>. Deep copy memoises already visited objects to preserve cycles and some sharing, and types can customise its behaviour. External resources and singleton-like objects may be returned unchanged. Treat it as a protocol-driven graph transformation, not metaphysical duplication.

### Worked example 5.6A — Sharing preserved inside a deep copy

~~~python
from copy import deepcopy

shared = [1, 2]
original = [shared, shared]
duplicate = deepcopy(original)

print(duplicate is original)
print(duplicate[0] is original[0])
print(duplicate[0] is duplicate[1])
~~~

The outer duplicate is distinct. Its copied inner list is ordinarily distinct from the original inner list. Within the duplicate, both positions still refer to one copied inner list because the memo preserves the original graph’s aliasing. A naive recursive copier that creates a fresh child per edge would change the graph topology and could recurse forever on cycles.

### 5.7.4 Views, snapshots, and iterators

A **view** reflects a live underlying object; a **snapshot** captures state at a selected time. Dictionary key, value, and item views are live:

~~~python
mapping = {"a": 1}
keys = mapping.keys()
mapping["b"] = 2
print(list(keys))
~~~

The later observation includes the added key. <code>list(mapping)</code>, by contrast, creates a shallow snapshot of keys at construction time.

An iterator is neither automatically a view nor a snapshot. It is a stateful traversal interface whose behaviour under underlying mutation is type-specific and often restricted. Chapter 6 establishes iterator mechanics. API documentation must use the precise term rather than promise “a list” when returning a one-pass iterator or a live view.

### 5.7.5 Mutation during iteration

Changing a collection’s structure while iterating over it can skip elements, revisit positions, or raise an error depending on the type. A safe transformation often iterates over a snapshot or builds a new collection:

~~~python
values = [1, -2, 3, -4]
non_negative = [value for value in values if value >= 0]
~~~

The list comprehension is a flagged forward construct formalised in Chapter 6. It creates a new list from admitted elements and leaves the source traversal stable.

When in-place mutation is necessary, derive an algorithm whose index movement and size changes are explicit. “Python lets me delete it” is not a correctness argument.

### 5.7.6 Defensive copying and its costs

Defensive copying can prevent callers from mutating internal state, but it costs time and memory proportional to the copied structure and can destroy intended shared identities. For large arrays, graphs, or immutable persistent structures, copying on every boundary can dominate the computation.

Alternatives include:

- immutable return values;
- read-only protocol types;
- iterators yielding immutable records;
- explicit mutation methods that preserve invariants;
- copy-on-write structures;
- documented ownership transfer.

The choice is an engineering trade-off among isolation, performance, identity, and clarity. Measure costs and state the contract.

> **Common misconception — “Deep copy makes data independent.”**  
> Independence is domain-specific. Deep copy follows customisable Python protocols, may preserve selected objects and sharing, and cannot duplicate external reality such as an open connection or another process.
