# 5.8 Equality, ordering, and hashing

Value comparison is type-defined. `a == b` ordinarily gives the left operand’s type an opportunity to compare, may delegate, and may return a non-Boolean object whose truth is later interpreted. Built-in scalar comparisons normally return `bool`, but the general object protocol is richer.

Ordering operators `<`, `<=`, `>`, and `>=` ask types for ordered relationships. Python does not impose a universal arbitrary order across unrelated types. The integer 3 and string `"3"` are not ordered merely because both can be displayed.

A **hash value** is an integer summary used by hash-based containers to choose candidate storage locations. Objects used as dictionary keys or set members must be **hashable**: their hash must remain stable during their participation, and objects that compare equal must have equal hashes. Unequal objects may share a hash; the container resolves collisions using equality checks.

Mutable built-in containers such as lists, dictionaries, and sets are unhashable because value-changing mutation would invalidate placement assumptions. Immutable does not automatically imply hashable: a tuple is hashable only if every element needed for its hash is hashable.

```python
print(hash((1, 2, 3)))
# hash(([1, 2], 3)) would raise TypeError because the nested list is unhashable.
```

Hash values for some types, notably strings and bytes in CPython, are deliberately randomised across processes as a security measure. A hash is not a stable file identifier, not encryption, and not necessarily reproducible between runs.

> **Common misconception — “Equal hashes mean equal objects.”**  
> Equality requires matching hashes for hashable objects, but collisions permit unequal objects to share a hash. A hash table uses equality to distinguish colliding candidates.

### 5.8.1 Equality is an operation

For user-defined types, <code>left == right</code> can call comparison methods and return a result reflecting domain semantics. It can compare structural fields, identifiers, normalised forms, or reject an unsupported counterpart through the special value <code>NotImplemented</code>. Python may then try a reflected comparison or apply fallback rules.

<code>NotImplemented</code> is a singleton used by binary-operation protocols to say “this implementation does not define the requested operand pairing”. It is not the same as raising <code>NotImplementedError</code>, an exception used to mark an operation body that a subclass or future implementation must supply.

Comparison can have side effects in poorly designed or instrumented classes. Hash containers can invoke equality while resolving collisions. Equality should ordinarily be stable, symmetric where the domain requires it, and free of surprising mutation, because large parts of the language assume it behaves like an equivalence relation.

### 5.8.2 Equivalence relations

A relation (sim) on a set is an **equivalence relation** when it is:

- reflexive: (a\sim a);
- symmetric: if (a\sim b), then (b\sim a);
- transitive: if (a\sim b) and (b\sim c), then (a\sim c).

Ordinary value equality is expected to approximate these properties, but certain domain values deliberately do not. IEEE floating-point NaN is not equal to itself:

~~~python
nan = float("nan")
print(nan == nan)
print(nan != nan)
~~~

The results are ordinarily <code>False</code> and <code>True</code>. Algorithms assuming reflexive equality must exclude or explicitly handle NaN. Identity still holds: <code>nan is nan</code> is true for the same bound object, demonstrating again that identity and equality are different relations.

### 5.8.3 Ordering can be partial

A **total order** makes every pair comparable and obeys appropriate consistency laws. A **partial order** permits some pairs to be incomparable. Sets under subset inclusion provide a partial-order example: neither <code>{1}</code> nor <code>{2}</code> is a subset of the other.

Python comparison syntax does not guarantee that a type offers a total order. Complex numbers reject ordinary magnitude ordering. Sets use <code>&lt;</code> and related operators for proper-subset and subset relations rather than arbitrary display order.

Sorting requires an ordering key or comparison behaviour that is consistent enough for the algorithm. For heterogeneous records, specify a key:

~~~python
records = [
    {"name": "Grace", "score": 91},
    {"name": "Ada", "score": 91},
    {"name": "Linus", "score": 87},
]

ordered = sorted(
    records,
    key=lambda record: (-record["score"], record["name"]),
)
~~~

The lambda construct is formally derived in Chapter 8. The key is a tuple: negative score makes larger scores sort first under ascending order, and name breaks ties. This creates a total policy for admitted records without imposing an order on dictionaries themselves.

### 5.8.4 The hash contract

For hashable objects, the essential implication is:

\[
a = b \Longrightarrow \operatorname{hash}(a)=\operatorname{hash}(b).
\]

The converse does not hold. If hashes differ, equal objects are ruled out under a correct implementation; if hashes match, equality must still be checked.

Hash stability is required while an object participates in a hash-based container. Suppose an object’s hash depends on a mutable field and that field changes after insertion. The container may search the new hash location while the object remains stored under the old one, making membership appear to fail and violating internal assumptions.

Python therefore makes ordinary mutable built-in containers unhashable. User-defined classes must maintain the same invariant. If equality depends on mutable state, instances should generally be unhashable. If identity equality is intended, identity-based hashing can be coherent.

### Worked example 5.7A — Equal numeric keys

Python’s numeric equality and hash contracts intentionally connect some cross-type values:

~~~python
mapping = {1: "integer"}
mapping[1.0] = "float"
mapping[True] = "boolean"

print(mapping)
print(len(mapping))
~~~

Because <code>1 == 1.0 == True</code> and their hashes agree, these assignments address one dictionary key equivalence class. The final value replaces earlier values; the mapping has length one. Type distinction alone does not create separate dictionary keys when equality unifies them.

If domain data must distinguish Boolean true, integer one, and floating one, use tagged values or a key containing the type category rather than relying on ordinary numeric equality.

### 5.8.5 Hash randomisation and persistence

An implementation may randomise hashes of selected types per process to make collision attacks less predictable. Consequently:

- set iteration order must not be used as a cross-process canonical order;
- a dictionary’s insertion order does not make its hash values stable;
- <code>hash(text)</code> must not be stored as a durable identifier;
- test expectations must not require one randomised numeric hash.

A content digest such as SHA-256 serves a different protocol: stable byte-sequence fingerprinting under a named cryptographic algorithm. It still requires canonical encoding and does not equal Python hashing.

### 5.8.6 Equality and mutable collection membership

List membership:

~~~python
candidate in values
~~~

performs comparisons according to the container protocol and can be linear in length. Set and dictionary membership use hashing to narrow candidates and then equality to resolve them. This explains both their average performance and their hashability requirement.

Mutating an object stored inside a list can change future equality-based membership results without breaking the list’s structure. Mutating an object in a way that changes its hash while it is a set member is a contract violation with more severe consequences. Collection choice and element mutability interact.

> **Common misconception — “A dictionary key is found by hash alone.”**  
> Hashing selects candidate placement; equality distinguishes colliding or equivalent keys. Correctness requires both compatible equality and stable hashing.
