# 5.9 Numeric objects

Python’s principal built-in numeric types are `int`, `float`, `complex`, and `bool`.

An `int` represents a mathematical integer within limits imposed by available memory and implementation safeguards. CPython uses variable-size representations rather than one fixed machine word for ordinary Python integers. Operations can therefore grow beyond 32 or 64 bits:

```python
large = 2**200
print(large)
print(large.bit_length())
```

`bit_length()` reports the number of bits necessary to represent the magnitude of the non-negative value. The object still occupies finite memory and operations still have costs that grow with magnitude.

A `float` ordinarily implements IEEE 754 binary64 floating-point on CPython’s supported mainstream platforms. It represents a finite subset of real numbers using sign, significand, and exponent. Most decimal fractions do not have finite binary expansions, so the nearest representable value is stored.

```python
print(0.1 + 0.2)
print(0.1 + 0.2 == 0.3)
```

Typical output is:

```text
0.30000000000000004
False
```

This is not random error. Each literal is rounded to a nearby binary floating-point value, and the operation rounds again. Display formatting usually chooses a short decimal that reconstructs the same stored value, which can hide the approximation until an operation exposes it.

Use exact integer units for quantities naturally discrete, such as pence rather than pounds, when the required range and operations permit. Use `decimal.Decimal` when a specified decimal arithmetic model is required, constructing from decimal text rather than an already approximated float. Use `fractions.Fraction` for exact rational arithmetic when numerator and denominator growth is acceptable. Representation follows the domain contract.

### Worked example 5.7 — Decimal construction boundary

```python
from decimal import Decimal

from_text = Decimal("0.1")
from_float = Decimal(0.1)

print(from_text)
print(from_float)
```

The first constructs the exact decimal value described by the text contract. The second constructs the exact decimal representation of the already approximated binary float value. `Decimal` cannot recover information discarded before it received the operand.

`complex` represents a pair of floating-point components conventionally written (a+bj), where (j^2=-1). Complex numbers do not have an ordinary less-than total order, so `<` is not defined merely because equality and arithmetic exist.

`bool` has exactly two instances, `False` and `True`, and is a subclass of `int` for historical and compatibility reasons. In numeric contexts they behave like 0 and 1, but predicates and flags should be modelled as Boolean conditions rather than obscure arithmetic.

### 5.9.1 Integer literal bases and conversion

Source literals use a radix prefix, but runtime integer values have no remembered base. Conversion from text can select a base:

~~~python
binary_value = int("101101", 2)
hex_value = int("2d", 16)
automatic = int("0b101101", 0)

print(binary_value, hex_value, automatic)
~~~

All produce decimal display 45 under <code>print</code>. The second argument is the radix; base zero asks the conversion grammar to recognise a prefix. Conversion should validate the entire admitted text. Silently deleting punctuation or accepting locale-dependent separators without a specification can turn malformed input into a different valid number.

Formatting chooses an output representation:

~~~python
value = 45
print(bin(value))
print(oct(value))
print(hex(value))
print(f"{value:08b}")
~~~

The final format requests eight binary digits padded with leading zeros. These functions and formatting expressions create strings; they do not alter the integer.

### 5.9.2 Integer size has computational cost

Calling Python integers “arbitrary precision” means their magnitude is not fixed to one machine-word range by the language interface. It does not mean unbounded or constant-cost. An integer occupying (n) machine-sized digits requires space (O(n)); addition is ordinarily linear in the number of digits, while multiplication uses algorithms whose complexity depends on size and implementation thresholds.

The expression:

~~~python
value = 10 ** 1_000_000
~~~

requests a real allocation and computation. Converting an enormous integer to decimal text can also be expensive; CPython versions include safeguards for certain conversions to resist denial-of-service inputs. Treat numeric magnitude as input size when analysing resource use.

Bit operations on negative integers use semantics consistent with an unbounded two’s-complement representation with infinitely many sign bits, even though CPython stores magnitudes using its own finite internal representation. This language-level model explains:

~~~python
print(~0)
print(-1 >> 100)
~~~

which produce -1 and -1 respectively. The bitwise complement obeys the identity <code>~x == -x - 1</code>.

### 5.9.3 Boolean arithmetic is legal but often semantically weak

Because <code>bool</code> is an <code>int</code> subclass:

~~~python
print(True + True)
print(False * 100)
~~~

produces 2 and 0. This is useful for counting predicates:

~~~python
admitted_count = sum(
    value >= 0
    for value in measurements
)
~~~

The generator expression is formalised in Chapter 6. Each comparison produces a Boolean, and numeric summation counts true results.

Do not exploit the subclass relation when it obscures domain categories. An API expecting a record count may reject Boolean values explicitly even though <code>isinstance(True, int)</code> is true. Type hierarchy and domain validity are not identical.

### 5.9.4 Binary floating-point model

A finite normal binary floating-point value has the form:

\[
(-1)^s \times m \times 2^e,
\]

where (s) is a sign bit, (m) is a finite binary significand, and (e) is an exponent within a bounded range. Subnormal values extend representation near zero with reduced precision. IEEE 754 also provides signed zeros, positive and negative infinity, and NaNs.

The method <code>float.as_integer_ratio()</code> exposes the exact rational value of a finite float:

~~~python
value = 0.1
numerator, denominator = value.as_integer_ratio()

print(numerator)
print(denominator)
print(numerator / denominator == value)
~~~

The denominator is a power of two. The ratio is not exactly one tenth, demonstrating that <code>0.1</code> is source decimal syntax rounded to a binary representable value.

<code>float.hex()</code> gives a hexadecimal form that represents the binary value exactly enough for reconstruction:

~~~python
encoded = 0.1.hex()
restored = float.fromhex(encoded)
print(encoded)
print(restored == 0.1)
~~~

This is valuable for diagnostics where ordinary decimal display suppresses representational detail.

### 5.9.5 Rounding and ties

Every basic floating operation is conceptually rounded to a representable result under the active arithmetic model. Python’s built-in <code>round</code> uses a specified tie policy for ordinary numeric types: ties are directed towards the even choice where applicable.

~~~python
print(round(2.5))
print(round(3.5))
~~~

The results are 2 and 4. “Always rounds .5 up” is false. Moreover, a decimal-looking input may not be an exact halfway binary value, so outcomes at a requested decimal position can surprise:

~~~python
print(round(2.675, 2))
~~~

The familiar result 2.67 follows from the stored binary approximation, not a secret exception to the tie rule. If a domain requires decimal quantisation, use an explicit decimal representation and rounding mode.

### 5.9.6 Signed zero, infinity, and NaN

Floating-point positive and negative zero compare equal but preserve a sign in some operations:

~~~python
import math

positive_zero = 0.0
negative_zero = -0.0

print(positive_zero == negative_zero)
print(math.copysign(1.0, negative_zero))
~~~

Infinities can arise through conversion or operations admitted by the floating model, though ordinary division by zero in Python raises <code>ZeroDivisionError</code> rather than returning infinity:

~~~python
positive_infinity = float("inf")
print(positive_infinity > 10**1000)
~~~

NaN comparisons are unordered. Test with <code>math.isnan(value)</code>, not equality with another NaN. Aggregations, sorting, serialisation, and database transfer require an explicit special-value policy.

### 5.9.7 Error is measured relative to a purpose

An **absolute error** is (\lvert \hat{x}-x\rvert), where (x) is the reference value and (\hat{x}) the approximation. A **relative error** is often (\lvert \hat{x}-x\rvert/\lvert x\rvert) when (x\neq0). Relative error is undefined at zero and unstable near it; tolerances need both absolute and relative components.

Python supplies <code>math.isclose</code>:

~~~python
import math

observed = 0.1 + 0.2
expected = 0.3

print(
    math.isclose(
        observed,
        expected,
        rel_tol=1e-12,
        abs_tol=0.0,
    )
)
~~~

Tolerance values are domain decisions. A laboratory instrument, financial ledger, geometric predicate, and iterative solver do not inherit one universal epsilon. <code>isclose</code> is inappropriate when exact representation is the contract, such as protocol bit fields or integer counts.

### 5.9.8 Decimal arithmetic has a context

The <code>decimal</code> module represents base-ten floating-point values under a **context** containing precision, rounding mode, exponent bounds, and signal handling. Therefore <code>Decimal</code> is not synonymous with “always exact”.

~~~python
from decimal import Decimal, localcontext

with localcontext() as context:
    context.prec = 6
    result = Decimal("1") / Decimal("7")
    print(result)
~~~

One seventh has no finite decimal expansion, so it is rounded to the context precision. Addition and multiplication of finite decimals can be exact when the exact result fits the context and exponent limits; division can still require rounding.

Construct values from text or integers when those are the specified inputs. Constructing from float faithfully imports the exact binary approximation, which is sometimes desired for analysis but not for entering a decimal monetary amount.

### 5.9.9 Rational arithmetic can grow

<code>fractions.Fraction</code> stores a rational number as a reduced numerator and positive denominator:

~~~python
from fractions import Fraction

value = Fraction(1, 3) + Fraction(1, 6)
print(value)
~~~

The exact result is <code>1/2</code>. Rational arithmetic avoids rounding for rational inputs and operations that stay rational, but numerator and denominator sizes can grow substantially. Transcendental functions such as sine do not generally produce rational results. Exactness changes the cost model; it does not abolish it.

### 5.9.10 Choosing a numeric representation

Use a decision table:

| Requirement | Candidate | Principal qualification |
|:---|:---|:---|
| exact whole counts | <code>int</code> | magnitude-dependent memory and time |
| fixed smallest currency unit | <code>int</code> | scale and rounding policy remain explicit |
| regulated decimal arithmetic | <code>Decimal</code> | context must be controlled |
| exact ratios | <code>Fraction</code> | numerator/denominator growth |
| measured continuous quantities | <code>float</code> | error and special-value policy |
| two-component complex quantity | <code>complex</code> | no ordinary total ordering |

Representation choice follows operations as well as stored values. Exact cents represented by integers do not by themselves specify how to divide an invoice total, allocate remainder cents, apply percentage tax, or convert currency. Those are domain algorithms.

> **Common misconception — “Arbitrary precision, decimal, rational, and floating point are competing accuracy levels.”**  
> They implement different algebras, rounding rules, ranges, and costs. Correctness depends on matching the representation to the domain contract.
