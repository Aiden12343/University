# 6.1 Control flow is selection over state

**Control flow** is the rule determining which operation executes next. At machine level the program counter records the next instruction address; branches replace its ordinary sequential advance. At Python level, statements such as `if`, `while`, `for`, `try`, `return`, `break`, and `continue` organise the same fundamental choice through structured syntax.

Structured control flow makes regions and conditions explicit. It permits local reasoning: a reader can identify the entry condition, body, exit paths, and preserved properties of a construct without following arbitrary instruction addresses. The machine still executes branches underneath; the language gives those branches named, nested form.

Control flow evolves through time. The truth value of a condition is evaluated at a particular point in a particular state. Repetition is not one instruction “being a loop”; it is control returning to a test or requesting another item while retained state differs from the previous visit.

### 6.1.1 State-transition model

Let a program state (S) contain every fact relevant to future execution: current instruction position, active frames, name bindings, reachable objects, pending exceptions, iterator positions, stream state, and relevant external conditions. A computational step applies a transition relation:

\[
S_i \longrightarrow S_{i+1}.
\]

For deterministic ordinary execution under fixed inputs, one state determines at most one next state. Input, scheduling, signals, randomness, and external systems can make the larger transition system nondeterministic. Control flow determines which operation contributes the next transition.

A statement sequence:

~~~python
width = 4
height = 5
area = width * height
~~~

establishes a path through at least three visible binding transitions. The third statement depends on bindings established by the first two. If the second statement raises or control never reaches it, the third transition does not occur.

### 6.1.2 Control-flow graphs

A **control-flow graph** is a directed graph whose nodes represent operations or basic blocks and whose edges represent possible transfers of control. A **basic block** is a maximal straight-line sequence with one entry and no internal branch except at its end.

For:

~~~python
if temperature < 0:
    state = "solid"
else:
    state = "liquid"
print(state)
~~~

the graph contains a condition node, two alternative assignment blocks, and a join before the print call. Exactly one assignment path is selected under ordinary execution, and both converge on a state in which <code>state</code> is bound.

Control-flow graphs support:

- reachability analysis;
- detection of paths lacking return or assignment;
- data-flow analysis;
- complexity reasoning;
- test-path selection;
- compiler optimisation;
- proofs about invariants.

They abstract away many object-level details. A graph edge saying “call returns” does not describe the call’s internal state changes.

### 6.1.3 Sequence, selection, iteration, and transfer

Structured programs are organised primarily through:

- **sequence:** execute one construct after another;
- **selection:** choose among alternative constructs;
- **iteration:** repeat a construct under a rule;
- **abstraction:** call a named computation and later resume;
- **exceptional transfer:** leave ordinary nested control when a failure is raised;
- **suspension:** retain a continuation for later generator or coroutine resumption.

The classical structured-programming result shows that arbitrary computable control can be represented using sequence, selection, and iteration with suitable state. Python adds functions, exceptions, generators, and asynchronous constructs because direct expression of intent matters even when lower-level simulation is theoretically possible.

### 6.1.4 Entry, exit, and join conditions

Every control construct has entry assumptions and possible exits. For an <code>if</code> chain:

- entry: the first condition is ready to be evaluated;
- branch exits: one selected suite completes normally or transfers elsewhere;
- join: normal branch exits converge after the statement.

For a loop:

- entry: initial state before the first test or item request;
- back edge: one iteration returns to the loop boundary;
- normal exit: condition false or iterator exhausted;
- abrupt exits: <code>break</code>, <code>return</code>, exception, or process termination.

A **join condition** is a property guaranteed on every path reaching a convergence point. In:

~~~python
if admitted:
    result = transform(value)
else:
    result = default

use(result)
~~~

the join condition includes “<code>result</code> is bound”, provided both calls return normally. If one branch omits assignment, the later lookup is not justified for all paths.

### 6.1.5 Reachability

A source statement is **reachable** if some admitted execution path can arrive at it. Code after an unconditional return in the same suite is unreachable:

~~~python
def classify(value: int) -> str:
    return "known"
    print(value)
~~~

The print call cannot execute through ordinary function control. Python can compile such source; static tools may report it. Unreachable code can indicate stale implementation, a mistaken indentation boundary, or an incomplete control model.

Unreachable under current assumptions differs from syntactically unreachable. A branch guarded by a condition that is always false only because of a domain invariant can become reachable if the invariant is violated. State both the program structure and the admitted input model.

### 6.1.6 Dominance

In a control-flow graph, node (A) **dominates** node (B) when every path from entry to (B) passes through (A). Dominance explains why a check can justify a later operation:

~~~python
if denominator == 0:
    raise ValueError("zero denominator")

quotient = numerator / denominator
~~~

The successful completion of the guard dominates the division. Any path reaching division has established <code>denominator != 0</code>, assuming no intervening effect changes it.

In concurrent or callback-driven code, a checked mutable object can change between validation and use. The simple dominance fact remains true about execution positions but no longer preserves the data predicate. Immutability, local snapshots, locks, or transactional operations may be required.

### 6.1.7 Abrupt completion

A suite completes **normally** when control reaches its end and proceeds to the construct’s ordinary successor. It completes **abruptly** when <code>return</code>, <code>break</code>, <code>continue</code>, or an exception transfers control elsewhere.

In:

~~~python
for value in values:
    if value < 0:
        continue
    if value == 0:
        break
    total += value
~~~

there are three body exits: continue to the next item request, break to after the loop, and normal fall-through after addition to the next request. An invariant must hold at every back-edge path; a postcondition after the loop must distinguish exhaustion from break.

### 6.1.8 Control flow and effects

Two source arrangements that calculate the same pure mathematical function can expose different effects:

~~~python
if ready():
    result = consume()
else:
    result = fallback()
~~~

~~~python
candidates = [consume(), fallback()]
result = candidates[0] if ready() else candidates[1]
~~~

The first evaluates <code>ready</code> and one selected call. The second calls both effectful alternatives before evaluating the condition. Value equality on selected return paths does not imply program equivalence.

Control constructs are therefore effect-control constructs. They decide which input is consumed, which mutation occurs, which resource is acquired, and which failure becomes possible.

> **Common misconception — “Control flow is just the order in which lines run.”**  
> Source lines are layout. Control flow is a graph over operations, including branches, joins, calls, exceptional exits, suspension, and paths that execute no visible line at all.
