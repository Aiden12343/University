# 6.10 Generator expressions, comprehensions, and materialisation

A **comprehension** constructs a collection from iteration and optional filtering:

```python
squares = [number * number for number in range(6)]
```

This list comprehension eagerly creates `[0, 1, 4, 9, 16, 25]`.

A **generator expression** uses parentheses and produces a lazy generator-like iterator:

```python
squares = (number * number for number in range(6))
```

No list of results is created immediately. Each result is computed when requested. Eager and lazy forms have different lifetime, reuse, memory, and failure timing.

Comprehensions can filter:

```python
even_squares = [number * number for number in range(10) if number % 2 == 0]
```

Read the clauses in iteration order: for each number, test the condition; if true, evaluate the leading expression and append its result to the new list.

Nested comprehensions mirror nested loops:

```python
pairs = [(left, right) for left in range(3) for right in range(2)]
```

produces `(0,0)`, `(0,1)`, `(1,0)`, `(1,1)`, `(2,0)`, `(2,1)`. When several transformations or branches obscure this order, explicit loops with named intermediate values are more rigorous.

### Worked example 6.7 — One-shot consumption

```python
values = (number * 2 for number in range(3))
print(list(values))
print(list(values))
```

Output:

```text
[0, 2, 4]
[]
```

The first `list` consumes the iterator to exhaustion. The second does not reconstruct the generator expression. A reusable iterable must be recreated or represented by an object whose `__iter__` supplies fresh iterators.

> **Common misconception — “A generator is a memory-efficient list.”**  
> A list is a reusable stored sequence. A generator is a one-pass stateful computation. It changes when work occurs, when failures occur, and whether results remain available.

### 6.10.1 Four comprehension products

Python provides:

~~~python
list_result = [transform(item) for item in source]
set_result = {transform(item) for item in source}
dict_result = {
    key(item): value(item)
    for item in source
}
lazy_result = (transform(item) for item in source)
~~~

The first three eagerly construct a list, set, or dictionary. The fourth constructs a generator expression whose element production is lazy. The delimiters and colon distinguish set from dictionary; empty braces alone construct a dictionary, so the empty set is <code>set()</code>.

Collection semantics remain active. A set discards equality-duplicate values and requires hashable elements. A dictionary requires hashable keys and later equal keys replace earlier values. A comprehension is not merely concise loop typography; its destination structure imposes invariants.

### 6.10.2 Translation to nested loops

Read:

~~~python
result = [
    combine(left, right)
    for left in left_source
    if admit_left(left)
    for right in right_source(left)
    if admit_pair(left, right)
]
~~~

as the structural equivalent:

~~~python
result = []

for left in left_source:
    if admit_left(left):
        for right in right_source(left):
            if admit_pair(left, right):
                result.append(combine(left, right))
~~~

Clauses nest from left to right. The leading expression runs only after every enclosing iteration and filter reaches the innermost production point. Reversing two <code>for</code> clauses changes both ordering and which names are available.

### 6.10.3 Evaluation order within dictionary comprehensions

For each admitted item in Python 3.8 and later, a dictionary comprehension evaluates the key expression before the value expression:

~~~python
mapping = {
    key_of(item): value_of(item)
    for item in source
}
~~~

Both can have effects or raise. If the key is unhashable, insertion fails after key construction and possibly after value construction according to the implementation of the item step; use the language reference for exact ordering. Avoid relying on effectful key/value expressions when a staged loop would make failure ownership clearer.

Equal later keys replace earlier associated values while retaining dictionary insertion-order rules. If duplicate keys indicate bad data, test and raise rather than let the display semantics silently choose the last.

### Worked example 6.7A — Detect duplicate derived keys

~~~python
def index_by_identifier(records):
    result = {}

    for record in records:
        identifier = record["id"]
        if identifier in result:
            raise ValueError(
                f"duplicate identifier: {identifier!r}"
            )
        result[identifier] = record

    return result
~~~

A dictionary comprehension would be shorter:

~~~python
{record["id"]: record for record in records}
~~~

but would silently retain the last equal-key record. The explicit loop represents the stronger uniqueness invariant.

### 6.10.4 Comprehension scope

Comprehensions execute their iteration-target bindings in a separate implicitly nested scope, apart from evaluation of the leftmost iterable expression:

~~~python
value = "outer"
result = [value * 2 for value in range(3)]
print(value)
~~~

The outer <code>value</code> remains <code>"outer"</code>. This differs from an ordinary <code>for</code> loop, whose target remains bound in the surrounding scope.

Names read by the comprehension can still come from enclosing scopes. Functions created inside it can close over its iteration variable, leading to late-binding behaviour developed in Chapter 8.

### 6.10.5 The leftmost iterable is obtained eagerly

In a generator expression:

~~~python
values = (
    transform(item)
    for item in obtain_source()
)
~~~

<code>obtain_source()</code> is evaluated immediately when the generator expression is created. Iteration over the obtained source and evaluation of <code>transform</code> are deferred.

This design reports errors in obtaining the primary source at the construction site:

~~~python
def fail():
    raise RuntimeError("cannot obtain source")


# The exception occurs here, during generator-expression creation.
values = (item for item in fail())
~~~

Later iterable expressions in nested clauses are deferred because they can depend on earlier produced values.

### 6.10.6 Failure timing

Compare:

~~~python
eager = [int(text) for text in fields]
lazy = (int(text) for text in fields)
~~~

The eager form parses every field before assignment completes. A malformed item raises at construction, and no <code>eager</code> binding is made by this statement, although prior conversion effects may have occurred.

The lazy form creates a generator after obtaining <code>fields</code>. Parsing happens as a consumer requests values. A malformed fifth field can occur after four results have already affected a downstream sum, file, or database operation.

Laziness can reduce memory and permit early stopping, but it distributes failure over consumption time. Transactional consumers may need validation or staging before committing effects.

### 6.10.7 Materialisation

Materialisation consumes an iterable and stores its results:

~~~python
snapshot = list(source)
~~~

Benefits:

- repeated traversal;
- known completion before later effects;
- random access;
- stable snapshot under an ownership policy;
- length availability.

Costs:

- memory proportional to item count and references;
- delay before first downstream result;
- inability to handle unbounded input;
- eager triggering of all source effects and failures;
- shallow sharing of yielded mutable objects.

Materialising a generator does not deep-copy its items. It stores the same yielded object references.

### 6.10.8 Early termination

A lazy pipeline can avoid unnecessary work:

~~~python
first_match = next(
    (
        item
        for item in source
        if predicate(item)
    ),
    None,
)
~~~

Production stops after the first matching item. If <code>None</code> is an admitted source item, use a unique sentinel to distinguish exhaustion.

An eager list comprehension evaluates the entire source before selecting its first element:

~~~python
matches = [
    item
    for item in source
    if predicate(item)
]
~~~

The lazy form can be asymptotically better for early success on large or unbounded sources. It can also leave source resources partially consumed, so cleanup remains an ownership concern.

### 6.10.9 Generator expressions as sole call arguments

Parentheses surrounding a generator expression can be omitted only when it is the sole argument form in a call:

~~~python
total = sum(value * value for value in source)
~~~

Additional arguments require explicit generator parentheses:

~~~python
result = consume(
    (transform(value) for value in source),
    policy,
)
~~~

A trailing comma inside the generator expression is not a way to create multiple yielded fields. Yield a tuple:

~~~python
pairs = (
    (key, value)
    for key, value in source
)
~~~

### 6.10.10 Assignment expressions in comprehensions

An assignment expression can retain an expensive intermediate:

~~~python
result = [
    transformed
    for item in source
    if (transformed := transform(item)) is not None
]
~~~

The scope rules deliberately prevent rebinding the comprehension iteration variable with the assignment expression, and the retained name can bind in the containing scope under specified conditions. Because these interactions are non-local and subtle, use the construct only when it materially clarifies one-evaluation semantics.

An explicit loop is preferable when the intermediate needs several validation steps or when leakage into the containing scope would surprise.

### 6.10.11 Nested list aliasing

This comprehension constructs independent rows:

~~~python
matrix = [
    [0 for column in range(width)]
    for row in range(height)
]
~~~

The inner list display executes once per outer iteration. Contrast:

~~~python
matrix = [[0] * width] * height
~~~

which repeats one inner-list reference. Both display equal values initially; only an identity graph or mutation test exposes the difference.

### 6.10.12 Comprehensions versus explicit loops

Use a comprehension when it expresses:

- one destination collection;
- a clear sequence of iteration and filtering;
- a local transformation;
- no complex effect choreography;
- no specialised failure recovery;
- no hidden uniqueness check.

Use explicit statements when:

- intermediate names carry essential meaning;
- several mutations or outputs occur;
- exceptions need narrow ownership;
- invariants require commentary;
- duplicate handling differs from the container default;
- control includes multiple exits.

Compression is not abstraction. A dense expression that forces reconstruction of five nested clauses is less economical than a named loop.

### Worked example 6.7B — Lazy transactional hazard

~~~python
converted = (
    int(text)
    for text in ["1", "2", "invalid", "4"]
)

for value in converted:
    write_external_record(value)
~~~

Two records can be written before conversion of <code>"invalid"</code> raises. If the requirement is “write all records or none”, the pipeline needs a transaction whose rollback is guaranteed, or a complete validation/materialisation phase followed by a commit phase:

~~~python
converted = [
    int(text)
    for text in source
]

with transaction():
    for value in converted:
        write_external_record(value)
~~~

The transaction construct is a flagged forward abstraction. Its actual atomicity depends on the external system; a Python <code>with</code> statement alone does not create rollback.

> **Common misconception — “A comprehension is always equivalent to writing the obvious loop.”**  
> Scope, destination collision semantics, eager or lazy timing, and leftmost-source evaluation are part of the construct. A translation must preserve all of them.
