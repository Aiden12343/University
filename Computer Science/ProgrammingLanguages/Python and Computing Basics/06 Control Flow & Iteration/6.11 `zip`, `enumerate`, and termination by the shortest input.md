# 6.11 `zip`, `enumerate`, and termination by the shortest input

`zip` produces tuples containing one item from each iterable per step. Ordinary `zip` stops when the shortest input is exhausted:

```python
names = ["Ada", "Grace", "Edsger"]
scores = [98, 95]

print(list(zip(names, scores)))
```

Output:

```text
[('Ada', 98), ('Grace', 95)]
```

`"Edsger"` is silently unpaired under the default contract. When unequal lengths indicate defective data, use `zip(..., strict=True)`:

```python
for name, score in zip(names, scores, strict=True):
    print(name, score)
```

This raises `ValueError` when exhaustion reveals a length mismatch. Strictness converts silent truncation into explicit contract enforcement.

`enumerate(iterable, start=0)` pairs successive integer counts with items without requiring the source to support indexing. It is superior to `range(len(items))` when only item and position are needed, because it operates on arbitrary iterables and avoids repeated subscription.

### 6.11.1 Zip is lazy

Calling <code>zip</code> constructs an iterator. It does not immediately consume all inputs or validate their lengths:

~~~python
pairs = zip(left_source, right_source)
~~~

Each request asks the component iterators for their next items in left-to-right order. Effects and failures occur during consumption.

~~~python
def marked(label: str, values):
    for value in values:
        print(label, value)
        yield value


pairs = zip(
    marked("L", [1, 2]),
    marked("R", [10, 20]),
)
print(next(pairs))
~~~

Only the first item from each source is requested for the first output tuple.

### 6.11.2 Default shortest-input semantics

Ordinary zip ends as soon as one component signals exhaustion. This is correct when the specification defines paired production only while all sources have items—for example, sampling several live sensors only at common time steps.

It is dangerous when lengths are expected to match:

~~~python
names = ["Ada", "Grace", "Edsger"]
scores = [98, 95]
records = dict(zip(names, scores))
~~~

The unmatched name disappears without an error. The resulting dictionary can appear valid while being incomplete.

### 6.11.3 Strict zip detects mismatch during consumption

<code>zip(..., strict=True)</code> raises <code>ValueError</code> when it discovers that one input ends before another. Detection is lazy:

~~~python
pairs = zip(names, scores, strict=True)
first = next(pairs)
second = next(pairs)
# The mismatch is discovered on a later request.
~~~

Consumers can therefore process valid-looking prefix pairs before the mismatch appears. Strict zip enforces equal exhaustion, not transactional use of the pairs.

If no partial external effect is allowed, materialise and validate:

~~~python
pairs = list(zip(names, scores, strict=True))
~~~

This requires finite inputs and memory proportional to the number of pairs.

### 6.11.4 One input may be advanced when mismatch is discovered

Zip requests component iterators in order. On the iteration that reveals mismatch, an earlier iterator may have produced an item before a later one reports exhaustion. That earlier item has then been consumed without appearing in an output tuple.

Do not assume component iterators remain aligned or reusable after zip failure. If source consumption is irreversible, define ownership and mismatch prevention upstream.

### 6.11.5 Longest-input alignment

<code>itertools.zip_longest</code> continues until every input is exhausted, filling missing positions:

~~~python
from itertools import zip_longest

_MISSING = object()

for left, right in zip_longest(
    left_source,
    right_source,
    fillvalue=_MISSING,
):
    if left is _MISSING or right is _MISSING:
        handle_mismatch(left, right)
    else:
        process_pair(left, right)
~~~

A unique sentinel distinguishes padding from legitimate <code>None</code> values. This form preserves trailing data for explicit policy rather than truncating or raising immediately.

On an infinite input paired with a finite one, <code>zip_longest</code> is infinite. Finiteness again belongs to source contracts.

### 6.11.6 Unzipping and transposition

Given a finite materialised sequence of equal-size tuples:

~~~python
pairs = [(1, "a"), (2, "b"), (3, "c")]
numbers, letters = zip(*pairs)
~~~

Starred expansion turns each pair into one positional argument to zip, which then traverses columns. The outputs are tuples. For an empty <code>pairs</code>, there are no arguments and unpacking into two targets fails; the empty-case policy must be defined.

This idiom materialises argument expansion and is unsuitable for a huge or unbounded outer source. A streaming transpose generally requires buffering because later rows contribute to earlier output columns.

### 6.11.7 Enumerate is lazy and single-pass

<code>enumerate(source, start)</code> constructs an iterator. Each request obtains one source item and pairs it with the current count, then advances the count:

~~~python
numbered = enumerate(source, start=1)
~~~

The starting value must support the required integer-index conversion under the interface. Counts can grow beyond machine-word bounds under Python integer semantics, subject to actual resources.

An error from the underlying source prevents a pair for that step. The count observable on later manual resumption depends on when the implementation increments; do not design recovery around private internal count state.

### 6.11.8 Enumerate and filtered positions

These pipelines number different things:

~~~python
# Original source positions:
for position, value in enumerate(source):
    if admitted(value):
        process(position, value)

# Positions among admitted values:
for position, value in enumerate(
    value for value in source if admitted(value)
):
    process(position, value)
~~~

The first preserves original iteration position. The second assigns contiguous positions only after filtering. Both are correct under different specifications.

### Worked example 6.7C — Validate two-column input

~~~python
def pair_columns(names, scores):
    pairs = list(zip(names, scores, strict=True))

    result = []
    for row_number, (name, score) in enumerate(
        pairs,
        start=1,
    ):
        if not name:
            raise ValueError(
                f"row {row_number}: empty name"
            )
        if not 0 <= score <= 100:
            raise ValueError(
                f"row {row_number}: score outside range"
            )
        result.append((name, score))

    return result
~~~

Materialisation first establishes equal finite lengths before row validation begins. The function still returns no partial result when validation fails because <code>result</code> is local and never returned. External effects would require a separate atomicity argument.

> **Common misconception — “Strict zip checks lengths when zip is called.”**  
> Zip is lazy. Strictness is enforced as consumption discovers unequal exhaustion, possibly after earlier pairs and source effects.
