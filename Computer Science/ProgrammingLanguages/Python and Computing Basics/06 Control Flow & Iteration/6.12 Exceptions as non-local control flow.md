# 6.12 Exceptions as non-local control flow

An **exception** changes the ordinary next-operation rule. `raise` creates or propagates an exceptional control transfer. Python searches dynamically outward through active calls for a matching handler. During this search, frames and controlled resources are unwound according to language rules.

Exception handling separates the main success path from inability to honour its assumptions. It does not make failures exceptional in the everyday sense of rare. End of iteration uses an exception internally at the protocol boundary; file absence may be routine input policy; cancellation may be expected concurrency control.

### 6.12.1 Raising

```python
def reciprocal(value: float) -> float:
    if value == 0:
        raise ValueError("reciprocal is undefined for zero")
    return 1 / value
```

The function chooses `ValueError` because the type is admitted but the particular value violates the function’s domain. The exception message states the violated condition. A caller may handle this expected domain failure or permit it to propagate.

Assertions are not substitutes for validating external input:

```python
assert value != 0
```

`assert` expresses an internal condition believed true and can be disabled by optimisation settings. If zero is an admitted caller error requiring stable behaviour, raise an explicit exception.

### 6.12.2 Handling

```python
try:
    number = int(text)
except ValueError:
    print("not a decimal integer")
else:
    print("accepted", number)
finally:
    print("attempt complete")
```

The `try` suite contains operations whose specified exceptions are under consideration. An `except` suite handles a matching propagated exception. `else` runs only when the `try` suite completes without an exception; it keeps subsequent success-only operations out of the protected region. `finally` runs during ordinary completion, handled failure, unhandled propagation, `return`, `break`, or `continue`, subject to process termination and catastrophic conditions outside ordinary language guarantees.

Keep the `try` suite narrow. If unrelated code is included, a handler may catch the right exception type from the wrong operation and misdiagnose it.

### Worked example 6.8 — Narrow handling preserves ownership

```python
def parse_age(text: str) -> int:
    try:
        age = int(text)
    except ValueError as error:
        raise ValueError(f"invalid age text: {text!r}") from error

    if age < 0:
        raise ValueError("age must be non-negative")
    return age
```

The conversion failure is caught and translated into domain context. `raise ... from error` establishes explicit **exception chaining**, retaining the original cause in the traceback. The range check occurs outside the `try`; its `ValueError` already belongs to this function and must not be mistaken for conversion failure.

Catching `Exception` can be appropriate at a carefully chosen application boundary that records unexpected failure and terminates. It is usually wrong inside arbitrary low-level functions that cannot restore an invariant or add meaningful context.

### 6.12.3 Exceptions are objects in a hierarchy

Exception classes inherit from <code>BaseException</code>. Most application failures inherit from <code>Exception</code>. Direct <code>BaseException</code> subclasses include control-significant conditions such as <code>SystemExit</code>, <code>KeyboardInterrupt</code>, and <code>GeneratorExit</code>.

A handler matches an exception when the raised object is an instance of the named class or its subclass:

~~~python
try:
    operation()
except LookupError:
    handle_lookup_failure()
~~~

This catches built-in subclasses such as <code>KeyError</code> and <code>IndexError</code>. It does not catch every <code>Exception</code>.

Catch the narrowest semantic category the handler owns. A handler for <code>Exception</code> at a low level can intercept programming defects it cannot repair. A bare <code>except:</code> also catches process-exit and keyboard-interruption signals and is almost never appropriate outside a boundary that immediately preserves and re-raises them.

### 6.12.4 Handler order

Handlers are tested in source order, and the first matching clause runs:

~~~python
try:
    lookup()
except KeyError:
    handle_missing_key()
except LookupError:
    handle_other_lookup_failure()
~~~

Reversing the clauses makes the <code>KeyError</code> handler unreachable because the broader <code>LookupError</code> clause matches first. Arrange subclasses before their superclasses.

One clause can name a tuple:

~~~python
except (UnicodeError, OSError) as error:
    handle_input_failure(error)
~~~

This is appropriate only when the same recovery or translation is valid for every named category. Similar-looking messages do not establish common semantics.

### 6.12.5 The exception target

In:

~~~python
except ValueError as error:
    ...
~~~

the name <code>error</code> is temporarily bound to the caught exception object. Python clears the binding at the end of the handler to reduce reference cycles involving traceback frames. Do not rely on it afterwards:

~~~python
try:
    int("invalid")
except ValueError as error:
    message = str(error)

print(message)
~~~

Retain only the specific information needed. Storing exception objects can keep tracebacks, frames, local data, and large object graphs alive.

### 6.12.6 Bare raise

Within an active exception handler, bare <code>raise</code> re-raises the currently handled exception while preserving its traceback:

~~~python
try:
    operation()
except DomainError:
    record_failure()
    raise
~~~

Writing <code>raise error</code> raises the object again but can alter traceback presentation by adding the current raise location. Use bare raise for transparent propagation after local logging or rollback.

Outside an active exception context, bare raise produces <code>RuntimeError</code> because there is no exception to resume.

### 6.12.7 Implicit context and explicit cause

If handling one exception raises another, Python records the earlier exception as **context**:

~~~python
try:
    int(source)
except ValueError:
    raise ConfigurationError("invalid count")
~~~

Explicit chaining:

~~~python
except ValueError as error:
    raise ConfigurationError(
        "invalid count"
    ) from error
~~~

sets the earlier exception as the direct **cause**. The traceback presentation states that the new exception arose directly from it. This is preferable when translating abstraction layers.

Using <code>from None</code> suppresses display of implicit context:

~~~python
except KeyError:
    raise AttributeError(name) from None
~~~

The underlying context remains inspectable on the exception object but is omitted from the default displayed chain. Suppress only when lower-level detail would confuse the public abstraction and remains available where diagnostics require it.

### 6.12.8 Exception notes

Modern Python exception objects support additional notes through <code>add_note</code>:

~~~python
try:
    process(record)
except ValueError as error:
    error.add_note(
        f"record identifier: {record.identifier}"
    )
    raise
~~~

Notes add context without changing exception type or replacing the original traceback. They can accumulate across layers. As with messages, never attach uncontrolled secrets or enormous user data.

### 6.12.9 Exception groups

Concurrent or batch operations can fail in several independent ways. <code>ExceptionGroup</code> and <code>BaseExceptionGroup</code> represent several exceptions as one tree. The <code>except*</code> syntax handles matching subgroups:

~~~python
try:
    raise ExceptionGroup(
        "batch failed",
        [
            ValueError("record 1"),
            OSError("record 2"),
        ],
    )
except* ValueError as group:
    handle_value_failures(group)
except* OSError as group:
    handle_io_failures(group)
~~~

Unlike ordinary handlers, several <code>except*</code> clauses can each handle disjoint matching parts from one group. Unhandled subexceptions are merged and continue propagating. The group structure preserves concurrency rather than pretending failures occurred sequentially.

Exception groups are particularly relevant to task groups in asynchronous code, treated in Chapter 14. A beginner should first master ordinary propagation; the group model extends, rather than replaces, it.

### 6.12.10 Assertions

The statement:

~~~python
assert invariant, "explanation"
~~~

is conceptually equivalent, when assertion checking is enabled, to testing the condition and raising <code>AssertionError</code> if false. Optimised execution can remove assertion code.

Appropriate uses:

- internal conditions that correct program construction should guarantee;
- proof checkpoints during development;
- unreachable-state documentation backed by tests.

Inappropriate uses:

- validating untrusted user input;
- enforcing access control;
- checking a required external resource;
- performing an effect needed by the program;
- replacing a public exception contract.

If disabling the assertion changes correct behaviour or security, it was not merely an assertion.

### 6.12.11 Warnings are not ordinary exceptions

The <code>warnings</code> module emits advisory records governed by filters. Warnings can be displayed once, ignored, repeated, or converted into exceptions by policy. They are suitable for deprecation, questionable but admitted use, and environmental concerns.

A warning should not replace failure when the operation cannot satisfy its postcondition. Conversely, raising an exception for every advisory compatibility concern can make gradual migration impossible. The interface owner chooses severity and consumers configure policy.

### 6.12.12 EAFP and LBYL

Two styles are often named:

- **EAFP**: “easier to ask forgiveness than permission”—attempt the operation and handle a defined failure;
- **LBYL**: “look before you leap”—test a condition before attempting.

EAFP can avoid duplicated lookup and time-of-check/time-of-use races:

~~~python
try:
    value = mapping[key]
except KeyError:
    handle_absence()
~~~

LBYL can be clearer when the test is cheap, stable, and part of ordinary branching:

~~~python
if key in mapping:
    value = mapping[key]
else:
    handle_absence()
~~~

Neither slogan decides correctness. If another actor can mutate state between check and use, LBYL may race. If the attempted operation can raise the same exception for a different internal reason, an overbroad EAFP region may misclassify. Minimise the protected operation and understand atomicity.

### 6.12.13 Exception-safe state changes

An operation has levels of **exception safety**:

- **no guarantee:** failure can leave invariants broken;
- **basic guarantee:** invariants hold and resources do not leak, but state may change;
- **strong guarantee:** failure leaves observable state unchanged;
- **no-fail guarantee:** the operation promises not to fail under admitted preconditions.

Python’s assignment and mutable operations do not automatically provide the strong guarantee. Build new state separately:

~~~python
updated = current.copy()
apply_changes(updated)
validate(updated)
current = updated
~~~

The final name rebinding is a narrow commit for in-process state. It does not make external I/O transactional, and aliases to the previous object retain the old state.

### 6.12.14 Custom exception design

Define a domain exception hierarchy when callers need to distinguish failures independent of low-level mechanism:

~~~python
class CensusError(Exception):
    """Base class for census-domain failures."""


class InvalidRecordError(CensusError):
    """A record violates the input contract."""


class DuplicateIdentifierError(CensusError):
    """Two records claim one unique identifier."""
~~~

Catch the shared base when one policy handles every domain failure; catch subclasses when responses differ. Preserve lower-level causes with chaining. Do not create a new class for every message if callers never need the distinction.

Exception objects can carry structured attributes:

~~~python
class InvalidRecordError(CensusError):
    def __init__(
        self,
        line_number: int,
        reason: str,
    ) -> None:
        self.line_number = line_number
        self.reason = reason
        super().__init__(
            f"line {line_number}: {reason}"
        )
~~~

Structured fields support logging and tests without parsing human message text.

### 6.12.15 Catch at the boundary that can act

A handler is justified when it can:

1. restore an invariant;
2. retry under a safe and bounded policy;
3. translate into a higher-level contract;
4. add material context and re-raise;
5. convert to an explicitly designed result state;
6. record and terminate at an application boundary.

“Prevent the program from crashing” is incomplete. Continuing from corrupted or misunderstood state can be worse than termination. The handler owns a recovery claim and must prove it.

### Worked example 6.8A — Narrow translation and strong local commit

~~~python
class SettingsError(Exception):
    pass


def update_settings(
    current: dict[str, int],
    source: dict[str, str],
) -> dict[str, int]:
    proposed = current.copy()

    for name in ("width", "height"):
        try:
            value = int(source[name], 10)
        except KeyError as error:
            raise SettingsError(
                f"missing setting: {name}"
            ) from error
        except ValueError as error:
            raise SettingsError(
                f"setting {name} is not an integer"
            ) from error

        if value <= 0:
            raise SettingsError(
                f"setting {name} must be positive"
            )

        proposed[name] = value

    return proposed
~~~

The input mapping is not mutated. The shallow copy accumulates proposed changes. Any failure prevents return and leaves <code>current</code> structurally unchanged, satisfying a local strong guarantee for integer values. The caller chooses whether to rebind its state to the successful result.

> **Common misconception — “Exception handling is defensive wrapping around as much code as possible.”**  
> A broad protected region destroys failure provenance. Exception safety comes from narrow ownership, preserved invariants, and explicit commit boundaries.
