# 6.13 Exception propagation and stack unwinding

Consider:

```python
def parse_count(text: str) -> int:
    return int(text)


def load_count(fields: list[str]) -> int:
    return parse_count(fields[0])


def main() -> None:
    try:
        print(load_count(["unknown"]))
    except ValueError as error:
        print("invalid count:", error)


main()
```

`int("unknown")` raises `ValueError` inside `parse_count`. No matching handler exists there, so that call does not return normally. Its frame is unwound. `load_count` also has no handler, so its frame is unwound. `main` contains a matching handler around the call, so control enters that suite. After the handler, `main` completes normally.

The exception does not jump by source-file distance; it follows active dynamic calls. A function defined nearby but not active is irrelevant. The traceback records the active path.

A `return` in `finally` can suppress an active exception or earlier return value and is therefore usually a design error. Cleanup should preserve the primary control outcome unless the cleanup itself genuinely fails under a specified policy.

### 6.13.1 Dynamic handler search

Handler selection follows the active call chain, not lexical proximity in a file. If function A calls B, which calls C, and C raises, Python:

1. inspects handlers dynamically active in C;
2. if none matches, begins unwinding C;
3. executes required cleanup associated with leaving C;
4. inspects the active call site in B;
5. repeats until a matching handler is found or the interpreter boundary is reached.

A handler defined inside a function that was never called is irrelevant. A handler textually below the raising statement can be relevant only if its <code>try</code> suite dynamically encloses that execution.

### 6.13.2 Frame unwinding

**Stack unwinding** is the orderly removal of active execution frames during abrupt transfer. Local bindings in an unwound frame cease to be active roots, though referenced objects survive if retained elsewhere or by the traceback.

Cleanup mechanisms executed during unwinding include:

- <code>finally</code> suites;
- context-manager exit methods;
- generator delegation and closure rules in relevant cases.

Destructors are not a substitute for this structured cleanup. Unwinding is a control-flow rule; garbage collection is an object-reachability mechanism.

### 6.13.3 Finally preserves a pending outcome unless replaced

When entering <code>finally</code>, there may be a pending:

- normal continuation;
- return value;
- break destination;
- continue destination;
- active exception.

If the finally suite completes normally, the pending outcome resumes. If finally itself executes another abrupt transfer, the new outcome replaces the old one:

~~~python
def defective() -> int:
    try:
        return 1
    finally:
        return 2
~~~

The function returns 2. The original return is suppressed. Similarly, a new exception from cleanup can replace an active primary exception, although Python records context.

Avoid <code>return</code>, <code>break</code>, or <code>continue</code> in finally because they obscure the primary outcome. Newer Python compilers can warn about some such patterns as language versions evolve.

### 6.13.4 Cleanup failure policy

Suppose both an operation and its cleanup fail:

~~~python
try:
    perform()
finally:
    release()
~~~

If <code>perform</code> raises A and <code>release</code> raises B, B is the propagating exception and A becomes context. This preserves evidence but changes which failure callers catch.

Robust resource abstractions decide:

- whether cleanup can be retried;
- whether failure means the resource state is unknown;
- how both failures are recorded;
- whether later operations are prohibited;
- which exception becomes public.

Silently suppressing cleanup failure can hide lost writes or locks. Replacing every primary error with a generic cleanup message can hide the initiating defect.

### 6.13.5 Traceback ownership and retention

An exception’s traceback links frames that can retain local objects. Long-lived storage of exceptions can therefore retain sensitive data and substantial memory:

~~~python
failures.append(error)
~~~

For durable records, extract bounded structured facts—type, message, domain identifier, and formatted traceback under a redaction policy—rather than retain every live traceback object indefinitely.

The <code>traceback</code> module formats and manipulates traceback information. Logging systems can record exceptions without converting their human messages into machine identifiers.

### 6.13.6 Exception state inside handlers

Within an ordinary handler, <code>sys.exception()</code> in modern Python returns the currently handled exception:

~~~python
import sys

try:
    int("invalid")
except ValueError:
    current = sys.exception()
    print(type(current).__name__)
~~~

<code>sys.exc_info()</code> exposes a compatible triple including type, value, and traceback. These are diagnostic interfaces; passing the exception explicitly to helper functions is usually clearer than relying on dynamic exception state.

### Worked example 6.8B — Unwinding order

~~~python
def inner(events: list[str]) -> None:
    try:
        events.append("inner work")
        raise ValueError("failure")
    finally:
        events.append("inner cleanup")


def outer(events: list[str]) -> None:
    try:
        inner(events)
    except ValueError:
        events.append("outer handler")
    finally:
        events.append("outer cleanup")


events: list[str] = []
outer(events)
print(events)
~~~

The order is:

~~~text
[
    'inner work',
    'inner cleanup',
    'outer handler',
    'outer cleanup',
]
~~~

Inner cleanup runs while the exception is leaving the inner frame. The outer handler then handles it. The outer finally executes as its try statement completes. Dynamic nesting, not source-file line distance, determines the sequence.

### 6.13.7 Exception boundaries

An **exception boundary** is a layer where failures are deliberately translated, logged, converted to protocol responses, or allowed to terminate a unit of work. Typical boundaries include:

- a library public API;
- one command invocation;
- one web request;
- one background job;
- one concurrent task group;
- a process supervisor interface.

Below the boundary, exceptions preserve detailed causes. At the boundary, they become a stable domain error, exit status, HTTP response, failed task record, or restart signal. Catching earlier without action fragments ownership; catching later can leak implementation details.

> **Common misconception — “Propagation skips intermediate functions.”**  
> Their ordinary remaining statements are skipped, but their frames are unwound and every active structured cleanup boundary is processed.
