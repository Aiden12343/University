# 6.14 Exceptions versus result values

Not every alternative outcome should be an exception. An interface can use:

- a distinguished ordinary result such as `None` for expected absence;
- a tagged result object carrying success or failure information;
- an exception when normal completion cannot satisfy the operation’s contract.

Choice depends on meaning and composition. Dictionary lookup with `.get` can return a default for absence; subscription with `mapping[key]` raises `KeyError` because the operation demands that key. The two interfaces support different caller intentions.

### Worked example 6.9 — Do not erase failure detail

```python
def read_optional_text(path):
    try:
        return path.read_text(encoding="utf-8")
    except OSError:
        return None
```

This collapses missing file, permission denial, directory misuse, disconnected storage, and other operating failures into one `None`. It is valid only if the caller’s contract intentionally treats all those states as equivalent absence. Otherwise catch a narrower exception, preserve error detail, or let the failure propagate.

Error handling is information design. Every conversion from exception to ordinary value discards distinctions unless they are carried elsewhere.

### 6.14.1 Outcome cardinality

First enumerate possible outcomes. A lookup might yield:

- found value;
- ordinary absence;
- invalid key syntax;
- unavailable storage;
- permission denial;
- internal corruption.

Returning <code>None</code> for all five non-success paths collapses information. Raising for ordinary absence can burden callers that expect frequent misses. The interface should preserve distinctions relevant to caller action.

### 6.14.2 Optional result

An optional result is suitable when absence is one expected, unelaborated alternative:

~~~python
def find_even(values: list[int]) -> int | None:
    for value in values:
        if value % 2 == 0:
            return value
    return None
~~~

If <code>None</code> can be a legitimate found value, this representation is ambiguous. Use a sentinel, index, tagged record, or exception.

### 6.14.3 Tagged result

A **tagged result** represents alternatives explicitly:

~~~python
from dataclasses import dataclass


@dataclass(frozen=True)
class Success:
    value: int


@dataclass(frozen=True)
class Failure:
    reason: str


def parse_count(text: str) -> Success | Failure:
    try:
        value = int(text, 10)
    except ValueError:
        return Failure("not decimal integer text")

    if value < 0:
        return Failure("count is negative")

    return Success(value)
~~~

Dataclasses are developed in Chapter 11 and union typing in Chapter 12. The minimal model is that the returned object’s class tags the branch and carries structured data.

Result values make alternatives visible in ordinary control and can be collected in batch processing. They can also be ignored accidentally unless types and review enforce handling. Exceptions propagate automatically until owned.

### 6.14.4 Exceptions for contract failure

An exception is suitable when the requested operation cannot return its promised ordinary result:

~~~python
def require_record(identifier: str) -> Record:
    ...
~~~

The name “require” and return type promise a record. Absence cannot be represented honestly as a record, so a domain exception is coherent. A separate <code>find_record</code> can return <code>Record | None</code> for exploratory lookup.

Providing both interfaces lets callers choose semantics without catching exceptions as a routine probing mechanism.

### 6.14.5 Status codes

Low-level C interfaces often return status integers and place results elsewhere. In Python, an untagged status can be ignored or confused with data:

~~~python
status = perform()
~~~

If zero means success and non-zero values encode failures, callers must consult a separate table and remember to branch. Exceptions or typed result objects usually express richer Python APIs. Process exit statuses remain appropriate at the operating-system boundary.

### 6.14.6 Batch validation

Fail-fast validation raises on the first defective record. Accumulating validation returns all independently detectable defects:

~~~python
def validate_records(records):
    errors = []

    for position, record in enumerate(records, start=1):
        errors.extend(validate_one(position, record))

    return errors
~~~

Accumulation is useful when a user can repair several fields together. It is inappropriate when later checks depend on trusted invariants established by earlier ones or when continuing could cause unsafe effects.

Exception groups can preserve several raised failures from concurrent or independent operations. A list of validation records may be simpler for anticipated data defects.

### 6.14.7 Retry outcomes

A retry policy must classify failures as:

- permanent under unchanged input;
- transient and safe to retry;
- unknown;
- already partially committed.

Catching <code>Exception</code> and retrying can repeat a non-idempotent effect:

~~~python
for attempt in range(3):
    try:
        charge_account()
        break
    except Exception:
        continue
~~~

If the charge committed but acknowledgement failed, retry can charge again. Safe retry requires an idempotency key, transaction status query, or operation-specific guarantee—not merely a loop.

### Worked example 6.9A — Three lookup interfaces

~~~python
_MISSING = object()


def contains(mapping, key) -> bool:
    return key in mapping


def find(mapping, key):
    return mapping.get(key, _MISSING)


def require(mapping, key):
    try:
        return mapping[key]
    except KeyError as error:
        raise LookupDomainError(
            f"required key absent: {key!r}"
        ) from error
~~~

The first returns a proposition. The second returns either the stored value or an identity sentinel. The third promises a value and translates absence into a domain failure. None is universally superior; each answers a different question.

### 6.14.8 Cancellation is not ordinary failure

Concurrent frameworks use cancellation exceptions to request that work stop and unwind. Broad handlers that convert cancellation into an ordinary fallback can make tasks unresponsive and violate shutdown guarantees.

Cancellation cleanup should release resources and then normally propagate the cancellation unless the abstraction explicitly owns suppression. Chapter 14 specifies concrete thread, process, and <code>asyncio</code> cancellation behaviour.

> **Common misconception — “Exceptions are for rare events and return values for common events.”**  
> Frequency matters for ergonomics and performance, but semantic ownership is decisive: does the operation have an ordinary result, and what information must compose across callers?
