# 6.15 Iteration, exceptions, and generator cleanup

Generator execution can be suspended inside `try`/`finally`. When a generator is explicitly closed, `GeneratorExit` is raised at its suspension point so cleanup can run. Relying on garbage collection to close an abandoned generator promptly is not portable resource management.

```python
def managed_sequence():
    print("acquire")
    try:
        yield 1
        yield 2
    finally:
        print("release")


iterator = managed_sequence()
print(next(iterator))
iterator.close()
```

The explicit close triggers the `finally` suite. For external resources, prefer a context manager whose ownership boundary is evident to the caller. A generator that holds a file open across yields imposes a lifetime contract on its consumer.

### 6.15.1 Resource lifetime can span suspension

~~~python
def lines(path):
    handle = open(path, encoding="utf-8")
    try:
        for line in handle:
            yield line
    finally:
        handle.close()
~~~

The file is acquired on first iteration, not generator construction. It remains open across every yield and suspended interval. If the consumer requests one line and retains the generator indefinitely, the resource remains owned.

The API must communicate this lifetime. A context manager returning an iterator can make caller ownership explicit:

~~~python
with open(path, encoding="utf-8") as handle:
    for line in handle:
        process(line)
~~~

Here the lexical <code>with</code> suite owns the open period. Context managers are formalised in Chapter 11.

### 6.15.2 Early consumer exit

A break from:

~~~python
for line in lines(path):
    if matches(line):
        break
~~~

does not itself express what should happen to the generator object. In CPython, temporary reference lifetimes can make cleanup appear immediate in some cases, but portable resource management must not depend on that observation.

Bind and close explicitly:

~~~python
generator = lines(path)
try:
    for line in generator:
        if matches(line):
            break
finally:
    generator.close()
~~~

or use <code>contextlib.closing</code> when appropriate. Better interface design can keep resource acquisition outside the yielded abstraction.

### 6.15.3 Closing delegated generators

When a generator delegates with <code>yield from</code>, closing the delegating generator attempts to close the active subiterator when it provides the appropriate method. Exceptions during delegated cleanup can propagate.

Delegation therefore transfers part of lifecycle control, not only item forwarding. A custom iterator lacking <code>close</code> cannot be assumed to release a resource through this protocol.

### 6.15.4 Finally executes on ordinary generator completion

The finally suite runs when:

- the generator reaches its normal end;
- a return terminates it;
- an exception leaves it;
- close successfully injects <code>GeneratorExit</code>;
- implementation finalisation eventually closes it under applicable rules.

Only the first four provide controlled program paths. Abrupt process termination can prevent all Python cleanup.

### 6.15.5 Exceptions after partial yields

~~~python
def convert(values):
    for value in values:
        yield int(value)
~~~

For <code>["1", "2", "bad"]</code>, consumers receive two integers before <code>ValueError</code>. The generator’s contract must say whether prefix items are valid despite later failure.

Aggregation without external effects:

~~~python
result = list(convert(source))
~~~

creates no returned partial list when conversion fails, though allocated intermediate objects become unreachable. Streaming to an external destination can commit prefix effects. Use staging or a transaction when all-or-nothing is required.

### 6.15.6 Iterator adapters and exception transparency

A well-designed transformation iterator usually propagates unexpected source exceptions rather than converting them to exhaustion:

~~~python
def squares(values):
    for value in values:
        yield value * value
~~~

If source iteration raises <code>OSError</code>, the adapter should not catch it and simply return, because doing so would present truncation as successful exhaustion. Translate only at an abstraction boundary with a documented failure type and preserved cause.

### 6.15.7 Generator finalisation during interpreter shutdown

At interpreter shutdown, global modules and names may already be partially cleared when generator finalisers execute. Cleanup relying on module globals can fail or become unpredictable. Explicitly close resource-owning generators while the application environment remains intact.

This is one reason context managers and application lifecycle managers dominate finalisation-based design in reliable systems.

### 6.15.8 Asynchronous generators

An asynchronous generator uses <code>async def</code> and <code>yield</code>, and is consumed with <code>async for</code>. Each resumption is awaitable and can interleave with other tasks. Early exit requires asynchronous closure through <code>aclose</code>; event loops provide hooks to finalise abandoned asynchronous generators.

This is a flagged forward definition. Chapter 14 derives coroutines, awaitables, tasks, event loops, cancellation, and asynchronous cleanup. The present principle already applies: suspension stretches resource lifetime across control transfers.

### Worked example 6.9B — Resource-neutral transformation

Prefer separating ownership:

~~~python
def admitted_lines(lines):
    for line_number, line in enumerate(lines, start=1):
        stripped = line.strip()
        if not stripped or stripped.startswith("#"):
            continue
        yield line_number, stripped


with open(path, encoding="utf-8") as handle:
    for line_number, text in admitted_lines(handle):
        process(line_number, text)
~~~

The transformation generator neither opens nor closes the resource. The surrounding context visibly owns the file lifetime. The generator still retains the file iterator while active, but its API does not claim resource creation.

> **Common misconception — “A generator’s finally makes resource management automatic.”**  
> It supplies a cleanup path when the generator is completed or closed. The caller must still establish when closure occurs.
