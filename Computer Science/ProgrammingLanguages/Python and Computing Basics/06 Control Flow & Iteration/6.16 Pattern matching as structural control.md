# 6.16 Pattern matching as structural control

Python’s `match` statement performs structural pattern matching. It is not a general replacement for `if`, and its `case` patterns are not ordinary equality expressions.

```python
def describe(command: object) -> str:
    match command:
        case ["move", int(x), int(y)]:
            return f"move to ({x}, {y})"
        case ["quit"]:
            return "quit"
        case _:
            return "invalid command"
```

The first pattern requires a three-element sequence whose first item matches literal `"move"` and whose later items match the `int` class patterns, binding `x` and `y`. The second matches a one-element sequence. `_` is a wildcard in this pattern context and binds no name.

Cases are attempted top to bottom; the first successful pattern whose optional guard is true supplies the suite. A bare name in a pattern usually captures rather than compares, which is a major source of mistaken assumptions. Named constants require qualified value patterns or other deliberate forms.

Pattern matching is useful when control depends on shape, decomposition, and type-like structure. A simple Boolean condition remains clearer for scalar predicates.

### 6.16.1 Match evaluates the subject once

~~~python
match obtain_command():
    case ...:
        ...
~~~

The subject expression is evaluated once before cases are attempted. Its resulting object is compared structurally against patterns from top to bottom. A successful pattern can bind names; an optional guard is then evaluated. The first pattern whose match succeeds and whose guard is true selects its suite.

<code>match</code> and <code>case</code> are soft keywords: their spelling is special in this grammar but can remain ordinary names elsewhere under the language rules.

### 6.16.2 Literal, wildcard, and capture patterns

~~~python
match status:
    case "ready":
        start()
    case "stopped":
        report_stop()
    case _:
        report_unknown(status)
~~~

Quoted strings are literal patterns. The underscore is a wildcard and binds nothing. A bare ordinary name is a capture:

~~~python
match status:
    case captured:
        print(captured)
~~~

This irrefutable case matches every subject and binds it. Placing another unguarded case afterwards is invalid or unreachable under the grammar because the capture already handles everything.

### 6.16.3 Value patterns require qualification

To compare with a named constant, use a qualified value pattern:

~~~python
import http

match status:
    case http.HTTPStatus.OK:
        handle_success()
~~~

A bare <code>OK</code> would normally capture rather than retrieve an existing binding. Pattern grammar deliberately makes qualification visually distinguish value lookup from capture.

The constants <code>None</code>, <code>True</code>, and <code>False</code> have singleton-pattern behaviour and compare by identity as specified.

### 6.16.4 Sequence patterns

~~~python
match command:
    case ["move", x, y]:
        move(x, y)
    case ["echo", *words]:
        echo(words)
    case []:
        no_command()
~~~

A sequence pattern decomposes an admitted sequence-like subject. String, bytes, and bytearray objects are deliberately excluded from ordinary sequence-pattern matching so text is not split into code points accidentally.

One starred subpattern can absorb zero or more items into a list. Exact patterns require exact length; starred patterns express minimum structure.

### 6.16.5 Mapping patterns

~~~python
match record:
    case {
        "kind": "user",
        "id": identifier,
        **remaining,
    }:
        process_user(identifier, remaining)
~~~

A mapping pattern requires the stated keys and binds their values. Additional keys are permitted unless captured with <code>**remaining</code>; unlike sequence patterns, mapping patterns do not require exact size by default.

The subject’s mapping operations can execute custom code. Pattern matching is not a side-effect-free structural oracle for arbitrary user-defined mappings.

### 6.16.6 Class patterns

~~~python
match event:
    case Point(x=0, y=y):
        print("vertical-axis point", y)
~~~

A class pattern first applies an instance relationship and then matches named attributes. Positional class subpatterns are mapped through the class’s <code>__match_args__</code> contract:

~~~python
case Point(0, y):
    ...
~~~

The class controls which attributes positional patterns mean. Attribute access can use properties or descriptors and can raise or produce effects. A class pattern is protocol-driven, not raw-memory destructuring.

### 6.16.7 Or patterns

An OR pattern uses <code>|</code>:

~~~python
match command:
    case ["quit"] | ["exit"]:
        stop()
~~~

Alternatives must bind the same set of names so the selected suite has a consistent namespace:

~~~python
case ["load", path] | ["open", path]:
    use(path)
~~~

An alternative binding <code>path</code> on only one side would leave the suite’s state ambiguous and is rejected.

### 6.16.8 As patterns

An <code>as</code> pattern binds the whole matched subject or substructure in addition to components:

~~~python
match record:
    case {"id": identifier, "value": value} as complete:
        audit(complete)
        process(identifier, value)
~~~

This preserves the original mapping object; it does not copy. Mutation through <code>complete</code> affects the same subject.

### 6.16.9 Guards

A guard follows a pattern:

~~~python
match point:
    case (x, y) if x == y:
        describe_diagonal(x)
    case (x, y):
        describe_other(x, y)
~~~

The guard runs only after its pattern succeeds and its capture names are bound. If false, matching proceeds to later cases. Guards can have effects or raise, so their order matters.

Do not rely on the values of names after a failed pattern or guard outside the selected suite. The language allows implementation freedom concerning partial bindings during failed matching. Use names only on controlled successful paths.

### 6.16.10 First match and subsumption

More general patterns can subsume later specific ones:

~~~python
match command:
    case [operation, *arguments]:
        handle(operation, arguments)
    case ["quit"]:
        stop()
~~~

The first pattern already matches <code>["quit"]</code>, so the second cannot be selected. Place specific cases before general ones or use a guard to exclude them.

This is analogous to overlapping <code>if</code> predicates, but pattern grammar can detect some irrefutable cases statically.

### 6.16.11 Matching is not complete validation

~~~python
case {"amount": int(amount), "currency": str(currency)}:
~~~

The class patterns establish runtime classes under match semantics. They do not prove amount is non-negative, currency is an admitted ISO code, extra fields are safe, or the record came from an authorised source. Pattern matching establishes structural facts; domain validation follows.

### Worked example 6.10 — Command algebra

Define commands:

- <code>["quit"]</code>;
- <code>["show", integer_identifier]</code>;
- <code>["move", integer_x, integer_y]</code>;
- anything else invalid.

~~~python
def interpret(command: object):
    match command:
        case ["quit"]:
            return ("quit",)
        case ["show", int(identifier)] if identifier >= 0:
            return ("show", identifier)
        case ["move", int(x), int(y)]:
            return ("move", x, y)
        case _:
            raise ValueError(
                f"invalid command: {command!r}"
            )
~~~

The list patterns validate arity and literal operation names. Class patterns require integers but also admit Boolean values because Boolean is an integer subclass. If Booleans are invalid, guards must reject them or a stricter domain type must be introduced. The show guard validates non-negativity; move coordinates intentionally admit negative integers.

### 6.16.12 Exhaustiveness

Python does not generally require a match statement to be exhaustive. If no case is selected and no wildcard exists, execution continues after the statement without an exception. This can be correct for optional handling and dangerous for a closed domain.

For a closed enumeration, include every case and a defensive unreachable assertion or wildcard according to static-analysis policy. Tests should fail when a new domain variant lacks handling.

> **Common misconception — “Match is a compact switch based on equality.”**  
> It is a structural pattern language with capture, decomposition, class protocols, alternatives, guards, and first-match priority.
