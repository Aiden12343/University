# 6.2 Conditional execution

An `if` statement selects exactly one suite from an ordered chain whose first true condition is encountered:

```python
if condition_a:
    suite_a
elif condition_b:
    suite_b
else:
    fallback_suite
```

Conditions are evaluated from top to bottom. Once one is true, its suite executes and later conditions in the same chain are not evaluated. The `else` suite requires no condition and executes only if every preceding condition is false. Both `elif` and `else` are optional.

### Worked example 6.1 — Classify a temperature without overlapping rules

```python
def classify_temperature(celsius: float) -> str:
    if celsius < 0:
        return "below freezing"
    elif celsius < 20:
        return "cool"
    elif celsius < 30:
        return "warm"
    else:
        return "hot"
```

For an input of 25, the first condition is false, the second is false, and the third is true, so the function returns `"warm"`. The third condition does not need to restate `celsius >= 20`; reaching it already establishes the negation of the second condition. The ordered structure partitions the numeric line into:

- (c<0);
- (0\leq c<20);
- (20\leq c<30);
- (c\geq30).

The boundaries belong to the specification. Changing `< 30` to `<= 30` changes classification of exactly 30. A reader should not infer whether 30 is “really” warm; the domain owner must decide.

Independent `if` statements differ from one `if`/`elif` chain:

```python
if score >= 70:
    print("distinction")
if score >= 40:
    print("pass")
```

At 80 both messages print because each condition is evaluated. That may be correct if distinction entails both labels. If categories must be exclusive, an ordered chain expresses that contract.

> **Common misconception — “`elif` means another separate `if`.”**  
> It belongs to one selection chain. Its condition is considered only when every earlier condition in that chain was false.

### 6.2.1 Conditions are expressions evaluated at a time

An <code>if</code> condition is an expression. Python evaluates it, applies truth testing to the resulting object, and either enters or skips the associated suite. The condition can call functions, mutate state, consume an iterator, or raise:

~~~python
if queue.pop():
    process()
~~~

This both removes an item and truth-tests it. An empty-list item would suppress <code>process</code> despite having been consumed, and an empty queue could raise. Separating the steps exposes the state transition:

~~~python
item = queue.pop()
if item:
    process()
~~~

Better still, state the intended empty-item and empty-queue policies explicitly.

### 6.2.2 Ordered predicates form residual domains

Each failed condition restricts the domain reaching the next clause. For:

~~~python
if value < 0:
    category = "negative"
elif value == 0:
    category = "zero"
else:
    category = "positive"
~~~

the second clause runs only under (value\geq0), and its equality test selects zero. The <code>else</code> residual is (value>0), assuming an ordinary totally ordered numeric value.

If <code>value</code> can be NaN, all three comparisons <code>value &lt; 0</code>, <code>value == 0</code>, and the implied positive conclusion behave differently: the <code>else</code> path is reached even though NaN is not positive. A partition proof must include the exact admitted domain.

### 6.2.3 Completeness and disjointness

A categorical selection is **complete** when every admitted input reaches a category. It is **disjoint** when no admitted input belongs to more than one category under the intended model.

An <code>if</code>/<code>elif</code> chain always selects at most one suite, but the predicates themselves can overlap:

~~~python
if score >= 40:
    category = "pass"
elif score >= 70:
    category = "distinction"
~~~

The second suite is unreachable because every score at least 70 already satisfies the first condition. Reordering repairs the exclusive priority policy:

~~~python
if score >= 70:
    category = "distinction"
elif score >= 40:
    category = "pass"
else:
    category = "fail"
~~~

Predicate disjointness is not required when order intentionally establishes priority, but overlapping regions and priority must be documented.

### Worked example 6.1A — Prove an interval classifier

Specification for an integer percentage (p):

- reject outside ([0,100]);
- fail for ([0,40));
- pass for ([40,70));
- distinction for ([70,100]).

~~~python
def classify_percentage(percentage: int) -> str:
    if not 0 <= percentage <= 100:
        raise ValueError("percentage outside [0, 100]")
    if percentage >= 70:
        return "distinction"
    if percentage >= 40:
        return "pass"
    return "fail"
~~~

After validation, the admitted domain is ([0,100]). The first successful category guard selects ([70,100]). Failure establishes ([0,70)), and the next guard selects ([40,70)). Its failure leaves ([0,40)). The returns make the categories exclusive without <code>elif</code>; dominance and abrupt completion carry the residual facts.

Boundary tests are -1, 0, 39, 40, 69, 70, 100, and 101. Interior samples alone cannot expose inequality mistakes at transitions.

### 6.2.4 Guard clauses

A **guard clause** rejects or completes a special path near function entry:

~~~python
def ratio(numerator: float, denominator: float) -> float:
    if denominator == 0:
        raise ValueError("denominator must be non-zero")
    return numerator / denominator
~~~

The guard makes the main path less indented and establishes a dominating precondition. Several independent guards are suitable when each violation should terminate immediately:

~~~python
if not isinstance(count, int):
    raise TypeError("count must be an integer")
if isinstance(count, bool):
    raise TypeError("count must not be Boolean")
if count < 0:
    raise ValueError("count must be non-negative")
~~~

Order affects the reported failure. Because Boolean is an integer subclass, testing the general integer condition before the Boolean exclusion still admits it through that first guard; the following explicit Boolean guard rejects it. A different arrangement can express the same final domain but produce different diagnostics.

### 6.2.5 Nested conditions represent dependent questions

Nested <code>if</code> statements are appropriate when the second question is meaningful only after the first:

~~~python
if user is not None:
    if user.is_active:
        grant_access(user)
~~~

A Boolean conjunction can be equivalent under stable values:

~~~python
if user is not None and user.is_active:
    grant_access(user)
~~~

Short-circuiting prevents attribute access on <code>None</code>. The nested form provides space for distinct failure handling or intermediate explanation. Choose structure according to the conceptual decision tree, not line count.

### 6.2.6 Empty suites and deliberate no-action

A branch sometimes intentionally performs no operation:

~~~python
if event.kind == "heartbeat":
    pass
else:
    process(event)
~~~

<code>pass</code> satisfies grammar and documents the deliberate empty path only weakly. A comment should state why ignoring the event is correct, or the condition can often be inverted:

~~~python
if event.kind != "heartbeat":
    process(event)
~~~

Silent no-action is itself behaviour. For security events, malformed records, and financial operations, ignoring may require audit or metrics rather than <code>pass</code>.

### 6.2.7 Conditional assignment and definite binding

This source does not bind <code>message</code> on every path:

~~~python
if error:
    message = "failed"

print(message)
~~~

When <code>error</code> is false and no earlier binding exists, lookup raises. Repair by covering the domain:

~~~python
message = "failed" if error else "succeeded"
~~~

or:

~~~python
if error:
    message = "failed"
else:
    message = "succeeded"
~~~

Initialising <code>message = None</code> before the conditional can establish binding but may widen the domain unnecessarily. Definite assignment should reflect a genuine state, not merely silence analysis.

### 6.2.8 Side effects in conditions

Repeatedly calling a condition can observe different state:

~~~python
if read_status() == "ready":
    ...
elif read_status() == "waiting":
    ...
~~~

The two calls may consume input or return values from different times. Sample once when classification concerns one observation:

~~~python
status = read_status()
if status == "ready":
    ...
elif status == "waiting":
    ...
~~~

Conversely, do not sample once when the specification requires a fresh check after an intervening operation. Temporal identity of the observation is part of the contract.

### 6.2.9 Conditions and type narrowing

Control-flow facts can narrow possible types:

~~~python
def length_or_zero(text: str | None) -> int:
    if text is None:
        return 0
    return len(text)
~~~

The second return is dominated by failure of the <code>None</code> test, so <code>text</code> is a string under the annotation contract. Static analysers model such paths.

Mutation and aliasing can invalidate refinements on mutable attributes:

~~~python
if record.value is not None:
    callback()
    use(record.value)
~~~

If <code>callback</code> can set <code>record.value</code> to <code>None</code>, the earlier check does not justify the later use. Save an immutable local snapshot when the operation concerns the checked value:

~~~python
value = record.value
if value is not None:
    callback()
    use(value)
~~~

### 6.2.10 Decision tables

When several independent Boolean factors interact, nested conditions can hide missing combinations. A **decision table** enumerates conditions and outcomes.

For access depending on authentication (A), account activity (B), and required role (R):

| A | B | R | Outcome |
|:---:|:---:|:---:|:---|
| false | any | any | request authentication |
| true | false | any | deny inactive account |
| true | true | false | deny insufficient role |
| true | true | true | grant |

“Any” denotes a condition irrelevant after an earlier decisive fact. Translate the priority:

~~~python
if not authenticated:
    request_authentication()
elif not active:
    deny_inactive()
elif not has_required_role:
    deny_role()
else:
    grant()
~~~

The table provides a completeness oracle and makes priority reviewable.

> **Common misconception — “An else branch means all previous predicates have mathematical opposites.”**  
> It means their truth tests did not select a suite. Inferring a positive domain fact requires proof that the predicates partition the admitted values.
