# 6.4 `while`: repetition under a predicate

A `while` statement repeatedly truth-tests its condition and executes its body while the condition is true:

```python
while condition:
    body
```

The body may execute zero times if the initial condition is false. A correct loop requires more than valid syntax:

1. a state from which the condition is evaluated;
2. an invariant required at a chosen loop boundary;
3. progress towards termination, unless non-termination is intentional;
4. a postcondition obtained when the condition becomes false.

### Worked example 6.2 — Decimal digit count

Specification: for non-negative integer `number`, return the number of decimal digits; zero has one digit.

```python
def decimal_digit_count(number: int) -> int:
    if number < 0:
        raise ValueError("number must be non-negative")

    remaining = number
    digits = 1

    while remaining >= 10:
        remaining //= 10
        digits += 1

    return digits
```

For `number = 5072`, trace:

| Loop boundary | `remaining` | `digits` |
|---:|---:|---:|
| before first test | 5072 | 1 |
| after iteration 1 | 507 | 2 |
| after iteration 2 | 50 | 3 |
| after iteration 3 | 5 | 4 |

Invariant: at every test, `digits` plus the number of further base-ten divisions needed to reduce `remaining` below 10 equals the digit count of the original number. A more algebraic relationship can be stated using powers of ten, but the operational invariant suffices at this level.

Termination: when `remaining >= 10`, floor division by 10 yields a smaller non-negative integer. A strictly decreasing non-negative integer cannot decrease forever. On exit, `remaining < 10`, so no further digit position remains and `digits` is the required count.

Initialising `digits = 1` handles zero without a special loop execution because zero’s representation contains one digit. Representation conventions influence algorithms.

### Infinite loops

A loop is **infinite** when execution continues its repetitions without reaching an exit. Some infinite loops are intentional, such as an event loop serving requests until externally stopped. Others arise because the condition cannot become false, the progress variable is updated in the wrong direction, or a state transition is omitted.

```python
remaining = 3
while remaining > 0:
    print(remaining)
    remaining += 1
```

Over mathematical integers, `remaining` grows and the condition stays true. CPython integers grow subject to memory, so the practical execution may eventually fail from resource exhaustion rather than complete. “The loop never ends” is an algorithmic claim; “the process runs forever” is physically impossible and semantically less precise.

### 6.4.1 The three loop proof obligations

Let (I) be an invariant, (C) the loop condition, and (B) the body. To prove partial correctness:

1. **Initialisation:** the precondition implies (I) before the first test.
2. **Preservation:** if (I\land C) holds before an iteration and the body completes normally, (I) holds before the next test.
3. **Exit use:** (I\land\neg C) implies the desired postcondition.

To prove total correctness, also supply a variant drawn from a well-founded set that strictly decreases on every continuing iteration.

A **well-founded relation** has no infinite descending chain. Non-negative integers under ordinary less-than form the most common beginner variant domain. A quantity merely changing is insufficient; it must progress under a relation that cannot descend forever.

### 6.4.2 Worked proof of repeated addition

Specification: for non-negative integers (a) and (b), compute (ab) using repeated addition.

~~~python
def multiply(a: int, b: int) -> int:
    if a < 0 or b < 0:
        raise ValueError("operands must be non-negative")

    remaining = b
    product = 0

    while remaining > 0:
        product += a
        remaining -= 1

    return product
~~~

Invariant:

\[
\text{product} + a\times\text{remaining} = a\times b
\quad\land\quad
0\leq\text{remaining}\leq b.
\]

Initialisation: product is zero and remaining is (b), so the left expression is (0+ab=ab).

Preservation: assume the invariant and remaining positive. The body sets:

\[
\text{product}'=\text{product}+a,\qquad
\text{remaining}'=\text{remaining}-1.
\]

Then:

\[
\text{product}' + a\text{remaining}'
=(\text{product}+a)+a(\text{remaining}-1)
=\text{product}+a\text{remaining}
=ab.
\]

The bounds remain valid. Variant: remaining is a positive integer before each continuing iteration and decreases by one. Exit establishes remaining zero, so the invariant reduces to product (=ab).

This proof explains every initial value and update. Testing several products supplies additional implementation evidence but is not the universal argument.

### 6.4.3 Loop invariants describe boundaries, not aspirations

“The answer becomes correct” is not an invariant. It is a goal. A useful invariant:

- is true at a named boundary;
- relates current state to original input;
- is strong enough to yield the postcondition at exit;
- is weak enough to hold initially;
- survives every back edge.

For linear search:

~~~python
index = 0
while index < len(values) and values[index] != target:
    index += 1
~~~

an invariant is:

\[
0\leq\text{index}\leq \operatorname{len}(\text{values})
\quad\land\quad
\text{target does not occur in values}[0:\text{index}].
\]

On exit, either index equals length, proving absence from the whole sequence, or the second condition is false because the current item equals target. The loop condition’s order prevents out-of-range subscription.

### 6.4.4 Off-by-one analysis

An **off-by-one error** misplaces a discrete boundary by one unit. Such defects arise from uncertainty about whether a bound is inclusive, whether state counts processed or remaining items, and whether update occurs before or after use.

For processing indices ([0,n)):

~~~python
index = 0
while index < length:
    process(index)
    index += 1
~~~

The invariant includes (0\leq index\leq length), and <code>index</code> counts already processed positions. Before processing, the condition ensures (index<length), so subscription is valid. After increment, exactly one additional position belongs to the processed prefix.

Using <code>index &lt;= length</code> attempts position (n), outside the half-open interval. Initialising to one omits position zero. Boundary algebra prevents both errors more reliably than visual intuition.

### 6.4.5 Sentinel-controlled loops

A **sentinel-controlled loop** stops when input equals a distinguished terminator:

~~~python
total = 0

while True:
    text = input("integer or END: ")
    if text == "END":
        break
    total += int(text)
~~~

The sentinel is text and must be checked before integer parsing. Empty input, end-of-file, and malformed numeric text remain distinct conditions. If <code>"END"</code> can be legitimate data, it is not a valid unescaped sentinel; use a length-delimited protocol or external termination signal.

The unconditional <code>while True</code> states that termination arises from an internal event rather than the loop header. Its proof must show that admitted finite interaction eventually supplies the sentinel or another exit. Without that environmental assumption, termination is not guaranteed.

### 6.4.6 Priming reads and duplicated input

Older loop patterns perform a **priming read** before the loop and repeat the read at the end:

~~~python
text = input("value: ")
while text != "END":
    process(text)
    text = input("value: ")
~~~

This has one header condition but duplicates the input operation. An exception or <code>continue</code> added before the bottom read can prevent progress. The unconditional loop with one read and explicit sentinel break often centralises the state transition more safely.

Do not choose mechanically. If the condition can be calculated naturally from existing state and every body path updates that state, a condition-controlled <code>while</code> is clearer.

### 6.4.7 Validation loops

A validation loop repeatedly requests input until one candidate satisfies the contract:

~~~python
while True:
    text = input("percentage [0..100]: ")
    try:
        percentage = int(text, 10)
    except ValueError:
        print("enter a decimal integer")
        continue

    if not 0 <= percentage <= 100:
        print("value is outside [0, 100]")
        continue

    break
~~~

There are three outcomes per iteration:

1. representation invalid: diagnostic and next request;
2. integer outside domain: different diagnostic and next request;
3. valid: break with <code>percentage</code> bound to an admitted value.

The postcondition after the loop is (percentage\in[0,100]). Termination depends on the user or input source eventually supplying valid text; the program cannot prove that environmental liveness assumption.

### 6.4.8 Floating-point loop conditions

Accumulating a float towards an equality boundary is unreliable:

~~~python
value = 0.0
while value != 1.0:
    value += 0.1
~~~

Binary approximation can skip exact 1.0, causing continued iterations. Use an integer count when repetition count is discrete:

~~~python
for step in range(11):
    value = step / 10
    process(value)
~~~

If a numerical iterative algorithm genuinely uses floating convergence, stop under a mathematically justified tolerance, iteration bound, residual measure, and non-finite-value policy. “Close enough” requires a domain error model.

### 6.4.9 Multiple progress variables

A loop can progress under a lexicographic variant. A pair ((a,b)) decreases lexicographically when either (a) decreases, or (a) stays equal while (b) decreases.

Suppose work is organised by pages and rows:

~~~python
page = 0
row = 0

while page < page_count:
    process(page, row)
    row += 1

    if row == rows_per_page:
        page += 1
        row = 0
~~~

A simple scalar remaining-work variant is:

\[
V=(\text{page_count}-\text{page})\times\text{rows_per_page}-\text{row},
\]

under positive fixed <code>rows_per_page</code>. Each iteration reduces (V) by one. Deriving the variant exposes invalid zero rows-per-page or mutation of page geometry.

### 6.4.10 Intentional non-termination and liveness

Servers, event loops, and operating-system services can be designed without an ordinary internal terminal state:

~~~python
while True:
    event = receive_event()
    dispatch(event)
~~~

Correctness then concerns:

- safety: no invalid state or unauthorised effect occurs;
- liveness: admitted events are eventually handled under scheduling assumptions;
- responsiveness: handling occurs within a bound or service objective;
- cancellation: an external stop request reaches a controlled exit;
- resource boundedness: state does not grow without policy.

An infinite-loop design still needs termination behaviour for deployment, tests, upgrades, and failure. Cancellation is part of its interface.

### 6.4.11 Watchdogs and iteration limits

An iteration limit converts uncertain convergence into a bounded outcome:

~~~python
maximum_iterations = 1_000
iteration = 0

while not converged(state):
    if iteration == maximum_iterations:
        raise RuntimeError("iteration limit reached")
    state = improve(state)
    iteration += 1
~~~

The limit proves bounded attempt count, not successful convergence. Its value needs evidence from problem scale and performance requirements. A watchdog based on wall-clock time introduces clock and scheduling dependencies; a deterministic iteration budget is often easier to test.

### Worked example 6.2A — Euclid’s algorithm with a variant

For non-negative integers (a,b), not both zero:

~~~python
def greatest_common_divisor(a: int, b: int) -> int:
    if a < 0 or b < 0:
        raise ValueError("operands must be non-negative")
    if a == 0 and b == 0:
        raise ValueError("gcd(0, 0) is undefined here")

    while b != 0:
        a, b = b, a % b

    return a
~~~

The set of common divisors is invariant because:

\[
\gcd(a,b)=\gcd(b,a\bmod b).
\]

For positive (b), the remainder satisfies (0\leq a\bmod b<b), so the new second component is a strictly smaller non-negative integer. It is the termination variant. At exit, (b=0), and (\gcd(a,0)=a), yielding the postcondition.

The simultaneous assignment obtains old (b) and old remainder before rebinding either name. Sequentially assigning <code>a = b</code> before calculating <code>a % b</code> would destroy the needed old dividend.

> **Common misconception — “A condition that eventually looks false proves a loop terminates.”**  
> Termination requires a state-transition argument: a well-founded variant progresses on every continuing path under stated environmental assumptions.
