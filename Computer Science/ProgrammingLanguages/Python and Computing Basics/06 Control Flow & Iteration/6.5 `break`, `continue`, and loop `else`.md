# 6.5 `break`, `continue`, and loop `else`

`break` exits the nearest enclosing loop immediately. `continue` ends the current iteration and returns control to the loop’s next test or item request. Both create additional control paths and must preserve the reasoning obligations at their destinations.

Python loops may have an `else` suite. It runs when the loop finishes normally—because a `while` condition becomes false or a `for` iterator is exhausted—but not when `break` exits the loop.

### Worked example 6.3 — Search with an honest not-found path

```python
def first_negative(values: list[int]) -> int | None:
    for value in values:
        if value < 0:
            return value
    return None
```

The direct `return` makes loop `else` unnecessary. To illustrate the construct while retaining an index:

```python
values = [4, 8, -3, 5]

for index, value in enumerate(values):
    if value < 0:
        print("found at", index)
        break
else:
    print("no negative value")
```

`else` corresponds to “no iteration executed `break`”, not “the condition of an `if` was false on the final iteration”. For an empty sequence the iterator is immediately exhausted and `else` runs.

Excessive `continue` can fragment a loop invariant because multiple routes lead to the next boundary. Guard clauses can still improve clarity when they remove exceptional cases early:

```python
total = 0
for text in fields:
    stripped = text.strip()
    if not stripped:
        continue
    total += int(stripped)
```

The invariant at the loop boundary is that `total` equals the sum of all admitted non-empty fields processed so far. Both the `continue` route and the addition route must preserve it.

### 6.5.1 Break changes the postcondition

After a loop containing <code>break</code>, normal control can arrive for at least two reasons:

- the loop condition became false or the iterator exhausted;
- a break condition was selected.

These paths can establish different facts:

~~~python
found = False

for value in values:
    if matches(value):
        found = True
        break
~~~

After exhaustion, <code>found</code> remains false. After break, it is true. The auxiliary flag records the exit reason but duplicates information Python’s loop <code>else</code> can sometimes encode structurally.

### 6.5.2 Loop else is completion-without-break

~~~python
for value in values:
    if matches(value):
        result = value
        break
else:
    result = None
~~~

The <code>else</code> suite runs on iterator exhaustion, including immediate exhaustion of an empty iterable. It does not run after <code>break</code>. A <code>return</code> or propagating exception also prevents it because control does not reach normal loop completion.

For a <code>while</code> loop, <code>else</code> runs when the condition becomes false. It does not run when break terminates the loop:

~~~python
while attempts_remaining > 0:
    if operation_succeeds():
        break
    attempts_remaining -= 1
else:
    report_exhausted_attempts()
~~~

Here <code>else</code> means the success break never occurred before the attempt condition failed.

### 6.5.3 Return can be clearer than break

Inside a search function:

~~~python
def find(values, predicate):
    for value in values:
        if predicate(value):
            return value
    return None
~~~

The direct return expresses the whole function outcome. A break would require a later result binding or flag. Return is inappropriate if the function must perform shared post-loop work; in that case, centralising the later step may justify break.

Every early return creates an abrupt path through <code>finally</code> and context-manager cleanup. It does not skip language-managed unwinding.

### 6.5.4 Continue and invariant preservation

At a <code>continue</code>, control transfers to the next iteration boundary. Any state that the loop invariant requires must already be restored.

Defective:

~~~python
index = 0
while index < len(values):
    if values[index] < 0:
        continue
    process(values[index])
    index += 1
~~~

A negative item reaches <code>continue</code> without incrementing <code>index</code>, so the same item is examined forever. Centralise progress:

~~~python
index = 0
while index < len(values):
    value = values[index]
    index += 1

    if value < 0:
        continue

    process(value)
~~~

Now every path reaching continue has advanced the index. Direct <code>for</code> iteration is simpler if index mutation is otherwise unnecessary.

### 6.5.5 Nested loops

<code>break</code> and <code>continue</code> apply only to the nearest enclosing loop:

~~~python
for row in rows:
    for value in row:
        if value == target:
            break
~~~

The break exits the inner traversal but the outer loop continues with another row. To exit both, options include:

- return from an enclosing function;
- record a flag and test it outside;
- factor the inner search into a function;
- use an exception only when exceptional transfer is semantically appropriate;
- use generator composition and request the first result.

Named functions frequently produce the clearest ownership of multi-level exit.

### Worked example 6.3A — Prime classification with loop else

~~~python
from math import isqrt


def is_prime(number: int) -> bool:
    if number < 2:
        return False

    for divisor in range(2, isqrt(number) + 1):
        if number % divisor == 0:
            break
    else:
        return True

    return False
~~~

If a divisor is found, break prevents the loop else and the function returns false. If every candidate through (\lfloor\sqrt n\rfloor) is exhausted, no factor pair can exist: any composite (n=ab) has at least one factor no larger than (\sqrt n). The else path therefore returns true.

The initial guard handles 0, 1, and negative integers; an empty divisor range for 2 or 3 then exhausts normally and correctly returns true.

### 6.5.6 Finally and abrupt loop transfer

<code>break</code> and <code>continue</code> execute active <code>finally</code> suites before reaching their destination:

~~~python
for value in values:
    try:
        if should_skip(value):
            continue
        if should_stop(value):
            break
        process(value)
    finally:
        record_attempt(value)
~~~

Every entered iteration records its attempt on these ordinary control paths. If <code>record_attempt</code> raises, its exception can replace the pending continue or break. Cleanup code therefore needs its own failure policy.

### 6.5.7 Excessive control exits obscure proofs

A loop with many breaks, continues, returns, and handled exceptions can be correct, but every path multiplies proof and test obligations. Refactor when:

- the invariant must be restated differently for many routes;
- exit reasons are encoded by several interacting flags;
- a continue can bypass progress;
- cleanup is duplicated;
- nested loops require non-local escape.

Useful refactorings include extracting a single-item classifier, representing outcomes with an enumeration, separating validation from accumulation, and using a generator pipeline.

> **Common misconception — “Break makes a loop condition false.”**  
> Break transfers control out without changing or re-evaluating the condition. The condition can remain true, which is why loop else distinguishes the path.
