# 6.6 `for` is iteration, not numeric counting

A `for` statement obtains successive items from an iterable and executes its suite once per item:

```python
for target in iterable_expression:
    body
```

The iterable expression is evaluated once to obtain an iterable. Python requests an iterator from it, repeatedly requests the iterator’s next item, binds the target, and executes the body. Normal iteration ends when the iterator signals exhaustion with `StopIteration` at the protocol boundary.

This is not fundamentally a disguised numeric index loop. Iteration can traverse files, dictionaries, generator pipelines, database cursors, tree walks, and custom streams without a meaningful integer position.

### Worked example 6.4 — Sum with state trace

```python
values = [7, -2, 5]
total = 0

for value in values:
    total += value

print(total)
```

| Boundary | Next item | `total` before | `total` after |
|:---|---:|---:|---:|
| initial | 7 | 0 | 7 |
| second | -2 | 7 | 5 |
| third | 5 | 5 | 10 |
| exhausted | — | 10 | — |

Invariant: at each request boundary, `total` is the sum of the items already produced. Exhaustion makes “already produced” equal to the complete iterable sequence for this finite list, establishing the result.

`range` creates an immutable range object representing an arithmetic progression. `range(stop)` begins at zero and excludes `stop`; `range(start, stop, step)` follows the given step while remaining before the exclusive bound in the step’s direction.

```python
print(list(range(5)))          # [0, 1, 2, 3, 4]
print(list(range(2, 9, 3)))   # [2, 5, 8]
print(list(range(5, 0, -2)))  # [5, 3, 1]
```

The call to `list` materialises the represented progression for display. A range need not store every integer individually.

Use direct item iteration when the items are required. Use `enumerate` when both position and item are required:

```python
names = ["Ada", "Grace", "Edsger"]

for position, name in enumerate(names, start=1):
    print(position, name)
```

Manually maintaining an index duplicates state and creates opportunities for off-by-one errors.

### 6.6.1 Operational expansion of for

The language-level behaviour of:

~~~python
for target in expression:
    body
~~~

can be modelled approximately as:

~~~python
iterator = iter(expression)

while True:
    try:
        target = next(iterator)
    except StopIteration:
        break
    body
~~~

This is explanatory pseudocode, not a source-to-source equivalence in every detail. A real <code>for</code> handles <code>StopIteration</code> at the iteration protocol boundary, supports loop else and abrupt transfers, and does not expose its hidden iterator name.

The iterable expression is evaluated once. If it calls:

~~~python
for item in obtain_source():
    process(item)
~~~

<code>obtain_source()</code> is called once, after which the obtained iterator controls successive requests.

### 6.6.2 The target is rebound, not scoped per iteration

Each item is assigned to the loop target. The loop does not ordinarily create a fresh enclosing scope:

~~~python
for value in [10, 20, 30]:
    pass

print(value)
~~~

After normal non-empty iteration, <code>value</code> remains bound to 30 in the surrounding local or module scope. If the iterable is empty and no prior binding exists, the body never assigns the target and later lookup fails.

Do not use post-loop target state as a hidden result. Bind a named result explicitly or return it. Comprehensions use a separate implicit scope for their iteration variables, a deliberate difference treated in §6.10.

### 6.6.3 Target unpacking

The loop target can unpack each yielded item:

~~~python
records = [
    ("Ada", 98),
    ("Grace", 95),
]

for name, score in records:
    print(name, score)
~~~

Every item must satisfy the two-element unpacking contract. A malformed later item can raise after earlier bodies have already executed. Validation is incremental unless the source is first materialised and checked.

Starred unpacking is also possible:

~~~python
for head, *middle, tail in rows:
    process(head, middle, tail)
~~~

Each iteration constructs a new list for <code>middle</code> and requires at least two source items. This allocation belongs in the cost model.

### 6.6.4 Range is an arithmetic progression

For non-zero step (d), <code>range(start, stop, step)</code> represents values:

\[
start,\ start+d,\ start+2d,\ldots
\]

while each remains strictly before <code>stop</code> for positive (d), or strictly after it for negative (d). The stop value is excluded.

For positive step, the number of elements is:

\[
\max\left(0,\left\lceil\frac{stop-start}{d}\right\rceil\right).
\]

For negative step, the inequality reverses. Python computes range length without materialising every integer, subject to representability of the reported length through the platform interface.

Step zero raises <code>ValueError</code> because no directed progression or termination can be derived.

### Worked example 6.4A — Derive range boundaries

For <code>range(3, 14, 4)</code>, candidate values are (3+4k) for non-negative integer (k), subject to:

\[
3+4k<14.
\]

Thus (k<11/4), admitting (k=0,1,2), and the values are 3, 7, and 11.

For <code>range(10, 1, -3)</code>, candidates satisfy:

\[
10-3k>1,
\]

admitting (k=0,1,2) and values 10, 7, and 4. The value 1 is excluded even though it lies exactly one more step away because stop is never included.

### 6.6.5 Index loops are justified only by index semantics

Direct iteration:

~~~python
for value in values:
    process(value)
~~~

states that values matter. Index iteration:

~~~python
for index in range(len(values)):
    process(values[index])
~~~

adds length lookup, integer progression, and subscription. Use it when the index itself controls another structure, when in-place position replacement is required, or when the algorithm genuinely reasons about neighbours.

For position and value, use:

~~~python
for index, value in enumerate(values):
    ...
~~~

This works for non-indexable iterables and keeps count synchronised with successful item production.

### 6.6.6 Enumeration count is not necessarily a source index

<code>enumerate(source, start=s)</code> pairs the first produced item with (s), then increments by one. On a filtered generator or database cursor, that number is a consumption count, not necessarily an original file offset, database identifier, or sequence index.

For text lines:

~~~python
for line_number, line in enumerate(stream, start=1):
    ...
~~~

the count is a logical iteration line number if the stream yields one item per line. Newline translation and prior consumption can qualify that interpretation.

### 6.6.7 Dictionary iteration

Iterating a dictionary directly yields keys:

~~~python
for key in mapping:
    value = mapping[key]
~~~

Use <code>mapping.items()</code> when both key and value are required:

~~~python
for key, value in mapping.items():
    ...
~~~

Modern Python dictionaries preserve insertion order as a language-level behaviour. This is not sorted order and does not make arbitrary construction histories reproducible. Updating an existing key does not ordinarily move its position; deleting and reinserting can.

Changing dictionary size during iteration raises a runtime error under ordinary built-in behaviour and is logically hazardous. Iterate over <code>list(mapping)</code> for a key snapshot when controlled structural mutation is required, recognising the extra memory cost.

### 6.6.8 Reverse iteration

<code>reversed(sequence)</code> requests a reverse iterator without necessarily copying:

~~~python
for value in reversed(values):
    process(value)
~~~

An object can support reversal through a dedicated protocol or through sequence length and integer subscription. A general iterable or one-pass generator cannot be reversed without retaining its items because its past values are no longer available.

<code>values[::-1]</code> often creates a reversed shallow copy for built-in sequences. The two forms differ in materialisation and returned type.

### 6.6.9 Nested iteration and Cartesian products

~~~python
for left in left_values:
    for right in right_values:
        process(left, right)
~~~

If both iterables are reusable finite collections of lengths (m) and (n), the body executes (mn) times. If <code>right_values</code> is a one-shot iterator created before the loops, the first outer iteration can exhaust it and later outer iterations see no items:

~~~python
right_iterator = iter([1, 2])

for left in ["A", "B"]:
    for right in right_iterator:
        print(left, right)
~~~

Only pairs for A are produced. Create a fresh iterable per outer iteration or materialise under an explicit memory policy.

### 6.6.10 Mutation while traversing

For lists, mutation during iteration has position-based effects:

~~~python
values = [1, 2, 3, 4]

for value in values:
    if value % 2 == 0:
        values.remove(value)
~~~

This particular example can appear to work for some arrangements and fail for adjacent even values because elements shift into positions the iterator has passed. Behaviour is not a filtering contract.

Build a new list:

~~~python
values = [value for value in values if value % 2 != 0]
~~~

or mutate through a carefully derived index algorithm. Do not use a successful small example as a universal proof.

### 6.6.11 Iteration over changing external sources

A file, socket, queue, or database cursor can yield data that becomes available over time. Exhaustion can mean:

- permanent end of a finite file;
- current end of a closed stream;
- temporary lack of queue items under a non-blocking interface;
- server-declared end of a result cursor.

The iterator protocol has one exhaustion signal, but the producing interface determines when it is emitted. A live source may block rather than signal exhaustion. Termination reasoning must include the external source contract.

> **Common misconception — “For knows the collection length and visits each index.”**  
> For repeatedly asks an iterator for another item. Length, indexing, storage, and finiteness are not required by the protocol.
