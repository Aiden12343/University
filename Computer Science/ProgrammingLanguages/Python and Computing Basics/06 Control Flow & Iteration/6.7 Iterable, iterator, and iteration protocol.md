# 6.7 Iterable, iterator, and iteration protocol

An **iterable** is an object from which an iterator can be requested, ordinarily through `iter(obj)`. An **iterator** is a stateful object that produces successive items through `next(iterator)` and returns itself from `iter(iterator)`. Exhaustion is signalled by `StopIteration`.

A list is iterable but not an iterator. Each request for `iter(a_list)` creates a separate list iterator with its own position. A file object is commonly its own iterator for lines. The distinction is behavioural, not based on a naming suffix.

### Worked example 6.5 — Two iterators over one iterable

```python
values = [10, 20, 30]
first = iter(values)
second = iter(values)

print(next(first))
print(next(first))
print(next(second))
print(next(first))
```

Output:

```text
10
20
10
30
```

`first` and `second` retain independent positions. The list stores elements; each iterator stores traversal state. Mutating a collection during iteration can violate assumptions and has type-specific behaviour; no universal snapshot is implied.

An exhausted iterator remains exhausted under ordinary protocol use:

```python
iterator = iter([1])
print(next(iterator))
print(next(iterator, "finished"))
print(next(iterator, "still finished"))
```

The two-argument form of `next` returns the supplied default instead of propagating `StopIteration`. It does not rewind the iterator.

> **Common misconception — “An iterable contains all its items.”**  
> An iterable promises a way to obtain an iterator. Items may be computed lazily, read from an external stream, or generated without simultaneous storage.

### 6.7.1 Protocol equations

For an iterable (X):

\[
I=\operatorname{iter}(X)
\]

must produce an iterator (I). For an iterator:

\[
\operatorname{iter}(I)\ \text{is}\ I
\]

under the ordinary protocol. Each:

\[
\operatorname{next}(I)
\]

either returns one item and advances state or raises <code>StopIteration</code> to report exhaustion.

An iterable can return itself if it is inherently one traversal, or a fresh iterator if it represents a reusable source. Calling <code>iter</code> is therefore not universally a copy or reset operation.

### 6.7.2 Sequence fallback

The primary modern iterable protocol uses <code>__iter__</code>. Python also supports a legacy sequence-style fallback for objects implementing integer subscription beginning at zero and raising <code>IndexError</code> at the end. New iterable types should implement <code>__iter__</code> directly because it states intent and supports non-index traversal.

The existence of fallback demonstrates protocol evolution: behaviour can be recognised through more than one mechanism. Reference prose must distinguish preferred interface from compatibility path.

### 6.7.3 Two-argument iter

The form <code>iter(callable, sentinel)</code> constructs an iterator that repeatedly calls the zero-argument callable until the returned value compares equal to the sentinel:

~~~python
chunks = iter(
    lambda: binary_stream.read(4096),
    b"",
)

for chunk in chunks:
    process(chunk)
~~~

This is a flagged forward use of lambda and file reading. Each request calls <code>read(4096)</code>. An empty bytes result marks end-of-stream and is not yielded.

Sentinel equality invokes value comparison. If the callable can legitimately return the sentinel as data before true termination, the protocol is ambiguous. Choose a sentinel outside the data domain or a richer result interface.

### 6.7.4 Consumption is a state change

Calling <code>next</code> is ordinarily destructive with respect to iterator position:

~~~python
iterator = iter([10, 20, 30])
first = next(iterator)
remaining = list(iterator)
~~~

The remaining list contains 20 and 30. The value 10 has not been deleted from the original list; it has been passed by this iterator’s traversal point.

Functions such as <code>sum</code>, <code>min</code>, <code>max</code>, <code>list</code>, tuple construction, membership tests, unpacking, and <code>any</code>/<code>all</code> can consume iterators. Their names may not visually advertise mutation of iterator state.

### 6.7.5 Membership can partially consume

~~~python
iterator = iter([2, 4, 6, 8])
print(6 in iterator)
print(list(iterator))
~~~

The membership search consumes 2, 4, and 6, stopping when equality succeeds. The remaining traversal contains only 8. Searching for an absent value exhausts the iterator completely. On an infinite iterator, absent membership may never terminate.

Membership in a reusable list does not mutate the list because it obtains a separate traversal. Interface category changes effect.

### 6.7.6 Defaults and ambiguous item values

The two-argument <code>next(iterator, default)</code> converts exhaustion to an ordinary value:

~~~python
item = next(iterator, None)
~~~

If <code>None</code> can also be yielded, exhaustion and a real item collapse. Use a unique sentinel:

~~~python
_EXHAUSTED = object()
item = next(iterator, _EXHAUSTED)

if item is _EXHAUSTED:
    handle_end()
else:
    handle_item(item)
~~~

The conversion is correct only when the sentinel lies outside the item identity domain.

### 6.7.7 Exhaustion should remain stable

Once an iterator raises <code>StopIteration</code>, well-behaved iterators remain exhausted on subsequent requests. Resuming production after exhaustion violates assumptions made by loops and consumers.

An external source that temporarily lacks data should not signal permanent iterator exhaustion if it intends later values under the same traversal. It needs a blocking operation, polling result, asynchronous iterator, queue protocol, or explicit “temporarily empty” state.

### 6.7.8 Finiteness is not a protocol property

The iterator interface does not state how many items remain or whether exhaustion will ever occur:

~~~python
def natural_numbers():
    number = 0
    while True:
        yield number
        number += 1
~~~

Calling <code>list(natural_numbers())</code> cannot complete under finite resources. Consumers need a bound:

~~~python
from itertools import islice

first_ten = list(islice(natural_numbers(), 10))
~~~

<code>islice</code> lazily selects a bounded interval from an iterable. Chapter 11 surveys <code>itertools</code> systematically.

### 6.7.9 Length hints are not correctness contracts

Some iterators expose an estimated remaining length used to preallocate output storage. A length hint can improve performance but is not required to be exact and must not control semantic correctness. Iteration ends only at exhaustion.

Likewise, <code>len(iterable)</code> is not required for iterability. A generator has no ordinary length because computing it could require consuming work, could be unbounded, or could depend on future input.

### 6.7.10 Duplicating an iterator requires storage

If two consumers need independent views of one one-pass iterator, <code>itertools.tee</code> can create proxy iterators while buffering values consumed at different rates:

~~~python
from itertools import tee

left, right = tee(source, 2)
~~~

This does not make the source computation execute twice. A shared buffer retains items until every proxy has passed them. If one consumer races far ahead or another never advances, memory can grow without bound. It is generally unsafe to use original <code>source</code> after teeing, and thread safety requires separate analysis.

Materialising once into a list gives clear bounded storage when the source is known finite and fits memory. Recomputing can be preferable when production is cheap and side-effect-free. There is no zero-cost universal duplication.

### 6.7.11 Iterator invalidation

An iterator can become invalid when its underlying object changes or closes. Examples include:

- a dictionary changes size;
- a file is closed;
- a database transaction ends;
- a network connection fails;
- a custom collection increments a modification counter.

The iterator contract must define whether mutation is rejected, tolerated with live semantics, or represented by a snapshot. Consumers should minimise lifetime across mutable external boundaries.

### Worked example 6.5A — Shared iterator consumers

~~~python
source = iter([10, 20, 30, 40])

first_consumer = next(source)
second_consumer = next(source)
remaining_for_first = list(source)

print(first_consumer)
print(second_consumer)
print(remaining_for_first)
~~~

The outputs are 10, 20, and <code>[30, 40]</code>. The two consumers do not receive independent streams merely because their result names differ. They advance one shared iterator object.

Constructing two iterators from a reusable list would create independent positions. The ownership question is “who owns traversal state?”, not merely “who owns the source collection?”

> **Common misconception — “Calling iter on an iterator restarts it.”**  
> An iterator returns itself and retains its current position. Restartability belongs to reusable iterable design, not to the generic iterator protocol.
