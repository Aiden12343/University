# 6.8 Custom iterators

Iterator state can be implemented by a class. The following countdown is deliberately explicit; generators later provide a more economical representation.

```python
class Countdown:
    def __init__(self, start: int) -> None:
        if start < 0:
            raise ValueError("start must be non-negative")
        self.current = start

    def __iter__(self) -> "Countdown":
        return self

    def __next__(self) -> int:
        if self.current == 0:
            raise StopIteration
        value = self.current
        self.current -= 1
        return value


for value in Countdown(3):
    print(value)
```

Output is 3, 2, 1 on separate lines. `Countdown(3)` is its own iterator. Each `next` call either returns the current positive value after arranging the next state or raises `StopIteration` at zero. Its variant is `current`, a non-negative integer that strictly decreases.

The quoted return annotation is a forward reference to the class name while its definition is still being executed. Modern annotation handling can postpone some evaluation, but tools and versions differ; `from __future__ import annotations` provides a consistent postponed representation in Python 3.12.

Class construction and methods are formalised in Chapter 9. The present example exposes the protocol: `for` depends on behaviour, not on a privileged built-in collection list.

### 6.8.1 Separate reusable collection from traversal

An iterable container should ordinarily return a fresh iterator:

~~~python
class InclusiveRange:
    def __init__(self, start: int, stop: int) -> None:
        self._start = start
        self._stop = stop

    def __iter__(self):
        return InclusiveRangeIterator(
            self._start,
            self._stop,
        )


class InclusiveRangeIterator:
    def __init__(self, start: int, stop: int) -> None:
        self._current = start
        self._stop = stop

    def __iter__(self):
        return self

    def __next__(self) -> int:
        if self._current > self._stop:
            raise StopIteration

        value = self._current
        self._current += 1
        return value
~~~

The range object stores reusable bounds. Each iterator stores an independent current position. Two loops over one <code>InclusiveRange</code> therefore do not interfere.

Annotations for iterator return types are omitted here to avoid forward generic protocol notation; Chapter 12 supplies <code>Iterator[int]</code> and <code>Self</code>.

### 6.8.2 Iterator invariant

For start (s), stop (t), and current (c), an invariant for a non-empty inclusive ascending iterator is:

\[
s\leq c\leq t+1,
\]

and all values in ([s,c)) have been produced exactly once. If (c\leq t), the next method returns (c) and increments it. If (c=t+1), it raises exhaustion. For (s>t), the iterator should begin exhausted; the invariant must be generalised or established with an empty-state branch.

Stating the invariant exposes integer overflow assumptions in fixed-width languages. Python integers expand, so the <code>t+1</code> sentinel state remains representable subject to memory.

### 6.8.3 Advance state before exposing re-entry

Iterator <code>__next__</code> can call user code while producing a value. If that code re-enters the same iterator before state advances, duplicate production or corruption can occur. A robust design often computes and commits the next state before invoking external callbacks.

Python generators reject re-entry while already executing. Custom iterator classes must establish their own policy if <code>__next__</code> can indirectly invoke itself.

### 6.8.4 StopIteration is a protocol signal

Raise <code>StopIteration</code> only to report that this iterator has no further items:

~~~python
def __next__(self):
    if self._finished:
        raise StopIteration
    ...
~~~

Do not use it as an ordinary internal “not found” exception inside generator code. Modern Python transforms an accidentally escaping <code>StopIteration</code> from a generator body into <code>RuntimeError</code> under the generator protocol, preventing silent truncation.

If an operation used while producing an item can independently raise <code>StopIteration</code>, catch and translate it unless it genuinely means exhaustion of the outer iterator.

### 6.8.5 Errors do not necessarily exhaust an iterator

An iterator can raise another exception on one request. Whether later <code>next</code> calls can continue is type-specific:

~~~python
class Fragile:
    def __init__(self) -> None:
        self._position = 0

    def __iter__(self):
        return self

    def __next__(self) -> int:
        self._position += 1
        if self._position == 2:
            raise ValueError("bad item")
        if self._position > 3:
            raise StopIteration
        return self._position
~~~

After the <code>ValueError</code>, another explicit <code>next</code> would produce 3. A normal <code>for</code> loop terminates abruptly at the error and does not automatically resume. APIs should document whether a production error poisons, advances, or preserves traversal.

### 6.8.6 Iterators are mutable state machines

Even when yielded values are immutable, the iterator changes state at every request. Consequently:

- sharing requires ownership;
- hashability is generally inappropriate;
- equality by current position can change;
- copying may duplicate, share, or reject traversal state;
- concurrency can race;
- debugging display should avoid consuming.

An iterator’s <code>repr</code> method must not call <code>list(self)</code> merely to show remaining contents, because inspection would exhaust it.

### Worked example 6.5B — A reusable line-numbering iterable

~~~python
class Numbered:
    def __init__(self, values, start: int = 0) -> None:
        self._values = values
        self._start = start

    def __iter__(self):
        position = self._start
        for value in self._values:
            yield position, value
            position += 1
~~~

This implementation’s <code>__iter__</code> is a generator function. Each call constructs a new generator and a new <code>position</code> binding. Reusability still depends on <code>self._values</code>: if it is a list, repeated traversal works; if it is a one-pass iterator, later generators inherit its exhausted state.

A wrapper cannot promise more reusability than its underlying source without materialising or recomputing it.

> **Common misconception — “Writing __iter__ makes an object reusable.”**  
> Reusability requires each traversal to obtain an independent or reconstructible source. Returning a fresh wrapper around one exhausted underlying iterator does not restore data.
