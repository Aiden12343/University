# 6.9 Generator functions and suspension

A **generator function** is a function whose body contains `yield` in the relevant scope. Calling it returns a **generator object** without executing the body to ordinary completion. The generator is an iterator. Each `next` request resumes execution until a `yield` produces a value and suspends the frame, or until the function returns and iteration ends.

```python
def countdown(start: int):
    current = start
    while current > 0:
        yield current
        current -= 1
```

The call `countdown(3)` creates a generator. The first `next` begins execution, binds `current = 3`, reaches `yield current`, produces 3, and suspends with local state intact. Later requests resume after the `yield`, decrement, and repeat.

`yield` is not an ordinary `return`. It produces an item while preserving resumable state. A `return` inside a generator ends iteration; a returned value is attached to the underlying `StopIteration` for advanced delegation protocols but is not another ordinary item in a `for` loop.

### Worked example 6.6 — Observe laziness and state lifetime

```python
def marked_countdown(start: int):
    print("generator begins")
    current = start
    while current > 0:
        print("about to yield", current)
        yield current
        print("resumed after", current)
        current -= 1
    print("generator ends")


iterator = marked_countdown(2)
print("created")
print(next(iterator))
print(next(iterator))
print(next(iterator, "exhausted"))
```

Output order:

```text
created
generator begins
about to yield 2
2
resumed after 2
about to yield 1
1
resumed after 1
generator ends
exhausted
```

The body does not begin at the call. Side effects occur only as consumption requests values. This matters when a pipeline reads files, acquires resources, or can fail: constructing a generator does not prove the deferred work succeeds.

Generators support potentially unbounded sequences because they need retain only the state required for the next value. They are not cost-free. Each item still requires computation, generator state occupies memory, and a consumer can demand infinitely many values from a non-terminating source.

### 6.9.1 Generator function versus ordinary function

The presence of <code>yield</code> in the relevant function body changes the call protocol. Compare:

~~~python
def ordinary() -> int:
    print("ordinary body")
    return 1


def generated():
    print("generator body")
    yield 1
~~~

Calling <code>ordinary()</code> enters its body and returns an integer. Calling <code>generated()</code> creates a generator object without executing the print call:

~~~python
ordinary_result = ordinary()
generator_result = generated()
~~~

The generator body begins only when a resumption operation requests progress. This is determined when the function is compiled; placing <code>yield</code> on a branch that runtime conditions never select still makes it a generator function.

### 6.9.2 Generator lifecycle

A synchronous generator moves among conceptual states:

- **created:** frame exists but body has not begun;
- **running:** body is actively executing;
- **suspended:** execution stopped at a yield with frame state retained;
- **closed:** body returned, raised outwards, or was successfully closed.

The <code>inspect</code> module can report a state for diagnostic experiments:

~~~python
import inspect


def source():
    yield 1


generator = source()
print(inspect.getgeneratorstate(generator))
print(next(generator))
print(inspect.getgeneratorstate(generator))
print(next(generator, None))
print(inspect.getgeneratorstate(generator))
~~~

Typical CPython state labels correspond to created, suspended, and closed. The language-level lifecycle matters; the exact diagnostic constants belong to the library contract.

### 6.9.3 A yield is an expression

Inside a generator:

~~~python
received = yield produced
~~~

has two temporal halves:

1. evaluate <code>produced</code>, return it to the resumer, and suspend;
2. on a later resumption, make the yield expression produce a received value and bind it.

Ordinary <code>next(generator)</code> resumes with <code>None</code> as the yield expression’s result. <code>generator.send(value)</code> can supply another value after the generator has reached a yield.

### Worked example 6.6A — Two-way generator communication

~~~python
def accumulator():
    total = 0
    while True:
        increment = yield total
        if increment is None:
            return total
        total += increment


generator = accumulator()
print(next(generator))
print(generator.send(5))
print(generator.send(7))

try:
    generator.send(None)
except StopIteration as finished:
    print("returned", finished.value)
~~~

Trace:

1. Creation executes no body.
2. First <code>next</code> binds <code>total = 0</code>, yields zero, and suspends before assigning <code>increment</code>.
3. <code>send(5)</code> makes the suspended yield expression evaluate to five, binds it, updates total to five, and yields five.
4. <code>send(7)</code> analogously yields twelve.
5. <code>send(None)</code> selects return. Generator termination raises <code>StopIteration</code> to the explicit caller with return value twelve attached.

This protocol is powerful but easy to obscure. Classes with named methods or asynchronous queues often provide clearer bidirectional interfaces.

### 6.9.4 Priming

A newly created generator has not yet reached a yield expression, so there is no suspended yield ready to receive a non-<code>None</code> value. Its first resumption must be <code>next(generator)</code> or <code>generator.send(None)</code>.

Decorators can prime generators automatically, but that changes the call contract and hides an effect. Document it explicitly if used. Modern asynchronous programming ordinarily uses coroutines and tasks rather than generator priming for general cooperative scheduling.

### 6.9.5 Return and StopIteration value

In a generator:

~~~python
return result
~~~

ends production. The result is carried as the <code>value</code> attribute of the <code>StopIteration</code> observed by an explicit resumer or delegation mechanism. It is not yielded as another item:

~~~python
def source():
    yield "item"
    return "summary"


generator = source()
print(next(generator))

try:
    next(generator)
except StopIteration as finished:
    print(finished.value)
~~~

A <code>for</code> loop consumes the item and treats the subsequent <code>StopIteration</code> as ordinary exhaustion; it does not expose the return value. Use <code>yield</code> if the value is part of the item stream, or an explicit higher-level protocol if consumers need both items and a summary.

### 6.9.6 Exceptions injected with throw

<code>generator.throw(exception)</code> resumes the generator by raising the supplied exception at its suspension point:

~~~python
def resilient():
    while True:
        try:
            value = yield "ready"
        except ValueError:
            yield "recovered"
        else:
            yield value
~~~

An injected <code>ValueError</code> can be handled by the generator. An unhandled exception propagates to the caller and ordinarily closes the generator.

Throwing an exception is a control transfer, not a value send. Its use requires an exact ownership protocol; casual consumers should not assume every iterator supports it, because it is generator-specific.

### 6.9.7 Closing

<code>generator.close()</code> raises <code>GeneratorExit</code> at the suspension point. If the generator exits normally or propagates <code>GeneratorExit</code>, close succeeds. Yielding another value while handling close is an error because the consumer requested termination.

~~~python
def managed():
    acquire()
    try:
        yield "resource"
    finally:
        release()
~~~

Explicit close requests the finally path. If a <code>for</code> loop breaks early, it does not universally promise to call <code>close</code> on every arbitrary iterator. A generator may eventually be finalised, but resource timing must not depend on that. Wrap resource ownership in a context manager or explicitly close under a controlled boundary.

### 6.9.8 GeneratorExit is not an ordinary error

<code>GeneratorExit</code> inherits directly under <code>BaseException</code>, not ordinary <code>Exception</code>. A broad <code>except Exception</code> therefore does not catch it. This allows closure to pass through typical application handlers.

Do not catch and suppress <code>GeneratorExit</code> merely to continue yielding. A generator can use <code>finally</code> for cleanup and then allow closure to complete. The same principle applies to other control exceptions such as keyboard interruption and process exit: an indiscriminate catch can block intended termination.

### 6.9.9 Delegation with yield from

The statement-like expression:

~~~python
yield from iterable
~~~

delegates item production to a subiterator. A simple use:

~~~python
def flatten_once(groups):
    for group in groups:
        yield from group
~~~

For groups <code>[[1, 2], [3], [], [4, 5]]</code>, the generator yields 1 through 5. Delegation is more than a textual abbreviation for a nested <code>for</code>. With a generator subiterator, it also mediates <code>send</code>, <code>throw</code>, <code>close</code>, and captures the subgenerator’s return value.

### Worked example 6.6B — Delegated return value

~~~python
def subgenerator():
    yield 1
    yield 2
    return 3


def delegating():
    summary = yield from subgenerator()
    yield summary * 10


print(list(delegating()))
~~~

The subgenerator yields 1 and 2, then returns 3. <code>yield from</code> receives that return value in <code>summary</code>. The outer generator then yields 30. The resulting list is <code>[1, 2, 30]</code>.

### 6.9.10 Generator exception transformation

If generator body code explicitly or accidentally lets <code>StopIteration</code> escape instead of using <code>return</code>, Python converts it to <code>RuntimeError</code> under the generator semantics:

~~~python
def defective():
    yield 1
    raise StopIteration("wrong termination")
~~~

This rule prevents a nested operation’s accidental <code>StopIteration</code> from silently truncating the outer generator. Proper completion uses <code>return</code>.

### 6.9.11 Generator frame retention

A suspended generator retains:

- local bindings;
- instruction position;
- evaluation state;
- active exception-handling context;
- references reachable through that frame.

Therefore a generator retaining a large local object can keep it alive between yields:

~~~python
def first_then_wait():
    large = build_large_object()
    yield summarise(large)
    use_later(large)
~~~

After the first yield, <code>large</code> remains reachable because later execution may use it. Delete or restructure state when retention is unnecessary, but do not compromise clarity without measurement.

### 6.9.12 Re-entry is rejected

A generator cannot be resumed while it is already executing. Indirectly calling <code>next</code> on the same generator from inside its body raises a runtime error. This prevents simultaneous mutation of one suspended frame’s instruction state.

The restriction does not make generators thread-safe. Different threads can still race to resume a currently suspended generator, and surrounding yielded objects can be shared. Ownership should ordinarily assign one active consumer.

### 6.9.13 Generator observability

Generator representations expose little about future values because obtaining those values would execute code. Debugging should inspect:

- creation site;
- current lifecycle state;
- known source object;
- explicit counters or metrics;
- a bounded sample only when consumption is acceptable.

Printing <code>list(generator)</code> is not neutral observation. It exhausts finite sources, can block, can raise, can trigger external I/O, and cannot finish for unbounded sources.

> **Common misconception — “Yield is return that can happen several times.”**  
> Yield suspends an active frame and later becomes a receive point. Return terminates the generator and communicates only through the exhaustion protocol.
