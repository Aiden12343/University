# 7.1 A collection is an invariant, not merely several values

A **collection** is an object that organises references to other objects under a behavioural contract. The contract determines whether order matters, whether duplicates are retained, how elements are addressed, whether the structure can mutate, and which operations it supports.

Python’s principal built-in collection types are `list`, `tuple`, `dict`, `set`, `frozenset`, and `str`. Although a string contains textual elements rather than arbitrary object references at the language level, it participates in sequence operations and belongs in any account of built-in structure selection.

A data structure is selected by required invariants and operations:

- If position and order matter, a sequence is natural.
- If unique keys designate associated values, a mapping is natural.
- If membership and uniqueness dominate while order is not semantic, a set is natural.
- If the structure must be hashable or protected from structural mutation, an immutable alternative may be required.

One can force most small problems into several structures. Correctness may survive while intent, cost, and invariants become obscure. The question is not “which type can hold these objects?” but “which type makes the required relationships native and the forbidden states difficult to express?”

### 7.1.1 Abstract data type and representation

An **abstract data type** is a set of values together with operations and laws, described independently of one concrete machine representation. A stack, for example, supports push, pop, and inspection of the most recently pushed unremoved item under last-in–first-out laws. It can be represented by a list, linked structure, or segmented buffer.

A **data structure** is a concrete organisation used to realise an abstract data type. Python’s <code>list</code> is a concrete built-in type with richer operations than the abstract stack. Using it as a stack requires an application invariant restricting which operations other code performs.

Separating abstraction from representation permits:

- implementation replacement without changing callers;
- proofs stated over operations rather than addresses;
- cost comparison among representations;
- identification of representation leaks;
- enforcement of domain-specific forbidden states.

### 7.1.2 Representation invariant

A **representation invariant** is a property every valid concrete state of an abstraction must satisfy. A mapping from unique student identifier to record might require:

- every key is a non-empty normalised identifier;
- each record’s internal identifier equals its key;
- no record object is shared across independent students;
- every score is an integer from 0 through 100.

A dictionary automatically enforces unique equality-keys but none of the remaining domain rules. Data-structure invariants and domain invariants compose; one does not replace the other.

Every public operation must:

1. require or establish its preconditions;
2. assume the representation invariant on entry;
3. preserve it on successful completion;
4. define what remains true on failure.

### 7.1.3 Five structural dimensions

Collection selection begins with five questions:

| Dimension | Question |
|:---|:---|
| Order | Does relative position carry meaning? |
| Multiplicity | May equal values occur more than once? |
| Association | Does one value act as a key designating another? |
| Mutation | Must the structure change through existing aliases? |
| Access | Which operations dominate: position, key lookup, membership, ends, range, or traversal? |

A sixth question, **scale**, determines whether constant factors, memory locality, hashing quality, and asymptotic growth matter in practice.

Examples:

- ordered event history with duplicates: list or tuple;
- current record by unique identifier: dictionary;
- set of granted capabilities: set or frozenset;
- Unicode document: string;
- FIFO work queue: deque rather than repeated list-front deletion.

### 7.1.4 Native invariant versus maintained convention

A list can store unique values, but uniqueness must be checked on every mutation:

~~~python
if candidate not in values:
    values.append(candidate)
~~~

This requires linear membership search and can race under concurrent access. A set represents uniqueness natively under equality and hashing:

~~~python
values.add(candidate)
~~~

The set still cannot decide whether equality corresponds to domain identity. Native structure narrows the invariant burden; it does not eliminate specification.

### 7.1.5 Structural equality and domain equivalence

Built-in collections define structural equality:

- sequences compare corresponding elements;
- mappings compare key–value associations independent of insertion order;
- sets compare membership independent of iteration order.

Two structures can therefore compare unequal while representing the same domain information under normalisation, or compare equal while differing in provenance, timestamps, ownership, or identity.

~~~python
left = ["Ada", "Grace"]
right = ["Grace", "Ada"]

print(left == right)
print(set(left) == set(right))
~~~

List equality says order differs. Set equality says membership is equal. Converting to set is correct only if order and multiplicity are irrelevant.

### 7.1.6 Information loss under conversion

Converting structures can discard:

- list to set: order and duplicate count;
- dictionary to list: values if iterating keys only;
- mapping items to dictionary: earlier equal-key associations;
- string to set: order, adjacency, and repeated code points;
- iterator to set: order plus traversal state after consumption.

A conversion is a semantic projection. State which distinctions cease to matter before performing it.

### Worked example 7.1A — Choose a representation for enrolment

Requirements:

- each student identifier designates at most one current record;
- lookup by identifier dominates;
- display order is alphabetical by surname and can be recomputed;
- historical duplicates must be rejected, not silently overwritten;
- records can be updated.

Use a dictionary from identifier to record for current state. Insertion must test duplicate identity before assignment:

~~~python
def add_student(
    students: dict[str, dict[str, object]],
    identifier: str,
    record: dict[str, object],
) -> None:
    if identifier in students:
        raise ValueError(
            f"duplicate student identifier: {identifier!r}"
        )
    students[identifier] = record
~~~

Alphabetical output is a derived sorted view, not the storage invariant. A list alone would make identifier lookup and duplicate detection linear. A set cannot directly associate the full record. The nested dictionaries remain mutable and aliased; a later class can enforce record-level invariants.

### 7.1.7 Collections retain references

For ordinary object collections:

~~~python
record = {"score": 10}
records = [record]
record["score"] = 20
~~~

The list still contains the same dictionary reference and now exposes score 20. The collection copied neither the dictionary nor its value at insertion. Structural copying of the outer collection also retains this element reference.

Ownership and mutability therefore affect every structure choice. An immutable tuple of mutable records is not a historical snapshot. Construct immutable element values or deep domain snapshots when temporal stability is required.

> **Common misconception — “Choosing the right container enforces the whole model.”**  
> A built-in structure enforces only its own ordering, key, uniqueness, and mutation rules. Domain validity, ownership, provenance, and cross-field relationships remain application invariants.
