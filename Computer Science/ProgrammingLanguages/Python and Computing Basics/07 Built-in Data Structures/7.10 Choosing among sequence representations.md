# 7.10 Choosing among sequence representations

Lists, tuples, strings, ranges, bytes, bytearrays, and deques all support ordered behaviour but publish different invariants.

| Need | Prefer | Reason |
|:---|:---|:---|
| mutable arbitrary object sequence with indexing | `list` | dynamic array and broad sequence operations |
| fixed structural positions, possibly hashable | `tuple` | immutable reference sequence |
| Unicode text | `str` | text-specific immutable operations |
| immutable byte sequence | `bytes` | binary data and protocol boundaries |
| mutable byte buffer | `bytearray` | in-place binary updates |
| arithmetic integer progression | `range` | compact represented progression |
| efficient operations at both ends | `collections.deque` | double-ended queue contract |

“Immutable” can improve reasoning because callers know the outer structure will not change. It can enable hashing. It does not guarantee semantic validity, recursive immutability, smaller memory, or thread safety of reachable objects.

### 7.10.1 “Sequence” denotes a behavioural family

A **sequence** is an ordered collection supporting integer indexing and usually slicing, length, forward iteration, reverse iteration, membership, and related operations. The family resemblance does not imply identical representation or cost. A list, tuple, string, bytes object, range, and several library types satisfy different portions or specialisations of the sequence protocol.

An iterable is more general than a sequence. A generator is iterable but normally has no length, index access, or reverse traversal. A set is iterable but not a sequence because its interface has no positions. A dictionary is iterable in insertion order but is a mapping: integer subscription addresses an integer key, not the element at a position.

~~~python
sequence = [10, 20, 30]
mapping = {0: "zero", 2: "two"}

print(sequence[2])             # third positional element: 30
print(mapping[2])              # value associated with key 2: 'two'
~~~

The shared brackets do not imply a shared addressing model.

### 7.10.2 Operation requirements precede type selection

A representation decision should begin with the operations and invariants a component must support. A useful worksheet asks:

1. Is order semantically meaningful, and if so, which order?
2. Are duplicates meaningful?
3. Must positions be indexed randomly, traversed sequentially, or both?
4. Which endpoints or interior positions mutate?
5. Is structural mutation permitted after publication?
6. Must the value be hashable?
7. Is the population bounded, finite but large, or potentially unbounded?
8. Are elements arbitrary Python objects, text code points, or raw bytes?
9. Are copies, shared views, or ownership transfer required?
10. Which costs dominate in the expected workload?

Only then should a type be chosen. Choosing a list because it is familiar often creates accidental \(O(n)\) front removal, mutable aliasing, or invalid “record fields by position” interfaces.

### 7.10.3 Comparative operation matrix

The following table gives ordinary growth for central operations. \(n\) is current length and \(k\) the selected or inserted span. Hash/equality, element destruction, allocation, and subclass behaviour can add costs.

| Representation | Index | Slice result | Append right | Add/remove left | Insert interior | Hashable |
|:---|:---:|:---:|:---:|:---:|:---:|:---:|
| <code>list</code> | \(O(1)\) | \(O(k)\) list | amortised \(O(1)\) | \(O(n)\) | \(O(n)\) | no |
| <code>tuple</code> | \(O(1)\) | \(O(k)\) tuple generally | new \(O(n)\) tuple | new \(O(n)\) tuple | new \(O(n)\) tuple | if components hashable |
| <code>str</code> | \(O(1)\) in ordinary CPython | \(O(k)\) string generally | new output | new output | new output | yes |
| <code>bytes</code> | \(O(1)\), returns integer | \(O(k)\) bytes generally | new output | new output | new output | yes |
| <code>bytearray</code> | \(O(1)\), returns integer | \(O(k)\) bytearray | amortised-like owned buffer growth | \(O(n)\) shift | \(O(n)\) | no |
| <code>range</code> | \(O(1)\) arithmetic | \(O(1)\) range | unsupported | unsupported | unsupported | yes |
| <code>deque</code> | ends \(O(1)\), middle \(O(n)\) | no general slicing | \(O(1)\) | \(O(1)\) | \(O(n)\) | no |

The table is a decision aid, not a complete specification. For example, tuple slicing the full range may reuse an object as an implementation optimisation, and deque indexed access is not uniformly linear at every position because it can approach from the nearer end. Consult the actual type contract and measure the application workload.

### 7.10.4 List versus deque

A CPython list is a resizable contiguous array of references. A <code>collections.deque</code> is a double-ended queue implemented using blocks arranged to support efficient endpoint operations. Their preferred access patterns differ.

~~~python
from collections import deque

work = deque(["compile", "test", "package"])
next_job = work.popleft()
work.append("deploy")
~~~

Both endpoint operations are \(O(1)\) in the deque contract. Replacing <code>popleft</code> with <code>list.pop(0)</code> shifts all remaining references one position, so draining a list from the front performs

\[
(n-1)+(n-2)+\cdots+1=\Theta(n^2)
\]

reference moves. Draining a deque from one end uses \(\Theta(n)\) endpoint operations.

Lists are preferable when frequent random indexing, slicing, sorting in place, or compact contiguous traversal dominates. Deques are preferable for queues, worklists, and sliding endpoints. A deque is not a generally faster list: access near the middle requires traversal, slicing is not its principal protocol, and memory locality differs.

### 7.10.5 Bounded deques and eviction semantics

A deque can have a <code>maxlen</code>. Appending to a full bounded deque automatically discards the same number of elements from the opposite end:

~~~python
from collections import deque

recent = deque(maxlen=3)
for event_id in ["e1", "e2", "e3", "e4"]:
    recent.append(event_id)

print(list(recent))            # ['e2', 'e3', 'e4']
~~~

Automatic eviction is convenient only when discarding an element requires no coordinated work. In the event-window case study, eviction must also remove a dictionary association and decrement counts. Silent deque eviction would hide the evicted identifier unless the program first inspects the endpoint. An unbounded deque plus explicit limit logic can therefore be safer for cross-structure invariants.

<code>appendleft</code>, <code>extendleft</code>, and rotations need exact reading. <code>extendleft(iterable)</code> performs successive left appends, reversing the iterable’s encounter order in the final deque:

~~~python
values = deque([3, 4])
values.extendleft([1, 2])
print(list(values))            # [2, 1, 3, 4]
~~~

If the desired prefix is <code>[1, 2]</code>, reverse the source deliberately or use another construction. Method names state the repeated endpoint operation, not every high-level ordering intention.

### 7.10.6 Range stores a progression, not its members

A range represents an arithmetic progression using start, stop, and step parameters. Its length can be enormous without storing one integer object per position.

~~~python
progression = range(1, 1_000_000_000, 3)
print(len(progression))
print(progression[100])        # 301
print(301 in progression)      # True
~~~

For non-negative position \(i), the conceptual element is

\[
r_i=start+i\cdot step,
\]

provided \(0\le i<len(r)\). Index access therefore uses arithmetic rather than traversal. Integer membership can also be answered through bounds and divisibility rather than scanning every represented value:

\[
x\in r
\iff
x\text{ lies in the directed interval and }(x-start)\bmod step=0.
\]

A zero step is invalid. A negative step represents a decreasing progression whose stop remains excluded. Empty ranges can have different parameter triples yet compare equal because range equality is sequence equality:

~~~python
print(range(0) == range(2, 1, 3))        # True: both empty
print(range(0, 3, 2) == range(0, 4, 2)) # True: both represent 0, 2
~~~

Slicing a range computes another range where possible, retaining compactness:

~~~python
every_tenth = range(1_000_000)[::10]
print(type(every_tenth), every_tenth[:3])
~~~

Converting an enormous range to a list abandons this compact representation and can exhaust memory. Materialisation must serve an actual requirement.

### 7.10.7 Bytes and bytearray are sequences of integers

<code>bytes</code> is an immutable sequence of integers from 0 through 255. <code>bytearray</code> is its mutable counterpart. Indexing returns an integer; slicing returns the same family of byte sequence rather than an integer sequence list.

~~~python
payload = b"ABC"
print(payload[0])              # 65
print(payload[:1])             # b'A'

buffer = bytearray(payload)
buffer[0] = 97
print(buffer)                  # bytearray(b'aBC')
~~~

The distinction between indexing and slicing is deliberate: one byte value is an integer, while a byte subsequence remains binary data. The valid assignment range prevents storing an arbitrary integer in one byte position.

Byte displays use printable ASCII-like characters where convenient and escapes elsewhere. This is a representation, not evidence that the byte sequence is text. An image, compressed stream, cryptographic digest, or encoded string can all be bytes; only an external format says what they mean.

Bytearray supports in-place slice updates that can change length:

~~~python
packet = bytearray(b"HEADxxxxTAIL")
packet[4:8] = b"payload"
print(packet)                  # bytearray(b'HEADpayloadTAIL')
~~~

As with list slice assignment, replacement may shift a suffix and reallocate storage. Mutation is visible through aliases to the same bytearray.

### 7.10.8 Memoryview separates a view from a copy

A <code>memoryview</code> exposes the buffer of a compatible object without immediately copying its bytes. This section uses it before the buffer protocol is formally developed; minimally, the **buffer protocol** is an interface by which one object exposes a region of raw memory to another.

~~~python
data = bytearray(b"abcdef")
window = memoryview(data)[2:5]

window[0] = ord("X")
print(data)                    # bytearray(b'abXdef')
~~~

The slice of the memoryview remains a view into the original mutable buffer, so assigning through it changes <code>data</code>. A bytes slice would construct an independent bytes object. This can avoid copying large binary regions, but it introduces aliasing and lifetime constraints.

A buffer cannot always be resized while exported views exist:

~~~python
data = bytearray(b"abc")
view = memoryview(data)
# data.append(100)             # BufferError in ordinary CPython
view.release()
data.append(100)
~~~

Resizing could relocate storage and invalidate the view’s address. The explicit release ends the view’s use of the export. A context manager can bound this lifetime. Memoryview shape, format, casting, contiguity, and multidimensional access become important in numerical and systems work; Branch A and Chapter 14 return to them.

### 7.10.9 Array, packed representation, and arbitrary objects

Python lists store references to separately represented Python objects. When a large homogeneous numeric collection is required, a packed representation can reduce indirection and memory. The standard-library <code>array</code> module stores C-like machine values under a type code:

~~~python
from array import array

temperatures = array("h", [18, 21, 19, 23])
temperatures.append(20)
~~~

This example’s <code>h</code> denotes a signed short representation whose exact size and byte order interactions must be checked for the target platform and serialisation protocol. An array is not a substitute for arbitrary heterogeneous objects. NumPy arrays add multidimensional shape, data types, vectorised operations, broadcasting, and a much richer memory model in Branch A.

Packed storage can improve memory locality and reduce per-element object overhead, but conversion, overflow rules, native representation, and ecosystem compatibility matter. Representation efficiency never removes the need for a domain range invariant.

### 7.10.10 Mutation ownership and publication

Mutable versus immutable is not merely a performance choice. It determines which component can change an observed structure after publication.

~~~python
def publish_wrong(items: list[str]) -> tuple[str, ...]:
    return tuple(items)
~~~

This tuple detaches the outer sequence from future structural list mutations. It does not deep-freeze mutable elements; here strings happen to be immutable, so the complete reachable payload is also immutable under ordinary string semantics.

For arbitrary elements:

~~~python
rows = [[1], [2]]
published = tuple(rows)
rows[0].append(3)
print(published)               # ([1, 3], [2])
~~~

A publication contract must state whether it promises:

- no mutation through the published outer interface;
- no later outer mutation by the owner;
- no reachable nested mutation;
- a moment-in-time snapshot;
- thread-safe observation;
- serialisable value semantics.

Tuple conversion guarantees only the first and detaches outer membership from the list. The stronger claims require deeper design.

### 7.10.11 Persistent and structural-sharing alternatives

An immutable built-in tuple update creates a new tuple and copies references. Repeated mid-sequence updates therefore cost \(O(n)\) each. **Persistent data structures** preserve access to prior logical versions while sharing safe internal structure, often using trees or tries. Python’s core built-ins are not general persistent vectors or maps.

This concept is flagged before its full algorithmic treatment: structural sharing can make new logical versions without copying every element, but it requires representations designed so shared nodes cannot be mutated incompatibly. A shallow copy of an ordinary nested list is sharing without persistence guarantees; either alias can mutate a shared inner list.

When version history, undo, concurrent snapshots, or functional transformations dominate, a specialised immutable library or application-specific tree may better express the workload. The decision should compare actual asymptotics, memory retention of old versions, interoperability, and team comprehension.

### 7.10.12 Streaming versus materialised sequence

Sometimes the correct choice is no sequence container at all. If a consumer needs each value once in order, an iterator or generator can retain only bounded pipeline state. Materialising a list adds \(O(n)\) references and delays the first downstream result until production completes.

Materialisation remains necessary when the consumer needs:

- repeated traversal without recomputation;
- length before processing;
- random indexing or reverse order;
- sorting or permutation;
- a stable snapshot detached from a changing source;
- aggregate validation before any effects are committed.

Laziness remains preferable when:

- the source may be large or unbounded;
- early termination is common;
- production is expensive and not every item is needed;
- bounded memory and low initial latency dominate;
- one-pass ownership is acceptable.

Neither is categorically more efficient. A generator recomputed five times may cost more than one list, while a list of an infinite source is impossible.

### Worked example 7.6A — Queue design with an explicit processing invariant

Requirement: process jobs in first-in, first-out order. New jobs may be added while existing jobs execute. Each dequeued job is attempted at most once by this loop; failures are collected, not automatically retried.

~~~python
from collections import deque
from collections.abc import Callable

Job = Callable[[], None]


def drain(initial_jobs: list[Job]) -> list[Exception]:
    pending = deque(initial_jobs)
    failures: list[Exception] = []

    while pending:
        job = pending.popleft()
        try:
            job()
        except Exception as error:
            failures.append(error)

    return failures
~~~

Immediately before each test, <code>pending</code> contains exactly the initial jobs not yet attempted, in original order, provided jobs cannot mutate this local deque. <code>popleft</code> chooses the oldest. The try statement makes one attempt; whether the call succeeds or raises, the job has already left the deque and is not reinserted. The failures list preserves attempt order among failures.

The type alias and callable details are formalised in Chapters 8 and 12. The representation argument is current: a deque makes FIFO endpoints native. If jobs must enqueue more jobs, the function must pass an explicit queue interface or own a callback, and the invariant must expand to include appended work. If a failed job must be retried, retry limits, idempotency, delay, and fairness become new specifications.

### Worked example 7.6B — Binary frame construction without text confusion

Requirement: construct a frame consisting of a two-byte unsigned big-endian payload length followed by a UTF-8 payload. Payloads longer than 65,535 bytes are invalid.

~~~python
def frame_text(text: str) -> bytes:
    payload = text.encode("utf-8")
    size = len(payload)

    if size > 65_535:
        raise ValueError("UTF-8 payload exceeds two-byte length field")

    header = size.to_bytes(2, byteorder="big", signed=False)
    return header + payload
~~~

The length field measures bytes, not code points. For non-ASCII text these counts differ. Encoding occurs before bounds validation because the wire-format constraint concerns the encoded payload. <code>to_bytes</code> states width, byte order, and signedness explicitly. The final concatenation copies a bounded two-byte header and the payload once into an immutable bytes result.

This is only a framing fragment. A receiver must handle partial reads, validate declared length before allocation, impose resource limits, decode strictly under the same codec, and define connection behaviour for malformed frames.

### 7.10.13 A defensible decision record

A short structure decision should be reproducible rather than intuitive. For example:

> The ready-work structure is a deque because scheduling order is FIFO, insertion occurs only at the right endpoint, removal only at the left endpoint, and no positional search is required. Both endpoint operations have constant growth under the deque contract. The queue has an explicit maximum population enforced before append; overflow is reported rather than silently evicted. Jobs are immutable identifiers, while job records live in a separate mapping. A list was rejected because repeated front removal has linear per-removal shifts; a set was rejected because it does not preserve FIFO order.

This record names semantics, operations, costs, bounds, element policy, composition, and rejected alternatives. Such reasoning scales from exercises to architectural review.

> **Common misconception — “All sequence operations have the same cost because every sequence supports the same syntax.”**  
> Protocol similarity says what an operation means, not how its representation performs it. Indexing a range is arithmetic, indexing a list addresses an array slot, and indexing near a deque’s middle traverses blocks.
