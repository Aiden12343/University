# 7.11 Sorting and ordering contracts

`list.sort()` mutates a list and returns `None`; `sorted(iterable)` creates a new list. Both support a `key` function and a `reverse` flag.

```python
records = [
    {"name": "Grace", "score": 95},
    {"name": "Ada", "score": 98},
    {"name": "Barbara", "score": 95},
]

ordered = sorted(records, key=lambda record: (-record["score"], record["name"]))
```

The key function returns a tuple. Higher scores are converted to lower negative values for ascending sort; names break equal-score ties in ascending order. A **lambda expression** creates an anonymous function and is derived in Chapter 8; here it receives one record and returns its comparison key.

Python sorting is **stable**: records whose keys compare equal retain their original relative order. Stability permits multi-pass sorting from least significant key to most significant, though one compound key is often clearer.

Comparison functions can have effects or inconsistent results, but sorting assumes a coherent ordering. A key function is evaluated once per input element in the ordinary sorting contract, which avoids repeated expensive extraction and makes the intended order explicit.

### Worked example 7.6 — Stability preserves an earlier order

```python
records = [
    ("north", 2),
    ("south", 1),
    ("north", 1),
    ("south", 2),
]

by_number = sorted(records, key=lambda item: item[1])
by_region_then_number = sorted(by_number, key=lambda item: item[0])
print(by_region_then_number)
```

The second stable sort groups by region while preserving numeric order established among records within each region. The result is `[("north", 1), ("north", 2), ("south", 1), ("south", 2)]`.

### 7.11.1 Sorting requires an ordering relation

Sorting rearranges a finite population so that adjacent or all relevant pairs satisfy an ordering relation. A **total order** over a set of values is a relation that is reflexive, antisymmetric, transitive, and total: every pair is comparable. Programming-language comparison methods often expose strict order <code>&lt;</code>; a coherent strict total order is irreflexive, transitive, and compares every distinct pair in exactly one direction.

Not every Python value family provides one common total order. Python 3 does not arbitrarily order unrelated types:

~~~python
mixed = [3, "2", 1]
# sorted(mixed)                # TypeError
~~~

This is preferable to a meaningless order based on type names or addresses. A program must derive a common key under a domain rule:

~~~python
as_text = sorted(mixed, key=str)
numeric_if_possible = sorted(mixed, key=lambda value: int(value))
~~~

The two results answer different questions. The first compares string renderings; the second interprets every value numerically and may fail on non-numeric text. A key function is a semantic declaration, not merely a way to suppress an exception.

### 7.11.2 Mutation and result ownership

<code>list.sort</code> rearranges one list object and returns <code>None</code>. All aliases to that list observe the reordered references.

~~~python
values = [3, 1, 2]
alias = values
result = values.sort()

print(result)                  # None
print(alias)                   # [1, 2, 3]
~~~

<code>sorted</code> consumes an iterable and creates a new list:

~~~python
source = (3, 1, 2)
ordered = sorted(source)

print(source)                  # (3, 1, 2)
print(ordered)                 # [1, 2, 3]
~~~

Even when the source is already a list, <code>sorted(source)</code> returns a distinct list. The elements themselves are not copied deeply; the result contains the same object references in a new order.

The expression <code>values = values.sort()</code> is defective because it first sorts the list, then binds <code>values</code> to <code>None</code>. The return convention exposes mutation and prevents ambiguous chaining.

### 7.11.3 Key extraction transforms the ordering domain

The <code>key</code> callable maps each element to a comparison key:

\[
k:X\rightarrow K,
\]

where \(X\) is the element domain and \(K\) has the intended ordering. The sort orders by \(k(x)\), not ordinarily by comparing elements directly.

~~~python
records = [
    {"name": "Grace", "score": 95},
    {"name": "Ada", "score": 98},
    {"name": "Barbara", "score": 95},
]

ordered = sorted(records, key=lambda record: record["score"])
~~~

Python’s sorting API computes the key once per element for an ordinary successful operation, stores the association, compares keys, and emits elements in key order. This is the modern built-in form of **decorate–sort–undecorate**:

1. decorate each element with a key;
2. sort decorated associations;
3. remove the decoration while returning original elements.

If key extraction costs \(K\) per element and key comparison costs \(C\), the rough cost includes \(nK\) plus \(O(n\log n)C\) worst-case comparison work for the implementation’s comparison sort, rather than recomputing expensive keys on every comparison.

### 7.11.4 Key functions must be temporally coherent

A key should depend on stable state for the duration of sorting. A key involving time, random draws, mutable globals, network lookups, or state changed by earlier key calls can assign incoherent values:

~~~python
counter = 0


def unstable_key(value: str) -> int:
    global counter
    counter += 1
    return counter
~~~

Because the key is called once per element in encounter order, this example effectively preserves encounter order regardless of text. It does not sort by a stable property of the values. More dangerously, a key that queries changing external state can produce an order that corresponds to no single snapshot.

Acquire or derive stable records first, then sort by pure projections of that snapshot. A function is **pure** here if its returned key depends only on its argument and it causes no observable external effects. Python does not enforce purity; it is a design obligation.

### 7.11.5 Compound keys use lexicographic order

Tuple keys express primary, secondary, and later criteria. Python compares the first component; if equal, it proceeds to the next.

~~~python
people = [
    {"family": "Lovelace", "given": "Ada", "year": 1815},
    {"family": "Hopper", "given": "Grace", "year": 1906},
    {"family": "Lovelace", "given": "Byron", "year": 1836},
]

ordered = sorted(
    people,
    key=lambda person: (person["family"], person["given"], person["year"]),
)
~~~

Every component reached by a comparison must itself be comparable under a coherent common relation. If family and given names are equal but one year is <code>None</code> and another is an integer, comparison can fail late. A key should encode missingness explicitly:

~~~python
def optional_year_key(year: int | None) -> tuple[bool, int]:
    return (year is None, 0 if year is None else year)
~~~

Because <code>False &lt; True</code>, known years precede missing years. The placeholder zero is compared only among entries with equal missingness status; for two missing values it is equal, and for two known values the actual year is used. This technique converts an optional partial domain into a total compound key under an explicit “missing last” policy.

### 7.11.6 Mixed ascending and descending criteria

The global <code>reverse=True</code> reverses the complete key order. It cannot by itself state “score descending, name ascending.” For numeric scores, negation can invert one component:

~~~python
ranked = sorted(
    records,
    key=lambda record: (-record["score"], record["name"]),
)
~~~

Negation is appropriate only for a numeric domain with suitable semantics. It does not generalise to strings, NaNs, overflow-prone external numeric types, or every custom ordered object.

Stable multi-pass sorting offers a general alternative. Sort first by the least significant criterion, then by the most significant:

~~~python
ranked = sorted(records, key=lambda record: record["name"])
ranked.sort(key=lambda record: record["score"], reverse=True)
~~~

Stability preserves name order among equal scores during the second pass. The two-pass method performs two sorts and should be chosen for clarity or when different direction transformations are awkward. It also permits a sequence of dynamically configured criteria by applying stable sorts in reverse priority order.

### 7.11.7 Stability is an observable guarantee

Let input positions be \(i&lt;j\). If \(k(x_i)=k(x_j)\), a stable sort places \(x_i\) before \(x_j\) in the output. The property preserves information already encoded by input order.

~~~python
events = [
    ("09:00", "warning", "first warning"),
    ("09:01", "info", "status"),
    ("09:02", "warning", "second warning"),
]

by_level = sorted(events, key=lambda event: event[1])
~~~

The two warning events retain their chronological input order. Stability does not establish that input order was correct or meaningful; it merely preserves it within equal-key groups.

Reverse sorting remains stable with respect to equal keys. It reverses the ordering of unequal key groups, not the relative order inside an equal-key group. A manual <code>list(reversed(sorted(...)))</code> would reverse equal groups too and therefore differs from <code>sorted(..., reverse=True)</code>.

### 7.11.8 Timsort and adaptive behaviour

CPython’s list sorting uses Timsort, a stable adaptive merge-based algorithm developed to exploit existing ordered runs. “Adaptive” means work can decrease when input already contains useful order. Its worst-case comparison growth is \(O(n\log n)\), while already ordered or strongly structured inputs can approach linear behaviour.

The implementation identifies monotonic runs, extends short runs using insertion techniques, and merges runs while maintaining stack invariants. Details such as minimum run selection, galloping, temporary storage, and comparison counts belong to an implementation and version, not the abstract Python language. Chapter 13 derives sorting algorithms and proof properties from first principles; Chapter 15 relates the Python operation to CPython internals.

The lower bound for arbitrary comparison sorting is \(\Omega(n\log n)\) comparisons in the worst case because a decision tree must distinguish \(n!\) possible input permutations, and a binary comparison yields at most two branches. Specialised non-comparison sorts can beat this bound only by exploiting additional key structure, such as bounded integers; they do not contradict the comparison-model theorem.

### 7.11.9 Exception safety and temporary invisibility

Sorting can fail because key extraction, key comparison, allocation, or user code raises. For <code>sorted</code>, the source container ordinarily remains structurally unchanged because work occurs in a new list, though consuming a source iterator and executing key functions can already have effects. For <code>list.sort</code>, documentation warns that mutation or inspection during sorting is undefined or guarded, and a failing operation may leave the list in a partially modified but valid state rather than restoring original order.

~~~python
def require_nonnegative(value: int) -> int:
    if value < 0:
        raise ValueError("negative value")
    return value


values = [3, -1, 2]
try:
    values.sort(key=require_nonnegative)
except ValueError:
    pass
~~~

Never make correctness depend on <code>values</code> retaining its original order after such failure unless a documented guarantee says so. If the strong exception guarantee is required, derive all keys first, validate them, sort a separate structure, and commit by one controlled replacement after success:

~~~python
decorated = [(require_nonnegative(value), value) for value in values]
decorated.sort(key=lambda pair: pair[0])
replacement = [value for _, value in decorated]
values[:] = replacement
~~~

Even the final slice assignment can invoke reference destruction and allocation details, but the domain-invalid key cannot fail after mutation begins. Exception-safety reasoning separates failure sources by phase.

### 7.11.10 Comparison methods can execute arbitrary code

Sorting built-in integers appears computationally closed, but comparing user-defined objects can invoke methods with effects. A comparison might mutate global state, re-enter application code, block, or raise. Hash-table and sorting operations are therefore not universally primitive or effect-free merely because their syntax is concise.

A coherent ordering comparison must satisfy laws. If <code>a &lt; b</code>, <code>b &lt; c</code>, but not <code>a &lt; c</code>, a sorting algorithm receives contradictory evidence. Results can be surprising and cannot represent a sorted order under a nonexistent transitive relation. Python generally does not validate all ordering axioms; exhaustive checking would itself require costly comparisons and could not control time-varying behaviour.

Property-based tests can sample laws for a custom value domain:

\[
\neg(a&lt;a),
\]

\[
(a&lt;b\land b&lt;c)\Rightarrow a&lt;c,
\]

and, for total comparability of distinct values,

\[
a\ne b\Rightarrow(a&lt;b\lor b&lt;a).
\]

Chapter 12 develops executable property testing.

### 7.11.11 Floating NaN breaks ordinary total-order assumptions

NaN is unordered under ordinary floating comparisons:

~~~python
nan = float("nan")
print(nan < 1.0)               # False
print(nan > 1.0)               # False
print(nan == 1.0)              # False
print(nan == nan)              # False
~~~

A list containing NaNs can yield an order that does not meet a naive numeric expectation because comparison sorting assumes coherent relation properties. Define placement explicitly:

~~~python
from math import isnan


def float_key(value: float) -> tuple[bool, float]:
    return (isnan(value), 0.0 if isnan(value) else value)


ordered = sorted([3.0, nan, 1.0, 2.0], key=float_key)
~~~

This places all non-NaNs in ascending order and all NaNs last, preserving input order among NaNs through stability. The chosen placeholder does not mix with non-NaNs because the Boolean first component distinguishes groups.

Signed zero, infinities, decimal contexts, and domain-specific missing values may require additional policy. “Sort numerically” is incomplete until exceptional values are located.

### 7.11.12 Minimum, maximum, and key reuse

If only one extreme is needed, sorting the entire population performs unnecessary ordering work. <code>min</code> and <code>max</code> scan once:

~~~python
best = max(records, key=lambda record: record["score"])
~~~

For \(n&gt;0\), finding a maximum under comparisons needs at least \(n-1\) comparisons in the worst case: every non-maximum candidate must lose at least one comparison. The scan meets this \(\Theta(n)\) bound, whereas full comparison sorting generally costs \(O(n\log n)\).

Tie behaviour matters. <code>min</code> and <code>max</code> return the first encountered maximal or minimal item under ordinary equal-key behaviour, aligning with sort stability. A source iterator is consumed. For an empty source, provide <code>default</code> when absence is an ordinary outcome or allow <code>ValueError</code> when a value is required:

~~~python
best = max(records, key=lambda record: record["score"], default=None)
~~~

Here <code>None</code> must not be a valid record, or the result is ambiguous.

### 7.11.13 Top-k selection

When only the smallest or largest \(k\) elements are needed and \(k\ll n\), <code>heapq.nsmallest</code> and <code>heapq.nlargest</code> can avoid a complete ordering:

~~~python
from heapq import nlargest

top_ten = nlargest(10, records, key=lambda record: record["score"])
~~~

Heap-based selection commonly uses \(O(n\log k)\) comparison work and \(O(k)\) auxiliary state, though implementation may choose alternatives for special values of \(k\). Sorting all values uses \(O(n\log n)\) comparisons and returns a complete order. The break-even point depends on constants, key costs, input representation, and required output ordering.

If the application needs repeated dynamic insertion and extraction of the next priority, maintain a heap rather than repeatedly selecting from a list. Heaps and their invariants are built from scratch in Chapter 13.

### 7.11.14 Binary search requires a maintained sorted invariant

The <code>bisect</code> module locates insertion points in a sorted sequence using binary search. It does not sort or validate the input:

~~~python
from bisect import bisect_left, insort

values = [2, 5, 5, 9]
position = bisect_left(values, 5)
print(position)                # 1

insort(values, 7)
print(values)                  # [2, 5, 5, 7, 9]
~~~

<code>bisect_left</code> returns the first position at which the target can be inserted without placing a smaller element after it. Search performs \(O(\log n)\) comparisons on an indexable sequence. Insertion into a list still shifts a suffix, so <code>insort</code> is \(O(n)\) overall despite logarithmic position search.

The invariant must use the same ordering/key policy for every operation. Mutating an element’s sort-relevant state while it remains in the list can invalidate the order. Concurrent search and insertion require coordination. Binary search is fast because it relies on a costly-to-maintain global invariant.

### 7.11.15 Determinism requires tie-breakers and stable inputs

A stable sort cannot make an unstable input order deterministic. Suppose records arrive from a set or from concurrent completion order and many share the same primary key. Equal-key output can vary because stability preserves whatever order happened to arrive.

Add a unique deterministic tie-breaker when reproducibility matters:

~~~python
ordered = sorted(
    records,
    key=lambda record: (record["score"], record["identifier"]),
)
~~~

This requires identifiers to be unique, stable, and ordered under an agreed representation. If identifiers are random per run, the result remains non-reproducible. Reproducibility is an end-to-end property involving source order, key data, locale, library versions, floating behaviour, and concurrency—not a single sorting flag.

### 7.11.16 External sorting and memory bounds

<code>sorted</code> materialises all input elements into a list. If the data exceeds available memory, an **external sort** divides input into chunks that fit memory, sorts each chunk, writes runs to external storage, and merges the ordered runs. The standard library’s <code>heapq.merge</code> lazily merges already sorted iterables but does not sort the runs itself.

For \(r\) sorted runs, a heap-based merge retains one current element per non-empty run and performs approximately \(O(N\log r)\) comparisons over \(N\) total outputs. File descriptors, serialisation, stable tie rules, cleanup after failure, and temporary-space limits become part of the algorithm.

This section flags external memory before Chapter 13’s full treatment. The important boundary is that in-memory asymptotics omit I/O block size, seek cost, filesystem behaviour, and crash recovery.

### Worked example 7.6C — A validated leaderboard order

Requirement: rank records by score descending, completion time ascending, and identifier ascending. Scores must be finite numbers; completion times must be non-negative integers; identifiers must be non-empty strings. No mutation may occur before all records validate.

~~~python
from math import isfinite
from typing import TypedDict


class Result(TypedDict):
    identifier: str
    score: float
    milliseconds: int


def ranking_key(record: Result) -> tuple[float, int, str]:
    identifier = record["identifier"]
    score = record["score"]
    milliseconds = record["milliseconds"]

    if not identifier:
        raise ValueError("empty identifier")
    if not isfinite(score):
        raise ValueError(f"non-finite score for {identifier!r}")
    if milliseconds < 0:
        raise ValueError(f"negative completion time for {identifier!r}")

    return (-score, milliseconds, identifier)


def rank(records: list[Result]) -> list[Result]:
    decorated = [(ranking_key(record), record) for record in records]
    decorated.sort(key=lambda pair: pair[0])
    return [record for _, record in decorated]
~~~

The comprehension completes validation and key derivation for every record before sorting begins. If any record is invalid, no caller-owned list is mutated. The keys then form a total lexicographic order under the assumptions: finite floats have ordinary numeric ordering, integers are ordered, and strings have code-point lexicographic ordering. The unique identifier tie-breaker yields a deterministic order if identifier uniqueness is enforced elsewhere.

Negating finite scores states descending numeric score. It deliberately rejects infinities and NaNs so exceptional floating cases cannot violate the key model. Returning a new list preserves the input’s outer order. Record dictionaries remain shared objects, so later mutation of their ranking fields can make the returned order stale; the interface should use immutable records if durable ranking is required.

### Worked example 7.6D — Grouping after a stable sort

The standard library’s <code>itertools.groupby</code> groups adjacent equal keys, not all equal keys scattered through a source. Sorting by the same key first makes equal groups adjacent:

~~~python
from itertools import groupby
from operator import itemgetter

transactions = [
    ("west", 40),
    ("east", 10),
    ("west", 20),
    ("east", 15),
]

by_region = sorted(transactions, key=itemgetter(0))
totals = {
    region: sum(amount for _, amount in group)
    for region, group in groupby(by_region, key=itemgetter(0))
}

print(totals)                  # {'east': 25, 'west': 60}
~~~

Each group iterator shares the underlying traversal and must be consumed before advancing to the next group. Sorting costs \(O(n\log n)\) worst-case comparisons; grouping and summation then scan linearly. For simple hashable region keys, a one-pass dictionary accumulation would have expected \(O(n)\) time and preserve first-key insertion order. Sort-and-group is appropriate when sorted group output or non-hashable/order-based grouping is required; it is not the universal aggregation method.

> **Common misconception — “Stable sorting makes output deterministic.”**  
> Stability preserves the input order of equal keys. If that input order is nondeterministic, equal-key output remains nondeterministic unless an explicit stable tie-breaker is added.
