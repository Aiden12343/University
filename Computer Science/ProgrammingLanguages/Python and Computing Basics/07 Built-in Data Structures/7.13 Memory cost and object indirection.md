# 7.13 Memory cost and object indirection

Collection length is not memory size. A CPython list stores references plus capacity metadata; each referred Python object has its own representation and may be shared elsewhere. A list of one million references to the same integer object differs from one million distinct large integer objects. A dictionary adds hash-table metadata and unused capacity. Strings use representation strategies influenced by their largest required code point.

`sys.getsizeof(obj)` reports an implementation-defined shallow size for the object itself, not a recursive total of everything reachable. Summing shallow sizes can double-count shared objects and still omit allocator, interpreter, or external buffers.

### Worked example 7.8 — Shared versus distinct reachability

```python
shared = [0] * 1_000
distinct = list(range(1_000))
```

Both outer lists contain 1,000 references. `shared` repeats a reference to one integer object; `distinct` refers to many integer objects, though CPython may reuse selected small integers and `range` materialisation creates implementation-governed objects. Shallow size of the outer lists cannot describe total reachable memory.

Memory profiling must define ownership. If two structures share an object, charging its full size to both exaggerates combined use; charging it to neither hides it. Chapter 14 develops retained-size and allocation measurement.

### 7.13.1 Four incompatible meanings of “the size of this object”

Memory questions require an ownership model. At least four quantities are commonly conflated:

1. **shallow size**: storage directly assigned to one object’s representation;
2. **reachable size**: shallow sizes of all objects reachable by following selected references;
3. **retained size**: memory that would become unreachable if a particular object or owner were removed, under a specified graph and root set;
4. **allocated process memory**: storage obtained from language allocators, native libraries, mappings, stacks, code, and runtime infrastructure.

These quantities need not agree. If two caches refer to the same 100-megabyte byte buffer, the buffer belongs to the reachable size of each cache but is not exclusively retained by either. Adding both reachable sizes double-counts the shared buffer. The operating system’s resident memory also includes pages and allocator arenas not attributed cleanly to one Python object.

### 7.13.2 Containers commonly store references, not inline objects

A CPython list of integers contains a contiguous array of pointers to Python integer objects. It does not ordinarily embed the integer payloads directly in its element slots:

~~~python
repeated = [10_000] * 1_000
distinct = [10_000 + index for index in range(1_000)]
~~~

Both outer lists have approximately 1,000 reference slots. The first has 1,000 references to one integer object created for the repeated value expression; the second reaches many distinct integer objects. Reachable memory differs substantially even if shallow outer sizes are similar.

Tuples also store references but omit mutable capacity management. Dictionaries and sets store hash-table metadata and entries or indices according to implementation-specific compact layouts. Each key and value remains a separately managed Python object unless some specialised representation says otherwise.

This indirection enables heterogeneous collections and sharing but adds object headers, pointers, allocator overhead, cache misses, and reference-management work. Packed numeric arrays trade that flexibility for dense homogeneous storage.

### 7.13.3 Capacity is retained memory

A dynamic array’s allocated capacity can exceed its logical length. After growth, unused reference slots remain reserved so later appends can avoid immediate reallocation. Deleting elements reduces length but need not shrink capacity at every step.

Similarly, hash tables retain empty capacity to keep probe sequences short. Deletions can leave tombstone-like internal states until rebuilding or resizing. Therefore:

\[
\text{logical cardinality}\ne\text{allocated slots}\ne\text{bytes held}.
\]

An application that temporarily expands a collection may continue to retain more allocated memory than its current length suggests. Reconstructing a container can sometimes compact it, but doing so costs time, peak memory, and alias replacement, and no portable shrink threshold should be assumed without implementation evidence.

### 7.13.4 Shallow measurement with getsizeof

<code>sys.getsizeof</code> calls the object’s size hook and adds garbage-collector overhead where applicable in CPython. Its result is shallow and implementation-defined:

~~~python
from sys import getsizeof

outer = [[0] * 100 for _ in range(100)]
print(getsizeof(outer))
print(sum(getsizeof(row) for row in outer))
~~~

The first call does not recursively include inner lists or integer objects. The sum includes inner list storage but still omits or double-counts element objects depending on how it is interpreted. An object can also own memory outside Python’s reported shallow size—for example, through a native extension or memory-mapped region.

Shallow size is useful for controlled representation comparisons when interpreted narrowly. It is not evidence of complete application memory.

### 7.13.5 A recursive size walker must choose graph semantics

A pedagogical reachable-size walker can avoid double-counting identities:

~~~python
from collections import deque
from sys import getsizeof


def selected_reachable_size(root: object) -> int:
    pending = deque([root])
    seen: set[int] = set()
    total = 0

    while pending:
        current = pending.popleft()
        identity = id(current)
        if identity in seen:
            continue
        seen.add(identity)
        total += getsizeof(current)

        if isinstance(current, dict):
            pending.extend(current.keys())
            pending.extend(current.values())
        elif isinstance(current, (list, tuple, set, frozenset, deque)):
            pending.extend(current)

    return total
~~~

This function is deliberately limited. It knows only selected built-in edge types, treats all reachable nodes as charged to the root, ignores attributes of arbitrary objects, omits native buffers, and uses shallow reports whose meanings vary. It is nevertheless better than naive recursion because it terminates on cycles and counts shared objects once within one traversal.

Extending it with <code>gc.get_referents</code> can reveal more CPython references but also walks interpreter implementation state that may not belong to an application ownership question. A general graph walk cannot infer economic ownership from reachability alone.

### 7.13.6 Retained size depends on roots and dominators

In a reachability graph rooted at live program roots, object \(d\) **dominates** object \(x\) if every root-to-\(x\) path passes through \(d\). Removing the last reference to a dominator can make dominated objects unreachable. This motivates retained-size analysis in heap profilers.

Suppose one session object owns a list of parse trees and no other root reaches those trees. The session dominates them, so releasing it can reclaim their graph. If a global cache also refers to one tree, that tree is not exclusively retained by the session.

Retained-size reasoning explains why the largest shallow object is often not the cause of memory retention. A small dictionary entry, closure, traceback, generator frame, or cache key can preserve a vast graph through one reference path.

### 7.13.7 Reference lifetime and logical leaks

A **memory leak** in a garbage-collected language often means memory remains reachable even though the application no longer needs it. The collector cannot infer semantic usefulness. Common roots include:

- unbounded dictionaries or sets used as caches;
- queues whose consumers cannot keep pace;
- global registries and callback lists;
- completed task or future objects retaining results and exceptions;
- exception tracebacks retaining stack frames and their locals;
- suspended generators retaining local variables;
- closures capturing a large enclosing object;
- accidental aliases in long-lived containers.

Bounding collection cardinality is only part of the remedy. A “1,000-entry cache” can still be unbounded in bytes if values vary without a size limit. Eviction can fail to release memory when external aliases retain values. Resource design must state count, byte, time, and ownership bounds as appropriate.

### 7.13.8 Cyclic garbage collection and finalisation

CPython reference counting can reclaim many objects when their reference count reaches zero, but a cycle gives every member an internal reference. A separate cyclic garbage collector identifies unreachable cycles among tracked objects.

~~~python
left: list[object] = []
right: list[object] = [left]
left.append(right)

del left
del right
~~~

The cycle can become unreachable even though its internal references remain. Exact collection timing is not a language-level destruction schedule. Alternative Python implementations use different memory management, and even CPython may delay cyclic collection.

Programs must not depend on object destruction to close files, release locks, commit transactions, or return scarce resources promptly. Context managers establish lexical lifetime. Chapter 11 formalises resource protocols; Chapter 15 explains CPython reference counting and cyclic collection.

### 7.13.9 Allocator retention and process measurements

When Python objects are deallocated, their memory may return to a Python allocator pool rather than immediately to the operating system. The process’s resident-set size can therefore stay high while that memory becomes reusable for future Python allocations. Conversely, virtual address space can be reserved without all pages being resident.

Terms must be separated:

- **virtual size**: address ranges mapped into a process;
- **resident set size**: pages presently resident in physical memory, subject to operating-system accounting;
- **private memory**: pages not shared under the measurement tool’s model;
- **peak memory**: maximum observed value over a defined interval;
- **allocation traffic**: cumulative bytes allocated, even if later freed.

A profiler that counts Python allocation traces answers a different question from an operating-system monitor. Both can be correct.

### 7.13.10 Tracing allocations with tracemalloc

The standard-library <code>tracemalloc</code> module records traces for Python memory allocations under its supported allocator hooks. A minimal before/after comparison is:

~~~python
import tracemalloc

tracemalloc.start()
before = tracemalloc.take_snapshot()

data = [{str(index): index} for index in range(10_000)]

after = tracemalloc.take_snapshot()
for statistic in after.compare_to(before, "lineno")[:10]:
    print(statistic)
~~~

The first snapshot establishes a baseline after tracing begins. The comparison groups net changes by allocation source line. Results include allocations retained at the second snapshot, not every temporary allocation that appeared and vanished between snapshots.

Measurement perturbs the program: trace storage consumes memory and tracing adds overhead. Native allocations invisible to tracemalloc may dominate workloads using extension libraries. Repeated trials, controlled inputs, warmed imports, and workload-specific grouping are needed before drawing conclusions.

### 7.13.11 Locality and traversal cost

Two algorithms with the same Big-O growth can differ because of memory locality. Iterating a list scans contiguous reference slots; following nodes in a linked structure may jump among allocations. Modern processors fetch memory in cache lines, predict access patterns, and pay large latency for cache misses relative to simple arithmetic.

Python object indirection means even list traversal may jump from the compact pointer array to scattered element objects. Operations that need only identities or references can remain mostly within the array; operations accessing each object’s payload perform further loads. Packed arrays improve locality by placing element payloads contiguously.

Locality is one reason a linked list’s theoretical \(O(1)\) insertion after a known node does not make it universally faster than a dynamic array. Workload, access pattern, allocation, cache behaviour, and interpreter overhead all matter. Chapter 14 turns these into measurement methodology.

### 7.13.12 Sharing can save memory and increase retention

Structural sharing avoids duplicate objects:

~~~python
common_header = {"version": 1, "encoding": "utf-8"}
documents = [
    {"header": common_header, "body": "alpha"},
    {"header": common_header, "body": "beta"},
]
~~~

One header object serves both documents. This saves storage and ensures that a deliberate shared update affects both. It also couples mutation and lifetime: retaining either document retains the common header, and accidental modification changes both views.

Sharing immutable values is easier to reason about. Strings, bytes, tuples of immutable components, frozensets, and immutable record classes can be safely shared with respect to their value state. Sharing still affects lifetime and retained memory even when mutation is impossible.

### Worked example 7.8A — Diagnose a retained generator frame

~~~python
def prefixes(data: bytes):
    prepared = data.decode("utf-8").splitlines()
    for line in prepared:
        yield line[:10]


stream = prefixes(large_payload)
first = next(stream)
~~~

After one <code>next</code>, the generator is suspended inside the loop. Its frame retains <code>prepared</code>, and perhaps <code>data</code> or decoded intermediates according to compiler liveness and implementation details. Keeping <code>stream</code> alive can therefore retain the complete list of lines even if the caller wants only <code>first</code>.

A redesign that accepts an iterable of lines moves ownership outward; a streaming decoder/file iterator can avoid complete splitting. Alternatively, if only one prefix is needed, use a function returning one value rather than leaving a generator suspended. The important diagnostic is the reference path from a small generator object to a large retained graph.

### Worked example 7.8B — Compare representation hypotheses empirically

An experiment comparing a million small integers in a list with a packed array should record more than one number:

~~~python
from array import array
from sys import getsizeof

n = 1_000_000
boxed = list(range(n))
packed = array("q", range(n))

print(getsizeof(boxed))
print(getsizeof(packed))
~~~

The list measurement reports its outer reference array, not the reachable integer objects. The array measurement generally includes its packed buffer in its own object-size report, but the exact meaning is implementation-specific. A fair report should include:

- Python implementation, version, build, pointer width, and platform;
- array type code and its item size;
- shallow sizes and a justified reachable-size estimate;
- construction peak and steady state;
- traversal or arithmetic workload, not storage alone;
- correctness constraints such as numeric range and overflow;
- repeated measurements and uncertainty.

Without this metadata, a ratio is an anecdote rather than a reproducible performance result.

> **Common misconception — “If memory is still in the process, Python leaked it.”**  
> Objects may be legitimately reachable, allocator pools may retain freed blocks for reuse, native libraries may own memory, or operating-system accounting may lag. A leak claim requires a reference/lifetime model and measurements appropriate to it.
