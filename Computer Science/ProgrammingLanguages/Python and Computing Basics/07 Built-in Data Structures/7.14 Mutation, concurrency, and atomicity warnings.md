# 7.14 Mutation, concurrency, and atomicity warnings

Some CPython built-in operations appear indivisible under a conventional GIL-enabled build, but Python source should not infer broad thread-safety contracts from present bytecode or implementation accidents. An operation can invoke user code through hashing, equality, comparison, descriptors, or finalisation. Compound invariants almost always span multiple operations.

```python
if key not in mapping:
    mapping[key] = create_value()
```

The check and insertion form a compound action. Another thread or process can alter relevant state between them under a concurrent design. Even if one dictionary assignment is protected internally, the two-step invariant is not thereby atomic. Use explicit coordination or an interface whose documented operation owns the whole transition.

**Atomic** means appearing as one indivisible operation relative to specified observers. It is always relative to a concurrency model and interface. “Dictionary operations are atomic” is too broad to guide portable Python, especially as CPython supports build configurations with different global-lock behaviour.

### 7.14.1 Atomicity is relative to observers and interruption points

An operation is atomic only with respect to a named model. The statement “assignment is atomic” is incomplete unless it identifies:

- which Python implementation and build;
- threads, processes, signal handlers, callbacks, or asynchronous tasks as observers;
- whether user-defined methods can run during the operation;
- which shared state comprises the invariant;
- what intermediate states observers are allowed to see.

At a hardware level, several memory accesses may implement one Python expression. At an interpreter level, one source statement may compile to several bytecode instructions. At an application level, even a single container method can invoke hashing, equality, iteration, allocation, or finalisation. Atomicity at one layer does not automatically compose upward.

### 7.14.2 The GIL is not a data-structure transaction

Conventional CPython builds use a global interpreter lock (GIL) that ordinarily permits one thread at a time to execute Python bytecode in one interpreter. Chapter 14 gives the precise qualifications and free-threaded developments. The GIL does not promise that an arbitrary source-level expression runs without thread switches, nor that a multi-operation invariant is protected.

~~~python
counts[key] = counts.get(key, 0) + 1
~~~

Conceptually, this performs lookup, default choice, addition, and assignment. Two threads can both read the same old count and each write the same incremented result, losing one update under an interleaving permitted by the runtime and invoked operations.

Even if one particular built-in mutation happens not to be interrupted in one CPython version, code based on that accident is fragile across implementations and build configurations. Synchronisation should protect the semantic transition, not merely a guessed bytecode boundary.

### 7.14.3 Hash and equality callbacks break the “primitive operation” illusion

Dictionary and set lookup may call <code>__hash__</code> and <code>__eq__</code> on user-defined objects. Those methods are arbitrary Python code:

~~~python
if candidate in shared_set:
    ...
~~~

The concise expression can therefore execute callbacks that acquire locks, mutate other structures, yield control through I/O implemented by extensions, raise exceptions, or re-enter the same collection indirectly. A safe concurrent design narrows key types to stable, well-behaved values where possible and does not assume membership is an indivisible machine primitive.

Comparison callbacks similarly affect sorting, list membership, removal by equality, and tuple comparison. Finalisation triggered by dropping a reference can also execute code. Container syntax hides dispatch; it does not remove it.

### 7.14.4 Check-then-act is a compound transition

The pattern

~~~python
if identifier not in records:
    records[identifier] = build_record()
~~~

has at least three distinct policies:

1. reject concurrent duplicates;
2. permit duplicate construction but retain one result;
3. ensure exactly one construction and share its success or failure.

A lock around both check and insertion can implement part of the first policy:

~~~python
from threading import Lock

records: dict[str, object] = {}
records_lock = Lock()


def insert_unique(identifier: str, record: object) -> None:
    with records_lock:
        if identifier in records:
            raise ValueError("duplicate identifier")
        records[identifier] = record
~~~

Constructing <code>record</code> outside the lock reduces critical-section duration but permits wasted duplicate work. Constructing inside the lock serialises potentially slow or re-entrant code and can deadlock if construction needs the same lock. Exactly-once initialisation may require a per-key future/promise state, failure propagation, cancellation policy, and cleanup. The data-structure operation alone does not choose these semantics.

### 7.14.5 Locks protect invariants, not variables

A lock should be associated with a set of invariants over one or more objects. In the event window, one lock might protect <code>by_id</code>, <code>order</code>, <code>categories</code>, and tag counts together. Locking each dictionary separately would permit observers to see cross-index disagreement between operations.

The critical section must include every read and write whose combination establishes the transition:

~~~python
with window_lock:
    # validate current shared state
    # mutate all coordinated structures
    # restore the complete invariant before releasing
~~~

Document:

- which lock guards each invariant;
- whether callers may hold other locks;
- lock acquisition order;
- whether callbacks occur while locked;
- whether iteration returns a snapshot or retains the lock;
- behaviour on exception and cancellation.

Locking prevents selected interleavings; it does not validate domain input or guarantee progress. Incorrect lock ordering can create deadlock.

### 7.14.6 Iteration needs a consistency model

An API returning an iterator over mutable shared state must define what the iteration observes:

- **live weakly consistent view:** may reflect some concurrent changes under defined rules;
- **fail-fast view:** detects selected structural changes and raises, without promising complete detection;
- **snapshot:** observes a fixed state as of a defined moment;
- **locked traversal:** excludes writers until iteration completes;
- **versioned traversal:** detects or labels changes using an epoch/version.

Built-in dictionary iterators are not a general concurrency-consistency facility. Their size-change error prevents some invalid internal traversal but does not provide an application snapshot.

A shallow snapshot under a lock is a common boundary:

~~~python
with records_lock:
    snapshot = tuple(records.items())

for identifier, record in snapshot:
    process(identifier, record)
~~~

The lock is released before slow processing. The key-item population and order are fixed, but mutable record objects remain shared. A deep or immutable snapshot may be needed if their fields must also remain stable.

### 7.14.7 Async tasks interleave at suspension, not arbitrary bytecodes

In one event-loop thread, ordinary asynchronous tasks switch cooperatively at suspension points such as <code>await</code>. Code containing no suspension can often reason as one event-loop turn, but called functions or context operations may suspend indirectly, and callbacks can still create re-entrancy.

~~~python
if key not in cache:
    value = await fetch(key)
    cache[key] = value
~~~

The explicit <code>await</code> permits another task to observe the absent key and begin the same fetch. This **cache stampede** wastes work and may overload the source. A per-key asynchronous lock or stored in-progress task can coalesce requests, but must define cancellation and failure handling.

The threading lock shown earlier must not be held across <code>await</code> in ordinary asynchronous code: it can block the event-loop thread and prevent the task that could release progress. Use asynchronous synchronisation primitives designed for the event loop and keep critical sections bounded.

### 7.14.8 Processes do not normally share ordinary Python containers

Separate processes ordinarily have separate address spaces. Passing a list or dictionary through a multiprocessing queue serialises a value representation; the receiver obtains a distinct object graph under the serialisation contract. Later mutation in one process does not automatically appear in the other.

Shared-memory objects, manager proxies, databases, and files provide explicit inter-process coordination with different costs and failure modes. A manager dictionary is not simply a local dictionary made safe: operations involve communication, serialisation, server state, and compound-action races. The same check-then-act analysis applies, now with process failures and network-like boundaries.

### 7.14.9 Thread-safe queues own compound endpoint coordination

The standard-library <code>queue.Queue</code> provides a synchronised multi-producer, multi-consumer queue with optional capacity and blocking operations. It is preferable to combining a bare deque with ad hoc condition variables when that contract fits.

~~~python
from queue import Queue

jobs: Queue[str] = Queue(maxsize=100)
jobs.put("compile")
job = jobs.get()
try:
    process(job)
finally:
    jobs.task_done()
~~~

The queue coordinates insertion/removal and waiting. It does not make <code>process</code> idempotent or guarantee exactly-once external effects. <code>task_done</code> accounts for completion tracking and must correspond to each successful <code>get</code>. Sentinel-based shutdown, cancellation, worker failure, backpressure, and queue draining remain protocol decisions.

### 7.14.10 Immutability reduces but does not eliminate concurrency problems

An immutable value can be read concurrently without another actor changing that value’s fields. This removes many data races. It does not ensure:

- atomic publication of a group of immutable values;
- absence of mutable objects reachable from a shallowly immutable wrapper;
- deterministic ordering of concurrent events;
- safe access to external resources referenced by the value;
- lifetime management;
- visibility semantics in every implementation and native extension.

Copy-on-write publication can make a mapping snapshot:

~~~python
from types import MappingProxyType

current = MappingProxyType({"mode": "safe"})


def updated(snapshot, key: str, value: str):
    replacement = dict(snapshot)
    replacement[key] = value
    return MappingProxyType(replacement)
~~~

Readers of the old proxy keep a stable outer mapping because no owner retains and mutates its underlying dictionary in this disciplined design. Publishing the new reference still needs a concurrency model, and nested mutable values would defeat deep snapshot semantics. Copy cost is \(O(n)\) per update, so this is suitable for read-heavy, modest configurations rather than high-frequency enormous maps.

### 7.14.11 Free-threaded evolution strengthens the need for contracts

CPython’s optional free-threaded work removes the assumption of one process-wide GIL in qualifying builds while adding internal safety mechanisms. This evolution does not mean built-in containers become multi-operation transactions, nor that unsynchronised logical races become correct. It reinforces a long-standing rule: rely on documented concurrency guarantees and explicit ownership, not an inferred global lock.

Portable library documentation should say whether an object is:

- immutable after construction;
- confined to one thread or task;
- safe for concurrent independent reads;
- internally synchronised for named operations;
- externally synchronised by the caller;
- unsafe for re-entrant callbacks.

“Thread-safe” without an operation set and invariant is too vague.

### Worked example 7.9A — Snapshot publication with a version

Requirement: many readers need a consistent immutable configuration mapping; one updater occasionally replaces it. Readers must be able to report which configuration version they used. The following illustrates the data model, not a complete cross-implementation synchronisation proof:

~~~python
from dataclasses import dataclass
from threading import Lock
from types import MappingProxyType
from collections.abc import Mapping


@dataclass(frozen=True)
class Configuration:
    version: int
    values: Mapping[str, str]


configuration_lock = Lock()
configuration = Configuration(0, MappingProxyType({}))


def read_configuration() -> Configuration:
    with configuration_lock:
        return configuration


def replace_configuration(values: Mapping[str, str]) -> Configuration:
    replacement_values = MappingProxyType(dict(values))

    global configuration
    with configuration_lock:
        replacement = Configuration(
            configuration.version + 1,
            replacement_values,
        )
        configuration = replacement
        return replacement
~~~

The copying and proxy construction occur before lock acquisition, so arbitrary iteration over the caller’s mapping does not run while the global lock is held. Under the function’s precondition, the copied strings are immutable values. The critical section reads the prior version, constructs the small immutable wrapper, and publishes one reference. Readers acquire the same lock and receive one version/value pair rather than independently reading fields across an update.

Returning the configuration after releasing the lock is safe with respect to its designed immutability. The mapping proxy is deeply stable here only because the hidden underlying dictionary is never mutated and its keys and values are strings. A hostile Mapping subclass supplied to replacement can still execute arbitrary code during the preliminary copy; input trust and exception policy must be specified.

### Worked example 7.9B — Lost update as an interleaving trace

Let a shared mapping initially contain <code>{"x": 0}</code>. Two workers execute <code>counts["x"] = counts.get("x", 0) + 1</code>. An allowed logical interleaving is:

| Step | Worker A | Worker B | Shared count |
|:---:|:---|:---|:---:|
| 1 | reads 0 | — | 0 |
| 2 | — | reads 0 | 0 |
| 3 | computes 1 | — | 0 |
| 4 | — | computes 1 | 0 |
| 5 | writes 1 | — | 1 |
| 6 | — | writes 1 | 1 |

The intended serial result is 2, but the observed result is 1. Every individual read and write can be internally valid; the composition violates the increment invariant. A lock around the read–modify–write transition, a queue that funnels updates to one owner, an atomic counter supplied by a suitable lower-level facility, or a transactional database update can repair it under different system models.

> **Common misconception — “The GIL means Python data structures need no locks.”**  
> The GIL is an interpreter implementation mechanism, not a transaction over application invariants. Compound actions, callbacks, I/O, alternative builds, and evolving free-threaded execution require explicit concurrency design.
