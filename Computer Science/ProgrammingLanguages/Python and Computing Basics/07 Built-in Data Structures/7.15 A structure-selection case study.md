# 7.15 A structure-selection case study

Requirement: process a stream of event records. Each record has a unique identifier, category, timestamp, and tags. The program must:

1. reject duplicate identifiers;
2. preserve arrival order for final reporting;
3. count events per category;
4. identify all unique tags;
5. retrieve a record by identifier;
6. retain only the most recent 1,000 records.

No single built-in structure makes every operation native. A composed design uses:

- `dict[id, record]` for identifier lookup and duplicate rejection;
- `deque[id]` for arrival order and efficient removal from the left;
- `dict[category, int]` for counts;
- `set[tag]` for global uniqueness.

When the deque exceeds 1,000, remove the oldest identifier and delete its record from the lookup dictionary. If category counts and tags must describe only retained records, eviction must also decrement or recompute them; global history and active-window state are different specifications.

Invariant:

- deque identifiers are unique and occur in dictionary keys;
- dictionary keys occur exactly once in the deque;
- deque length is at most 1,000;
- counts equal the category frequencies over whichever population the specification names;
- tag set equals the union of tags over that same population.

The data structure is the coordinated set of containers plus cross-container invariants. Merely declaring types does not maintain consistency when an exception interrupts a multi-container update. The update procedure must either validate before mutation, arrange rollback, or construct replacement state before committing.

### Worked example 7.9 — Validate, derive, then commit

```python
from collections import Counter, deque
from dataclasses import dataclass


@dataclass(frozen=True)
class Event:
    identifier: str
    category: str
    tags: frozenset[str]


class EventWindow:
    def __init__(self, limit: int = 1_000) -> None:
        if limit <= 0:
            raise ValueError("limit must be positive")
        self.limit = limit
        self.by_id: dict[str, Event] = {}
        self.order: deque[str] = deque()
        self.categories: Counter[str] = Counter()

    def add(self, event: Event) -> None:
        if event.identifier in self.by_id:
            raise ValueError(f"duplicate identifier: {event.identifier}")

        self.by_id[event.identifier] = event
        self.order.append(event.identifier)
        self.categories[event.category] += 1

        if len(self.order) > self.limit:
            oldest_id = self.order.popleft()
            oldest = self.by_id.pop(oldest_id)
            self.categories[oldest.category] -= 1
            if self.categories[oldest.category] == 0:
                del self.categories[oldest.category]
```

This preview uses classes and dataclasses from later chapters. The structure-selection reasoning is current: dictionary lookup, deque endpoints, immutable tag sets, and explicit cross-container update. A production design must still address failure during mutation and concurrent access.

### 7.15.1 Refine the ambiguous requirements

The initial prose contains unresolved choices. Before implementation, ask:

- Is identifier uniqueness global over all history or only over the retained window?
- Does “preserve arrival order” mean source order, accepted-record order, or timestamp order?
- Do category counts and unique tags describe all history or only retained records?
- Can a record be replaced, corrected, or deleted explicitly?
- Is the capacity a count of records or a byte/resource bound?
- What validates timestamps and tags?
- What happens if one update step fails?
- May multiple callers add and query concurrently?

For this worked design, adopt the following specification:

1. identifier uniqueness applies only to currently retained records;
2. order records successful calls to <code>add</code>, not record timestamps;
3. category counts and tag membership describe exactly the current window;
4. there is no replacement or explicit deletion operation;
5. the positive <code>limit</code> bounds record count;
6. identifiers and categories are non-empty strings, and tags are non-empty strings stored in a frozenset;
7. a failed validation leaves state unchanged;
8. the object is confined to one thread unless an outer owner synchronises all access.

These decisions turn vague nouns into testable behaviour.

### 7.15.2 Choose one source of truth and derived indexes

Let <code>by_id</code> be the primary record store. The deque <code>order</code> and the counters are derived indexes. An alternative would store full records in the deque and an ID-to-record dictionary; that duplicates record references but still requires coordination. Storing only IDs in <code>order</code> centralises record lookup in <code>by_id</code>.

Use:

- <code>dict[str, Event]</code> for unique current identifier lookup;
- <code>deque[str]</code> for FIFO arrival order;
- <code>Counter[str]</code> for current category multiplicity;
- <code>Counter[str]</code> for current tag multiplicity.

A set of tags alone cannot support exact eviction because it loses how many retained events contribute each tag. The counter’s keys derive the active-tag set.

### 7.15.3 State the representation invariant formally

Let \(B\) be <code>by_id</code>, \(Q\) be the deque sequence, \(C\) the category counter, \(T\) the tag counter, and \(L\) the limit. A valid state satisfies:

\[
L>0,
\]

\[
0\le |Q|=|B|\le L,
\]

\[
Q\text{ contains no duplicate identifier},
\]

\[
set(Q)=keys(B),
\]

\[
\forall c,\quad C[c]
=\#\{i\in Q:B[i].category=c\}>0
\quad\text{for stored }c,
\]

and

\[
\forall t,\quad T[t]
=\#\{i\in Q:t\in B[i].tags\}>0
\quad\text{for stored }t.
\]

The “greater than zero for stored keys” clause requires deletion of zero counter entries. It makes <code>set(T)</code> exactly the active tag set and <code>set(C)</code> exactly the active category set.

### 7.15.4 Derive the add transition

Assume a valid initial state and a valid event \(e\) whose identifier is absent from \(B\). First insert it into each structure:

\[
B'=B\cup\{e.id\mapsto e\},
\]

\[
Q'=Q\mathbin{+}[e.id],
\]

\[
C'=C+\{e.category\mapsto1\},
\]

\[
T'=T+\sum_{t\in e.tags}\{t\mapsto1\}.
\]

If \(|Q'|\le L\), this is the final state. If \(|Q'|=L+1\), let \(o\) be the leftmost identifier. Eviction removes \(o\) from \(Q'\), removes \(B'[o]\) from the primary store, and decrements the category and every tag of that old record. Any zero count is deleted.

Because the pre-state length is at most \(L\), one addition can require at most one eviction. This fact is a derived precondition for the single <code>if</code>; if a future bulk-add API can exceed the limit by several records, it needs a loop or batch derivation.

### 7.15.5 Complete single-owner implementation

~~~python
from __future__ import annotations

from collections import Counter, deque
from collections.abc import Iterator
from dataclasses import dataclass


@dataclass(frozen=True, slots=True)
class Event:
    identifier: str
    category: str
    tags: frozenset[str]

    def __post_init__(self) -> None:
        if not self.identifier:
            raise ValueError("event identifier must be non-empty")
        if not self.category:
            raise ValueError("event category must be non-empty")
        if any(not tag for tag in self.tags):
            raise ValueError("event tags must be non-empty")


class EventWindow:
    def __init__(self, limit: int = 1_000) -> None:
        if isinstance(limit, bool) or not isinstance(limit, int):
            raise TypeError("limit must be an exact integer domain value")
        if limit <= 0:
            raise ValueError("limit must be positive")

        self._limit = limit
        self._by_id: dict[str, Event] = {}
        self._order: deque[str] = deque()
        self._categories: Counter[str] = Counter()
        self._tags: Counter[str] = Counter()

    def __len__(self) -> int:
        return len(self._order)

    def __contains__(self, identifier: object) -> bool:
        return identifier in self._by_id

    def get(self, identifier: str) -> Event | None:
        return self._by_id.get(identifier)

    def events(self) -> Iterator[Event]:
        for identifier in self._order:
            yield self._by_id[identifier]

    def category_counts(self) -> dict[str, int]:
        return dict(self._categories)

    def active_tags(self) -> frozenset[str]:
        return frozenset(self._tags)

    def add(self, event: Event) -> Event | None:
        if event.identifier in self._by_id:
            raise ValueError(f"duplicate identifier: {event.identifier!r}")

        self._by_id[event.identifier] = event
        self._order.append(event.identifier)
        self._categories[event.category] += 1
        self._tags.update(event.tags)

        evicted: Event | None = None
        if len(self._order) > self._limit:
            oldest_identifier = self._order.popleft()
            evicted = self._by_id.pop(oldest_identifier)
            self._decrement(self._categories, (evicted.category,))
            self._decrement(self._tags, evicted.tags)

        return evicted

    @staticmethod
    def _decrement(counter: Counter[str], values) -> None:
        for value in values:
            counter[value] -= 1
            if counter[value] == 0:
                del counter[value]

    def _assert_invariant(self) -> None:
        identifiers = list(self._order)
        assert 0 <= len(identifiers) <= self._limit
        assert len(identifiers) == len(set(identifiers))
        assert set(identifiers) == set(self._by_id)

        expected_categories = Counter(
            self._by_id[identifier].category
            for identifier in identifiers
        )
        expected_tags = Counter(
            tag
            for identifier in identifiers
            for tag in self._by_id[identifier].tags
        )

        assert self._categories == expected_categories
        assert self._tags == expected_tags
        assert all(count > 0 for count in self._categories.values())
        assert all(count > 0 for count in self._tags.values())
~~~

This implementation previews future syntax and object-model features while exposing present structure decisions. The fields are private by convention: callers cannot legitimately mutate the containers directly. Query methods return immutable event objects or detached/frozen aggregate values. <code>events</code> is a live generator and therefore requires single-owner non-mutating use during traversal; a public concurrent version should return a snapshot or define consistency.

The exact-integer check excludes Boolean limits because <code>bool</code> is a subclass of <code>int</code> but is not accepted by this domain. Event field annotations are not runtime validators by themselves; <code>__post_init__</code> validates emptiness but assumes constructor callers honour types. Chapter 12 develops stronger validation and static checking boundaries.

### 7.15.6 Proof sketch for normal addition

Assume invariant \(I\) and \(|Q|<L\). The new identifier is absent, so appending it preserves uniqueness and inserting it creates exactly the same new member in <code>by_id</code> and <code>order</code>. Thus set equality and equal length are preserved.

Incrementing the event’s category adds one to exactly the count set described by the new event. Updating the tag counter iterates the event’s frozenset, whose tags are unique, and adds one contribution per tag. Existing positive counts remain positive; new counts become one. No eviction occurs because new length is at most \(L\). Therefore every conjunct of \(I\) holds.

### 7.15.7 Proof sketch for addition with eviction

Assume \(|Q|=L\) before addition. The preliminary insertion produces a state of length \(L+1\) satisfying all correspondence and count equations except the bound. Let \(o\) be the unique oldest identifier. Removing the leftmost deque occurrence and the mapping association for \(o\) removes the same identifier from both populations, restoring length \(L\) and set equality.

The evicted event contributed exactly one to its category count and one to each tag it contains because event tags are a set. Decrementing those components therefore restores the count equations over the remaining IDs. Deleting any resulting zero ensures the positive-key normal form. Other counts are unchanged. Thus \(I\) holds again.

The proof assumes every mutation completes successfully. It is a functional-state proof, not an exception-safety proof.

### 7.15.8 Operation-cost table

Let \(w\le L\) be current window size and \(t=|event.tags|\). Under ordinary CPython built-ins and expected hashing:

| Operation | Expected time | Additional result/state space | Qualification |
|:---|:---:|:---:|:---|
| identifier membership | \(O(1)\) | \(O(1)\) | hash/equality costs excluded |
| <code>get</code> by ID | \(O(1)\) | \(O(1)\) | returns shared immutable event |
| add without eviction | \(O(t)\) | \(O(t)\) new distinct tag keys worst case | deque/map/category contributions otherwise expected constant |
| add with eviction | \(O(t+t_o)\) | bounded by retained index changes | \(t_o\) is old event tag count |
| iterate events | \(O(w)\) | generator state \(O(1)\) | live consistency restriction |
| category snapshot | \(O(c)\) | \(O(c)\) | \(c\) active categories |
| active-tag snapshot | \(O(u)\) | \(O(u)\) | \(u\) active tags |
| invariant checker | expected \(O(w+s)\) | \(O(w+s)\) | \(s\) total tag memberships |

Worst-case hash behaviour can make mapping/set/counter operations linear in their current table population and invoke expensive equality. The total number of tag memberships can be as large as \(w\cdot t_{max}\); a record-count limit alone does not bound it unless each event’s tag count and string sizes are also bounded.

### 7.15.9 Failure analysis

Validation occurs during Event construction before insertion. Duplicate checking occurs before mutation. Yet the <code>add</code> method can still fail during hashing, allocation, counter update, or reference management. With exact built-in strings and frozensets whose contents are exact strings, hash/equality behaviour is well-controlled, but <code>MemoryError</code> and asynchronous process termination remain.

The sequence of mutations does not provide a formal strong exception guarantee. For example, the dictionary insertion can succeed and the deque append allocation can then fail. Production options include:

- accept the basic guarantee and rebuild derived indexes after detected failure;
- precompute a complete replacement state, then replace an outer immutable state reference;
- write an explicit rollback log, accepting that rollback can also fail;
- place authoritative state in a transactional database;
- restrict failure model and document which catastrophic failures are outside recovery.

Copy-on-write replacement costs \(O(w+s)\) per addition but can make publication atomic under a suitable outer lock and immutable record values. The in-place version has better ordinary update complexity. Exception guarantees are part of the performance/correctness trade-off.

### 7.15.10 Aliasing audit

Each Event is frozen and stores tags as a frozenset, so the window can safely share event references with callers with respect to these fields. Strings are immutable. Query snapshots construct fresh dictionaries or frozensets, preventing callers from mutating internal counters.

The <code>events</code> generator exposes references to immutable Events but reads live internal structures. If the owner calls <code>add</code> between yielded events, eviction can remove a later identifier and dictionary lookup may fail. A safe public snapshot method could acquire ownership coordination and return:

~~~python
def event_snapshot(self) -> tuple[Event, ...]:
    return tuple(self._by_id[identifier] for identifier in self._order)
~~~

This costs \(O(w)\) time and references but fixes outer membership/order at return time. Because Event values are deeply immutable under their defined fields, the snapshot is stable.

### 7.15.11 Invariant-based transition tests

Tests should verify general properties after every operation, not only one expected output:

~~~python
def test_window_eviction_and_counts() -> None:
    window = EventWindow(limit=2)
    first = Event("e1", "open", frozenset({"red", "shared"}))
    second = Event("e2", "close", frozenset({"blue", "shared"}))
    third = Event("e3", "open", frozenset({"green"}))

    assert window.add(first) is None
    window._assert_invariant()

    assert window.add(second) is None
    window._assert_invariant()
    assert window.active_tags() == frozenset({"red", "blue", "shared"})

    evicted = window.add(third)
    window._assert_invariant()

    assert evicted == first
    assert "e1" not in window
    assert list(window.events()) == [second, third]
    assert window.category_counts() == {"close": 1, "open": 1}
    assert window.active_tags() == frozenset({"blue", "shared", "green"})
~~~

The crucial assertion is that <code>shared</code> remains after evicting the first record because the second still contributes it. This is precisely the case a plain union set cannot handle correctly.

Further transition tests must cover limit one, duplicate rejection at full capacity, invalid Event construction, category count reaching zero, tag count reaching zero, empty initial state, and a long random sequence compared against a simple reference model.

### 7.15.12 A simple reference oracle

For tests, a less optimised representation can act as an **oracle**—an independently understandable implementation used to predict results. A list of Events is sufficient for small cases:

~~~python
def model_add(events: list[Event], event: Event, limit: int) -> Event | None:
    if any(existing.identifier == event.identifier for existing in events):
        raise ValueError("duplicate identifier")

    events.append(event)
    if len(events) > limit:
        return events.pop(0)
    return None


def model_categories(events: list[Event]) -> Counter[str]:
    return Counter(event.category for event in events)


def model_tags(events: list[Event]) -> set[str]:
    return {tag for event in events for tag in event.tags}
~~~

This oracle has linear duplicate lookup and front-removal costs, but tests use small populations. Its direct definitions reduce the chance of reproducing the production implementation’s same index-maintenance defect. Property-based tests can generate operation sequences and compare the optimised window against this model after every successful transition.

### 7.15.13 Requirement changes and representation consequences

Small wording changes can require new structures:

- **Global historical uniqueness:** retain a separate set of every seen identifier, whose memory grows with history or use durable storage/probabilistic membership under a changed error model.
- **Timestamp order:** use sorted insertion, a heap for pending order, or periodic sorting; define equal timestamps and late arrivals.
- **Fast category query in arrival order:** the category counter is insufficient; maintain per-category ordered IDs or filter \(O(w)\).
- **Arbitrary deletion:** remove from the dictionary in expected constant time, but locating/removing an interior deque ID is \(O(w)\); use a linked/indexed ordering structure or tolerate lazy tombstones.
- **Byte-bounded capacity:** track estimated or exact record weight and evict in a loop until within budget.
- **Concurrent readers/writers:** add one invariant-owning synchronisation boundary and snapshot semantics.
- **Crash recovery:** move authoritative transitions to durable transactional storage and reconstruct in-memory indexes.

Data structures follow requirements. An implementation optimised for one operation vector can be fundamentally unsuitable after a specification change.

### 7.15.14 Case-study dossier

A complete structure-selection dossier records:

1. domain vocabulary and clarified requirements;
2. accepted input and failure contracts;
3. source of truth and every derived index;
4. formal representation invariant;
5. state transitions and proof sketches;
6. expected, worst-case, space, and output-sensitive costs;
7. aliasing and mutation authority;
8. exception-safety and concurrency model;
9. resource bounds beyond cardinality;
10. executable invariant checks and independent oracle tests;
11. observability and serialisation boundaries;
12. predicted consequences of likely requirement changes.

This is the level at which a data structure becomes an engineered component rather than a collection of convenient built-ins.

> **Common misconception — “Once each container is internally valid, the combined data structure is valid.”**  
> Every dictionary, deque, and counter can be internally well formed while their cross-container facts disagree. The representation invariant belongs to the composed state and must be preserved by each transition.
