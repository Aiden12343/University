# 7.2 A minimal cost vocabulary

An operation’s **time complexity** describes how its required work grows with a defined input size. **Space complexity** describes growth in additional storage or retained representation. Chapter 13 develops formal asymptotic analysis; this chapter uses the following forward definitions:

- (O(1)), **constant growth**, means an upper bound independent of collection length under the stated model.
- (O(n)), **linear growth**, means an upper bound proportional to the number (n) of relevant elements.
- (O(\log n)), **logarithmic growth**, means repeated constant-factor reduction, such as halving a search interval.
- **Amortised (O(1))** means that although occasional operations are expensive, the total cost of a sequence of (m) operations is (O(m)), giving constant average charge per operation across that sequence.
- **Expected (O(1))** means constant expected cost under assumptions about hashing and table state; it is not a worst-case guarantee.

Big-O notation discards constant factors and lower-order terms to describe growth. It does not mean instantaneous, one processor instruction, or fast for every size. Every complexity claim must name the operation, implementation or abstract structure, input size, and relevant case.

### 7.2.1 Cost requires a model

A cost claim must identify:

- operation;
- input-size variable;
- abstract or concrete implementation;
- worst, average, expected, amortised, or best case;
- cost unit;
- assumptions about element operations;
- whether output construction is counted.

“Dictionary lookup is O(1)” suppresses that it is expected rather than worst-case, that hashing and equality have their own costs, that the dictionary must fit memory, and that pathological collisions can degrade behaviour.

### 7.2.2 Upper bounds and tight bounds

Big-O gives an asymptotic upper bound. If (T(n)\in O(f(n))), there exist positive constants (c) and (n_0) such that:

\[
T(n)\leq c f(n)
\quad\text{for every }n\geq n_0.
\]

Big-O alone need not describe the exact or tight growth. **Big-Omega**, (\Omega), gives an asymptotic lower bound. **Big-Theta**, (\Theta), gives matching upper and lower bounds.

Saying list traversal is (\Theta(n)) under constant-cost item visits is stronger than saying it is (O(n)): every element must be produced, so both bounds apply.

Chapter 13 derives asymptotic notation completely. Here it prevents “O(1)” from being read as one clock cycle.

### 7.2.3 Worst, average, expected, and amortised

These analyses answer different questions:

- **worst case:** maximum cost over admitted inputs of size (n);
- **best case:** minimum cost;
- **average case:** mean under an explicitly stated input distribution;
- **expected cost:** expectation over algorithmic randomness or model assumptions;
- **amortised cost:** deterministic charge averaged across an operation sequence.

List append is amortised constant under dynamic-array growth; no randomness is required. Hash-table lookup is commonly expected constant under hashing assumptions; one lookup can still take linear time in a pathological collision case.

### 7.2.4 Element-operation cost

Container algorithms invoke element protocols. List membership can perform up to (n) equality comparisons:

\[
T(n)=\sum_{i=1}^{n} C_{=}(i)+O(n),
\]

where (C_{=}(i)) is the cost of comparing the candidate with element (i). If each comparison examines a string of length (m), a bound can be (O(nm)), not simply (O(n)).

Sorting performs (O(n\log n)) comparisons in the worst case for Python’s comparison sort, but a user key function is evaluated once per element under the built-in sorting contract, and each comparison of resulting keys has its own cost.

### 7.2.5 Output-sensitive lower bounds

An operation producing (k) new references ordinarily requires at least (\Omega(k)) work and storage to materialise them. List slicing of length (k), list concatenation producing (n+m) positions, and converting an iterable of (n) items to a list cannot be true constant-time materialisations.

A view can avoid copying but changes aliasing and lifetime semantics. Python list slices are copies of the outer reference segment, not views.

### 7.2.6 Space has layers

Distinguish:

- shallow container storage;
- storage of referenced element objects;
- unused capacity;
- allocator overhead;
- temporary work space;
- retained source objects due to aliases;
- operating-system pages and fragmentation.

<code>sys.getsizeof(container)</code> reports an implementation-specific shallow size, not the transitive object graph. If 1,000 list positions all refer to one object, summing element shallow sizes 1,000 times overcounts unique retained memory; ignoring elements undercounts.

### 7.2.7 Locality and constants

Two structures with the same asymptotic bound can differ materially. Contiguous pointer arrays support cache-friendly sequential traversal. Linked nodes require pointer chasing and more allocations. Python object indirection means even list traversal follows references to separately stored objects, but the reference array itself remains compact and contiguous in CPython.

Asymptotic reasoning selects scalable candidates; measurement on representative workloads resolves constants, cache behaviour, allocator effects, and interpreter overhead.

### 7.2.8 Mutation cost includes reference management

Replacing or deleting a collection element changes object reachability. In CPython, decrementing a removed object’s reference count can trigger immediate deallocation and arbitrary finalisation code. An operation described as shifting pointers can therefore invoke much more work through object lifecycle.

Portable complexity claims usually assume element retention/release is bounded or exclude destructor effects. State the assumption when adversarial user-defined objects are admitted.

### 7.2.9 Adversarial inputs

Public services must consider inputs chosen to maximise cost:

- colliding hashes;
- deeply nested structures;
- extremely long equal-prefix strings;
- enormous integer magnitudes;
- repeated insertions at a list front;
- degenerate serialised records;
- infinite iterables supplied to materialising APIs.

Expected or amortised performance under ordinary input is not a denial-of-service guarantee. Bound input size, time, nesting, and output.

### Worked example 7.1B — Compare duplicate detection

List-based:

~~~python
unique = []

for value in source:
    if value not in unique:
        unique.append(value)
~~~

For (n) distinct values under constant-cost equality, membership examines 0, 1, ..., (n-1) elements:

\[
0+1+\cdots+(n-1)=\frac{n(n-1)}{2}\in\Theta(n^2).
\]

Set-assisted while preserving first occurrence order:

~~~python
seen = set()
unique = []

for value in source:
    if value not in seen:
        seen.add(value)
        unique.append(value)
~~~

Under expected constant hash-table membership and insertion, total expected time is (O(n)), with (O(n)) additional references. It requires hashable values and coherent equality/hash semantics. The faster asymptotic method has a stronger element-type precondition and more memory.

### 7.2.10 Benchmarking is an experiment

A responsible microbenchmark records:

- Python implementation and build;
- version and platform;
- input construction outside the measured region when appropriate;
- warm-up policy;
- repetitions and distribution;
- realistic element types and sizes;
- garbage-collection and process conditions;
- summary statistics, not one best time;
- semantic equivalence of compared operations.

Do not benchmark list and set membership by rebuilding the set inside every measured lookup unless construction belongs to the actual workload. Complexity and measurement answer complementary questions.

> **Common misconception — “Big-O predicts which line is faster.”**  
> It describes growth under a model. Constants, element operations, memory layout, input distribution, and one-time construction can dominate finite workloads.
