# 7.3 Lists as mutable sequences

A `list` is a mutable sequence of object references. It preserves element order, admits duplicates, supports integer indexing and slicing, and can grow or shrink.

```python
names = ["Ada", "Grace", "Ada"]
names.append("Edsger")
names[1] = "Barbara"
print(names)
```

Output:

```text
['Ada', 'Barbara', 'Ada', 'Edsger']
```

The list owns its sequence of references, not necessarily the referred objects. Assignment to `names[1]` changes which object occupies one position. It does not mutate the old string or every occurrence of an equal string.

Negative indices count from the end: `items[-1]` selects the last element when one exists. For length (n), an ordinary valid index belongs to (-n\leq i<n). An out-of-range subscription raises `IndexError`.

A **slice** specifies a half-open interval and optional step. `items[start:stop]` includes `start` and excludes `stop`. Omitted bounds default according to direction. Slicing a list creates a new list containing references to the selected elements.

```python
letters = ["a", "b", "c", "d", "e"]
print(letters[1:4])
print(letters[:3])
print(letters[::2])
print(letters[::-1])
```

Output:

```text
['b', 'c', 'd']
['a', 'b', 'c']
['a', 'c', 'e']
['e', 'd', 'c', 'b', 'a']
```

Half-open intervals compose: the length of an ordinary forward slice from `start` to `stop` is `stop - start` when bounds are valid and `start <= stop`; adjacent intervals `[a:b]` and `[b:c]` meet without overlap.

### 7.3.1 CPython’s dynamic-array representation

In CPython, a list is implemented as a **dynamic array** of pointers to Python objects. A contiguous array allows direct address calculation for index (i), giving (O(1)) indexing. The list object tracks logical length and allocated capacity. Capacity may exceed length so that many appends fit without allocating a new array each time.

When capacity is exhausted, CPython allocates a larger pointer array and copies existing references. That individual append is (O(n)), but capacity growth is arranged so a long append sequence has amortised (O(1)) cost per append. The exact growth formula is an implementation detail and can change; programs should rely on the documented list behaviour, not a private capacity schedule.

Inserting or deleting near the front requires shifting later references, hence (O(n)) movement. Popping the final element is amortised (O(1)); popping index zero is (O(n)). For a queue with frequent removal from the left, `collections.deque` is the appropriate standard-library structure.

Typical CPython costs for a list of length (n), with a slice of length (k):

| Operation | Typical cost | Reason |
|:---|:---:|:---|
| `items[i]` | (O(1)) | direct array position |
| `items[i] = value` | (O(1)) | replace one stored reference |
| `append(value)` | amortised (O(1)) | spare capacity, occasional resize |
| `pop()` | amortised (O(1)) | remove final reference |
| `insert(0, value)` | (O(n)) | shift existing references |
| `pop(0)` | (O(n)) | shift remaining references |
| `value in items` | (O(n)) worst case | equality scan |
| `items[a:b]` | (O(k)) | construct new list and copy references |
| `items.copy()` | (O(n)) | shallow-copy reference array |
| iteration | (O(n)) | produce every element |
| `sort()` | (O(n\log n)) comparisons worst case | comparison sorting with adaptive behaviour |

These figures omit the cost of user-defined equality, comparison, destruction, or allocation effects. If `x == element` is expensive, membership inherits that cost.

### Worked example 7.1 — Choose a queue representation

Defective queue for repeated left removal:

```python
queue = []
queue.append("A")
queue.append("B")
queue.append("C")

while queue:
    print(queue.pop(0))
```

The behaviour is correct for three items, but each `pop(0)` shifts every remaining reference. Across (n) removals the total shifting is proportional to

\[
(n-1)+(n-2)+\cdots+1,
\]

which grows quadratically.

Use a deque:

```python
from collections import deque

queue = deque(["A", "B", "C"])
while queue:
    print(queue.popleft())
```

A deque supports efficient appends and removals at both ends under its standard-library implementation contract. Selection follows the dominant operation, not familiarity with list syntax.

> **Common misconception — “List append is (O(1)), therefore every append takes the same time.”**  
> The bound is amortised. Most appends use spare capacity; occasional growth reallocates and copies the reference array.

### 7.3.2 Logical length and capacity

In a dynamic array, **length** is the number of occupied element positions visible through the sequence. **Capacity** is the number of positions for which backing storage is currently reserved. The invariant is:

\[
0\leq \text{length}\leq\text{capacity}.
\]

Indexing is valid only below logical length; spare capacity is not a collection of accessible <code>None</code> elements. Appending writes at the old logical end and increments length. When length equals capacity, growth first obtains a larger backing array.

CPython’s exact capacity schedule is private implementation policy. It deliberately over-allocates by a moderate factor so append-heavy workloads avoid one allocation per item.

### 7.3.3 Aggregate proof of amortised append

Assume for analysis that capacity doubles whenever full. Beginning from capacity one, resizes copy:

\[
1+2+4+\cdots+2^k < 2^{k+1}
\]

references by the time capacity reaches (2^{k+1}). For (n) appends, total resize copying is less than a constant multiple of (n). Adding the (n) ordinary writes gives total (O(n)), hence amortised (O(1)) per append.

CPython does not use exact doubling indefinitely, but geometric-style over-allocation supports the same aggregate conclusion. Amortised analysis does not say the expensive append’s latency is bounded independently of length.

### 7.3.4 Index normalisation

For a list of length (n), Python interprets a negative index (i) conceptually as (n+i). Valid indices satisfy:

\[
-n\leq i<n.
\]

Thus <code>-1</code> selects (n-1), and <code>-n</code> selects zero. The index <code>-n-1</code> remains out of range.

An index object must support the integer-index protocol, not merely conversion from arbitrary float:

~~~python
values = ["a", "b", "c"]
# values[1.0] raises TypeError.
~~~

Silently truncating 1.9 would conceal a domain error, so list subscription does not call general <code>int</code> parsing.

### 7.3.5 Slice normalisation

A slice contains start, stop, and step components, any of which can initially be absent:

~~~python
selection = values[start:stop:step]
~~~

Python normalises omitted and out-of-range bounds according to sequence length and step direction. Ordinary slicing clips rather than raises for distant bounds:

~~~python
print([1, 2, 3][0:1_000])
~~~

This returns the whole list. Step zero raises <code>ValueError</code> because no progression exists.

The method <code>slice.indices(length)</code> exposes normalised progression parameters:

~~~python
selection = slice(None, None, -1)
print(selection.indices(5))
~~~

The result supplies values suitable for <code>range</code>-like reasoning. Use this to implement custom sequence slicing consistently.

### 7.3.6 Slices copy references

~~~python
inner = {"value": 1}
source = [inner, {"value": 2}]
copy = source[:]

print(copy is source)
print(copy[0] is source[0])
~~~

The outer lists are distinct; corresponding elements remain aliases. Slice cost is proportional to the number (k) of selected references, not the entire source length unless the slice covers it.

A stepped slice still constructs a new list:

~~~python
every_second = source[::2]
~~~

Its cost is (\Theta(k)) for (k) selected elements. Negative-step reversal copies the whole reference sequence.

### 7.3.7 Slice assignment

Ordinary slice assignment replaces a region with items obtained from an iterable:

~~~python
values = [0, 1, 2, 3, 4]
values[1:4] = [10, 20]
~~~

The list becomes <code>[0, 10, 20, 4]</code>. Length changes from five to four. Later references may shift, so cost includes movement proportional to the affected suffix.

Extended slice assignment with step other than one must preserve selected-position count:

~~~python
values = [0, 1, 2, 3, 4, 5]
values[::2] = [10, 20, 30]
~~~

Three replacements fit positions zero, two, and four. Supplying two or four replacement items raises <code>ValueError</code>. Extended assignment replaces positions rather than opening a contiguous region.

### 7.3.8 Deletion

~~~python
del values[index]
del values[start:stop]
~~~

Deletion removes references and compacts the list as required. Deleting near the front shifts a large suffix. <code>clear()</code> removes all items while preserving the list object’s identity:

~~~python
alias = values
values.clear()
print(alias)
~~~

Both names observe the empty list. Rebinding <code>values = []</code> would leave <code>alias</code> pointing to the previous list.

### 7.3.9 Append, extend, and concatenation

These operations differ:

~~~python
values.append(iterable)
values.extend(iterable)
combined = values + list(iterable)
~~~

<code>append</code> adds the iterable object as one element. <code>extend</code> consumes it and adds each produced item to the existing list. Concatenation constructs a new list containing references from both operands and requires list-compatible operands under built-in semantics.

Extending a list from itself is defined:

~~~python
values = [1, 2]
values.extend(values)
print(values)
~~~

The result is <code>[1, 2, 1, 2]</code>. An implementation must avoid an endless traversal of newly appended items. Custom mutation-while-iteration code does not inherit this specialised guarantee.

### 7.3.10 Insert is position normalisation, not keyed placement

<code>values.insert(index, item)</code> inserts before the normalised position. Very negative indices place near the beginning, and overly large indices append at the end under list semantics. Existing suffix references shift right.

Repeatedly inserting at zero is quadratic:

~~~python
values = []
for item in source:
    values.insert(0, item)
~~~

For reversed accumulation, append and reverse once, use a deque, or construct from an appropriate reversed iterable.

### 7.3.11 Remove searches by equality

<code>values.remove(candidate)</code> removes the first equal element and raises <code>ValueError</code> if absent. Its cost combines linear search with suffix shifting:

~~~python
values = [record_a, record_b, record_c]
values.remove(equal_to_b)
~~~

The object removed need not be identical to <code>equal_to_b</code>; equality determines the match. If duplicates matter, “remove first equal” needs explicit domain justification.

### 7.3.12 Pop combines retrieval and mutation

<code>pop()</code> removes and returns the final element. <code>pop(index)</code> removes and returns a selected element:

~~~python
last = values.pop()
first = values.pop(0)
~~~

Final pop is amortised constant in ordinary CPython usage; front pop shifts the remainder. Empty pop raises <code>IndexError</code>. A guard <code>if values</code> can establish non-emptiness in single-threaded stable state, but a shared concurrent list needs synchronisation or an atomic queue interface.

### 7.3.13 Count and index

<code>count(value)</code> traverses the entire list and counts equal elements. <code>index(value)</code> returns the first equal position and stops, raising <code>ValueError</code> if absent. Optional bounds restrict the searched range without slicing:

~~~python
position = values.index(target, start, stop)
~~~

This avoids allocating a slice and preserves the original coordinate system. Repeated index searches can produce quadratic algorithms; build a mapping when stable key-to-position lookup dominates.

### 7.3.14 Repetition and aliasing

~~~python
rows = [[]] * 3
rows[0].append("x")
~~~

Sequence repetition copies references, not element objects. All positions designate one inner list. For independent rows:

~~~python
rows = [[] for _ in range(3)]
~~~

Repeating immutable scalar references is ordinarily harmless:

~~~python
zeros = [0] * 1_000
~~~

The list contains 1,000 references to an immutable integer object; positions can later be rebound independently.

### 7.3.15 Lists as stacks

Using <code>append</code> for push and <code>pop</code> for removal at the same end gives an efficient last-in–first-out stack:

~~~python
stack: list[str] = []
stack.append("first")
stack.append("second")
top = stack.pop()
~~~

The application must prevent arbitrary middle insertion or removal if stack laws matter. A wrapper class can expose only stack operations and preserve a clearer abstraction.

### Worked example 7.2 — Stable in-place compaction

Requirement: remove negative integers in place while preserving order and list identity because aliases must observe the result.

~~~python
def remove_negatives(values: list[int]) -> None:
    write = 0

    for value in values:
        if value >= 0:
            values[write] = value
            write += 1

    del values[write:]
~~~

Invariant after consuming a prefix: <code>values[:write]</code> contains exactly the non-negative items from that original prefix in order. Write never exceeds the traversal position, so assigning cannot overwrite an unread item. After traversal, deleting the suffix removes obsolete positions.

This runs in linear time and constant auxiliary reference storage. It mutates values during list iteration without changing length until traversal is complete; its invariant explicitly justifies that controlled use.

> **Common misconception — “A list is an array of its values.”**  
> In ordinary CPython it is a dynamic array of object references. Contiguity applies to references, while element objects can reside elsewhere and be shared.
