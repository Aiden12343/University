# 7.4 List mutation and iterator interaction

List methods can mutate in place and conventionally return `None`:

```python
numbers = [3, 1, 2]
result = numbers.sort()
print(numbers)
print(result)
```

Output:

```text
[1, 2, 3]
None
```

Returning `None` prevents accidental claims that the method produced an independent sorted list. The built-in `sorted(iterable)` instead consumes an iterable and returns a new list.

Do not add or remove list elements while iterating unless the exact iterator semantics and invariant are deliberate. A list iterator advances an index through the live list; shifting elements can skip or repeat logical candidates.

```python
values = [1, 2, 2, 3]
for value in values:
    if value == 2:
        values.remove(value)
print(values)
```

This can leave a 2 because removing the first shifts the second into a position the iterator has already advanced beyond. Construct a filtered result or mutate through a carefully designed index algorithm:

```python
values = [value for value in values if value != 2]
```

The new-list approach separates traversal of the old structure from construction of the new invariant.

### 7.4.1 Iterator position follows indices

A CPython list iterator conceptually retains a next index into the live list. Structural mutation changes which element occupies that index. This explains, without legitimising every mutation pattern, why deletion can skip and insertion can repeat.

~~~python
values = ["A", "B", "C"]
iterator = iter(values)

print(next(iterator))
values.insert(0, "X")
print(next(iterator))
~~~

An implementation following live index semantics commonly produces A and then A again: insertion shifted the original A from index zero to one, which was the iterator’s next position. Treat this as an implementation experiment, not a portable mutation contract.

### 7.4.2 Mutation-neutral element updates

Replacing elements without changing list length leaves index geometry stable:

~~~python
for index, value in enumerate(values):
    values[index] = transform(value)
~~~

This can be correct when <code>transform</code> does not alter list structure through an alias. A list comprehension constructing a new list often provides a stronger exception guarantee: if transformation fails, the original list remains structurally unchanged.

### 7.4.3 Reverse traversal for deletion

Deleting selected positions from right to left prevents earlier indices from shifting:

~~~python
for index in range(len(values) - 1, -1, -1):
    if should_remove(values[index]):
        del values[index]
~~~

This preserves the relative order of retained items. Deletion still shifts a suffix; repeated middle deletions can remain quadratic. Stable compaction or new-list construction is linear.

### 7.4.4 Mutation methods return None

Methods such as <code>append</code>, <code>extend</code>, <code>insert</code>, <code>remove</code>, <code>reverse</code>, and <code>sort</code> mutate and conventionally return <code>None</code>. This prevents misleading chains:

~~~python
# Defective:
ordered = values.sort()
~~~

After the call, <code>values</code> is sorted and <code>ordered</code> is <code>None</code>. Use:

~~~python
values.sort()
ordered_copy = sorted(values)
~~~

according to identity and mutation requirements.

### 7.4.5 Exception safety of in-place transformation

If a key function or comparison raises during <code>list.sort</code>, the list remains a valid list but its order can be partially modified. The operation provides documented implementation-level guarantees rather than a universal strong rollback promise.

When preserving original order on failure matters:

~~~python
ordered = sorted(values, key=key_function)
~~~

Only rebind or publish <code>ordered</code> after successful completion. Element-level effects performed by the key function are not rolled back.

### 7.4.6 Alias-visible versus replacement updates

~~~python
alias = values
values = [value for value in values if admitted(value)]
~~~

This rebinds only <code>values</code>; <code>alias</code> retains the old list. Slice assignment can replace contents while preserving list identity:

~~~python
values[:] = [
    value
    for value in values
    if admitted(value)
]
~~~

The right side is fully constructed before slice assignment. If filtering raises, the original list remains structurally unchanged by the assignment itself. If it succeeds, aliases observe the new contents.

### 7.4.7 Concurrency warning

Some individual list operations are memory-safe or atomic under particular CPython builds, but compound reasoning is not:

~~~python
if values:
    item = values.pop()
~~~

Another thread or re-entrant callback can alter the list between condition and pop. Free-threaded CPython builds and GIL-enabled builds have different mechanisms, and neither turns a multi-operation invariant into an atomic transaction. Use an owned queue or lock as Chapter 14 specifies.

### Worked example 7.3 — Three filtering contracts

New value:

~~~python
filtered = [
    value
    for value in source
    if admitted(value)
]
~~~

Preserve identity after successful staging:

~~~python
replacement = [
    value
    for value in values
    if admitted(value)
]
values[:] = replacement
~~~

Constant-extra-reference in-place compaction:

~~~python
write = 0
for value in values:
    if admitted(value):
        values[write] = value
        write += 1
del values[write:]
~~~

The first preserves the source. The second gives strong structural failure behaviour before the commit but uses another list. The third minimises auxiliary structure but can leave a partially overwritten list if <code>admitted</code> raises. “Filter a list” is incomplete until identity, memory, failure, and aliasing contracts are selected.

> **Common misconception — “Avoid mutating lists during iteration” is the entire rule.**  
> The real obligation is to preserve traversal and representation invariants. New-list construction is the safest default; carefully proved fixed-length replacement or compaction can be correct.
