# 7.5 Tuples as immutable sequences

A `tuple` is an immutable sequence of object references. Parentheses often aid grouping, but the comma creates an ordinary tuple expression:

```python
empty = ()
singleton = (42,)
pair = 1, 2
```

The comma in `(42,)` distinguishes a one-element tuple from parenthesised integer `(42)`. Tuples support indexing, slicing, iteration, equality, and lexicographic ordering when corresponding elements support it.

**Lexicographic order** compares the first unequal corresponding elements; if all shared positions compare equal, the shorter sequence comes first. The comparison may fail when a required element pairing lacks an ordering.

Tuples serve several roles:

- fixed-position records whose component meanings are established externally;
- multiple return values and unpacking;
- immutable composite keys when every element is hashable;
- snapshots of an element-reference sequence.

For public records with named fields, a dataclass or named tuple can make meaning clearer than positional indices.

### Worked example 7.2 — Tuple immutability is shallow

```python
record = ("Ada", [98, 95])
record[1].append(100)
print(record)
```

The tuple’s two positions still refer to the same string and list. The nested list changes. Attempting `record[1] = []` fails because it would replace a tuple position.

Hashing `record` fails because the nested list is unhashable. A tuple’s hashability is conditional on its elements, since equal tuples must receive equal hashes and their element values participate.

Tuple concatenation and repetition produce new tuples because the original cannot change:

```python
base = (1, 2)
extended = base + (3,)
print(base, extended)
```

Repeated tuple concatenation in a loop can copy growing prefixes and become quadratic. Build a list with amortised append, then convert once when an immutable tuple is required.

### 7.5.1 Tuple construction and packing

Comma-separated expression lists create tuple values in relevant contexts:

~~~python
point = 3, 4
~~~

is conventionally described as **tuple packing**. Unpacking performs the inverse structural assignment:

~~~python
x, y = point
~~~

The words packing and unpacking are conceptual. An implementation need not always allocate an intermediate tuple when optimisation can preserve observable semantics.

A trailing comma is valuable in multi-line records:

~~~python
record = (
    identifier,
    timestamp,
    value,
)
~~~

It makes later line insertion mechanically independent and unambiguously retains tuple syntax for one element.

### 7.5.2 Tuple does not imply record meaning

The value:

~~~python
("Ada", 1815, "mathematics")
~~~

contains positions but no runtime field names. Meaning is supplied by external convention: position zero is name, one is birth year, two is discipline. Swapping two same-typed fields can remain syntactically and type-correct while becoming semantically wrong.

For private short-lived local data, positional tuples are economical. For public or evolving records, use:

- <code>typing.NamedTuple</code>;
- <code>collections.namedtuple</code>;
- a frozen dataclass;
- a domain class;
- a mapping when field sets are genuinely dynamic.

These choices differ in mutability, inheritance, pattern matching, memory, validation, and compatibility. Chapters 9, 11, and 12 develop them.

### 7.5.3 Structural immutability

No tuple operation can replace, insert, or delete its stored positions. This permits safe sharing of the position array and eligibility for hashing when every element is hashable.

The tuple can still provide a route to mutable state:

~~~python
configuration = (
    "production",
    {"retries": 3},
)
configuration[1]["retries"] = 4
~~~

Calling this “an immutable configuration” would be false at the graph level. Use immutable nested representations, such as tuples and frozensets of immutable values, or a domain object enforcing mutation policy.

### 7.5.4 Conditional hashability

Tuple hashing combines element hashes under an implementation-defined algorithm while obeying:

\[
a=b\Longrightarrow hash(a)=hash(b).
\]

Every element whose comparison contributes must be hashable. A tuple containing a list fails:

~~~python
key = ("student", [1, 2])
# hash(key) raises TypeError.
~~~

Converting the nested list to a tuple can establish structural hashability only if its elements are also hashable:

~~~python
key = ("student", (1, 2))
~~~

Hashability does not prove semantic stability if a user-defined element lies about mutation and hashing.

### 7.5.5 Tuple slicing and identity

Slicing a tuple produces a tuple value. An implementation may return the original object for a full slice because immutable value cannot expose structural copying:

~~~python
whole = values[:]
~~~

Do not rely on distinct identity as a copying contract. If a new domain identity is required, represent it explicitly; copying an immutable tuple has no ordinary structural benefit.

### 7.5.6 Concatenation cost

Tuple concatenation allocates enough positions for both operands and copies their references:

~~~python
result = left + right
~~~

For lengths (m) and (n), output work and storage are (\Theta(m+n)).

Repeated growth:

~~~python
result = ()
for item in source:
    result += (item,)
~~~

copies prefixes of lengths 0 through (n-1), giving (\Theta(n^2)) reference movement. Accumulate into a list and convert once:

~~~python
builder = []
for item in source:
    builder.append(item)
result = tuple(builder)
~~~

This has expected linear aggregate construction under amortised list append.

### 7.5.7 Lexicographic comparison

Tuple and list comparison proceeds from the first position until an unequal pair decides the result or one sequence ends:

~~~python
print((1, 9) < (2, 0))
print((1, 2) < (1, 2, 0))
~~~

Both are true. In the first, 1 is less than 2, so later elements are irrelevant. In the second, the common prefix is equal and the shorter tuple is less.

Comparison can short-circuit before reaching incompatible later elements:

~~~python
print((0, object()) < (1, object()))
~~~

The first integers decide the order, so the unrelated objects are not compared. Changing first elements to equality can make the later comparison raise.

### 7.5.8 Tuple assignment is rebinding

~~~python
point = (3, 4)
point += (5,)
~~~

The original tuple is not extended. Concatenation produces a new tuple and augmented assignment rebinds <code>point</code>. Any alias retains the original:

~~~python
alias = point
point += (6,)
print(alias)
~~~

This contrasts with list augmented assignment, which ordinarily mutates.

### 7.5.9 Return values and tuples

~~~python
def divide_with_remainder(
    dividend: int,
    divisor: int,
) -> tuple[int, int]:
    return divmod(dividend, divisor)


quotient, remainder = divide_with_remainder(17, 5)
~~~

Python functions return one object. Here that object is a tuple containing two references; unpacking assigns them to two targets. The phrase “returns two values” is conventional shorthand that can obscure this object structure.

### Worked example 7.4 — Composite coordinate key

Suppose a sparse grid maps integer coordinate pairs to labels:

~~~python
grid: dict[tuple[int, int], str] = {}
grid[(2, 5)] = "occupied"
~~~

The tuple natively preserves ordered components, is structurally immutable, and is hashable because its integers are hashable. A frozenset would be wrong because coordinates (2,5) and (5,2) differ. A string such as <code>"2,5"</code> would require parsing and escaping. A nested dictionary could work but adds another structural level.

> **Common misconception — “Tuples are read-only lists.”**  
> They share sequence operations but carry different construction, identity, hashability, record, concatenation, and ownership implications. Immutability changes what implementations and callers may assume.
