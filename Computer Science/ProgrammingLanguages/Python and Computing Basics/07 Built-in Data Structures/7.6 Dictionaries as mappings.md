# 7.6 Dictionaries as mappings

A `dict` is a mutable mapping from unique hashable keys to object references called values. A **mapping** associates keys with values; it is not positionally defined even though modern Python dictionaries preserve insertion order as part of the language contract.

```python
scores = {"Ada": 98, "Grace": 95}
scores["Edsger"] = 91
scores["Ada"] = 100

print(scores["Ada"])
print(list(scores))
```

The first assignment for `"Edsger"` adds a key-value association. The second assignment for an equal existing key replaces its associated value; it does not add a duplicate key. Iterating a dictionary produces keys in insertion order. Replacing a value does not ordinarily create a new insertion position; deleting and reinserting can.

Subscription `mapping[key]` requires the key and raises `KeyError` when absent. `mapping.get(key, default)` returns a default instead. Membership `key in mapping` tests keys, not values.

```python
record = {"name": "Ada", "active": False}

print("name" in record)       # True
print("Ada" in record)        # False
print(record.get("missing"))  # None
```

Using `.get` without a distinguished default can collapse an absent key and a present key whose value is `None`. Use membership or a unique sentinel when that distinction matters:

```python
missing = object()
value = record.get("field", missing)

if value is missing:
    print("field absent")
```

The new `object()` instance is a suitable private sentinel because no ordinary caller value is identical to it unless deliberately given access.

### 7.6.1 Hash-table mechanism

CPython implements dictionaries using a compact hash-table design. Conceptually:

1. Compute the key’s hash.
2. Derive a candidate table position.
3. If the slot is empty, lookup fails.
4. If it identifies a key with matching hash, test equality.
5. If equality succeeds, return the associated value.
6. If occupied by a non-equal key, follow the collision-resolution probing rule.

A **collision** occurs when different keys map to the same candidate location or share a hash. Correct hash tables expect collisions and resolve them; collision does not mean data corruption.

The table maintains unused capacity so probe sequences remain short under ordinary conditions. As it fills, resizing allocates a larger table and reorganises placement. Lookup, insertion, and deletion are expected (O(1)) under appropriate hash distribution and load. Worst-case lookup is (O(n)), and user-defined `__hash__` or `__eq__` can add arbitrary cost or behaviour.

The invariants of a dictionary key are strict:

- its hash must remain stable while stored;
- if two keys compare equal, their hashes must be equal;
- equality should behave coherently enough for mapping use.

Mutating state that contributes to an object’s hash after insertion makes it logically unfindable or misclassified. Built-in mutable containers prevent this by being unhashable.

### 7.6.2 Hash computation and equality

For lookup key (k), a dictionary first requests (h=hash(k)). It uses bits of (h) to begin a probe sequence. At a candidate occupied entry:

1. identity can establish a match immediately;
2. otherwise stored and requested hashes can be compared;
3. if hashes permit, equality is tested.

Unequal hashes rule out equality for correctly hashable objects. Equal hashes do not establish equality.

User-defined hash and equality can raise or mutate state. A dictionary lookup is therefore not inherently a pure constant-time memory read:

~~~python
value = mapping[key]
~~~

can execute Python methods belonging to <code>key</code> or resident keys. Keys should have fast, stable, side-effect-free comparison behaviour.

### 7.6.3 Open addressing

CPython dictionaries use **open addressing**: entries are found by probing positions within table-owned arrays rather than following a separately allocated linked bucket for each collision. A **probe sequence** is the deterministic sequence of candidate positions derived from a hash and table geometry.

The table preserves empty capacity so a probe will encounter a genuinely unused position and average sequences remain short. As occupancy grows, resizing builds larger indexing storage. Deletion must distinguish “never occupied” from “occupied then deleted”; a deleted marker, often called a **tombstone** or dummy slot, prevents lookup from stopping before a later colliding entry.

These are CPython implementation principles, not requirements for every Python implementation. The language promises mapping behaviour and insertion order, not one probing formula.

### 7.6.4 Compact order representation

Modern CPython separates sparse lookup indices from a compact insertion-ordered entry region. Iteration can walk entries in insertion order without scanning every empty hash slot. The design supports both expected hash lookup and deterministic insertion order.

Replacing the value for an equal existing key retains its insertion position. Deleting removes that entry from the live order. Reinserting an equal key later places it at the end:

~~~python
mapping = {"a": 1, "b": 2, "c": 3}
mapping["b"] = 20
print(list(mapping))

del mapping["b"]
mapping["b"] = 200
print(list(mapping))
~~~

The key orders are <code>["a", "b", "c"]</code> and then <code>["a", "c", "b"]</code>.

### 7.6.5 Load and resizing

The **load factor** is a ratio relating occupied table state to available positions. High load increases expected probe length; low load consumes more memory. CPython resizes under internal thresholds and can compact away deletion markers.

One insertion can therefore allocate and relocate table metadata in (O(n)) time while ordinary insertions remain expected amortised constant. Holding an iterator or view does not freeze table representation.

Exact capacities, thresholds, and growth factors are version-specific. Code cannot reserve dictionary capacity through a stable Python-level API merely by assuming a CPython table size.

### 7.6.6 Key immutability means hash stability

The actual requirement is not “key objects must be immutable” as a metaphysical category. It is that keys are hashable and preserve compatible hash/equality behaviour while stored.

Integers, strings, bytes, frozensets, and suitably composed tuples are common keys. A user-defined mutable object can retain identity-based equality and hash and remain logically usable while other non-key state changes. Conversely, an ostensibly frozen wrapper can be invalid if its hash depends on a mutable nested object.

Prefer keys whose equality-defining state is transitively immutable.

### 7.6.7 Mutable-hash defect

This deliberately defective class demonstrates the invariant:

~~~python
class BadKey:
    def __init__(self, value: str) -> None:
        self.value = value

    def __hash__(self) -> int:
        return hash(self.value)

    def __eq__(self, other: object) -> bool:
        return (
            isinstance(other, BadKey)
            and self.value == other.value
        )


key = BadKey("before")
mapping = {key: "stored"}
key.value = "after"
~~~

The key remains physically present, but lookup begins from a hash derived from <code>"after"</code> whereas placement used <code>"before"</code>. Membership can fail. The dictionary is not required to detect or repair this contract violation.

### 7.6.8 Construction and duplicate resolution

Dictionary displays evaluate items left to right. Later equal keys replace earlier values:

~~~python
mapping = {
    "mode": "first",
    "mode": "second",
}
~~~

The result contains one association to <code>"second"</code>. This can be intentional override layering or a silent source defect.

Double-star unpacking follows the same later-wins rule:

~~~python
combined = {
    **defaults,
    **configuration,
    **command_line,
}
~~~

The ordering expresses precedence. Every operand must be a mapping in a dictionary display. The result is a shallow new dictionary; nested values remain shared.

### 7.6.9 The dict constructor

The constructor admits several forms:

~~~python
from_mapping = dict(existing_mapping)
from_pairs = dict([("a", 1), ("b", 2)])
from_keywords = dict(a=1, b=2)
~~~

The first creates a shallow mapping copy under the source protocol. The second consumes an iterable whose each item yields exactly two elements. The third restricts keys to identifier-like keyword spellings at the call site.

Pair construction silently applies later-equal-key replacement. Validate uniqueness before construction when duplicates are errors.

### 7.6.10 fromkeys and shared defaults

~~~python
mapping = dict.fromkeys(
    ["a", "b", "c"],
    [],
)
mapping["a"].append(1)
print(mapping)
~~~

Every key is associated with the same default list object, so all displayed values show <code>[1]</code>. <code>fromkeys</code> evaluates or receives one value and repeats its reference; it does not call a factory.

Use a comprehension for independent mutable values:

~~~python
mapping = {
    key: []
    for key in ["a", "b", "c"]
}
~~~

### 7.6.11 Subscription, get, and setdefault

Subscription demands presence:

~~~python
value = mapping[key]
~~~

<code>get</code> converts absence to a default without mutating:

~~~python
value = mapping.get(key, default)
~~~

<code>setdefault</code> returns the existing value or inserts and returns the supplied default:

~~~python
bucket = mapping.setdefault(key, [])
bucket.append(item)
~~~

The default expression <code>[]</code> is evaluated before the call even when the key already exists, so a temporary list can be constructed and discarded. The inserted mutable list is then intentionally shared with <code>bucket</code>.

For systematic factory creation, <code>collections.defaultdict</code> makes the missing-value policy explicit and calls a factory only on relevant missing subscription.

### 7.6.12 Custom missing-key behaviour

A dictionary subclass can define <code>__missing__</code>, which ordinary subscription invokes for absent keys under the built-in protocol. Other operations such as <code>get</code>, membership, and <code>setdefault</code> do not universally route through it.

This difference warns against assuming all lookup spellings share one implementation path. Choose the operation whose absence contract matches the intended semantics.

### 7.6.13 Update and union

<code>update</code> mutates:

~~~python
target.update(source)
~~~

The union operator creates a new dictionary:

~~~python
combined = left | right
~~~

For equal keys, right-side values win. Augmented union:

~~~python
left |= right
~~~

updates <code>left</code> in place under the built-in contract. Nested mappings are not recursively merged; values are replaced at one association level.

A **deep merge** has no universal definition. Conflicts could replace, recurse, concatenate, reject, or preserve both. Implement the domain rule rather than assume a library’s use of the word “merge”.

### 7.6.14 Pop and popitem

<code>pop(key)</code> removes and returns a value, raising <code>KeyError</code> unless a default is supplied. A default can again collapse an admitted equal value unless it is unique.

<code>popitem()</code> removes and returns the most recently inserted live key-value pair under modern Python’s last-in–first-out contract:

~~~python
key, value = mapping.popitem()
~~~

It raises on an empty dictionary. This supports destructive reverse-insertion processing but is not sorted priority.

### 7.6.15 Copy and structural sharing

~~~python
copy = mapping.copy()
~~~

creates a new dictionary with the same key and value references. Key identities and nested mutable values remain shared. Insertion-order state is reproduced for live entries.

Deep copying a dictionary recursively follows copy protocols but can change intended identity and remains unsuitable for external resources. Define snapshot semantics explicitly.

### 7.6.16 Dictionary equality

Dictionaries compare equal when they have equal key-value associations, independent of insertion order:

~~~python
left = {"a": 1, "b": 2}
right = {"b": 2, "a": 1}
print(left == right)
~~~

The result is true while iteration orders differ. Mapping equality and serialised order are separate properties.

Values need not be hashable because dictionary lookup hashes keys, not values. Equality can still invoke value comparison with arbitrary cost or behaviour.

### 7.6.17 Mapping versus object record

A dictionary is appropriate for dynamic keys, external schemas, indexes, and genuinely mapping-oriented data. A fixed domain entity often benefits from a dataclass or class:

~~~python
student["nmae"] = "Ada"
~~~

silently creates a misspelled new key, whereas a controlled class can reject unknown attributes or static analysis can detect a misspelled field. Mapping flexibility is useful and carries weaker structural constraints.

### Worked example 7.3A — Frequency table

~~~python
def frequencies(values):
    counts = {}

    for value in values:
        counts[value] = counts.get(value, 0) + 1

    return counts
~~~

Invariant after consuming a prefix: for every key in <code>counts</code>, its value is the number of equal occurrences in that prefix, and absent keys have count zero conceptually.

Expected time is (O(n)) for (n) values under expected constant hashing/equality, with space (O(k)) for (k) distinct equivalence classes. Values must be hashable. <code>collections.Counter</code> supplies a richer standard abstraction, discussed in Chapter 11.

### Worked example 7.3 — Equality collapses numeric keys

```python
mapping = {1: "integer"}
mapping[1.0] = "float"
mapping[True] = "boolean"

print(mapping)
print(len(mapping))
```

The numeric values `1`, `1.0`, and `True` compare equal and have compatible hashes, so they designate one mapping key position. Later assignments replace the associated value. A typical display retains the original key object’s representation and shows `{1: 'boolean'}` with length 1.

This behaviour follows the equality/hash contract, not textual spelling. If a domain must distinguish integer, floating, and Boolean categories despite numeric equality, include an explicit type tag in the key, for example `(type(value), value)` under a carefully stated policy.

> **Common misconception — “Dictionary lookup is always (O(1)).”**  
> CPython hash-table operations have expected constant growth under assumptions. Collisions, resizing, malicious or poor hashes, and expensive equality can increase cost; worst case is linear.
