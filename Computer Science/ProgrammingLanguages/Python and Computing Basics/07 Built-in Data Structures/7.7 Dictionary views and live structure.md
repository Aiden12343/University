# 7.7 Dictionary views and live structure

`dict.keys()`, `dict.values()`, and `dict.items()` return **view objects**. A view reflects later dictionary changes rather than copying a static list.

```python
scores = {"Ada": 98}
items = scores.items()
scores["Grace"] = 95
print(list(items))
```

The list materialised at the final line includes both associations. A view is iterable and sized but not an independent snapshot.

Keys and item views also support selected set-like operations when their elements satisfy required hashability. Values views do not behave as mathematical sets because duplicate values are admitted and association identity matters.

Changing dictionary size during iteration raises `RuntimeError` in ordinary CPython/Python behaviour. Updating a value for an existing key may not change size, but relying on live mutation during traversal can still obscure invariants. Iterate over `list(mapping.items())` when an explicit shallow snapshot is required, understanding its (O(n)) time and space cost.

### 7.7.1 Views are dependent objects

A dictionary view is neither the dictionary itself nor a container detached from it. It is a small dependent object whose iteration and length operations consult a particular mapping. The dependency is observable:

~~~python
inventory = {"bolt": 40, "washer": 75}
names = inventory.keys()

print(len(names))              # 2
inventory["nut"] = 25
print(len(names))              # 3
print("nut" in names)          # True
~~~

The assignment to <code>names</code> binds one view object. It does not schedule repeated calls to <code>inventory.keys()</code>, yet the view remains associated with <code>inventory</code>. This is a general interface pattern: an object can expose live derived access to another object without copying its present contents.

The view keeps the dictionary reachable. Deleting the original name does not invalidate the view:

~~~python
mapping = {"x": 1}
view = mapping.items()
del mapping
print(list(view))              # [('x', 1)]
~~~

Only the name <code>mapping</code> was unbound. The view still refers, directly or through implementation state, to the same dictionary object. Consequently, retaining a view can extend the lifetime of a large mapping. A view is cheap to create, but its reachability implications are not necessarily cheap.

### 7.7.2 Keys, values, and items expose different projections

For a mapping \(M\), the three standard views project different components:

\[
K(M)=\{k : k \text{ is a key of }M\},
\]

\[
V(M)=\langle M[k] : k \text{ occurs in mapping order}\rangle,
\]

and

\[
I(M)=\langle (k,M[k]) : k \text{ occurs in mapping order}\rangle.
\]

The angle brackets indicate an iterable encounter order, not uniqueness. Keys are unique by the mapping invariant. Values need not be unique. Items have unique keys, but two distinct keys may map to equal values. These distinctions explain why key views are set-like, value views are not, and item views are set-like only when their item pairs can participate in the requested set operation.

~~~python
grades = {"Ada": "A", "Grace": "A", "Edsger": "B"}

print(len(grades.keys()))      # 3
print(len(grades.values()))    # 3, despite duplicate "A"
print(len(set(grades.values())))  # 2 distinct values
~~~

Converting a values view to a set is an explicit change of abstraction: multiplicity and association with keys are discarded. That conversion is correct only when the consumer asks for distinct values.

### 7.7.3 Membership has projection-specific meaning

Membership in a dictionary or its key view tests keys. Membership in a values view tests values by scanning them. Membership in an items view tests a complete key-value pair.

~~~python
prices = {"pen": 3, "book": 12}

print("pen" in prices)                  # True: key membership
print("pen" in prices.keys())           # True: same logical question
print(12 in prices.values())             # True: value scan
print(("book", 12) in prices.items())   # True: association membership
print(("book", 3) in prices.items())    # False
~~~

For ordinary built-in dictionaries, key membership has expected constant growth under the hash-table assumptions already stated. Value membership may inspect every value and therefore has linear worst-case growth in the number of associations, in addition to the cost of equality comparisons. Item membership can first locate the key and then compare the associated value, so its expected lookup growth resembles key membership when the candidate is a suitable two-element item. The abstract question determines the cost; the shared spelling <code>in</code> does not.

Writing <code>key in mapping.keys()</code> is usually redundant. The direct expression <code>key in mapping</code> states the mapping protocol more plainly, avoids creating even a lightweight transient view, and works for mappings whose key-view implementation is specialised.

### 7.7.4 Set-like operations on key views

Key views implement set-like comparisons and binary operations. This permits relational questions without first materialising both key collections:

~~~python
expected = {"name", "email", "age"}
record = {"name": "Ada", "email": "ada@example.test", "country": "GB"}

present = record.keys()
missing = expected - present
unexpected = present - expected
complete = expected <= present

print(missing)                 # {'age'}
print(unexpected)              # {'country'}
print(complete)                # False
~~~

The results of difference, union, intersection, and symmetric difference are ordinary sets rather than live views. The relational comparisons answer a Boolean question. The operation therefore separates a live source projection from a newly materialised result.

The other operand need not always be a set object; view operations accept suitable set-like or iterable operands according to the method or operator contract. A design should nevertheless make domain meaning explicit. If <code>expected</code> represents a schema, representing it as a set communicates that uniqueness and order are irrelevant.

### 7.7.5 Set-like operations on item views

An item view behaves set-like when its items are hashable enough for the requested operation. Because each item is conceptually a two-tuple, an unhashable value can make a materialised set operation fail even though dictionary keys themselves remain valid.

~~~python
left = {"x": 1, "y": 2}
right = {"y": 2, "z": 3}

print(left.items() & right.items())      # {('y', 2)}
print(left.items() - right.items())      # {('x', 1)}
~~~

Now replace the scalar values with lists:

~~~python
left = {"x": [1], "y": [2]}
right = {"y": [2]}

print(("y", [2]) in left.items())       # True
# left.items() & right.items()           # TypeError: list is unhashable
~~~

Direct association membership can compare the located value without hashing the complete pair. Constructing an intersection set must insert item pairs into a hash structure, so each pair—and therefore each component—must be hashable. “Items views are set-like” is thus a protocol summary, not a claim that every operation succeeds for every possible value type.

### 7.7.6 Values-view equality is intentionally not sequence equality

Values views do not define content equality as lists do. Two calls on the same dictionary create distinct view objects, and comparing them does not ask whether their iterated values form equal sequences:

~~~python
d = {"a": 1}
print(d.values() == d.values())          # False in ordinary Python behaviour

v = d.values()
print(v == v)                            # True by object identity fallback
~~~

There is no single obvious value-view equality relation. Should duplicate values count? Should order count? Should the comparison be a multiset comparison? Should associations be preserved? Python avoids choosing one implicitly. A program requiring a particular relation should materialise or count according to that relation—for example, <code>list(d.values())</code> for ordered sequence equality or <code>Counter(d.values())</code> for multiplicity-sensitive equality when values are hashable.

### 7.7.7 Reversal and insertion order

Modern Python dictionaries preserve insertion order as part of the language contract. Reassigning the value for an existing key does not move that key. Deleting a key and inserting it again creates a new insertion at the end. Dictionary views follow the same order and support reverse iteration.

~~~python
states = {"queued": 3, "running": 1, "done": 8}
states["queued"] = 4          # position unchanged
del states["running"]
states["running"] = 2         # reinserted at the end

print(list(states))            # ['queued', 'done', 'running']
print(list(reversed(states)))  # ['running', 'done', 'queued']
print(list(reversed(states.items())))
~~~

Insertion order is not sorted order. It records a history of successful key insertions, modified by deletion and reinsertion. If a domain requires chronological order, insertion must actually occur chronologically or the records must be sorted by an explicit timestamp. If it requires key order, use a sorting operation. A storage order should never silently impersonate a domain order.

### 7.7.8 Iteration aliases and unpacking

Iteration over a dictionary yields keys. The following forms therefore have distinct meanings:

~~~python
dimensions = {"width": 8, "height": 5}

for key in dimensions:
    print(key)

for value in dimensions.values():
    print(value)

for key, value in dimensions.items():
    print(key, value)
~~~

In the final loop, each yielded item is a two-element tuple-like object that is unpacked into two targets. Writing <code>for key, value in dimensions</code> instead would attempt to unpack each key. A two-character string key might make this defect appear to work while assigning characters rather than key-value components. The bug is especially treacherous because it is input-dependent.

~~~python
badly_named = {"xy": 10, "z": 20}

for key, value in badly_named:
    print(key, value)          # prints x y, then fails on z
~~~

The loop target follows the iterable’s produced elements, not the programmer’s variable names.

### 7.7.9 Structural mutation during traversal

A dictionary iterator assumes that the key structure does not change incompatibly while it advances. Adding or removing keys during traversal ordinarily raises <code>RuntimeError</code> when detected:

~~~python
stock = {"pen": 0, "paper": 5}

for name, quantity in stock.items():
    if quantity == 0:
        del stock[name]        # RuntimeError: dictionary changed size
~~~

The detection is a defensive implementation contract, not a transaction. Mutation may already have occurred before the exception. The dictionary remains a valid mapping, but the intended multi-step operation is only partially complete.

Three repairs correspond to three specifications:

~~~python
# 1. Traverse a shallow snapshot of associations.
for name, quantity in list(stock.items()):
    if quantity == 0:
        del stock[name]

# 2. Determine removals, then apply them.
obsolete = [name for name, quantity in stock.items() if quantity == 0]
for name in obsolete:
    del stock[name]

# 3. Construct a replacement mapping.
stock = {name: quantity for name, quantity in stock.items() if quantity != 0}
~~~

The first preserves object identity and mutates the original after paying for a snapshot. The second separates decision from mutation and can expose the planned change for validation or audit. The third gives replacement semantics: aliases to the old dictionary do not observe the filtered result. These are not interchangeable implementation tricks.

Changing only an existing value does not alter dictionary size and is ordinarily permitted during iteration:

~~~python
for name in stock:
    stock[name] *= 2
~~~

Yet callbacks invoked by multiplication or assignment may have broader effects for user-defined values or mappings. The narrow observation “this built-in example works” must not become an unrestricted mutation rule.

### 7.7.10 Snapshots are shallow and time-specific

Materialising <code>list(mapping.items())</code> freezes which item references are present and their order at one moment. It does not recursively copy values:

~~~python
config = {"paths": ["/input"]}
snapshot = list(config.items())

config["paths"].append("/archive")
print(snapshot)                # [('paths', ['/input', '/archive'])]
~~~

The outer list and item tuple are new, but both snapshot and mapping reach the same nested list. A snapshot contract must name its depth. Alternatives include immutable values, explicit deep copying under a defined object model, serialisation into a detached representation, or application-specific copying. Unqualified “take a copy” is not a sufficient consistency specification.

### 7.7.11 The mapping-proxy distinction

A read-only view of a mapping interface is different from a keys or items view. <code>types.MappingProxyType</code> exposes a dynamic, read-only mapping proxy: reads reflect changes to the wrapped mapping, while mutations through the proxy are rejected.

~~~python
from types import MappingProxyType

mutable_settings = {"timeout": 30}
settings = MappingProxyType(mutable_settings)

print(settings["timeout"])
mutable_settings["timeout"] = 45
print(settings["timeout"])             # 45
# settings["timeout"] = 60             # TypeError
~~~

The proxy controls one route of mutation; it does not freeze the underlying dictionary or its nested values. It is useful for publishing a non-mutating interface while an owner retains mutation authority. Security must not be inferred merely from read-only syntax: code holding another alias to the original object can still change it.

### Worked example 7.3B — Schema drift report

Suppose an ingestion boundary admits exactly four required fields and two optional fields. The report must distinguish missing required fields, accepted optional fields, and all unknown fields without modifying the record.

~~~python
from collections.abc import Mapping


def schema_report(record: Mapping[str, object]) -> dict[str, set[str]]:
    required = {"id", "timestamp", "kind", "payload"}
    optional = {"source", "trace_id"}
    present = record.keys()

    missing = required - present
    accepted_optional = optional & present
    unknown = present - required - optional

    return {
        "missing": missing,
        "accepted_optional": accepted_optional,
        "unknown": unknown,
    }


event = {
    "id": "e-19",
    "timestamp": "2030-05-04T12:00:00Z",
    "kind": "opened",
    "payload": {},
    "trace_id": "t-7",
    "legacy_code": 41,
}

print(schema_report(event))
~~~

Line by line:

1. The parameter uses the read-only <code>Mapping</code> interface because validation needs no mutation authority.
2. Required and optional names are sets because each name is unique and order is irrelevant to classification.
3. <code>present</code> is a live key view, but the function performs no concurrent mutation; its lifetime is bounded to the call.
4. Set differences and intersection state the classification algebra directly.
5. Every returned value is an independent ordinary set. The report no longer changes if the input mapping later changes.

Assuming ordinary hashing, each classification is expected linear in the total number of relevant field names. The fixed schema sets make their contribution constant with respect to record size, while identifying unknown fields must inspect the present names. The lower bound is therefore \(\Omega(n)\) for a record with \(n\) keys because every key may be unknown and must be considered.

> **Common misconception — “A dictionary view is an immutable snapshot.”**  
> A view disallows direct structural mutation through its own interface, but it reflects the associated mapping. Immutability of an interface and temporal stability of observed data are different properties.
