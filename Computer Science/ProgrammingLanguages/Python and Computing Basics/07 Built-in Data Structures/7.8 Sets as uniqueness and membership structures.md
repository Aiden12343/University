# 7.8 Sets as uniqueness and membership structures

A `set` is a mutable unordered collection of unique hashable elements. A `frozenset` provides the corresponding immutable form. “Unordered” means no language-level positional or insertion-order contract should be used; an iteration order observed in one run is not a semantic ordering.

```python
permissions = {"read", "write"}
permissions.add("read")
permissions.add("execute")
print(len(permissions))
```

Adding an equal existing element does not increase cardinality, so length is 3. **Cardinality** is the number of distinct members.

Set algebra maps directly to methods and operators:

| Operation | Syntax | Meaning |
|:---|:---:|:---|
| union | `a | b` | members in either set |
| intersection | `a & b` | members in both |
| difference | `a - b` | members in `a` but not `b` |
| symmetric difference | `a ^ b` | members in exactly one |
| subset | `a <= b` | every member of `a` belongs to `b` |
| proper subset | `a < b` | subset and unequal |

### Worked example 7.4 — Permission analysis

```python
required = {"read", "write"}
granted = {"read", "execute"}

missing = required - granted
unexpected = granted - required
complete = required <= granted

print(missing)
print(unexpected)
print(complete)
```

`missing` contains `"write"`; `unexpected` contains `"execute"`; `complete` is false. The representation makes the invariant—unique capabilities, order irrelevant—native. A list would admit duplicate permissions and make difference/membership scans linear.

CPython sets are hash tables specialised for membership without separate associated values. Membership, insertion, and removal are expected (O(1)) under ordinary hashing assumptions and (O(n)) worst case. Set operations scale with operand sizes and implementation choices; one must consult the exact operation rather than label all set work constant.

`remove(value)` raises `KeyError` if absent; `discard(value)` does nothing when absent. The methods express different contracts. `pop()` removes an arbitrary element under the unordered interface; it must not be used to mean “first” or “last”.

A `frozenset` can be hashable when its elements are hashable, permitting sets of sets:

```python
edge = frozenset({"A", "B"})
graph_edges = {edge}
```

This can represent an undirected edge because `{A, B}` and `{B, A}` should be identical under the domain model. If direction matters, a two-element tuple is the suitable ordered representation.

### 7.8.1 The mathematical abstraction and the Python object

A mathematical set is determined solely by which elements belong to it. It has neither order nor multiplicity. Python’s <code>set</code> approximates this abstraction for finite collections of hashable Python objects, while also supplying mutation operations and observable iteration. Its central invariant is:

\[
\forall x,\quad \#\{e \in S : e = x\} \leq 1.
\]

Here \(\#\) means cardinality. Equality, not identity, determines whether a candidate duplicates an existing member. The invariant therefore depends on the equality and hashing contracts of elements.

~~~python
values = {1, 1.0, True}
print(values)                  # typically {1}
print(len(values))             # 1
~~~

These three numeric objects compare equal and have hashes compatible with that equality, so the set has one equivalence-class representative. The displayed representative is an implementation-observable retained object, not evidence that the domain distinctions survived. If numeric category matters, store an explicit tag such as <code>(type(value), value)</code> under a policy that deliberately treats exact types as meaningful.

Python set equality follows membership equality. Two sets compare equal when each is a subset of the other, regardless of construction or iteration order:

~~~python
left = {"red", "green", "blue"}
right = {"blue", "red", "green"}
print(left == right)           # True
~~~

### 7.8.2 Construction is a lossy fold

Constructing a set consumes an iterable and inserts each produced element. Conceptually:

\[
S_0=\varnothing,\qquad S_{i+1}=S_i\cup\{x_i\}.
\]

The transformation discards order and multiplicity. It can also fail after consuming only a prefix if an element is unhashable or if hashing or equality raises an exception.

~~~python
source = ["a", "b", "a", "c", "b"]
unique = set(source)

print(len(source))             # 5 occurrences
print(len(unique))             # 3 distinct values
~~~

The conversion is correct for the question “which distinct values occurred?” It is incorrect for “how many times did each occur?” or “in which order did first occurrences appear?” A <code>Counter</code> preserves multiplicities; an insertion-ordered dictionary can preserve the order of first occurrences:

~~~python
ordered_unique = list(dict.fromkeys(source))
print(ordered_unique)          # ['a', 'b', 'c']
~~~

This idiom relies on dictionary insertion order and on the same hash/equality equivalence rules as a set. It preserves first representatives, not every type distinction or later occurrence.

An empty set must be written <code>set()</code>. Empty braces create a dictionary because the brace grammar historically and presently assigns <code>{}</code> to mappings:

~~~python
empty_set = set()
empty_mapping = {}

print(type(empty_set))         # <class 'set'>
print(type(empty_mapping))     # <class 'dict'>
~~~

### 7.8.3 Literals, comprehensions, and evaluation

A set display evaluates its element expressions from left to right, then inserts the resulting objects under set equivalence. The final iteration order is not the evaluation order contract.

~~~python
def observe(label: str, result: int) -> int:
    print(label)
    return result


numbers = {observe("first", 2), observe("second", 1), observe("third", 2)}
print(numbers)
~~~

All three calls occur in source order even though one value is duplicate and the displayed set may use another order. Effects belong to expression evaluation; uniqueness belongs to destination insertion.

A set comprehension performs lazy-looking syntax but constructs its entire set eagerly:

~~~python
remainders = {number % 4 for number in range(20)}
print(remainders)              # {0, 1, 2, 3}, in unspecified display order
~~~

The output size can be far smaller than the input count. Time still includes all 20 transformations and insertions. In general, processing \(n\) inputs into \(u\) unique outputs uses expected \(O(n)\) insertion work and \(O(u)\) retained set space, excluding element-operation costs.

### 7.8.4 Operators and methods have different operand contracts

Binary set operators require set-like operands in the built-in interface, whereas named methods accept general iterables in several cases:

~~~python
letters = {"a", "b", "c"}

print(letters.intersection("cabd"))      # {'a', 'b', 'c'}
# print(letters & "cabd")                # TypeError
~~~

The method treats the string as an iterable of one-character strings. The operator insists that both operands advertise set semantics, reducing accidental operations between conceptually unrelated collections. Method forms can also accept more than two operands:

~~~python
common = {1, 2, 3, 4}.intersection([2, 3, 5], (0, 2, 3))
print(common)                 # {2, 3}
~~~

Operator precedence matters. Set intersection <code>&</code> binds more tightly than union <code>|</code>, difference <code>-</code>, and symmetric difference <code>^</code> according to Python’s expression grammar. Parentheses should express domain grouping even when precedence is known:

~~~python
eligible = (licensed & trained) - suspended
~~~

This reads as a requirement: a subject must be both licensed and trained, then must not be suspended.

### 7.8.5 Non-mutating and mutating forms

The expression <code>a | b</code> constructs a new set; <code>a.update(b)</code> mutates <code>a</code>. Similar pairs exist for intersection, difference, and symmetric difference:

| Pure-looking result form | In-place method | Compound operator |
|:---|:---|:---|
| <code>a \| b</code> | <code>a.update(b)</code> | <code>a \|= b</code> |
| <code>a & b</code> | <code>a.intersection_update(b)</code> | <code>a &= b</code> |
| <code>a - b</code> | <code>a.difference_update(b)</code> | <code>a -= b</code> |
| <code>a ^ b</code> | <code>a.symmetric_difference_update(b)</code> | <code>a ^= b</code> |

The result form leaves both operand objects unchanged. The mutating method returns <code>None</code>, following the built-in convention that in-place structural updates should not masquerade as computed values.

~~~python
active = {"u1", "u2"}
newly_active = {"u3"}

combined = active | newly_active
print(active)                  # {'u1', 'u2'} in unspecified order

result = active.update(newly_active)
print(result)                  # None
print(active)                  # now also contains 'u3'
~~~

The compound operators mutate a mutable set when its type supports the operation. For immutable <code>frozenset</code>, augmented assignment computes a new object and rebinds the target. Aliases therefore observe different outcomes:

~~~python
mutable = {1, 2}
mutable_alias = mutable
mutable |= {3}
print(mutable_alias)           # {1, 2, 3}

frozen = frozenset({1, 2})
frozen_alias = frozen
frozen |= {3}
print(frozen_alias)            # frozenset({1, 2})
print(frozen)                  # frozenset({1, 2, 3})
~~~

Syntax alone does not decide mutation; the left operand’s data model participates.

### 7.8.6 Add, remove, discard, pop, and clear

The individual mutators differ principally in their absent-member contracts:

| Operation | Present member | Absent member |
|:---|:---|:---|
| <code>add(x)</code> | no cardinality change | inserts |
| <code>remove(x)</code> | removes | raises <code>KeyError</code> |
| <code>discard(x)</code> | removes | no effect |
| <code>pop()</code> | removes and returns an arbitrary member | raises <code>KeyError</code> if empty |
| <code>clear()</code> | removes all members | remains empty |

Use <code>remove</code> when absence violates a precondition and should be detected. Use <code>discard</code> when the required postcondition is simply absence:

~~~python
subscriptions = {"alerts", "reports"}

subscriptions.remove("alerts")    # asserts membership through its contract
subscriptions.discard("alerts")   # idempotently ensures absence
~~~

An operation is **idempotent** when applying it more than once has the same relevant result as applying it once. Under an ordinary single-threaded state model, <code>discard(x)</code> is idempotent with respect to set contents.

<code>pop()</code> is intentionally arbitrary. “Arbitrary” does not mean random or uniformly distributed; it means the caller receives no semantic choice contract. Tests should assert that the returned item was a member and that cardinality decreased, not that a particular member was chosen.

### 7.8.7 Subset relations form a partial order

Set inclusion is reflexive, antisymmetric, and transitive:

1. \(A\subseteq A\) for every set \(A\);
2. if \(A\subseteq B\) and \(B\subseteq A\), then \(A=B\);
3. if \(A\subseteq B\) and \(B\subseteq C\), then \(A\subseteq C\).

These properties make inclusion a **partial order**. It is not a total order because two sets can be incomparable:

~~~python
left = {1, 2}
right = {2, 3}

print(left <= right)           # False
print(right <= left)           # False
~~~

Neither result implies equality; each set has a member absent from the other. Consequently, sorting arbitrary sets by <code><</code> does not provide a coherent total ordering. The operator means proper subset, not “comes before.”

<code>isdisjoint</code> states that intersection is empty:

\[
A \mathbin{\text{isdisjoint}} B \iff A\cap B=\varnothing.
\]

It can answer the Boolean question without materialising the intersection and may stop at the first shared member:

~~~python
duties_a = {"approve_invoice", "issue_payment"}
duties_b = {"audit_payment", "reconcile"}
print(duties_a.isdisjoint(duties_b))     # True
~~~

This is a computational expression of a separation-of-duties invariant.

### 7.8.8 Algebraic laws and mutation boundaries

For mathematical sets, union and intersection are commutative and associative; each is idempotent. Difference is neither commutative nor associative.

\[
A\cup B=B\cup A,
\qquad
(A\cup B)\cup C=A\cup(B\cup C),
\]

\[
A\cup A=A,
\qquad
A-B\ne B-A \text{ in general}.
\]

These laws support refactoring only when effects and object identity are outside the specification. Python expressions must also evaluate operands, allocate results, hash elements, and perhaps invoke user-defined methods. Reordering <code>produce_a() | produce_b()</code> changes effect order even though the final mathematical membership might be equal. Algebra licenses transformations over already established values, not arbitrary effectful programs.

Symmetric difference consists of elements in exactly one operand:

\[
A\triangle B=(A-B)\cup(B-A)=(A\cup B)-(A\cap B).
\]

It is valuable for detecting change between snapshots:

~~~python
before = {"alpha", "beta", "gamma"}
after = {"beta", "gamma", "delta"}

changed_membership = before ^ after
print(changed_membership)      # {'alpha', 'delta'}
~~~

The result says which values changed membership, but not which were added and which were removed. Preserve direction with the two differences when that distinction matters.

### 7.8.9 Cost equations for binary set operations

Let \(n=|A|\) and \(m=|B|\). Precise implementation costs depend on which operand is traversed, whether a result is allocated, table occupancy, hashes, equality, and result cardinality. Useful expected-growth statements for ordinary built-in sets include:

- membership in one set: expected \(O(1)\), worst-case \(O(n)\);
- copying a set: \(\Theta(n)\) references and insert/copy work;
- intersection: expected growth proportional to the smaller operand for implementations that scan it and probe the other, plus result allocation;
- union: at least \(\Omega(n+m)\) input or copy contribution when producing an independent result, with expected \(O(n+m)\) ordinary behaviour;
- difference: ordinarily proportional to the left operand plus relevant probes, because the result must decide each left member;
- subset: can terminate at a missing member, but successful proof requires examining all members of the candidate subset.

These statements exclude element-level costs. If equality between two keys costs \(E\), collision resolution can multiply that cost. If computing an object’s hash costs \(H\), an insertion not benefiting from a cached hash incurs it. Built-in immutable strings commonly cache hashes as an implementation detail, but portable complexity arguments should identify rather than assume such caching.

An operation returning \(r\) members also has an output-space lower bound of \(\Omega(r)\) references for an independent set result. The concise expression <code>a | b | c | d</code> may construct intermediate sets whose peak allocation exceeds the final result. A mutating accumulation can reduce intermediates when mutation ownership is explicit:

~~~python
combined: set[str] = set()
for group in groups:
    combined.update(group)
~~~

This is not automatically faster for every input; it states one owned accumulator and avoids semantically required preservation of intermediate results.

### 7.8.10 Frozenset and hashability

<code>frozenset</code> has set membership semantics without element-changing methods. Its hash can therefore remain stable, provided its elements are themselves hashable. This permits a frozen set to occur as a dictionary key or set member.

~~~python
undirected_edge = frozenset({"A", "B"})
weights = {undirected_edge: 7}

print(weights[frozenset({"B", "A"})])   # 7
~~~

The representation correctly erases endpoint order. It does not enforce exactly two distinct endpoints. A self-loop written <code>frozenset({"A", "A"})</code> has cardinality one, and a three-way hyperedge has cardinality three. Domain validation remains necessary:

~~~python
def make_simple_edge(left: str, right: str) -> frozenset[str]:
    edge = frozenset({left, right})
    if len(edge) != 2:
        raise ValueError("a simple edge requires two distinct endpoints")
    return edge
~~~

The return type communicates unordered immutable membership. The explicit length check enforces the graph-specific arity invariant.

Frozenset operations usually return a result whose type follows the left operand for mixed built-in set operations:

~~~python
frozen = frozenset({1, 2})
mutable = {2, 3}

print(type(frozen | mutable))  # <class 'frozenset'>
print(type(mutable | frozen))  # <class 'set'>
~~~

Do not infer a commutative result type merely because mathematical union is commutative. Membership can be equal while representation type differs.

### 7.8.11 Hashable does not mean deeply frozen

An object may be hashable while holding internal mutable state, provided its hash and equality identity do not change while it is stored. User-defined classes are explored in Chapter 9; the structural lesson is present now. Conversely, a tuple or frozenset is not hashable if a component is unhashable.

~~~python
valid_key = ("region", frozenset({"north", "east"}))
# invalid_key = ("region", {"north", "east"})
# hash(invalid_key)            # TypeError: set is unhashable
~~~

The outer tuple’s immutability cannot stabilise the contents of a mutable set component. Hashability is a recursive contract over components participating in equality and hash computation, not a label inherited from the outermost type.

Values stored alongside set members may remain mutable through other references. A frozenset of custom objects is not necessarily a frozen object graph. A trustworthy immutable domain value requires control over every state component that determines its observable equality and behaviour.

### 7.8.12 NaN and non-reflexive equality

Most familiar values satisfy reflexivity: \(x=x\). IEEE floating-point NaN (“not a number”) is exceptional because it ordinarily compares unequal to itself. Set behaviour must combine hash-table identity optimisations with equality, so seemingly paradoxical results can appear:

~~~python
nan = float("nan")
values = {nan}

print(nan == nan)              # False
print(nan in values)           # True for the identical stored object
print(float("nan") in values) # ordinarily False
~~~

The set can recognise the identical object reference even though general equality is false, while a distinct NaN normally does not match it. Distinct NaN objects may coexist in one set. Algorithms that assume set membership is merely repeated <code>==</code> reasoning overlook identity shortcuts and the requirement that element equivalence behave sensibly.

For domains containing NaNs, define a policy: reject them, canonicalise them to a sentinel, or specify that distinct NaNs remain distinct. Data-science libraries may adopt their own missing-value semantics; those contracts must be studied separately in Branch A.

### 7.8.13 Sets are not multisets

A **multiset** associates each distinct element with a non-negative multiplicity. Python’s <code>collections.Counter</code> provides a mapping-based multiset-like tool, whereas <code>set</code> retains only presence.

~~~python
from collections import Counter

left = Counter("mississippi")
right = Counter("impossible")

print(left["s"])               # 4
print(set(left))                # distinct elements only
print(left & right)             # minimum positive counts
~~~

The Counter intersection shown is not set intersection: each result count is the minimum positive count in the operands. Choosing between set and multiset is a choice between Boolean membership and quantitative occurrence.

### 7.8.14 Sets are not sequences or queues

A set provides no positional indexing:

~~~python
members = {"a", "b", "c"}
# members[0]                   # TypeError
~~~

Converting to a list merely to select index zero chooses whichever iteration order the set happens to expose; it does not recover an original or canonical first element. Sorting can impose an order if all members share an appropriate comparison or key:

~~~python
canonical = sorted(members)
first = canonical[0]
~~~

This costs at least materialisation and sorting work, and “alphabetically first” must be the intended domain rule. For FIFO or LIFO removal, use a queue or stack representation. For random sampling, use an API explicitly designed for sampling and state its probability model.

### Worked example 7.4A — Stable streaming deduplication

Requirement: accept an iterable of record identifiers, yield the first occurrence of each identifier in encounter order, and reject unhashable identifiers through the natural set contract. The input may be too large to materialise.

~~~python
from collections.abc import Hashable, Iterable, Iterator


def first_occurrences(values: Iterable[Hashable]) -> Iterator[Hashable]:
    seen: set[Hashable] = set()
    for value in values:
        if value in seen:
            continue
        seen.add(value)
        yield value


print(list(first_occurrences(["b", "a", "b", "c", "a"])))
# ['b', 'a', 'c']
~~~

The <code>seen</code> set records the invariant

\[
\text{seen}=\{x_i:0\le i<j\},
\]

immediately before input position \(j\). If the current value belongs to <code>seen</code>, an equal representative has already been yielded. Otherwise the function adds and yields it, preserving the invariant for the next position. Each distinct equivalence class is yielded exactly once, at its first encountered representative.

For \(n\) consumed inputs and \(u\) distinct values, expected time is \(O(n)\) hash-table work plus element hashing/equality and source costs; retained auxiliary space is \(O(u)\). Laziness avoids storing the output sequence, but it cannot avoid storing all distinct values if exact duplicate rejection must cover the entire unbounded history. This is an information requirement, not merely an implementation limitation.

### Worked example 7.4B — Role constraints as set algebra

An account may be activated only if it possesses all baseline permissions, possesses at least one authentication factor, and possesses none of the prohibited administrative combinations.

~~~python
BASELINE = frozenset({"read_profile", "change_own_password"})
FACTORS = frozenset({"totp", "hardware_key", "recovery_code"})
PROHIBITED = (
    frozenset({"approve_payment", "issue_payment"}),
    frozenset({"create_user", "grant_admin"}),
)


def activation_defects(granted: set[str]) -> list[str]:
    defects: list[str] = []

    missing = BASELINE - granted
    if missing:
        defects.append(f"missing baseline permissions: {sorted(missing)}")

    if granted.isdisjoint(FACTORS):
        defects.append("no authentication factor granted")

    for forbidden_combination in PROHIBITED:
        if forbidden_combination <= granted:
            defects.append(
                f"forbidden combination: {sorted(forbidden_combination)}"
            )

    return defects
~~~

The constants are frozensets because the policy definitions are immutable membership values and may safely be shared. Difference identifies precisely which baseline permissions are absent. Disjointness expresses an existential condition negatively: there is no shared factor. Subset testing detects possession of every member in a forbidden combination. The function accumulates independent defects rather than stopping at the first, which suits a validation report.

Security does not follow from the set expressions alone. The caller must authenticate the account, obtain an authoritative permission snapshot, define consistency under concurrent policy changes, and ensure that diagnostic text does not disclose sensitive privileges. The data structure makes policy relations explicit; it does not supply the surrounding trust model.

### Worked example 7.4C — Exact active-tag accounting under eviction

Maintaining the union of tags for a sliding window is harder than merely adding tags. When one record is evicted, a tag must remain active if another retained record still has it. A set alone has forgotten multiplicity; a counter retains the information needed for removal.

~~~python
from collections import Counter


tag_counts: Counter[str] = Counter()


def add_tags(tags: frozenset[str]) -> None:
    tag_counts.update(tags)


def remove_tags(tags: frozenset[str]) -> None:
    for tag in tags:
        tag_counts[tag] -= 1
        if tag_counts[tag] == 0:
            del tag_counts[tag]


def active_tags() -> set[str]:
    return set(tag_counts)
~~~

The representation invariant is

\[
\text{tag\_counts}[t]
=\#\{r\text{ retained}:t\in r.\text{tags}\}>0.
\]

The active-tag set is exactly the counter’s key set. Deleting zero counts is not cosmetic: it makes key presence coincide with positive membership and bounds the mapping to presently active tags. This example demonstrates a recurrent principle: if future deletion must know how many contributors support a derived set member, preserve counts rather than only the union.

> **Common misconception — “Removing an item from a set reveals which occurrence was removed.”**  
> A set never retained occurrence multiplicity. It stores one representative of an equality class. Questions about individual occurrences require a sequence, multiset, or separate provenance structure.
