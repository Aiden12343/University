# 7.9 Strings as immutable sequences with textual semantics

Chapter 5 established that `str` is an immutable sequence of Unicode code points. Sequence operations therefore apply, but algorithms must remain conscious of text semantics.

Indexing and slicing are (O(1)) and (O(k))-like operations respectively in ordinary CPython’s flexible internal Unicode representation, with important implementation qualifications. Indexing returns a one-code-point string. Slicing generally constructs a new string. Searching for a substring depends on both lengths and the employed algorithm; simplistic “string membership is (O(n))” statements suppress the pattern length and implementation.

Repeated string concatenation deserves care. Strings cannot grow in place under the language model, so a conceptual sequence of `result = result + piece` can repeatedly copy an expanding prefix, producing quadratic total work. CPython can optimise selected cases, but portable design should not depend on fragile refcount-based behaviour. Collect pieces and join once:

```python
pieces: list[str] = []
for number in range(1_000):
    pieces.append(str(number))

result = ",".join(pieces)
```

`join` first determines the required result under its implementation strategy and constructs the final string without a chain of semantically required intermediate prefixes.

### Worked example 7.5 — Split has a contract, not one universal meaning

```python
text = "  alpha   beta  "
print(text.split())
print(text.split(" "))
```

Output:

```text
['alpha', 'beta']
['', '', 'alpha', '', '', 'beta', '', '']
```

With no separator, `split` treats runs of whitespace specially and omits boundary empties. With explicit separator `" "`, each exact separator occurrence divides fields and empty fields are retained. Method choice encodes a data-format rule. It is not cosmetic.

Text normalisation, grapheme segmentation, locale-specific collation, and case-insensitive identity exceed the ordinary sequence contract. A string can be the right container while a naive code-point algorithm is the wrong text algorithm.

### 7.9.1 Four different units called a character

The everyday word “character” is too ambiguous for exact programming. At least four units must be distinguished:

1. an **abstract character**, such as LATIN SMALL LETTER A, is an element of a writing-system repertoire;
2. a **Unicode code point** is an integer position in the Unicode codespace, conventionally written <code>U+XXXX</code>;
3. a **code unit** is a storage unit of an encoding form, such as an 8-bit unit in UTF-8 or a 16-bit unit in UTF-16;
4. an **extended grapheme cluster** is an approximation to one user-perceived textual unit under Unicode segmentation rules.

Python’s <code>str</code> interface is a sequence of Unicode code points. Its length and indexing operate at that level, not at the level of bytes or grapheme clusters.

~~~python
plain = "A"
accented_precomposed = "é"
accented_decomposed = "e\u0301"
family = "👨‍👩‍👧‍👦"

print(len(plain))                   # 1 code point
print(len(accented_precomposed))    # 1 code point
print(len(accented_decomposed))     # 2 code points
print(len(family))                  # several code points, often one displayed cluster
~~~

The decomposed accent consists of LATIN SMALL LETTER E followed by COMBINING ACUTE ACCENT. The family emoji contains several emoji code points joined by ZERO WIDTH JOINER characters. A screen may render each string as one visible unit, but <code>len</code> does not count display cells or grapheme clusters.

This distinction affects cursor movement, deletion, truncation, validation, database field limits, and user-interface layout. A loop over a string visits code points:

~~~python
for code_point_string in accented_decomposed:
    print(repr(code_point_string), hex(ord(code_point_string)))
~~~

Each produced element is itself a length-one string. <code>ord</code> maps that one-code-point string to its integer code point; <code>chr</code> performs the inverse for a valid scalar range accepted by Python.

### 7.9.2 Source spelling, runtime value, and representation

A string literal is source syntax that constructs a runtime string value. Escape sequences allow source text to denote characters inconvenient or impossible to write literally:

~~~python
newline = "\n"
letter = "\N{GREEK SMALL LETTER LAMBDA}"
same_letter = "\u03bb"

print(len(newline))            # 1
print(letter == same_letter)   # True
~~~

The source spelling <code>"\n"</code> uses two visible source characters between quotes, but its runtime value contains one newline code point. The representation returned by <code>repr</code> chooses an escaped, diagnostic spelling; <code>print</code> writes the string’s content according to the output stream:

~~~python
value = "line 1\nline 2"
print(value)
print(repr(value))
~~~

Confusing source syntax, diagnostic representation, and displayed rendering causes persistent mistakes. A value has no quotation marks stored around it merely because a literal or <code>repr</code> uses quotation marks to denote it.

Raw string literals change how the Python lexer handles most backslashes; they do not create a distinct runtime type:

~~~python
ordinary = "C:\\data\\new"
raw = r"C:\data\new"
print(ordinary == raw)         # True
~~~

Raw literals still obey syntactic restrictions, including the inability to end with an odd number of backslashes before the closing quote. They are a source-notation facility, not a universal “literal text” mode.

### 7.9.3 Immutability and operation products

String methods never alter the receiving string. Methods described colloquially as replacing, stripping, padding, or changing case compute string results.

~~~python
original = "  Alpha  "
trimmed = original.strip()
lowered = trimmed.lower()

print(repr(original))          # '  Alpha  '
print(repr(trimmed))           # 'Alpha'
print(repr(lowered))           # 'alpha'
~~~

Whether an implementation reuses the identical object for a no-op result is not usually a language-level promise. Code must reason from equality and immutability, not identity:

~~~python
text = "already lowercase"
result = text.lower()
assert result == text
# Do not require: result is text
~~~

Because strings are immutable and their equality-relevant state is fixed, strings are hashable and may be dictionary keys or set members. This does not make every string a valid identifier, path, hostname, or security principal. Hashability is a structural capability, not domain validation.

### 7.9.4 Indexing, slicing, and boundary algebra

For a string of length \(n\), valid direct indices are \(-n\) through \(n-1\). A negative index \(i\) is normalised conceptually to \(n+i\). Direct out-of-range access raises <code>IndexError</code>:

~~~python
word = "Python"
print(word[0])                 # 'P'
print(word[-1])                # 'n'
# print(word[6])               # IndexError
~~~

A slice uses clamped boundaries and returns a string, possibly empty:

~~~python
print(word[1:4])               # 'yth'
print(word[100:200])           # ''
print(word[::-1])              # 'nohtyP'
~~~

The reversal is by code point. It can destroy grapheme structure:

~~~python
decomposed = "e\u0301"
print(decomposed[::-1])        # combining accent precedes e
~~~

Therefore the common expression <code>text[::-1]</code> reverses the sequence Python defines, but it is not a linguistically complete reversal algorithm. Bidirectional scripts, combining sequences, emoji clusters, and punctuation require a text-layout specification far beyond slicing.

In ordinary CPython, indexing uses the string’s compact internal representation to retrieve a code point without scanning from the beginning, so direct indexing is treated as constant-time with respect to string length. Slicing a span of \(k\) code points generally allocates and copies a new string, yielding \(O(k)\) time and space. These are implementation-qualified cost claims, not consequences of abstract sequence syntax alone.

### 7.9.5 Concatenation, repetition, and total copied volume

Binary concatenation computes a string containing both operands:

\[
|a+b|=|a|+|b|.
\]

If an algorithm repeatedly appends fixed-size pieces to an immutable prefix, the total amount copied can grow quadratically. Suppose the \(i\)-th step constructs a result of length approximately \(ic\), where each new piece has length \(c\). Then the copied output lengths sum to

\[
c+2c+\cdots+nc
=c\frac{n(n+1)}{2}
=\Theta(n^2c).
\]

~~~python
# Semantically valid, but potentially quadratic as a general construction pattern.
result = ""
for piece in pieces:
    result = result + piece
~~~

CPython contains optimisations that can reuse storage in selected concatenation situations when reference conditions permit. Such an optimisation is not a portable algorithmic guarantee and can disappear when aliases, tracing, alternative implementations, or expression shape change.

The stable construction pattern collects pieces and joins once:

~~~python
parts: list[str] = []
for record in records:
    parts.append(format_record(record))

document = "\n".join(parts)
~~~

If the final parts have total length \(L\) and there are \(n\) separators of bounded size, any materialised final string requires \(\Omega(L)\) writing. A well-designed join performs work proportional to the actual output rather than repeatedly copying completed prefixes.

Repetition <code>text * count</code> similarly constructs a new string with repeated content. A non-positive count yields the empty string. The operation’s output size is already \(\Theta(|text|\cdot count)\) for positive count, and memory limits must be considered before attempting enormous repetitions.

### 7.9.6 Join places the separator between complete strings

The receiver of <code>join</code> is the separator, not the collection. For finite strings \(s_0,\ldots,s_{n-1}\),

\[
\text{sep.join}(s_0,\ldots,s_{n-1})
=s_0+\text{sep}+s_1+\cdots+\text{sep}+s_{n-1}.
\]

There is no leading or trailing separator unless one is already part of an element.

~~~python
fields = ["Ada", "Lovelace", "36"]
row = ",".join(fields)
print(row)                     # Ada,Lovelace,36
~~~

Every element must be a string. Join does not silently convert arbitrary objects:

~~~python
numbers = [2, 3, 5]
# ",".join(numbers)            # TypeError
rendered = ",".join(str(number) for number in numbers)
~~~

The explicit conversion forces the program to own textual representation. For real CSV, manual joining is insufficient because delimiters, quotation marks, newlines, and dialect rules require escaping; use the <code>csv</code> module under a specified dialect, as Chapter 11 develops.

Join consumes an iterable. For an iterator, this consumption is destructive and finite completion is required before the final string can exist. An infinite source can never produce a completed joined string.

### 7.9.7 Prefixes, suffixes, and exact containment

<code>startswith</code> and <code>endswith</code> express anchored tests and accept a tuple of alternatives:

~~~python
filename = "archive.tar.gz"
print(filename.endswith((".gz", ".bz2", ".xz")))  # True
print(filename.startswith("archive"))               # True
~~~

The optional start and end arguments restrict the tested slice conceptually without requiring the caller to construct that slice:

~~~python
line = "INFO: ready"
print(line.startswith("ready", 6))                  # True
~~~

The containment expression <code>needle in haystack</code> asks whether an exact contiguous code-point subsequence occurs. It does not apply case folding, Unicode normalisation, word boundaries, or regular-expression syntax.

~~~python
print("cat" in "concatenate")       # True: substring, not word
print("Cat" in "concatenate")       # False: case-sensitive
~~~

Complexity depends on both haystack length \(n\), needle length \(m\), and the implementation’s search algorithm. A naive upper bound of \(O(nm)\) describes one algorithm, not necessarily CPython’s implementation. A defensible application claim either treats search as an abstract operation whose measured/runtime contract is implementation-specific or names the algorithm and version being analysed.

### 7.9.8 Find, index, count, and sentinel ambiguity

<code>find</code> returns the lowest matching index or <code>-1</code> when absent. <code>index</code> returns the lowest matching index or raises <code>ValueError</code>. The methods encode two failure interfaces:

~~~python
text = "bananas"

print(text.find("ana"))        # 1
print(text.find("xyz"))        # -1
print(text.index("ana"))       # 1
# text.index("xyz")            # ValueError
~~~

The <code>-1</code> sentinel is outside valid non-negative start indices but is itself a valid Python negative index. Careless reuse causes a classic defect:

~~~python
position = text.find("xyz")
if position:                   # wrong: -1 is truthy; 0 is falsey
    print(text[position])      # prints final character when absent
~~~

Correct tests are <code>position != -1</code> or, when the index is not needed, <code>"xyz" in text</code>. Use <code>index</code> when absence violates the expected input and should take an exceptional path.

<code>count</code> counts non-overlapping occurrences:

~~~python
print("aaaa".count("aa"))     # 2, not 3 overlapping start positions
~~~

If overlapping matches matter, the algorithm and advancement policy must be written explicitly. Also note the empty-needle rule: a string of length \(n\) has \(n+1\) empty boundaries, so <code>"abc".count("")</code> is 4.

### 7.9.9 Partition is a three-way structural contract

<code>partition(separator)</code> always returns a three-tuple <code>(before, separator_or_empty, after)</code>. It splits only at the first occurrence:

~~~python
header = "Content-Type: text/plain; charset=utf-8"
name, marker, value = header.partition(":")

if not marker:
    raise ValueError("header lacks colon")

print(name)                    # Content-Type
print(value.lstrip())          # text/plain; charset=utf-8
~~~

When absent, the result is <code>(original, "", "")</code>. Unlike a variable-length split result, the tuple shape is fixed, making unpacking and absence detection straightforward. <code>rpartition</code> uses the last occurrence and returns <code>("", "", original)</code> when absent.

Partition is often superior when a grammar has one structural delimiter and unrestricted remainder. Splitting every colon in a timestamp-bearing value would destroy information the parser did not intend to interpret.

### 7.9.10 Split requires a lexical policy

The no-argument and explicit-separator forms implement different tokenisation rules. With no separator, runs of Unicode whitespace separate fields; leading and trailing whitespace does not create empty tokens. With a non-empty explicit separator, exact occurrences delimit fields and adjacent or boundary separators create empty strings.

~~~python
record = "  alpha\tbeta   gamma  "
print(record.split())
# ['alpha', 'beta', 'gamma']

fields = "alpha,,gamma,".split(",")
print(fields)
# ['alpha', '', 'gamma', '']
~~~

The <code>maxsplit</code> argument bounds the number of divisions, not the result length directly; an ordinary left split produces at most <code>maxsplit + 1</code> fields:

~~~python
key, separator, remainder = "path=/a=b=c".partition("=")
first_two = "path=/a=b=c".split("=", maxsplit=1)
print(first_two)               # ['path', '/a=b=c']
~~~

<code>rsplit</code> applies the bound from the right. This is useful for extracting a suffix such as a final extension, though path semantics should generally use <code>pathlib</code> rather than ad hoc string splitting.

An empty explicit separator raises <code>ValueError</code>; every boundary could otherwise be interpreted as a split point, and Python requires the caller to state a different operation such as iteration or <code>list(text)</code>.

### 7.9.11 Splitlines is not merely split on newline

<code>splitlines</code> recognises a defined collection of Unicode line boundaries and handles terminal boundaries differently from splitting on a literal newline. Its <code>keepends</code> flag controls whether recognised delimiters remain attached.

~~~python
text = "alpha\r\nbeta\ngamma\n"

print(text.splitlines())
# ['alpha', 'beta', 'gamma']

print(text.splitlines(keepends=True))
# ['alpha\r\n', 'beta\n', 'gamma\n']

print(text.split("\n"))
# ['alpha\r', 'beta', 'gamma', '']
~~~

The appropriate method depends on whether the delimiter itself is data. Source-code tools, patch processors, and exact round trips may need endings retained; semantic line analysis often does not. Opening text files with newline translation adds another layer, addressed in Chapter 11.

### 7.9.12 Strip removes a set of boundary characters

The argument to <code>strip</code>, <code>lstrip</code>, or <code>rstrip</code> is a set-like collection of individual characters, not a prefix or suffix string:

~~~python
print("Arthur: three".lstrip("Arthur: "))
# 'ee' under character-set removal, not 'three'
~~~

The method repeatedly removes any leading character belonging to the supplied collection until encountering one outside it. To remove one exact prefix or suffix, use <code>removeprefix</code> or <code>removesuffix</code>:

~~~python
label = "prefix:value"
print(label.removeprefix("prefix:"))     # value

filename = "report.txt"
print(filename.removesuffix(".txt"))     # report
~~~

These exact methods return an equal unchanged string when the affix is absent. A defective use of <code>rstrip(".txt")</code> can remove any trailing run composed of dot, t, or x characters; it does not mean “remove the extension .txt.”

The no-argument strip methods use Unicode whitespace semantics, not only ASCII space. Whitespace removal can be a valid presentation cleanup, but it can corrupt fixed-width fields, passwords, signatures, or protocols in which boundary space is significant. Normalisation must be justified by the data contract.

### 7.9.13 Unicode normalisation and canonical equivalence

Unicode can represent some apparently identical text with different code-point sequences. The precomposed <code>é</code> and the sequence <code>e</code> plus a combining acute accent are canonically equivalent under Unicode, but Python string equality compares code-point sequences:

~~~python
precomposed = "\u00e9"
decomposed = "e\u0301"

print(precomposed == decomposed)         # False
print(len(precomposed), len(decomposed)) # 1 2
~~~

The <code>unicodedata.normalize</code> function converts text to a named normalisation form:

~~~python
from unicodedata import normalize

left = normalize("NFC", precomposed)
right = normalize("NFC", decomposed)
print(left == right)                     # True
~~~

The four principal forms are NFC, NFD, NFKC, and NFKD. C means composition, D decomposition, and K compatibility processing. Canonical forms preserve canonical equivalence. Compatibility forms may erase distinctions such as presentation variants that some domains consider meaningful. Normalisation is therefore a policy, not an unconditional cleanup.

A robust equality pipeline decides:

- which Unicode version and normalisation form govern the domain;
- whether compatibility distinctions are significant;
- whether case, whitespace, punctuation, or script differences are significant;
- whether original spelling must be preserved separately for display or audit;
- when normalisation occurs relative to validation and storage.

Normalising only one side at comparison time creates asymmetric results. Normalising inconsistently at several boundaries permits canonically equivalent duplicate keys. A system commonly preserves original input for presentation while deriving a consistently normalised comparison key.

### 7.9.14 Case conversion is not one-to-one

<code>lower</code>, <code>upper</code>, <code>title</code>, <code>capitalize</code>, <code>swapcase</code>, and <code>casefold</code> apply Unicode-defined transformations. They can change length and are not generally mutual inverses.

~~~python
word = "Straße"
print(word.lower())            # straße
print(word.upper())            # STRASSE
print(word.casefold())         # strasse
~~~

Case folding is designed for caseless comparison and is more aggressive than ordinary lowercasing. A basic comparison key might be:

~~~python
from unicodedata import normalize


def caseless_key(text: str) -> str:
    return normalize("NFC", normalize("NFD", text).casefold())
~~~

The two normalisation stages address transformations that can introduce sequences requiring re-normalisation. Even this function does not define human-language collation, username security, or visually confusable detection. Locale-sensitive casing—for example, distinctions involving Turkish dotted and dotless I—cannot be solved by assuming one universal human convention.

Never use case conversion as a substitute for a protocol’s named comparison algorithm. DNS labels, email local parts, file paths, programming identifiers, and natural-language words have different standards and environments.

### 7.9.15 Classification methods define Unicode predicates

String predicates such as <code>isalpha</code>, <code>isdecimal</code>, <code>isdigit</code>, <code>isnumeric</code>, <code>isalnum</code>, <code>isspace</code>, <code>isidentifier</code>, <code>isprintable</code>, <code>islower</code>, and <code>isupper</code> implement related but distinct Unicode-based conditions.

~~~python
samples = ["5", "²", "⅕", "四"]
for sample in samples:
    print(
        repr(sample),
        sample.isdecimal(),
        sample.isdigit(),
        sample.isnumeric(),
    )
~~~

The inclusion relationship is broadly:

\[
\text{decimal} \subseteq \text{digit} \subseteq \text{numeric},
\]

although a domain must consult the precise Unicode property definitions rather than infer them from typography. <code>int</code> accepts a grammar that does not coincide with every string satisfying <code>isnumeric</code>. Thus this is defective:

~~~python
text = "⅕"
print(text.isnumeric())        # True
# int(text)                    # ValueError
~~~

Validate by attempting the actual conversion whose grammar matters, then catch the narrow exception, or validate against the exact external grammar. Predicate similarity does not establish parser acceptance.

Most classification methods require at least one character and every relevant character to satisfy the property. Consequently, <code>"".isalpha()</code> is false. This differs from the vacuous truth of <code>all</code> over an empty iterable because the string predicate’s contract explicitly requires a non-empty string.

### 7.9.16 Identifiers, keywords, and confusability

<code>isidentifier</code> tests whether a string has the lexical shape of a Python identifier. It does not test whether the string is a reserved keyword:

~~~python
import keyword

for candidate in ["total", "class", "two words", "λ"]:
    print(
        candidate,
        candidate.isidentifier(),
        keyword.iskeyword(candidate),
    )
~~~

The Greek letter lambda is a valid Unicode identifier character even though the ASCII word <code>lambda</code> is a Python keyword. A name generator must check both conditions and consider soft keywords in the relevant grammar context.

Lexical validity is not security suitability. Unicode contains visually confusable characters across scripts. Two identifiers can appear nearly identical to a reader while consisting of different code points. Security-sensitive identifiers may require script restrictions, confusable analysis, normalisation, length limits, and collision policy defined by an applicable standard. Merely applying <code>isidentifier</code> or NFC does not prevent impersonation.

### 7.9.17 Encoding maps text to bytes

A string is not “UTF-8 internally” as a language-level fact. An **encoding** maps a code-point string to a byte sequence according to a named scheme; **decoding** attempts the inverse.

~~~python
text = "café"
payload = text.encode("utf-8")
restored = payload.decode("utf-8")

print(payload)                 # b'caf\xc3\xa9'
print(len(text))               # 4 code points
print(len(payload))            # 5 bytes
print(restored == text)        # True
~~~

Encoding and decoding belong at boundaries: files, sockets, subprocess streams, and binary protocols. Inside a text-processing layer, keep values as <code>str</code>; inside a byte-oriented protocol layer, keep values as <code>bytes</code>. Repeatedly guessing or mixing the two obscures ownership of the encoding decision.

The codec and error policy are both part of the contract:

~~~python
text = "price: €10"

# text.encode("ascii")                 # UnicodeEncodeError
print(text.encode("ascii", errors="replace"))
print(text.encode("ascii", errors="backslashreplace"))
~~~

Replacement avoids failure by losing or changing information. That may be acceptable for a diagnostic preview and unacceptable for identifiers, legal text, signatures, or round trips. <code>errors="ignore"</code> silently deletes unencodable content and should be treated as an explicit lossy transformation, never a generic repair.

Decoding arbitrary bytes with the wrong codec can fail or, worse, succeed with incorrect text. The classic corruption called **mojibake** arises when bytes encoded under one scheme are decoded or re-encoded under another. There is no universal algorithm that infers a byte stream’s intended codec without metadata or constrained heuristics.

### Worked example 7.5A — A strict UTF-8 record boundary

Requirement: a binary input record must be valid UTF-8, must not contain a NUL code point, and must end in exactly one logical newline that is excluded from the returned value.

~~~python
def decode_record(payload: bytes) -> str:
    try:
        text = payload.decode("utf-8", errors="strict")
    except UnicodeDecodeError as error:
        raise ValueError("record is not valid UTF-8") from error

    if "\x00" in text:
        raise ValueError("record contains NUL")

    if text.endswith("\r\n"):
        body = text[:-2]
    elif text.endswith("\n"):
        body = text[:-1]
    else:
        raise ValueError("record lacks a terminal line ending")

    if body.endswith(("\r", "\n")):
        raise ValueError("record has more than one terminal line ending")

    return body
~~~

Line-by-line semantic obligations:

1. The parameter type declares a byte boundary; the caller cannot accidentally supply already-decoded text.
2. Strict UTF-8 decoding either produces text or raises a codec-specific exception.
3. Exception translation gives the application one domain-facing invalid-record category while retaining the cause.
4. NUL validation occurs after decoding because the requirement concerns a Unicode code point.
5. The two-character CRLF sequence is tested before the one-character LF suffix.
6. Slicing removes exactly the recognised delimiter rather than applying broad whitespace stripping.
7. The final test rejects another immediately preceding line boundary, enforcing the “exactly one” policy.

The function does not normalise Unicode, alter case, or remove other whitespace because none of those transformations follows from the stated contract.

### 7.9.18 Replacement is non-overlapping and returns new text

<code>replace(old, new, count)</code> replaces non-overlapping occurrences from left to right, with an optional maximum count:

~~~python
print("aaaa".replace("aa", "b"))       # bb
print("aaaa".replace("aa", "b", 1))    # baa
~~~

Replacement is literal, not regular-expression based. It does not reinterpret capture groups or patterns. Replacements can expand, contract, or preserve length; any positional offsets recorded before replacement may cease to designate the same logical content.

Sequential replacements are order-sensitive:

~~~python
text = "ab"
first = text.replace("a", "b").replace("b", "c")
second = text.replace("b", "c").replace("a", "b")
print(first, second)            # cc bc
~~~

If several symbols must be mapped simultaneously, <code>translate</code> expresses a per-code-point table and avoids cascading interpretation of newly produced characters:

~~~python
table = str.maketrans({"a": "b", "b": "c", "-": None})
print("a-b".translate(table))  # bc
~~~

The source <code>a</code> maps to <code>b</code> once; that produced <code>b</code> is not translated again. Mapping to <code>None</code> deletes the character. Translation still operates by code point, not by arbitrary substring or grapheme cluster.

### 7.9.19 Formatting is a mini-language and a trust boundary

Formatted string literals, <code>str.format</code>, and <code>format</code> use a format-specification mini-language. Formatting combines value conversion, alignment, width, precision, sign, grouping, and type-specific rules.

~~~python
name = "Ada"
completed = 17
total = 23
ratio = completed / total

report = f"{name:<12} {completed:>4}/{total:<4} {ratio:7.2%}"
print(report)
~~~

Within each replacement field:

- <code>&lt;12</code> left-aligns the name in a minimum width of 12;
- <code>&gt;4</code> right-aligns the completed count;
- <code>7.2%</code> renders a percentage with two fractional digits in minimum width 7.

Width counts formatted code points or implementation-defined field length, not necessarily terminal display columns. Combining marks and double-width East Asian characters can make visual columns misalign. Terminal layout requires a display-width model.

Formatting invokes object-defined behaviour through <code>__format__</code>, <code>__str__</code>, or <code>__repr__</code>. Those methods can execute arbitrary code for user-defined objects and can fail. A logging or exception path that formats hostile or defective objects must account for that possibility.

Do not treat arbitrary user input as a trusted format template. Although Python’s format language is not a general evaluator in the same sense as <code>eval</code>, attribute and item traversal can expose data, and malformed fields can raise errors. Use a fixed application-owned template with user values inserted as data.

### 7.9.20 Representation, conversion, and debugging syntax

<code>str(value)</code> requests an informal human-facing representation; <code>repr(value)</code> requests an unambiguous diagnostic representation where practical. F-string conversion flags select these operations:

~~~python
value = "line 1\nline 2"

print(f"display={value!s}")
print(f"diagnostic={value!r}")
print(f"ascii-safe={value!a}")
~~~

The <code>!a</code> conversion applies <code>ascii</code>, escaping non-ASCII code points in the resulting representation. None of these is a general serialisation format. Representations can change between versions, omit state, contain memory addresses, or be impossible to parse back. JSON, CSV, and domain-specific serialisation require explicit protocols.

Debug-style f-string syntax such as <code>f"{total=}"</code> includes source expression text and a representation of the result. It is useful for local diagnostics but can expose sensitive values or tie output to source spelling. Production observability needs structured fields, redaction, stability, and volume controls.

### 7.9.21 Ordering compares code-point sequences, not words in a language

String comparison is lexicographic over code points. It does not implement dictionary collation for a human locale:

~~~python
words = ["Zebra", "apple", "Ångström", "ábaco"]
print(sorted(words))
~~~

The result follows Unicode code-point ordering and Python’s lexicographic rule. Case, accents, composed forms, language-specific letter order, numeric substrings, and punctuation may differ from a user’s expected collation.

A sorting key such as <code>normalize("NFC", text).casefold()</code> creates one explicitly caseless normalised code-point order. It still is not locale-aware collation and can produce equal keys for strings whose display forms differ. Stability then retains their input order. When user-facing collation matters, use a library implementing the relevant Unicode Collation Algorithm and locale tailoring, and version that dependency.

### 7.9.22 Security-sensitive comparison

Ordinary string equality can short-circuit at the first unequal portion, so its execution time can correlate with common-prefix length. For secrets such as authentication tags, a timing side channel may matter. The standard library provides <code>hmac.compare_digest</code> for byte-like or suitable ASCII string comparisons under its documented constraints:

~~~python
from hmac import compare_digest


def tag_matches(received: bytes, expected: bytes) -> bool:
    return compare_digest(received, expected)
~~~

This does not make the surrounding protocol secure. Length, parsing, error responses, network behaviour, key handling, and cryptographic construction can still leak or fail. The lesson is that textual equality has a computational contract; a security domain may require a specialised comparison primitive.

Passwords generally should not be normalised or case-folded ad hoc after a system has defined its credential protocol. They must be processed according to a versioned password-storage design using an appropriate password-hashing function, salt, parameter policy, and migration strategy. Branch D develops this defensive context.

### 7.9.23 Internal representation and memory qualifications

CPython uses a flexible internal Unicode representation capable of choosing storage widths according to a string’s largest code point, together with object metadata and selected caches. Thus two strings with equal code-point length can occupy different shallow memory. The language contract does not require this representation, and another Python implementation may use UTF-8, UTF-16, ropes, or another strategy internally.

Several consequences follow:

- <code>len(text)</code> is a code-point count independent of encoded byte length;
- <code>sys.getsizeof(text)</code> is a shallow, implementation-specific observation;
- appending one non-ASCII code point can cause a new result to require a wider internal representation;
- encoding always constructs or obtains a byte representation governed by the codec, regardless of internal storage;
- performance measured on ASCII-only data may not transfer unchanged to multilingual input.

Use representative corpora when profiling text systems. A benchmark containing only short ASCII tokens does not test normalisation, combining sequences, multi-byte I/O, varied storage kinds, or user-facing collation.

### 7.9.24 Interning is not a semantic identity rule

An implementation may **intern** selected strings: it may reuse one object for equal values to save storage or speed comparisons. Literal folding and identifier handling can make some equal strings identical in one build:

~~~python
left = "compiler"
right = "compiler"
print(left == right)           # True
# The result of left is right is not a portable value-equality rule.
~~~

Never use <code>is</code> to compare textual content. Interning policy depends on implementation, version, compilation context, and construction history. Use <code>==</code> for exact string equality. Explicit <code>sys.intern</code> is an optimisation tool for controlled workloads with many repeated keys; it does not alter equality semantics and should follow measurement rather than folklore.

### Worked example 7.5B — Preserve spelling while deriving an identity key

Suppose a bibliography application wants author lookup to ignore canonical Unicode composition, case distinctions, and boundary whitespace, while preserving the entered form for display. It must reject an empty normalised name.

~~~python
from dataclasses import dataclass
from unicodedata import normalize


def author_key(display_name: str) -> str:
    trimmed = display_name.strip()
    if not trimmed:
        raise ValueError("author name is empty")
    return normalize("NFC", normalize("NFD", trimmed).casefold())


@dataclass(frozen=True)
class Author:
    display_name: str

    @property
    def key(self) -> str:
        return author_key(self.display_name)
~~~

This example previews dataclasses and properties from later chapters. The structural decision is current: <code>display_name</code> preserves user spelling, while <code>key</code> is a derived comparison form. The two are not conflated.

The policy deliberately does not:

- collapse internal whitespace;
- remove accents by compatibility decomposition;
- apply locale-specific collation;
- identify nicknames or transliterations;
- detect visually confusable scripts.

Those are distinct domain decisions. A key derivation function should be narrow enough that its equivalence classes can be explained and tested.

### Worked example 7.5C — Linear-time escaped rendering

Requirement: render a sequence of text fields separated by a vertical bar. Backslash, vertical bar, newline, carriage return, and tab must be escaped. The output grammar must be reversible by a corresponding parser.

~~~python
ESCAPES = str.maketrans(
    {
        "\\": "\\\\",
        "|": "\\|",
        "\n": "\\n",
        "\r": "\\r",
        "\t": "\\t",
    }
)


def render_fields(fields: list[str]) -> str:
    escaped = [field.translate(ESCAPES) for field in fields]
    return "|".join(escaped)
~~~

Each field is traversed once by translation, producing an escaped piece. Join then traverses the pieces to construct the final record. If input and output lengths total \(L\), the work is \(O(L)\) under ordinary per-code-point table operations, and retained temporary space is also \(O(L)\). Sequential calls to <code>replace</code> would require careful ordering to avoid re-escaping newly inserted backslashes and would traverse intermediate strings repeatedly.

Reversibility is not proven merely by this renderer. A parser must recognise escapes as a state machine, reject incomplete or unknown escapes according to policy, and treat only unescaped vertical bars as separators. An exercise at the end of this chapter requires that proof.

> **Common misconception — “One Python string element is one visible character.”**  
> One element is one Unicode code point represented as a length-one string. A visible grapheme may comprise several code points, and display width is a further independent property.

> **Common misconception — “Unicode normalisation and case folding make text universally safe to compare.”**  
> They create particular equivalence relations. Locale, protocol, confusability, compatibility distinctions, and domain identity still require explicit policies.
