# 8.1 Why functions exist

A **function** is a callable object packaging parameterised behaviour. Functions solve three related problems. They give a computation a name, allow the same rule to be applied to different arguments, and establish a boundary within which state and obligations can be reasoned about locally.

Merely avoiding repeated source text is not the deepest purpose. A well-designed function publishes an interface: admitted arguments, returned value, effects, failures, and resource behaviour. Callers reason from that contract. The implementation can change while the contract remains stable.

```python
def rectangle_area(width: float, height: float) -> float:
    if width < 0 or height < 0:
        raise ValueError("dimensions must be non-negative")
    return width * height
```

`def` is a statement. When executed, it creates a function object from compiled code and the current defining context, then binds the name `rectangle_area` to that object. The body is not executed during definition. It runs when the function is called.

The contract is:

- `width` and `height` represent non-negative linear measures in a shared unit;
- the result represents area in the square of that unit;
- negative arguments raise `ValueError`;
- no external state is intentionally changed.

The annotations record intended Python types but do not encode units or non-negativity and are not automatically enforced. Prose, tests, and possibly richer static or runtime models complete the contract.

### 8.1.1 Mathematical functions and program functions

In mathematics, a function \(f:A\rightarrow B\) assigns exactly one element of codomain \(B\) to every element of domain \(A\). The same input has the same mathematical output; “calling” does not consume time, mutate a file, or fail because a network is unavailable.

A Python function is a runtime object governing a computation. It may:

- accept only a subset of values suggested by its annotations;
- return normally, raise, loop forever, suspend, or terminate the process;
- read time, randomness, files, devices, or shared state;
- mutate arguments or external objects;
- produce different results on different calls with equal arguments;
- retain state between calls through closures, defaults, attributes, or referenced objects.

Thus mathematical-function notation is useful for pure cores but not a complete operational model. A Python callable’s behaviour can be represented as a relation from an initial state and arguments to one of several outcomes:

\[
F:(S,A)\rightarrow (S',R)\;|\;E\;|\;\bot,
\]

where \(S\) is observable state, \(R\) a normal result, \(E\) an exceptional outcome, and \(\bot\) non-termination. A generator or coroutine adds suspension outcomes. This richer model prevents “input and output” prose from erasing mutation, failure, or liveness.

### 8.1.2 Abstraction removes irrelevant variation

An **abstraction** preserves properties relevant to a client while hiding representation choices irrelevant to that client. A function is one abstraction mechanism: callers need the contract, not every internal statement.

~~~python
def contains_identifier(records: list[dict[str, object]], identifier: str) -> bool:
    return any(record.get("id") == identifier for record in records)
~~~

A caller relies on the Boolean membership result, not on whether the implementation uses a generator expression, explicit loop, or future index. If performance is contractual—perhaps expected constant-time lookup is required—then the representation and complexity cease to be irrelevant and must enter the interface or owning object design.

Hiding a fact does not make it harmless. A function that secretly modifies <code>records</code>, caches without a bound, or performs network I/O violates reasonable expectations unless those effects are documented by its abstraction.

### 8.1.3 Contract dimensions

A complete function contract can be partitioned into dimensions:

| Dimension | Question |
|:---|:---|
| domain | Which argument values and relationships are admitted? |
| normal result | What value and invariants are returned? |
| effects | Which reachable or external state may change? |
| exceptional result | Which failures are reported and with what types/data? |
| termination | Under which conditions must the call complete? |
| resource use | What time, memory, I/O, descriptor, or recursion bounds matter? |
| determinism | Which environmental inputs may alter the result? |
| concurrency | May calls overlap, re-enter, or share state? |
| ownership | Are arguments retained, copied, consumed, or mutated? |
| stability | Which details are public across versions? |

For <code>rectangle_area</code>, non-negativity alone is incomplete. NaN passes both <code>width &lt; 0</code> and <code>height &lt; 0</code>; positive infinity can produce infinity; Boolean values satisfy many integer/float operations; units can be mixed. A scientific contract might require finite real-valued measures in metres, while a graphics contract might admit infinity as a clipping sentinel. Validation follows domain meaning.

### 8.1.4 Preconditions, postconditions, and frame conditions

A **precondition** is a property required at call entry. A **postcondition** is a property promised on normal return. A **frame condition** identifies state the function may modify; everything else is required to remain unchanged under the specified model.

For an in-place normalization:

~~~python
def clamp_in_place(values: list[int], lower: int, upper: int) -> None:
    if lower > upper:
        raise ValueError("lower exceeds upper")

    for index, value in enumerate(values):
        values[index] = min(max(value, lower), upper)
~~~

One contract is:

- precondition: <code>values</code> is an owned mutable list of integers and <code>lower &lt;= upper</code>;
- postcondition: same list length and, for every index \(i\), result value equals \(\min(\max(old_i,lower),upper)\);
- frame condition: only list element bindings in <code>values</code> may change;
- result: <code>None</code>;
- exceptional condition: invalid bounds raise before list mutation.

Whether integer subclasses or user-defined comparable values are admitted changes callback and failure behaviour. A contract precise enough for proof may deliberately restrict the domain more than ordinary duck typing.

### 8.1.5 Partial functions and validation placement

A **partial function** is defined only for part of an apparent input domain. Division as \(a/b\) is undefined for \(b=0\) in ordinary real arithmetic. Python represents that excluded case with an exception:

~~~python
def ratio(numerator: float, denominator: float) -> float:
    if denominator == 0:
        raise ZeroDivisionError("ratio denominator is zero")
    return numerator / denominator
~~~

The explicit check can improve context but may duplicate the operator’s own validation and interact with unusual numeric types. An alternative lets division raise naturally. Boundary validation is valuable when it converts a wider low-level failure space into a stable domain error or prevents any partial effect; it is wasteful when it merely restates a trusted primitive without adding a contract.

Some functions totalise a partial operation by returning an optional or tagged result. That changes caller obligations; it does not make the exceptional input disappear.

### 8.1.6 Referential transparency and substitution

An expression is **referentially transparent** under an observation model if it can be replaced by its value without changing program behaviour. A call to a pure deterministic function over immutable values can often be reasoned about this way:

~~~python
def square(number: int) -> int:
    return number * number
~~~

Within ordinary arithmetic assumptions, replacing <code>square(5)</code> by <code>25</code> preserves relevant behaviour. The following does not have that property:

~~~python
counter = 0


def next_identifier() -> int:
    global counter
    counter += 1
    return counter
~~~

Replacing a call with its previous result changes later identifiers. Referential transparency enables equational reasoning, memoisation, parallel evaluation, and local testing. It is not a moral requirement: I/O boundaries must have effects. The design goal is often a large pure core surrounded by narrow effect-owning functions.

### 8.1.7 Cohesion and semantic naming

A function is **cohesive** when its operations contribute to one intelligible responsibility. Line count is not the criterion. A three-line function that parses input, writes a database, and swallows errors may have low cohesion; a thirty-line finite-state parser may implement one precise grammar.

Names should identify the abstraction and effects. Compare:

- <code>calculate_total</code>: suggests value computation;
- <code>update_account_total</code>: suggests mutation;
- <code>load_account</code>: suggests I/O or retrieval;
- <code>get_account</code>: ambiguous unless project convention defines whether it may fetch remotely or create state.

Names cannot replace contracts, but misleading names increase the proof burden at every call site.

### 8.1.8 Definition execution creates runtime state

Executing a <code>def</code> statement performs observable work. It evaluates decorator expressions, evaluates defaults, evaluates some annotations under the active annotation regime, creates a function object, applies decorators, and binds a name. In a loop or conditional, the statement may create several distinct function objects or no binding on one path.

~~~python
functions = []

for offset in range(3):
    def add_offset(value: int, offset: int = offset) -> int:
        return value + offset

    functions.append(add_offset)
~~~

The <code>def</code> executes three times. Each execution creates a function with a separately evaluated default. The body is shared as code conceptually, but function objects and defaults are distinct. The module name <code>add_offset</code> is rebound each iteration; the list retains every created function.

### Worked example 8.1A — Refine a function contract until it is testable

Initial requirement: “average some readings.” A testable refinement is:

~~~python
from math import fsum, isfinite
from collections.abc import Iterable


def finite_mean(readings: Iterable[float]) -> float:
    values = list(readings)

    if not values:
        raise ValueError("at least one reading is required")
    if any(not isfinite(value) for value in values):
        raise ValueError("every reading must be finite")

    return fsum(values) / len(values)
~~~

The refined contract states:

1. the function consumes a finite iterable exactly once to completion during materialisation;
2. every produced value must support <code>isfinite</code> under the annotated float policy;
3. an empty or non-finite population raises <code>ValueError</code> before the summation result is returned;
4. normal return is the floating arithmetic mean computed with <code>math.fsum</code> and ordinary division;
5. the source iterable’s own effects and exceptions can occur during materialisation;
6. memory is \(O(n)\) because values are retained to validate and count;
7. the caller’s containers are not intentionally mutated, but a one-shot iterator is consumed.

A one-pass implementation could use a count and <code>fsum</code> over a validating generator, reducing explicit list storage but changing when failure appears and complicating exact handling of source effects. Even a small numerical function embodies choices about finiteness, materialisation, accuracy, and failure.

> **Common misconception — “A function is just reusable lines of code.”**  
> Reuse is one benefit. The deeper abstraction is a named boundary over domain, results, effects, failures, ownership, and resource behaviour.
