# 8.10 Lambda expressions

A `lambda` expression creates a function with one expression body:

```python
square = lambda value: value * value
```

This is behaviourally similar to:

```python
def square(value):
    return value * value
```

for simple use, though metadata such as the default function name differs. Lambda is appropriate for short local behaviour whose role is evident at the call site, especially key functions:

```python
records.sort(key=lambda record: record["timestamp"])
```

It is not a tool for compressing multi-stage logic into unreadable nested expressions. A named `def` supports documentation, annotations, breakpoints, reuse, and a meaningful traceback name.

### 8.10.1 Lambda is an expression, def is a statement

Because a lambda is an expression, it can occur where a value is required:

~~~python
key = (lambda record: record["score"])
~~~

A <code>def</code> statement instead binds a name in its containing block. This syntactic distinction is why lambdas are convenient as small immediate arguments and why named definitions better support larger behaviour.

Both create function objects when evaluated/executed. Both obey ordinary parameter binding, default timing, closure capture, and exception propagation. Lambda is not evaluated each time its containing call invokes the resulting function unless the lambda expression itself is re-evaluated.

### 8.10.2 The body is one expression, not one trivial operation

The grammar permits one expression, and expressions can contain conditionals, comprehensions, calls, and nested lambdas:

~~~python
absolute = lambda value: -value if value < 0 else value
~~~

The restriction does not prevent complexity; it merely makes complex control flow harder to name and inspect. Compressing multiple conceptual steps into a nested expression can be worse than a short <code>def</code> with guard clauses and intermediate names.

Statements such as <code>try</code>, <code>while</code>, ordinary assignment, and <code>return</code> cannot form the direct lambda body. An assignment expression can occur where grammar permits, but using it to simulate a multi-statement function usually damages clarity.

### 8.10.3 Return is implicit only syntactically

~~~python
square = lambda value: value * value
~~~

The evaluated body expression supplies the normal result. This does not mean lambdas always return a useful value:

~~~python
announce = lambda message: print(message)
result = announce("ready")
assert result is None
~~~

<code>print</code> returns <code>None</code>, which becomes the lambda result. Effects and failure semantics remain those of the expression.

### 8.10.4 Lambda parameters support most ordinary kinds

Lambdas can have positional-only markers, defaults, variadic collectors, and keyword-only parameters under their grammar:

~~~python
affine = lambda x, /, scale=1, *, offset=0: scale * x + offset
print(affine(3, 2, offset=5))  # 11
~~~

Direct parameter annotations are not part of lambda syntax. Assign a compatible callable annotation to a name or use a named definition when parameter documentation matters:

~~~python
from collections.abc import Callable

affine_typed: Callable[[float, float], float] = (
    lambda value, scale: value * scale
)
~~~

This callable annotation cannot express the keyword-only detail in the simple form, illustrating why named signatures are often better public interfaces.

### 8.10.5 Lambda follows the same late-binding rules

~~~python
factor = 2
operation = lambda value: factor * value
factor = 10
print(operation(3))            # 30
~~~

At module level <code>factor</code> is a global lookup; inside a factory it can be a closure cell. The word “lambda” causes no snapshot. A default parameter can capture the current reference for the same definition-time reason described earlier.

### 8.10.6 Tracebacks and names favour def for substantial behaviour

Ordinary lambdas have the diagnostic name <code>&lt;lambda&gt;</code> unless tools use an assigned variable or wrapper metadata to add context. Several lambdas in one call chain therefore yield less informative tracebacks and profiler reports than named functions.

~~~python
def score_by_recency(record: dict[str, int]) -> int:
    return record["timestamp"]
~~~

This name conveys why timestamp is the key, supports a docstring and annotations, and provides a stable breakpoint. Use a lambda when its entire meaning is locally obvious, not merely because it saves vertical space.

### 8.10.7 Callable factories are not improved by nested lambda puzzles

The expression

~~~python
make_adder = lambda amount: lambda value: value + amount
~~~

is valid and demonstrates closures, but a named version exposes roles:

~~~python
from collections.abc import Callable


def make_adder(amount: int) -> Callable[[int], int]:
    def add(value: int) -> int:
        return value + amount
    return add
~~~

The source length is larger; the cognitive state is smaller. Concision should be measured by concepts a reader must reconstruct, not character count.

### 8.10.8 Projection helpers can replace trivial lambdas

~~~python
from operator import attrgetter, itemgetter

by_second = itemgetter(1)
by_name = attrgetter("name")
~~~

These callable objects precisely name subscription or attribute projection and can extract multiple fields. A lambda remains better when transformation is genuinely custom or the helper would be obscure to the audience. Neither avoids exceptions from missing items/attributes.

### Worked example 8.4D — Make a sorting policy readable

Compact version:

~~~python
records.sort(
    key=lambda r: (
        r["status"] != "active",
        -r["score"],
        r["name"].casefold(),
        r["id"],
    )
)
~~~

Named version:

~~~python
def ranking_key(record: dict[str, object]) -> tuple[bool, float, str, str]:
    status = record["status"]
    score = record["score"]
    name = record["name"]
    identifier = record["id"]

    if not isinstance(status, str):
        raise TypeError("status must be text")
    if not isinstance(score, (int, float)) or isinstance(score, bool):
        raise TypeError("score must be numeric")
    if not isinstance(name, str) or not isinstance(identifier, str):
        raise TypeError("name and id must be text")

    return (
        status != "active",
        -float(score),
        name.casefold(),
        identifier,
    )
~~~

The named function provides a validation boundary, typed result shape, breakpoints, and vocabulary. Active records sort first because <code>False &lt; True</code>; score is descending through negation; case-folded name and then ID break ties. The compact lambda may be appropriate only when validated record types already guarantee every assumption and the key is used once locally.

> **Common misconception — “Lambda functions are faster or fundamentally lighter than def functions.”**  
> Both create ordinary function objects with code and binding context. Performance depends on the actual computation and call path; lambda’s primary distinction is expression syntax and limited body grammar.
