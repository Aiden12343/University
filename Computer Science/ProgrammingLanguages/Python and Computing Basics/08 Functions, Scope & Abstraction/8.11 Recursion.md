# 8.11 Recursion

**Recursion** occurs when solving a problem invokes the same operation on a smaller or structurally simpler instance. A recursive definition needs:

1. one or more **base cases** answered without recursion;
2. a **recursive case** reducing the problem;
3. a well-founded measure proving progress towards a base case;
4. a rule for combining the recursive result.

### Worked example 8.4 — Factorial and its proof

For non-negative integer (n), factorial is

\[
n! = \begin{cases}
1 & n=0,\\
n\times(n-1)! & n>0.
\end{cases}
\]

```python
def factorial(number: int) -> int:
    if number < 0:
        raise ValueError("factorial requires a non-negative integer")
    if number == 0:
        return 1
    return number * factorial(number - 1)
```

For 4, calls expand as:

```text
factorial(4)
4 * factorial(3)
4 * 3 * factorial(2)
4 * 3 * 2 * factorial(1)
4 * 3 * 2 * 1 * factorial(0)
4 * 3 * 2 * 1 * 1
24
```

Termination follows because each recursive call reduces a non-negative integer by one until zero. Partial correctness follows by induction: base case returns (0!=1); assuming the recursive call returns ((n-1)!), multiplication by (n) returns (n!).

Each active call needs a frame. CPython enforces a recursion-depth limit to prevent unbounded native/interpreter stack exhaustion. Python does not require **tail-call optimisation**, and ordinary CPython does not eliminate tail-recursive frames. Iteration is often more appropriate for a simple linear fold.

```python
def factorial_iterative(number: int) -> int:
    if number < 0:
        raise ValueError("factorial requires a non-negative integer")
    result = 1
    for factor in range(2, number + 1):
        result *= factor
    return result
```

Recursion remains natural for recursively structured data such as trees, divide-and-conquer algorithms, parsing, and backtracking. The criterion is structural fit and resource bounds, not ideological preference.

### 8.11.1 Recursive definitions and recursive executions

A recursively defined mathematical object need not be computed recursively, and a recursively executing program need not directly mirror a mathematical recurrence. Factorial is recursively definable but can be folded iteratively. Graph traversal can recurse through structure even when its output has no recursive mathematical formula.

Separate three questions:

1. Is the domain inductively or recursively structured?
2. Does a recursive algorithm clarify decomposition and proof?
3. Is recursion an appropriate execution strategy under Python’s resource model?

Answering yes to the first does not force yes to the third.

### 8.11.2 Structural recursion

**Structural recursion** makes recursive calls on direct substructures. A recursively nested tree can be defined as either a leaf or a node containing child trees. A size function follows that definition:

~~~python
from dataclasses import dataclass


@dataclass(frozen=True)
class Leaf:
    value: int


@dataclass(frozen=True)
class Branch:
    children: tuple[Leaf | "Branch", ...]


Tree = Leaf | Branch


def leaf_count(tree: Tree) -> int:
    if isinstance(tree, Leaf):
        return 1
    return sum(leaf_count(child) for child in tree.children)
~~~

The type aliases/classes are formally developed later. The recursive structure is current: each Branch call invokes the function on strict child subtrees. Termination follows for a finite acyclic tree because subtree size strictly decreases along every child edge.

If object sharing turns the structure into a DAG, this function counts leaf occurrences along paths, not distinct leaf objects. If a cycle is admitted, structural decrease fails and recursion may not terminate. The representation invariant determines the algorithm’s meaning.

### 8.11.3 Generative recursion

**Generative recursion** computes a smaller or otherwise progressing subproblem rather than merely selecting a stored substructure. Euclid’s greatest-common-divisor algorithm is an example:

~~~python
def gcd(left: int, right: int) -> int:
    left = abs(left)
    right = abs(right)

    if right == 0:
        return left
    return gcd(right, left % right)
~~~

For positive <code>right</code>, the remainder satisfies

\[
0\le left\bmod right<right.
\]

The second non-negative component strictly decreases, proving termination. Common divisors are preserved because

\[
\gcd(a,b)=\gcd(b,a\bmod b).
\]

Generative recursion requires a well-founded progress argument; no visible tree shape supplies it automatically.

### 8.11.4 Proof by induction mirrors recursive correctness

To prove a recursively defined function correct over non-negative integers:

1. prove the base input;
2. assume the recursive result is correct for a smaller input (the induction hypothesis);
3. prove the current combination yields the required result;
4. separately prove termination reaches the base.

For factorial, base returns 1 for zero. Assume <code>factorial(n - 1)</code> returns \((n-1)!\). Then multiplication by \(n\) returns \(n!\). The variant \(n\) decreases by one and remains non-negative until zero.

Partial correctness plus termination gives total correctness for admitted inputs. An induction proof that assumes recursive calls return does not alone prove they ever do.

### 8.11.5 Validate the domain before recursive descent

The original factorial annotation says integer but does not enforce it. A robust exact domain boundary can reject Boolean and non-integer values:

~~~python
def factorial(number: int) -> int:
    if isinstance(number, bool) or not isinstance(number, int):
        raise TypeError("factorial requires an integer")
    if number < 0:
        raise ValueError("factorial requires a non-negative integer")

    def calculate(current: int) -> int:
        if current == 0:
            return 1
        return current * calculate(current - 1)

    return calculate(number)
~~~

The public boundary validates once. The private core relies on the established invariant rather than rechecking every recursive frame. This reduces duplicated work and separates untrusted input from the inductive recurrence.

Whether integer subclasses should be admitted is a domain decision. The check above admits non-Boolean subclasses. Using <code>type(number) is int</code> would demand exact built-in integers.

### 8.11.6 Call expansion and result contraction

For <code>factorial(4)</code>, the call phase creates frames until the base case. Only then does multiplication occur while returns contract the chain:

| Active call | Deferred operation |
|:---|:---|
| factorial(4) | multiply returned result by 4 |
| factorial(3) | multiply returned result by 3 |
| factorial(2) | multiply returned result by 2 |
| factorial(1) | multiply returned result by 1 |
| factorial(0) | return 1 immediately |

The operands and return destinations are retained in frames. Recursive algorithms can therefore have small final outputs but large peak stacks.

### 8.11.7 Tail position does not imply tail-call elimination

A call is in **tail position** when its result becomes the caller’s result without further computation:

~~~python
def factorial_tail(number: int, accumulator: int = 1) -> int:
    if number == 0:
        return accumulator
    return factorial_tail(number - 1, accumulator * number)
~~~

The recursive call is in tail position, but Python does not require the frame to be reused. Ordinary CPython retains frames for tracebacks and debugging semantics and does not perform general tail-call optimisation. Stack use remains \(O(n)\).

The loop form makes state explicit and uses constant Python call-stack depth:

~~~python
def factorial_loop(number: int) -> int:
    result = 1
    current = number
    while current > 0:
        result *= current
        current -= 1
    return result
~~~

Tail recursion is not an optimization request in Python.

### 8.11.8 Linear recursion has linear frame space

For a recurrence that makes one call on \(n-1\), maximum active depth is \(n+1\), so stack space is \(\Theta(n)\) under constant per-frame state. Time can also be \(\Theta(n)\), but the two measures are independent.

A recursive sum that slices on every call can be worse:

~~~python
def sum_bad(values: list[int]) -> int:
    if not values:
        return 0
    return values[0] + sum_bad(values[1:])
~~~

Each slice copies a shrinking suffix. Total copying is

\[
(n-1)+(n-2)+\cdots+1=\Theta(n^2),
\]

and peak retained slice references can also be large. Passing an index avoids slicing but not recursion depth; iteration avoids both.

### 8.11.9 Multiple recursive calls require a recurrence

Naive Fibonacci executes two recursive calls:

\[
T(n)=T(n-1)+T(n-2)+\Theta(1).
\]

This grows exponentially with \(n\) because subproblems repeat. The recursion tree contains many calls for the same arguments. Memoisation reduces distinct computed states to \(n+1\), or an iterative recurrence uses constant state if earlier results beyond two are not needed.

Do not infer time from recursion depth alone. Fibonacci depth is \(O(n)\) while total calls are exponential. A balanced binary traversal may have depth \(O(\log n)\) and total work \(O(n)\).

### 8.11.10 Divide and conquer

**Divide and conquer** splits a problem into subproblems, solves them recursively, and combines results. Merge sort follows:

\[
T(n)=2T(n/2)+\Theta(n),
\]

which yields \(\Theta(n\log n)\) time under balanced splitting. Recursion depth is \(\Theta(\log n)\), while merging needs additional storage in a straightforward implementation.

~~~python
def merge_sort(values: list[int]) -> list[int]:
    if len(values) < 2:
        return values.copy()

    middle = len(values) // 2
    left = merge_sort(values[:middle])
    right = merge_sort(values[middle:])
    return merge(left, right)
~~~

The helper <code>merge</code> must be defined to combine two sorted lists stably in linear time. Slices add linear work per recursion level, which remains within \(\Theta(n\log n)\), but increase allocations. Chapter 13 implements and proves the complete algorithm.

### 8.11.11 Tree traversal order changes semantics

For a node with children, **preorder** processes the node before children, **postorder** after children, and **inorder** (for an ordered binary tree) between left and right subtrees. Breadth-first order processes by depth and typically uses a queue.

~~~python
def preorder(tree: Tree):
    yield tree
    if isinstance(tree, Branch):
        for child in tree.children:
            yield from preorder(child)
~~~

This generator has recursive suspension: every active ancestor generator frame remains suspended while a descendant yields. Peak frame count is proportional to depth. Early consumer termination requires closing/resource policies if traversal owns resources.

Traversal order affects observable output, pruning opportunities, memory, and dependency semantics. It is not merely an implementation detail.

### 8.11.12 Explicit stacks reproduce depth-first traversal

~~~python
def preorder_iterative(root: Tree):
    pending: list[Tree] = [root]

    while pending:
        current = pending.pop()
        yield current

        if isinstance(current, Branch):
            pending.extend(reversed(current.children))
~~~

Children are pushed in reverse so the leftmost/first child is popped next, matching recursive preorder. The list represents deferred subtrees explicitly. It can grow with frontier size and remains subject to memory limits, but it avoids the interpreter recursion limit and allows instrumentation or cancellation at the loop.

Proving equivalence requires showing that the stack order equals the recursive continuation order, not merely that both visit every node.

### 8.11.13 Graph traversal needs visited state

A tree recursion assumes one parent and no cycles. For a general graph:

~~~python
def reachable(graph: dict[str, set[str]], start: str) -> set[str]:
    visited: set[str] = set()

    def visit(node: str) -> None:
        if node in visited:
            return
        visited.add(node)
        for neighbour in graph[node]:
            visit(neighbour)

    visit(start)
    return visited
~~~

The node must be marked before descending. Marking after recursive calls loops on a cycle such as A→B→A. The invariant is that every visited node has been discovered and will not be expanded twice; every recursive call is for a newly discovered node.

Set iteration makes traversal order unspecified. If deterministic output matters, traverse sorted neighbours under an explicit key or store ordered adjacency. Recursion depth can reach the number of nodes in a path.

### 8.11.14 Mutual recursion

Functions are **mutually recursive** when each can call the other:

~~~python
def is_even(number: int) -> bool:
    if number == 0:
        return True
    return is_odd(number - 1)


def is_odd(number: int) -> bool:
    if number == 0:
        return False
    return is_even(number - 1)
~~~

For admitted non-negative integers, the measure decreases across the pair. Definitions succeed because names in bodies are resolved at call time, after both top-level <code>def</code> statements have executed. Calling <code>is_even</code> between the two definitions would fail when it first needed <code>is_odd</code>.

Modulo arithmetic is a simpler solution for parity. Mutual recursion becomes natural in grammars with alternating nonterminals or state machines, but termination must be proven across the entire call cycle.

### 8.11.15 Backtracking explores a decision tree

**Backtracking** chooses an alternative, recursively explores consequences, and undoes or abandons the choice on failure. Generating binary strings of length \(n\):

~~~python
def binary_strings(length: int):
    prefix: list[str] = []

    def search() -> None:
        if len(prefix) == length:
            yield_value = "".join(prefix)
            results.append(yield_value)
            return

        for digit in ("0", "1"):
            prefix.append(digit)
            search()
            prefix.pop()

    results: list[str] = []
    search()
    return results
~~~

The prefix is shared mutable state. The invariant before each alternative is that it represents choices on the path to the current node. Append makes one choice; recursive return restores control; pop undoes exactly that choice. If <code>search</code> raises, <code>pop</code> is skipped. A <code>try/finally</code> or immutable prefix construction provides stronger restoration.

There are \(2^n\) outputs of length \(n\), so output size alone requires \(\Omega(n2^n)\) characters to materialise them. Exponential work is unavoidable when all outputs are demanded, even though pruning can improve constrained searches.

### 8.11.16 Exception safety in recursive mutation

~~~python
path.append(node)
visit(node)
path.pop()
~~~

This restoration pattern is valid only for normal return. Use:

~~~python
path.append(node)
try:
    visit(node)
finally:
    removed = path.pop()
    assert removed == node
~~~

Now ordinary exceptions restore the path. Process termination or corruption still lies outside the guarantee. Alternatively, pass <code>path + [node]</code> to create independent path values, trading \(O(depth)\) copying per edge for simpler aliasing.

### 8.11.17 Recursion limit errors are not domain results

If a structurally valid input is deeper than the implementation’s recursion capacity, <code>RecursionError</code> reports an execution-resource failure. Catching it and returning a normal “not found” result would confuse computational failure with a domain answer.

An API that admits adversarial nesting should enforce a maximum depth as input validation or use an iterative algorithm. Increasing <code>sys.setrecursionlimit</code> without stack analysis can crash the process; it is not a general repair.

### 8.11.18 Recursive I/O and resource fan-out

A recursive directory walk can encounter cycles through symbolic links, permission failures, enormous depth, and changing filesystem state. Opening one resource per depth and retaining all handles can exhaust descriptors. Traversal contracts must define link following, error policy, ordering, race tolerance, and resource lifetime.

The convenience of a recursive source shape does not remove outside-world hazards. Standard library traversal functions often embody better platform handling than ad hoc recursion, but their precise contracts still require study.

### Worked example 8.5A — Structural sum with a depth bound

Requirement: sum integer leaves in nested lists, reject cycles, reject Boolean leaves, and reject nesting deeper than a caller-supplied non-negative bound.

~~~python
def nested_sum(root: object, *, max_depth: int = 100) -> int:
    if max_depth < 0:
        raise ValueError("max_depth must be non-negative")

    active: set[int] = set()

    def visit(current: object, depth: int) -> int:
        if isinstance(current, bool) or not isinstance(current, (int, list)):
            raise TypeError("leaves must be integers and branches lists")
        if isinstance(current, int):
            return current
        if depth > max_depth:
            raise ValueError("maximum nesting depth exceeded")

        identity = id(current)
        if identity in active:
            raise ValueError("cycle detected")

        active.add(identity)
        try:
            return sum(visit(child, depth + 1) for child in current)
        finally:
            active.remove(identity)

    return visit(root, 0)
~~~

<code>active</code> records list identities on the current recursion path, not every previously visited list. This rejects cycles while permitting a shared acyclic sublist to contribute once per occurrence. A global visited set would instead avoid repeated DAG traversal and change semantics for shared references.

The depth convention assigns the root list depth zero and its nested child lists depth one. The check occurs after leaf classification, so an integer leaf below a branch at the maximum depth is admitted; a further list branch is rejected when its depth exceeds the bound. Such boundary choices must be tested explicitly.

The <code>finally</code> restores <code>active</code> if any descendant fails. Auxiliary active-state and call depth are \(O(h)\); total successful work is \(O(n)\) occurrences for an acyclic structure, plus integer addition costs.

### Worked example 8.5B — Backtracking without shared-mutation leakage

Find all subsets of integers summing to a target, treating equal values at different positions as distinct choices:

~~~python
def subset_indices(values: tuple[int, ...], target: int) -> list[tuple[int, ...]]:
    solutions: list[tuple[int, ...]] = []

    def search(index: int, total: int, chosen: tuple[int, ...]) -> None:
        if index == len(values):
            if total == target:
                solutions.append(chosen)
            return

        search(index + 1, total, chosen)
        search(index + 1, total + values[index], chosen + (index,))

    search(0, 0, ())
    return solutions
~~~

Every state considers exactly two branches for the current position: exclude or include. <code>index</code> strictly increases, proving termination. Immutable tuples eliminate undo logic; concatenating a tuple costs proportional to chosen length, increasing total allocation. A mutable path with <code>try/finally</code> can reduce copies.

Without pruning, the decision tree has \(2^{n+1}-1\) calls and up to \(2^n\) solutions. If values can be negative, pruning on <code>total &gt; target</code> is invalid because later negatives may reduce the total. Pruning rules require domain assumptions.

### Worked example 8.5C — Convert recursive DFS to an explicit continuation stack

Recursive preorder:

~~~python
def walk(node):
    process(node)
    for child in children(node):
        walk(child)
~~~

Equivalent explicit worklist for finite acyclic trees:

~~~python
def walk_iterative(root) -> None:
    pending = [root]
    while pending:
        node = pending.pop()
        process(node)
        child_snapshot = tuple(children(node))
        pending.extend(reversed(child_snapshot))
~~~

The stack contains roots of recursive calls that the original execution would make later, in reverse execution order. Materialising children fixes one node’s child population before proceeding and permits reversal; if <code>children(node)</code> is expensive, infinite, or effectful, this changes timing. Equivalence claims must cover source behaviour, not only final node order.

> **Common misconception — “A recursive call automatically receives a copy of all local state.”**  
> Each call has new local bindings, but arguments can reference the same mutable objects. Backtracking code often shares a path intentionally and must restore it on every exit.
