# 8.12 Contracts and defensive boundaries

A function contract should state:

- accepted argument meaning and structure;
- returned-value meaning and structure;
- mutations and external effects;
- exceptions and their conditions;
- determinism or environmental dependence;
- relevant time and space properties;
- thread or reentrancy assumptions where applicable.

**Defensive programming** validates information at boundaries where trust or responsibility changes. Validating the same invariant inside every private helper can duplicate work and obscure ownership. Validating nowhere relies on callers to infer hidden preconditions.

### Worked example 8.5 — Core and boundary separation

```python
def mean_non_empty(values: list[float]) -> float:
    if not values:
        raise ValueError("mean requires at least one value")
    return sum(values) / len(values)


def parse_measurements(fields: list[str]) -> list[float]:
    values: list[float] = []
    for position, field in enumerate(fields, start=1):
        try:
            value = float(field)
        except ValueError as error:
            raise ValueError(f"measurement {position} is invalid") from error
        values.append(value)
    return values
```

Parsing owns text-to-number failure context. Mean owns the mathematical non-empty precondition. Neither prints or exits, so a command-line, web, or test caller can choose presentation and status policy.

NaN and infinity remain admitted by `float`; if the domain excludes them, `parse_measurements` must check finiteness explicitly with `math.isfinite`. The name `float` alone does not encode domain validity.

### 8.12.1 Design by contract

**Design by contract** treats a software element as an agreement between caller and implementation. The caller establishes preconditions; the implementation establishes postconditions and preserves invariants. This does not mean every contract must be checked at runtime. Some are statically verified, some established by construction, some checked at a trust boundary, and some documented assumptions within a private core.

For a binary search helper:

- caller precondition: input is sorted under the same key/order relation used by the search;
- implementation postcondition: returned index is a matching position, or absence is reported under the chosen interface;
- frame condition: source sequence is not mutated;
- resource claim: logarithmic index probes for an indexable sequence;
- callback claim: key comparisons obey a stable coherent order.

Checking sortedness inside every call would cost \(O(n)\), eliminating the asymptotic reason to use binary search. The sorted invariant should be owned and maintained by the containing abstraction.

### 8.12.2 Boundary validation and trusted cores

A **trust boundary** is a transition where data or authority enters from a source whose guarantees the receiving component cannot assume. Examples include command-line text, files, network messages, database rows under a changing schema, plugin callbacks, deserialised objects, and public library calls.

A layered flow is:

\[
\text{untrusted representation}
\xrightarrow{parse}
\text{structured candidate}
\xrightarrow{validate}
\text{domain value}
\xrightarrow{core}
\text{domain result}.
\]

Once a validated immutable domain value exists, private core functions can avoid repeatedly checking its construction invariant. This improves clarity and prevents inconsistent validation policies. It also means construction pathways must be controlled; any bypass invalidates the reasoning.

### 8.12.3 Parsing, validation, normalisation, and sanitisation differ

- **Parsing** recognizes a representation and constructs structured values.
- **Validation** determines whether a value satisfies a predicate or schema.
- **Normalisation** maps admitted alternatives into a selected canonical form.
- **Sanitisation** transforms or removes content to make it acceptable for a particular sink or policy.

These phases are often conflated. HTML escaping is not input validation; it is output encoding for a particular context. Removing punctuation from a username is not neutral normalization if punctuation is meaningful. Parsing an integer does not prove it lies within a permitted account range.

Function names and contracts should identify the phase. Applying a transformation too early can destroy evidence needed to reject malformed input or audit the original.

### 8.12.4 Type annotations are propositions for tools, not automatic guards

~~~python
def percentage(numerator: float, denominator: float) -> float:
    return 100.0 * numerator / denominator
~~~

At runtime, Python normally accepts any objects whose operations succeed. Annotations populate metadata and support static tools, documentation, IDEs, and frameworks; the interpreter does not automatically reject a string before body entry.

Even a perfect runtime type check would not establish denominator nonzero, finiteness, units, or permitted range. Types eliminate some invalid states only when the type system and construction discipline can express them. Chapter 12 treats static analysis formally.

### 8.12.5 Be liberal in what you accept is not universally safe

Implicit coercion can make interfaces convenient but ambiguous:

~~~python
def set_attempts(value: object) -> int:
    return int(value)
~~~

This admits strings, floats by truncation, Booleans, numeric objects, and custom conversion methods. The domain “positive exact retry count” likely needs narrower acceptance:

~~~python
def require_attempts(value: object) -> int:
    if isinstance(value, bool) or not isinstance(value, int):
        raise TypeError("attempts must be an integer")
    if value < 1:
        raise ValueError("attempts must be positive")
    return value
~~~

Permissive parsing is appropriate at a user-representation boundary when alternatives are specified. A core API benefits from canonical, predictable values. Silent coercion can turn mistakes into plausible but wrong computations.

### 8.12.6 Validate relationships, not only individual parameters

~~~python
def extract(values: list[int], start: int, stop: int) -> list[int]:
    ...
~~~

Checking that all three arguments have acceptable types does not prove <code>0 &lt;= start &lt;= stop &lt;= len(values)</code>. Many contracts are relational:

- lower bound does not exceed upper bound;
- matrix dimensions agree;
- identifiers are unique across a batch;
- timestamp intervals do not overlap;
- requested amount does not exceed balance;
- two collections use the same normalization policy.

Container-level validation is irreducible to per-element type checking.

### 8.12.7 Error taxonomy communicates responsibility

Python convention often uses:

- <code>TypeError</code> for an object of an inappropriate kind or unsupported operation;
- <code>ValueError</code> for an object of an admitted kind whose value violates the operation’s domain;
- domain-specific exception types for stable application categories;
- <code>KeyError</code>/<code>IndexError</code> for missing mapping/sequence selections under those protocols.

These are conventions, not a mechanical theorem. A public API should choose exceptions callers can handle meaningfully. Wrapping every failure in one generic error destroys distinctions; leaking every low-level exception couples clients to implementation.

Exception messages aid humans but should not be the only structured field. Sensitive input should not be copied indiscriminately into diagnostics.

### 8.12.8 Assertions are internal consistency checks

An assertion states a condition believed necessarily true if program logic and trusted preconditions hold:

~~~python
def midpoint(lower: int, upper: int) -> int:
    if lower > upper:
        raise ValueError("invalid interval")
    result = lower + (upper - lower) // 2
    assert lower <= result <= upper
    return result
~~~

The public invalid interval receives a stable explicit exception. The assertion checks a derived programmer invariant. Since assertions can be disabled, they must not perform essential validation, mutation, authorization, or I/O.

Postcondition assertions can be valuable during development but may cost as much as the computation. Keep expensive invariant checkers available for tests/debug builds rather than silently changing production complexity.

### 8.12.9 Defensive copies need threat and ownership models

Copying every input does not automatically make a function safe. Shallow copies preserve nested aliases; deep copies may invoke user hooks, duplicate identity-sensitive resources, or consume excessive memory. Immutable conversion can lose order/multiplicity or fail on unhashable elements.

Decide:

- whether the caller may mutate during or after the call;
- whether the callee retains data;
- whether values are trusted built-ins or arbitrary user objects;
- whether a snapshot, live view, or ownership transfer is intended;
- which depth must be stable;
- what cost/denial-of-service bounds apply.

The cheapest safe contract is often to construct a validated immutable domain value at the boundary and share it thereafter.

### 8.12.10 Determinism through explicit environmental dependencies

~~~python
from datetime import datetime


def expired(deadline: datetime) -> bool:
    return datetime.now(deadline.tzinfo) >= deadline
~~~

This function hides clock access. Injecting current time makes the core deterministic:

~~~python
def expired_at(deadline: datetime, current: datetime) -> bool:
    return current >= deadline
~~~

An outer boundary reads the clock once and passes the value to all related calculations, creating a coherent snapshot. Similar dependencies include randomness, environment configuration, locale, filesystem, and network clients.

Injection is not automatically object-oriented or framework-based. An explicit value or callable parameter often suffices. The objective is to make the behavioural input visible and controllable.

### 8.12.11 Re-entrancy and callback contracts

A function is **re-entrant** if it can be safely invoked again before a prior invocation completes, possibly through a callback or signal-like path. Local-only pure functions are commonly re-entrant; functions mutating module scratch buffers or holding non-reentrant locks may not be.

~~~python
_scratch: list[str] = []


def render_non_reentrant(parts: list[str]) -> str:
    _scratch.clear()
    for part in parts:
        _scratch.append(part.upper())
    return "".join(_scratch)
~~~

If <code>part.upper()</code> were a user callback that re-entered this function, it could clear outer state. Using a local list creates per-frame state and supports overlapping calls better:

~~~python
def render(parts: list[str]) -> str:
    scratch = [part.upper() for part in parts]
    return "".join(scratch)
~~~

Thread safety and re-entrancy overlap but are not identical. One thread can re-enter via callbacks; multiple threads can access non-reentrant or re-entrant code concurrently under different shared state.

### 8.12.12 Complexity is part of some contracts

A function called on attacker-controlled input may require explicit limits even if its output is correct. Regular-expression backtracking, recursive nesting, hash collisions, enormous integers, decompression expansion, and output construction can exhaust resources.

A resource contract can state:

- maximum accepted byte/code-point/element count;
- asymptotic expected and worst-case work;
- bounded recursion depth;
- output size or pagination;
- timeout/cancellation response;
- external requests and retry limits;
- cache/queue growth.

Rejecting over-limit input is a semantic choice. Truncating silently produces a different result and can create security inconsistencies between validators and consumers.

### 8.12.13 Documentation is executable only through tests and tools

A docstring can state a contract but cannot enforce it. Tests should cover:

- valid equivalence classes and boundaries;
- each invalid precondition and exception category;
- aliasing and mutation observations;
- empty, singleton, maximum, and adversarial sizes;
- callback/effect order where public;
- deterministic environmental injection;
- performance claims with appropriate benchmarks;
- concurrency schedules or model checks where relevant.

Static annotations, runtime validators, assertions, and generated documentation each cover different fragments. Contract confidence comes from aligned mechanisms, not one format.

### Worked example 8.5D — Construct a trusted interval value

~~~python
from dataclasses import dataclass


@dataclass(frozen=True, slots=True)
class Interval:
    start: int
    stop: int

    def __post_init__(self) -> None:
        if isinstance(self.start, bool) or not isinstance(self.start, int):
            raise TypeError("start must be an integer")
        if isinstance(self.stop, bool) or not isinstance(self.stop, int):
            raise TypeError("stop must be an integer")
        if self.start > self.stop:
            raise ValueError("start exceeds stop")

    @property
    def length(self) -> int:
        return self.stop - self.start


def overlaps(left: Interval, right: Interval) -> bool:
    return left.start < right.stop and right.start < left.stop
~~~

Construction establishes exact integer components and the half-open invariant <code>start &lt;= stop</code>. The core <code>overlaps</code> need not revalidate those facts when it receives genuine Interval instances through controlled construction. Empty intervals have equal endpoints and overlap none under the strict formula.

The dataclass preview is formalized in Chapters 9 and 11. The contract pattern is current: turn related primitive arguments into one validated value so invalid relationships cannot travel freely through the core.

### Worked example 8.5E — Accumulate independent validation defects

~~~python
from dataclasses import dataclass


@dataclass(frozen=True)
class Defect:
    field: str
    code: str
    message: str


def validate_registration(record: dict[str, object]) -> list[Defect]:
    defects: list[Defect] = []

    username = record.get("username")
    if not isinstance(username, str):
        defects.append(Defect("username", "type", "must be text"))
    elif not username:
        defects.append(Defect("username", "empty", "must not be empty"))

    age = record.get("age")
    if isinstance(age, bool) or not isinstance(age, int):
        defects.append(Defect("age", "type", "must be an integer"))
    elif not 0 <= age <= 150:
        defects.append(Defect("age", "range", "must be between 0 and 150"))

    return defects
~~~

Independent fields are checked even when another fails, producing a useful batch report. Within each field, type failure prevents operations requiring the expected type. Structured codes support callers without parsing prose. The function does not silently repair values and performs no registration effect. A later constructor should run only if the defect list is empty.

> **Common misconception — “Defensive programming means checking everything everywhere.”**  
> Effective defense assigns validation to trust and responsibility boundaries, then lets trusted cores rely on established invariants. Repeated inconsistent checks can weaken rather than strengthen a system.
