# 8.13 Decorators derived from first-class functions

A **decorator** is a callable that receives the object produced by a function or class definition and returns the object to bind under the definition’s name. Function decorator syntax:

```python
@decorator
def operation():
    ...
```

is approximately equivalent at definition time to:

```python
def operation():
    ...

operation = decorator(operation)
```

The decorator is evaluated, the function object is created, the decorator is called with it, and the name is bound to the returned object. The result need not be a function, though callable-preserving decorators ordinarily return a callable.

### Worked example 8.6 — Build a tracing decorator

```python
from collections.abc import Callable
from functools import wraps
from typing import Any, TypeVar


R = TypeVar("R")


def traced(function: Callable[..., R]) -> Callable[..., R]:
    @wraps(function)
    def wrapper(*args: Any, **kwargs: Any) -> R:
        print(f"enter {function.__name__}")
        try:
            return function(*args, **kwargs)
        finally:
            print(f"leave {function.__name__}")

    return wrapper


@traced
def add(left: int, right: int) -> int:
    return left + right


print(add(2, 3))
```

Definition trace:

1. `traced` is already bound to a decorator function.
2. The `def add` statement creates the original `add` function.
3. `traced(original_add)` is called.
4. Inside `traced`, `wrapper` closes over parameter binding `function`.
5. `wraps(function)` copies selected metadata and establishes a `__wrapped__` link for introspection.
6. `traced` returns `wrapper`.
7. Module name `add` is bound to `wrapper`, not directly to the original function.

Call trace:

1. `add(2, 3)` calls `wrapper`.
2. It prints entry, forwards arguments to the closed-over original function, obtains 5, prints departure in `finally`, and returns 5.

The `finally` ensures departure is reported for ordinary return and propagated exception. It does not guarantee execution after abrupt process termination.

`Callable[..., R]` preserves only the return type and loses the precise parameter signature in static analysis. Production typing can use `ParamSpec` to carry that signature:

```python
from collections.abc import Callable
from functools import wraps
from typing import ParamSpec, TypeVar

P = ParamSpec("P")
R = TypeVar("R")


def traced(function: Callable[P, R]) -> Callable[P, R]:
    @wraps(function)
    def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        print(f"enter {function.__name__}")
        return function(*args, **kwargs)
    return wrapper
```

Typing syntax is explained in Chapter 12; here it demonstrates that transparent wrapping has runtime and static-interface obligations.

### 8.13.1 Decoration is rebinding at definition execution

For one decorator:

\[
name = decorator(function\_object).
\]

The original function object can remain reachable through a wrapper closure, <code>__wrapped__</code>, a registry, or another alias. The source-level name ordinarily refers to the replacement.

~~~python
def identity_decorator(function):
    print("decorate", function.__name__)
    return function


@identity_decorator
def operation() -> int:
    return 1
~~~

The message appears when the definition statement executes, not when <code>operation()</code> is later called. Importing a module therefore runs top-level decorator logic.

### 8.13.2 Decorator expressions evaluate before function creation is finished and applied

When decorator syntax contains expressions, Python evaluates those expressions in the order specified by the language before applying the resulting decorators after function creation. Stacked application is bottom-up:

~~~python
@outer(argument())
@inner
def target():
    ...
~~~

Conceptually, the decorator expressions <code>outer(argument())</code> and <code>inner</code> are evaluated in source order, the function is created, then <code>inner</code> is called on it, then the result is passed to the previously obtained outer decorator. Evaluation order and application order are different axes.

Effects during decorator-expression evaluation can occur even if later function creation or decoration fails. Decorators used at import time should avoid surprising external mutations or slow remote work.

### 8.13.3 A wrapper defines a new call contract

Even a forwarding wrapper can change:

- accepted call signature;
- return value or type;
- exceptions and traceback frames;
- effect ordering;
- synchronization and re-entrancy;
- timing and resource use;
- descriptor binding when used as a method;
- coroutine/generator identity and suspension behaviour;
- metadata and introspection;
- pickling/import identity.

“Transparent decorator” is an aspiration requiring proof along relevant dimensions. <code>functools.wraps</code> copies metadata; it cannot make changed semantics disappear.

### 8.13.4 Argument forwarding must preserve both channels

~~~python
from functools import wraps
from typing import ParamSpec, TypeVar
from collections.abc import Callable

P = ParamSpec("P")
R = TypeVar("R")


def logged(function: Callable[P, R]) -> Callable[P, R]:
    @wraps(function)
    def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        print(function.__qualname__)
        return function(*args, **kwargs)
    return wrapper
~~~

Omitting <code>**kwargs</code>, changing positional order, or constructing a new mapping with different duplicate handling can reject calls the original accepted. <code>ParamSpec</code> lets a type checker relate wrapper and wrapped signatures, while <code>wraps</code> establishes runtime metadata linkage. Neither verifies semantic forwarding.

### 8.13.5 wraps and update_wrapper

<code>functools.wraps(original)</code> is a decorator factory built on <code>update_wrapper</code>. It copies selected attributes such as <code>__module__</code>, <code>__name__</code>, <code>__qualname__</code>, <code>__doc__</code>, and <code>__annotations__</code>, updates the wrapper attribute dictionary by default, and sets <code>__wrapped__</code>.

Tools such as <code>inspect.signature</code> can follow <code>__wrapped__</code> to report the original signature. The actual wrapper may still accept <code>*args, **kwargs</code> at runtime and impose additional restrictions. Copied annotations describe the advertised interface, not an enforcement mechanism.

### 8.13.6 Decorated recursion resolves the rebound global name

~~~python
def traced(function):
    @wraps(function)
    def wrapper(*args, **kwargs):
        print("call", args)
        return function(*args, **kwargs)
    return wrapper


@traced
def factorial(number: int) -> int:
    if number == 0:
        return 1
    return number * factorial(number - 1)
~~~

Inside the original body, global name <code>factorial</code> is resolved at call time and now refers to the wrapper. Therefore every recursive step passes through tracing. The wrapper closes over the original function for its direct call, but the original’s recursive name lookup reaches the decorated binding.

If recursion instead used a private undecorated helper, only the public outer call would be traced. Decorator behaviour depends on name topology.

### 8.13.7 Methods require descriptor-compatible replacements

A normal function stored on a class becomes a bound method when retrieved through an instance. A decorator returning another normal function preserves this common binding behaviour. A decorator returning an arbitrary callable instance may not bind a receiver unless it implements the descriptor protocol.

~~~python
def wrapper_decorator(function):
    @wraps(function)
    def wrapper(*args, **kwargs):
        return function(*args, **kwargs)
    return wrapper
~~~

Applied to a method, <code>args[0]</code> receives the instance through normal function descriptor binding. Chapter 9 explains <code>__get__</code>. Decorator authors should test free functions, instance methods, class methods, and static methods only under supported stacking orders.

### 8.13.8 Ordering with classmethod and staticmethod matters

<code>classmethod</code> and <code>staticmethod</code> are decorator-like descriptor constructors. The order in which another decorator sees a raw function versus a descriptor object affects behaviour:

~~~python
class Example:
    @classmethod
    @logged
    def build(cls, value: int):
        return cls()
~~~

Here <code>logged</code> wraps the function first; <code>classmethod</code> then makes the wrapper receive the class. Reversing the order gives <code>logged</code> a classmethod descriptor rather than a plain function, which a decorator may not support as expected. Stacking is functional composition, so types at every intermediate stage must align.

### 8.13.9 Synchronous wrappers can destroy coroutine identity

An <code>async def</code> function returns a coroutine object when called. A synchronous wrapper that simply returns that object may still be awaitable but is no longer recognized as a coroutine function by introspection:

~~~python
def wrong_async_trace(function):
    @wraps(function)
    def wrapper(*args, **kwargs):
        print("creating coroutine")
        return function(*args, **kwargs)
    return wrapper
~~~

It logs coroutine creation, not completion or exception during awaited execution. A semantic async wrapper must itself be async and await:

~~~python
def async_trace(function):
    @wraps(function)
    async def wrapper(*args, **kwargs):
        print("enter")
        try:
            return await function(*args, **kwargs)
        finally:
            print("leave")
    return wrapper
~~~

Cancellation flows through the await and finally block. Logging, cleanup, and cancellation exceptions still need a policy. A universal decorator that supports sync functions, coroutine functions, generators, and async generators must detect and preserve four distinct protocols.

### 8.13.10 Generator wrappers must preserve laziness deliberately

~~~python
def eager_collect(function):
    @wraps(function)
    def wrapper(*args, **kwargs):
        return list(function(*args, **kwargs))
    return wrapper
~~~

Applied to a generator function, this changes the return from iterator to list, consumes the entire source at call time, requires finiteness, shifts exception timing, increases memory, and discards close/send/throw semantics.

A generator-preserving wrapper can use <code>yield from</code>:

~~~python
def trace_generator(function):
    @wraps(function)
    def wrapper(*args, **kwargs):
        print("iteration starts")
        try:
            return_value = yield from function(*args, **kwargs)
            return return_value
        finally:
            print("iteration ends")
    return wrapper
~~~

The messages occur when iteration starts/ends, not merely when the generator object is created. Correct delegation must account for <code>send</code>, <code>throw</code>, <code>close</code>, and return values, which <code>yield from</code> supplies.

### 8.13.11 Registration decorators may return the original

A decorator can perform definition-time registration and return the same function:

~~~python
from collections.abc import Callable

COMMANDS: dict[str, Callable[..., object]] = {}


def command(name: str):
    def register(function):
        if name in COMMANDS:
            raise ValueError(f"duplicate command: {name!r}")
        COMMANDS[name] = function
        return function
    return register


@command("status")
def status() -> str:
    return "ready"
~~~

Call semantics remain those of the original function, while import/definition changes the registry. The registry retains the function and can affect plugin ordering, reload behaviour, duplicates, and test isolation. Registration is an effect deserving lifecycle design.

An allowlisted registry is safer than dynamic global lookup, but only code authorized to register should execute at the boundary.

### 8.13.12 A decorator may return a non-callable

~~~python
def call_now(function):
    return function()


@call_now
def answer() -> int:
    return 42
~~~

After definition, <code>answer</code> is bound to integer 42, not a function. The syntax permits this because a decorator returns the object to bind. Most function decorators preserve callability by convention, but reasoning must follow the actual transformation.

### 8.13.13 Exception translation in decorators can erase meaning

~~~python
def hide_failures(function):
    @wraps(function)
    def wrapper(*args, **kwargs):
        try:
            return function(*args, **kwargs)
        except Exception:
            return None
    return wrapper
~~~

This collapses every ordinary exception into <code>None</code>, making absent result indistinguishable from legitimate <code>None</code>, suppressing programming defects, and losing traceback context. A boundary decorator may translate a narrow domain exception into a protocol response, but broad conversion belongs at a layer that owns all covered failures and preserves diagnostics securely.

### 8.13.14 Timing decorators need clocks and reporting policy

A credible timing decorator uses a monotonic performance clock, reports even on exception under a chosen policy, and does not claim CPU time when measuring elapsed wall time:

~~~python
from time import perf_counter_ns


def timed(report):
    def decorate(function):
        @wraps(function)
        def wrapper(*args, **kwargs):
            started = perf_counter_ns()
            outcome = "returned"
            try:
                return function(*args, **kwargs)
            except BaseException:
                outcome = "raised"
                raise
            finally:
                elapsed = perf_counter_ns() - started
                report(function.__qualname__, outcome, elapsed)
        return wrapper
    return decorate
~~~

The reporter itself can raise and replace the original result/exception in <code>finally</code>. A robust observability system should isolate or chain reporting failure according to policy. Decoration adds overhead, and one invocation does not form a benchmark distribution.

### 8.13.15 Authorization decorators require call-time context

An authorization decorator must check the current authenticated principal and requested resource/action at call time, not at module import. Caching authorization decisions requires policy version, principal state, resource, revocation, and time in the key. A decorative name such as <code>@admin_required</code> is not security evidence unless every path to the underlying capability goes through it.

The wrapped function may also be called through <code>__wrapped__</code> or another original alias within trusted code. Security boundaries must be enforced at an architecture layer that untrusted callers cannot bypass merely by object access.

### Worked example 8.6A — A result-checking decorator

~~~python
from collections.abc import Callable
from functools import wraps
from typing import ParamSpec, TypeVar

P = ParamSpec("P")
R = TypeVar("R")


def ensures(
    predicate: Callable[[R], bool],
    *,
    message: str,
) -> Callable[[Callable[P, R]], Callable[P, R]]:
    def decorate(function: Callable[P, R]) -> Callable[P, R]:
        @wraps(function)
        def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
            result = function(*args, **kwargs)
            if not predicate(result):
                raise RuntimeError(message)
            return result
        return wrapper
    return decorate


@ensures(lambda value: value >= 0, message="result must be non-negative")
def distance(left: int, right: int) -> int:
    return abs(left - right)
~~~

The factory retains the predicate and message. The decorator retains the original function. The wrapper forwards the call, then checks the normal result. If the original raises, the predicate is not evaluated. If the predicate raises, that exception propagates; if it returns false, the wrapper raises a contract-failure exception after the original’s effects have already occurred.

Therefore this is suitable for checking a pure result or detecting programmer defects, not rolling back an effectful operation. Calling an arbitrary predicate also adds callback and re-entrancy concerns.

> **Common misconception — “functools.wraps makes a decorator transparent.”**  
> It preserves selected metadata and an unwrapping link. Call protocol, effects, exceptions, timing, coroutine/generator behaviour, and descriptor semantics still require explicit preservation.
