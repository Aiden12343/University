# 8.14 Decorator factories and timing

A decorator needing configuration is ordinarily produced by a **decorator factory**:

```python
from collections.abc import Callable
from functools import wraps
from typing import ParamSpec, TypeVar

P = ParamSpec("P")
R = TypeVar("R")


def repeat(times: int):
    if times < 1:
        raise ValueError("times must be positive")

    def decorate(function: Callable[P, R]) -> Callable[P, R]:
        @wraps(function)
        def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
            result: R
            for _ in range(times):
                result = function(*args, **kwargs)
            return result
        return wrapper

    return decorate
```

Use:

```python
@repeat(3)
def announce(message: str) -> None:
    print(message)
```

Timing:

1. `repeat(3)` runs when the decorated definition executes, validates 3, and returns `decorate` closing over `times`.
2. The original `announce` function is created.
3. `decorate(original_announce)` returns `wrapper`.
4. Name `announce` binds to `wrapper`.
5. Each later call invokes the original three times.

The decorator changes semantics: effects occur three times and only the final return is exposed. Applying it to a non-idempotent operation, resource acquisition, or expensive function may be inappropriate. Decorators are program transformations with contracts, not visual labels.

Stacked decorators apply from the function outward:

```python
@outer
@inner
def function():
    ...
```

binds approximately as `function = outer(inner(function))`. Calls then enter whatever wrapper `outer` returns before reaching the inner result.

### 8.14.1 Three phases must be separated

A configured decorator has at least three temporal phases:

1. **factory evaluation:** configuration arguments are evaluated and the factory is called;
2. **decoration:** the returned decorator receives the newly created function and returns a replacement;
3. **invocation:** the replacement is called zero or more times later.

State created in each phase has a different sharing pattern. Factory-local state is typically shared by every call to one decorated function. State created inside the decorator but outside the wrapper is also per decoration. State created inside the wrapper is per invocation.

~~~python
def labelled(label: str):                 # factory phase
    factory_state: list[str] = []

    def decorate(function):               # decoration phase
        decorated_state: list[int] = []

        @wraps(function)
        def wrapper(*args, **kwargs):      # invocation phase
            local_state: list[object] = []
            ...

        return wrapper
    return decorate
~~~

Understanding these lifetimes prevents accidental cross-call state and memory retention.

### 8.14.2 Configuration arguments are ordinary expressions

~~~python
@retry(load_policy())
def operation():
    ...
~~~

<code>load_policy()</code> runs when the definition executes. If it reads a file or environment variable, its result is captured then. Later configuration changes do not affect the produced wrapper unless the wrapper performs a new lookup. Import can fail before <code>operation</code> is bound.

For reloadable configuration, pass a provider callable or resolve policy at invocation time. For stable deployment configuration, definition-time capture can be desirable. The decorator syntax does not choose.

### 8.14.3 Validate configuration in the factory

The <code>repeat</code> factory rejects non-positive counts before any decorated function can be called. This makes an invalid program/module fail at definition/import rather than on a rare runtime path.

The existing check <code>times &lt; 1</code> still permits values whose comparison works but whose <code>range</code> use later fails. A strict boundary might be:

~~~python
def repeat(times: int):
    if isinstance(times, bool) or not isinstance(times, int):
        raise TypeError("times must be an integer")
    if times < 1:
        raise ValueError("times must be positive")
    ...
~~~

Validate once at the phase owning configuration. Per-call validation would duplicate work and delay discovery.

### 8.14.4 One factory result can decorate several functions

~~~python
trace_io = traced_to(report_sink)


@trace_io
def read_record():
    ...


@trace_io
def write_record():
    ...
~~~

Both decoration calls share whatever state is captured by <code>trace_io</code> itself. If the factory returns one decorator with a shared counter or lock, calls to both functions interact. If state is allocated inside <code>decorate</code>, each function receives its own state. Placement defines sharing topology.

### 8.14.5 Stateful decorators need reset and concurrency contracts

~~~python
def count_calls(function):
    calls = 0

    @wraps(function)
    def wrapper(*args, **kwargs):
        nonlocal calls
        calls += 1
        return function(*args, **kwargs)

    return wrapper
~~~

This count is hidden, cannot be queried/reset through a stated API, and can lose increments under concurrent calls. An explicit callable class or wrapper attributes can expose lifecycle, but mutable attributes remain shared and need synchronization.

Decide whether attempted calls, successful calls, completed calls, or underlying invocations are counted. If argument binding fails at the wrapper signature, the body may not count. If the original raises, a pre-call increment still counts the attempt. Metrics vocabulary must match placement.

### 8.14.6 Stacking order composes policies

Let <code>A</code> and <code>B</code> be wrapper decorators. For

~~~python
@A
@B
def operation():
    ...
~~~

the bound object is \(A(B(original))\). A call enters A’s wrapper, then B’s, then the original; returns unwind through B then A.

Order can change correctness:

- cache outside authorization may return protected data without rerunning current authorization;
- authorization outside cache checks every request before cache access;
- retry outside timing measures all attempts together;
- timing outside retry differs from timing each underlying attempt;
- transaction outside retry may keep one transaction across attempts;
- retry outside transaction can create one transaction per attempt.

There is no universal preferred order. Draw the call nesting and state which policy owns each attempt, result, and failure.

### 8.14.7 Retry is a semantic protocol, not a loop decorator

A retry decorator must classify transient failures, cap attempts and elapsed time, back off, add jitter, respond to cancellation, and ensure the operation is idempotent or protected by an idempotency protocol. Retrying an uncertain payment or message publication can duplicate effects.

It must also decide whether to preserve the last exception, aggregate attempts, or raise a retry-specific error with causes. Sleeping in async code must use an async clock/suspension, not block the event loop. A generic decorator cannot infer these domain facts from an exception class alone.

### 8.14.8 Caching decorators bind state to function identity

~~~python
from functools import lru_cache


@lru_cache(maxsize=256)
def parse_schema(text: str):
    ...
~~~

The factory creates a bounded cache wrapper during definition. Cache keys derive from bound call arguments according to the decorator implementation, and returned object references are retained. Equal logical calls written with different argument forms may or may not share keys under a specific caching contract; normalize at an explicit layer when semantic equivalence matters.

The wrapper exposes management such as <code>cache_info</code> and <code>cache_clear</code>. Clearing affects all callers sharing that decorated function object. Reloading a module can create a new function/cache while old references keep the prior one alive.

### 8.14.9 Class-based decorator objects make state explicit

This previews the object model:

~~~python
from typing import Generic, ParamSpec, TypeVar

P = ParamSpec("P")
R = TypeVar("R")


class CallCounter(Generic[P, R]):
    def __init__(self, function):
        self.function = function
        self.calls = 0

    def __call__(self, *args: P.args, **kwargs: P.kwargs) -> R:
        self.calls += 1
        return self.function(*args, **kwargs)
~~~

An instance exposes count and underlying function plainly. Applied to a method, however, this object needs descriptor support to bind instances correctly. A closure-based function wrapper gets ordinary function descriptor behaviour automatically. Explicit state is one benefit; protocol obligations increase.

### 8.14.10 Parameter-preserving typing has limits

<code>ParamSpec</code> represents a callable’s parameter specification and allows forwarding wrappers to preserve it for static checkers. <code>Concatenate</code> can model adding/removing a leading context parameter in selected cases. Runtime decorators can perform transformations more dynamic than the static type system expresses.

A typed decorator that changes a sync function into an async one, catches exceptions into a result union, or adds supported keyword options must state that changed signature accurately. Copying original annotations with <code>wraps</code> can become misleading if the wrapper changes the return protocol.

### 8.14.11 Decoration can be conditional without syntax magic

Because decorators are callables, a factory can return identity or a wrapper based on configuration:

~~~python
def maybe_trace(enabled: bool):
    def decorate(function):
        if not enabled:
            return function

        @wraps(function)
        def wrapper(*args, **kwargs):
            print(function.__qualname__)
            return function(*args, **kwargs)
        return wrapper
    return decorate
~~~

The choice occurs at decoration time. Toggling <code>enabled</code> later has no effect. A call-time flag would impose a branch and dynamic configuration lookup on every invocation. Again, timing is contract.

### Worked example 8.6B — Bounded retry with injected delay

This pedagogical synchronous implementation deliberately supports only explicitly supplied retryable exception classes and assumes the operation is safe to retry:

~~~python
from collections.abc import Callable
from functools import wraps
from typing import ParamSpec, TypeVar

P = ParamSpec("P")
R = TypeVar("R")


def retrying(
    *,
    attempts: int,
    retry_on: tuple[type[Exception], ...],
    delay: Callable[[int], None],
) -> Callable[[Callable[P, R]], Callable[P, R]]:
    if isinstance(attempts, bool) or not isinstance(attempts, int):
        raise TypeError("attempts must be an integer")
    if attempts < 1:
        raise ValueError("attempts must be positive")
    if not retry_on:
        raise ValueError("retry_on must be non-empty")

    def decorate(function: Callable[P, R]) -> Callable[P, R]:
        @wraps(function)
        def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
            for attempt in range(1, attempts + 1):
                try:
                    return function(*args, **kwargs)
                except retry_on:
                    if attempt == attempts:
                        raise
                    delay(attempt)

            raise AssertionError("positive attempt loop must return or raise")
        return wrapper
    return decorate
~~~

Factory validation happens once. The wrapper calls the original at most <code>attempts</code> times. Only named ordinary exception subclasses are caught; control exceptions propagate. The last retryable exception is re-raised with its traceback. Delay occurs only between attempts and receives the completed attempt number so a caller can implement policy.

The impossible-looking final assertion documents a control-flow proof for static/runtime defense: with a positive finite range, each iteration either returns, retries, or re-raises on the final attempt. The implementation omits deadlines, jitter, logging, cancellation abstraction, async support, and idempotency enforcement; those omissions must prevent marketing it as a universal retry facility.

### Worked example 8.6C — Trace stacked decorator order

~~~python
def mark(label: str):
    print(f"factory {label}")

    def decorate(function):
        print(f"decorate {label}")

        @wraps(function)
        def wrapper(*args, **kwargs):
            print(f"enter {label}")
            try:
                return function(*args, **kwargs)
            finally:
                print(f"leave {label}")
        return wrapper
    return decorate


@mark("outer")
@mark("inner")
def work() -> None:
    print("body")
~~~

Definition output distinguishes expression evaluation from application:

~~~text
factory outer
factory inner
decorate inner
decorate outer
~~~

Call output is nesting:

~~~text
enter outer
enter inner
body
leave inner
leave outer
~~~

The trace is a reusable method for reasoning about caching, authorization, transactions, retries, and instrumentation without guessing from vertical syntax.

> **Common misconception — “Decorator factories run when the decorated function is called.”**  
> The factory and decoration normally run when the definition executes. Only the returned wrapper’s body runs per later call.
