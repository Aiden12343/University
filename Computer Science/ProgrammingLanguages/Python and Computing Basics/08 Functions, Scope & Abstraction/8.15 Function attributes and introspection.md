# 8.15 Function attributes and introspection

Functions expose attributes such as `__name__`, `__doc__`, `__annotations__`, `__defaults__`, `__kwdefaults__`, `__module__`, `__closure__`, and `__code__` in CPython and the documented data model. Some are language-level conventions; code object internals are implementation-facing.

```python
def power(base: int, exponent: int = 2) -> int:
    """Raise base to a non-negative integer exponent."""
    if exponent < 0:
        raise ValueError("exponent must be non-negative")
    return base**exponent


print(power.__name__)
print(power.__defaults__)
print(power.__annotations__)
```

`__defaults__` demonstrates that positional parameter defaults are retained by the function object. Mutating a default through this reference would change later calls and should be treated as deliberate metaprogramming, not normal API use.

**Introspection** is examination of program objects and runtime structure by the program itself. It supports debuggers, documentation tools, dependency injection, serializers, and frameworks, but can couple code to implementation details. Inspect only attributes whose contract is appropriate to the portability required.

### 8.15.1 Metadata has provenance and mutability

Function attributes describe a mixture of source intent, compilation, defining environment, and later decoration/mutation. For example:

- <code>__name__</code> is the simple function name assigned at creation or later changed;
- <code>__qualname__</code> records a dotted lexical qualification useful for diagnostics;
- <code>__module__</code> names the defining module by convention;
- <code>__doc__</code> holds the docstring or <code>None</code>;
- <code>__annotations__</code> holds annotation metadata under the active evaluation regime;
- <code>__dict__</code> stores arbitrary assigned attributes for ordinary Python functions;
- <code>__wrapped__</code>, when established by a wrapper, links to another callable by convention.

Most are writable. A function can claim a different name or module; metadata is not cryptographic provenance. Frameworks should validate what they rely on and avoid granting authority merely because an attribute says “trusted.”

### 8.15.2 Qualified names are diagnostic, not universal locators

~~~python
def outer():
    def inner():
        return 1
    return inner


function = outer()
print(function.__qualname__)
~~~

The qualified name includes lexical nesting such as <code>outer.&lt;locals&gt;.inner</code>. There may be no import path that retrieves this dynamically created function. Lambdas and repeated definitions can share similar names while being distinct objects. Serialization systems cannot assume every callable is globally importable from its metadata.

### 8.15.3 Signatures are structured objects

~~~python
from inspect import Parameter, signature


def sample(a: int, /, b: str = "x", *, c: float) -> bool:
    return bool(a and b and c)


sig = signature(sample)
for name, parameter in sig.parameters.items():
    print(name, parameter.kind, parameter.default, parameter.annotation)
print(sig.return_annotation)
~~~

Missing defaults/annotations use sentinel objects such as <code>Parameter.empty</code>, not <code>None</code>. Parameter order is significant. Signature binding can validate call shape, apply defaults, and support adapters.

Built-ins and extension callables may expose signatures through implementation metadata or may not. Decorators can supply <code>__signature__</code> to override introspection. The reported signature is an interface claim that may differ from actual low-level acceptance if metadata is wrong.

### 8.15.4 Annotations may be values, strings, or lazily mediated

Python’s annotation evaluation rules have evolved. Depending on version, future imports, and newer annotation scopes, <code>__annotations__</code> may contain evaluated objects or deferred/string-like forms, and resolving them can execute name lookups or code through supported mechanisms.

Use <code>typing.get_type_hints</code> when evaluated hints are required and supply appropriate namespaces, understanding that resolution can import/evaluate references and is unsafe on untrusted annotation content. Do not assume printing <code>__annotations__</code> gives canonical type objects.

Annotations are metadata, not serialization schemas or validation by themselves. Chapter 12 treats forward references, generics, protocols, type parameters, and version-specific evaluation.

### 8.15.5 Defaults expose retained references

~~~python
def append(value: int, target: list[int] = []) -> list[int]:
    target.append(value)
    return target


default_list = append.__defaults__[0]
default_list.clear()
~~~

This mutation changes later omitted calls. Introspection has crossed into program mutation because the defaults tuple exposes the same retained object. Diagnostic tools should avoid altering inspected values. Security-sensitive code should not expose mutable internals merely because they are easy to reach through Python’s reflective model.

### 8.15.6 Code objects describe executable structure

The <code>__code__</code> attribute of a Python function refers to a code object containing bytecode and metadata such as constants, names, variable names, source line information, argument counts, and flags. Code objects are immutable data-model objects, while function objects supply environment and defaults.

~~~python
def add(left: int, right: int) -> int:
    return left + right


print(add.__code__.co_varnames)
print(add.__code__.co_argcount)
~~~

Exact fields and bytecode meanings are CPython/version-facing. Use the <code>dis</code> module rather than manually parsing bytecode, and never derive language semantics solely from one version’s instruction sequence. Chapter 15 develops this capstone.

### 8.15.7 Closure introspection follows free-variable order

<code>function.__closure__</code> is <code>None</code> when no closure cells are required, or a tuple of cells corresponding to free-variable names in code metadata.

~~~python
def make_affine(scale: int, offset: int):
    return lambda value: scale * value + offset


operation = make_affine(3, 2)
names = operation.__code__.co_freevars
values = [cell.cell_contents for cell in operation.__closure__ or ()]
print(dict(zip(names, values, strict=True)))
~~~

This is valuable for learning and debugging. Building application logic that depends on private closure variable names violates encapsulation and makes refactoring break clients. Expose state through an explicit API when clients need it.

### 8.15.8 unwrap traverses a convention, not an authority chain

<code>inspect.unwrap</code> follows <code>__wrapped__</code> links until reaching an object without one or a stopping condition. This recovers original signatures or annotations from well-behaved decorators.

Any object can assign a misleading <code>__wrapped__</code>. Unwrapping can bypass wrappers implementing authorization, locking, validation, or caching if code then calls the result. Treat unwrapping as trusted introspection, not a routine escape hatch around semantic layers.

### 8.15.9 Source retrieval is contingent

<code>inspect.getsource</code> can retrieve source when loaders, files, line caches, and metadata make it available. It can fail for interactive definitions, dynamically generated code, built-ins, stripped deployments, or changed source files. The retrieved text might no longer correspond exactly to the running code object.

Runtime correctness must not depend on source retrieval unless the deployment explicitly guarantees it. Package source, version identifiers, hashes, debug symbols, and reproducible builds provide stronger provenance mechanisms.

### 8.15.10 inspect versus execution

Some inspection is passive; other forms invoke dynamic protocols. <code>getattr</code> can execute descriptors or <code>__getattr__</code>. Evaluating annotations can run code. Calling <code>repr</code> on values can execute user methods. Iterating a registry can invoke custom iteration.

The <code>inspect.getattr_static</code> function can examine attributes without normal dynamic descriptor resolution in selected diagnostics, but returns raw descriptor objects and has its own limitations. Inspection tools must have a threat model when examining untrusted objects.

### 8.15.11 Introspection supports adapters but can hide coupling

A framework may inspect a function’s parameters to inject database sessions, HTTP request objects, or configuration. This reduces explicit wiring at call sites but makes parameter names/annotations part of a framework protocol and moves errors to runtime registration.

An explicit higher-order factory or object constructor often gives stronger static visibility. Introspection is justified when it meaningfully improves an extensible interface and validation produces clear startup errors. It is not free abstraction.

### 8.15.12 Docstrings and help are one documentation layer

A string literal as the first statement in a function body becomes its docstring:

~~~python
def area(width: float, height: float) -> float:
    """Return rectangular area for non-negative finite dimensions."""
    ...
~~~

Docstrings should state semantics not obvious from the signature: units, mutation, exception policy, ordering, complexity, and examples. They can drift from implementation. Documentation tests, static analysis, and contract tests reduce drift but do not eliminate review.

Optimized execution can omit docstrings under certain interpreter flags, so they should not carry essential runtime configuration.

### Worked example 8.7A — Validate plugin call shape without invoking it

Suppose a trusted plugin must expose a handler accepting exactly one positional event and one keyword-only context parameter. Signature inspection can reject incompatible plugins at registration:

~~~python
from inspect import Parameter, signature
from collections.abc import Callable


def validate_handler(handler: Callable[..., object]) -> None:
    parameters = list(signature(handler).parameters.values())

    if len(parameters) != 2:
        raise TypeError("handler must declare exactly two parameters")

    event, context = parameters
    if event.kind not in (
        Parameter.POSITIONAL_ONLY,
        Parameter.POSITIONAL_OR_KEYWORD,
    ):
        raise TypeError("event must accept a positional argument")

    if context.kind is not Parameter.KEYWORD_ONLY:
        raise TypeError("context must be keyword-only")
    if context.name != "context":
        raise TypeError("keyword-only parameter must be named context")
~~~

This validates declared shape, not behaviour. The handler can still raise, block, mutate the event, return an invalid value, or advertise a false custom signature. Registration operates within a trusted plugin boundary; arbitrary untrusted Python plugins already possess code-execution authority.

The rigid “exactly two” rule rejects handlers with compatible variadic collectors or optional metadata, intentionally making the protocol narrow. An extensible system might instead test whether a representative bind succeeds, but then must define how extra required parameters are detected.

> **Common misconception — “Introspection reveals objective truth about a callable.”**  
> It reveals metadata and runtime structures that may be mutable, incomplete, decorated, unavailable, or deliberately customized. Use only the guarantees appropriate to the source and interface.
