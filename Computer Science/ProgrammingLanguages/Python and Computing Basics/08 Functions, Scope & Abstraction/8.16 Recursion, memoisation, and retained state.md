# 8.16 Recursion, memoisation, and retained state

Recursive algorithms can repeat identical subproblems. **Memoisation** retains results keyed by arguments so later calls can reuse them.

```python
from functools import cache


@cache
def fibonacci(number: int) -> int:
    if number < 0:
        raise ValueError("number must be non-negative")
    if number < 2:
        return number
    return fibonacci(number - 1) + fibonacci(number - 2)
```

Without caching, the naive recursion recomputes overlapping subproblems exponentially many times. With caching, each integer argument from 0 through (n) is computed once, giving linear numbers of distinct calls and retaining linear cached state.

The cache changes the function’s operational contract:

- arguments must be hashable;
- results and keys remain referenced by the cache;
- memory grows with distinct calls unless bounded or cleared;
- effects in the original body occur only on cache misses;
- concurrent calls follow the decorator’s documented synchronisation behaviour, which may still permit duplicate underlying computation.

Memoisation is correct when a result is determined by the cache key and relevant hidden state does not change. Caching a function that reads a changing file by path alone can return stale content.

### 8.16.1 Memoisation changes time by spending state

Let a deterministic function repeatedly solve subproblem \(x\). A memo table implements:

\[
M[x]=f(x).
\]

On a hit, lookup replaces recomputation; on a miss, the function computes and stores the result. This trades memory, hash/equality work, synchronization, and invalidation complexity for fewer body executions.

It improves asymptotic time only when overlapping subproblems exist. A recursion that visits every unique tree node once receives no repeated-computation benefit and merely stores every result.

### 8.16.2 Cache validity is a dependency equation

A cache key is valid only if it captures every input on which the result semantically depends. If

\[
r=f(a,b,E_t),
\]

where \(E_t\) is environment at time \(t\), caching solely by \((a,b)\) assumes the relevant environment is constant for the cache lifetime.

Hidden dependencies include:

- module configuration;
- current time and locale;
- file or database contents;
- network service state;
- mutable argument internals not represented stably by hash/equality;
- permissions and authenticated principal;
- random-number-generator state;
- library/model versions.

Either include a stable version/identity in the key, shorten/invalidate lifetime, or do not cache.

### 8.16.3 Arguments must form stable hash keys

<code>functools.cache</code> and <code>lru_cache</code> require hashable arguments because they use a mapping-like cache. A list cannot be passed directly as a cached key. Converting it to a tuple is correct only if ordered shallow value equality is the intended dependency and elements are hashable.

~~~python
from functools import cache


@cache
def polynomial(coefficients: tuple[int, ...], x: int) -> int:
    result = 0
    for coefficient in coefficients:
        result = result * x + coefficient
    return result
~~~

If a custom hashable argument changes equality-relevant state after caching, retrieval becomes invalid just as with dictionary keys. Immutable domain values are natural cache keys.

### 8.16.4 Call spelling and cache-key normalization

Caching decorators construct keys from call arguments under documented implementation rules. Calls such as <code>f(a=1, b=2)</code> and <code>f(b=2, a=1)</code> may occupy distinct entries even if normal function binding produces equal parameter values, depending on the cache contract/version. Positional and keyword spellings can likewise differ.

If semantic canonicalization matters, create a public binder that normalizes arguments and invokes a private cached function with one canonical positional representation:

~~~python
from functools import cache


@cache
def _area_cached(width: int, height: int) -> int:
    return width * height


def area(width: int, height: int) -> int:
    return _area_cached(width, height)
~~~

Every valid public call reaches the cache with the same positional order. This also keeps input validation outside the cache so invalid calls are not treated as values.

### 8.16.5 Unbounded cache and least-recently-used cache

<code>@cache</code> is an unbounded memo table: distinct keys remain until manual clearing or wrapper destruction. <code>@lru_cache(maxsize=N)</code> bounds entry count and evicts least-recently-used entries under its policy.

Entry count does not bound bytes. One cached result can be enormous, keys can retain graphs, and shared references complicate ownership. A bounded cache can still retain sensitive data longer than desired. Eviction by recency is only one workload policy and may thrash under scans larger than capacity.

<code>maxsize=None</code> makes <code>lru_cache</code> unbounded. <code>maxsize=0</code> effectively records statistics without result caching under ordinary implementation behaviour. Verify current documentation rather than infer edge semantics.

### 8.16.6 Cached mutable results are shared

~~~python
from functools import cache


@cache
def defaults_for(kind: str) -> dict[str, int]:
    return {"retries": 3}


first = defaults_for("network")
first["retries"] = 99
second = defaults_for("network")
print(second["retries"])      # 99
~~~

The cache returns the same stored object reference on a hit. This can be intentional shared state or a serious corruption. Prefer immutable results, return defensive copies, or cache a private immutable representation and construct caller-owned outputs.

Copying on every hit reduces the benefit and needs depth semantics. A cache contract must state result ownership.

### 8.16.7 Exceptions are ordinarily not cached by lru_cache

If the wrapped function raises, the ordinary <code>lru_cache</code> implementation does not store that exception as a successful result. A later identical call executes again. This is often desirable for transient failures and can create a repeated expensive failure storm for deterministic invalid input.

To cache a failure, convert it into an explicit immutable result variant under a deliberate policy. Retaining exception objects directly can retain tracebacks and frames. Failure caching also needs expiry/invalidation when conditions can recover.

### 8.16.8 Concurrent misses can compute more than once

The standard caching wrappers maintain internal data-structure coherence under their documented threading behaviour, but another thread can invoke the underlying function for the same key before the first result has been stored. Thus cache coherence does not guarantee exactly-once computation.

For pure deterministic computation, duplicate work affects performance. For an effectful function, it can duplicate effects and proves the function was not a safe memoisation candidate. Per-key single-flight coordination is a different abstraction with states for in-progress, success, failure, cancellation, and waiter notification.

### 8.16.9 Method caches retain instances

~~~python
class Parser:
    @lru_cache(maxsize=128)
    def parse(self, text: str):
        ...
~~~

The bound call includes <code>self</code> in the cache key. The wrapper is normally stored on the class and can retain instance references through keys, preventing instances from being collected until entries are evicted or the cache is cleared. Different instances have distinct identities/equality keys unless their class defines otherwise.

Per-instance caching, weak-key structures, explicit cache fields, or immutable shared parsing functions may better fit lifecycle. Weak references introduce collection timing and equality concerns; no decorator flag can infer ownership.

### 8.16.10 Recursive memoisation must call through the wrapper

The decorated Fibonacci body resolves global <code>fibonacci</code> to the cache wrapper, so recursive calls benefit. If the body closed over or called an alias to the undecorated function, internal recursion could bypass caching.

For \(n\ge2\), cached Fibonacci computes each state 0 through \(n\) once, then performs constant lookup/combine work per state, so time is \(O(n)\) in arithmetic operations ignoring growing integer bit costs, cache space \(O(n)\), and maximum recursion depth \(O(n)\). Caching fixes exponential repeated calls but not the recursion-depth limit.

The integers themselves grow in bit length approximately proportional to \(n\), so treating addition as constant eventually understates bit complexity. Complexity models must include value size when numbers grow.

### 8.16.11 Dynamic programming can remove recursion

**Dynamic programming** solves overlapping subproblems while retaining necessary results. Top-down memoisation discovers states recursively; bottom-up tabulation orders them explicitly.

~~~python
def fibonacci_iterative(number: int) -> int:
    if number < 0:
        raise ValueError("number must be non-negative")
    previous, current = 0, 1
    for _ in range(number):
        previous, current = current, previous + current
    return previous
~~~

Only the two most recent values are needed, so auxiliary state is \(O(1)\) Python integers rather than \(O(n)\) cached entries/frames, again excluding their growing bit size. This computes one requested value; a cache is better if many later calls for varied \(n\) must reuse prior work.

### 8.16.12 Cyclic dependencies need an in-progress state

Plain memoisation marks a key only after computation. If computing A requests B and computing B requests A, neither is cached yet and recursion cycles. Algorithms over cyclic dependency graphs need a visitation state such as unseen, active, and complete.

~~~python
UNSEEN = 0
ACTIVE = 1
COMPLETE = 2
~~~

Encountering ACTIVE detects a back edge/cycle; COMPLETE permits reuse. This is not merely caching a result—it is controlling a graph traversal state machine. Chapter 13 develops depth-first search and cycle proofs.

### 8.16.13 Cache invalidation is a state-transition problem

When underlying data changes, every derived cached key affected by the change must be removed or versioned. Strategies include:

- clear all entries;
- invalidate explicitly named keys;
- include an immutable data/version identifier in the key;
- use short expiry, accepting staleness bounds;
- subscribe to change events, accepting missed-event/recovery complexity;
- make data immutable and create a new cache owner per version.

Time-to-live expiration is not semantic validation: data can change immediately after insertion and remain stale until expiry. Distributed caches add clock, replication, serialization, and partial-failure problems.

### 8.16.14 Cache observation guides measurement

Caching wrappers expose <code>cache_info()</code> with hits, misses, capacity, and current size, and <code>cache_clear()</code>. A high hit ratio alone does not prove value: cheap computations may cost more to hash/cache than recompute, and a small fraction of expensive misses can dominate latency.

Measure:

- hit and miss latency distributions;
- key construction/hash cost;
- retained bytes, not only entry count;
- eviction/churn;
- staleness incidents;
- duplicate concurrent computation;
- cold-start behaviour;
- invalidation cost.

### Worked example 8.7B — Memoised edit distance and its state space

The edit distance between prefixes of strings can be defined recursively. State \((i,j)\) means distance between <code>left[:i]</code> and <code>right[:j]</code>:

~~~python
from functools import cache


def edit_distance(left: str, right: str) -> int:
    @cache
    def distance(i: int, j: int) -> int:
        if i == 0:
            return j
        if j == 0:
            return i
        if left[i - 1] == right[j - 1]:
            return distance(i - 1, j - 1)

        return 1 + min(
            distance(i - 1, j),
            distance(i, j - 1),
            distance(i - 1, j - 1),
        )

    return distance(len(left), len(right))
~~~

There are at most \((|left|+1)(|right|+1)\) distinct states. Each cached state performs constant recursive combinations excluding character comparison/hash/cache mechanics, giving \(O(mn)\) time and space for lengths \(m,n\). Without memoisation, overlapping branches cause exponential repeated work.

The closure cache belongs to one outer call and becomes unreachable afterward, so it cannot leak across unrelated string pairs. Maximum recursion depth can be \(O(m+n)\), which remains a practical limitation for long strings. A bottom-up table or row-compressed algorithm can avoid recursion and reduce memory when reconstruction of the edit path is unnecessary.

### Worked example 8.7C — Version a cache key explicitly

~~~python
from dataclasses import dataclass
from functools import lru_cache


@dataclass(frozen=True)
class CatalogueVersion:
    identifier: str


@lru_cache(maxsize=1_024)
def price_for(
    version: CatalogueVersion,
    product_id: str,
) -> int:
    return load_price_from_immutable_snapshot(version, product_id)
~~~

The semantic claim is that a catalogue version names immutable price data. A new publication uses a new version key, so old and new results cannot collide. Old cache entries remain until eviction/clear and can retain snapshots indirectly. The loader must truly read by supplied version; if it silently reads current state, the key is decorative rather than valid.

> **Common misconception — “Caching a deterministic-looking function is correct if its explicit arguments are hashable.”**  
> Correctness also requires that those arguments capture every semantic dependency and that cached result sharing, lifetime, invalidation, and concurrent misses satisfy the interface.
