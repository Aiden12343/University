# 8.17 Functions as units of proof and change

A function is well-factored when its contract is smaller and more stable than the source it replaces. Splitting every line into a separate function adds indirection without abstraction. Leaving unrelated policies in one function expands the state space that must be understood at once.

Useful decomposition boundaries often occur at:

- parsing versus domain calculation;
- pure transformation versus I/O;
- policy choice versus mechanism;
- validation versus trusted core operation;
- resource acquisition versus use;
- representation conversion;
- one invariant-owning state transition.

### Worked example 8.7 — Decompose a report pipeline

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class Summary:
    count: int
    total: float
    minimum: float
    maximum: float


def parse_lines(lines: list[str]) -> list[float]:
    values: list[float] = []
    for line_number, line in enumerate(lines, start=1):
        stripped = line.strip()
        if not stripped:
            continue
        try:
            values.append(float(stripped))
        except ValueError as error:
            raise ValueError(f"line {line_number}: invalid number") from error
    return values


def summarise(values: list[float]) -> Summary:
    if not values:
        raise ValueError("at least one value is required")
    return Summary(
        count=len(values),
        total=sum(values),
        minimum=min(values),
        maximum=max(values),
    )


def format_summary(summary: Summary) -> str:
    mean = summary.total / summary.count
    return (
        f"count={summary.count}\n"
        f"minimum={summary.minimum:.2f}\n"
        f"maximum={summary.maximum:.2f}\n"
        f"mean={mean:.2f}"
    )
```

`parse_lines` owns source positions and conversion. `summarise` owns the non-empty aggregate invariant. `format_summary` owns display rounding. File access and command-line policy can be tested separately. The `Summary` class is a forward reference to Chapter 9; it provides an immutable named record.

If exact arithmetic or NaN rejection is required, the representation and parser contract must change. Decomposition localises that change but cannot decide the domain requirement.

### 8.17.1 Decomposition follows invariants and reasons for change

Two operations belong in one function when they jointly establish one postcondition and cannot be separated without exposing an invalid intermediate state. They belong in separate functions when they implement independently variable policies or one can be reused/tested under a smaller contract.

An account transfer should not be split into public <code>debit</code> and <code>credit</code> calls if observers can see the state between them and atomic transfer is required. Internally, pure balance calculations can be helpers while one owner commits both changes.

Conversely, parsing CSV, computing statistics, choosing display precision, and writing a file change for different reasons and deserve boundaries.

### 8.17.2 Cohesion reduces proof state

Suppose one function has \(p\) independent Boolean modes. It can expose up to \(2^p\) mode combinations before considering input data. Several combinations may be invalid or untested.

~~~python
def process(data, *, validate=True, save=False, notify=False, dry_run=False):
    ...
~~~

This signature suggests several responsibilities and interactions: Can dry-run notify? Does save occur before notification? Does validation false permit malformed persistence? Separate phase functions and a workflow coordinator make allowed sequences explicit.

Small functions are not automatically cohesive. A helper named <code>do_step</code> that depends on ten globals has a tiny body and enormous hidden contract.

### 8.17.3 Parameter lists reveal abstraction pressure

Many primitive parameters that always travel together may represent a missing value object:

~~~python
def ship(name, street, city, postal_code, country, weight, width, height, depth):
    ...
~~~

An Address, Dimensions, and Parcel value can enforce relationships and reduce argument transposition. This is not an instruction to wrap every pair in a class. Group values when they share invariants, vocabulary, or lifecycle.

Boolean parameters often hide multiple operations. <code>open_report(path, writable=True)</code> may be better than a Boolean because the name remains clear; <code>render(data, html=True)</code> becomes brittle when PDF and text are added—separate format objects/functions scale better.

### 8.17.4 Return shape should reflect one abstraction

Returning a long positional tuple couples callers to order:

~~~python
count, total, minimum, maximum, mean, variance = analyse(values)
~~~

A named immutable result makes fields explicit and permits compatible evolution under controlled rules. A dictionary permits dynamic optional fields but can defer spelling/type defects. The function’s result representation should make its invariants native.

Avoid returning internal mutable containers merely to save copying unless shared ownership is explicit. Encapsulation failures often begin at return boundaries.

### 8.17.5 Separate policy from mechanism

A retry mechanism can schedule attempts; policy decides which exceptions, maximum delay, idempotency, and reporting. A sorting mechanism orders by keys; policy derives keys. A parser recognizes syntax; policy decides permitted ranges and normalization.

Higher-order functions, strategy objects, or explicit parameters can inject policy. But a callback is not always needed: a small finite policy can be an enum or pattern-matched value, which is easier to serialize and audit than arbitrary executable behaviour.

### 8.17.6 Separate pure derivation from commit

A state-changing workflow can often be divided into:

1. read a coherent current snapshot;
2. validate request against it;
3. derive proposed new state and effects as values;
4. commit under an owning transaction/lock;
5. publish external effects under a reliable protocol.

Pure derivation functions admit deterministic tests and do not leave partial state when validation fails. The final commit may still fail or encounter concurrent change; optimistic concurrency can compare the version read in phase one.

This pattern appears in compilers (parse/analyse/emit), web applications (validate/domain transaction/respond), and infrastructure systems (plan/apply).

### 8.17.7 Error context belongs where information meets ownership

A low-level parser knows byte offset and grammar rule. A service knows record identifier and user action. A command boundary knows display format and exit status. Each layer should add the context it uniquely owns while preserving causes.

~~~python
try:
    record = parse_record(payload)
except RecordSyntaxError as error:
    raise ImportErrorForRecord(record_id) from error
~~~

Translating too early loses useful distinctions; translating nowhere exposes implementation details. Catch only exceptions the layer can contextualize, recover from, or convert to its protocol.

### 8.17.8 A test seam is a controlled dependency boundary

Injecting a clock, random generator, filesystem interface, or reporter creates a **test seam** where deterministic substitutes can be supplied. The seam should correspond to a real architectural dependency, not exist solely to mock every internal call.

~~~python
def choose_identifier(random_bytes) -> str:
    return random_bytes(16).hex()
~~~

Tests can supply a deterministic byte producer. Production supplies a cryptographically appropriate source if the identifier has security requirements. Injecting <code>hex</code> or every arithmetic operation would fragment the implementation without improving boundary control.

### 8.17.9 Function size metrics are weak proxies

Line count, cyclomatic complexity, parameter count, and nesting depth can identify review candidates, but none measures semantic cohesion directly. A parser may legitimately have many branches corresponding to a grammar. A one-line regular expression can encode enormous complexity and catastrophic behaviour.

Review asks:

- How many invariants and effect domains are active?
- How many independent reasons can this function change?
- Can its contract be stated compactly?
- Are intermediate invalid states exposed?
- Can error and resource paths be understood?
- Does extraction create a real reusable/nameable concept?

### 8.17.10 Over-abstraction has costs

Extracting a function used once can still name a crucial concept, but indirection has costs: readers navigate definitions, parameters shuttle transient state, stack traces deepen, and local control becomes distributed. A generic callback framework for two fixed cases may be harder to verify than an <code>if</code> statement.

Wait for stable common semantics before unifying code. Two similar-looking blocks may implement different policies that should diverge. **Duplication** of syntax is not automatically duplication of knowledge.

### 8.17.11 Functions are versioned APIs even inside a repository

Changing a private helper and all its controlled callers can be one atomic change. Changing a public function requires compatibility analysis over signature, accepted domain, result type, effects, exceptions, ordering, timing, and performance.

Adding validation can break callers that relied on permissive behaviour. Improving an algorithm can alter callback order or exception timing. Replacing a list result with a generator changes consumption and lifetime. Semantic versioning cannot be based only on parameter names.

### Worked example 8.7D — Derive and commit an account transfer

Pure proposed-state calculation:

~~~python
from dataclasses import dataclass


@dataclass(frozen=True)
class Balances:
    source: int
    destination: int


def propose_transfer(current: Balances, amount: int) -> Balances:
    if amount <= 0:
        raise ValueError("amount must be positive")
    if current.source < amount:
        raise ValueError("insufficient funds")
    return Balances(
        source=current.source - amount,
        destination=current.destination + amount,
    )
~~~

The function does not know accounts, locks, databases, currencies, or notifications. It proves conservation:

\[
new.source+new.destination
=old.source+old.destination.
\]

An effectful repository operation must read both actual accounts under a transaction, confirm currency and version, call the pure transition, write both balances atomically, record a transfer identity, and commit. A notification should follow a reliable post-commit protocol. The pure helper improves arithmetic proof but does not make the overall transfer atomic.

### Worked example 8.7E — Refactor one mixed pipeline

Mixed version (conceptual): read file, skip blank lines, parse floats, reject non-finite values, compute summary, round, print, and exit inside one function.

Refined contracts:

~~~python
from collections.abc import Iterable
from math import isfinite


def parse_finite_lines(lines: Iterable[str]) -> list[float]:
    values: list[float] = []
    for line_number, line in enumerate(lines, 1):
        text = line.strip()
        if not text:
            continue
        try:
            value = float(text)
        except ValueError as error:
            raise ValueError(f"line {line_number}: invalid number") from error
        if not isfinite(value):
            raise ValueError(f"line {line_number}: non-finite number")
        values.append(value)
    return values
~~~

<code>summarise</code> owns non-empty aggregate mathematics. <code>format_summary</code> owns presentation precision. <code>read_measurements(path)</code> owns encoding, newline, and resource lifetime. <code>main(arguments)</code> owns user-facing diagnostics and status code.

This decomposition creates explicit seams at representation changes:

\[
bytes/file\rightarrow lines\rightarrow floats\rightarrow Summary\rightarrow text.
\]

Each boundary has distinct failure vocabulary. The design does not split the arithmetic into one function per operator; it separates stable semantic stages.

### 8.17.12 Function dossier template

For a function important enough to serve as a reusable reference, record:

1. name and purpose;
2. signature and parameter kinds;
3. admitted domain and relational preconditions;
4. normal result and ownership/aliasing;
5. effects and frame condition;
6. exceptions, causes, and partial effects;
7. evaluation/consumption timing;
8. termination and cancellation;
9. time/space/output bounds;
10. determinism and environmental dependencies;
11. closure/default/cache retained state;
12. concurrency and re-entrancy;
13. proof invariant or recurrence;
14. tests and observability;
15. compatibility surface.

This dossier is intentionally more demanding than typical docstrings. It is a reasoning instrument for critical functions, reviews, and study—not boilerplate required verbatim for every trivial helper.

> **Common misconception — “The ideal function is as short as possible.”**  
> The useful goal is a coherent, explicit contract and manageable proof state. Arbitrary extraction can hide control and create unstable interfaces without reducing semantic complexity.
