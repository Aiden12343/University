# 8.2 Parameters and arguments

A **parameter** is a name in a function definition that receives a binding when a call begins. An **argument** is a value supplied by a call. “Pass the parameter” reverses these roles: the caller passes an argument; the callee declares a parameter.

Python supports several parameter kinds:

```python
def demonstrate(
    positional_only,
    /,
    positional_or_keyword,
    *additional_positionals,
    keyword_only,
    defaulted="default",
    **additional_keywords,
):
    ...
```

- Parameters before `/` are **positional-only**.
- Parameters between `/` and `*` can receive positional or keyword arguments.
- `*additional_positionals` gathers remaining positional arguments into a tuple.
- Parameters after `*` are **keyword-only**.
- A default expression makes an argument optional under the call-binding rule.
- `**additional_keywords` gathers unmatched keyword arguments into a dictionary.

The markers `/` and `*` publish API flexibility or constraint. Positional-only parameters allow an implementation to rename an internal parameter without breaking keyword callers and can permit names that also appear in `**kwargs`. Keyword-only parameters make call-site meaning explicit.

### Worked example 8.1 — Bind a mixed signature

```python
def render(name: str, /, value: float, *, precision: int = 2) -> str:
    return f"{name}: {value:.{precision}f}"


print(render("temperature", 21.375, precision=1))
print(render("temperature", value=21.375))
```

Output:

```text
temperature: 21.4
temperature: 21.38
```

`name` must be positional. `value` can be positional or keyword. `precision` must be keyword because it follows `*`. In the second call its default 2 is used. Formatting rounds the displayed text; it does not change the original float.

A call fails before the function body begins if argument binding cannot satisfy the signature: missing required argument, duplicate assignment, unexpected keyword without `**kwargs`, or too many positional arguments without `*args`.

### 8.2.1 Signature grammar constrains parameter order

A Python signature is not an arbitrary mixture of parameter forms. Its conceptual order is:

1. positional-only parameters;
2. positional-or-keyword parameters;
3. optional variadic positional collector;
4. keyword-only parameters;
5. optional variadic keyword collector.

Within applicable groups, a parameter without a default generally cannot follow one with a default when both can be filled through the same positional progression. The grammar prevents a call from needing to skip an earlier positional parameter ambiguously.

~~~python
def valid(a, b=2, /, c=3, *, d, e=5, **extras):
    ...
~~~

Here <code>a</code> is required positional-only; <code>b</code> is defaulted positional-only; <code>c</code> is defaulted positional-or-keyword; <code>d</code> is required keyword-only; <code>e</code> is defaulted keyword-only; and <code>extras</code> collects unmatched keywords.

Parameter names are local bindings. The conventional names <code>args</code> and <code>kwargs</code> have no syntactic power; the stars determine kind:

~~~python
def collect(*fish, **birds):
    print(fish, birds)
~~~

### 8.2.2 A conceptual binding algorithm

After all argument expressions and expansions have been evaluated, binding conceptually proceeds by satisfying the signature:

1. assign positional argument values from left to right to parameters that accept positions;
2. collect surplus positions into <code>*args</code>, or fail if no collector exists;
3. assign explicit and expanded keyword entries to matching parameters that accept keywords;
4. reject a keyword that attempts to fill positional-only state unless a <code>**kwargs</code> collector legitimately captures that name;
5. reject any parameter receiving more than one value;
6. collect otherwise unmatched keywords into <code>**kwargs</code>, or reject them;
7. bind omitted parameters to retained defaults where available;
8. reject every still-unbound required parameter.

The exact error wording and some precedence among simultaneous defects are implementation details. Code should test that invalid calls fail for the right category, not depend needlessly on entire diagnostic strings.

### 8.2.3 Positional arguments allocate by position, not name

~~~python
def describe(left: str, right: str) -> str:
    return f"{left} -> {right}"


print(describe("source", "target"))
~~~

The first argument binds <code>left</code>; the second binds <code>right</code>. Argument expressions execute in call-site order before body entry. If the second expression fails, effects of the first evaluation remain, but no frame begins executing the function body.

Keyword calls decouple source ordering from parameter ordering while preserving argument-expression evaluation order:

~~~python
print(describe(right="target", left="source"))
~~~

The interface is clearer when parameter names carry stable meaning. It is more brittle when an internal name is likely to change and callers need not know it.

### 8.2.4 Positional-only parameters protect naming freedom

Consider a public API whose first argument is merely the object being processed:

~~~python
def checksum(data, /, *, algorithm="sha256"):
    ...
~~~

Callers cannot write <code>checksum(data=...)</code>, so a future version may rename <code>data</code> to <code>payload</code> without breaking valid calls. The name remains useful in implementation and documentation while not becoming call syntax.

Positional-only names can also coexist with identical keyword names captured by <code>**kwargs</code>:

~~~python
def include(name, /, **metadata):
    return name, metadata


print(include("Ada", name="display name"))
# ('Ada', {'name': 'display name'})
~~~

Without the slash, <code>name</code> would receive two values. This capability matters for mapping-oriented APIs that must accept arbitrary external field names.

### 8.2.5 Keyword-only parameters prevent Boolean blindness

Calls containing several positional flags are difficult to interpret:

~~~python
# configure(True, False, True)
~~~

Keyword-only parameters make policy visible:

~~~python
def configure(
    path: str,
    *,
    recursive: bool = False,
    overwrite: bool = False,
    preserve_metadata: bool = True,
) -> None:
    ...


configure(
    "/archive",
    recursive=True,
    overwrite=False,
    preserve_metadata=True,
)
~~~

Even named Booleans can permit invalid combinations. An enumeration or separate functions can express mutually exclusive modes better. Keyword-only syntax improves call readability; it does not complete API modelling.

### 8.2.6 Variadic positional collection creates a tuple

<code>*args</code> binds a tuple of surplus positional arguments, including an empty tuple when none remain:

~~~python
def product(first: int, *rest: int) -> int:
    result = first
    for value in rest:
        result *= value
    return result


print(product(2))              # 2; rest == ()
print(product(2, 3, 4))        # 24; rest == (3, 4)
~~~

The required <code>first</code> parameter makes an empty call invalid and avoids inventing an identity policy in this API. A general mathematical product might deliberately return 1 for no factors; that is a different contract.

All additional positional objects are collected before body execution. The tuple is shallow: it holds the same objects evaluated by the caller.

### 8.2.7 Variadic keyword collection creates a dictionary

<code>**kwargs</code> binds a fresh dictionary of unmatched keyword names to argument objects:

~~~python
def metadata(**entries: object) -> dict[str, object]:
    return entries


source = {"language": "Python"}
result = metadata(**source, version="3.12")
source["language"] = "changed"

print(result)                  # independent outer mapping
~~~

The outer dictionary <code>result</code> is not <code>source</code>. Nested values remain shared. Keyword names must be strings at the call boundary; a non-string mapping key in a double-star expansion causes <code>TypeError</code> before body entry.

An unrestricted <code>**kwargs</code> can hide spelling mistakes and weaken discoverability. Use it when forwarding extensible protocol fields or implementing adapters with a deliberate unknown-key policy, not automatically on every public function.

### 8.2.8 Starred positional expansion consumes iterables

At a call site, <code>*iterable</code> expands produced values into positional arguments:

~~~python
def point(x: int, y: int, z: int) -> tuple[int, int, int]:
    return x, y, z


coordinates = (2, 3, 5)
print(point(*coordinates))
~~~

The expansion must determine and supply all positional values before the body runs. Expanding a generator consumes it:

~~~python
coordinates = (value for value in [2, 3, 5])
result = point(*coordinates)
print(list(coordinates))       # []
~~~

An infinite iterable cannot finish expanding into a call. A large expansion can allocate substantial temporary argument state and exceed the callable’s accepted arity. If a function conceptually accepts a stream, pass the iterable as one argument rather than expanding it.

### 8.2.9 Double-star expansion and duplicate detection

At a call site, <code>**mapping</code> contributes keyword entries in mapping iteration order under the call machinery. Duplicate names across explicit keywords or multiple expansions are errors rather than silent right-precedence merges:

~~~python
def connect(*, host: str, port: int) -> tuple[str, int]:
    return host, port


network = {"host": "localhost"}
print(connect(**network, port=8080))

# connect(host="a", **{"host": "b", "port": 80})
# TypeError: multiple values for keyword argument 'host'
~~~

This differs from dictionary display/union rules that can let later values replace earlier ones. A function call requires one unambiguous binding per named parameter.

Mapping iteration, key validation, and value retrieval can execute user-defined code before body entry. A custom mapping can fail after earlier argument effects; no general rollback occurs.

### 8.2.10 Multiple assignment paths are rejected

~~~python
def scale(value: int, factor: int = 2) -> int:
    return value * factor


# scale(10, value=20)          # value receives positional and keyword values
~~~

The runtime rejects the call even if the two objects compare equal. Binding is about one source of a parameter value, not reconciling values by equality.

A bound method call supplies a receiver implicitly through attribute binding, as Chapter 9 explains. Supplying that receiver again can similarly create an arity mismatch. Error messages are best interpreted by reconstructing every implicit and explicit argument source.

### 8.2.11 Defaults make omission meaningful, not the value optional

For

~~~python
def retry(operation, attempts: int = 3):
    ...
~~~

the default says omission binds <code>attempts</code> to the retained object 3. It does not say that <code>None</code>, zero, a float, or a negative integer is accepted. **Optional argument** can mean “may be omitted” in call syntax, whereas an **optional value type** such as <code>int | None</code> means <code>None</code> is a legitimate supplied value. These notions must not be conflated.

~~~python
def find(
    query: str,
    *,
    limit: int | None = None,
) -> list[str]:
    ...
~~~

Here <code>limit</code> may be omitted, and its default <code>None</code> also deliberately denotes “no limit.”

### 8.2.12 Signature evolution and compatibility

Changing a parameter name can break keyword callers. Inserting a new positional parameter can reinterpret old calls. Removing a default turns formerly valid omissions into failures. Broadening accepted arguments is often source-compatible but can change which errors are detected; narrowing them is a breaking contract change.

Keyword-only additions with defaults are commonly safer because old calls omit them and positional interpretation is unchanged. Positional-only parameters reserve implementation naming freedom. Deprecation periods can accept old and new names while warning, but duplicate or ambiguous supply must be handled explicitly.

A public signature is part of a library’s versioned interface. Internal helpers have more freedom because their callers change within one controlled codebase.

### 8.2.13 inspect.Signature as a binding model

The standard-library <code>inspect</code> module exposes signatures and can apply binding rules without executing the target body:

~~~python
from inspect import signature


def render(name: str, /, value: float, *, precision: int = 2) -> str:
    return f"{name}: {value:.{precision}f}"


sig = signature(render)
bound = sig.bind("temperature", value=21.375, precision=1)
bound.apply_defaults()
print(bound.arguments)
~~~

Frameworks use introspection for dependency injection, command interfaces, and validation. Dynamic binding can reproduce call rules, but it also couples the framework to signatures and annotations. Calling <code>bind</code> validates shape, not domain meaning: a negative precision or inappropriate value type can still bind successfully.

### Worked example 8.1B — Full evaluation and binding trace

~~~python
def observe(label: str, value):
    print(label)
    return value


def target(a, /, b, *rest, c, d=40, **extras):
    return a, b, rest, c, d, extras


positional_tail = observe("tail source", [3, 4])
keyword_tail = observe("keyword source", {"e": 50})

result = target(
    observe("a", 1),
    b=observe("b", 2),
    *positional_tail,
    c=observe("c", 30),
    **keyword_tail,
)
~~~

The starred positional values are combined with the explicit positional argument before binding. Therefore <code>a</code> receives 1; the expanded 3 would next attempt to fill <code>b</code>; the explicit keyword also attempts to fill <code>b</code>. The call raises <code>TypeError</code> for multiple values before the target body begins. Nevertheless, every argument/source expression shown has already executed in language-defined evaluation order as governed by the call grammar, and its printed effects remain.

A corrected call moves 2 into positional form and lets the tail become <code>rest</code>:

~~~python
result = target(
    observe("a", 1),
    observe("b", 2),
    *positional_tail,
    c=observe("c", 30),
    **keyword_tail,
)

assert result == (1, 2, (3, 4), 30, 40, {"e": 50})
~~~

The retained default supplies <code>d</code>. A fresh tuple and dictionary hold surplus arguments. The target receives object references produced by the call expressions; it does not receive the caller’s names.

> **Common misconception — “If argument binding fails, nothing in the call happened.”**  
> The function body did not begin, but argument expressions and iterable/mapping expansions may already have executed effects or consumed sources.
