# 8.3 Python passes object references by assignment

Argument passing uses the same binding model as assignment. Argument expressions are evaluated; the resulting objects are bound to parameter names in a new call frame. Python does not use a source-level “pass by value versus pass by reference” switch. The precise description is **call by sharing** or **object-reference passing by assignment**.

### Worked example 8.2 — Mutation crosses the call; rebinding does not

```python
def alter(items: list[int]) -> None:
    items.append(3)
    items = [99]
    print("inside", items)


outside = [1, 2]
alter(outside)
print("outside", outside)
```

Output:

```text
inside [99]
outside [1, 2, 3]
```

At call entry, `items` and `outside` designate the same list. `append` mutates that shared object. The later assignment rebinds local parameter name `items` to a new list; it does not rebind caller name `outside`. Parameter binding creates a local name, not a caller-variable portal.

For an immutable object, an apparent update produces a new object and rebinds the parameter:

```python
def increment(number: int) -> None:
    number += 1


value = 10
increment(value)
print(value)  # 10
```

The distinction follows mutability and binding; no special “immutable pass mode” exists.

> **Common misconception — “Lists are passed by reference but integers by value.”**  
> Both calls bind parameter names to argument objects. A list exposes mutation; integer operations produce new immutable values. The argument-passing rule is one rule.

### 8.3.1 Call entry extends the reference graph

Suppose caller name <code>outside</code> refers to list object \(L\). At function entry, parameter name <code>items</code> is added in a new local namespace and also refers to \(L\):

\[
outside\longrightarrow L\longleftarrow items.
\]

No list copy is implied. Mutating \(L\) is visible through every alias; rebinding one arrow changes only its namespace:

\[
items\longrightarrow L'\qquad outside\longrightarrow L.
\]

This graph model explains list, dictionary, set, user object, and nested-container behaviour uniformly. It also explains why a function can return an argument and thereby create another alias.

### 8.3.2 The historical parameter-passing vocabulary

In classic **call by value**, a parameter receives a copy of a value, so assignment to it cannot assign the caller’s variable. In classic **call by reference**, a parameter aliases a caller variable or storage location, so assigning the parameter can assign that caller location. Python matches neither folk simplification exactly.

The value placed into a Python parameter binding is an object reference, but that reference is assigned to a new local name. The callee can use it to mutate a mutable object; it cannot directly rebind the caller’s name. Terms such as **call by sharing**, **call by object reference**, or “assignment semantics” preserve this distinction.

Saying “Python passes everything by reference” encourages the false prediction that <code>items = new_list</code> rebinds the caller. Saying “everything is passed by value” without specifying that the value is an object reference encourages the false prediction that mutations are isolated. The graph model is less ambiguous than slogans.

### 8.3.3 Mutation depth matters

~~~python
def update(rows: list[list[int]]) -> None:
    rows.append([9])           # outer mutation
    rows[0].append(7)          # nested mutation
    rows[1] = [8]              # outer slot replacement
~~~

All three operations are visible through a caller alias to the outer list, but their graph effects differ:

- append adds a new outgoing edge from the outer list;
- nested append mutates an existing child node;
- slot assignment redirects one outer edge to a new child.

A shallow copy before the call isolates outer-edge changes while preserving nested sharing:

~~~python
caller_rows = [[1], [2]]
update(caller_rows.copy())
print(caller_rows)             # first inner row contains 7; outer shape unchanged
~~~

Thus “pass a copy” requires a copy-depth and ownership policy.

### 8.3.4 Augmented assignment dispatches before rebinding

An augmented assignment such as <code>x += y</code> may mutate the object bound to <code>x</code> through an in-place method, or may compute a new object and rebind <code>x</code>. Lists and integers illustrate the difference:

~~~python
def augment_list(values: list[int]) -> None:
    values += [3]


def augment_integer(value: int) -> None:
    value += 3
~~~

The list operation normally extends the shared list in place; the integer operation constructs a new integer and rebinds the local parameter. A user-defined type can choose its in-place protocol. The source token <code>+=</code> does not itself promise mutation or replacement.

Even an immutable outer container can participate in a failed augmented assignment after nested mutation, as the tuple exercise in Chapter 7 shows. Analyse the dispatched operation and assignment target separately.

### 8.3.5 Mutation does not require reassignment syntax

A call can mutate an object even when no assignment appears in the caller:

~~~python
def consume(values: list[int]) -> int:
    return values.pop()


numbers = [1, 2, 3]
last = consume(numbers)
~~~

The name <code>consume</code> signals the ownership effect. A function annotated <code>list[int] -&gt; int</code> does not express that effect in ordinary Python typing. Documentation and naming remain necessary.

Conversely, assignment inside a function need not affect any external object:

~~~python
def local_only(value: object) -> None:
    value = object()
~~~

Distinguish target rebinding from operations invoked on a referenced object.

### 8.3.6 A function can retain an argument after return

A closure, global collection, cache, callback registry, or object field can preserve an argument reference beyond call completion:

~~~python
subscribers: list[object] = []


def subscribe(callback: object) -> None:
    subscribers.append(callback)
~~~

The contract is not merely “returns None.” It transfers or shares lifetime: the registry keeps the callback reachable until explicit removal or registry destruction. If the callback closes over a large object graph, the one stored reference can retain it all.

An API must state whether it borrows an argument only during the call, retains it, copies a representation, or assumes ownership. Python does not enforce affine or linear ownership types, so convention and encapsulation carry this responsibility.

### 8.3.7 Defensive copying is an interface choice

~~~python
def remember_tags(tags: set[str]) -> frozenset[str]:
    return frozenset(tags)
~~~

This function snapshots tag membership under set iteration and returns an immutable value. Later structural mutation of the supplied set does not alter the frozenset. Since strings are immutable, the result is also deeply stable for its selected payload.

For arbitrary values, conversion to tuple or frozenset may be shallow or impossible. Defensive copying can cost \(O(n)\), consume a one-shot source, trigger user code, lose order or multiplicity, and fail. It should follow an explicit publication requirement rather than reflexive distrust of every caller.

### 8.3.8 Return aliasing is as important as argument aliasing

~~~python
_configuration = {"mode": "safe"}


def configuration_wrong() -> dict[str, str]:
    return _configuration
~~~

The returned dictionary gives callers mutation authority over module state:

~~~python
configuration_wrong()["mode"] = "unsafe"
~~~

Alternatives implement different contracts:

~~~python
from types import MappingProxyType
from collections.abc import Mapping


def configuration_copy() -> dict[str, str]:
    return _configuration.copy()


def configuration_view() -> Mapping[str, str]:
    return MappingProxyType(_configuration)
~~~

The copy is a shallow time-specific outer snapshot that the caller may mutate independently. The proxy is a live read-only interface reflecting owner updates. The correct choice depends on temporal consistency and ownership.

### Worked example 8.2A — Three append interfaces

~~~python
from collections.abc import Sequence


def append_owned(values: list[int], value: int) -> None:
    """Mutate an exclusively owned list by appending value."""
    values.append(value)


def appended(values: Sequence[int], value: int) -> list[int]:
    """Return a new list containing the source values followed by value."""
    result = list(values)
    result.append(value)
    return result


def appended_tuple(values: tuple[int, ...], value: int) -> tuple[int, ...]:
    """Return an immutable tuple value with one additional component."""
    return (*values, value)
~~~

<code>append_owned</code> has constant amortised structural work and exposes mutation to aliases. <code>appended</code> accepts a broader sequence, performs \(\Theta(n)\) copying of references, and leaves the source’s outer structure unchanged. <code>appended_tuple</code> also performs \(\Theta(n)\) construction but publishes immutable outer membership. None deeply copies arbitrary elements.

An API choosing the first form should either require exclusive ownership or explicitly promise shared mutation. Choosing the second does not make nested element effects impossible. Choosing the third is valuable when the result is a small immutable value, but repeated tuple append is quadratic over a long build.

### Worked example 8.2B — Callback retention audit

~~~python
from collections.abc import Callable


def make_handler(records: list[str]) -> Callable[[str], None]:
    def handle(record: str) -> None:
        records.append(record)

    return handle
~~~

At call entry, local parameter <code>records</code> refers to the caller’s list. The inner function uses that binding, so closure construction creates a cell or equivalent retained binding. Returning <code>handle</code> keeps both the binding and list reachable. Each handler call mutates the original list. Rebinding the caller’s name later does not alter the retained list:

~~~python
original: list[str] = []
handler = make_handler(original)
original = []
handler("event")
print(original)                # []
~~~

The first list still exists through the closure but no longer has the caller name <code>original</code>. This example unifies argument binding, closure capture, mutation, and lifetime.

> **Common misconception — “Returning from a function releases all its arguments.”**  
> The frame’s ordinary local ownership ends, but returned closures, globals, caches, and other objects may retain references indefinitely.
