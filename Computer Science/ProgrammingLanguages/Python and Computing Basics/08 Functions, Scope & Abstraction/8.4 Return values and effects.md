# 8.4 Return values and effects

`return expression` evaluates the expression and completes the current function call with the resulting object. Bare `return`, or reaching the end of the body, returns `None`.

A function can produce a return value and effects. Design should distinguish them:

```python
def normalise_name(name: str) -> str:
    return " ".join(name.split()).casefold()


def display_name(name: str) -> None:
    print(normalise_name(name))
```

`normalise_name` is **pure** relative to ordinary observation: its result depends on its argument and it intentionally changes no external state. `display_name` performs output. “Pure” requires a defined observation model; allocation, CPU time, and exceptional resource exhaustion still occur, but these are normally excluded from the functional result model.

Separating calculation from I/O permits deterministic unit tests and reuse. A function that reads input, calculates, formats, prints, and mutates shared state in one body exposes many coupled failure paths.

Returning several comma-separated expressions creates one tuple:

```python
def bounds(values: list[int]) -> tuple[int, int]:
    return min(values), max(values)


low, high = bounds([8, 3, 11])
```

The caller unpacks one returned tuple. Python does not perform several independent returns from one call.

### 8.4.1 A call has several completion modes

An ordinary function invocation can:

- complete normally through <code>return</code>;
- reach the body’s end and return <code>None</code>;
- propagate an exception;
- fail to terminate;
- terminate the process or thread through a control exception/environmental event.

If the function contains <code>yield</code> in the relevant body, calling it creates a generator rather than immediately executing this ordinary-return model. If declared with <code>async def</code>, calling creates a coroutine object. Those are distinct invocation protocols developed in Chapters 6 and 14.

### 8.4.2 Return evaluates before leaving the frame

For <code>return expression</code>, the expression executes while the frame is active. If it raises, the call has no normal return:

~~~python
def final_element(values: list[int]) -> int:
    return values[-1]
~~~

An empty list causes <code>IndexError</code> during return-expression evaluation. It is incorrect to say the function “returns an error”; it propagates an exception instead of producing a normal result.

A <code>finally</code> suite executes during departure and can replace a pending result or exception:

~~~python
def misleading() -> int:
    try:
        return 1
    finally:
        return 2
~~~

This returns 2. Returning from <code>finally</code> usually obscures control flow and suppresses failures; it should be avoided unless replacement is an explicitly justified contract.

### 8.4.3 Returning a mutable object transfers an alias

~~~python
def new_bucket() -> list[str]:
    return []
~~~

Each call evaluates the list display and returns a new list, so callers own independent buckets. Contrast:

~~~python
bucket: list[str] = []


def shared_bucket() -> list[str]:
    return bucket
~~~

Every call returns an alias to one global object. A return type alone cannot distinguish fresh ownership, borrowed view, shared mutable state, cached identity, or immutable value. The function contract must.

### 8.4.4 Multiple return paths need one coherent result algebra

~~~python
def classify(number: int) -> str:
    if number < 0:
        return "negative"
    if number == 0:
        return "zero"
    return "positive"
~~~

Every reachable normal path returns a string from the intended finite vocabulary. A missing final return would implicitly produce <code>None</code>, silently widening the runtime result domain. Static type checking can detect some missing returns, but path reasoning remains necessary.

Functions returning unrelated shapes from different branches force callers into dynamic inspection:

~~~python
# Avoid an undocumented result such as int on success and str on failure.
~~~

Prefer a uniform value, a tagged result type, or an exception under a stated policy. Result cardinality and failure should be designed, not emerge from control-flow accidents.

### 8.4.5 Command–query separation

A **query** returns information without intentionally changing observable domain state. A **command** changes state. **Command–query separation** recommends distinguishing them so a call site reveals whether observation or mutation occurs.

~~~python
def current_balance(account: dict[str, int]) -> int:
    return account["balance"]


def deposit(account: dict[str, int], amount: int) -> None:
    if amount <= 0:
        raise ValueError("deposit must be positive")
    account["balance"] += amount
~~~

The recommendation is not absolute. <code>dict.pop</code> usefully returns the removed value because retrieval and removal form one atomic abstract operation. Iterators return an item while advancing state. A combined command-query is justified when the state transition and result are inseparable and its name/contract make this clear.

### 8.4.6 Effect taxonomy

Effects extend beyond printing and mutation of explicit arguments. A call may:

- mutate reachable Python objects;
- perform file, network, terminal, database, or device I/O;
- consume an iterator or random-number generator;
- read clocks, environment variables, locale, process state, or globals;
- allocate and retain cache entries;
- acquire locks or other resources;
- register callbacks or spawn work;
- log, warn, or emit metrics;
- alter imported module state;
- invoke callbacks supplied by callers.

Reads can be effects for determinism and security even when no state is changed. A time-reading function is not referentially transparent. A function that consumes an iterator changes that iterator’s state even if it constructs only a return list.

### 8.4.7 Idempotency concerns effects, not only return equality

If <code>f(x)</code> returns the same value twice but appends twice to a log, it is not idempotent under a model observing the log. An idempotent command reaches the same relevant state after repeated identical requests:

~~~python
def ensure_disabled(features: set[str], name: str) -> None:
    features.discard(name)
~~~

Repeating this yields the same set state as one call. Network retries require stronger identity: two attempts bearing the same idempotency key must correspond to one logical operation even after uncertain responses. Pure function calls are ordinarily idempotent in result, but resource exhaustion or hidden implementation effects can sit outside the abstract model.

### 8.4.8 None is a real result object

<code>None</code> is a singleton value used to denote absence or no meaningful result under many APIs. It is not “no object.” A function with no explicit return still supplies the object <code>None</code> to its caller.

~~~python
def announce() -> None:
    print("ready")


result = announce()
assert result is None
~~~

Identity comparison is appropriate for the singleton sentinel <code>None</code>. Whether <code>None</code> means absence, unknown, unbounded, invalid, or command completion depends on the interface. Reusing it for several outcomes creates ambiguity.

### 8.4.9 Result objects make outcomes explicit

Suppose parsing can either succeed or report one structured error without raising. A tagged result can encode the alternatives. This section previews dataclasses and generic types:

~~~python
from dataclasses import dataclass


@dataclass(frozen=True)
class ParseSuccess:
    value: int


@dataclass(frozen=True)
class ParseFailure:
    position: int
    message: str


def parse_positive(text: str) -> ParseSuccess | ParseFailure:
    try:
        value = int(text)
    except ValueError:
        return ParseFailure(0, "not an integer")
    if value <= 0:
        return ParseFailure(0, "not positive")
    return ParseSuccess(value)
~~~

The caller must inspect both variants. This is useful when failure is ordinary data to aggregate, transport, or display. Exceptions are often better when most callers cannot continue locally and failure should propagate through several layers. The choice is control architecture, not a universal style law.

### Worked example 8.2C — Pure core and effectful shell

~~~python
from dataclasses import dataclass


@dataclass(frozen=True)
class Invoice:
    subtotal_cents: int
    tax_cents: int

    @property
    def total_cents(self) -> int:
        return self.subtotal_cents + self.tax_cents


def calculate_invoice(subtotal_cents: int, tax_basis_points: int) -> Invoice:
    if subtotal_cents < 0:
        raise ValueError("subtotal must be non-negative")
    if not 0 <= tax_basis_points <= 10_000:
        raise ValueError("tax rate outside 0..100%")

    tax_cents = (subtotal_cents * tax_basis_points + 5_000) // 10_000
    return Invoice(subtotal_cents, tax_cents)


def print_invoice(invoice: Invoice) -> None:
    print(f"subtotal={invoice.subtotal_cents / 100:.2f}")
    print(f"tax={invoice.tax_cents / 100:.2f}")
    print(f"total={invoice.total_cents / 100:.2f}")
~~~

The core uses integer minor units and a stated half-up rounding formula for non-negative amounts. It returns an immutable value and performs no output. The shell formats and prints. Tests for taxation do not capture a terminal, and another caller can serialise the Invoice without parsing printed text.

The formula and permitted rate remain domain policies requiring jurisdictional authority; the example demonstrates separation, not tax law.

> **Common misconception — “A function annotated to return None returns nothing.”**  
> It returns the singleton <code>None</code> normally. The annotation communicates that callers should not expect a meaningful data result; it does not erase the object or any effects.
