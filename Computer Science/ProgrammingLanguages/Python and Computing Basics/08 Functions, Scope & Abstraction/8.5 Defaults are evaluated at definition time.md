# 8.5 Defaults are evaluated at definition time

Default argument expressions execute when the `def` statement executes, not at every later call. The resulting objects are retained in the function object.

```python
def append_record(record: str, records: list[str] = []) -> list[str]:
    records.append(record)
    return records


print(append_record("A"))
print(append_record("B"))
```

Output:

```text
['A']
['A', 'B']
```

One list is created during definition and reused whenever the caller omits `records`. This is not a bug in Python; it is the direct consequence of definition-time evaluation. It is usually a bug in an API intending a new list per call.

Use a sentinel default:

```python
def append_record(
    record: str,
    records: list[str] | None = None,
) -> list[str]:
    if records is None:
        records = []
    records.append(record)
    return records
```

Now each omitted argument constructs a new list during that call. An explicitly supplied list is still mutated, which must be part of the contract. If `None` is itself a meaningful argument, use a private sentinel object.

Defaults can intentionally retain shared state, for example memoisation, but hidden mutable state is inferior to an explicit cache object or a standard caching decorator because ownership and reset behaviour matter.

> **Common misconception — “Default values are substituted into missing calls.”**  
> Default expressions are evaluated when the function definition executes. Missing arguments bind parameters to those retained objects.

### 8.5.1 Definition time is an execution event

Defaults are evaluated from left to right when control executes the <code>def</code> statement. A name referenced by a default is resolved then; the default retains the resulting object even if the name is later rebound.

~~~python
rate = 2


def scale(value: int, factor: int = rate) -> int:
    return value * factor


rate = 10
print(scale(3))                # 6
~~~

The function does not perform a global lookup of <code>rate</code> for an omitted argument. Its positional defaults tuple contains the integer object 2. By contrast, a reference to <code>rate</code> in the body would be resolved when the call executes.

### 8.5.2 Effects in defaults occur once per definition execution

~~~python
def announce_default() -> list[str]:
    print("construct default")
    return []


def record(value: str, target: list[str] = announce_default()) -> None:
    target.append(value)
~~~

The message appears when the definition executes, before any call to <code>record</code>. If the definition is inside a loop and executes three times, the factory runs three times and three function objects receive three defaults. “Once” means once per execution of that definition statement, not once per source file forever.

Module import ordinarily executes top-level definitions once per module object in an interpreter import cache, but reloading, dynamic execution, or separate processes can execute them again. Default construction should therefore be deterministic and appropriate for import/definition time.

### 8.5.3 Mutable defaults are retained hidden state

The classic list example is a special case of a general rule. Dictionaries, sets, instances, iterators, open resources, random generators, and caches can all retain state:

~~~python
def take_next(source=iter([1, 2, 3])):
    return next(source)


print(take_next())             # 1
print(take_next())             # 2
~~~

The omitted default is one iterator whose consumption spans calls. This could be deliberate, but its ownership, exhaustion, reset, thread safety, and test isolation are hidden inside the function object.

Default objects also extend lifetime. A large object referenced only through <code>function.__defaults__</code> remains reachable as long as the function does.

### 8.5.4 None is sufficient only when it is outside the value domain

~~~python
def collect(value: int, target: list[int] | None = None) -> list[int]:
    if target is None:
        target = []
    target.append(value)
    return target
~~~

This works because <code>None</code> means omission/default construction and is not an accepted list. If <code>None</code> is itself meaningful, a private identity sentinel distinguishes it:

~~~python
_MISSING = object()


def configure(value: str | None | object = _MISSING) -> str | None:
    if value is _MISSING:
        return "system default"
    if value is None:
        return None             # explicit disable
    if not isinstance(value, str):
        raise TypeError("value must be text, None, or omitted")
    return value
~~~

The broad annotation is pedagogically awkward because the raw sentinel type appears as <code>object</code>; advanced typing can hide it with overloads or a private sentinel class. Runtime comparison must use <code>is</code> because sentinel uniqueness, not equality, defines omission.

### 8.5.5 Default factories belong in the call body or an owning object

For a fresh timestamp, random token, collection, or context-dependent value, call the factory during each omitted call:

~~~python
from datetime import datetime, timezone


def make_record(
    message: str,
    created_at: datetime | None = None,
) -> tuple[str, datetime]:
    if created_at is None:
        created_at = datetime.now(timezone.utc)
    return message, created_at
~~~

Writing <code>created_at=datetime.now(timezone.utc)</code> would freeze one definition-time timestamp. The body form samples at call time. If callers may explicitly supply <code>None</code> as a meaningful timestamp state, use a unique sentinel.

Injecting the clock can improve deterministic testing:

~~~python
from collections.abc import Callable


def make_record_with_clock(
    message: str,
    *,
    clock: Callable[[], datetime],
) -> tuple[str, datetime]:
    return message, clock()
~~~

Whether a default clock should be retained as a function object or looked up dynamically is itself an API/testing choice.

### 8.5.6 Defaults can deliberately capture configuration

Definition-time capture can provide stable behaviour despite later module rebinding:

~~~python
_normalizer = str.casefold


def normalize(text: str, operation=_normalizer) -> str:
    return operation(text)
~~~

The default retains the original callable. This pattern has historically appeared as a local-lookup optimisation or dependency capture, but it exposes the dependency in the public signature and can confuse introspection. A closure factory or explicit dependency object often communicates intent better:

~~~python
from collections.abc import Callable


def make_normalizer(operation: Callable[[str], str]):
    def normalize(text: str) -> str:
        return operation(text)
    return normalize
~~~

Use default capture only when omission semantics genuinely belong to the API.

### 8.5.7 Keyword defaults are retained separately

Positional and positional-or-keyword defaults are exposed through <code>__defaults__</code> as a tuple corresponding to the final defaulted positional parameters. Keyword-only defaults appear in <code>__kwdefaults__</code> as a dictionary:

~~~python
def example(a: int, b: int = 2, *, c: int = 3) -> int:
    return a + b + c


print(example.__defaults__)     # (2,)
print(example.__kwdefaults__)   # {'c': 3}
~~~

These attributes are introspection and metaprogramming surfaces. Reassigning or mutating them can change later call behaviour. Ordinary application code should not use them as configuration stores.

### 8.5.8 Default capture repairs late binding for a specific reason

~~~python
functions = [lambda value=index: value for index in range(3)]
~~~

Each lambda expression creates a function, and its default expression <code>index</code> is evaluated at that moment. The lambda body then reads local parameter <code>value</code>, whose default is distinct per function. This does not cause the closure to capture loop state early; it avoids closing over <code>index</code> at all for the returned value.

If a mutable loop object is captured as a default, only its reference is captured; later mutation remains visible:

~~~python
row = [1]
function = lambda row=row: tuple(row)
row.append(2)
print(function())             # (1, 2)
~~~

Early reference capture is not deep value freezing.

### 8.5.9 Intentional default caches require explicit lifecycle

~~~python
def parse_symbol(text: str, _cache: dict[str, str] = {}) -> str:
    if text not in _cache:
        _cache[text] = text.strip().casefold()
    return _cache[text]
~~~

This intentionally uses a retained dictionary, but it has an unbounded key lifetime, hidden reset behaviour, possible concurrency races, and a public-looking private parameter that callers can replace. <code>functools.lru_cache</code> or <code>cache</code> makes caching visible to introspection and provides cache-management methods, though it still requires key/result validity analysis.

Better still, an explicit cache owner can set capacity and lifecycle. The lesson is not “mutable defaults are forbidden”; it is that persistent state deserves a named owner and contract.

### Worked example 8.2D — Diagnose four timing policies

~~~python
from collections.abc import Callable


current_rate = 2


def captured(value: int, rate: int = current_rate) -> int:
    return value * rate


def dynamic(value: int) -> int:
    return value * current_rate


def factory(rate: int) -> Callable[[int], int]:
    def apply(value: int) -> int:
        return value * rate
    return apply


def explicit(value: int, rate: int) -> int:
    return value * rate
~~~

The four interfaces define different temporal ownership:

- <code>captured</code> uses the object obtained when its definition executed unless the caller overrides it;
- <code>dynamic</code> consults module state on every call;
- <code>factory(2)</code> constructs an operation retaining one factory-call binding;
- <code>explicit</code> makes every caller provide the dependency.

After <code>current_rate = 10</code>, <code>captured(3)</code> remains 6 and <code>dynamic(3)</code> becomes 30. Neither is intrinsically correct. Configuration stability, testability, hot reloading, concurrency, and public API shape determine the right policy.

> **Common misconception — “Using None fixes every default problem.”**  
> It works only when <code>None</code> is not a distinct valid argument or when its chosen meaning is explicit. Otherwise use a unique sentinel or redesign the interface.
