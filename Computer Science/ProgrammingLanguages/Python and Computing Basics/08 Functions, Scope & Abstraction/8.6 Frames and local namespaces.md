# 8.6 Frames and local namespaces

A **frame** is an execution context for code, containing local state, links to other contexts, and implementation machinery required to resume execution. Each ordinary function call creates a new frame. Recursive calls to the same function therefore have distinct parameter bindings and local state.

```python
def scale(value: int, factor: int) -> int:
    result = value * factor
    return result


first = scale(3, 4)
second = scale(5, 2)
```

The first frame binds `value=3`, `factor=4`, `result=12` and then ends. The second frame independently binds `value=5`, `factor=2`, `result=10`. Local names are not permanent properties of the function object.

In CPython, fast local storage is not literally a dictionary lookup for every access, though `locals()` exposes a mapping-like view with context-dependent synchronisation semantics. The language model says the frame has a local namespace; implementation layout can optimise it.

A **call stack** is the ordered collection of active calls under ordinary nested execution. When function A calls B and B calls C, A and B remain suspended awaiting results. Return from C resumes B; return from B resumes A. Tracebacks report this dynamic path when an exception propagates.

### 8.6.1 Code object, function object, and frame are distinct

Three runtime concepts are easily conflated:

- a **code object** represents compiled executable instructions and associated metadata;
- a **function object** combines a code object with a defining global namespace, defaults, closure cells, annotations, and attributes;
- a **frame** is one active or suspended execution context for code, with its current instruction position and bindings.

Calling one function twice ordinarily uses the same function and code objects but creates distinct frames:

~~~python
def add(left: int, right: int) -> int:
    total = left + right
    return total


first = add(2, 3)
second = add(5, 7)
~~~

The local <code>total</code> is not stored as one mutable attribute of <code>add</code>. Each call has its own binding. This is why ordinary overlapping or recursive invocations do not overwrite one shared local variable, although shared objects reached through globals, closures, or arguments can still race.

### 8.6.2 Scope is lexical; frame is dynamic

A **scope** is a region of source code in which a binding/resolution rule applies. A frame is a runtime instance of executing a code block. One function scope can produce zero, one, or many frames over program life.

~~~python
def repeat(value: int, times: int) -> list[int]:
    if times == 0:
        return []
    return [value] + repeat(value, times - 1)
~~~

There is one lexical function scope in source but <code>times + 1</code> active/sequential frames at maximum recursion depth for non-negative input. Every frame uses the same rule that <code>value</code> and <code>times</code> are local names, while storing distinct bindings.

### 8.6.3 Local classification precedes execution

The compiler analyses a code block to classify names. A name assigned anywhere in an ordinary function block is local throughout that block unless a valid <code>global</code> or <code>nonlocal</code> declaration changes classification.

~~~python
status = "global"


def choose(flag: bool) -> str:
    if flag:
        status = "local"
    return status
~~~

<code>choose(True)</code> returns <code>"local"</code>. <code>choose(False)</code> raises <code>UnboundLocalError</code> because the local binding path did not execute. The runtime does not fall back to the global name based on the branch. Definite binding is a control-flow property after lexical classification.

Assignments include more than a simple equals statement: parameters, loop targets, import bindings, exception targets, capture patterns, assignment expressions, function/class definition names, and augmented assignment can all bind under their respective scopes.

### 8.6.4 Frame creation and argument binding

A function body cannot observe a half-bound ordinary argument set. Call machinery evaluates argument expressions, validates the signature, creates/prepares the call context, and establishes parameter bindings before executing the first body operation. Binding failure means body statements do not run.

Default objects are not copied into a frame. The missing parameter is bound to the retained default reference. Variadic positional/keyword collectors receive newly created tuple/dictionary containers whose members are the supplied object references.

The frame may also expose local temporary state not named directly in source, such as exception machinery, comprehension execution, or interpreter stack values. The language-level namespace model intentionally abstracts from these implementation details.

### 8.6.5 Nested calls form a dynamic chain

~~~python
def parse(text: str) -> int:
    return int(text)


def double_text(text: str) -> int:
    value = parse(text)
    return value * 2


def application() -> int:
    return double_text("21")
~~~

During the deepest point, the dynamic call chain is <code>application -&gt; double_text -&gt; parse -&gt; int</code>, though built-in implementation frames may differ. Lexical enclosure is different: <code>parse</code> is not textually inside <code>double_text</code>, so its locals are not an enclosing namespace for the caller or callee.

A call stack explains return destinations and traceback order. It must not be confused with the lexical chain used for free-variable resolution.

### 8.6.6 Returning normally releases activation, not necessarily data

When an ordinary call returns and no diagnostic/runtime object retains its frame, the activation is no longer needed. Objects referenced only by its locals may become unreachable. But a local can escape:

~~~python
def build() -> list[int]:
    values = [1, 2, 3]
    return values
~~~

The frame can end while <code>values</code>’s list lives through the returned reference. A closure can preserve selected enclosing bindings. An exception traceback, debugger, tracer, or explicit frame introspection can preserve the entire frame and all locals.

Thus “local variable lifetime ends at return” is shorthand about binding accessibility in normal source, not a guarantee that referenced objects are destroyed then.

### 8.6.7 Suspended frames

Generator and coroutine execution can suspend rather than return. Their frames retain instruction position, local bindings, pending exception/finally state, and references needed for resumption.

~~~python
def running_totals(values: list[int]):
    total = 0
    for value in values:
        total += value
        yield total
~~~

After yielding once, the frame retains <code>values</code>, its iterator, <code>total</code>, and <code>value</code> as required by execution. Closing or exhausting the generator ends this resumable state. Chapter 6 introduced the lifecycle; the frame model explains its memory retention.

An ordinary frame is not necessarily implemented as one contiguous native stack record. CPython’s internal frame representation has evolved. “Call stack” is an abstract dynamic structure; chapter 15 qualifies physical layout.

### 8.6.8 locals is an observation interface, not a portable mutation portal

<code>locals()</code> returns a mapping representing current local bindings. At module scope it corresponds to the module namespace; in optimized function scopes, its update/snapshot semantics and write-back behaviour are specially defined and implementation/version-sensitive.

~~~python
def inspect_local(value: int) -> dict[str, object]:
    doubled = value * 2
    return dict(locals())
~~~

Copying the mapping yields a diagnostic snapshot of observed bindings. Code should not attempt to create or change fast local variables by assigning into <code>locals()</code>. Use ordinary assignments, explicit dictionaries, or an object model for dynamic names.

Reading locals for logging can retain or expose sensitive data. Returning <code>dict(locals())</code> transfers references to every included object, potentially extending lifetimes and bypassing intended encapsulation.

### 8.6.9 Tracebacks retain dynamic evidence

When an exception propagates, a traceback records frames along the failing dynamic path. This enables diagnosis:

~~~python
def reciprocal(text: str) -> float:
    number = float(text)
    return 1.0 / number
~~~

For <code>reciprocal("0")</code>, the traceback can expose that failure occurred in division after parsing. It may also retain <code>text</code>, <code>number</code>, and other local graphs. Long-lived exception storage can therefore become a memory and confidentiality issue.

Translate exceptions with bounded structured context rather than dumping all locals. Clear references to completed exceptions/tracebacks when retaining them is unnecessary, while preserving enough cause information for debugging under a controlled diagnostics policy.

### 8.6.10 Recursion depth is a resource precondition

Each active recursive call consumes interpreter/runtime resources. CPython maintains a recursion limit primarily to prevent uncontrolled C/interpreter stack exhaustion. Raising the limit does not make arbitrary recursion safe; the native stack, per-frame memory, input depth, and platform remain finite.

For an input tree with maximum depth \(h\), a depth-first recursive traversal uses \(O(h)\) active frames. A skewed tree with \(n\) nodes can have \(h=n\). An explicit heap-allocated worklist also uses \(O(h)\) or \(O(n)\) storage but can be bounded/managed without the Python recursion limit and often provides clearer cancellation.

### Worked example 8.3A — Frame trace for nested failure

~~~python
def denominator(fields: list[str]) -> int:
    return int(fields[1])


def compute(fields: list[str]) -> float:
    divisor = denominator(fields)
    return 100 / divisor


def report(line: str) -> str:
    fields = line.split(",")
    result = compute(fields)
    return f"result={result}"
~~~

For <code>report("sample,0")</code>:

1. <code>report</code> binds <code>line</code>, then <code>fields</code> to a two-element list.
2. <code>compute</code> creates another frame, binding its parameter to the same list.
3. <code>denominator</code> creates a third Python frame and returns integer zero.
4. That frame ends; <code>compute</code> binds local <code>divisor</code> to zero.
5. Division raises <code>ZeroDivisionError</code>; <code>compute</code> never returns a float.
6. With no handler, unwinding leaves <code>compute</code> and then <code>report</code>.
7. The traceback links the active failing route and can retain both frames’ locals.

The list object has aliases <code>fields</code> in <code>report</code> and parameter <code>fields</code> in <code>compute</code>/<code>denominator</code> while those frames are active. No function mutates it. Lexical scope does not allow <code>compute</code> to read <code>report</code>’s local name directly; the reference is conveyed by an argument.

> **Common misconception — “A call frame is the function.”**  
> The function is a reusable callable object. Each invocation creates a distinct execution frame, and suspended/retained frames can outlive ordinary dynamic stack activity.
