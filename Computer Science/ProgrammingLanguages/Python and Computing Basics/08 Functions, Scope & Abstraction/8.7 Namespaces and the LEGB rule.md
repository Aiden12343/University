# 8.7 Namespaces and the LEGB rule

When a name is used in an expression, Python resolves it through lexical and runtime rules often summarised as **LEGB**:

1. **Local:** bindings in the current function scope.
2. **Enclosing:** bindings in lexically enclosing function scopes.
3. **Global:** bindings in the module namespace where the function was defined.
4. **Builtins:** names supplied by the built-in namespace.

LEGB is a useful summary, not the complete rule for every class body, comprehension, annotation, exception target, or dynamic operation. “Global” means module-global, not universal across the process.

```python
rate = 2


def outer() -> int:
    offset = 3

    def inner(value: int) -> int:
        return value * rate + offset

    return inner(5)
```

Inside `inner`, `value` is local, `offset` is enclosing, `rate` is global to the module, and `int` is found among builtins when annotations are evaluated under the relevant annotation regime.

Assignment makes a name local to a function scope unless declared `global` or `nonlocal` under applicable rules. This is determined statically for the code block, which can produce `UnboundLocalError`:

```python
count = 10


def broken() -> None:
    print(count)
    count = 11
```

Because `count` is assigned anywhere in the function body, it is classified as local. The print attempts to read that local binding before the assignment executes. It does not fall back to the module binding.

`global count` declares that assignments in the function target the module-global binding. `nonlocal count` targets a binding in a nearest applicable enclosing function scope. Both create non-local effects and should be used when that shared state is an intentional interface, not as a substitute for returning a value.

### Worked example 8.3 — `nonlocal` state

```python
def make_counter(start: int = 0):
    count = start

    def increment() -> int:
        nonlocal count
        count += 1
        return count

    return increment


counter = make_counter(10)
print(counter())
print(counter())
```

Output is 11 then 12. The returned `increment` function retains access to the enclosing binding `count` after the outer call has returned. `nonlocal` makes augmented assignment target that cell rather than creating a new local `count`.

### 8.7.1 Namespace, scope, and binding are distinct

A **namespace** is a mapping-like association from names to objects. A **scope** is a source-text region in which a namespace or binding rule is directly applicable. A **binding** is one association established under those rules.

The module namespace can be inspected through <code>globals()</code>. Built-in names come from the <code>builtins</code> module under ordinary execution. Function locals are represented by frames and optimized storage, even though <code>locals()</code> exposes a mapping view. These namespaces do not combine into one physical dictionary called LEGB; LEGB summarizes a resolution search for many expression-name loads.

### 8.7.2 Global means the defining module

A function retains the global namespace in which it was defined. Calling it from another module does not make the caller’s globals visible by unqualified name.

Conceptually, if module <code>rates</code> defines:

~~~python
tax_rate = 0.20


def tax(amount: float) -> float:
    return amount * tax_rate
~~~

then importing and calling <code>rates.tax</code> elsewhere resolves <code>tax_rate</code> in module <code>rates</code>. This lexical/module stability enables a function to use its implementation dependencies regardless of who calls it.

Module globals remain dynamic. Rebinding <code>rates.tax_rate</code> can change later calls unless the dependency was captured in a default or closure. “Lexical resolution” identifies the namespace, not a frozen value.

### 8.7.3 Built-ins are the last ordinary fallback

Names such as <code>len</code>, <code>int</code>, <code>open</code>, and <code>Exception</code> ordinarily resolve in the built-in namespace if not shadowed earlier.

~~~python
len = 5
# len([1, 2])                 # TypeError: integer is not callable
~~~

The module binding shadows the built-in. The built-in remains accessible explicitly:

~~~python
import builtins

print(builtins.len([1, 2]))
~~~

Avoid shadowing established built-ins in scopes where readers or tools will expect them. Shadowing is not syntactically prohibited because domain names sometimes legitimately coincide, but it changes all unqualified uses in that scope.

The injected name <code>__builtins__</code> can be a module or dictionary and is primarily an implementation facility. Use the documented <code>builtins</code> module when explicit access is required.

### 8.7.4 Local bindings are determined by the whole code block

The compiler constructs a symbol table before calls execute. In an ordinary function, any binding operation makes the name local unless declared otherwise. This includes an assignment that is textually after a return or on a branch believed impossible:

~~~python
value = 10


def broken() -> int:
    result = value
    if False:
        value = 20
    return result
~~~

Calling <code>broken</code> raises <code>UnboundLocalError</code> at <code>result = value</code>. Runtime branch reachability does not change lexical classification.

Deleting a local name also counts as a binding-affecting operation because deletion targets the local namespace:

~~~python
item = "global"


def remove_local() -> str:
    result = item
    del item
    return result
~~~

This likewise reads an unbound local. Name classification and runtime binding state are separate axes.

### 8.7.5 Free variables and cell variables

A **free variable** in a code block is used there but bound in an enclosing function scope. A **cell variable** is a local binding retained so nested code can access it.

~~~python
def outer(prefix: str):
    count = 0

    def inner(message: str) -> str:
        return f"{prefix}:{count}:{message}"

    return inner
~~~

For <code>inner</code>, <code>prefix</code> and <code>count</code> are free variables. In <code>outer</code>, they become cell-backed bindings because nested code needs them after the outer frame’s ordinary return. The closure retains cells, not a copied dictionary of all outer locals. An unused outer local need not be retained.

Introspection can reveal closure cells:

~~~python
function = outer("INFO")
print(function.__code__.co_freevars)
print([cell.cell_contents for cell in function.__closure__ or ()])
~~~

Names/order and code-object details should be treated as introspection surfaces with implementation/version qualifications, not stable application storage.

### 8.7.6 nonlocal selects an existing enclosing function binding

<code>nonlocal name</code> tells the compiler that assignments target the nearest applicable binding in an enclosing function scope. It cannot create a new binding and cannot designate a module global.

~~~python
def make_toggle(initial: bool = False):
    state = initial

    def toggle() -> bool:
        nonlocal state
        state = not state
        return state

    return toggle
~~~

If no enclosing function scope binds <code>state</code>, the declaration is a syntax error. The requirement makes lexical ownership statically identifiable.

In several nested scopes, the nearest binding wins:

~~~python
def level_one():
    value = 1

    def level_two():
        value = 2

        def level_three():
            nonlocal value
            value = 3

        level_three()
        return value

    return level_two(), value
~~~

The result is <code>(3, 1)</code>. <code>level_three</code> changes <code>level_two</code>’s cell, not the more distant <code>level_one</code> binding.

### 8.7.7 global is a compile-time declaration with module effects

~~~python
counter = 0


def increment() -> int:
    global counter
    counter += 1
    return counter
~~~

The declaration makes both load and store target the defining module’s namespace. It does not create process-wide shared state across modules or processes. It applies to the code block containing the declaration, not automatically to nested functions.

Using or binding the same name before its <code>global</code> declaration in that block is a syntax error. The declaration is a parser/compiler directive, not a statement whose effect begins only when control reaches it.

Global mutable state couples tests, call ordering, reload behaviour, and concurrency. It is appropriate for some module constants and registries with explicit ownership; updates often benefit from an object or injected dependency rather than scattered <code>global</code> statements.

### 8.7.8 Enclosing resolution reads cells dynamically

~~~python
def pair():
    value = "before"

    def read() -> str:
        return value

    value = "after"
    return read


reader = pair()
print(reader())                # after
~~~

The inner function consults the retained binding at call time. The cell was rebound before <code>outer</code> returned. If another enclosed function later uses <code>nonlocal</code> to rebind it, <code>read</code> observes the new object. This is late binding.

Mutation can change a captured object without <code>nonlocal</code> because the binding itself remains fixed:

~~~python
def collector():
    values: list[int] = []

    def add(value: int) -> None:
        values.append(value)

    return add
~~~

<code>nonlocal values</code> would be needed only to rebind <code>values</code>, not to call mutation methods on the list it already designates.

### 8.7.9 Class bodies are not ordinary enclosing function scopes

A class statement executes a body in a new namespace, later passed to class construction. Methods defined within it do not generally resolve unqualified names through that class namespace as an enclosing lexical scope:

~~~python
class Scale:
    factor = 3

    def apply(self, value: int) -> int:
        return value * self.factor
~~~

Writing <code>return value * factor</code> would search the method’s locals, enclosing function scopes if any, module globals, and built-ins—not ordinary class attribute <code>factor</code>. Attribute access through <code>self</code> or <code>Scale</code> states class/instance lookup.

Class body name resolution has special rules: an unbound local-style name can fall back to globals, and the compiler may create an implicit <code>__class__</code> closure for methods using zero-argument <code>super()</code> or <code>__class__</code>. Chapter 9 gives the full class construction and descriptor model.

### 8.7.10 Comprehensions usually have their own function-like scope

In Python 3, comprehension iteration variables do not ordinarily leak into the surrounding scope:

~~~python
index = 100
squares = [index * index for index in range(3)]
print(index)                   # 100
~~~

The comprehension’s <code>index</code> is local to its implicit scope. The leftmost iterable expression is evaluated in the enclosing scope before the implicit nested execution proceeds, as Chapter 6 established.

Comprehensions inside class bodies expose a notorious consequence: their nested scope does not generally treat class-local bindings as an enclosing function namespace.

~~~python
class Example:
    base = 10
    # values = [base + item for item in range(3)]
    # The unqualified base is not an ordinary enclosing class-cell lookup.
~~~

Move the computation outside, use a helper, or assign after class creation according to the intended design. Python 3.12 annotation scopes have additional class-namespace visibility for type-related syntax; this special case belongs to Chapter 12 and should not be generalized to ordinary comprehensions.

### 8.7.11 Exception target names are cleared

An exception handler target is local to the surrounding block but is cleared after the handler to break reference cycles involving exceptions, tracebacks, frames, and locals:

~~~python
def handle() -> None:
    try:
        int("not an integer")
    except ValueError as error:
        print(error)

    # print(error)             # UnboundLocalError
~~~

Conceptually, the target is cleaned up as the handler ends. If information must survive, derive a bounded value into another name:

~~~python
def message() -> str:
    text = "no failure"
    try:
        int("bad")
    except ValueError as error:
        text = str(error)
    return text
~~~

Retaining the exception itself can retain the traceback graph; retain only what the later contract needs.

### 8.7.12 Pattern captures are bindings

Structural pattern matching capture names bind in the containing local scope rather than a hidden case-only scope:

~~~python
def coordinate(subject: object) -> int:
    match subject:
        case (x, y):
            return x + y
        case _:
            return 0
~~~

The compiler classifies <code>x</code> and <code>y</code> as locals. A successful matching case binds them. Code after matching must account for paths on which no capture occurred. The language deliberately leaves some bindings after a failed pattern as unspecified implementation latitude, so programs must not rely on partial captures from a pattern that did not succeed.

### 8.7.13 Import statements bind names

~~~python
import math
from collections import deque as queue_type
~~~

The first statement binds <code>math</code>; the second binds <code>queue_type</code>. Inside a function, these are local unless declared global. This can create the same read-before-local defect:

~~~python
import math


def broken_import(flag: bool):
    if flag:
        import math
    return math.pi
~~~

With false flag, local <code>math</code> was never bound. Imports are executable binding operations, not compiler-only inclusions.

### 8.7.14 Function and class definitions bind names

Inside a function, a nested <code>def helper</code> or <code>class Record</code> binds its name locally when execution reaches that statement. A call before the statement raises because the local exists lexically but has not yet been bound dynamically:

~~~python
def outer() -> int:
    # return helper()          # would read before binding
    def helper() -> int:
        return 3
    return helper()
~~~

This differs from languages that hoist function declarations. In Python, definition statements execute in sequence.

### 8.7.15 Assignment expressions obey scope-specific rules

The assignment expression operator <code>:=</code> binds a name while yielding the assigned value. In a function it ordinarily creates/updates a local under the same static classification. Comprehensions have special rules designed so selected assignment-expression targets bind in the containing scope rather than the implicit comprehension scope, while binding in iterable clauses is restricted.

~~~python
def last_long(words: list[str]) -> str | None:
    found: str | None = None
    matches = [word for word in words if len(found := word) > 10]
    return found
~~~

This code returns the last iterated word, not necessarily the last match, because assignment occurs before the length condition for every word. It also constructs an unused list. The example is intentionally poor: scope-aware compact syntax can still obscure the intended temporal meaning. An explicit loop is better.

### 8.7.16 Dynamic evaluation does not rewrite lexical compilation

<code>eval</code> and <code>exec</code> can evaluate code with supplied global and local mappings, but they do not provide a reliable mechanism for creating optimized local bindings that surrounding compiled bytecode then treats as declared locals.

~~~python
namespace: dict[str, object] = {}
exec("answer = 42", namespace)
print(namespace["answer"])
~~~

Here the explicit dictionary owns the dynamic namespace. This is the tractable model. Executing untrusted text is arbitrary code execution, not data parsing; never use it for configuration or user expressions without a security design. Safer parsers and domain grammars belong at such boundaries.

### 8.7.17 Dependency injection avoids hidden global lookup

Compare:

~~~python
def load_global(identifier: str):
    return database.fetch(identifier)
~~~

with:

~~~python
def load_explicit(database, identifier: str):
    return database.fetch(identifier)
~~~

The first resolves a module-global dependency at call time. The second receives it explicitly. Explicit dependency injection makes tests and concurrent configurations easier, but can produce long parameter chains. A closure factory or service object can bind a stable dependency once while keeping it visible in construction.

Scope rules are not only language trivia: they determine configuration timing, test substitution, lifecycle, and coupling.

### Worked example 8.3B — Symbol classification dossier

~~~python
threshold = 10


def make_filter(offset: int):
    accepted = 0

    def keep(value: int) -> bool:
        nonlocal accepted
        adjusted = value + offset
        if adjusted >= threshold:
            accepted += 1
            return True
        return False

    def count() -> int:
        return accepted

    return keep, count
~~~

For <code>make_filter</code>, <code>offset</code> and <code>accepted</code> are locals and cell variables because nested functions use them. <code>keep</code> and <code>count</code> are local bindings created by definition statements. For <code>keep</code>, <code>value</code> and <code>adjusted</code> are locals; <code>offset</code> and <code>accepted</code> are free variables; <code>threshold</code> is global; ordinary types/functions referenced by annotations/operations resolve according to their evaluation contexts. <code>nonlocal</code> permits rebinding <code>accepted</code>. For <code>count</code>, <code>accepted</code> is free.

Both returned functions share the same accepted cell created by one <code>make_filter</code> call. A second factory call creates an independent cell. Rebinding module <code>threshold</code> affects later <code>keep</code> calls because it is global and not captured as a default. This one example distinguishes local, cell, free, global, shared closure, and call-instance state.

### Worked example 8.3C — Remove hidden state by returning a transition

Closure state:

~~~python
def make_accumulator(start: int = 0):
    total = start

    def add(value: int) -> int:
        nonlocal total
        total += value
        return total

    return add
~~~

Pure transition alternative:

~~~python
def add_to_total(total: int, value: int) -> int:
    return total + value


total = 0
total = add_to_total(total, 5)
~~~

The closure encapsulates mutation and offers convenient sequential use, but its state is implicit in the callable’s identity, not serializable by value through the signature, and needs coordination for overlapping calls. The pure transition makes old and new state explicit and is easier to replay, test, and distribute; callers must manage the state binding. Neither universally dominates.

> **Common misconception — “LEGB means Python searches every enclosing block.”**  
> Ordinary lexical enclosure is primarily through functions. Class bodies, comprehensions, exception targets, annotation scopes, and dynamic execution have specific rules that the mnemonic does not encode.
