# 8.8 First-class functions

Functions are **first-class objects**: they can be bound to names, stored in collections, passed as arguments, returned as results, and inspected like other objects.

```python
def double(value: int) -> int:
    return value * 2


operation = double
print(operation(6))
```

`operation = double` does not call the function because there are no call parentheses. It binds another name to the same function object. `operation(6)` later invokes it.

A **higher-order function** accepts a function, returns a function, or both.

```python
from collections.abc import Callable, Iterable


def transform_all(
    operation: Callable[[int], int],
    values: Iterable[int],
) -> list[int]:
    return [operation(value) for value in values]


print(transform_all(double, [1, 2, 3]))
```

`Callable[[int], int]` states an intended callable accepting one integer and returning one integer. The contract is structural: any compatible callable can be supplied, not only a function created with `def`.

`map` and `filter` are built-in higher-order functions returning lazy iterators, but comprehensions often make simple transformation and selection clearer. Higher-order functions become especially valuable when behaviour itself is configurable or composed.

### 8.8.1 Callable is a behavioural protocol

A **callable** is an object that supports call syntax. Functions are callable, but so are built-in functions, bound methods, classes, and instances whose classes define <code>__call__</code>. The predicate <code>callable(obj)</code> asks whether an object appears callable; it does not prove that every argument list will bind or that a call will succeed.

~~~python
print(callable(len))           # True
print(callable(str))           # True: calling a class constructs/converts
print(callable(42))            # False
~~~

An interface accepting behaviour should specify the signature and semantic contract, not merely “callable.” A callback that accepts one event but blocks for an hour technically binds and yet may violate latency requirements.

### 8.8.2 Function aliases share one object and its state

~~~python
def transform(value: int) -> int:
    return value * 2


first_name = transform
second_name = transform
assert first_name is second_name
~~~

The aliases designate one function object, including defaults, annotations, attributes, and closure cells. Assigning an attribute through one alias is visible through the other:

~~~python
first_name.description = "double an integer"
print(second_name.description)
~~~

Arbitrary function attributes can carry metadata but are mutable shared state and often poorly discoverable. Prefer explicit registration structures or decorated metadata with a defined schema.

Function equality ordinarily falls back to identity: two separately evaluated but textually identical lambda expressions are distinct keys in a set or dictionary. Behavioural equivalence of arbitrary functions is not generally decidable.

### 8.8.3 Passing behaviour implements policy injection

~~~python
from collections.abc import Callable, Iterable


def select_best(
    values: Iterable[str],
    score: Callable[[str], int],
) -> str:
    return max(values, key=score)
~~~

The traversal mechanism is fixed; the scoring policy is injected. Callers can choose <code>len</code>, a named function, a closure with configuration, or another compatible callable.

The contract must decide how often and in what order <code>score</code> runs, whether it may have effects, how ties are resolved, and what happens for an empty iterable. Here <code>max</code> consumes the iterable, evaluates keys under its contract, returns the first maximal item under ordinary ties, and raises <code>ValueError</code> on empty input.

Higher-order design reduces duplicated mechanisms only when the callback boundary is more stable than separate functions would be. Passing numerous tiny behaviours through many layers can obscure control flow.

### 8.8.4 Callbacks invert control

When a function calls a caller-supplied function, control temporarily returns to code chosen by the caller. This is **inversion of control**. The host must treat the callback as a re-entrancy and failure boundary:

~~~python
def visit(values: list[int], callback: Callable[[int], None]) -> None:
    for value in values:
        callback(value)
~~~

The callback may mutate <code>values</code>, raise, retain <code>value</code>, call <code>visit</code> recursively, or block. If the host requires stable iteration, it can document “callback must not mutate values,” iterate a snapshot, or hide the structure entirely and expose immutable values.

Framework callbacks similarly reverse the usual dependency: user code does not directly determine when it is called. Lifecycle, ordering, exception routing, thread/task context, and deregistration become interface requirements.

### 8.8.5 Map, filter, comprehensions, and explicit loops

<code>map(function, iterable)</code> lazily applies one function to successive values. <code>filter(predicate, iterable)</code> lazily retains values whose predicate is truthy.

~~~python
numbers = [1, 2, 3, 4]
doubled = map(lambda value: value * 2, numbers)
even = filter(lambda value: value % 2 == 0, numbers)
~~~

Equivalent simple comprehensions are often more legible:

~~~python
doubled_list = [value * 2 for value in numbers]
even_list = [value for value in numbers if value % 2 == 0]
~~~

These lists are eager, while <code>map</code>/<code>filter</code> return iterators. Generator expressions preserve laziness. <code>map</code> is especially clear with an already named callable or several parallel iterables; comprehension syntax is clear when transformation and filtering need local expressions. Explicit loops are best when control flow, multiple effects, error accumulation, or intermediate names matter.

### 8.8.6 Reduction folds a sequence into state

A **fold** repeatedly combines an accumulator with each input. The built-in <code>sum</code>, <code>min</code>, <code>max</code>, <code>any</code>, and <code>all</code> are specialised folds. <code>functools.reduce</code> expresses a general binary fold:

~~~python
from functools import reduce
from operator import mul

product = reduce(mul, [2, 3, 5], 1)
~~~

The initial accumulator 1 is the multiplicative identity. The conceptual transition is:

\[
a_0=1,\qquad a_{i+1}=a_i\times x_i.
\]

An explicit loop often communicates the invariant more clearly and can validate or short-circuit. Reduction order matters for non-associative operations, floating rounding, effects, and exceptions. A parallel fold is valid only when the combining algebra and ordering policy permit regrouping.

### 8.8.7 Function composition

For compatible pure functions \(f:A\to B\) and \(g:B\to C\), composition is

\[
(g\circ f)(x)=g(f(x)).
\]

~~~python
from collections.abc import Callable
from typing import TypeVar

A = TypeVar("A")
B = TypeVar("B")
C = TypeVar("C")


def compose(
    outer: Callable[[B], C],
    inner: Callable[[A], B],
) -> Callable[[A], C]:
    def composed(value: A) -> C:
        return outer(inner(value))
    return composed
~~~

Runtime Python does not enforce the type variables; static analysis can check many uses. Operational composition means <code>inner</code> runs first. If it raises, <code>outer</code> does not run. Effects do not commute merely because mathematical diagrams do.

Deep chains of anonymous composition can make tracebacks and debugging harder. Named pipeline stages often provide better domain vocabulary and error context.

### 8.8.8 Partial application binds some arguments

**Partial application** creates a callable by fixing selected arguments of another callable:

~~~python
from functools import partial


def power(base: int, exponent: int) -> int:
    return base**exponent


square = partial(power, exponent=2)
print(square(7))               # 49
~~~

The partial object retains references to <code>power</code> and the bound argument object. It is not a closure function, though both can implement similar behaviour. Mutable bound arguments remain shared. Signature introspection and metadata differ, and type inference for complex partial calls may be limited.

Partial application differs from currying. **Currying** transforms a multi-argument function into nested one-argument functions across its complete argument structure; partial application simply fixes some arguments.

### 8.8.9 Operator functions make syntax passable

The <code>operator</code> module exposes functions corresponding to operators and common projections:

~~~python
from operator import attrgetter, itemgetter

rows = [
    {"name": "Grace", "score": 95},
    {"name": "Ada", "score": 98},
]

rows.sort(key=itemgetter("score"), reverse=True)
~~~

<code>itemgetter("score")</code> creates a callable performing subscription with that key. <code>attrgetter</code> performs attribute access, potentially traversing dotted names. These functions can be clearer and sometimes faster than trivial lambdas, but they still invoke the underlying object protocol and can raise.

### 8.8.10 Dispatch tables replace some conditional chains

Because functions are values, a mapping can associate command names with handlers:

~~~python
from collections.abc import Callable


def add(left: int, right: int) -> int:
    return left + right


def subtract(left: int, right: int) -> int:
    return left - right


OPERATIONS: dict[str, Callable[[int, int], int]] = {
    "add": add,
    "subtract": subtract,
}


def calculate(name: str, left: int, right: int) -> int:
    try:
        operation = OPERATIONS[name]
    except KeyError as error:
        raise ValueError(f"unknown operation: {name!r}") from error
    return operation(left, right)
~~~

The table centralises name-to-behaviour association and supports expected direct lookup. It also becomes a registry whose mutation authority, duplicate registration, initialization order, and thread safety must be controlled. For a closed command algebra with distinct data shapes, structural matching or classes may be clearer.

Never populate a dispatch table from untrusted names by calling <code>globals()</code> or arbitrary attribute lookup. An allowlisted mapping defines the capability boundary.

### 8.8.11 Bound methods are temporary callable objects

Chapter 9 explains descriptor binding in full. Minimally, retrieving a normal function through an instance produces a bound method that retains the instance as its receiver:

~~~python
class Counter:
    def increment(self, amount: int) -> int:
        ...


counter = Counter()
operation = counter.increment
~~~

The callable <code>operation</code> retains <code>counter</code>. Storing it in a long-lived registry therefore retains the instance. Two separate attribute accesses may create distinct bound-method objects that nevertheless compare according to method semantics; do not assume attribute retrieval returns the identical method object each time.

### 8.8.12 Callback failure policy belongs to the host

A host invoking several callbacks must decide whether to:

- stop at the first failure;
- invoke all and aggregate exceptions;
- isolate and log individual failures;
- retry selected failures;
- remove failing callbacks;
- run callbacks transactionally or outside a committed transition.

~~~python
def notify_all(
    callbacks: list[Callable[[str], None]],
    message: str,
) -> list[Exception]:
    failures: list[Exception] = []
    for callback in tuple(callbacks):
        try:
            callback(message)
        except Exception as error:
            failures.append(error)
    return failures
~~~

The tuple snapshot prevents registration-list structural changes from altering this notification’s membership. It does not isolate mutable callback state or asynchronous effects. Catching <code>Exception</code> lets control exceptions such as <code>KeyboardInterrupt</code> propagate, while aggregating ordinary callback failures as data. Retaining exception objects can retain tracebacks, so production code may convert them to bounded diagnostics.

### Worked example 8.4A — Strategy injection with proof obligations

Requirement: choose one shortest string from a non-empty iterable, breaking equal-length ties using a supplied ranking key.

~~~python
from collections.abc import Callable, Iterable
from typing import TypeVar

T = TypeVar("T")


def shortest_by(
    values: Iterable[str],
    tie_key: Callable[[str], T],
) -> str:
    iterator = iter(values)
    try:
        best = next(iterator)
    except StopIteration as error:
        raise ValueError("shortest_by requires a value") from error

    best_key = (len(best), tie_key(best))
    for candidate in iterator:
        candidate_key = (len(candidate), tie_key(candidate))
        if candidate_key < best_key:
            best = candidate
            best_key = candidate_key

    return best
~~~

Loop invariant: after consuming a non-empty prefix, <code>best</code> belongs to that prefix and <code>best_key</code> is minimal among its derived keys; ties retain the earliest equal complete key because replacement uses strict less-than. Initialization establishes the invariant for the first element. Each comparison either retains the minimal prior candidate or installs a strictly smaller one. At exhaustion, the prefix is the full input, proving the result.

The callback must return keys sharing a coherent ordering, and it runs once per input. If it has effects or depends on changing state, the proof’s fixed-key assumption fails. The source is consumed exactly once and may be infinite, in which case the function never returns.

> **Common misconception — “Passing a function passes its result.”**  
> A function object is passed when the name is used without a call. Parentheses invoke it and pass or use the resulting object instead.
