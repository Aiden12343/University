# 8.9 Closures

A **closure** is a function together with retained access to bindings from its lexical environment. The function does not freeze the current values by textual substitution; it retains cells or equivalent binding relationships.

```python
def make_multiplier(factor: int):
    def multiply(value: int) -> int:
        return value * factor
    return multiply


triple = make_multiplier(3)
print(triple(7))
```

The `make_multiplier` call returns, but `triple` retains access to that call’s `factor` binding. This permits function factories, callbacks, and encapsulated state without a class.

### 8.9.1 Late binding in closures

Closures capture bindings, not snapshots of their values. This produces the **late-binding closure** misconception:

```python
functions = []
for number in range(3):
    functions.append(lambda: number)

print([function() for function in functions])
```

The result is ordinarily `[2, 2, 2]`. Each lambda refers to the same surrounding `number` binding. Calls occur after the loop, when that binding holds 2.

If a per-iteration value is required, bind it to a default parameter at function creation:

```python
functions = []
for number in range(3):
    functions.append(lambda number=number: number)
```

Each default expression evaluates during that lambda’s creation, retaining a distinct object in its parameter default. This repair works because default timing and closure timing are understood, not because `lambda` has a special loop exception.

An alternative helper function can establish a new call scope per iteration:

```python
def constant(value: int):
    return lambda: value


functions = [constant(number) for number in range(3)]
```

> **Common misconception — “Closures copy all surrounding variables when created.”**  
> They retain access to needed lexical bindings. If a binding later changes, a closure can observe the new value unless a distinct binding or value capture is deliberately established.

### 8.9.2 Closures retain only referenced lexical bindings

~~~python
def factory(used: object, unused: object):
    def result() -> object:
        return used
    return result
~~~

The inner code has <code>used</code> as a free variable but never mentions <code>unused</code>. The closure needs to retain the former binding, not an entire snapshot of every factory local. This distinction matters for memory: removing an accidental free-variable reference can release a large graph that the returned function otherwise keeps alive.

Default parameter values are retained in the function’s defaults, not closure cells. Module globals are looked up through the function’s global namespace, not captured as cells. Several retention mechanisms can coexist in one function and have different timing.

### 8.9.3 Sibling closures can share one cell

~~~python
def make_account(initial: int = 0):
    balance = initial

    def deposit(amount: int) -> int:
        nonlocal balance
        if amount <= 0:
            raise ValueError("amount must be positive")
        balance += amount
        return balance

    def inspect() -> int:
        return balance

    return deposit, inspect
~~~

The two returned functions retain the same <code>balance</code> cell from one factory call. Depositing through one changes what the other reads. Calling the factory again creates a different cell and independent state.

This gives encapsulation: ordinary callers cannot directly assign the cell by a public name. It does not provide transactional safety, audit history, serialization, or concurrency control. A class can expose the same state relationship with more explicit methods and introspection.

### 8.9.4 Mutation and rebinding remain different in a closure

~~~python
def make_collection():
    values: list[int] = []

    def add(value: int) -> None:
        values.append(value)       # mutate object; no nonlocal needed

    def reset() -> None:
        nonlocal values
        values = []                # rebind cell; nonlocal required

    def snapshot() -> tuple[int, ...]:
        return tuple(values)

    return add, reset, snapshot
~~~

After <code>reset</code>, every sibling closure resolves the cell to the new list. Any external alias to the old list would still see its old contents. If reset instead used <code>values.clear()</code>, aliases would observe an emptied same object. Reset semantics therefore require an identity/alias policy.

### 8.9.5 Late binding is often the desired behaviour

Late binding permits a closure to observe updated shared configuration:

~~~python
def make_formatter():
    precision = 2

    def format_value(value: float) -> str:
        return f"{value:.{precision}f}"

    def set_precision(value: int) -> None:
        nonlocal precision
        if value < 0:
            raise ValueError("precision must be non-negative")
        precision = value

    return format_value, set_precision
~~~

Capturing a snapshot default in <code>format_value</code> would defeat the configuration update. The defect is not late binding itself but a mismatch between desired per-creation snapshot semantics and shared-cell semantics.

### 8.9.6 Loop variables and one shared surrounding binding

At module level, loop variable <code>number</code> is global; lambdas defined there look it up globally. Inside a function, it is a local/cell binding shared by the created closures. In both cases, calls after the loop usually observe the final bound value.

Several repairs encode different intentions:

~~~python
# Capture the current object reference in a default.
functions = [lambda number=number: number for number in range(3)]


# Create one factory-call cell per value.
def make_constant(number: int):
    return lambda: number


functions = [make_constant(number) for number in range(3)]


# Use partial application.
from functools import partial


def identity(number: int) -> int:
    return number


functions = [partial(identity, number) for number in range(3)]
~~~

The default stores values in each function object; the factory stores each in a distinct closure cell; partial objects store bound arguments. Behaviour matches for immutable integers, while introspection, metadata, mutability, and typing differ.

### 8.9.7 Capturing a mutable loop object does not freeze it

~~~python
row = [1]
functions = [lambda row=row: tuple(row)]
row.append(2)
print(functions[0]())          # (1, 2)
~~~

Default capture fixes which list object is referenced, not its future contents. A time-specific value snapshot would require <code>tuple(row)</code> at creation:

~~~python
snapshot = tuple(row)
function = lambda snapshot=snapshot: snapshot
~~~

This is shallow; mutable elements within the tuple remain shared. Capture semantics must name both identity timing and depth.

### 8.9.8 Closure introspection and empty cells

The function object exposes free-variable names through its code object and cells through <code>__closure__</code>. A cell’s contents can raise <code>ValueError</code> if the binding has been deleted and is empty.

~~~python
def make_reader():
    value = 3

    def read():
        return value

    return read


reader = make_reader()
print(reader.__code__.co_freevars)
print(reader.__closure__[0].cell_contents)
~~~

This supports debuggers and educational inspection. Depending on cell order or mutating closure internals is brittle application design. A closure’s behavioural interface should not require callers to know its captured variable names.

### 8.9.9 Closures can create reference cycles

A closure may capture an object that in turn references the closure, forming a cycle:

~~~python
callbacks: list[object] = []


def install():
    def callback() -> int:
        return len(callbacks)

    callbacks.append(callback)
    return callback
~~~

Here <code>callback</code> uses the global list rather than a closure cell, but the global list retains the function indefinitely. A local list captured by a closure and containing the closure would form a direct cycle. CPython’s cyclic collector can reclaim unreachable cycles, but a global registry remains a root and is not garbage.

Callback APIs need deregistration or weak-reference policies when lifetimes should not be global. Weak references introduce their own disappearance and race semantics and are developed with objects in Chapter 9.

### 8.9.10 Closure state is not automatically thread-safe or re-entrant

~~~python
def make_counter():
    count = 0

    def increment() -> int:
        nonlocal count
        count += 1
        return count

    return increment
~~~

The read–add–write transition can lose updates under overlapping execution. A GIL-enabled build does not turn the entire source operation into a contractual transaction. A lock captured alongside state can protect it:

~~~python
from threading import Lock


def make_counter():
    count = 0
    lock = Lock()

    def increment() -> int:
        nonlocal count
        with lock:
            count += 1
            return count

    return increment
~~~

The contract must still address forked processes, callback re-entry, lock ordering, and whether the counter needs persistence. Encapsulation and synchronization are orthogonal.

### 8.9.11 Closure versus callable object

Closure:

~~~python
def make_multiplier(factor: int):
    def multiply(value: int) -> int:
        return factor * value
    return multiply
~~~

Callable object preview:

~~~python
class Multiplier:
    def __init__(self, factor: int) -> None:
        self.factor = factor

    def __call__(self, value: int) -> int:
        return self.factor * value
~~~

The closure is compact and makes captured state private to lexical code. The class offers named state, several methods, inheritance/composition hooks, clearer representation, and more direct serialization/customization possibilities. Both create callable objects retaining a factor. Choose based on interface complexity and lifecycle, not on a rule that one paradigm is superior.

### Worked example 8.4B — Online mean as closure state

For finite numeric observations, the running mean can be updated without retaining all samples:

\[
n'=n+1,
\qquad
\mu'=\mu+\frac{x-\mu}{n'}.
\]

~~~python
from math import isfinite


def make_running_mean():
    count = 0
    mean = 0.0

    def add(value: float) -> float:
        nonlocal count, mean
        if not isfinite(value):
            raise ValueError("value must be finite")

        new_count = count + 1
        new_mean = mean + (value - mean) / new_count

        count = new_count
        mean = new_mean
        return mean

    def state() -> tuple[int, float]:
        return count, mean

    return add, state
~~~

Validation and derivation occur before either cell is rebound, so a domain-invalid value leaves state unchanged. After \(n\) successful calls, the invariant is that <code>count == n</code> and <code>mean</code> equals the result of the stated recurrence over the accepted sequence, subject to floating rounding. Two closures share both cells. Auxiliary state is constant, but numerical error behaviour differs from exact summation followed by division and must be studied for the application.

### Worked example 8.4C — Snapshot versus live configuration closure

~~~python
def make_live_renderer(settings: dict[str, int]):
    def render(value: float) -> str:
        return f"{value:.{settings['precision']}f}"
    return render


def make_snapshot_renderer(settings: dict[str, int]):
    precision = settings["precision"]

    def render(value: float) -> str:
        return f"{value:.{precision}f}"
    return render
~~~

The live renderer captures the dictionary reference and consults its current entry on every call. It observes mutation, can fail if the key is removed, and retains the entire mapping. The snapshot renderer reads one value at factory time and retains only that immutable integer binding. Its behaviour is stable under later dictionary changes.

Neither name-binding mechanism automatically documents the temporal promise; the factory name and contract must.

> **Common misconception — “Capturing a value in a default makes a deep immutable snapshot.”**  
> It captures one object reference at definition time. Mutable state reachable through that object can still change.
