# 9.1 Classes organise object construction and behaviour

A **class** is an object used to construct instances and define behaviour shared through attribute lookup. An **instance** is an object whose type is that class. Classes do not introduce objecthood—integers, functions, modules, and classes themselves are already objects. They provide a programmable way to define new types and participate in Python’s data model.

The problem solved by a class is not “put functions in a container”. A class establishes:

- how valid instances are created;
- which state each instance owns;
- which invariants every public operation preserves;
- how attribute names resolve;
- which protocols the instances support;
- how the type relates to other types.

### Worked example 9.1 — Define a bounded counter

```python
class Counter:
    def __init__(self, start: int = 0) -> None:
        if start < 0:
            raise ValueError("start must be non-negative")
        self._value = start

    @property
    def value(self) -> int:
        return self._value

    def increment(self, amount: int = 1) -> None:
        if amount < 0:
            raise ValueError("amount must be non-negative")
        self._value += amount

    def reset(self) -> None:
        self._value = 0
```

Create and use an instance:

```python
counter = Counter(3)
counter.increment(2)
print(counter.value)  # 5
```

The invariant is `_value >= 0`. Construction establishes it; `increment` and `reset` preserve it. The leading underscore signals that `_value` is a non-public implementation attribute by convention. It is not an access-control barrier: Python permits deliberate access, while API users agree not to depend on it.

`self` is an ordinary parameter conventionally naming the instance receiving a method call. The language does not reserve the spelling, but departing from it harms shared readability.

### 9.1.1 Object, identity, type, and state

Every Python object has an **identity**, a **type**, and a **value/state** as defined by its data model. Identity distinguishes that object from every other object during its lifetime. Type determines supported operations and participates in representation. State comprises information that can affect observable behaviour.

~~~python
left = [1, 2]
right = [1, 2]
alias = left

print(left == right)           # equal list values
print(left is right)           # distinct identities
print(left is alias)           # one identity through two names
print(type(left))              # <class 'list'>
~~~

A class definition creates a new class object, which normally becomes the type of its instances. A class is itself an object with identity, state, and a type—usually a metaclass.

### 9.1.2 State is a graph, not necessarily a flat record

An instance can reach other objects through attributes. Its observable state is therefore often a graph:

~~~python
class Team:
    def __init__(self, name: str, members: list[str]) -> None:
        self.name = name
        self.members = members
~~~

The constructor stores the supplied list reference. Caller and Team can mutate one shared list. If the class contract requires a membership snapshot, it might store <code>tuple(members)</code>. If it requires live shared ownership, retaining the list can be correct. “The object contains a list” is an informal description of a reference edge, not necessarily embedded exclusive storage.

### 9.1.3 Entities and value objects

An **entity** is distinguished by a stable domain identity across changes, such as an account with identifier A-19. A **value object** is distinguished by its attributes: two money values of equal amount/currency are interchangeable under the domain.

This is a modelling distinction, not a Python syntax category. Entity equality may use an immutable identifier even while other fields change. Value equality typically includes all semantic components and usually benefits from immutability and compatible hashing.

~~~python
from dataclasses import dataclass


@dataclass(frozen=True)
class Money:
    minor_units: int
    currency: str
~~~

The dataclass can generate equality from fields, fitting a simple value model. It does not validate currency codes, scale, numeric range, or cross-currency arithmetic. Generated mechanics do not choose domain semantics.

### 9.1.4 A class is a protocol implementation and invariant owner

The strongest reason for a class is to make valid transitions the only supported public way to evolve state. The bounded Counter’s public methods establish/preserve <code>_value &gt;= 0</code>. Exposing a writable <code>value</code> attribute would let callers violate it.

One proof pattern is:

1. constructor establishes invariant \(I\);
2. every public mutator assumes \(I\), validates its own preconditions, and restores \(I\);
3. observers do not mutate invariant-relevant state;
4. internal representation does not escape through mutable aliases that bypass mutators.

If callers can obtain and mutate a referenced list directly, step 4 fails even if every method is correct.

### 9.1.5 Representation exposure

~~~python
class Roster:
    def __init__(self, names: list[str]) -> None:
        self._names = list(names)

    @property
    def names_wrong(self) -> list[str]:
        return self._names
~~~

The constructor defensively snapshots outer membership, but the property returns the internal list. A caller can append without validation. Safer interfaces include:

~~~python
class Roster:
    def __init__(self, names: list[str]) -> None:
        self._names = list(names)

    @property
    def names(self) -> tuple[str, ...]:
        return tuple(self._names)

    def add(self, name: str) -> None:
        if not name:
            raise ValueError("name must be non-empty")
        self._names.append(name)
~~~

The tuple snapshot costs \(O(n)\) per access. An iterator can avoid immediate copy but exposes live mutation timing. A persistent immutable internal representation or read-only sequence wrapper offers other trade-offs. Encapsulation has resource consequences.

### 9.1.6 Classes versus dictionaries

A dictionary can represent fields dynamically:

~~~python
counter = {"value": 0, "maximum": 10}
~~~

It is suitable at schema-flexible boundaries such as decoded JSON. It does not automatically bind behaviour, restrict keys, prevent field deletion, distinguish instances by nominal type, or centralise transitions. A class gives named methods, attribute protocol, construction logic, and a type identity.

Conversely, a class whose only purpose is arbitrary key storage may obscure mapping semantics. Use a mapping when dynamic key membership is the abstraction; use a record/value class when a fixed field vocabulary and invariants are the abstraction.

### 9.1.7 Classes versus closures

Chapter 8 showed a closure-based counter. Both closure and class can retain private evolving state. A class is usually preferable when:

- several operations share state;
- state needs named inspection or serialization;
- inheritance/protocol participation matters;
- many instances need a recognizable type;
- lifecycle and representation require explicit methods.

A closure is attractive for one small callable behaviour with limited state and no need for public structural introspection. Both can leak state through captured/referenced mutables and both require concurrency design.

### 9.1.8 Nominal and structural relationships

<code>isinstance(obj, Class)</code> asks about a nominal/runtime type relationship, influenced by inheritance, abstract base class registration, and metaclass hooks. A **structural protocol** asks whether an object provides required behaviour regardless of declared ancestry.

Python supports both. A function needing iteration should ordinarily accept an Iterable protocol, not demand that every input inherit from one application base class. A domain entity may require nominal identity to distinguish semantically different records with similar fields.

Duck typing—using supported behaviour rather than exact type—does not mean “ignore contracts.” It shifts the contract from ancestry to operations and laws.

### 9.1.9 Type objects are callable factories by convention

~~~python
print(int("42"))
print(list((1, 2)))
print(Counter(3))
~~~

Calling a class invokes its metaclass’s call protocol, normally producing an instance through <code>__new__</code> and <code>__init__</code>. But a metaclass can return another object, cache instances, or modify call semantics. “Class call constructs a fresh instance” is a common convention, not an unrestricted theorem.

### 9.1.10 Class annotations do not necessarily create instance attributes

~~~python
class Point:
    x: float
    y: float
~~~

The annotations populate class annotation metadata but ordinary execution has not assigned <code>x</code> or <code>y</code> values to an instance. Access can fail until construction binds them. A dataclass decorator interprets annotations to generate fields/initialization; that is decorator/library behaviour, not the meaning of every annotated class body.

### 9.1.11 Object responsibilities and aggregate boundaries

An object with one hundred unrelated methods is not cohesive merely because state is placed behind <code>self</code>. A domain **aggregate** groups entities/value objects whose invariants must be changed through one consistency boundary. Other associations can remain references to separately owned objects.

For example, an Order may own line-item consistency but refer to a Customer ID rather than embed and mutate an entire Customer. Aggregate boundaries limit transaction scope and representation graphs. They are application design decisions, not Python inheritance features.

### Worked example 9.1A — Strengthen the bounded counter contract

~~~python
class BoundedCounter:
    def __init__(self, maximum: int, start: int = 0) -> None:
        self._require_integer(maximum, "maximum")
        self._require_integer(start, "start")
        if maximum < 0:
            raise ValueError("maximum must be non-negative")
        if not 0 <= start <= maximum:
            raise ValueError("start outside counter bounds")

        self._maximum = maximum
        self._value = start

    @staticmethod
    def _require_integer(value: object, name: str) -> None:
        if isinstance(value, bool) or not isinstance(value, int):
            raise TypeError(f"{name} must be an integer")

    @property
    def value(self) -> int:
        return self._value

    @property
    def maximum(self) -> int:
        return self._maximum

    def increment(self, amount: int = 1) -> None:
        self._require_integer(amount, "amount")
        if amount < 0:
            raise ValueError("amount must be non-negative")

        proposed = self._value + amount
        if proposed > self._maximum:
            raise OverflowError("counter maximum exceeded")
        self._value = proposed

    def reset(self) -> None:
        self._value = 0
~~~

The invariant is

\[
0\le self._value\le self._maximum,
\qquad
self._maximum\text{ is fixed after construction}.
\]

Construction validates before binding invariant-bearing state. Increment derives <code>proposed</code> and validates it before commit, so ordinary domain failure leaves state unchanged. Properties expose immutable integers. The underscore convention discourages but cannot physically prevent deliberate mutation such as <code>counter._value = -1</code>; Python encapsulation relies on interface discipline.

This implementation is not thread-safe for compound increments and does not persist state. It owns one in-memory, single-owner abstraction.

### Worked example 9.1B — Value semantics versus entity semantics

~~~python
from dataclasses import dataclass


@dataclass(frozen=True)
class Coordinate:
    x: int
    y: int


class Device:
    def __init__(self, identifier: str, location: Coordinate) -> None:
        if not identifier:
            raise ValueError("identifier must be non-empty")
        self.identifier = identifier
        self.location = location
~~~

Two Coordinates with equal components compare equal under generated dataclass value semantics and are hashable because frozen fields are hashable. Two Device instances with the same identifier use identity equality unless Device defines otherwise. That default can be appropriate while the domain’s entity-equality policy is unsettled; defining equality by identifier later requires hash/mutation analysis.

Moving a device can replace its immutable Coordinate value while preserving Device identity. The model separates “same place value” from “same evolving device entity.”

> **Common misconception — “Using a class automatically encapsulates state.”**  
> Encapsulation requires controlled construction, non-leaking representations, and methods that preserve invariants. Public or returned mutable aliases can bypass an otherwise well-written class.
