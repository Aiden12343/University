# 9.10 Composition and delegation

**Composition** constructs an object from cooperating component objects. **Delegation** forwards a responsibility to another object. Composition often produces more explicit ownership and permits components to vary independently.

```python
from collections.abc import Callable
from dataclasses import dataclass


@dataclass(frozen=True)
class Message:
    recipient: str
    body: str


class Notifier:
    def __init__(self, send: Callable[[Message], None]) -> None:
        self._send = send

    def notify(self, message: Message) -> None:
        if not message.recipient:
            raise ValueError("recipient is required")
        self._send(message)
```

`Notifier` composes a sending callable rather than inheriting from a particular mail or messaging client. Tests can supply a recording callable; production can supply a network adapter. The notifier owns validation while delegating transport.

Composition does not automatically eliminate coupling. If `Notifier` depends on many private details of one sender, the boundary remains fragile. The component contract determines flexibility.

### 9.10.1 Composition creates explicit object graphs

If object A stores a reference to B, A is composed with or associated to B under some ownership relation. “Has-a” is only a mnemonic. A may exclusively own B, borrow it temporarily, share it with others, or refer to it weakly. These lifetimes produce different invariants.

~~~python
class ReportService:
    def __init__(self, repository, renderer) -> None:
        self._repository = repository
        self._renderer = renderer
~~~

The service retains both components. It need not construct them, so a composition root can choose implementations. Whether it closes them, whether they are shared, and whether they are thread-safe must be specified.

### 9.10.2 Dependency injection separates assembly from use

Construction injection makes required collaborators explicit and prevents a partially configured service:

~~~python
service = ReportService(
    repository=PostgresReportRepository(connection_pool),
    renderer=HtmlRenderer(template_environment),
)
~~~

An outer **composition root** owns application assembly. Core classes depend on interfaces/protocols rather than importing concrete global clients. Tests substitute in-memory implementations.

Dependency injection does not require a container framework. Explicit constructors preserve discoverability and static checking. Automated containers become useful at large scale but add introspection, lifecycle, and error complexity.

### 9.10.3 Delegation can be narrow or transparent

Narrow delegation exposes only operations the outer abstraction intends:

~~~python
class ReadOnlyCatalogue:
    def __init__(self, repository) -> None:
        self._repository = repository

    def get(self, identifier: str):
        return self._repository.get(identifier)
~~~

Broad dynamic delegation through <code>__getattr__</code> forwards nearly everything and can leak mutators, implementation-specific methods, and future attributes. Explicit methods are verbose but define a stable capability surface and allow translation of types/errors.

### 9.10.4 Adapter changes one interface into another

An **adapter** wraps a component and presents a required interface:

~~~python
class LegacySenderAdapter:
    def __init__(self, legacy_client) -> None:
        self._legacy_client = legacy_client

    def send(self, message: Message) -> None:
        result_code = self._legacy_client.deliver(
            address=message.recipient,
            content=message.body,
        )
        if result_code != 0:
            raise DeliveryError(result_code)
~~~

The adapter translates call shape and error protocol. It may also translate representations, units, async/sync boundaries, and ownership. Translation must preserve meaning; merely renaming methods does not make semantics compatible.

### 9.10.5 Decorator objects add behaviour around a component

The design-pattern sense of **Decorator** uses composition to preserve an interface while adding behaviour:

~~~python
class LoggingRepository:
    def __init__(self, inner, report) -> None:
        self._inner = inner
        self._report = report

    def get(self, identifier: str):
        self._report("get", identifier)
        return self._inner.get(identifier)
~~~

This is related to but not identical with <code>@decorator</code> syntax. The wrapper object can be assembled dynamically and may expose the same Repository protocol. It still changes effects, timing, failure modes, and perhaps identity.

### 9.10.6 Strategy makes policy replaceable

A **strategy** encapsulates one variable algorithm/policy behind a common operation:

~~~python
class Checkout:
    def __init__(self, pricing_policy) -> None:
        self._pricing_policy = pricing_policy

    def total(self, basket) -> int:
        return self._pricing_policy.price(basket)
~~~

Strategies can be objects when configuration/state/multiple methods matter, or plain callables for one operation. Runtime replacement should be controlled: changing policy mid-transaction can produce incoherent results. Snapshot policy per operation when consistency matters.

### 9.10.7 Component ownership includes cleanup

If A constructs and exclusively owns a closeable B, A should define when B is closed. If B is injected/shared, closing it from A may break other owners. Ownership transfer must be explicit.

~~~python
class Service:
    def __init__(self, connection, *, owns_connection: bool = False) -> None:
        self._connection = connection
        self._owns_connection = owns_connection

    def close(self) -> None:
        if self._owns_connection:
            self._connection.close()
~~~

A Boolean ownership flag can be error-prone; separate constructors or context managers may express owned and borrowed lifetimes better. Cleanup must be idempotent or define repeated-close behaviour.

### 9.10.8 Composition can produce cyclic dependencies

A refers to B and B refers to A, preventing independent construction and complicating lifetime:

~~~python
service.repository = repository
repository.service = service
~~~

Cycles may indicate two responsibilities should be one aggregate, or communication should use events/callbacks through a mediator. If a real bidirectional association exists, establish it atomically and use weak references where one direction should not own lifetime.

Garbage collection can reclaim unreachable cycles; it does not solve architectural initialization, serialization, or coupling.

### 9.10.9 Law of Demeter as coupling heuristic

The **Law of Demeter** heuristically advises an object to communicate with close collaborators rather than navigate long chains of internals:

~~~python
# Fragile navigation
order.customer.address.country.tax_policy.rate
~~~

A domain operation such as <code>order.tax_quote(policy_context)</code> or a separate pricing service can own the traversal. The goal is not to ban all chained access—immutable data projections can be transparent—but to avoid coupling callers to several objects’ representation and lifecycle.

### 9.10.10 Null Object versus None

A **Null Object** implements a protocol with neutral behaviour:

~~~python
class NullReporter:
    def record(self, event: str, fields: dict[str, object]) -> None:
        pass
~~~

Injecting it can avoid repeated <code>if reporter is not None</code> branches. It is appropriate when “do nothing successfully” is a legitimate strategy. It is dangerous when absence should be detected, when dropped events matter, or when a no-op conceals misconfiguration.

### 9.10.11 Component failure needs translation boundaries

Notifier delegates to a transport. If the transport raises socket/library-specific errors, should Notifier expose them? A stable outer contract may translate into <code>NotificationDeliveryError</code> with the original cause.

The outer component should not catch failures it cannot contextualize or recover from. It also must not claim atomic notification if the transport can deliver and then lose the acknowledgement. Composition makes the boundary explicit, but partial failure remains a systems problem.

### 9.10.12 Prefer composition is not an absolute law

Composition introduces extra objects, forwarding methods, lifetime management, and potential identity distinctions. Inheritance can be the clearest expression for genuine substitutable families and framework-defined extension protocols.

The defensible principle is:

- choose inheritance for a stable behavioural subtype relation;
- choose composition to assemble capabilities or reuse implementation without asserting subtype;
- choose a plain function/module when persistent object identity adds no value.

### Worked example 9.5A — Composed export service

~~~python
from dataclasses import dataclass
from typing import Protocol


@dataclass(frozen=True)
class Export:
    media_type: str
    payload: bytes


class RecordSource(Protocol):
    def records(self, report_id: str) -> tuple[dict[str, object], ...]: ...


class Renderer(Protocol):
    def render(self, records: tuple[dict[str, object], ...]) -> Export: ...


class ExportService:
    def __init__(self, source: RecordSource, renderer: Renderer) -> None:
        self._source = source
        self._renderer = renderer

    def export(self, report_id: str) -> Export:
        if not report_id:
            raise ValueError("report ID must be non-empty")
        records = self._source.records(report_id)
        return self._renderer.render(records)
~~~

The service owns input validation and sequencing. The source owns retrieval; the renderer owns representation. Tuple snapshots provide a stable outer collection if source honours the protocol; mutable dictionaries inside remain a weakness. Export is immutable only shallowly because bytes/string are immutable and its fields contain no mutable values.

Tests inject recording components and assert call order. Production can combine database/cloud sources and CSV/PDF renderers without an inheritance cross-product. Error translation and async behaviour remain to be designed.

### Worked example 9.5B — Explicit delegation over __getattr__ forwarding

~~~python
class SafeStore:
    def __init__(self, inner) -> None:
        self._inner = inner

    def read(self, key: str) -> bytes | None:
        return self._inner.read(key)

    def write(self, key: str, value: bytes) -> None:
        if not key:
            raise ValueError("empty key")
        self._inner.write(key, value)
~~~

Dynamic delegation would also expose <code>delete_all</code>, <code>raw_connection</code>, or future methods accidentally. Explicit forwarding defines the capability set, adds validation, and permits error translation. The cost is maintained boilerplate; code generation or Protocol checking can reduce drift without making the surface implicit.

> **Common misconception — “Composition means the outer object owns every component exclusively.”**  
> A stored reference may be owned, borrowed, or shared. Construction, mutation, cleanup, and lifetime authority must be specified independently.
