# 9.11 Polymorphism and protocols

**Polymorphism** is the ability to use one operation across values of different types under a shared contract. Python frequently uses **structural polymorphism**: suitability follows supported behaviour rather than declared inheritance. The informal phrase **duck typing** means that code relies on relevant operations rather than demanding one concrete type.

```python
def total_length(items) -> int:
    return sum(len(item) for item in items)
```

This works for any iterable whose produced objects support `len`, regardless of a shared application class. The contract should still be documented or typed; “duck typing” is not permission to discover arbitrary requirements only through failure.

A **protocol** is a behavioural interface recognised through supported operations. Iteration, context management, numeric operations, containment, and callability are protocols in Python’s data model. Static typing can express structural protocols with `typing.Protocol`.

```python
from typing import Protocol


class SupportsClose(Protocol):
    def close(self) -> None: ...


def close_resource(resource: SupportsClose) -> None:
    resource.close()
```

An object need not inherit `SupportsClose` to satisfy the static structural contract. Runtime behaviour still depends on the method being present and correct.

### 9.11.1 Several meanings of polymorphism

Computer science uses **polymorphism** for several mechanisms:

- **subtype polymorphism:** a value of a subtype is used through a supertype interface;
- **structural polymorphism:** compatibility follows available members rather than declared ancestry;
- **parametric polymorphism:** code works uniformly over a type parameter, such as selecting the first element of <code>Sequence[T]</code>;
- **ad hoc polymorphism:** one operation has type-specific implementations, as with <code>+</code> or <code>len</code> protocols.

Python combines these at runtime and in static typing. Calling them all “duck typing” loses useful distinctions.

### 9.11.2 A protocol includes laws, not only method names

An iterator has <code>__iter__</code> and <code>__next__</code>, but the protocol also requires that <code>iter(iterator)</code> return the iterator itself and that exhaustion remain stable under ordinary calls. A mapping’s keys are unique under equality/hash and subscription corresponds to those keys.

A class can expose correctly spelled methods while violating these laws. Runtime attribute checks and static structural typing verify shapes, not all temporal/algebraic behaviour. Protocol documentation and contract tests remain necessary.

### 9.11.3 Structural use without a declared Protocol

~~~python
def first_line(source) -> str:
    return source.readline()
~~~

At runtime this accepts any object whose attribute lookup yields a compatible callable. This is dynamic structural polymorphism. Failure appears when the operation is missing or misbehaves.

Annotations can make the requirement visible:

~~~python
from typing import Protocol


class LineReader(Protocol):
    def readline(self) -> str: ...


def first_line(source: LineReader) -> str:
    return source.readline()
~~~

Implementations need not inherit LineReader. Static tools compare structure. Runtime execution remains ordinary attribute/call dispatch.

### 9.11.4 Protocol segregation

Depending on one small capability is more reusable than requiring a large service interface:

~~~python
class SupportsRead(Protocol):
    def read(self, size: int = -1) -> bytes: ...


def digest_source(source: SupportsRead) -> bytes:
    ...
~~~

Requiring a complete file class would exclude sockets, memory buffers, compressed streams, or test doubles that can satisfy reading. This is the **interface segregation principle**: clients should not depend on operations they do not use.

Over-segregating every method into a new named protocol can burden a codebase. Define capability boundaries that recur or carry meaningful laws.

### 9.11.5 Attributes in Protocols

~~~python
class Named(Protocol):
    name: str
~~~

A writable protocol attribute generally implies both reading and assignment compatibility, which creates invariance concerns in static typing. If consumers only read, a read-only property expresses narrower requirements:

~~~python
class Named(Protocol):
    @property
    def name(self) -> str: ...
~~~

An implementation may satisfy it with a property or compatible attribute. Read/write capability affects subtype variance and mutability contracts; Chapter 12 formalises these static rules.

### 9.11.6 Runtime-checkable Protocols are shallow probes

~~~python
from typing import Protocol, runtime_checkable


@runtime_checkable
class Closeable(Protocol):
    def close(self) -> None: ...
~~~

Then <code>isinstance(obj, Closeable)</code> can inspect required member presence under documented version behaviour. It does not verify the full signature, return value, effects, idempotency, or correctness of close. Dynamic attribute access can make checks expensive or misleading.

If the code will call <code>close</code> immediately and can naturally handle <code>AttributeError</code>/<code>TypeError</code>, direct use may be clearer. Runtime protocol checking is useful when dispatch or diagnostics need a declared category, not as proof.

### 9.11.7 EAFP and capability invocation

Python style often prefers attempting a narrowly expected operation and handling its specified failure (**EAFP**) over broad pre-probing. For example, rather than <code>hasattr(resource, "close")</code> and then calling, an owner may define a Closeable contract and call directly.

Pre-probing can race with mutation and execute dynamic lookup twice. Yet catching <code>AttributeError</code> around an entire complex operation can suppress an internal bug. Keep try regions narrow and know which exception means unsupported capability.

### 9.11.8 Nominal types distinguish equal structure with different meaning

Metres and seconds can both expose a numeric <code>value</code> attribute and arithmetic methods. Structural sameness does not make them substitutable. Nominal wrapper types or distinct value classes preserve units and prevent accidental mixing.

~~~python
@dataclass(frozen=True)
class Metres:
    value: float


@dataclass(frozen=True)
class Seconds:
    value: float
~~~

Protocol-oriented design is not a demand to erase nominal domain categories. Use structural interfaces for shared operations whose semantics truly align.

### 9.11.9 Protocol default implementations require inheritance

A Protocol class can contain method bodies, but an implementation that merely structurally matches does not inherit those bodies. Only explicit inheritance supplies them through MRO.

~~~python
class JsonWritable(Protocol):
    def to_mapping(self) -> dict[str, object]: ...

    def to_json(self) -> str:
        import json
        return json.dumps(self.to_mapping())
~~~

A class with <code>to_mapping</code> satisfies part of structure but does not magically gain <code>to_json</code> without inheriting or defining it. If reusable implementation matters without nominal coupling, a free function <code>to_json(value: JsonWritable)</code> is explicit.

### 9.11.10 Optional protocol members are design tension

A client that sometimes uses <code>flush</code> and sometimes does not may define two protocols—Writer and FlushableWriter—rather than one method that may raise <code>NotImplementedError</code>. Capability-specific functions can accept the narrow type.

An operation advertised in a protocol but unsupported for some implementations weakens substitutability. Optional capability discovery is appropriate for extensible systems but must have a clear fallback and runtime detection method.

### 9.11.11 Protocol composition

~~~python
class Readable(Protocol):
    def read(self, size: int = -1) -> bytes: ...


class Writable(Protocol):
    def write(self, data: bytes) -> int: ...


class ReadWrite(Readable, Writable, Protocol):
    pass
~~~

The composite requires both capabilities structurally. It does not supply implementation or object ownership. Multiple Protocol inheritance expresses interface conjunction more safely than using large concrete implementation hierarchies.

### 9.11.12 Callable protocols express rich call interfaces

<code>Callable</code> can express many positional call shapes but not every overloaded/keyword-rich interface clearly. A Protocol with <code>__call__</code> can name parameters and add attributes:

~~~python
class Formatter(Protocol):
    media_type: str

    def __call__(self, value: object, *, compact: bool = False) -> bytes: ...
~~~

Functions do not naturally have a statically declared <code>media_type</code> unless assigned/annotated; callable objects can. The protocol describes both call and metadata. Runtime conformance remains behavioural.

### 9.11.13 Parametric functions should not inspect arbitrary T

A function truly parametric over <code>T</code> can only store, return, compare under declared bounds, or pass T values through supported protocols. If it branches on exact runtime type, it becomes ad hoc/subtype-specific rather than uniform.

~~~python
from typing import TypeVar

T = TypeVar("T")


def first(values: tuple[T, ...]) -> T:
    if not values:
        raise ValueError("empty tuple")
    return values[0]
~~~

The result preserves the element type. Runtime Python does not instantiate separate machine code for each T; the type parameter guides static reasoning.

### 9.11.14 Variance follows input/output positions

If a Producer returns Animals, a producer of Dogs can often substitute because every Dog is an Animal—covariance. If a Consumer can accept every Animal, it can consume Dogs; a consumer restricted to Dogs cannot substitute where arbitrary Animals may be passed—contravariance.

Mutable containers both accept and return their element type, making them commonly invariant. These relationships explain why structural signature compatibility cannot be decided by name matching alone. Chapter 12 supplies formal typing syntax and examples.

### 9.11.15 Protocol versioning

Adding a required method to a structural Protocol can break every existing implementation. Adding an optional default body does not give structural implementers that method. Evolving protocols may use smaller capability extensions, versioned interfaces, adapters, or feature negotiation.

Semantic changes to an existing method can be more dangerous than syntax changes because static checkers continue to accept old implementations. Reusable contract suites help detect drift.

### Worked example 9.5C — Storage protocol and two implementations

~~~python
from typing import Protocol


class ByteStore(Protocol):
    def get(self, key: str) -> bytes | None: ...
    def put(self, key: str, value: bytes) -> None: ...


class MemoryByteStore:
    def __init__(self) -> None:
        self._data: dict[str, bytes] = {}

    def get(self, key: str) -> bytes | None:
        return self._data.get(key)

    def put(self, key: str, value: bytes) -> None:
        self._data[key] = value


class PrefixStore:
    def __init__(self, inner: ByteStore, prefix: str) -> None:
        self._inner = inner
        self._prefix = prefix

    def get(self, key: str) -> bytes | None:
        return self._inner.get(self._prefix + key)

    def put(self, key: str, value: bytes) -> None:
        self._inner.put(self._prefix + key, value)
~~~

MemoryByteStore satisfies structurally without inheriting. PrefixStore is both adapter/decorator composition. A contract must additionally define valid keys, whether bytes are copied (immutable here), overwrite semantics, concurrency, durability, and failure. Static shape supplies only the two method signatures.

### Worked example 9.5D — Contract test for context managers

A context-manager protocol has more than <code>__enter__</code>/<code>__exit__</code> presence. A resource test can assert:

1. entry returns the documented object;
2. resource is usable inside;
3. normal exit closes exactly once;
4. exceptional exit closes and either propagates or suppresses according to return value;
5. failed entry does not call exit automatically under the with protocol;
6. repeated use is accepted or rejected explicitly;
7. overlapping entry is handled under contract.

These behavioural laws require executable tests for every implementation. A runtime-checkable Protocol cannot establish them.

> **Common misconception — “If a type checker accepts a Protocol implementation, the object obeys the protocol.”**  
> Static checking establishes a structural approximation. Algebraic laws, effects, exceptions, lifetime, performance, and runtime honesty still require implementation and tests.
