# 9.13 Cooperative binary operations and `NotImplemented`

An infix expression such as <code>left + right</code> visually resembles one indivisible operation, but its implementation must reconcile two independently designed operand types. Python therefore treats most binary operators as a **cooperative dispatch protocol**: it asks operand types whether they know how to implement the ordered pair of values. The protocol exists because neither class can reasonably know every type that may later be placed on its other side.

For addition, the relevant methods are <code>__add__</code> on the left type and <code>__radd__</code>, the **reflected addition method**, on the right type. “Reflected” describes reversal of the dispatch role, not necessarily reversal of the mathematical operands. Inside <code>right.__radd__(left)</code>, the operation is still conceptually <code>left + right</code>.

### 9.13.1 The ordinary dispatch order

Ignoring the subclass refinement explained next, evaluation of <code>x + y</code> proceeds conceptually as follows:

1. find the addition implementation on <code>type(x)</code>, using special-method lookup;
2. call it with <code>x</code> as receiver and <code>y</code> as the other operand;
3. if it returns an ordinary value, that value is the expression result;
4. if it returns <code>NotImplemented</code> and the operand types are eligible for a distinct reflected attempt, find <code>__radd__</code> on <code>type(y)</code> and call it for the original ordered expression;
5. if no route supplies a value, raise <code>TypeError</code>.

This is a semantic model, not literal Python source for the interpreter. Special methods are looked up on types under rules introduced in §9.12; assigning a function named <code>__add__</code> to one instance does not ordinarily participate.

~~~python
class Left:
    def __add__(self, other: object) -> object:
        print("Left.__add__")
        return NotImplemented


class Right:
    def __radd__(self, other: object) -> str:
        print("Right.__radd__")
        return "cooperatively handled"


result = Left() + Right()
print(result)
~~~

The first method declines the operand pair. The second accepts it. The output is therefore:

~~~text
Left.__add__
Right.__radd__
cooperatively handled
~~~

Returning <code>NotImplemented</code> is not failure of the whole expression. It is a local statement: “this implementation does not support this operand combination; continue the language protocol.”

### 9.13.2 A strict right-hand subtype receives priority

An important refinement protects specialised subtypes. If the right operand’s type is a proper subclass of the left operand’s type and supplies a distinct reflected implementation, Python gives that reflected implementation priority. Otherwise the more general left implementation might eagerly consume the subtype before the subtype can preserve its stronger semantics.

~~~python
class Quantity:
    def __add__(self, other: object) -> str:
        return "Quantity.__add__"


class Temperature(Quantity):
    def __radd__(self, other: object) -> str:
        return "Temperature.__radd__"


print(Quantity() + Temperature())
~~~

The result is <code>Temperature.__radd__</code>. This priority is based on actual class inheritance, not virtual subclass registration. It is asymmetric: subclass specificity is relevant because the right operand might know facts that the base implementation cannot know.

Do not infer that Python performs an unrestricted search for the “best overload” among arbitrary functions. Binary special-method negotiation is a small, specified protocol involving the operand types and their inheritance relation.

### 9.13.3 <code>NotImplemented</code> is a value, not an exception

<code>NotImplemented</code> is a singleton object used by selected binary and comparison protocols. <code>NotImplementedError</code> is an exception class conventionally used when an invoked operation has deliberately been left without an implementation. Similar spelling does not imply similar semantics.

~~~python
class BadDistance:
    def __add__(self, other: object):
        raise NotImplementedError
~~~

This method terminates dispatch immediately by raising. The right operand is not thereby invited to cooperate. A correct unsupported-type branch returns the sentinel:

~~~python
class Distance:
    def __add__(self, other: object):
        if not isinstance(other, Distance):
            return NotImplemented
        return Distance()
~~~

Nor should an arithmetic method return <code>False</code> for an unsupported operand. <code>False</code> is an ordinary successful result, so Python stops dispatch and gives the caller a Boolean where an arithmetic value was expected.

An implementation should also distinguish unsupported *types* from invalid *values* of a supported type. Suppose a duration accepts integer seconds but prohibits negative results. A string operand is a dispatch mismatch and may merit <code>NotImplemented</code>; an integer that would violate a documented invariant may merit <code>ValueError</code>. The division is contractual, not merely syntactic.

### 9.13.4 Result annotations and the sentinel

A special method that may return the sentinel should make that possibility legible to readers and static analysis. Modern annotations can use <code>NotImplementedType</code> from <code>types</code>:

~~~python
from types import NotImplementedType


class Sample:
    def __add__(self, other: object) -> "Sample | NotImplementedType":
        if not isinstance(other, Sample):
            return NotImplemented
        return Sample()
~~~

Some type-checker conventions infer the protocol without requiring this union, and library stubs sometimes use broader return annotations. The semantic requirement remains: the actual method may return either a valid operation result or the distinguished sentinel.

### 9.13.5 Reflected methods implement the original ordering

For a non-commutative operation, a reflected method must preserve operand order. If <code>a - b</code> reaches <code>b.__rsub__(a)</code>, the required computation is still “<code>a</code> minus <code>b</code>,” not “<code>b</code> minus <code>a</code>.”

~~~python
from dataclasses import dataclass
from types import NotImplementedType


@dataclass(frozen=True)
class Offset:
    amount: int

    def __rsub__(self, other: object) -> int | NotImplementedType:
        if not isinstance(other, int):
            return NotImplemented
        return other - self.amount


print(100 - Offset(7))  # 93
~~~

The receiver is the syntactic right operand. The explicit parameter is the syntactic left operand. Naming the parameter <code>left</code> rather than <code>other</code> can make this relationship clearer in non-commutative reflected methods.

### 9.13.6 A closed operation and an open operation

An operation is **closed** over a set when applying it to members of that set produces another member of the same set. Integer addition is closed over integers. Division is not closed over integers under Python’s true-division semantics because <code>1 / 2</code> yields a floating-point value.

User-defined arithmetic must state whether it is closed. A vector added to a vector naturally yields a vector; multiplying a vector by a scalar yields a vector; multiplying two vectors could mean a dot product, elementwise product, or be deliberately unsupported. Syntax cannot decide the domain model.

~~~python
from dataclasses import dataclass
from numbers import Real
from types import NotImplementedType


@dataclass(frozen=True)
class Vector2:
    x: float
    y: float

    def __add__(
        self, other: object
    ) -> "Vector2 | NotImplementedType":
        if not isinstance(other, Vector2):
            return NotImplemented
        return Vector2(self.x + other.x, self.y + other.y)

    def __mul__(
        self, scalar: object
    ) -> "Vector2 | NotImplementedType":
        if not isinstance(scalar, Real):
            return NotImplemented
        return Vector2(self.x * float(scalar), self.y * float(scalar))

    def __rmul__(
        self, scalar: object
    ) -> "Vector2 | NotImplementedType":
        return self * scalar

    def dot(self, other: "Vector2") -> float:
        return self.x * other.x + self.y * other.y
~~~

Line by line, the class makes separate claims:

- addition is supported only for two <code>Vector2</code> values and is closed over the type;
- multiplication accepts a scalar satisfying the runtime test chosen here;
- reflected multiplication delegates because scalar multiplication is intended to be commutative in operand placement;
- vector–vector dot product receives a named method rather than overloading <code>*</code> ambiguously.

The runtime use of <code>numbers.Real</code> is a policy choice, not a universal numeric test. For example, some third-party scalar types have their own interoperability rules. A general-purpose numerical class needs a documented promotion and coercion policy.

### 9.13.7 Coercion must preserve information and meaning

**Coercion** converts an operand into a representation an operation can consume. Automatic coercion can make types interoperate, but uncontrolled coercion loses information or blurs domains. Converting an arbitrary value with <code>float(other)</code>, for example, can discard exact rational or decimal information and can accept strings unexpectedly.

Consider monetary quantities. Adding two amounts with unequal currencies is not a numerical inconvenience; it is undefined without an exchange rate, rate time, rounding policy, and authority. Silently coercing both to floats would erase the domain distinction.

### Worked example 9.5H — A money value with explicit interoperability

~~~python
from dataclasses import dataclass
from decimal import Decimal
from types import NotImplementedType


@dataclass(frozen=True)
class Money:
    amount: Decimal
    currency: str

    def __post_init__(self) -> None:
        if not self.currency.isascii() or len(self.currency) != 3:
            raise ValueError("currency must be a three-character ASCII code")
        object.__setattr__(self, "currency", self.currency.upper())

    def __add__(
        self, other: object
    ) -> "Money | NotImplementedType":
        if not isinstance(other, Money):
            return NotImplemented
        if self.currency != other.currency:
            raise ValueError("cannot add amounts in different currencies")
        return Money(self.amount + other.amount, self.currency)

    def __sub__(
        self, other: object
    ) -> "Money | NotImplementedType":
        if not isinstance(other, Money):
            return NotImplemented
        if self.currency != other.currency:
            raise ValueError("cannot subtract amounts in different currencies")
        return Money(self.amount - other.amount, self.currency)

    def __neg__(self) -> "Money":
        return Money(-self.amount, self.currency)
~~~

The type check and currency check have different meanings. A date is not an operand this implementation understands, so it returns <code>NotImplemented</code>. Another <code>Money</code> object is structurally understood, but a mismatched currency makes the requested domain operation invalid, so the method raises <code>ValueError</code>. Conversion between currencies should be a separate operation supplied with an exchange-rate object and rounding policy.

Normalising the currency code in <code>__post_init__</code> ensures equal semantic currencies have equal representation. The frozen dataclass then obtains equality and hashing consistent with that representation, assuming <code>Decimal</code> values and strings are themselves hashable.

### 9.13.8 Augmented assignment has its own first opportunity

The statement <code>x += y</code> first seeks an **in-place operation** through <code>type(x).__iadd__</code>. If that method is absent or returns <code>NotImplemented</code>, Python falls back to ordinary addition negotiation and rebinds <code>x</code> to the result. “In place” names the protocol opportunity; it does not guarantee mutation or preservation of object identity.

~~~python
left = (1, 2)
before = id(left)
left += (3,)

print(left)               # (1, 2, 3)
print(id(left) == before) # ordinarily False
~~~

Tuples are immutable, so tuple augmentation computes a new tuple and rebinds <code>left</code>. Lists generally mutate:

~~~python
left = [1, 2]
alias = left
left += [3]

print(left is alias)  # True
print(alias)          # [1, 2, 3]
~~~

The alias observes the list mutation. Thus replacing <code>x = x + y</code> with <code>x += y</code> can change externally visible behaviour when aliases exist.

### 9.13.9 The mutable object inside an immutable container puzzle

Augmented assignment can partially mutate before a later rebinding fails. Consider:

~~~python
container = ([1, 2], "fixed")

try:
    container[0] += [3]
except TypeError as error:
    print(type(error).__name__)

print(container)  # ([1, 2, 3], 'fixed')
~~~

Evaluation first retrieves the list at index zero. List in-place addition mutates that list. Python then attempts to store the result back into the tuple position; tuple item assignment is forbidden, so <code>TypeError</code> is raised. The earlier mutation is not rolled back. This is not a contradiction in tuple immutability: the tuple still refers to the same list object; that referenced object changed internally.

The example reveals a general principle: a compound expression is not automatically transactional. Earlier successful effects remain unless an explicit transaction or rollback mechanism reverses them.

### 9.13.10 In-place methods need an aliasing contract

A mutable numerical object may implement <code>__iadd__</code> by changing itself and returning <code>self</code>. An immutable object normally returns a new value. Either can satisfy syntax, but callers need predictable alias behaviour.

~~~python
class MutableCounter:
    def __init__(self, value: int = 0) -> None:
        self.value = value

    def __iadd__(self, increment: object):
        if not isinstance(increment, int):
            return NotImplemented
        self.value += increment
        return self
~~~

A valid in-place method must return the object that becomes the new left-hand binding. Forgetting <code>return self</code> implicitly returns <code>None</code>, so <code>counter += 1</code> rebinds <code>counter</code> to <code>None</code> after mutating the original object. The forgotten return is therefore a state-and-binding defect, not merely a cosmetic omission.

### 9.13.11 Operator laws are part of the abstraction

Implementing syntax does not make the resulting algebra coherent. Depending on its advertised meaning, a type may promise some of the following laws:

- **closure:** <code>a ⊕ b</code> remains in the domain;
- **identity:** there exists <code>e</code> such that <code>a ⊕ e = e ⊕ a = a</code>;
- **associativity:** <code>(a ⊕ b) ⊕ c = a ⊕ (b ⊕ c)</code>;
- **commutativity:** <code>a ⊕ b = b ⊕ a</code>;
- **inverse:** for each <code>a</code>, an element may undo it under the operation;
- **distributivity:** one operation may distribute over another.

These are mathematical properties, not automatic consequences of method names. String concatenation is associative in value but not commutative. Floating-point addition is not generally associative because intermediate rounding changes results. Matrix multiplication is generally non-commutative. A test suite must encode the laws actually claimed, including known qualifications.

For exact vectors, an illustrative property test over representative values might assert:

~~~python
def test_vector_addition_identity() -> None:
    zero = Vector2(0.0, 0.0)
    values = [Vector2(1.0, 2.0), Vector2(-3.0, 4.5)]

    for value in values:
        assert value + zero == value
        assert zero + value == value
~~~

Because this particular representation uses binary floating-point, broader algebraic tests may require approximate comparison. Approximation itself needs an error model; replacing every equality assertion with a tolerance can conceal genuine defects.

### 9.13.12 Equality negotiation differs in its final fallback

Equality and inequality also use cooperative special methods, but their terminal behaviour differs from arithmetic. If equality routes return <code>NotImplemented</code>, Python can fall back to identity-based comparison rather than raising the arithmetic <code>TypeError</code>. Ordering comparisons such as <code><</code> ordinarily raise <code>TypeError</code> when unsupported.

Consequently, an <code>__eq__</code> method should return <code>NotImplemented</code> for an unrelated type rather than prematurely returning <code>False</code>. The distinction allows the other type to provide a meaningful cross-type equality relation.

~~~python
from dataclasses import dataclass
from types import NotImplementedType


@dataclass(frozen=True)
class Millimetres:
    value: int

    def __eq__(self, other: object) -> bool | NotImplementedType:
        if isinstance(other, Millimetres):
            return self.value == other.value
        if isinstance(other, Centimetres):
            return self.value == other.value * 10
        return NotImplemented


@dataclass(frozen=True)
class Centimetres:
    value: int
~~~

This example is deliberately incomplete as a domain design: symmetric interoperability, hashing consistency, numeric precision, and unit conversion all need explicit treatment. It demonstrates why “unrecognised” and “recognised but unequal” are distinct outcomes.

### 9.13.13 Ordering methods are paired by reflection

The reflected partner of <code>__lt__</code> is <code>__gt__</code>, because <code>a < b</code> is equivalent in operand reversal to <code>b > a</code>. Similarly, <code>__le__</code> pairs with <code>__ge__</code>. There are no methods named <code>__rlt__</code> or <code>__rgt__</code>.

Python does not infer every comparison from one arbitrary method. <code>functools.total_ordering</code> can synthesize missing ordering methods from equality and one ordering method, but the generated operations inherit the semantic correctness and possible performance cost of those primitives. Dataclasses can also generate ordering from fields when requested. Both are policy choices about lexicographic record order; neither proves that the domain possesses a meaningful total order.

### 9.13.14 A total, partial, or absent order

A **total order** makes every pair comparable and satisfies consistency laws such as transitivity and antisymmetry. A **partial order** permits incomparable pairs. Version constraints, sets under subset ordering, and task dependencies may be naturally partial.

Python’s comparison syntax can represent a partial order, but generic sorting expects a sufficiently consistent ordering for encountered values. If <code>a < b</code> and <code>b < a</code> are both false because the pair is incomparable, a sort may treat them as equivalent for ordering purposes even though <code>a != b</code>. A domain with essential incomparability should expose named relations or a comparison result expressing “incomparable,” rather than pretending to offer a total ordering.

### 9.13.15 Matrix testing for cooperative operators

An operator implementation should be tested over a matrix, not only the happy path. For every supported operator, examine:

1. same-type operands in both meaningful orders;
2. supported cross-type operands in both syntactic orders;
3. an unrelated left type and unrelated right type;
4. a base and strict subtype in both orders;
5. supported type with invalid value;
6. direct, reflected, and in-place routes;
7. aliasing before and after augmentation;
8. promised algebraic laws and documented exceptions;
9. exception type and absence of partial mutation on rejected operations;
10. equality/hash coherence if results or operands are hashable.

### Worked example 9.5I — Recording dispatch without guessing

~~~python
events: list[str] = []


class General:
    def __add__(self, other: object):
        events.append("General.__add__")
        return NotImplemented

    def __radd__(self, other: object):
        events.append("General.__radd__")
        return NotImplemented


class Specific(General):
    def __radd__(self, other: object):
        events.append("Specific.__radd__")
        return "specific result"


answer = General() + Specific()

assert answer == "specific result"
assert events == ["Specific.__radd__"]
~~~

The event log is evidence for the subtype-priority rule. A pedagogical experiment of this kind is useful when learning a protocol, but production code should depend on the documented semantic rule rather than interpreter-specific incidental call traces.

> **Common misconception — “The left operand always gets the first chance.”**  
> A strict right-hand subtype with a distinct reflected implementation can receive priority, preserving specialised semantics.

> **Common misconception — “In-place syntax necessarily mutates.”**  
> <code>+=</code> offers <code>__iadd__</code> a first chance and then may fall back to ordinary addition and rebinding. Identity and alias effects depend on the type’s contract.

> **Common misconception — “Operator overloading should accept anything convertible.”**  
> Implicit conversion is a domain policy. It can lose precision, accept nonsensical values, or erase unit and authority boundaries. Support only operand pairs with a defined meaning.
