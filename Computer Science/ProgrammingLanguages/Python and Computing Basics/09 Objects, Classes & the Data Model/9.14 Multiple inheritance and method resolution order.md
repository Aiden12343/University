# 9.14 Multiple inheritance and method resolution order

Python permits **multiple inheritance**, in which a class has more than one direct base. This feature lets one object participate in several nominal subtype relations and lets behaviour be assembled from compatible base implementations. It also creates a question that single inheritance can often conceal: when several ancestors define the same attribute, which definition is next?

Python answers with a class’s **method resolution order** (**MRO**), a linear sequence of classes used for ordinary inherited lookup and cooperative <code>super</code> traversal. “Linear” means that the branching inheritance graph is converted into one ordered list. The list includes the class itself and ordinarily ends with <code>object</code>.

### 9.14.1 The inheritance graph is not the lookup order

Suppose <code>Child</code> derives from <code>Left</code> and <code>Right</code>, both of which derive from <code>Root</code>. The inheritance relationships form a diamond:

~~~text
        Root
       /    \
    Left    Right
       \    /
        Child
~~~

This plain-text figure is only a compact statement of graph edges; the essential point is that <code>Root</code> is reachable by two paths. A naive depth-first walk could visit <code>Root</code> twice or place it before <code>Right</code>, even though <code>Right</code> is a direct base explicitly named by <code>Child</code>. Python instead computes a consistent linearisation.

~~~python
class Root:
    pass


class Left(Root):
    pass


class Right(Root):
    pass


class Child(Left, Right):
    pass


print([cls.__name__ for cls in Child.__mro__])
~~~

The result is:

~~~text
['Child', 'Left', 'Right', 'Root', 'object']
~~~

The shared ancestor appears once and after both of its subclasses.

### 9.14.2 C3 linearisation and its guarantees

Python uses **C3 linearisation**, an algorithm selected to preserve three central requirements:

1. a class precedes each of its bases;
2. the local left-to-right order of direct bases is respected;
3. the ordering is **monotonic**: if one class precedes another in a parent’s MRO, subclassing does not reverse that established precedence.

Monotonicity matters for extension. Adding a subclass should not silently make an ancestor relationship already resolved in a base mean its opposite.

For a class <code>C(B1, B2, ..., Bn)</code>, the C3 result can be expressed as

\[
L(C)=[C]+\operatorname{merge}(L(B_1),L(B_2),\ldots,L(B_n),[B_1,B_2,\ldots,B_n]),
\]

where <code>L(X)</code> means the linearisation of <code>X</code>. The **merge** operation repeatedly chooses the first list head that does not appear in the tail—that is, anywhere except the first position—of any other remaining list. It appends that eligible head and removes it wherever it is a head. If no head is eligible while lists remain, the constraints are inconsistent and class creation fails.

For the diamond above:

\[
L(Left)=[Left,Root,object],
\]

\[
L(Right)=[Right,Root,object].
\]

The merge inputs are those two sequences plus <code>[Left, Right]</code>. <code>Left</code> is an eligible head and is selected. <code>Root</code> is then the first head of the shortened left sequence, but it occurs in the tail of <code>[Right, Root, object]</code>, so selecting it would place a base before its subclass. <code>Right</code> is selected first. Only then is <code>Root</code> eligible, followed by <code>object</code>.

One need not manually run C3 for ordinary designs. Understanding its constraints explains why the observed MRO is principled rather than an arbitrary “left side wins” rule.

### 9.14.3 Some base combinations are inconsistent

Python rejects a class whose requested precedence constraints cannot all hold.

~~~python
class X:
    pass


class Y:
    pass


class A(X, Y):
    pass


class B(Y, X):
    pass


# This definition raises TypeError:
# class Impossible(A, B):
#     pass
~~~

<code>A</code> establishes <code>X</code> before <code>Y</code>. <code>B</code> establishes <code>Y</code> before <code>X</code>. No monotonic linear order can satisfy both. The resulting <code>TypeError</code> is a proof of contradictory ordering requirements, not a request to rearrange bases until the interpreter happens to accept them. The architecture must resolve which precedence is semantically correct.

### 9.14.4 <code>super</code> is relative traversal, not a parent call

The zero-argument expression <code>super()</code> used inside an ordinary method produces a proxy parameterised by the method’s defining class and current receiver. Attribute lookup through that proxy begins *after the defining class* in the receiver type’s MRO.

~~~python
class Root:
    def identify(self) -> list[str]:
        return ["Root"]


class Left(Root):
    def identify(self) -> list[str]:
        return ["Left", *super().identify()]


class Right(Root):
    def identify(self) -> list[str]:
        return ["Right", *super().identify()]


class Child(Left, Right):
    def identify(self) -> list[str]:
        return ["Child", *super().identify()]


print(Child().identify())
~~~

The result is:

~~~text
['Child', 'Left', 'Right', 'Root']
~~~

The call written in <code>Left</code> reaches <code>Right</code>, even though <code>Right</code> is not a base of <code>Left</code>. The receiver is a <code>Child</code>, whose MRO says that lookup after <code>Left</code> proceeds to <code>Right</code>. Therefore translating <code>super()</code> as “my parent” is not merely imprecise; it predicts the wrong call.

### 9.14.5 The explicit two-argument form

The expression <code>super(Current, receiver)</code> starts after <code>Current</code> in the MRO applicable to <code>receiver</code>. The zero-argument form is compiler-supported shorthand in a method body where the defining class and first argument can be recovered.

~~~python
child = Child()
proxy = super(Left, child)
print(proxy.identify())  # begins at Right
~~~

The first argument does not need to be the immediate type of the object, but it must participate appropriately in the relationship. Arbitrarily changing it can skip invariants. Explicit <code>super</code> is useful for explanation and certain dynamic techniques; ordinary methods generally use the zero-argument form because it remains correct if class names are rebound or definitions are refactored.

Zero-argument <code>super()</code> relies on a compiler-created <code>__class__</code> closure cell. Moving the expression into an unrelated nested function or rebinding the method in unusual ways can remove the expected context. The normal pattern is to call it lexically inside the method defined by the participating class.

### 9.14.6 Direct base calls freeze one route

Compare:

~~~python
class Left(Root):
    def identify(self) -> list[str]:
        return ["Left", *Root.identify(self)]
~~~

The direct call names <code>Root</code>, bypassing any class that the eventual MRO places between <code>Left</code> and <code>Root</code>. In the diamond, <code>Right.identify</code> would be skipped. Direct base calls can be intentional when a design explicitly refuses cooperation, but they should not masquerade as equivalent to <code>super</code>.

### 9.14.7 Cooperative methods form a chain of obligations

A **cooperative method** performs its local contribution and delegates the continuation with <code>super</code>. Cooperation succeeds only if all participating implementations agree on:

- the method name and purpose;
- compatible arguments and return semantics;
- whether every implementation must call <code>super</code>;
- where the chain terminates;
- whether work occurs before or after delegation;
- exception and rollback behaviour;
- idempotence if a call can be retried.

One non-cooperative implementation can terminate the chain. One implementation that calls a named ancestor can skip or duplicate another. Multiple inheritance is therefore not a magical composition system; it is composition through an implicit, MRO-ordered protocol.

### Worked example 9.5J — A diamond contributes exactly once

~~~python
class PipelineEnd:
    def stages(self) -> list[str]:
        return []


class ValidateStage(PipelineEnd):
    def stages(self) -> list[str]:
        return ["validate", *super().stages()]


class AuditStage(PipelineEnd):
    def stages(self) -> list[str]:
        return ["audit", *super().stages()]


class ExportPipeline(ValidateStage, AuditStage):
    def stages(self) -> list[str]:
        return ["export", *super().stages()]


pipeline = ExportPipeline()
assert pipeline.stages() == ["export", "validate", "audit"]
assert ExportPipeline.__mro__ == (
    ExportPipeline,
    ValidateStage,
    AuditStage,
    PipelineEnd,
    object,
)
~~~

<code>PipelineEnd</code> supplies an explicit cooperative endpoint whose signature matches the rest of the chain. Each class contributes once because C3 contains it once and each implementation advances once.

### 9.14.8 Initialisation is a particularly difficult chain

Cooperative <code>__init__</code> methods must arrange that each class consumes its own parameters and forwards the remainder. A common mixin pattern uses keyword-only parameters and <code>**kwargs</code>:

~~~python
class Identified:
    def __init__(self, *, identifier: str, **kwargs: object) -> None:
        self.identifier = identifier
        super().__init__(**kwargs)


class Timestamped:
    def __init__(self, *, created_at: float, **kwargs: object) -> None:
        self.created_at = created_at
        super().__init__(**kwargs)


class Record(Identified, Timestamped):
    def __init__(
        self,
        *,
        payload: bytes,
        **kwargs: object,
    ) -> None:
        self.payload = payload
        super().__init__(**kwargs)


record = Record(identifier="r-1", created_at=10.5, payload=b"data")
~~~

Dispatch follows <code>Record</code>, <code>Identified</code>, <code>Timestamped</code>, and finally <code>object</code>. Each implementation removes its named keyword. The endpoint receives no unused arguments because <code>object.__init__</code> does not accept arbitrary application configuration.

This pattern has costs. <code>**kwargs: object</code> weakens static visibility of accepted parameters, misspellings may travel far before rejection, and every participant must preserve the convention. For public construction APIs, a dataclass configuration object or explicit composition often communicates requirements more clearly.

### 9.14.9 Initialisation order establishes invariant dependencies

Whether a cooperative method acts before or after <code>super</code> is semantically significant.

~~~python
class RequiresIdentifier:
    def __init__(self, **kwargs: object) -> None:
        super().__init__(**kwargs)
        if not hasattr(self, "identifier"):
            raise RuntimeError("identifier was not established")
~~~

This class assumes an earlier MRO participant has established <code>identifier</code> before the chain returns. Such hidden temporal coupling is fragile: reordering bases may violate it while leaving type relations syntactically valid. A mixin needing state should either document a clear required protocol, establish its own state, or accept a collaborator explicitly.

An object can also escape while only partly initialised if a base publishes <code>self</code>, calls an overridable method, or registers the object before the full chain completes. Constructors should avoid invoking subclass-overridable behaviour unless the design explicitly defines a two-phase lifecycle.

### 9.14.10 Cooperative <code>__new__</code> and immutable types

Construction can require cooperation before <code>__init__</code>. A custom <code>__new__</code> must pass appropriate arguments to the next allocator and return a valid instance. Immutable built-in subtypes often establish their value in <code>__new__</code>; a stateful multiple-inheritance graph involving such types can have incompatible layout or allocation requirements.

The key distinction is:

- cooperative <code>__new__</code> negotiates object allocation and initial representation;
- cooperative <code>__init__</code> negotiates post-allocation initialisation;
- both depend on a shared signature and endpoint contract;
- returning an instance of an unrelated class from <code>__new__</code> can prevent the expected <code>__init__</code> from running.

These facts make “combine arbitrary classes by listing them as bases” unsound. Classes must be designed to cooperate.

### 9.14.11 Class methods also follow the MRO

<code>super()</code> in a class method continues relative lookup while the receiver is a class rather than an ordinary instance.

~~~python
class BaseFactory:
    @classmethod
    def describe(cls) -> list[str]:
        return [f"receiver={cls.__name__}"]


class LabelledFactory(BaseFactory):
    @classmethod
    def describe(cls) -> list[str]:
        return ["labelled", *super().describe()]


class ConcreteFactory(LabelledFactory):
    pass


assert ConcreteFactory.describe() == [
    "labelled",
    "receiver=ConcreteFactory",
]
~~~

The implementation was defined on <code>LabelledFactory</code>, but <code>cls</code> remains the dynamic receiver <code>ConcreteFactory</code>. Cooperative lookup and dynamic binding are related but distinct dimensions.

### 9.14.12 Mixins are narrow behavioural contributors

A **mixin** is a class intended to contribute a focused capability within an inheritance composition rather than represent a complete standalone domain kind. A disciplined mixin usually has these properties:

- a small, explicit behavioural purpose;
- few or no constructor requirements;
- little independently owned mutable state;
- documented methods or attributes required from the eventual host;
- cooperative <code>super</code> use where it overrides shared methods;
- no assumption that it occupies a fixed MRO position;
- a name making its contributory role visible, often ending in <code>Mixin</code>.

~~~python
class AsDictionaryMixin:
    def as_dict(self) -> dict[str, object]:
        fields = self.dictionary_fields()
        return {name: getattr(self, name) for name in fields}

    def dictionary_fields(self) -> tuple[str, ...]:
        raise NotImplementedError
~~~

This mixin requires a host protocol but owns no constructor state. For production typing, that requirement could be made explicit with an abstract method or structural protocol. If the capability can instead be a function <code>as_dictionary(value)</code>, inheritance may offer no advantage; a mixin earns its place when method integration and substitutability genuinely help.

### 9.14.13 Stateful bases create shared-invariant risk

Two bases may independently believe they own the same attribute, lifecycle event, lock, or external resource. Even different attribute names do not prevent semantic collision. One base might close a stream while another still needs it; two retry mixins might multiply retry counts; two equality implementations might disagree about identity.

Name mangling can reduce accidental attribute-name collision but cannot reconcile incompatible invariants. Multiple inheritance should be assessed at the level of behaviour and lifecycle, not just namespace spelling.

### 9.14.14 Built-in and extension layouts impose constraints

Some classes, especially extension types implemented outside ordinary Python object layout, cannot be multiply inherited in arbitrary combinations. Python may report an instance layout conflict at class creation. The failure reflects incompatible memory-layout requirements, not merely an MRO problem.

Even when a combination is accepted, assumptions about <code>__dict__</code>, slots, weak references, pickling, or allocation can conflict. Composition puts each component in its own object with its own layout and is therefore often the safer representation boundary.

### 9.14.15 Abstract base classes do not erase cooperation requirements

An abstract base class may provide both abstract declarations and concrete cooperative implementations. An abstract method can even contain a useful endpoint or partial implementation callable via <code>super</code>. “Abstract” means the class cannot ordinarily be instantiated until requirements are resolved; it does not mean the method body is absent.

Every subclass still needs compatible signatures and semantics. Registration as a virtual subclass does not insert the registered class into the registrant’s MRO and does not make <code>super</code> traverse the abstract base. Nominal recognition and implementation inheritance are separate mechanisms.

### 9.14.16 Diagnosing an MRO chain

When cooperative behaviour is surprising, collect evidence systematically:

1. inspect <code>type(instance).__mro__</code>;
2. identify the class in which the currently executing method was defined;
3. find the next class after that definition site in the receiver MRO;
4. check whether it defines or inherits the requested attribute;
5. inspect whether each method calls <code>super</code>, a named base, both, or neither;
6. compare signatures and which keyword arguments each method consumes;
7. locate any descriptor whose binding changes the retrieved object;
8. record state before and after each contribution without changing timing-sensitive behaviour more than necessary.

<code>Class.mro()</code> returns the computed list through a method; <code>Class.__mro__</code> exposes the stored tuple. A metaclass can customise MRO computation, which is an advanced and rarely justified extension discussed in §9.18.

### Worked example 9.5K — Exposing a broken cooperative chain

~~~python
class End:
    def render(self) -> list[str]:
        return ["end"]


class CooperativeA(End):
    def render(self) -> list[str]:
        return ["A", *super().render()]


class NonCooperativeB(End):
    def render(self) -> list[str]:
        return ["B"]  # deliberately terminates the chain


class CooperativeC(End):
    def render(self) -> list[str]:
        return ["C", *super().render()]


class Combined(CooperativeA, NonCooperativeB, CooperativeC):
    pass


assert [c.__name__ for c in Combined.__mro__] == [
    "Combined",
    "CooperativeA",
    "NonCooperativeB",
    "CooperativeC",
    "End",
    "object",
]
assert Combined().render() == ["A", "B"]
~~~

<code>CooperativeC</code> is present in the MRO but never reached. An MRO determines where cooperative lookup *would* continue; it cannot force a method to continue.

### 9.14.17 Choosing multiple inheritance deliberately

Multiple inheritance is strongest when all of the following are true:

- each base relation is a defensible subtype or narrowly scoped mixin relation;
- methods that share names were designed for cooperative traversal;
- constructor and lifecycle contracts are compatible;
- the complete MRO is understandable and tested;
- state ownership does not overlap ambiguously;
- an explicit component graph would be more cumbersome without being clearer.

Prefer composition when collaborators have independent lifetimes, must be replaced at runtime, need explicit construction order, own external resources, or should not alter type identity. There is no rule that inheritance is always bad or composition always good; the decision concerns which relationship tells the truth and makes invariants inspectable.

> **Common misconception — “Python searches the first parent completely, then the second.”**  
> C3 linearises the entire graph while preserving local order and monotonicity. Shared ancestors appear once, and a sibling can precede a shared ancestor.

> **Common misconception — “Calling <code>super()</code> is optional style.”**  
> In a cooperative hierarchy it is a protocol obligation. Omitting it can prevent every later MRO participant from running.

> **Common misconception — “If the MRO is legal, the classes are semantically compatible.”**  
> C3 proves only that precedence constraints can be linearised. It does not prove compatible signatures, invariants, resource ownership, or meanings.
