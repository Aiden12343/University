# 9.15 Descriptors

A **descriptor** is an object that defines at least one attribute-management method—<code>__get__</code>, <code>__set__</code>, or <code>__delete__</code>—and is encountered as an attribute on a class. The descriptor protocol lets one class-owned object mediate access for any number of instances. It exists to centralise repeated attribute policy: binding a function to its receiver, validating values, computing a property, representing a slot, loading lazily, or adapting access to another storage system.

The essential relationship has three objects:

1. the **descriptor object**, stored in a class namespace;
2. the **owner class**, through whose MRO the descriptor is found;
3. the **managed instance**, whose apparent attribute is being read, assigned, or deleted.

The descriptor is not normally copied into each instance. It is shared infrastructure, while managed values may live separately in each instance or in another store selected by the descriptor.

### 9.15.1 The protocol signatures

A retrieval descriptor supports conceptually:

~~~python
descriptor.__get__(instance, owner)
~~~

For access through an instance, <code>instance</code> is that object and <code>owner</code> is ordinarily its class. For access through a class, <code>instance</code> is <code>None</code> and <code>owner</code> is the class used for access. A descriptor decides what to return in either case.

Mutation protocols are conceptually:

~~~python
descriptor.__set__(instance, value)
descriptor.__delete__(instance)
~~~

These methods receive a managed instance because assignment and deletion target an instance attribute expression. A metaclass can itself host descriptors governing class attributes; that is the same protocol at the next object/type level.

### 9.15.2 Data and non-data descriptors

A descriptor whose *type* defines <code>__set__</code> or <code>__delete__</code> is a **data descriptor**. A descriptor defining <code>__get__</code> but neither mutation method is a **non-data descriptor**. The classification controls precedence:

- a data descriptor normally wins over an entry with the same name in the instance dictionary;
- an instance dictionary entry normally wins over a non-data descriptor;
- a non-data descriptor wins only when the instance has not shadowed its name.

A <code>__set__</code> method that merely raises <code>AttributeError</code> still makes its object a data descriptor. The presence of the method on the descriptor type, not whether assignment succeeds, determines the category. Read-only properties exploit this precedence to prevent an instance dictionary entry from silently replacing managed retrieval.

### 9.15.3 Instance retrieval precedence, derived

For an ordinary expression <code>obj.name</code>, a useful semantic model is:

1. search <code>type(obj)</code> and its MRO for <code>name</code>;
2. if the result is a data descriptor, call its <code>__get__</code>;
3. otherwise, if <code>obj</code> has an instance dictionary containing <code>name</code>, return that value;
4. otherwise, if the class search found a non-data descriptor, call its <code>__get__</code>;
5. otherwise, if the class search found an ordinary value, return it;
6. otherwise normal lookup raises <code>AttributeError</code>, after which a suitable <code>__getattr__</code> fallback may be invoked.

The real implementation handles metaclasses, slots, proxies, and internal details, but this ordering predicts ordinary Python classes accurately. It explains both properties and methods from one mechanism.

### Worked example 9.5L — Observe all three precedence layers

~~~python
class DataDescriptor:
    def __get__(self, instance, owner=None) -> str:
        return "data descriptor"

    def __set__(self, instance, value: object) -> None:
        raise AttributeError("read-only")


class NonDataDescriptor:
    def __get__(self, instance, owner=None) -> str:
        return "non-data descriptor"


class Example:
    data = DataDescriptor()
    non_data = NonDataDescriptor()
    ordinary = "class value"


item = Example()
item.__dict__["data"] = "instance data"
item.__dict__["non_data"] = "instance non-data"
item.__dict__["ordinary"] = "instance ordinary"

assert item.data == "data descriptor"
assert item.non_data == "instance non-data"
assert item.ordinary == "instance ordinary"
~~~

Directly inserting <code>data</code> into <code>__dict__</code> proves that precedence, not absence, makes the descriptor win. The non-data descriptor and ordinary class value are shadowed by instance entries.

### 9.15.4 Functions are non-data descriptors

A function object stored in a class implements <code>__get__</code>. Access through an instance returns a **bound method** containing the function and receiver; access through the class returns the function in the ordinary case.

~~~python
class Greeter:
    def greet(self, name: str) -> str:
        return f"hello, {name}"


person = Greeter()
bound = person.greet

assert bound.__self__ is person
assert bound.__func__ is Greeter.__dict__["greet"]
assert bound("Ada") == "hello, Ada"
~~~

Because functions are non-data descriptors, an instance attribute can shadow a method name:

~~~python
person.greet = lambda name: f"intercepted {name}"
assert person.greet("Ada") == "intercepted Ada"
~~~

This flexibility is sometimes useful for testing or per-instance adaptation, but routinely shadowing methods makes behaviour difficult to locate. A data descriptor could prohibit such replacement if the contract required it.

### 9.15.5 <code>staticmethod</code> and <code>classmethod</code> alter binding

The objects created by <code>staticmethod</code> and <code>classmethod</code> are descriptors that transform retrieval:

- <code>staticmethod</code> returns the underlying callable without automatically binding an instance or class;
- <code>classmethod</code> binds the dynamic owner class as the first argument.

They do not create fundamentally separate kinds of function at definition time. They wrap a function in class-level binding policy.

~~~python
class Factory:
    @staticmethod
    def validate_code(code: str) -> bool:
        return code.isascii() and code.isupper()

    @classmethod
    def named(cls, code: str) -> "Factory":
        if not cls.validate_code(code):
            raise ValueError("invalid code")
        instance = cls()
        instance.code = code
        return instance
~~~

The class method uses the dynamic <code>cls</code>, so an inherited call can construct a subclass. The static method expresses a namespaced operation requiring neither receiver. If the validation has broader independent meaning, a module-level function may provide a clearer home.

### 9.15.6 Properties are reusable protocol objects

<code>property</code> constructs a data descriptor from getter, setter, and deleter callables. Decorator syntax is a convenient staged rebinding:

~~~python
class Celsius:
    def __init__(self, value: float) -> None:
        self.value = value

    @property
    def value(self) -> float:
        return self._value

    @value.setter
    def value(self, candidate: float) -> None:
        if candidate < -273.15:
            raise ValueError("below absolute zero")
        self._value = float(candidate)
~~~

After the getter suite, the name <code>value</code> refers to a property descriptor. The setter decorator builds a related property containing both callables and rebinds <code>value</code>. Assignment in <code>__init__</code> therefore invokes validation rather than bypassing it.

A property is more than a “method disguised as a field.” Attribute syntax communicates an access contract: callers reasonably expect retrieval to be conceptually observational, reasonably bounded in cost, and unsurprising in side effects. A property that performs an unbounded network request or commits a transaction hides an important boundary; a named method such as <code>fetch_status()</code> or <code>save()</code> better exposes that effect.

### 9.15.7 <code>__set_name__</code> supplies definition context

When <code>type</code> creates a class, it calls <code>__set_name__(owner, name)</code> on class-namespace values that define that hook. A descriptor can thereby learn the source-level attribute name assigned to it.

~~~python
class Named:
    def __set_name__(self, owner: type, name: str) -> None:
        self.public_name = name
        self.storage_name = f"_{name}"
~~~

The hook is not exclusive to descriptors; any class attribute object can define it. It runs after the class namespace has been prepared and populated but as part of class construction.

If a descriptor is attached *after* class creation, automatic <code>__set_name__</code> notification does not occur:

~~~python
descriptor = Named()


class Later:
    pass


Later.field = descriptor
descriptor.__set_name__(Later, "field")  # explicit if required
~~~

Frameworks that mutate classes dynamically must own this lifecycle step. Assuming the hook is triggered by every <code>setattr</code> produces descriptors with missing metadata.

### 9.15.8 Storage in the managed instance

The simplest validating descriptor chooses a private storage key in each managed instance’s dictionary.

### Worked example 9.5M — A typed validating field

~~~python
from typing import Generic, TypeVar, overload


T = TypeVar("T")


class Validated(Generic[T]):
    def __init__(
        self,
        *,
        expected_type: type[T],
        predicate,
        requirement: str,
    ) -> None:
        self.expected_type = expected_type
        self.predicate = predicate
        self.requirement = requirement
        self.public_name = "<unbound>"
        self.storage_name = "<unbound>"

    def __set_name__(self, owner: type, name: str) -> None:
        self.public_name = name
        self.storage_name = f"_{owner.__name__}__managed_{name}"

    @overload
    def __get__(self, instance: None, owner: type) -> "Validated[T]": ...

    @overload
    def __get__(self, instance: object, owner: type | None = None) -> T: ...

    def __get__(self, instance: object | None, owner: type | None = None):
        if instance is None:
            return self
        try:
            return object.__getattribute__(instance, "__dict__")[
                self.storage_name
            ]
        except KeyError as error:
            raise AttributeError(
                f"{self.public_name!r} has not been assigned"
            ) from error

    def __set__(self, instance: object, value: T) -> None:
        if not isinstance(value, self.expected_type):
            raise TypeError(
                f"{self.public_name} must be {self.expected_type.__name__}"
            )
        if not self.predicate(value):
            raise ValueError(
                f"{self.public_name} must satisfy {self.requirement}"
            )
        object.__getattribute__(instance, "__dict__")[
            self.storage_name
        ] = value


class Parcel:
    mass_kg = Validated(
        expected_type=float,
        predicate=lambda value: value > 0.0,
        requirement="value > 0",
    )
    destination = Validated(
        expected_type=str,
        predicate=lambda value: bool(value.strip()),
        requirement="non-blank text",
    )

    def __init__(self, mass_kg: float, destination: str) -> None:
        self.mass_kg = mass_kg
        self.destination = destination
~~~

The overloads describe two retrieval modes: class access yields the descriptor; instance access yields the stored value. Assignment first distinguishes wrong type from invalid same-type value, then commits only after validation. Reading a never-initialised field raises <code>AttributeError</code>, preserving the attribute protocol.

The type parameter and annotation appear here because Chapter 8 introduced generic functions and this chapter is using them to make a reusable object protocol explicit. The unannotated <code>predicate</code> could be declared as <code>Callable[[T], bool]</code>; it is left visually compact in the listing, not semantically mysterious.

The storage key incorporates the owner name and public name to reduce ordinary collisions. It is not globally unique: two classes with equal names or reuse under complex inheritance can still require stronger identity management.

### 9.15.9 Avoid descriptor self-recursion

If <code>Parcel.mass_kg.__set__</code> stores with <code>setattr(instance, "mass_kg", value)</code>, it invokes itself again indefinitely. Storage must use a distinct key or lower-level mechanism. Likewise, a getter that evaluates <code>instance.mass_kg</code> while implementing <code>mass_kg</code> recursively re-enters itself.

Using <code>instance.__dict__</code> can itself invoke a custom <code>__getattribute__</code>. The example uses <code>object.__getattribute__</code> to request the base attribute mechanism directly. That choice assumes the managed object actually has a dictionary.

### 9.15.10 Slots and dictionary storage are not interchangeable

A slotted class without <code>__dict__</code> cannot support a descriptor that assumes dictionary storage. Options include:

- declare a dedicated storage slot and have the descriptor access it;
- include <code>__dict__</code> among the slots, sacrificing some memory constraint;
- store data externally, usually through weak references;
- generate slot descriptors as part of class construction;
- use a property that mediates an already declared slot.

The descriptor’s storage contract must therefore be compatible with the owner’s representation. A framework field that works on an ordinary test class may fail on a slotted production class for a principled reason.

### 9.15.11 External storage and weak references

A descriptor can map managed instances to values externally. A normal dictionary would retain every instance strongly and cause a lifetime leak. <code>weakref.WeakKeyDictionary</code> can allow entries to disappear when instances are otherwise unreachable, provided the instances support weak references and satisfy the mapping’s hash/equality requirements.

~~~python
from weakref import WeakKeyDictionary


class ExternalValue:
    def __init__(self) -> None:
        self._values: WeakKeyDictionary[object, object] = WeakKeyDictionary()

    def __get__(self, instance, owner=None):
        if instance is None:
            return self
        try:
            return self._values[instance]
        except KeyError as error:
            raise AttributeError("value is unset") from error

    def __set__(self, instance, value: object) -> None:
        self._values[instance] = value
~~~

This design moves mutable state into the shared descriptor, introducing concurrency and serialisation questions. Weak-key lookup can also behave surprisingly for objects whose equality and hash merge distinct instances. Identity-based storage may require a different design with explicit weak-reference cleanup. External storage is a tradeoff, not a universal way to support slots.

### 9.15.12 One descriptor assigned more than once

Because the descriptor object is shared, assigning the same descriptor instance under multiple names can overwrite metadata stored in a single <code>self.storage_name</code> field.

~~~python
shared = Named()


class Ambiguous:
    first = shared
    second = shared
~~~

<code>__set_name__</code> is called twice on the same object. After the second call, a single stored name describes only <code>second</code>. A reusable descriptor must either prohibit multiple binding, clone itself, or keep owner/name-specific metadata in a mapping. The correct policy depends on whether two aliases are intentional.

The same issue arises when one descriptor object is reused across different owner classes. Descriptor objects are ordinary mutable objects; their own state has lifetime and sharing semantics that deserve the same scrutiny as any other class attribute.

### 9.15.13 Deletion is an invariant transition

Defining <code>__delete__</code> makes deletion programmable. It must decide whether an unset value raises <code>AttributeError</code>, whether deletion is permitted after construction, and whether dependent invariants remain valid.

~~~python
class RequiredValue:
    def __set_name__(self, owner: type, name: str) -> None:
        self.storage_name = f"_{name}"

    def __get__(self, instance, owner=None):
        if instance is None:
            return self
        return getattr(instance, self.storage_name)

    def __set__(self, instance, value: object) -> None:
        object.__setattr__(instance, self.storage_name, value)

    def __delete__(self, instance) -> None:
        raise AttributeError("required value cannot be deleted")
~~~

Prohibiting deletion does not create security; code with sufficient access may still mutate lower-level representation. It preserves the documented ordinary interface against accidental invariant violation.

### 9.15.14 Non-data descriptors enable caching by shadowing

A non-data descriptor can compute a value on first access and place the result in the instance dictionary under the same public name. Subsequent lookup finds the instance entry before the non-data descriptor, so computation is bypassed. <code>functools.cached_property</code> uses this broad idea for compatible objects.

~~~python
class Once:
    def __init__(self, function) -> None:
        self.function = function
        self.name = function.__name__

    def __get__(self, instance, owner=None):
        if instance is None:
            return self
        value = self.function(instance)
        instance.__dict__[self.name] = value
        return value


class Document:
    def __init__(self, text: str) -> None:
        self.text = text

    @Once
    def word_count(self) -> int:
        return len(self.text.split())
~~~

This educational implementation omits important production concerns: a slotted object may lack <code>__dict__</code>; concurrent first access can compute more than once; changing <code>text</code> leaves a stale cache; exceptions and re-entrancy need policy; assigning <code>word_count</code> can replace the cache. The precedence rule provides the mechanism, not a complete cache contract.

### 9.15.15 Descriptor access through the class

Returning <code>self</code> when <code>instance is None</code> is conventional, not compulsory. A descriptor can return metadata, a query expression, a bound class-level object, or anything else. <code>classmethod</code> intentionally returns a class-bound method. Frameworks often make <code>Model.field</code> build an expression while <code>model.field</code> retrieves a value.

This dual interface is powerful but must be documented. A descriptor that assumes <code>instance</code> is never <code>None</code> often fails during introspection, documentation generation, or class-level access.

### 9.15.16 Inheritance changes the owner but not necessarily the descriptor

If a subclass inherits a descriptor, the same descriptor object remains stored on the defining base. Instance retrieval ordinarily passes the dynamic owner class to <code>__get__</code>. A descriptor can therefore adapt to subclasses, although <code>__set_name__</code> was originally called for the class body that directly contained it, not automatically for every inheriting subclass.

~~~python
class OwnerReporter:
    def __get__(self, instance, owner=None) -> str:
        return owner.__name__


class Base:
    report_owner = OwnerReporter()


class Derived(Base):
    pass


assert Base.report_owner == "Base"
assert Derived.report_owner == "Derived"
~~~

Overriding the class attribute in a subclass replaces that lookup route. An instance entry can shadow it only if the original was non-data under the precedence rules.

### 9.15.17 Descriptor exceptions affect fallback

If a descriptor’s <code>__get__</code> raises <code>AttributeError</code>, ordinary attribute machinery may treat the requested attribute as missing and invoke <code>__getattr__</code>. Therefore a property getter that accidentally raises <code>AttributeError</code> while accessing an internal attribute can make an existing property appear absent.

~~~python
class Confusing:
    @property
    def value(self) -> int:
        return self.misspelled_internal

    def __getattr__(self, name: str) -> str:
        return f"fallback for {name}"
~~~

Here <code>Confusing().value</code> may reach fallback behaviour rather than exposing the internal defect as expected. Descriptor implementations should translate or prevent accidental <code>AttributeError</code> where “attribute missing” is not the intended public meaning.

### 9.15.18 Introspection can trigger descriptors

Ordinary <code>getattr(obj, name)</code> executes the lookup protocol and may run descriptor code. If retrieval performs computation, logging, or I/O, introspection is not observationally free. <code>inspect.getattr_static</code> can inspect attributes while avoiding normal dynamic lookup and descriptor invocation in many cases:

~~~python
from inspect import getattr_static


raw = getattr_static(Celsius, "value")
assert isinstance(raw, property)
~~~

Static inspection has its own limitations and returns protocol objects rather than the values ordinary callers see. Debuggers, serializers, dependency injectors, and documentation tools must choose explicitly between raw structure and dynamic semantics.

### 9.15.19 Concurrency and descriptor-owned state

A descriptor is often shared across every instance of an owner class and its subclasses. Mutable descriptor state is therefore shared state. Incrementing a descriptor-level counter, maintaining an external cache, or changing validation configuration can require synchronisation and lifecycle policy under concurrency.

Per-instance dictionary storage avoids sharing the values but does not make multi-step operations atomic. A descriptor that reads, validates against another field, and then writes can race with another mutation. Chapter 14 develops concurrency in full; the present rule is that attribute syntax provides no automatic lock or transaction.

### 9.15.20 Descriptors do not establish an authority boundary

Descriptors coordinate ordinary language-level access. They do not prevent code with a reference to an object from calling descriptor methods directly, modifying the descriptor, reaching private storage, or using low-level reflection. Their role is encapsulation and invariant management among cooperating code, not containment of malicious code.

### 9.15.21 A descriptor design checklist

Before publishing a descriptor, specify:

1. whether it is data or non-data and why shadowing is or is not permitted;
2. class-access behaviour when <code>instance is None</code>;
3. storage location, collision policy, and compatibility with slots;
4. unset-value behaviour and exact exception;
5. validation order and absence of partial commits;
6. deletion and reassignment policy;
7. reuse under multiple names, owners, and inheritance;
8. typing of both class and instance access;
9. copying, pickling, and representation behaviour;
10. thread-safety, cache invalidation, and lifecycle of shared state;
11. side effects and cost visible behind attribute syntax;
12. interaction with <code>__getattr__</code>, custom <code>__getattribute__</code>, and introspection.

> **Common misconception — “A descriptor stores the field.”**  
> A descriptor controls access. The managed value may be in the instance dictionary, a slot, an external weak mapping, a database, or nowhere because it is computed.

> **Common misconception — “Only properties are descriptors.”**  
> Ordinary functions, <code>staticmethod</code>, <code>classmethod</code>, properties, slot members, and many framework fields all use descriptor semantics.

> **Common misconception — “<code>__get__</code> alone guarantees priority over instance attributes.”**  
> A retrieval-only descriptor is non-data and is ordinarily shadowed by an instance dictionary entry. Mutation methods create data-descriptor priority.
