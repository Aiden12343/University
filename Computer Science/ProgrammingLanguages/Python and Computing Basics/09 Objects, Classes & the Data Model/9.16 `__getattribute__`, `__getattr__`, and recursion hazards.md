# 9.16 `__getattribute__`, `__getattr__`, and recursion hazards

The descriptor protocol customises particular class-owned attributes. Python also exposes hooks around general attribute access. <code>__getattribute__</code> participates in every ordinary instance attribute retrieval; <code>__getattr__</code> is a fallback considered only after the primary route reports that an attribute is absent. These methods exist for proxies, virtual attributes, lazy loading, compatibility aliases, auditing, and specialised object models. Their breadth also makes them unusually capable of hiding defects.

### 9.16.1 Every ordinary retrieval begins with <code>__getattribute__</code>

For <code>obj.name</code>, Python invokes the attribute-retrieval machinery associated with <code>type(obj)</code>. An ordinary user-defined class inherits <code>object.__getattribute__</code>, whose behaviour includes the descriptor and instance-dictionary precedence derived in §9.15.

Overriding <code>__getattribute__</code> places code before every normal retrieval:

~~~python
class Observed:
    def __init__(self, value: int) -> None:
        self.value = value

    def __getattribute__(self, name: str):
        print(f"reading {name}")
        return object.__getattribute__(self, name)


item = Observed(12)
print(item.value)
~~~

The override records the request and delegates to the base implementation, which performs descriptors, instance storage, and inherited lookup. Returning <code>object.__getattribute__(self, name)</code> is not a mere fallback: it is the mechanism that preserves normal semantics.

### 9.16.2 Why naive implementations recurse

This implementation is defective:

~~~python
class Recursive:
    def __getattribute__(self, name: str):
        print(self.prefix, name)
        return self.__dict__[name]
~~~

Evaluating <code>self.prefix</code> invokes <code>self.__getattribute__("prefix")</code> again. Reaching <code>self.__dict__</code> also requires attribute retrieval. The method recurses before it can obtain either value and eventually raises <code>RecursionError</code>.

A safe implementation retrieves internal state through an implementation known not to restart the same override:

~~~python
class Safer:
    def __init__(self, prefix: str) -> None:
        self.prefix = prefix

    def __getattribute__(self, name: str):
        prefix = object.__getattribute__(self, "prefix")
        print(prefix, name)
        return object.__getattribute__(self, name)
~~~

In a cooperative hierarchy, <code>super().__getattribute__(name)</code> may be appropriate because another base deliberately participates. Calling <code>object.__getattribute__</code> bypasses intervening overrides; it is safer against self-recursion but can violate a designed cooperative chain. The correct delegate depends on ownership.

### 9.16.3 <code>__getattr__</code> handles absence, not all access

<code>__getattr__(self, name)</code> is consulted when ordinary lookup fails with <code>AttributeError</code>. Existing attributes do not pass through it.

~~~python
class Fallback:
    def __init__(self) -> None:
        self.known = 42

    def __getattr__(self, name: str) -> str:
        if name.startswith("label_"):
            return name.removeprefix("label_").replace("_", " ")
        raise AttributeError(name)


item = Fallback()
assert item.known == 42
assert item.label_account_owner == "account owner"
~~~

The dynamic namespace has a narrow grammar. A misspelling such as <code>item.konwn</code> raises <code>AttributeError</code> instead of being converted into plausible-looking data.

### 9.16.4 Fallback must preserve the missing-attribute signal

For an unsupported name, <code>__getattr__</code> should ordinarily raise <code>AttributeError</code>, not return <code>None</code> and not raise <code>KeyError</code>.

~~~python
class Configuration:
    def __init__(self, values: dict[str, str]) -> None:
        self._values = values

    def __getattr__(self, name: str) -> str:
        try:
            return self._values[name]
        except KeyError as error:
            raise AttributeError(name) from error
~~~

The translation preserves the attribute protocol while retaining a causal chain for diagnostics. Returning <code>None</code> would make absence indistinguishable from an explicitly stored null-like value and would make <code>hasattr</code> report that every name exists.

### 9.16.5 <code>getattr</code> and <code>hasattr</code> execute code

<code>getattr(obj, name)</code> performs normal dynamic attribute access. The optional default is returned only for an <code>AttributeError</code> indicating absence; other exceptions propagate. <code>hasattr(obj, name)</code> effectively attempts retrieval and returns false when <code>AttributeError</code> is raised. It can therefore invoke properties, descriptors, <code>__getattribute__</code>, and <code>__getattr__</code>.

~~~python
class Costly:
    @property
    def report(self) -> str:
        print("computing report")
        return "ready"


assert hasattr(Costly(), "report")
~~~

The print occurs. A check that looks like metadata inspection can perform arbitrary user-defined computation. Furthermore, an accidental <code>AttributeError</code> inside a property may make <code>hasattr</code> return false, concealing an implementation defect as absence.

### 9.16.6 Dynamic access should not swallow operational failures

Suppose a virtual attribute is loaded from a database. A missing field may justify <code>AttributeError</code>; a disconnected database does not. Translating every exception into <code>AttributeError</code> causes callers to interpret operational failure as a nonexistent interface.

~~~python
def __getattr__(self, name: str):
    if name not in self.allowed_remote_fields:
        raise AttributeError(name)
    return self.repository.fetch_field(self.identifier, name)
~~~

Repository timeout and permission exceptions should ordinarily propagate or be translated into meaningful domain exceptions. Interface absence, missing domain data, and infrastructure failure are different states.

### 9.16.7 Lazy attributes need an invalidation and race policy

A common fallback computes an attribute once and stores it:

~~~python
class ParsedDocument:
    def __init__(self, source: str) -> None:
        self.source = source

    def __getattr__(self, name: str):
        if name != "tokens":
            raise AttributeError(name)

        tokens = tuple(self.source.split())
        self.tokens = tokens
        return tokens
~~~

The first <code>document.tokens</code> misses and invokes fallback. Assignment creates an instance entry, so later access uses ordinary lookup. The design must still answer:

- What invalidates <code>tokens</code> if <code>source</code> changes?
- May two threads compute simultaneously?
- What happens if computation recursively requests <code>tokens</code>?
- Is a failed computation cached?
- Should callers be allowed to assign their own <code>tokens</code>?
- Does copying or pickling retain the cached value?

The few lines implement a mechanism, not these policies. Immutability of <code>source</code> would remove one invalidation problem; a descriptor such as <code>cached_property</code> can standardise part of the mechanism.

### 9.16.8 Transparent proxies are not obtained by one fallback

A **proxy** is an object that mediates access to another object, the **target**. A minimal forwarding proxy can use <code>__getattr__</code>:

~~~python
class Proxy:
    def __init__(self, target: object) -> None:
        object.__setattr__(self, "_target", target)

    def __getattr__(self, name: str):
        target = object.__getattribute__(self, "_target")
        return getattr(target, name)
~~~

Only names absent on the proxy are forwarded. Proxy-owned methods and class attributes take priority. This is often desirable because it preserves an explicit mediation interface.

It is not transparent for language protocols. Expressions such as <code>len(proxy)</code>, <code>proxy + value</code>, iteration, context management, and truth testing generally look up special methods on <code>type(proxy)</code>, bypassing ordinary instance fallback. A proxy must deliberately implement each special protocol it promises.

### Worked example 9.5N — An explicit sequence proxy

~~~python
from collections.abc import Iterator, Sequence
from typing import Generic, TypeVar, overload


T = TypeVar("T")


class ReadOnlySequenceProxy(Sequence[T], Generic[T]):
    def __init__(self, target: Sequence[T]) -> None:
        self._target = target

    def __len__(self) -> int:
        return len(self._target)

    @overload
    def __getitem__(self, index: int) -> T: ...

    @overload
    def __getitem__(self, index: slice) -> Sequence[T]: ...

    def __getitem__(self, index: int | slice):
        return self._target[index]

    def __iter__(self) -> Iterator[T]:
        return iter(self._target)

    def __getattr__(self, name: str):
        raise AttributeError(
            f"{type(self).__name__!s} does not expose {name!r}"
        )
~~~

The proxy declares the sequence protocols it supports rather than forwarding every target attribute. It does not expose mutators merely because the underlying target might have them. “Read-only” here means through this interface; a caller retaining the original mutable target can still change what the proxy observes.

### 9.16.9 Attribute assignment has corresponding hooks

<code>__setattr__(self, name, value)</code> participates in ordinary instance assignment, and <code>__delattr__(self, name)</code> participates in deletion. As with retrieval, naive use of <code>self.name = value</code> inside <code>__setattr__</code> re-enters the method.

~~~python
class NonNegativeFields:
    def __setattr__(self, name: str, value: object) -> None:
        if name.startswith("quantity_"):
            if not isinstance(value, int):
                raise TypeError(f"{name} must be an integer")
            if value < 0:
                raise ValueError(f"{name} cannot be negative")
        object.__setattr__(self, name, value)
~~~

This broad naming convention may be less explicit than individual properties or descriptors. It applies to future attributes automatically, which is both its benefit and its risk. Assignment delegation should preserve data-descriptor behaviour; <code>object.__setattr__</code> does so for ordinary objects rather than writing blindly into <code>__dict__</code>.

### 9.16.10 Freezing after initialisation is subtle

A custom <code>__setattr__</code> can prohibit rebinding after construction, but the object may still contain mutable children, and construction, copying, unpickling, or dataclass machinery may need controlled writes.

~~~python
class FrozenAfterInit:
    def __init__(self, value: int) -> None:
        object.__setattr__(self, "value", value)
        object.__setattr__(self, "_frozen", True)

    def __setattr__(self, name: str, value: object) -> None:
        if object.__getattribute__(self, "_frozen"):
            raise AttributeError("instance is frozen")
        object.__setattr__(self, name, value)
~~~

This minimal example assumes <code>_frozen</code> exists whenever public assignment occurs and does not address subclasses. A subclass constructor that needs new attributes after <code>super().__init__</code> is blocked. Frozen dataclasses handle more mechanics but still provide shallow rather than transitive immutability.

### 9.16.11 Attribute delegation and descriptor binding

<code>getattr(target, name)</code> performs descriptor binding with <code>target</code> as the receiver. Returning that result from a proxy means a target method remains bound to the target, not the proxy. This is usually correct:

~~~python
class Target:
    def identity(self) -> object:
        return self


target = Target()
proxy = Proxy(target)
assert proxy.identity() is target
~~~

A framework that retrieves raw attributes from <code>type(target).__dict__</code> and invokes <code>__get__</code> manually can bind differently, but doing so changes semantics and must account for MRO and descriptor precedence. Ordinary delegation should prefer ordinary <code>getattr</code> unless intentional rebinding is part of the abstraction.

### 9.16.12 Compatibility aliases should be narrow and temporary

<code>__getattr__</code> can preserve a renamed attribute:

~~~python
import warnings


class Endpoint:
    def __init__(self, address: str) -> None:
        self.address = address

    def __getattr__(self, name: str):
        if name == "url":
            warnings.warn(
                "url is deprecated; use address",
                DeprecationWarning,
                stacklevel=2,
            )
            return self.address
        raise AttributeError(name)
~~~

The alias is explicit, warns at the caller’s location, and leaves unrelated spelling errors visible. An unrestricted mapping such as replacing all underscores with hyphens would create a difficult-to-enumerate API.

### 9.16.13 Auditing must avoid sensitive leakage and semantic change

A <code>__getattribute__</code> logger sees names for secrets, internal locks, authentication tokens, and diagnostic machinery. Logging values can disclose data; even logging names may reveal behaviour. The logger itself can recurse, acquire locks in an unsafe order, or change timing.

For high-assurance auditing, intercept at a narrower domain boundary and define event schemas, redaction, failure handling, and append guarantees. General attribute interception is a language mechanism, not automatically an audit trail.

### 9.16.14 Performance and optimisation

General interception adds work to every ordinary access and can inhibit interpreter optimisations. That cost may be irrelevant for a configuration proxy and material for millions of numerical records. Measure an application-representative workload before choosing interception for performance reasons. Descriptors attached only to relevant fields or explicit methods often localise both semantic and runtime cost.

### 9.16.15 Class access is governed one level higher

Defining <code>__getattr__</code> on an ordinary class governs missing attributes on its *instances*, not missing attributes on the class object itself. Since a class is an instance of its metaclass, class-level interception belongs to the metaclass.

~~~python
class Meta(type):
    def __getattr__(cls, name: str) -> str:
        if name == "generated_label":
            return cls.__name__.lower()
        raise AttributeError(name)


class Model(metaclass=Meta):
    pass


assert Model.generated_label == "model"
~~~

This is rarely needed. A class method or explicit registry usually communicates class-level computation more directly. The example reinforces the uniform model: behaviour of an object is defined by its type; the type of a class is its metaclass.

### 9.16.16 A safe selection hierarchy

Choose the narrowest mechanism that owns the requirement:

1. use an ordinary stored attribute for plain state;
2. use a property for one class-specific managed attribute;
3. use a descriptor for reusable per-attribute policy;
4. use <code>__getattr__</code> for a constrained missing-name space or compatibility fallback;
5. use <code>__getattribute__</code> only when virtually all retrieval must be mediated;
6. use a proxy with explicitly implemented protocols when object-level mediation is the real abstraction;
7. use a metaclass hook only when class objects themselves require interception.

This hierarchy is not a rule of prestige. Broader hooks increase the amount of ordinary language behaviour that must be reconstructed and tested.

> **Common misconception — “<code>__getattr__</code> sees every attribute read.”**  
> It is a missing-attribute fallback. <code>__getattribute__</code> sees every ordinary retrieval.

> **Common misconception — “A forwarding <code>__getattr__</code> makes a transparent proxy.”**  
> Many special operations bypass ordinary instance fallback and must be implemented on the proxy type. Identity, type checks, introspection, and lifecycle can remain observably different as well.

> **Common misconception — “<code>hasattr</code> only inspects metadata.”**  
> It performs retrieval and can run arbitrary descriptor and fallback code; <code>AttributeError</code> controls its result.
