# 9.17 Slots and instance representation

Ordinary user-defined instances commonly own a dictionary mapping attribute names to values. This representation is flexible: a new name can be added at runtime, and different instances can have different sets of names. Its flexibility consumes memory and adds an indirection. A class declaration may instead use <code>__slots__</code> to request named storage positions represented by class-owned descriptors.

~~~python
class Point:
    __slots__ = ("x", "y")

    def __init__(self, x: float, y: float) -> None:
        self.x = x
        self.y = y
~~~

For this class, class construction creates a member descriptor for each declared name. An instance ordinarily stores references in fixed layout positions rather than in its own name-to-value dictionary.

### 9.17.1 Slots are descriptors, not declarations of static fields

Inspect the class namespace:

~~~python
point = Point(1.0, 2.0)

print(Point.__dict__["x"])
print(hasattr(point, "__dict__"))
~~~

<code>Point.__dict__["x"]</code> is a descriptor supplied by the runtime. Assignment to <code>point.x</code> invokes slot-setting behaviour; retrieval invokes slot-getting behaviour. Under the stated class, <code>point</code> ordinarily has no <code>__dict__</code>.

<code>__slots__</code> therefore participates in the same attribute model as §9.15. It is not a separate compile-time field system, and it does not make Python statically typed.

### 9.17.2 Undeclared names usually fail when no dictionary exists

~~~python
point = Point(1.0, 2.0)

try:
    point.z = 3.0
except AttributeError as error:
    print(error)
~~~

No slot named <code>z</code> and no instance dictionary can receive the assignment, so it fails. This catches some spelling mistakes and makes the intended per-instance namespace explicit.

It does not prove every assignment is meaningful. <code>point.x = "north"</code> succeeds unless another mechanism validates the value. Slots constrain attribute names and representation, not types or domain invariants.

### 9.17.3 Slot values need not exist yet

Declaring a slot creates capacity and access machinery, not an initial value.

~~~python
class Incomplete:
    __slots__ = ("value",)


item = Incomplete()

try:
    print(item.value)
except AttributeError:
    print("slot has not been assigned")
~~~

The descriptor reports absence until assignment. Constructors should establish every required slot before the object escapes. Optional state should be represented deliberately, perhaps with <code>None</code>, a sentinel, or a property that documents absence.

### 9.17.4 A subclass can restore a dictionary

If a subclass does not declare <code>__slots__</code>, it ordinarily gains an instance dictionary even when its base is slotted.

~~~python
class LabelledPoint(Point):
    def __init__(self, x: float, y: float, label: str) -> None:
        super().__init__(x, y)
        self.label = label


labelled = LabelledPoint(1.0, 2.0, "origin-ish")
assert labelled.__dict__ == {"label": "origin-ish"}
~~~

The inherited <code>x</code> and <code>y</code> remain in base slots; <code>label</code> lives in the subclass instance dictionary. Saying “the base has slots, so all descendants lack dictionaries” is false.

A subclass that wants only additional fixed positions declares its own slots:

~~~python
class FixedLabelledPoint(Point):
    __slots__ = ("label",)

    def __init__(self, x: float, y: float, label: str) -> None:
        super().__init__(x, y)
        self.label = label
~~~

The subclass lists only *new* slot names. Inherited slots remain available automatically.

### 9.17.5 An empty slot declaration preserves a base layout

A subclass that adds no instance state can declare an empty tuple:

~~~python
class Origin(Point):
    __slots__ = ()

    def __init__(self) -> None:
        super().__init__(0.0, 0.0)
~~~

Without <code>__slots__ = ()</code>, the subclass would ordinarily acquire a dictionary. Empty slots are common in stateless mixins designed to coexist with a slotted hierarchy, although overall multiple-inheritance layout must still be valid.

### 9.17.6 Explicitly requesting <code>__dict__</code>

The special slot name <code>__dict__</code> requests dictionary support:

~~~python
class ExtensiblePoint:
    __slots__ = ("x", "y", "__dict__")

    def __init__(self, x: float, y: float) -> None:
        self.x = x
        self.y = y


point = ExtensiblePoint(1.0, 2.0)
point.label = "A"
assert point.__dict__ == {"label": "A"}
~~~

The named slots still exist, while arbitrary additional attributes use the dictionary. This hybrid can support frameworks that require <code>__dict__</code>, but it removes much of the fixed-namespace guarantee and some memory benefit.

### 9.17.7 Weak-reference support is separate

A weak reference observes an object without keeping it alive. Ordinary dictionary-based instances generally support weak references; a slotted class needs the special <code>__weakref__</code> slot unless support is inherited.

~~~python
from weakref import ref


class WeakPoint:
    __slots__ = ("x", "y", "__weakref__")

    def __init__(self, x: float, y: float) -> None:
        self.x = x
        self.y = y


point = WeakPoint(1.0, 2.0)
observer = ref(point)
assert observer() is point
~~~

Weak-reference capability affects caches, registries, descriptor external storage, and lifecycle observation. Omitting it can break collaborators even when ordinary attribute access works.

### 9.17.8 Slot names and name mangling

A slot name with two leading underscores and no trailing double underscore is name-mangled using the declaring class, just as corresponding source-level attribute references are.

~~~python
class SecretCoordinate:
    __slots__ = ("__x",)

    def __init__(self, x: float) -> None:
        self.__x = x
~~~

The generated slot is effectively associated with a mangled name such as <code>_SecretCoordinate__x</code>. This reduces accidental collision with a subclass’s own <code>__x</code>; it does not provide confidentiality or hostile-code protection.

### 9.17.9 Do not redeclare an inherited slot name

If a subclass declares a slot with the same name as one in a base, it can hide the base descriptor and make the original storage reachable only by directly invoking that base descriptor. Behaviour is obscure and not a stable design foundation. Treat inherited slot names as already owned and declare only genuinely new names.

Namespace collision is particularly damaging because overwriting the class’s slot descriptor can make stored values inaccessible through normal syntax:

~~~python
class OneSlot:
    __slots__ = ("value",)


# Assigning OneSlot.value = 10 here would replace the member descriptor.
~~~

A slot name cannot simultaneously use an ordinary class attribute as a default, because that class attribute would occupy the name needed by the descriptor. Establish defaults in <code>__init__</code>, <code>__new__</code>, or another constructor.

### 9.17.10 Multiple slotted bases can have incompatible layouts

Multiple inheritance among bases with non-empty instance layouts is restricted. A class definition may raise <code>TypeError</code> because no single instance layout can satisfy both. Empty-slot mixins often combine successfully because they contribute behaviour without another physical layout.

~~~python
class BehaviourMixin:
    __slots__ = ()

    def coordinates(self) -> tuple[float, float]:
        return (self.x, self.y)


class BehaviouralPoint(BehaviourMixin, Point):
    __slots__ = ()
~~~

The mixin assumes a host protocol containing <code>x</code> and <code>y</code> but adds no storage. This is a more compatible use than independently stateful bases that both demand layout ownership.

MRO consistency and memory-layout compatibility are separate checks. A graph can have a valid C3 order and still be impossible to represent as one object.

### 9.17.11 Memory savings require whole-object measurement

<code>sys.getsizeof(instance)</code> reports the shallow size of the instance object, not necessarily the separately allocated instance dictionary or referenced values. Comparing only two shallow numbers can therefore make an ordinary instance appear deceptively small.

### Worked example 9.5O — Measure representation cautiously

~~~python
import sys


class DictPoint:
    def __init__(self, x: float, y: float) -> None:
        self.x = x
        self.y = y


class SlotPoint:
    __slots__ = ("x", "y")

    def __init__(self, x: float, y: float) -> None:
        self.x = x
        self.y = y


ordinary = DictPoint(1.0, 2.0)
slotted = SlotPoint(1.0, 2.0)

ordinary_shallow = sys.getsizeof(ordinary)
ordinary_dictionary = sys.getsizeof(ordinary.__dict__)
slotted_shallow = sys.getsizeof(slotted)

print(ordinary_shallow, ordinary_dictionary, slotted_shallow)
~~~

Exact results depend on interpreter build, platform, allocator state, key-sharing optimisations, inheritance, and measurement method. Referenced floats are shared conceptually between both designs in this example and should not be double-counted differently. A serious comparison creates representative populations, uses a tool such as <code>tracemalloc</code>, includes peak allocations, and measures the workload on supported runtimes.

For ten objects, saved bytes may not justify reduced flexibility. For tens of millions of long-lived objects, representation can dominate memory. Scale converts a small per-instance difference into an architectural constraint.

### 9.17.12 Attribute speed is an empirical secondary effect

Slots can make some accesses faster by avoiding dictionary lookup, but interpreter specialisation and dictionary optimisations complicate blanket claims. Construction, mutation, garbage collection, cache locality, and surrounding work may dominate. “Use slots because attributes are faster” is not an adequate performance argument without a representative benchmark and memory profile.

### 9.17.13 Slots are shallow and mutable

Slots do not make an object immutable:

~~~python
point = Point(1.0, 2.0)
point.x = 9.0
~~~

Nor do they make referenced objects immutable:

~~~python
class Bucket:
    __slots__ = ("items",)

    def __init__(self) -> None:
        self.items: list[str] = []


bucket = Bucket()
bucket.items.append("changed")
~~~

Immutability requires a behavioural contract over all observable state transitions. A frozen, slotted dataclass can prevent ordinary field rebinding and reduce layout, yet referenced lists can still mutate.

### 9.17.14 Slots do not make attributes private

The slot descriptor lives on the class and is introspectable. Callers can read and assign public slots. Name-mangled slots remain reachable by determined code. Slots prevent unlisted ordinary storage; they do not enforce an authority boundary.

### 9.17.15 Copying and serialisation must know the representation

Code that serialises only <code>obj.__dict__</code> omits slotted state or fails because no dictionary exists. Robust generic machinery must inspect supported protocols rather than assume representation. Pickle often has support for ordinary slot state, but custom reduction methods, inheritance, external resources, and changed class versions still need explicit design.

~~~python
class Pair:
    __slots__ = ("left", "right")

    def __init__(self, left: object, right: object) -> None:
        self.left = left
        self.right = right

    def __getstate__(self) -> tuple[object, object]:
        return (self.left, self.right)

    def __setstate__(self, state: tuple[object, object]) -> None:
        self.left, self.right = state
~~~

These methods make one state representation explicit but do not make untrusted pickle data safe; unpickling remains code-execution-capable and is addressed in Chapter 11.

### 9.17.16 Dataclasses can generate slotted classes

Modern dataclasses support a slots option:

~~~python
from dataclasses import dataclass


@dataclass(slots=True, frozen=True)
class Coordinate:
    x: float
    y: float
~~~

The decorator creates or returns a class with generated slots and dataclass methods. Interactions with inheritance, <code>__init_subclass__</code>, weak-reference support, field defaults, and custom methods must follow the dataclass contract. Generated code reduces boilerplate; it does not remove representation decisions.

### 9.17.17 Slots affect subclass and framework extensibility

Libraries sometimes expect to attach instrumentation, cached values, ORM state, test doubles, or debugging metadata to instances. A class without a dictionary rejects such additions unless the framework has a slot-aware route. Publishing a slotted base therefore constrains downstream subclass and tooling behaviour.

That constraint may be desirable for a closed value type and harmful for an extension-oriented base class. Representation is part of extensibility even when the public documentation mentions only methods.

### 9.17.18 When slots are justified

Slots are well motivated when:

- measurement shows substantial aggregate memory benefit;
- a large homogeneous population has a stable fixed shape;
- prevention of accidental attribute creation is valuable;
- weak-reference, serialisation, subclassing, and tooling requirements are known;
- multiple-inheritance layout is controlled;
- the project accepts the representation as an API constraint.

They are poorly motivated as decoration intended to make a class look advanced. Begin with an ordinary class when flexibility is useful; adopt slots when the fixed-shape contract or measured resource saving outweighs compatibility cost.

> **Common misconception — “Slots are just a list of permitted attribute names.”**  
> They request a different instance representation implemented by descriptors, with inheritance, weak-reference, layout, and serialisation consequences.

> **Common misconception — “A slotted base means every subclass is slotted.”**  
> A subclass without its own slot declaration ordinarily receives an instance dictionary.

> **Common misconception — “<code>sys.getsizeof</code> proves the saving.”**  
> Shallow size can exclude a separate instance dictionary and all referenced objects. Measure representative populations and the complete allocation effect.
