# 9.18 Metaclasses

Every class is an object and therefore has a type. A **metaclass** is the type of a class: an object whose instance-construction protocol constructs class objects. The ordinary metaclass is <code>type</code>.

~~~python
class Ordinary:
    pass


assert isinstance(Ordinary, type)
assert type(Ordinary) is type
assert isinstance(Ordinary(), Ordinary)
~~~

The two instance relations occur at adjacent levels. <code>Ordinary()</code> is an instance of <code>Ordinary</code>; <code>Ordinary</code> is an instance of <code>type</code>. Moreover, <code>type</code> is itself an instance of <code>type</code>. This self-description terminates the otherwise tempting infinite regress of “what is the class of the class of the class?”

Metaclasses exist because class creation sometimes needs programmable policy: collect field declarations, enforce class-level invariants, build registries, synthesise methods, customise instance checks, or integrate with a foreign runtime. They operate at a wide semantic boundary and can affect every subclass and instance, so they require proportionately strong justification.

### 9.18.1 A class statement executes

A class statement is not passive record syntax. Its body is executable Python run in a newly prepared namespace.

~~~python
events: list[str] = []


class Example:
    events.append("class body ran")
    scale = 2 + 3

    def apply(self, value: int) -> int:
        return value * self.scale


assert events == ["class body ran"]
assert Example.scale == 5
~~~

The body executes once when control reaches the statement. It binds <code>scale</code> and <code>apply</code> into the class namespace being assembled. Constructing each <code>Example</code> later does not rerun the class body.

Because bodies execute, class definitions can fail, perform I/O, register callbacks, or depend on ambient state. Production class bodies should ordinarily remain deterministic and lightweight; import-time class creation is part of module execution.

### 9.18.2 The conceptual creation pipeline

For a statement of the form:

~~~python
class Report(Base, metaclass=Meta, category="financial"):
    field = Descriptor()
~~~

the language performs a pipeline conceptually containing these stages:

1. evaluate the base expressions and explicit keyword arguments;
2. resolve non-type base entries that provide MRO-entry substitution;
3. determine a metaclass compatible with all bases and any explicit metaclass;
4. ask the metaclass to prepare a class namespace;
5. execute the class body in that namespace, adding compiler-supplied entries where required;
6. call the selected metaclass with class name, resolved bases, namespace, and class keywords;
7. within ordinary <code>type</code> construction, build the class, set metadata, establish the MRO, notify suitable attributes through <code>__set_name__</code>, and invoke the inherited subclass-initialisation hook;
8. apply class decorators from the innermost/bottom decorator upward;
9. bind the final returned object to the class statement’s name.

This ordering is a semantic guide. Custom metaclasses can alter parts of construction, and detailed implementation steps should not be inferred beyond the documented hooks. The decisive point is that the name <code>Report</code> is bound only after creation and decoration succeed.

### 9.18.3 Metaclass selection uses compatibility, not simple inheritance

If no explicit metaclass is supplied and there are no bases imposing another one, Python selects <code>type</code>. With bases, the selected metaclass must be a subclass of the metaclass of every base. Python chooses the most-derived compatible candidate among the explicit metaclass, if any, and the base metaclasses.

~~~python
class MetaA(type):
    pass


class MetaB(type):
    pass


class A(metaclass=MetaA):
    pass


class B(metaclass=MetaB):
    pass


# class Conflict(A, B):
#     pass
~~~

The commented definition raises a metaclass-conflict <code>TypeError</code>: neither <code>MetaA</code> nor <code>MetaB</code> is a subclass of the other, so neither can govern a class that must satisfy both base policies.

One mechanical repair is a combined metaclass:

~~~python
class CombinedMeta(MetaA, MetaB):
    pass


class Combined(A, B, metaclass=CombinedMeta):
    pass
~~~

This works only if the metaclasses themselves cooperate through compatible MRO, signatures, and invariants. Creating a combined metaclass to silence an error can unite contradictory policies. Composition or removal of one inheritance relation may be the semantic repair.

### 9.18.4 <code>type</code> can construct a class dynamically

The three-argument form of <code>type</code> demonstrates that a class object can be constructed from a name, bases, and namespace:

~~~python
def area(self) -> int:
    return self.width * self.height


Rectangle = type(
    "Rectangle",
    (object,),
    {
        "width": 3,
        "height": 4,
        "area": area,
        "__module__": __name__,
    },
)

assert Rectangle().area() == 12
~~~

This is broadly analogous to an ordinary class statement after its body has created a namespace, but a class statement additionally handles lexical context, <code>__class__</code> cells, decorators, source metadata, and other protocol details. Dynamic <code>type</code> construction is not a textual macro and should not be used merely to avoid writing clear class syntax.

### 9.18.5 Namespace preparation with <code>__prepare__</code>

Before executing a class body, Python calls the selected metaclass’s <code>__prepare__</code> if provided. It must return a mapping-like namespace into which body assignments are made.

~~~python
class RecordingNamespace(dict[str, object]):
    def __setitem__(self, key: str, value: object) -> None:
        print(f"binding {key}")
        super().__setitem__(key, value)


class RecordingMeta(type):
    @classmethod
    def __prepare__(
        mcls,
        name: str,
        bases: tuple[type, ...],
        **kwargs: object,
    ) -> RecordingNamespace:
        return RecordingNamespace()
~~~

Defining a class with <code>RecordingMeta</code> records assignments including compiler-provided names such as <code>__module__</code> and <code>__qualname__</code>. The prepared namespace can preserve metadata, reject duplicate declarations, or interpret field objects.

Ordinary dictionaries already preserve insertion order in modern Python, so order preservation alone no longer requires a custom mapping. A nonstandard namespace must support the operations the compiler and <code>type</code> expect; exotic semantics can break class creation and tooling.

### 9.18.6 Rejecting duplicate class-body bindings

Normal class bodies allow later assignment to replace an earlier one:

~~~python
class Replaced:
    value = 1
    value = 2
~~~

A specialised schema language may want duplicate fields to be an error. A prepared namespace can enforce this while permitting compiler-managed names carefully.

### Worked example 9.6 — A duplicate-aware declaration metaclass

~~~python
class UniqueNamespace(dict[str, object]):
    def __setitem__(self, key: str, value: object) -> None:
        if key in self and key not in {"__annotations__"}:
            raise TypeError(f"duplicate class binding: {key}")
        super().__setitem__(key, value)


class UniqueBindings(type):
    @classmethod
    def __prepare__(
        mcls,
        name: str,
        bases: tuple[type, ...],
        **kwargs: object,
    ) -> UniqueNamespace:
        return UniqueNamespace()


class Schema(metaclass=UniqueBindings):
    account_id = str
    balance = int
~~~

This policy is intentionally narrow and still simplified. Decorated methods can require deliberate rebinding patterns; augmented annotations mutate <code>__annotations__</code>; compiler or framework entries may need exceptions. A real declaration language specifies which duplicate forms are legal rather than rejecting blindly.

### 9.18.7 Class-body scope is not an enclosing function scope

Names assigned earlier in a class body can be used by later expressions in that body, but a method body does not normally close over arbitrary class-local names.

~~~python
class ScopeExample:
    factor = 3
    doubled = factor * 2

    def apply(self, value: int) -> int:
        return value * self.factor
~~~

The method uses <code>self.factor</code>. Writing <code>return value * factor</code> would seek a local or enclosing function/global/built-in name under LEGB, not automatically the class namespace. Class attribute lookup is explicit through an instance, class, or special <code>__class__</code> reference.

Methods using <code>super()</code> or <code>__class__</code> can cause the compiler to create a <code>__classcell__</code> entry. A metaclass that copies or transforms the namespace must pass that cell correctly to <code>type.__new__</code>; discarding it can cause a runtime error during class creation.

### 9.18.8 <code>__new__</code> creates the class object

A metaclass’s <code>__new__</code> receives the metaclass, proposed name, resolved bases, namespace, and applicable class keywords. It can validate or transform the namespace before delegating to <code>type.__new__</code>.

~~~python
class RequiresCategory(type):
    def __new__(
        mcls,
        name: str,
        bases: tuple[type, ...],
        namespace: dict[str, object],
        **kwargs: object,
    ):
        if name != "Categorised":
            category = namespace.get("category")
            if not isinstance(category, str) or not category:
                raise TypeError(f"{name} must define non-empty category")

        cls = super().__new__(mcls, name, bases, namespace, **kwargs)
        return cls


class Categorised(metaclass=RequiresCategory):
    pass


class Report(Categorised):
    category = "financial"
~~~

Validation before <code>super().__new__</code> sees the proposed namespace but not a completed class or its computed MRO. Validation after delegation can inspect inherited attributes and descriptors after ordinary class construction. The chosen timing should match the invariant.

The example deliberately requires the subclass body itself to define <code>category</code> by inspecting <code>namespace</code>. Using <code>getattr(cls, "category", None)</code> after creation would also accept an inherited category. Neither is universally correct; “must declare” and “must provide after inheritance” are different contracts.

### 9.18.9 <code>__init__</code> initialises the class object

After <code>__new__</code> returns a class object of the expected metaclass lineage, the metaclass initialiser can perform post-construction work.

~~~python
class CountedMeta(type):
    created: list[type] = []

    def __init__(cls, name, bases, namespace, **kwargs) -> None:
        super().__init__(name, bases, namespace, **kwargs)
        CountedMeta.created.append(cls)
~~~

As at the instance level, <code>__new__</code> creates and returns the object; <code>__init__</code> initialises it. Class registries created here hold strong references unless designed otherwise, execute during imports, and accumulate across tests or reloads. Their lifetime is part of the system architecture.

### 9.18.10 Descriptor notification and subclass initialisation

Ordinary <code>type.__new__</code> participates in two important hooks encountered elsewhere:

- it calls <code>__set_name__</code> on suitable objects in the new class namespace;
- after the class object exists, subclass-initialisation machinery calls the next <code>__init_subclass__</code> hook in the new class’s parent chain.

Consequently, a metaclass that fails to delegate through <code>type</code> correctly may prevent ordinary descriptor setup or subclass hooks. A class decorator runs later and attaching a descriptor there requires explicit <code>__set_name__</code> notification if the descriptor depends on it.

The exact relative ordering among custom metaclass code, descriptor notifications, and subclass hooks matters. Tests that record events can verify a framework’s intended lifecycle, but framework code should rely on documented hook guarantees rather than CPython-private implementation functions.

### 9.18.11 Metaclass <code>__call__</code> governs ordinary instance construction

Calling a class such as <code>Report()</code> actually invokes call behaviour supplied by its metaclass. <code>type.__call__</code> ordinarily coordinates the class’s <code>__new__</code> and <code>__init__</code>.

~~~python
class TracingMeta(type):
    def __call__(cls, *args: object, **kwargs: object):
        print(f"constructing {cls.__name__}")
        instance = super().__call__(*args, **kwargs)
        print(f"constructed {instance!r}")
        return instance


class Traced(metaclass=TracingMeta):
    def __init__(self, value: int) -> None:
        self.value = value


item = Traced(5)
~~~

The metaclass can cache, reject, wrap, or substitute constructed instances. Doing so changes identity, subclassing, exception, concurrency, and serialisation semantics globally for governed classes.

### 9.18.12 The singleton metaclass illustrates hidden complexity

A common demonstration caches one instance per class in metaclass <code>__call__</code>. It appears concise:

~~~python
class SingletonMeta(type):
    _instances: dict[type, object] = {}

    def __call__(cls, *args: object, **kwargs: object):
        if cls not in cls._instances:
            cls._instances[cls] = super().__call__(*args, **kwargs)
        return cls._instances[cls]
~~~

This code leaves unresolved:

- concurrent first construction;
- whether later arguments are ignored, rejected, or reinitialise state;
- subclass instance separation;
- garbage collection and test reset;
- process and interpreter boundaries;
- copying, pickling, and reconstruction;
- failure during partial construction;
- dependency injection and replacement.

An explicit module-owned instance or factory often makes lifetime and configuration clearer. The example is useful precisely because it shows how a few metaclass lines can imply a large contract.

### 9.18.13 Custom instance and subclass checks

A metaclass may define <code>__instancecheck__</code> and <code>__subclasscheck__</code>, influencing <code>isinstance</code> and <code>issubclass</code>. <code>abc.ABCMeta</code> uses related machinery for abstract base classes and virtual subclassing.

~~~python
class HasSerializeMeta(type):
    def __instancecheck__(cls, instance: object) -> bool:
        return callable(getattr(instance, "serialize", None))


class Serializable(metaclass=HasSerializeMeta):
    pass


class Message:
    def serialize(self) -> bytes:
        return b"message"


assert isinstance(Message(), Serializable)
~~~

This runtime check proves only that retrieval produced a callable at that moment. It does not verify the signature, return type, determinism, safety, or other behavioural laws. Structural <code>Protocol</code> annotations are generally clearer for static interface expression, while ordinary capability tests can suffice at runtime.

Custom instance checks should be fast, side-effect controlled, and recursion safe. Calling <code>getattr</code> can execute arbitrary dynamic access, as §9.16 showed.

### 9.18.14 Customising <code>mro</code> changes inherited meaning

A metaclass can override MRO computation. This changes which descriptors, methods, constructors, and cooperative hooks every instance sees. It can invalidate the assumptions of bases that were written for C3’s normal guarantees.

Such customisation belongs to specialised interoperability systems, not ordinary application architecture. If a design seems to require hand-authored lookup order, first make collaborators explicit through composition or refactor conflicting responsibilities.

### 9.18.15 Non-class bases and <code>__mro_entries__</code>

In a class statement, a base expression need not initially evaluate to a class. A non-type object may provide <code>__mro_entries__(bases)</code>, returning replacement classes used as actual bases. This mechanism supports generic-alias and class-adaptation facilities.

The original base expressions can be recovered through metadata such as <code>__orig_bases__</code> in applicable cases, while <code>__bases__</code> contains resolved class bases. The mechanism is advanced because visually written bases may differ from the final inheritance graph. Libraries using it must make introspection and error messages unusually clear.

### 9.18.16 Class subscription need not be metaclass subscription

An expression such as <code>Container[int]</code> may be handled by <code>Container.__class_getitem__</code>, commonly used to parameterise generic classes for annotations. A metaclass <code>__getitem__</code> can also govern subscription of its class objects and may take precedence under the language rules.

These operations create or return objects representing parameterisation; they do not necessarily construct new runtime subclasses, enforce element types on assignment, or change instance layout. Static generic meaning and runtime metaclass behaviour should not be conflated.

### 9.18.17 Metaclass state is shared at class scale

Attributes on a metaclass can be visible through governed class objects. Mutable metaclass state may be shared across many classes, modules, and tests. It needs ownership just like module globals or descriptor state.

~~~python
class RegistryMeta(type):
    registry: dict[str, type] = {}

    def __new__(mcls, name, bases, namespace, **kwargs):
        cls = super().__new__(mcls, name, bases, namespace, **kwargs)
        key = f"{cls.__module__}.{cls.__qualname__}"
        if key in mcls.registry:
            raise RuntimeError(f"duplicate class key: {key}")
        mcls.registry[key] = cls
        return cls
~~~

Even the qualified key is not universally stable: local classes include enclosing scopes, reload can create a new class object with the same key, and plugins may require unloading. A registry design must specify collision, replacement, discovery, and cleanup semantics.

### 9.18.18 Metaclass methods and class methods occupy different receivers

A method defined on a metaclass and accessed through a governed class binds that class as receiver. A class method defined in the class body also receives the governed class, but it participates in the class’s own inheritance namespace. Their placement conveys different ownership:

- a class method is behaviour of the domain class and is inherited by its subclasses;
- a metaclass method is behaviour governing class objects and may apply across unrelated classes sharing the metaclass.

Most domain factories belong as class methods. Metaclass methods suit operations over the class system itself, such as schema introspection across all governed classes.

### 9.18.19 Framework declaration versus ordinary object design

Metaclasses are common in frameworks because a class body can serve as a declarative language:

~~~python
class Customer(Table):
    identifier = Integer(primary_key=True)
    email = Text(unique=True)
~~~

Here field objects, descriptors, namespace order, inheritance, and class creation can be converted into a database schema. The metaclass is justified when the framework needs to transform an open-ended family of class declarations consistently.

In application code with three known variants, an explicit data structure may be clearer:

~~~python
customer_schema = TableSchema(
    name="customer",
    fields=(
        IntegerField("identifier", primary_key=True),
        TextField("email", unique=True),
    ),
)
~~~

The object form makes construction order, dependencies, and test isolation ordinary. Declarative class syntax is valuable when its ergonomic and integration benefits outweigh the hidden lifecycle.

### 9.18.20 Failure atomicity during class creation

If a metaclass registers a class and a later hook raises, external state may retain a class whose defining statement never bound successfully. Similar partial effects can occur when descriptors register themselves during <code>__set_name__</code> or subclass hooks mutate registries.

A robust framework validates before committing where possible. When commit must precede later work, it needs rollback. Import retry and module cleanup make this especially important because a failed import can leave external registries even if the partially initialised module is removed from ordinary import caching.

### Worked example 9.6A — Validate, build, then commit registration

~~~python
class CommandMeta(type):
    registry: dict[str, type] = {}

    def __new__(
        mcls,
        name: str,
        bases: tuple[type, ...],
        namespace: dict[str, object],
        *,
        command: str | None = None,
        **kwargs: object,
    ):
        if command is not None:
            if not command or any(char.isspace() for char in command):
                raise TypeError("command must be non-empty without whitespace")
            if command in mcls.registry:
                raise TypeError(f"duplicate command: {command}")

        cls = super().__new__(mcls, name, bases, namespace, **kwargs)

        if command is not None:
            mcls.registry[command] = cls
            cls.command_name = command
        return cls


class Command(metaclass=CommandMeta):
    pass


class ListCommand(Command, command="list"):
    pass
~~~

Validation precedes construction and registration follows successful ordinary class creation. Yet assignment of <code>cls.command_name</code> after registry insertion could itself fail under a more restrictive metaclass, leaving partial state. The most robust form completes all fallible class configuration before the single registry commit or removes the entry in an exception handler.

### 9.18.21 Interaction with class decorators

A class decorator receives the class object after metaclass construction and returns the object ultimately bound to the class statement name. It may return the same class, a modified class, a replacement class, or even a non-class object.

~~~python
def labelled(cls: type) -> type:
    cls.label = cls.__name__.lower()
    return cls


@labelled
class Event:
    pass
~~~

The metaclass has already selected and created <code>Event</code> before <code>labelled</code> runs. A decorator cannot retroactively change metaclass selection without returning a newly constructed replacement. Conversely, a metaclass does not automatically see transformations performed later by decorators.

With multiple decorators:

~~~python
@outer
@inner
class C:
    pass
~~~

creation is followed conceptually by <code>C = outer(inner(C))</code>. Decorator application order is bottom-up, just as for function decorators.

### 9.18.22 Choosing the least powerful class hook

Class-level customisation mechanisms differ in scope:

| Requirement | Usually smallest suitable mechanism |
|---|---|
| Transform one completed class explicitly | class decorator |
| Validate every subclass of one base | <code>__init_subclass__</code> |
| Reuse attribute-access policy | descriptor and <code>__set_name__</code> |
| Construct variants on request | factory function or class method |
| Inspect or alter the class namespace before creation | metaclass <code>__prepare__</code>/<code>__new__</code> |
| Control construction of instances across a class family | metaclass <code>__call__</code>, only if class-local factories cannot own it |
| Combine nominal abstract-class machinery | <code>ABCMeta</code> through <code>ABC</code> |

“Least powerful” means smallest affected semantic surface, not least sophisticated. A narrow mechanism is easier to compose because fewer unrelated behaviours pass through it.

### 9.18.23 Testing a metaclass as a lifecycle system

Tests should cover more than a valid class declaration:

1. invalid namespaces fail before external commit;
2. inherited versus directly declared values follow the stated rule;
3. descriptors receive correct names;
4. subclass hooks run once in cooperative order;
5. class keywords are consumed or forwarded correctly;
6. multiple bases either select a compatible metaclass or fail deliberately;
7. decorators observe the intended post-metaclass state;
8. repeated import, reload, and test isolation do not corrupt registries;
9. concurrent class creation, if supported, has defined synchronisation;
10. copying, pickling, and instance construction still satisfy their contracts;
11. error messages identify the source declaration, not only an internal hook;
12. static analysis and introspection can recover declared interfaces.

### 9.18.24 Metaclasses complete rather than violate the object model

Metaclasses can initially appear to be an exception to the simpler claim that classes create instances. They are instead a recursive application of it. Ordinary objects are created under class call semantics; class objects are created under metaclass call semantics. Descriptors govern attributes at either level. MRO governs lookup for classes and metaclasses. <code>__new__</code> and <code>__init__</code> retain their allocation/initialisation distinction.

This capstone revises no earlier rule. It exposes the level at which those same rules construct the objects that programmers normally treat as types.

> **Common misconception — “A metaclass is a class factory.”**  
> That phrase is directionally useful but incomplete. A metaclass is itself a class whose instances are classes; its protocols can govern namespace preparation, class construction, class behaviour, and instance construction.

> **Common misconception — “Metaclasses run when an instance is created.”**  
> Metaclass class-construction hooks run when the class is created. The metaclass’s <code>__call__</code> also participates later when that class is called to create an instance.

> **Common misconception — “A metaclass conflict is solved whenever a combined metaclass compiles.”**  
> A legal metaclass MRO proves structural compatibility only. The policies of the component metaclasses must also cooperate semantically.
