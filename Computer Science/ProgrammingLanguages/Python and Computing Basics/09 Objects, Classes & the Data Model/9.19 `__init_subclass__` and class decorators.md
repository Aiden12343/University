# 9.19 `__init_subclass__` and class decorators

Metaclasses govern an entire class-creation regime, but many requirements are narrower. A base class may need to validate or register only its descendants; <code>__init_subclass__</code> supplies that hook. A particular class declaration may need explicit post-processing; a class decorator supplies that transformation. Both preserve ordinary metaclass selection unless their implementations deliberately construct replacements.

### 9.19.1 <code>__init_subclass__</code> observes new descendants

When a class is created as a subclass, Python calls an inherited <code>__init_subclass__</code> hook on the new class. The hook is implicitly a class method: <code>cls</code> is the newly created subclass, not the base on which the source definition appears.

~~~python
class ObservableBase:
    def __init_subclass__(cls, **kwargs: object) -> None:
        super().__init_subclass__(**kwargs)
        print(f"created subclass {cls.__qualname__}")


class First(ObservableBase):
    pass


class Second(First):
    pass
~~~

The hook runs for both <code>First</code> and <code>Second</code>. It runs during their class creation, commonly while the defining module is being imported, not when their instances are constructed.

### 9.19.2 Class-header keywords form a configuration channel

Extra keywords in a class header can be consumed by subclass hooks:

~~~python
class Versioned:
    version: int

    def __init_subclass__(
        cls,
        *,
        version: int,
        **kwargs: object,
    ) -> None:
        super().__init_subclass__(**kwargs)
        if version < 1:
            raise TypeError("version must be positive")
        cls.version = version


class CurrentFormat(Versioned, version=3):
    pass
~~~

The keyword is configuration for class creation; it is not an argument to <code>CurrentFormat.__init__</code>. A participating hook consumes keywords it owns and forwards the rest. Eventually <code>object.__init_subclass__</code> accepts no arbitrary class keywords, so an unconsumed keyword ordinarily exposes a <code>TypeError</code> rather than disappearing silently.

### 9.19.3 Cooperative hooks follow the MRO

Multiple bases can each own a class keyword if their hooks cooperate.

~~~python
class Versioned:
    def __init_subclass__(
        cls,
        *,
        version: int,
        **kwargs: object,
    ) -> None:
        cls.version = version
        super().__init_subclass__(**kwargs)


class Labelled:
    def __init_subclass__(
        cls,
        *,
        label: str,
        **kwargs: object,
    ) -> None:
        cls.label = label
        super().__init_subclass__(**kwargs)


class Message(Versioned, Labelled, version=2, label="event"):
    pass
~~~

The MRO determines the hook chain. Each method consumes one keyword and advances. As with cooperative initialisers, compatible signatures and exactly-once delegation are obligations. Calling <code>object.__init_subclass__</code> directly from <code>Versioned</code> would skip <code>Labelled</code>.

### 9.19.4 Validate inherited capability versus local declaration

After ordinary class creation, <code>cls</code> exposes inherited attributes. A hook using <code>hasattr(cls, "encode")</code> accepts an inherited implementation. Sometimes the requirement is instead that every subclass declare its own method. Then inspect <code>cls.__dict__</code>.

~~~python
class MustOverride:
    def process(self) -> None:
        raise NotImplementedError

    def __init_subclass__(cls, **kwargs: object) -> None:
        super().__init_subclass__(**kwargs)
        if "process" not in cls.__dict__:
            raise TypeError(f"{cls.__name__} must declare process")
~~~

This exact policy can be too strict for intermediate abstract subclasses, generated methods, or deliberate inheritance. <code>abc.abstractmethod</code> ordinarily expresses abstract implementation requirements more accurately. The example illustrates the difference between namespace declaration and effective interface, not a recommended replacement for abstract base classes.

### 9.19.5 Registration is an import-time side effect

~~~python
class Plugin:
    registry: dict[str, type["Plugin"]] = {}

    def __init_subclass__(
        cls,
        *,
        plugin_name: str,
        **kwargs: object,
    ) -> None:
        super().__init_subclass__(**kwargs)
        if not plugin_name:
            raise TypeError("plugin name cannot be empty")
        if plugin_name in Plugin.registry:
            raise ValueError(f"duplicate plugin name: {plugin_name}")
        Plugin.registry[plugin_name] = cls


class TextPlugin(Plugin, plugin_name="text"):
    pass
~~~

The registry becomes populated only if the module defining <code>TextPlugin</code> is imported. Discovery therefore depends on import topology. Retaining the class keeps its module objects and associated state reachable. Reloading can attempt to register a new class under the same name. Test suites that define temporary subclasses can pollute later tests.

A plugin architecture must specify:

- which modules are discovered and imported;
- whether names are global or namespaced;
- duplicate and version policy;
- whether replacement and unloading are supported;
- lifetime and weak/strong ownership;
- synchronisation during concurrent discovery;
- security, because importing a plugin executes code;
- how failures avoid partial registry state.

The hook makes registration concise; it does not answer those system questions.

### 9.19.6 Avoid accidentally sharing a registry across unrelated roots

Using <code>cls.registry</code> can allow a subclass to shadow the registry and split registration unexpectedly; always using <code>Plugin.registry</code> deliberately centralises it. Alternatively, each root may initialise its own registry when directly subclassed. The intended ownership must be explicit.

~~~python
class RegistryRoot:
    registry: dict[str, type] = {}

    def __init_subclass__(
        cls,
        *,
        abstract: bool = False,
        key: str | None = None,
        **kwargs: object,
    ) -> None:
        super().__init_subclass__(**kwargs)
        if abstract:
            return
        if key is None:
            raise TypeError("concrete subclass requires key")
        if key in RegistryRoot.registry:
            raise TypeError(f"duplicate key: {key}")
        RegistryRoot.registry[key] = cls
~~~

An explicit <code>abstract</code> flag is one possible policy. Integration with <code>inspect.isabstract</code> and <code>ABC</code> may be preferable when abstractness already has formal meaning.

### 9.19.7 A class decorator is explicit at the declaration site

A **class decorator** is a callable applied to a completed class object. The syntax:

~~~python
@register
class JsonCodec:
    pass
~~~

is approximately equivalent, after class construction, to:

~~~python
class JsonCodec:
    pass


JsonCodec = register(JsonCodec)
~~~

The decorator’s visible presence is useful when only selected classes opt into behaviour. <code>__init_subclass__</code>, by contrast, applies implicitly to every descendant of a base.

### Worked example 9.6B — A parameterised class decorator

~~~python
from collections.abc import Callable
from typing import TypeVar


C = TypeVar("C", bound=type)
codec_registry: dict[str, type] = {}


def codec(name: str) -> Callable[[C], C]:
    if not name or not name.isascii():
        raise ValueError("codec name must be non-empty ASCII")

    def decorate(cls: C) -> C:
        if name in codec_registry:
            raise ValueError(f"duplicate codec: {name}")
        cls.codec_name = name
        codec_registry[name] = cls
        return cls

    return decorate


@codec("json")
class JsonCodec:
    pass
~~~

Evaluation has two stages. <code>codec("json")</code> runs when Python evaluates the decorator expressions and returns <code>decorate</code>. After the class object is created, <code>decorate(JsonCodec)</code> runs and its return value is bound to <code>JsonCodec</code>.

The generic annotation expresses that this decorator returns the same class type it receives, although dynamically adding <code>codec_name</code> may not become visible to every static checker. A decorator that returns a different class or wrapper needs a different type contract.

### 9.19.8 Decorators can replace the class entirely

Python does not require a class decorator to return the original class:

~~~python
def replace_with_factory(cls: type):
    def make(*args: object, **kwargs: object):
        return cls(*args, **kwargs)
    return make
~~~

After decoration, the source-level class name would refer to a function. This can surprise <code>isinstance</code>, inheritance, introspection, pickling, documentation, and static analysis. Mutating and returning the original class is usually less disruptive when the abstraction remains a class. Replacement should be a conspicuous, documented semantic choice.

### 9.19.9 Attaching descriptors after creation requires notification

A decorator that adds a descriptor after <code>type.__new__</code> has completed does not receive automatic <code>__set_name__</code> handling:

~~~python
def add_identifier(cls: type) -> type:
    descriptor = Named()
    setattr(cls, "identifier", descriptor)
    descriptor.__set_name__(cls, "identifier")
    return cls
~~~

If the descriptor requires other class-creation integration, manual attachment may still be insufficient. A metaclass that places it in the namespace before delegating to <code>type.__new__</code>, or an explicit descriptor in the original class body, may be more correct.

### 9.19.10 Decorator stacking has directional effects

~~~python
@audit
@register
class Handler:
    pass
~~~

<code>register</code> receives the newly created class first. <code>audit</code> receives whatever <code>register</code> returned. If <code>register</code> stores its argument and <code>audit</code> later replaces it, the registry and public name refer to different objects. Decorators that register, wrap, or replace must document ordering requirements or be designed to commute.

### 9.19.11 Dataclass is a class transformation

<code>@dataclass</code> is a prominent class decorator. It inspects annotated fields and can add methods such as <code>__init__</code>, <code>__repr__</code>, and <code>__eq__</code>. Options such as slots can require returning a new class rather than merely mutating the old one. This explains why custom <code>__init_subclass__</code> hooks and decorator ordering can interact in non-obvious ways: subclass hooks occur during the original class construction, while decorators transform afterward.

Frameworks combining dataclasses, abstract bases, descriptors, and registration should test actual lifecycle order. Assumptions based only on surface decorator placement are insufficient.

### 9.19.12 Comparing the mechanisms

| Property | <code>__init_subclass__</code> | Class decorator | Metaclass |
|---|---|---|---|
| Opt-in form | inherit from a base | annotate a declaration | inherit governed base or specify metaclass |
| Scope | all descendants following hook chain | selected decorated class | all classes governed by metaclass |
| Runs relative to class creation | during ordinary subclass initialisation | after class object is created | controls class construction itself |
| Sees prepared namespace before class exists | no | no | yes |
| Can naturally affect metaclass selection | no | no | yes |
| Composition concern | cooperative MRO hooks | decorator ordering | metaclass compatibility and MRO |
| Typical use | descendant validation/registration | explicit transformation/registration | declaration frameworks and class-wide policy |

The table describes normal use, not absolute power. Any hook can call general Python code and construct replacements. Design should be based on the smallest truthful lifecycle, not on what is technically possible.

### 9.19.13 Error location and diagnostic quality

Class hooks run while a class statement is executing, often during import. Errors can therefore surface as import failures several frames removed from the declaration. A good error identifies:

- the class’s qualified name and module;
- the offending field, keyword, or method;
- the violated requirement;
- conflicting registered owner where applicable;
- corrective action without exposing secrets.

Raise <code>TypeError</code> for a malformed class interface or unsupported class-definition argument and <code>ValueError</code> for an unacceptable value of an otherwise accepted form, unless a framework documents a different exception taxonomy.

### 9.19.14 Test isolation and reversibility

Tests commonly create local subclasses. If creation mutates a permanent registry, garbage collection of the local name will not remove the registry entry. Options include:

- an explicit registry object injected into registration;
- a context manager that snapshots and restores registry state;
- weak-value storage when lifecycle semantics permit it;
- unique test namespaces;
- an explicit unregister operation with ownership checks;
- discovery that computes current plugins instead of mutating global state.

Do not solve contamination by clearing an unrelated global registry indiscriminately; another concurrent test or application component may own its contents.

### 9.19.15 Selection rules

Use <code>__init_subclass__</code> when inheriting from the base truthfully means accepting the policy for all descendants. Use a class decorator when transformation should be explicit on selected declarations. Use a descriptor when the policy belongs to individual attributes. Use a metaclass only when the namespace-before-class or class-of-classes level is essential. Use an ordinary function or data object when no class lifecycle is needed.

> **Common misconception — “<code>__init_subclass__</code> initialises instances of subclasses.”**  
> It runs when each subclass object is created. Instance initialisation remains the role of that class’s construction protocol.

> **Common misconception — “A class decorator always preserves a class.”**  
> The decorator’s return value replaces the name and can be any object. Replacement may disrupt type identity, inheritance, introspection, and serialisation.

> **Common misconception — “Registration means discovery is solved.”**  
> Registration occurs only for class definitions that execute. Module discovery, import authority, duplicate policy, failure recovery, and unloading remain system responsibilities.
