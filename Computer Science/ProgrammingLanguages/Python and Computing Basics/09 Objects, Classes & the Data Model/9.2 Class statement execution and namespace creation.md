# 9.2 Class statement execution and namespace creation

A `class` statement executes a body to produce a class namespace, then asks a metaclass to construct the class object. The body executes at definition time, once per class definition, not once per instance.

```python
class Demonstration:
    print("class body executes")
    category = "example"

    def method(self) -> str:
        return self.category
```

The print occurs when execution reaches the class statement. `category` is placed in the class namespace. The `def` statement creates a function and binds it under `method` in that namespace. Later instance creation does not rerun the class body.

After the body completes, the class object is bound to `Demonstration` in the surrounding namespace. As with a function name, that binding can be rebound; the class object can also have aliases.

Class scope has specialised name-resolution behaviour. A method body does not treat class-body bindings as an enclosing function scope. It accesses class attributes through an instance or class object, such as `self.category` or `type(self).category`, rather than through bare lexical closure resolution.

### 9.2.1 A class statement is executable construction syntax

At a high level, executing

~~~python
class Example(Base, metaclass=Meta):
    body
~~~

performs a protocol roughly comprising:

1. evaluate the class name’s base expressions and explicit keyword expressions;
2. resolve non-type bases through the base-entry protocol where applicable;
3. determine a compatible metaclass;
4. ask the metaclass for a class namespace through <code>__prepare__</code> if supplied;
5. execute the body using that namespace as locals and the defining module as globals;
6. pass name, resolved bases, populated namespace, and class keywords to the metaclass to create the class;
7. apply class decorators from the class outward in bottom-up order;
8. bind the surrounding name to the final returned object.

Details are developed through §9.18. The essential point is that class syntax drives a protocol; it is not a static record declaration.

### 9.2.2 Base expressions execute before the body

~~~python
def choose_base():
    print("choose base")
    return object


class Example(choose_base()):
    print("execute body")
~~~

The call selecting the base occurs before body execution. Failure prevents the body and final name binding. Dynamically chosen bases are possible, but ordinary explicit bases are more comprehensible and statically analysable.

### 9.2.3 The class namespace begins as a prepared mapping

The metaclass can define <code>__prepare__</code> to return the mapping used for body locals. The default metaclass <code>type</code> supplies an insertion-ordered mapping compatible with normal class creation. The body binds methods, attributes, nested classes, imports, annotations, and any other assigned names into it.

~~~python
class Palette:
    primary = "blue"
    secondary = "white"

    def mix(self) -> tuple[str, str]:
        return self.primary, self.secondary
~~~

The body’s sequential execution means later statements can read earlier class-local bindings under class-scope rules. They cannot read later ones before binding.

### 9.2.4 Body effects happen once per class construction

~~~python
registrations: list[str] = []


class Registered:
    registrations.append("Registered")
~~~

This mutates the external list at definition time. Creating ten instances does not repeat it. Re-executing the class statement creates a new class object and repeats the effect.

Import-time class-body I/O or registration can make module loading order-sensitive and difficult to isolate. Prefer explicit startup registration when lifecycle matters, or document decorator/subclass registration as a deliberate import protocol.

### 9.2.5 The body can use ordinary control flow

~~~python
debug_build = False


class Service:
    if debug_build:
        mode = "debug"
    else:
        mode = "normal"

    for code in range(3):
        locals()[f"label_{code}"] = f"L{code}"
~~~

Class bodies support control statements because they execute as code. Dynamic mutation through <code>locals()</code> in class scope can create attributes because the prepared namespace is the active local mapping; it remains metaprogramming that obscures static discovery. A post-construction loop with <code>setattr</code> or a descriptor/generator can be clearer when dynamic fields are genuinely required.

The loop variable <code>code</code> itself remains in the class namespace after the loop unless removed, becoming a class attribute unintentionally. Class bodies do not provide block scope.

### 9.2.6 Annotations and assigned attributes are different entries

~~~python
class Sample:
    declared: int
    assigned: int = 3
~~~

Both names appear in annotation metadata, but only <code>assigned</code> receives an ordinary class value through the assignment. <code>Sample.declared</code> ordinarily raises <code>AttributeError</code> unless another mechanism supplies it. Frameworks such as dataclasses or validation libraries can interpret annotations to synthesize instance fields; that is an added transformation.

### 9.2.7 Methods close over enclosing function scopes, not ordinary class locals

A class defined inside a function can have methods that capture the function’s bindings:

~~~python
def make_scaled_type(factor: int):
    class Scaled:
        def apply(self, value: int) -> int:
            return factor * value

    return Scaled
~~~

<code>factor</code> is an enclosing function cell for <code>apply</code>. In contrast, a bare class-local name is not an ordinary closure source:

~~~python
def make_type():
    class Example:
        factor = 3

        def apply(self, value: int) -> int:
            return self.factor * value
    return Example
~~~

Attribute access uses class/instance lookup. This distinction lets methods inherit/override class state dynamically instead of freezing one class-body lexical binding.

### 9.2.8 The implicit __class__ cell

Methods referring to <code>__class__</code> or using zero-argument <code>super()</code> require an implicit closure cell populated with the newly created class:

~~~python
class Example:
    def kind(self) -> type:
        return __class__
~~~

The compiler and class-construction protocol coordinate a <code>__classcell__</code> entry. A custom metaclass that discards or mishandles it can cause runtime failure. This is an advanced example of the class body preparing information that only becomes fully defined after class creation.

### 9.2.9 Descriptor name notification occurs during type creation

If an object stored in the class namespace defines <code>__set_name__</code>, normal type creation calls it with the owner class and attribute name:

~~~python
class Named:
    def __set_name__(self, owner: type, name: str) -> None:
        self.public_name = name


class Record:
    field = Named()
~~~

The descriptor object is constructed during body execution. After the class object exists, it learns that it is stored as <code>Record.field</code>. This enables reusable descriptors without repeating field names in constructor arguments. Reassigning the same descriptor to a class after creation does not automatically reproduce all class-creation notifications; dynamic installation needs explicit handling.

### 9.2.10 Base-class subclass hooks run on creation

After a new class is created, a parent’s <code>__init_subclass__</code> hook can validate or register it. This occurs per subclass definition, not per instance.

~~~python
class NamedPlugin:
    registry: dict[str, type] = {}

    def __init_subclass__(cls, *, name: str, **kwargs) -> None:
        super().__init_subclass__(**kwargs)
        if name in cls.registry:
            raise ValueError(f"duplicate plugin: {name!r}")
        cls.registry[name] = cls


class ReportPlugin(NamedPlugin, name="report"):
    pass
~~~

The keyword <code>name</code> in the class header is passed through class-creation hooks rather than becoming an automatic class attribute. Multiple inheritance requires cooperative consumption/forwarding of keywords. Registration retains class objects and creates import/reload/test-lifecycle concerns.

### 9.2.11 Class decorators run after class creation

~~~python
def register(cls):
    registry[cls.__name__] = cls
    return cls


@register
class Handler:
    pass
~~~

The metaclass has already constructed Handler, descriptors have received name notifications, and subclass hooks have run before the class decorator receives it. The decorator can return a replacement object, so surrounding name <code>Handler</code> need not ultimately bind the original class.

Class decorators affect only the decorated class unless they modify inherited/shared state; metaclasses and subclass hooks can influence an entire family. Prefer the least powerful mechanism matching the lifecycle.

### 9.2.12 Failure can occur after some definition effects

If a late body statement, metaclass hook, subclass hook, or decorator raises, the surrounding class name may remain unbound. Earlier effects—prints, registry mutations, file access, creation of helper objects—are not generally rolled back.

~~~python
registry: list[str] = []

try:
    class Broken:
        registry.append("body ran")
        raise RuntimeError("definition failed")
except RuntimeError:
    pass

print(registry)                # ['body ran']
~~~

Definition-time protocols should validate before irreversible registration where possible and provide cleanup/transaction design when partial import state matters.

### 9.2.13 Rebinding the class name does not change existing instance types

~~~python
class Version:
    pass


instance = Version()
OldVersion = Version


class Version:
    pass


print(type(instance) is OldVersion)  # True
print(type(instance) is Version)     # False
~~~

The second class statement creates a new class object and rebinds the module name. Existing instances retain their original type object. Reloading modules can similarly create multiple generations of nominally named classes, causing <code>isinstance</code>, registries, pickling, and singleton assumptions to surprise.

### Worked example 9.2A — Trace the entire definition phase

~~~python
events: list[str] = []


def class_decorator(cls):
    events.append(f"decorate {cls.__name__}")
    return cls


class Base:
    def __init_subclass__(cls, **kwargs) -> None:
        events.append(f"subclass {cls.__name__}")
        super().__init_subclass__(**kwargs)


class Descriptor:
    def __set_name__(self, owner: type, name: str) -> None:
        events.append(f"set_name {owner.__name__}.{name}")


@class_decorator
class Child(Base):
    events.append("body")
    field = Descriptor()
~~~

For ordinary <code>type</code> construction, the relevant event order is:

1. <code>body</code> while the namespace is populated;
2. <code>set_name Child.field</code> during class creation;
3. <code>subclass Child</code> through the base hook;
4. <code>decorate Child</code> after the class object has been created.

This ordering determines which metadata each hook can observe and which partial effects remain if a later phase fails.

> **Common misconception — “A class body is a template copied into each instance.”**  
> It is executable code used to prepare a class namespace once per class-statement execution. Instances later acquire state through construction and attribute operations.
