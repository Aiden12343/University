# 9.20 Integrated object-model trace

The individual protocols become reliable only when their order is understood. This section follows one small class family from source execution to class objects, from class call to instance, and from attribute syntax to descriptor and method results. The event recorder is pedagogical instrumentation: it deliberately makes normally implicit protocol transitions visible.

### 9.20.1 Instrumented definitions

~~~python
from __future__ import annotations

from typing import Any


events: list[str] = []


class TraceMeta(type):
    @classmethod
    def __prepare__(
        mcls,
        name: str,
        bases: tuple[type, ...],
        **kwargs: object,
    ) -> dict[str, object]:
        events.append(f"prepare:{name}")
        return super().__prepare__(name, bases, **kwargs)

    def __new__(
        mcls,
        name: str,
        bases: tuple[type, ...],
        namespace: dict[str, object],
        **kwargs: object,
    ) -> TraceMeta:
        events.append(f"meta-new-before:{name}")
        cls = super().__new__(mcls, name, bases, namespace, **kwargs)
        events.append(f"meta-new-after:{name}")
        return cls

    def __init__(
        cls,
        name: str,
        bases: tuple[type, ...],
        namespace: dict[str, object],
        **kwargs: object,
    ) -> None:
        events.append(f"meta-init:{name}")
        super().__init__(name, bases, namespace, **kwargs)

    def __call__(cls, *args: object, **kwargs: object):
        events.append(f"meta-call-before:{cls.__name__}")
        instance = super().__call__(*args, **kwargs)
        events.append(f"meta-call-after:{cls.__name__}")
        return instance


class Measured:
    def __set_name__(self, owner: type, name: str) -> None:
        self.public_name = name
        self.storage_name = f"_{name}"
        events.append(f"set-name:{owner.__name__}.{name}")

    def __get__(self, instance: object | None, owner: type | None = None):
        owner_name = owner.__name__ if owner is not None else "None"
        if instance is None:
            events.append(f"get-class:{owner_name}.{self.public_name}")
            return self
        events.append(f"get-instance:{type(instance).__name__}.{self.public_name}")
        raw = object.__getattribute__(instance, "__dict__")[self.storage_name]
        return raw * 2

    def __set__(self, instance: object, value: int) -> None:
        events.append(f"set-instance:{type(instance).__name__}.{self.public_name}")
        if value < 0:
            raise ValueError("measurement must be non-negative")
        object.__getattribute__(instance, "__dict__")[self.storage_name] = value


class HookRoot(metaclass=TraceMeta):
    def __init_subclass__(cls, **kwargs: object) -> None:
        events.append(f"init-subclass:{cls.__name__}")
        super().__init_subclass__(**kwargs)


def mark(cls: type) -> type:
    events.append(f"decorate:{cls.__name__}")
    cls.marked = True
    return cls
~~~

Defining <code>TraceMeta</code> itself is governed by <code>type</code>, not by <code>TraceMeta</code>, so its own hooks do not log its definition. Defining <code>HookRoot</code> does produce events; clear them before isolating the next declaration:

~~~python
events.clear()


@mark
class Base(HookRoot):
    measured = Measured()

    def __new__(cls, value: int) -> Base:
        events.append(f"instance-new:{cls.__name__}")
        return super().__new__(cls)

    def __init__(self, value: int) -> None:
        events.append(f"instance-init:{type(self).__name__}")
        self.measured = value

    def report(self) -> int:
        events.append("report:Base")
        return self.measured
~~~

### 9.20.2 Class creation trace

After the <code>Base</code> statement completes, the relevant event order is:

~~~text
prepare:Base
meta-new-before:Base
set-name:Base.measured
init-subclass:Base
meta-new-after:Base
meta-init:Base
decorate:Base
~~~

The order can now be explained without invoking magic:

1. Python evaluates the decorator expression <code>mark</code> and base expression <code>HookRoot</code>.
2. <code>TraceMeta</code> is selected because it is the metaclass of <code>HookRoot</code>.
3. <code>TraceMeta.__prepare__</code> supplies the namespace.
4. The body executes, constructing one <code>Measured</code> object and several function objects, then binding them into that namespace.
5. Calling the metaclass enters <code>TraceMeta.__new__</code>.
6. Its delegation to <code>type.__new__</code> creates <code>Base</code>. During that ordinary construction, the descriptor receives <code>__set_name__</code>, then the inherited <code>HookRoot.__init_subclass__</code> runs with the new <code>Base</code> as <code>cls</code>.
7. Control returns to the remainder of metaclass <code>__new__</code>, then metaclass <code>__init__</code> initialises the new class object.
8. The decorator receives the completed class, adds <code>marked</code>, and returns it.
9. The module namespace is finally bound so <code>Base</code> refers to that returned class.

The event ordering also explains why <code>Base</code> cannot ordinarily refer to its eventual global name inside its own class body: that binding has not happened. Methods can use the compiler-supported <code>__class__</code> closure once invoked later.

### 9.20.3 Creating a subclass adds no descriptor copy

~~~python
events.clear()


class Child(Base):
    def report(self) -> int:
        events.append("report:Child")
        return super().report() + 1
~~~

The event order is:

~~~text
prepare:Child
meta-new-before:Child
init-subclass:Child
meta-new-after:Child
meta-init:Child
~~~

No <code>set-name:Child.measured</code> event occurs. <code>Child</code> inherits the descriptor object stored in <code>Base.__dict__</code>; the descriptor is not copied into the child namespace and is not automatically notified again. The dynamic <code>owner</code> argument supplied during later access can nevertheless be <code>Child</code>.

The decorator also does not recur: decorators apply to the particular class statement they annotate and are not inherited transformations. The attribute <code>marked</code>, however, is inherited through ordinary lookup.

### 9.20.4 Calling the class traverses the metaclass and class protocols

~~~python
events.clear()
item = Child(5)
~~~

The resulting events are:

~~~text
meta-call-before:Child
instance-new:Child
instance-init:Child
set-instance:Child.measured
meta-call-after:Child
~~~

Detailed derivation:

1. <code>Child(5)</code> is a call on a class object whose type is <code>TraceMeta</code>.
2. <code>TraceMeta.__call__</code> receives <code>Child</code> as <code>cls</code> and logs before delegation.
3. <code>type.__call__</code> locates inherited <code>Base.__new__</code> and calls it with dynamic class <code>Child</code> and argument <code>5</code>.
4. <code>Base.__new__</code> delegates allocation and returns a newly allocated <code>Child</code>.
5. Because the returned object is an instance of the class being constructed, ordinary construction locates inherited <code>Base.__init__</code> and calls it.
6. Assignment to <code>self.measured</code> finds a data descriptor in <code>Base</code> through <code>Child.__mro__</code> and invokes <code>Measured.__set__</code>.
7. The descriptor validates and stores <code>_measured: 5</code> in the instance dictionary.
8. Control returns through <code>type.__call__</code> and then <code>TraceMeta.__call__</code>, which logs completion and returns the instance.

The integer argument was passed to both <code>__new__</code> and <code>__init__</code> under ordinary construction. Neither the descriptor nor the metaclass invented the argument flow.

### 9.20.5 Stored representation differs from apparent attribute value

~~~python
assert item.__dict__ == {"_measured": 5}

events.clear()
answer = item.measured

assert answer == 10
assert events == ["get-instance:Child.measured"]
~~~

The public read does not return a stored <code>measured</code> entry. Lookup finds the data descriptor, which retrieves raw <code>_measured</code> and doubles it. Thus three distinct notions must not be conflated:

- **public attribute name:** <code>measured</code>;
- **physical storage key:** <code>_measured</code>;
- **retrieved semantic value:** <code>10</code> from stored raw value <code>5</code>.

Serialising the dictionary directly would expose the physical representation, not necessarily the public state contract.

### 9.20.6 Class access invokes the same descriptor differently

~~~python
events.clear()
descriptor = Child.measured

assert descriptor is Base.__dict__["measured"]
assert events == ["get-class:Child.measured"]
~~~

Lookup through <code>Child</code> finds the inherited descriptor and calls <code>__get__</code> with <code>instance=None</code> and dynamic owner <code>Child</code>. The descriptor returns itself. Directly indexing <code>Base.__dict__</code> retrieves the raw namespace entry without invoking its protocol.

### 9.20.7 Method binding precedes the call body

For <code>item.report()</code>, first evaluate <code>item.report</code>. Class lookup finds the function in <code>Child.__dict__</code>. The function is a non-data descriptor, so its <code>__get__</code> returns a bound method retaining <code>item</code>. Calling that bound method supplies <code>item</code> as <code>self</code>.

~~~python
bound = item.report
assert bound.__self__ is item
assert bound.__func__ is Child.__dict__["report"]
~~~

This binding stage is why the call syntax contains no explicit receiver argument even though the function definition names <code>self</code>.

### 9.20.8 <code>super</code> continues relative to the defining class

~~~python
events.clear()
result = item.report()

assert result == 11
assert events == [
    "report:Child",
    "report:Base",
    "get-instance:Child.measured",
]
~~~

The call chain is:

1. the bound <code>Child.report</code> logs its contribution;
2. zero-argument <code>super()</code> is parameterised by defining class <code>Child</code> and receiver <code>item</code>;
3. lookup after <code>Child</code> in <code>Child.__mro__</code> finds <code>Base.report</code> and binds it to the same <code>item</code>;
4. <code>Base.report</code> logs, then reads <code>self.measured</code>;
5. the descriptor sees an instance of <code>Child</code>, retrieves and doubles its stored value to <code>10</code>;
6. <code>Child.report</code> adds one and returns <code>11</code>.

The same receiver flows through both methods; <code>super</code> changes the lookup starting point, not the object.

### 9.20.9 Rejected descriptor assignment is commit-safe

~~~python
events.clear()

try:
    item.measured = -1
except ValueError:
    pass

assert item.__dict__ == {"_measured": 5}
assert item.measured == 10
~~~

<code>Measured.__set__</code> validates before updating the dictionary. The rejected value therefore leaves prior state intact. Had it written first and validated second, the raised exception would not automatically roll back mutation.

### 9.20.10 Shadowing cannot bypass this data descriptor

Even direct insertion of a same-named dictionary key does not change public retrieval:

~~~python
item.__dict__["measured"] = 999
assert item.measured == 10
~~~

Data-descriptor precedence selects <code>Measured.__get__</code> before the instance dictionary entry. The unused key still consumes memory and may confuse naive serializers. Encapsulation mechanisms should prevent or detect such representational debris where relevant.

### 9.20.11 Replacing the class attribute changes future lookup

If code performs <code>Base.measured = 100</code>, it replaces the descriptor in the class namespace. Existing raw <code>_measured</code> values remain in instances but ordinary <code>item.measured</code> now finds the ordinary class value unless a subclass overrides it. Class-level mutation can therefore change the semantics of all current instances without touching them.

This operation is omitted from the executable trace because destructive mutation would make later assertions dependent on repair. The principle is central: class namespaces are live shared objects, not immutable templates consumed at construction.

### 9.20.12 A compact lookup calculus

For an ordinary instance <code>x</code>, dynamic type <code>T</code>, and attribute name <code>n</code>, use the following decision sequence:

1. Does a custom <code>T.__getattribute__</code> intercept? If so, follow its semantics and delegation.
2. Under ordinary base semantics, find the first <code>n</code> in the MRO.
3. If that object is a data descriptor, invoke it.
4. Else, if <code>x.__dict__</code> contains <code>n</code>, return that entry.
5. Else, if the class result is a non-data descriptor, invoke it.
6. Else, if a class result exists, return it.
7. Else, invoke a suitable <code>__getattr__</code> fallback if defined.
8. Otherwise raise <code>AttributeError</code>.

For a class object <code>C</code>, repeat the object/type idea one level higher: <code>C</code> is an instance of metaclass <code>M</code>, and lookup can involve metaclass descriptors, the class MRO, and <code>M.__getattribute__</code>. Exact class lookup has additional precedence details, but no new ontological category is needed.

### 9.20.13 A compact construction calculus

For an ordinary call <code>C(args)</code> where <code>C</code> is a class:

1. dispatch callability through <code>type(C).__call__</code>;
2. under <code>type.__call__</code>, invoke <code>C.__new__(C, args)</code> through inherited lookup;
3. receive the created object <code>x</code>;
4. if <code>x</code> has the required instance relation, invoke the applicable <code>C.__init__(x, args)</code>;
5. ignore <code>__init__</code> as a value-producing operation—it must return <code>None</code>;
6. return <code>x</code> through the metaclass call chain.

Custom metaclass call behaviour and unusual <code>__new__</code> returns can change steps. Factories that are not classes simply follow their own call protocol.

### 9.20.14 A compact class-creation calculus

For <code>class C(Bases, keywords): body</code>:

1. evaluate header expressions;
2. resolve bases and select a compatible metaclass;
3. prepare namespace;
4. execute body into namespace;
5. ask metaclass to construct and initialise class object;
6. within ordinary type construction, compute MRO and integrate descriptors and subclass hooks;
7. apply decorators;
8. bind final object to <code>C</code>.

These three calculi—lookup, instance construction, and class construction—explain most “magic” attributed to Python OOP. The language supplies dispatch protocols; user code supplies policy.

### 9.20.15 Object orientation as coordinated namespaces and protocols

The full mental model can now replace the loose “blueprint” metaphor. A Python object-oriented program is a graph of objects. Some objects are classes; some classes are metaclasses. Namespaces bind names to objects. Attribute lookup walks instance storage, class MROs, and descriptor protocols under defined precedence. Function descriptors bind receivers. Class calling invokes construction protocols. <code>super</code> advances through an MRO. Special syntax invokes type-level protocols. Invariants and substitutability constrain which programmable behaviours remain coherent.

Nothing in that account requires mystical dispatch. The difficulty is real because several ordinary mechanisms compose, and each hook can run arbitrary code. Precision comes from identifying the receiver, its dynamic type, the definition site, the MRO, the descriptor category, the namespace containing each binding, and the exact protocol transition currently occurring.
