# 9.3 Instance attributes, class attributes, and lookup

An **attribute** is a named value accessed through syntax such as `object.name`. Attribute access is governed by the object’s type and Python’s descriptor protocol; it is not necessarily a direct dictionary lookup.

For ordinary user-defined instances, simplified lookup of `instance.name` considers:

1. data descriptors in the class or its method-resolution order;
2. the instance’s own attribute storage;
3. non-data descriptors and other class attributes;
4. fallback mechanisms such as `__getattr__` when defined.

This order is refined later in the chapter. It immediately explains why class and instance attributes differ.

```python
class Account:
    currency = "GBP"

    def __init__(self, owner: str, balance_pence: int = 0) -> None:
        self.owner = owner
        self.balance_pence = balance_pence
```

`currency` is initially a class attribute shared through lookup. `owner` and `balance_pence` are instance attributes created separately for each instance.

```python
first = Account("Ada", 500)
second = Account("Grace", 800)

print(first.currency, second.currency)
first.currency = "EUR"
print(first.currency, second.currency, Account.currency)
```

The assignment `first.currency = "EUR"` ordinarily creates an instance attribute shadowing the class attribute for `first`. It does not mutate the class string or change lookup for `second`.

### Common mutable-class-attribute defect

```python
class Notebook:
    pages: list[str] = []

    def add(self, text: str) -> None:
        self.pages.append(text)
```

Unless an instance shadows `pages`, every instance lookup finds the same class-owned list. Adding through one notebook appears through the others. If each instance owns a list, construct it in `__init__`:

```python
class Notebook:
    def __init__(self) -> None:
        self.pages: list[str] = []
```

This is the class analogue of mutable default timing: determine when the object is constructed and which owners share the resulting reference.

### 9.3.1 Attribute syntax invokes a protocol

The expression <code>obj.name</code> does not mean “read key name from obj’s dictionary.” It invokes <code>type(obj).__getattribute__(obj, "name")</code> under the data model. That machinery can search class dictionaries, invoke descriptors, inspect instance storage, synthesize values, or raise.

Similarly, <code>obj.name = value</code> invokes attribute-assignment protocol, ordinarily through <code>type(obj).__setattr__</code>; deletion invokes <code>__delattr__</code>. Classes can intercept these operations, though doing so safely requires delegation to avoid recursion.

### 9.3.2 A refined ordinary instance lookup algorithm

For a normal new-style Python object (all ordinary Python 3 classes), a useful conceptual algorithm for <code>instance.name</code> is:

1. search the instance type’s method-resolution order for a class attribute named <code>name</code>;
2. if that class attribute is a **data descriptor**—it defines descriptor assignment/deletion participation as specified—call its <code>__get__</code> before consulting ordinary instance storage;
3. otherwise, if the instance has a stored attribute named <code>name</code>, return it;
4. otherwise, if a class attribute was found and is a descriptor, call its <code>__get__</code> (a non-data descriptor); if not a descriptor, return it;
5. if normal lookup raises <code>AttributeError</code>, an applicable <code>__getattr__</code> fallback may be called;
6. otherwise propagate <code>AttributeError</code>.

Custom <code>__getattribute__</code>, metaclasses, proxies, extension types, and specialized slots can refine the mechanics. This ordering explains properties, methods, and instance shadowing.

### 9.3.3 Instance storage is commonly but not always __dict__

Ordinary user instances often have a mutable dictionary:

~~~python
class Record:
    pass


record = Record()
record.name = "Ada"
record.score = 98
print(record.__dict__)
~~~

The dictionary maps strings to referenced objects. It is created/managed by the implementation and can be inspected or mutated directly. Direct mutation bypasses <code>__setattr__</code> logic if one writes the dictionary itself and should be reserved for controlled metaprogramming.

Classes using <code>__slots__</code> may omit a per-instance dictionary and store selected attributes in fixed descriptors. Extension types can use native layouts. Attribute semantics do not require one universal dictionary.

### 9.3.4 Class lookup follows the method resolution order

If an attribute is absent from the instance, lookup examines its class and base classes along the method resolution order (MRO), not merely the direct class.

~~~python
class Base:
    category = "base"


class Child(Base):
    pass


item = Child()
print(item.category)           # base
~~~

Assigning <code>Child.category = "child"</code> shadows Base for Child instances. Deleting it reveals the inherited Base attribute again. Assignment to a subclass does not overwrite the base-class dictionary entry.

### 9.3.5 Class attributes are shared lookup state, not copied fields

~~~python
class Configuration:
    retries = 3


first = Configuration()
second = Configuration()
~~~

Neither instance needs a <code>retries</code> entry. Both searches reach the same class integer. Rebinding <code>Configuration.retries = 5</code> changes later lookup for both unless an instance has shadowed the name.

The word “shared” describes lookup ownership. Immutable integers do not themselves change; the class name is rebound to a different integer object.

### 9.3.6 Instance assignment ordinarily shadows non-data class state

~~~python
first.retries = 10
Configuration.retries = 5

print(first.retries)           # 10
print(second.retries)          # 5
~~~

The first instance’s dictionary now wins over the ordinary class attribute. Deleting <code>first.retries</code> reveals the class value 5 again. This layered behaviour differs from copying a default at construction: changes to the class remain visible only to unshadowed instances.

### 9.3.7 Data descriptors override instance dictionaries

A property defining a setter/deletion protocol is a data descriptor and takes precedence over an identically named instance-dictionary entry under ordinary lookup:

~~~python
class Temperature:
    def __init__(self, celsius: float) -> None:
        self.celsius = celsius

    @property
    def celsius(self) -> float:
        return self._celsius

    @celsius.setter
    def celsius(self, value: float) -> None:
        if value < -273.15:
            raise ValueError("below absolute zero")
        self._celsius = value
~~~

The assignment <code>self.celsius = value</code> calls the property setter; storage uses a separate <code>_celsius</code> name. The getter runs on every normal read. A caller cannot bypass it by ordinary assignment to <code>celsius</code>, though deliberate mutation of <code>__dict__</code> or <code>_celsius</code> remains possible.

### 9.3.8 Non-data descriptors can be shadowed

Ordinary Python functions implement non-data descriptor retrieval. An instance dictionary entry of the same name can shadow a method if assignment is allowed:

~~~python
class Greeter:
    def greet(self) -> str:
        return "class method"


greeter = Greeter()
greeter.greet = lambda: "instance callable"
print(greeter.greet())         # instance callable
~~~

The class function still exists as <code>Greeter.greet</code>. This flexibility supports per-instance customization but can break invariants and tooling. Slots or a custom assignment policy can restrict it when method names must not be shadowed.

### 9.3.9 The mutable class attribute defect is aliasing plus lookup

~~~python
class Notebook:
    pages: list[str] = []
~~~

The class body creates one list and stores it in the class namespace. Every instance lacking an own <code>pages</code> attribute retrieves that same list. Calling <code>instance.pages.append</code> mutates it; no instance assignment occurs, so no shadow is created.

By contrast:

~~~python
notebook.pages = notebook.pages + ["new"]
~~~

The right side retrieves the shared class list and creates a new list; assignment stores that new list on this instance, shadowing the class. With <code>+=</code>, list in-place behavior can mutate the shared class list before assignment stores the same object as an instance attribute. Subtle expression choices can alter alias topology.

### 9.3.10 Class-level mutable state can be intentional

A class-wide registry or cache can deliberately live on the class:

~~~python
class Codec:
    _registry: dict[str, type["Codec"]] = {}
~~~

Then ownership must be explicit. Writing through <code>self._registry</code> retrieves shared state but makes the scope ambiguous; <code>type(self)._registry</code> can permit per-subclass override, while <code>Codec._registry</code> fixes one base owner. Assignment rather than mutation can accidentally create subclass/instance shadow state.

Shared class state needs reset, synchronization, inheritance, reload, and lifetime policies just like module globals.

### 9.3.11 Assignment to class and instance are distinct protocols

~~~python
class Example:
    value = 1


item = Example()
item.value = 2               # invokes instance assignment protocol
Example.value = 3            # invokes class object's assignment protocol
~~~

The second target object is the class, whose type is its metaclass. A descriptor stored on Example generally mediates assignment through instances, but assigning <code>Example.attribute</code> itself is controlled by the metaclass and can replace the descriptor in the class namespace rather than call the descriptor’s setter.

This distinction is important for properties: <code>instance.property = x</code> invokes its setter, while <code>Class.property = x</code> ordinarily overwrites the property object unless a metaclass prevents it.

### 9.3.12 getattr, setattr, and delattr use dynamic names

~~~python
field = "score"
value = getattr(record, field)
setattr(record, field, 99)
delattr(record, field)
~~~

These built-ins invoke normal attribute protocols using runtime strings. They are appropriate for serializers, adapters, and generic tools with an allowlisted schema. Using unchecked user-supplied names can expose methods, private state, or descriptors with effects. A mapping is often better when arbitrary dynamic keys are the core abstraction.

<code>getattr(obj, name, default)</code> returns the default only when attribute lookup raises <code>AttributeError</code>. It does not catch other exceptions raised by a descriptor/property. A present attribute whose value is <code>None</code> is not missing.

### 9.3.13 hasattr can execute code and suppress AttributeError

<code>hasattr(obj, name)</code> effectively attempts <code>getattr</code> and returns false if <code>AttributeError</code> arises. A property getter can perform expensive work or raise <code>AttributeError</code> internally due to a defect, causing <code>hasattr</code> to report absence.

~~~python
class Fragile:
    @property
    def value(self) -> int:
        raise AttributeError("internal defect")


print(hasattr(Fragile(), "value"))       # False
~~~

Use static inspection for tooling that must distinguish declaration from dynamic retrieval, or design a direct protocol rather than probing arbitrary attributes.

### 9.3.14 vars exposes namespaces where available

<code>vars(obj)</code> ordinarily returns <code>obj.__dict__</code>; called without an argument, it parallels current locals. Objects without a dictionary cause <code>TypeError</code>. The returned dictionary for an object is often live and mutable.

~~~python
attributes = vars(record)
~~~

This is not a safe serialization method. It can expose private caches, omit slots and computed properties, retain arbitrary objects, and bypass validation when mutated. Serialization requires an explicit schema and version.

### 9.3.15 Name mangling avoids accidental subclass collision

Within a class body, an identifier beginning with at least two underscores and not ending with two undergoes compile-time **name mangling**, incorporating the class name:

~~~python
class Base:
    def __init__(self) -> None:
        self.__state = 1


print(Base().__dict__)          # typically {'_Base__state': 1}
~~~

This helps a base class avoid accidental name collision with a subclass using its own <code>__state</code>. It is not security or absolute privacy: the transformed name is predictable and introspectable. Leading single underscore remains the general non-public API convention.

### 9.3.16 Attribute deletion can reveal a lower layer

~~~python
class Theme:
    color = "blue"


theme = Theme()
theme.color = "red"
del theme.color
print(theme.color)             # blue
~~~

Deletion did not make the attribute universally absent; it removed one instance layer and exposed the class layer. A descriptor’s <code>__delete__</code> or custom <code>__delattr__</code> can enforce other semantics. Postconditions should be stated as resolution results, not only dictionary-key removal.

### 9.3.17 Attribute errors should identify genuine absence

<code>__getattr__</code> is invoked after normal lookup fails with <code>AttributeError</code>. If a property raises <code>AttributeError</code> for an internal missing dependency, fallback can mask the defect by synthesizing another value.

Properties should generally let domain failures use appropriate exception types and reserve <code>AttributeError</code> for the attribute protocol’s meaning of absence. This supports tools such as <code>hasattr</code> and delegation fallbacks.

### 9.3.18 Attribute access can be computationally expensive

~~~python
class Report:
    @property
    def total(self) -> int:
        return sum(self._values)
~~~

The syntax <code>report.total</code> looks like a field read but performs \(O(n)\) work. Properties are most comprehensible when access is reasonably cheap, deterministic, and unsurprising. A method named <code>calculate_total</code> can better signal expensive or effectful work.

Caching a property changes invalidation and memory. <code>functools.cached_property</code> ordinarily stores a computed value in instance storage, allows later shadowing, and needs explicit invalidation when dependencies change. It also requires compatible instance representation.

### 9.3.19 Attribute versus item access communicates schema

<code>record.name</code> suggests a fixed attribute vocabulary governed by a type. <code>record["name"]</code> suggests mapping membership in a potentially dynamic key space. Both can be customized, but interface syntax conveys expectation.

Supporting both for the same fields can create ambiguity over missing errors, iteration, assignment, serialization, and precedence. An adapter may deliberately bridge external mappings into domain objects; the domain core should choose one authoritative model.

### Worked example 9.2B — Trace four lookup layers

~~~python
class LoggedValue:
    def __init__(self, default: int) -> None:
        self.default = default
        self.storage_name = ""

    def __set_name__(self, owner: type, name: str) -> None:
        self.storage_name = f"_{name}"

    def __get__(self, instance, owner=None):
        if instance is None:
            return self
        return instance.__dict__.get(self.storage_name, self.default)

    def __set__(self, instance, value: int) -> None:
        if value < 0:
            raise ValueError("value must be non-negative")
        instance.__dict__[self.storage_name] = value


class Sample:
    value = LoggedValue(5)
~~~

<code>Sample.value</code> calls <code>__get__</code> with <code>instance=None</code> and returns the descriptor. <code>Sample().value</code> invokes the data descriptor before ordinary instance storage and returns its default 5. Assigning <code>sample.value = 8</code> invokes <code>__set__</code>, which stores under <code>_value</code>. Even if <code>sample.__dict__["value"] = 99</code> is inserted manually, data-descriptor lookup for <code>value</code> still wins.

This preview is expanded in §9.15. It demonstrates why “attributes live in the instance dictionary” is insufficient.

### Worked example 9.2C — Avoid a class-level accumulator

Defective:

~~~python
class Batch:
    records: list[str] = []

    def add(self, record: str) -> None:
        self.records.append(record)
~~~

Correct per-instance ownership:

~~~python
class Batch:
    def __init__(self, records=()) -> None:
        self._records = list(records)

    def add(self, record: str) -> None:
        if not record:
            raise ValueError("record must be non-empty")
        self._records.append(record)

    def snapshot(self) -> tuple[str, ...]:
        return tuple(self._records)
~~~

The default empty tuple is immutable and safe to retain at definition time. Construction creates one list per instance and snapshots the input iterable. <code>snapshot</code> prevents outer mutation of internal storage. It consumes/copies only when requested and costs \(O(n)\).

> **Common misconception — “obj.attribute is always one dictionary lookup.”**  
> It is protocol dispatch whose ordinary order includes data descriptors, instance storage, non-data descriptors/class attributes, inheritance, and fallback hooks.
