# 9.4 Methods are functions transformed by descriptor access

A function stored in a class implements the descriptor protocol. Access through an instance produces a **bound method**, which retains both the underlying function and the receiving instance.

```python
class Greeter:
    def greet(self, name: str) -> str:
        return f"Hello, {name}."


greeter = Greeter()
bound = greeter.greet

print(bound("Ada"))
print(Greeter.greet(greeter, "Ada"))
```

The two calls have the same intended result. `greeter.greet` triggers attribute lookup; the function’s descriptor behaviour returns a method with `greeter` already bound as the first argument. `Greeter.greet` retrieves the function through the class, so the instance is supplied explicitly.

The phrase “Python automatically passes `self`” is an incomplete simplification. The deeper mechanism is attribute access producing a bound method. Store the same function in an ordinary list and no automatic binding occurs.

`@staticmethod` suppresses instance/class binding for a function stored in a class. `@classmethod` binds the class object as the first argument, conventionally named `cls`.

```python
class Temperature:
    def __init__(self, celsius: float) -> None:
        self.celsius = celsius

    @classmethod
    def from_fahrenheit(cls, fahrenheit: float) -> "Temperature":
        return cls((fahrenheit - 32) * 5 / 9)

    @staticmethod
    def absolute_zero() -> float:
        return -273.15
```

A class method is appropriate for an alternative constructor because `cls(...)` respects subclasses. A static method is appropriate only when behaviour conceptually belongs in the type’s namespace but needs no instance or class state; an ordinary module function is often simpler.

### 9.4.1 Function descriptor binding

For an ordinary function object \(f\) stored in class \(C\), descriptor access behaves conceptually as:

- <code>C.method</code>: obtain a callable corresponding to \(f\) without an instance receiver;
- <code>instance.method</code>: obtain a bound method containing \(f\) and <code>instance</code>;
- calling the bound method with arguments \(a\): invoke \(f(instance, a)\).

The underlying protocol call is analogous to <code>f.__get__(instance, C)</code>. Descriptor access occurs every time the attribute is retrieved, though implementations can optimize details.

### 9.4.2 Bound method structure

~~~python
class Greeter:
    def greet(self, name: str) -> str:
        return f"Hello, {name}."


greeter = Greeter()
bound = greeter.greet

print(bound.__self__ is greeter)         # True
print(bound.__func__ is Greeter.greet)   # True
~~~

The bound method’s <code>__self__</code> is the receiver; <code>__func__</code> is the underlying function. Calling <code>bound("Ada")</code> supplies only the remaining argument because receiver binding has already occurred.

Storing <code>bound</code> retains <code>greeter</code>. Event callbacks and registries that store bound methods can therefore extend instance lifetime, including everything that instance reaches.

### 9.4.3 Repeated retrieval need not preserve method identity

~~~python
first = greeter.greet
second = greeter.greet

print(first is second)         # ordinarily False
print(first == second)         # ordinarily True for same function/receiver
~~~

Attribute retrieval can create a fresh bound-method wrapper each time. Tests should compare call behaviour or documented method equality, not require identity. If deregistration uses callbacks as dictionary keys, it must understand bound-method equality/hash/lifetime rather than assuming the same object will be retrieved.

### 9.4.4 self is supplied by binding, not a keyword

~~~python
Greeter.greet(greeter, "Ada")
~~~

Access through the class returns the underlying function-like descriptor result and does not check that the first explicit argument is actually a Greeter before body execution. If a foreign object happens to support every attribute the body uses, the call might work. Normal instance syntax supplies the intended receiver and is the public interface.

<code>self</code> is conventional, not reserved. Renaming it does not change binding:

~~~python
class Unconventional:
    def value(this_object) -> int:
        return 3
~~~

The convention matters because readers, linters, documentation tools, and cooperative code expect <code>self</code> and <code>cls</code> vocabulary.

### 9.4.5 Method calls evaluate receiver access before arguments

In <code>object.method(argument())</code>, Python first evaluates <code>object</code>, resolves <code>method</code> through attribute/descriptor access, then evaluates the call arguments before invoking the obtained callable. A property or custom descriptor can therefore have effects or fail before <code>argument()</code> runs.

This matters when rewriting:

~~~python
callable_object = object.method
callable_object(argument())
~~~

The two-statement form freezes which callable/receiver is used before argument evaluation and before possible later attribute mutation. Keeping a bound method also retains its receiver.

### 9.4.6 Methods can be installed after class creation

~~~python
def describe(self) -> str:
    return type(self).__name__


class Item:
    pass


Item.describe = describe
print(Item().describe())
~~~

The assigned function implements descriptor binding because the object itself carries that protocol; it did not need to originate inside the class body. Dynamic installation is useful for frameworks and experiments but reduces static discoverability and can bypass <code>__set_name__</code> or class-creation hooks expected by other descriptors.

Assigning a bound method instead of a function creates different sharing:

~~~python
source = Item()
Item.fixed = source.describe
~~~

Every instance retrieving <code>fixed</code> can receive a callable already bound to <code>source</code>, not to itself. Always identify whether the installed object is a function descriptor, bound method, or arbitrary callable.

### 9.4.7 Per-instance function attributes do not bind automatically

~~~python
item = Item()
item.operation = describe

# item.operation()             # missing required self
print(item.operation(item))
~~~

The function sits in instance storage, which takes precedence over the non-data class layer but does not invoke class-function descriptor binding in the same way. Descriptors generally receive automatic binding when found on the type, not merely because a descriptor-like object is stored in an instance dictionary.

<code>types.MethodType</code> can explicitly bind a function to an instance, but per-instance method injection is advanced and often better represented as a stored strategy callable with a clear signature.

### 9.4.8 Class methods bind the dynamic class

~~~python
class Document:
    kind = "document"

    @classmethod
    def label(cls) -> str:
        return cls.kind


class Report(Document):
    kind = "report"


print(Report.label())          # report
~~~

Retrieving the classmethod through Report binds <code>cls</code> to Report, not necessarily the class where the function was written. This supports polymorphic alternative constructors and class-relative configuration.

Calling <code>Document.label()</code> binds Document. Retrieving through an instance also ordinarily binds its class, not the instance. The descriptor object wrapping the original function lives in the class namespace.

### 9.4.9 Alternative constructors must preserve subclass contracts

~~~python
class Temperature:
    def __init__(self, celsius: float) -> None:
        self.celsius = celsius

    @classmethod
    def from_fahrenheit(cls, fahrenheit: float):
        return cls((fahrenheit - 32.0) * 5.0 / 9.0)
~~~

Using <code>cls</code> allows a subclass call to construct that subclass. But this is correct only if every subclass constructor accepts the same celsius argument contract. A subclass that changes <code>__init__</code> incompatibly breaks inherited alternative constructors. Constructor signature compatibility is part of substitutability.

An alternative constructor can instead call <code>__new__</code> or a protected factory hook under a stable protocol, but complexity should follow a real hierarchy need.

### 9.4.10 Static methods suppress binding

~~~python
class Identifier:
    @staticmethod
    def valid(text: str) -> bool:
        return bool(text) and text.isascii()
~~~

Whether accessed through class or instance, the underlying function receives no automatic receiver. Static methods provide namespacing and inheritance/override lookup while declaring no use of instance/class state.

A module-level <code>valid_identifier</code> function is often simpler. Put it on the class when it is conceptually part of the type’s public vocabulary or is intended to vary through subclass attribute lookup. Do not use staticmethod merely to make a private helper look object-oriented.

### 9.4.11 Method overriding is attribute replacement along the MRO

~~~python
class Base:
    def describe(self) -> str:
        return "base"


class Child(Base):
    def describe(self) -> str:
        return "child"
~~~

Child’s class namespace contains a new function under the same name, so MRO lookup finds it first. The base function remains accessible through <code>Base.describe</code> or cooperative <code>super()</code> lookup. “Override” is not a separate storage slot connected magically to the base; it is ordered attribute resolution under a behavioural expectation.

The child method must satisfy the base contract for substitutability. Returning an unrelated type or strengthening preconditions can break callers even though attribute lookup succeeds.

### 9.4.12 super is a directed MRO proxy

<code>super()</code> does not mean “call my parent class” in the singular. It creates a proxy that continues attribute lookup after a specified class in the receiver’s MRO.

~~~python
class Base:
    def describe(self) -> str:
        return "base"


class Child(Base):
    def describe(self) -> str:
        return f"child({super().describe()})"
~~~

In multiple inheritance, the next method may belong to a sibling-like class in the MRO rather than the lexical base one imagines. Cooperative methods must use compatible signatures and call <code>super()</code> exactly as their protocol requires.

### 9.4.13 Method extraction freezes a receiver but not its state

~~~python
counter = BoundedCounter(10)
increment = counter.increment
counter.increment(2)
increment(3)
~~~

The bound method retains which Counter object receives later calls. It does not snapshot that object’s state; the extracted call observes the current value. Rebinding variable <code>counter</code> to another instance does not change <code>increment.__self__</code>.

This distinction is useful for callbacks and dangerous for lifecycle: a scheduled method can keep an obsolete service object alive and operate on evolved state long after registration.

### 9.4.14 Callable attributes need not be methods

An instance can have a strategy callable stored as data:

~~~python
from collections.abc import Callable


class Transformer:
    def __init__(self, operation: Callable[[str], str]) -> None:
        self.operation = operation

    def transform(self, text: str) -> str:
        return self.operation(text)
~~~

<code>operation</code> may be a function, bound method, partial, or callable object. The class delegates policy without inheriting from it. This is composition of behaviour.

If the callable is a descriptor object stored in instance state, normal descriptor binding generally does not activate as it would on the class. The stored value is simply called according to its own already-established call interface.

### 9.4.15 Method annotations omit no receiver at runtime

~~~python
class Scale:
    def apply(self, value: int) -> int:
        return value * 2
~~~

The underlying function signature includes <code>self</code>; inspecting the bound method typically presents a signature with the bound receiver removed for caller convenience. Static checkers infer receiver types through class context or explicit annotations. Runtime binding still supplies a concrete object.

A decorator that fails to preserve descriptor/signature metadata can confuse both inspection and typing. Method compatibility includes receiver binding in addition to ordinary argument forwarding.

### Worked example 9.2D — A callback registry that does not accidentally retain instances

Bound methods retain receivers. A registry that wants listeners to disappear when their objects do can use <code>weakref.WeakMethod</code> under a deliberate weak-lifetime contract:

~~~python
from collections.abc import Callable
from weakref import WeakMethod


class ListenerRegistry:
    def __init__(self) -> None:
        self._listeners: list[WeakMethod] = []

    def add(self, listener: Callable[[str], None]) -> None:
        self._listeners.append(WeakMethod(listener))

    def notify(self, message: str) -> list[Exception]:
        failures: list[Exception] = []
        surviving: list[WeakMethod] = []

        for reference in self._listeners:
            listener = reference()
            if listener is None:
                continue
            surviving.append(reference)
            try:
                listener(message)
            except Exception as error:
                failures.append(error)

        self._listeners = surviving
        return failures
~~~

WeakMethod supports bound methods whose receiver is weak-referenceable; it is not a universal wrapper for every callable. Resolving a weak reference returns a temporary strong bound method or <code>None</code> if the target is gone. The registry cleans dead references during notification.

This trades deterministic registration lifetime for owner-dependent disappearance. Concurrent destruction/notification, duplicate listener identity, thread safety, exception retention, and ordinary function callbacks require further policy. Weak references solve a specific lifetime edge, not general event design.

### Worked example 9.2E — Preserve polymorphism in an alternative constructor

~~~python
class Vector:
    def __init__(self, components: tuple[float, ...]) -> None:
        if not components:
            raise ValueError("vector requires a component")
        self._components = components

    @classmethod
    def zeros(cls, dimension: int):
        if isinstance(dimension, bool) or not isinstance(dimension, int):
            raise TypeError("dimension must be an integer")
        if dimension < 1:
            raise ValueError("dimension must be positive")
        return cls((0.0,) * dimension)


class LabelledVector(Vector):
    def __init__(self, components: tuple[float, ...], label: str = "") -> None:
        super().__init__(components)
        self.label = label
~~~

<code>LabelledVector.zeros(3)</code> calls <code>cls</code> as LabelledVector and succeeds because the subclass retains a compatible one-positional-component constructor with an optional label. If LabelledVector required a label, it would violate the inherited constructor’s assumption. A subclass can override <code>zeros</code> or the hierarchy can expose a stable internal construction hook.

> **Common misconception — “Python inserts self because a function is indented inside a class.”**  
> The function object stored on the class participates in descriptor lookup. Access through an instance creates a bound method; storing the function elsewhere does not automatically bind it.
