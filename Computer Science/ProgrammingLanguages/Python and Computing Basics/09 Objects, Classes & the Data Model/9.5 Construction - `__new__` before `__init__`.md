# 9.5 Construction: `__new__` before `__init__`

Calling a class normally invokes its metaclass’s call machinery. Conceptually, object construction separates allocation/creation from initialisation:

1. `__new__(cls, ...)` creates and returns an instance, usually of `cls`.
2. If the returned object is an instance of `cls`, `__init__(self, ...)` initialises it.
3. The class call returns the object; `__init__` itself must return `None`.

Most user-defined mutable classes override only `__init__` and inherit suitable `__new__`. Immutable subclasses often customise `__new__` because the value must be established before the immutable object exists.

### Worked example 9.2 — An immutable positive integer subtype

```python
class PositiveInt(int):
    def __new__(cls, value: int | str) -> "PositiveInt":
        converted = int(value)
        if converted <= 0:
            raise ValueError("value must be positive")
        return super().__new__(cls, converted)
```

`int` instances cannot be changed after creation. `__new__` validates and asks the superclass implementation to create the correctly valued instance. An `__init__` assignment could not replace the integer value already established.

`__new__` may return an object not belonging to `cls`; in that case the usual `__init__` step for `cls` is skipped. Such behaviour is advanced and should be used only with a precise factory or caching contract.

> **Common misconception — “`__init__` is the constructor that creates the object.”**  
> `__new__` is responsible for producing the instance; `__init__` receives an already created instance and establishes its initial state.

### 9.5.1 The metaclass owns class-call dispatch

For an ordinary class <code>C</code> whose metaclass is <code>type</code>, <code>C(*args, **kwargs)</code> conceptually follows logic similar to:

~~~python
instance = C.__new__(C, *args, **kwargs)
if isinstance(instance, C):
    result = C.__init__(instance, *args, **kwargs)
    if result is not None:
        raise TypeError("__init__ must return None")
return instance
~~~

This is a semantic sketch, not literal Python implementation. Attribute resolution, inherited methods, vectorcall optimisations, metaclass overrides, and exact subtype checks refine it. It correctly separates object production from initialization.

### 9.5.2 __new__ is invoked with the class

<code>__new__</code> receives <code>cls</code> because it must create an instance of the requested dynamic class, possibly a subclass. It is conventionally defined as a static method without writing <code>@staticmethod</code>; the object model treats it specially.

~~~python
class Record:
    def __new__(cls, *args, **kwargs):
        instance = super().__new__(cls)
        return instance
~~~

For ordinary mutable user classes, <code>object.__new__(cls)</code> allocates a blank instance with its representation prepared. Passing application constructor arguments to <code>object.__new__</code> is generally inappropriate because it does not consume them.

### 9.5.3 __init__ establishes state on an existing identity

~~~python
class Pair:
    def __init__(self, left: object, right: object) -> None:
        self.left = left
        self.right = right
~~~

At the first body statement, <code>self</code> already has identity and type Pair (or a subclass). <code>__init__</code> assigns state. Returning a non-None value is an error because the class-call result is the instance produced by <code>__new__</code>, not an arbitrary initializer result.

Calling <code>obj.__init__(...)</code> manually can reinitialize the same identity and is ordinarily outside the public contract. It can leave stale aliases, caches, invariants, and subclass state. Expose an explicit reset/reconfigure transition when reinitialization is meaningful.

### 9.5.4 Validation order and partially initialized objects

If <code>__init__</code> raises, the class call fails, but the allocated object existed. It can escape through callbacks, registries, weak references, global assignment, or poorly designed base initializers before failure.

~~~python
registry: list[object] = []


class Dangerous:
    def __init__(self, value: int) -> None:
        registry.append(self)
        if value < 0:
            raise ValueError("negative")
        self.value = value
~~~

After <code>Dangerous(-1)</code> fails, registry contains an object without <code>value</code>. Constructors should validate arguments and derive fallible state before publishing <code>self</code>. Do not register, start threads, or invoke arbitrary callbacks until the invariant is established, or implement rollback.

### 9.5.5 Assign after validating relational state

~~~python
class Interval:
    def __init__(self, start: int, stop: int) -> None:
        if start > stop:
            raise ValueError("start exceeds stop")
        self._start = start
        self._stop = stop
~~~

Both inputs are validated before invariant-bearing attributes are committed. For complex construction, compute local temporary structures first, then assign them. Python does not make a group of attribute assignments atomic, but delaying publication and using immutable fields reduces partial-state exposure.

### 9.5.6 Base initialization is an explicit cooperative call

~~~python
class Named:
    def __init__(self, name: str, **kwargs) -> None:
        if not name:
            raise ValueError("name must be non-empty")
        super().__init__(**kwargs)
        self.name = name


class Tagged(Named):
    def __init__(self, name: str, tag: str, **kwargs) -> None:
        super().__init__(name=name, **kwargs)
        self.tag = tag
~~~

Python does not automatically invoke every base initializer. A subclass chooses whether/how to use <code>super()</code> or a named base method. In cooperative multiple inheritance, every participating initializer consumes its parameters and forwards the rest exactly once along the MRO. Calling two base initializers directly can duplicate a shared ancestor.

Attribute assignment order matters when subclass methods/properties are invoked during base initialization. Base constructors should avoid calling overridable methods on partially established subclass instances unless the protocol is designed for it.

### 9.5.7 Immutable value must be fixed in __new__

An int subclass’s numeric payload is established by <code>int.__new__</code>. Instance attributes assigned later cannot change it:

~~~python
class EvenInt(int):
    def __new__(cls, value: int | str):
        converted = int(value)
        if converted % 2:
            raise ValueError("value must be even")
        return super().__new__(cls, converted)
~~~

Calling <code>EvenInt("4")</code> yields an object whose int value is 4. An <code>__init__</code> could attach extra mutable attributes if the representation permits, but it cannot turn the integer into 6.

Subclassing immutable built-ins requires care: inherited operations may return base-type results rather than preserve the subtype, and equality/hash may collapse distinctions. A constrained domain wrapper that contains an int can preserve invariants more reliably than inheriting numeric algebra.

### 9.5.8 __new__ can return an existing instance

An interning or singleton-like class can cache by construction key:

~~~python
class Symbol:
    _instances: dict[str, "Symbol"] = {}

    def __new__(cls, text: str):
        normalized = text.casefold()
        existing = cls._instances.get(normalized)
        if existing is not None:
            return existing
        instance = super().__new__(cls)
        cls._instances[normalized] = instance
        return instance

    def __init__(self, text: str) -> None:
        self.text = text.casefold()
~~~

Every class call whose <code>__new__</code> returns a Symbol instance ordinarily invokes <code>__init__</code> again, so cached instances are repeatedly initialized. This may overwrite state. A guard, initialization in <code>__new__</code>, metaclass call override, or external factory is required.

The cache is unbounded, strongly retains instances, and races under concurrency. Interning should be justified by identity semantics and memory measurements, not used as a casual singleton pattern.

### 9.5.9 Returning another type skips the requested initializer

~~~python
class Flexible:
    def __new__(cls, value: object):
        if value is None:
            return ()
        return super().__new__(cls)

    def __init__(self, value: object) -> None:
        self.value = value
~~~

<code>Flexible(None)</code> returns an empty tuple; Flexible’s <code>__init__</code> is not called because the returned object is not an instance of Flexible. This makes type annotations, introspection, and caller expectations difficult. A named factory returning a union communicates alternate types more honestly.

### 9.5.10 __init__ is not a fallible conversion method by necessity

Class calls often parse or convert, but named constructors can clarify representations:

~~~python
class Date:
    @classmethod
    def from_iso_text(cls, text: str) -> "Date":
        ...

    @classmethod
    def from_timestamp(cls, seconds: float) -> "Date":
        ...
~~~

One <code>__init__</code> overloaded to guess strings, integers, tuples, and existing Date objects creates ambiguous coercion. Named factories define which grammar, unit, timezone, and failure applies. They can still delegate to one canonical initializer once validated values exist.

### 9.5.11 Factory function versus class call

A module function can select subclasses, cache, perform async I/O, or return a protocol object without distorting a class constructor:

~~~python
def open_store(url: str) -> "Store":
    if url.startswith("memory:"):
        return MemoryStore()
    if url.startswith("file:"):
        return FileStore.from_url(url)
    raise ValueError("unsupported store scheme")
~~~

The return contract is a Store protocol/base abstraction, not necessarily a fresh instance of a class named <code>open_store</code>. Factories are ordinary functions and can be injected/tested. Use metaclass/<code>__new__</code> machinery only when class-call syntax and type construction semantics genuinely belong together.

### 9.5.12 Dataclass initialization is generated behaviour

The <code>@dataclass</code> decorator can generate <code>__init__</code> from annotated fields. <code>default_factory</code> creates a fresh mutable value per instance:

~~~python
from dataclasses import dataclass, field


@dataclass
class Notebook:
    title: str
    pages: list[str] = field(default_factory=list)
~~~

The factory is called during each generated initialization where the field is omitted. This is the class-field counterpart to avoiding mutable function defaults.

<code>__post_init__</code> runs after generated assignments and can validate relationships, but a raised exception occurs after fields have been assigned. Avoid publishing <code>self</code> before post-initialization succeeds. Frozen dataclasses use generated mechanisms to restrict ordinary assignment; they do not imply deep immutability.

### 9.5.13 Copying and deserialization may bypass __init__

Object reconstruction protocols such as copying and pickling can allocate and populate objects without an ordinary public class call/<code>__init__</code> path, depending on type hooks. Therefore an invariant enforced only in <code>__init__</code> can be bypassed by custom or unsafe reconstruction.

Pickle is unsafe for untrusted data because loading can execute arbitrary code. For trusted persistence, classes with invariants must implement/version their reduction/state hooks carefully and validate restored state. Chapter 11 treats serialization boundaries.

### 9.5.14 Finalizers are not constructor rollback

<code>__del__</code>, when defined, is a finalization hook with difficult timing, cycle, shutdown, resurrection, and exception constraints. It is not a reliable way to undo a partially failed <code>__init__</code>. The object may not have every attribute the finalizer expects.

Use local context managers while constructing resources:

~~~python
class ResourceOwner:
    @classmethod
    def open(cls, path):
        resource = acquire(path)
        try:
            instance = cls(resource)
        except BaseException:
            resource.close()
            raise
        return instance
~~~

The factory owns cleanup until successful transfer to the instance. The instance then needs explicit close/context-manager semantics.

### Worked example 9.3A — Constructor with validate–derive–commit ordering

~~~python
class UserProfile:
    def __init__(
        self,
        username: str,
        roles,
        metadata: dict[str, str] | None = None,
    ) -> None:
        normalized_username = username.strip().casefold()
        if not normalized_username:
            raise ValueError("username must be non-empty")

        normalized_roles = frozenset(role.strip().casefold() for role in roles)
        if not normalized_roles or "" in normalized_roles:
            raise ValueError("roles must be non-empty strings")

        metadata_snapshot = dict(metadata) if metadata is not None else {}
        if any(not isinstance(key, str) or not isinstance(value, str)
               for key, value in metadata_snapshot.items()):
            raise TypeError("metadata keys and values must be strings")

        self._username = normalized_username
        self._roles = normalized_roles
        self._metadata = metadata_snapshot
~~~

Argument iteration/copying can execute before any instance attributes are committed. Only after validation succeeds are three fields assigned. The roles become an immutable membership value; metadata is an independent outer dictionary whose strings are immutable.

The comprehension assumes each role supports <code>strip</code>; a non-string produces AttributeError rather than the advertised ValueError. A production boundary should validate type before normalization and perhaps report positions. The example’s analysis exposes rather than hides that contract gap.

### Worked example 9.3B — Safe interning through an explicit factory

~~~python
from weakref import WeakValueDictionary


class Symbol:
    def __init__(self, normalized: str) -> None:
        self._text = normalized

    @property
    def text(self) -> str:
        return self._text


_symbols: WeakValueDictionary[str, Symbol] = WeakValueDictionary()


def symbol(text: str) -> Symbol:
    normalized = text.strip().casefold()
    if not normalized:
        raise ValueError("empty symbol")

    existing = _symbols.get(normalized)
    if existing is not None:
        return existing

    created = Symbol(normalized)
    _symbols[normalized] = created
    return created
~~~

The explicit factory makes possible identity reuse visible through its name/documentation and avoids repeated <code>__init__</code>. The weak-value cache does not keep otherwise unused Symbols alive. It is still not safe for concurrent exactly-one identity without synchronization: two callers can both miss and create distinct live objects. If identity uniqueness is semantically required, use a lock and define weak disappearance; if reuse is only an optimization, equal value semantics may be sufficient.

> **Common misconception — “If __init__ raises, no object ever existed and no state can escape.”**  
> Allocation occurred first. A partially initialized object can escape if construction publishes it or invokes callbacks before the invariant is established.
