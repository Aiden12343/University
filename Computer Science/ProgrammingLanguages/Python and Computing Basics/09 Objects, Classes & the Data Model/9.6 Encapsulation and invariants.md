# 9.6 Encapsulation and invariants

**Encapsulation** is the organisation of state and behaviour behind an interface that owns its invariants. It is not synonymous with making attributes impossible to access. Python relies heavily on conventions, properties, descriptors, and module boundaries rather than compulsory private fields.

```python
class BankAccount:
    def __init__(self, opening_pence: int = 0) -> None:
        if opening_pence < 0:
            raise ValueError("opening balance must be non-negative")
        self._balance_pence = opening_pence

    @property
    def balance_pence(self) -> int:
        return self._balance_pence

    def deposit(self, amount_pence: int) -> None:
        if amount_pence <= 0:
            raise ValueError("deposit must be positive")
        self._balance_pence += amount_pence

    def withdraw(self, amount_pence: int) -> None:
        if amount_pence <= 0:
            raise ValueError("withdrawal must be positive")
        if amount_pence > self._balance_pence:
            raise ValueError("insufficient funds")
        self._balance_pence -= amount_pence
```

The invariant is non-negative balance. Exposing unrestricted assignment to `balance_pence` would let callers bypass it. A read-only property preserves familiar attribute syntax while routing access through a descriptor.

This model is still incomplete for real money: concurrency, durable transactions, currency, overflow in external systems, audit history, authorisation, and legal requirements matter. The class is a precise local example, not a banking design claim.

Double-leading-underscore names trigger **name mangling** within a class definition, transforming a name to include the class name. Mangling helps avoid accidental collisions in subclasses; it is not security or absolute privacy.

### 9.6.1 Encapsulation is authority control by interface

Encapsulation asks not “can determined code reach this attribute?” but “which operations are supported and responsible for preserving meaning?” Python users can often inspect <code>_balance_pence</code>; by convention they accept that depending on or modifying it may break across versions.

This openness supports debugging, scientific inspection, serialization tools, and metaprogramming. It places greater responsibility on API documentation and disciplined clients. Security cannot rely on underscore naming because hostile code in the same interpreter already has extensive authority.

### 9.6.2 Public, non-public, and mangled names

Common conventions are:

- <code>name</code>: public unless documentation says otherwise;
- <code>_name</code>: non-public implementation detail;
- <code>__name</code> inside a class: mangled to reduce accidental subclass collisions;
- <code>__name__</code>: reserved-style “dunder” names implementing documented data-model protocols; do not invent arbitrary ones casually.

Name mangling depends on lexical class spelling and strips leading underscores from the class name under defined rules. It can complicate inheritance and testing; use it when collision avoidance matters, not to simulate secure privacy.

### 9.6.3 Properties preserve attribute syntax while adding mediation

~~~python
class Circle:
    def __init__(self, radius: float) -> None:
        self.radius = radius

    @property
    def radius(self) -> float:
        return self._radius

    @radius.setter
    def radius(self, value: float) -> None:
        if value < 0:
            raise ValueError("radius must be non-negative")
        self._radius = value

    @property
    def area(self) -> float:
        return 3.141592653589793 * self._radius**2
~~~

The same public attribute vocabulary works during construction and later assignment; the setter owns validation. Area is derived and read-only. No redundant area state can become stale.

Properties enable a public plain attribute to evolve into computed access without changing caller syntax. They should not hide surprising network I/O, long computation, or mutation because attribute-looking code suggests inexpensive observation.

### 9.6.4 A setter must validate the proposed complete state

Suppose an interval exposes independently writable start and stop:

~~~python
interval.start = 10
interval.stop = 5
~~~

Whichever assignment occurs first may violate the cross-field invariant. Individual setters cannot support every atomic two-field transition without an intermediate invalid state. Better interfaces include:

~~~python
interval.replace(start=10, stop=15)
~~~

or immutable replacement returning a new Interval. The method validates both proposed values before commit. Properties are suitable for locally constrained fields; relational transitions often deserve named methods.

### 9.6.5 Tell the object the domain operation

External code manipulating fields:

~~~python
if amount <= account.balance:
    account.balance -= amount
~~~

splits the withdrawal invariant across caller and object and creates a time-of-check/time-of-use race. A method:

~~~python
account.withdraw(amount)
~~~

lets the owner validate and commit under one synchronization/transaction boundary. This is sometimes summarized as “tell, do not ask,” but observers remain necessary. The principle targets state transitions that belong to the object’s invariant, not every query.

### 9.6.6 Invariants include relationships to owned children

~~~python
class Playlist:
    def __init__(self, tracks: list[str]) -> None:
        self._tracks = list(tracks)
~~~

If invariant says every track ID is non-empty and unique, constructor and add/remove/reorder methods must preserve it. Returning <code>self._tracks</code> would let callers bypass checks. Storing mutable Track objects whose IDs can change can also invalidate uniqueness even if the list itself never escapes.

Encapsulation boundaries follow the reachable graph. Either own immutable child values, subscribe/cooperate with child transitions, or weaken the claimed invariant.

### 9.6.7 Representation exposure through iterators

~~~python
def tracks(self):
    return iter(self._tracks)
~~~

This does not allow structural mutation through the iterator itself, but it provides live references and iteration state. If the playlist mutates during traversal, elements can be skipped or repeated. Returned mutable track elements can still be changed.

A tuple snapshot offers stable outer membership at \(O(n)\) cost. A callback-based visitor keeps traversal control inside the object but invokes re-entrant external code. A custom read-only view can define version checking. Encapsulation is a consistency contract, not merely the absence of an <code>append</code> method.

### 9.6.8 Exception-safe mutators derive before commit

~~~python
class Inventory:
    def __init__(self) -> None:
        self._quantities: dict[str, int] = {}

    def remove(self, item: str, amount: int) -> None:
        if amount <= 0:
            raise ValueError("amount must be positive")

        current = self._quantities.get(item, 0)
        proposed = current - amount
        if proposed < 0:
            raise ValueError("insufficient quantity")

        if proposed == 0:
            self._quantities.pop(item, None)
        else:
            self._quantities[item] = proposed
~~~

All domain checks precede mutation. The sparse invariant—stored quantities strictly positive—is restored by deleting zero. Exact strings/integers make callbacks relatively controlled, though allocation/reference failures remain. A user-defined mapping would weaken the guarantee.

### 9.6.9 Multi-object invariants need a larger owner

If transferring stock between two Inventory objects must be atomic, neither object alone owns the complete invariant. Calling <code>source.remove</code> then <code>destination.add</code> can fail halfway. A warehouse aggregate, transaction service, or database transaction must own both.

Object orientation does not imply that every noun should control every relationship. Choose an ownership boundary large enough to commit the invariant and small enough to remain cohesive.

### 9.6.10 Immutable objects move validation to construction

~~~python
from dataclasses import dataclass


@dataclass(frozen=True)
class Percentage:
    basis_points: int

    def __post_init__(self) -> None:
        if not 0 <= self.basis_points <= 10_000:
            raise ValueError("percentage outside 0..100%")
~~~

Once valid and not circumvented, the field does not change. Operations return new Percentage values rather than mutate this one. This simplifies sharing and hashing.

Frozen dataclasses prevent ordinary attribute assignment through generated machinery but can reach mutable components and can be circumvented using low-level mechanisms. Deep value immutability is a representation discipline, not one flag.

### 9.6.11 Cached derived state threatens invariants

~~~python
class Polygon:
    def __init__(self, points):
        self._points = tuple(points)
        self._perimeter_cache: float | None = None
~~~

If points are immutable and never replaced, cached perimeter remains valid. If a mutator changes points, it must invalidate/update the cache. A cached value introduces an invariant linking source state and derived state:

\[
cache\ne None\Rightarrow cache=perimeter(points).
\]

Computing on demand avoids invalidation but repeats work. Immutable replacement lets each object own one stable cache. Performance optimisations enlarge the invariant set.

### 9.6.12 Lazy initialization needs concurrency and failure states

~~~python
@property
def index(self):
    if self._index is None:
        self._index = build_index(self._records)
    return self._index
~~~

The property conflates “not initialized” with a possibly valid <code>None</code> result and can build twice under concurrency. If construction recursively accesses <code>index</code>, it can re-enter. If it fails after effects, later calls retry.

A robust state machine may distinguish absent, building, ready, and failed; use a unique sentinel, lock/condition, immutable records, and explicit reset. Lazy evaluation shifts work and errors to first access, which must be part of the contract.

### 9.6.13 Capabilities can be narrower than the object

Instead of returning a mutable aggregate, provide a callable or protocol exposing one authorized operation:

~~~python
def depositor(account: BankAccount):
    return account.deposit
~~~

The bound method retains the account and permits deposit under its validation but not direct withdrawal through that reference alone. Python reflection can still expose receiver metadata for trusted in-process code, so this is organizational capability narrowing rather than a hostile sandbox. Across process/service boundaries, enforce authority cryptographically and architecturally.

### 9.6.14 Invariants and subclassing conflict when internals are open

A subclass can override a method that a base class relies upon, mutate protected attributes, or skip <code>super()</code>. If a base constructor calls an overridable method before its own state is complete, the subclass receives a partially initialized object.

~~~python
class Base:
    def __init__(self) -> None:
        self.configure()       # risky virtual call
        self.ready = True

    def configure(self) -> None:
        pass
~~~

Prefer private/non-overridable internal steps during initialization, explicit hooks called after invariants are established, or composition. A class intended for inheritance must document protected extension points and call order.

### 9.6.15 Context managers encode temporary invariants

Some invariants hold only within a dynamic extent. A lock-owning object may expose:

~~~python
with repository.transaction() as transaction:
    transaction.update(...)
~~~

Entry establishes an active transaction; exit commits or rolls back according to exception outcome. Methods can reject use after exit. Context management makes resource/state lifetime syntactically visible and centralizes cleanup, developed fully in Chapter 11.

### Worked example 9.3C — An invariant-safe roster

~~~python
class Roster:
    def __init__(self, names=()) -> None:
        normalized = [self._normalize(name) for name in names]
        if len(normalized) != len(set(normalized)):
            raise ValueError("duplicate normalized name")
        self._names = normalized

    @staticmethod
    def _normalize(name: str) -> str:
        if not isinstance(name, str):
            raise TypeError("name must be text")
        normalized = " ".join(name.split()).casefold()
        if not normalized:
            raise ValueError("name must be non-empty")
        return normalized

    def add(self, name: str) -> None:
        normalized = self._normalize(name)
        if normalized in self._names:
            raise ValueError("duplicate normalized name")
        self._names.append(normalized)

    def remove(self, name: str) -> None:
        normalized = self._normalize(name)
        self._names.remove(normalized)

    def snapshot(self) -> tuple[str, ...]:
        return tuple(self._names)
~~~

The representation preserves order and uniqueness under the chosen normalization. Membership/add is \(O(n)\); a parallel set index could make it expected constant but add a cross-container invariant. Constructor fully derives/validates before assigning state. Mutation validates before commit. Snapshot prevents structural alias escape.

The normalization policy collapses whitespace and case but does not implement all Unicode or human identity semantics. The class should name a versioned domain-specific policy in a real system.

### Worked example 9.3D — Atomic relational replacement

~~~python
class Window:
    def __init__(self, start: int, stop: int) -> None:
        self._start = 0
        self._stop = 0
        self.replace(start=start, stop=stop)

    @property
    def start(self) -> int:
        return self._start

    @property
    def stop(self) -> int:
        return self._stop

    def replace(self, *, start: int, stop: int) -> None:
        if start > stop:
            raise ValueError("start exceeds stop")
        self._start, self._stop = start, stop
~~~

The method validates the complete proposed pair before the multi-target assignment. Within single-threaded ordinary execution using exact integers, callers do not observe an invalid intermediate relation through public code. Concurrent readers still need coordination if they can interleave between underlying assignments in a relevant implementation. An immutable Window returning a replacement provides stronger snapshot semantics.

> **Common misconception — “A property setter can always preserve multi-field invariants.”**  
> Independent assignments expose intermediate states. Relational updates often require one method accepting the complete proposed state or immutable replacement.
