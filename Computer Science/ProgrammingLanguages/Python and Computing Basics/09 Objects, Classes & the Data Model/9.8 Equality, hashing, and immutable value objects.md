# 9.8 Equality, hashing, and immutable value objects

Without an override, ordinary user-defined instances compare by identity under `object` behaviour. A value-oriented type can define `__eq__` and, when immutable under equality-relevant state, `__hash__`.

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class Coordinate:
    x: int
    y: int
```

The `dataclass` decorator can generate initialisation, representation, and equality from annotated fields. `frozen=True` blocks ordinary field assignment and allows suitable hash generation when rules permit. “Frozen” is not deep immutability: a frozen dataclass can still refer to mutable objects, and low-level circumvention exists.

Equality should be reflexive, symmetric, and transitive for ordinary value use, subject to intentional exceptions such as NaN. Hash compatibility requires:

```text
if a == b, then hash(a) == hash(b)
```

The converse is not required. If equality depends on mutable state, instances should generally be unhashable because changing that state after dictionary insertion corrupts lookup assumptions.

### Worked example 9.3 — Why hash and equality form one contract

Suppose coordinates compare by `(x, y)` but hash only by object identity. Two distinct `Coordinate(1, 2)` instances would compare equal yet occupy unrelated hash search regions. A set could retain both or fail to find one using the other, violating set semantics. Equal objects must enter compatible candidate paths, which is why their hashes must match.

### 9.8.1 Identity equality and value equality answer different questions

<code>is</code> asks whether two expressions designate the same object. <code>==</code> invokes an equality protocol intended to ask whether values are equivalent under type-defined semantics.

Entity code may use identity internally to detect the same in-memory aggregate while domain equality uses a stable entity identifier. Value objects ordinarily compare components. Neither relation should be chosen merely to make tests convenient.

### 9.8.2 Equality should define an equivalence relation for ordinary keys

An equivalence relation satisfies:

1. reflexivity: \(a=a\);
2. symmetry: \(a=b\Rightarrow b=a\);
3. transitivity: \(a=b\land b=c\Rightarrow a=c\).

Hash maps and sets behave best when equality also remains stable while objects are stored. IEEE NaN is an intentional non-reflexive numeric exception; domain objects should not imitate such anomalies accidentally.

~~~python
class Approximate:
    def __init__(self, value: float) -> None:
        self.value = value

    def __eq__(self, other: object) -> bool:
        if not isinstance(other, Approximate):
            return NotImplemented
        return abs(self.value - other.value) < 1.0
~~~

This “within one” relation is not transitive: 0.0 equals 0.75, 0.75 equals 1.5, but 0.0 does not equal 1.5. It is unsuitable as general object equality or a hash key. Approximate comparison should be a named predicate with explicit tolerance.

### 9.8.3 Return NotImplemented for unsupported operands

<code>__eq__</code> should return the singleton <code>NotImplemented</code> when it does not know how to compare the other type. This lets Python try the reflected/other operand’s implementation and eventually apply fallback rules.

~~~python
class Coordinate:
    def __init__(self, x: int, y: int) -> None:
        self.x = x
        self.y = y

    def __eq__(self, other: object) -> bool:
        if not isinstance(other, Coordinate):
            return NotImplemented
        return (self.x, self.y) == (other.x, other.y)
~~~

Returning <code>False</code> immediately claims authoritative inequality and can prevent a cooperating foreign type from defining cross-type equality. Raising <code>TypeError</code> for ordinary unsupported equality is usually contrary to Python comparison conventions.

<code>NotImplemented</code> is truthy in historical/runtime contexts and must not be used as a Boolean result by callers; it is a protocol signal returned by special methods.

### 9.8.4 Type policy determines symmetry

Using <code>isinstance(other, Coordinate)</code> permits equality with subclasses. A subclass may add a semantic dimension such as coordinate system, making base equality ignore state the subclass considers relevant. Then symmetry or transitivity can break.

An exact-type policy is safer for closed value representations:

~~~python
def __eq__(self, other: object) -> bool:
    if type(other) is not type(self):
        return NotImplemented
    return (self.x, self.y) == (other.x, other.y)
~~~

A structural cross-type policy is appropriate when two types deliberately share one value algebra, as integers and compatible numeric types do. The hierarchy alone cannot choose; document the equality domain.

### 9.8.5 Defining equality affects hashability

For a user class that defines <code>__eq__</code> but not an appropriate <code>__hash__</code>, Python normally sets <code>__hash__ = None</code>, making instances unhashable. This prevents identity hashing from conflicting with value equality.

~~~python
class Name:
    def __init__(self, text: str) -> None:
        self.text = text

    def __eq__(self, other: object) -> bool:
        if not isinstance(other, Name):
            return NotImplemented
        return self.text == other.text


# hash(Name("Ada"))            # TypeError
~~~

Do not restore <code>object.__hash__</code> for value-equal instances; it hashes by identity-like semantics and can violate equal-implies-equal-hash.

### 9.8.6 Hash must derive from equality-relevant immutable state

~~~python
class FrozenCoordinate:
    __slots__ = ("_x", "_y")

    def __init__(self, x: int, y: int) -> None:
        object.__setattr__(self, "_x", x)
        object.__setattr__(self, "_y", y)

    def __eq__(self, other: object) -> bool:
        if type(other) is not type(self):
            return NotImplemented
        return (self._x, self._y) == (other._x, other._y)

    def __hash__(self) -> int:
        return hash((type(self), self._x, self._y))
~~~

The tuple delegates combination to Python’s tuple hash and includes type to match exact-type equality. But this class is not actually frozen yet: slots prevent arbitrary dictionary fields but ordinary code can still assign <code>_x</code>. A complete immutable implementation must prevent post-construction assignment or use a frozen dataclass/other discipline.

Hash equality is required, but a good hash also distributes unequal common values to reduce collisions. Never invent simple addition/XOR combinations without analysing symmetry and distribution; delegate to tuples of components.

### 9.8.7 Hash values are process- and implementation-qualified

Python may randomize hashes for strings and related values between process runs as a denial-of-service defense. Hash widths and algorithms vary by build/version. Never persist <code>hash(obj)</code> as a stable identifier, checksum, partition key shared across runtimes, or cryptographic digest.

A hash collision is expected and not corruption. Cryptographic hashes have different adversarial/collision goals and APIs; even they are not object equality proofs without a protocol.

### 9.8.8 Mutation after insertion breaks table location assumptions

~~~python
class MutableKey:
    def __init__(self, value: int) -> None:
        self.value = value

    def __hash__(self) -> int:
        return hash(self.value)

    def __eq__(self, other: object) -> bool:
        return isinstance(other, MutableKey) and self.value == other.value
~~~

After inserting a MutableKey into a dictionary, changing <code>value</code> can make lookup search a new hash path while the entry remains in the old position. Membership may fail, equal duplicates may appear, and deletion can become difficult. Restoring the old value may appear to repair lookup but does not make the design valid.

Make key state immutable or base equality/hash on a permanently stable identifier. Mutable non-key fields are acceptable only if they do not participate in equality/hash and the entity semantics support that choice.

### 9.8.9 Entity equality by ID has lifecycle consequences

~~~python
class Account:
    def __init__(self, identifier: str, balance: int) -> None:
        self._identifier = identifier
        self.balance = balance

    def __eq__(self, other: object) -> bool:
        if type(other) is not type(self):
            return NotImplemented
        return self._identifier == other._identifier

    def __hash__(self) -> int:
        return hash((type(self), self._identifier))
~~~

Balance changes do not affect equality/hash. Two in-memory snapshots of the same account ID compare equal despite different balances. This can be correct entity semantics, but placing both in a set collapses versions and can hide stale data. Domain operations may need explicit version equality or snapshot identity instead.

The identifier must be immutable and globally unique within the equality domain. Reassigning it after insertion is forbidden by contract and should be prevented through representation.

### 9.8.10 Dataclass equality is generated by field order and type policy

By default, <code>@dataclass(eq=True)</code> generates equality comparing instances as if their declared fields formed an ordered tuple, usually requiring identical class types. Fields can be excluded with <code>compare=False</code>.

~~~python
from dataclasses import dataclass, field


@dataclass(frozen=True)
class DocumentKey:
    path: str
    version: int
    cached_size: int = field(compare=False, hash=False, repr=False)
~~~

The cached size does not affect equality/hash/repr. This is safe only if it is truly derived/non-semantic. Two equal DocumentKeys can then carry different cached sizes, which callers must tolerate. Generated code encodes field configuration; review that configuration as domain logic.

### 9.8.11 frozen dataclass hash matrix

Dataclass hash generation depends on <code>eq</code>, <code>frozen</code>, and <code>unsafe_hash</code>. In the common value case <code>eq=True, frozen=True</code>, a field-based hash is generated when appropriate. With mutable equality-bearing fields, dataclasses ordinarily leave instances unhashable. <code>unsafe_hash=True</code> forces generation but does not make mutation safe; its name signals that the programmer assumes responsibility.

An unhashable component still makes the generated hash fail when called, even if outer dataclass is frozen. Deep hashability remains component-dependent.

### 9.8.12 Inequality usually derives from equality

Python’s comparison machinery can derive <code>!=</code> from <code>==</code> under standard object behaviour when <code>__ne__</code> is absent. Defining inconsistent <code>__ne__</code> breaks Boolean complement expectations.

Ordering comparisons (<code>&lt;</code>, <code>&lt;=</code>, <code>&gt;</code>, <code>&gt;=</code>) are separate protocols. Equality does not imply an order. A coordinate has obvious component equality but several plausible orders—lexicographic, distance, row-major—so no natural ordering may be best.

### 9.8.13 Equality can execute arbitrary code and raise

List, tuple, dictionary-value, set-candidate, and custom-object equality may invoke user methods. <code>a == b</code> can be expensive, effectful, re-entrant, non-Boolean-returning, or exceptional. Python comparisons can return specialized objects (for example array libraries) whose truth conversion is ambiguous.

Implement equality as pure, total over supported comparison operands, and cheap enough for container use where possible. If an operation can fail, a named comparison method may be more honest than general <code>==</code>.

### 9.8.14 Equality results undergo context-dependent truth conversion

The expression <code>a == b</code> returns whatever rich comparison protocol produces. In an <code>if</code>, Python then requests its truth value. NumPy arrays, introduced in Branch A, perform elementwise equality and reject ambiguous whole-array truth. This is a reminder that operators are dispatch protocols, not guaranteed built-in Booleans for every type.

Object <code>__eq__</code> implementations conventionally return <code>bool</code> or <code>NotImplemented</code> for scalar value types, preserving container assumptions.

### 9.8.15 Identity shortcuts can affect container equality paths

Built-in containers may treat identical element references as matching without calling a non-reflexive equality method, helping them satisfy internal reflexivity-like behavior. This explains NaN membership cases from Chapter 7. User reasoning should not rely on an equality callback running for identical objects.

If equality has effects, such shortcuts become observable and further demonstrate why effectful equality is a defective general design.

### 9.8.16 Weak references and hashing

A weak reference can be hashable when its referent is hashable, with behavior affected by whether hashing occurred before referent collection. Weak-reference equality can delegate to live referents and change fallback behavior after collection. These subtleties make weak references implementation/lifecycle tools rather than ordinary domain keys.

WeakKeyDictionary and WeakValueDictionary serve caches/registries whose entries should disappear with object lifetime, but identity/equality interactions and callbacks require current documentation.

### Worked example 9.4A — A rigorously immutable coordinate

~~~python
from dataclasses import dataclass


@dataclass(frozen=True, slots=True)
class Coordinate:
    x: int
    y: int

    def __post_init__(self) -> None:
        for name, value in (("x", self.x), ("y", self.y)):
            if isinstance(value, bool) or not isinstance(value, int):
                raise TypeError(f"{name} must be an integer")
~~~

Generated equality uses both fields and exact class-compatible dataclass semantics; generated hashing is suitable because the instance is frozen and integer fields are hashable. Slots omit an ordinary per-instance dictionary and restrict arbitrary attributes. Low-level <code>object.__setattr__</code> can still circumvent generated freezing, so “rigorously” here means under the supported public interface, not hostile reflection.

### Worked example 9.4B — Reject approximate equality as object identity

~~~python
from math import isclose


class Measurement:
    def __init__(self, value: float) -> None:
        self.value = value

    def close_to(
        self,
        other: "Measurement",
        *,
        relative_tolerance: float = 1e-9,
        absolute_tolerance: float = 0.0,
    ) -> bool:
        return isclose(
            self.value,
            other.value,
            rel_tol=relative_tolerance,
            abs_tol=absolute_tolerance,
        )
~~~

The named method exposes tolerances and avoids claiming an equivalence relation for hashing/set membership. Ordinary Measurement equality remains identity unless exact value semantics are separately defined. Closeness can still be non-transitive; callers must not use it to form equivalence classes without a clustering policy.

### Worked example 9.4C — Cross-type equality decision

Suppose Celsius and Fahrenheit objects represent temperature. Defining them equal after unit conversion seems natural, but floating conversion/rounding can threaten transitivity and hash compatibility. A safer model converts both at construction to one exact canonical unit, such as rational microkelvin under a defined rounding rule, then delegates equality/hash to that canonical value. Alternatively, keep types unequal and expose <code>equivalent_temperature</code> explicitly.

The design exercise demonstrates that cross-type equality is an algebra/API decision. Returning NotImplemented is preferable until one coherent shared value domain and hash function are proven.

> **Common misconception — “If objects compare equal, giving each its identity hash is still acceptable because collisions are allowed.”**  
> Collisions permit unequal objects to share a hash. The reverse requirement is strict: equal objects must have equal hashes so lookup searches compatible regions.
