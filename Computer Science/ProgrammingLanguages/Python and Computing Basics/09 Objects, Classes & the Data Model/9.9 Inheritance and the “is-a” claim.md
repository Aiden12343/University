# 9.9 Inheritance and the “is-a” claim

**Inheritance** allows a class to derive behaviour and attributes from base classes. A subclass instance is also an instance of its base classes under Python’s type relation. This is a strong substitutability claim, not merely a code-reuse mechanism.

```python
class Shape:
    def area(self) -> float:
        raise NotImplementedError


class Rectangle(Shape):
    def __init__(self, width: float, height: float) -> None:
        self.width = width
        self.height = height

    def area(self) -> float:
        return self.width * self.height
```

Code accepting a `Shape` and calling `area` can operate on a `Rectangle`. But the base class’s method uses a runtime placeholder rather than a formally declared abstract method. The `abc` module provides explicit abstract base classes when nominal registration and instantiation prevention are required.

The **Liskov substitution principle** states, informally, that objects of a subtype should be usable where objects of the supertype are expected without violating the supertype’s behavioural contract. A subclass that strengthens preconditions, weakens postconditions, or breaks invariants is not a sound behavioural subtype even if Python’s inheritance syntax permits it.

### Rectangle–square warning

If a mutable `Rectangle` interface allows width and height to be set independently, a `Square` subclass that forces them always equal cannot honour every base transition without surprising callers. The mathematical relation “every square is a rectangle” does not automatically make mutable software interfaces substitutable. Interface operations determine the subtype claim.

> **Common misconception — “Use inheritance whenever two classes share code.”**  
> Inheritance asserts a type and behaviour relationship. Shared implementation alone can be factored into composition, helper functions, or delegation without making the stronger claim.

### 9.9.1 Inheritance creates nominal subtype relations

If <code>Child</code> inherits from <code>Base</code>, ordinary runtime relations include:

~~~python
issubclass(Child, Base)
isinstance(Child(), Base)
~~~

This permits code dispatching or validating by Base to accept Child. It does not mechanically prove that Child honours Base’s semantic contract. Python enforces method resolution, not the Liskov substitution principle.

### 9.9.2 Substitutability is observer-relative

A subtype \(S\) is substitutable for a supertype \(T\) when every program relying only on T’s contract continues to satisfy its correctness properties when given an S. The phrase “is-a” is useful only after specifying what observers may do.

A Square is mathematically a set of points satisfying rectangle properties. A mutable Rectangle API exposing independent width and height changes supplies operations not closed over the stricter square invariant. Under that API, mutable Square is not behaviourally substitutable even though the mathematical value set is included.

An immutable Rectangle value with read-only width/height and area may admit Square as a subtype more coherently, though equality, construction, and return types still require analysis. Mutability changes subtype algebra.

### 9.9.3 Preconditions cannot be strengthened

Suppose Base promises <code>process(value)</code> accepts every non-negative integer. A subclass accepting only even non-negative integers rejects calls valid under Base:

~~~python
class Processor:
    def process(self, value: int) -> int:
        if value < 0:
            raise ValueError("negative")
        return value


class EvenProcessor(Processor):
    def process(self, value: int) -> int:
        if value % 2:
            raise ValueError("odd")
        return value
~~~

A client holding Processor may call <code>process(3)</code> validly; substitution fails. A subtype may accept a broader domain, not a narrower one, assuming result guarantees remain compatible. In type-theoretic terms, parameter acceptance is contravariant in a simple function-subtyping model.

### 9.9.4 Postconditions cannot be weakened

If Base promises a positive integer result, a subclass returning <code>None</code> or a negative integer violates callers’ established reasoning. A subtype may strengthen the result guarantee—for example, promise an even positive integer—provided that value is still valid under the Base result type/semantics.

Static return-type covariance captures part of this relation. It cannot prove units, sortedness, freshness, effects, or exception safety.

### 9.9.5 Invariants and history constraints must survive

A Base invariant applies to every subclass instance viewed as Base. A subclass cannot expose a new operation that corrupts inherited expectations:

~~~python
class MonotonicCounter:
    def __init__(self) -> None:
        self._value = 0

    @property
    def value(self) -> int:
        return self._value

    def increment(self) -> None:
        self._value += 1


class ResettableCounter(MonotonicCounter):
    def reset(self) -> None:
        self._value = 0
~~~

If Base’s contract includes history monotonicity—value never decreases—ResettableCounter violates it even though inherited methods remain unchanged. Substitutability concerns the whole public behaviour and temporal history.

### 9.9.6 Exceptions are part of postconditions

A subclass that raises new ordinary exceptions for previously valid calls weakens the supertype’s normal-result guarantee. It may refine a documented base exception into a subtype callers already agree to handle, but introducing arbitrary failures can break clients.

Resource and timing guarantees matter too. A subclass that turns local constant-time lookup into an unbounded network call may satisfy value typing while violating latency, availability, and effect contracts. Behavioural subtyping exceeds signatures.

### 9.9.7 Abstract base classes declare nominal obligations

~~~python
from abc import ABC, abstractmethod


class Shape(ABC):
    @abstractmethod
    def area(self) -> float:
        """Return non-negative finite area."""


class Rectangle(Shape):
    def __init__(self, width: float, height: float) -> None:
        if width < 0 or height < 0:
            raise ValueError("negative dimension")
        self.width = width
        self.height = height

    def area(self) -> float:
        return self.width * self.height
~~~

ABC machinery prevents ordinary instantiation of a class whose abstract methods remain unimplemented. It checks that an attribute is considered implemented, not that the method meets the docstring’s non-negative finite guarantee. NaN inputs still expose a validation gap in this example.

Abstract methods may contain a cooperative default implementation and be called through <code>super()</code>. “Abstract” means subclasses must override/resolve it for concrete instantiation, not necessarily that its body is empty.

### 9.9.8 Virtual subclass registration is nominal acceptance without inheritance

An ABC can register another class as a virtual subclass, making <code>issubclass</code>/<code>isinstance</code> recognize it without changing its MRO or injecting methods:

~~~python
class ExternalShape:
    def area(self) -> float:
        return 1.0


Shape.register(ExternalShape)
print(isinstance(ExternalShape(), Shape))  # True
~~~

Registration asserts the contract; it does not verify or supply it. ExternalShape does not gain Shape implementations or <code>super</code> relationships. Use registration only when an authority can vouch for behavioural compatibility.

Some standard ABCs implement structural subclass hooks for methods such as iteration. Runtime checks remain deliberately shallow and cannot certify semantics.

### 9.9.9 Abstract base class versus Protocol

An ABC supplies nominal ancestry/registration, shared implementations, class-level hooks, and runtime instantiation restrictions. A <code>typing.Protocol</code> supplies a primarily static structural interface: any type with compatible members can satisfy it without inheriting.

Use an ABC when a family needs shared runtime identity and controlled construction. Use a protocol when consumers care only about behaviour and implementations should remain decoupled. A class can do both, but combining mechanisms should serve a stated need.

Runtime-checkable protocols can support <code>isinstance</code> after <code>@runtime_checkable</code>, but checks generally inspect member presence rather than full signatures or behaviour and can invoke/inspect attributes under evolving version rules. They are not validators.

### 9.9.10 Override signatures must preserve valid calls

~~~python
class Repository:
    def get(self, identifier: str, *, fresh: bool = False) -> object:
        ...


class CachedRepository(Repository):
    def get(self, identifier: str) -> object:
        ...
~~~

The subclass rejects the valid Base call <code>repo.get("x", fresh=True)</code>. A static checker can flag this override; runtime inheritance permits it until that call occurs.

Renaming positional-or-keyword parameters also breaks keyword callers. Positional-only base parameters can preserve naming freedom. Variadic collectors can accept calls but still ignore required semantics, so call shape is necessary but not sufficient.

### 9.9.11 Return self types and fluent interfaces

A base method returning a new instance can use <code>Self</code> in modern typing when subclasses should receive their dynamic type:

~~~python
from typing import Self


class Vector:
    def scaled(self, factor: float) -> Self:
        return type(self)(component * factor for component in self)
~~~

The implementation assumes every subclass constructor accepts that iterable. If not, annotation and runtime diverge. A protected factory hook can let subclasses construct compatible results. Fluent <code>return self</code> methods also need mutation/identity contracts.

### 9.9.12 The fragile base class problem

A subclass can depend on undocumented details of base method calls. If a base implementation changes from directly updating state to calling an overridable helper, the subclass may receive a new callback or double effect without any public signature change.

~~~python
class Base:
    def save(self) -> None:
        self._write()

    def _write(self) -> None:
        ...
~~~

Protected extension points become contracts even with a leading underscore when subclasses are expected to override them. Document call order, pre/post-state, whether <code>super</code> is required, and exception policy. Otherwise prefer composition that keeps private implementation replaceable.

### 9.9.13 Template Method

The **Template Method** pattern defines an algorithm skeleton in a base and delegates selected steps to overrides:

~~~python
from abc import ABC, abstractmethod


class Importer(ABC):
    def import_payload(self, payload: bytes) -> int:
        records = self.parse(payload)
        valid = self.validate(records)
        return self.commit(valid)

    @abstractmethod
    def parse(self, payload: bytes): ...

    def validate(self, records):
        return records

    @abstractmethod
    def commit(self, records) -> int: ...
~~~

The base owns sequencing; subclasses own hooks. Every hook needs explicit types, effects, exception, and consumption contracts. A composition alternative injects parser, validator, and repository strategies, avoiding subclass coupling and allowing independent runtime assembly.

### 9.9.14 Mixins provide narrow orthogonal behaviour

A **mixin** is a class intended to contribute a focused behaviour to another class rather than stand alone as the principal domain type.

~~~python
class JsonReprMixin:
    def to_mapping(self) -> dict[str, object]:
        raise NotImplementedError

    def to_json(self) -> str:
        import json
        return json.dumps(self.to_mapping())
~~~

This mixin assumes <code>to_mapping</code> and supplies serialization. A more explicit Protocol and free function may avoid hidden requirements. Good mixins are narrow, stateless or carefully cooperative, and clear about MRO/super use. A mixin named <code>ManagerHelperMixin</code> with dozens of fields is an obscured base class.

### 9.9.15 Inheriting concrete collection implementations is hazardous

Subclassing list or dict to enforce invariants can fail because inherited methods may bypass one overridden hook, return base types, expose mutation routes, or have internal implementation paths not expressed through public overrides.

~~~python
class PositiveList(list[int]):
    def append(self, value: int) -> None:
        if value <= 0:
            raise ValueError("positive values only")
        super().append(value)
~~~

This leaves <code>extend</code>, slice assignment, <code>insert</code>, <code>+=</code>, constructor input, and perhaps unpickling pathways to audit. Composition around an internal list can expose only validated operations. <code>collections.UserList</code> provides a Python-level wrapper base for some customization but still requires full protocol review.

### 9.9.16 Inheritance couples representation and lifecycle

A subclass shares the same instance identity and often the same attribute namespace as its base. Base and child invariants can collide. Composition gives components separate identities and state, allowing replacement and independent testing.

Inheritance is strongest when:

- the subtype relation is semantically durable;
- the base contract is intentionally designed for extension;
- overrides preserve substitutability;
- shared implementation belongs to that relation;
- MRO and initialization remain tractable.

### 9.9.17 final communicates non-extension intent statically

<code>typing.final</code> can mark a class as not intended for subclassing or a method as not intended for override:

~~~python
from typing import final


@final
class SecurityToken:
    ...
~~~

This is a static-analysis contract; ordinary runtime Python does not automatically prevent subclass creation merely because of the decorator. A runtime <code>__init_subclass__</code> guard can reject subclasses, but determined code can still circumvent many in-process controls. Use finality to protect design assumptions and evolution, not as a hostile security barrier.

### Worked example 9.4D — Rectangle and square as immutable values

~~~python
from dataclasses import dataclass


@dataclass(frozen=True)
class Rectangle:
    width: float
    height: float

    def __post_init__(self) -> None:
        if self.width < 0 or self.height < 0:
            raise ValueError("dimensions must be non-negative")

    @property
    def area(self) -> float:
        return self.width * self.height


@dataclass(frozen=True)
class Square(Rectangle):
    def __init__(self, side: float) -> None:
        super().__init__(side, side)
~~~

The removal of independent mutators avoids the classic state-transition conflict. Yet constructor signatures differ, dataclass-generated equality may require identical classes, and inherited methods returning Rectangle might not preserve Square. The subtype is suitable only for clients restricted to the Rectangle observer contract, not for code assuming interchangeable construction or exact-type equality.

Finite validation remains incomplete because NaN can evade negative checks. The example demonstrates improvement, not automatic proof.

### Worked example 9.4E — Substitution test suite

~~~python
def repository_contract(factory) -> None:
    repository = factory()

    repository.put("a", b"one")
    assert repository.get("a") == b"one"
    assert repository.get("missing") is None

    repository.put("a", b"two")
    assert repository.get("a") == b"two"

    assert list(repository.keys()) == ["a"]
~~~

Running this contract suite against memory, file, and database-backed implementations samples substitutability: result values, missing semantics, overwrite, and ordering. It does not prove concurrency, crash durability, performance, encoding, or every input. A base/protocol contract should have both reusable tests and prose/formal obligations.

### Worked example 9.4F — Replace code-reuse inheritance with a component

Inheritance solely for retry:

~~~python
class RetryingClient(HttpClient):
    ...
~~~

Composition:

~~~python
class RetryingTransport:
    def __init__(self, transport, policy) -> None:
        self._transport = transport
        self._policy = policy

    def send(self, request):
        return self._policy.run(lambda: self._transport.send(request))
~~~

The wrapper is substitutable only for the narrower Transport protocol and delegates actual I/O. Retry policy can be tested separately and different transports wrapped without joining their implementation hierarchies. It still requires idempotency and request replay semantics; composition improves coupling, not protocol correctness automatically.

> **Common misconception — “If isinstance(sub, Base) is true, Liskov substitution is proven.”**  
> The runtime relation records inheritance/registration. Behavioural substitution additionally requires compatible domains, results, effects, exceptions, invariants, history, and resources.
