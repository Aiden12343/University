# 10.1 Modularity is control over knowledge and change

A **module** is a Python object serving as a namespace for definitions loaded under the import system. A **package** is a module capable of containing submodules. Modularity solves more than file length: it assigns ownership, limits which facts one component must know, publishes stable interfaces, and controls the spread of change.

A module boundary is useful when it separates responsibilities with distinct invariants. Splitting every class into a file or collecting unrelated helpers in `utils.py` creates filenames without a coherent model. A module should answer a recognisable question and expose a deliberate public surface.

Example project:

```text
ledger/
    pyproject.toml
    README.md
    src/
        ledger/
            __init__.py
            __main__.py
            model.py
            parsing.py
            reporting.py
    tests/
        test_model.py
        test_parsing.py
```

The outer `ledger/` is the project root. `src/ledger/` is the import package. Reusing the name is conventional but the two roles differ. `pyproject.toml` describes a distribution project; `__init__.py` initialises an ordinary package; `model.py` and others define submodules.

### 10.1.1 Four boundaries that are often conflated

A Python project commonly contains at least four distinct organisational units:

1. a **source file**, which is a persistent filesystem artefact containing text;
2. a **module**, which is a runtime namespace object loaded under a name;
3. an **import package**, which is a module that can contain submodules;
4. a **distribution**, which is an installable versioned collection described by packaging metadata.

One source file can be executed under different module names and thereby produce distinct module objects. A module can be supplied by a built-in or custom loader without an ordinary source file. One distribution can install several top-level import packages, and several distributions can contribute portions of one namespace package. The repository name, distribution name, and import name are therefore mappings, not identities.

For the example, a repository and distribution might be named <code>careful-ledger</code> while callers write <code>import ledger</code>. Package installers reason primarily about the distribution name; the import machinery reasons primarily about <code>ledger</code> and its search path.

### 10.1.2 Cohesion determines what belongs together

**Cohesion** is the degree to which the responsibilities inside a component belong to one comprehensible purpose. A cohesive <code>parsing</code> module converts external representations into validated domain values. An incoherent <code>helpers</code> module may contain timestamp formatting, database retries, checksum calculation, and user authorisation merely because all four are “utilities.”

Cohesion is evaluated semantically, not by line count. A 1,500-line parser implementing one grammar may be more cohesive than a 70-line module containing seven unrelated conveniences. Size can signal a need to inspect responsibilities, but arbitrary size limits can fragment one abstraction into files whose changes must always travel together.

One practical test asks: can the module’s purpose be stated without “and” joining independent reasons to change? “Parses ledger transaction syntax” is cohesive. “Parses transactions and sends notification email” joins distinct boundary and policy concerns.

### 10.1.3 Coupling measures dependency knowledge

**Coupling** is the dependency between components: one component relies on another’s name, interface, data representation, timing, exceptions, side effects, or lifecycle. Coupling is not inherently bad. A program works because components deliberately depend on contracts. The design objective is to make essential coupling explicit and prevent dependence on accidental details.

~~~python
# reporting.py
from collections.abc import Iterable

from .model import Transaction


def total(transactions: Iterable[Transaction]) -> int:
    return sum(transaction.amount_pence for transaction in transactions)
~~~

This module intentionally knows the public <code>Transaction.amount_pence</code> interface. It need not know which file format produced transactions, which database stores them, or how the total is displayed. Those absences are reductions in coupling.

Coupling has several dimensions:

- **name coupling:** imported symbol and module paths;
- **representation coupling:** assumptions about private fields or concrete containers;
- **control coupling:** flags telling another component which internal branch to take;
- **temporal coupling:** operations required in a particular unstated order;
- **failure coupling:** dependence on exception types and partial effects;
- **deployment coupling:** components that must be released or configured together;
- **authority coupling:** access to resources or credentials broader than the task requires.

Counting imports detects only part of this structure.

### 10.1.4 Information hiding stabilises change

**Information hiding** means that a component publishes the smallest stable knowledge callers need while retaining freedom to change implementation decisions. A package can re-export <code>Transaction</code> from a public façade, allowing the source file that defines it to move without changing client imports.

Information hiding does not mean hiding all implementation source from inspection. Python code and objects are highly introspectable. It means declaring which facts are contractual and which are not supported dependencies. Leading underscores, documentation, re-export modules, protocols, and tests all communicate that boundary; none alone enforces it against determined access.

### 10.1.5 The dependency graph should reflect policy

Treat modules as nodes and imports as directed edges. If <code>reporting</code> imports <code>model</code>, draw <code>reporting → model</code>. A useful layered design directs volatile boundary concerns toward stable domain policy:

~~~text
command interface  ->  application coordination  ->  domain model
file adapter        ->  application coordination  ->  domain model
database adapter    ->  domain protocols
~~~

Arrows represent compile/load-time knowledge, not the direction data flows at runtime. A database adapter can send records “up” to an application while its source code depends “inward” on a domain-owned protocol.

A **dependency inversion** places an interface near the higher-level policy that needs it, then makes lower-level adapters implement that interface. Higher policy no longer imports one concrete database. This is the module-level form of dependency injection from Chapter 9.

### 10.1.6 Import graph and call graph differ

An **import graph** records which modules require names from which others during loading. A **call graph** records possible runtime calls among functions or methods. They need not point the same way.

~~~python
# policy.py
from typing import Protocol


class Writer(Protocol):
    def write(self, text: str) -> None: ...


def publish(writer: Writer, text: str) -> None:
    writer.write(text)
~~~

~~~python
# file_adapter.py
from .policy import Writer


class FileWriter:
    def write(self, text: str) -> None:
        # Filesystem boundary omitted here.
        pass
~~~

The adapter imports the policy protocol, so the import edge points from adapter to policy. At runtime, <code>policy.publish</code> calls a method on the injected adapter, so one call edge points from policy code to adapter behaviour. Dynamic dispatch inverts runtime control without reversing source dependency.

### 10.1.7 Stable and volatile modules

A stable module changes infrequently or has many dependants whose compatibility matters. A volatile module changes often because it represents user-interface decisions, vendor APIs, deployment configuration, or experimental policy. Directing many stable modules toward one volatile module amplifies change.

Stability is observed, not inferred from an attractive name such as <code>core</code>. Version history, ownership, interface breadth, and reasons for change provide evidence. A module with many incoming dependencies deserves a small, deliberate public surface and strong compatibility tests.

### 10.1.8 Granularity is an optimisation problem

Modules that are too large mix ownership and make independent testing or reuse difficult. Modules that are too small increase import edges, navigation cost, naming burden, and circular-dependency risk. Choose granularity so that:

- concepts that maintain one invariant remain near each other;
- code that changes together is usually reviewed together;
- public interfaces are smaller than implementation interiors;
- dependency direction remains legible;
- tests can exercise meaningful units without excessive mocking;
- names describe domain or architectural roles rather than accidental code shapes.

One-class-per-file is a convention from some ecosystems, not a Python design law. Related value classes and functions can form one cohesive module.

### 10.1.9 A public façade can decouple layout from API

Suppose version 1 defines <code>Transaction</code> in <code>ledger.model</code>. Callers that import its physical location are coupled to that layout. The package can instead publish:

~~~python
# ledger/__init__.py
from .model import Transaction

__all__ = ["Transaction"]
~~~

Clients use <code>from ledger import Transaction</code>. A later version can move implementation to <code>ledger.transactions</code> while preserving the façade import. The façade does not remove semantic compatibility obligations; it separates a public name from one internal file boundary.

Avoid re-exporting every internal name. A façade that mirrors the whole package exposes layout indirectly and creates import-time cycles or expense. Publish a curated interface.

### 10.1.10 The <code>src</code> layout tests installation assumptions

In a flat project layout, the repository root may contain the import package directly. Running tests from that root can import the working directory even if packaging configuration would omit files or use a different mapping. A <code>src</code> layout places import packages below a directory such as <code>src/</code>; normal development then uses an installation, commonly editable, to make them importable.

This layout helps reveal missing installation configuration. It does not itself prove the built wheel is correct and does not prevent tests from manipulating <code>sys.path</code>. Clean-wheel verification remains necessary.

### 10.1.11 Module state has process lifetime by default

Once imported ordinarily, a module object is retained in <code>sys.modules</code> and its namespace persists. Module-level caches, registries, locks, and clients thereby become shared process-lifetime state unless explicitly reset or replaced.

~~~python
# counters.py
count = 0


def next_count() -> int:
    global count
    count += 1
    return count
~~~

Every importer using the same cached <code>counters</code> module observes the same binding. That may be the intended owner of a monotonic process counter, but tests, subinterpreters, process forks, reload, and concurrency need defined semantics. A module is a convenient singleton-like namespace, not a magically safe state container.

### 10.1.12 Boundary review questions

For every proposed module or package, answer:

1. What invariant or responsibility does it own?
2. Which names and behaviours are public?
3. Which modules may depend on it, and why?
4. Which external effects occur on import versus explicit calls?
5. Which state persists in the module object?
6. What is the lifecycle and concurrency policy for that state?
7. Which exceptions cross the boundary?
8. Can implementation move without breaking callers?
9. How is the boundary tested as a unit and through integration?
10. Does its import direction create a cycle?
11. Which distribution installs it, and under which import name?
12. What authority is granted merely by importing it?

> **Common misconception — “Modularity means splitting code into more files.”**  
> Useful modularity assigns coherent responsibility and controls dependencies. More files can increase coupling and obscure invariants.

> **Common misconception — “If a name begins with an underscore, callers cannot depend on it.”**  
> The underscore communicates non-public status. Compatibility depends on social and tooling discipline, not access prevention.
