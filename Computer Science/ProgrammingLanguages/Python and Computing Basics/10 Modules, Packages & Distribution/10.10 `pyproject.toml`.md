# 10.10 `pyproject.toml`

`pyproject.toml` is the standard configuration file through which projects declare build-system requirements and project metadata. A fuller example:

```toml
[build-system]
requires = ["hatchling>=1.25"]
build-backend = "hatchling.build"

[project]
name = "careful-ledger"
version = "0.1.0"
description = "A demonstrative transaction ledger"
readme = "README.md"
requires-python = ">=3.12"
license = "MIT"
license-files = ["LICENSE*"]
authors = [
  { name = "Example Author" },
]
dependencies = []

[project.optional-dependencies]
test = [
  "pytest>=8,<9",
]

[project.scripts]
careful-ledger = "ledger.__main__:entry"

[tool.pytest.ini_options]
testpaths = ["tests"]
```

The build-system table states which backend builds the project and which packages are required to run that backend in an isolated build context. The project table supplies core metadata. Optional dependencies group additional capabilities. A script entry point asks installation tooling to create a command that imports `ledger.__main__`, finds `entry`, and calls it under the entry-point contract.

The precise accepted fields and version syntax belong to packaging standards and selected tools. Tool-specific configuration lives under namespaced `[tool.NAME]` tables.

Do not execute `pyproject.toml` as Python; it is TOML data interpreted by build and development tools.

### 10.10.1 One file serves standard and tool-specific roles

<code>pyproject.toml</code> can contain:

- <code>[build-system]</code>, which tells a build frontend how to bootstrap the project’s build backend;
- <code>[project]</code>, which contains standard project metadata;
- standard companion tables such as entry-point and optional-dependency tables;
- namespaced <code>[tool.NAME]</code> tables interpreted only by the named tool.

The file is not one tool’s proprietary configuration. A formatter must ignore the build backend’s table; a backend must not reinterpret another tool’s namespace. Unknown standard fields and unknown tool tables follow their consumers’ respective validation rules.

### 10.10.2 TOML types are part of metadata correctness

TOML distinguishes strings, arrays, tables, integers, dates, and other values. These are not interchangeable textual spellings.

~~~toml
[project]
name = "careful-ledger"
requires-python = ">=3.12"
keywords = ["ledger", "accounting"]
~~~

<code>requires-python</code> is a string containing a version specifier; it is not a TOML number. <code>keywords</code> is an array of strings. Dotted table names and arrays of tables have structural meaning. Validate with build/metadata tools rather than assuming parse success means specification conformance.

### 10.10.3 Build frontend and backend are different roles

A **build frontend** is the user-facing tool requesting a standard build operation. A **build backend** is the project-selected implementation that knows how to turn this source tree into an sdist or wheel under defined hooks.

~~~toml
[build-system]
requires = ["hatchling>=1.25"]
build-backend = "hatchling.build"
~~~

The frontend creates an isolated build environment when applicable, installs <code>requires</code> there, imports the backend object, and invokes standard hooks. The dependencies in <code>build-system.requires</code> are needed to run the build; they are not automatically runtime dependencies of the installed library.

The lower bound shown is illustrative, not a universal recommendation. A project should constrain build requirements to features it uses while avoiding unnecessary exclusion of compatible releases. Reproducible release pipelines additionally lock or retain the actual build environment outside the broad source metadata contract.

### 10.10.4 Build isolation prevents ambient accidental dependencies

Without isolation, a build might succeed only because the developer environment happens to contain an undeclared plugin or compiler helper. An isolated build asks whether declared build requirements suffice.

Isolation does not isolate from malicious build code: the backend and build requirements execute with process authority. It also does not supply operating-system compilers, headers, or libraries unless the broader environment provides them. Build reproducibility spans Python and non-Python inputs.

### 10.10.5 Static and dynamic metadata

Most <code>[project]</code> fields are written statically. A project can list selected fields in <code>dynamic</code> so its backend supplies them:

~~~toml
[project]
name = "careful-ledger"
dynamic = ["version"]
~~~

Backend-specific configuration then identifies the version source. A field cannot coherently be both statically specified and declared dynamic, and required metadata must ultimately be supplied.

Static metadata is easiest for generic tools to inspect without executing project code. Deriving a version by importing the package can create a build cycle when that package imports dependencies not yet installed. Prefer a backend-supported source that does not import the full runtime package.

### 10.10.6 Project name, version, and Python requirement

~~~toml
[project]
name = "careful-ledger"
version = "0.1.0"
requires-python = ">=3.12"
~~~

The name identifies the distribution under packaging normalisation. The version follows the packaging version scheme, which is richer than naive decimal comparison. <code>requires-python</code> filters interpreter compatibility during resolution; it does not itself prevent source from being run by an unsupported interpreter outside packaging tools.

Set the Python lower bound to the oldest version actually tested and supported. Raising it can exclude environments and is a compatibility change. A claim of <code>>=3.12</code> should be backed by continuous tests on supported versions and syntax/features consistent with that bound.

### 10.10.7 Readme and description metadata

~~~toml
[project]
description = "A transaction ledger with explicit integer-money semantics"
readme = "README.md"
~~~

The short description is plain project metadata. The readme path tells the backend to include/read long-description content with content type inferred or configured under specification rules. Links and rendered markup should be tested on the target index; repository-relative links may not resolve in an index page.

Packaging inclusion and documentation quality are distinct. A readme can be present in metadata yet omit API or migration contracts.

### 10.10.8 Licence expressions and files

Current packaging metadata supports an SPDX licence expression string and patterns for licence files:

~~~toml
[project]
license = "MIT"
license-files = ["LICENSE*"]
~~~

The expression identifies licensing under the packaging specification; it is not a substitute for including the actual licence notices required by the selected licence and dependencies. Compound expressions use SPDX operators under their grammar. A project-specific custom identifier follows the allowed <code>LicenseRef-...</code> form.

Older examples used a table such as <code>license = { text = "MIT" }</code>. That legacy table form has been superseded/deprecated by newer licence metadata. A long-lived reference should label it as compatibility history, not teach it as the preferred current form.

### 10.10.9 People and project URLs

~~~toml
[[project.authors]]
name = "Example Author"
email = "author@example.invalid"

[project.urls]
Documentation = "https://example.invalid/careful-ledger/docs"
Source = "https://example.invalid/careful-ledger/source"
Issues = "https://example.invalid/careful-ledger/issues"
~~~

Authors and maintainers are arrays of tables because there can be several people or organisations. Do not publish personal contact information without consent. URLs are labelled metadata for tools and indexes; labels are conventions rather than arbitrary code hooks.

### 10.10.10 Runtime dependencies use requirement strings

~~~toml
[project]
dependencies = [
  "platformdirs>=4,<5",
  "importlib-resources>=6; python_version < '3.12'",
]
~~~

Each string uses the dependency-specifier grammar and can include a project name, extras, version constraints, direct references under permitted policies, and an environment marker. The example’s backport marker is pedagogical; a project requiring Python 3.12 would not need that particular backport and should omit irrelevant dependencies.

Environment markers are evaluated for a target installation environment. They are not ordinary Python expressions and use defined marker variables/operators. Test resolution on every supported platform; a branch never exercised by the developer’s machine can remain broken.

### 10.10.11 Do not overconstrain library dependencies

A reusable library should state versions it is actually incompatible with, not freeze the entire environment to one lock set in its public metadata. Exact transitive pins from one development machine can make the library impossible to compose with others.

An application deployment needs a reproducible resolved environment and may maintain a lock file or constraints under its toolchain. Source metadata states compatibility intent; a lock records one selected solution. These are complementary artefacts.

Upper bounds should be evidence-based. Assuming every next major release is incompatible can be prudent for some dependencies and needlessly block security updates for others. Establish an update/testing policy.

### 10.10.12 Optional dependencies describe installable feature sets

~~~toml
[project.optional-dependencies]
postgres = ["psycopg[binary]>=3.2,<4"]
plot = ["matplotlib>=3.9"]
test = ["pytest>=8", "mypy>=1.11"]
~~~

Users can request a distribution extra through requirement syntax such as <code>careful-ledger[postgres]</code>. An extra groups additional distribution requirements; it does not automatically activate code at runtime. Application code still detects/configures the capability and reports absence meaningfully.

Using <code>test</code> as an extra is common but not the only development-dependency mechanism. Development tools may support dependency groups or lock configurations that need not become published extras. Choose deliberately which groups are part of public installation metadata.

### 10.10.13 Command entry points

~~~toml
[project.scripts]
careful-ledger = "ledger.cli:main"

[project.gui-scripts]
careful-ledger-gui = "ledger.gui:main"
~~~

The value names an import module and object reference consumed by installation tooling. It is not a shell command string and should not contain arbitrary command-line arguments. The object must be present in the installed artefact with all runtime dependencies declared.

GUI script behaviour differs by platform, particularly console/window handling. Test generated commands on target operating systems.

### 10.10.14 General entry-point groups

Frameworks can define named entry-point groups for plugin discovery:

~~~toml
[project.entry-points."careful_ledger.exporters"]
json = "ledger_json:JsonExporter"
csv = "ledger_csv:CsvExporter"
~~~

In a real ecosystem, plugin distributions ordinarily declare their own entries pointing to their implementations; the host queries installed metadata for the group. Loading an entry point imports code and requires interface validation and failure isolation. Group and entry names are public coordination namespaces and should be globally chosen with collision policy.

### 10.10.15 Classifiers and keywords are discovery metadata

Classifiers come from a controlled vocabulary used by package indexes. They can communicate supported Python versions, development status, audience, and topics. They do not override <code>requires-python</code>, licence expressions, or test evidence.

Do not list every conceivable platform as supported because pure Python source happens to parse there. Support includes dependencies, tests, documentation, and issue policy.

### 10.10.16 Backend-specific package discovery

The standard <code>[project]</code> table does not by itself tell every backend exactly which source packages and non-code files to include. Backend-specific tables may configure <code>src</code> layout, inclusion/exclusion, generated files, and extension builds.

Because this configuration is backend-specific, consult the selected backend’s primary documentation and pin required feature versions. Verify artefact contents rather than inferring them from a successful build.

### 10.10.17 Tool tables do not become runtime metadata automatically

~~~toml
[tool.pytest.ini_options]
testpaths = ["tests"]

[tool.mypy]
python_version = "3.12"
strict = true
~~~

These tables configure named development tools. They are not automatically embedded as public distribution metadata, installed as dependencies, or enforced for downstream users. A misspelled tool table may be ignored unless the tool validates configuration strictly; CI should run configuration checks.

### 10.10.18 Environment-specific values do not belong in source metadata

Database passwords, deployment URLs, private tokens, and machine-specific absolute paths should not be committed to <code>pyproject.toml</code>. Build metadata is commonly published inside distributions and indexes. Keep secrets in an authorised deployment mechanism and feed them to runtime configuration without embedding them in built artefacts or logs.

### 10.10.19 Validate metadata at several stages

1. parse and validate <code>pyproject.toml</code> under the chosen backend/frontends;
2. build sdist and wheel in isolation;
3. inspect archive file lists and core metadata;
4. install the wheel into a clean environment;
5. query installed metadata with <code>importlib.metadata</code>;
6. run entry points and imports outside the repository;
7. resolve optional extras on supported targets;
8. render the long description as the target index will;
9. audit that secrets and unintended files are absent;
10. compare sdist-to-wheel rebuild behaviour.

### 10.10.20 A current minimal library skeleton

~~~toml
[build-system]
requires = ["hatchling>=1.25"]
build-backend = "hatchling.build"

[project]
name = "careful-ledger"
version = "0.1.0"
description = "Integer-valued transaction ledger"
readme = "README.md"
requires-python = ">=3.12"
license = "MIT"
license-files = ["LICENSE*"]
authors = [
  { name = "Example Author" },
]
dependencies = []

[project.optional-dependencies]
test = [
  "pytest>=8",
]

[project.scripts]
careful-ledger = "ledger.cli:main"
~~~

This example is intentionally not universal. Backend choice, dependency ranges, licence, author, entry point, and Python support must match the actual project. Copying metadata without owning its claims produces a formally buildable but semantically false distribution.

> **Common misconception — “<code>pyproject.toml</code> installs dependencies when Python imports the package.”**  
> Installation/resolution tools consume metadata before runtime. The import system does not invoke them to repair missing dependencies.

> **Common misconception — “Build-system requirements are application dependencies.”**  
> They bootstrap the backend in the build environment. Runtime dependencies belong under <code>project.dependencies</code>.
