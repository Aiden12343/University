# 10.11 Source distributions and wheels

A **source distribution**, commonly called an **sdist**, is an archive containing source and metadata sufficient for a compatible build frontend/backend to produce an installation artefact. A **wheel** is a built distribution format designed for installation without rerunning arbitrary project build steps in the target environment.

A **pure Python wheel** can be broadly platform-compatible when it contains no platform-specific compiled components. A wheel containing native extensions carries compatibility tags for Python/ABI/platform constraints. **ABI**, application binary interface, is the low-level calling, layout, and binary compatibility contract between compiled components.

Building and installing are distinct:

```text
python -m build
python -m pip install dist/careful_ledger-0.1.0-py3-none-any.whl
```

The `build` frontend is itself an external tool and must be present in the development environment. A build commonly produces both sdist and wheel under `dist/`. Installation should be tested in a clean environment; an editable working-tree install can conceal omitted files and undeclared dependencies.

### Worked example 10.4 — Clean-wheel verification

1. Create the project environment and run tests against source.
2. Build the wheel.
3. Create a new empty virtual environment.
4. Install only the wheel and its declared dependencies.
5. Change to a directory outside the repository.
6. Import the package, run its command entry point, and execute installed-distribution tests or smoke tests.

Leaving the repository prevents the current working tree from satisfying imports accidentally. This procedure tests the artefact users receive, not merely the source tree.

### 10.11.1 An sdist is a source release contract

A source distribution is not simply <code>git archive</code>. It has a standardised filename/container and project metadata, and should contain the source and configuration needed for a build frontend to ask the backend for a wheel on a compatible system.

An sdist may omit development-only files while requiring licence files, readme, build configuration, generated-source inputs, and package data. Whether generated C files or documentation sources belong depends on the project’s build contract. A user should not need the project’s unlisted version-control plugins merely to build.

### 10.11.2 A wheel is an installation-oriented archive

A wheel is a ZIP-based built distribution with a defined internal layout and metadata. It can contain pure Python modules, package data, scripts/entry metadata, and platform-specific compiled files. Installation mainly unpacks and arranges those contents under a scheme rather than running the project’s arbitrary source build process.

Wheel installation can still execute installer/tooling code and later imports execute package code. “Built” reduces target-side build work; it does not make the artefact inert or trusted.

### 10.11.3 Wheel filename tags express compatibility

A wheel filename includes distribution/version components and a triple of Python, ABI, and platform tags. The familiar suffix:

~~~text
py3-none-any.whl
~~~

means a broadly Python-3-compatible wheel with no specific compiled ABI and no platform-specific tag. A native extension wheel might use tags identifying a CPython version/ABI and an operating-system/architecture family.

Installers compare wheel tags with tags supported by the target interpreter. A matching tag means claimed binary compatibility, not proof that every external shared library or CPU feature is available. Projects must build and test appropriate artefacts for supported targets.

### 10.11.4 ABI compatibility is below Python source compatibility

Pure Python code depends on language and library interfaces. A compiled extension additionally depends on an application binary interface: calling conventions, symbol availability, object layouts, and binary formats. An extension built for one CPython ABI may not load in another even if source syntax is identical.

Some extensions target a limited stable ABI to cover several CPython versions; others use version-specific internal APIs for features or performance. The choice affects wheel tags, test matrix, and release burden.

### 10.11.5 Build wheels from a release source boundary

A disciplined release can:

1. create an sdist from the version-controlled release state;
2. inspect and verify the sdist;
3. build a wheel from that sdist in an isolated environment;
4. compare expected metadata and run tests on the installed wheel;
5. build platform wheels in controlled target builders where needed;
6. publish exactly the verified artefacts and hashes.

Building the wheel from the sdist tests that the source archive is sufficient. Building only from a rich checkout can hide omitted generated inputs or accidental dependence on untracked files.

### 10.11.6 Artefact contents are the truth delivered

List both archives:

~~~text
python -m build
python -m zipfile --list dist/careful_ledger-0.1.0-py3-none-any.whl
python -m tarfile --list dist/careful_ledger-0.1.0.tar.gz
~~~

Exact commands depend on filenames and available tools. Inspect for:

- every intended import module;
- type stubs or <code>py.typed</code> marker;
- licence and notice files;
- package resources;
- core metadata and entry points;
- absence of tests, secrets, local databases, credentials, and enormous unintended artefacts according to project policy.

A successful upload does not validate application completeness.

### 10.11.7 Package data versus user data

Read-only templates, schemas, and small reference datasets required by the package can be **package resources**. Runtime configuration, caches, mutable databases, and user documents do not belong inside the installed package directory.

Installed package locations may be read-only, replaced during upgrades, shared by users, or loaded from non-directory sources. Use platform-appropriate configuration/cache/data directories and explicit user paths for mutable data.

### 10.11.8 Reproducible builds require deterministic inputs

Two builds from logically identical source can differ because of archive timestamps, file ordering, generated identifiers, compiler versions, locale, paths, dependency versions, or nondeterministic code generation. A **reproducible build** is one whose defined inputs produce bit-for-bit identical outputs under the project’s reproduction specification.

Techniques include fixed source-date metadata, deterministic archive ordering, pinned/retained build tools, path normalisation, stable code generation, and controlled compiler flags. Reproducibility does not prove source safety; it lets independent builders compare that an artefact corresponds to declared inputs.

### 10.11.9 Installation integrity and <code>RECORD</code>

Wheel metadata includes a record of installed files and hashes/sizes under specification rules. This supports uninstall and integrity inspection. Some generated entries have special treatment, and an attacker able to modify the environment may modify records too.

Operational deployments can verify environments against immutable images or retained artefact hashes. A mutable developer environment is convenient but weak provenance evidence.

### 10.11.10 Native builds expand the toolchain

A package with C, C++, Rust, Fortran, or other native components may require compilers, headers, linkers, platform SDKs, and external libraries when no compatible wheel is available. Source installation can therefore fail even though a pure Python dependency resolver found compatible versions.

Error logs distinguishing “no compatible wheel was available” from “native build failed” guide remediation. Installing random compiler packages is not appropriate on a production host when policy requires prebuilt reviewed wheels.

### 10.11.11 Cross-compilation and target testing

Building on one platform for another requires a target toolchain and correct compatibility tags. A successful link does not prove runtime behaviour on the target. Execute tests in actual or faithfully emulated target environments, including architecture, operating-system baseline, and external library versions.

### 10.11.12 Wheel caching can conceal build defects

Installers often cache downloaded or locally built wheels. A second installation command may reuse a cached success instead of rebuilding changed source. During diagnosis, inspect logs, cache keys, resolved artefact hashes, and whether the command built or reused.

Do not disable caches permanently as a substitute for versioning artefacts correctly. Caches improve performance when their identity inputs are sound.

### 10.11.13 Test the installed interface outside source

A clean verification script might run:

~~~python
from importlib.metadata import version

import ledger


assert version("careful-ledger") == "0.1.0"
assert ledger.__file__ is not None
assert ledger.Transaction is not None
~~~

It should execute from a temporary directory that does not contain the checkout, run the installed command, load every required package resource, and perhaps type-check a consumer fixture. A full test suite may be omitted from the wheel, so retain external integration tests in the release pipeline.

### 10.11.14 Build and installation are security boundaries

Build backends and requirements execute code. Source distributions can cause target-side builds. Wheels contain code that executes when imported and can install entry-point wrappers. Security policy should control indexes, hashes, allowed build systems, network access during builds, and secrets available to builders.

A sandboxed builder with no publishing credential should create artefacts; a separate controlled step can verify and publish them. This limits what compromised build code can steal or release.

### 10.11.15 Artefact version must match code semantics

Every published artefact for one distribution version should represent one coherent release contract. Re-uploading different bytes under the same filename/version, where repositories permit any analogous mutation, destroys cache and provenance assumptions. Increment version for changed release content under repository policy.

### 10.11.16 Release verification matrix

For each artefact, record:

| Concern | Sdist | Pure wheel | Native wheel |
|---|---|---|---|
| archive format/name | verify | verify | verify |
| metadata/version | verify | verify | verify |
| source sufficiency | build wheel | not applicable | not applicable |
| import package files | source inputs | installed files | installed files |
| resources/licences | verify | verify | verify |
| target compatibility | build environments | supported Python range | Python/ABI/platform matrix |
| clean installation | build then install | install | install on target |
| command entry points | after installation | test | test |
| reproducible hash | compare under policy | compare | compare per toolchain |

> **Common misconception — “An sdist is for developers and a wheel is the source with a new extension.”**  
> They are distinct standard distribution formats: one supplies a source-build boundary; the other supplies an installation-oriented built layout.

> **Common misconception — “A wheel never runs code.”**  
> It avoids project source build steps during ordinary installation, but installers still operate, generated commands execute later, and importing installed modules runs code.
