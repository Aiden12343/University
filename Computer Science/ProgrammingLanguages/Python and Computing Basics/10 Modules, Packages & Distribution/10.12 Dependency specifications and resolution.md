# 10.12 Dependency specifications and resolution

A dependency requirement combines a distribution name with optional version constraints, environment markers, and extras. A **resolver** selects a mutually compatible set of distribution versions from available candidates.

Broad requirements support libraries that should interoperate with many environments. Applications often need a locked, reviewed environment for deployment. Exact pins alone do not guarantee reproducibility if artefacts disappear, platform markers vary, or build inputs remain uncontrolled. Hash checking, retained indexes or artefacts, interpreter constraints, and operating-system dependencies can matter.

**Semantic Versioning** is one project policy using major, minor, and patch numbers to communicate compatibility intent. Python packaging does not force every project to follow SemVer, and dependency solvers cannot infer behavioural compatibility beyond declared metadata. Read each project’s actual version policy.

Transitive dependencies are code brought into the environment without direct source imports in the application. They remain part of the attack surface and compatibility graph. Review and update policy must cover the solved graph, not only top-level declarations.

### 10.12.1 Anatomy of a requirement

An illustrative requirement is:

~~~text
http-client[http2]>=4.2,<5; python_version >= "3.12"
~~~

Its components are:

- distribution project name <code>http-client</code>;
- requested extra <code>http2</code>;
- version specifier set <code>>=4.2,<5</code>;
- environment marker restricting when the requirement applies.

This string does not name an import package, guarantee that version 4.9 is compatible, or select one artefact by itself. It defines constraints consumed by a resolver for a target environment.

### 10.12.2 Version ordering is specified, not lexical

Packaging versions have parsed components covering epochs, release segments, pre-releases, post-releases, development releases, and local versions under defined rules. Lexical string sorting gives wrong results for values such as <code>1.10</code> and <code>1.9</code>.

Use packaging-aware tools and classes when interpreting versions. Do not convert versions to floats: <code>1.10</code> as a decimal-like float becomes indistinguishable from <code>1.1</code>, and pre-release labels cannot be represented.

### 10.12.3 Specifier operators communicate sets

Common forms include:

- <code>>=2</code>: releases at or above a lower bound;
- <code><3</code>: releases below an upper bound;
- <code>!=2.4.1</code>: exclusion of a known bad release;
- <code>==2.4.*</code>: prefix matching under version-specifier rules;
- <code>~=2.4</code>: compatible-release constraint with a defined lower bound and compatible prefix.

Do not translate <code>~=</code> into an informal “approximately” without deriving its exact release-clause boundary. Test the set with a packaging version/specifier implementation.

Exact <code>==2.4.1</code> in published library metadata sharply restricts composition. Exact selections are usually recorded in application locks or constraints when reproducibility requires them.

### 10.12.4 A resolver solves a graph of constraints

Suppose application <code>A</code> requires <code>B>=2</code> and <code>C>=4</code>. Candidate <code>B 2.5</code> requires <code>D<3</code>; candidate <code>C 4.1</code> requires <code>D>=3</code>. No single <code>D</code> satisfies both, so that candidate combination is unsatisfiable.

A modern resolver may backtrack to other versions of <code>B</code> or <code>C</code>. Failure does not mean either top-level requirement is invalid alone; it means the combined graph has no found solution under indexes, markers, Python version, platform, pre-release policy, and other constraints.

### 10.12.5 Resolution may have many valid answers

If requirements allow ten versions of each of several packages, many graphs may satisfy them. Resolver strategy, index state, release time, and preferences determine one selection. Re-running broad resolution months later can legitimately choose newer versions without source metadata changing.

A lock captures one selection and, ideally, artefact identities for intended target environments. It converts repeated solving into verification of a recorded solution, subject to the lock format and installer.

### 10.12.6 Constraints differ from requirements

A requirement causes a project to be part of the desired environment and constrains it. A constraints file or analogous mechanism limits versions of projects that are otherwise required; it does not necessarily request their installation independently.

This distinction lets an organisation cap a vulnerable transitive version without pretending every constrained project is a direct application dependency. Tool semantics vary, so use the chosen installer’s documented format.

### 10.12.7 Locking across platforms is conditional

One operating system may select a platform-specific dependency or wheel unavailable on another. Python-version markers and extras alter the graph. A universal lock must encode conditional selections and artefacts; a single-platform lock should declare its target.

Testing only resolution on one developer machine does not prove Linux deployment, alternative architecture, or future Python support. Generate/verify locks under an explicit environment matrix.

### 10.12.8 Hashes bind names and versions to bytes

Pinning <code>package==1.2.3</code> selects a version label, potentially with several wheels and an sdist. Hash verification identifies accepted artefact bytes. For strict reproducibility, record hashes for every permitted target artefact and prevent implicit builds from unverified source.

Hashes do not prove the bytes are non-malicious; they prove equality to reviewed or otherwise authorised bytes. The trust decision occurs when hashes enter the lock or policy.

### 10.12.9 Pre-releases and yanked releases need policy

Resolvers ordinarily apply defined rules around pre-releases and repository-yanked files. A pre-release may be the only candidate satisfying an explicit range or may be excluded by default policy. A yanked release can remain addressable for exact historical pins while being avoided for new broad selection.

Do not infer vulnerability or incompatibility solely from these labels. Read project/repository metadata and security advisories, then update constraints deliberately.

### 10.12.10 Extras union additional requirements

If two dependants request <code>package[sql]</code> and <code>package[http]</code>, resolution generally combines the base project with dependencies activated by both extras. Extras do not install two independent copies of the base distribution.

Code cannot assume an extra was requested merely from metadata at runtime; it can test the capability dependency and configuration. Extras are installation features, not runtime feature flags.

### 10.12.11 Direct references trade index selection for location identity

A requirement can refer directly to an archive or version-control location under allowed syntax and repository policy. For reproducibility, a moving branch name is insufficient; use immutable commit/artefact identity and hashes where supported.

Direct references can be disallowed by public indexes or organisational policy and may require network credentials during installation. Never embed credentials in project metadata or URLs that enter logs and built artefacts.

### 10.12.12 Dependency confusion is a namespace attack

If an internal requirement name is also resolvable from a public index and the resolver considers both, an attacker may publish a higher-preference project under that name. Mitigations include segregated indexes, explicit source mapping, reserved names, authenticated repositories, hash-locked artefacts, and controlled resolution.

Merely putting a private index first may not be sufficient under every installer’s candidate-selection semantics. Test and enforce the chosen tool’s source policy.

### 10.12.13 Typosquatting exploits guessed project names

A misspelled install command can retrieve a malicious lookalike distribution. Copy names from authoritative documentation, inspect publisher and metadata, use approved lock files, and avoid “try installing the import name” troubleshooting.

### 10.12.14 Direct dependencies deserve direct declarations

If application source imports or otherwise relies on project <code>X</code>, declare <code>X</code> even when current dependency <code>Y</code> also depends on it. <code>Y</code> can remove or constrain <code>X</code> in a later release because it never promised to supply your application’s dependency.

Static import scanning can help detect missing declarations but cannot see all dynamic/resource/entry-point uses or map names perfectly. Combine scanning with runtime clean-environment tests.

### 10.12.15 Minimal dependency is not zero dependency

Every dependency adds compatibility, security, download, build, and maintenance cost. Reimplementing cryptography, protocol parsing, or platform integration can create much greater risk. Evaluate:

- correctness difficulty and standards burden;
- project maintenance and governance;
- release/security response;
- transitive graph size;
- licences;
- platform/ABI support;
- API stability;
- ability to isolate or replace it.

The decision is engineering risk allocation, not a count contest.

### 10.12.16 Update policy balances freshness and evidence

Never updating preserves known vulnerabilities and compatibility debt. Unreviewed automatic updates can introduce malicious or defective releases. A mature process periodically proposes lock changes, reviews changelogs/advisories, runs the complete target matrix, and rolls out with observability and rollback.

Security fixes may require accelerated exceptions to normal release cadence. Upper bounds and abandoned dependencies can block them; monitor resolution health before an emergency.

### 10.12.17 Check installed consistency, then test behaviour

Installer commands such as <code>python -m pip check</code> can report whether installed distributions’ declared requirements are satisfied. A clean result does not prove runtime compatibility: metadata may be wrong, optional paths untested, native libraries unavailable, or behavioural APIs changed within allowed ranges.

Run application tests and startup/import smoke tests in the exact resolved environment.

### 10.12.18 Vendoring changes ownership

**Vendoring** copies dependency code into a project or distribution, often under a private namespace. It can isolate version conflicts or ensure availability, but the vendor now owns update tracking, licence notices, security patches, namespace rewriting, and divergence.

Vendoring is not equivalent to eliminating the dependency; it internalises it.

### 10.12.19 Resolution report

For each release environment, retain:

1. direct requirement intent;
2. target Python/platform markers;
3. selected versions and extras;
4. transitive dependency edges;
5. selected artefact filenames and hashes;
6. index/source provenance;
7. yanked/pre-release/direct-reference decisions;
8. vulnerability/licence review results;
9. build versus downloaded-wheel status;
10. test evidence and deployment image identity.

> **Common misconception — “A lock file proves the dependencies are secure.”**  
> It records a selected graph and perhaps artefact identity. Security requires trustworthy selection, review, updates, and runtime controls.

> **Common misconception — “The newest version satisfying each direct range is the solution.”**  
> Transitive constraints, markers, extras, Python/ABI/platform compatibility, and available artefacts must be solved as one graph.
