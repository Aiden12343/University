# 10.13 Namespace packages and resources

A **namespace package** allows portions of one import package to be contributed from multiple locations and may lack `__init__.py`. It solves distribution composition use cases but changes assumptions about package paths and initialisation. Do not teach “every package is a directory containing `__init__.py`” as an absolute rule; that describes ordinary packages, not all packages.

Package-owned data should be accessed through resource APIs rather than assuming it exists as an ordinary file beside `__file__`. Installed packages can reside in archives, specialised loaders, or layouts where direct path arithmetic is inappropriate.

```python
from importlib.resources import files


template_text = (
    files("ledger")
    .joinpath("templates", "summary.txt")
    .read_text(encoding="utf-8")
)
```

This asks the import resource system for package data under its traversable interface. Packaging configuration must include the resource in built artefacts.

### 10.13.1 Regular packages execute an initializer

A regular package commonly corresponds to a directory containing <code>__init__.py</code>. Import creates one package module object, executes that initializer, and gives the module a <code>__path__</code> used to search for submodules.

The initializer may define a façade, metadata, or lightweight registration. It should not import the entire implementation tree reflexively; broad eager re-exports increase startup cost and cycles.

### 10.13.2 Implicit namespace packages combine portions

An **implicit namespace package** can exist without <code>__init__.py</code>. When the import search finds matching directories or other portions across path entries but no overriding regular package/module under the applicable algorithm, it constructs a namespace package whose search locations combine those portions.

Example installations might contribute:

~~~text
environment-A/site-packages/acme/payments/
environment-B/site-packages/acme/reporting/
~~~

Both can appear under namespace <code>acme</code>. The <code>acme</code> package itself has no single initializer that owns all portions.

### 10.13.3 Namespace package paths are dynamic search state

The namespace package’s <code>__path__</code> represents locations considered for children and can respond to changes in parent search paths according to import-system behaviour. Do not convert it to one assumed directory.

~~~python
import acme


for location in acme.__path__:
    print(location)
~~~

A regular package may also expose more than one search location by manipulating <code>__path__</code>, but such customisation is specialised and security-sensitive.

### 10.13.4 Adding <code>__init__.py</code> changes composition

If one distribution installs a regular <code>acme</code> package with <code>__init__.py</code>, it can change or prevent implicit namespace aggregation depending on search order. Namespace participants must coordinate the namespace convention. A stray initializer is not harmless boilerplate.

### 10.13.5 Portions can collide

Two distributions may both provide <code>acme.reporting</code>. Search order selects one or installation overlaps files; the namespace protocol does not merge two modules of the same fully qualified name. Assign globally coordinated child names and detect duplicates in deployment inspection.

### 10.13.6 Namespace packages lack one distribution owner

Uninstalling one contributing distribution should remove only its portion, but application code importing <code>acme</code> cannot infer which plugins are installed from the namespace object alone. Query distribution metadata or enumerate modules under a defined discovery contract, with awareness that enumeration can be incomplete for custom finders.

### 10.13.7 Resources are logical package contents

A **package resource** is non-code data associated with an importable package: a template, schema, certificate bundle, small reference table, or similar read-only artefact. The resource may reside in a normal directory, wheel installation, ZIP importer, or another loader-supported representation.

Path arithmetic on <code>__file__</code> assumes a real adjacent filesystem path and excludes other representations. <code>importlib.resources</code> exposes a **Traversable** abstraction with path-like read/navigation operations appropriate to package resources.

### 10.13.8 Text and bytes require explicit choice

~~~python
from importlib.resources import files


root = files("ledger")
schema_bytes = root.joinpath("schemas", "transaction.json").read_bytes()
template_text = root.joinpath("templates", "summary.txt").read_text(
    encoding="utf-8"
)
~~~

Use bytes when byte identity matters and text with an explicit encoding when interpreting characters. Newline semantics and parsing occur at higher layers.

### 10.13.9 Some consumers require a real path temporarily

A third-party API may insist on a filesystem path. <code>importlib.resources.as_file</code> can provide a context-managed path, extracting a resource temporarily when necessary:

~~~python
from importlib.resources import as_file, files


resource = files("ledger").joinpath("schemas", "transaction.json")

with as_file(resource) as concrete_path:
    consume_path(concrete_path)
~~~

The path’s lifetime belongs to the context. Do not store it for later use after exit. If the consumer can accept bytes or a file-like object, avoid materialising a path.

### 10.13.10 Choose the correct resource anchor

Anchoring at a specific package makes ownership explicit. A resource used only by <code>ledger.reporting</code> can live under that package and be located relative to an importable anchor under the supported API. Moving modules or splitting distributions can then require deliberate resource migration.

String package names are convenient; module objects can avoid some spelling ambiguity. Follow the minimum supported Python version’s API signatures because resource functions have evolved.

### 10.13.11 Resources are normally read-only deployment inputs

Writing beside installed code is unreliable and can violate deployment immutability or permissions. A default configuration resource should be read, parsed, then copied to a user-writable configuration location if mutation is required.

Never use a package resource as a global mutable database. Upgrades can replace it, concurrent users can conflict, and archive-backed packages may not provide a writable path.

### 10.13.12 Inclusion must be tested in both artefacts

A resource present in the checkout may be absent from an sdist, absent from a wheel built from that sdist, or installed under an unexpected path. Backend file-selection rules determine inclusion.

Add a clean-wheel test that calls the same resource API used by production and verifies content or schema version. Listing archives complements but does not replace that functional test.

### 10.13.13 Resource names are not arbitrary user paths

If a caller supplies a resource name, validate it against a finite catalogue or strict grammar. Do not join untrusted strings containing parent traversal and assume the resource abstraction is an access-control boundary. Package resources may contain sensitive internal data unintentionally; built artefacts are commonly distributable and inspectable.

### 10.13.14 Large data may not belong in the wheel

Large models or datasets increase every installation and update, may have separate licences, and can exceed index policies. Consider a versioned external data artefact with explicit download, integrity verification, cache, offline, and consent semantics.

External retrieval is then a network/data lifecycle, not an import resource. Keep a small schema or manifest in the package if it supports validation.

### 10.13.15 Resource caching and extraction

Repeated reading can cost I/O or decompression. Application-level caching may help, but must specify memory, invalidation, and package-version semantics. Temporary extraction has cleanup and concurrent-use considerations. Measure before caching small files already handled efficiently by the operating system.

### Worked example 10.4A — Parse a packaged JSON schema safely

~~~python
import json
from importlib.resources import files


def load_transaction_schema() -> dict[str, object]:
    resource = files("ledger").joinpath(
        "schemas",
        "transaction.json",
    )
    text = resource.read_text(encoding="utf-8")
    parsed = json.loads(text)
    if not isinstance(parsed, dict):
        raise RuntimeError("packaged transaction schema must be an object")
    return parsed
~~~

The package owns the trusted resource bytes, yet the parser still validates expected top-level shape because packaging or development mistakes are possible. The function returns a new mutable dictionary; callers need ownership documentation or an immutable domain conversion.

### 10.13.16 Namespace-package resources need unambiguous ownership

A namespace package can have multiple portions, so placing a same-named resource at its root can be ambiguous or unsupported depending on reader constraints. Prefer resources within a concrete child package owned by one distribution. The fully qualified anchor then identifies the provider.

> **Common misconception — “A package is always one directory.”**  
> Regular packages often are; namespace packages can combine portions, and loaders can represent packages outside normal directories.

> **Common misconception — “Package data can be opened with <code>Path(__file__).parent</code> everywhere.”**  
> That assumes a concrete adjacent filesystem layout. Resource APIs express logical package ownership and can materialise paths only when needed.
