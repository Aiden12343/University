# 10.14 Import security and shadowing

Imports execute code. Installing or importing an untrusted distribution grants it the current process’s authority. Similar names, compromised maintainers, dependency confusion, and unreviewed build steps are supply-chain risks.

Local files can **shadow** standard-library or dependency modules. A project file named `json.py` can be found before the intended standard-library module, causing circular or missing-attribute symptoms. Diagnose by printing the imported module’s `__file__` or specification, not by reinstalling at random.

Never add writable untrusted directories to import search paths. Do not deserialize or execute module names from untrusted input without an explicit allowlist and authority model. Plugin loading is code execution, not data parsing.

### 10.14.1 Import grants ambient process authority

Imported code ordinarily has the same operating-system identity, environment variables, filesystem access, network access, memory access, and Python-object reachability as the importer. A package has no lesser privilege merely because it is called a library.

Therefore dependency review is code-authority review. A malicious top-level statement can act before the application calls any advertised function.

### 10.14.2 Search-path precedence can select attacker-controlled code

If an untrusted writable directory appears before trusted library locations, a file named after an expected module can be imported instead. The attacker need not modify the application source; controlling resolution is sufficient.

Current working directories, script directories, environment path variables, notebook conveniences, and test configuration can introduce early entries. Production launchers should use controlled working directories and interpreter/path configuration, and avoid executing privileged applications from untrusted directories.

### 10.14.3 Standard-library shadowing produces both defects and attacks

A local <code>secrets.py</code>, <code>typing.py</code>, <code>json.py</code>, or <code>email/</code> can shadow a standard-library package. Symptoms often mention a partially initialised module because the local file imports something that imports the expected standard library name again.

Inspect origin:

~~~python
import json

print(json.__spec__)
print(getattr(json, "__file__", None))
~~~

Do not delete a file until its ownership is confirmed. Rename the project module, remove stale bytecode only as a secondary cleanup, and rerun in a fresh process.

### 10.14.4 Installed path configuration can execute startup code

Python environment startup can process site configuration, including path configuration files and customisation modules under documented rules. Certain path-file lines can execute imports. Installing a distribution can therefore arrange code to run at interpreter startup, before an application’s explicit imports.

Audit environment-level files and use isolated deployment environments. “Our source never imports that package” does not prove it cannot execute through startup hooks, instrumentation, plugins, or build/install machinery.

### 10.14.5 Custom import hooks enlarge the trusted base

Objects on <code>sys.meta_path</code>, path hooks, and loader implementations can observe or alter import resolution. Instrumentation, frozen applications, and plugin systems use this power legitimately. A compromised hook can substitute code for many names.

Record and constrain import hooks in high-assurance environments. Debugging code that mutates global hook lists must restore them even after exceptions and coordinate with other threads.

### 10.14.6 Dynamic import requires identifier-to-authority mapping

This is unsafe when <code>request_value</code> is arbitrary:

~~~python
module = import_module(request_value)
~~~

A syntactic dotted-name validator only limits spelling. Use an allowlist mapping public identifiers to reviewed entry points:

~~~python
EXPORTERS = {
    "json": "ledger.exporters.json:JsonExporter",
    "csv": "ledger.exporters.csv:CsvExporter",
}
~~~

Parse the selected fixed entry, load it under controlled error handling, and verify its behavioural interface. If extensions are genuinely third-party and untrusted, execute them in a separately constrained process or stronger sandbox appropriate to the threat model.

### 10.14.7 Interface validation is not security isolation

Checking that a plugin implements <code>export</code> prevents one class of configuration mistake. It does not stop its import body or method from reading files, exfiltrating secrets, mutating globals, or exhausting resources. Static type checking likewise provides no containment.

Security isolation requires an authority boundary—often an operating-system process/container/user with restricted filesystem, network, credentials, time, and memory—plus a validated interprocess protocol.

### 10.14.8 Build dependencies execute before runtime review

A source distribution’s build backend and build requirements execute while producing a wheel. A compromised build dependency can read publishing credentials or alter artefacts even if it is never listed as a runtime dependency.

Build in an ephemeral least-privileged environment without unnecessary secrets or network. Separate signing/publishing authority and verify output metadata/files before release.

### 10.14.9 Repository source policy must be explicit

When multiple indexes or direct links are available, dependency names can resolve from an unintended source. Pinning only a version does not identify the repository or bytes. Use an installer/lock policy that binds internal names to authorised sources and hashes, and test that public candidates cannot supersede them.

### 10.14.10 Namespace packages can accept unexpected portions

An open namespace permits additional distributions to contribute children. If an application dynamically enumerates and imports every child, installing an unrelated or malicious portion can achieve execution. Namespace discovery must filter by authoritative metadata, allowlisted names, signatures/hashes under policy, or deployment inventory.

Importing a specific known child is narrower than scanning everything found.

### 10.14.11 Verify artefacts before exposing secrets

Dependency fetching/building should occur before deployment secrets enter the environment. Runtime startup imports should not have package-index write credentials. CI jobs that both execute untrusted pull-request build code and possess publication tokens collapse trust boundaries.

Use staged jobs and short-lived scoped credentials whose issuance depends on verified release conditions.

### 10.14.12 Origin checks have race and loader limits

Checking <code>module.__file__</code> after import tells which origin claims to have loaded, but malicious code has already executed and can falsify attributes. Checking <code>find_spec</code> before import can itself invoke finder code and a filesystem path can change between check and use.

Security must control the environment and artefact provenance before execution; diagnostic origin checks are not preventive sandboxing.

### 10.14.13 Import-time network retrieval undermines reproducibility

A module that downloads executable code or data on import makes behaviour depend on network state after installation, bypasses ordinary artefact review, and can fail offline. Package required code in verified artefacts. If updating data or plugins is a feature, implement an explicit authenticated update protocol with version, integrity, cache, rollback, and consent.

### 10.14.14 Exceptions must not leak environment secrets

Import failures can contain filesystem paths, repository URLs with credentials, environment-derived configuration, compiler commands, or server responses. Diagnostics should preserve enough provenance to debug while redacting secrets before user-facing or shared logs.

Never solve an import problem by publishing the entire environment or path listing without review.

### 10.14.15 Dependency removal reduces latent execution paths

Unused dependencies remain candidates for startup hooks, transitive vulnerabilities, resolver conflicts, and supply-chain compromise. Periodically compare declared requirements with actual supported uses, accounting for dynamic entry points and build tooling before removal.

### 10.14.16 Threat-model checklist

For every importable external component, ask:

1. Who controls its project and release credentials?
2. From which authorised repository and exact artefact is it obtained?
3. Does installation build untrusted source?
4. Which startup/import hooks can execute it?
5. Which process credentials and secrets exist at execution time?
6. Can its import name be shadowed?
7. Can namespace or plugin enumeration discover unexpected code?
8. What containment limits filesystem, network, CPU, memory, and subprocesses?
9. How are vulnerabilities and ownership changes monitored?
10. How can the component be disabled, rolled back, or removed?

> **Common misconception — “Only calling a library function gives the library authority.”**  
> Module top-level code runs during import, and environment/startup hooks can run even earlier.

> **Common misconception — “Validating a plugin protocol makes untrusted plugins safe.”**  
> Interface conformance addresses compatibility, not authority. In-process code ordinarily has the process’s privileges.
