# 10.15 Integrated package design

For the ledger project, assign responsibilities:

- `model.py`: immutable transaction records and ledger invariants;
- `parsing.py`: text/CSV boundary to validated transactions;
- `reporting.py`: pure report construction from model queries;
- `__init__.py`: deliberate stable exports;
- `__main__.py`: command arguments, filesystem boundary, stdout/stderr/status;
- `tests/`: unit and integration evidence;
- `pyproject.toml`: build, metadata, dependencies, and entry point.

Dependency direction:

```text
__main__ → parsing → model
    └────→ reporting → model
```

`model` knows nothing about CLI, file paths, or display. `parsing` constructs model objects. `reporting` queries model state. `__main__` coordinates effects. This directed graph avoids a model importing its adapters.

At application start, imports execute definitions and lightweight configuration. The entry function then parses arguments, acquires input, invokes pure or domain components, emits output, and returns status. An import of `ledger` for use as a library does not launch the command.

The tree separates domain policy, boundary adapters, process entry, package resources, and verification levels. It is an example, not a prescription that every project needs each file. <code>errors.py</code> is justified only if several modules share a coherent public exception vocabulary; otherwise errors can remain beside their owning operation.

### 10.15.2 Domain model owns exact monetary invariants

<code>model.py</code>:

~~~python
from dataclasses import dataclass
from datetime import date

from .errors import InvalidTransaction


@dataclass(frozen=True, slots=True)
class Transaction:
    identifier: str
    booked_on: date
    amount_pence: int
    description: str

    def __post_init__(self) -> None:
        identifier = self.identifier.strip()
        description = self.description.strip()
        if not identifier:
            raise InvalidTransaction("identifier cannot be blank")
        if not description:
            raise InvalidTransaction("description cannot be blank")
        if isinstance(self.amount_pence, bool) or not isinstance(
            self.amount_pence, int
        ):
            raise InvalidTransaction("amount_pence must be an integer")

        object.__setattr__(self, "identifier", identifier)
        object.__setattr__(self, "description", description)
~~~

Integers make sub-unit representation exact under the chosen currency assumption. The model does not parse decimal text or know a filename. Normalisation precedes stable frozen state. Rejecting <code>bool</code> matters because <code>bool</code> is an <code>int</code> subtype but semantically inappropriate as money.

The model still needs a declared range/overflow policy and currency model for production. Python integers do not overflow at a fixed machine bound, while external stores may.

### 10.15.3 Public exceptions translate boundary meaning

<code>errors.py</code>:

~~~python
class LedgerError(Exception):
    """Base for anticipated ledger-domain failures."""


class InvalidTransaction(LedgerError, ValueError):
    """A transaction violates the domain representation."""


class ParseFailure(LedgerError, ValueError):
    """External text cannot be converted into a transaction."""


class StorageFailure(LedgerError):
    """A storage boundary could not satisfy its operation."""
~~~

Multiple inheritance from <code>ValueError</code> communicates compatibility with callers handling invalid values while preserving a project root. Whether this complexity is useful depends on the API. Internal vendor exceptions should be chained as causes when translating, not exposed unpredictably.

### 10.15.4 Parsing separates syntax from domain validity

<code>parsing.py</code>:

~~~python
from datetime import date
from decimal import Decimal, InvalidOperation, ROUND_HALF_EVEN

from .errors import InvalidTransaction, ParseFailure
from .model import Transaction


PENNY = Decimal("0.01")


def parse_amount_pence(text: str) -> int:
    try:
        amount = Decimal(text)
    except InvalidOperation as error:
        raise ParseFailure("amount is not decimal text") from error

    if not amount.is_finite():
        raise ParseFailure("amount must be finite")

    quantised = amount.quantize(PENNY, rounding=ROUND_HALF_EVEN)
    if quantised != amount:
        raise ParseFailure("amount has sub-penny precision")
    return int(quantised * 100)


def parse_transaction(fields: dict[str, str]) -> Transaction:
    try:
        identifier = fields["id"]
        booked_on = date.fromisoformat(fields["date"])
        amount_pence = parse_amount_pence(fields["amount"])
        description = fields["description"]
    except KeyError as error:
        raise ParseFailure(f"missing field: {error.args[0]}") from error
    except ValueError as error:
        if isinstance(error, ParseFailure):
            raise
        raise ParseFailure("date is not ISO calendar syntax") from error

    try:
        return Transaction(
            identifier=identifier,
            booked_on=booked_on,
            amount_pence=amount_pence,
            description=description,
        )
    except InvalidTransaction as error:
        raise ParseFailure("transaction violates domain rules") from error
~~~

The parser owns field names, date syntax, decimal rounding policy, and translation into the domain exception vocabulary. A production diagnostic might attach line/field information in structured exception attributes while redacting sensitive source content.

The <code>isinstance</code> branch inside the <code>ValueError</code> handler works because <code>ParseFailure</code> inherits <code>ValueError</code>, but separate smaller <code>try</code> suites could make control flow clearer. Exception hierarchy design affects handler overlap.

### 10.15.5 Ports express application-owned capabilities

<code>ports.py</code>:

~~~python
from collections.abc import Iterable
from typing import Protocol

from .model import Transaction


class TransactionSource(Protocol):
    def read_transactions(self) -> Iterable[Transaction]: ...


class ReportSink(Protocol):
    def write_report(self, text: str) -> None: ...
~~~

The protocols are owned inward because application/domain policy defines what it needs. Adapters implement them structurally. Returning <code>Iterable</code> leaves one-shot/resource questions; a more rigorous interface might be a context manager yielding an iterator or a method returning an immutable collection.

### 10.15.6 Reporting remains deterministic

<code>reporting.py</code>:

~~~python
from collections.abc import Iterable
from dataclasses import dataclass

from .model import Transaction


@dataclass(frozen=True, slots=True)
class Summary:
    transaction_count: int
    total_pence: int


def summarise(transactions: Iterable[Transaction]) -> Summary:
    count = 0
    total = 0
    for transaction in transactions:
        count += 1
        total += transaction.amount_pence
    return Summary(transaction_count=count, total_pence=total)


def render_text(summary: Summary) -> str:
    sign = "-" if summary.total_pence < 0 else ""
    absolute = abs(summary.total_pence)
    pounds, pennies = divmod(absolute, 100)
    return (
        f"transactions: {summary.transaction_count}\n"
        f"total: {sign}£{pounds}.{pennies:02d}\n"
    )
~~~

The traversal is single-pass and accepts generators. It does not retain transactions. The renderer has fixed sterling semantics; if multiple currencies are introduced, the model and summary must change rather than guessing from symbols.

### 10.15.7 A JSON-file adapter owns filesystem and schema concerns

<code>adapters/json_file.py</code>:

~~~python
import json
from collections.abc import Iterator
from pathlib import Path

from ..errors import ParseFailure, StorageFailure
from ..model import Transaction
from ..parsing import parse_transaction


class JsonLinesSource:
    def __init__(self, path: Path) -> None:
        self._path = path

    def read_transactions(self) -> Iterator[Transaction]:
        try:
            with self._path.open("r", encoding="utf-8") as stream:
                for line_number, line in enumerate(stream, start=1):
                    try:
                        value = json.loads(line)
                        if not isinstance(value, dict):
                            raise ParseFailure("line must contain an object")
                        fields = {
                            str(key): str(item)
                            for key, item in value.items()
                        }
                        yield parse_transaction(fields)
                    except (json.JSONDecodeError, ParseFailure) as error:
                        raise ParseFailure(
                            f"invalid transaction at line {line_number}"
                        ) from error
        except OSError as error:
            raise StorageFailure(f"cannot read {self._path.name!r}") from error
~~~

The generator keeps the file context open across iteration and closes it on exhaustion, generator closure, or ordinary exception unwinding. A consumer that abandons the iterator while retaining it can delay closure. An explicit source context-manager protocol could make lifetime more visible.

Converting every JSON value to <code>str</code> is a simplifying policy that may wrongly accept arrays or nulls. A rigorous schema validator should reject wrong JSON types field by field. The example exposes where that policy belongs.

The public error mentions only the basename, reducing accidental path disclosure; the chained <code>OSError</code> still contains diagnostic details and must be handled according to logging audience.

### 10.15.8 Application service coordinates ports

An <code>application.py</code> module may be warranted:

~~~python
from .ports import ReportSink, TransactionSource
from .reporting import render_text, summarise


def generate_report(
    source: TransactionSource,
    sink: ReportSink,
) -> None:
    summary = summarise(source.read_transactions())
    sink.write_report(render_text(summary))
~~~

The function defines operation order but knows no concrete path or console. It owns whether a report is emitted only after full successful parsing. Because <code>summarise</code> consumes lazily and <code>write_report</code> follows afterward, a parse failure produces no report through this coordinator.

This does not make filesystem input and output one atomic transaction. If a sink partially writes then fails, its own contract must address replacement or recovery.

### 10.15.9 CLI is the process translation boundary

<code>cli.py</code>:

~~~python
import argparse
import sys
from collections.abc import Sequence
from pathlib import Path

from .adapters.json_file import JsonLinesSource
from .application import generate_report
from .errors import LedgerError


class StandardOutputSink:
    def write_report(self, text: str) -> None:
        sys.stdout.write(text)


def parser() -> argparse.ArgumentParser:
    result = argparse.ArgumentParser(prog="careful-ledger")
    result.add_argument("input", type=Path)
    return result


def main(arguments: Sequence[str] | None = None) -> int:
    namespace = parser().parse_args(arguments)
    try:
        generate_report(
            JsonLinesSource(namespace.input),
            StandardOutputSink(),
        )
    except LedgerError as error:
        print(f"error: {error}", file=sys.stderr)
        return 1
    return 0
~~~

Passing <code>None</code> delegates argument acquisition to <code>argparse</code>; tests pass an explicit list. The CLI translates anticipated ledger errors to one process status. It does not catch programming defects such as <code>AttributeError</code>, which should remain visible during development and produce failure in deployment supervision.

For stronger test isolation, inject output/error streams rather than using <code>sys.stdout</code> inside the sink, or test the installed command in a subprocess.

### 10.15.10 Entry adapters converge

<code>__main__.py</code>:

~~~python
from .cli import main


if __name__ == "__main__":
    raise SystemExit(main())
~~~

<code>pyproject.toml</code> points the installed script to <code>ledger.cli:main</code>. Both launch routes share argument and status logic. Importing <code>ledger</code> runs neither.

### 10.15.11 Public package surface

<code>__init__.py</code>:


Concrete adapters and CLI internals are not exposed at the root. Advanced callers can use documented submodule APIs if the project chooses to support them; underscore names and documentation should make the policy unambiguous.

### 10.15.12 Import-direction audit

The principal edges are:

~~~text
model ------> errors
parsing ----> model, errors
reporting --> model
ports ------> model
adapter ----> parsing, model, errors
application -> ports, reporting
cli --------> adapter, application, errors
__main__ ---> cli
__init__ ---> selected public defining modules
~~~

There is no edge from model/reporting policy outward to CLI or filesystem adapters. The root façade imports several modules and can therefore be cycle-sensitive; internal modules do not import through it.

### 10.15.13 Unit tests align with ownership

<code>test_model.py</code> attacks normalisation and invariants without files. <code>test_parsing.py</code> tests text/field conversion and exception chaining. <code>test_reporting.py</code> uses generated iterables to prove single-pass behaviour and exact formatting.

Tests should not mock private functions merely to increase isolation. A unit is a coherent behaviour boundary, not necessarily one function.

### 10.15.14 Integration tests cross deliberate boundaries

<code>test_json_file.py</code> creates a temporary UTF-8 JSON-lines file and consumes the iterator fully and partially, testing closure and line diagnostics. <code>test_command.py</code> launches the command in a subprocess, checking status and separated streams. <code>test_installed_package.py</code> runs after wheel installation outside the checkout.

Property-based tests can generate valid and invalid amounts/dates. Fuzzing the parser can probe resource limits and malformed Unicode/JSON. Neither replaces manually specified domain cases.

### 10.15.15 Package resource decision

If <code>templates/summary.txt</code> is truly used, <code>render_text</code> can load it with <code>importlib.resources</code>. But the current renderer is clearer as Python because the template is tiny and formatting contains exact money logic. Do not create package data merely to demonstrate package data.

If a user-customisable template is required, treat it as explicit external configuration with validation rather than mutate the installed default.

### 10.15.16 Failure table

| Boundary | Internal failure | Public translation | Partial effect policy |
|---|---|---|---|
| decimal/date parse | parser-specific exception | <code>ParseFailure</code> | no transaction created |
| transaction invariant | <code>InvalidTransaction</code> | chained <code>ParseFailure</code> at input boundary | no invalid object returned |
| file open/read | <code>OSError</code> | <code>StorageFailure</code> | no report emitted by coordinator |
| output write | stream <code>OSError</code> | requires sink/application policy | partial stdout may exist |
| CLI argument grammar | argparse control flow | parser diagnostic/status | application not invoked |
| programming defect | unexpected exception | not translated as user error | process fails visibly |

The unresolved output-write row is intentional. A design review should decide whether stdout partial output is acceptable or whether rendering/writing must use a temporary file and atomic replacement.

### 10.15.17 Build metadata aligns with imports

The project declares distribution name <code>careful-ledger</code>, import package <code>ledger</code>, Python requirement, licence files, runtime dependencies if any, type marker inclusion, and script entry point. Backend configuration must map <code>src/ledger</code> into the wheel and include any resources.

Clean-wheel tests query metadata using the distribution name and import using the package name, deliberately proving the mapping.

### 10.15.18 Security review

The minimal project has no third-party runtime dependency in the illustrated core. That reduces but does not eliminate risk: build requirements execute, standard-library parsers can face hostile resource consumption, paths can escape intended directories if authority is not limited, and imported plugins would run in process.

The command should impose input size/line length policies for adversarial files, avoid echoing complete sensitive lines, run with only needed filesystem permissions, and use trusted build artefacts. If it later supports plugins, discovery and process isolation need separate threat modelling.

### 10.15.19 Evolution scenarios

- Moving <code>Transaction</code>: retain root re-export identity.
- Adding currency: revise model, parser, summary, renderer, serialised schema, and compatibility rather than add a display-only field.
- Adding CSV: implement another source adapter; keep parser/domain rules shared where representation permits.
- Adding database persistence: implement a source under the port and add lifecycle ownership at composition root.
- Streaming report output: reconsider atomicity, generator lifetime, and sink interface.
- Adding asynchronous I/O: do not make every pure/domain function async; adapt only the coordination and boundaries whose waits benefit.

### 10.15.20 Completion criteria

The package is ready for one release only when:

1. public imports and behaviours are documented;
2. domain invariants have adversarial tests;
3. every effect has an owner and exception policy;
4. the import graph is acyclic under supported paths;
5. importing does not launch or require external services;
6. sdist and wheel contain intended code, types, licences, and resources;
7. wheel installs and runs outside source in each supported environment;
8. dependency and build artefacts are reviewed and recorded;
9. CLI status/stdout/stderr contracts pass subprocess tests;
10. release version and migration notes match actual compatibility.
