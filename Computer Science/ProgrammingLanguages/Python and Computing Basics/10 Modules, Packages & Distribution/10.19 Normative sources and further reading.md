# 10.19 Normative sources and further reading

The import and packaging systems are versioned standards. The explanatory models above are grounded in the following primary specifications and should be read alongside the documentation for the minimum and maximum Python/tool versions a project supports.

1. Python Software Foundation, [The import system](https://docs.python.org/3/reference/import.html), *Python Language Reference*. Defines module search, caches, finders, loaders, packages, specifications, and relative imports.
2. Python Software Foundation, [<code>importlib</code> — The implementation of import](https://docs.python.org/3/library/importlib.html), *Python Standard Library*. Provides public machinery for dynamic imports and importer implementations.
3. Python Software Foundation, [<code>importlib.metadata</code> — Accessing package metadata](https://docs.python.org/3/library/importlib.metadata.html), *Python Standard Library*. Defines installed-distribution metadata queries and package-to-distribution mappings.
4. Python Software Foundation, [<code>importlib.resources</code> — Package resource reading, opening and access](https://docs.python.org/3/library/importlib.resources.html), *Python Standard Library*. Defines loader-aware resource access and temporary path materialisation.
5. Python Packaging Authority, [<code>pyproject.toml</code> specification](https://packaging.python.org/en/latest/specifications/pyproject-toml/). Normative project/build metadata fields.
6. Python Packaging Authority, [Core metadata specifications](https://packaging.python.org/en/latest/specifications/core-metadata/). Defines installed and distribution metadata fields and their versioned evolution.
7. Python Packaging Authority, [Version specifiers](https://packaging.python.org/en/latest/specifications/version-specifiers/). Defines public version and specifier syntax/ordering semantics.
8. Python Packaging Authority, [Dependency specifiers](https://packaging.python.org/en/latest/specifications/dependency-specifiers/). Defines requirement names, extras, constraints, direct references, and markers.
9. Python Packaging Authority, [Binary distribution format](https://packaging.python.org/en/latest/specifications/binary-distribution-format/). Defines wheel archive names, compatibility tags, layout, and installation metadata.
10. Python Packaging Authority, [Source distribution format](https://packaging.python.org/en/latest/specifications/source-distribution-format/). Defines modern source distribution filenames, archives, and metadata expectations.
11. Python Packaging Authority, [Licence expression](https://packaging.python.org/en/latest/specifications/license-expression/). Defines SPDX-based licence metadata introduced through PEP 639.
12. Python Packaging Authority, [Entry points specification](https://packaging.python.org/en/latest/specifications/entry-points/). Defines metadata-based object and plugin discovery groups.
13. D. L. Parnas, “On the Criteria To Be Used in Decomposing Systems into Modules,” *Communications of the ACM* 15(12), 1972, pp. 1053–1058. Establishes information hiding and change-oriented module decomposition.
14. W. P. Stevens, G. J. Myers, and L. L. Constantine, “Structured Design,” *IBM Systems Journal* 13(2), 1974, pp. 115–139. Develops cohesion and coupling as system-structure criteria.
15. J. H. Saltzer and M. D. Schroeder, “The Protection of Information in Computer Systems,” *Proceedings of the IEEE* 63(9), 1975, pp. 1278–1308. Provides least privilege and other protection principles relevant to import/build authority.
16. K. Thompson, “Reflections on Trusting Trust,” *Communications of the ACM* 27(8), 1984, pp. 761–763. Demonstrates why trust in source alone is insufficient when compilers and build chains can alter executable artefacts.
