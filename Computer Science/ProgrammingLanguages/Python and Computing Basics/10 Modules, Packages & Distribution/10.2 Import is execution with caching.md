# 10.2 Import is execution with caching

The statement

```python
import ledger.model
```

does not textually paste another file into the current one. The import system conceptually:

1. resolves the requested name through finders and the package context;
2. obtains a module specification describing how it can be loaded;
3. creates a module object when needed;
4. places it in `sys.modules` early enough to manage recursive imports;
5. executes its top-level code in its module namespace;
6. returns or binds the appropriate module object;
7. reuses the cached module on later ordinary imports in the same process.

`sys.modules` is a mapping from loaded module names to module objects. It is a runtime cache and registry, not a list of installed distributions. Removing or mutating entries is advanced and can create multiple module objects or inconsistent references.

### Worked example 10.1 — Top-level effects happen once per ordinary process import

`observed.py`:

```python
print("executing observed")
value = 42
```

`main.py`:

```python
import observed
import observed

print(observed.value)
```

A fresh ordinary run prints `executing observed` once and then 42. The second import finds the cached module. This is not a language promise that code can never be re-executed: explicit reload, separate module names, separate processes, test machinery, and custom import hooks can change circumstances. Top-level code should nevertheless be designed as import-time execution.

Import-time network calls, file mutation, expensive computation, or process startup create hidden effects for every importer. Prefer definitions and small deterministic registration; place application actions behind functions and entry points.

### 10.2.1 Import has a name, context, and search machinery

An import request is not merely a path lookup. It contains a module name, possibly a package context for resolving relative dots, and for submodules a parent package search path. The import machinery uses registered **finders** to obtain a **module specification** and a **loader** to create and execute the module when necessary.

The public <code>importlib</code> package exposes much of this machinery. Ordinary code should use <code>import</code> statements for statically known dependencies and <code>importlib.import_module</code> for deliberately dynamic names:

~~~python
from importlib import import_module


module = import_module("ledger.reporting")
report = module.build_report
~~~

Dynamic import is still code execution. If the string comes from untrusted input, an allowlist must decide which modules may execute; validating only that the text resembles a dotted name is not an authority policy.

### 10.2.2 <code>sys.modules</code> defines ordinary module identity

The cache maps fully qualified import names to module objects:

~~~python
import sys
import ledger.model


assert sys.modules["ledger.model"] is ledger.model
~~~

Ordinary repeated import under the same name reuses this object. Existing references do not consult the cache again on every attribute access. Replacing <code>sys.modules["ledger.model"]</code> later does not transform the module object already held by <code>ledger.model</code> or other variables.

The cache key matters. If the same source is made importable under two different names, it can execute twice and produce distinct class objects, registries, and exception types. Objects created from the two nominally identical class definitions may fail <code>isinstance</code> checks against one another.

### 10.2.3 Early cache insertion breaks recursive creation, not cycles of knowledge

Before a loader executes a new module’s body, import machinery normally places its module object in <code>sys.modules</code>. If execution recursively requests the same name, it can receive that in-progress object instead of allocating another indefinitely.

This solves recursion of module *creation*. It does not guarantee that requested attributes have already been assigned. A circular importer can observe the module after its first five statements but before its sixth. The resulting object is real and cached, yet **partially initialised**.

### 10.2.4 Failed imports do not imply global rollback

When execution of a newly loading module fails, import machinery ordinarily removes the failing module’s cache entry. Side effects already performed are not generally undone, and modules successfully imported as consequences can remain cached.

Suppose <code>plugin.py</code> registers a callback, imports <code>support</code>, then raises. A second import may execute <code>plugin.py</code> again and register a duplicate callback, while reusing the already loaded <code>support</code>. Import is not a transaction spanning the process.

Robust import-time registration should validate before commit, be idempotent under explicit repeated execution when feasible, or provide rollback around fallible later steps. The simplest policy is to defer mutable registration to an explicit application assembly phase.

### Worked example 10.1A — Observe retained side effects after failure

<code>registry.py</code>:

~~~python
entries: list[str] = []
~~~

<code>broken_plugin.py</code>:

~~~python
import registry

registry.entries.append("attempt")
raise RuntimeError("definition failed")
~~~

<code>probe.py</code>:

~~~python
import registry

for _ in range(2):
    try:
        import broken_plugin
    except RuntimeError:
        pass

print(registry.entries)
~~~

In an ordinary environment, each failed attempt can append, producing two entries. The failing module is retried because its incomplete cache entry was removed; <code>registry</code> remains successfully cached with mutated state.

### 10.2.5 A module specification describes loading

A module’s <code>__spec__</code> ordinarily refers to a <code>ModuleSpec</code> describing facts such as its name, loader, origin, parent package relationship, and submodule search locations where applicable.

~~~python
import importlib.util


spec = importlib.util.find_spec("ledger.model")
if spec is None:
    raise RuntimeError("ledger.model cannot be found")

print(spec.name)
print(spec.loader)
print(spec.origin)
~~~

Finding a specification can import the parent package for a submodule and can therefore cause effects. An origin may be <code>None</code> or a non-filesystem description for namespace, built-in, frozen, or custom-loaded modules. Do not assume every module has a meaningful <code>__file__</code>.

### 10.2.6 Meta-path finders and path-based discovery

Python consults finder objects in <code>sys.meta_path</code>. Built-in machinery can recognise built-in modules, frozen modules, and modules found through import paths. For path-based imports, path hooks and importer caches translate entries such as directories or archives into finders.

A finder answers “can I supply a specification for this fully qualified name in this context?” A loader answers “how is the module object created and executed?” Modern loader protocols commonly expose <code>create_module</code> and <code>exec_module</code>. The import system coordinates cache insertion and metadata.

Custom finders can load code from databases, encrypted stores, generated sources, or remote systems. Doing so broadens the trusted computing base and complicates debugging, caching, reproducibility, and audit. Most applications should not replace ordinary file/package loading.

### 10.2.7 <code>sys.path</code> is search configuration, not a dependency manifest

For top-level path-based imports, <code>sys.path</code> contains search entries assembled from launch context, interpreter installation, environment configuration, virtual environment, and site customisation. Exact entries depend on platform and invocation.

~~~python
import sys


for entry in sys.path:
    print(repr(entry))
~~~

The first matching candidate can determine what executes. This makes writable early entries security-sensitive and explains local shadowing. <code>sys.path</code> does not record which distribution declared a dependency, which version should be installed, or why an entry is trusted.

Editing it within library modules is usually an architectural defect. It makes import meaning depend on execution order and current filesystem layout. Configure installation, invocation, or a controlled application entry point instead.

### 10.2.8 Parent packages are loaded before submodules

Importing <code>ledger.model</code> requires a <code>ledger</code> package context. The parent package is imported first if necessary. Its <code>__init__.py</code>, for an ordinary package, therefore executes before the child module.

After the child loads, import machinery ordinarily binds it as an attribute of its parent package, so <code>ledger.model</code> refers to the submodule. Package <code>__init__.py</code> can also define or replace names, which makes overly elaborate initialisation a source of ambiguity and cycles.

### 10.2.9 Import locking coordinates concurrent attempts

Multiple threads can attempt imports concurrently. The import implementation coordinates module loading so one name is not ordinarily executed simultaneously as two independent initialisations in the same interpreter. This does not make arbitrary module body effects thread-safe, nor does it make imports across processes share state.

A module can release control, import other modules, start threads, or expose itself through external registries while only partly initialised. Do not use the existence of import locks as a substitute for lifecycle design.

### 10.2.10 Bytecode caches are an optimisation layer

For eligible source modules, Python may cache compiled bytecode in <code>__pycache__</code> files. A later process can avoid reparsing and recompiling unchanged source under applicable invalidation rules. The module body still executes to create runtime bindings.

Deleting bytecode caches should not change correct program semantics. A stale or unwritable cache can affect startup performance or diagnostics, but reinstalling dependencies because a module prints twice misunderstands the execution/cache distinction.

Bytecode is Python-version and implementation qualified, not a portable long-term source substitute. Chapter 15 examines bytecode itself.

### 10.2.11 Reload re-executes into an existing module context

<code>importlib.reload(module)</code> recompiles/re-executes a module using its specification while retaining the module object and generally its namespace dictionary. Names rebound by new code change; old names not overwritten may remain. External references bound earlier remain external references.

~~~python
from importlib import reload

import settings
from settings import Configuration


old_class = Configuration
reload(settings)
new_class = settings.Configuration

print(old_class is new_class)
~~~

If execution creates a new class, <code>old_class</code> and instances already made from it remain related to the old class object. Existing <code>from settings import Configuration</code> bindings are not automatically rebound. Registries may contain both generations; extension modules may not support meaningful repeated initialisation.

Reload is useful in controlled interactive development, not a general deployment update protocol. Application hot-reload needs explicit state migration and compatibility boundaries.

### 10.2.12 Import-time type-only dependencies

Annotations can create import cycles even when runtime computation does not need the imported class. Deferred annotations and <code>typing.TYPE_CHECKING</code> can separate static-only imports:

~~~python
from __future__ import annotations

from typing import TYPE_CHECKING

if TYPE_CHECKING:
    from .model import Transaction


def describe(transaction: Transaction) -> str:
    return str(transaction)
~~~

Static checkers treat the guarded import as available; at runtime <code>TYPE_CHECKING</code> is false. This is appropriate only because the function body does not require the class object. Runtime introspection of annotations may need explicit resolution and imports, and hiding a genuine architectural cycle behind the guard is not a repair.

### 10.2.13 Import cost belongs to startup architecture

Every imported module consumes discovery, possible bytecode validation/compilation, body execution, and retained objects. A command that imports a large optional stack before parsing <code>--help</code> can have poor startup latency. Measure import profiles and move optional heavy dependencies behind the operation that needs them when doing so preserves clear failures and contracts.

Lazy import introduces its own complexity: failures occur later, first-use latency moves into an operation, thread races and partial setup need policy, and static tools see less direct dependency structure. Optimise measured startup paths rather than distributing imports unpredictably through function bodies.

### 10.2.14 Import invariants

A well-behaved library module should ordinarily satisfy:

- import either completes with a coherent public namespace or raises a meaningful exception;
- importing does not launch the application;
- import does not require unrelated network availability or mutable current-directory state;
- repeated ordinary import through the canonical name reuses compatible module state;
- public objects do not depend on a second alias import of the same source;
- optional dependencies fail at the capability boundary with actionable diagnostics;
- imports do not mutate unrelated global state without an explicit registry contract;
- import ordering among independent modules does not change semantics.

> **Common misconception — “Importing twice executes twice unless guarded.”**  
> The import cache normally prevents re-execution under the same canonical name within one interpreter. Guards inside a module do not create that cache behaviour.

> **Common misconception — “A failed import leaves no trace.”**  
> The failing cache entry is normally removed, but completed side effects and successfully imported dependencies can remain.
