# 10.3 Import statement forms and bindings

```python
import ledger.model
```

binds name `ledger` in the importing namespace; `ledger.model` becomes accessible as an attribute after successful import.

```python
from ledger import model
```

binds local name `model` to the resolved object.

```python
from ledger.model import Transaction
```

binds local name `Transaction` to the object found under that attribute at import time. Later rebinding of `ledger.model.Transaction` does not automatically rebind the importing module’s local name.

Aliases change local spelling:

```python
import ledger.reporting as reporting
```

They do not rename the actual module in the import registry.

Wildcard import, `from module import *`, imports names selected by the module’s `__all__` or by fallback rules. It obscures name origin, can overwrite bindings, and makes static reasoning difficult. It is primarily suitable for carefully designed interactive or package-export contexts, not ordinary internal dependencies.

### Worked example 10.2 — Imported binding versus module lookup

`settings.py`:

```python
rate = 2
```

`consumer.py`:

```python
import settings
from settings import rate

settings.rate = 3
print(settings.rate)
print(rate)
```

Output is 3 then 2. The `from` import bound local `rate` to the earlier integer object. Assignment later changed the attribute binding in the module namespace; it did not reach into every importing namespace.

### 10.3.1 Import both loads and binds

An import statement has two distinguishable effects:

1. ensure the requested module objects are found and loaded under import-system rules;
2. bind one or more names in the namespace where the statement executes.

Caching concerns the first effect. Scope and alias syntax govern the second. Repeating an import inside a function can reuse the cached module while performing a local binding on every call.

~~~python
def calculate() -> float:
    import math
    return math.sqrt(81.0)
~~~

Here <code>math</code> is a local name because the import statement binds inside the function. The module is not re-executed on every call under normal caching, but the local binding operation still occurs.

### 10.3.2 Dotted import without alias binds the top-level name

After:

~~~python
import ledger.reporting
~~~

the local binding is ordinarily <code>ledger</code>, not <code>reporting</code>. Successful loading makes the child available through the package, so the caller writes <code>ledger.reporting</code>. By contrast:

~~~python
import ledger.reporting as reporting
~~~

binds local <code>reporting</code> directly to the submodule object. The alias changes only the importing namespace; <code>reporting.__name__</code> remains its canonical module name.

### 10.3.3 From-import binds a snapshot reference, not a live path

At import time:

~~~python
from settings import rate
~~~

Python obtains the object currently exposed as <code>settings.rate</code> and binds that object locally as <code>rate</code>. If the source module later rebinds its attribute, the two namespaces diverge. If the object itself is mutable and either side mutates it, both references can still observe the same object.

~~~python
# settings.py
options = ["safe"]
~~~

~~~python
import settings
from settings import options

options.append("verbose")
assert settings.options == ["safe", "verbose"]

settings.options = []
assert options == ["safe", "verbose"]
~~~

Mutation follows object identity; rebinding changes one namespace edge. Import introduces no special sharing model beyond the reference semantics of Chapter 5.

### 10.3.4 Import location determines monkeypatch location

Suppose <code>service.py</code> contains:

~~~python
from clock import now


def timestamp() -> float:
    return now()
~~~

Replacing <code>clock.now</code> after <code>service</code> imported it does not replace <code>service.now</code>. A test must patch the name looked up by the code under test: <code>service.now</code>. If <code>service</code> instead used <code>import clock</code> and called <code>clock.now()</code>, patching <code>clock.now</code> would affect that lookup.

This is not a testing-library peculiarity. It follows directly from which namespace contains the binding evaluated at call time. Dependency injection can avoid global patching and make the collaborator explicit.

### 10.3.5 Imports obey ordinary scope rules

An import at module top level creates a global binding in that module. An import inside a function creates a local binding unless declared otherwise. A conditional branch may leave the name unbound on paths where it did not execute.

~~~python
def formatter(use_json: bool):
    if use_json:
        import json
    return json.dumps({"ready": True})
~~~

Calling with false raises because local <code>json</code> was never bound. Static unconditional imports at module top usually make dependencies and failures clearest. Local or conditional imports are justified for optional capabilities, cycle management with explicit rationale, or measured startup cost—not as arbitrary style.

### 10.3.6 Catch optional-dependency failure narrowly

This broad pattern is defective:

~~~python
try:
    import optional_backend
except Exception:
    optional_backend = None
~~~

It treats syntax errors, runtime defects, transitive dependency failures, and even some interruption-like conditions as “not installed.” A narrower approach catches the import failure whose absence is actually optional and checks its identity where necessary:

~~~python
try:
    import optional_backend
except ModuleNotFoundError as error:
    if error.name != "optional_backend":
        raise
    optional_backend = None
~~~

If <code>optional_backend</code> exists but its body imports a missing <code>backend_dependency</code>, <code>error.name</code> differs and the real broken installation propagates. Even this logic should be placed near an explicit capability boundary with an actionable message.

### 10.3.7 <code>ImportError</code> and <code>ModuleNotFoundError</code>

<code>ModuleNotFoundError</code> is a subclass of <code>ImportError</code> used when a module cannot be found, including certain <code>None</code> cache cases. <code>ImportError</code> can also report failure to import a requested name from an existing module.

Do not assume every <code>ImportError</code> means “install a package.” Causes include a misspelled import name, incompatible version, circular initialisation, local shadowing, platform-specific extension load failure, or a source module explicitly raising the exception. Diagnose the resolved origin and traceback.

### 10.3.8 Aliases should reduce ambiguity without erasing provenance

Conventional aliases such as a well-known short library name can improve readability in domains where their meaning is established. An alias like <code>x</code> for an infrastructure module hides provenance. Renaming two different <code>config</code> modules as <code>application_config</code> and <code>database_config</code> can clarify ownership.

Avoid aliases that make a module look like a class or function, or that shadow built-ins and local domain names. Import readability is part of dependency documentation.

### 10.3.9 Importing a symbol couples to its defining interface

<code>from package import Name</code> may retrieve a re-export from the package façade, not necessarily a definition physically written in <code>package/__init__.py</code>. The supported import path is whichever path the package documents. Importing deeper internal paths because they reveal implementation can forfeit compatibility.

Conversely, a package’s convenient top-level API can import a large dependency graph. Internal performance-sensitive code may choose a documented submodule path when the project explicitly supports it. Publicness and cost are contractual facts, not deduced solely from path depth.

### 10.3.10 Wildcard import performs a runtime selection

For <code>from module import *</code>, the source module’s <code>__all__</code>, when present, supplies names to retrieve. Without it, fallback selection generally excludes names beginning with an underscore. The operation binds into the receiving namespace and can replace existing names.

~~~python
# palette.py
__all__ = ["RED", "BLUE"]

RED = "#ff0000"
BLUE = "#0000ff"
_CACHE = {}
~~~

<code>__all__</code> is a sequence of strings naming exports; it does not hold the exported objects themselves. Listing an absent name causes import failure when retrieval is attempted. It does not prevent explicit access to unlisted attributes.

Wildcard import is prohibited inside function scope by the language and is difficult for static readers because bindings depend on another module’s runtime state. A curated interactive namespace or package façade is its main defensible use.

### 10.3.11 Importing from a package can seek a submodule

In <code>from ledger import reporting</code>, import machinery can attempt to find the <code>ledger.reporting</code> submodule if the attribute is not already supplied in the expected way. This makes package imports more than a simple dictionary lookup. Package initialisation and submodule loading can interact, especially during cycles.

Do not rely on accidental prior imports to populate package attributes. Explicitly import and re-export supported submodules or symbols in the package API where that is the contract.

### 10.3.12 Dynamic names move errors from analysis to runtime

~~~python
from importlib import import_module


def load_codec(name: str):
    module = import_module(f"codecs_{name}")
    return module.Codec()
~~~

This design conceals the allowed set, dependencies, and required interface. A safer plugin loader maps validated identifiers to known entry points or obtains installed entry-point metadata, then validates the loaded object’s contract. Dynamic import should be an intentional extensibility boundary with error isolation and authority review.

### 10.3.13 Prefer module qualification when provenance matters

Compare:

~~~python
from decimal import Decimal, ROUND_HALF_EVEN
~~~

with:

~~~python
import decimal

amount = decimal.Decimal("1.25")
~~~

Direct symbol imports can be concise; qualified module access makes origin and patch location explicit. There is no universal rule. Frequently used domain types may deserve direct import, while operations with common names such as <code>open</code>, <code>parse</code>, or <code>load</code> often benefit from qualification.

> **Common misconception — “From-import copies a value.”**  
> It binds another reference to the current object. Later object mutation can be shared; later source-module rebinding is not propagated.

> **Common misconception — “An import inside a function reloads the module every call.”**  
> It normally reuses the cached module and creates a local binding. Deferred failure and hidden dependency remain design concerns.
