# 10.4 Absolute and relative imports

An **absolute import** names a module from the import-system root:

```python
from ledger.model import Transaction
```

An **explicit relative import** uses leading dots from the current package:

```python
from .model import Transaction
from ..shared import Clock
```

One dot means the current package; additional dots move through parent packages under the import rules. Relative imports require a recognised package context. Running an internal module file directly can deprive it of that context, producing the familiar “attempted relative import with no known parent package” failure.

Launch package code through its package entry point:

```text
python -m ledger
```

rather than:

```text
python src/ledger/__main__.py
```

The `-m` route asks the import system to locate the module and establishes package metadata consistently.

Absolute imports make cross-package origin explicit. Relative imports can make internal refactoring and package cohesion clear. Choose a project policy and do not manipulate `sys.path` inside modules to conceal a broken installation or launch model.

### 10.4.1 “Absolute” is relative to configured import roots

An absolute name begins with a top-level module name rather than a filesystem root. <code>ledger.model</code> is resolved by import finders over configured locations, built-ins, archives, or custom sources. It does not necessarily mean <code>/ledger/model.py</code>, and a leading operating-system slash is not valid Python module syntax.

The same absolute name can resolve to different code in different virtual environments or launch configurations. Reproducibility therefore requires controlled distributions and search paths, not merely absolute import spelling.

### 10.4.2 Relative dots use package identity

Within <code>ledger.reporting.summary</code>:

- <code>from . import formatters</code> refers from current package <code>ledger.reporting</code>;
- <code>from .formatters import render</code> refers to a sibling submodule or exported attribute;
- <code>from ..model import Transaction</code> moves to parent package <code>ledger</code>;
- <code>from ...shared import Clock</code> attempts another parent level.

The first dot means “current package,” and each additional dot moves one level upward. A request beyond the top-level package fails. Relative syntax is supported in the <code>from</code> form; <code>import .model</code> is not the corresponding grammar.

### 10.4.3 <code>__package__</code> supplies relative context

Relative resolution uses package metadata, ordinarily based on <code>__package__</code> and the module specification. An imported module <code>ledger.reporting</code> has a recognised package parent. A source file launched directly as a bare script commonly has <code>__name__ == "__main__"</code> and no suitable package context, even if it physically resides inside a directory containing <code>__init__.py</code>.

Filesystem containment alone does not assign runtime package identity. The import system must load or execute the module under that identity.

### Worked example 10.2A — One file, two execution identities

Suppose <code>ledger/probe.py</code> contains:

~~~python
print(__name__)
print(__package__)
print(__spec__)
~~~

Direct invocation:

~~~text
python ledger/probe.py
~~~

typically executes it as top-level <code>__main__</code> with no package specification. Module invocation from the project’s configured import root:

~~~text
python -m ledger.probe
~~~

still uses <code>__name__ == "__main__"</code> for entry execution but supplies package/specification context identifying <code>ledger</code> as the parent. Exact displayed object representations vary, but the relative-import capability difference is contractual.

### 10.4.4 Entry execution can create a second module identity

Code run as <code>__main__</code> is stored under that name. If it or another module subsequently imports its canonical name, the same source may execute again as a distinct module object.

For example, directly executing a module that defines <code>class Token</code>, then importing that file canonically, can produce <code>__main__.Token</code> and <code>package.module.Token</code> as distinct classes. Instances fail identity-based nominal relationships across them.

Keep substantial definitions in canonically importable modules and make entry modules thin coordinators. Then <code>__main__</code> imports the canonical implementation rather than other modules importing definitions from <code>__main__</code>.

### 10.4.5 <code>-m</code> locates before executing

The <code>-m</code> command-line option asks Python to locate a module through the import system and execute its code as the top-level environment. For a package name, Python executes its <code>__main__</code> submodule. This preserves package context and tests that the module is discoverable through configured import roots.

It does not imply the distribution is installed globally; the current environment and search path still govern discovery. Nor does it make relative filesystem data paths safe. A module should use package-resource APIs for packaged data and explicit user paths for external data.

### 10.4.6 Absolute and relative imports encode different stability assumptions

An absolute internal import:

~~~python
from ledger.model import Transaction
~~~

asserts that the package’s top-level public identity is <code>ledger</code>. A relative import:

~~~python
from .model import Transaction
~~~

asserts a sibling relationship within the current package. If the whole package is vendored or renamed, relative internal edges may require fewer edits. If code moves to another subpackage level, dot depth changes.

For imports crossing architectural package boundaries, absolute names usually reveal provenance. For tightly cohesive internal siblings, explicit relative imports can make locality evident. Consistency matters because a mixture can make the same dependency appear to be two concepts.

### 10.4.7 Relative imports do not prevent cycles

Changing <code>from ledger import model</code> to <code>from . import model</code> changes resolution spelling, not dependency direction. If <code>model</code> imports the caller during top-level execution, the cycle remains. Resolve circular ownership structurally.

### 10.4.8 Running an internal file directly is not a package test

Developers sometimes insert the parent directory into <code>sys.path</code> so <code>python package/internal.py</code> works. This creates a launch mode different from installed use and can import sibling files as top-level modules under wrong names.

Use one of these patterns instead:

- execute a supported package or module entry with <code>python -m ...</code>;
- install the distribution into the active environment;
- expose a declared console-script entry point;
- keep standalone maintenance scripts outside the import package and make them import its public API.

### 10.4.9 Test runners can disguise package mistakes

A test runner may add the repository root to <code>sys.path</code>, import tests as packages, or use an editable installation. A test can pass while a built wheel omits the package or resolves different modules. Record <code>module.__file__</code> during diagnosis and run clean-wheel tests outside the repository.

Do not make tests rely on ambiguous relative imports between test files. Shared fixtures and helpers should have an explicit package/module structure or be provided through the testing framework’s supported discovery model.

### 10.4.10 Refactoring safely across package boundaries

When moving a public object:

1. choose and document the canonical public import path;
2. preserve a compatibility re-export at the old supported path for a deprecation window;
3. update internal imports toward the canonical path without creating a façade cycle;
4. test object identity across old and new imports;
5. ensure pickled or dynamically referenced qualified names have an evolution plan;
6. test type-checker stubs and documentation references;
7. remove the old path only under the versioning policy.

Simply copying the class definition to a new module creates two class identities. Re-export the same class object during migration.

### 10.4.11 Diagnosing a resolution surprise

Collect:

~~~python
import importlib.util
import sys


name = "ledger.model"
spec = importlib.util.find_spec(name)
print("spec:", spec)
print("cached:", sys.modules.get(name))

if name in sys.modules:
    module = sys.modules[name]
    print("file:", getattr(module, "__file__", None))
    print("package:", getattr(module, "__package__", None))
    print("loader:", getattr(module, "__loader__", None))
~~~

Perform this within the actual failing environment and invocation. A shell, notebook kernel, test worker, IDE, and deployed service may use different interpreters and search paths.

> **Common misconception — “A directory with <code>__init__.py</code> makes every direct file execution package-aware.”**  
> Package identity comes from how the import system loads or executes the module, not only its physical location.

> **Common misconception — “Absolute imports always select the project’s own package.”**  
> They select the first matching module under the active import machinery. Environment control and origin inspection establish which code was found.
