# 10.5 `__name__` and entry execution

Every module has a `__name__` attribute. When imported normally, it contains the module’s import name. Code selected as the top-level entry environment receives `__name__ == "__main__"`.

```python
def main() -> int:
    print("application runs")
    return 0


if __name__ == "__main__":
    raise SystemExit(main())
```

This guard distinguishes definition/import from application execution. Importing the module creates `main` but does not call it through the guarded path. Executing the file as the entry script calls `main` and turns its integer result into process status.

The idiom is not a security boundary and does not prevent all import effects. Every statement outside the guarded suite still executes on import. Nor does it make the module automatically distributable; packaging metadata and installation remain separate.

`__main__.py` gives a package or archive an executable module. `python -m ledger` locates and executes `ledger.__main__` as the entry module while the package remains importable.

### 10.5.1 <code>__main__</code> names the top-level execution environment

Python assigns <code>__name__ == "__main__"</code> to the top-level code environment, including code launched from a file, with <code>-m</code>, with <code>-c</code>, from standard input, or interactively. It does not mean that the file is literally named <code>__main__.py</code>.

The active top-level module is ordinarily available as <code>sys.modules["__main__"]</code>. Importing a module whose canonical name is <code>application.main</code> is a separate operation and normally sets that module’s <code>__name__</code> to <code>application.main</code>.

### 10.5.2 The guard tests execution role

~~~python
if __name__ == "__main__":
    raise SystemExit(main())
~~~

The condition asks whether this module currently occupies the top-level execution role. It does not ask whether the file was “opened by a user,” whether a function is called main, or whether the code is safe to execute.

Everything needed merely to define <code>main</code> remains outside the guard and runs on import. Keep that definition phase free of application-start effects.

### 10.5.3 Return values become process status through <code>SystemExit</code>

Operating systems expose a small integer-like **exit status** from a process. By convention, zero denotes success and nonzero denotes a class of failure. <code>raise SystemExit(status)</code> asks Python to terminate normally with the supplied status after ordinary cleanup paths.

~~~python
def main() -> int:
    try:
        run_application()
    except ConfigurationError as error:
        print(f"configuration error: {error}", file=sys.stderr)
        return 2
    return 0
~~~

Passing a non-integer object such as a string to <code>SystemExit</code> can print it and produce a failure status under interpreter rules; returning explicit integers is clearer for command contracts. A Boolean is an integer subtype but obscures status meaning.

Do not call <code>sys.exit</code> deep inside reusable domain logic. It raises <code>SystemExit</code>, crossing normal application boundaries and making the code difficult to compose. Raise a domain exception or return a result; translate to status at the entry point.

### 10.5.4 Separate argument parsing, coordination, and computation

A testable command architecture has layers:

~~~python
from collections.abc import Sequence


def calculate_total(values: Sequence[int]) -> int:
    return sum(values)


def run(arguments: Sequence[str]) -> int:
    try:
        values = [int(argument) for argument in arguments]
    except ValueError as error:
        print(f"invalid integer: {error}", file=sys.stderr)
        return 2

    print(calculate_total(values))
    return 0


def main() -> int:
    return run(sys.argv[1:])
~~~

<code>calculate_total</code> is pure. <code>run</code> accepts explicit arguments and owns textual boundary translation. <code>main</code> adapts process-global <code>sys.argv</code>. Tests can call <code>run(["2", "3"])</code> while capturing streams, or move streams into explicit parameters for still narrower effects.

### 10.5.5 Standard output and standard error have different contracts

Commands commonly write ordinary machine- or user-consumable results to standard output and diagnostics to standard error. This permits shell pipelines to consume valid output without mixing error text.

The distinction should be tested. A command returning status zero while printing a traceback to output violates likely automation expectations even if a human can read it. Command-line interface stability includes status codes, stream selection, encodings, line formats, and partial-output policy.

### 10.5.6 <code>__main__.py</code> is a package adapter

A thin package entry module can import canonical application code:

~~~python
# ledger/__main__.py
from .cli import main


if __name__ == "__main__":
    raise SystemExit(main())
~~~

<code>python -m ledger</code> locates <code>ledger</code>, initialises the package, then executes this submodule as top-level code. Keeping implementation in <code>ledger.cli</code> avoids other modules importing definitions from <code>__main__</code> and acquiring a second execution identity.

### 10.5.7 Installed console scripts are metadata-driven adapters

A project can declare:

~~~toml
[project.scripts]
careful-ledger = "ledger.cli:main"
~~~

Installation tooling creates an environment-appropriate command wrapper. Invoking <code>careful-ledger</code> imports <code>ledger.cli</code>, retrieves <code>main</code>, calls it, and translates the result according to the generated entry-point convention.

The wrapper is generated at installation; merely adding metadata does not create a command in an environment until installed. Renaming or removing the target callable without rebuilding/reinstalling leaves a broken wrapper.

Console-script and <code>python -m ledger</code> entry paths should normally call the same implementation so they do not drift in status, arguments, or effects.

### 10.5.8 Import-safe does not mean side-effect-free

A module may legitimately create immutable constants, compile regular expressions, define classes, or register a small declared adapter during import. “Import-safe” means those effects satisfy an explicit, deterministic loading contract and do not unexpectedly launch work, prompt for input, alter user files, or require external service availability.

There is no absolute ban on computation. The relevant questions are cost, failure mode, authority, repeatability, and whether every importer consented to the effect.

### 10.5.9 The guard is required for some process-spawning patterns

Forward reference: Chapter 14 formally introduces multiprocessing, in which work runs in separate operating-system processes. Under start methods that import the entry module in a child process, unguarded top-level process creation can recursively create more processes. Placing application launch under the <code>__main__</code> guard prevents imported child setup from relaunching the parent entry path.

This does not mean every function needed by child processes belongs inside the guard. Importable worker functions should remain at module scope; only initiating calls belong behind the execution-role boundary.

### 10.5.10 <code>runpy</code> executes modules under controlled naming

The standard <code>runpy</code> module underlies related execution use cases and can run a module or path while establishing a special globals dictionary. It is not an isolation mechanism: code executes in the current process and can mutate shared state. Thread-safety and alterations to <code>sys</code> state need attention under its documented options.

For ordinary applications, subprocess execution supplies a clearer process boundary. <code>runpy</code> is useful for tooling that intentionally reproduces Python’s script/module execution semantics.

### 10.5.11 Entry-point error policy

An entry point should classify failures:

- anticipated user/input errors: concise diagnostic and stable nonzero status;
- unavailable optional capability: actionable installation/configuration message;
- interrupted operation: cleanup and a status consistent with platform policy;
- internal defect: nonzero status and diagnostic evidence, possibly a traceback under debug configuration;
- partial external write: explicit warning and recovery instructions.

Do not catch <code>BaseException</code> and report success. <code>KeyboardInterrupt</code>, <code>SystemExit</code>, and process-control conditions have specialised meanings. Catch only failures the boundary can translate responsibly.

### 10.5.12 Entry-point tests

Test at three levels:

1. pure computation with ordinary unit tests;
2. coordinator function with explicit arguments and injected streams/dependencies;
3. installed command in a subprocess, asserting status, stdout, stderr, current-directory independence, and environment behaviour.

The subprocess test proves the generated wrapper or <code>-m</code> route, interpreter selection, import installation, and process-status integration. Directly calling <code>main()</code> cannot prove all of those.

> **Common misconception — “The name guard makes a file both library and application automatically.”**  
> It prevents one guarded launch path during import. Public API design, import-time effects, package context, and distribution entry points remain separate.

> **Common misconception — “Returning 1 from <code>main</code> exits with status 1.”**  
> A normal Python function return is just a value. The entry adapter must pass it to <code>SystemExit</code> or an equivalent wrapper.
