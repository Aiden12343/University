# 10.6 Circular imports

A **circular import** occurs when modules depend on one another during import initialisation. Because a module is placed in `sys.modules` before its top-level execution completes, another module may observe it in a partially initialised state.

`a.py`:

```python
from b import value_b
value_a = "A"
```

`b.py`:

```python
from a import value_a
value_b = "B"
```

Importing `a` begins execution and immediately imports `b`. `b` imports `a`, but the cached `a` object has not yet executed `value_a = "A"`. Retrieval fails from the partially initialised module.

Moving imports inside functions can defer the cycle but may merely hide an architectural problem. Stronger repairs include:

- moving shared abstractions into a lower-level module;
- reversing a dependency through an injected interface;
- merging modules that are one responsibility;
- separating import-time registration from runtime collaboration;
- importing modules rather than early-bound attributes where appropriate.

A dependency graph should ordinarily be directed from higher policy towards lower stable mechanisms without cycles. Real plugin systems and mutual type references require deliberate patterns, but accidental circles indicate unclear ownership.

### 10.6.1 A cycle is both structural and temporal

In a directed import graph, a cycle exists when a path returns to its starting module. Graph theory calls a maximal mutually reachable group a **strongly connected component**. Every module in such a component depends, directly or indirectly, on every other for loading.

The runtime failure depends on timing. A cycle can appear to work if neither side retrieves a not-yet-bound name during initialisation, then fail after an innocent statement reorder. Structural cyclicity creates temporal coupling even when one current execution order succeeds.

### 10.6.2 From-import often demands the value too early

In the original <code>a.py</code>/<code>b.py</code> example, <code>from a import value_a</code> requires the attribute while <code>a</code> is incomplete. Replacing it with <code>import a</code> can defer attribute retrieval until a later function call:

~~~python
# b.py
import a


def describe() -> str:
    return a.value_a
~~~

If <code>describe</code> is not called until both imports complete, this variant may work. It has not removed the cycle; it has moved the temporal requirement. The graph remains harder to initialise, test, and refactor.

### 10.6.3 Error text identifies partial initialisation, not necessarily root ownership

Modern Python often reports that an attribute cannot be imported from a partially initialised module and suggests a circular import. The named line is where the temporal contradiction surfaced, not necessarily where architectural responsibility is misplaced.

Follow the full traceback and construct the import chain. Repeatedly moving the failing import downward can hide the symptom without clarifying which module should own the shared concept.

### 10.6.4 Package façades can create invisible cycles

Suppose <code>ledger/__init__.py</code> re-exports from <code>reporting</code>, while <code>reporting.py</code> writes <code>from ledger import Transaction</code>. Importing the package begins the façade, enters <code>reporting</code>, then asks the still-running façade for <code>Transaction</code>. A cycle exists even though no source line names <code>ledger.__init__</code> explicitly.

Internal modules should often import the lower-level defining module directly, while external callers use the public façade:

~~~python
# inside ledger/reporting.py
from .model import Transaction
~~~

This does not universally prohibit internal façade imports, but it prevents the root package initializer from becoming a hub through which every internal edge passes.

### 10.6.5 Extract a lower-level shared abstraction

Suppose <code>orders.py</code> imports <code>payments.py</code> to call a charger, while <code>payments.py</code> imports <code>Order</code> for type and state access. The responsibilities can be separated:

~~~text
orders.py   -> contracts.py
payments.py -> contracts.py
checkout.py -> orders.py
checkout.py -> payments.py
~~~

<code>contracts.py</code> can define value types and protocols needed by both. <code>checkout.py</code> coordinates an order and a payment adapter. The cycle becomes two inward edges plus one higher-level composition point.

Extraction is correct only if the new module is cohesive. A <code>common.py</code> dumping ground that every module imports creates a low-level dependency magnet and may eventually recreate cycles.

### Worked example 10.2B — Invert a concrete dependency

Defective <code>reporting.py</code>:

~~~python
from .database import Database


def build_report(database: Database) -> str:
    return str(database.load_rows())
~~~

If <code>database.py</code> imports report schemas from <code>reporting.py</code>, the modules cycle. Place the requirement with the policy:

~~~python
# reporting.py
from typing import Protocol


class RowSource(Protocol):
    def load_rows(self) -> list[tuple[str, int]]: ...


def build_report(source: RowSource) -> str:
    return "\n".join(f"{name}: {amount}" for name, amount in source.load_rows())
~~~

~~~python
# database.py
from .reporting import RowSource


class DatabaseRowSource:
    def load_rows(self) -> list[tuple[str, int]]:
        # Real database interaction omitted.
        return []
~~~

The adapter depends on the policy-owned protocol, while an application module imports both and injects the adapter. Runtime calls can flow from reporting to the adapter without reporting importing its concrete implementation.

### 10.6.6 Merge modules that are falsely separated

Sometimes a cycle indicates that two files are one abstraction. If nearly every change to <code>node.py</code> requires <code>edge.py</code>, both share private representation, and neither has independent clients, a single <code>graph.py</code> module may have higher cohesion and fewer false boundaries.

Splitting later remains possible when a genuine stable interface emerges. Maintaining two files solely to satisfy a small-file preference imposes dependency complexity without modular benefit.

### 10.6.7 Defer an import only when use is genuinely deferred

A local import can be correct for an optional backend or rarely invoked adapter:

~~~python
def export_pdf(report: Report) -> bytes:
    from .pdf_backend import render_pdf
    return render_pdf(report)
~~~

Now users who never request PDF need not load that backend. If this also avoids a cycle, document why the delayed dependency is semantically appropriate. If every call immediately needs both modules, local import is a tactical workaround that moves failure to runtime and should prompt architectural review.

### 10.6.8 Type annotations should not force a runtime cycle

Use deferred annotations and <code>TYPE_CHECKING</code> when only a static type relation crosses the edge, as §10.2.12 showed. Alternatively, define a protocol or shared value type in a lower module.

Do not quote annotations randomly without understanding runtime consumers. Frameworks may resolve annotations using module globals and need the referenced names importable when schemas are built. Test the actual reflection lifecycle.

### 10.6.9 Registration should not require mutual top-level imports

A plugin base importing every implementation while implementations import the base creates a classic cycle. Let an application discovery layer enumerate plugin modules or use distribution entry points. The base defines the contract without knowing implementations.

~~~text
plugin_contract.py <- plugin_text.py
plugin_contract.py <- plugin_json.py
application.py -> discovery metadata -> plugin modules
~~~

This also reverses authority: low-level contract code no longer decides which untrusted or optional plugin code to execute.

### 10.6.10 Diagnose with strongly connected components

For a large codebase:

1. extract module-level import edges with a static analysis tool;
2. distinguish runtime imports from type-check-only and platform-conditional edges;
3. compute strongly connected components;
4. inspect each component containing more than one node, or a self-loop;
5. classify shared abstraction, misplaced coordination, façade re-entry, registration, or genuine mutual recursion;
6. add architecture tests preventing forbidden layer edges from returning.

Static analysis can miss dynamic imports and over-report conditional ones. Runtime import traces show observed paths but miss unexecuted branches. Use both kinds of evidence.

### 10.6.11 Import order should not be a secret configuration

If <code>import a; import b</code> works while <code>import b; import a</code> fails, independent clients face a hidden ordering precondition. Tests should import public modules in fresh subprocesses and vary order. A package public surface should establish its own prerequisites or reject unsupported use clearly.

Notebook sessions can mask this defect because earlier cells have populated caches and globals. Reproduce in a fresh interpreter.

### 10.6.12 Cycles and module-level instances

Constructing service objects at module top level deepens cycles because construction may immediately request other module state. Move assembly to a composition root after all definitions are importable:

~~~python
def build_application() -> Application:
    repository = SqlRepository(...)
    reporter = Reporter(repository)
    return Application(reporter)
~~~

The function can still be called too early, but the lifecycle becomes explicit and test-controlled.

### 10.6.13 Deliberate mutual recursion belongs below the module boundary

Two algorithms can call one another recursively without residing in mutually importing modules. Place them in one cohesive module, pass callables explicitly, or extract a shared dispatcher. Runtime recursion is not a justification for load-time dependency recursion.

### 10.6.14 Cycle repair checklist

When a cycle appears, ask in order:

1. Is the edge only for an annotation? Remove its runtime requirement.
2. Is one import used only for a genuinely optional/late operation? Defer it at that boundary.
3. Do both modules depend on a smaller shared abstraction? Extract it downward.
4. Does higher-level coordination live in a lower module? Move it to an application layer.
5. Is a concrete dependency pointing from policy to infrastructure? Invert it through a policy-owned protocol.
6. Are two modules actually one cohesive responsibility? Merge them.
7. Is a package façade re-entering itself? Import internal defining modules directly.
8. Is automatic registration forcing discovery into the contract module? Externalise discovery.
9. If the cycle is intentional, what exact initialisation order and deferred lookup prove it safe under reload, tests, and concurrency?

> **Common misconception — “A cycle is repaired if moving one import inside a function stops the error.”**  
> The structural dependency remains. Deferral is correct only when the dependency’s semantic use is genuinely late or optional.

> **Common misconception — “Circular imports are forbidden by Python.”**  
> Python’s early module caching permits some cycles to complete. Their partial-initialisation and ordering contracts are fragile, so architecture should eliminate accidental ones.
