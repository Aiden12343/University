# 10.7 Public APIs and `__all__`

A **public API** is the supported interface on which external callers may rely. In Python, names without a leading underscore are conventionally public unless documentation says otherwise; a leading underscore marks a non-public name by convention.

Package `__init__.py` can re-export a stable surface:

```python
from .model import Account, Transaction
from .parsing import parse_transaction

__all__ = ["Account", "Transaction", "parse_transaction"]
```

Callers can then use:

```python
from ledger import Account
```

instead of depending on internal file layout. The package may later move `Account` while preserving the re-export.

`__all__` controls wildcard export selection and documents intent for tools; it does not make other attributes inaccessible. API stability requires semantic compatibility: retaining a name while changing its exceptions, mutation, ordering, or timing can still break callers.

### Worked example 10.3 — Compatibility is behavioural

Version 1 contract:

```python
def lookup(identifier: str) -> Record | None:
    """Return a record, or None when absent."""
```

Version 2 retains the name but raises `KeyError` when absent. Source code still imports and calls, yet clients written to test `is None` now fail. The API break is semantic. Versioning must describe behaviour, not merely symbols.

### 10.7.1 Publicness is a support promise

A public API consists of names, call forms, types, behaviours, and evolution commitments that maintainers support for external callers. Accessibility is broader: Python callers can often reach underscore-prefixed names, module globals, implementation submodules, and class internals. Accessible does not mean stable.

The distinction allows implementation evolution. If every inspectable name were permanently public, refactoring would become impossible. Conversely, maintainers cannot erase a widely documented, deliberately exported function merely by later calling it internal.

### 10.7.2 API dimensions extend beyond signatures

For a public function, compatibility can include:

- import path and bound name;
- positional, keyword, variadic, and default argument acceptance;
- accepted value domain and coercions;
- return type, shape, identity, ownership, and mutability;
- exceptions and when they occur;
- external effects and their ordering;
- thread, process, and async safety;
- time and space complexity promises;
- determinism and ordering;
- resource lifetime;
- warning behaviour;
- subclass and override hooks;
- serialised or textual formats;
- security and authority assumptions.

Changing a return from list to generator may preserve iteration syntax while breaking repeatability, indexing, eager validation timing, resource closure, or truth testing. “The examples still run” is insufficient compatibility analysis.

### 10.7.3 Public façade versus implementation modules

A package façade can expose stable concepts while implementation remains distributed:

~~~python
# ledger/__init__.py
from ._model import Account as Account
from ._model import Transaction as Transaction
from ._parsing import parse_transaction as parse_transaction

__all__ = ["Account", "Transaction", "parse_transaction"]
~~~

The repeated <code>as</code> spelling can make an intentional re-export explicit to static tools. Underscore-prefixed implementation module names signal that callers should use the façade.

All internal modules importing through the façade can cause cycles. They should usually depend directly on lower internal definitions; external callers receive the façade. This creates asymmetric import policy by design.

### 10.7.4 <code>__all__</code> is export metadata with operational effects

When defined, <code>__all__</code> should contain strings naming attributes the module intends wildcard import to retrieve. Tools also read it as public-surface evidence.

~~~python
__all__ = [
    "Account",
    "Transaction",
    "parse_transaction",
]
~~~

It does not:

- prevent <code>from ledger import _internal</code>;
- remove other attributes from <code>dir</code> automatically;
- prove listed names satisfy documentation;
- recursively control submodule APIs;
- guarantee a name remains stable;
- hide imported implementation dependencies from memory.

Treat the list as one executable declaration backed by tests and documentation.

### 10.7.5 Re-export the same object during moves

Suppose <code>Record</code> moves from <code>ledger.model</code> to <code>ledger.records</code>. A compatibility module should import and bind the new class:

~~~python
# ledger/model.py during a compatibility period
from .records import Record as Record

__all__ = ["Record"]
~~~

Defining a subclass wrapper or copying source creates a different class identity, which can alter <code>isinstance</code>, equality policies, dataclass type checks, registries, pickling, and singledispatch registration. A re-export preserves identity:

~~~python
from ledger.model import Record as OldPathRecord
from ledger.records import Record as NewPathRecord

assert OldPathRecord is NewPathRecord
~~~

### 10.7.6 Signature compatibility is directional

Adding a new optional keyword-only parameter is often backward compatible for callers, while adding a required parameter is not. Renaming a parameter can break callers that used it by keyword even when positional calls still work. Making a formerly positional parameter keyword-only or the reverse changes accepted calls.

For methods designed to be overridden, compatibility is bidirectional across callers and subclasses. Adding a new argument that the base begins passing can break old overrides lacking it. Base-class evolution therefore requires an explicit extension protocol, not only caller-side signature review.

### 10.7.7 Broadening inputs can still break behaviour

Accepting more types appears monotonic, but it can alter overload selection, previously raised exceptions, ambiguity, and performance. If a function formerly rejected strings and a caller used <code>TypeError</code> to select another path, silently accepting strings changes control flow. Exception behaviour should not be used casually as feature detection, yet published behaviour can still have dependants.

Backward compatibility is an engineering judgement based on documented and reasonably relied-upon contracts, not a purely syntactic relation.

### 10.7.8 Deprecation is a staged protocol

A **deprecation** announces that a supported interface remains temporarily available but is scheduled for removal or change. A disciplined sequence is:

1. introduce the replacement and migration path;
2. document the old interface as deprecated with target policy/version where known;
3. emit an appropriate warning at the caller location;
4. retain compatibility for the stated interval;
5. test both old and new paths during that interval;
6. remove under a release boundary that permits the break;
7. document the removal and any automatic migration tooling.

Warnings must avoid secrets and excessive volume. The <code>stacklevel</code> should normally identify caller code rather than an internal compatibility wrapper.

### Worked example 10.3A — A module-level compatibility alias

Modern Python modules can define <code>__getattr__</code> for missing module attributes:

~~~python
# ledger/__init__.py
import warnings

from .records import Record

__all__ = ["Record"]


def __getattr__(name: str):
    if name == "Entry":
        warnings.warn(
            "ledger.Entry is deprecated; use ledger.Record",
            DeprecationWarning,
            stacklevel=2,
        )
        return Record
    raise AttributeError(name)
~~~

The fallback preserves an old attribute without listing it as a preferred wildcard export. Static type checkers may need a stub or explicit deprecated declaration to understand the alias. A direct top-level binding is simpler if warning-on-access is unnecessary.

### 10.7.9 Module <code>__dir__</code> can aid discovery

A module can define <code>__dir__</code> to customise names returned by <code>dir(module)</code>. This can advertise dynamic attributes, but it does not create them and does not establish public support by itself.

Dynamic module attributes complicate static analysis and documentation. Use them for narrow compatibility or lazy-loading boundaries with measured benefit, not to make an arbitrary dictionary look like a module API.

### 10.7.10 Lazy exports change failure timing

A package may defer importing an expensive optional submodule until a public attribute is requested through module <code>__getattr__</code>. This can reduce startup cost, but now:

- <code>import package</code> succeeds while <code>package.Feature</code> may fail later;
- first access bears latency and possible concurrency;
- type tools need separate declarations;
- <code>dir</code>, documentation, and pickling need coherent names;
- partial lazy-loading state needs rollback.

The optimisation should be backed by import-time measurements and tests across first use, failure, repeated use, and concurrent access.

### 10.7.11 Exceptions are public types

Callers catch exception classes by identity and hierarchy. Moving an exception while re-exporting the same class preserves catches; redefining a lookalike does not. Changing from <code>ValueError</code> to <code>KeyError</code>, wrapping without <code>raise ... from ...</code>, or expanding the set of routine failures can be an API change.

Publish a small exception hierarchy when callers need stable recovery categories. Do not expose every vendor exception from an implementation dependency unless binding callers to that vendor is intentional.

### 10.7.12 Mutability and ownership are API properties

If a function returns its internal list and version 2 returns a copy, callers that intentionally mutated shared state change behaviour. If version 1 returned a copy and version 2 returns the internal list, callers can now corrupt invariants. Both return annotations may remain <code>list[T]</code>.

Document whether results are borrowed live views, owned mutable values, immutable snapshots, iterators tied to resources, or cached shared objects.

### 10.7.13 Ordering can be contractual even without an annotation

A dictionary return type does not alone state iteration order semantics. If documentation promises insertion order, sorted order, or priority order, changing it can break deterministic output and caller selection. If order is explicitly unspecified, tests should avoid pinning one incidental implementation order.

### 10.7.14 Performance compatibility matters selectively

Changing a lookup from amortised constant time to linear time can break a caller processing millions of records even if values remain identical. Libraries need not promise exact timing, but may document complexity classes or suitable scale. Performance promises require representative benchmarks and account for worst-case/adversarial inputs where security matters.

### 10.7.15 Static typing surfaces and runtime surfaces can diverge

A package may ship <code>.pyi</code> stub files or a <code>py.typed</code> marker describing annotations. A symbol can exist at runtime but be absent from the supported typing surface, or vice versa because of a packaging defect. Test both runtime imports and static consumer examples.

Annotation changes can be breaking for statically checked clients even when runtime accepts the same calls. Overloads, generic variance, and protocol members form part of the type-level API.

### 10.7.16 Version discovery belongs to distribution metadata

A package may expose <code>__version__</code>, but the installed distribution’s authoritative version is recorded in metadata. <code>importlib.metadata.version("distribution-name")</code> queries that metadata when the mapping is known.

Hard-coding a second version string in source risks divergence. Build tools can derive both from one source or code can query metadata. Remember that distribution and import names may differ.

### 10.7.17 API contract tests

A public API test suite can assert:

- documented imports resolve to the intended identical objects;
- <code>__all__</code> names exist and match the support policy;
- signatures accept legacy call forms;
- return ownership, ordering, and repeatability remain stable;
- documented exception categories and causal chains hold;
- deprecations warn once or at the specified frequency and point to callers;
- pickled/serialised forms migrate or fail under an explicit policy;
- static consumer snippets type-check;
- clean installed artefacts expose the same API as source tests.

Snapshotting every <code>dir(package)</code> entry over-constrains implementation. Test the declared public surface and explicitly forbidden accidental exports.

> **Common misconception — “Keeping the same function name preserves compatibility.”**  
> Call forms, values, effects, failures, ownership, ordering, typing, and complexity can break clients while the name remains.

> **Common misconception — “<code>__all__</code> makes unlisted names private.”**  
> It controls wildcard export selection and communicates intent. Explicit attribute access remains possible.
