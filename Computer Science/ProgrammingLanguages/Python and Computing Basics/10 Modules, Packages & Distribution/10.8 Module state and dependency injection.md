# 10.8 Module state and dependency injection

Module namespaces persist for the process lifetime under ordinary caching, which makes them convenient owners of immutable definitions and hazardous owners of mutable global state.

```python
cache: dict[str, object] = {}
```

This dictionary is shared by all importers of that module object. Tests can influence one another; concurrency requires coordination; state reset and memory growth require policy. If shared state is intentional, encapsulate it behind functions or an object and publish lifetime semantics.

**Dependency injection** supplies a collaborator from outside rather than having a component locate or construct it invisibly.

```python
from collections.abc import Callable


def generate_report(
    load: Callable[[], list[int]],
    write: Callable[[str], None],
) -> None:
    values = load()
    result = f"total={sum(values)}"
    write(result)
```

The function does not import a global database client or write a fixed path. Production and tests can supply different boundary implementations. Injection is not automatically superior for every constant or pure helper; it is valuable where variation, effects, or test control matter.

### 10.8.1 A module is one shared namespace per cached identity

Module globals are bindings in the module object’s dictionary. A function defined there resolves global names against that dictionary when called, subject to normal scope rules.

~~~python
# limits.py
threshold = 10


def accepts(value: int) -> bool:
    return value <= threshold
~~~

Rebinding <code>limits.threshold</code> changes what later <code>accepts</code> calls observe because the function performs a global lookup. A caller that used <code>from limits import threshold</code> holds a separate binding and does not control <code>accepts</code> by rebinding its local name.

### 10.8.2 <code>global</code> selects a namespace; it does not create process universality

Inside a function, <code>global name</code> means assignments target the defining module’s global namespace rather than a local. It does not mean one value shared across all modules, processes, interpreters, machines, or import aliases.

~~~python
count = 0


def increment() -> int:
    global count
    count += 1
    return count
~~~

Each process normally has its own memory and module cache. A second import identity can have another <code>count</code>. Threads share the module object but <code>count += 1</code> is not thereby a documented atomic transaction; Chapter 14 develops concurrency.

### 10.8.3 Constants are conventionally stable bindings

Uppercase spelling such as <code>SECONDS_PER_DAY = 86_400</code> communicates that callers should treat a binding as constant. Python does not generally enforce rebinding prohibition. Prefer immutable constant values and avoid deriving them from mutable environment state at unpredictable times.

A configuration value that changes between deployments is not necessarily a source constant. Parse it at an application boundary into a validated configuration object and inject that object.

### 10.8.4 Module-owned caches require a complete policy

~~~python
_cache: dict[str, bytes] = {}
~~~

Before adding this line, define:

- key and value semantics;
- maximum size and eviction;
- freshness and invalidation;
- negative-result caching;
- exception caching;
- thread/async/process coordination;
- memory ownership and weak references;
- reset for tests and configuration changes;
- observability and sensitive-data handling;
- behaviour across reload and fork.

An unbounded dictionary is a lifetime-long accumulation policy, even if the author did not intend one.

### 10.8.5 Import-time clients conflate loading with environment access

~~~python
# hazardous.py
client = DatabaseClient.from_environment()
~~~

Importing this module now reads environment configuration, may load credentials, and may establish resources before the caller selects an operation. Documentation tools, test collection, shell completion, and unrelated commands all inherit the requirement.

Prefer explicit assembly:

~~~python
def build_client(configuration: DatabaseConfiguration) -> DatabaseClient:
    return DatabaseClient(
        host=configuration.host,
        credentials=configuration.credentials,
    )
~~~

The composition root decides when to read configuration and how to close the client.

### 10.8.6 Parameter injection is the most local form

~~~python
from collections.abc import Callable
from datetime import datetime


def expired(
    deadline: datetime,
    *,
    now: Callable[[], datetime],
) -> bool:
    return now() >= deadline
~~~

The dependency is visible in the call signature and a test can supply a fixed clock. For a small number of collaborators, this is often clearer than building a class solely to store them.

Repeatedly threading many dependencies through many calls can signal that a cohesive service object or context value should own them. Do not hide them in globals merely to shorten signatures.

### 10.8.7 Constructor injection defines object capability

~~~python
from typing import Protocol


class TransactionSource(Protocol):
    def all(self) -> list[Transaction]: ...


class ReportService:
    def __init__(self, source: TransactionSource) -> None:
        self._source = source

    def total(self) -> int:
        return sum(item.amount_pence for item in self._source.all())
~~~

A <code>ReportService</code> can perform only operations exposed by its source reference and other reachable objects. Constructor injection makes the required capability part of valid construction. A setter-injected collaborator can leave the object temporarily unusable unless optionality or lifecycle is explicit.

### 10.8.8 Factory injection controls repeated construction

If each operation needs a fresh session, injecting one session object gives the wrong lifetime. Inject a factory or context-manager factory:

~~~python
from collections.abc import Callable
from contextlib import AbstractContextManager


SessionFactory = Callable[[], AbstractContextManager[Session]]


class ImportService:
    def __init__(self, sessions: SessionFactory) -> None:
        self._sessions = sessions

    def import_batch(self, batch: Batch) -> None:
        with self._sessions() as session:
            session.store(batch)
~~~

The factory dependency states that the service owns one scoped session per batch. Tests can supply a recording context manager and assert closure.

### 10.8.9 A service locator hides dependencies

A **service locator** is a registry from which code requests collaborators during execution:

~~~python
def generate() -> str:
    repository = services.resolve("repository")
    return repository.report()
~~~

The function signature does not reveal its requirement; missing configuration fails at runtime; any code with the locator may obtain broad capabilities. Dependency injection resolves collaborators at an outer assembly boundary and supplies only what a component needs.

A locator can be appropriate inside a plugin framework or application composition mechanism, but domain code should not use it as ambient global access.

### 10.8.10 Default arguments can freeze a dependency too early

~~~python
from clock import now


def stamp(value: str, clock=now) -> str:
    return f"{clock()}:{value}"
~~~

The default object is evaluated when the function is defined. Later patching <code>clock.now</code> does not change this default. Explicit required injection or a <code>None</code> sentinel resolved inside the function has different semantics.

Defaults are useful for stable pure policies, but hidden effectful collaborators create tests that patch the wrong namespace and applications that cannot reconfigure lifetime.

### 10.8.11 Configuration is data, not scattered global reads

Reading <code>os.environ</code> throughout modules creates implicit dependencies and inconsistent parse timing. Gather external strings at startup, parse and validate once, then pass an immutable configuration value:

~~~python
from dataclasses import dataclass


@dataclass(frozen=True, slots=True)
class Configuration:
    database_url: str
    timeout_seconds: float
    debug: bool
~~~

Secret-bearing fields need redacted representation or separate capability objects. Immutability means components share one configuration snapshot; dynamic reconfiguration requires an explicit versioned update protocol rather than silent environment rereads.

### 10.8.12 Pure core and effectful shell

A useful architecture concentrates deterministic transformation in a **functional core** and external effects in an **imperative shell**:

~~~python
def summarise(records: tuple[Record, ...]) -> Summary:
    # Pure domain transformation.
    ...


def run_import(source: Source, destination: Destination) -> None:
    records = tuple(source.read())
    summary = summarise(records)
    destination.write(summary)
~~~

The division improves testability and failure reasoning. It is not absolute: some domain rules concern time or transactions and need controlled effects. Injection turns those effects into explicit interfaces rather than pretending they are pure.

### 10.8.13 Module state and fork/spawn differ

Forward reference to Chapter 14: a new process may inherit a snapshot of memory under a fork-like mechanism or start a fresh interpreter that imports modules under a spawn-like mechanism. Neither produces a transparently shared mutable module dictionary. Updates require interprocess communication or shared external storage.

Code whose correctness depends on “the module singleton” should state whether uniqueness means per import name, interpreter, process, user, host, or distributed deployment. These scopes are not interchangeable.

### 10.8.14 Testing module state without global contamination

Prefer testing explicit owner objects. When module state is itself the contract:

1. expose narrow reset/close operations only if production lifecycle also needs them;
2. use test fixtures that restore exact prior state, even after failure;
3. avoid deleting unrelated cache entries;
4. isolate import-lifecycle tests in subprocesses;
5. test concurrent access if state is shared across threads;
6. avoid relying on test execution order;
7. assert that sensitive state is not leaked in representations.

Reload rarely provides a clean reset because external references and retained namespace entries can survive.

### Worked example 10.3B — Replace global patching with a composition root

Before:

~~~python
# service.py
from .database import global_database


def account_total(account_id: str) -> int:
    rows = global_database.query(account_id)
    return sum(row.amount for row in rows)
~~~

After:

~~~python
class AccountRows(Protocol):
    def query(self, account_id: str) -> list[Transaction]: ...


def account_total(source: AccountRows, account_id: str) -> int:
    rows = source.query(account_id)
    return sum(row.amount_pence for row in rows)


def build_application(configuration: Configuration) -> Application:
    database = Database(configuration.database_url)
    return Application(database=database)
~~~

The pure calculation still depends on transaction meaning but no longer on one module-owned connection. The application object or outer context owns database closure. A test supplies an in-memory source without patching import bindings.

> **Common misconception — “Module globals are bad by definition.”**  
> Immutable definitions and deliberately process-scoped state can have clear module ownership. Hidden mutable dependencies without lifecycle policy are the problem.

> **Common misconception — “Dependency injection means using a framework container.”**  
> Passing a value, protocol implementation, or factory as an argument is dependency injection. Containers are optional assembly machinery and can become service locators if used inside domain code.
