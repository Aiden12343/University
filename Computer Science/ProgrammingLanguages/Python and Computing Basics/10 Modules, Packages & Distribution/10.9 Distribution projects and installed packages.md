# 10.9 Distribution projects and installed packages

A Python **distribution project** is a versioned unit that can be built and installed. It contains metadata and one or more import packages or modules. Distribution name, import name, and repository name need not match.

An installed distribution records metadata such as name, version, dependencies, files, and entry points. The import system ordinarily searches directories recorded in `sys.path`; it does not ask `pip` each time an import occurs. Installation arranges files and metadata so import finders can locate modules.

This distinction explains four separate questions:

1. Is a distribution installed in this environment?
2. Which version and metadata are installed?
3. Which import modules does it provide?
4. Which file and module object did this particular import resolve?

Use `python -m pip show distribution-name` for distribution metadata and inspect `module.__file__`, `module.__spec__`, and `importlib.metadata` under their contracts for runtime evidence. Do not infer one solely from the other’s spelling.

### 10.9.1 Project name and import name inhabit different registries

Distribution project names are compared under packaging normalisation rules; differences in case and runs of certain punctuation may normalise to one project key. Python import identifiers follow Python name syntax and are case-sensitive on the language level, even when filesystem behaviour adds platform complications.

A distribution named <code>careful-ledger</code> can provide import package <code>ledger</code>. The hyphen would not be an ordinary identifier in <code>import careful-ledger</code>. Never derive a pip command mechanically from an <code>ImportError</code> name without consulting project documentation or distribution metadata; attackers exploit plausible name confusion.

### 10.9.2 Installation places files and metadata into an environment

A standard wheel installation commonly places importable modules in an environment’s site-packages location and metadata in a <code>.dist-info</code> directory. Metadata can include project name, version, requirements, entry points, licences, and a record of installed files.

The exact paths depend on interpreter, environment, platform, and installation scheme. The import system sees search locations and loaders; <code>importlib.metadata</code> sees distribution metadata discoverable there. Neither requires that all files come from one installer or remain unmodified after installation.

### 10.9.3 Mapping packages back to distributions is many-to-many

The standard metadata API can offer a mapping from top-level import packages to distributions:

~~~python
from importlib.metadata import packages_distributions


providers = packages_distributions().get("ledger", [])
print(providers)
~~~

The result can be empty, one name, or several names. Editable source, modules without distribution metadata, namespace packages, and imperfect package declarations limit the inference. Use it as evidence, not an identity theorem.

### 10.9.4 Query an installed distribution explicitly

~~~python
from importlib.metadata import PackageNotFoundError, metadata, version


try:
    installed_version = version("careful-ledger")
    project_metadata = metadata("careful-ledger")
except PackageNotFoundError:
    print("distribution metadata not found")
~~~

Finding metadata does not prove a particular import resolves to its files when shadowing exists. Conversely, an import may succeed from the working tree without installed metadata. Diagnose both sides.

### 10.9.5 Editable installation changes the code-location contract

An **editable installation** makes a development source tree importable while recording project metadata in the environment, using a mechanism selected by the build backend/frontend. Edits can affect later imports without rebuilding a wheel.

Editable behaviour is intentionally development-oriented and can differ from a regular wheel in package discovery, generated files, extension builds, and resource inclusion. It is not the artefact shipped to users. Test both editable development and a clean regular installation.

Legacy descriptions that editable installation always creates one particular link file are too narrow; modern backend protocols can implement editability in different compliant ways.

### 10.9.6 Environment selection precedes package installation

The command <code>pip</code> found by a shell may belong to a different interpreter than <code>python</code>. Use:

~~~text
python -m pip install careful-ledger
~~~

to run pip as a module of the selected <code>python</code>. Then verify:

~~~python
import sys

print(sys.executable)
print(sys.prefix)
print(sys.base_prefix)
~~~

In a conventional virtual environment, <code>sys.prefix</code> identifies the environment while <code>sys.base_prefix</code> identifies the base interpreter. Environment managers may add further layers, so report the actual executable and paths during diagnosis.

### 10.9.7 Installation success and import success are distinct

A distribution can install successfully yet fail to import because:

- packaging omitted modules or native libraries;
- a runtime dependency was undeclared or incompatible;
- an import package has a different name;
- current-directory shadowing selects another file;
- platform dynamic linking fails;
- import-time configuration or code raises;
- the command and interpreter use different environments.

An import can succeed without an installation because the module is built in, on <code>PYTHONPATH</code>, in the current directory, injected by a notebook, or otherwise discoverable.

### 10.9.8 Multiple distributions can collide

Two distributions can install the same ordinary module path. The later file operation may overwrite another distribution’s file, or search-order paths may select one copy. Uninstalling one can remove files the other expected. Packaging metadata alone cannot make overlapping ownership safe.

Namespace packages intentionally permit different distributions to contribute distinct subpackages under one namespace. They must still avoid owning the same concrete module and coordinate naming and API policy.

### 10.9.9 Installation records support inspection, not perfect provenance

Wheel metadata records installed paths and hashes for many files. Administrators can compare records to detect modification. Some generated files and installer behaviours have special treatment, and privileged processes can alter both code and records.

For high-assurance supply chains, retain artefact hashes/signatures under organisational policy, use controlled indexes, build reproducibly where feasible, and deploy immutable environments. An installed directory is operational state, not by itself an authenticated source of truth.

### 10.9.10 Version is qualified by environment and artefact

“Version 2.1 is installed” is incomplete without the environment/interpreter and potentially build tag or direct-source revision. Local version identifiers, platform wheels, downstream rebuilds, and editable worktrees can contain different code under related version strings.

Record lock data, artefact hashes, Python version, platform, and deployment image identity when reproducibility matters. Do not mutate installed source files in place and continue relying on unchanged metadata.

### 10.9.11 Import names are not dependency declarations

Source code can import <code>yaml</code>, while project metadata must require the distribution that intentionally supplies it. Static import scanning cannot always infer dependencies because names differ, imports may be optional, and dynamic plugins may be discovered by metadata.

Declare direct runtime dependencies even if another direct dependency happens to install them transitively. Depending on an undeclared transitive package couples the project to another project’s internal requirement graph.

### 10.9.12 Diagnose environment identity end to end

For an unexpected version or module:

1. record <code>sys.executable</code> and interpreter version;
2. record virtual-environment prefixes;
3. inspect <code>sys.path</code> in the failing process;
4. inspect <code>module.__spec__</code> and <code>module.__file__</code> after import;
5. query the intended distribution metadata through the same interpreter;
6. map the top-level package to candidate distributions cautiously;
7. inspect installation files and hashes when necessary;
8. reproduce outside the repository to rule out shadowing;
9. compare the built artefact with source/editable state.

> **Common misconception — “The pip name and import name are the same with punctuation changed.”**  
> There is no universal one-to-one naming transformation. Consult authoritative project metadata.

> **Common misconception — “If distribution metadata reports a version, that exact code handled my import.”**  
> Search-path shadowing, editable sources, overlapping installations, or file modification can separate metadata from the resolved module. Inspect both.
