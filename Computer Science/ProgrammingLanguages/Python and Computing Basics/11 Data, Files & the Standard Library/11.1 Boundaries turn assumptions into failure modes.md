# 11.1 Boundaries turn assumptions into failure modes

Inside a pure calculation, inputs are already Python objects satisfying some contract. Outside the process lie byte streams, filesystems, clocks, terminals, networks, environment variables, and other processes. A boundary adapter converts external representation and failure into domain objects and exceptions.

Every external operation is contingent. A file can disappear after an existence check. A read can return fewer bytes than requested. Text can violate its promised encoding. A write can fill storage. A network peer can stop mid-message. Correct software does not treat these conditions as mysterious interruptions; it assigns them to interface contracts.

The central boundary sequence is:

1. acquire a resource under stated authority;
2. receive bytes or another external representation;
3. frame the data into units;
4. decode or parse those units;
5. validate domain meaning;
6. perform internal computation;
7. encode and emit results;
8. release resources under a defined lifetime.

### 11.1.1 The boundary/core separation

A useful architecture divides a program into a comparatively small **boundary layer** and a comparatively pure **computational core**. Here, *pure* means that a function's result depends only on its explicit arguments and that evaluating it does not intentionally alter externally observable state. Purity is a degree and a design property rather than a Python-enforced category: Python permits any called function to perform effects unless convention, review, or additional tooling constrains it. A pure core is valuable because bytes, clocks, process state, and partial I/O have already been translated into explicit values before computation begins.

Consider a tax calculation. The mathematical rule should not open a file merely because rates happen to arrive in a file:

~~~python
from decimal import Decimal


def tax_due(net: Decimal, rate: Decimal) -> Decimal:
    if net < 0:
        raise ValueError("net amount must be non-negative")
    if not Decimal("0") <= rate <= Decimal("1"):
        raise ValueError("rate must lie in the closed interval 0..1")
    return net * rate
~~~

The function accepts domain values and enforces domain preconditions. A separate adapter owns text and files:

~~~python
from decimal import Decimal, InvalidOperation
from pathlib import Path


def read_rate(path: Path) -> Decimal:
    try:
        source = path.read_text(encoding="utf-8")
    except OSError as error:
        raise RuntimeError(f"cannot read rate file {path}") from error

    try:
        rate = Decimal(source.strip())
    except InvalidOperation as error:
        raise ValueError(f"{path}: rate is not a decimal numeral") from error

    if not Decimal("0") <= rate <= Decimal("1"):
        raise ValueError(f"{path}: rate must lie in 0..1")
    return rate
~~~

The separation is not merely aesthetic. It localises several different claims:

- <code>Path.read_text</code> concerns resource acquisition, byte transfer, and decoding;
- <code>strip</code> embodies a format decision that surrounding whitespace is insignificant;
- <code>Decimal</code> conversion concerns lexical numeric syntax;
- the interval test concerns domain validity;
- <code>tax_due</code> concerns the calculation.

When all five claims inhabit one unstructured block, a failure report such as “invalid input” conceals which contract failed. Separation gives tests stable seams: the core can be tested without a filesystem, while the adapter can be tested with fixtures designed around encoding, permissions, absence, and malformed representations.

This architecture is not a command to create one wrapper function per expression. Excessive fragmentation can obscure the transaction being performed. The criterion is ownership of assumptions: operations that interpret the same boundary contract normally belong together; operations whose truth can be established using only domain values normally belong in the core.

> **Common misconception 11.1 — “Pure functions never raise exceptions.”** Purity concerns dependence and effects, not guaranteed success. A deterministic function can reject an argument with an exception and remain pure in the relevant sense.

### 11.1.2 Six distinct validity layers

“Valid data” is too imprecise for boundary reasoning. At least six questions may need independent answers:

1. **Representation validity:** Are the received physical or logical units well formed at the lowest selected layer? A byte sequence may, for example, be valid UTF-8.
2. **Syntactic validity:** Does the decoded input conform to the grammar of its format? Text may be valid UTF-8 but invalid JSON.
3. **Structural or schema validity:** Does the parsed structure contain the required members and value shapes? A JSON object can be syntactically valid while omitting a required field.
4. **Semantic validity:** Do values make sense in the domain? A date may have valid syntax while lying outside an enrolment period.
5. **Authenticity and integrity:** Is there adequate evidence about who produced the data and whether it changed? A digital signature or message authentication code addresses particular claims, not truth in general.
6. **Authority:** Even if a request is authentic and meaningful, is its principal permitted to cause the requested operation?

These are ordered for processing convenience, not logical implication. Passing one layer proves none of the later layers. Nor does authenticity imply semantic truth: an authorised employee can submit an erroneous amount, and an uncompromised sensor can be miscalibrated.

The following small parser makes three layers visible:

~~~python
import json
from dataclasses import dataclass


@dataclass(frozen=True, slots=True)
class TransferRequest:
    source: str
    destination: str
    amount_pence: int


def parse_transfer(source_text: str) -> TransferRequest:
    try:
        value = json.loads(source_text)
    except json.JSONDecodeError as error:
        raise ValueError(
            f"invalid JSON at line {error.lineno}, column {error.colno}"
        ) from error

    if not isinstance(value, dict):
        raise ValueError("transfer document must be a JSON object")

    expected = {"source", "destination", "amount_pence"}
    if set(value) != expected:
        missing = expected - set(value)
        extra = set(value) - expected
        raise ValueError(f"transfer fields differ: missing={missing}, extra={extra}")

    source = value["source"]
    destination = value["destination"]
    amount = value["amount_pence"]
    if not isinstance(source, str) or not isinstance(destination, str):
        raise ValueError("source and destination must be strings")
    if type(amount) is not int:
        raise ValueError("amount_pence must be an integer")
    if source == destination:
        raise ValueError("source and destination must differ")
    if amount <= 0:
        raise ValueError("amount_pence must be positive")

    return TransferRequest(source, destination, amount)
~~~

The exact test <code>type(amount) is not int</code> is intentional because <code>bool</code> is a subclass of <code>int</code>; accepting <code>true</code> as one penny would conflate distinct schema types. Whether unknown members should be rejected, ignored, or retained is a versioning decision. Strict rejection catches misspellings but makes additive schema evolution harder. Permissive acceptance aids evolution but can conceal a producer/consumer mismatch. The interface must choose and document one policy.

Authentication and authorisation are absent from this example. Their absence must not be mistaken for an implicit success. A parser is not an access-control system.

> **Common misconception 11.2 — “A schema proves the data is true.”** A schema can establish shape and selected constraints. It cannot establish that a claimant is honest, a measurement is accurate, or an action is authorised.

### 11.1.3 Observation, state, and time

External state is observed at a time. A filesystem query, environment lookup, network response, or clock reading is not an eternal fact about the world. Between two operations another process, user, device, or failure can intervene. This yields three important distinctions.

A **snapshot** is a representation intended to describe state at one logical instant or version. Whether an API provides a coherent snapshot is part of its contract. Iterating a directory does not generally mean that every returned entry coexisted throughout the iteration. Reading a normal file while another process overwrites it does not automatically provide transaction isolation.

A **handle** is a process-visible reference to an acquired resource, such as an open file object. Once acquired, the handle can have stronger identity properties than repeatedly resolving a pathname, although precise behaviour is operating-system and filesystem dependent. A pathname is a request to resolve names; it is not the file's permanent identity.

A **lease** is time-bounded authority or ownership whose validity must be renewed. Leases appear in distributed systems and locks; they are introduced here only to prevent an unstated assumption that acquisition lasts indefinitely. Concurrency is treated fully in Chapter 14.

Suppose code checks a configuration file twice:

~~~python
if config_path.exists():
    size = config_path.stat().st_size
    text = config_path.read_text(encoding="utf-8")
~~~

The three calls may observe three filesystem states. The path might be replaced after <code>exists</code>; <code>stat</code> may describe one object and <code>read_text</code> another. If the requirement is simply “read the object found when opening succeeds”, open once and operate through that handle. If the requirement is “read only a file whose identity and metadata satisfy a security policy”, a platform-aware design must validate through race-resistant handle-relative operations. A sequence of pathname pre-checks is not enough.

### 11.1.4 Partial success and failure atomicity

An operation can fail after producing effects. **Failure atomicity** is the property that an operation either has its full specified effect or has no externally visible effect within a named observation model. It must never be inferred merely because a Python function raised one exception.

Consider copying ten records to a destination stream:

~~~python
def write_lines(stream: object, lines: list[str]) -> None:
    for line in lines:
        stream.write(line + "\n")  # type: ignore[attr-defined]
~~~

If the sixth write fails, the first five may remain visible. Catching the exception cannot retract bytes already passed to another component. There are four broad strategies:

- **Prevalidation:** establish all properties that can be established before the first effect. This reduces, but cannot eliminate, mid-operation failures.
- **Staging and commit:** construct a complete candidate in an isolated location, then expose it with one commit operation such as a supported atomic rename.
- **Transaction:** use a subsystem that records and coordinates a set of changes with defined commit and rollback semantics.
- **Compensation:** perform new effects intended to counteract completed effects. Compensation is not literal rollback: sending a refund does not erase the history of a charge.

Each strategy has a scope. Renaming one prepared file can make one directory entry switch atomically for relevant observers on supported filesystems, but it does not atomically update a database row, send an email, and replace a second file. A database transaction cannot retract an email already accepted by a mail server.

The phrase **commit point** denotes the transition after which the operation is regarded as accepted and ordinary rollback is no longer available. Good interfaces decide what may fail before and after this point. Irreversible or expensive effects should usually follow validation and reversible preparation.

### Worked example 11.1-A — Stage, validate, then replace

The following function writes a complete UTF-8 document to a temporary sibling, flushes Python's buffers, optionally requests operating-system synchronisation, and replaces one destination pathname:

~~~python
import os
from collections.abc import Iterable
from pathlib import Path
from tempfile import NamedTemporaryFile


def replace_text_lines(
    destination: Path,
    lines: Iterable[str],
    *,
    durable_file: bool = False,
) -> None:
    destination = destination.resolve()
    parent = destination.parent

    temporary_name: str | None = None
    try:
        with NamedTemporaryFile(
            mode="w",
            encoding="utf-8",
            newline="\n",
            dir=parent,
            prefix=f".{destination.name}.",
            suffix=".tmp",
            delete=False,
        ) as stream:
            temporary_name = stream.name
            for line_number, line in enumerate(lines, start=1):
                if "\n" in line or "\r" in line:
                    raise ValueError(
                        f"line {line_number} contains an embedded line ending"
                    )
                stream.write(line)
                stream.write("\n")
            stream.flush()
            if durable_file:
                os.fsync(stream.fileno())

        os.replace(temporary_name, destination)
        temporary_name = None
    finally:
        if temporary_name is not None:
            try:
                Path(temporary_name).unlink()
            except FileNotFoundError:
                pass
~~~

Line by line, the design establishes the following:

1. Resolving the destination chooses a concrete current location before staging. This is a policy, not universal protection against later link or mount changes.
2. Creating the temporary file inside the destination directory makes same-filesystem replacement likely and avoids predictable names.
3. <code>delete=False</code> is required because the name must survive closing for replacement; it consequently creates an explicit cleanup obligation.
4. Each logical line is validated before its two writes, but the generator may still fail after earlier temporary output. Because the temporary object is not yet the destination, that partial output is not committed there.
5. <code>flush</code> transfers Python-buffered bytes towards the operating system. <code>fsync</code>, where supported with these semantics, requests stronger file-data synchronisation.
6. <code>os.replace</code> is the namespace commit point. Its precise atomicity and cross-platform constraints are governed by the operating system; it can fail.
7. The <code>finally</code> block removes an uncommitted temporary name where possible.

This function still does **not** prove that the new directory entry survives immediate power loss. On systems where that property matters, synchronising the containing directory after replacement may be required and may itself be platform-specific. Nor does the function preserve all old metadata, coordinate readers that already hold the old file open, prevent another writer from replacing the name later, or make an iterable's external side effects transactional. Its value lies partly in the explicit limit of its claim.

> **Common misconception 11.3 — “An exception means nothing happened.”** An exception reports that the operation did not return normally. Effects completed before the exception may persist.

### 11.1.5 Retries, idempotence, and duplicate effects

A **retry** repeats an operation after an absent, delayed, or failed response. Retrying is safe only under an adequate model of the first attempt's outcome. A timeout means “the caller did not receive completion evidence by its deadline”; it does not mean “the callee did nothing”.

An operation is **idempotent** when applying it repeatedly has the same relevant effect as applying it once:

\[
f(f(x)) = f(x).
\]

The equation is a model, not a complete systems specification. Setting a named configuration value to 7 may be idempotent with respect to final configuration, while still creating a new audit record or notification on each request. Incrementing a balance is not idempotent. Appending a line is not idempotent.

One common retry design attaches a stable **idempotency key** to one logical request. The receiver records the key and the corresponding outcome in the same transactional scope as the effect. Repeated delivery of that key returns the recorded outcome rather than applying the effect again. Merely keeping a process-local set is inadequate when the process can crash between effect and record, when records expire too soon, or when multiple workers race.

“Exactly once” is often an imprecise slogan. A transport can ordinarily offer such behaviours as at-most-once delivery, at-least-once delivery, or ordered delivery under stated failures. Exactly-once *domain effects* require cooperation among delivery, deduplication, state storage, commit, retention, and recovery. The correct claim names the observation layer: a message may be delivered twice while its idempotently identified database mutation becomes visible once.

### Worked example 11.1-B — Make duplicate detection part of state

This in-memory model is pedagogical; it demonstrates the state transition but not crash durability or process coordination:

~~~python
from dataclasses import dataclass, field


@dataclass
class Ledger:
    balances: dict[str, int]
    completed: dict[str, tuple[str, str, int]] = field(default_factory=dict)

    def transfer(
        self,
        request_id: str,
        source: str,
        destination: str,
        amount: int,
    ) -> None:
        request = (source, destination, amount)
        previous = self.completed.get(request_id)
        if previous is not None:
            if previous != request:
                raise ValueError("request ID was reused for different content")
            return

        if amount <= 0:
            raise ValueError("amount must be positive")
        if self.balances.get(source, 0) < amount:
            raise ValueError("insufficient funds")

        self.balances[source] -= amount
        self.balances[destination] = (
            self.balances.get(destination, 0) + amount
        )
        self.completed[request_id] = request
~~~

The equality check prevents a client from accidentally reusing one key for a different request. Yet a process interruption could occur between the two balance assignments or between a balance change and recording <code>completed</code>. A real implementation needs a transactional store whose commit covers balances and the deduplication record together. The example therefore states a modelling assumption: each method call is observed only before entry or after normal completion. Chapter 12 develops testing and evidence; Chapter 14 develops interleavings.

> **Common misconception 11.4 — “Retrying after a timeout is harmless.”** The first operation may have committed even though its acknowledgement was lost. Retry policy depends on effect semantics and duplicate control.

### 11.1.6 Bounded consumption and adversarial inputs

An input need not exploit arbitrary code execution to cause harm. A small compressed object can expand enormously; a JSON value can nest deeply; one CSV record can contain a gigabyte-long quoted field; a declared length can exceed available memory; an iterator can be infinite. **Resource exhaustion** occurs when work consumes a scarce resource—memory, CPU time, storage, file descriptors, processes, network capacity, or human attention—beyond an acceptable budget.

“Stream the file” is necessary but insufficient. Streaming bounds retained content only if:

- records themselves have a maximum size;
- the parser does not retain all prior state;
- aggregation cardinality is bounded or externally stored;
- decompression has output and ratio limits;
- diagnostics do not copy the entire offending value;
- downstream consumers accept data at an adequate rate.

A **resource budget** states a limit and the action taken when it is exceeded. Budgets may include total bytes, decoded code points, record count, per-record bytes, nesting depth, elapsed time, output size, and number of distinct keys. Limits should be enforced as early as the relevant quantity becomes knowable.

~~~python
from collections.abc import BinaryIO


class InputTooLarge(ValueError):
    pass


def read_at_most(stream: BinaryIO, limit: int) -> bytes:
    if limit < 0:
        raise ValueError("limit must be non-negative")

    data = stream.read(limit + 1)
    if len(data) > limit:
        raise InputTooLarge(f"input exceeds {limit} bytes")
    return data
~~~

Requesting one extra byte distinguishes “exactly the limit” from “more than the limit” without reading the remainder. The guarantee depends on the stream implementation respecting the requested upper bound. For raw non-blocking streams, availability and partial results require a richer loop. The function also leaves the stream positioned after the bytes it consumed; rejection does not rewind a non-seekable source.

When a protocol declares a size, treat that declaration as a claim to validate, not permission to allocate blindly:

~~~python
def validate_declared_length(length: int, maximum: int) -> int:
    if length < 0:
        raise ValueError("negative length")
    if length > maximum:
        raise InputTooLarge(
            f"declared length {length} exceeds maximum {maximum}"
        )
    return length
~~~

Resource limits are part of functional correctness whenever the environment is finite—which is always. Their numerical values are operational policies and should be measured, documented, and revisited rather than hidden as unexplained constants.

### 11.1.7 Backpressure and rate mismatch

When a producer can create units faster than a consumer can process them, an intermediate queue grows unless some component slows, discards, aggregates, spills, or rejects work. **Backpressure** is a mechanism by which downstream capacity constrains upstream production.

A synchronous iterator naturally provides a simple form of pull-based backpressure: the producer is asked for the next item only when the loop advances. Materialising the same iterator with <code>list</code> removes that property and requests all items immediately. Filesystem and network buffers can still read ahead, but the core relation remains.

~~~python
def normalised_lines(source: object) -> object:
    for raw_line in source:  # type: ignore[union-attr]
        line = raw_line.rstrip("\n")
        if line:
            yield line.casefold()
~~~

The generator performs work on demand. It does not by itself solve slow-output problems, cancellation, fairness, or asynchronous flow control. Those require the concurrency models of Chapter 14; this paragraph is an explicitly flagged forward reference.

Possible rate-mismatch policies have different semantics:

| Policy | Memory consequence | Information consequence | Typical obligation |
|---|---:|---|---|
| block or slow producer | bounded if propagation succeeds | preserves units | prevent deadlock; define timeout/cancellation |
| bounded queue and reject | bounded | rejects new work | expose overload clearly |
| discard oldest | bounded | loses history | identify loss and ordering |
| discard newest | bounded | loses current arrivals | signal or measure drops |
| aggregate | bounded by aggregate state | loses individual detail | define aggregation algebra |
| spill to storage | shifts pressure to storage | may preserve detail | bound storage and recovery |

There is no neutral “keep buffering” policy: it selects eventual memory or storage exhaustion when overload persists.

### 11.1.8 Provenance and diagnostic context

**Provenance** is information about the origin and transformation history of data. At a minimum, a diagnostic for external input often needs the source identity, record or byte position, field name, rejected value in a safely bounded representation, and the violated rule. This context should be attached near the layer that knows it.

~~~python
from dataclasses import dataclass


@dataclass(frozen=True, slots=True)
class SourceLocation:
    source: str
    record: int
    field: str


class FieldError(ValueError):
    def __init__(self, location: SourceLocation, message: str) -> None:
        self.location = location
        self.detail = message
        super().__init__(
            f"{location.source}: record {location.record}, "
            f"field {location.field!r}: {message}"
        )


def parse_percentage(raw: str, location: SourceLocation) -> int:
    try:
        value = int(raw)
    except ValueError as error:
        raise FieldError(location, f"not an integer: {raw[:40]!r}") from error
    if not 0 <= value <= 100:
        raise FieldError(location, f"outside 0..100: {value}")
    return value
~~~

The original <code>ValueError</code> is retained as the explicit cause through <code>raise ... from error</code>. The domain-facing exception adds location. The rejected text is truncated to reduce accidental log amplification, though a security-sensitive system must also consider secrets, control characters, bidirectional text, and personal data before logging it.

Diagnostics and machine-readable errors serve different audiences. A stable error code can support software decisions; prose can support people. Consumers should not parse incidental English punctuation to discover error kind.

~~~python
@dataclass(frozen=True, slots=True)
class Problem:
    code: str
    message: str
    location: SourceLocation | None = None
~~~

The type does not determine transport encoding. A command-line program may render it to standard error; an HTTP adapter may map it to a status and JSON document; a batch import may collect a bounded set of problems. Boundary policy decides whether to fail fast or continue after an invalid record.

> **Common misconception 11.5 — “Logging the whole input is best for debugging.”** Unbounded input can exhaust logs, and input can contain secrets or crafted control data. Diagnostics require minimisation, escaping, and retention policy.

### 11.1.9 Translating exceptions without erasing evidence

Low-level exceptions frequently expose an implementation vocabulary inappropriate for callers. An adapter can translate them into a stable domain exception, provided it preserves useful causal information.

~~~python
from pathlib import Path


class CatalogueUnavailable(RuntimeError):
    pass


def load_catalogue_text(path: Path) -> str:
    try:
        return path.read_text(encoding="utf-8")
    except FileNotFoundError as error:
        raise CatalogueUnavailable(
            f"catalogue does not exist: {path}"
        ) from error
    except PermissionError as error:
        raise CatalogueUnavailable(
            f"catalogue is not readable: {path}"
        ) from error
    except UnicodeDecodeError as error:
        raise CatalogueUnavailable(
            f"catalogue is not valid UTF-8: {path}"
        ) from error
~~~

Translation serves three purposes:

- it decouples the caller from the storage mechanism;
- it adds boundary-specific context;
- it defines which failures the caller is expected to handle together.

Overbroad translation is harmful:

~~~python
try:
    return build_catalogue()
except Exception as error:
    raise CatalogueUnavailable("catalogue failed") from error
~~~

This catches programming defects such as <code>AttributeError</code> and falsely classifies them as expected availability failures. Catch the narrow exceptions whose meaning the layer understands. If cleanup must occur for every exception, use <code>finally</code> or a context manager rather than pretending all exceptions have the same semantics.

Exception messages are not generally stable APIs. Exception types, explicit attributes, and documented codes are better programmatic contracts. At a process boundary, decide which diagnostic details may safely cross; exposing a local path, query, credential fragment, or stack trace can violate confidentiality.

> **Common misconception 11.6 — “Catching <code>Exception</code> makes an interface robust.”** An indiscriminate catch can conceal defects, corrupt control flow, and misreport failures. Robustness requires classification and a recovery policy.

### 11.1.10 Trust boundaries and least authority

A **trust boundary** separates components governed by different assumptions about identity, integrity, or behaviour. Data crossing it should be treated according to the weaker side's guarantees. “Internal” is not synonymous with “trusted”: internal producers can be buggy, compromised, stale, or operated under different policy.

**Least authority** means granting a component only the operations and resources required for its task. A report generator that needs to read one input directory and write one output directory should not require unrestricted access to all user files. Python objects can express capabilities at a small scale: accepting an already-open readable stream grants less pathname-resolution power than accepting an arbitrary path; accepting a callback dedicated to one operation grants less than accepting an entire service object.

Compare:

~~~python
def count_records_from_path(path_text: str) -> int:
    with open(path_text, encoding="utf-8") as stream:
        return sum(1 for _ in stream)
~~~

and:

~~~python
from collections.abc import Iterable


def count_records(lines: Iterable[str]) -> int:
    return sum(1 for _ in lines)
~~~

The second function has no direct authority to choose or open filesystem objects. Its caller retains that decision. This does not create an operating-system security sandbox—an arbitrary Python object could execute effects from its iterator methods—but it improves ordinary architectural accountability and testability.

Pathnames supplied by an untrusted party, archive members, environment variables, configuration values, and serialised class identifiers are all authority-bearing when later used to select resources or code. Validation must address the eventual interpretation, not merely the surface string.

### 11.1.11 Chapter claim ledger

Because boundary behaviour varies by interface, implementation, platform, and failure model, this chapter labels the kind of claim being made:

| Claim category | Meaning | Example in this chapter |
|---|---|---|
| definition | stipulated technical meaning used consistently | a text stream translates between strings and bytes under an encoding |
| derivation | conclusion following from stated premises | if retry can follow an unobserved commit, non-idempotent effects can duplicate |
| language rule | behaviour required by Python's language reference | a <code>with</code> statement invokes the context-management protocol |
| library specification | documented public-library contract | <code>json.dump</code> writes text, not bytes |
| implementation fact | behaviour of a named implementation/version | CPython uses particular buffered I/O classes in the usual <code>open</code> stack |
| operating-system or filesystem property | platform-qualified external contract | replacement of one directory entry may be atomic under documented conditions |
| empirical observation | measured result under recorded conditions | a chosen buffer size produced a measured throughput on one machine |
| modelling assumption | deliberate simplification required for reasoning | no other writer changes the test fixture during one test |
| substantive judgement | design recommendation supported by trade-offs | reject unknown financial-transfer fields under a strict versioned interface |

These categories prevent an experiment from masquerading as a specification and prevent a platform-specific fact from masquerading as Python semantics. Whenever a later result varies, first ask whether the disagreement concerns the same category and the same named conditions.

### 11.1.12 A complete boundary walk-through

The following example receives bytes representing one command, limits size, decodes strictly, parses JSON, validates schema and domain semantics, and calls a pure core. It deliberately stops before persistence or authentication, which would require additional contracts.

~~~python
import json
from dataclasses import dataclass
from decimal import Decimal, InvalidOperation


MAX_COMMAND_BYTES = 4_096


@dataclass(frozen=True, slots=True)
class PriceCommand:
    product_id: str
    price: Decimal


def decode_command(raw: bytes) -> PriceCommand:
    if len(raw) > MAX_COMMAND_BYTES:
        raise InputTooLarge(
            f"command is {len(raw)} bytes; maximum is {MAX_COMMAND_BYTES}"
        )

    try:
        text = raw.decode("utf-8", errors="strict")
    except UnicodeDecodeError as error:
        raise ValueError(
            f"command is not UTF-8 near byte {error.start}"
        ) from error

    try:
        document = json.loads(text)
    except json.JSONDecodeError as error:
        raise ValueError(
            f"command is not JSON at line {error.lineno}, "
            f"column {error.colno}"
        ) from error

    if not isinstance(document, dict):
        raise ValueError("command must be an object")
    if set(document) != {"product_id", "price"}:
        raise ValueError("command has missing or unknown fields")

    product_id = document["product_id"]
    price_text = document["price"]
    if not isinstance(product_id, str) or not product_id:
        raise ValueError("product_id must be a non-empty string")
    if not isinstance(price_text, str):
        raise ValueError("price must be a decimal string")

    try:
        price = Decimal(price_text)
    except InvalidOperation as error:
        raise ValueError("price is not a decimal numeral") from error
    if not price.is_finite() or price < 0:
        raise ValueError("price must be finite and non-negative")

    return PriceCommand(product_id=product_id, price=price)
~~~

The price is represented in JSON as a string by schema decision. This avoids first parsing it as a binary floating-point value and then converting an already-rounded approximation. The decision transfers responsibility to an explicit decimal lexical grammar. If exponential notation, maximum scale, or leading zeroes matter, further validation is required.

The maximum is enforced on received bytes, not characters. The decoded string can have at most the same number of Unicode code points as UTF-8 bytes, but Python object memory is not thereby limited to 4,096 bytes; object representation and parsed structures add overhead. A robust service applies budgets at multiple layers.

The pure downstream rule can now depend on a <code>PriceCommand</code>:

~~~python
from decimal import ROUND_HALF_EVEN


PENNY = Decimal("0.01")


def price_including_tax(command: PriceCommand, rate: Decimal) -> Decimal:
    if not rate.is_finite() or not Decimal("0") <= rate <= Decimal("1"):
        raise ValueError("tax rate must be finite and lie in 0..1")
    gross = command.price * (Decimal("1") + rate)
    return gross.quantize(PENNY, rounding=ROUND_HALF_EVEN)
~~~
