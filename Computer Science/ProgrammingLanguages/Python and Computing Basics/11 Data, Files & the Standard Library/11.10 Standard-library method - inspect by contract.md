# 11.10 Standard-library method: inspect by contract

The Python standard library is too broad to memorise as an undifferentiated function catalogue. Systematic use begins with five questions:

1. What abstraction does the module own?
2. Which input and output types define its boundary?
3. Is operation eager or lazy?
4. Which effects, exceptions, and resource lifetimes occur?
5. Which costs, ordering, platform, and thread-safety guarantees are documented?

Read module documentation, then inspect signatures and construct boundary experiments. Do not infer general behaviour from one function name.

### 11.10.1 Documentation has levels of authority

When determining behaviour, distinguish:

1. the Python language reference, which specifies language syntax and semantics;
2. standard-library documentation for the supported Python version;
3. a PEP or external standard that supplies design rationale or protocol rules;
4. type annotations and signatures, which describe accepted call shapes but not every semantic condition;
5. implementation source, which explains one implementation and version;
6. experiments, which demonstrate observations under recorded conditions;
7. tutorials, discussions, and remembered folklore, which can guide search but are not authoritative contracts.

An implementation detail can be indispensable for performance work while remaining unsafe as a portability assumption. Conversely, a specification can deliberately leave a choice open, requiring measurement on each target.

Version selection matters. Reading Python 3.14 documentation while supporting 3.12 can lead to use of new APIs or changed defaults. A project should record a minimum and maximum tested version range and consult each relevant version's change notes.

### 11.10.2 Build a contract card

For any function or class central to a system, write a compact **contract card**:

| Question | Example for <code>json.loads</code> |
|---|---|
| accepted representation | <code>str</code>, <code>bytes</code>, or <code>bytearray</code> containing one JSON document |
| returned representation | nested Python values under configured hooks |
| effects | allocates objects; invokes supplied hooks |
| failure classes | decoding, JSON syntax, hook, integer-limit, and resource failures |
| eager/lazy | eager construction of one result graph |
| ordering | exposes member order through dictionaries under current documented behaviour |
| limits | application must impose appropriate encoded, structural, and semantic budgets |
| trust | data-only parser, but hostile inputs can exhaust resources |
| version dependencies | default hooks and runtime numeric safeguards can evolve |

The card is not a substitute for full documentation. It records precisely the dimensions the application relies upon and becomes a review/test checklist.

### 11.10.3 Signatures describe calls, not complete meaning

<code>inspect.signature</code> reveals parameters and defaults for many Python callables:

~~~python
from inspect import signature
import json


print(signature(json.dumps))
~~~

A signature can show that <code>allow_nan</code> is keyword-only and has a default. It cannot explain why non-finite numbers harm JSON interoperability, whether a callable releases the GIL, or how deeply it traverses a graph.

<code>help</code>, <code>__doc__</code>, annotations, and <code>dir</code> support interactive discovery:

~~~python
help(json.JSONDecoder)
print(json.dumps.__doc__)
~~~

These values come from the installed runtime and can differ from online documentation. Record <code>sys.version</code> when a finding depends on the local environment.

Reflection can itself invoke user-defined behaviour. <code>getattr</code> can run a descriptor or <code>__getattr__</code>; <code>repr</code> can execute arbitrary method code. “Inspecting an object” is not necessarily effect-free when the object is untrusted.

### 11.10.4 Minimal boundary experiments

A **boundary experiment** isolates one uncertain claim with the smallest relevant input and records observed result, exception type, and environment:

~~~python
import csv
from io import StringIO
import sys


def observe_duplicate_header() -> None:
    reader = csv.DictReader(StringIO("x,x\n1,2\n"))
    print(next(reader))
    print(sys.version)
~~~

This can establish what the installed runtime did with duplicate header names. It cannot by itself establish future compatibility or application acceptability. After observing, locate the corresponding specification or label the result empirical.

Good experiments include:

- a normal case;
- empty and boundary-sized inputs;
- one case just outside each bound;
- malformed and partially valid representations;
- failure during acquisition, iteration, and release;
- aliases or repeated references where identity matters;
- platform variants when the contract is platform-dependent.

Avoid large exploratory scripts whose output depends on several undocumented variables. An experiment should falsify one hypothesis cleanly.

### 11.10.5 Read cost words carefully

Documentation uses terms such as “efficient”, “approximately \(O(1)\)”, “thread-safe”, “atomic”, and “may”. Each has a scope.

- \(O(1)\) describes asymptotic growth, not zero time or a universal fixed latency.
- “Thread-safe append” does not make a read-check-write sequence atomic.
- “Atomic rename” does not imply durable file contents.
- “May cache” forbids dependence on either caching or non-caching.
- “Implementation detail” can change without the compatibility treatment given to a public contract.

When documentation is silent about an ordering, complexity, or concurrency property, do not manufacture a guarantee from an observed implementation. Either avoid depending on it, constrain the environment, or test and label the dependency.

### 11.10.6 Source reading and implementation archaeology

Reading source can explain how a function fulfils its contract and reveal performance constants, internal caching, and exception paths. For a Python implementation, inspect the source corresponding to the exact release tag, including C or Rust components where applicable.

Source establishes an implementation fact. A patch release can change it if public behaviour remains compatible. Write implementation-sensitive code only when the benefit justifies:

- pinning and testing interpreter versions;
- maintaining alternate paths;
- benchmarking realistic workloads;
- monitoring release notes;
- documenting which assumption is non-portable.

A comment such as “CPython 3.12 list append is implemented here in amortised constant time” is more honest than “Python always does this”.

### 11.10.7 Create evidence, not cargo cult

An API-selection record should connect requirement to evidence:

~~~text
Requirement:
    Consume a potentially million-record source without retaining all rows.

Selected abstraction:
    csv.reader over a text stream, one validated record at a time.

Evidence:
    reader iteration is lazy at the record interface; application aggregate
    retains at most 10,000 distinct keys; field size and total record count
    are bounded.

Rejected shortcut:
    list(reader), because it retains every parsed row.

Residual risk:
    one logical CSV record may span physical lines and approach the configured
    field/count limits; storage and decoder buffering add overhead.
~~~

This is more durable than memorising “generators save memory”. The reasoning names what is lazy, what remains bounded, and what still allocates.

> **Common misconception 11.30 — “The implementation source is the Python specification.”** Source explains one implementation and version. Public portability follows documented contracts unless a project explicitly accepts an implementation dependency.
