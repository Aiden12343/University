# 11.11 `collections`

`collections` supplies specialised containers.

### `deque`

A `deque` is a double-ended queue with efficient appends and pops at both ends. Indexed access near the middle is not its purpose.

```python
from collections import deque

pending = deque(["A", "B"])
pending.append("C")
current = pending.popleft()
```

With `maxlen`, adding beyond the bound discards items from the opposite end. This is a lossy bounded-history policy, not an exception.

### `Counter`

`Counter` is a dictionary subclass for hashable-item counts:

```python
from collections import Counter

counts = Counter("abracadabra")
print(counts["a"])
print(counts["z"])
```

Missing keys return zero under lookup, but zero and negative counts can remain stored after arithmetic. `elements()` and set-like counter operations apply their own rules. A Counter is a multiset-like tool, not automatically a validated probability distribution.

### `defaultdict`

`defaultdict(factory)` calls its factory on missing-key subscription and stores the result:

```python
from collections import defaultdict

groups: defaultdict[str, list[int]] = defaultdict(list)
groups["even"].append(2)
```

`.get` does not invoke the default factory. Merely reading a missing key through subscription mutates the mapping, which matters for debugging and concurrent code.

### `namedtuple`

`namedtuple` creates tuple subclasses with named fields. Dataclasses offer a broader class-generation model; named tuples remain valuable for lightweight immutable positional records and tuple interoperability.

### 11.11.1 Select by operations and invariants

A specialised container exists because the same mathematical contents can support different operations and policies. Selection begins with:

- which end or key is accessed;
- whether order matters;
- whether duplicates matter;
- whether missing values should mutate state;
- whether size is bounded;
- whether aliases to underlying mappings should remain live;
- which asymptotic and constant-factor costs dominate.

“Use a list for a collection” is underspecified. A stack, queue, multiset, cache, scope chain, and immutable positional record have different invariants even when all could be forced into a list or dictionary.

### 11.11.2 <code>deque</code> as a double-ended sequence

<code>deque</code> supports approximately constant-time appends and pops at either end. A list supports approximately constant-time append/pop at its right end but requires shifting references for insertion or removal at its left, producing linear work in its length.

~~~python
from collections import deque


queue: deque[str] = deque()
queue.append("first")
queue.append("second")

assert queue.popleft() == "first"
assert queue.popleft() == "second"
~~~

This is first-in, first-out (FIFO) queue behaviour. A stack uses <code>append</code> and <code>pop</code> on the same end, producing last-in, first-out (LIFO) behaviour.

Random indexing is efficient near either end but slows towards the middle. If an algorithm repeatedly indexes arbitrary positions, a list is usually the more appropriate sequence. If it repeatedly removes from the left, a deque is usually appropriate.

<code>extendleft</code> adds each input item to the left and therefore reverses their iteration order:

~~~python
values = deque([3])
values.extendleft([1, 2])

assert list(values) == [2, 1, 3]
~~~

The method's name says which end receives items, not that the source sequence's left-to-right order is preserved.

Rotation moves items cyclically:

~~~python
ring = deque(["A", "B", "C", "D"])
ring.rotate(1)
assert list(ring) == ["D", "A", "B", "C"]
ring.rotate(-2)
assert list(ring) == ["B", "C", "D", "A"]
~~~

Large rotations are normalised by the implementation, but algorithm design should not depend on an undocumented internal representation.

### 11.11.3 Bounded deques encode eviction

A positive <code>maxlen</code> fixes the maximum element count:

~~~python
history = deque(maxlen=3)
for value in [10, 20, 30, 40]:
    history.append(value)

assert list(history) == [20, 30, 40]
~~~

Appending on the right evicts from the left when full. Appending on the left evicts from the right. This silent eviction is useful for rolling history and moving windows, but it is data loss by policy.

<code>insert</code> into a full bounded deque raises rather than evicting because insertion at an arbitrary position has no unambiguous opposite item. Callers should not assume every mutator shares append's overflow policy.

A rolling mean can update in constant aggregate space:

~~~python
from collections import deque


class RollingMean:
    def __init__(self, width: int) -> None:
        if width <= 0:
            raise ValueError("width must be positive")
        self.values: deque[float] = deque()
        self.width = width
        self.total = 0.0

    def add(self, value: float) -> float:
        if len(self.values) == self.width:
            self.total -= self.values.popleft()
        self.values.append(value)
        self.total += value
        return self.total / len(self.values)
~~~

The result inherits binary floating-point rounding. For financial decimals, use a decimal type and define precision. The state invariant is

\[
\texttt{total} = \sum_{x \in \texttt{values}}x
\quad\text{and}\quad
0 < |\texttt{values}| \leq \texttt{width}
\]

after at least one addition.

Individual deque append/pop operations have documented thread-safety properties in CPython's library contract, but a compound “if non-empty, then pop” sequence can interleave with another thread. Chapter 14 develops concurrency.

> **Common misconception 11.31 — “A bounded deque raises when append would overflow.”** It discards from the opposite end. Overflow semantics are part of the container's policy.

### 11.11.4 <code>Counter</code> is a signed count mapping

<code>Counter</code> generalises a multiset by permitting zero and negative counts:

~~~python
from collections import Counter


stock = Counter(apples=3, pears=1)
stock.subtract({"apples": 4, "oranges": 2})

assert stock["apples"] == -1
assert stock["oranges"] == -2
assert stock["missing"] == 0
~~~

Missing-key subscription returns zero without inserting the key:

~~~python
before = set(stock)
_ = stock["unknown"]
assert set(stock) == before
~~~

Assigning zero leaves a stored entry until deletion:

~~~python
stock["pears"] = 0
assert "pears" in stock
del stock["pears"]
assert "pears" not in stock
~~~

Unary plus creates a Counter retaining only positive counts; unary minus negates and retains resulting positives. Binary operations have multiset-oriented policies:

~~~python
left = Counter(a=3, b=-1)
right = Counter(a=1, b=4)

assert +(left - right) == Counter(a=2)
assert left | right == Counter(a=3, b=4)
assert left & right == Counter(a=1)
~~~

The union and intersection use maximum and minimum positive counts under Counter semantics; they are not dictionary merge and set operations on keys alone.

<code>most_common</code> sorts by count, preserving first-encounter order for equal counts under current documented behaviour:

~~~python
counts = Counter("cabca")
assert counts.most_common() == [("c", 2), ("a", 2), ("b", 1)]
~~~

If tie order is a domain requirement independent of encounter order, sort with an explicit secondary key.

<code>total</code> sums counts including negative ones. A Counter with negative values is not a probability distribution or valid inventory until corresponding invariants are checked.

### 11.11.5 <code>defaultdict</code> moves construction into lookup

A <code>defaultdict</code> invokes its <code>default_factory</code> only when <code>__getitem__</code> encounters a missing key:

~~~python
from collections import defaultdict


groups: defaultdict[str, list[int]] = defaultdict(list)
groups["odd"].append(1)

assert groups == {"odd": [1]}
assert groups.get("even") is None
assert "even" not in groups
~~~

Calling <code>groups["even"]</code> would create and store a new list. Calling <code>get</code>, membership testing, or iteration does not invoke <code>__missing__</code>. This difference matters when a read should not mutate state.

The factory receives no key:

~~~python
serials: defaultdict[str, int] = defaultdict(lambda: 1000)
assert serials["north"] == 1000
~~~

If initial value depends on the key, use explicit logic or a custom mapping. A closure factory can refer to external mutable state, making a missing lookup unexpectedly effectful.

A common nested grouping pattern is:

~~~python
matrix: defaultdict[str, defaultdict[str, list[int]]] = defaultdict(
    lambda: defaultdict(list)
)
matrix["north"]["temperature"].append(18)
~~~

Convenience can hide deep mutation and accidental key creation. For public domain models, named methods often communicate allowable dimensions and validate them more clearly.

> **Common misconception 11.32 — “Every missing-key operation invokes a defaultdict factory.”** Only subscription through <code>__getitem__</code> engages its missing-key mechanism; <code>get</code> does not.

### 11.11.6 <code>ChainMap</code> is a live layered view

<code>ChainMap</code> searches several mappings from first to last without copying them:

~~~python
from collections import ChainMap


defaults = {"colour": "blue", "timeout": 30}
environment = {"timeout": 10}
command_line = {"colour": "red"}

settings = ChainMap(command_line, environment, defaults)

assert settings["colour"] == "red"
assert settings["timeout"] == 10
~~~

Writes and deletions affect only the first mapping:

~~~python
settings["timeout"] = 5
assert command_line["timeout"] == 5
assert environment["timeout"] == 10
~~~

Underlying mappings are retained by reference. Later changes become visible:

~~~python
defaults["retries"] = 3
assert settings["retries"] == 3
~~~

This live view differs from merging copies:

~~~python
merged = defaults | environment | command_line
~~~

The merge takes a snapshot of key/value references at that time and follows right-operand precedence. ChainMap's search order is explicit left-to-right precedence.

<code>new_child</code> prepends a writable mapping, modelling nested scopes:

~~~python
global_scope = ChainMap({"x": 1})
local_scope = global_scope.new_child({"y": 2})

assert local_scope["x"] == 1
local_scope["x"] = 99
assert local_scope.maps[0]["x"] == 99
assert global_scope["x"] == 1
~~~

Deleting <code>x</code> from <code>local_scope</code> now removes only the local shadow, revealing the parent value. This is useful for configuration and interpreters but can surprise code expecting deletion of the first found key.

### 11.11.7 <code>namedtuple</code> and typed named tuples

A named tuple is a tuple subclass whose positions also have field names:

~~~python
from collections import namedtuple


Point = namedtuple("Point", ["x", "y"], defaults=[0])
point = Point(3)

assert point.x == 3
assert point.y == 0
assert point[0] == 3
assert tuple(point) == (3, 0)
~~~

It is immutable in the same shallow sense as a tuple: fields cannot be rebound, but a mutable object stored in a field can still change. <code>_replace</code> returns a new instance, <code>_asdict</code> returns a mapping of fields to values, and <code>_fields</code> exposes field names.

<code>typing.NamedTuple</code> gives static field types with class syntax:

~~~python
from typing import NamedTuple


class Coordinate(NamedTuple):
    latitude: float
    longitude: float
    label: str = ""
~~~

Named tuples compare as tuples. Two unrelated named-tuple classes with equal positional values can compare equal, which may be inappropriate for strong domain types. Dataclasses compare under different class-sensitive generated rules and support more configuration. Choose a named tuple when tuple protocol and compact immutable positional semantics are genuinely desired.

### 11.11.8 <code>OrderedDict</code> after ordered <code>dict</code>

Ordinary dictionaries preserve insertion order as a language guarantee in modern Python, but <code>OrderedDict</code> retains specialised ordering operations:

~~~python
from collections import OrderedDict


cache = OrderedDict([("A", 1), ("B", 2), ("C", 3)])
cache.move_to_end("A")
assert list(cache) == ["B", "C", "A"]

oldest_key, oldest_value = cache.popitem(last=False)
assert (oldest_key, oldest_value) == ("B", 2)
~~~

These operations support least-recently-used-like policies. Implementing a correct cache additionally requires capacity validation, refresh policy, exception semantics, and concurrency control; <code>functools.lru_cache</code> is often preferable for pure function results.

Equality between two OrderedDict instances is order-sensitive. Equality between an OrderedDict and another mapping follows mapping-like comparison, so reviewers should not assume one equality rule across operand types.

### 11.11.9 Wrapper containers for controlled specialisation

Subclassing built-in <code>dict</code>, <code>list</code>, or <code>str</code> can be subtle because some built-in operations may bypass overridden methods. <code>UserDict</code>, <code>UserList</code>, and <code>UserString</code> wrap underlying data in Python-level classes intended for easier specialisation.

~~~python
from collections import UserDict


class NormalisedKeys(UserDict[str, int]):
    @staticmethod
    def normalise(key: str) -> str:
        return key.casefold()

    def __getitem__(self, key: str) -> int:
        return super().__getitem__(self.normalise(key))

    def __setitem__(self, key: str, value: int) -> None:
        super().__setitem__(self.normalise(key), value)


counts = NormalisedKeys()
counts["Alpha"] = 1
assert counts["ALPHA"] == 1
~~~

The example is not a complete caseless identifier mapping. It must normalise consistently in containment, deletion, update, initialisation, merge, and every key-taking method; Unicode normalisation and collision policy remain. A composition-based domain class exposing only required operations is often safer.

### 11.11.10 Complexity and memory are workload claims

The principal container choices can be summarised:

| Need | Candidate | Important limitation |
|---|---|---|
| FIFO queue in one thread | <code>deque</code> | no blocking/coordination; middle indexing is linear |
| bounded recent history | bounded <code>deque</code> | silent eviction |
| frequency or signed inventory deltas | <code>Counter</code> | zero/negative entries require domain policy |
| automatic per-key accumulator | <code>defaultdict</code> | missing subscription mutates |
| layered lookup without copying | <code>ChainMap</code> | writes affect first mapping only |
| immutable positional record with names | <code>namedtuple</code> | tuple equality and shallow immutability |
| reorderable mapping | <code>OrderedDict</code> | not needed for insertion order alone |

Asymptotic complexity does not determine memory layout or constant factors. Measure large representative workloads after selecting the semantically correct abstraction. Chapter 13 derives complexity formally; here it suffices to avoid an operation whose cost grows in the wrong dimension.

> **Common misconception 11.33 — “A specialised container is always faster.”** It encodes a different operation set and policy. Performance depends on the actual operation distribution, sizes, and implementation.
