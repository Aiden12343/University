# 11.12 `itertools`

`itertools` supplies lazy iterator building blocks designed for composition.

```python
from itertools import chain, islice

combined = chain(range(3), range(10, 13))
print(list(islice(combined, 4)))
print(list(combined))
```

The first materialisation consumes 0, 1, 2, 10. The same chained iterator retains its position, so the second produces 11, 12.

Important categories:

- finite combinators: `chain`, `accumulate`, `pairwise`, `batched`;
- selectors/groupers: `compress`, `filterfalse`, `groupby`, `islice`, `takewhile`;
- combinatorics: `product`, `permutations`, `combinations`;
- potentially infinite sources: `count`, `cycle`, `repeat` without a bound.

`groupby` groups only consecutive equal keys, not all equal keys globally. Sort first when global grouping is required and ordering cost is acceptable.

```python
from itertools import groupby

values = ["A", "A", "B", "A"]
for key, group in groupby(values):
    print(key, list(group))
```

This produces three groups: A, B, A. Each `group` iterator shares the underlying source and must be consumed or materialised before the outer iterator advances if retained contents are required.

### 11.12.1 Laziness defers work; it does not abolish cost

An iterator-producing function can return before consuming its input. Computation then occurs as downstream code requests elements. This changes *when* effects and failures happen:

~~~python
from itertools import islice


def observed_numbers() -> object:
    for number in range(5):
        print(f"produce {number}")
        yield number


pipeline = (number * number for number in observed_numbers())
first_two = list(islice(pipeline, 2))
~~~

Constructing <code>pipeline</code> produces no numbers. Materialising the slice requests two, which triggers two prints and two multiplications. The remaining iterator retains its position.

Laziness can:

- avoid computing unused suffixes;
- bound retained elements in a single-pass pipeline;
- support infinite conceptual sequences;
- propagate downstream backpressure.

It can also:

- delay errors far from construction;
- retain resources in suspended generators;
- repeat effects if a reusable iterable is iterated again;
- make one-shot consumption easy to overlook;
- conceal internal caching in utilities such as <code>cycle</code> and <code>tee</code>.

The correct question is not “is this lazy?” but “what input is consumed, what state is retained, and when?”

### 11.12.2 Concatenation and flattening

<code>chain</code> traverses each input iterable fully before moving to the next:

~~~python
from itertools import chain


combined = chain([1, 2], (3, 4), range(5, 7))
assert list(combined) == [1, 2, 3, 4, 5, 6]
~~~

<code>chain.from_iterable</code> accepts one iterable of iterables and obtains inner iterables lazily:

~~~python
batches = ([number, -number] for number in range(3))
flattened = chain.from_iterable(batches)

assert list(flattened) == [0, 0, 1, -1, 2, -2]
~~~

This flattens exactly one level. A string is iterable, so accidentally supplying strings as batches yields characters. Recursive flattening is not well-defined without rules for atomic container types, cycle detection, and maximum depth.

### 11.12.3 Slicing consumes positions

<code>islice</code> applies non-negative start, stop, and step positions to an iterable:

~~~python
from itertools import islice


source = iter(range(20))
selected = list(islice(source, 2, 10, 3))

assert selected == [2, 5, 8]
assert next(source) == 10
~~~

Fully consuming this slice advances the underlying iterator to the stop position, not merely by the number of yielded values. Skipped elements are consumed and unavailable. Negative indices are unsupported because finding an item relative to the end would generally require exhausting or buffering the source.

An unbounded stop is useful for discarding a prefix:

~~~python
tail = islice(source, 5, None)
~~~

If <code>source</code> is infinite, <code>tail</code> is infinite. Every terminal consumer must supply a stopping condition.

### 11.12.4 Prefix predicates consume a boundary element

<code>takewhile(predicate, source)</code> yields the longest prefix satisfying the predicate and consumes the first failing item:

~~~python
from itertools import takewhile


source = iter([1, 2, 3, 0, 4])
prefix = list(takewhile(lambda value: value > 0, source))

assert prefix == [1, 2, 3]
assert next(source) == 4
~~~

The zero is gone. If it belongs to the next parser phase, use a lookahead abstraction that preserves it. <code>dropwhile</code> likewise consumes while a predicate is true, then yields the first false item and every later item without further predicate filtering:

~~~python
from itertools import dropwhile


assert list(dropwhile(lambda value: value < 3, [1, 2, 4, 1])) == [4, 1]
~~~

This differs from <code>filterfalse</code>, which tests every item:

~~~python
from itertools import filterfalse


assert list(filterfalse(lambda value: value < 3, [1, 2, 4, 1])) == [4]
~~~

Prefix operators encode state transitions; filters encode per-item selection.

> **Common misconception 11.34 — “<code>takewhile</code> leaves the first failing item for later.”** It must consume that item to discover the boundary.

### 11.12.5 Grouping means runs, not global equivalence classes

<code>groupby</code> partitions adjacent runs for which the key value remains equal:

~~~python
from itertools import groupby
from operator import itemgetter


records = [
    ("north", 1),
    ("north", 2),
    ("south", 3),
    ("north", 4),
]

runs = [
    (key, list(group))
    for key, group in groupby(records, key=itemgetter(0))
]
~~~

There are two <code>north</code> runs. Sorting by the same key first produces global grouping at \(O(n \log n)\) comparison cost and \(O(n)\) materialisation for an arbitrary iterable:

~~~python
ordered = sorted(records, key=itemgetter(0))
groups = [
    (key, list(group))
    for key, group in groupby(ordered, key=itemgetter(0))
]
~~~

If input is already sorted by contract, <code>groupby</code> supports one-pass aggregation with one current group. If it is not, a dictionary-based aggregation can run in expected linear time while retaining one entry per distinct key. These algorithms have different ordering, memory, and input requirements.

Group iterators share the outer source:

~~~python
outer = groupby("AAABBC")
key_a, group_a = next(outer)
key_b, group_b = next(outer)

assert list(group_a) == []
assert list(group_b) == ["B", "B"]
~~~

Advancing <code>outer</code> consumes the remainder of the previous group to find the next boundary. Materialise or process each group before advancing.

> **Common misconception 11.35 — “<code>groupby</code> behaves like SQL <code>GROUP BY</code>.”** It groups consecutive equal keys. Global grouping requires preordering or another aggregation structure.

### 11.12.6 Duplication with <code>tee</code> can buffer without bound

<code>tee(source, n)</code> creates iterators that independently traverse one source by storing values needed by lagging branches:

~~~python
from itertools import tee


left, right = tee(range(5), 2)
assert next(left) == 0
assert next(left) == 1
assert next(right) == 0
~~~

When <code>left</code> moves ahead, values remain buffered until <code>right</code> consumes them. If one branch processes a billion elements while another remains idle, retained storage can grow correspondingly. If one branch will be fully consumed before the other begins, materialising a finite source once can be more transparent.

The derived iterators are not generally threadsafe for concurrent use. <code>tee</code> duplicates traversal, not the external effects that already occurred in obtaining a source item. A source reading a network still reads each item once; branches receive buffered references to the same yielded objects.

Mutating one shared yielded object affects what the other branch later sees:

~~~python
source = iter([[1], [2]])
left, right = tee(source)
item = next(left)
item.append(99)

assert next(right) == [1, 99]
~~~

<code>tee</code> does not deep-copy values.

### 11.12.7 Infinite iterators require explicit termination

<code>count</code>, <code>cycle</code>, and an unbounded <code>repeat</code> can produce indefinitely:

~~~python
from itertools import count, cycle, repeat


identifiers = count(start=1)
colours = cycle(["red", "green", "blue"])
padding = repeat(None)
~~~

Calling <code>list</code>, <code>tuple</code>, <code>sum</code>, or an unbounded loop on these streams does not terminate under ordinary arithmetic and available resources.

<code>cycle</code> must save values from its first pass so it can replay a one-shot input. Cycling a very large finite source therefore retains that source's yielded references. Cycling an infinite source never reaches replay and can keep accumulating values indefinitely.

Floating-point <code>count(start, step)</code> repeatedly adds and can accumulate rounding error. A multiplicative expression such as <code>start + step * index</code> can sometimes improve error characteristics; exact requirements may call for integers, fractions, or decimals.

### 11.12.8 Accumulation exposes every prefix result

<code>accumulate</code> applies a binary function and yields each intermediate state:

~~~python
from itertools import accumulate
from operator import mul


assert list(accumulate([2, 3, 4], mul)) == [2, 6, 24]
assert list(accumulate([2, 3], initial=10)) == [10, 12, 15]
~~~

With <code>initial</code>, output has one more element than input. Without it, empty input yields no elements.

The binary function need not be associative:

~~~python
assert list(accumulate([10, 3, 2], lambda total, value: total - value)) == [
    10,
    7,
    5,
]
~~~

Order and grouping then matter. A stateful or effectful combining function also runs once per later input only as output is consumed.

Running minima, maxima, balance projections, and finite-state transitions are natural uses. If only the final result matters, a loop or <code>reduce</code> may be clearer and avoids exposing intermediate states.

### 11.12.9 Pairwise and change detection

<code>pairwise</code> produces overlapping adjacent pairs:

~~~python
from itertools import pairwise


temperatures = [18.0, 18.5, 17.0, 20.0]
changes = [
    current - previous
    for previous, current in pairwise(temperatures)
]

assert changes == [0.5, -1.5, 3.0]
~~~

An input of length zero or one produces no pair. Values are retained by reference just long enough to overlap. Pairwise comparison does not sort timestamps or account for missing intervals; those are domain requirements.

### 11.12.10 Batching and incomplete final groups

Python 3.12's <code>itertools.batched(source, n)</code> lazily yields tuples of at most \(n\) items:

~~~python
from itertools import batched


assert list(batched(range(7), 3)) == [
    (0, 1, 2),
    (3, 4, 5),
    (6,),
]
~~~

The shorter final tuple is part of the 3.12 contract. Later Python versions add options affecting incomplete batches; a library supporting 3.12 must not assume those parameters exist.

Reject an incomplete final batch explicitly:

~~~python
def complete_batches(source: object, width: int) -> object:
    if width <= 0:
        raise ValueError("width must be positive")
    for batch_number, batch in enumerate(batched(source, width), start=1):
        if len(batch) != width:
            raise ValueError(
                f"batch {batch_number} has {len(batch)} of {width} items"
            )
        yield batch
~~~

Earlier complete batches may already have been processed when the error is discovered. If all-or-nothing semantics are required, validate size before effects or stage them.

### 11.12.11 Lockstep traversal and missing values

Built-in <code>zip</code> stops at the shortest input by default. <code>strict=True</code> instead raises if lengths differ:

~~~python
names = ["A", "B"]
scores = [10, 20]

assert list(zip(names, scores, strict=True)) == [
    ("A", 10),
    ("B", 20),
]
~~~

Use strict mode when equal lengths are an invariant; silent truncation can discard data.

<code>zip_longest</code> continues to the longest input and inserts a fill value:

~~~python
from itertools import zip_longest


MISSING = object()
pairs = list(zip_longest([1, 2], ["A"], fillvalue=MISSING))

assert pairs[1][1] is MISSING
~~~

A unique sentinel distinguishes missing from legitimate <code>None</code>. If one input can be infinite, <code>zip_longest</code> is also infinite unless bounded.

### 11.12.12 Combinatorial iterators can produce enormous outputs

Given \(n\) input positions and result length \(r\):

\[
|\operatorname{product}(A_1,\dots,A_k)| = \prod_{i=1}^{k}|A_i|,
\]

\[
P(n,r)=\frac{n!}{(n-r)!},
\qquad
C(n,r)=\frac{n!}{r!(n-r)!}.
\]

These formulas count product tuples, permutations, and combinations respectively under their positional semantics. Laziness prevents storing every output simultaneously but does not reduce how many outputs exist if all are consumed.

~~~python
from itertools import combinations, permutations, product
from math import comb, perm


items = range(20)
assert sum(1 for _ in combinations(items, 10)) == comb(20, 10)
assert sum(1 for _ in permutations(range(8), 4)) == perm(8, 4)
assert len(list(product(range(3), repeat=4))) == 3**4
~~~

The first counting loop performs 184,756 iterations merely to confirm the formula; production code should calculate the count first and reject infeasible generation. Inputs are treated as distinct by position, so duplicate values can yield duplicate-looking tuples.

<code>product</code>, <code>permutations</code>, and <code>combinations</code> first pool finite input values because repeated access is required. They are not suitable for infinite input sources.

> **Common misconception 11.36 — “A lazy combinatorial iterator makes an exponential search cheap.”** Laziness controls retention and permits early stopping; exhaustive consumption still has combinatorial output cost.

### 11.12.13 Composing an iterator algebra

Iterator utilities become most valuable when each stage owns one transformation:

~~~python
from itertools import chain, islice


def positive_integers(lines: object) -> object:
    stripped = (line.strip() for line in lines)
    non_empty = (line for line in stripped if line)
    parsed = (int(line) for line in non_empty)
    return (value for value in parsed if value > 0)


with Path("numbers.txt").open("r", encoding="utf-8") as stream:
    preview = list(islice(positive_integers(stream), 10))
~~~

Each stage is lazy; conversion failure occurs when the bad line is requested. This concise pipeline loses line-number provenance. A more diagnostic generator loop can be superior:

~~~python
def positive_integers_with_location(lines: object) -> object:
    for line_number, line in enumerate(lines, start=1):
        text = line.strip()
        if not text:
            continue
        try:
            value = int(text)
        except ValueError as error:
            raise ValueError(
                f"line {line_number}: invalid integer {text[:40]!r}"
            ) from error
        if value > 0:
            yield value
~~~

Functional composition is not automatically clearer. Choose the expression that preserves domain context, ownership, and failure semantics.

### 11.12.14 Side effects and repeated consumption

Iterator pipelines are easiest to reason about when transformations are pure. If mapping sends emails or mutates a database, partial consumption creates partial effects:

~~~python
actions = (send_notice(address) for address in addresses)
first_ten_results = list(islice(actions, 10))
~~~

Only ten notices are attempted. If the ninth raises, eight might already be sent. Reconstructing the generator and retrying can duplicate them. The same partial-failure analysis as files applies.

Use iterators to *describe* pending commands as values, then execute them through an idempotent or transactional boundary where possible. Do not confuse a lazy expression with a rollback mechanism.
