# 11.13 `functools`

`functools` supplies higher-order function tools.

`partial` fixes selected arguments:

```python
from functools import partial


def power(base: int, exponent: int) -> int:
    return base**exponent


square = partial(power, exponent=2)
print(square(7))
```

The returned callable retains references to the original function and supplied arguments. Mutable retained arguments remain shared.

`reduce` repeatedly combines items, but a named loop or specialised `sum`, `min`, `max`, or `math.prod` is often clearer. A reduction requires an associative-like reasoning contract when parallelisation or grouping changes are contemplated.

`cache` and `lru_cache` memoise calls, carrying the state and staleness obligations discussed in Chapter 8. `singledispatch` selects implementations by the runtime type of the first argument, providing extensible nominal dispatch; it does not inspect all argument types.

### 11.13.1 Higher-order utilities manipulate call structure

A **higher-order function** accepts a function, returns a function, or both. The abstraction is not “functional style” as decoration; it factors recurring call mechanics—argument binding, caching, dispatch, reduction, and metadata preservation—out of domain logic.

These utilities retain references. A wrapper can therefore extend the lifetime of its wrapped function, supplied arguments, cached results, and instances captured through bound methods. Memory ownership must be included in the contract.

### 11.13.2 Partial application

<code>partial</code> constructs a callable with selected positional and keyword arguments pre-bound:

~~~python
from functools import partial


def convert_temperature(
    value: float,
    *,
    offset: float,
    scale: float,
) -> float:
    return (value + offset) * scale


celsius_to_fahrenheit = partial(
    convert_temperature,
    offset=0.0,
    scale=9 / 5,
)
~~~

This particular formula omits the Fahrenheit additive 32 and is intentionally a warning: argument binding can be syntactically correct while the domain model is wrong. A correct conversion might use a dedicated named function:

~~~python
def celsius_to_fahrenheit(value: float) -> float:
    return value * 9 / 5 + 32
~~~

Use <code>partial</code> when one generic operation and its fixed policy remain clear. Use a named wrapper when the derived operation needs documentation, validation, transformed arguments, or a distinct domain identity.

The partial object's <code>func</code>, <code>args</code>, and <code>keywords</code> expose retained bindings. Mutable arguments remain aliased:

~~~python
def append_to(value: int, destination: list[int]) -> None:
    destination.append(value)


shared: list[int] = []
record = partial(append_to, destination=shared)
record(1)
record(2)

assert shared == [1, 2]
~~~

This can be desired stateful behaviour, but it is not a fresh default per call. <code>partialmethod</code> serves related binding needs in class descriptors.

### 11.13.3 Wrapper metadata

A decorator normally replaces one function object with another. Without explicit copying, introspection sees the wrapper's name, documentation, annotations, and signature:

~~~python
from collections.abc import Callable
from functools import wraps
from typing import ParamSpec, TypeVar


P = ParamSpec("P")
R = TypeVar("R")


def traced(function: Callable[P, R]) -> Callable[P, R]:
    @wraps(function)
    def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        print(f"calling {function.__qualname__}")
        return function(*args, **kwargs)

    return wrapper
~~~

<code>wraps</code> applies <code>update_wrapper</code>, copying selected metadata and setting <code>__wrapped__</code>. Introspection tools can follow that chain. It does not make the wrapper semantically identical: the trace is an effect, exceptions can now arise from output, timing changes, and identity changes.

Metadata copying is shallow. A wrapper that changes the accepted call contract should expose an honest signature and documentation rather than blindly masquerade as the original.

### 11.13.4 Memoisation contracts

<code>cache</code> and <code>lru_cache</code> remember results indexed by call arguments:

~~~python
from functools import lru_cache


@lru_cache(maxsize=256)
def parse_schema(schema_text: str) -> tuple[str, ...]:
    return tuple(part.strip() for part in schema_text.split(","))
~~~

Arguments used as cache keys must be hashable. Cache correctness additionally requires referential stability: for the desired lifetime, equal cache keys must imply an acceptable same result. Functions depending on time, files, environment variables, database state, randomness, mutable globals, or caller identity can return stale or cross-context results.

<code>maxsize=None</code> makes an unbounded least-recently-used cache; <code>@cache</code> is the simpler equivalent for unbounded memoisation. “Unbounded” means entries remain until explicit clearing or function object release, so attacker-controlled key variety can exhaust memory.

~~~python
information = parse_schema.cache_info()
parse_schema.cache_clear()
~~~

<code>cache_info</code> exposes hits, misses, maximum size, and current size for observation. Hit rate alone does not prove value: cache lookup, hashing, retained memory, and staleness can outweigh recomputation.

The cache retains strong references to arguments and return values until eviction or clearing. Decorating an instance method includes <code>self</code> in the key, potentially retaining many instances.

Keyword argument order can produce separate entries under documented behaviour:

~~~python
@lru_cache(maxsize=16)
def combine(*, left: int, right: int) -> int:
    return left + right


combine(left=1, right=2)
combine(right=2, left=1)
~~~

Do not depend on semantic normalisation the cache does not promise. A wrapper can canonicalise calls first if required.

The cache's internal mapping is coherent under its thread-safety contract, but two threads can compute the same missing key before either result is stored. Memoisation is not once-only execution and must not wrap a non-idempotent effect on that assumption.

> **Common misconception 11.37 — “A cached function runs at most once per argument.”** Concurrent or re-entrant misses can compute more than once, and eviction permits later recomputation.

### 11.13.5 Cached attributes

<code>cached_property</code> computes on first attribute access and then stores the result in the instance:

~~~python
from functools import cached_property


class Document:
    def __init__(self, source: str) -> None:
        self.source = source

    @cached_property
    def words(self) -> tuple[str, ...]:
        return tuple(self.source.split())


document = Document("one two")
assert document.words == ("one", "two")
~~~

If <code>source</code> later changes, <code>words</code> remains stale until deletion:

~~~python
document.source = "three"
del document.words
assert document.words == ("three",)
~~~

This design is coherent only if source mutation and invalidation are coordinated. Immutable instances or explicit versioning reduce the risk.

The descriptor requires compatible instance attribute storage; slot-only classes without a dictionary need another strategy. Concurrency semantics changed across Python releases, and a getter can run more than once. If computation must execute once under parallel access, add explicit synchronisation around the domain state.

### 11.13.6 Reduction

<code>reduce(function, iterable, initial)</code> repeatedly combines one accumulated value with the next element and returns only the final result:

~~~python
from functools import reduce
from operator import mul


factorial_five = reduce(mul, range(1, 6), 1)
assert factorial_five == 120
~~~

The initial value handles empty input and states the identity for multiplication. Without it, an empty iterable raises and the first element becomes the initial accumulator.

A named loop is often clearer when the operation validates, logs, short-circuits, or has a domain-specific invariant:

~~~python
product = 1
for factor in range(1, 6):
    product *= factor
~~~

For parallel or regrouped reduction, the operation usually needs an associative law:

\[
(a \circ b) \circ c = a \circ (b \circ c).
\]

Floating-point addition is not exactly associative because rounding occurs after operations, so changing reduction order can change the result. <code>reduce</code> itself uses left-to-right order; the law matters when an optimisation changes grouping.

### 11.13.7 Single dispatch

<code>singledispatch</code> creates a generic function whose implementation is selected from the runtime type of its first argument:

~~~python
from functools import singledispatch


@singledispatch
def render(value: object) -> str:
    return repr(value)


@render.register
def _(value: int) -> str:
    return f"integer:{value}"


@render.register
def _(value: list) -> str:
    return "[" + ", ".join(render(item) for item in value) + "]"
~~~

The other arguments do not participate in dispatch. Registration follows nominal class relationships and abstract base classes according to the documented resolution mechanism. It is not arbitrary pattern matching on values, shapes, or several types.

The base implementation should define a meaningful fallback or raise a clear unsupported-type error. Registered implementations remain ordinary functions and can be independently tested:

~~~python
integer_renderer = render.dispatch(int)
assert integer_renderer(7) == "integer:7"
~~~

<code>render.registry</code> exposes a read-only mapping useful for introspection. Registration at import time is global mutation of the generic function; plugin systems need deterministic import and conflict policy.

<code>singledispatchmethod</code> adapts the idea to methods, dispatching on the first non-<code>self</code>/<code>cls</code> argument. It must be composed with other decorators under documented ordering.

> **Common misconception 11.38 — “Single dispatch considers all argument types.”** It selects by the first dispatch argument only. Multiple dispatch requires a different abstraction.

### 11.13.8 Ordering adapters

<code>total_ordering</code> can derive missing rich comparison methods from equality and one ordering method:

~~~python
from functools import total_ordering


@total_ordering
class Version:
    def __init__(self, major: int, minor: int) -> None:
        self.parts = (major, minor)

    def __eq__(self, other: object) -> bool:
        if not isinstance(other, Version):
            return NotImplemented
        return self.parts == other.parts

    def __lt__(self, other: object) -> bool:
        if not isinstance(other, Version):
            return NotImplemented
        return self.parts < other.parts
~~~

Returning <code>NotImplemented</code> allows reflected comparison or a proper <code>TypeError</code>; returning <code>False</code> for unrelated types would falsely claim comparability.

Generated methods can add call-stack depth and overhead. Implement all six comparisons only if profiling demonstrates need and consistency can be maintained. More importantly, decide whether the domain really has a total order. Semantic versions, partial information, and interval sets can require partial ordering or specialised comparison.

<code>cmp_to_key</code> adapts an old-style three-way comparison function for key-based sorting. A key function is usually simpler and computed once per element. Comparison functions must be consistent; non-transitive results make ordering ill-defined.

### 11.13.9 Function adaptation checklist

Before applying a <code>functools</code> utility, answer:

| Utility | Required semantic question |
|---|---|
| <code>partial</code> | do retained arguments and references remain correct for all calls? |
| <code>wraps</code> | does the wrapper preserve the original contract or merely metadata? |
| <code>lru_cache</code> | what invalidates results, bounds keys, and releases retained objects? |
| <code>cached_property</code> | what mutation invalidates the attribute, and how is access coordinated? |
| <code>reduce</code> | what is the accumulator invariant and empty-input identity? |
| <code>singledispatch</code> | is first-argument nominal type the true axis of variation? |
| <code>total_ordering</code> | does the domain have a coherent total order? |

Utilities remove boilerplate, not obligations. Their value is greatest when the semantic answers are already precise.
