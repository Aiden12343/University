# 11.14 `dataclasses`

The `dataclasses` module transforms annotated class definitions to generate selected methods.

```python
from dataclasses import dataclass, field


@dataclass(frozen=True, slots=True)
class Reading:
    sensor_id: str
    value: float
    tags: tuple[str, ...] = field(default_factory=tuple)
```

`default_factory` is called for each omitted field during instance initialisation, avoiding shared mutable defaults. Here tuple is immutable, so plain `()` would also be safe; the example exposes the mechanism.

Generated equality compares instances field by field under dataclass rules. Ordering is optional and should be generated only if field order represents a coherent domain order. `frozen=True` prevents ordinary assignment but does not recursively freeze referred objects. `slots=True` requests generated slots subject to inheritance constraints.

Use `asdict` with care: it recursively constructs dictionaries and deep-copies under its documented behaviour, which can be expensive and can erase type distinctions. Explicit serialisation functions make schemas and conversions visible.

### 11.14.1 Dataclasses generate methods from declared fields

<code>@dataclass</code> examines annotated class attributes and generates selected methods such as <code>__init__</code>, <code>__repr__</code>, and <code>__eq__</code>. Except for <code>ClassVar</code> and <code>InitVar</code> classification, the decorator does not ordinarily interpret annotation meaning or validate runtime values.

~~~python
from dataclasses import dataclass


@dataclass
class Reading:
    sensor_id: str
    value: float


reading = Reading(sensor_id=123, value="high")  # runtime construction succeeds
~~~

A static type checker should report both mismatches, but the generated initializer assigns them. Boundary code must validate external values before or during construction.

Generated representation is useful for diagnostics but can reveal secrets or produce large output. A field can be excluded:

~~~python
from dataclasses import field


@dataclass
class Credential:
    username: str
    secret: str = field(repr=False)
~~~

This prevents the ordinary generated <code>repr</code> from displaying <code>secret</code>. It does not encrypt the field, prevent debugger inspection, or stop another method from logging it.

### 11.14.2 Field order is semantic

Fields are ordered as they appear after inheritance processing. That order governs generated initializer parameters, representation, tuple-like equality comparison sequence, optional ordering, pattern-matching position, and helpers such as <code>fields</code>.

~~~python
@dataclass
class Interval:
    start: int
    stop: int
~~~

Changing order can therefore break positional callers:

~~~python
interval = Interval(10, 20)
~~~

Keyword construction communicates meaning and survives many reorderings:

~~~python
interval = Interval(start=10, stop=20)
~~~

<code>kw_only=True</code> can enforce keyword-only generated parameters:

~~~python
@dataclass(kw_only=True)
class Request:
    source: str
    destination: str


request = Request(source="A", destination="B")
~~~

This is often appropriate for public records with several same-typed fields.

An inherited non-default field cannot follow a default field in the combined order. Design base classes carefully rather than treating the resulting error as arbitrary decorator behaviour.

### 11.14.3 Defaults and factories

A field default is evaluated when the class body executes and then reused. Dataclasses reject common unhashable mutable defaults as a defence against accidental sharing, but hashability is only a heuristic for mutability.

Use <code>default_factory</code> for per-instance construction:

~~~python
@dataclass
class Batch:
    identifiers: list[str] = field(default_factory=list)


left = Batch()
right = Batch()
left.identifiers.append("A")

assert right.identifiers == []
assert left.identifiers is not right.identifiers
~~~

The factory is called with no arguments when the field is omitted. It can perform arbitrary work and raise; a simple built-in constructor is easiest to reason about.

An immutable default such as an empty tuple can be shared safely:

~~~python
@dataclass(frozen=True)
class FrozenBatch:
    identifiers: tuple[str, ...] = ()
~~~

Immutability is shallow: a tuple can contain mutable elements, and <code>frozen=True</code> does not recursively inspect them.

### 11.14.4 Post-initialisation and invariants

If generated <code>__init__</code> is used, it calls <code>__post_init__</code> after assigning fields:

~~~python
@dataclass(frozen=True, slots=True)
class Percentage:
    value: int

    def __post_init__(self) -> None:
        if type(self.value) is not int:
            raise TypeError("percentage value must be an integer")
        if not 0 <= self.value <= 100:
            raise ValueError("percentage must lie in 0..100")
~~~

The type is immutable under ordinary assignment after construction. Validation occurs after the raw field has briefly been assigned but before normal construction returns.

Derived stored fields can be assigned in a frozen class through <code>object.__setattr__</code> during post-initialisation:

~~~python
@dataclass(frozen=True)
class Rectangle:
    width: int
    height: int
    area: int = field(init=False)

    def __post_init__(self) -> None:
        if self.width < 0 or self.height < 0:
            raise ValueError("dimensions must be non-negative")
        object.__setattr__(self, "area", self.width * self.height)
~~~

Using this escape after construction would violate the intended contract. “Frozen” emulates read-only fields; determined code can bypass it, and referred mutable objects remain mutable.

### 11.14.5 <code>InitVar</code> and non-field class variables

An <code>InitVar</code> is an initializer-only pseudo-field passed to <code>__post_init__</code> but not retained as an ordinary dataclass field:

~~~python
from dataclasses import InitVar


@dataclass
class User:
    name: str
    raw_password: InitVar[str]
    password_digest: bytes = field(init=False, repr=False)

    def __post_init__(self, raw_password: str) -> None:
        self.password_digest = derive_password_digest(raw_password)
~~~

The raw password remains present in caller memory and temporarily in function frames; non-retention as a field is not secure erasure. Password hashing requires a maintained password-hashing construction with salt and work-factor policy, not a general fast hash.

<code>typing.ClassVar</code> marks an annotated class variable that is excluded from dataclass fields:

~~~python
from typing import ClassVar


@dataclass
class Message:
    schema_version: ClassVar[int] = 1
    body: str
~~~

Every instance resolves the class-level version unless shadowed by ordinary assignment where permitted. It is metadata about the class, not serialised instance state unless an explicit encoder includes it.

### 11.14.6 Equality, ordering, and heterogeneous classes

Generated equality compares field values in order and ordinarily requires identical classes:

~~~python
@dataclass
class Metres:
    value: int


@dataclass
class Seconds:
    value: int


assert Metres(3) != Seconds(3)
~~~

This protects unlike domain types better than bare tuple equality. Subclasses also do not automatically compare equal to base instances solely because fields match.

<code>order=True</code> generates ordering methods after equality-like field comparison. It should be used only if every field order composes into the domain's intended total order:

~~~python
@dataclass(order=True, frozen=True)
class QueuePriority:
    priority: int
    sequence: int
    payload: object = field(compare=False)
~~~

The payload does not participate, so equal priority and sequence values compare equal regardless of payload. A system must ensure sequence uniqueness if it needs distinct queue positions.

### 11.14.7 Hash generation and mutability

Hashable objects used as dictionary keys or set elements must keep equality-relevant state stable while stored. Dataclasses choose hash generation based on <code>eq</code> and <code>frozen</code>:

- equality plus frozen state ordinarily permits a generated hash;
- equality plus mutable state ordinarily makes instances unhashable;
- <code>unsafe_hash=True</code> forces generation but transfers correctness responsibility to the programmer.

~~~python
@dataclass(frozen=True)
class Coordinate:
    x: int
    y: int


locations = {Coordinate(1, 2): "station"}
~~~

A frozen dataclass can still contain an unhashable list, causing hashing to fail, or a mutable hashable object whose equality changes. Frozen syntax is evidence, not a proof of deep value semantics.

Fields can be excluded from hashing independently of comparison, but a field used by equality and omitted from hashing can increase collisions. A field included in hashing but omitted from equality would violate the requirement that equal objects have equal hashes and should not be engineered through unsafe customisation.

> **Common misconception 11.39 — “<code>frozen=True</code> makes any dataclass safely hashable.”** Referred fields can be unhashable or mutable, and deep invariants remain the class designer's responsibility.

### 11.14.8 Slots and weak references

<code>slots=True</code> asks the decorator to generate a class with slots for fields, commonly avoiding a per-instance attribute dictionary and rejecting arbitrary new attribute names:

~~~python
@dataclass(slots=True)
class Pixel:
    red: int
    green: int
    blue: int


pixel = Pixel(10, 20, 30)
try:
    pixel.alpha = 255
except AttributeError:
    pass
~~~

Slots can reduce memory for many instances and catch misspelled attributes. The exact memory difference is an implementation measurement. Inheritance, descriptors, pickling, weak references, and libraries expecting <code>__dict__</code> require testing.

<code>weakref_slot=True</code> adds support needed for weak references and requires slots. A weak reference observes an object without retaining it strongly; Chapter 15 relates this to CPython lifetime management.

With slots, the decorator returns a generated class object rather than merely modifying the original in the simplest mental model. Metaclass and <code>__init_subclass__</code> interactions can therefore require care.

### 11.14.9 Pattern matching

Dataclasses ordinarily generate <code>__match_args__</code> from non-keyword-only initializer parameters, permitting positional class patterns:

~~~python
@dataclass
class Event:
    kind: str
    value: int


event = Event("temperature", 18)
match event:
    case Event("temperature", value):
        print(value)
~~~

This makes field order part of the pattern API. Keyword patterns are clearer and more stable:

~~~python
match event:
    case Event(kind="temperature", value=value):
        print(value)
~~~

Set <code>match_args=False</code> where positional deconstruction should not be public. Pattern matching tests structure; it does not validate an instance that was constructed through another path.

### 11.14.10 Introspection and conversion

<code>dataclasses.fields</code> returns field descriptors for a dataclass class or instance:

~~~python
from dataclasses import fields, is_dataclass


assert is_dataclass(Event)
assert [item.name for item in fields(Event)] == ["kind", "value"]
~~~

This supports generic tooling, but field metadata is not automatically a stable serialisation schema. Private fields, computed fields, class refactoring, and types unsupported by the target format still require explicit conversion.

<code>asdict</code> recursively descends into nested dataclasses, dictionaries, lists, and tuples and deep-copies other objects through its documented behaviour:

~~~python
from dataclasses import asdict


document = asdict(event)
assert document == {"kind": "temperature", "value": 18}
~~~

For large graphs this can allocate substantially. Cycles can fail. Type identity and aliasing are lost in the resulting generic structure. A shallow projection can be written explicitly:

~~~python
shallow = {
    descriptor.name: getattr(event, descriptor.name)
    for descriptor in fields(event)
}
~~~

Even this exposes every field regardless of confidentiality or wire compatibility. Public schemas deserve explicit encoders.

### 11.14.11 Replacement is reconstruction

<code>dataclasses.replace</code> calls the generated initializer with selected changes, causing <code>__post_init__</code> to run:

~~~python
from dataclasses import replace


original = Percentage(20)
updated = replace(original, value=25)

assert updated == Percentage(25)
assert original == Percentage(20)
~~~

Fields with <code>init=False</code> are not simply copied by <code>replace</code>; they are expected to be recomputed by construction. Custom initialisation and derived resources should be tested. Replacement is not an in-place mutation and does not preserve object identity.

### 11.14.12 Dataclass or ordinary class?

Use a dataclass when the object is primarily a declared set of fields and generated value-oriented methods match its semantics. Prefer an ordinary class when:

- construction involves several mutually exclusive workflows;
- public behaviour matters more than field exposure;
- invariants require controlled mutation through methods;
- representation must hide most state;
- identity, lifecycle, and resources dominate value equality;
- generated ordering or equality would be misleading.

A dataclass can still have methods and rich invariants. The distinction is about whether field declaration is the organising abstraction, not whether the class is “simple”.

> **Common misconception 11.40 — “A dataclass is merely a shorter class.”** It selects generated equality, representation, construction, matching, field ordering, and possibly hashing/slots semantics. Those are API decisions.
