# 11.16 Temporary resources

### 11.16.1 Unnamed and named temporary files

<code>TemporaryFile</code> creates a temporary binary file by default and returns a file-like object. The directory entry may be absent or removed immediately on platforms supporting that technique:

~~~python
from tempfile import TemporaryFile


with TemporaryFile() as stream:
    stream.write(b"intermediate")
    stream.seek(0)
    assert stream.read() == b"intermediate"
~~~

Use it when code needs seekable temporary storage but no other component needs a pathname.

<code>NamedTemporaryFile</code> provides a visible name as well as a stream:

~~~python
from pathlib import Path
from tempfile import NamedTemporaryFile


with NamedTemporaryFile(
    mode="w",
    encoding="utf-8",
    suffix=".json",
) as stream:
    stream.write('{"status":"temporary"}')
    stream.flush()
    visible_path = Path(stream.name)
    consume_by_name(visible_path)
~~~

Whether another open of the name succeeds while the original remains open, and whether automatic deletion succeeds, depends on platform sharing and delete parameters. Code intended for Windows and POSIX must test the exact lifecycle it uses.

The suffix helps a consumer choose a parser; it provides no security and does not validate content.

### 11.16.2 Delete-on-close and explicit transfer of ownership

Automatic deletion is convenient only while the temporary object remains temporary. A staged file intended to become the destination needs a distinct ownership transition:

~~~python
temporary_name: str | None = None
try:
    with NamedTemporaryFile(
        mode="wb",
        dir=destination.parent,
        delete=False,
    ) as stream:
        temporary_name = stream.name
        stream.write(payload)
        stream.flush()

    os.replace(temporary_name, destination)
    temporary_name = None
finally:
    if temporary_name is not None:
        Path(temporary_name).unlink(missing_ok=True)
~~~

Setting the variable to <code>None</code> after replacement records that cleanup no longer owns the name. The destination now has its own lifecycle. A cleanup error before commit should normally be reported or logged without masking the primary failure; after commit, deleting the destination would be catastrophic.

<code>delete=False</code> makes recovery of orphaned temporaries an operational concern if the process crashes before cleanup. Use recognisable prefixes, restrictive permissions, bounded locations, and a conservative age/ownership-based scavenger.

### 11.16.3 Temporary directories

<code>TemporaryDirectory</code> creates a directory and recursively attempts removal on context exit:

~~~python
from tempfile import TemporaryDirectory


with TemporaryDirectory(prefix="compiler-test-") as name:
    workspace = Path(name)
    (workspace / "source.txt").write_text("input", encoding="utf-8")
    run_compilation(workspace)
~~~

Cleanup can fail because handles remain open, permissions changed, a child process still uses the directory, or another actor inserted content. Suppressing all cleanup errors can leave sensitive artefacts; treating every cleanup failure as fatal can mask a successful primary result. Policy depends on confidentiality and operation.

A temporary directory is not a sandbox. Code running within it may still access the rest of the filesystem and network with the process's authority. Path traversal through generated or extracted names can escape it.

### 11.16.4 Spooling from memory to storage

<code>SpooledTemporaryFile</code> begins with an in-memory buffer and rolls over to an on-disk temporary file after a size threshold or selected operations:

~~~python
from tempfile import SpooledTemporaryFile


with SpooledTemporaryFile(max_size=1_000_000, mode="w+b") as stream:
    stream.write(generate_report_bytes())
    stream.seek(0)
    publish(stream)
~~~

This can avoid filesystem I/O for small results while bounding in-memory buffering for larger results. The threshold is not a maximum total size; after rollover, output can keep growing until storage limits intervene. <code>generate_report_bytes()</code> in this example already materialises its complete result; writing chunks would be needed to bound producer memory too.

Calling <code>fileno</code> can force rollover because an operating-system descriptor is required. Do not assume the storage location remains in memory based only on current size.

### 11.16.5 Low-level creation APIs

<code>mkstemp</code> and <code>mkdtemp</code> securely create a unique temporary file or directory and return low-level ownership:

~~~python
import os
from tempfile import mkstemp


descriptor, name = mkstemp(prefix="analysis-", suffix=".bin")
path = Path(name)
try:
    with os.fdopen(descriptor, "wb") as stream:
        descriptor = -1
        stream.write(b"result")
finally:
    if descriptor != -1:
        os.close(descriptor)
    path.unlink(missing_ok=True)
~~~

The descriptor is already open; reopening by name would unnecessarily re-enter pathname resolution. The caller must remove the path manually. High-level context managers are preferable unless the low-level ownership is needed.

Never use <code>mktemp</code>, which returns an unused name without atomically creating it and therefore permits a race before opening.

### 11.16.6 Directory selection and environmental trust

Temporary APIs choose a default directory using platform and environment conventions. Environment variables can influence selection. A privileged or security-sensitive program must decide whether those inputs are trusted and whether the resulting directory has suitable ownership, permissions, capacity, mount options, and filesystem semantics.

Passing <code>dir=destination.parent</code> is appropriate for same-filesystem staged replacement, but that directory may be publicly readable or lack space. Passing a private temporary root improves confidentiality while potentially preventing atomic rename to another filesystem. These are distinct requirements.

Temporary data can enter backups, snapshots, swap, crash dumps, antivirus scans, and filesystem journals. Deletion on exit does not guarantee erasure.

### 11.16.7 Names are visible metadata

Prefixes and suffixes can leak project, user, or document information through directory listings and monitoring even when file contents are protected. Avoid placing secrets in temporary names:

~~~python
# Avoid: prefix=f"{customer_email}-"
with NamedTemporaryFile(prefix="upload-", delete=True) as stream:
    ...
~~~

Randomised names reduce collision and guessing. They do not make contents inaccessible when directory permissions allow reading or when handles leak.

### 11.16.8 Testing temporary-resource behaviour

Tests should verify:

- normal cleanup;
- cleanup after body exception;
- behaviour when a handle remains open;
- staged-file removal after producer failure;
- no removal of the committed destination;
- size threshold and rollover for spooled files;
- permission/capacity failure where the platform can simulate it;
- process-crash orphan recovery in an integration environment.

Do not assert one platform's path visibility or deletion timing as a universal Python property. Mark platform-specific tests and document why.

> **Common misconception 11.41 — “Temporary means in memory, private, and automatically erased.”** A temporary resource may be named on persistent storage, visible to others under permissions, retained after a crash, or recoverable from lower storage layers.
