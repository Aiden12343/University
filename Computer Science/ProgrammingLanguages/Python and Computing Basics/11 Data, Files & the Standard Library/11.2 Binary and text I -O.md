# 11.2 Binary and text I/O

At an operating-system file boundary, data is byte-oriented. Python can expose a **binary stream**, which reads and writes bytes, or a **text stream**, which adds decoding, encoding, newline handling, and buffering.

```python
from pathlib import Path

path = Path("message.txt")
path.write_text("café\n", encoding="utf-8")
text = path.read_text(encoding="utf-8")
print(repr(text))
```

The explicit encoding is part of the contract. Omitting it can select an environment-dependent default and make the same bytes decode differently across systems.

Binary access preserves exact bytes:

```python
data = path.read_bytes()
print(data)
```

For the given text under UTF-8, the result is typically `b'caf\xc3\xa9\n'`. The code point for `é` occupies two UTF-8 bytes.

A text stream’s newline translation can map platform line endings to `\n` on reading and perform translation on writing under its `newline` parameter. If exact bytes or protocol line endings matter, use binary mode or configure newline behaviour deliberately.

### Worked example 11.1 — Decode failure belongs at the text boundary

```python
raw = b"price=\xff"
raw.decode("utf-8")
```

Byte `0xff` cannot appear as a standalone valid UTF-8 byte, so decoding raises `UnicodeDecodeError`. Possible policies include rejecting the input, using a different known encoding, or applying a documented error handler such as replacement. Guessing or silently discarding bytes changes information and must be an explicit domain decision.

`errors="replace"` produces replacement characters, preserving position but losing original distinction. `errors="ignore"` deletes undecodable input and is particularly dangerous in identifiers, security checks, and financial data.

### 11.2.1 I/O is a stack of interpretations

The word **stream** denotes an ordered interface through which units are transferred over time. It does not imply that all units already exist, that the total length is known, that the stream can be revisited, or that transfer occurs at a uniform rate. A regular file, terminal, pipe, in-memory buffer, compressed decoder, and network connection can all present stream interfaces while differing substantially in seekability, latency, partial-transfer behaviour, and failure modes.

Python's I/O abstractions are layered:

| Layer | Principal units | Principal responsibility |
|---|---|---|
| raw I/O | bytes accepted by or obtained from an operating-system-like resource | one low-level transfer operation and resource handle |
| buffered binary I/O | bytes | reduce calls, combine writes, and often satisfy larger read requests through repeated raw operations |
| text I/O | strings | decode/encode characters, recognise or translate newlines, and buffer text/bytes |
| format parser | records, tokens, or domain-neutral structures | interpret a grammar such as CSV or JSON |
| domain adapter | domain objects | validate schema, units, ranges, relationships, and policy |

Each layer adds semantics and can fail independently. A text read can obtain bytes successfully but fail during decoding. A JSON parser can decode text successfully but reject its grammar. A schema validator can accept the JSON grammar but reject a missing member. Collapsing these failures into “could not read file” discards actionable information.

The usual text file returned by <code>open("name.txt", "r", encoding="utf-8")</code> is a high-level object whose implementation coordinates an encoder/decoder with buffered binary storage and a raw resource. This is a library abstraction. Code should depend on the documented text-stream contract unless it specifically needs a lower layer.

### 11.2.2 Bytes are integers under an interpretation

A Python <code>bytes</code> object is an immutable sequence whose elements are integers from 0 through 255. Its printed form uses ASCII characters where convenient and escapes elsewhere, but that notation does not make it text:

~~~python
packet = bytes([65, 0, 255])

assert len(packet) == 3
assert packet[0] == 65
assert packet[:1] == b"A"
print(packet)  # b'A\x00\xff'
~~~

Indexing a bytes object produces an integer; slicing produces another bytes object. This differs from <code>str</code>, where indexing and slicing produce strings. The distinction prevents ambiguity between the numeric byte value 65 and a one-byte sequence containing it.

<code>bytearray</code> is the mutable counterpart:

~~~python
header = bytearray(b"\x00\x00\x00\x00")
header[0] = 0x7F
header[1:3] = b"\x01\x02"
assert header == bytearray(b"\x7f\x01\x02\x00")
~~~

Mutation is valuable for building packets or receiving data into reusable storage. It also means that code retaining the same bytearray observes later modification. Convert to <code>bytes</code> when an immutable snapshot is required.

A <code>memoryview</code> exposes the **buffer protocol**, an interface through which one object grants structured access to underlying memory without an obligatory copy:

~~~python
storage = bytearray(b"abcdefgh")
middle = memoryview(storage)[2:6]
middle[0] = ord("X")

assert storage == bytearray(b"abXdefgh")
middle.release()
~~~

The slice shares storage; it is not an independent byte sequence. This can avoid allocation in high-throughput binary processing, but it creates aliasing and lifetime obligations. Some exporters cannot be resized while a view exists. A memory view also carries element format, shape, strides, and mutability information; it should not be reduced mentally to “faster bytes”.

> **Common misconception 11.7 — “A bytes literal is encoded text.”** It is a sequence of byte values. It represents text only under an independently chosen encoding and validity claim.

### 11.2.3 Unicode code points, graphemes, and glyphs

Unicode assigns integer **code points** conventionally written as <code>U+</code> followed by hexadecimal digits. A Python <code>str</code> is a sequence of Unicode code points for most language-level purposes. This statement does not mean one string element always equals one visible character.

Four units must be distinguished:

- a **code point** is a numbered position in the Unicode codespace;
- a **code unit** is a fixed-width storage unit used by an encoding form, such as an 8-bit unit in UTF-8 or a 16-bit unit in UTF-16;
- an **extended grapheme cluster** is a standardised approximation to one user-perceived text element, potentially containing several code points;
- a **glyph** is a rendered visual form selected by a font and shaping system; one glyph can correspond to several code points, and one code point can contribute to several glyphs.

Python length and indexing operate on code points:

~~~python
precomposed = "é"          # U+00E9
decomposed = "e\u0301"     # U+0065 followed by U+0301

assert len(precomposed) == 1
assert len(decomposed) == 2
assert precomposed != decomposed
~~~

The two strings can render similarly and are **canonically equivalent** under Unicode's normalisation model, yet ordinary Python equality compares their code-point sequences and therefore reports inequality. Normalisation makes a chosen equivalence representation explicit:

~~~python
from unicodedata import normalize

assert normalize("NFC", decomposed) == precomposed
~~~

NFC is one Unicode normalisation form. NFD decomposes canonical combinations; NFKC and NFKD additionally apply compatibility mappings that can erase distinctions significant in some domains. Normalisation policy must therefore be chosen for a purpose, not applied reflexively.

An emoji sequence may contain a base, skin-tone modifier, zero-width joiner, and another symbol. Flags commonly use pairs of regional-indicator code points. <code>len</code> consequently does not answer “how many characters will a user perceive?” Unicode Standard Annex #29 defines default grapheme-cluster boundaries; language- or operation-specific tailoring may still be required.

Likewise, <code>lower</code> and <code>casefold</code> are not complete identity policies. Case folding is designed for caseless matching and can change length:

~~~python
assert "Straße".casefold() == "STRASSE".casefold()
assert len("ß") == 1
assert len("ß".casefold()) == 2
~~~

Usernames, identifiers, and search keys may require normalisation, case policy, script restrictions, locale-sensitive rules, and confusable-character defences. Unicode support does not supply those domain decisions automatically.

> **Common misconception 11.8 — “One Python string element is one screen character.”** Python indexes code points. Grapheme clusters and rendered glyphs can span different boundaries.

### 11.2.4 Encoding and decoding are directional

An **encoding** maps text to bytes. A **decoding** maps valid bytes under an encoding to text:

~~~python
word = "café"
octets = word.encode("utf-8")
recovered = octets.decode("utf-8")

assert octets == b"caf\xc3\xa9"
assert recovered == word
~~~

The method locations reinforce direction: strings know how to encode themselves into bytes, and byte sequences know how to decode themselves into strings. The round trip

\[
\operatorname{decode}_E(\operatorname{encode}_E(s)) = s
\]

holds for strings representable under encoding \(E\) when compatible strict operations are used. The reverse round trip does not hold for every arbitrary byte sequence because some byte sequences are invalid and some legacy encodings admit non-canonical or stateful behaviour.

UTF-8 encodes Unicode scalar values using one to four bytes. ASCII code points U+0000 through U+007F use the same single-byte values as ASCII; this compatibility does not imply that arbitrary ASCII-oriented byte processing is Unicode-aware. For the sample:

~~~python
sample = "Aé水🙂"
encoded = sample.encode("utf-8")

assert len(sample) == 4
assert len(encoded) == 10
assert [len(ch.encode("utf-8")) for ch in sample] == [1, 2, 3, 4]
~~~

Byte limits and text-element limits are therefore different requirements. A database column measured in UTF-8 bytes, a Python validation measured in code points, and a user interface measured in grapheme clusters can disagree without any component malfunctioning.

The names of encodings are looked up through Python's codec registry, with common aliases normalised. The name is protocol metadata. Trying several decoders until one does not raise is generally not reliable detection because many encodings assign meanings to most or all byte values. Format-level declarations, byte-order marks where defined, or out-of-band contracts are stronger evidence.

### 11.2.5 Decode and encode error policies

The <code>errors</code> parameter chooses what happens when a mapping cannot be performed. The common handlers have materially different information properties:

| Handler | Typical decode effect | Information consequence |
|---|---|---|
| <code>strict</code> | raise <code>UnicodeDecodeError</code> | preserves evidence by refusing transformation |
| <code>replace</code> | insert U+FFFD replacement character | preserves approximate location; loses original byte identity |
| <code>ignore</code> | omit invalid bytes | loses both values and often visible evidence |
| <code>backslashreplace</code> | insert textual byte escapes | preserves a readable representation, not the original text |
| <code>surrogateescape</code> | map selected undecodable bytes to low-surrogate code points | permits controlled round trip with the same handler |

Some handlers apply only to encoding or to selected codecs. Their names are not evidence that they suit a domain.

~~~python
raw = b"name=\xff\xfe"

for policy in ("replace", "ignore", "backslashreplace"):
    print(policy, raw.decode("utf-8", errors=policy))
~~~

With replacement, two invalid bytes may become two replacement code points; code must not assume one error always maps to one marker. With ignore, the value becomes <code>"name="</code>, perhaps colliding with a genuinely empty field. With backslash replacement, literal characters such as <code>\xff</code> appear in the string; re-encoding that string as UTF-8 encodes those visible characters rather than restoring the original byte by default.

<code>surrogateescape</code> is specialised for carrying undecodable operating-system bytes through text-oriented code:

~~~python
raw_name = b"report-\xff.dat"
carried = raw_name.decode("utf-8", errors="surrogateescape")
restored = carried.encode("utf-8", errors="surrogateescape")

assert restored == raw_name
~~~

The resulting string can contain surrogate code points not valid as Unicode scalar values. Many external formats, encoders, databases, and display systems reject or mishandle them. This is a reversible transport technique under a matching contract, not a way to declare malformed bytes valid text.

Encoding can fail too:

~~~python
"cost: €10".encode("ascii")  # raises UnicodeEncodeError
~~~

Replacement on output may turn unknown characters into question marks or escape sequences. In legal names, passwords, identifiers, or cryptographic inputs, such substitution can change identity. Strict failure is the appropriate default whenever exact content matters.

> **Common misconception 11.9 — “<code>errors='ignore'</code> fixes bad text.”** It deletes evidence and can merge distinct inputs. It is a lossy transformation, not repair.

### 11.2.6 Byte-order marks and protocol signatures

A **byte-order mark** (BOM) is the encoded form of U+FEFF placed at the start of some text streams to signal byte order or encoding convention. Its meaning depends on the format and codec.

UTF-16 and UTF-32 have little-endian and big-endian byte orders. Python's generic <code>"utf-16"</code> and <code>"utf-32"</code> codecs use a BOM to establish order when decoding. Explicit endian codecs such as <code>"utf-16-le"</code> interpret bytes under the selected order without the same generic BOM contract.

UTF-8 has no endianness. A leading UTF-8 encoding of U+FEFF is therefore a signature used by some systems, not an ordering requirement. Python's <code>"utf-8-sig"</code> codec skips one such leading signature on decoding and writes it at the beginning on encoding:

~~~python
signed = b"\xef\xbb\xbfalpha"

assert signed.decode("utf-8") == "\ufeffalpha"
assert signed.decode("utf-8-sig") == "alpha"
~~~

Neither choice is universally correct. A protocol may forbid a BOM, require it, or regard it as content. Stripping the first U+FEFF from every decoded string would incorrectly remove a legitimate character under contracts where it is content.

### 11.2.7 Newlines are a text-layer policy

Historically and currently, systems represent line boundaries with different byte or character sequences: line feed (<code>\n</code>), carriage return followed by line feed (<code>\r\n</code>), and, in legacy contexts, carriage return alone (<code>\r</code>). Python text I/O can perform **universal newline** recognition.

For reading through <code>TextIOWrapper</code>:

- <code>newline=None</code> recognises <code>\n</code>, <code>\r</code>, and <code>\r\n</code> and returns each as <code>\n</code>;
- <code>newline=""</code> recognises all three but returns the original endings untranslated;
- <code>newline="\n"</code>, <code>"\r"</code>, or <code>"\r\n"</code> recognises only the selected terminator and returns endings untranslated.

For writing:

- <code>newline=None</code> translates each written <code>\n</code> to the platform line separator;
- <code>newline=""</code> or <code>"\n"</code> performs no translation;
- another permitted value translates written <code>\n</code> to that value.

~~~python
from pathlib import Path


path = Path("mixed-lines.txt")
path.write_bytes(b"alpha\r\nbeta\rgamma\n")

with path.open("r", encoding="utf-8", newline=None) as stream:
    translated = stream.readlines()

with path.open("r", encoding="utf-8", newline="") as stream:
    preserved = stream.readlines()

assert translated == ["alpha\n", "beta\n", "gamma\n"]
assert preserved == ["alpha\r\n", "beta\r", "gamma\n"]
~~~

Universal recognition is useful for human-authored files. Exact protocols, cryptographic hashes, source-preserving editors, and binary formats need deliberate byte or newline semantics. The <code>csv</code> module has its own record grammar and should normally receive a text stream opened with <code>newline=""</code> so that it, rather than an earlier universal-newline translation, owns embedded newline handling.

The newline recorded by a file object after reading can be inspected through its <code>newlines</code> attribute, but that observation is not a guarantee about future data and can report a tuple when multiple forms occurred.

> **Common misconception 11.10 — “A line always ends with <code>\n</code> in the file.”** A Python text stream may translate several external representations into <code>\n</code>. The stored bytes can differ.

### 11.2.8 Defaults are environmental inputs

When text mode is requested without an explicit <code>encoding</code>, <code>open</code> uses a locale- and runtime-dependent default in Python 3.12's ordinary configuration. UTF-8 mode and later Python changes affect this behaviour, which is precisely why a persistent data format should name its encoding.

~~~python
with open("report.txt", "w", encoding="utf-8", newline="\n") as stream:
    stream.write("Δ revenue\n")
~~~

Explicit parameters make the representation reproducible. They are not necessary in every context. A command-line tool intentionally communicating with the user's terminal or a local legacy tool may need the configured environmental encoding. The rule is:

- for a defined storage or interchange format, state the format encoding;
- for an environmental human interface, obtain and respect that interface's encoding, with a failure policy.

Python can optionally warn about omitted encodings under a runtime configuration intended to help find ambiguous code. A warning is a diagnostic aid, not a substitute for interface analysis.

### 11.2.9 The <code>open</code> stack and capability surface

In ordinary use, <code>open</code> returns different kinds of objects according to mode and buffering. Binary unbuffered mode can expose a raw file object. Binary buffered modes return buffered readers, writers, random-access objects, or buffered pairs. Text mode returns a <code>TextIOWrapper</code> over a binary buffer.

The public stream interfaces advertise **capabilities**:

~~~python
from pathlib import Path


with Path("sample.bin").open("w+b") as stream:
    print(stream.readable())
    print(stream.writable())
    print(stream.seekable())
~~~

Rather than infer capability from a class name, generic code can consult <code>readable</code>, <code>writable</code>, and <code>seekable</code>, then still handle <code>UnsupportedOperation</code> or external failure. Capability can be stable for an object's lifetime while successful operations remain contingent.

Text streams expose attributes including <code>encoding</code>, <code>errors</code>, and newline observations. <code>reconfigure</code> can change selected text parameters under restrictions; changing policy after reading is constrained because buffered decoder state may already exist. <code>detach</code> separates the underlying binary buffer and leaves the wrapper unusable. These are advanced lifecycle operations, not routine ways to switch encoding mid-file.

A function that accepts <code>TextIO</code> rather than <code>Path</code> transfers acquisition and closure policy to its caller:

~~~python
from typing import TextIO


def emit_header(stream: TextIO, title: str) -> None:
    stream.write(title)
    stream.write("\n")
    stream.write("=" * len(title))
    stream.write("\n")
~~~

This function must not close <code>stream</code> because it did not acquire it and its contract does not transfer ownership. Resource ownership belongs in an explicit interface, not in a guess based on object type.

### 11.2.10 Short reads, short writes, and completion loops

The expression <code>stream.read(n)</code> requests at most \(n\) units under general stream interfaces. A regular buffered file often returns \(n\) until end of file, but pipes, sockets, raw devices, non-blocking resources, and custom streams can return fewer. Correct binary protocols distinguish:

- no units currently available;
- end of stream;
- an interrupted operation;
- a partial result;
- a complete frame.

The exact signals differ by API. A portable helper for a blocking binary stream can accumulate until a required length or raise on premature end:

~~~python
from collections.abc import Callable


class TruncatedInput(EOFError):
    pass


def read_exactly(read: Callable[[int], bytes], count: int) -> bytes:
    if count < 0:
        raise ValueError("count must be non-negative")

    chunks: list[bytes] = []
    remaining = count
    while remaining:
        chunk = read(remaining)
        if not chunk:
            received = count - remaining
            raise TruncatedInput(
                f"expected {count} bytes but received {received}"
            )
        chunks.append(chunk)
        remaining -= len(chunk)
    return b"".join(chunks)
~~~

The callable contract here assumes each non-empty result has length at most the requested count and that an empty result means permanent end of stream. It is unsuitable without adaptation for an API where a non-blocking read signals temporary unavailability differently. It also allocates the complete result, so the caller must validate <code>count</code> before calling it.

At lower levels, writes may also be short. A write-completion loop must preserve the unwritten suffix:

~~~python
from collections.abc import Callable


def write_all(write: Callable[[memoryview], int], data: bytes) -> None:
    view = memoryview(data)
    try:
        while view:
            written = write(view)
            if written <= 0:
                raise OSError("write made no progress")
            view = view[written:]
    finally:
        view.release()
~~~

This deliberately narrow callable contract requires a positive integer progress count or an exception. Real raw or non-blocking APIs may return <code>None</code> or raise <code>BlockingIOError</code>; event-driven handling belongs to their specific contract. Buffered Python file writes normally provide a higher-level guarantee, so manually looping around every <code>write</code> call without reading its documentation can be unnecessary or wrong.

> **Common misconception 11.11 — “One call corresponds to one physical I/O operation.”** Buffering can combine, split, defer, or repeat lower-level transfers. The public result is governed by the layer's contract.

### 11.2.11 Incremental decoding and frame boundaries

An arbitrary byte chunk is not necessarily a complete encoded text unit. A multi-byte UTF-8 sequence can be divided across reads:

~~~python
face = "🙂".encode("utf-8")
left = face[:2]
right = face[2:]

assert len(face) == 4
~~~

Decoding <code>left</code> as if it were a complete document raises because it ends within a sequence. Concatenating all input before decoding works but forfeits streaming. An **incremental decoder** retains incomplete codec state between chunks:

~~~python
import codecs


decoder_type = codecs.getincrementaldecoder("utf-8")
decoder = decoder_type(errors="strict")

first_text = decoder.decode(left, final=False)
second_text = decoder.decode(right, final=False)
tail_text = decoder.decode(b"", final=True)

assert first_text == ""
assert second_text == "🙂"
assert tail_text == ""
~~~

The final call asserts that the stream ended; it raises if an incomplete sequence remains. A stateful encoding may retain more than a byte suffix, so hand-written “save the last three bytes” logic is not a general codec implementation.

Text framing has an analogous problem. Network chunks do not preserve application message boundaries. A JSON document might span ten reads, and one read might contain three documents plus part of a fourth. The application protocol must define framing: fixed length, delimiter with escaping, length prefix, self-delimiting grammar with an incremental parser, or connection close under a restricted model.

### 11.2.12 In-memory streams are semantic test doubles

<code>io.StringIO</code> presents a text-stream interface backed by an in-memory string buffer; <code>io.BytesIO</code> presents a binary stream backed by bytes:

~~~python
from io import StringIO


destination = StringIO()
emit_header(destination, "Results")
rendered = destination.getvalue()

assert rendered == "Results\n=======\n"
~~~

This is useful for testing format logic without a filesystem. It is not behaviourally identical to every real file:

- it does not encounter permissions, storage exhaustion, device loss, or filesystem races;
- it has no encoding step when using <code>StringIO</code>;
- operations are memory-speed and seekable;
- retaining output consumes process memory.

To test the text/binary boundary itself, wrap a <code>BytesIO</code> in <code>TextIOWrapper</code>:

~~~python
from io import BytesIO, TextIOWrapper


binary = BytesIO()
text_stream = TextIOWrapper(
    binary,
    encoding="utf-8",
    newline="\r\n",
)
text_stream.write("one\ntwo\n")
text_stream.flush()

assert binary.getvalue() == b"one\r\ntwo\r\n"
text_stream.detach()
~~~

Flushing is needed before inspecting the underlying buffer because the text wrapper may retain encoded output. Detaching prevents wrapper finalisation from closing the <code>BytesIO</code> if the test intends to keep using it. This lifecycle subtlety is itself evidence that a test double should reproduce only the layer under test.

### 11.2.13 Structured binary data and byte order

Not all bytes represent text. Image formats, executable files, compressed streams, cryptographic messages, and device protocols define binary fields. A binary integer requires at least a width, signedness, and byte order.

The <code>struct</code> module packs and unpacks values according to an explicit format:

~~~python
import struct


HEADER = struct.Struct(">4sBI")
encoded_header = HEADER.pack(b"DATA", 1, 12_345)
magic, version, payload_length = HEADER.unpack(encoded_header)

assert magic == b"DATA"
assert version == 1
assert payload_length == 12_345
assert HEADER.size == 9
~~~

The leading greater-than character selects big-endian standard sizes; <code>4s</code> selects four bytes; <code>B</code> selects one unsigned byte; and <code>I</code> selects a four-byte unsigned integer under this prefix. The format is a protocol contract, not merely a compact encoding trick.

A safe reader validates the length before allocation and rejects unknown versions:

~~~python
MAX_PAYLOAD = 1_000_000


def read_frame(stream: object) -> bytes:
    header = read_exactly(stream.read, HEADER.size)  # type: ignore[attr-defined]
    magic, version, payload_length = HEADER.unpack(header)
    if magic != b"DATA":
        raise ValueError("invalid frame signature")
    if version != 1:
        raise ValueError(f"unsupported frame version {version}")
    validate_declared_length(payload_length, MAX_PAYLOAD)
    return read_exactly(stream.read, payload_length)  # type: ignore[attr-defined]
~~~

The signature detects a class of accidental misinterpretation; four public bytes do not authenticate the sender. The version allows parsers to reject or route changed layouts. The length frames one payload but can still lie; premature end remains a checked error. A checksum can detect selected accidental corruption, whereas cryptographic integrity and authenticity require keyed or signed constructions and key-management policy.

### 11.2.14 Text I/O at terminals

A terminal is an interactive device interface, not a persistent text file. Standard input, standard output, and standard error are streams attached by the invoking environment and may instead be redirected to files or pipes. Their encodings, interactivity, newline behaviour, and error handlers can differ.

~~~python
import sys


if sys.stdout.isatty():
    print("interactive presentation")
else:
    print("machine-consumable presentation")
~~~

<code>isatty</code> reports whether the stream is attached to a terminal-like device under the current environment. It is useful evidence, not proof of a human reader. Accessibility tools, notebooks, emulators, redirection layers, and test harnesses complicate the audience.

Programs should place ordinary results on standard output and diagnostics on standard error when composing shell pipelines:

~~~python
print("processed=42")
print("warning: one record skipped", file=sys.stderr)
~~~

The separation lets a caller redirect results without mixing diagnostic prose into a data stream. If output is a defined protocol, explicitly control encoding and escaping or use a binary buffer where appropriate. Terminal text can contain control sequences; echoing untrusted strings without sanitisation can change display behaviour even though it does not execute Python code.

### 11.2.15 A boundary experiment for text

The following program records the quantities that beginners often conflate:

~~~python
from unicodedata import name, normalize


def describe_text(text: str) -> dict[str, object]:
    encoded = text.encode("utf-8")
    return {
        "text": text,
        "code_points": len(text),
        "utf8_bytes": len(encoded),
        "hex_bytes": encoded.hex(" "),
        "code_point_names": [
            name(character, "<unnamed>") for character in text
        ],
        "nfc_equal": text == normalize("NFC", text),
    }


samples = ["A", "é", "e\u0301", "水", "🙂"]
for sample in samples:
    print(describe_text(sample))
~~~

This is an empirical inspection of selected strings under UTF-8 and the runtime's Unicode database. It does not count grapheme clusters, predict display width, or prove font support. A rigorous report records the Python and Unicode database versions if those details affect repeatability:

~~~python
import sys
import unicodedata

print(sys.version)
print(unicodedata.unidata_version)
~~~

The distinction between specification and observation is central. Unicode defines code points and algorithms; Python documents string and codec behaviour; a particular build incorporates a particular Unicode Character Database; a terminal and font choose rendering. “It displayed as one symbol on my screen” is evidence only about that measured stack.
