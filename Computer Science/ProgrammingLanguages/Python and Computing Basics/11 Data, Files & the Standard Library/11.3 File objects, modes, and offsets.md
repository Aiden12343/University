# 11.3 File objects, modes, and offsets

`open` returns a file-like object under a selected mode. Common modes include:

| Mode | Meaning |
|:---:|:---|
| `"r"` | read text; require existing file |
| `"w"` | write text; create or truncate |
| `"x"` | create text exclusively; fail if existing |
| `"a"` | append text, creating if needed |
| `"rb"`, `"wb"` | corresponding binary modes |
| `"r+"` | read and write existing file |

Mode is a policy. Opening with `"w"` can destroy previous content immediately through truncation before later computation succeeds. When replacement must be atomic relative to observers, write a complete temporary file in the same filesystem, flush under the required durability level, and replace the destination using a supported atomic-replacement operation. Atomic namespace replacement does not automatically guarantee physical-media durability or transactional coordination with other files.

A file stream has a current **offset**, a position used by sequential operations. `read(n)` requests up to `n` units; an empty result signals end of file under ordinary blocking file semantics. `seek` changes the offset under mode and stream restrictions; `tell` reports it.

Text-stream positions are not universally byte counts because decoding and newline translation intervene. Only use offsets returned by `tell` for later `seek` unless the interface documents other valid positions.

### Worked example 11.2 — Stream instead of materialising

```python
def count_non_empty_lines(path: Path) -> int:
    count = 0
    with path.open("r", encoding="utf-8") as stream:
        for line in stream:
            if line.strip():
                count += 1
    return count
```

The file object is an iterator over text lines. The function retains one current line and a count rather than the complete file. Its additional Python-level space is bounded independently of line count, though one exceptionally long line can itself be large and I/O layers buffer data.

`line.strip()` defines “non-empty” as containing some non-whitespace code point after removal according to Python’s whitespace rules. A format in which spaces are data would require another predicate.

### 11.3.1 Pathnames, descriptors, and file objects

Three entities commonly called “the file” should be distinguished:

1. a **pathname** is a sequence of components used to ask a filesystem namespace to resolve an object;
2. a **file descriptor** is a small process-local integer used by POSIX-like operating-system interfaces to identify an open resource; Windows provides related but not identical handle machinery;
3. a Python **file object** is a higher-level object implementing an I/O interface and usually owning an underlying descriptor or handle.

The pathname may be renamed or removed after a handle is opened. On systems with Unix-like unlink semantics, an open handle can continue to access the underlying object even after its last pathname is removed; other platforms impose different sharing and deletion rules. Code that stores a path and code that stores an open stream therefore retain different relationships to external state.

Python's <code>open</code> accepts a path-like object or, under documented conditions, an integer descriptor. Passing <code>closefd=False</code> can leave a supplied descriptor open when the file object closes. This is an ownership decision and should rarely be implicit:

~~~python
import os


descriptor = os.open("sample.bin", os.O_RDONLY)
try:
    with open(descriptor, "rb", closefd=False) as stream:
        prefix = stream.read(4)
    os.fstat(descriptor)  # descriptor remains open
finally:
    os.close(descriptor)
~~~

The example uses the low-level <code>os</code> API only to expose ownership. In routine code, let <code>open</code> acquire and close its own descriptor. Two wrappers around one descriptor can interfere through shared offsets and closure, especially when buffering is involved.

An **open file description** is an operating-system concept on POSIX-like systems that retains status flags and the current offset behind one or more descriptors. A descriptor duplicated from another may share that description. This implementation-level distinction explains why copying an integer descriptor does not necessarily create an independent cursor.

### 11.3.2 Modes are bundles of policy

An opening mode combines an initial access direction with optional modifiers:

| Mode component | Contract |
|---|---|
| <code>r</code> | open an existing resource for reading; fail if absent |
| <code>w</code> | open for writing; create if absent and truncate if present |
| <code>x</code> | create exclusively for writing; fail if the path already exists |
| <code>a</code> | open for writing at the end; create if absent |
| <code>+</code> | permit both reading and writing under update-stream rules |
| <code>b</code> | expose bytes and suppress text encoding/newline conversion |
| <code>t</code> | expose text; this is the default where neither <code>b</code> nor <code>t</code> appears |

Exactly one of <code>r</code>, <code>w</code>, <code>x</code>, or <code>a</code> selects the primary mode. Modifiers do not commute conceptually even though accepted spellings such as <code>rb+</code> and <code>r+b</code> denote the same mode.

Opening with <code>w</code> can truncate before the first explicit <code>write</code>:

~~~python
from pathlib import Path


path = Path("important.txt")
path.write_text("previous contents", encoding="utf-8")

stream = path.open("w", encoding="utf-8")
try:
    assert path.read_bytes() == b""
finally:
    stream.close()
~~~

The assertion is an illustrative observation under ordinary local-file behaviour; the library contract is that <code>w</code> truncates first. Delaying a later calculation until after opening therefore risks destroying the previous version before the calculation succeeds. Compute and validate before destructive acquisition, or stage output as §11.1.4 described.

Exclusive creation with <code>x</code> combines the existence decision and creation in one filesystem operation:

~~~python
with Path("run.lock").open("x", encoding="ascii") as stream:
    stream.write("owner=example\n")
~~~

This avoids the elementary race in “if not exists, then create”. It does not by itself implement a reliable lock: stale files, process identity, network filesystems, permissions, symbolic links, cleanup, crash recovery, and ownership verification remain design issues. A dedicated locking primitive is preferable when mutual exclusion is the actual requirement.

> **Common misconception 11.12 — “Opening in write mode changes data only when <code>write</code> runs.”** Mode <code>w</code> truncates an existing file as part of opening.

### 11.3.3 Append is not a general transaction

Append mode arranges for writes to occur at the end according to the underlying platform contract. It is useful for logs and journals, but several distinct properties must not be conflated:

- positioning a write at the then-current end;
- keeping all bytes from one high-level call contiguous;
- preventing interleaving between concurrent writers;
- preserving a complete logical record;
- making the record durable after a crash;
- ordering records consistently across processes or machines.

Append mode may strengthen the first property for a local descriptor. Python text buffering can merge several calls or defer them, while a large logical record can require several lower-level operations. Filesystems and remote mounts can provide different atomicity. Therefore a log format intended for concurrent writers needs a documented maximum record size, serialisation mechanism, framing, integrity detection, and recovery policy.

~~~python
import json
from pathlib import Path


def append_event(path: Path, event: dict[str, object]) -> None:
    line = json.dumps(
        event,
        ensure_ascii=False,
        allow_nan=False,
        separators=(",", ":"),
    )
    if "\n" in line or "\r" in line:
        raise AssertionError("JSON encoder emitted a literal line ending")
    with path.open("a", encoding="utf-8", newline="\n") as stream:
        stream.write(line + "\n")
~~~

The function creates a JSON Lines-like record and avoids literal newlines within the encoded JSON string. It does not claim multi-process atomicity or durable acceptance. Opening for every event narrows buffering lifetime but increases overhead; keeping a stream open changes flushing and rotation behaviour. The correct choice follows operational requirements.

### 11.3.4 Read/write update streams

Modes containing <code>+</code> permit reads and writes through one stream. They do not mean “read the old file and automatically append a replacement”. The one current position, buffering, and text decoder state make transitions delicate.

~~~python
from pathlib import Path


path = Path("counter.txt")
path.write_text("41\n", encoding="ascii")

with path.open("r+", encoding="ascii", newline="\n") as stream:
    current = int(stream.read())
    stream.seek(0)
    stream.write(f"{current + 1}\n")
    stream.truncate()
~~~

The explicit <code>seek(0)</code> returns to the beginning after the read. <code>truncate()</code> removes any old suffix; without it, writing a shorter representation could leave stale bytes. This is still not safe concurrent increment: two processes can both read 41 and both write 42, losing one update. It is also not failure-atomic because a crash or write error can leave partial content.

Buffered update streams require repositioning or flushing at appropriate transitions as specified by the interface. A simpler and safer design often separates read and staged replacement, or delegates transactional mutation to a database.

> **Common misconception 11.13 — “<code>r+</code> makes file updates atomic.”** It grants both capabilities on one stream; it supplies no transaction or mutual exclusion.

### 11.3.5 Positions in binary and text streams

For an ordinary seekable binary file, offsets are byte positions relative to a reference point:

~~~python
import io
from pathlib import Path


path = Path("positions.bin")
path.write_bytes(b"abcdef")

with path.open("rb") as stream:
    stream.seek(2, io.SEEK_SET)
    assert stream.read(2) == b"cd"
    assert stream.tell() == 4
    stream.seek(-1, io.SEEK_CUR)
    assert stream.read(1) == b"d"
~~~

<code>SEEK_SET</code>, <code>SEEK_CUR</code>, and <code>SEEK_END</code> select the origin where supported. Seeking beyond the current end and then writing can create a gap. On filesystems supporting **sparse files**, the gap may be represented without allocating physical storage for every zero byte; apparent size and allocated storage then differ.

A text stream's <code>tell</code> result is an opaque position value—a **cookie**—sufficient for certain later <code>seek</code> operations on that stream under documented restrictions. Decoder state, buffered bytes, and newline translation can all be encoded in it. Arithmetic on that cookie is generally meaningless:

~~~python
from pathlib import Path


Path("words.txt").write_text("α\nβ\n", encoding="utf-8")
with Path("words.txt").open("r", encoding="utf-8") as stream:
    checkpoint = stream.tell()
    first = stream.readline()
    stream.seek(checkpoint)
    assert stream.readline() == first
~~~

Use byte mode when a protocol defines numeric byte offsets. Use saved text cookies when revisiting decoded positions. Reopening a file and reusing a text cookie after the content or configuration changes is not a general persistence format.

### 11.3.6 Seeking is a capability, not a universal stream property

Regular files are normally seekable. Terminals, pipes, sockets, compressed streams, and generators often are not. A parser that requires rewinding has a stronger input contract than one that consumes forward only.

~~~python
from typing import TextIO


def inspect_prefix(stream: TextIO, count: int) -> str:
    if not stream.seekable():
        raise ValueError("stream must be seekable")
    position = stream.tell()
    try:
        return stream.read(count)
    finally:
        stream.seek(position)
~~~

The function restores the position even if reading raises, as far as the subsequent seek succeeds. It cannot restore external device state, elapsed time, or other side effects. A more composable interface might accept the prefix separately rather than requiring rewind.

When sniffing a format from a non-seekable source, retain only a bounded prefix and then replay it before the remainder:

~~~python
from collections.abc import Iterable, Iterator


def prepend(prefix: bytes, chunks: Iterable[bytes]) -> Iterator[bytes]:
    if prefix:
        yield prefix
    yield from chunks
~~~

This solves chunk replay, not byte-stream method emulation. Libraries requiring a file-like object may need a purpose-built wrapper with clearly implemented methods.

### 11.3.7 Iteration, lines, and bounded memory

Iterating a text file requests logical lines lazily:

~~~python
with Path("events.log").open(
    "r",
    encoding="utf-8",
    errors="strict",
    newline=None,
) as stream:
    for line_number, line in enumerate(stream, start=1):
        process(line_number, line)
~~~

The loop does not retain all previous lines unless <code>process</code> does. However, laziness alone gives no fixed memory bound because a line terminator may be absent for an arbitrarily large prefix. A format with untrusted input should state a maximum record size and use a reader capable of enforcing it before allocating the whole record.

<code>read()</code> without a size and <code>readlines()</code> materialise the remaining content or list of lines. They are appropriate when a validated size is small and the simpler whole-value algorithm reduces risk. “Streaming is always better” is false: streaming introduces incremental state and partial-output concerns. The trade-off is between bounded resources, algorithmic simplicity, and transactional needs.

For binary block processing, a sentinel iterator expresses repeated reads:

~~~python
from functools import partial
from pathlib import Path


def checksum_xor(path: Path, block_size: int = 64 * 1024) -> int:
    if block_size <= 0:
        raise ValueError("block_size must be positive")
    accumulator = 0
    with path.open("rb") as stream:
        for block in iter(partial(stream.read, block_size), b""):
            for octet in block:
                accumulator ^= octet
    return accumulator
~~~

The two-argument form of <code>iter</code> repeatedly calls the zero-argument callable until it returns the sentinel. The example's XOR is not a secure hash and is a poor corruption detector; it exists only to demonstrate block iteration. Use <code>hashlib</code> with an appropriate cryptographic algorithm where cryptographic digest properties are required, while remembering that an unkeyed digest does not authenticate an adversarial source.

### 11.3.8 Closing, finalisation, and ownership

Calling <code>close</code> releases a stream's owned resources and flushes as its contract specifies. On Python's I/O base classes, repeated close calls are harmless. Operations on a closed stream generally fail, but relying on garbage collection to close a resource makes lifetime non-local and implementation-dependent.

~~~python
stream = Path("sample.txt").open("r", encoding="utf-8")
try:
    first = stream.readline()
finally:
    stream.close()

assert stream.closed
~~~

The <code>with</code> statement expresses the same lifetime more safely, especially across returns and exceptions. A function should ordinarily close resources it acquires and leave caller-supplied resources open:

~~~python
from typing import TextIO


def first_line_from_stream(stream: TextIO) -> str:
    return stream.readline()


def first_line_from_path(path: Path) -> str:
    with path.open("r", encoding="utf-8") as stream:
        return first_line_from_stream(stream)
~~~

The names make ownership visible. Returning a lazy iterator derived from a stream opened inside <code>with</code> is a common error because iteration begins after closure:

~~~python
def broken_lines(path: Path) -> object:
    with path.open("r", encoding="utf-8") as stream:
        return (line.rstrip("\n") for line in stream)
~~~

The generator expression retains the closed stream. A generator function can instead make the resource lifetime coincide with iteration:

~~~python
from collections.abc import Iterator


def stripped_lines(path: Path) -> Iterator[str]:
    with path.open("r", encoding="utf-8") as stream:
        for line in stream:
            yield line.rstrip("\n")
~~~

Now closing occurs when iteration ends normally, raises, or the generator is explicitly closed. If a caller abandons the generator without closing it, timely cleanup can still depend on finalisation. An explicit outer context manager or callback-based consumer may provide a stronger ownership contract for critical resources.

> **Common misconception 11.14 — “Returning a generator from inside <code>with</code> keeps the context open.”** A generator expression returned after the block refers to a resource that the block has already closed. A generator function whose <code>with</code> encloses <code>yield</code> has different timing.

### 11.3.9 Buffer position and mixed access

Buffered objects can read ahead. The operating-system descriptor position may therefore lie beyond the logical position exposed by the buffered wrapper. Mixing high-level operations with direct descriptor operations can observe surprising positions or reorder data:

~~~python
# Do not treat this as a recommended pattern.
with Path("sample.bin").open("rb") as stream:
    first = stream.read(1)
    descriptor = stream.fileno()
    # A direct os.read(descriptor, ...) may begin after bytes already
    # prefetched into stream's buffer, not immediately after first.
~~~

If low-level and high-level access must coexist, use an API specifically designed for the required coordination and establish buffering rules. Similarly, two file objects opened independently on the same pathname usually have independent descriptors and offsets, but they do not gain coherent caching or writer coordination.

Text encoders may hold pending state, and output buffers may defer bytes. <code>flush</code> coordinates downward transfer through the wrapper; <code>seek</code> on a supported update stream can also force coordination under documented rules. Directly manipulating the descriptor behind a wrapper violates the abstraction unless the documentation expressly supports the operation.

### 11.3.10 File errors are structured observations

Filesystem operations commonly raise subclasses of <code>OSError</code>, including <code>FileNotFoundError</code>, <code>FileExistsError</code>, <code>PermissionError</code>, <code>IsADirectoryError</code>, and <code>NotADirectoryError</code>. These classifications describe the failed operation under one observed state. They do not always establish a permanent cause.

~~~python
def load_required_text(path: Path) -> str:
    try:
        return path.read_text(encoding="utf-8")
    except FileNotFoundError as error:
        raise ValueError(f"required input is absent: {path}") from error
    except IsADirectoryError as error:
        raise ValueError(f"input path names a directory: {path}") from error
~~~

Do not use exception text as a portable error code. The exception object may expose <code>errno</code>, <code>filename</code>, and platform information, but a domain adapter should publish only what its caller needs.

Permission failure does not prove that an object exists: access controls can deliberately conceal existence, path traversal can fail at an ancestor, and state can change. “Not found” similarly may describe one pathname resolution rather than deletion of an object whose handle another process retains.

### 11.3.11 File-like protocols and dependency inversion

Many standard-library parsers accept **file-like objects**: objects providing the methods needed by the parser rather than requiring one concrete class. This is an instance of structural interface design. A producer can write to a real file, compressed wrapper, terminal, or in-memory stream when each satisfies the required protocol.

Python typing can make the smallest interface explicit:

~~~python
from typing import Protocol


class TextWriter(Protocol):
    def write(self, text: str, /) -> int:
        ...


def write_record(destination: TextWriter, name: str, score: int) -> None:
    destination.write(f"{name}\t{score}\n")
~~~

The protocol says nothing about closure because this function does not own the writer. It says nothing about <code>flush</code> because the function does not promise immediate transmission. The return count is accepted but unused because common text writers report characters accepted. A stronger interface should be introduced only when its operation is genuinely required.

Structural compatibility does not make all streams semantically interchangeable. A writer can satisfy <code>write</code> while failing after a threshold, transforming output, blocking indefinitely, or performing remote effects. Tests should include fault-injecting implementations when partial failure matters:

~~~python
class FailingWriter:
    def __init__(self, allowance: int) -> None:
        self.allowance = allowance
        self.received = ""

    def write(self, text: str, /) -> int:
        if len(text) > self.allowance:
            raise OSError("simulated capacity exhaustion")
        self.received += text
        self.allowance -= len(text)
        return len(text)
~~~

This deterministic double makes the failure boundary testable. It does not faithfully emulate buffering, encodings, or every operating-system write failure. A test double should be justified by the property it probes.
