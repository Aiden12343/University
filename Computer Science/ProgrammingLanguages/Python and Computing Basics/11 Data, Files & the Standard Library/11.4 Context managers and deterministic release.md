# 11.4 Context managers and deterministic release

A **context manager** controls entry into and exit from a runtime context using `__enter__` and `__exit__`, ordinarily through `with`.

```python
with path.open("r", encoding="utf-8") as stream:
    text = stream.read()
```

Conceptually:

1. evaluate the context expression;
2. call its entry protocol;
3. bind the `as` target to the returned object;
4. execute the body;
5. call the exit protocol with exception information if the body raised;
6. propagate the exception unless the exit method truthfully suppresses it.

The exit operation runs for ordinary body completion and ordinary Python control transfers. It does not promise execution after power loss, forced process termination, or fatal runtime failure.

### Worked example 11.3 — Build a context manager

```python
from contextlib import contextmanager
from collections.abc import Iterator


@contextmanager
def labelled_section(label: str) -> Iterator[None]:
    print("begin", label)
    try:
        yield
    finally:
        print("end", label)


with labelled_section("calculation"):
    print(6 * 7)
```

The generator-based adapter runs to `yield` on entry and resumes for cleanup on exit. It must yield exactly once under this protocol. The `finally` preserves cleanup for body return or exception. A class-based context manager is preferable when richer reusable state or separate methods improve the model.

`contextlib.ExitStack` manages a dynamic number of context managers and callbacks in last-in-first-out order. It is useful when resource count depends on data and acquisition can fail partway; each successful acquisition is registered immediately for later release.

### 11.4.1 The protocol as a control-flow transformation

For a single manager, the essential semantics of

~~~python
with expression as target:
    body()
~~~

can be understood through an approximate transformation:

~~~python
manager = expression
enter = type(manager).__enter__
exit_method = type(manager).__exit__
value = enter(manager)
normal_completion = False
try:
    target = value
    body()
    normal_completion = True
finally:
    if normal_completion:
        exit_method(manager, None, None, None)
    else:
        # Conceptual only: Python supplies the active exception details.
        suppress = exit_method(manager, exception_type, exception, traceback)
        if not suppress:
            raise
~~~

This is explanatory pseudocode, not an exact substitute for the language reference. It exposes four facts:

1. the context expression is evaluated once;
2. <code>__enter__</code> runs before target binding and body execution;
3. if <code>__enter__</code> itself fails, that manager has not entered and its <code>__exit__</code> is not invoked by this statement;
4. after successful entry, <code>__exit__</code> runs for normal completion and for an exception leaving the body.

The language looks up the special methods through the type as part of special-method semantics. Assigning an <code>__exit__</code> attribute to one instance is therefore not a dependable way to change <code>with</code> behaviour; Chapter 9's special-method lookup model applies.

Several managers in one statement behave like nested <code>with</code> statements:

~~~python
with first() as left, second() as right:
    use(left, right)
~~~

is conceptually ordered as:

~~~python
with first() as left:
    with second() as right:
        use(left, right)
~~~

Thus acquisition proceeds left to right and release proceeds right to left. If entering <code>second</code> fails, <code>first</code> has entered and is exited. This last-in-first-out discipline mirrors the call stack and permits each outer resource to remain valid while inner cleanup runs.

### 11.4.2 Suppression is a semantic decision

When a body raises, <code>__exit__</code> receives the exception type, value, and traceback. If it returns a truthy value, the <code>with</code> statement suppresses that exception; otherwise propagation continues.

~~~python
class SuppressOnlyKeyError:
    def __enter__(self) -> None:
        return None

    def __exit__(
        self,
        exception_type: type[BaseException] | None,
        exception: BaseException | None,
        traceback: object | None,
    ) -> bool:
        return exception_type is KeyError


with SuppressOnlyKeyError():
    {}["missing"]

print("execution continued")
~~~

The equality test suppresses exactly <code>KeyError</code>, not subclasses. <code>issubclass(exception_type, KeyError)</code> after a <code>None</code> check would include subclasses. Which is correct depends on the contract.

Most resource managers should return <code>False</code> or <code>None</code>, ensuring cleanup without suppression. Accidental truthy returns can hide failures:

~~~python
class BrokenManager:
    def __enter__(self) -> "BrokenManager":
        return self

    def __exit__(self, *details: object) -> list[str]:
        release_resource()
        return ["released"]  # truthy: suppresses every body exception
~~~

This is why an explicit <code>return False</code> can communicate intent even though falling off the function returns <code>None</code>. Suppression belongs only where an exception is an anticipated control outcome and continuing is correct.

If <code>__exit__</code> itself raises, cleanup failure becomes part of exception propagation. Python can retain the earlier exception as context or cause, but callers must decide which failure is primary. Cleanup code should be narrow, idempotent where feasible, and designed not to obscure evidence.

> **Common misconception 11.15 — “<code>with</code> swallows exceptions.”** It guarantees an exit-protocol call after successful entry. The original exception is suppressed only when the exit method returns truthy.

### 11.4.3 Context-manager state machines

A context manager has states even if its implementation does not name them:

~~~mermaid
stateDiagram-v2
    [*] --> New
    New --> Entered: enter succeeds
    New --> Failed: enter raises
    Entered --> Exited: exit completes
    Entered --> ExitFailed: exit raises
    Exited --> [*]
    Failed --> [*]
    ExitFailed --> [*]
~~~

A manager may be **single-use**, **reusable**, or **re-entrant**:

- single-use means one instance supports one entry/exit lifetime;
- reusable means the same instance can be used in separate, non-overlapping statements;
- re-entrant means the same instance supports nested entry before an earlier exit.

These properties are independent. A lock type, redirector, or transactional manager may have specific documented behaviour. Never infer re-entrancy merely because a second use happened to work in one test.

The following single-use manager makes its state explicit:

~~~python
from enum import Enum, auto


class State(Enum):
    NEW = auto()
    ENTERED = auto()
    EXITED = auto()


class ManagedBuffer:
    def __init__(self) -> None:
        self.state = State.NEW
        self.data = bytearray()

    def __enter__(self) -> bytearray:
        if self.state is not State.NEW:
            raise RuntimeError("manager is single-use")
        self.state = State.ENTERED
        return self.data

    def __exit__(self, *details: object) -> bool:
        if self.state is not State.ENTERED:
            raise RuntimeError("manager is not entered")
        self.data.clear()
        self.state = State.EXITED
        return False
~~~

Clearing the bytearray is deterministic application cleanup; it is not secure memory erasure because copies, allocator behaviour, operating-system paging, and interpreter internals remain outside the guarantee.

### 11.4.4 Generator-based managers and the yield boundary

<code>@contextmanager</code> adapts a generator function containing exactly one yielded value. Code before <code>yield</code> implements entry; code after it implements exit. If the body raises, that exception is thrown into the generator at the yield point.

~~~python
from collections.abc import Iterator
from contextlib import contextmanager
from pathlib import Path


@contextmanager
def temporary_current_directory(path: Path) -> Iterator[None]:
    import os

    previous = Path.cwd()
    os.chdir(path)
    try:
        yield
    finally:
        os.chdir(previous)
~~~

This example illustrates the protocol but has a major design hazard: the working directory is process-global state, so unrelated code and threads observe the change. A context manager gives lexical lifetime, not isolation. Prefer passing explicit root paths.

If a generator manager catches an exception only to log it, it must re-raise unless suppression is intended:

~~~python
@contextmanager
def report_failure(label: str) -> Iterator[None]:
    try:
        yield
    except Exception:
        print(f"{label} failed")
        raise
~~~

If the <code>except</code> block ended normally, <code>contextmanager</code> would interpret the handled exception as suppressed. A <code>finally</code> is usually the right construct for unconditional release.

The generator must yield exactly once. Returning before yielding means entry fails; yielding twice means exit cannot complete according to the one-boundary protocol. A class-based manager is clearer when entry and exit require a rich state model, multiple helper methods, or explicit reuse.

> **Common misconception 11.16 — “Code after <code>yield</code> always runs in a generator context manager.”** It runs only if control reaches it. Place mandatory cleanup in <code>finally</code>, because an exception thrown at the yield point otherwise bypasses subsequent ordinary statements.

### 11.4.5 Small adapters in <code>contextlib</code>

The module supplies focused adapters for recurring lifetime patterns:

- <code>closing(value)</code> calls <code>value.close()</code> on exit for an object that lacks its own context protocol;
- <code>aclosing(value)</code> does the analogous operation for asynchronous generators and resources;
- <code>nullcontext(value)</code> returns the value and otherwise does nothing, allowing optional ownership without duplicated control flow;
- <code>suppress(E1, E2, ...)</code> deliberately suppresses the named exception classes;
- <code>redirect_stdout</code> and <code>redirect_stderr</code> temporarily rebind process-global stream objects and therefore affect other code using those globals;
- <code>chdir</code> temporarily changes the process working directory and carries the global-state caveat demonstrated above.

<code>nullcontext</code> is particularly useful when a function accepts either a path it must open or a caller-owned stream:

~~~python
from contextlib import nullcontext
from os import PathLike
from typing import TextIO


def count_text_lines(source: str | PathLike[str] | TextIO) -> int:
    if isinstance(source, (str, PathLike)):
        manager = open(source, "r", encoding="utf-8")
    else:
        manager = nullcontext(source)

    with manager as stream:
        return sum(1 for _ in stream)
~~~

The function closes only the stream it creates. Runtime use of <code>PathLike</code> here is illustrative and should be tested for the supported Python version; an overload-based public signature can describe the alternatives more precisely to static tools.

<code>suppress</code> should enclose the smallest operation for which absence is genuinely acceptable:

~~~python
from contextlib import suppress


with suppress(FileNotFoundError):
    temporary_path.unlink()
~~~

Placing a large body inside the manager could suppress an unrelated <code>FileNotFoundError</code> from a later operation. Narrow lexical scope is part of correct exception classification.

### 11.4.6 Dynamic acquisition with <code>ExitStack</code>

Static nesting works when the number and types of resources are known in source code. <code>ExitStack</code> represents an explicit stack of exit actions for dynamic acquisition:

~~~python
from contextlib import ExitStack
from pathlib import Path
from typing import TextIO


def open_all(paths: list[Path]) -> tuple[ExitStack, list[TextIO]]:
    stack = ExitStack()
    try:
        streams = [
            stack.enter_context(path.open("r", encoding="utf-8"))
            for path in paths
        ]
    except BaseException:
        stack.close()
        raise
    return stack, streams
~~~

The caller must close the returned stack, so a better public interface normally wraps it in its own context manager:

~~~python
from collections.abc import Iterator, Sequence
from contextlib import contextmanager


@contextmanager
def opened_texts(paths: Sequence[Path]) -> Iterator[list[TextIO]]:
    with ExitStack() as stack:
        streams = [
            stack.enter_context(path.open("r", encoding="utf-8"))
            for path in paths
        ]
        yield streams
~~~

If opening path three fails, streams two and one are closed in that order. If the body fails, all acquired streams are likewise closed in reverse order. Acquisition is registered immediately rather than after the entire list succeeds.

<code>callback</code> registers an ordinary callback for unconditional exit:

~~~python
with ExitStack() as stack:
    path = create_named_temporary_file()
    stack.callback(path.unlink, missing_ok=True)
    use(path)
~~~

Callbacks registered this way do not receive exception details and cannot suppress a body exception. <code>push</code> registers an exit-protocol-compatible callable or manager exit method and can participate in suppression. The distinction should be explicit in review.

<code>pop_all</code> transfers the entire cleanup stack to a new <code>ExitStack</code> without invoking it. This supports an acquire-all-or-release-all pattern:

~~~python
def acquire_files(paths: list[Path]) -> tuple[ExitStack, list[TextIO]]:
    with ExitStack() as provisional:
        streams = [
            provisional.enter_context(path.open("rb"))
            for path in paths
        ]
        ownership = provisional.pop_all()
    return ownership, streams
~~~

Ownership has moved to the returned stack. Such an API is powerful but places a non-obvious release obligation on the caller; a context-manager facade is generally safer.

### 11.4.7 Transactions as context managers

A context manager can express commit on normal completion and rollback on exception:

~~~python
from typing import Protocol, Self


class Transaction(Protocol):
    def __enter__(self) -> Self:
        ...

    def commit(self) -> None:
        ...

    def rollback(self) -> None:
        ...

    def __exit__(
        self,
        exception_type: type[BaseException] | None,
        exception: BaseException | None,
        traceback: object | None,
    ) -> bool:
        ...
~~~

One possible implementation delegates actual atomicity to a transactional backend:

~~~python
class UnitOfWork:
    def __init__(self, connection: object) -> None:
        self.connection = connection
        self.committed = False

    def __enter__(self) -> "UnitOfWork":
        self.connection.begin()  # type: ignore[attr-defined]
        return self

    def commit(self) -> None:
        self.connection.commit()  # type: ignore[attr-defined]
        self.committed = True

    def __exit__(self, *details: object) -> bool:
        if not self.committed:
            self.connection.rollback()  # type: ignore[attr-defined]
        return False
~~~

The context manager itself does not create transaction semantics; the backend must define isolation, atomicity, durability, nested behaviour, and failure recovery. If <code>commit</code> returns and later exit performs no rollback, the application regards that point as committed. A commit call can also fail with an ambiguous outcome in remote systems, bringing retry analysis back into scope.

An alternative convention commits automatically only when the body exits normally. Both conventions are defensible:

- explicit commit makes acceptance visible and rolls back forgotten work;
- automatic commit reduces ceremony but can commit merely because no exception happened.

The API must make its choice unmistakable.

### 11.4.8 Contexts are lexical, not magical

A <code>with</code> statement gives an operation a lexical beginning and end. It does not:

- make global state thread-local;
- make an object immutable;
- guarantee cleanup after process destruction or power loss;
- turn several effects into one transaction;
- impose a timeout;
- cancel background work;
- make finalisation errors impossible;
- grant or revoke operating-system authority by itself.

These limitations explain when a context manager is the correct abstraction: the resource has a composable enter/exit lifetime and the program can perform meaningful release during ordinary Python control flow.

Asynchronous context managers use <code>__aenter__</code>, <code>__aexit__</code>, and <code>async with</code> because their acquisition or release can await asynchronous operations. This is an explicitly flagged forward reference to Chapter 14. The lifetime reasoning—successful entry, reverse-order exit, suppression policy, and ownership—remains applicable.

### Worked example 11.4-A — Verify cleanup ordering

~~~python
from contextlib import contextmanager
from collections.abc import Iterator


@contextmanager
def observed(name: str, events: list[str]) -> Iterator[str]:
    events.append(f"enter:{name}")
    try:
        yield name
    finally:
        events.append(f"exit:{name}")


events: list[str] = []
with observed("outer", events), observed("inner", events):
    events.append("body")

assert events == [
    "enter:outer",
    "enter:inner",
    "body",
    "exit:inner",
    "exit:outer",
]
~~~

This test establishes one language-level ordering claim using an observable trace. It does not establish what an operating system does when a real close fails. Replacing one resource with a controlled observer is valid because the property under test is protocol order, not filesystem behaviour.
