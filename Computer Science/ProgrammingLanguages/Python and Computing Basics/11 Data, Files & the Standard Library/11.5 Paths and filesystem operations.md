# 11.5 Paths and filesystem operations

`pathlib.Path` represents concrete paths for the current platform. Construction and composition do not prove existence:

```python
root = Path("project")
input_path = root / "data" / "input.txt"
```

The `/` operator is overloaded for path composition. Filesystem methods then cross the external boundary.

Useful distinctions:

- `exists()` observes whether accessible state presently resolves; the result can become stale immediately.
- `is_file()` and `is_dir()` classify a presently resolved target, subject to links and permissions.
- `resolve()` performs canonicalisation under platform and argument rules; it may access the filesystem.
- `absolute()` and path anchoring do not necessarily resolve symbolic links.
- `iterdir()` yields directory entries in filesystem-provided order; sort when stable order is required.
- `glob()` and `rglob()` select paths by patterns; pattern rules are not full regular expressions.

Avoid **time-of-check to time-of-use** assumptions:

```python
if path.exists():
    text = path.read_text(encoding="utf-8")
```

Another process can remove or replace the entry between check and read. Attempt the required operation and handle its defined failure. Pre-checks remain useful for user messaging or branching when races are harmless, but they cannot guarantee later state.

### Worked example 11.4 — Safe project-root containment is semantic

Joining a user path to a root does not by itself confine resolution:

```python
candidate = root / user_text
```

`user_text` may be absolute, contain parent components, or traverse symbolic links. A defensive file-serving interface must define whether links are followed, whether missing targets are allowed, which root identity matters, and how races are handled. Lexical removal of `..` is not equivalent to filesystem containment. Security-sensitive path confinement should use platform-aware, race-resistant operations and avoid granting a path resolver more authority than necessary.

### 11.5.1 Path syntax is not object identity

A path is a structured name interpreted by a path grammar and a resolution context. On POSIX-like systems, a leading separator ordinarily denotes a path from the root directory. On Windows, drive letters, rooted paths, UNC shares, reserved names, and multiple separator conventions produce a different grammar. <code>pathlib</code> offers concrete current-platform classes and pure grammar classes:

~~~python
from pathlib import PurePosixPath, PureWindowsPath


posix = PurePosixPath("/srv", "data", "report.csv")
windows = PureWindowsPath("C:/", "data", "report.csv")

assert posix.name == "report.csv"
assert posix.parent == PurePosixPath("/srv/data")
assert windows.drive == "C:"
~~~

Pure paths perform lexical manipulation without consulting a filesystem. They can analyse paths for a foreign platform, but they cannot establish existence, identity, permissions, link targets, or case-equivalence rules of a concrete filesystem.

A **relative path** is resolved relative to a context, normally the process current working directory or an explicitly supplied directory handle. The process current working directory is mutable global state:

~~~python
from pathlib import Path


relative = Path("config/settings.json")
captured_root = Path.cwd()
anchored = captured_root / relative
~~~

The composed <code>anchored</code> records one lexical choice. Another thread or library can change the process current directory before a later operation on <code>relative</code>. Passing an explicit project root is more stable than repeatedly relying on ambient state.

An **absolute path** is anchored according to its grammar. It is still not a globally permanent identity: mounts can change, directory entries can be replaced, drive mappings can differ between sessions, names can vary in case and Unicode normalisation, and links can redirect resolution.

> **Common misconception 11.17 — “An absolute path uniquely identifies a file forever.”** It anchors name resolution; it does not freeze mounts, directory entries, links, or the referred object's lifetime.

### 11.5.2 Components, names, stems, and suffixes

<code>Path</code> exposes lexical components:

~~~python
from pathlib import Path


path = Path("/var/archive/results.tar.gz")

assert path.name == "results.tar.gz"
assert path.stem == "results.tar"
assert path.suffix == ".gz"
assert path.suffixes == [".tar", ".gz"]
assert path.parent == Path("/var/archive")
~~~

These are syntactic operations. A “file extension” is a naming convention, not a content guarantee. An attacker can name executable content <code>image.jpg</code>; a valid JPEG can have no suffix. Robust format handling uses a declared protocol and validates its internal structure. Content-signature checks can reduce accidental misclassification but are not authorisation.

<code>with_name</code>, <code>with_stem</code>, and <code>with_suffix</code> construct related names without accessing storage:

~~~python
source = Path("measurements.csv")
temporary = source.with_name(f".{source.name}.tmp")
output = source.with_suffix(".json")
~~~

Predictable temporary names are unsafe for shared directories because another principal can create or redirect them first. Use <code>tempfile</code> secure creation APIs when the name crosses a trust boundary.

Joining has a replacement rule: an absolute later operand can discard the earlier anchor according to the path flavour:

~~~python
root = Path("/srv/application")
candidate = root / "/etc/passwd"

assert candidate == Path("/etc/passwd")
~~~

Consequently, joining a trusted root to untrusted text is not confinement.

### 11.5.3 Lexical normalisation and resolved canonicalisation

Lexical path processing manipulates components according to grammar without observing the filesystem. Resolved canonicalisation follows links and consults actual directory state. They answer different questions.

The component <code>.</code> ordinarily denotes the current directory. The component <code>..</code> ordinarily denotes the parent during resolution, but eliminating it lexically can change meaning in the presence of symbolic links:

~~~text
/safe/link/../record
~~~

If <code>link</code> refers to <code>/elsewhere/subdirectory</code>, filesystem resolution can enter that target before processing <code>..</code>. Treating the text as if <code>link/..</code> simply cancels may identify a different object.

<code>Path.resolve</code> makes a path absolute and resolves symbolic links under its versioned <code>strict</code> rules. <code>Path.absolute</code> produces an absolute path without necessarily resolving links or normalising every special component. <code>os.path.abspath</code> is also primarily a lexical current-directory operation on common platforms. None creates an immutable capability to the resolved object.

~~~python
candidate = Path("data/../data/report.csv")
lexical_absolute = candidate.absolute()
resolved = candidate.resolve(strict=False)
~~~

The two results can print identically in a simple fixture and diverge under links or missing components. A test showing equality in one directory is not a specification that the operations are interchangeable.

### 11.5.4 Symbolic links, hard links, and aliases

A **symbolic link** is a filesystem object whose content directs pathname resolution to another path. It can refer to a missing target, form a loop, cross a filesystem boundary, or be changed independently. <code>Path.is_symlink</code> asks about the directory entry itself, while many other operations follow it by default.

A **hard link** is another directory entry referring to the same underlying filesystem object where the filesystem supports that model. Hard-linked paths are peers; there is no intrinsic “original name”. Modifying contents through either name ordinarily affects the same object. Replacing one pathname with a new object does not necessarily update the other link.

~~~python
import os
from pathlib import Path
from tempfile import TemporaryDirectory


with TemporaryDirectory() as directory:
    root = Path(directory)
    first = root / "first.txt"
    second = root / "second.txt"
    first.write_text("A", encoding="utf-8")
    os.link(first, second)
    second.write_text("B", encoding="utf-8")
    assert first.read_text(encoding="utf-8") == "B"
~~~

This experiment depends on a filesystem and platform supporting hard links and may fail under restricted permissions. It demonstrates aliasing, not a universal implementation detail.

Identity can be compared through <code>Path.samefile</code>, which consults filesystem identity and requires resolvable objects. The result is a temporal observation. On POSIX-like systems, device and inode numbers often contribute to identity, but reuse after deletion and platform variation prevent them from being universal permanent IDs.

> **Common misconception 11.18 — “Different path strings imply different files.”** Links, case rules, mount aliases, and normalisation can make several names resolve to the same object.

### 11.5.5 Metadata and <code>stat</code>

**Metadata** describes an object rather than being its ordinary file content. Common metadata includes type, logical size, timestamps, ownership, permissions, and filesystem identity. <code>Path.stat()</code> follows symbolic links; <code>Path.lstat()</code> describes a link entry itself where supported.

~~~python
from pathlib import Path
import stat


path = Path("report.txt")
information = path.stat()

print(information.st_size)
print(stat.S_ISREG(information.st_mode))
print(information.st_mtime_ns)
~~~

The <code>st_size</code> meaning varies by object type. A regular file's logical byte length is not necessarily allocated disk consumption. Timestamp resolution and semantics vary by filesystem; “modification time changed” is not a cryptographic integrity proof, and equal modification times do not prove equal content.

Separate calls can observe different versions. If code opens a file, then asks <code>path.stat()</code>, the pathname may by then refer to another object. <code>os.fstat(stream.fileno())</code> asks about the opened descriptor where supported:

~~~python
import os


with path.open("rb") as stream:
    opened_metadata = os.fstat(stream.fileno())
    payload = stream.read()
~~~

This ties metadata more closely to the opened resource, although content can still be concurrently modified unless the environment supplies stronger exclusion or snapshot semantics.

### 11.5.6 Permissions, ownership, and creation masks

On POSIX-like systems, mode bits express read, write, and execute permissions for owner, group, and others, modified by access-control lists and other policy. Directories interpret these permissions differently from regular files: directory read permits listing names under ordinary rules, while execute/search permits traversal. Windows security uses access-control mechanisms not faithfully represented by POSIX bits.

The process **umask** is a creation mask applied by POSIX-like systems when permissions are requested for a new object. It removes selected permission bits from the requested mode. It does not retroactively alter existing objects.

~~~python
import os


flags = os.O_WRONLY | os.O_CREAT | os.O_EXCL
descriptor = os.open("private.dat", flags, 0o600)
try:
    os.write(descriptor, b"private\n")
finally:
    os.close(descriptor)
~~~

The requested mode permits only owner read/write before further policy, but operating-system access-control lists, mount options, process privileges, and platform semantics can affect the effective result. Writing secrets also involves backups, swap, crash dumps, inherited handles, logs, and later permission changes. Mode <code>0o600</code> is one control, not a confidentiality proof.

Changing permissions after creating a broadly accessible file leaves an exposure interval. Secure creation requests restrictive access at the creation operation itself. Conversely, overly restrictive permissions can break legitimate service accounts or recovery procedures. Least privilege is determined by system roles, not by always selecting the numerically smallest mode.

### 11.5.7 Directory traversal and ordering

<code>Path.iterdir</code> yields direct entries. <code>glob</code> applies a path pattern, and <code>rglob</code> traverses recursively. Their output order should not be used as a stable semantic order unless documentation specifically promises it; explicit sorting supplies a chosen order:

~~~python
python_sources = sorted(
    Path("src").rglob("*.py"),
    key=lambda item: item.as_posix(),
)
~~~

The sorting key is itself a policy. Lexical code-point order is not locale collation, natural-number order, creation order, or filesystem order. Case sensitivity varies across filesystems, and <code>as_posix</code> is a presentation conversion rather than a portable identity.

Recursive traversal must consider:

- symbolic links and cycles;
- permission failure at a subtree;
- entries disappearing or appearing during iteration;
- mount points and filesystem boundaries;
- total entry count and path depth;
- special files whose reading can block or cause device effects;
- errors encountered after partial results have already been emitted.

A search tool should define whether one unreadable directory aborts the complete search, produces a warning and continues, or becomes a result-level error. Silently skipping it can turn “no match” into a false claim.

<code>os.scandir</code> exposes directory-entry objects and can reuse metadata supplied by the filesystem, often avoiding additional system calls. That is a performance opportunity, not a promise that cached metadata remains current.

### 11.5.8 Creating and removing directories

<code>Path.mkdir</code> can create one directory or missing parents:

~~~python
target = Path("build/reports")
target.mkdir(parents=True, exist_ok=True)
~~~

<code>parents=True</code> creates missing ancestors. <code>exist_ok=True</code> accepts an already existing directory but does not mean all states are acceptable: a conflicting regular file still fails, and permissions or races remain.

Removal operations have type-specific semantics:

- <code>Path.unlink</code> removes a file or symbolic-link directory entry;
- <code>Path.rmdir</code> removes an empty directory;
- recursive tree removal is a higher-risk operation requiring exact target validation.

Never construct a recursive deletion target from an unresolved empty string, broad root, or unchecked user input. A safe design first resolves and verifies a narrow expected parent, refuses roots and project-wide directories, records what it will remove, and considers recovery. Deletion through a symbolic link and traversal beneath a directory require platform-aware treatment.

“Delete” generally removes a namespace reference. Storage blocks can persist in snapshots, backups, journals, remapped device sectors, or until overwritten. Files with other hard links or open handles can remain accessible. Secure erasure is a separate storage-system problem.

### 11.5.9 Rename, replace, and cross-filesystem movement

A **rename** changes a directory entry's name or parent under filesystem rules. <code>Path.rename</code> and <code>Path.replace</code> expose related operations, while <code>os.replace</code> specifically permits replacing an existing destination file where successful.

One-filesystem rename can often provide an atomic namespace transition: observers resolving the destination see the old or new entry rather than a half-name. The guarantee is platform- and filesystem-qualified. Moving across filesystems generally cannot be one rename and may require copy-then-delete, which has partial-copy and duplicate-state windows.

Atomicity, visibility, and durability are independent:

| Property | Question |
|---|---|
| atomic namespace switch | can an observer see a partially installed name? |
| content completeness | was the staged object's complete intended content written? |
| metadata preservation | which permissions, owner, times, links, or extended attributes survived? |
| durability | does the update survive the stated crash or power-loss model? |
| exclusivity | can another writer replace the destination before or after this operation? |
| multi-object consistency | do related files change as one state transition? |

Staging should occur in the same destination filesystem when rename atomicity is required. A random system temporary directory can reside on another filesystem, causing replacement to fail or degrade into a non-atomic copy if a higher-level utility chooses that fallback.

### 11.5.10 Path containment is an authority problem

Suppose a service intends to expose descendants of <code>/srv/public</code>. The tempting check is:

~~~python
root = Path("/srv/public").resolve()
requested = (root / user_text).resolve()
requested.relative_to(root)
~~~

This can reject obvious lexical escape and resolve links at the time of checking. It still separates check from subsequent open. A directory component can be replaced after resolution, and platform-specific aliases or mount changes can complicate the security model. It is suitable only where those races are out of scope or otherwise controlled.

Race-resistant designs resolve and open relative to already-open directory handles, refuse link following where supported, inspect opened handles rather than prechecked names, and reduce process authority. On POSIX-like platforms, selected <code>os</code> functions support <code>dir_fd</code> parameters and flags such as <code>O_NOFOLLOW</code> where the operating system provides them. Availability and exact semantics must be checked:

~~~python
import os


def open_direct_child(directory_fd: int, name: str) -> int:
    if name in {"", ".", ".."} or "/" in name or "\x00" in name:
        raise ValueError("expected one simple path component")
    if os.altsep is not None and os.altsep in name:
        raise ValueError("alternate separator is forbidden")

    flags = os.O_RDONLY
    no_follow = getattr(os, "O_NOFOLLOW", 0)
    return os.open(name, flags | no_follow, dir_fd=directory_fd)
~~~

This example narrows the problem to one direct child and one platform family. It does not portably reject Windows separators, prevent hard-link aliases, restrict special device types, or walk multiple components safely. A production confinement mechanism should use the operating system's supported sandboxing and capability facilities rather than extrapolate this fragment.

> **Common misconception 11.19 — “Resolve, compare prefixes, then open is race-free.”** It improves lexical validation but leaves a time interval in which pathname resolution can change.

### 11.5.11 Filenames are not ordinary portable text

Operating systems differ in how filenames relate to bytes and Unicode. POSIX interfaces fundamentally permit arbitrary non-null bytes other than the separator in a component; Python translates them through the filesystem encoding and error handler. Windows uses a Unicode-oriented API but has reserved names, separators, and path forms. Filesystems can be case-sensitive, case-insensitive, case-preserving, normalising, or combinations thereof.

Consequences include:

- a Python string accepted as a name on one platform may be invalid on another;
- two canonically equivalent Unicode strings may name distinct entries on one filesystem and the same entry on another;
- changing only letter case may or may not create a distinct object;
- a name that prints identically can contain different code points or control characters;
- maximum lengths can be measured in different units and apply to components or whole paths.

Portable projects choose a conservative naming subset and detect collisions under every supported target's comparison rules. They do not use <code>lower</code> alone as a universal filesystem key.

Python's <code>os.fsencode</code> and <code>os.fsdecode</code> apply the configured filesystem codec and error handler. They exist because converting a pathname is not necessarily the same operation as encoding an application document as UTF-8.

### 11.5.12 Paths and shells occupy different grammars

A pathname string is not a shell command. Passing a path through a shell causes characters such as spaces, quotes, wildcards, semicolons, dollar signs, and redirection operators to acquire shell grammar.

Prefer argument-vector APIs:

~~~python
import subprocess
from pathlib import Path


source = Path("reports/quarter 1.csv")
result = subprocess.run(
    ["wc", "-l", str(source)],
    check=True,
    capture_output=True,
    text=True,
    encoding="utf-8",
)
~~~

Here the path is one argument regardless of spaces. Program availability and the meaning of <code>wc</code> are platform assumptions. Passing <code>shell=True</code> would require correct quoting for the selected shell and makes untrusted interpolation dangerous. Shell quoting is not one cross-platform algorithm: POSIX shells and Windows command processors have different grammars, and the invoked program can apply further parsing.

Use Python library functions for filesystem operations when they express the needed semantics. Invoke external programs when their behaviour is actually required, passing a sequence of arguments and documenting environment, encoding, exit-status, timeout, and error policies.

### 11.5.13 Archive paths are another namespace

Archive formats contain member names that can be interpreted as paths during extraction. A member named <code>../../outside</code>, an absolute path, or a link can escape a naive destination. This is **path traversal** through an archive namespace.

Safe extraction requires format- and library-version-specific controls:

1. bound archive and expanded sizes;
2. inspect member types and names;
3. reject absolute and parent-escaping targets;
4. define whether links, devices, permissions, owners, and timestamps are permitted;
5. extract through a mechanism resistant to races and link substitution;
6. run with minimal filesystem authority.

The fact that <code>destination / member_name</code> can be constructed proves nothing about containment. Use secure extraction filters supplied by the relevant maintained library where available, and verify their versioned defaults.

### Worked example 11.5-A — Inventory with explicit uncertainty

The following function gathers a deterministic inventory of regular files beneath a trusted test root without following directory symlinks through <code>os.walk</code>'s default:

~~~python
from dataclasses import dataclass
import os
from pathlib import Path


@dataclass(frozen=True, slots=True)
class InventoryEntry:
    relative_path: str
    size: int


def inventory(root: Path) -> list[InventoryEntry]:
    root = root.resolve(strict=True)
    entries: list[InventoryEntry] = []

    for directory, names, filenames in os.walk(
        root,
        topdown=True,
        followlinks=False,
    ):
        names.sort()
        filenames.sort()
        base = Path(directory)
        for filename in filenames:
            path = base / filename
            try:
                if path.is_file() and not path.is_symlink():
                    metadata = path.stat()
                    entries.append(
                        InventoryEntry(
                            relative_path=path.relative_to(root).as_posix(),
                            size=metadata.st_size,
                        )
                    )
            except OSError as error:
                raise RuntimeError(f"cannot inventory {path}") from error

    return entries
~~~

Sorting provides reproducible traversal within the observed names. The code rejects symbolic-link file entries under the observed state. It is not race-free: an entry can change between <code>is_file</code>, <code>is_symlink</code>, and <code>stat</code>, and the tree can mutate during traversal. For a controlled build directory with no adversarial writer, that may be an acceptable modelling assumption. For a security scanner or privileged service, handle-relative traversal, snapshots, or operating-system sandboxing is required. The example demonstrates how to state that boundary rather than conceal it.
