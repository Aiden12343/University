# 11.6 Buffers, flushing, and durability

A **buffer** temporarily retains data to combine transfers and reduce boundary overhead. Python text streams can buffer characters above a binary buffer, which can buffer bytes above kernel caches and device caches. `flush()` moves data through the current stream’s user-space buffers but does not universally prove stable physical persistence.

Durability is layered:

1. function accepted characters;
2. text encoder produced bytes;
3. user-space buffer passed bytes to the OS;
4. kernel accepted bytes into its cache;
5. filesystem ordering metadata was committed;
6. device acknowledged stable retention;
7. storage survives the named failure model.

Applications such as databases use specific synchronisation calls, write-ahead logging, checksums, ordering protocols, and recovery procedures. Calling `close` is necessary for resource release but not a substitute for a durability specification.

### 11.6.1 Why buffering exists

Crossing an abstraction or hardware boundary has fixed overhead. If one million characters are each passed through a separate system call, call overhead can dominate useful transfer. A buffer accumulates units so that fewer, larger transfers amortise that overhead.

Let \(N\) be total bytes, \(b\) the average batch size, \(c\) the fixed cost per lower-level call, and \(p\) the incremental cost per byte. A simplified transfer model is

\[
T(N,b) \approx \left\lceil\frac{N}{b}\right\rceil c + Np.
\]

Increasing \(b\) reduces the first term until other constraints dominate. The model omits caching, device queues, copying, contention, latency, and asynchronous overlap; it is a modelling assumption useful for identifying why batching helps, not a benchmark prediction.

Buffering trades throughput against:

- latency before data becomes visible downstream;
- memory retained per stream;
- amount of data endangered by process failure;
- complexity when reads, writes, seeks, or multiple wrappers interact;
- delay before an error is reported.

A call to <code>write</code> can succeed because data entered a Python buffer even though the eventual operating-system transfer will fail during <code>flush</code> or <code>close</code>. Correct code must allow release itself to raise.

### 11.6.2 Buffering modes

The <code>buffering</code> argument to <code>open</code> selects implementation policy within documented constraints. Binary I/O can be unbuffered with a zero value. A positive integer requests an approximate buffer size. Text I/O is built over binary buffering; line buffering can be requested for writable text streams, and interactive text streams often receive line-oriented policy.

**Line buffering** means that writing a line-ending character can trigger a flush under the text-stream contract. It does not mean every line becomes physically durable. <code>write_through</code> on <code>TextIOWrapper</code> can pass each text write immediately to the underlying binary buffer while that lower layer remains buffered.

~~~python
import io
from pathlib import Path


with Path("trace.txt").open(
    "w",
    encoding="utf-8",
    buffering=1,
) as stream:
    assert stream.line_buffering
    stream.write("phase one\n")
~~~

Whether another process immediately observes the line also depends on filesystem caches, its own buffers, scheduling, and the way it reads. Buffer settings should be selected for a measured workload and required latency rather than copied as folklore.

Setting an enormous buffer can increase retained memory for many simultaneously open streams. Setting a very small buffer can increase calls. The optimal size is empirical and environment-specific; correctness must not depend on a guessed performance optimum.

### 11.6.3 Visibility is not durability

Suppose a writer flushes and a reader then sees new bytes. This establishes **visibility** to that reader under that observation. It does not establish **durability** across a later power loss. Conversely, a storage subsystem might durably record bytes that another process has not yet observed because its own cache or snapshot hides them.

The layers can be pictured as follows:

~~~mermaid
flowchart TD
    A["Python text state"] --> B["Python binary buffer"]
    B --> C["Kernel page cache"]
    C --> D["Filesystem metadata/data"]
    D --> E["Device cache"]
    E --> F["Persistent medium"]
~~~

This is a conceptual stack; actual operating systems and storage devices can combine, reorder, copy, or bypass layers. Virtual machines, network filesystems, RAID controllers, and cloud block storage add further contracts.

<code>stream.flush()</code> requests transfer through Python-level buffers. <code>os.fsync(stream.fileno())</code> asks the operating system to synchronise the file according to its platform contract:

~~~python
import os
from pathlib import Path


with Path("checkpoint.bin").open("wb") as stream:
    stream.write(b"state-v1\n")
    stream.flush()
    os.fsync(stream.fileno())
~~~

Calling <code>fsync</code> before <code>flush</code> can omit data still retained by Python. A successful call strengthens the durability claim but does not make it platform-independent: device firmware, filesystem configuration, remote servers, faulty hardware, and dishonest acknowledgements are part of the failure model.

Some systems expose <code>fdatasync</code>, which can synchronise file data while treating metadata differently. Portability and the metadata needed to retrieve new bytes must be considered. A performance comparison between <code>fsync</code> and <code>fdatasync</code> is an empirical result, not semantic permission to substitute one for the other.

> **Common misconception 11.20 — “If another process can read it, it is safely stored.”** Visibility through caches and durability across a named failure are independent properties.

### 11.6.4 Durable replacement includes directory state

Replacing a destination pathname changes directory metadata as well as file content. A robust POSIX-oriented sequence for one-file replacement often has the following shape:

1. create a temporary file in the destination directory without a naming race;
2. write complete bytes;
3. flush language-runtime buffers;
4. synchronise the temporary file;
5. atomically replace the destination name;
6. synchronise the containing directory so the namespace change itself is requested durable.

Python can express the final directory synchronisation on platforms that permit opening and synchronising directories:

~~~python
import os
from pathlib import Path


def synchronise_directory(path: Path) -> None:
    flags = os.O_RDONLY
    directory_flag = getattr(os, "O_DIRECTORY", 0)
    descriptor = os.open(path, flags | directory_flag)
    try:
        os.fsync(descriptor)
    finally:
        os.close(descriptor)
~~~

This is not a portable universal recipe. Some platforms do not expose <code>O_DIRECTORY</code>, do not permit <code>fsync</code> on a directory, or give different guarantees. The sequence also leaves questions about preservation of permissions and ownership, old-file removal durability, errors after rename, and storage devices. A library should document the platforms on which it makes a strong durability claim and fail or weaken the claim explicitly elsewhere.

### 11.6.5 Atomic write size and torn updates

A **torn write** is an update for which only part of the intended lower-level units becomes persistent or visible after failure. Application call boundaries need not coincide with device atomic units:

~~~python
stream.write(b"A" * 8192)
~~~

One call does not prove one indivisible physical update. The runtime may split it, the kernel may divide it into pages, and storage may commit sectors or blocks independently. Even sector-level atomicity varies with hardware and configuration.

Checksums can detect many partial or corrupted records. They do not restore the missing old or new version and do not authenticate untrusted mutation unless used in an appropriate keyed construction. Redundant copies, sequence numbers, and commit markers can let recovery select a complete version.

One simple two-slot conceptual scheme stores:

~~~text
slot A: generation, payload, checksum
slot B: generation, payload, checksum
selector: chosen generation
~~~

A writer constructs and synchronises the inactive slot, then changes the selector. Recovery validates checksums and generations. The scheme still depends on selector atomicity, write ordering, media guarantees, and how conflicting valid slots are resolved. Storage formats are protocols with recovery algorithms, not mere byte layouts.

### 11.6.6 Write-ahead logging

A **write-ahead log** (WAL) records intended state changes in an append-oriented log before exposing corresponding updates to primary state. “Write ahead” means the log information required for recovery reaches the defined durable state before the data pages whose recovery it governs.

At a high level:

1. assign a transaction identity;
2. append redo and/or undo information;
3. synchronise the log through the commit record;
4. report commit;
5. apply changes to primary storage, perhaps before or after commit under the design;
6. checkpoint and reclaim log space only when recovery no longer needs it.

A **redo record** contains information needed to reproduce an accepted change. An **undo record** contains information needed to reverse an uncommitted change. Systems can use one or both, and details such as physiological logging, page identifiers, log sequence numbers, group commit, and checkpointing belong to database and filesystem literature.

Writing a line to a log file before a data file is not by itself a WAL. The design must establish ordering, completeness, record framing, checksums, transaction boundaries, synchronisation, idempotent recovery, and log retention.

### 11.6.7 Atomicity across several files

Suppose <code>index.json</code> names objects in <code>objects/</code>. Replacing the two independently allows observers to see:

- old index and old objects;
- old index and new objects;
- new index and old objects;
- new index and new objects.

Only the first and last may be valid. There are several design responses:

- store the related state in a database transaction;
- write immutable, content-addressed objects first, then atomically replace one root manifest that refers to them;
- create a complete versioned directory and atomically switch one supported indirection;
- make readers tolerate and recover from intermediate combinations;
- coordinate readers and writers through locking with defined crash recovery.

The immutable-object/manifest pattern narrows the commit point:

~~~text
objects/sha256-...   complete immutable object
objects/sha256-...   complete immutable object
current.json         one replaceable manifest
~~~

Old objects can be garbage-collected only after no retained manifest can refer to them. Hash-based names provide content addressing if the digest is computed and verified correctly; collision, authenticity, and deletion policies remain separate.

### 11.6.8 Error handling after the commit point

The most difficult failures occur when an operation may have committed but acknowledgement fails. Consider:

~~~python
os.replace(temporary, destination)
synchronise_directory(destination.parent)
~~~

If the second call raises, the destination may already name the new file. The function cannot truthfully report “no change”. Its outcome is **indeterminate with respect to the requested durability level**: namespace replacement may be visible, while persistence across the named failure remains unconfirmed.

Interfaces should avoid a Boolean success/failure model when ambiguity matters. Possible result states include:

~~~python
from enum import Enum, auto


class CommitStatus(Enum):
    NOT_COMMITTED = auto()
    COMMITTED = auto()
    COMMIT_VISIBLE_DURABILITY_UNCONFIRMED = auto()
~~~

An exception can carry the stage reached and an operation ID so recovery can inspect authoritative state. The caller must not blindly retry a non-idempotent operation after an indeterminate result.

Cleanup after commit must also distinguish the now-owned destination from an obsolete temporary file. A <code>finally</code> block that always deletes “the output path” can destroy successfully committed state. State transitions should be represented explicitly, as the <code>temporary_name = None</code> assignment in §11.1.4 did.

### 11.6.9 Backups and replication answer different questions

A backup is a retained independent recovery copy governed by a retention and restoration process. Replication creates additional live copies to improve availability or read capacity. Immediate replication can faithfully copy accidental deletion or corruption; it is not necessarily a historical backup. A backup that has never been restored in a test is an unverified recovery hypothesis.

Durability requirements should state:

- which failures are in scope: process crash, host loss, device loss, site loss, operator error, malicious deletion;
- the maximum acceptable data loss, often expressed as a recovery point objective;
- the maximum acceptable restoration time, often expressed as a recovery time objective;
- retention, encryption, key recovery, access control, and deletion requirements;
- how restoration is regularly tested.

Python file calls occupy only a small part of this system. A program can synchronise one local file perfectly while failing the larger requirement because its encryption keys are unavailable or its backup contains an inconsistent multi-file snapshot.

### 11.6.10 Measure buffering without turning measurements into laws

A valid buffering experiment controls input size, storage medium, warm/cold cache state, Python version, operating system, buffer size, repetitions, and measurement clock. It reports distribution rather than one best run:

~~~python
from pathlib import Path
from time import perf_counter_ns


def timed_copy(source: Path, destination: Path, block_size: int) -> int:
    started = perf_counter_ns()
    with source.open("rb") as reader, destination.open("wb") as writer:
        while block := reader.read(block_size):
            writer.write(block)
    return perf_counter_ns() - started
~~~

The function is a measurement kernel, not a complete benchmark. It omits cache clearing, trial randomisation, correctness verification, synchronisation, environmental recording, and statistical analysis. The destination write may finish in kernel cache rather than on durable media. Chapter 12 formalises experimental discipline, and Chapter 14 treats profiling and performance.

The semantic conclusion is modest: buffer size can affect throughput. The optimal value cannot be inferred from this source code alone.

> **Common misconception 11.21 — “The fastest benchmark buffer is the correct production setting.”** A measured optimum is conditional on workload, hardware, cache state, concurrency, and the required latency/durability semantics.
