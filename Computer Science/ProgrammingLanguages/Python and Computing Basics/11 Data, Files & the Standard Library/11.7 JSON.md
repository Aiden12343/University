# 11.7 JSON

**JSON**, JavaScript Object Notation, is a text data-interchange format defining objects, arrays, strings, numbers, Booleans, and null. Python’s `json` module maps these to selected Python structures.

```python
import json

record = {
    "name": "Ada",
    "scores": [98, 95],
    "active": True,
    "note": None,
}

encoded = json.dumps(record, ensure_ascii=False, sort_keys=True)
decoded = json.loads(encoded)
```

`dumps` returns a string; `dump` writes to a text file-like object. `loads` parses a string/bytes-like input; `load` reads from a file-like object. The names contain `s` historically for string.

JSON is not a lossless representation of arbitrary Python objects. Tuples become arrays and ordinarily decode as lists; dictionary keys in JSON objects are strings; sets, bytes, decimals, dates, and custom instances require an explicit schema and conversion.

Numbers require care. JSON syntax does not itself require IEEE binary64, but receivers may use limited numeric representations. Large Python integers can lose precision in another system. Non-finite values such as NaN are outside strict JSON; configure strict emission when interoperability matters:

```python
json.dumps(value, allow_nan=False)
```

### Worked example 11.5 — Parsing is not validation

```python
payload = json.loads('{"name": 42, "active": "yes"}')
```

This is valid JSON and parsing succeeds. It may violate an application schema requiring text `name` and Boolean `active`. Syntax validation answers whether the representation belongs to JSON; domain validation answers whether its values satisfy the application contract.

Never assume object-key order has domain meaning merely because Python dictionaries preserve decoded insertion order. JSON object semantics are interoperable name/value members; use an array where sequence is required.

### 11.7.1 JSON values and Python values are different algebras

An **algebra of values** here means a set of value forms and the operations or structural relationships among them. JSON has six forms: object, array, string, number, Boolean, and null. Python has many more types and makes distinctions JSON does not.

Python's standard mapping is:

| Python input to encoder | JSON form | Ordinary decoder result |
|---|---|---|
| <code>dict</code> with supported keys | object | <code>dict</code> |
| <code>list</code> or <code>tuple</code> | array | <code>list</code> |
| <code>str</code> | string | <code>str</code> |
| <code>int</code> | number | <code>int</code> |
| finite <code>float</code> | number | <code>float</code> |
| <code>True</code>, <code>False</code> | Boolean | <code>bool</code> |
| <code>None</code> | null | <code>None</code> |

This mapping is not a type-preserving bijection. A tuple and a list can encode identically. A dictionary key can be coerced to a string. Several numeric spellings can decode to equal Python values. Whitespace and escape choices disappear during parsing.

~~~python
import json


original = {1: "one", None: "nothing"}
round_trip = json.loads(json.dumps(original))

assert round_trip == {"1": "one", "null": "nothing"}
assert round_trip != original
~~~

The encoder accepts selected non-string primitive keys by converting them because its default <code>skipkeys=False</code> policy permits string, integer, floating-point, Boolean, and null-like keys. The result is a JSON object whose names are strings. Set <code>skipkeys=True</code> only when silent omission is part of an explicit schema; otherwise it can convert a programming defect into data loss.

JSON arrays may contain heterogeneous values. A schema can impose homogeneity, fixed positions, or other constraints, but the base format does not.

> **Common misconception 11.22 — “JSON round-tripping preserves Python types.”** It preserves only distinctions represented by the chosen JSON schema and conversion rules.

### 11.7.2 A JSON text can be any JSON value

The current JSON grammar permits a complete JSON text to be any value, including:

~~~json
42
~~~

or:

~~~json
"ready"
~~~

Earlier specifications and some application interfaces restricted top-level values to objects or arrays. An application can still impose that requirement:

~~~python
def require_object(text: str) -> dict[str, object]:
    value = json.loads(text)
    if not isinstance(value, dict):
        raise ValueError("top-level JSON value must be an object")
    return value
~~~

This is a schema restriction layered over JSON syntax, not a fact about JSON itself. Distinguishing those layers helps interoperability diagnosis: a payload can conform to RFC 8259 yet be rejected by a particular API.

JSON has no comments, trailing commas, single-quoted strings, or unquoted object names in its standard grammar. Configuration formats that accept those features implement an extension or another language. Calling every JavaScript-like object literal “JSON” weakens error reports and can create incompatible producers.

### 11.7.3 Object names, duplicates, and order

RFC 8259 states that object member names should be unique for interoperable behaviour. The grammar can represent duplicate names, but receivers differ: some reject them, some preserve every pair, and many retain only the last value.

Python's ordinary decoder retains the last value:

~~~python
decoded = json.loads('{"role": "reader", "role": "administrator"}')
assert decoded == {"role": "administrator"}
~~~

This behaviour can be dangerous when one validator inspects the first occurrence and a later component acts on the last. Reject duplicates at one trusted parsing boundary:

~~~python
from typing import Any


def unique_object(
    pairs: list[tuple[str, Any]],
) -> dict[str, Any]:
    result: dict[str, Any] = {}
    for name, value in pairs:
        if name in result:
            raise ValueError(f"duplicate JSON object name: {name!r}")
        result[name] = value
    return result


document = json.loads(
    '{"role": "reader", "active": true}',
    object_pairs_hook=unique_object,
)
~~~

<code>object_pairs_hook</code> receives member pairs in source order for each object and takes precedence over <code>object_hook</code>. The type <code>Any</code> reflects that nested JSON values can have several runtime forms; domain validation should narrow it after parsing.

Python's decoder preserves observed object member order in its dictionaries, and the encoder preserves mapping iteration order by default. This is useful for readable fixtures. JSON object meaning should not depend on order unless a surrounding application deliberately imposes a non-standard convention. Arrays are the standard ordered structure.

### 11.7.4 Numeric syntax and semantic precision

JSON numbers use decimal syntax with optional fraction and exponent; hexadecimal, leading plus signs, and non-finite values are absent from the standard grammar. Syntax does not prescribe one in-memory numeric type. A receiver can limit range and precision.

Python's default decoder maps integer syntax to arbitrary-precision <code>int</code> within runtime safeguards and fractional/exponent syntax to binary floating-point <code>float</code>:

~~~python
value = json.loads('{"integer": 9007199254740993, "fraction": 0.1}')

assert value["integer"] == 9_007_199_254_740_993
assert value["fraction"] == 0.1
~~~

The assertions describe Python values, not cross-language exactness. Many systems store numbers as IEEE 754 binary64, for which all integers only through a particular magnitude are consecutively exact. A large identifier should therefore often be a JSON string rather than a number:

~~~json
{
  "account_id": "9007199254740993"
}
~~~

Monetary decimals can be decoded directly as <code>Decimal</code>:

~~~python
from decimal import Decimal


document = json.loads(
    '{"amount": 12.30, "rate": 0.075}',
    parse_float=Decimal,
)

assert document["amount"] == Decimal("12.30")
~~~

This preserves decimal significance in the lexical coefficient, but ordinary <code>json.dumps</code> cannot serialise <code>Decimal</code> directly. A schema must choose a representation, commonly a decimal string with rules for sign, scale, exponent, and bounds.

Hooks also permit a bounded integer parser:

~~~python
MAX_INTEGER_DIGITS = 100


def bounded_integer(text: str) -> int:
    digits = text.removeprefix("-")
    if len(digits) > MAX_INTEGER_DIGITS:
        raise ValueError("JSON integer has too many digits")
    return int(text)


value = json.loads("12345", parse_int=bounded_integer)
~~~

Modern Python runtimes also apply versioned integer-string conversion limits in relevant paths. Application limits remain useful because runtime limits may be configured differently and do not express domain range.

### 11.7.5 Non-finite extensions must be made strict

The JSON number grammar excludes NaN and infinities. Python's encoder and decoder nevertheless accept JavaScript-style <code>NaN</code>, <code>Infinity</code>, and <code>-Infinity</code> by default as an extension.

Strict output requires:

~~~python
import math


try:
    json.dumps({"result": math.nan}, allow_nan=False)
except ValueError:
    pass
else:
    raise AssertionError("non-finite number was unexpectedly accepted")
~~~

Strict input can reject the extension through <code>parse_constant</code>:

~~~python
from typing import Never


def reject_non_finite(token: str) -> Never:
    raise ValueError(f"non-standard numeric constant: {token}")


json.loads(
    '{"result": 1.25}',
    parse_constant=reject_non_finite,
)
~~~

Schema validation should additionally call <code>math.isfinite</code> or <code>Decimal.is_finite</code> on values that might arise internally. Strict serialisation catches a defect at output, but earlier validation can attach more domain context.

> **Common misconception 11.23 — “Python's default JSON output is necessarily standards-strict.”** Its default permits non-finite numeric spellings for compatibility. Use <code>allow_nan=False</code> when RFC-conforming interchange is required.

### 11.7.6 Strings, escaping, and transport encoding

JSON string escapes are part of JSON syntax; UTF-8 is the interoperable encoding for JSON exchanged between systems outside a closed ecosystem. These are separate transformations:

~~~python
record = {"label": "café\nlevel 2"}
json_text = json.dumps(record, ensure_ascii=False)
wire_bytes = json_text.encode("utf-8")
~~~

The newline inside the value becomes a JSON escape sequence because a literal control character cannot occur unescaped inside a JSON string. The <code>é</code> remains a non-ASCII character in <code>json_text</code> under <code>ensure_ascii=False</code> and then becomes UTF-8 bytes.

With the default <code>ensure_ascii=True</code>, non-ASCII characters are escaped so the returned Python string contains only ASCII code points:

~~~python
ascii_json = json.dumps({"label": "café"}, ensure_ascii=True)
assert ascii_json == '{"label": "caf\\u00e9"}'
assert json.loads(ascii_json) == {"label": "café"}
~~~

Both texts can represent the same JSON string value. <code>ensure_ascii=False</code> often improves human readability when the surrounding stream is explicitly UTF-8. Neither setting normalises Unicode or prevents visually confusable names.

JSON escaping is contextual. A valid JSON string embedded directly into HTML or JavaScript occupies another grammar and can need additional safe embedding rules. Likewise, putting JSON into a shell argument, SQL statement, or log record does not become safe merely because <code>json.dumps</code> was used. Encode once for each actual boundary using that boundary's mechanism; do not invent chains of manual replacement.

### 11.7.7 Parsing, validating, and constructing

A robust decoder has three stages:

~~~mermaid
flowchart LR
    A["JSON text"] --> B["Generic values"]
    B --> C["Validated domain object"]
    C --> D["Domain operation"]
~~~

Parsing should not instantiate arbitrary classes based on a class name supplied by input. An <code>object_hook</code> can be useful for local transformations, but a registry of explicitly permitted schema tags is safer than dynamic imports.

The following complete decoder rejects duplicates, unknown members, Boolean-as-integer confusion, and invalid timestamps:

~~~python
from dataclasses import dataclass
from datetime import datetime, timezone
from typing import Any


@dataclass(frozen=True, slots=True)
class Observation:
    sensor_id: str
    observed_at: datetime
    value_milliunits: int


def parse_observation_json(source: str) -> Observation:
    generic: Any = json.loads(
        source,
        object_pairs_hook=unique_object,
        parse_constant=reject_non_finite,
    )
    if not isinstance(generic, dict):
        raise ValueError("observation must be an object")

    expected = {"schema_version", "sensor_id", "observed_at", "value_milliunits"}
    if set(generic) != expected:
        raise ValueError(
            f"fields differ: missing={expected - set(generic)}, "
            f"unknown={set(generic) - expected}"
        )
    if generic["schema_version"] != 1:
        raise ValueError("unsupported observation schema version")

    sensor_id = generic["sensor_id"]
    timestamp_text = generic["observed_at"]
    milliunits = generic["value_milliunits"]

    if not isinstance(sensor_id, str) or not sensor_id:
        raise ValueError("sensor_id must be a non-empty string")
    if not isinstance(timestamp_text, str):
        raise ValueError("observed_at must be a string")
    if type(milliunits) is not int:
        raise ValueError("value_milliunits must be an integer")

    try:
        observed_at = datetime.fromisoformat(timestamp_text)
    except ValueError as error:
        raise ValueError("observed_at has invalid date-time syntax") from error
    if observed_at.tzinfo is None or observed_at.utcoffset() is None:
        raise ValueError("observed_at must include a UTC offset")

    return Observation(
        sensor_id=sensor_id,
        observed_at=observed_at.astimezone(timezone.utc),
        value_milliunits=milliunits,
    )
~~~

<code>datetime.fromisoformat</code> accepts a defined family of date-time strings, not every imaginable ISO 8601 profile. The schema should document the exact accepted profile and canonical output. Converting to UTC makes comparison simpler but loses the original offset representation; retain it separately if it has domain meaning.

The reverse conversion should be explicit:

~~~python
def observation_document(value: Observation) -> dict[str, object]:
    if value.observed_at.tzinfo is None or value.observed_at.utcoffset() is None:
        raise ValueError("observed_at must be offset-aware")
    return {
        "schema_version": 1,
        "sensor_id": value.sensor_id,
        "observed_at": value.observed_at.isoformat(),
        "value_milliunits": value.value_milliunits,
    }


def encode_observation(value: Observation) -> str:
    return json.dumps(
        observation_document(value),
        ensure_ascii=False,
        allow_nan=False,
        sort_keys=True,
        separators=(",", ":"),
    )
~~~

This preserves no arbitrary private attributes and makes every wire member reviewable.

### 11.7.8 Schema evolution and migrations

A **schema version** identifies the interpretation of a representation. It is not the same as the software release version. A program release can support several schema versions; a schema version changes only when representation semantics require it.

Backward compatibility asks whether a newer reader can interpret older data. Forward compatibility asks whether an older reader can tolerate data from a newer producer. Unknown-field policy, default values, enum expansion, numeric ranges, and changed units affect both.

Suppose version 1 stores Celsius as a floating number and version 2 stores integer millikelvins:

~~~python
def migrate_temperature(document: dict[str, object]) -> dict[str, object]:
    version = document.get("schema_version")
    if version == 2:
        return document.copy()
    if version != 1:
        raise ValueError(f"unsupported schema version: {version!r}")

    celsius = document.get("temperature_celsius")
    if not isinstance(celsius, (int, float)) or isinstance(celsius, bool):
        raise ValueError("version 1 temperature must be numeric")

    millikelvins = round((float(celsius) + 273.15) * 1_000)
    return {
        "schema_version": 2,
        "sensor_id": document.get("sensor_id"),
        "temperature_millikelvins": millikelvins,
    }
~~~

The migration makes an unavoidable rounding policy visible. It must still validate finite range and required fields; the abbreviated example isolates transformation. In high-integrity software, migration functions are tested against archived fixtures and never silently reinterpret an existing field's units.

An additive optional field can sometimes avoid a version increment when unknown fields are tolerated and absence has a defined meaning. A required field or changed interpretation ordinarily requires coordinated versioning. There is no universal rule independent of consumer contracts.

### 11.7.9 JSON is not framed

Calling <code>json.dump</code> twice on one stream concatenates two JSON texts:

~~~python
from io import StringIO


stream = StringIO()
json.dump({"id": 1}, stream)
json.dump({"id": 2}, stream)

assert stream.getvalue() == '{"id": 1}{"id": 2}'
~~~

That concatenation is not one valid JSON document because no enclosing array or framing separator connects the values. There are several solutions:

- encode one JSON array, possibly with an incremental writer;
- use a length-prefixed protocol;
- use a documented record format such as JSON Text Sequences;
- use newline-delimited JSON under a convention that each complete JSON text occupies one physical line.

For newline-delimited JSON, compact encoding ensures strings contain escaped rather than literal line breaks:

~~~python
def write_json_lines(
    stream: object,
    records: object,
) -> None:
    for record in records:  # type: ignore[union-attr]
        line = json.dumps(
            record,
            ensure_ascii=False,
            allow_nan=False,
            separators=(",", ":"),
        )
        stream.write(line + "\n")  # type: ignore[attr-defined]
~~~

The record iterator and stream should receive precise protocols in production annotations. The convention must state encoding, blank-line policy, maximum line size, error recovery, and whether final newline is required. Reading with ordinary <code>for line in stream</code> can still allocate an unbounded line.

### 11.7.10 Incremental generation is not incremental parsing

<code>JSONEncoder.iterencode</code> yields pieces of encoded text:

~~~python
encoder = json.JSONEncoder(
    ensure_ascii=False,
    allow_nan=False,
    separators=(",", ":"),
)

for piece in encoder.iterencode({"values": list(range(5))}):
    destination.write(piece)
~~~

The encoder can avoid constructing the final JSON string as one object, but the input structure shown is already materialised. A list of ten million items still consumes memory before encoding. Truly streaming a large sequence may require writing the array delimiters and elements incrementally under careful error handling, or choosing a record-oriented format.

Python's standard <code>json.load</code> parses one complete document and constructs its Python value graph. Reading from a file-like object does not imply bounded-memory incremental domain processing. For huge inputs, choose a streaming parser with a documented security and correctness model, or adopt framed records whose individual size is bounded.

If output fails after an opening bracket and several elements, the destination contains invalid partial JSON. Stage before commit when consumers must see only complete documents.

### 11.7.11 Canonicalisation is stronger than sorting keys

<code>sort_keys=True</code> provides deterministic member ordering for mappings under the encoder's other settings. It does not define a universal canonical JSON representation. Canonicalisation can also require rules for:

- numeric spelling and negative zero;
- string escape choice;
- Unicode handling;
- prohibited duplicate names;
- whitespace;
- property ordering measured under a particular representation;
- admissible values and interoperable numeric domain.

RFC 8785 defines one JSON Canonicalization Scheme for cryptographic applications. A protocol requiring it should use a conforming implementation and validate its input domain. Do not assume:

~~~python
json.dumps(value, sort_keys=True)
~~~

is interchangeable with JCS or another canonical scheme.

A cryptographic signature over raw JSON bytes authenticates exactly those bytes under its key and algorithm; semantically equivalent reformatting changes the signature. Signing canonical bytes can allow independent producers to agree, but only if they implement precisely the same canonicalisation and schema. Authentication does not validate the truth or authority of fields.

> **Common misconception 11.24 — “Sorted keys make JSON canonical.”** Key ordering is only one of several canonicalisation rules and does not standardise numbers, escapes, whitespace, or admissible values.

### 11.7.12 Resource limits and hostile documents

JSON parsing can consume substantial CPU and memory without executing arbitrary reconstruction code. Inputs can contain:

- huge strings;
- enormous integer literals;
- deeply nested arrays or objects;
- millions of small members with high object overhead;
- duplicate names designed to exploit component disagreement;
- long escape sequences;
- data that expands when converted into richer domain objects.

Apply an encoded-byte limit before parsing when the whole document is expected to be small:

~~~python
def parse_bounded_json(raw: bytes, maximum_bytes: int) -> object:
    if len(raw) > maximum_bytes:
        raise InputTooLarge(
            f"JSON input has {len(raw)} bytes; maximum is {maximum_bytes}"
        )
    try:
        text = raw.decode("utf-8", errors="strict")
    except UnicodeDecodeError as error:
        raise ValueError("JSON transport is not valid UTF-8") from error
    return json.loads(
        text,
        object_pairs_hook=unique_object,
        parse_constant=reject_non_finite,
        parse_int=bounded_integer,
    )
~~~

Then traverse the generic result with explicit limits on depth, member count, string length, and aggregate elements before expensive domain conversion. Because the complete standard decoder graph already exists at that point, post-parse limits do not prevent all allocation attacks. Strong hostile-input requirements can justify a parser that enforces limits during tokenisation.

Timeouts are difficult to impose safely on CPU-bound parsing in the same thread; Chapter 14 discusses process isolation and cancellation. A maximum byte size is simple, deterministic, and should precede more complex defences.

### 11.7.13 Deterministic documents and reproducible evidence

Reproducible JSON fixtures need a declared representation profile:

~~~python
def fixture_json(value: object) -> str:
    return (
        json.dumps(
            value,
            ensure_ascii=False,
            allow_nan=False,
            sort_keys=True,
            indent=2,
        )
        + "\n"
    )
~~~

The final newline is a project convention useful to text tools. Indentation increases size but aids review. Stable keys reduce irrelevant diffs. This profile remains specific to Python's encoder version and settings; it is deterministic for supported values under the project's environment, not a cross-implementation canonicalisation claim.

Snapshot tests over encoded text can detect representation changes, but semantic tests should also decode and compare validated domain meaning. Otherwise a harmless whitespace change appears as a failure while an incorrect decoder shared by producer and test may go unnoticed.

### Worked example 11.7-A — Versioned repository boundary

~~~python
from pathlib import Path


class ObservationRepository:
    def __init__(self, path: Path, maximum_bytes: int = 1_000_000) -> None:
        self.path = path
        self.maximum_bytes = maximum_bytes

    def load(self) -> list[Observation]:
        try:
            raw = self.path.read_bytes()
        except OSError as error:
            raise RuntimeError(
                f"cannot read observation repository {self.path}"
            ) from error
        generic = parse_bounded_json(raw, self.maximum_bytes)
        if not isinstance(generic, dict):
            raise ValueError("repository root must be an object")
        if generic.get("schema_version") != 1:
            raise ValueError("unsupported repository schema version")
        records = generic.get("observations")
        if not isinstance(records, list):
            raise ValueError("observations must be an array")
        if len(records) > 10_000:
            raise ValueError("too many observations")

        result: list[Observation] = []
        for index, record in enumerate(records):
            try:
                text = json.dumps(record, allow_nan=False)
                result.append(parse_observation_json(text))
            except (TypeError, ValueError) as error:
                raise ValueError(
                    f"invalid observation at array index {index}"
                ) from error
        return result
~~~

Re-encoding each generic record to reuse a text parser is clear but inefficient and can alter representational detail. A mature design factors validation into <code>observation_from_value</code> and calls it directly. The example makes a larger methodological point: resource acquisition, transport bounds, generic parsing, container schema, per-record schema, and domain construction remain distinct even when one repository method orchestrates them.
