# 11.8 CSV

**CSV**, comma-separated values, names a family of tabular text formats rather than one sufficient “split on commas” rule. Quoting, embedded delimiters, embedded line breaks, escaping, newline handling, encoding, and dialect must be specified.

```python
import csv
from pathlib import Path


path = Path("records.csv")
with path.open("r", encoding="utf-8", newline="") as stream:
    reader = csv.DictReader(stream)
    for row_number, row in enumerate(reader, start=2):
        print(row_number, row)
```

The `csv` module documentation recommends opening files with `newline=""` so the parser owns CSV newline handling. `DictReader` uses header fields as keys and produces strings or `None` under conditions; it does not infer domain types.

A field can contain a comma or newline when correctly quoted. Therefore:

```python
line.split(",")
```

is not a CSV parser. It cannot represent the grammar state required to distinguish delimiter commas from data commas.

### Worked example 11.6 — Convert with source position

```python
def parse_score(row: dict[str, str | None], row_number: int) -> int:
    raw = row.get("score")
    if raw is None:
        raise ValueError(f"row {row_number}: score column is missing")
    try:
        score = int(raw)
    except ValueError as error:
        raise ValueError(f"row {row_number}: invalid score {raw!r}") from error
    if not 0 <= score <= 100:
        raise ValueError(f"row {row_number}: score outside 0..100")
    return score
```

The CSV parser owns quoting and field framing. The domain parser owns presence, integer conversion, and range. The row number crosses the boundary as provenance for diagnosis.

Spreadsheet applications can interpret fields beginning with `=`, `+`, `-`, or `@` as formulae when exported CSV is opened. A CSV producer targeting spreadsheets must address formula injection under that consumer contract; syntactically valid CSV is not automatically safe display data.

### 11.8.1 A dialect is part of the schema

A **CSV dialect** is a collection of lexical parameters specifying such choices as delimiter, quote character, escaping, treatment of spaces after delimiters, and line terminator. The table's column meanings form a schema above that dialect.

~~~python
import csv


class MeasurementDialect(csv.Dialect):
    delimiter = ","
    quotechar = '"'
    doublequote = True
    escapechar = None
    lineterminator = "\r\n"
    quoting = csv.QUOTE_MINIMAL
    skipinitialspace = False
    strict = True
~~~

This class defines a project-local dialect without mutating the process-global named dialect registry. <code>QUOTE_MINIMAL</code> asks the writer to quote fields containing special characters. <code>doublequote=True</code> represents an internal quote by doubling it. <code>strict=True</code> asks the reader to raise on malformed CSV it detects; it does not validate column types or enforce every project rule.

RFC 4180 documents a widely used comma-and-CRLF format and registers <code>text/csv</code>, but it is informational and explicitly acknowledges variation. A file extension or MIME type therefore cannot determine all parser parameters. The producer/consumer agreement should state at least:

- character encoding and BOM policy;
- delimiter, quote, escape, and double-quote rules;
- record line-ending policy;
- whether a header is present;
- exact column names and duplicate-name policy;
- column order and whether extra/missing fields are permitted;
- representation of null, empty string, Boolean, dates, decimals, and units;
- maximum field, row, and record counts.

The delimiter is not necessarily a comma. Semicolon-separated and tab-separated files are common where decimal or regional conventions make commas ambiguous. Calling them all CSV is customary; the dialect still must be named.

### 11.8.2 Records are not physical lines

A quoted CSV field can contain a line break:

~~~text
id,comment,score
1,"first line
second line",98
~~~

This text has a header record and one data record, but three physical lines. A parser must remain inside the quoted field across the second line ending. Consequently:

- reading one physical line and splitting it is incorrect;
- line numbers and record numbers are not interchangeable;
- a maximum physical-line length does not necessarily bound a logical record;
- error recovery after malformed quoting requires a defined resynchronisation policy.

The reader's <code>line_num</code> reports the number of source lines consumed, not the number of records returned:

~~~python
from io import StringIO


source = StringIO('id,note\n1,"left\nright"\n')
reader = csv.reader(source, dialect=MeasurementDialect)

header = next(reader)
row = next(reader)

assert header == ["id", "note"]
assert row == ["1", "left\nright"]
assert reader.line_num == 3
~~~

For user diagnostics, record index and ending physical line can both be useful. The exact starting physical line requires tracking the previous <code>line_num</code> before requesting the next record.

### 11.8.3 Why <code>newline=""</code> matters

The CSV parser needs to observe line endings because they can terminate records or appear within quoted fields. Opening a CSV file with <code>newline=""</code> enables the text layer's universal recognition while returning endings untranslated, leaving CSV-specific interpretation to <code>csv</code>.

~~~python
from pathlib import Path


path = Path("measurements.csv")
with path.open(
    "r",
    encoding="utf-8",
    errors="strict",
    newline="",
) as stream:
    reader = csv.reader(stream, dialect=MeasurementDialect)
    for row in reader:
        consume(row)
~~~

On writing, the same recommendation prevents the text layer from independently translating the line terminators emitted by the CSV writer, which can otherwise produce doubled carriage returns on some platforms.

The encoding remains a separate contract. A spreadsheet may emit a UTF-8 signature; if the agreed input allows it, <code>encoding="utf-8-sig"</code> consumes that initial signature. Choosing it indiscriminately changes how a leading U+FEFF is interpreted.

### 11.8.4 Headers require validation

<code>DictReader</code> uses the first record as field names when none are supplied. Duplicate header names cannot coexist as distinct dictionary keys, so one value can overwrite another:

~~~python
source = StringIO("id,value,value\nA,10,20\n")
reader = csv.DictReader(source)
row = next(reader)

assert row["value"] == "20"
~~~

Validate the raw header before dictionary mapping:

~~~python
EXPECTED_HEADER = ["sensor_id", "observed_at", "value"]


def validated_rows(stream: object) -> object:
    reader = csv.reader(stream, dialect=MeasurementDialect)
    try:
        header = next(reader)
    except StopIteration as error:
        raise ValueError("CSV input is empty") from error

    if header != EXPECTED_HEADER:
        raise ValueError(
            f"unexpected CSV header: expected {EXPECTED_HEADER!r}, "
            f"received {header!r}"
        )

    for record_number, row in enumerate(reader, start=2):
        if len(row) != len(EXPECTED_HEADER):
            raise ValueError(
                f"record {record_number}: expected "
                f"{len(EXPECTED_HEADER)} fields, received {len(row)}"
            )
        yield dict(zip(EXPECTED_HEADER, row, strict=True))
~~~

Exact ordering is one schema choice. Another interface might permit arbitrary column order but require unique names and a fixed name set:

~~~python
if len(header) != len(set(header)):
    raise ValueError("duplicate header names")
if set(header) != set(EXPECTED_HEADER):
    raise ValueError("missing or unknown columns")
~~~

The two policies should not be mixed accidentally. Exact order makes diffs and positional consumers predictable; order-independent input is friendlier to producers.

<code>DictReader</code> can place surplus values under <code>restkey</code> and fill missing fields with <code>restval</code>. Its defaults can make malformed row widths look like ordinary <code>None</code> values. Strict importers should inspect these conditions or use the positional reader as above.

> **Common misconception 11.25 — “<code>DictReader</code> guarantees one unique value per header name.”** Duplicate names collide in a dictionary; validate header uniqueness first.

### 11.8.5 CSV has no intrinsic scalar types

Ordinary CSV readers return strings. The text <code>0012</code> might be an integer, a product code whose leading zero matters, or arbitrary text. The empty field might mean an empty string, missing value, unavailable measurement, or zero under a defective convention.

Each column needs an explicit parser:

~~~python
from dataclasses import dataclass
from datetime import datetime
from decimal import Decimal, InvalidOperation


@dataclass(frozen=True, slots=True)
class Measurement:
    sensor_id: str
    observed_at: datetime
    value: Decimal | None


def parse_optional_decimal(
    raw: str,
    *,
    record_number: int,
) -> Decimal | None:
    if raw == "":
        return None
    try:
        value = Decimal(raw)
    except InvalidOperation as error:
        raise ValueError(
            f"record {record_number}: value is not decimal: {raw!r}"
        ) from error
    if not value.is_finite():
        raise ValueError(
            f"record {record_number}: value must be finite"
        )
    return value
~~~

This schema distinguishes empty field from decimal zero. It does not strip whitespace, because RFC-style CSV regards spaces as field content and silently stripping could change identifiers. If surrounding whitespace is permitted, state so per column.

The quoting option <code>QUOTE_NONNUMERIC</code> converts unquoted fields to floats. That inference is unsuitable for identifiers, exact decimals, large integers, and schemas where quoting is a presentation choice rather than a type marker. Python 3.12 introduced additional quote policies that can help represent nulls or string distinctions under coordinated producers and consumers; compatibility with older runtimes and non-Python tools must be verified.

### 11.8.6 Writing can be lossy

The standard writer converts <code>None</code> to an empty string and other non-string values through <code>str</code>. The <code>None</code> conversion is deliberately not reversible:

~~~python
destination = StringIO(newline="")
writer = csv.writer(destination)
writer.writerow([None, "", 12, Decimal("1.20")])

print(destination.getvalue())
~~~

Both <code>None</code> and <code>""</code> become empty fields under the ordinary policy. The decimal's textual scale depends on <code>str(Decimal("1.20"))</code>, while arbitrary objects can have presentation strings unsuitable for interchange.

Convert domain values explicitly before writing:

~~~python
NULL_TOKEN = "NULL"


def encode_optional_text(value: str | None) -> str:
    if value is None:
        return NULL_TOKEN
    if value == NULL_TOKEN:
        raise ValueError("literal NULL token is reserved by the CSV schema")
    return value
~~~

This toy sentinel makes null reversible only because the literal token is forbidden. A richer escape convention or companion validity column may be preferable. The schema must distinguish token syntax from values.

<code>DictWriter</code> raises on extra mapping keys by default. Keeping <code>extrasaction="raise"</code> catches schema drift. <code>"ignore"</code> silently discards fields and should be chosen only for a documented projection.

### 11.8.7 Quoting and escaping are grammar operations

Under the usual double-quote dialect, a field containing a comma, quote, or newline is enclosed in quotes; an internal quote is doubled:

~~~python
destination = StringIO(newline="")
writer = csv.writer(
    destination,
    delimiter=",",
    quotechar='"',
    doublequote=True,
    lineterminator="\r\n",
    quoting=csv.QUOTE_MINIMAL,
)
writer.writerow(["Ada, A.", 'said "hello"', "line 1\nline 2"])

assert destination.getvalue() == (
    '"Ada, A.","said ""hello""","line 1\nline 2"\r\n'
)
~~~

Manual wrapping in quote characters is wrong because it does not escape internal quotes and can double-quote already encoded data. Keep values unencoded until one CSV writer owns the grammar.

Quoting all fields can reduce visual ambiguity, but it does not create types or make spreadsheet interpretation safe. Not quoting a field does not prove it is numeric. Dialect parsing and domain conversion remain separate.

### 11.8.8 Sniffing is heuristic evidence

<code>csv.Sniffer</code> examines a sample to guess a dialect and heuristically estimate whether the first row is a header. A guess can be wrong, especially for short, irregular, adversarial, or semantically unusual samples.

~~~python
with path.open("r", encoding="utf-8", newline="") as stream:
    sample = stream.read(4096)
    stream.seek(0)
    dialect = csv.Sniffer().sniff(sample, delimiters=",;\t")
    reader = csv.reader(stream, dialect)
~~~

Bounding candidate delimiters narrows uncertainty. The sample can end inside a quoted field and may not represent later rows. Sniffing is appropriate for an interactive import assistant that displays the inferred dialect for confirmation. It is weak for an unattended security or financial pipeline, which should receive explicit metadata or reject ambiguity.

Header inference is especially semantic: a first row of strings followed by numbers may look like names, but it could be ordinary data. Never make authorisation or irreversible transformation depend solely on a header heuristic.

> **Common misconception 11.26 — “<code>Sniffer</code> discovers the true CSV format.”** It infers from a finite sample using heuristics. Its result is a hypothesis to confirm or constrain.

### 11.8.9 Parser limits and malformed input

<code>csv.field_size_limit</code> reports or changes the process-wide parser field limit:

~~~python
previous_limit = csv.field_size_limit()
try:
    csv.field_size_limit(1_000_000)
    read_import()
finally:
    csv.field_size_limit(previous_limit)
~~~

Because this is module-global mutable state, changing it can affect unrelated parsing and concurrent code. Configure it at a controlled application boundary or enforce record limits through a dedicated process or parser when isolation matters.

A field limit does not bound:

- number of fields per record;
- record count;
- total decoded bytes;
- number of distinct grouping keys retained;
- time spent in domain validation;
- output size.

Catch <code>csv.Error</code> near the parser and add provenance:

~~~python
try:
    row = next(reader)
except csv.Error as error:
    raise ValueError(
        f"malformed CSV near physical line {reader.line_num}"
    ) from error
~~~

After a syntax error, continuing with the same reader may not be safe because its grammar state and record boundary are uncertain. A fail-fast importer can reject the file. A fault-tolerant ingestion service needs a format with reliable framing or a formally defined resynchronisation algorithm.

### 11.8.10 Spreadsheet formula injection is downstream interpretation

CSV itself contains text fields, not formula objects. Spreadsheet programs may interpret certain leading characters, tabs, or other patterns as formulae when opening a CSV. If attacker-controlled fields reach that consumer, formula evaluation can trigger data disclosure, external requests, deceptive links, or other consumer-specific effects.

Quoting a field according to CSV grammar does not necessarily prevent formula interpretation because the spreadsheet first parses CSV and then interprets the resulting cell value. Mitigations must be selected for the named spreadsheet and workflow:

- import all affected columns explicitly as text;
- use a format with typed cells and safe producer APIs;
- reject dangerous leading constructs where the domain permits;
- transform for display using a documented escaping convention and retain original data separately;
- warn users and restrict formula/external-link behaviour at the consumer.

Prefixing an apostrophe is commonly suggested but can become visible data, can be handled differently by import paths, and is not a universal CSV rule. Prefixing a space changes the value. A system must not silently corrupt canonical source data to solve a presentation risk without recording the transformation.

### 11.8.11 Streaming aggregation with bounded state

CSV naturally supports record-wise processing, but aggregation memory depends on the aggregate:

~~~python
from dataclasses import dataclass
from decimal import Decimal


@dataclass
class RunningSummary:
    count: int = 0
    total: Decimal = Decimal(0)
    minimum: Decimal | None = None
    maximum: Decimal | None = None

    def add(self, value: Decimal) -> None:
        self.count += 1
        self.total += value
        self.minimum = value if self.minimum is None else min(self.minimum, value)
        self.maximum = value if self.maximum is None else max(self.maximum, value)
~~~

One global summary uses constant-sized aggregate state with respect to record count, ignoring growth in arbitrary-precision numeric representation. A dictionary of summaries keyed by sensor consumes space proportional to the number of distinct sensors:

~~~python
summaries: dict[str, RunningSummary] = {}

for measurement in measurements:
    summary = summaries.setdefault(
        measurement.sensor_id,
        RunningSummary(),
    )
    if measurement.value is not None:
        summary.add(measurement.value)
~~~

An attacker can therefore exhaust memory through unbounded distinct keys even though records are streamed. Enforce a key-cardinality limit, spill to a transactional store, or sort externally and aggregate one group at a time.

### Worked example 11.8-A — Strict typed CSV reader

~~~python
from collections.abc import Iterator
from datetime import datetime
from decimal import Decimal
from pathlib import Path


MAX_RECORDS = 100_000


def read_measurements(path: Path) -> Iterator[Measurement]:
    try:
        stream = path.open(
            "r",
            encoding="utf-8",
            errors="strict",
            newline="",
        )
    except OSError as error:
        raise RuntimeError(f"cannot open CSV input {path}") from error

    with stream:
        reader = csv.reader(stream, dialect=MeasurementDialect)
        try:
            header = next(reader)
        except StopIteration as error:
            raise ValueError(f"{path}: missing header") from error
        except csv.Error as error:
            raise ValueError(f"{path}: malformed header") from error

        if header != EXPECTED_HEADER:
            raise ValueError(f"{path}: unexpected header {header!r}")

        for record_number, row in enumerate(reader, start=2):
            if record_number > MAX_RECORDS + 1:
                raise ValueError(f"{path}: too many data records")
            if len(row) != 3:
                raise ValueError(
                    f"{path}: record {record_number}: "
                    f"expected 3 fields, received {len(row)}"
                )

            sensor_id, timestamp_text, value_text = row
            if not sensor_id:
                raise ValueError(
                    f"{path}: record {record_number}: empty sensor_id"
                )
            try:
                observed_at = datetime.fromisoformat(timestamp_text)
            except ValueError as error:
                raise ValueError(
                    f"{path}: record {record_number}: invalid timestamp"
                ) from error

            value = parse_optional_decimal(
                value_text,
                record_number=record_number,
            )
            yield Measurement(sensor_id, observed_at, value)
~~~

This generator owns the stream for the duration of active iteration. It validates a fixed header, row width, record count, identifiers, timestamps, and decimal values. It still needs a timestamp offset policy, field-size configuration, sensor-ID length/normalisation rule, decimal magnitude/scale bounds, and a documented response if the caller abandons iteration. Those omissions are explicit remaining work rather than hidden assurances.
