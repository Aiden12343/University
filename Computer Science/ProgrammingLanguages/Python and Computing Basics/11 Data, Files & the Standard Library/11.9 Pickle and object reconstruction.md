# 11.9 Pickle and object reconstruction

The `pickle` module serialises and reconstructs many Python object graphs, preserving sharing and supporting custom reduction protocols. **Serialisation** transforms state into a representation suitable for storage or transmission. **Deserialisation** reconstructs state from such a representation.

Pickle is Python-specific and unsafe for untrusted data. Unpickling can import modules and invoke callable reconstruction operations; a malicious pickle can execute arbitrary code with process authority. The rule is absolute for ordinary design:

> Never unpickle data received from an untrusted or unauthenticated source. Treat pickle as executable capability, not passive data.

Authentication of origin does not solve every risk: a trusted source can be compromised, old object paths can disappear, and a valid historical pickle can trigger behaviour inappropriate in a newer environment. Pickle is useful for controlled caches and internal artefacts under a strict trust/lifetime/version policy, not for public interchange.

JSON is safer in the narrow sense that parsing JSON does not intentionally encode arbitrary callable execution, but parsed values still require size limits, schema validation, and safe downstream use. No format eliminates validation obligations.

### 11.9.1 Pickle represents an object graph

A Python value can be a graph rather than a tree because several references can point to one object and cycles can lead back to an earlier object. Pickle uses a **memo**, a mapping from encountered object identities to positions in the serialisation process, so it can preserve selected aliasing and recursion.

~~~python
import pickle


shared: list[int] = [1, 2]
graph = [shared, shared]
restored = pickle.loads(pickle.dumps(graph, protocol=5))

assert restored[0] == restored[1]
assert restored[0] is restored[1]
~~~

JSON conversion through two arrays would ordinarily preserve equality of contents but not shared identity. Whether aliasing matters depends on the domain. Mutating one restored list in this example affects the other reference:

~~~python
restored[0].append(3)
assert restored == [[1, 2, 3], [1, 2, 3]]
~~~

Cycles are also representable:

~~~python
cycle: list[object] = []
cycle.append(cycle)
restored_cycle = pickle.loads(pickle.dumps(cycle, protocol=5))

assert restored_cycle[0] is restored_cycle
~~~

The ability is powerful but increases reasoning complexity. A serializer that preserves graph topology can recreate aliases a validation routine does not expect. Resource limits must consider nesting, memo entries, and reconstructed object behaviour.

### 11.9.2 Protocol version is a compatibility decision

Pickle has numbered protocols. Newer protocols add opcodes and efficiency features and require sufficiently new readers. <code>pickle.HIGHEST_PROTOCOL</code> is the newest protocol implemented by the current runtime; <code>pickle.DEFAULT_PROTOCOL</code> is the runtime's default and has changed across Python releases.

~~~python
import pickle


payload = pickle.dumps(
    {"schema_version": 1, "values": [1, 2, 3]},
    protocol=5,
)
~~~

Naming protocol 5 makes the minimum pickle-protocol requirement explicit for Python 3.12+ environments. Using <code>HIGHEST_PROTOCOL</code> can be suitable for an ephemeral cache produced and consumed by the same deployment, but it silently raises compatibility requirements when the producer upgrades. Long-lived artefacts need a tested reader matrix and an application-state version in addition to the pickle protocol.

The protocol identifies byte-stream instructions, not the version of every imported class. A protocol-4 stream can still fail because a referenced module moved, a class changed invariants, or a third-party library is absent.

> **Common misconception 11.27 — “A supported pickle protocol guarantees application compatibility.”** It guarantees only that the unpickler understands that protocol's instruction vocabulary; referenced code and state schemas must also remain compatible.

### 11.9.3 Classes and functions are generally referenced by name

Top-level functions and classes are ordinarily pickled by qualified module/name reference rather than by embedding their implementation. On unpickling, the module must be importable and expose a compatible object at the expected name.

~~~python
# inventory.py
from dataclasses import dataclass


@dataclass
class Item:
    sku: str
    quantity: int
~~~

A pickle of <code>inventory.Item("A-1", 4)</code> does not freeze the source code of <code>Item</code>. Refactoring it to <code>catalogue.StockItem</code> can break old artefacts unless a compatibility alias or migration path remains. A local nested class or lambda does not ordinarily have a stable importable name.

This name resolution is one reason unpickling can execute code: importing the module executes its top-level statements, and reconstruction can call permitted callables. Even an apparently data-only class can have descriptors, <code>__setattr__</code>, <code>__setstate__</code>, or later methods with effects.

### 11.9.4 Instance reconstruction is not ordinary construction

For ordinary instances, unpickling usually creates an uninitialised instance and restores state without calling <code>__init__</code>. Invariants established only by <code>__init__</code> can therefore be absent while attributes are restored.

Classes can participate through:

- <code>__getnewargs_ex__</code> or <code>__getnewargs__</code>, which supply arguments for <code>__new__</code>;
- <code>__getstate__</code>, which selects serialised instance state;
- <code>__setstate__</code>, which validates, migrates, and applies restored state;
- <code>__reduce__</code> or <code>__reduce_ex__</code>, the lower-level copy/reconstruction protocol;
- registered reduction functions in <code>copyreg</code> or a pickler-specific dispatch table.

A versioned state method can migrate trusted historical artefacts:

~~~python
class Account:
    def __init__(self, identifier: str, balance_pence: int) -> None:
        self.identifier = identifier
        self.balance_pence = balance_pence

    def __getstate__(self) -> dict[str, object]:
        return {
            "state_version": 2,
            "identifier": self.identifier,
            "balance_pence": self.balance_pence,
        }

    def __setstate__(self, state: dict[str, object]) -> None:
        version = state.get("state_version", 1)
        identifier = state.get("identifier")

        if version == 1:
            pounds = state.get("balance_pounds")
            if not isinstance(pounds, int):
                raise ValueError("invalid version 1 account balance")
            balance_pence = pounds * 100
        elif version == 2:
            candidate = state.get("balance_pence")
            if type(candidate) is not int:
                raise ValueError("invalid version 2 account balance")
            balance_pence = candidate
        else:
            raise ValueError(f"unsupported account state version {version!r}")

        if not isinstance(identifier, str) or not identifier:
            raise ValueError("invalid account identifier")
        if balance_pence < 0:
            raise ValueError("negative account balance")

        self.identifier = identifier
        self.balance_pence = balance_pence
~~~

This validates trusted legacy state; it does not make untrusted pickle safe. The dangerous callable/import machinery executes before or during the point at which <code>__setstate__</code> is reached.

Directly implementing <code>__reduce__</code> is error-prone because it can specify a reconstruction callable, arguments, state, and iterators for populating the object. Prefer higher-level state hooks unless the lower-level protocol is necessary and reviewed.

### 11.9.5 Why arbitrary code execution is inherent

A pickle is an instruction stream for a stack-based virtual machine. Its opcodes can identify global callables and direct their invocation to reconstruct objects. This is not an accidental parser bug; it is a core capability of the format.

The following deliberately benign class demonstrates that loading may call code:

~~~python
def rebuild_label(text: str) -> str:
    print("reconstruction function executed")
    return text.upper()


class Label:
    def __reduce__(self) -> tuple[object, tuple[str]]:
        return rebuild_label, ("demonstration",)


encoded = pickle.dumps(Label(), protocol=5)
decoded = pickle.loads(encoded)

assert decoded == "DEMONSTRATION"
~~~

The result is a string, not a <code>Label</code>, because the reduction callable decides reconstruction. A malicious stream can select much more consequential callables available to the process. Do not “inspect a few leading bytes” and then load: dangerous instructions can occur later.

Renaming the file extension, base64-encoding the pickle, compressing it, encrypting it without authenticating it, or placing it inside JSON does not remove executable semantics.

> **Common misconception 11.28 — “Only pickles of custom classes can be dangerous.”** A crafted stream can invoke reconstruction machinery regardless of what benign object the receiver expected.

### 11.9.6 Trust, authenticity, and authorisation

The minimum safe precondition is that pickle bytes originate from a source trusted to cause arbitrary behaviour with the unpickling process's authority and have not been altered. That is stronger than “came from our network”.

A message authentication code can bind bytes to a secret key:

~~~python
import hashlib
import hmac
import pickle


TAG_BYTES = hashlib.sha256().digest_size


def seal_pickle(value: object, key: bytes) -> bytes:
    payload = pickle.dumps(value, protocol=5)
    tag = hmac.digest(key, payload, "sha256")
    return tag + payload


def open_pickle(blob: bytes, key: bytes) -> object:
    if len(blob) < TAG_BYTES:
        raise ValueError("authenticated pickle is truncated")
    received_tag = blob[:TAG_BYTES]
    payload = blob[TAG_BYTES:]
    expected_tag = hmac.digest(key, payload, "sha256")
    if not hmac.compare_digest(received_tag, expected_tag):
        raise ValueError("pickle authentication failed")
    return pickle.loads(payload)
~~~

This pattern is incomplete as a production protocol. It lacks:

- key identifiers and rotation;
- separation of keys by environment and purpose;
- secure key generation, storage, distribution, and revocation;
- context binding so a valid blob for one purpose cannot be replayed in another;
- creation time, expiry, sequence number, or replay control;
- payload-size limits before verification and loading;
- application schema/version validation;
- a response to compromise of a legitimate producer.

Encryption without integrity can permit malicious modification and should use a maintained authenticated-encryption construction rather than an invented composition. Even correctly authenticated bytes remain executable instructions from whoever holds the key. If producers do not need code-execution authority, choose a data-only format.

### 11.9.7 Restricted unpicklers have a narrow role

An <code>Unpickler</code> subclass can override <code>find_class</code> to permit only selected module/name pairs. This can reduce attack surface:

~~~python
from io import BytesIO
import pickle


class PrimitiveOnlyUnpickler(pickle.Unpickler):
    def find_class(self, module: str, name: str) -> object:
        raise pickle.UnpicklingError(
            f"global reconstruction is forbidden: {module}.{name}"
        )


def load_primitive_pickle(payload: bytes) -> object:
    return PrimitiveOnlyUnpickler(BytesIO(payload)).load()
~~~

This is not a universal sandbox:

- permitted classes can contain exploitable reconstruction behaviour;
- new interpreter/library versions can change available gadget behaviour;
- resource-exhausting graphs remain possible;
- parser or implementation vulnerabilities remain;
- persistent IDs and out-of-band buffers add channels if enabled;
- the resulting primitive graph still needs schema validation.

If untrusted legacy pickles absolutely must be processed, isolate conversion in a minimal, disposable process with no credentials, minimal filesystem/network authority, strict input/output/resource limits, a pinned reviewed environment, and a data-only output schema. Even then, risk is reduced rather than mathematically eliminated.

### 11.9.8 Inspecting opcodes

<code>pickletools</code> can disassemble and optimise pickle instruction streams:

~~~python
import pickletools


payload = pickle.dumps({"x": [1, 2]}, protocol=5)
pickletools.dis(payload)
~~~

Disassembly helps study protocols and audit a known artefact. It is not proof of safety: manually recognising every dangerous composition is difficult, and future global objects can change behaviour. Treat hostile binary analysis itself as a resource-limited activity and avoid loading the stream to “see what it contains”.

Opcode names distinguish protocol mechanism from application meaning. The stream might request a dictionary and list, but only a schema can say whether <code>{"x": [1, 2]}</code> is an acceptable domain value.

### 11.9.9 Partial output and framing

Pickling can fail after writing an unspecified number of bytes to the destination. Therefore direct dumping to the committed file can leave a corrupt artefact:

~~~python
with destination.open("wb") as stream:
    pickle.dump(value, stream, protocol=5)
~~~

Use in-memory encoding for bounded objects or stage to a temporary sibling before replacement. In-memory <code>dumps</code> provides failure atomicity with respect to the destination but can exhaust process memory.

Multiple pickle objects can be written sequentially and read by repeated <code>load</code>, because one load stops after one pickle:

~~~python
from io import BytesIO


stream = BytesIO()
pickle.dump({"id": 1}, stream, protocol=5)
pickle.dump({"id": 2}, stream, protocol=5)
stream.seek(0)

assert pickle.load(stream) == {"id": 1}
assert pickle.load(stream) == {"id": 2}
~~~

Using <code>EOFError</code> as the sole end marker cannot always distinguish clean end from a truncated final record. A durable record store needs explicit framing, checksums, commit markers, and recovery semantics.

### 11.9.10 Persistent IDs and external object references

A custom pickler can replace selected objects with **persistent IDs**. A matching unpickler resolves those IDs through <code>persistent_load</code>. This avoids embedding large or shared external objects, but it converts one byte stream into a graph spanning another store.

The design must then answer:

- Is the ID stable and globally unique within its namespace?
- What authorises resolution?
- Is the referenced object immutable or versioned?
- What happens when it is absent?
- Can a valid pickle cause enumeration or retrieval of an unauthorised object?
- Is resolution part of the same transaction or snapshot?
- How is garbage collection coordinated?

The word “persistent” describes the reference hook, not guaranteed persistence. A pickle referring to a deleted database row is valid syntax with an unresolvable dependency.

### 11.9.11 Protocol 5 out-of-band buffers

Protocol 5 can place large buffer-compatible data outside the main pickle stream. A pickler invokes <code>buffer_callback</code>, and the unpickler consumes corresponding buffers in order. This can reduce copies for numerical arrays and inter-process data paths.

It also means that the pickle byte string alone may no longer be a complete artefact. Correct transport binds:

- main pickle bytes;
- exact ordered buffer sequence;
- lengths and formats;
- integrity/authentication for every part;
- lifetime and ownership of exported memory;
- compatible protocol and object libraries.

Supplying the wrong buffer order can reconstruct incorrect data or fail. Retaining a view can extend the lifetime of substantial memory. Out-of-band transport is an optimisation with a compound protocol, not free performance.

### 11.9.12 Caches are disposable; durable records are migratable

Pickle often suits a **cache**: derived data that can be discarded and rebuilt from authoritative sources. A cache reader can treat incompatibility, corruption, or absence as a miss:

~~~python
def load_cache(path: Path) -> object | None:
    try:
        raw = path.read_bytes()
        return pickle.loads(raw)
    except (
        FileNotFoundError,
        EOFError,
        ImportError,
        AttributeError,
        pickle.PickleError,
    ):
        return None
~~~

This example assumes the cache directory is trusted against malicious modification. Catching these exceptions is appropriate only because losing cache content is acceptable; <code>OSError</code> from broad storage failure might deserve propagation or diagnosis rather than “miss”.

Authoritative long-lived data should generally use an explicit, documented, language-neutral schema with migration tools. If pickle is chosen, archive the exact software environment, application schema version, migration readers, authenticity policy, and recovery tests. Serialisation convenience does not establish maintainable persistence.

> **Common misconception 11.29 — “If a value can be pickled, pickle is an appropriate database.”** Picklability says the object graph can be represented. It supplies no query model, transaction, concurrency control, retention, migration, or recovery policy.
