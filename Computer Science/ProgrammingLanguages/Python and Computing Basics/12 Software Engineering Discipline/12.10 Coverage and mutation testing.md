# 12.10 Coverage and mutation testing

**Code coverage** reports which source regions, branches, or conditions executed during tests. Uncovered code has no dynamic test observation. Covered code is not necessarily asserted correctly.

One test can execute every line while checking nothing meaningful:

```python
def test_runs() -> None:
    calculate_invoice(sample_invoice)
```

Line coverage may be high; no oracle judges the result.

**Mutation testing** deliberately makes small source changes—negating conditions, changing operators, removing calls—and checks whether tests fail. A surviving mutant identifies a behaviour distinction the suite did not detect or an equivalent transformation. Mutation score is diagnostic, not a goal to game with implementation-coupled assertions.

Coverage finds absence of execution. Mutation testing probes assertion sensitivity. Neither replaces risk-based test design.

### 12.10.1 Structural coverage criteria

Coverage has several denominators:

- **statement or line coverage** asks whether mapped source statements/lines executed;
- **branch coverage** asks whether decision outcomes occurred;
- **condition coverage** asks whether component Boolean conditions took relevant truth values;
- **path coverage** asks whether control-flow paths executed;
- **function coverage** asks whether callable units were entered.

Tools differ in how they map bytecode events to source lines, treat comprehensions, exclude code, and combine subprocess data. Quote the tool, version, configuration, and denominator when reporting a percentage.

Consider:

~~~python
def eligible(age: int, has_consent: bool) -> bool:
    return age >= 16 and has_consent
~~~

Two tests—<code>(15, True)</code> and <code>(16, False)</code>—can make each simple condition both true and false across the suite, yet never exercise the overall true result. Decision/condition criteria distinguish such gaps. **Modified condition/decision coverage** (**MC/DC**) requires evidence that each condition can independently affect the decision outcome under suitable pairs; it is used in some safety standards but remains structural evidence, not semantic completeness.

Path coverage becomes infeasible or infinite with loops. Treat coverage criteria as observation lenses rather than a finish line.

### 12.10.2 Interpreting uncovered code

An uncovered region can mean:

- missing test;
- unreachable defensive branch;
- platform-specific path absent from this run;
- obsolete code;
- instrumentation limitation;
- intentionally excluded generated or diagnostic code.

Each interpretation demands a different action. Deleting unreachable code can be better than manufacturing a test. A platform path requires a test matrix. A defensive assertion thought impossible may need a lower-level fault injection test.

A coverage threshold prevents large accidental regressions in execution breadth, but a global threshold permits new critical code to hide behind well-covered old code. Changed-line coverage can focus attention on a patch, while risk review protects important unchanged paths.

> **Common misconception 12.37 — “One hundred per cent coverage means every branch has been tested.”**  
> The statement is meaningless without a coverage criterion. Even complete branch coverage omits many values, histories, interactions, and oracle defects.

### 12.10.3 Mutation operators and equivalent mutants

A mutation tool constructs **mutants**, each a modified program such as:

- replacing <code>&lt;</code> with <code>&lt;=</code>;
- replacing addition with subtraction;
- negating a predicate;
- deleting a statement or call;
- changing a constant;
- returning a default value.

The suite **kills** a mutant if at least one test fails. A mutant **survives** if selected tests pass. A **stillborn** mutant cannot compile or import; a **timeout** may reveal changed termination or merely an inadequate execution bound.

An **equivalent mutant** has the same observable behaviour as the original over the specified domain. For example, replacing <code>x * 2</code> with <code>x + x</code> is equivalent for Python integers but not necessarily for every user-defined object. Determining equivalence can be undecidable in general, so mutation reports require analysis.

Mutation score is usually killed non-equivalent mutants divided by attempted non-equivalent mutants under a declared policy. Comparing scores across tools or projects without matching operators and exclusions is unsound.

### Worked example 12.3E — Analyse a surviving boundary mutant

Production:

~~~python
def may_register(age: int) -> bool:
    return age >= 18
~~~

Suite:

~~~python
def test_adult_may_register() -> None:
    assert may_register(25)


def test_child_may_not_register() -> None:
    assert not may_register(12)
~~~

The mutant <code>age &gt; 18</code> survives because neither case distinguishes the boundary. Add:

~~~python
def test_eighteenth_birthday_is_included() -> None:
    assert may_register(18)
~~~

The new test has a domain rationale independent of mutation score. If policy actually says “older than 18”, then the mutant exposed an ambiguous or wrong requirement rather than a missing test.

### 12.10.4 Coverage-guided and fuzz testing

**Fuzz testing** supplies large volumes of generated, malformed, or adversarial input to find crashes, hangs, resource exhaustion, and invariant violations. **Coverage-guided fuzzing** uses execution feedback to favour inputs reaching new program regions. It is particularly effective at parsers and binary boundaries.

Python-level fuzzing can call a pure entry point with bytes:

~~~python
def fuzz_one_input(data: bytes) -> None:
    try:
        record = parse_record(data)
    except ParseError:
        return
    assert encode_record(record).startswith(b"LR")
~~~

The harness must bound input size and distinguish expected rejection from defects. Catching <code>Exception</code> would hide unexpected failures. Native extensions may require process isolation and memory-safety instrumentation.

Fuzzing explores implementation behaviour; it does not know business correctness unless the harness supplies semantic invariants or differential oracles.

> **Common misconception 12.38 — “Fuzzing is random invalid-input testing.”**  
> Modern fuzzers can mutate structured corpora and use feedback to navigate execution. Their effectiveness still depends on harness reachability, sanitisation, dictionaries, seed corpus, and oracles.
