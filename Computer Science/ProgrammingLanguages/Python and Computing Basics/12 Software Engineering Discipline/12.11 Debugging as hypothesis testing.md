# 12.11 Debugging as hypothesis testing

**Debugging** is the disciplined localisation and explanation of a divergence between expected and observed behaviour. Random edits generate new experiments without a hypothesis and destroy evidence.

A rigorous cycle is:

1. state the expected behaviour and its source;
2. reproduce the observation under recorded conditions;
3. reduce to the smallest failing example;
4. identify the earliest state divergence;
5. propose a causal hypothesis;
6. design a discriminating observation that would differ if the hypothesis were false;
7. change one relevant factor;
8. repair the cause;
9. add a regression test protecting the rule;
10. review adjacent paths sharing the cause.

### Worked example 12.4 — Find first divergence

Defect: a report total is 120 instead of expected 102.

Weak action: alter formatting until output looks right.

Evidence path:

- fixture contains `10`, `20`, `72` → independent arithmetic oracle 102;
- parser trace produces `[10, 20, 72]` → no divergence;
- aggregator states 10, 30, 102 → no divergence;
- formatter receives 102 but emits `120` → first divergence;
- inspect formatting transformation and find reversed string slicing.

The earliest divergence localises the defective boundary. The regression test should assert formatter behaviour and one integrated report path; only the former localises, only the latter preserves composition.

A debugger permits breakpoints, step execution, stack inspection, and conditional observation. Logging preserves events across time and environments. Print statements are legitimate small experiments but require removal or channel discipline; they are not a substitute for a persistent observability design.

### 12.11.1 Observation is not explanation

A **symptom** is an observed departure from expectation. A **fault** or **defect** is an incorrect artefact or state that can cause a failure. A **failure** is externally observed behaviour that does not satisfy a requirement. One defect can cause many failures; one failure can require several contributing defects and environmental conditions.

“The parser crashed” records a symptom. “An unchecked index assumes every escape introducer has a following byte” identifies a candidate defect. “The input ends in one escape introducer, causing the index operation at parser state ESCAPE to raise <code>IndexError</code> rather than the specified <code>ParseError</code>” is a causal account that can be challenged.

Correlation is not causation. If a failure disappears after adding logging, the log statement may alter timing, memory layout, buffering, or exception handling. The observation narrows hypotheses but does not prove that missing logging caused the original failure.

> **Common misconception 12.39 — “The line named at the bottom of the traceback is the root cause.”**  
> It is usually the point where an exception was raised or propagated without handling. The invalid state may have been created much earlier or outside that process.

### 12.11.2 Reproduction records

A **minimal reproducible example** is the smallest self-contained case presently known to exhibit the relevant failure. “Minimal” is relative to current knowledge: further reduction may reveal a smaller cause. A reproduction record should contain:

- expected and observed outcomes;
- exact input, with sensitive data reduced safely;
- program and dependency versions;
- Python implementation and build;
- operating system and architecture;
- configuration and feature flags;
- state preparation and command;
- frequency and timing;
- concurrency and resource conditions;
- complete traceback or failure record;
- last known working version when available.

Do not attach confidential production data indiscriminately. Construct a synthetic input preserving the structural property—length, encoding, field relationship, or timing—needed for failure. If reduction removes the failure, the removed property becomes evidence.

A failure that cannot be reproduced still deserves structured investigation. Preserve telemetry, crash dumps where lawful, request identifiers, and environmental deltas. Absence of reproduction is uncertainty, not proof of user error.

### Worked example 12.4A — Reduce a parser failure

Initial report: a 40 MiB customer export causes <code>IndexError</code>. Begin by fixing the version and retaining the original securely. Use a **reduction predicate** that returns true only when the failure of interest occurs:

~~~python
def reproduces(data: bytes) -> bool:
    try:
        parse_records(data)
    except IndexError:
        return True
    except Exception:
        return False
    return False
~~~

A line-level reducer removes groups of records while preserving <code>reproduces</code>. Suppose it reaches:

~~~text
identifier,name
7,abc\
~~~

Byte-level reduction reveals that the terminal backslash is sufficient within a quoted-field state. The 40 MiB size was correlated because the malformed row happened to be late, not causal. The final regression test should use the smallest semantically meaningful malformed record and assert the specified error type, offset, and lack of partial output.

The reducer must not run unsafe inputs against a privileged production service. It is a controlled diagnostic instrument.

> **Common misconception 12.40 — “If reducing the input removes the failure, reduction failed.”**  
> The boundary between reproducing and non-reproducing cases identifies necessary conditions. Restore one removed factor at a time and continue.

### 12.11.3 Reading tracebacks as causal evidence

A Python **traceback** records frames through which an exception propagated. Each frame identifies a code location and may permit inspection of local variables. Read from the exception type and message upward through the call chain, while asking:

1. which operation rejected or failed;
2. which values reached it;
3. which caller established those values;
4. where the violated invariant should have been enforced;
5. whether the visible exception is primary or arose during handling.

Explicit exception chaining with <code>raise NewError(...) from error</code> states causation. Raising during cleanup can mask an earlier exception if not handled carefully; modern Python can represent several concurrent failures through an exception group.

Never paste tracebacks containing secrets, tokens, query values, or personal data into public issues. Locals and representations can contain far more than the message suggests.

### Worked example 12.4B — Preserve boundary meaning with chaining

~~~python
from pathlib import Path


class ConfigurationError(RuntimeError):
    pass


def load_configuration(path: Path) -> Configuration:
    try:
        text = path.read_text(encoding="utf-8")
    except OSError as error:
        raise ConfigurationError(
            f"cannot read configuration at {path.name}"
        ) from error

    try:
        return parse_configuration(text)
    except ParseError as error:
        raise ConfigurationError(
            f"invalid configuration at {path.name}"
        ) from error
~~~

The outer exception communicates application-boundary meaning. The cause retains the filesystem or parse detail for diagnostics. Using only <code>raise ConfigurationError</code> would discard causation; allowing every low-level exception to escape would couple callers to implementation details. Whether a filename itself is sensitive depends on the application.

### 12.11.4 Hypothesis ledgers and discriminating experiments

A **hypothesis ledger** prevents investigation from becoming an unrecorded sequence of intuitions:

| Hypothesis | Predicted observation if true | Experiment | Result | Status |
|:---|:---|:---|:---|:---|
| stale cache | bypassing cache returns correct value | query source directly with same identifier | still wrong | rejected |
| timezone conversion | UTC record correct, local display wrong near DST | inspect stored instant and conversion zone | stored instant wrong | rejected |
| parser swaps day/month | failure only when both fields valid as months | test 04/05 and 13/05 | 04/05 swapped; 13/05 rejected | supported |

A **discriminating experiment** separates at least two plausible explanations. Merely rerunning the same request gives a frequency observation but may not distinguish causes.

Change one relevant factor where possible. In complex systems, controlled factorial experiments may vary several factors deliberately, but the design must still permit attribution.

### 12.11.5 Binary search over histories and inputs

When a deterministic test passes at one commit and fails at a later commit, Git bisection can locate the first failing commit in logarithmically many classifications. If there are <code>n</code> candidate commits, ideal binary division requires approximately <code>ceil(log2(n))</code> test steps, though merges, skipped unbuildable commits, and nondeterminism complicate this.

~~~text
git bisect start
git bisect bad <failing-commit>
git bisect good <known-working-commit>
git bisect run python -m pytest tests/regression/test_issue_417.py
git bisect reset
~~~

The test command must return a conventional success/failure status and must classify historical environments fairly. A dependency fetched without a historical lock can make an old source revision fail for a new external reason. The first bad commit is where the predicate changes, not automatically the sole conceptual cause; it may expose a latent data or environment assumption.

The same principle applies to input reduction and execution traces: divide the candidate space based on a stable failure predicate.

> **Common misconception 12.41 — “The first bad commit identifies who caused the incident.”**  
> It identifies a history boundary under a particular test. Causation may include earlier latent assumptions, missing review controls, deployment state, or an external change; blame is not a debugging method.

### 12.11.6 Interactive debugging with pdb

Python’s standard debugger, <code>pdb</code>, controls execution and inspects frames. The built-in <code>breakpoint()</code> normally enters the configured breakpoint hook:

~~~python
def calculate_total(lines: list[Line]) -> int:
    total = 0
    for line in lines:
        total += line.amount_pence
        if total < 0:
            breakpoint()
    return total
~~~

At the prompt, ordinary operations include listing source, printing expressions, moving up and down the stack, continuing, stepping into a call, and executing the next line. Exact commands belong to the debugger’s official documentation and version.

A debugger observes and can mutate live state. Evaluating a property can execute code; changing a variable can make the run unrepresentative. Record what was evaluated, and do not attach an interactive debugger to production without authorisation and an understanding of pause, confidentiality, and availability consequences.

Post-mortem debugging begins after an uncaught exception and inspects preserved frames. Pytest can expose a debugger on failure. This is efficient for local analysis but unsuitable as the only CI diagnostic because unattended runs need persistent output.

### 12.11.7 Debugging concurrency and Heisenbugs

A **Heisenbug** is a defect whose manifestation changes when it is observed, named by analogy with measurement effects. Concurrency failures are common examples because breakpoints and prints alter scheduling.

For concurrent defects:

- record logical events with monotonic timestamps and correlation identifiers;
- preserve thread, task, or process identity;
- model happens-before relations rather than trusting close wall-clock timestamps;
- reduce shared mutable state;
- control schedulers or use barriers in focused tests where possible;
- repeat under stress while retaining every failing seed and schedule;
- inspect lock ordering and ownership;
- distinguish deadlock, livelock, starvation, and data race.

A **deadlock** is a state in which participants wait cyclically for events only those participants can cause. A **livelock** involves continued activity without progress. **Starvation** means a participant is indefinitely denied progress while others proceed. A **data race** is concurrent conflicting memory access without required synchronisation under the relevant memory model. Python’s GIL does not erase higher-level races; Chapter 14 treats this precisely.

> **Common misconception 12.42 — “Adding a lock around the failing line fixes a race.”**  
> Correct synchronisation protects a shared invariant across every access and has a defined lock order and lifetime. A local lock held by only one participant protects nothing from others.

### 12.11.8 Repair, regression, and causal closure

A repair is complete only when:

1. the original failure is reproducible or otherwise explained;
2. a regression test fails on the defective version and passes on the repair;
3. the causal invariant is restored, not merely the visible output;
4. adjacent paths sharing the defect are examined;
5. operational data confirms the expected effect after release;
6. documentation or process controls change where the cause was systemic.

A workaround reduces impact without removing the underlying cause. Workarounds can be correct emergency responses, but label them and track their removal criteria.

**Root-cause analysis** should not force a single root when causes form a graph. “Operator error” is rarely a terminal explanation; ask why the interface permitted the action, why detection failed, and which safeguards were absent. Likewise, “missing test” explains non-detection, not necessarily why the defect was introduced.

### Worked example 12.4C — Five-whys used critically

Failure: invoices were charged twice.

1. Why? The retry sent a second provider request.
2. Why? The client timed out after the provider committed but before receiving the response.
3. Why did retry duplicate the effect? Requests lacked a stable idempotency key.
4. Why was that absent? The interface model treated timeout as equivalent to “not processed”.
5. Why was the model accepted? Requirements and integration tests covered rejection before commit, not ambiguous completion.

The chain identifies design and evidence changes: stable operation identity, provider-supported idempotency, persisted retry state, tests for timeout after commit, and telemetry for duplicate attempts. It does not prove these are the only contributors.

> **Common misconception 12.43 — “A regression test should reproduce the entire production incident.”**  
> Preserve a focused test for the causal rule and enough integration evidence for the failed composition. Reconstructing every incidental production condition can make the test costly and fragile without improving discrimination.
