# 12.12 Logging and diagnostics

A **log event** is a structured record of an operational occurrence. Useful fields include timestamp, severity, event name, request or correlation identifier, component, outcome, and bounded context. Logs should support a question, not narrate every line.

Python’s `logging` module separates event creation from handlers, formatters, destinations, and severity policy.

```python
import logging

logger = logging.getLogger(__name__)


def load_account(identifier: str) -> Account:
    logger.info("account_load_started", extra={"account_id": identifier})
    try:
        account = repository.get(identifier)
    except DatabaseError:
        logger.exception(
            "account_load_failed",
            extra={"account_id": identifier},
        )
        raise
    logger.info("account_load_succeeded", extra={"account_id": identifier})
    return account
```

`logger.exception` inside an exception handler records traceback information. Do not log and suppress unless the boundary owns recovery. Repeated logging of the same propagated failure at every layer creates noise; each layer should add information only when it owns meaningful context.

Never log credentials, access tokens, complete payment data, or sensitive content by default. Hashing a secret is not automatic anonymisation: low-entropy values can be guessed, hashes can remain personal identifiers, and retention policy still applies.

### 12.12.1 Observability and diagnostic channels

**Observability**, in engineering practice, is the ability to infer relevant internal system state from emitted signals. The term derives from control theory but is used more loosely in software operations. Common signals are:

- **logs**: discrete event records;
- **metrics**: numerical measurements aggregated over dimensions and time;
- **traces**: causally related spans representing a request or operation across components;
- **profiles**: sampled or instrumented resource use;
- **crash reports**: exceptional termination state;
- **audit records**: controlled evidence of security- or business-significant actions.

These channels have different semantics. An audit record should not disappear because diagnostic verbosity is reduced. A metric should not use an unbounded customer identifier as a dimension, because each distinct value creates a time series and can exhaust the monitoring system. A trace samples individual causal paths and cannot by itself count all events if sampling discards some.

An observable system is not one that emits everything. Excess events increase cost, hide signal, and create confidentiality exposure. Begin with operational questions and failure modes, then design bounded signals that answer them.

### 12.12.2 Log levels are policy

Python’s standard logging levels conventionally include DEBUG, INFO, WARNING, ERROR, and CRITICAL. Their numeric ordering enables filtering, but their meaning must be defined by the project:

| Level | Example policy |
|:---|:---|
| DEBUG | detailed diagnostic state disabled in ordinary production |
| INFO | normal lifecycle event useful for operation |
| WARNING | unexpected or degraded condition from which operation continues |
| ERROR | requested operation failed and needs investigation or counted response |
| CRITICAL | service or data integrity is broadly at risk |

Do not log every caught exception as ERROR. A malformed public request can be an expected outcome measured by a bounded counter; an exhausted database after retries may be an error. Severity reflects operational response, not Python exception hierarchy.

Logger names form a hierarchy. Library code should obtain <code>logging.getLogger(__name__)</code>, emit records, and leave global handler configuration to the application. Calling <code>basicConfig</code> from an imported library takes policy away from its host.

> **Common misconception 12.44 — “ERROR means an exception occurred.”**  
> Severity classifies operational significance. Some exceptions are routine boundary outcomes; some silent invariant violations are critical.

### 12.12.3 Structured event design

Free-form text is readable but difficult to aggregate reliably. A **structured log event** has a stable event name and typed fields. The standard logging API stores a <code>LogRecord</code>; handlers or adapters can encode it as JSON.

~~~python
logger.info(
    "report_export_completed",
    extra={
        "event_name": "report_export_completed",
        "request_id": request_id,
        "record_count": record_count,
        "duration_ms": round(duration_seconds * 1_000),
        "schema_version": 2,
    },
)
~~~

The stable event name is machine-facing. A human-readable message can coexist, but downstream alerts should not parse changing prose. Fields need units and bounded cardinality. <code>duration_ms</code> names its unit; <code>request_id</code> is high-cardinality and belongs in logs/traces, not usually a metric label.

Schema evolution applies to events. Removing or changing a field can break dashboards and incident queries. Treat operational event shapes as maintained interfaces.

### 12.12.4 Correlation and causality

A **correlation identifier** links records believed to concern one operation. It does not prove causality and should not automatically be trusted when supplied by an external caller. Generate or validate identifiers at trust boundaries, propagate them explicitly, and distinguish request, user action, job, and business transaction identities.

Distributed tracing represents work as **spans** with parent or link relations, timings, attributes, and status. Asynchronous queues can break simple parent-child timing: a producer span may finish before a consumer begins, and one consumer may process a batch from many producers. Use the tracing model’s explicit links rather than inventing a misleading tree.

Clock skew means timestamps from different machines are not a total causal order. Protocol identifiers and message relations can establish causality where wall clocks cannot.

### 12.12.5 Metrics and service objectives

A **metric** maps observations to numbers over time. Common metric forms include counters, gauges, and distributions/histograms:

- a counter accumulates occurrences, such as completed requests;
- a gauge records a value that can rise or fall, such as queue depth;
- a histogram or distribution records observations across value ranges, such as latency.

A **service-level indicator** (**SLI**) is a quantitative measure of provided service, such as the proportion of valid requests completed successfully below a latency threshold. A **service-level objective** (**SLO**) is a target range for an SLI over a period. A contractual **service-level agreement** (**SLA**) may attach consequences and must not be conflated with internal engineering targets.

Averages conceal tail behaviour. If 99 requests take 10 ms and one takes 10 seconds, the mean is approximately 110 ms, a value experienced by none. Report distributions and percentiles under a defined aggregation method. Percentiles cannot in general be averaged across arbitrary windows to obtain the combined percentile.

### Worked example 12.4D — Derive an availability indicator

Let eligible events be requests the service contract says it should handle. Let good events be eligible requests that produce a correct response within 300 ms. Over window <code>W</code>:

\[
\operatorname{SLI}(W)
=
\frac{\text{good eligible events in }W}
{\text{all eligible events in }W}.
\]

If there are 999,400 good events among 1,000,000 eligible events, the observed indicator is 0.9994 or 99.94%. This empirical result depends on classification: excluding every timeout from the denominator would manufacture perfect availability. Define client cancellations, invalid requests, dependency failures, and planned maintenance explicitly.

### 12.12.6 Assertions, health checks, and crash diagnostics

An assertion detects a programmer-assumed invariant at a specific point. A **health check** reports whether a running component can perform a defined role. A process being alive is a shallow liveness check; readiness may require configuration, essential dependencies, and capacity. An overly deep health check can amplify a dependency outage by restarting healthy processes.

Python’s <code>faulthandler</code> can dump Python tracebacks on fatal signals and hangs under supported platforms. <code>tracemalloc</code> traces Python memory allocation locations. These are CPython/runtime diagnostic facilities, not language semantics; their overhead and coverage should be measured in the target environment.

Diagnostic endpoints can expose versions, topology, or secrets. Authenticate or restrict them according to threat model, and return only what the consumer needs.

> **Common misconception 12.45 — “More telemetry makes a system more observable.”**  
> Observability depends on whether bounded, trustworthy signals distinguish relevant states. Unstructured volume can make diagnosis slower and the system less reliable.

### 12.12.7 Incident response and learning

An **incident** is an event that disrupts or threatens required service, safety, security, or data integrity. Incident response commonly separates:

1. detection and triage;
2. containment;
3. mitigation or restoration;
4. evidence preservation;
5. root-cause and contributing-factor analysis;
6. corrective actions and verification;
7. follow-up on residual risk.

The immediate priority can be to reduce harm, not to find an elegant permanent fix. Rollback, traffic shedding, feature disabling, or credential rotation may be correct containment. Record a timeline using evidence and confidence levels; memory after a stressful event is not a reliable clock.

A **post-incident review** should explain mechanisms and controls rather than search for a person to blame. Accountability remains possible: deliberate policy violation and negligent practice can require action. The engineering purpose is to change the system so the same initiating event is less likely, detected earlier, or less harmful.

Corrective actions should be specific and verifiable. “Be more careful” has no completion evidence. “Make idempotency key mandatory in the gateway protocol; reject its absence statically and at runtime; add an ambiguous-timeout integration case” changes artefacts and can be tested.
