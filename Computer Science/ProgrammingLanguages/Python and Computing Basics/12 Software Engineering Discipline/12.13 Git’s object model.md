# 12.13 Git’s object model

**Version control** records and relates states of a project over time. Git is a distributed version-control system organised around content-addressed objects and references.

The working model has three principal states:

- **working tree:** files currently checked out and editable;
- **index** or **staging area:** proposed content for the next commit;
- **repository:** stored objects and references representing committed history.

A **commit** is an object containing a tree reference, parent commit reference(s), author/committer metadata, and message. A **tree** records names, modes, and references to blobs or subtrees. A **blob** stores file content without its filename. Object identifiers are hashes over typed content under Git’s format.

A **branch** is a movable reference to a commit. `HEAD` identifies the currently checked-out branch or commit. Committing creates a new commit whose parent is the prior tip and advances the branch reference. Git does not store “a folder of changed files” as the fundamental commit model; it records a project tree and shares unchanged objects efficiently.

### Worked example 12.5 — Stage only an intended change

Suppose `model.py` and `notes.txt` are modified, but only the model repair belongs to the next commit.

```text
git status
git diff -- model.py
git add model.py
git diff --cached
git commit -m "Reject negative opening balances"
```

`git diff` inspects working-tree changes relative to the index by default. `git add` updates the index with selected content. `git diff --cached` reviews the proposed commit. The commit captures staged `model.py`; unrelated `notes.txt` remains modified in the working tree.

The unit of history should be one coherent change that builds and whose message explains intent. A small commit can still be incoherent; a large commit can sometimes be one unavoidable migration. Reviewability and reversible reasoning are the criteria.

### 12.13.1 Repository topology and reachability

Git’s object database and its reference names are distinct. Objects form a directed graph:

- a commit references one root tree, zero or more parents, and metadata;
- a tree references blobs and nested trees;
- an annotated tag object references another object and contains tag metadata;
- a reference, such as <code>refs/heads/main</code>, stores an object identifier, normally a commit identifier.

An object is **reachable** when traversal from a retained reference or other root can reach it. Deleting a branch removes a name; it does not immediately erase every object formerly reached through that name. Reflogs and object-retention policy can keep it recoverable for a time. Eventually unreachable objects may be pruned by maintenance. Recovery is therefore possible, not guaranteed.

The term **content-addressed** means an identifier is derived from object content under Git’s object format. Altering any hashed part yields a different identifier with overwhelming probability. This detects accidental or malicious alteration relative to a trusted identifier, but the hash alone does not establish who authored content, whether it is safe, or whether the repository’s reference was itself substituted.

Git historically uses SHA-1 object identifiers and supports a SHA-256 repository format in relevant versions. Algorithm and interoperability details are implementation/version facts; never infer identifier length from examples when writing long-lived tooling.

> **Common misconception 12.46 — “A commit hash proves who wrote the commit.”**  
> It identifies hashed content. Authorship fields are data inside that content and can be chosen freely. Authenticity requires a trusted distribution channel or a verified cryptographic signature under an identity policy.

### 12.13.2 A commit is a snapshot with ancestry

Git presents diffs because humans review change, but a commit names a complete project tree. Unchanged subtrees and blobs are shared, so snapshots need not duplicate all bytes. A diff is computed by comparing two trees, often with rename similarity heuristics.

This distinction matters:

- a file rename is not necessarily stored as an explicit rename event;
- the same commit can be compared with different parents or working states;
- merge commits have more than one parent and therefore more than one parent-relative diff;
- path history is derived and can become ambiguous through copies and rewrites.

Commit identity includes the root tree, parents, author, committer, message, and relevant timestamps/headers. Amending a message therefore produces a new commit even if every file is unchanged.

### Worked example 12.5A — Inspect objects without changing history

In a disposable repository:

~~~text
git rev-parse HEAD
git cat-file -t HEAD
git cat-file -p HEAD
git ls-tree HEAD
git show --stat --oneline HEAD
git diff HEAD^ HEAD
~~~

<code>rev-parse</code> resolves a revision expression; <code>cat-file -t</code> reports object type; <code>cat-file -p</code> prints an object in an appropriate representation; <code>ls-tree</code> lists a tree; <code>show</code> presents commit and derived change; <code>diff</code> compares the first parent with the commit. Commands and revision syntax are Git interfaces and should be checked against the installed manual.

If the commit is the repository’s first, <code>HEAD^</code> has no parent and the final command fails. This is a boundary case in history structure, not file content.

### 12.13.3 The working tree and index are independent states

For an ordinary tracked path, there can be three relevant versions:

1. the version in <code>HEAD</code>;
2. the version in the index;
3. the version in the working tree.

Consequently:

| Command | Principal comparison |
|:---|:---|
| <code>git diff</code> | working tree versus index |
| <code>git diff --cached</code> | index versus <code>HEAD</code> |
| <code>git diff HEAD</code> | working tree versus <code>HEAD</code> |

The index is not merely a list of filenames. It records path, mode, object identifier, and conflict stages. <code>git add</code> copies selected working content into the index; later working edits do not alter the staged blob until another add.

Interactive staging can select hunks, but a hunk is a textual partition generated by diff heuristics. If two conceptual changes occupy the same line, edit deliberately or sequence commits in a temporary working state. Never leave the working file broken merely to manufacture tiny commits without verifying each snapshot.

> **Common misconception 12.47 — “Staging saves my work.”**  
> It prepares content for the next commit and stores associated objects, but it is not a durable substitute for a named commit and remote backup. Later index operations can replace it.

### 12.13.4 References, HEAD, and detached state

A local branch name is usually a reference under <code>refs/heads/</code>. A remote-tracking reference, such as <code>refs/remotes/origin/main</code>, records the last locally fetched state of a remote reference; it does not update continuously. A tag normally resides under <code>refs/tags/</code>.

<code>HEAD</code> is usually a symbolic reference to the current branch. In a **detached HEAD** state it identifies a commit directly. New commits are valid objects but no branch name advances to retain them. Before switching away, create a branch or tag if the work should remain conveniently reachable.

A **revision expression** such as <code>main~3</code> or <code>release^2</code> resolves relative to graph ancestry. The tilde follows first parents repeatedly; a numbered caret selects a particular parent. Merge topology makes this different from “three chronological commits ago”.

### 12.13.5 Remotes, fetch, pull, and push

A **remote** is a named set of repository locations and refspec configuration. It is not inherently central; Git remains distributed. Common operations:

- <code>fetch</code> obtains objects and updates configured remote-tracking references;
- <code>merge</code> integrates another history into the current branch;
- <code>rebase</code> copies selected commits onto another base;
- <code>pull</code> normally performs fetch followed by a configured integration strategy;
- <code>push</code> asks a remote to update references after transferring needed objects.

Because <code>pull</code> combines two conceptual operations, explicit <code>fetch</code> followed by inspection and chosen integration can be clearer. A push can be rejected if the remote reference would cease to contain its current tip under a fast-forward policy.

Authentication proves control of credentials to a transport endpoint. It does not make fetched code trustworthy. Review repository identity, protected reference policy, signatures where used, and dependency changes.

> **Common misconception 12.48 — “origin is the authoritative repository.”**  
> <code>origin</code> is a conventional remote name created by many clone workflows. Authority comes from project governance and verified location, not from the spelling of a local configuration entry.
