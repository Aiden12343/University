# 12.14 Branching, merging, and conflicts

A branch permits a line of commits to advance independently. Merging relates histories and combines tree changes. A **merge conflict** means Git cannot safely choose one combined content automatically; it does not mean the developers are personally in conflict or that one side is correct.

Conflict resolution requires understanding the intended post-merge program, not merely deleting marker lines. After editing resolved content:

1. inspect every conflict region and adjacent invariant;
2. run focused and integration tests;
3. stage the resolved files;
4. inspect the resulting diff;
5. complete the merge commit under the repository workflow.

Rebasing copies a sequence of changes onto a new base by creating new commit objects. It rewrites commit identities. Do not rebase shared published history without a team policy because collaborators’ references still point to the original commits.

`git revert` creates a new commit applying the inverse of an earlier change under current context. It preserves public history and is distinct from resetting references or discarding working files.

### 12.14.1 Fast-forward and true merges

Suppose branch <code>feature</code> descends directly from <code>main</code> and <code>main</code> has not advanced. Moving <code>main</code> to the feature tip is a **fast-forward**: no new merge commit is required because the feature tip already contains the previous main tip as an ancestor.

If both branches have new commits, a three-way merge uses:

1. the merge base, representing shared ancestry;
2. one branch tip;
3. the other branch tip.

Changes from base to each side are combined. A clean textual merge is not necessarily a correct semantic merge. One branch may rename a configuration value while the other adds a new use of the old name on different lines; no markers appear, yet the combined program is wrong.

### Worked example 12.5B — A semantic conflict without markers

Base:

~~~python
TIMEOUT_SECONDS = 5


def fetch(client: Client) -> Response:
    return client.get(timeout=TIMEOUT_SECONDS)
~~~

Branch A changes units:

~~~python
TIMEOUT_MILLISECONDS = 5_000


def fetch(client: Client) -> Response:
    return client.get(timeout=TIMEOUT_MILLISECONDS / 1_000)
~~~

Branch B adds:

~~~python
def refresh(client: Client) -> Response:
    return client.get(timeout=TIMEOUT_SECONDS * 2)
~~~

A textual merge can retain Branch A’s renamed constant and Branch B’s new function referring to the removed name. Tests and static analysis detect what the merge algorithm cannot infer. Integration review must reason about the combined tree.

> **Common misconception 12.49 — “No conflict markers means the merge succeeded.”**  
> It means Git produced a textual tree automatically. Semantic compatibility remains an engineering claim requiring build, analysis, and tests.

### 12.14.2 Conflict stages and resolution

During an unresolved merge, the index can hold up to three staged entries for a conflicted path: merge base, “ours”, and “theirs”. These labels are contextual and can be surprising during rebase, where the checked-out side and replayed commit have roles different from a simple branch merge.

Conflict markers in a working file delimit candidate regions:

~~~text
<<<<<<< current-side
selected content
=======
other-side content
>>>>>>> other-side
~~~

Resolution is not “choose ours”, “choose theirs”, or concatenate both by default. Reconstruct the intended post-integration requirement, inspect surrounding changes and history, edit a coherent result, stage it, and test. Generated files should normally be regenerated from resolved sources rather than hand-merged.

Binary files require domain-specific merge tools or selection because line merging has no meaningful general rule. Database migrations, lock files, and generated schemas may be textual yet still require specialised semantic resolution.

### 12.14.3 Rebase as change replay

If commits <code>F1</code> and <code>F2</code> descend from base <code>B</code>, rebasing onto <code>M</code> computes their changes and applies equivalents, producing new commits <code>F1'</code> and <code>F2'</code>. Content can match while identifiers differ because parents and metadata differ.

Interactive rebase can reorder, combine, edit, or omit commits. It is useful for preparing an intelligible unpublished change series. It can also destroy review context if used to conceal the actual evolution of a risky change. Project policy should distinguish cleanup from falsification.

After rebase, test the resulting series. Resolving the same conceptual conflict at several replayed commits may produce intermediate states that do not build. Whether every intermediate commit must pass depends on the project’s history policy, but bisectability and review improve when it does.

Force-updating a remote reference can discard another contributor’s new tip. A lease-protected force operation checks the expected remote state and is safer than unconditional force, but it still rewrites history and requires authorisation and coordination.

> **Common misconception 12.50 — “Rebase moves existing commits.”**  
> It normally creates new commits representing replayed changes on a new parent chain. Names are then updated to reach the new objects.

### 12.14.4 Merge, rebase, squash, and cherry-pick

These operations answer different history questions:

| Operation | Result |
|:---|:---|
| merge | combines ancestries, possibly with a multi-parent commit |
| rebase | replays changes as new commits on another base |
| squash merge | integrates the net change as one new commit without feature ancestry in the main line |
| cherry-pick | applies the change introduced by selected commit(s) as new commit(s) elsewhere |
| revert | applies an inverse change as new history |

Cherry-picking duplicates a change but not its ancestry relation. Later merging branches containing both original and cherry-picked changes can require careful reasoning. Record the source commit in the message when policy supports traceability.

No strategy is universally cleanest. Merge commits preserve topology; a linear rebased history can simplify first-parent reading; squashing hides internal steps; cherry-picking is useful for targeted backports. Choose based on collaboration, audit, release, and recovery needs.

### 12.14.5 Reset, restore, and revert

These commands are often confused:

- <code>git revert</code> creates a new commit that attempts to reverse an earlier commit’s change;
- <code>git reset</code> moves the current branch reference and, depending on mode, may also change index and working tree;
- <code>git restore</code> replaces selected working-tree or index content from another source;
- <code>git checkout</code> historically combines branch switching and path restoration, which newer commands separate.

Reset and restore can discard uncommitted work. Before any destructive mode, inspect status and diffs, identify the exact path/reference, and create a recoverable commit or stash when appropriate. This book shows concepts, not an invitation to run destructive commands in a valuable working tree.

Reverting a merge requires choosing a mainline parent: the inverse depends on which parent represents the line being retained. Later attempts to merge the same topic can be surprising because ancestry records that it was already merged. Consult the official manual and rehearse in a disposable clone.

> **Common misconception 12.51 — “Revert returns the repository to exactly an old state.”**  
> It applies an inverse patch in current context. Intervening changes remain, conflicts can occur, and external effects—deployments, messages, migrations—are not undone by source history.

### 12.14.6 Stashes and worktrees

A **stash** records selected working/index states in commit-like objects and restores a cleaner working tree. It is useful for brief context switches, not a substitute for named, reviewed history. Stash application can conflict after the base changes; include untracked content only deliberately.

A Git **worktree** permits multiple working trees associated with one repository, often with different branches checked out. Worktrees reduce the need to stash when switching between a release repair and ongoing work. They share object storage and some repository administration; deleting directories manually can leave administrative records requiring repair.

Both mechanisms manage local workflow. Neither communicates intent to collaborators until commits and references are exchanged.

### 12.14.7 Reflogs and recovery

A **reflog** records local updates to a reference or to <code>HEAD</code>, including previous object identifiers. If a branch is reset or deleted, a recent commit may be recoverable while its object and reflog entry remain.

~~~text
git reflog
git show <candidate-object-id>
git branch recovered-work <candidate-object-id>
~~~

The safe conceptual sequence is inspect, verify, then create a new retaining reference. Reflogs are normally local, expire under configuration, and may not exist for every reference or server. Do not promise recovery based on them; commit coherent work and push authorised references.

> **Common misconception 12.52 — “Git can always recover anything.”**  
> Recovery depends on whether content was stored as an object and remains reachable through a reference, reflog, or retention window. Never-added working bytes may never have entered Git.

### 12.14.8 Automated bisection and testable history

The debugging section introduced <code>git bisect</code>. Its effectiveness depends on a history whose intermediate commits can build and on a predicate that classifies them. A **bisectable history** makes each commit coherent enough that regression tests have meaning.

If a schema change and application change must deploy together, an intermediate commit containing only half may be untestable. The solution is not arbitrary splitting; use backward-compatible steps:

1. add schema capable of serving old and new code;
2. deploy code that writes/reads compatible forms;
3. migrate existing data with verification;
4. stop using old form;
5. remove old schema after compatibility window.

Each step has a rollback and mixed-version story. This history is both deployable and diagnosable.

### 12.14.9 Tags, releases, and signatures

A lightweight tag is a reference directly to an object. An **annotated tag** normally points to a tag object containing a name, tagger, message, and target, and can carry a cryptographic signature. Release policy should specify which form is authoritative.

A signature establishes that a holder of a private key signed specified bytes. Trust additionally requires validating key ownership, key status, algorithm policy, and the relationship between signed commit/tag and built artefact. A signed tag does not prove that an uploaded wheel was built from it unless the build and provenance chain connects them.

Release names should be immutable. Moving a published version tag makes caches and users disagree about what the version means. Correct an erroneous release with a new version and explicit advisory under ordinary package practice.

### 12.14.10 Collaborative integration policy

A maintainable collaboration policy answers:

- which branches or references are protected;
- which checks and approvals are required;
- whether review authors may approve their own changes;
- whether force updates are permitted;
- merge strategy and commit-message requirements;
- how emergency changes are authorised and reviewed afterwards;
- how release tags and artefacts are produced;
- retention and audit requirements.

Automation enforces only encoded policy. An administrator bypass may be necessary during an incident, but it should be visible, narrowly authorised, and followed by retrospective verification.

> **Common misconception 12.53 — “A protected branch guarantees good code.”**  
> Protection can require checks and approvals. It cannot make weak tests discriminating, reviewers knowledgeable, credentials uncompromised, or requirements correct.
