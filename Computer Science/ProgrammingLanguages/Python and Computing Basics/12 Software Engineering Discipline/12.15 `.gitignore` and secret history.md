# 12.15 `.gitignore` and secret history

`.gitignore` prevents untracked matching paths from being considered by ordinary add operations. It does not remove files already tracked and does not erase secrets from prior commits.

Typical Python exclusions include environment directories, bytecode caches, build outputs, coverage data, tool caches, and local secret/configuration files. The exact file should follow project tools and deployment model rather than copy every global template entry.

If a secret enters Git history, deleting the current file is insufficient. Treat the secret as compromised: revoke or rotate it, then follow repository policy for history rewriting where necessary. Rewriting does not retract clones, caches, logs, or already used credentials.

### 12.15.1 Ignore rules are path-selection rules

An ignore pattern affects untracked paths considered by commands such as status and add. Rules can come from repository files, per-repository exclusions, and user-level configuration. Negation can re-include a path only under the documented traversal constraints; pattern order and directory matching matter.

Use:

~~~text
git check-ignore -v path/to/file
~~~

to inspect which rule applies to an ignored path. This is more reliable than guessing from a large template.

Repository <code>.gitignore</code> should contain project-wide generated or local-only paths. A developer’s editor backups can live in a global excludes file. Files required for a reproducible build must not be ignored merely because they are generated locally; either version their source and reproduce them or version the artefact under explicit policy.

> **Common misconception 12.54 — “Ignoring a directory makes its contents private.”**  
> Ignore rules are client-side convenience. Any process can read the local files, and explicit force-add can store them. Confidentiality requires access controls and secret-management practice.

### 12.15.2 Secret prevention and response

Secrets include passwords, private keys, bearer tokens, signing material, and connection strings containing credentials. Keep them out of source through:

- environment or secret-manager injection at runtime;
- committed example configuration containing no real secret;
- least-privilege, short-lived credentials;
- pre-commit and server-side secret scanning;
- review of generated artefacts and logs;
- separate authorised storage for development secrets.

Scanning is probabilistic. High-entropy detectors miss structured low-entropy secrets and can flag harmless test values. A test credential must be visibly non-production and unusable outside its isolated service.

If a secret is committed:

1. contain risk and rotate or revoke first;
2. determine scope, privileges, access logs, and exposure;
3. remove it from current source;
4. decide whether history rewriting is necessary;
5. coordinate rewritten references and cached copies;
6. invalidate derived credentials or sessions;
7. record the incident without reproducing the secret;
8. add preventive controls.

History rewriting changes commit identities for every descendant. Collaborators must replace or carefully rebase old clones so the secret is not reintroduced. Hosted pull requests, CI logs, package artefacts, and forks may retain copies beyond repository history.

### 12.15.3 Large and generated files

Git stores content versions efficiently when they share compressible structure, but repeated large binary artefacts can make clone and maintenance expensive. Systems such as Git LFS replace selected working paths with small pointer files while storing payloads separately. This introduces a second storage, authentication, retention, and availability dependency.

Do not commit virtual environments, caches, ordinary build directories, database dumps, or credentials. Whether to commit generated source, lock files, migrations, or documentation output is project-specific:

- commit when consumers cannot reliably regenerate it or review needs the exact form;
- omit when deterministic generation from versioned sources is established;
- never hand-edit a generated file without changing its source;
- verify generated output is current in CI.

### 12.15.4 Hooks and trust

Git hooks are programs invoked at selected client or server operations. Client hooks can format, scan, or validate before commit; server controls can enforce policy independent of a contributor’s local configuration.

Local hooks are not a security boundary because users can bypass or lack them. A repository does not ordinarily activate cloned hook scripts automatically, which avoids executing untrusted code merely by cloning. Hook-distribution tools themselves become dependencies to review.

Build scripts, test plugins, package configuration, and hooks from an untrusted repository can execute code. Inspect before running, use least-privileged environments, and do not expose unrelated credentials to arbitrary builds.

> **Common misconception 12.55 — “Pre-commit hooks enforce repository policy.”**  
> They provide fast local feedback. Authoritative enforcement belongs on controlled integration infrastructure, because local execution is voluntary and environment-dependent.
