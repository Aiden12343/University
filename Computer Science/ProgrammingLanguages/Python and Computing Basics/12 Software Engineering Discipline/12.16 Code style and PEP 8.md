# 12.16 Code style and PEP 8

**PEP 8** is the principal style guide for Python code. Style supports consistent reading, diff quality, and tool cooperation. It does not define language semantics and is not an argument against domain-appropriate exceptions.

Important principles include:

- four spaces per indentation level;
- meaningful naming conventions;
- readable line structure;
- separation of top-level definitions;
- imports organised and normally placed near the top;
- whitespace that exposes grouping;
- comparisons to `None` with `is`/`is not`;
- truth testing rather than unnecessary equality to `True`;
- consistency with the surrounding maintained project.

Automated formatters can settle presentation mechanically. Linters detect selected defects and policy violations. A formatter does not improve names, contracts, decomposition, or algorithm choice. A linter warning should be understood before suppression; a suppression should be narrow and justified.

### Worked example 12.6 — Style reveals semantics

Obscure:

```python
def f(x=[]):
    if x==None:return []
    else:x.append(1);return x
```

Formatted source remains semantically defective because the mutable default persists and `x == None` permits equality dispatch. A meaningful repair is:

```python
def append_marker(values: list[int] | None = None) -> list[int]:
    if values is None:
        values = []
    values.append(1)
    return values
```

Style made the flow inspectable, but the repair required object and identity reasoning.

### 12.16.1 Readability is an engineering property

Source code is read to predict behaviour, review change, diagnose failure, and construct new behaviour. **Readability** is the degree to which an intended reader can form an accurate mental model with bounded effort. It is not identical to visual beauty or brevity.

Readable code makes important distinctions visible:

- domain concepts have stable names;
- units and representations are explicit;
- state mutation and external effects are localised;
- ordinary and exceptional paths can be followed;
- control nesting is bounded;
- invariants are expressed near the operations that depend on them;
- interfaces expose required variation without incidental mechanism;
- similar structures mean similar things.

Empirical measurement of readability is difficult and context-dependent. Style rules serve as standardised defaults that reduce unproductive variation. They are strongest where consistency assists scanning and weakest when applied as substitutes for semantic judgement.

### 12.16.2 Naming as model construction

A name asserts a category. <code>elapsed_seconds</code> asserts duration and unit; <code>deadline</code> asserts a point against a clock; <code>user</code> may ambiguously denote an authenticated principal, database row, customer, or display profile.

Good names distinguish:

- identifier from the identified object;
- raw input from parsed value;
- current state from requested transition;
- collection from one element;
- predicate from command;
- unit and coordinate system;
- trusted from untrusted representation.

~~~python
def schedule_retry(
    request_id: str,
    attempt_count: int,
    delay_seconds: float,
) -> ScheduledRetry:
    ...
~~~

This signature is more informative than <code>retry(id, n, timeout)</code>, but it still needs contracts: whether attempt count includes the first try, which clock schedules delay, permissible range, and idempotency.

Avoid encoding mutable type information in names such as <code>customer_dict</code> when the conceptual object is a customer. Conversely, representation distinctions such as <code>payload_bytes</code> and <code>payload_text</code> can prevent encoding errors.

> **Common misconception 12.56 — “Long names are self-documenting.”**  
> Length can carry distinctions, but a long name can still assert the wrong model or repeat obvious context. Documentation includes contracts, structure, examples, and rationale—not identifier length alone.

### 12.16.3 Formatting and line structure

PEP 8 recommends a consistent indentation and layout vocabulary. Modern projects often delegate many choices to an opinionated formatter. A formatter:

- parses source;
- emits a canonical or narrowly variable layout;
- reduces review noise;
- makes formatting reproducible across editors and CI.

It does not preserve every hand-aligned visual table, and that loss is often intentional: manual alignment creates large diffs when one name grows. Formatting should be applied as a separate mechanical change when introducing it to an established repository, so semantic review is not buried.

Line length is a readability and tooling constraint, not a Python parser limit. Long URLs, generated code, string literals, tables, and mathematical expressions can justify exceptions. Configure one policy and let tools agree.

Parentheses are preferable to a backslash for most explicit line continuation because comments and editing are safer:

~~~python
accepted = (
    request.authenticated
    and request.account_id in permitted_accounts
    and not request.expired
)
~~~

The layout reveals three conditions. Whether the policy is correct still requires a decision table.

### 12.16.4 Linters and rule provenance

A **linter** performs static checks for selected suspicious or non-conforming patterns. Rules may concern:

- definite errors, such as an undefined name;
- probable errors, such as a mutable default;
- maintainability, such as excessive complexity;
- style, such as import ordering;
- security patterns, such as unsafe temporary-file use;
- project architecture, such as forbidden dependencies.

Not every diagnostic has the same epistemic status. An undefined name is usually a specification-level source error. A “too many arguments” threshold is a maintainability heuristic. A security pattern can be a real vulnerability only under particular input trust. Configure severity accordingly.

A suppression is an assertion that the rule is inapplicable at one site. Make it narrow, include the rule identifier, and explain non-obvious reasoning:

~~~python
payload = pickle.loads(trusted_fixture_bytes)  # noqa: S301
~~~

Even this comment is insufficient unless “trusted fixture” provenance is genuinely controlled. Prefer formats that do not require a hazardous primitive. Periodically review suppressions because surrounding assumptions change.

> **Common misconception 12.57 — “A clean linter run means the code follows best practice.”**  
> It means enabled rules found no reportable pattern. Disabled rules, dynamic behaviour, architecture, domain contracts, and runtime evidence lie outside that conclusion.

### 12.16.5 Complexity measures and decomposition

**Cyclomatic complexity** is a control-flow measure related to the number of linearly independent paths through a graph. Tools approximate it from source constructs. A high value suggests many decisions to understand and test, but a low value does not guarantee simplicity: a one-line regular expression or call into a complex framework can be cognitively difficult.

**Cognitive complexity** and similar measures attempt to model human comprehension by weighting nesting and flow disruption. They are heuristic and tool-specific. Use thresholds to identify review candidates, not to force mechanical extraction.

Extracting every condition into a tiny function can scatter one policy across files. Good decomposition groups a coherent rule behind a name and reduces the amount of state considered at once.

### Worked example 12.6A — Refactor a decision, preserving its table

Before:

~~~python
def can_refund(order: Order, actor: Actor, now: datetime) -> bool:
    return (
        actor.is_staff
        or (
            actor.customer_id == order.customer_id
            and order.status == Status.PAID
            and now <= order.paid_at + timedelta(days=30)
            and not order.has_chargeback
        )
    )
~~~

After:

~~~python
def is_customer_refund_window_open(
    order: Order,
    *,
    customer_id: str,
    now: datetime,
) -> bool:
    return (
        customer_id == order.customer_id
        and order.status is Status.PAID
        and now <= order.paid_at + timedelta(days=30)
        and not order.has_chargeback
    )


def can_refund(order: Order, actor: Actor, now: datetime) -> bool:
    if actor.is_staff:
        return True
    return is_customer_refund_window_open(
        order,
        customer_id=actor.customer_id,
        now=now,
    )
~~~

The helper names one policy and the outer function reveals the staff override. The refactor could accidentally change equality semantics by using <code>is</code> for an enum; that is correct only because <code>Status</code> members are singleton enum objects. Regression tests derived from the original decision table must run before and after.

### 12.16.6 Refactoring and semantic preservation

**Refactoring** is a change to internal structure intended to preserve externally observable behaviour. The boundary of “observable” must be stated. Improving query count changes performance; renaming a public symbol changes API; changing exception text may affect callers; changing object identity can affect code even if equality remains.

A safe refactoring workflow:

1. identify the behaviour boundary to preserve;
2. strengthen characterisation tests where specification is incomplete;
3. make one structural transformation;
4. run focused static and dynamic checks;
5. inspect the diff for unintended semantic changes;
6. measure relevant performance if structure affects cost.

A refactoring can expose a latent defect without creating it. Treat the observation causally: compare traces and invariants rather than reverting reflexively.

> **Common misconception 12.58 — “Refactoring means cleaning code without changing features.”**  
> The intent is behavioural preservation under a declared observation boundary. Without evidence, a large cleanup can be a high-risk semantic change wearing a reassuring label.
