# 12.17 Documentation

Documentation serves distinct audiences and timescales:

- **reference** precisely records an interface;
- **explanation** develops a mental model and reasons about design;
- **tutorial** guides a learner through a controlled first result;
- **how-to** gives steps for a specific task under stated conditions;
- architecture records explain boundaries and decisions;
- comments explain constraints, non-obvious reasons, and invariants near code.

A **docstring** is a string literal in the designated first statement position of a module, class, function, or method, available through `__doc__` and documentation tools.

```python
def withdraw(amount_pence: int) -> None:
    """Withdraw a positive amount.

    Raises:
        ValueError: If the amount is not positive or exceeds the balance.
    """
```

Docstrings should state semantic facts not already obvious from the signature: units, mutation, failure, ordering, ownership, and constraints. Comments that restate syntax become stale:

```python
count += 1  # Increment count by one.
```

A valuable comment explains *why* the update occurs or which invariant it maintains.

Examples in documentation should be tested when practical. Untested examples become plausible-looking obsolete programs.

### 12.17.1 Documentation genres answer different questions

Combining every genre into one page serves none well. Four useful categories are:

| Genre | Reader’s question | Typical structure |
|:---|:---|:---|
| tutorial | How do I learn this through a guided first experience? | controlled sequence with explanation |
| how-to guide | How do I accomplish this specific task? | goal-directed steps and conditions |
| reference | What exactly does this interface mean? | systematic, complete, precise entries |
| explanation | Why is the system designed or behaving this way? | concepts, alternatives, reasoning |

This classification is a documentation design model, not a law. A page can link genres and small projects may combine them, but the author should know which reader problem each passage addresses.

Operational runbooks are another genre: executable procedures for diagnosis, containment, recovery, and verification. A runbook must state prerequisites, authority, irreversible steps, expected output, abort conditions, and escalation. A command list without interpretation is dangerous during an incident.

### 12.17.2 API reference as a contract

For each public function, class, command, or endpoint, reference documentation should state as applicable:

- purpose and stability;
- parameters, types, units, ranges, and defaults;
- return value and ownership;
- mutation and external effects;
- exceptions or failure results;
- ordering and concurrency;
- complexity or resource bounds when contractual;
- security and confidentiality constraints;
- version introduced, deprecated, or changed;
- examples of ordinary and boundary use.

Type hints remove some repetition but not semantics. <code>timeout: float</code> does not say seconds, whether zero disables or immediately expires, whether it covers connection and response together, or which exception signals expiry.

### Worked example 12.6B — A contract-bearing docstring

~~~python
def read_prefix(
    path: Path,
    limit_bytes: int,
) -> bytes:
    """Read at most limit_bytes bytes from the start of path.

    Args:
        path: Regular file to open for binary reading. Symbolic-link handling
            follows the host platform and is not restricted by this function.
        limit_bytes: Maximum byte count. Must be non-negative.

    Returns:
        Between zero and limit_bytes bytes. An empty file returns an empty
        byte string.

    Raises:
        ValueError: If limit_bytes is negative.
        OSError: If the path cannot be opened or read.

    The function does not promise that the file remains unchanged while it is
    read. Callers requiring a stable snapshot must provide that synchronisation.
    """
    if limit_bytes < 0:
        raise ValueError("limit_bytes must be non-negative")
    with path.open("rb") as stream:
        return stream.read(limit_bytes)
~~~

The docstring identifies a security-relevant omission—symbolic-link restriction—rather than implying safety. It distinguishes byte count from character count and states concurrent mutation semantics. A project’s chosen docstring convention may format sections differently; semantic completeness matters more than one syntax.

> **Common misconception 12.59 — “Type annotations make parameter documentation redundant.”**  
> Annotations classify values and relationships. They rarely encode units, side effects, authority, ordering, error policy, or operational limitations.

### 12.17.3 Comments explain constraints and reasons

A comment should reduce the gap between code and the reasoning needed to maintain it. Valuable comments include:

- a non-obvious invariant;
- a compatibility constraint and removal condition;
- why an apparently simpler algorithm is invalid;
- provenance for a protocol constant;
- security assumptions;
- relationship to a standard or issue;
- deliberate complexity or performance trade-off.

Example:

~~~python
# The provider can commit a charge before this request times out. Reuse the
# persisted key on every retry; generating a new key can duplicate the charge.
result = gateway.charge(
    amount_pence=amount_pence,
    idempotency_key=operation.provider_key,
)
~~~

The comment explains a distributed failure mode. A comment such as “call gateway” would restate syntax.

Outdated comments are defects because readers may trust them over code. Review comment validity during changes and attach external references that are expected to remain stable.

### 12.17.4 Doctest and executable examples

Python’s <code>doctest</code> module can discover interactive-looking examples in docstrings and compare output. It is effective for small deterministic expressions:

~~~python
def slugify_words(words: list[str]) -> str:
    """Join lowercase words with hyphens.

    >>> slugify_words(["Ada", "LOVELACE"])
    'ada-lovelace'
    >>> slugify_words([])
    ''
    """
    return "-".join(word.lower() for word in words)
~~~

Exact output comparison becomes brittle for unordered representations, paths, tracebacks, floating values, timestamps, and version-specific <code>repr</code>. Doctest examples can prioritise readable narrative and delegate thorough testing to ordinary tests. If examples are copied into separate tests, establish a process that prevents divergence.

Examples must not contain real credentials or destructive commands. Use reserved domains such as <code>example.test</code> and visibly fictional values.

### 12.17.5 Architecture and decision documentation

Architecture documentation should offer several **views**, each selected for a concern:

- context: system and external actors/systems;
- container or deployment: independently running/storage units;
- component: internal responsibility boundaries;
- data: schemas, ownership, flow, retention;
- runtime: important interactions and failure paths;
- security: trust boundaries, assets, threats, controls;
- decision history: ADRs and supersession.

One giant diagram becomes stale because it cannot serve every question. Generate mechanical API/schema facts from source where possible and write human reasoning around them.

Diagrams need legends, version/context, direction, and omitted-detail statements. A box labelled “service” says little without responsibility and boundary semantics.

### 12.17.6 Documentation build and verification

Treat documentation as source:

- version it with related code where appropriate;
- review it;
- check links and code snippets;
- build it in CI;
- publish the version matching a release;
- retain old-version reference when users still operate old releases.

An example that imports the working tree while documenting the last release can silently use future behaviour. Documentation tooling should install or select the intended artefact.

Accessibility applies: meaningful headings, alternative text for informative images, sufficient contrast, keyboard navigation in generated sites, and explanations that do not depend on colour alone.

> **Common misconception 12.60 — “Documentation can be generated from source.”**  
> Tools can extract signatures, docstrings, schemas, and cross-references. They cannot infer stakeholder intent, rationale, operational procedure, examples, or which caveats readers need.
