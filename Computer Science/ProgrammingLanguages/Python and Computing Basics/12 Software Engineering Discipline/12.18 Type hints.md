# 12.18 Type hints

A **type hint** is metadata expressing intended relationships among values. Python’s runtime generally preserves annotations without automatically enforcing them. A **static type checker** analyses source without executing every path, approximating which values can flow where.

```python
from collections.abc import Iterable


def mean(values: Iterable[float]) -> float:
    collected = list(values)
    if not collected:
        raise ValueError("mean requires at least one value")
    return sum(collected) / len(collected)
```

The annotation admits any iterable of values compatible with float use. The implementation materialises because it needs length and repeated aggregate access. A more memory-efficient one-pass implementation could accept `Iterable[float]` without storage.

**Nominal typing** relates types through declarations and inheritance. **Structural typing** relates them through supported operations. `Protocol` expresses static structural interfaces.

Use unions for alternatives:

```python
def find(identifier: str) -> Account | None:
    ...
```

Callers must narrow the possibility before using account-only operations. `None` is not automatically ignored.

Generics preserve relationships:

```python
from collections.abc import Iterable
from typing import TypeVar

T = TypeVar("T")


def first(values: Iterable[T]) -> T:
    iterator = iter(values)
    try:
        return next(iterator)
    except StopIteration as error:
        raise ValueError("values must be non-empty") from error
```

The same type variable states that the result type is the produced element type, rather than losing it to `object`.


### 12.18.1 Three different meanings of type

The word **type** can refer to related but distinct things:

1. a runtime class or type object used by Python’s execution semantics;
2. a static type expression interpreted by a checker;
3. a domain category, such as AccountIdentifier, that may share a runtime representation with other categories.

For example, <code>list[int]</code> is a runtime generic-alias object when evaluated in modern Python and a static expression denoting lists whose elements are integers. CPython does not inspect every append to enforce that expression. A static checker analyses source and reports incompatible operations before execution, subject to its model.

Annotations reside in <code>__annotations__</code> under version-dependent evaluation rules. Tools may inspect them at runtime, but library code should use documented facilities such as <code>typing.get_type_hints</code> rather than assuming every annotation is already an object. Forward references, deferred evaluation policy, imports, and Python version affect runtime introspection. Static meaning is governed by the typing specification and checker behaviour, not solely by the runtime dictionary.

> **Common misconception 12.61 — “Python becomes statically typed when annotations are added.”**  
> Python’s runtime semantics remain dynamic unless explicit runtime validation is introduced. An external checker supplies a separate analysis whose guarantees depend on coverage, configuration, and soundness limits.

### 12.18.2 Gradual typing and the boundary of precision

Python uses **gradual typing**: annotated and unannotated code can coexist, and precision can be introduced incrementally. This supports adoption but creates boundaries at which information may be lost.

The special static type <code>Any</code> is dynamically permissive. Operations on an <code>Any</code> value are largely accepted, and results often remain <code>Any</code>. It therefore acts as both top and bottom in many compatibility rules, allowing values to flow through checks unsafely.

<code>object</code> is different. Every ordinary Python value is compatible with <code>object</code>, but a value known only as <code>object</code> supports only operations guaranteed by that type until narrowed:

~~~python
def length_if_text(value: object) -> int | None:
    if isinstance(value, str):
        return len(value)
    return None
~~~

The <code>isinstance</code> branch narrows <code>value</code> to <code>str</code>. Had the parameter been <code>Any</code>, the checker would permit <code>len(value)</code> even without proof. Use <code>object</code> to represent an unknown value that must be validated; use <code>Any</code> only when deliberately crossing a dynamic boundary.

At the opposite extreme, <code>Never</code> denotes no possible values in the static model. It can describe functions that do not return normally or prove exhaustiveness. Checker support and import location are version-dependent.

### Worked example 12.6C — Validate dynamic JSON into a precise model

~~~python
from dataclasses import dataclass
from typing import Any


@dataclass(frozen=True)
class ImportRequest:
    account_id: str
    amounts_pence: tuple[int, ...]


class SchemaError(ValueError):
    pass


def parse_import_request(value: Any) -> ImportRequest:
    if not isinstance(value, dict):
        raise SchemaError("request must be an object")

    account_id = value.get("account_id")
    amounts = value.get("amounts_pence")

    if not isinstance(account_id, str) or not account_id:
        raise SchemaError("account_id must be non-empty text")
    if not isinstance(amounts, list):
        raise SchemaError("amounts_pence must be an array")
    if not all(
        isinstance(amount, int) and not isinstance(amount, bool)
        for amount in amounts
    ):
        raise SchemaError("every amount must be an integer")

    return ImportRequest(account_id, tuple(amounts))
~~~

The dynamic value is confined to the boundary. After validation, internal code receives a frozen record with a precise tuple. The checker cannot prove that arbitrary JSON conforms; runtime validation and static analysis cooperate.

For very large arrays, <code>all</code> followed by tuple construction traverses twice. A one-pass parser can validate while appending to a local list, then freeze it. That is a performance refinement whose correctness needs separate tests.

> **Common misconception 12.62 — “Replacing Any with object fixes the type problem.”**  
> It makes unsafe operations visible to the checker. The programmer must still narrow or parse the value according to a real runtime contract.

### 12.18.3 Union types and narrowing

A union <code>A | B</code> denotes a value compatible with either alternative. Narrowing uses control-flow evidence:

~~~python
def display_name(account: Account | None) -> str:
    if account is None:
        return "anonymous"
    return account.display_name
~~~

The checker understands that after the guard, <code>account</code> cannot be <code>None</code>. Narrowing mechanisms include identity checks, <code>isinstance</code>, discriminant literals, pattern matching, and checker-specific inference.

A **discriminated union** gives each variant a literal tag:

~~~python
from dataclasses import dataclass
from typing import Literal


@dataclass(frozen=True)
class Accepted:
    kind: Literal["accepted"]
    identifier: str


@dataclass(frozen=True)
class Rejected:
    kind: Literal["rejected"]
    reason: str


type SubmissionResult = Accepted | Rejected


def describe(result: SubmissionResult) -> str:
    match result:
        case Accepted(identifier=identifier):
            return f"accepted as {identifier}"
        case Rejected(reason=reason):
            return f"rejected: {reason}"
~~~

The <code>type</code> statement and generic syntax introduced in Python 3.12 create a type alias; they do not create a runtime subclass enforcing values. Checkers differ in exhaustiveness diagnostics. A final assertion helper accepting <code>Never</code> can make an omitted variant reportable, but runtime defence may still be required at untrusted boundaries.

<code>Literal["accepted"]</code> expresses one exact static value. It does not cause an ordinary string read from JSON to acquire that type without validation or inference.

### 12.18.4 Type aliases, NewType, and domain distinction

A **type alias** gives another name to a type expression:

~~~python
type AccountId = str
type BalanceTable = dict[AccountId, int]
~~~

<code>AccountId</code> and <code>str</code> remain statically interchangeable because the alias is transparent. When two concepts share a representation but must not mix, <code>NewType</code> creates a distinct static type with an identity-like runtime constructor:

~~~python
from typing import NewType


AccountId = NewType("AccountId", str)
RequestId = NewType("RequestId", str)


def load_account(identifier: AccountId) -> Account:
    ...


account_id = AccountId("A-7")
request_id = RequestId("R-4")
~~~

A checker rejects passing <code>request_id</code> to <code>load_account</code>. At runtime these values are still strings and <code>isinstance(value, AccountId)</code> is not a valid nominal check. If runtime methods, validation, or invariant-bearing construction are needed, define a class or frozen dataclass.

### 12.18.5 Typed mappings and structural records

<code>TypedDict</code> describes dictionary-shaped records for static checking, including required and optional keys:

~~~python
from typing import NotRequired, TypedDict


class AccountPayload(TypedDict):
    identifier: str
    balance_pence: int
    note: NotRequired[str]
~~~

At runtime an <code>AccountPayload</code> value is an ordinary dictionary. Construction does not validate external JSON. Typed dictionaries are useful at serialisation and interoperability boundaries where mapping shape is intrinsic. For rich behaviour and invariants, a class or dataclass is often clearer.

Width and mutability make compatibility subtle. A mapping with extra fields can sometimes be used where fewer fields are read, but writable fields and deletion permissions constrain substitutability. Follow the typing specification rather than assuming structural records behave like immutable mathematical records.

> **Common misconception 12.63 — “TypedDict creates a typed dictionary class.”**  
> It supplies a static structural description. Runtime values are dictionaries unless another validation system is deliberately used.

### 12.18.6 Generic functions and classes

A **generic** definition expresses relationships while abstracting over one or more types. Python 3.12’s parameter syntax makes the variable local to the definition:

~~~python
from collections.abc import Sequence


def first_or[T](values: Sequence[T], default: T) -> T:
    if values:
        return values[0]
    return default
~~~

The repeated <code>T</code> relates sequence elements, default, and result. Replacing it with <code>object</code> would lose that relation:

~~~python
result = first_or(["a", "b"], "none")  # Inferred as str.
~~~

A generic class:

~~~python
from dataclasses import dataclass


@dataclass
class Cell[T]:
    value: T

    def replace(self, value: T) -> None:
        self.value = value
~~~

<code>Cell[int]</code> and <code>Cell[str]</code> share one runtime class in ordinary implementation terms but receive different static specialisations. Generic parameters can have bounds or constraints when operations require more than arbitrary <code>object</code>.

The older <code>TypeVar</code> syntax remains important for supported Python versions before 3.12 and for tools not yet implementing every new form. A project should declare its minimum Python and checker versions.

### 12.18.7 Bounds, constraints, and overloads

A bounded type variable permits any subtype of a bound and preserves the specific input type. A constrained variable selects among enumerated alternatives. The distinction affects inference.

An **overload** describes multiple call signatures for one runtime implementation:

~~~python
from typing import Literal, overload


@overload
def decode(data: bytes, *, as_text: Literal[False] = False) -> bytes: ...


@overload
def decode(data: bytes, *, as_text: Literal[True]) -> str: ...


def decode(data: bytes, *, as_text: bool = False) -> bytes | str:
    plain = decompress(data)
    if as_text:
        return plain.decode("utf-8")
    return plain
~~~

The overloads relate a literal argument to result type. They have no independent runtime implementation; the final function executes. The implementation must accept every overload and return accordingly. Tests must still establish decompression and decoding behaviour.

Too many overloads can signal an interface whose behaviour depends on hidden combinations. Separate methods or a generic protocol may be clearer.

### 12.18.8 Callable types, ParamSpec, and decorators

<code>Callable[[A, B], R]</code> describes positional parameter types and a result but cannot express every keyword, overload, or parameter-kind relation. A callback <code>Protocol</code> can name a precise <code>__call__</code> signature.

Decorators often preserve an arbitrary callable’s parameters. <code>ParamSpec</code> captures a parameter specification and a result type variable captures its return:

~~~python
from collections.abc import Callable
from functools import wraps
from typing import ParamSpec, TypeVar


P = ParamSpec("P")
R = TypeVar("R")


def traced(function: Callable[P, R]) -> Callable[P, R]:
    @wraps(function)
    def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        logger.debug(
            "call_started",
            extra={"function": function.__qualname__},
        )
        return function(*args, **kwargs)

    return wrapper
~~~

Static preservation does not make the decorator semantically transparent. It adds logging, cost, and possible confidentiality exposure. <code>wraps</code> copies selected metadata and establishes <code>__wrapped__</code>; it does not make object identity equal.

### 12.18.9 Protocols and structural subtyping

A <code>Protocol</code> defines required operations for static structural compatibility. Implementing classes need not inherit from it:

~~~python
from typing import Protocol


class ByteReader(Protocol):
    def read(self, size: int = -1) -> bytes: ...


def read_header(stream: ByteReader) -> bytes:
    header = stream.read(8)
    if len(header) != 8:
        raise EOFError("incomplete header")
    return header
~~~

Any statically compatible class can be supplied. The protocol should be as small as the client’s need, avoiding coupling to a concrete file class.

Protocols can contain writable attributes, properties, methods, and generic parameters. Mutation affects variance and safety. <code>@runtime_checkable</code> permits limited <code>isinstance</code> checks against member presence, but runtime checks do not validate full signatures or type annotations. Do not mistake them for schema validation.

> **Common misconception 12.64 — “Protocols formalise duck typing at runtime.”**  
> Their principal role is static structural checking. Optional runtime checks are shallow and obey separate documented rules.

### 12.18.10 Self types and fluent interfaces

The special type <code>Self</code> expresses that a result has the same most-specific class as the receiver:

~~~python
from typing import Self


class Query:
    def limit(self, count: int) -> Self:
        if count < 0:
            raise ValueError("limit cannot be negative")
        self._limit = count
        return self
~~~

A subclass call can remain typed as the subclass. <code>Self</code> is appropriate only when implementations return a compatible instance of their actual class. A factory that always returns the base class should annotate that base class instead.

Fluent mutation remains mutation. Returning <code>self</code> can make aliasing and partial configuration less visible; an immutable builder returning new values may offer clearer semantics.

### 12.18.11 Recursive and recursive-looking types

Data structures can refer to themselves:

~~~python
from dataclasses import dataclass


@dataclass(frozen=True)
class Directory:
    name: str
    children: tuple["Directory", ...] = ()
~~~

The quoted reference is a forward reference under relevant runtime evaluation behaviour. Static checkers resolve it from scope. Recursive aliases can describe JSON-like structures, but unrestricted recursion can make error messages and narrowing difficult.

A common alias:

~~~python
type JsonValue = (
    None
    | bool
    | int
    | float
    | str
    | list["JsonValue"]
    | dict[str, "JsonValue"]
)
~~~

This models parsed JSON-like Python values but is not identical to the JSON standard: non-finite floats and arbitrary-size integer interoperability need runtime policy. Types are approximations of permitted structure, not the entire serialisation contract.

### 12.18.12 Types and exceptions

Annotations describe normal returns but Python’s ordinary function type does not enumerate checked exceptions. A callable annotated <code>-> Account</code> can still raise <code>OSError</code>, <code>ValueError</code>, or terminate. Document public failure policy and test it.

Some designs represent expected domain alternatives as a union, reserving exceptions for unexpected or boundary failures:

~~~python
@dataclass(frozen=True)
class Found:
    account: Account


@dataclass(frozen=True)
class Missing:
    identifier: AccountId


type LookupResult = Found | Missing
~~~

This makes callers handle absence through narrowing, but it can create verbose wrappers. <code>Account | None</code> may be sufficient when one absence category exists. Type design should expose distinctions consumers must act upon.

> **Common misconception 12.65 — “If the type checker accepts a function, every return path has the declared runtime type.”**  
> The conclusion is bounded by the checker’s soundness, typed dependencies, suppressions, dynamic operations, and configuration. Exceptions and non-termination are also possible.
