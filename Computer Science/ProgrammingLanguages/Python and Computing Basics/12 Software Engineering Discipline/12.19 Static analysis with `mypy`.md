# 12.19 Static analysis with `mypy`

`mypy` is a static type checker for Python. Under configured strictness it can detect missing annotations, incompatible assignments, impossible member access, unchecked `None`, inconsistent overrides, and other flow errors.

Example defect:

```python
def label(account: Account | None) -> str:
    return account.name
```

A checker reports that `None` has no `name`. Repair by handling the state:

```python
def label(account: Account | None) -> str:
    if account is None:
        return "unknown"
    return account.name
```

The branch narrows the type and, more importantly, forces a domain policy for absence.

Run through the selected environment:

```text
python -m mypy src tests
```

Static typing is deliberately unsound in some practical respects and interacts with untyped code, `Any`, dynamic imports, decorators, mutation, variance, and reflection. A clean report is evidence under the checker version and configuration, not a proof of runtime correctness.

`Any` is an escape from type checking that propagates permissiveness. Use it at truly dynamic boundaries, validate, and convert into precise internal types. Do not use `Any` merely to silence a misunderstanding.

### 12.19.1 Static analysis is an abstract execution

A static analyser computes an approximation of possible program behaviours without running every concrete input. It represents sets of values and control states abstractly, propagates them through source, and emits a diagnostic when an operation is inconsistent with the model.

Exact prediction of arbitrary program behaviour is impossible in general. Useful analysers therefore trade:

- **soundness**: whether all behaviours of interest are conservatively included;
- **completeness**: whether every reported issue corresponds to a real defect;
- precision;
- termination;
- performance;
- compatibility with dynamic idioms.

Mypy is intentionally practical rather than a proof system for all Python execution. Untyped functions, <code>Any</code>, unchecked external data, reflection, native extensions, monkeypatching, and unsound library stubs create escape routes. The relevant goal is to reduce defect classes and make interfaces explicit, while retaining runtime tests and validation.

### 12.19.2 Configuration defines the claim

A statement such as “mypy passes” is incomplete without:

- mypy version;
- Python language target;
- modules/files included and excluded;
- import-following policy;
- enabled strictness and optional error codes;
- per-module overrides;
- plugin set;
- stub/package versions;
- cache assumptions if relevant.

Illustrative project configuration:

~~~toml
[tool.mypy]
python_version = "3.12"
files = ["src", "tests"]
strict = true
warn_unreachable = true
show_error_codes = true
pretty = true

[[tool.mypy.overrides]]
module = ["untyped_legacy.*"]
disallow_untyped_defs = false
~~~

The override acknowledges a migration boundary. It should be narrowed by module and tracked; a global relaxation lets new untyped code spread. Exact option names and their membership in <code>strict</code> are tool-version facts, so the checked-in configuration and official manual take precedence over this illustration.

Run analysis from the same declared environment as dependencies. A globally installed checker may see different stubs and Python target:

~~~text
python -m mypy
~~~

> **Common misconception 12.66 — “Strict mode is one timeless guarantee.”**  
> It is a versioned bundle of checker options plus project-specific scope. Record the effective configuration; new releases can add diagnostics or change inference.

### 12.19.3 Revealed types, casts, and assertions

Mypy’s <code>reveal_type</code> is a diagnostic form recognised during checking:

~~~python
def process(value: str | bytes) -> int:
    if isinstance(value, str):
        reveal_type(value)  # Revealed as str by the checker.
        return len(value.encode("utf-8"))
    reveal_type(value)  # Revealed as bytes.
    return len(value)
~~~

Depending on Python/runtime context, leaving diagnostic forms in executable code can have runtime consequences; use them temporarily or through documented typing facilities.

<code>cast(Target, value)</code> tells the checker to treat a value as <code>Target</code>. It returns the value unchanged at runtime and performs no validation:

~~~python
from typing import cast


account = cast(Account, cache.get(key))
~~~

This can silence a genuine <code>None</code> defect. Prefer a runtime check or redesign the cache API. A cast is justified when the programmer possesses evidence the checker cannot express; document that evidence near the cast.

An exhaustiveness helper:

~~~python
from typing import Never, assert_never


def outcome_code(result: SubmissionResult) -> int:
    match result:
        case Accepted():
            return 0
        case Rejected():
            return 1
        case unreachable:
            assert_never(unreachable)
~~~

If a new statically known variant is added, a capable checker reports that the final value is not <code>Never</code>. At runtime <code>assert_never</code> also raises if reached under the standard library’s implementation contract.

### 12.19.4 Error suppression is local unsoundness

A line-specific ignore typically has the form:

~~~python
legacy_value = plugin.load()  # type: ignore[no-untyped-call]
~~~

The error code documents which diagnostic is suppressed. The suppression should answer:

- why the analyser cannot prove safety;
- what runtime validation or test supplies evidence;
- who owns removal;
- what version or upstream fix changes the condition.

Warnings for unused ignores prevent obsolete suppressions from masking future errors. Never use a file-wide ignore to make an unfamiliar error disappear without studying the resulting unchecked surface.

Generated code may require configured exclusions or generated stubs, but its boundary still needs runtime and integration evidence.

### 12.19.5 Stubs and typed distributions

A **stub file**, with suffix <code>.pyi</code>, declares static interfaces without ordinary runtime implementations. Stub bodies commonly use ellipses. A stub can accompany a library, reside in a separate stub distribution, or be supplied by the checker ecosystem.

~~~python
class Client:
    def __init__(self, endpoint: str, *, timeout: float = ...) -> None: ...
    def fetch(self, identifier: str) -> bytes: ...
~~~

If the implementation accepts <code>timeout=None</code> but the stub does not, correctly working caller code can be rejected. If the stub claims <code>fetch</code> always returns bytes while runtime can return <code>None</code>, checked code can still fail. Stub accuracy is a maintained compatibility obligation.

PEP 561 defines mechanisms by which distributions advertise inline typing information, including a <code>py.typed</code> marker, and how type checkers resolve stub packages. Shipping annotations in source is not enough if consumers’ tools cannot discover the intended typed package under the relevant rules.

Test public stubs against runtime signatures with specialised tools where appropriate, and include representative downstream type-check cases.

### 12.19.6 Incremental adoption

For an untyped codebase, adding <code>Any</code> everywhere satisfies annotation-count metrics while providing little protection. Adopt types along dependency and trust boundaries:

1. configure a reproducible checker baseline;
2. type a coherent leaf module or domain model;
3. replace dynamic input with parsing at its boundary;
4. expose precise public interfaces;
5. prevent new untyped definitions in migrated modules;
6. ratchet diagnostics rather than accepting a permanent broad ignore list;
7. measure <code>Any</code> ingress and propagation.

A **type-coverage** percentage needs interpretation. Annotated declarations can still contain <code>Any</code>, wrong stubs, or unsound casts. Use it to monitor migration, not to claim correctness.

### 12.19.7 Checker disagreement and specification

Different checkers can infer differently while conforming to much of the shared typing specification. Some behaviour is intentionally checker-specific or evolving. A library intended for broad typed use should test against chosen supported checkers or state one normative target.

When a checker rejects code:

1. determine whether the runtime behaviour is valid;
2. determine whether the annotation expresses the intended contract;
3. consult the typing specification and tool documentation;
4. minimise a suspected checker defect;
5. redesign a needlessly dynamic interface where that improves the program;
6. otherwise use the narrowest justified suppression.

Do not distort a clear runtime design solely to satisfy an analyser’s incidental limitation; equally, do not dismiss a diagnostic merely because Python executes the happy case.

> **Common misconception 12.67 — “A type error is either definitely a runtime bug or merely tool noise.”**  
> It can reveal a real path, a contract mismatch, an imprecise stub, unsupported dynamic design, or analyser limitation. Classification requires reasoning and evidence.
