# 12.2 Requirements and acceptance criteria

A **requirement** states a capability, property, or constraint the system must satisfy. A **functional requirement** concerns behaviour or results. A **quality attribute** concerns properties such as reliability, performance, security, usability, maintainability, or portability. The phrase “non-functional requirement” is common but can misleadingly suggest optionality; quality attributes are often decisive.

An **acceptance criterion** is an observable condition by which a stakeholder can judge whether a requirement is met. “The service should be fast” is not testable. “For payloads of at most 10,000 valid records, the 95th percentile response latency is below 200 ms under the stated hardware, concurrency, warm-up, and measurement procedure” identifies a measure and conditions.

Requirements must identify:

- actor or caller;
- input and preconditions;
- behaviour and result;
- failure policy;
- relevant state changes;
- quantitative constraints;
- authority and trust boundaries;
- evidence required for acceptance.

### Worked example 12.1 — Refine “save a report”

Vague: “The user can save a report.”

Refined:

> Given a validated report and a user-selected destination within an authorised directory, the application writes a UTF-8 JSON representation conforming to schema version 2. It must not replace an existing file unless the user selected overwrite. A successful status is returned only after the complete replacement is visible under the filesystem atomic-replacement contract. On validation, permission, capacity, or I/O failure, the prior destination remains readable and unchanged where the platform’s stated guarantees permit; the application records a diagnostic without report content classified as confidential.

The refined form reveals implementation and test questions: validation timing, encoding, schema, authorisation, overwrite policy, atomicity, durability, and redaction.

### 12.2.1 Software as a maintained socio-technical system

A program can be studied as a mathematical object, a sequence of instructions, or a collection of Python objects. A maintained software product must also be studied as a **socio-technical system**: a system whose behaviour arises from software, hardware, people, institutions, procedures, incentives, and environmental conditions together. This term does not imply that technical facts are subjective. Rather, it identifies additional causal variables. A perfectly implemented access-control rule can still be wrong because the organisation assigned the wrong role; a correct recovery mechanism can still fail operationally because no one rehearsed restoration; a precisely specified interface can still harm users because the specification omitted an affected population.

Software engineering therefore manages at least four coupled descriptions:

1. the **problem model**, describing the relevant part of the world and the goals of affected people;
2. the **requirements model**, describing externally required behaviour and constraints;
3. the **design model**, describing responsibilities, boundaries, state, and permitted dependencies;
4. the **implementation model**, consisting of executable source, configuration, data definitions, and deployment artefacts.

The descriptions must correspond, but they are not identical. A customer has an account in the problem model; an account may be represented by several database rows, Python objects, cached projections, and audit records in the implementation model. Treating one representation as though it were the real-world entity produces errors when identities merge, legal status changes, or cached data becomes stale.

**Verification** asks whether an artefact satisfies its stated specification: *did we build the specified thing correctly?* **Validation** asks whether the specification and resulting system address the actual need: *did we specify and build the right thing?* The questions overlap in practice but expose different failure modes. An implementation may be verified against a requirement that itself fails validation.

> **Common misconception 12.1 — “Software engineering is programming plus paperwork.”**  
> Engineering artefacts are instruments for controlling consequences: a requirement selects behaviour, a test challenges a claim, a version record makes change attributable, and an operational procedure governs failure. An artefact that informs no decision is bureaucracy; the existence of bad artefacts does not make the underlying control problem disappear.

### 12.2.2 Lifecycles, feedback, and the cost of delayed information

A **software lifecycle** is the sequence of activities through which software is conceived, specified, designed, implemented, evaluated, released, operated, changed, and retired. A lifecycle need not be a one-way “waterfall”. Even a formally staged safety project contains feedback, while an iterative project still performs specification, design, verification, and operation. The relevant engineering question is not which slogan names the process, but when information becomes available and how cheaply a decision can then change.

Consider an import format whose identifier is assumed to be an integer. During requirements analysis, changing the domain to an opaque string may alter one sentence. After implementation it may alter types, parser code, tests, and database schema. After public release it may require a data migration and compatibility period. The **cost of change** rises when assumptions become embedded in more artefacts and external dependencies. Early feedback is valuable because it invalidates assumptions before that propagation, not because every decision must be frozen early.

A short iteration is useful only when it returns relevant evidence. Releasing an uninstrumented feature to users can produce less actionable information than running a carefully designed prototype with ten representative cases. Conversely, months of internal refinement cannot validate an interaction that depends on actual working practice. Feedback frequency, fidelity, and risk must be selected together.

> **Common misconception 12.2 — “Iterative development means requirements are unnecessary.”**  
> Iteration makes requirements revisable; it does not remove the need to state what an increment is intended to accomplish. Without an explicit claim, feedback cannot distinguish a failed implementation from a changed goal.

### 12.2.3 Stakeholders, interests, and authority

A **stakeholder** is a person, group, or institution that affects, is affected by, or has legitimate authority over a system. Users are stakeholders, but so are operators, maintainers, auditors, support staff, data subjects, purchasers, regulators, and people exposed to externalities. Their interests can conflict. A purchaser may prefer exhaustive telemetry; data subjects may require minimisation; operators may prefer uniformity; specialist users may require configurability.

A requirements record should distinguish:

- the source of a claim;
- the person authorised to accept or change it;
- the population affected by it;
- the evidence on which it rests;
- its priority and rationale;
- dependencies and conflicts;
- the consequences of omission or failure.

Authority is domain-specific. A product owner may prioritise features but cannot waive a statutory obligation. A security team may define authentication controls but cannot alone determine whether a clinical workflow is medically valid. “The stakeholder asked for it” is therefore incomplete unless the stakeholder and scope of authority are identified.

Ethical analysis is not reducible to legal compliance. Law supplies mandatory constraints within jurisdictions; engineering judgement must also consider foreseeable harm, unequal error distribution, accessibility, deceptive interaction, environmental cost, and the ease with which a feature can be repurposed. These are substantive judgements and should be labelled as such rather than disguised as purely technical necessities.

### 12.2.4 Requirements as claims over observable traces

An execution can be viewed as a **trace**: an ordered record of relevant inputs, state transitions, outputs, and interactions. A behavioural requirement denotes which traces are permitted, required, or prohibited. This mental model clarifies several forms:

- a **safety property** says that an undesirable event never occurs, such as “an unauthorised caller never receives another customer’s report”;
- a **liveness property** says that a desirable event eventually occurs under stated assumptions, such as “every accepted job eventually reaches succeeded or failed”;
- an **invariant** is a property intended to hold in every relevant reachable state, such as “the sum of posted debit and credit amounts is zero”;
- a **precondition** is a condition required before an operation;
- a **postcondition** is a condition guaranteed after normal completion when its preconditions held;
- a **failure guarantee** states what remains true when an operation does not complete normally.

The terms “always” and “eventually” require boundaries. Does “eventually” permit a year? Does “always” include recovery after power loss? A requirement should state its operating assumptions, observation point, and time model.

### Worked example 12.1A — Turn a policy into contracts

Suppose the policy is: “Transfers must not overdraw an account.” A first executable domain model might be:

~~~python
from dataclasses import dataclass


class InsufficientFundsError(ValueError):
    """Raised when a debit would violate the non-negative-balance rule."""


@dataclass
class Account:
    identifier: str
    balance_pence: int

    def __post_init__(self) -> None:
        if self.balance_pence < 0:
            raise ValueError("an account balance cannot start below zero")

    def debit(self, amount_pence: int) -> None:
        if amount_pence <= 0:
            raise ValueError("a debit amount must be positive")
        if amount_pence > self.balance_pence:
            raise InsufficientFundsError(self.identifier)
        self.balance_pence -= amount_pence
~~~

Line by line, the class states a representation and its local contracts:

- the two annotated attributes define the state represented by each instance;
- <code>__post_init__</code> rejects construction that violates the class invariant;
- <code>debit</code> first enforces the operation’s positive-amount precondition;
- the second guard enforces the no-overdraft policy;
- mutation occurs only after both guards, so either anticipated validation failure leaves the balance unchanged.

This implementation does **not** yet satisfy a complete transfer requirement. It does not credit another account, coordinate persistence, prevent concurrent lost updates, establish idempotency after a retry, or record an audit event. The example illustrates a local contract, not a banking system.

For a transfer operation, a more complete contract could state:

| Dimension | Required claim |
|:---|:---|
| Preconditions | distinct existing accounts; positive integer amount; authenticated principal authorised for source |
| Success | exactly one debit and one credit of equal amount; durable transfer identifier returned |
| Domain failure | no balance changes; typed reason returned |
| Retry | repeated request with the same idempotency key has no additional monetary effect |
| Concurrency | accepted transfers are equivalent to some serial order under the stated isolation model |
| Audit | immutable event records actor, request identifier, accounts, amount, outcome, and trusted time |
| Confidentiality | response and diagnostics expose only authorised fields |

The table is a **contract matrix**: a compact mapping from concern to observable claim. It exposes omissions before they become distributed defects.

> **Common misconception 12.3 — “A function signature is its contract.”**  
> A signature constrains call shape and, with annotations, intended value classes. It rarely states units, permitted ranges, mutation, persistence, ordering, authorisation, failure atomicity, timing, or retry semantics. Those properties remain part of the contract whether documented or accidental.

### 12.2.5 Functional requirements, quality attributes, and constraints

A functional requirement identifies an effect: “the system exports selected transactions as CSV.” A quality attribute modifies the conditions or quality of effects: “the export of one million transactions completes within 60 seconds without exceeding 512 MiB of resident memory.” A **constraint** restricts the solution space: “the export must use the regulator’s schema version 4” or “data must remain in the approved region.”

Quality attributes often conflict. Redundant replication may increase availability while increasing cost and the surface over which confidential data exists. Stronger synchronisation may improve consistency while increasing latency or reducing availability during a partition. Engineering does not maximise every attribute independently; it chooses acceptable trade-offs under priorities and hazards.

ISO/IEC 25010 uses a quality model to organise characteristics such as functional suitability, performance efficiency, compatibility, interaction capability, reliability, security, maintainability, flexibility, and safety. Such taxonomies are checklists for questions, not universal scoring formulas. A low-latency trading system and an archival converter assign radically different weights and measures.

For each important quality attribute, specify a **stimulus-response scenario**:

1. source of stimulus;
2. stimulus;
3. environment in which it occurs;
4. affected artefact;
5. required response;
6. measurable response criterion.

Example: “During ordinary production load, when an authenticated user requests a cached report no older than five minutes, the API returns a complete representation within 300 ms at the 99th percentile over rolling ten-minute windows, measured at the service boundary, with an error rate below 0.1%.” This still requires traffic distribution, clock, exclusion, and sampling rules, but it can be challenged empirically.

> **Common misconception 12.4 — “Non-functional requirements can be added after the features work.”**  
> A quality attribute can determine architecture. Retrofitting auditability, bounded memory, geographical residency, or crash consistency may require changing data models and boundaries rather than adding a final wrapper.

### 12.2.6 Elicitation, ambiguity, and operational definitions

**Requirements elicitation** is the systematic discovery of needs, constraints, assumptions, and conflicts through observation, interviews, document analysis, workshops, prototypes, incident study, and examination of existing systems. “Elicitation” does not mean requirements already exist fully formed in a stakeholder’s mind. People know parts of their work tacitly, disagree about exceptional cases, and adapt around defects.

Ambiguity occurs when plausible readers can assign different meanings. Terms especially likely to hide ambiguity include *fast*, *secure*, *user-friendly*, *real time*, *duplicate*, *available*, *valid*, *normal*, and *support*. Replace them with **operational definitions**: definitions stated in terms of observable procedures or measures.

Consider “remove duplicate customers”. At least five relations might be intended:

- equal customer identifiers;
- equal normalised email addresses;
- records referring to the same legal person;
- rows identical in all exported fields;
- records judged sufficiently similar by a probabilistic model.

The choice changes error costs. Incorrectly merging two people is not the symmetric opposite of retaining two records for one person. A requirement must identify the equivalence relation, confidence policy, review mechanism, reversibility, and provenance.

### Worked example 12.1B — An ambiguity review

Original story:

> As an analyst, I want recent failed payments so that I can investigate.

Questions and resulting decisions:

| Ambiguous phrase | Question | Decision recorded |
|:---|:---|:---|
| analyst | Which role and authorisation scope? | fraud-analyst role; assigned regions only |
| recent | Event time or ingestion time; what interval? | event time in preceding 72 hours |
| failed | Which terminal and transient states? | terminal processor rejection; exclude pending timeout |
| payments | Attempts or business payment identities? | attempts, grouped under payment identity |
| investigate | Which fields and actions are required? | listed fields; link to separately authorised case creation |
| time | Which clock and timezone? | stored UTC instant; display in analyst preference |
| completeness | What about delayed events? | watermark displayed; refresh incorporates late arrivals |

The revised acceptance cases should include a payment at each temporal boundary, a delayed event, a cross-region record, repeated attempts for one identity, and an unauthorised caller. The table does not merely improve prose; it selects concrete tests and data-model fields.

> **Common misconception 12.5 — “A user story is a complete requirement.”**  
> The common role–capability–benefit sentence records intent compactly. It usually omits exceptional behaviour, quantities, permissions, state transitions, quality attributes, and acceptance evidence.

### 12.2.7 Acceptance criteria and executable examples

Acceptance criteria should be precise without prematurely dictating implementation. **Given–when–then** notation is one useful structure:

- **Given** establishes relevant initial state;
- **when** names a stimulus;
- **then** states an observable result.

The notation has no magical semantics. A scenario can remain vague (“Given the system is ready”) or overfit the interface (“When button coordinates 418,92 are clicked”). State the domain condition and observable result at the most stable boundary.

For the percentage parser:

~~~text
Given the input text is "100"
When it is parsed as a percentage
Then the integer result is 100

Given the input text is "101"
When it is parsed as a percentage
Then parsing fails with the range-error category
And no destination record is created
~~~

The second example includes an effect outside the parser because acceptance concerns the use case. A focused parser unit test and a broader workflow test can derive from the same criterion while observing different boundaries.

Acceptance examples cannot enumerate all behaviour. They are selected witnesses to a more general rule. Record the rule as well as its examples so implementers do not infer that unlisted values are unconstrained.

### 12.2.8 Traceability and the claim–evidence graph

**Traceability** is the ability to follow a relationship among needs, requirements, design decisions, implementation units, tests, releases, and observed outcomes. A **traceability matrix** is one representation, but a graph is more accurate because relationships are many-to-many.

For each high-risk requirement, a useful record links:

~~~text
stakeholder need
    -> requirement and rationale
    -> hazard or failure mode
    -> design control
    -> implementation change
    -> verification cases
    -> build artefact
    -> operational measure
~~~

Traceability serves both directions. Forward traversal asks whether a requirement was implemented and evaluated. Backward traversal asks why a line, dependency, or test exists. Orphan requirements lack implementation evidence; orphan code lacks a justified need; orphan tests may preserve obsolete behaviour.

Trace links need not be a bureaucratic identifier on every line. A small project can use issue references in commit messages, named test modules, and release notes. A regulated or safety-critical project may require controlled identifiers, review signatures, and formal coverage records. The mechanism should be proportional to the cost of a lost relationship.

> **Common misconception 12.6 — “Traceability means every requirement has one test.”**  
> One requirement can need many tests at several levels, and one test can supply evidence for several interacting requirements. Traceability records justified relationships; it is not a forced one-to-one table.

### 12.2.9 Risk, hazards, and failure modes

**Risk** combines uncertainty about an event with the severity of its consequences. Multiplying an estimated probability by a monetary loss is one model, not the definition of risk and not always appropriate. Rare catastrophic failures, poorly known probabilities, irreversible harm, and unequal distribution require explicit treatment.

A **hazard** is a condition with the potential to contribute to harm. A **failure mode** is a way in which a component or process can fail to provide its required function. A **threat** is a potential cause of an unwanted incident, especially in security analysis. These terms overlap but direct attention differently.

A lightweight risk register can contain:

| Field | Purpose |
|:---|:---|
| scenario | causal sequence and affected asset/person |
| initiating conditions | assumptions needed for the scenario |
| likelihood confidence | estimate and uncertainty source |
| impact | safety, financial, legal, operational, or social consequence |
| prevention | controls reducing occurrence |
| detection | signals revealing occurrence |
| response | containment and recovery |
| residual risk | remaining exposure and acceptance authority |
| evidence | test, analysis, drill, or operational measure |

Test effort should follow risk, not merely line count. A seven-line authorisation function can deserve more independent review and adversarial tests than a thousand-line report formatter.

### Worked example 12.1C — Failure-mode analysis for report replacement

For the refined “save a report” requirement:

| Failure mode | Observable consequence | Design control | Verification |
|:---|:---|:---|:---|
| invalid report discovered after truncation | valid prior file lost | validate before opening destination | seed prior file; fail validation; compare bytes |
| process stops during direct write | partial destination | write temporary sibling, flush as required, replace atomically where supported | inject interruption at each stage |
| disk fills | partial temporary data | cleanup owned temporary; preserve prior destination | bounded fake or constrained filesystem test |
| destination is symbolic link | write crosses intended boundary | resolve and enforce platform-specific path policy | adversarial filesystem integration cases |
| log contains report body | confidentiality breach | structured allow-list fields | capture logs and scan classified fixtures |
| success returned before required durability | acknowledged data lost after crash | define and implement flush/synchronisation contract | platform-specific fault/recovery experiment |

No single Python unit test validates all rows. Some require an actual filesystem and controlled fault injection; durability claims may require platform and hardware qualification.

> **Common misconception 12.7 — “Risk-based testing means testing only the likely path.”**  
> Risk includes consequence. An improbable authorisation bypass or irreversible data loss can justify deeper evaluation than a frequent cosmetic defect.

### 12.2.10 Architecture as allocation of responsibilities

**Software architecture** is the set of structures needed to reason about a system, including elements, relations, externally visible properties, and consequential decisions. Architecture is not synonymous with a diagram, framework, or folder layout. A diagram is a view of selected architectural facts.

A **component** is a unit considered as a whole at a chosen level; a **connector** is a mechanism of interaction such as a function call, event stream, file, or network protocol. A **boundary** separates responsibilities or trust, failure, deployment, consistency, or ownership domains. Boundaries are valuable when they correspond to a reason for independent change or control.

Two qualitative properties guide decomposition:

- **cohesion** is the degree to which responsibilities within a unit belong together;
- **coupling** is the degree and kind of dependency between units.

High cohesion and low coupling are heuristics, not scalar objectives. A parser should be strongly coupled to its declared grammar. Reducing visible calls by sharing a global database creates worse hidden coupling. The aim is explicit, stable, appropriately directed dependency.

The **dependency inversion principle** states, in one formulation, that high-level policy should not depend directly on low-level detail; both depend on abstractions appropriate to the policy. In Python, the abstraction can be a small <code>Protocol</code>, not necessarily an inheritance hierarchy.

### Worked example 12.1D — Separate policy from an external sender

~~~python
from dataclasses import dataclass
from typing import Protocol


@dataclass(frozen=True)
class Notice:
    recipient: str
    subject: str
    body: str


class NoticeSender(Protocol):
    def send(self, notice: Notice) -> str:
        """Send one notice and return the provider's stable identifier."""


def notify_overdue(
    account_id: str,
    email: str,
    amount_pence: int,
    sender: NoticeSender,
) -> str:
    if amount_pence <= 0:
        raise ValueError("overdue amount must be positive")
    notice = Notice(
        recipient=email,
        subject=f"Account {account_id}: payment overdue",
        body=f"Amount due: GBP {amount_pence / 100:.2f}",
    )
    return sender.send(notice)
~~~

The policy constructs a notice and depends only on the operation it requires. A production adapter can call an external service; a test spy can record the notice. This structure does not prove the external adapter works. It creates a boundary at which focused policy evidence and integration evidence can be collected separately.

The example’s monetary formatting is intentionally incomplete for international production use: binary floating-point conversion, currency rules, localisation, and confidential-data policy require explicit decisions. Identifying that limitation is part of honest modelling.

> **Common misconception 12.8 — “More layers mean better architecture.”**  
> Each layer adds indirection and a coordination cost. A boundary is justified by a distinct policy, volatility, trust, failure, deployment, or test-control concern—not by a desire to make a small call graph taller.

### 12.2.11 Design by contract and defensive boundaries

**Design by contract** specifies obligations between caller and supplier through preconditions, postconditions, and invariants. Python has no built-in complete contract system, but checks, types, tests, and documentation can express portions of a contract.

A caller is responsible for satisfying a precondition only if it can know and control it. External text is untrusted data, not a caller that violated a contract. Parse and report invalid input at the boundary. An internal function receiving an impossible negative count may indicate a programmer defect; an assertion can document that invariant.

~~~python
def allocate(total: int, parts: int) -> tuple[int, ...]:
    if not isinstance(total, int) or isinstance(total, bool):
        raise TypeError("total must be an integer")
    if not isinstance(parts, int) or isinstance(parts, bool):
        raise TypeError("parts must be an integer")
    if total < 0:
        raise ValueError("total cannot be negative")
    if parts <= 0:
        raise ValueError("parts must be positive")

    quotient, remainder = divmod(total, parts)
    result = tuple(
        quotient + (index < remainder)
        for index in range(parts)
    )
    assert len(result) == parts
    assert sum(result) == total
    assert max(result) - min(result) <= 1
    return result
~~~

The explicit checks define the public runtime boundary. The assertions state consequences that should follow from the algorithm. They are valuable during testing but must not be the sole validation of hostile input because Python can remove assert statements when optimisation is requested.

The Boolean checks reflect Python’s type relation: <code>bool</code> is a subclass of <code>int</code>. Whether to reject it is a domain decision, not a universal style rule.

### 12.2.12 Decisions, alternatives, and architecture records

An **architecture decision record** (**ADR**) is a short durable record of a consequential design decision. A useful ADR states:

- context and forces;
- decision;
- considered alternatives;
- consequences, including disadvantages;
- status and superseding decisions;
- evidence or assumptions that could cause reconsideration.

“Use PostgreSQL” is an outcome, not an adequate argument. A record might explain that transactions span several related rows, operators already support the technology, anticipated scale fits measured capacity, and a document store was rejected because the dominant access paths require relational constraints. Later maintainers can then distinguish a current constraint from historical accident.

Decisions differ in **reversibility**. Naming a private helper is cheap to reverse. Publishing an identifier format, choosing an on-disk schema, or emitting an external event creates long-lived compatibility obligations. Review and experimentation should be proportional to the cost of reversal.

> **Common misconception 12.9 — “Architecture is decided once before coding.”**  
> Some high-cost decisions require early analysis, but implementation and operation reveal information that changes architecture. The discipline is to make consequential decisions explicit, test assumptions, and preserve the reasons for later revision.
