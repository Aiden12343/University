# 12.20 Variance and mutable containers

Suppose `Cat` is a subtype of `Animal`. It might seem that `list[Cat]` should be usable as `list[Animal]`. That would be unsafe:

```python
def add_animal(animals: list[Animal]) -> None:
    animals.append(Dog())
```

If a `list[Cat]` were admitted, the function would insert a `Dog`, violating the original list’s element invariant. Mutable lists are therefore invariant in their type parameter under ordinary static typing.

Read-only producer interfaces can be covariant because callers cannot insert a broader value. `Sequence[Cat]` can often be used where `Sequence[Animal]` is required under the type system’s declared variance. **Variance** describes how a generic type’s subtype relationship follows or reverses its parameter subtype relation.

This is not abstract bureaucracy; it is mutation and substitutability expressed statically.

### 12.20.1 Covariance, contravariance, and invariance

Let <code>Cat</code> be a subtype of <code>Animal</code>. For a generic constructor <code>G</code>:

- **covariance** means <code>G[Cat]</code> is a subtype of <code>G[Animal]</code>;
- **contravariance** means <code>G[Animal]</code> is a subtype of <code>G[Cat]</code>;
- **invariance** means neither relationship follows merely from the parameter relation.

Producers tend towards covariance: a source of Cats can serve a consumer needing Animals. Consumers tend towards contravariance: a handler capable of every Animal can handle a Cat. Mutable structures both produce and consume values and are commonly invariant.

### Worked example 12.6D — Why callback parameters reverse

~~~python
from collections.abc import Callable


class Animal:
    pass


class Cat(Animal):
    pass


def describe_animal(animal: Animal) -> str:
    return animal.__class__.__name__


def render_cats(
    cats: list[Cat],
    describe: Callable[[Cat], str],
) -> list[str]:
    return [describe(cat) for cat in cats]


names = render_cats([Cat()], describe_animal)
~~~

<code>describe_animal</code> accepts any Animal, so it certainly accepts every Cat supplied by <code>render_cats</code>. A function accepting only a particular Cat subtype would not be safe where arbitrary Cats can arrive. Callable parameter types therefore vary contravariantly in the static model, while return types vary covariantly.

### 12.20.2 Read-only views and aliasing

Annotating a parameter as <code>Sequence[Animal]</code> prevents that function from calling list mutation methods through the parameter. It does not make the underlying object immutable. Another alias can mutate a list during or after the call.

If a stable snapshot is required, copy to an immutable representation:

~~~python
def snapshot_names(animals: Sequence[Animal]) -> tuple[str, ...]:
    snapshot = tuple(animals)
    return tuple(animal.name for animal in snapshot)
~~~

Even the tuple only freezes references; mutable Animal objects can change internally. “Read-only interface”, “shallow immutable container”, and “deep immutable value” are different contracts.

### 12.20.3 Variance declarations and inferred variance

Traditional <code>TypeVar</code> declarations can explicitly mark covariance or contravariance for user-defined generics. Newer generic syntax can permit checker inference under specified rules. The correct declaration follows how the parameter appears in public operations, not the author’s preferred assignability.

A supposedly covariant box with a setter is unsafe: after viewing <code>Box[Cat]</code> as <code>Box[Animal]</code>, a caller could insert a Dog. Hide mutation or remain invariant.

Private attributes, properties, and checker conventions can influence inferred variance. Treat unexpected inference as a reason to inspect interface semantics, not merely to force a flag.

> **Common misconception 12.68 — “Immutable syntax makes a generic covariant.”**  
> Variance follows substitutability of the exposed interface. Runtime immutability, static read-only access, and absence of writable aliases are related but distinct facts.
