# 12.21 Continuous integration

**Continuous integration** (**CI**) is the practice and automation of frequently combining changes and running repeatable verification. A CI pipeline commonly performs:

1. clean checkout;
2. declared interpreter/tool setup;
3. dependency installation from controlled inputs;
4. formatting or format check;
5. lint and static analysis;
6. unit and integration tests;
7. build of distributable artefacts;
8. clean-artefact smoke tests;
9. security or licence checks under policy;
10. publication only from authorised reviewed state.

CI does not make tests more true. It removes dependence on one developer’s hidden environment and makes the evidence repeatable for every change.

A failing CI job should preserve logs, versions, and artefacts needed to reproduce the failure. Automatically rerunning until green can conceal nondeterminism; a flaky test is an uncontrolled experiment and requires diagnosis.

### 12.21.1 A pipeline is a dependency graph

A CI pipeline is better modelled as a directed acyclic graph of jobs than as one long script. A node consumes declared inputs, executes in an environment, and produces status and artefacts. An edge states that a downstream job requires an upstream result.

For example:

~~~text
source checkout
    -> source-format check
    -> lint
    -> static types
    -> unit tests
    -> integration tests
    -> build sdist and wheel
    -> install-wheel smoke test
    -> provenance and publication
~~~

Independent jobs can run concurrently, while publication depends on every required gate. The apparent sequence is not itself evidence: each node must fail on tool failure, retain meaningful output, and use exactly the source revision claimed.

A command hidden behind <code>|| true</code>, a shell pipeline that returns only the final command’s status, or a test runner configured to accept zero tests can produce false green. CI code deserves the same review as production code because it defines the evidence and release authority.

### 12.21.2 Clean construction and environmental parity

A fresh runner detects undeclared dependencies that a long-lived developer machine supplies accidentally: an environment variable, global package, cached generated file, local database schema, or earlier build output.

“Works in CI” still does not guarantee production parity. Compare:

- operating system and CPU architecture;
- Python implementation and patch version;
- dependency resolution;
- native libraries;
- locale, timezone, and filesystem;
- permission model;
- network topology and proxies;
- service versions and schemas;
- resource limits;
- secrets and identity.

Exact identity is rarely attainable or desirable; tests need controlled fidelity for the relevant claim. A Linux CI runner cannot establish Windows path behaviour. A matrix can test declared supported platforms and Python versions, with expensive cases scheduled under risk policy.

### 12.21.3 Matrices, fail-fast, and evidence preservation

A **test matrix** evaluates combinations such as Python 3.12/3.13, Linux/Windows/macOS, and minimum/latest dependencies. The Cartesian product can become expensive. Select combinations deliberately:

- every supported Python version on a primary platform;
- every supported platform on a primary Python version;
- minimum dependency versions where compatibility is promised;
- latest compatible dependencies to detect upcoming conflict;
- special native or optional features in targeted jobs.

This “covering” matrix omits some interactions. Add a full matrix periodically or when a risk suggests one.

Fail-fast saves resources after one failure but can discard independent diagnostic evidence. For a small matrix, allowing remaining jobs to finish can show whether failure is platform-specific. For an expensive deployment stage, stopping immediately is safer. Choose by cost and information value.

### Worked example 12.6E — Distinguish source tests from artefact tests

An illustrative local sequence:

~~~text
python -m pytest
python -m mypy
python -m build
python -m venv .wheel-test
.wheel-test/bin/python -m pip install --no-deps dist/example_pkg-1.4.0-py3-none-any.whl
.wheel-test/bin/python -c "import example_pkg; print(example_pkg.__version__)"
~~~

Platform-specific activation paths differ, and a real pipeline should create its environment in disposable workspace rather than a retained project path. The conceptual distinction is critical:

- tests against the checkout establish source-tree behaviour;
- installation of the built wheel establishes that packaging included the necessary modules, metadata, data files, and entry points;
- an import/smoke test in a directory outside the repository avoids accidental imports from the working tree.

A package can pass every source test and produce a broken wheel. Build artefacts are subjects of verification, not by-products assumed correct.

> **Common misconception 12.69 — “CI reproduces the developer’s commands on a server.”**  
> A sound pipeline reconstructs declared state, evaluates policy, preserves evidence, and authorises later actions. Its identity, permissions, artefacts, and failure semantics are part of the engineered system.

### 12.21.4 Caches and reproducibility

CI caches trade isolation for speed. A cache key should incorporate every input affecting cached output: operating system, architecture, Python ABI, dependency declaration or lock hash, tool version, and relevant build options. An overly broad key can reuse incompatible artefacts; an overly narrow key wastes storage.

Treat caches as untrusted accelerators. A clean build without cache should succeed, and cache corruption should cause a miss or rebuild rather than silently alter a release. Do not cache secrets. Control who can populate caches used by privileged release jobs, because cache poisoning can cross trust boundaries.

A **reproducible build** yields bit-for-bit identical output from the same declared source and build inputs under the specified process. Deterministic timestamps, file order, paths, locale, compression, and dependency tooling all matter. Reproducibility allows independent parties to compare artefacts, but identical malicious builds remain malicious; source and build-environment trust still matter.

### 12.21.5 Pipeline identity and least privilege

CI executes repository-controlled code, often automatically on contributions. Grant untrusted change jobs the least privilege:

- read-only source access;
- no production credentials;
- no release-signing key;
- no ability to alter protected policy;
- bounded network and compute where feasible;
- isolated caches from privileged branches.

Publication jobs should run only for authorised immutable revisions, use short-lived scoped credentials where available, and require protected environment policy. Pull-request code can modify test scripts to print secrets; merely marking a value “secret” in UI masking does not make exposing it safe.

Dependency installation also executes code through build backends and plugins. Pin or constrain tools, verify sources and hashes under policy, and separate untrusted evaluation from privileged release.

### 12.21.6 Continuous delivery and deployment

**Continuous delivery** keeps software in a releasable state and automates the path to a release decision. **Continuous deployment** automatically deploys every change that satisfies policy. Teams use the terms inconsistently, so define local meaning.

Deployment is not validation’s endpoint. Observe:

- error and latency indicators;
- resource saturation;
- business invariants;
- migration progress;
- security signals;
- user-visible outcomes.

Progressive delivery exposes a change to a controlled fraction or group and compares signals. A **canary** can detect environment-specific failure before full rollout. It cannot detect silent harm unless the relevant indicator exists, and comparison can be confounded by non-random populations.

Rollback must include data and protocol compatibility. Reverting application code after an irreversible schema or event change can make the old version unable to run. Prefer expand–migrate–contract sequences and roll-forward repair where rollback cannot restore state.

> **Common misconception 12.70 — “A green pipeline makes a revision safe to deploy.”**  
> It satisfies encoded pre-deployment checks. Deployment introduces real load, data, dependencies, identities, and interactions; progressive exposure and operational verification close part of that evidence gap.
