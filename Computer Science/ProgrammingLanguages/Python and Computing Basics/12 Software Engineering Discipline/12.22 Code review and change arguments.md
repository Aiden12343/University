# 12.22 Code review and change arguments

A reviewable change includes a claim:

- what behaviour or structure changed;
- why it is required;
- which alternatives were considered;
- which risks were introduced;
- which evidence supports acceptance;
- how it can be rolled back or migrated.

Review examines correctness, clarity, tests, security, performance, compatibility, and operational impact. Style automation should remove mechanical disputes so human attention can focus on semantic questions.

Comments such as “looks good” provide no durable evidence. A strong review observation points to a contract or trace: “When parsing fails after the output file is opened in `w` mode, the prior report has already been truncated; write and validate to a temporary sibling before replacement.”

### 12.22.1 Review the change, not only the resulting files

Code review has at least three objects:

1. the desired requirement or problem;
2. the delta introduced by the change;
3. the resulting system state.

A correct final function can arrive through a change that deletes a security check elsewhere. A locally sensible diff can produce an incoherent architecture when viewed in the resulting tree. Review both representations.

The author should provide:

- concise problem and scope;
- requirement or issue links;
- design argument and alternatives for consequential choices;
- risk and trust-boundary changes;
- evidence commands and results;
- compatibility, migration, and rollback implications;
- generated files and dependency changes;
- known omissions or follow-up.

The reviewer independently checks claims rather than treating the description as proof.

### 12.22.2 Change size and cognitive load

Review effectiveness declines when unrelated semantic, formatting, generated, dependency, and mechanical changes are mixed. Separate changes when they can be integrated coherently. A preparation refactor should preserve behaviour and land with its own evidence before a feature where practical.

Line count is an imperfect measure. A one-line dependency update can introduce thousands of lines of transitive code; a large machine-generated schema diff may require checking the generator and summary rather than every repeated line. Label generated content and provide reproducibility checks.

Small review batches should not create incomplete deployed states. Feature flags, backward-compatible schema steps, and dormant code can permit incremental integration, but dormant paths require tests and removal policy.

### 12.22.3 A semantic review checklist

For each change, ask:

**Contract**

- What new behaviour is required?
- Which existing behaviour must remain?
- Are units, boundaries, errors, ordering, and effects explicit?

**Data and state**

- What invariant changes?
- Can partial failure leave an invalid state?
- Are migrations compatible with mixed versions and retries?

**Security and privacy**

- Where does untrusted data enter?
- Which identity authorises the action?
- Do logs, errors, caches, and metrics disclose information?
- Has dependency or privilege surface changed?

**Concurrency and operations**

- What happens on duplicate, timeout, cancellation, and concurrent execution?
- Are observability and rollback adequate?
- Are capacity assumptions measured?

**Evidence**

- Does each important claim have an independent oracle?
- Are tests at the right boundaries?
- Can the reported commands be reproduced from the built artefact?

A checklist reminds; it cannot replace expertise. Rotate or tailor questions so completion does not become a ritual detached from the change.

### 12.22.4 Review dialogue and decision ownership

Classify comments to reduce ambiguity:

- blocking correctness or policy issue;
- required clarification;
- non-blocking suggestion;
- question;
- optional style preference.

Support claims with mechanism: “This can be called twice after timeout, and the gateway key is regenerated, so the second request can duplicate the charge.” Avoid personal attribution such as “you forgot”.

The author remains responsible for understanding accepted changes; a reviewer’s approval does not transfer ownership. Reviewers should acknowledge uncertainty and request domain expertise rather than approve outside competence. High-risk changes may require independent security, data, safety, or operations review.

### 12.22.5 Automation and human attention

Formatters, linters, type checkers, tests, schema diff tools, licence scanners, and dependency analysers should run before or within review. Humans should not spend scarce attention counting spaces.

Automation can overwhelm reviewers with undifferentiated output. Configure actionable diagnostics and surface deltas: a new permission, exported symbol, dependency, database lock, or coverage gap. A tool’s success is one input to review; a tool’s finding needs classification.

### Worked example 12.6F — Review an apparently harmless retry

Change:

~~~python
for attempt in range(3):
    try:
        return gateway.charge(amount_pence)
    except TimeoutError:
        if attempt == 2:
            raise
~~~

Review argument:

1. a timeout does not reveal whether the remote charge committed;
2. retrying the same amount without stable operation identity can repeat the effect;
3. the loop has no delay or global deadline;
4. every timeout is assumed transient;
5. no telemetry relates attempts;
6. cancellation during retry is unmodelled.

A correct change needs provider-supported or application-enforced idempotency, a classified retry policy, bounded backoff/deadline, persistent operation state where process failure matters, and integration tests that simulate timeout before and after commit.

> **Common misconception 12.71 — “Two approvals make a change twice as safe.”**  
> Independent knowledgeable review can reduce risk. Rubber-stamped, duplicated, or same-assumption review adds little evidence; authority count is not evidence quality.
