# 12.23 Integrated engineering workflow

For a new ledger capability:

1. write requirement and acceptance cases;
2. identify affected invariants and public interfaces;
3. create a branch from a known commit;
4. add a failing focused test with an independent oracle;
5. implement the smallest coherent change;
6. run focused tests, then full configured checks;
7. inspect types, diagnostics, dependencies, and resource effects;
8. update reference and explanatory documentation;
9. build and test the actual wheel in a clean environment;
10. review the staged diff and commit one coherent change;
11. submit for review with evidence and migration/rollback notes;
12. integrate through CI and observe deployment or release outcomes.

The order is not dogma. A research spike may precede a final specification, and a production incident demands containment before perfect documentation. Discipline means making deviations explicit and later restoring the missing evidence.

### 12.23.1 Release engineering completes the change

**Release engineering** governs construction, identification, verification, distribution, and support of software versions. Chapter 10 established how Python projects declare builds in <code>pyproject.toml</code>. Here the concern is evidence that a particular distributed artefact corresponds to an authorised source state.

A release record should connect:

~~~text
approved source commit and tag
    -> declared build environment
    -> dependency/build inputs
    -> build invocation
    -> wheel and source-distribution hashes
    -> test and analysis results
    -> signing/provenance attestations
    -> package-index identity
    -> release notes and support status
~~~

Building once for testing and again for publication weakens identity: the published bytes were not the tested bytes. Prefer building an immutable artefact once, promoting that same artefact through verification and authorised publication.

### 12.23.2 Versions and compatibility contracts

A **version scheme** orders and identifies releases. Python package indexes and tooling interpret versions according to the packaging specifications, notably PEP 440. **Semantic Versioning** is a separate convention expressing incompatible API changes, backward-compatible features, and backward-compatible fixes through major, minor, and patch components. A project must define what counts as its public API and compatibility.

Compatibility dimensions include:

- import names and call signatures;
- accepted and returned values;
- exception types and timing;
- serialised schemas;
- command-line flags, output, and exit status;
- performance and resource ceilings;
- typing interfaces and stub behaviour;
- platform/Python support;
- side effects, ordering, and concurrency;
- security policy.

A “minor” change can break callers that relied on unspecified behaviour. The project decides whether to preserve, deprecate, or explicitly reject that dependence; version numbers do not mechanically decide.

### 12.23.3 Deprecation as a migration protocol

A **deprecation** announces that a supported interface is intended for removal or incompatible change after a transition. A responsible deprecation supplies:

1. replacement and rationale;
2. version in which notice begins;
3. earliest removal version/date under policy;
4. a detectable warning or analysis signal;
5. migration instructions;
6. compatibility shim where proportionate;
7. tests for old warning and new behaviour;
8. release-note visibility.

Warnings should identify the caller-facing operation and avoid flooding one request with thousands of duplicates. Python normally filters <code>DeprecationWarning</code> differently by execution context; library maintainers should test with warnings enabled or promoted to errors.

Removing a security-dangerous interface may justify an accelerated schedule. State the risk and provide the safest feasible migration.

### 12.23.4 Source distributions and wheels as different claims

A Python **source distribution** contains source and metadata intended for a build process. A **wheel** is an installation-format archive with defined layout and metadata. A pure-Python wheel may be platform-independent; a wheel containing native extension code is tagged for compatible Python, ABI, and platform combinations.

Verify both when distributing both:

- archive contains intended licence, typing marker, package data, and build inputs;
- metadata name, version, dependencies, Python requirement, and entry points are correct;
- source distribution can build in an isolated environment under supported policy;
- wheel installs without importing from the checkout;
- public imports and commands run;
- native wheels run on actual supported platforms;
- no credentials, tests containing private data, caches, or unwanted files are included.

Listing archive contents is necessary but not sufficient. Install into a fresh environment and execute consumer-facing smoke tests.

### 12.23.5 Dependency ranges, locks, and environments

Libraries and applications face different dependency goals. A reusable library usually declares the range of dependency versions its public implementation supports, avoiding an exact transitive environment that would overconstrain consumers. An application deployment often uses a lock or resolved manifest to reproduce the tested environment.

These are not opposites. A library can:

- declare compatible ranges in package metadata;
- test lower bounds where promised;
- test recent resolution;
- use a lock for its own CI tool environment;
- publish no accidental dependency beyond its public metadata.

Upper bounds can protect against known incompatibility but also prevent resolution after a compatible new major release. Lower bounds should be real tested minima, not copied from the version currently installed.

A lock records a resolution, not eternal availability or safety. Retain artefacts or approved indexes as required, scan for advisories, and update deliberately.

### 12.23.6 Build isolation and trusted inputs

Modern Python build front ends create an isolated environment and install build requirements declared by the project before invoking a backend. Isolation prevents undeclared local packages from influencing the build, but it can fetch executable build dependencies. Control indexes, versions, hashes, and network according to threat model.

Builds should not depend on the developer’s Git untracked files, current time without normalisation, network response, or environment secrets. If version metadata is derived from Git, define behaviour for source archives without repository metadata and dirty trees.

An offline rebuild from retained, verified inputs is valuable for long support horizons. It requires preserving more than source: interpreter/toolchain, native headers, dependency artefacts, and platform images may matter.

### 12.23.7 Hashes, signatures, provenance, and SBOMs

A cryptographic hash identifies bytes with strong collision resistance under the chosen algorithm. It supports integrity comparison only when the expected hash is obtained through a trusted channel.

A digital signature binds artefact bytes or a statement to a private-key operation. Verification needs trusted public-key identity and revocation/rotation policy.

**Build provenance** records claims about how an artefact was produced: source identity, builder, invocation, and materials. An **attestation** is a signed statement about such claims. A **software bill of materials** (**SBOM**) inventories components in an artefact or product.

None is a magic safety certificate:

- provenance can faithfully record a compromised builder;
- an SBOM can be incomplete or identify a component without establishing exploitability;
- a valid signature can belong to a compromised key;
- a hash says nothing about behaviour.

Together with isolated builds, least privilege, review, and vulnerability response, they improve traceability and incident analysis.

### 12.23.8 Publication and immutable promotion

Before publication:

1. select an authorised source commit;
2. ensure the working tree and version metadata are controlled;
3. build in the release environment;
4. record hashes and provenance;
5. test the exact artefacts;
6. publish first to a staging or test index when useful;
7. install from that index in a fresh environment;
8. publish to the production index with scoped credentials;
9. verify index metadata and downloadable hashes;
10. announce compatibility, changes, and known issues.

Many package repositories do not permit replacing published files safely, and clients/cache layers may retain old bytes. Treat a released version as immutable; publish a corrected higher version.

Test indexes may not reproduce every production-index policy and can permit dependency confusion if installers combine indexes carelessly. Use isolated names and explicit source policy.

### 12.23.9 Rollback, withdrawal, and incident release

Package publication is not the same as service deployment. A package consumer may install at any later time. If a release is defective:

- mark or yank it through the index’s supported mechanism where appropriate;
- publish a fixed version;
- issue a security advisory if relevant;
- describe affected versions and mitigations;
- do not silently replace bytes under the same version;
- preserve forensic artefacts and timeline.

A **yank** generally discourages new resolution while allowing exact pins under packaging semantics; it is not deletion from every cache. The exact index behaviour is specification and service dependent.

Emergency releases still require identity and evidence. Compress the process by prioritising the failing risk, not by removing traceability. Follow with full regression, review, and post-incident work.

### 12.23.10 Maintenance, support, and end of life

Every supported release line consumes security, compatibility, test, and operational capacity. Define:

- supported Python/platform versions;
- security-fix policy;
- support duration;
- deprecation window;
- backport criteria;
- end-of-life communication;
- archival and reproducibility obligations.

Backports should minimise semantic surface. Cherry-picking a patch from a newer architecture can omit dependencies or introduce incompatible assumptions; review and test on the target branch.

At end of life, documentation should remain clear about unsupported status. “No longer supported” means defects may remain uncorrected; it does not erase installed copies or data migration responsibilities.

> **Common misconception 12.72 — “Publishing a package is uploading the dist directory.”**  
> A release is an identity- and evidence-preserving process connecting authorised source to exact tested artefacts, metadata, provenance, distribution, support, and incident response.

### 12.23.11 The claim ledger

This treatise distinguishes several kinds of statement. Apply the same discipline to project records:

| Claim kind | Example | Appropriate evidence |
|:---|:---|:---|
| definition | “a fixture is controlled test state” | declared terminology |
| derivation | boundary cases follow from interval closure | inspectable reasoning |
| specification rule | <code>list</code> is invariant in ordinary typing | typing specification |
| implementation fact | pytest rewrites assertions | versioned implementation documentation/test |
| empirical observation | p99 latency was 180 ms | measurement with method and data |
| modelling assumption | retries arrive within 24 hours | explicit assumption and validation plan |
| substantive judgement | residual risk is acceptable | authorised decision with rationale |

Confusing kinds produces false certainty. A benchmark does not establish a language guarantee; a specification does not prove one deployed implementation conforms; a judgement is not made objective by placing it in a configuration file.

### 12.23.12 Definition of done as a local control

A **definition of done** is a team’s explicit minimum evidence for considering a change complete. It can include:

- acceptance criteria satisfied;
- code reviewed;
- tests at required levels;
- static analysis and style checks;
- documentation and migration updated;
- artefact built and smoke-tested;
- security/privacy review triggers resolved;
- telemetry and rollback prepared.

It is a floor, not a universal checklist. A spelling repair and a funds-transfer redesign need different depth. Add risk-specific acceptance rather than treating every tick as equivalent.

### Integrated case study 12.A — Engineer a resumable ledger import

**Requirement.** An authorised operator imports a UTF-8 CSV file containing at most ten million transaction rows. Each accepted row is applied exactly once with respect to a stable file-and-row identity. Invalid rows are reported without exposing other customers’ data. Process interruption can be resumed. A completed import preserves the ledger’s balancing invariant and emits a signed summary.

**Problem model.** “Exactly once” is not a property of transport alone. Define identity as a cryptographic content hash plus logical row number only if byte-identical files should deduplicate; otherwise use an issued import identifier persisted before processing. A corrected file may share row numbers but must be a new import.

**Architecture.**

- streaming decoder and CSV parser;
- runtime schema validator producing typed commands;
- transaction application service;
- database table recording import, row identity, outcome, and checkpoint;
- report writer using atomic replacement;
- audit and metrics adapter;
- command-line boundary.

**Critical invariants.**

1. every posted transaction balances under ledger rules;
2. one row identity has at most one committed monetary effect;
3. checkpoint never advances beyond committed effects;
4. rejection data is scoped to the authorised import;
5. completion is set only after every row is terminal and summary durable under the declared contract.

**Focused tests.** Parser partitions cover empty file, header-only file, quoted delimiters, embedded newlines, malformed UTF-8, maximum field size, duplicate headers, and terminal escapes. Schema tests distinguish absent, empty, malformed, and out-of-range fields. Property tests generate balanced transactions and verify conservation after serialise/parse.

**Integration tests.** The real database receives concurrent duplicate submissions; one effect commits. Fault injection stops execution after effect commit but before checkpoint update; resume discovers the persisted row identity and does not apply it twice. Disk-full simulation during summary write preserves the previous summary and incomplete status.

**Static model.** Dynamic CSV strings are parsed into <code>AccountId</code>, integer pence, timezone-aware instants, and discriminated command variants. Repository and clock interfaces are protocols. Any untyped driver boundary is wrapped, checked, and prevented from propagating <code>Any</code>.

**Diagnostics.** Logs carry import and row identifiers but not complete row data. Counters record terminal outcomes with bounded reason codes. A progress gauge is derived from committed records rather than in-memory count. Audit records are separate from diagnostic log retention.

**Version history.** Commits introduce compatible schema, domain model, parser, application path, resume behaviour, and CLI in bisectable increments. The merge request links requirement, risk table, tests, migration plan, and a rollback limitation: once real transactions are posted, application rollback cannot unpost them; compensation is a domain operation.

**Release.** CI builds one wheel, installs it in a clean environment, runs a miniature import through the installed command, records hashes/provenance, and publishes the exact artefact after review. The operator runbook states capacity checks, abort conditions, resumption, verification queries, and incident escalation.

The case demonstrates that engineering discipline is not a sequence of independent tools. Requirement identity determines schema; schema determines idempotency; idempotency determines failure tests; failure tests determine observability; distribution determines whether the tested program is the one operators run.
