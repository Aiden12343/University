# 12.3 Testing is executable claim checking

A **test** is an executable experiment comparing observed behaviour with an expected claim. A test contains:

1. setup establishing controlled initial state;
2. stimulus invoking behaviour;
3. observation collecting results and effects;
4. oracle determining expected behaviour;
5. assertion comparing observation with oracle;
6. cleanup restoring owned resources.

A test passes when its assertions hold in that execution. This is evidence for the covered claim under the test environment. It is not proof that the program has no defects.

A **test case** is one specified setup/stimulus/expectation. A **test suite** is an organised collection of cases. A **fixture** is controlled state or a resource supplied to tests. A **regression test** preserves behaviour after a defect is found or a capability is established.

### Test levels

- A **unit test** exercises a small behavioural unit with controlled collaborators.
- An **integration test** exercises cooperation across real component boundaries.
- A **system test** exercises the assembled system under a representative environment.
- An **acceptance test** evaluates stakeholder-facing criteria.

The labels describe scope and purpose, not intrinsic quality. A test using no network can still be an integration test across parser and database adapter; a test of one class with a real clock and filesystem may be broad and unstable.

### 12.3.1 The proposition tested

Every test should be reducible to a proposition: under stated initial conditions and stimulus, a named observation has an expected relation to an independently justified oracle. This formulation prevents a common degeneration in which a test merely executes code or restates its implementation.

Suppose a tax function multiplies a price by a rate. The test:

~~~python
def test_tax() -> None:
    assert tax(100, 0.2) == 100 * 0.2
~~~

does not establish an independent expected result if the uncertainty concerns the multiplication rule itself. The right-hand side repeats the presumed algorithm. A clearer example supplies an already reasoned outcome and exact domain representation:

~~~python
from decimal import Decimal


def test_standard_rate_on_ten_pounds() -> None:
    assert tax_pence(1_000, Decimal("0.20")) == 200
~~~

The name states the behaviour; integers state the minor currency unit; the expected 200 pence can be checked independently by arithmetic and domain rules. Further cases must establish rounding, exemptions, invalid rates, and large values.

A test proposition has a **scope condition**. A parser test conducted on CPython 3.12 under Linux does not automatically establish identical filesystem behaviour on Windows. A concurrency test that passed once does not establish absence of every race. Record environmental dimensions when they could alter the claim.

> **Common misconception 12.10 — “A passing test says the code is correct.”**  
> It says that one execution did not reveal a disagreement between observations and that test’s oracle. The oracle may be wrong, the test may omit effects, and the environment may not represent deployment.

### 12.3.2 Oracles and the oracle problem

A **test oracle** is a mechanism or body of knowledge that determines the expected result. Oracles can come from:

- a manually derived example;
- an executable specification simpler than the implementation;
- a trusted reference implementation;
- an invariant or algebraic law;
- a previous approved result, called a **golden master** or **snapshot**;
- agreement among independent implementations;
- a human domain expert;
- a metamorphic relation between executions.

Each source has a failure mode. A golden master preserves accidental output as readily as correct output. A reference implementation may share the same algorithmic error. A human reviewer can overlook large output differences. An invariant can be too weak: a sorting function that returns the empty list is ordered but does not preserve elements.

Use multiple partially independent oracles for critical behaviour. A sorting test can assert:

1. non-decreasing order;
2. equal element multiplicities between input and output;
3. the result agrees with a separately trusted sorter for selected cases;
4. idempotence under a second sort.

No single relation is sufficient. Together they narrow the space of false implementations.

### Worked example 12.2A — A false oracle that copies the defect

Production code:

~~~python
def inclusive_total(start: int, stop: int) -> int:
    """Return the sum of every integer from start through stop."""
    return sum(range(start, stop))  # Defect: range excludes stop.
~~~

Weak test:

~~~python
def test_inclusive_total_weak() -> None:
    expected = sum(range(3, 6))
    assert inclusive_total(3, 6) == expected
~~~

Both expressions omit 6, so the test passes while contradicting the docstring. An independent finite calculation exposes the defect:

~~~python
def test_inclusive_total_includes_both_endpoints() -> None:
    assert inclusive_total(3, 6) == 3 + 4 + 5 + 6
~~~

The repair is <code>sum(range(start, stop + 1))</code>, accompanied by contracts for reversed intervals and extreme integer sizes. The lesson is not that literal arithmetic is always superior; it is that expected results must not inherit the unverified transformation.

> **Common misconception 12.11 — “Expected values generated by the production function save test maintenance.”**  
> They remove the independent comparison. Such code can be useful for recording observations during exploration, but not as an oracle until a separate process validates the recorded result.

### 12.3.3 False positives, false negatives, and test reliability

In testing terminology, a **false positive** is a reported failure when the required behaviour is actually satisfied; a **false negative** is a passing result despite a defect relevant to the tested claim. Communities sometimes reverse “positive” because they treat a positive as “the test passed”. Always state the event: *false failure* or *missed defect*.

A **flaky test** has inconsistent outcomes without a relevant change to the program or declared environment. Typical uncontrolled causes include:

- wall-clock time and timezone databases;
- thread or process scheduling;
- random-number seeds;
- iteration order assumed without a contract;
- network services;
- shared files, ports, databases, or environment variables;
- resource exhaustion;
- eventual consistency and fixed sleeps;
- locale, encoding, and platform conventions;
- dependence on another test’s residue.

Flakiness is not merely inconvenient. It changes team behaviour: genuine failures are rerun, alerts are ignored, and the suite stops functioning as trusted evidence. Quarantining a flaky test can protect the main signal temporarily, but the quarantined claim then lacks automated evidence and must have an owner and repair deadline.

### Worked example 12.2B — Replace elapsed sleeping with state observation

Fragile:

~~~python
def test_job_finishes_fragile(client: Client) -> None:
    job_id = client.submit({"value": 7})
    time.sleep(0.5)
    assert client.status(job_id) == "succeeded"
~~~

The fixed delay is simultaneously too long on fast systems and too short on slow systems. A bounded polling helper makes the timing contract explicit:

~~~python
from collections.abc import Callable
from time import monotonic, sleep
from typing import TypeVar

T = TypeVar("T")


class DeadlineExceededError(TimeoutError):
    pass


def eventually(
    observe: Callable[[], T],
    accepts: Callable[[T], bool],
    *,
    timeout_seconds: float,
    interval_seconds: float = 0.01,
) -> T:
    deadline = monotonic() + timeout_seconds
    while True:
        value = observe()
        if accepts(value):
            return value
        if monotonic() >= deadline:
            raise DeadlineExceededError(
                f"condition not met; last observation was {value!r}"
            )
        sleep(interval_seconds)
~~~

Test:

~~~python
def test_accepted_job_reaches_success(client: Client) -> None:
    job_id = client.submit({"value": 7})
    status = eventually(
        lambda: client.status(job_id),
        lambda value: value == "succeeded",
        timeout_seconds=2.0,
    )
    assert status == "succeeded"
~~~

This remains a real-time integration test and can still fail under overloaded infrastructure. It is better because it observes the required state, terminates promptly after success, retains the last observation, and states a maximum latency. A unit test of transition policy should inject a fake clock and scheduler; the integration test should retain real components where their timing interaction is the subject.

> **Common misconception 12.12 — “Retrying a flaky test makes the pipeline robust.”**  
> Automatic retry can estimate instability or gather diagnostics, but treating any eventual pass as success converts nondeterministic evidence into a hidden false-negative mechanism.

### 12.3.4 Isolation, independence, and order

Tests are **isolated** when relevant state created by one test cannot alter another’s result. They are **order-independent** when any permitted execution order yields the same outcomes. Isolation commonly requires:

- a fresh object graph or explicit reset;
- unique temporary filesystem paths;
- transaction rollback or independently created database schemas;
- unique service identifiers and idempotent cleanup;
- restoration of patched names, environment, current directory, and logging state;
- no reliance on module-level mutable caches unless deliberately controlled.

Framework teardown does not absolve a test from ownership. Cleanup should be safe when setup fails halfway and ideally idempotent—performing it twice has the same relevant effect as once.

The four-phase **Arrange–Act–Assert–Cleanup** model and Given–When–Then notation are organising conventions. They help reviewers distinguish precondition, stimulus, and oracle. A test with several actions can be legitimate for a stateful protocol, but each additional transition expands what a failure could mean.

### Worked example 12.2C — Detect hidden order dependence

Bad production-global state:

~~~python
_next_identifier = 0


def allocate_identifier() -> int:
    global _next_identifier
    _next_identifier += 1
    return _next_identifier
~~~

Tests that assume exact identifiers:

~~~python
def test_first_identifier() -> None:
    assert allocate_identifier() == 1


def test_second_identifier() -> None:
    allocate_identifier()
    assert allocate_identifier() == 2
~~~

Neither test owns the starting state; their results depend on order and prior calls. A more testable design encapsulates allocation:

~~~python
@dataclass
class IdentifierSequence:
    next_value: int = 1

    def allocate(self) -> int:
        result = self.next_value
        self.next_value += 1
        return result
~~~

Each test constructs its own sequence. Production may still need a persistent, concurrent allocator; that adapter requires separate integration tests. Encapsulation makes the state dependency explicit rather than pretending the distributed problem vanished.

> **Common misconception 12.13 — “Tests should run in source-file order.”**  
> A framework may currently collect them in a predictable order, but independent tests should not require it. When sequence is part of the behaviour, express the whole protocol in one state-machine test or an explicitly managed fixture.

### 12.3.5 Testability as a design property

**Testability** is the degree to which a system permits controlled stimulation and informative observation. It increases when:

- dependencies are explicit rather than discovered through global state;
- nondeterministic sources can be supplied or bounded;
- effects are separated from deterministic policy;
- interfaces return meaningful results and typed failures;
- state transitions are observable without exposing arbitrary internals;
- components can run in representative local or ephemeral environments;
- diagnostics preserve causal context.

Designing for testability does not mean exposing private fields solely to tests or dividing every function into trivial wrappers. It means making real dependencies and outcomes controllable through stable boundaries.

Functional-core/imperative-shell is one useful pattern. A **functional core** performs deterministic transformations over explicit values; an **imperative shell** obtains time, files, network results, or database state and applies effects. The core receives broad example and property testing; the shell receives focused integration tests.

~~~python
from dataclasses import dataclass
from datetime import date


@dataclass(frozen=True)
class Invoice:
    due_on: date
    paid: bool


def is_overdue(invoice: Invoice, *, today: date) -> bool:
    return not invoice.paid and invoice.due_on < today
~~~

The caller obtains today’s date. Tests can reason over exact dates without patching the global clock:

~~~python
def test_unpaid_invoice_before_today_is_overdue() -> None:
    invoice = Invoice(due_on=date(2026, 4, 9), paid=False)
    assert is_overdue(invoice, today=date(2026, 4, 10))
~~~

> **Common misconception 12.14 — “Private methods should be unit-tested directly.”**  
> Test stable behaviour at the narrowest useful public boundary. Direct private-method tests are sometimes justified for a complex algorithm, but they couple evidence to a decomposition that callers were never promised.

### 12.3.6 Test-first work, test-driven development, and characterisation

Writing a test before production code can clarify the desired interface and ensure the test can fail. **Test-driven development** (**TDD**) is a more specific micro-cycle: write a failing test, make it pass with a small change, then refactor while the tests remain green. TDD is a design and feedback practice, not a claim that the resulting suite is complete.

A **characterisation test** records the observed behaviour of an existing system when no adequate specification exists. It is especially useful before refactoring legacy code. Its initial oracle is descriptive: “this is what happens now”, not normative: “this is what ought to happen”. Label the distinction. Otherwise defects acquire undeserved authority merely because a snapshot captured them.

Before trusting a new test, observe it fail for the intended reason. A test that starts green may address already implemented behaviour, fail to execute, or contain a weak oracle. After repairing a defect, temporarily reintroducing the defect or using mutation testing can confirm that the regression test detects it.

> **Common misconception 12.15 — “A test written first is automatically a better test.”**  
> Timing can improve interface feedback and demonstrate sensitivity, but oracle quality, risk selection, isolation, and level remain independent concerns.
