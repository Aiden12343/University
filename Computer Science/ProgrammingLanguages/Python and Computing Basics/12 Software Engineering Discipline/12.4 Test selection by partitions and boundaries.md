# 12.4 Test selection by partitions and boundaries

Exhaustive testing is impossible for most non-trivial input spaces. **Equivalence partitioning** divides inputs into classes expected to receive similar treatment. **Boundary-value analysis** selects values at and around transitions where defects concentrate.

For a function accepting integer scores from 0 through 100:

- below range: `-1` and possibly a more distant negative;
- lower boundary: `0`;
- ordinary interior: `1`, `50`, `99` as justified;
- upper boundary: `100`;
- above range: `101`;
- wrong type or representation at an external boundary;
- Boolean values if `bool` must be rejected despite being an `int` subclass.

Every case states the risk it protects. Adding 51 after already testing 50 without a distinct partition is usually weaker than testing `True` when the domain means literal integers excluding Booleans.

### Worked example 12.2 — Test an interval parser

```python
def parse_percentage(text: str) -> int:
    try:
        value = int(text)
    except ValueError as error:
        raise ValueError("percentage must be an integer") from error
    if not 0 <= value <= 100:
        raise ValueError("percentage must be within 0..100")
    return value
```

Claims and cases:

| Claim | Representative case | Expected |
|:---|:---|:---|
| lower endpoint admitted | `"0"` | 0 |
| upper endpoint admitted | `"100"` | 100 |
| lower neighbour rejected | `"-1"` | range error |
| upper neighbour rejected | `"101"` | range error |
| ordinary interior admitted | `"37"` | 37 |
| malformed syntax rejected | `"3.7"` | chained integer error |
| empty input rejected | `""` | chained integer error |
| whitespace policy follows `int` | `" 5 "` | 5 |

The last case exposes an implicit contract: `int` accepts surrounding whitespace. If the application prohibits it, validation must precede conversion.

### 12.4.1 Deriving partitions from decisions

Partitions should come from semantic decisions, not arbitrary sampling. Begin with the contract, identify every predicate that changes treatment, and construct representatives that make each predicate true and false under otherwise controlled conditions.

For an access decision:

~~~python
def may_view_report(
    *,
    authenticated: bool,
    owns_report: bool,
    has_audit_role: bool,
    report_restricted: bool,
) -> bool:
    if not authenticated:
        return False
    if owns_report and not report_restricted:
        return True
    return has_audit_role
~~~

There are sixteen Boolean combinations. Testing all sixteen is inexpensive, but for dozens of conditions exhaustive combinations grow exponentially. A **decision table** documents relevant rules and exposes combinations:

| Rule | Authenticated | Owner | Auditor | Restricted | Result |
|:---|:---:|:---:|:---:|:---:|:---:|
| unauthenticated | no | — | — | — | deny |
| ordinary owner | yes | yes | no | no | allow |
| owner, restricted | yes | yes | no | yes | deny |
| auditor | yes | — | yes | either | allow |
| unrelated user | yes | no | no | either | deny |

The dash means the input does not affect that rule, not that the value is absent. A parameterised test can expand both dash values or choose representatives while a property test evaluates the complete finite space.

### Worked example 12.2D — Exhaust a small logical domain

~~~python
from itertools import product


def oracle(
    authenticated: bool,
    owns_report: bool,
    has_audit_role: bool,
    report_restricted: bool,
) -> bool:
    return authenticated and (
        has_audit_role or (owns_report and not report_restricted)
    )


def test_every_access_combination() -> None:
    for values in product([False, True], repeat=4):
        observed = may_view_report(
            authenticated=values[0],
            owns_report=values[1],
            has_audit_role=values[2],
            report_restricted=values[3],
        )
        assert observed is oracle(*values), values
~~~

The independent oracle is a Boolean expression derived from the policy. Independence is imperfect because both encode the same interpretation; review the decision table and include stakeholder acceptance cases. The assertion’s second expression supplies the failing tuple as context.

> **Common misconception 12.16 — “One test per function is a unit-test rule.”**  
> Functions define input spaces containing many behavioural partitions. Test count follows distinct claims and risks, not definition count.

### 12.4.2 Boundaries in ordered, structural, and temporal domains

An ordered numeric interval has obvious neighbours. Many important boundaries are not numeric:

- empty, singleton, and multiple-element collections;
- missing, present-empty, and present-non-empty fields;
- one Unicode code point represented by one or several code units or combining sequences;
- path at, below, and outside an authorised root;
- event just before, exactly at, and just after a deadline;
- resource count immediately below, at, and above a quota;
- state transition from pending to cancelled versus pending to completed;
- valid message split at every possible streaming chunk boundary.

For time, specify interval closure. “Between 09:00 and 17:00” could mean closed, open, or half-open. The half-open interval <code>[09:00, 17:00)</code> contains its start and excludes its end, allowing adjacent intervals without overlap.

For strings, length can mean bytes, Unicode code points, grapheme clusters perceived as characters, or display columns. A “20 character” limit is incomplete until the counting model and normalisation policy are stated.

### 12.4.3 Invalidity is structured, not residual

Tests often devote careful partitions to valid data and group everything else as “invalid”. Invalid input has structure:

- lexical invalidity: characters cannot form tokens;
- syntactic invalidity: tokens violate grammar;
- semantic invalidity: syntax is valid but meaning violates rules;
- contextual invalidity: value is valid generally but not in this state;
- authorisation failure: operation is meaningful but caller lacks authority;
- resource failure: required capacity or dependency is unavailable;
- conflict: concurrent or prior state makes the request inapplicable.

Different categories can require different status codes, retry policies, messages, logging, and transaction effects. Tests should ensure malformed confidential input is not echoed, conflicts do not partially mutate state, and transient failures are not mislabelled as permanent validation errors.

> **Common misconception 12.17 — “Invalid inputs all need the same exception test.”**  
> A shared public error can be deliberate, especially to avoid information disclosure, but internal classification, state guarantees, retryability, and diagnostic evidence may still differ and need verification.

### 12.4.4 Combinatorial interaction

Defects can depend on interactions among factors: a filename containing a combining character may fail only on one filesystem; a timeout may occur only with compression enabled and a maximum payload; a permission defect may appear only after ownership transfer.

Testing every combination of many factors is infeasible. **Pairwise testing** chooses cases so that every pair of factor values appears at least once; more generally, **t-wise testing** covers every combination of <code>t</code> factors. This is a sampling strategy based on the empirical observation that many interaction faults involve few factors. It is not proof against higher-order interactions, and security-critical combinations should be selected directly from threat analysis.

A covering array generator can reduce combinations, but its model must declare values and constraints. An impossible generated combination wastes effort; an omitted state cannot be discovered.

### 12.4.5 State-transition testing

For stateful systems, input validity depends on history. A **state machine** comprises states, events, transition rules, and outputs/effects. State-transition tests cover:

- every permitted transition;
- every prohibited event in each relevant state;
- transition sequences likely to interact;
- repeated events and idempotency;
- recovery after interruption;
- terminal-state behaviour.

Example job states:

~~~text
pending --start--> running --succeed--> succeeded
   |                   |
 cancel              fail
   v                   v
cancelled             failed
~~~

Questions hidden by the picture include whether running jobs can be cancelled, whether cancel is idempotent, what happens when success races cancellation, and whether a failed job can retry under the same identity. A formal transition table is less visually immediate but can state guards and effects precisely.

### Worked example 12.2E — Encode a transition table

~~~python
from enum import StrEnum, auto


class JobState(StrEnum):
    PENDING = auto()
    RUNNING = auto()
    SUCCEEDED = auto()
    FAILED = auto()
    CANCELLED = auto()


class InvalidTransitionError(ValueError):
    pass


_TRANSITIONS: dict[tuple[JobState, str], JobState] = {
    (JobState.PENDING, "start"): JobState.RUNNING,
    (JobState.PENDING, "cancel"): JobState.CANCELLED,
    (JobState.RUNNING, "succeed"): JobState.SUCCEEDED,
    (JobState.RUNNING, "fail"): JobState.FAILED,
}


def transition(state: JobState, event: str) -> JobState:
    try:
        return _TRANSITIONS[state, event]
    except KeyError as error:
        raise InvalidTransitionError(f"{state=} does not accept {event=}") from error
~~~

A complete finite test iterates every state and supported event, comparing against a table reviewed independently. Separate tests establish that an invalid transition has no persistence effect in the application layer.

> **Common misconception 12.18 — “Testing every line tests every state.”**  
> The same line can execute under many histories and combinations. Structural coverage of code and behavioural coverage of a state model answer different questions.

### 12.4.6 Random testing and reproducibility

Random generation can explore more cases than a small hand-written suite. A failure must retain enough information to reproduce it: seed, generated input, framework version, and relevant environment. A fixed seed makes repetition exact but explores the same sample forever; a robust pipeline can use deterministic per-run seeds, report them, and retain minimal counterexamples.

Uniform random values are rarely the right distribution. If an integer input spans a billion values, uniformly drawing values almost never selects 0, 1, -1, the maximum, or a power-of-two boundary. A strategy should deliberately weight semantic boundaries and structural shapes.

Randomness is a selection method, not an oracle. The test still needs a relation that distinguishes correct output.

> **Common misconception 12.19 — “A thousand random cases are stronger than ten chosen cases.”**  
> Strength depends on whether cases reach distinct failure-sensitive regions and whether their oracles discriminate defects. Repetition inside one ordinary partition adds little evidence.

### 12.4.7 Negative space and absence claims

Many requirements concern absence: no unauthorised disclosure, no duplicate charge, no file change after failure, no resource leak. An absence claim cannot usually be established by observing one output. Identify all relevant channels:

- return value and exception;
- persistent state;
- files and temporary paths;
- emitted messages;
- network calls;
- logs, metrics, and traces;
- timing differences where they disclose information;
- resource ownership and process state.

For an authorisation rejection, a test that checks HTTP status alone may miss a queued email, audit omission, cache insertion, or detailed error body. Construct a **side-effect ledger** listing permitted and forbidden effects for each outcome.

> **Common misconception 12.20 — “An exception means nothing happened.”**  
> Exceptions report control transfer. Unless the operation specifies failure atomicity, earlier writes, messages, mutations, and external calls can remain.
