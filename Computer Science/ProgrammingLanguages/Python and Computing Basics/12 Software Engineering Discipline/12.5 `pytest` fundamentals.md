# 12.5 `pytest` fundamentals

`pytest` is a third-party testing framework. It discovers test modules and functions by naming conventions, rewrites assertions to provide diagnostic detail, manages fixtures, and supports extensions.

```python
import pytest

from ledger.percentages import parse_percentage


@pytest.mark.parametrize(
    ("text", "expected"),
    [
        ("0", 0),
        ("37", 37),
        ("100", 100),
        (" 5 ", 5),
    ],
)
def test_parse_percentage_accepts_valid_values(
    text: str,
    expected: int,
) -> None:
    assert parse_percentage(text) == expected


@pytest.mark.parametrize("text", ["-1", "101", "3.7", ""])
def test_parse_percentage_rejects_invalid_values(text: str) -> None:
    with pytest.raises(ValueError):
        parse_percentage(text)
```

Parameterisation states one behavioural rule across selected cases without copying the test body. Distinct failure messages may justify separate tests or matching exception text/attributes. Overly broad `pytest.raises(Exception)` can pass when the wrong defect occurs.

Use the interpreter-bound invocation:

```text
python -m pytest
```

This makes environment selection explicit. A passing suite should report collected count, skipped or expected failures, warnings, and version/configuration context in reproducible automation.

### 12.5.1 Discovery and collection are part of the result

Before executing tests, pytest performs **collection**: it imports or otherwise examines configured paths and constructs test items from recognised modules, classes, and functions. Default naming conventions commonly recognise files named <code>test_*.py</code> or <code>*_test.py</code>, functions named <code>test_*</code>, and suitable classes named <code>Test*</code>. Exact behaviour is configuration- and version-dependent; the project configuration is the authority.

A report of “0 tests passed” is not a successful empty suite. It may mean the wrong directory, a naming mistake, an import failure handled elsewhere, or an unintended selection expression. CI should know the expected collection scale and treat an implausible fall as a failure requiring explanation.

Collection imports modules. Import-time network access, database mutation, environment validation, or expensive object construction therefore makes even listing tests unsafe or fragile. Production modules should generally define objects on import and perform application startup through an explicit entry point.

Useful diagnostic invocations include:

~~~text
python -m pytest --collect-only
python -m pytest -q
python -m pytest tests/unit/test_percentages.py
python -m pytest tests/unit/test_percentages.py::test_parse_percentage_accepts_valid_values
python -m pytest -k "percentage and not whitespace"
~~~

Node identifiers and selection syntax are pytest interfaces rather than Python language features. Record the exact command in failure reports; a selected subset is different evidence from the complete configured suite.

> **Common misconception 12.21 — “No red tests means all tests passed.”**  
> Tests can be uncollected, deselected, skipped, marked expected to fail, or terminated before execution. The collection and outcome summary is part of the evidence.

### 12.5.2 Assertion rewriting and diagnostic expressions

Python’s <code>assert</code> statement raises <code>AssertionError</code> when its expression is false. During collection, pytest rewrites assertions in test modules so failures can show subexpression values. This is a pytest implementation facility, not a change to Python’s language semantics.

Prefer direct semantic comparisons:

~~~python
def test_normalise_record_preserves_identifier() -> None:
    observed = normalise_record(
        {"identifier": " A-17 ", "display_name": "  Ada  Lovelace "}
    )
    assert observed == {
        "identifier": "A-17",
        "display_name": "Ada Lovelace",
    }
~~~

A manual form such as <code>assert observed == expected, f"...{observed}"</code> can hide pytest’s richer structural diff or eagerly construct a costly message. Add context when the expression alone cannot identify the case, especially inside a loop.

Do not combine unrelated claims into one Boolean expression:

~~~python
assert result.status == "accepted" and result.identifier is not None
~~~

Separate assertions reveal which relation failed:

~~~python
assert result.status == "accepted"
assert result.identifier is not None
~~~

Multiple assertions are appropriate when they describe one coherent outcome. If the first failure prevents later diagnostics, a specialised comparison helper or data structure may report all relevant differences.

Floating-point values often require a tolerance because representation and rounding were introduced in Chapter 5. Pytest’s <code>approx</code> compares according to configured relative and absolute tolerances:

~~~python
import pytest


def test_ratio_uses_fractional_division() -> None:
    assert ratio(1, 3) == pytest.approx(0.3333333333333333)
~~~

The default tolerance is a tool rule that can change and may not match the domain. For a physical measurement, derive tolerance from instrument and numerical error. For money, prefer an exact decimal or integer-minor-unit model rather than loosening a float assertion until it passes.

> **Common misconception 12.22 — “Approximate comparison fixes floating-point tests.”**  
> It encodes an error budget. An unjustified tolerance can accept a material defect, while an exact assertion can be correct for operations whose result is exactly representable or whose contract specifies exact bits.

### 12.5.3 Parameterisation as a quantified claim

Parameterisation applies one test relation to several argument tuples. Treat the table as a set of deliberately selected witnesses. Give cases readable identifiers when values alone obscure the protected rule:

~~~python
import pytest


@pytest.mark.parametrize(
    ("text", "expected"),
    [
        pytest.param("0", 0, id="lower-bound"),
        pytest.param("100", 100, id="upper-bound"),
        pytest.param("+7", 7, id="explicit-positive-sign"),
        pytest.param(" 9 ", 9, id="surrounding-whitespace"),
    ],
)
def test_parse_percentage_contract(text: str, expected: int) -> None:
    assert parse_percentage(text) == expected
~~~

An identifier should express why the case exists, not merely repeat its data. Large parameter tables can become an undocumented alternative programming language. If rows require many flags and conditional assertions, separate behavioural rules or build domain-specific case objects.

Indirect parameterisation can feed parameters through fixtures, but it makes data flow less immediate. Use it when construction genuinely belongs to a fixture lifecycle, not to demonstrate framework cleverness.

Parameterisation composes multiplicatively. Two decorators with 5 and 7 values produce 35 cases. This is useful for deliberate cross-products but can inflate time without increasing behavioural diversity. Pair values explicitly where only certain combinations have meaning.

### Worked example 12.2F — Typed case records

~~~python
from dataclasses import dataclass

import pytest


@dataclass(frozen=True)
class RejectionCase:
    text: str
    message: str


REJECTION_CASES = [
    RejectionCase("-1", "percentage must be within 0..100"),
    RejectionCase("101", "percentage must be within 0..100"),
    RejectionCase("", "percentage must be an integer"),
    RejectionCase("3.5", "percentage must be an integer"),
]


@pytest.mark.parametrize(
    "case",
    REJECTION_CASES,
    ids=lambda case: repr(case.text),
)
def test_parse_percentage_rejections(case: RejectionCase) -> None:
    with pytest.raises(ValueError, match=case.message):
        parse_percentage(case.text)
~~~

The record names fields and lets a type checker inspect table construction. There is one subtle defect: <code>match</code> interprets its string as a regular expression, so punctuation in future messages could acquire special meaning. When exact literal text is intended, escape it:

~~~python
import re


with pytest.raises(ValueError, match=re.escape(case.message)):
    parse_percentage(case.text)
~~~

Better still, public exception types can carry structured attributes so tests do not depend on wording intended for humans.

> **Common misconception 12.23 — “Parameterisation removes duplication by definition.”**  
> It removes repeated test control flow. A table that conflates unrelated contracts can reduce clarity and make one change affect conceptually independent evidence.

### 12.5.4 Exceptions, warnings, and causal structure

An exception test should constrain the narrowest statement expected to raise. This test is weak:

~~~python
def test_invalid_record_weak() -> None:
    with pytest.raises(ValueError):
        record = make_valid_record()
        serialised = encode(record)
        parse(serialised + b"!")
~~~

If setup unexpectedly raises <code>ValueError</code>, the test passes without exercising the parser. Move setup outside the context:

~~~python
def test_parser_rejects_trailing_byte() -> None:
    record = make_valid_record()
    serialised = encode(record)

    with pytest.raises(ParseError) as captured:
        parse(serialised + b"!")

    assert captured.value.offset == len(serialised)
    assert captured.value.code == "trailing-data"
~~~

The test checks type and structured details. If exception chaining is part of the diagnostic contract, inspect <code>__cause__</code>; avoid exposing a library-specific cause as public API unless compatibility requires it.

Warnings signal suspicious or deprecated behaviour without necessarily stopping execution. Pytest can assert them:

~~~python
def test_legacy_name_reports_deprecation() -> None:
    with pytest.warns(
        DeprecationWarning,
        match="use new_name",
    ):
        legacy_name()
~~~

A warning policy in CI can promote unexpected warnings to failures while permitting explicitly tested deprecations. Blanket suppression converts advance notice of incompatibility into a later surprise.

### 12.5.5 Marks, skips, and expected failures

A **mark** attaches metadata used by pytest and plugins. Projects commonly declare categories such as <code>integration</code>, <code>slow</code>, or <code>requires_postgres</code>. Register custom marks so misspellings do not silently create new categories under permissive settings.

~~~python
import pytest


@pytest.mark.integration
def test_repository_round_trip(postgres_repository: Repository) -> None:
    account = Account("A-1", 500)
    postgres_repository.save(account)
    assert postgres_repository.get("A-1") == account
~~~

A **skip** says the test cannot or should not run in this environment. An **expected failure**, represented by pytest’s <code>xfail</code>, says a known defect or unsupported case is expected to fail. They communicate different states:

- skip: evidence was not attempted under this condition;
- xfail: the test ran or was selected under an expectation of failure;
- pass: expected relation held;
- xpass: an expected failure unexpectedly passed and may indicate repair, environmental variation, or a weak test.

Use strict expected failures where an unexpected pass should force review. Every persistent skip or expected failure needs a reason, owner, and removal condition. Otherwise the suite accumulates silently abandoned claims.

> **Common misconception 12.24 — “A skipped test is harmless because it is not failing.”**  
> It is an explicit absence of evidence. A rising or environment-specific skip count can conceal that the most important integration path is never exercised.

### 12.5.6 Configuration and reproducible invocation

Pytest configuration can reside in project-standard files, including <code>pyproject.toml</code> under the framework’s documented table. Configuration controls paths, warning policy, markers, default options, and plugin behaviour. Keep essential policy in the repository rather than in a developer’s shell alias.

Illustrative configuration:

~~~toml
[tool.pytest.ini_options]
minversion = "8.0"
addopts = [
    "--strict-config",
    "--strict-markers",
    "-ra",
]
testpaths = ["tests"]
xfail_strict = true
filterwarnings = [
    "error",
]
markers = [
    "integration: exercises real component boundaries",
    "slow: exceeds the ordinary focused-test budget",
]
~~~

This is a project policy, not a universally optimal configuration. Promoting all warnings can expose warnings emitted by dependencies beyond immediate control; manage narrow, documented exceptions while working upstream or upgrading.

The effective test environment includes the Python implementation and version, operating system, dependency resolution, locale, timezone, environment variables, external services, and framework plugins. Capture versions in CI and reproduce from declared inputs.

Plugins execute within the test process and can affect collection and hooks. Treat them as build dependencies: constrain compatible versions, review provenance, and avoid assuming a globally installed plugin exists.

> **Common misconception 12.25 — “The command pytest and python -m pytest are interchangeable.”**  
> They may resolve to the same installation, but the shell script can belong to a different interpreter. Module invocation makes the interpreter–environment relationship explicit.
