# 12.6 Fixtures and lifetime scopes

A pytest fixture is a function whose return or yielded resource is injected into requesting tests by name and dependency graph.

```python
from collections.abc import Iterator
from pathlib import Path

import pytest


@pytest.fixture
def sample_file(tmp_path: Path) -> Path:
    path = tmp_path / "sample.txt"
    path.write_text("alpha\nbeta\n", encoding="utf-8")
    return path
```

`tmp_path` is itself a pytest fixture providing a unique temporary directory as a `Path`. The fixture creates controlled exact bytes via a text contract and returns the path.

Fixtures can use `yield` for cleanup:

```python
@pytest.fixture
def service() -> Iterator[Service]:
    instance = Service()
    instance.start()
    try:
        yield instance
    finally:
        instance.stop()
```

Fixture **scope** controls reuse across functions, classes, modules, packages, or the session. Broader scope can reduce setup cost but increases shared-state coupling. Select the narrowest scope compatible with the resource cost and isolation requirement.

A fixture that silently performs many unrelated steps makes tests hard to understand. Compose small fixtures through dependencies and name them by the state they establish.

### 12.6.1 Fixtures form a dependency graph

Pytest resolves fixture requests transitively. If fixture <code>order</code> requests <code>customer</code> and <code>repository</code>, then the test requesting <code>order</code> indirectly depends on both. This is a directed dependency graph; cycles are invalid.

~~~python
from collections.abc import Iterator

import pytest


@pytest.fixture
def repository() -> Iterator[InMemoryRepository]:
    instance = InMemoryRepository()
    try:
        yield instance
    finally:
        instance.close()


@pytest.fixture
def customer(repository: InMemoryRepository) -> Customer:
    value = Customer(identifier="C-17", credit_pence=10_000)
    repository.save_customer(value)
    return value


@pytest.fixture
def order(
    repository: InMemoryRepository,
    customer: Customer,
) -> Order:
    value = Order(identifier="O-3", customer_id=customer.identifier)
    repository.save_order(value)
    return value
~~~

Dependency names make some setup visible at the signature, but transitive effects remain hidden. If requesting <code>order</code> sends email or changes a global clock, the name is misleading. Fixtures should establish narrowly described state and avoid unrelated assertions. Assertions that fixture setup itself is valid can be appropriate when they detect infrastructure failure more clearly, but the fixture must not duplicate the behaviour under test.

### 12.6.2 Scope is a sharing contract

Fixture scopes—function, class, module, package, and session in ordinary pytest terminology—determine caching lifetime within a test run. A broader-scoped fixture cannot ordinarily depend on a narrower-scoped one because the narrower value would expire while the broader value remains.

Scope creates a sharing contract:

| Scope choice | Benefit | Principal risk |
|:---|:---|:---|
| function | strongest default isolation | repeated expensive setup |
| class/module | amortised local setup | mutation leaks among nearby tests |
| package/session | expensive service reused | broad coupling and order-dependent contamination |

If a session-scoped database service is expensive, keep the service process broad but create a fresh logical database, schema, or transaction per test. Separate **resource lifetime** from **test-data lifetime**.

Parallel test execution adds another dimension. A session fixture may be instantiated once per worker process, not once across every worker, depending on the plugin’s documented execution model. Port numbers, database names, and paths must be unique across workers.

> **Common misconception 12.26 — “Session scope is just a faster function scope.”**  
> It changes isolation and concurrency semantics. Any mutable state retained by the fixture can couple the entire suite.

### 12.6.3 Yield cleanup and partial setup failure

Code after a fixture’s <code>yield</code> performs teardown once execution reaches the yield. If setup fails before that point, later cleanup code is not reached. Acquire resources so each successful acquisition immediately establishes its cleanup, or use context managers and an <code>ExitStack</code>.

~~~python
from contextlib import ExitStack
from collections.abc import Iterator

import pytest


@pytest.fixture
def running_cluster() -> Iterator[Cluster]:
    with ExitStack() as stack:
        database = stack.enter_context(start_database())
        broker = stack.enter_context(start_broker())
        cluster = stack.enter_context(
            start_application(database=database, broker=broker)
        )
        yield cluster
~~~

If broker startup fails, the stack still closes the previously started database. On ordinary teardown it closes resources in reverse acquisition order. The context managers must themselves handle failures during entry where they have acquired partial resources.

Cleanup failure matters. A test can pass its behavioural assertion and then fail during teardown, correctly making the test item unsuccessful because the promised isolation was not restored. Preserve both the test failure and cleanup failure when the framework reports an exception group.

### 12.6.4 Factories and data builders

A fixture returns one value per cache scope. Tests needing several related values should often request a **factory fixture**—a callable that constructs values while retaining cleanup ownership:

~~~python
from collections.abc import Callable

import pytest


@pytest.fixture
def account_factory(
    repository: Repository,
) -> Callable[..., Account]:
    created: list[Account] = []

    def create(
        *,
        balance_pence: int = 0,
        status: AccountStatus = AccountStatus.ACTIVE,
    ) -> Account:
        account = Account(
            identifier=repository.next_identifier(),
            balance_pence=balance_pence,
            status=status,
        )
        repository.save(account)
        created.append(account)
        return account

    return create
~~~

If repository teardown deletes the whole isolated store, the local <code>created</code> list is unnecessary. If individual external objects require deletion, the fixture can yield the factory and clean recorded identifiers in a finally block.

A **test-data builder** provides valid defaults and permits explicit variation. Defaults reduce irrelevant noise but can hide why a value matters. A test for expired status should state the relevant expiry rather than inherit it accidentally from a “standard account”.

> **Common misconception 12.27 — “DRY requires all repeated test setup to become a fixture.”**  
> Test duplication can make each case locally intelligible. Extract setup when it represents one stable concept or lifecycle, not merely because three literal lines recur.

### 12.6.5 Temporary paths and filesystem assertions

The <code>tmp_path</code> fixture supplies a unique <code>pathlib.Path</code> for a test. It controls location, not every filesystem semantic. Permissions, case sensitivity, Unicode normalisation, atomic replacement, symbolic links, and durability remain platform-dependent.

~~~python
from pathlib import Path


def test_export_writes_exact_utf8_bytes(tmp_path: Path) -> None:
    destination = tmp_path / "report.txt"

    export_lines(["café", "東京"], destination)

    assert destination.read_bytes() == "café\n東京\n".encode("utf-8")
    assert list(tmp_path.iterdir()) == [destination]
~~~

Reading bytes makes encoding and newline assertions exact. The directory assertion checks absence of leaked temporary files, but its order assumption is safe only because exactly one entry is expected. A production export test should also cover pre-existing destinations, failure during write, and platform-specific replacement guarantees.

### 12.6.6 Controlled mutation with monkeypatch

Pytest’s <code>monkeypatch</code> fixture temporarily sets attributes, mapping entries, environment variables, current directory, or import paths and restores them after the requesting test. It is useful for legacy global dependencies and process configuration.

~~~python
def test_cache_directory_uses_environment(
    monkeypatch: pytest.MonkeyPatch,
    tmp_path: Path,
) -> None:
    selected = tmp_path / "cache"
    monkeypatch.setenv("LEDGER_CACHE_DIR", str(selected))

    assert cache_directory() == selected
~~~

The example assumes <code>cache_directory</code> reads the environment when called. If its module captured the value at import time, patching later will not change that binding. Prefer explicit configuration injection for core policy:

~~~python
@dataclass(frozen=True)
class Settings:
    cache_directory: Path
~~~

Use monkeypatch to control the outer configuration loader, not to make every internal dependency implicit.

Patching built-ins or framework internals can interfere with pytest itself. Keep patches narrow, use documented helpers, and restore them through fixture scope.

> **Common misconception 12.28 — “Monkeypatch changes the original object everywhere.”**  
> It changes a selected binding or mapping entry. Other modules that already bound the original name may continue to use it.

### 12.6.7 Capturing output and logs

Pytest provides fixtures such as <code>capsys</code> for text written through Python’s standard streams, <code>capfd</code> for file-descriptor-level output, and <code>caplog</code> for logging records. Selection depends on the channel the code actually uses.

~~~python
import logging


def test_rejection_log_has_identifier_but_not_payload(
    caplog: pytest.LogCaptureFixture,
) -> None:
    caplog.set_level(logging.WARNING, logger="ledger.imports")
    secret_payload = "account=17;token=do-not-record"

    reject_import("request-42", secret_payload)

    records = [
        record
        for record in caplog.records
        if record.name == "ledger.imports"
    ]
    assert len(records) == 1
    assert records[0].request_id == "request-42"
    assert secret_payload not in caplog.text
~~~

This is a confidentiality regression test over the chosen logger and formatting path. It does not inspect external log processors, exception reporters, or infrastructure metadata. Those need integration or operational controls.

Capturing output should test an intentional interface. If a library’s incidental debug print becomes asserted output, the test turns an implementation accident into a compatibility obligation.

> **Common misconception 12.29 — “Captured logs are just another return value.”**  
> Logs are an operational interface with retention, confidentiality, cardinality, and downstream parsing consequences. Assert stable event semantics rather than decorative wording unless wording is the contract.
