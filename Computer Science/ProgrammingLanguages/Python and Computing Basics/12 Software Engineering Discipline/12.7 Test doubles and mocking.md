# 12.7 Test doubles and mocking

A **test double** replaces a collaborator for a test purpose. Common roles include:

- **stub:** supplies predetermined responses;
- **fake:** provides a working but simplified implementation, such as an in-memory repository;
- **spy:** records calls for later assertions;
- **mock:** is configured with interaction expectations and verifies them.

Terminology varies across communities; name the behaviour rather than argue labels.

Test doubles are useful at slow, unreliable, destructive, or uncontrollable boundaries. Excessive mocking of internal method calls makes tests mirror implementation rather than behaviour, causing harmless refactoring to break them.

### Worked example 12.3 — Inject a clock

```python
from collections.abc import Callable
from datetime import datetime, timezone


def create_record(
    value: int,
    now: Callable[[], datetime] = lambda: datetime.now(timezone.utc),
) -> dict[str, object]:
    return {"value": value, "created_at": now()}
```

Test:

```python
def test_create_record_uses_supplied_clock() -> None:
    fixed = datetime(2026, 1, 2, 3, 4, tzinfo=timezone.utc)
    record = create_record(7, now=lambda: fixed)
    assert record == {"value": 7, "created_at": fixed}
```

The test controls time without patching a global module. The default lambda is immutable and intentionally retained; it reads the real clock only when called.

When patching is appropriate, patch the name looked up by the code under test, not necessarily the library’s original definition. Imports create bindings. Misplaced patches can give a false sense of control.

### 12.7.1 Classify doubles by behaviour, not library class

One object can play several double roles. An in-memory mailer that records messages both fakes delivery and spies on interactions. A generic mocking-library object becomes a stub when configured only to return data and a mock when the test establishes required calls. Role language explains why the double exists.

The important distinction is between **state verification** and **interaction verification**:

- state verification inspects the resulting value or state;
- interaction verification inspects calls made to collaborators.

Prefer state verification when externally meaningful state is accessible. Use interaction verification when the interaction itself is the required effect, such as “publish exactly one event after commit” or “do not call the payment gateway after local validation fails”.

### Worked example 12.3A — A recording fake with a narrow interface

~~~python
from dataclasses import dataclass, field


@dataclass
class RecordingNoticeSender:
    sent: list[Notice] = field(default_factory=list)
    next_identifier: int = 1

    def send(self, notice: Notice) -> str:
        self.sent.append(notice)
        identifier = f"notice-{self.next_identifier}"
        self.next_identifier += 1
        return identifier


def test_overdue_notification_contains_domain_information() -> None:
    sender = RecordingNoticeSender()

    provider_id = notify_overdue(
        account_id="A-7",
        email="reader@example.test",
        amount_pence=1_250,
        sender=sender,
    )

    assert provider_id == "notice-1"
    assert sender.sent == [
        Notice(
            recipient="reader@example.test",
            subject="Account A-7: payment overdue",
            body="Amount due: GBP 12.50",
        )
    ]
~~~

The fake contains no network, retry, authentication, or provider-specific validation. It supports a focused policy claim. A contract test for the real sender must establish payload mapping, error translation, timeouts, idempotency, and the provider test environment’s actual semantics.

> **Common misconception 12.30 — “A fake proves the real adapter will behave the same way.”**  
> A fake supplies controlled semantics chosen by the test author. Only shared contract tests and real integration evidence can detect divergence between fake and adapter.

### 12.7.2 Patching follows name resolution

Suppose <code>ledger.reminders</code> contains:

~~~python
from ledger.mail import send


def remind(address: str) -> None:
    send(address, "Payment due")
~~~

The function resolves the global name <code>send</code> in <code>ledger.reminders</code>. Patching <code>ledger.mail.send</code> after import does not change the already established binding. Patch <code>ledger.reminders.send</code>:

~~~python
from unittest.mock import Mock, patch


def test_remind_sends_expected_message() -> None:
    fake_send = Mock()
    with patch("ledger.reminders.send", fake_send):
        remind("person@example.test")

    fake_send.assert_called_once_with(
        "person@example.test",
        "Payment due",
    )
~~~

This mechanical rule follows Python’s namespace model from Chapter 8. It is also a design signal: pervasive string-based patching indicates hidden dependencies. Supplying a <code>NoticeSender</code> explicitly usually makes the relationship clearer and statically inspectable.

Patching where used can still be fragile if refactoring an import changes the lookup site while preserving behaviour. Test public outcomes where possible.

### 12.7.3 Specifications and autospeccing

Unconstrained mock objects often accept arbitrary attribute names and argument lists. A misspelled method can make both production and test agree on an interface that does not exist. A **specification-constrained mock** limits accessible members; **autospeccing** additionally derives callable signatures from a target.

~~~python
from unittest.mock import create_autospec


def test_service_supplies_idempotency_key() -> None:
    gateway = create_autospec(PaymentGateway, instance=True)
    gateway.charge.return_value = ChargeResult("accepted", "P-9")

    result = settle_invoice(
        invoice=Invoice("I-4", 1_500),
        gateway=gateway,
        idempotency_key="request-82",
    )

    assert result.provider_identifier == "P-9"
    gateway.charge.assert_called_once_with(
        amount_pence=1_500,
        idempotency_key="request-82",
    )
~~~

Autospeccing checks Python-level shape, not semantic behaviour. It does not know that keys must be unique, that an amount uses pence, or that retryable exceptions can occur after the provider commits.

Mock return values and child attributes are themselves mocks by default in many libraries. If the code accidentally traverses an unconfigured chain, it may continue rather than fail. Configure only required calls and prefer small typed fakes for richer behaviour.

> **Common misconception 12.31 — “A mock with a spec is equivalent to the collaborator.”**  
> It resembles selected names and signatures. It does not reproduce state, protocol ordering, latency, failures, transactions, or external interpretation.

### 12.7.4 Interaction contracts and overspecification

An interaction assertion is strong when it protects externally relevant multiplicity, ordering, or content. It is brittle when it records incidental decomposition.

Suppose an implementation computes a balance by calling <code>repository.debits()</code> and <code>repository.credits()</code>. A test asserting both calls breaks if the repository gains one <code>balance()</code> query, even when the public contract is unchanged. Unless query count is a performance requirement, assert the returned balance and test the repository’s query behaviour separately.

Interaction testing is warranted for:

- no call after rejected validation;
- one charge per idempotency identity;
- commit before publication under an outbox protocol;
- cleanup after partial acquisition;
- audit emission with required fields;
- bounded retries under classified transient failures.

Ordering assertions should state why order matters. “Call A before B” can be a transaction guarantee or merely current implementation sequence.

### Worked example 12.3B — Verify an absence of external effect

~~~python
from unittest.mock import create_autospec

import pytest


def test_invalid_amount_never_reaches_gateway() -> None:
    gateway = create_autospec(PaymentGateway, instance=True)

    with pytest.raises(ValueError, match="positive"):
        charge_account(-1, gateway=gateway)

    gateway.charge.assert_not_called()
~~~

The negative interaction is part of the contract: invalid local input must not initiate an external charge. If the gateway can be called through other dependencies, one mock assertion is not a system-wide absence proof; architecture and broader tests must control those channels.

### 12.7.5 Time, randomness, and unique identifiers

Time is more than one function returning “now”. Systems use:

- civil time with timezone and calendar rules;
- monotonic elapsed time for deadlines;
- CPU time;
- scheduled events;
- externally assigned timestamps;
- logical or hybrid clocks in distributed systems.

Inject the concept needed. A fake civil clock should not be used to test monotonic timeout arithmetic unless it models that clock.

~~~python
from datetime import datetime, timedelta, timezone


@dataclass
class FakeClock:
    current: datetime

    def now(self) -> datetime:
        return self.current

    def advance(self, delta: timedelta) -> None:
        if delta < timedelta():
            raise ValueError("fake clock cannot move backwards")
        self.current += delta
~~~

Randomness can likewise be represented by a supplied generator or by domain operations such as <code>choose_token()</code>. A fixed seed reproduces a pseudo-random sequence; it does not make tokens secure. Tests for cryptographic token generation should verify shape, error handling, and use of an approved source, not infer unpredictability from a small uniqueness sample.

> **Common misconception 12.32 — “Mock every nondeterministic function to make a unit test pure.”**  
> Control nondeterminism relevant to the claim. Over-mocking can erase scheduling, persistence, or protocol interactions that the test level is meant to examine.
