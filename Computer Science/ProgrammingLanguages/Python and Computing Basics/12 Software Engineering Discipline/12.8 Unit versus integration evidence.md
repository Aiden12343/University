# 12.8 Unit versus integration evidence

Unit tests isolate logic and localise failure. Integration tests expose misunderstandings between real components: SQL syntax, encoding, filesystem semantics, schema migrations, network framing, and packaging.

For a repository interface:

```python
class AccountRepository(Protocol):
    def save(self, account: Account) -> None: ...
    def get(self, identifier: str) -> Account | None: ...
```

Core service unit tests can use an in-memory fake. The production database adapter requires contract tests against the real database technology. Running only the fake proves the service uses the interface as the fake implements it; it does not prove the adapter, transaction, schema, encoding, or database isolation behaviour.

Use a **test pyramid** only as a heuristic: many focused tests, fewer expensive boundary tests, and a small number of end-to-end paths. The right distribution depends on risk and system architecture. A critical integration can deserve many cases.

### 12.8.1 A test-level taxonomy by boundary

Test-level labels become useful when a project defines them operationally. One workable policy is:

| Level | In-process code | Filesystem | Database | Network | Principal purpose |
|:---|:---:|:---:|:---:|:---:|:---|
| unit | narrow policy unit | fake or temporary if intrinsic | fake | none | logic and local contracts |
| component | assembled package/service | permitted | ephemeral real engine or faithful substitute | loopback/in-process | internal component collaboration |
| integration | selected real boundary | real where relevant | real selected technology | selected real protocol/service substitute | interface and semantic compatibility |
| system | deployed assembly | deployment-realistic | deployment-realistic | real entry point | end-to-end requirements |
| acceptance | any necessary | representative | representative | representative | stakeholder acceptance criteria |

This table is a local convention, not an international law. A filesystem parser’s unit boundary may legitimately use <code>tmp_path</code> because path semantics are intrinsic. State what is real, controlled, and omitted.

A **contract test** applies a shared behavioural suite to every implementation of an interface. For repository adapters:

~~~python
from collections.abc import Callable
from contextlib import AbstractContextManager


class RepositoryContract:
    make_repository: Callable[
        [],
        AbstractContextManager[AccountRepository],
    ]

    def test_missing_identifier_returns_none(self) -> None:
        with self.make_repository() as repository:
            assert repository.get("missing") is None

    def test_saved_account_round_trips(self) -> None:
        with self.make_repository() as repository:
            account = Account("A-2", 700)
            repository.save(account)
            assert repository.get("A-2") == account
~~~

Concrete test classes or parameterised factories can bind the in-memory and database implementations. The shared suite checks selected substitutability. Adapter-specific cases remain necessary for transactions, indexes, serialisation, and errors.

### 12.8.2 Databases: rollback is not complete isolation

Wrapping each test in a transaction and rolling it back is fast, but it can differ from production:

- code may commit internally, ending the test transaction;
- other connections cannot see uncommitted setup;
- after-commit hooks never execute;
- sequences may not roll back;
- locks and isolation phenomena change;
- schema and migration behaviour are untested.

Use a mixture appropriate to risk: transactional cases for ordinary repository behaviour, clean-database cases for commit/recovery behaviour, and migration tests that create an old schema and apply the actual migration chain.

A migration must be evaluated in both directions conceptually even if rollback is not supported: what happens to existing rows, concurrent application versions, constraints, indexes, duration, locks, and partial failure? “The migration command exited zero on an empty database” is weak evidence.

### Worked example 12.3C — Test constraints at the database boundary

Assume the domain requires unique external identifiers. A unit fake using a dictionary naturally overwrites duplicates and may conceal the intended rejection. An integration test should execute against the configured database:

~~~python
def test_external_identifier_is_unique(
    repository: SqlAccountRepository,
) -> None:
    repository.save(Account("external-7", 100))

    with pytest.raises(DuplicateAccountError):
        repository.save(Account("external-7", 200))

    assert repository.get("external-7") == Account("external-7", 100)
~~~

The test checks translated failure and preservation of the first row. Separate inspection of schema migration establishes that the uniqueness constraint exists rather than being enforced only by a race-prone pre-query.

> **Common misconception 12.33 — “SQLite is a drop-in test substitute for every SQL database.”**  
> SQL dialects, type coercion, constraints, concurrency, transactions, query planning, and extensions differ. It is useful when its semantics are the intended boundary or when differences are irrelevant and explicitly covered elsewhere.

### 12.8.3 Hermetic tests and external dependencies

A **hermetic test** depends only on declared, controlled inputs and isolates its outputs. Hermeticity improves reproducibility and permits parallel execution. It is a direction, not an excuse to eliminate every real dependency.

Tests calling a public third-party service are vulnerable to rate limits, changing data, outages, cost, and destructive effects. Prefer:

1. unit tests against a narrow client abstraction;
2. protocol tests against a local fake server that validates requests and emits difficult responses;
3. a smaller provider sandbox or contract suite using dedicated identities;
4. monitored production canaries where authorised.

A fake HTTP response that returns ideal JSON cannot reveal TLS, DNS, proxy, authentication, redirect, compression, framing, or provider-schema behaviour. Each omitted layer is an explicit limit.

### 12.8.4 End-to-end tests and observability

An end-to-end test enters through a production-like interface and observes a user-relevant result across the assembled system. It offers broad composition evidence but weak localisation: many causes can produce one failure. Keep flows few, consequential, and diagnosable.

Stable end-to-end tests require test hooks that respect production architecture: dedicated tenants, queryable job status, correlation identifiers, controllable external sandboxes, and idempotent cleanup. Bypassing the interface to seed data can be reasonable when the seed mechanism is separately validated and the bypass does not remove the behaviour under test.

> **Common misconception 12.34 — “End-to-end tests give the highest-quality evidence.”**  
> They give broad evidence at high cost and low localisation. Focused tests can establish boundary cases and invariants much more thoroughly; a sound strategy combines levels.
