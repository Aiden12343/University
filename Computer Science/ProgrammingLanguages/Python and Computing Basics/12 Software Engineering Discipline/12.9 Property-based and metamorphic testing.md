# 12.9 Property-based and metamorphic testing

An **example-based test** supplies selected concrete cases. **Property-based testing** generates many inputs satisfying strategies and checks general properties. A framework such as Hypothesis also shrinks failures towards a simpler counterexample.

For encode/decode functions:

```python
from hypothesis import given, strategies as st


@given(st.text())
def test_utf8_round_trip(text: str) -> None:
    assert text.encode("utf-8").decode("utf-8") == text
```

The property is round-trip identity for every generated Unicode string under UTF-8. It does not prove compatibility with arbitrary invalid byte strings, streaming boundaries, or external encoders.

A **metamorphic relation** states how outputs should relate when inputs are transformed, useful when exact oracles are difficult. Sorting a sequence twice should give the same result as sorting once; adding a zero-valued transaction should preserve a total under the relevant model; permuting inputs should not change a set result.

Generated tests are only as sound as their properties and strategies. A property restating the implementation can reproduce its defect. Include domain boundaries and independently justified relations.

### 12.9.1 Properties are quantified specifications

A property test approximates a universally quantified statement: for every generated value satisfying the precondition, a relation holds. Because execution samples finitely many values, the result remains empirical evidence. The specification, however, is more general than a list of examples.

Good properties often combine:

- **invariants**, which remain true after an operation;
- **round trips**, where decoding reverses encoding within a defined domain;
- **idempotence**, where repeating an operation has no further relevant effect;
- **commutativity**, where operand order should not matter;
- **monotonicity**, where increasing an input cannot decrease an output under stated conditions;
- **conservation**, where a quantity is neither created nor destroyed;
- **equivalence**, where two independent formulations agree.

Algebraic terms require domain constraints. Floating-point addition is not generally associative; text normalisation may be idempotent for one Unicode form but not preserve byte identity; database retries may be idempotent only when the same key and payload are used.

### Worked example 12.3D — Properties for fair allocation

For <code>allocate(total, parts)</code>, define:

~~~python
from hypothesis import given
from hypothesis import strategies as st


@given(
    total=st.integers(min_value=0, max_value=10**12),
    parts=st.integers(min_value=1, max_value=10_000),
)
def test_allocate_conserves_and_balances(
    total: int,
    parts: int,
) -> None:
    shares = allocate(total, parts)

    assert len(shares) == parts
    assert sum(shares) == total
    assert all(share >= 0 for share in shares)
    assert max(shares) - min(shares) <= 1
~~~

No expected tuple is generated by copying the implementation. The properties still permit different fair orderings of the larger shares; if the contract requires earlier indices to receive remainders, add:

~~~python
    assert tuple(sorted(shares, reverse=True)) == shares
~~~

Strategy bounds here are modelling choices to keep memory and time finite. They do not imply Python integers stop at one trillion. Add focused examples at important operational limits.

### 12.9.2 Strategy design, filtering, and shrinking

A **generation strategy** describes how test inputs are produced. Construct valid values structurally rather than generating arbitrary values and rejecting almost all with a filter. Heavy filtering wastes attempts and can bias reachable shapes.

For a non-empty list of unique identifiers:

~~~python
identifiers = st.lists(
    st.text(
        alphabet=st.characters(
            whitelist_categories=("Lu", "Ll", "Nd"),
        ),
        min_size=1,
        max_size=20,
    ),
    min_size=1,
    max_size=50,
    unique=True,
)
~~~

The exact character strategy should follow the identifier contract. If identifiers are ASCII by specification, generating arbitrary Unicode is testing a different domain. If external input may contain Unicode but must be rejected, generate it in invalid-input properties.

**Shrinking** searches from a failing generated input towards a simpler counterexample while preserving failure. The minimal result is relative to the strategy and shrinker, not necessarily the semantic root cause. Preserve framework output and add a focused regression example when its domain significance deserves durable documentation.

> **Common misconception 12.35 — “Property-based testing automatically discovers edge cases.”**  
> A framework explores the space represented by its strategies and health settings. An omitted state, weak property, or over-filtered generator remains invisible.

### 12.9.3 Metamorphic and differential tests

When exact outputs are difficult to know, a metamorphic test compares related executions. For a search ranking system, adding a document that cannot match the query should not change the order of existing results under a declared ranking policy. For an image transformation, applying identity parameters should preserve pixels. For a compiler, inserting semantically dead code should not alter observable output.

**Differential testing** supplies the same input to independent implementations and compares results. It is powerful for parsers, numerical routines, protocol implementations, and refactors. Disagreement reveals at least one mismatch but does not identify which result is correct. Shared standards ambiguity and common dependencies can make all implementations agree wrongly.

~~~python
@given(st.lists(st.integers()))
def test_merge_sort_agrees_with_python_sorted(values: list[int]) -> None:
    assert merge_sort(values) == sorted(values)
~~~

Here Python’s built-in sorter is treated as a trusted reference for integer ordering. The test does not establish stability for objects whose keys compare equal unless the generated data makes identity/order observable.

### 12.9.4 Stateful property testing

A rule-based state machine generates sequences of commands and compares a system against an abstract model. This can expose defects requiring histories that example tests rarely anticipate: create, update, delete, retry, then query under a reused identifier.

The model must be simpler and independently justified. If it reuses production persistence methods, it ceases to be an oracle. Preconditions restrict which commands are legal in a model state; invariants are checked after transitions.

State-space growth is severe. Limit sequence length and value domains deliberately, retain found traces, and complement generation with named scenarios for safety-critical sequences.

> **Common misconception 12.36 — “A generated failing sequence is the explanation.”**  
> It is a reproducible observation. Debugging must still identify the first divergent state and causal defect; shrinking helps but does not supply causal reasoning.
