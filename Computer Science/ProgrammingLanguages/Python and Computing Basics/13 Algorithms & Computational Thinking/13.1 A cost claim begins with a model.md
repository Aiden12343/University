# 13.1 A cost claim begins with a model

An algorithm is judged not only by correctness but by resources. A **cost model** defines which elementary operations are counted and how input size is measured. Without it, “this is (O(n))” lacks a referent.

For scanning a sequence, (n) may mean element count and the model may charge constant cost per indexing, comparison, and loop step. If elements are arbitrarily large integers or comparisons are user-defined operations, those costs are not constant in their own input size. A useful analysis states the abstraction level.

Resources include:

- execution time or operation count;
- additional memory;
- data transfers and cache misses;
- storage or network I/O;
- parallel work and longest dependency path;
- energy or monetary cost under a deployment model.

**Input size** is a numeric measure of the instance. For a graph it may include vertices (V) and edges (E); for an integer it may be bit length rather than numeric magnitude; for a matrix it may include row and column counts.

### 13.1.1 Problems, instances, algorithms, and implementations

A **computational problem** specifies a relation between admissible inputs and acceptable outputs. One concrete input is an **instance**. An **algorithm** is a finite, unambiguous method that produces an acceptable output for every admitted instance and terminates under its preconditions. An **implementation** expresses an algorithm for a particular language, representation, runtime, and machine.

These levels must remain distinct. “Sort these records” is incomplete as a problem until it states:

- admitted record representations;
- the key or ordering relation;
- whether equal-key order must be stable;
- whether the input may be mutated;
- handling of incomparable keys and key-function failure;
- required output representation;
- resource constraints.

Merge sort is an algorithmic family. The implementation in §13.8 uses Python list slicing and allocation. A different merge-sort implementation can operate over external files, linked runs, or arrays of fixed-width records and have different constant factors and auxiliary-space costs while sharing the divide-and-merge idea.

A **specification** determines correctness; an implementation does not become its own specification merely because it runs. If a program returns one arbitrary shortest path where the problem requires every shortest path, it solves a different problem even if its output is individually short.

> **Common misconception 13.1 — “An algorithm is code.”**  
> Code is one representation of an algorithm plus representation, language, runtime, and engineering choices. The same algorithm can have many implementations, and visually similar code can implement different contracts.

### 13.1.2 Abstract machines and charged operations

A cost analysis is conducted relative to an **abstract machine**: a simplified model assigning costs to operations. Common models include:

- the **unit-cost random-access machine** (**RAM**) model, in which selected arithmetic, comparison, and random memory access take constant time;
- the **word-RAM** model, in which a machine word holds \(\Theta(\log n)\) bits and word operations cost constant time;
- the **comparison model**, in which information about order is obtained only through pairwise comparisons;
- the **bit-complexity model**, which charges according to operand bit lengths;
- the **external-memory** or **I/O model**, which emphasises transfers between fast and slow storage in blocks;
- a **parallel model**, which distinguishes total work from dependency depth or span.

No model is universally correct. It is an abstraction chosen to preserve costs relevant to a question.

Python complicates unit-cost analysis because ostensibly simple operations can invoke arbitrary methods. The expression <code>a &lt; b</code> may call <code>a.__lt__</code>, fall back to another method, allocate results, or raise. Integer addition costs depend on operand digit length once values exceed fixed machine-word representations. A list index is treated as \(O(1)\) at the data-structure level, although bounds checking, cache access, and reference-count effects contribute finite machine cost in CPython.

State analysis at two levels where necessary:

> Under a model charging one unit per comparison and list access, binary search performs \(\Theta(\log n)\) comparisons. If each comparison of keys of length \(m\) costs \(O(m)\), its comparison work is \(O(m\log n)\), excluding key derivation.

The second statement refines rather than contradicts the first.

### Worked example 13.1A — Count primitive comparisons exactly

~~~python
def all_pairs_equal(values: list[int]) -> bool:
    for left in range(len(values)):
        for right in range(left + 1, len(values)):
            if values[left] == values[right]:
                return True
    return False
~~~

For \(n\) distinct values, the inner loop executes

\[
(n-1)+(n-2)+\cdots+1
=
\frac{n(n-1)}{2}
\]

equality comparisons. Hence the worst-case comparison count is exactly \(n(n-1)/2\), which lies in \(\Theta(n^2)\).

If the first two values are equal, the function returns after one comparison. The code therefore has best-case \(\Theta(1)\) and worst-case \(\Theta(n^2)\) comparison cost. An average requires a probability distribution over values and their order.

The type annotation restricts the intended static input to lists of integers, but Python integers have unbounded language-level magnitude. Equality of enormous integers is not necessarily one hardware operation. The exact count and the bit-level time bound are separate claims.

> **Common misconception 13.2 — “Every Python operator counts as one step.”**  
> One step is a modelling decision. Operators dispatch on types and may perform work proportional to value size or execute user code.

### 13.1.3 Encoding determines input size

Complexity is expressed as a function of an encoded instance’s size, not merely the magnitude of a number printed on the page. An integer \(N\) written in binary needs

\[
\lfloor \log_2 N \rfloor + 1
\]

bits for \(N>0\). An algorithm taking \(O(N)\) steps is therefore exponential in the bit length \(b=\Theta(\log N)\), because \(N\) can be \(\Theta(2^b)\).

This explains **pseudo-polynomial** algorithms such as the target-indexed coin-change table. Their time is polynomial in a numeric target but not necessarily in the number of bits needed to encode it.

For compound inputs, introduce separate variables rather than hiding relations:

- string count \(n\) and total character count \(L\);
- graph vertices \(V\) and edges \(E\);
- matrix dimensions \(r\) and \(c\);
- database records \(n\), key bytes \(k\), and output size \(z\).

A graph encoded as an adjacency matrix already occupies \(\Theta(V^2)\) entries; an adjacency-list input occupies \(\Theta(V+E)\). Calling both input size “\(V\)” obscures the cost of reading the representation.

The output itself can impose a lower bound. Producing every subset of \(n\) distinct items requires writing \(2^n\) subsets, so no algorithm can take polynomial total time in \(n\) while explicitly emitting them all.

> **Common misconception 13.3 — “Linear in the input number is efficient.”**  
> If the number is compactly encoded, linear in its magnitude can be exponential in representation length. Complexity follows the encoding read by the algorithm.

### 13.1.4 Worst, best, average, expected, and amortised costs

For inputs of size \(n\):

- **worst-case cost** is the maximum cost over admitted inputs of that size;
- **best-case cost** is the minimum;
- **average-case cost** is an expectation over a stated distribution of inputs;
- **expected cost** often refers to expectation over an algorithm’s internal randomness for a fixed input, though authors must state the probability space;
- **amortised cost** bounds a sequence of operations without requiring probability.

The terms are not interchangeable. Randomised quicksort has expected \(O(n\log n)\) comparisons for every fixed input under a suitable random pivot process, but a particular random sequence can produce quadratic work. A hash-table lookup can have expected constant cost under hashing assumptions and linear worst case under collision.

Median or percentile empirical latency is neither average-case asymptotic complexity nor expected algorithmic cost. It describes measured observations from a workload and environment.

### 13.1.5 Space, mutation, and retained resources

**Auxiliary space** is storage used in addition to the input and required output under a declared representation. **Total space** includes them. In-place is an imprecise phrase unless the allowed additional storage is stated: \(O(1)\) words, \(O(\log n)\) stack frames, or reuse of input cells.

Python-specific accounting can include:

- list objects and their reference arrays;
- element objects, which may be shared rather than copied;
- iterator and generator frames;
- recursion frames;
- temporary keys;
- allocator capacity not visible through logical length;
- retained objects caused by references.

When <code>values[:middle]</code> creates a list slice, it copies references into a new list, not necessarily the element objects. Calling that operation \(O(n)\) additional reference storage is more precise than saying it “copies all data”.

Peak space and cumulative allocation differ. A program can allocate gigabytes cumulatively while releasing each block and maintaining a small peak; allocator retention can make operating-system resident memory differ again.

> **Common misconception 13.4 — “An in-place algorithm uses no extra memory.”**  
> It normally means bounded or sublinear auxiliary element storage under a convention. Call stacks, local variables, object headers, and runtime machinery still occupy memory.

### 13.1.6 Problem lower bounds and algorithm upper bounds

An **upper bound** shows that a particular algorithm uses no more than some resource. A **lower bound** shows that every algorithm in a stated model, or one particular algorithm, needs at least some resource. Matching bounds identify an asymptotically optimal algorithm within that model.

Reading an unsummarised array of \(n\) values to determine whether it contains a negative has a worst-case \(\Omega(n)\) inspection lower bound: if an algorithm leaves a position unread, an adversary can place the only negative there while keeping all observed positions equal.

This lower bound does not apply if preprocessing has constructed a maintained minimum, if the input promises sorted order, or if approximate probabilistic answers are allowed. Lower bounds attach to information and model assumptions.

An algorithm with \(O(n\log n)\) upper bound is not automatically optimal. The comparison-sorting lower bound applies to arbitrary order through comparisons; bounded-integer sorting can use key structure outside that model.

> **Common misconception 13.5 — “Big-O describes the problem’s complexity.”**  
> A stated algorithm has an upper bound. A problem receives a model-relative lower or upper complexity only after quantifying over admissible algorithms and encodings.
