# 13.11 Stacks, queues, and heaps

A **stack** follows last-in, first-out discipline. Python lists support `append` and `pop` at the end with amortised (O(1)) behaviour.

A **queue** follows first-in, first-out discipline. `deque.append` and `deque.popleft` provide efficient endpoints.

A **priority queue** removes an item of minimum or maximum priority rather than earliest insertion. A binary **heap** is a nearly complete tree commonly stored in an array. In a min-heap, every parent key is no greater than its children.

With zero-based index (i):

- left child: (2i+1);
- right child: (2i+2);
- parent for (i>0): ((i-1)//2).

`heapq` implements a min-heap on a list:

```python
import heapq

pending: list[tuple[int, int, str]] = []
sequence = 0

heapq.heappush(pending, (2, sequence, "normal"))
sequence += 1
heapq.heappush(pending, (1, sequence, "urgent"))

priority, _, task = heapq.heappop(pending)
```

Push and pop cost (O(\log n)); viewing `pending[0]` costs (O(1)). The sequence field supplies deterministic tie-breaking and prevents comparison of non-comparable task objects. A heap’s array is not globally sorted; only the heap invariant is promised.

### 13.11.1 Stack and queue semantics

The words stack and queue name access disciplines, not particular classes. A stack exposes the most recently inserted unremoved item; a queue exposes the earliest. Their principal operations are conventionally named:

| ADT | Insert | Inspect next | Remove next | Discipline |
|---|---|---|---|---|
| stack | push | top/peek | pop | LIFO |
| queue | enqueue | front/peek | dequeue | FIFO |
| deque | append at either end | inspect either end | remove either end | chosen by caller |
| priority queue | insert with priority | minimum/maximum | extract minimum/maximum | priority order |

A **deque** (double-ended queue) permits efficient insertion and removal at both ends. Python’s <code>collections.deque</code> documents approximately \(O(1)\) appends and pops at either end. Indexed access is fast near the ends but slows toward the middle; it is not a drop-in dynamic array for arbitrary indexing.

Removing the front of a Python list with <code>pop(0)</code> shifts all remaining references and is \(O(n)\). Maintaining a front index avoids shifts but can retain consumed objects and unused capacity unless compaction is designed. A deque encapsulates the appropriate representation.

Bounded deques support streaming policies. With <code>maxlen=k</code>, appending to a full deque discards an item from the opposite end. This is useful for recent-history windows but is destructive by contract:

~~~python
from collections import deque

recent: deque[int] = deque(maxlen=3)
for reading in [10, 11, 12, 13]:
    recent.append(reading)

assert list(recent) == [11, 12, 13]
~~~

The asymptotic endpoint guarantee does not specify a single-node implementation. CPython uses a block-linked representation as an implementation detail, balancing locality and endpoint growth. Portable code should rely on documented operations, not block sizes.

> **Common misconception 13.45 — “A queue is a list where index zero is the front.”**  
> That is one interface mapping but a poor Python-list implementation for repeated removal. An ADT does not dictate a representation.

### 13.11.2 Monotone stacks and queues

A **monotone stack** retains items in non-decreasing or non-increasing order while scanning input. It answers “next greater”, span, and boundary questions in linear total time because each item is pushed once and popped at most once.

~~~python
def next_greater_indices(values: list[int]) -> list[int | None]:
    result: list[int | None] = [None] * len(values)
    pending: list[int] = []

    for index, value in enumerate(values):
        while pending and values[pending[-1]] < value:
            earlier = pending.pop()
            result[earlier] = index
        pending.append(index)

    return result
~~~

The stack contains unresolved indices in decreasing value order and increasing index order. When a new value exceeds the stack top, it is the first greater value for that top: any intervening value failed to resolve it. Each index enters and leaves the stack at most once, giving \(\Theta(n)\) time despite a <code>while</code> nested inside a <code>for</code>.

A **monotone deque** similarly supports sliding-window extrema. Remove expired indices from one end and dominated values from the other; each index undergoes a constant number of deque operations across the scan. This is another aggregate-analysis pattern.

> **Common misconception 13.46 — “A while loop inside a for loop makes the monotone-stack algorithm quadratic.”**  
> Count operations globally: no index can be popped twice. The total number of inner iterations is at most \(n\).

### 13.11.3 Heap construction and invariant restoration

For a zero-based min-heap array \(a\), the invariant is

\[
a[\lfloor(i-1)/2\rfloor]\le a[i]
\quad\text{for every }i>0.
\]

Insertion appends at the final leaf position and **sifts up** while the new key is smaller than its parent. Removing the minimum replaces the root with the final item and **sifts down** toward its smaller child. Only one root-to-leaf path can violate the invariant after either local change.

~~~python
class MinHeap:
    def __init__(self) -> None:
        self._data: list[int] = []

    def push(self, value: int) -> None:
        data = self._data
        data.append(value)
        child = len(data) - 1

        while child > 0:
            parent = (child - 1) // 2
            if not data[child] < data[parent]:
                break
            data[parent], data[child] = data[child], data[parent]
            child = parent

    def pop(self) -> int:
        if not self._data:
            raise IndexError("pop from empty heap")

        minimum = self._data[0]
        final = self._data.pop()
        if self._data:
            self._data[0] = final
            self._sift_down(0)
        return minimum

    def _sift_down(self, parent: int) -> None:
        data = self._data
        while True:
            left = 2 * parent + 1
            if left >= len(data):
                return
            child = left
            right = left + 1
            if right < len(data) and data[right] < data[left]:
                child = right
            if not data[child] < data[parent]:
                return
            data[parent], data[child] = data[child], data[parent]
            parent = child
~~~

The array shape is implicitly complete: all levels are full except possibly the last, filled left to right. Therefore height is \(\lfloor\log_2 n\rfloor\), so either sift performs \(O(\log n)\) comparisons and swaps.

### 13.11.4 Stable priorities and incomparable payloads

Python compares tuples lexicographically. A queue entry <code>(priority, sequence, task)</code> first compares priority, then sequence, and reaches the payload only if both tie. A strictly increasing sequence number therefore:

- supplies FIFO ordering among equal priorities;
- prevents comparison of payload objects;
- makes replay deterministic given the same insertion sequence.

This is stability at the priority-queue interface, not heap stability in memory. Equal-priority entries may move internally as long as extraction obeys the tuple order.

Max-priority behaviour for numeric priorities can negate the number, but negation is not generic and special floating values require policy. Python 3.12’s <code>heapq</code> interface is a min-heap interface; later versions may offer additional max-heap conveniences, but a 3.12-targeted work should not assume them.

> **Common misconception 13.47 — “Equal priorities are automatically removed in insertion order.”**  
> A heap promises only its comparison order. Add an explicit monotone sequence component when stable tie-breaking is required.

### 13.11.5 Updating and deleting heap entries

A binary heap can update a known array position in \(O(\log n)\), but Python’s public <code>heapq</code> does not maintain a mapping from application identities to current positions. Searching for an entry would cost \(O(n)\), and swaps would continually invalidate external indices.

A common strategy is **lazy deletion**:

~~~python
import heapq
import itertools
from dataclasses import dataclass, field


@dataclass(order=True)
class QueueEntry:
    priority: int
    sequence: int
    task_id: str = field(compare=False)


class MutablePriorityQueue:
    def __init__(self) -> None:
        self._heap: list[QueueEntry] = []
        self._current: dict[str, QueueEntry] = {}
        self._sequence = itertools.count()

    def put(self, task_id: str, priority: int) -> None:
        entry = QueueEntry(priority, next(self._sequence), task_id)
        self._current[task_id] = entry
        heapq.heappush(self._heap, entry)

    def remove(self, task_id: str) -> None:
        del self._current[task_id]

    def pop(self) -> tuple[str, int]:
        while self._heap:
            entry = heapq.heappop(self._heap)
            if self._current.get(entry.task_id) is entry:
                del self._current[entry.task_id]
                return entry.task_id, entry.priority
        raise KeyError("priority queue is empty")
~~~

Updating a task calls <code>put</code> again. The mapping points to the newest entry; older heap entries become stale. <code>pop</code> discards stale entries until it finds the identical current one. The identity test matters because a newly created entry could compare equal by fields.

Logical queue size is <code>len(self._current)</code>, not heap-array length. Repeated updates without extraction can accumulate stale entries and consume memory. A production implementation may periodically rebuild the heap in \(O(n)\), using an amortised threshold. Exceptions and concurrency also need policy.

The same lazy pattern appeared in Dijkstra’s algorithm: a distance-map check rejects obsolete priorities. A technique should be recognised by its invariant, not memorised as isolated code.

> **Common misconception 13.48 — “A heap supports arbitrary priority changes in \(O(\log n)\) by itself.”**  
> The structural repair is logarithmic once the entry is located. Identity-to-position maintenance or lazy stale entries are additional representation choices with their own costs.
