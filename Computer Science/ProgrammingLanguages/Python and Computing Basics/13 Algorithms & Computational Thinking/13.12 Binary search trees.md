# 13.12 Binary search trees

A **binary search tree** (**BST**) stores keys so every key in a node’s left subtree is less under the chosen policy and every key in the right subtree is greater, with duplicate handling explicitly defined.

```python
@dataclass(slots=True)
class TreeNode:
    key: int
    left: "TreeNode | None" = None
    right: "TreeNode | None" = None


def insert(root: TreeNode | None, key: int) -> TreeNode:
    if root is None:
        return TreeNode(key)
    if key < root.key:
        root.left = insert(root.left, key)
    elif key > root.key:
        root.right = insert(root.right, key)
    return root
```

This policy ignores duplicate keys. Search follows one root-to-leaf path. Its time is (O(h)), where (h) is tree height. A balanced tree has (h=O(\log n)); inserting already sorted keys into this unbalanced implementation yields height (n) and (O(n)) operations.

An in-order traversal produces sorted keys:

```python
def inorder(root: TreeNode | None):
    if root is not None:
        yield from inorder(root.left)
        yield root.key
        yield from inorder(root.right)
```

Correctness follows by structural induction on the BST invariant. Recursion depth can reach (n) for a degenerate tree and exceed CPython’s recursion limit; iterative traversal or balanced implementations address the operational boundary.

Balanced search trees such as AVL or red-black trees maintain additional invariants and use rotations to keep logarithmic height. Python’s built-in dictionary uses hashing rather than a search tree, so it does not provide sorted-key traversal by key order.

### 13.12.1 Search-tree policy is more than a shape

A BST needs a key relation and a duplicate policy. Common policies are:

- reject or ignore an equal key, as the teaching insertion does;
- replace the value associated with an equal key;
- store a multiplicity count or collection at one node;
- direct equivalent keys consistently to one side.

The last choice can create a linear chain under many duplicates even when distinct inputs would distribute well. A counted node avoids that shape but changes iteration and deletion semantics.

For a map, nodes ordinarily store key–value pairs. The ordering relation need not be identical to equality, but equivalent-order keys require a clear identity policy. If neither \(a<b\) nor \(b<a\), does inserting \(b\) replace \(a\), coexist, or fail? Balanced-tree libraries define this precisely.

Search correctness follows from the subtree invariant. At node \(x\), if target \(k<x.key\), every key in the right subtree is too large to equal \(k\); only the left subtree remains possible. Each comparison discards an entire subtree. The cost is proportional to height \(h\), not directly to node count \(n\).

~~~python
def find_node(
    root: TreeNode | None,
    key: int,
) -> TreeNode | None:
    current = root
    while current is not None:
        if key < current.key:
            current = current.left
        elif current.key < key:
            current = current.right
        else:
            return current
    return None
~~~

The symmetric less-than tests classify order equivalence without requiring <code>==</code>. They assume a coherent strict ordering. With floating NaN, both tests can be false and the search would incorrectly treat NaN as equivalent to an arbitrary root key; domain validation or a total key policy is required.

> **Common misconception 13.49 — “A binary tree is a binary search tree.”**  
> Binary describes at most two child positions. Search-tree behaviour additionally requires a global ordering invariant across every subtree.

### 13.12.2 Deletion has three structural cases

Deleting a key first locates its node. The repair depends on child count:

1. a leaf is replaced by empty;
2. a node with one child is replaced by that child;
3. a node with two children is replaced by its in-order successor or predecessor, after which that replacement node is deleted from its original position.

~~~python
def delete(
    root: TreeNode | None,
    key: int,
) -> TreeNode | None:
    if root is None:
        return None

    if key < root.key:
        root.left = delete(root.left, key)
        return root
    if root.key < key:
        root.right = delete(root.right, key)
        return root

    if root.left is None:
        return root.right
    if root.right is None:
        return root.left

    successor = minimum_node(root.right)
    root.key = successor.key
    root.right = delete(root.right, successor.key)
    return root


def minimum_node(root: TreeNode) -> TreeNode:
    current = root
    while current.left is not None:
        current = current.left
    return current
~~~

The successor is the minimum key in the right subtree. It has no left child, so deleting it reduces to a zero- or one-child case. Its key exceeds every left-subtree key and is no greater than every remaining right-subtree key, preserving the BST invariant.

Copying only <code>key</code> is sufficient for this key-only node. A key–value node must move or copy the complete entry. If node identity is exposed to callers, overwriting one node with another logical entry can violate identity expectations; an implementation may transplant nodes instead.

The operation costs \(O(h)\) search and repair in an unbalanced tree. In a balanced tree, deletion may propagate height or colour repairs back toward the root.

> **Common misconception 13.50 — “Deleting a two-child BST node means deleting its whole subtree.”**  
> The node can be replaced by the adjacent ordered entry—successor or predecessor—and that entry has a simpler structural deletion case.

### 13.12.3 Traversal orders encode different meanings

Depth-first binary-tree traversals differ by when the node itself is visited:

- **pre-order:** node, left, right;
- **in-order:** left, node, right;
- **post-order:** left, right, node.

In-order yields sorted keys only because of the BST invariant. Pre-order is useful for prefix-like serialisation and copying shape; post-order processes children before parents and supports aggregate computation or safe conceptual destruction.

Breadth-first or **level-order** traversal uses a queue:

~~~python
from collections import deque
from collections.abc import Iterator


def level_order(
    root: TreeNode | None,
) -> Iterator[int]:
    if root is None:
        return

    pending = deque([root])
    while pending:
        node = pending.popleft()
        yield node.key
        if node.left is not None:
            pending.append(node.left)
        if node.right is not None:
            pending.append(node.right)
~~~

An iterative in-order traversal replaces recursion with an explicit stack:

~~~python
def iterative_inorder(
    root: TreeNode | None,
) -> Iterator[int]:
    stack: list[TreeNode] = []
    current = root

    while current is not None or stack:
        while current is not None:
            stack.append(current)
            current = current.left
        current = stack.pop()
        yield current.key
        current = current.right
~~~

Both recursive and iterative versions need \(O(h)\) traversal state. The explicit form avoids the interpreter’s recursion-depth limit but does not asymptotically remove the path memory. Morris traversal can achieve \(O(1)\) auxiliary references by temporarily threading the tree and restoring it; that mutation has concurrency and exception-safety consequences.

> **Common misconception 13.51 — “An iterative traversal uses no stack.”**  
> It often moves the stack from interpreter frames into an explicit container. This improves control and depth tolerance but preserves \(O(h)\) auxiliary state.

### 13.12.4 Rotations preserve order while changing height

A **rotation** is a local pointer transformation preserving in-order key sequence. A left rotation around \(x\), with right child \(y\), changes

\[
x(A,\ y(B,C))
\quad\longrightarrow\quad
y(x(A,B),\ C).
\]

The ordered ranges remain

\[
A < x < B < y < C.
\]

Only parent–child structure and associated metadata change.

~~~python
@dataclass(slots=True)
class AVLNode:
    key: int
    height: int = 1
    left: "AVLNode | None" = None
    right: "AVLNode | None" = None


def height(node: AVLNode | None) -> int:
    return 0 if node is None else node.height


def refresh(node: AVLNode) -> None:
    node.height = 1 + max(height(node.left), height(node.right))


def rotate_left(root: AVLNode) -> AVLNode:
    pivot = root.right
    if pivot is None:
        raise ValueError("left rotation requires a right child")

    moved_subtree = pivot.left
    pivot.left = root
    root.right = moved_subtree

    refresh(root)
    refresh(pivot)
    return pivot
~~~

An **AVL tree** maintains balance factor

\[
height(left)-height(right)\in\{-1,0,1\}
\]

at every node. Insertion or deletion updates heights and applies single or double rotations where the invariant is violated. The minimum-node count \(N(h)\) of an AVL tree of height \(h\) satisfies

\[
N(h)=1+N(h-1)+N(h-2),
\]

so it grows at least exponentially in \(h\); equivalently \(h=O(\log n)\). Search, insertion, and deletion are therefore \(O(\log n)\).

A double rotation handles a bent heavy path: rotate the child in one direction, then the unbalanced root in the other. Memorising four case names is less reliable than identifying the heavy child and grandchild while checking order preservation.

> **Common misconception 13.52 — “A rotation sorts a disordered search tree.”**  
> A rotation assumes the BST order invariant already holds and preserves its in-order sequence. It repairs shape or balance metadata, not arbitrary key disorder.

### 13.12.5 Red–black trees, B-trees, and tries

A **red–black tree** augments a BST with a colour bit and invariants restricting red adjacency and equalising black-node counts along root-to-leaf paths. These imply longest root-to-leaf path is at most twice the shortest relevant path and height is \(O(\log n)\). Compared with AVL trees, red–black trees commonly accept looser balance in exchange for different update behaviour. Exact performance is implementation- and workload-dependent.

A **B-tree** generalises search trees so a node holds many separator keys and children. High branching factor reduces height and therefore slow storage-page accesses. Database and filesystem indexes frequently use B-tree family structures because the external-memory cost model values block transfers. A binary tree’s elegant pointer count is not automatically suitable for disks or cache hierarchies.

A **trie** branches on components of a key—often characters or bits—rather than comparing whole keys by order. Search time can be \(O(L)\) for key length \(L\), largely independent of number of stored keys, but memory use can be large and representation choices such as compressed edges matter. Prefix enumeration is natural because all keys sharing a prefix occupy one subtree.

Python’s standard built-ins do not expose a general balanced ordered map. Depending on requirements, an application can use sorted lists plus <code>bisect</code> for read-heavy small data, heaps for priority-only access, dictionaries for equality lookup, a database index for persistent ordering, or a third-party balanced structure after evaluating its contract.

> **Common misconception 13.53 — “A balanced BST is the universally best ordered structure.”**  
> Workload and memory hierarchy decide among balanced trees, B-trees, tries, sorted arrays, heaps, skip structures, and indexes. Each accelerates a particular operation set under particular costs.
