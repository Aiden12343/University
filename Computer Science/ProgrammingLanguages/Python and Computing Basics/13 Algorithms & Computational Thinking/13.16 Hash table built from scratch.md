# 13.16 Hash table built from scratch

To expose what `dict` abstracts, implement a separate-chaining hash map. Each table position holds a bucket list of key-value pairs.

```python
from typing import Generic, Iterator, TypeVar

K = TypeVar("K")
V = TypeVar("V")


class HashMap(Generic[K, V]):
    def __init__(self, capacity: int = 8) -> None:
        if capacity < 1:
            raise ValueError("capacity must be positive")
        self._buckets: list[list[tuple[K, V]]] = [
            [] for _ in range(capacity)
        ]
        self._size = 0

    def _bucket_index(self, key: K) -> int:
        return hash(key) % len(self._buckets)

    def __setitem__(self, key: K, value: V) -> None:
        bucket = self._buckets[self._bucket_index(key)]
        for index, (existing_key, _) in enumerate(bucket):
            if existing_key == key:
                bucket[index] = (existing_key, value)
                return
        bucket.append((key, value))
        self._size += 1
        if self._size / len(self._buckets) > 0.75:
            self._resize(len(self._buckets) * 2)

    def __getitem__(self, key: K) -> V:
        bucket = self._buckets[self._bucket_index(key)]
        for existing_key, value in bucket:
            if existing_key == key:
                return value
        raise KeyError(key)

    def _resize(self, capacity: int) -> None:
        old_items = list(self.items())
        self._buckets = [[] for _ in range(capacity)]
        self._size = 0
        for key, value in old_items:
            self[key] = value

    def items(self) -> Iterator[tuple[K, V]]:
        for bucket in self._buckets:
            yield from bucket
```

Invariants:

- every stored key occurs in exactly one bucket selected by current capacity;
- equal keys occur at most once;
- `_size` equals total bucket entry count;
- capacity is positive;
- key hashes remain stable while stored.

Expected bucket length is bounded when hashes distribute well and the load factor is controlled. Worst case places all keys in one bucket and makes lookup linear. Resizing requires rehashing because modulo changes bucket indices.

This teaching map omits deletion, insertion order, mutation-failure safety, recursive equality hazards, key-view semantics, and CPython’s compact open-addressing design. Building it reveals why the built-in carries far more engineering than a dictionary literal suggests.

### 13.16.1 Hashing narrows candidates; equality decides

A **hash function** maps a key to an integer hash code. A table compresses that unbounded code to a finite bucket or probe origin. Distinct keys can share a hash; such a **collision** is unavoidable whenever a larger key domain maps into fewer table positions.

Hash equality must obey:

\[
a==b\quad\Longrightarrow\quad hash(a)==hash(b).
\]

The converse is false. A matching hash identifies candidates that may then be compared for equality. If equal objects have different hashes, lookup can search a different bucket and fail to find a logically present key.

Python makes classes overriding <code>__eq__</code> unhashable by default unless a compatible <code>__hash__</code> is supplied. Immutable value objects can derive both from the same fields:

~~~python
from dataclasses import dataclass


@dataclass(frozen=True)
class Coordinate:
    row: int
    column: int
~~~

The frozen dataclass can receive value-based equality and a compatible generated hash under its documented dataclass rules. This does not make the objects deeply immutable if fields refer to mutable objects; here both fields are integers.

A stored key’s equality- and hash-relevant state must remain stable. Consider an improperly hashable mutable key. If mutation changes its hash after insertion, lookup probes according to the new hash while the entry remains placed according to the old one. The table’s representation invariant becomes false.

Hash quality has two levels:

- a key hash should mix relevant value distinctions;
- the table’s reduction and probing should distribute resulting codes across capacity.

Returning one constant is contract-correct for unequal objects but performance-catastrophic: every key collides. Correctness and performance obligations differ.

> **Common misconception 13.63 — “Different objects must have different hashes.”**  
> Collisions are permitted and mathematically unavoidable. Equal objects must share a hash; unequal objects may share one and are distinguished by equality.

### 13.16.2 Chaining deletion and resizing

Deletion in a chained table removes an equal-key entry from its bucket and decrements size:

~~~python
def delete_from_bucket(
    buckets: list[list[tuple[object, object]]],
    key: object,
) -> bool:
    bucket = buckets[hash(key) % len(buckets)]
    for index, (existing_key, _) in enumerate(bucket):
        if existing_key == key:
            del bucket[index]
            return True
    return False
~~~

The full map must update <code>_size</code> only after successful removal. It may shrink when load becomes low, but growth and shrink thresholds should differ to avoid thrashing. Rehashing must not merely move each bucket wholesale because the new modulus changes each entry’s destination.

**Load factor** for a chained table is commonly

\[
\alpha=\frac{n}{m},
\]

where \(n\) is entry count and \(m\) bucket count. It may exceed one. Under a simple uniform-hashing assumption, expected unsuccessful lookup examines \(O(1+\alpha)\) entries. This is an analytical assumption, not a guarantee produced by syntax.

Resizing one update can cost \(\Theta(n)\), while geometric growth yields amortised expected \(O(1)\) updates under hashing assumptions. The amortised qualifier addresses resizing sequences; the expected qualifier addresses collision distribution. They refer to different reasoning and both must be retained.

Exception safety is non-trivial. During resize, calls to user-defined <code>__hash__</code> or <code>__eq__</code> may raise or re-enter the map. A production implementation’s internal order must preserve a valid externally observable state or restrict re-entrancy. The teaching map’s clean loop omits this engineering.

> **Common misconception 13.64 — “Hash-table operations are amortised \(O(1)\), full stop.”**  
> Typical claims combine controlled load, suitable hash distribution, stable keys, and amortised resizing. Worst-case collision chains or probes remain linear.

### 13.16.3 Open addressing and tombstones

**Open addressing** stores entries directly in a fixed array. On collision it follows a **probe sequence** until it finds the key or an available cell. Strategies include:

- linear probing: consecutive positions;
- quadratic probing: offsets growing quadratically;
- double hashing: a second hash determines step size.

Linear probing has excellent locality but suffers **primary clustering**, where long occupied runs attract further insertions. Quadratic and double-hash schemes change clustering behaviour but require capacity and step policies that eventually cover suitable positions.

Deletion cannot simply turn a cell into “never occupied”. A lookup for a displaced key might stop there and report absence. A **tombstone** marks “formerly occupied; continue probing”. Insertion can reuse the first tombstone encountered after confirming the key does not occur later.

~~~python
_EMPTY = object()
_DELETED = object()


class OpenAddressSet:
    def __init__(self, capacity: int = 8) -> None:
        if capacity < 1 or capacity & (capacity - 1):
            raise ValueError("capacity must be a positive power of two")
        self._cells: list[object] = [_EMPTY] * capacity
        self._size = 0
        self._used = 0

    def _indices(self, value: object):
        mask = len(self._cells) - 1
        start = hash(value) & mask
        for offset in range(len(self._cells)):
            yield (start + offset) & mask

    def add(self, value: object) -> bool:
        if (self._used + 1) * 3 >= len(self._cells) * 2:
            self._resize(len(self._cells) * 2)

        first_deleted: int | None = None
        for index in self._indices(value):
            current = self._cells[index]
            if current is _EMPTY:
                destination = (
                    index if first_deleted is None else first_deleted
                )
                if self._cells[destination] is _EMPTY:
                    self._used += 1
                self._cells[destination] = value
                self._size += 1
                return True
            if current is _DELETED:
                if first_deleted is None:
                    first_deleted = index
            elif current == value:
                return False

        raise RuntimeError("probe sequence exhausted")

    def discard(self, value: object) -> bool:
        for index in self._indices(value):
            current = self._cells[index]
            if current is _EMPTY:
                return False
            if current is not _DELETED and current == value:
                self._cells[index] = _DELETED
                self._size -= 1
                return True
        return False

    def __contains__(self, value: object) -> bool:
        for index in self._indices(value):
            current = self._cells[index]
            if current is _EMPTY:
                return False
            if current is not _DELETED and current == value:
                return True
        return False

    def _resize(self, capacity: int) -> None:
        values = [
            cell
            for cell in self._cells
            if cell is not _EMPTY and cell is not _DELETED
        ]
        self._cells = [_EMPTY] * capacity
        self._size = 0
        self._used = 0
        for value in values:
            self.add(value)
~~~

The class is a study implementation, not a replacement for <code>set</code>. It tracks <code>_size</code> as live entries and <code>_used</code> as live entries plus tombstones. Growth responds to used cells because tombstones lengthen probes even though they do not appear in logical size. Rebuilding removes tombstones.

The generator lacks a return annotation only to avoid introducing the full generic iterator type again; it still yields at most capacity indices. The power-of-two capacity makes bit masking equivalent to non-negative modulo for the chosen range.

> **Common misconception 13.65 — “Deleting an open-addressed entry means replacing it with an empty cell.”**  
> That can break the probe chain for displaced entries. A tombstone or backward-shift repair must preserve lookup reachability.

### 13.16.4 Python dictionaries: contract and implementation boundary

At the language level, dictionaries are mutable mappings with unique keys and insertion-order iteration. Updating an existing key does not create a second entry; deleting and reinserting places it at a later insertion position. Equality-based key identity has subtleties: numerically equal keys such as <code>1</code> and <code>1.0</code> share an entry because they compare equal and hash compatibly.

CPython 3.12 uses a compact open-addressing dictionary design. Its split/combined table layouts, perturbation probing, index widths, resize thresholds, and memory arrangement are implementation facts subject to change. The teaching open-address set does not model insertion order or CPython’s exact design.

Iteration order is a language guarantee; expected constant-time lookup is a complexity property of conventional implementations under ordinary hashing conditions, not a promise that no input can trigger long work. Hash flooding deliberately creates collisions. Python implementations use protections including hash randomisation for selected built-in types; PEP 456 documents CPython’s adoption of SipHash-based string and bytes hashing as a defence against collision attacks. Security does not eliminate worst-case reasoning for arbitrary user-defined hashes.

Hash randomisation means a set’s iteration order can differ across process runs even when no mutation occurs. Dictionary insertion order remains defined independently of numerical hash placement. Tests should compare sets as sets and should not rely on incidental bucket order.

A dictionary view is dynamic: changes to the mapping can be reflected by existing views, while mutation during iteration may raise or omit/duplicate observations depending on the prohibited operation. Snapshot with <code>list(mapping.items())</code> when a stable copy is required, accepting \(O(n)\) time and storage.

> **Common misconception 13.66 — “Python dictionary order comes from sorted hashes.”**  
> Dictionary iteration follows insertion order by contract. Hash-table placement is an implementation mechanism and hash randomisation would make it unsuitable as the semantic ordering rule.
