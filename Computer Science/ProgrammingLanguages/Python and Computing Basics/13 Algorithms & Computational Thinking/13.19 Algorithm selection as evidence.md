# 13.19 Algorithm selection as evidence

Choose algorithms through:

- admitted input and representation;
- correctness proof and boundary conditions;
- expected and worst-case sizes;
- operation costs at the actual type level;
- memory and I/O constraints;
- latency versus throughput goals;
- adversarial inputs;
- implementation complexity and maintainability;
- representative measurement after asymptotic rejection of poor candidates.

Benchmarking cannot repair a wrong asymptotic design at scale; asymptotic analysis cannot determine constants, cache behaviour, or external bottlenecks alone. Theory narrows candidates; measurement evaluates a stated implementation and workload.

### 13.19.1 Decision, search, and optimisation forms

A **decision problem** asks a yes/no question. A **search problem** asks for a witness. An **optimisation problem** asks for a feasible object attaining the best objective. For example:

- decision: is there a route from \(s\) to \(t\) of weight at most \(B\)?
- search: produce such a route;
- optimisation: produce a minimum-weight route.

The forms are related but not definitionally identical. A decision procedure can sometimes recover an optimum through repeated threshold questions and then reconstruct a witness, provided numeric bounds and self-reduction structure permit it. Complexity theory often studies decision forms because yes/no languages support clean reductions.

A problem is **tractable** in the conventional theoretical sense when it has a deterministic polynomial-time algorithm in encoded input length. The class **P** contains decision problems solvable in polynomial time by a deterministic Turing-machine model. The class **NP** contains decision problems whose yes-instances have polynomial-size certificates verifiable in polynomial time; equivalently, they are solvable by a nondeterministic polynomial-time Turing machine.

NP does not mean “non-polynomial”. P is a subset of NP because a polynomial-time solver can verify by solving. Whether \(P=NP\) remains unresolved. A claim that no polynomial algorithm exists for an NP-complete problem would resolve a major open question and must not be inferred from failed attempts.

A **polynomial-time many-one reduction** from problem \(A\) to \(B\) transforms every instance \(x\) into an instance \(f(x)\) in polynomial time such that

\[
x\text{ is a yes-instance of }A
\quad\Longleftrightarrow\quad
f(x)\text{ is a yes-instance of }B.
\]

If \(A\) is already known hard and \(A\) reduces to \(B\), then \(B\) is at least as hard. Reversing the reduction direction proves the wrong statement.

A problem is **NP-hard** if every problem in NP reduces to it under the selected reduction. It need not itself be a decision problem or belong to NP. It is **NP-complete** if it is both in NP and NP-hard. To prove NP-completeness, show certificate verification and a correctly directed reduction from a known NP-complete problem.

Complexity classes describe families of arbitrarily growing instances, not one finite dataset. They also use worst-case encoded length and abstract resource models. They guide expectations but do not select an implementation alone.

### 13.19.2 Undecidability is different from intractability

A **decidable** problem has an algorithm that terminates with the correct answer on every admitted input. An **undecidable** problem has no such algorithm under the standard model of computation. This is stronger than “no efficient algorithm is known”.

The halting problem asks whether an arbitrary program terminates on a given input. It is undecidable. Resource-bounded complexity such as polynomial versus exponential applies to decidable problems and asks how much resource an algorithm needs. No amount of hardware converts an undecidable universal specification into an algorithm, while exponential decidable problems remain solvable on bounded instances.

Practical tools can conservatively analyse restricted languages, impose time limits, answer “unknown”, or accept false positives/negatives. They thereby solve a different, explicitly weakened problem. A static analyser that sometimes reports “possibly non-terminating” has not decided the general halting problem.

### 13.19.3 Approximation, heuristics, and exactness

When exact optimisation is expensive, three categories must remain distinct:

- an **exact algorithm** always returns an optimum;
- an **approximation algorithm** runs under a stated resource bound and guarantees solution quality relative to optimum;
- a **heuristic** aims for good empirical solutions without the same universal quality guarantee.

For a minimisation problem, an algorithm has approximation ratio \(\rho\ge1\) when

\[
cost(A(I))\le \rho\,OPT(I)
\]

for every admitted instance \(I\), subject to the exact convention. For maximisation, the inequality direction or ratio definition is adjusted. Additive approximation bounds and probabilistic guarantees are other contracts.

A **polynomial-time approximation scheme** (**PTAS**) accepts an accuracy parameter \(\varepsilon>0\) and returns a \((1+\varepsilon)\)-approximate minimisation result in time polynomial in input size for each fixed \(\varepsilon\). An **FPTAS** additionally requires polynomial dependence on \(1/\varepsilon\). These names encode formal guarantees, not informal claims of closeness.

Local search begins from a feasible solution and repeatedly moves to an improving neighbour. Simulated annealing, genetic algorithms, and other metaheuristics explore more broadly. Their usefulness is empirical and domain-specific unless a theorem provides a guarantee. Report random seeds, termination budgets, distributions, and objective gaps when evaluating them.

### 13.19.4 Measurement is an experiment

An empirical performance statement requires:

1. a question and competing implementations with equivalent semantics;
2. representative input distributions, shapes, and sizes;
3. controlled software and hardware environment;
4. a clock or profiler appropriate to the resource;
5. warm-up and setup policy;
6. repeated observations and distribution summaries;
7. checks that results are consumed and correct;
8. a record sufficient for reproduction.

Python’s <code>time.perf_counter()</code> supplies a high-resolution monotonic performance counter for measuring short durations. Only differences between readings have defined meaning. The <code>timeit</code> module repeats statements and, by default, temporarily disables cyclic garbage collection during timings; that choice can make results less representative if collection is part of the workload.

~~~python
from collections.abc import Callable
from statistics import median
from time import perf_counter
from typing import TypeVar

T = TypeVar("T")


def benchmark(
    operation: Callable[[], T],
    *,
    repeats: int = 15,
) -> tuple[float, list[float]]:
    if repeats < 1:
        raise ValueError("repeats must be positive")

    durations: list[float] = []
    retained: T | None = None
    for _ in range(repeats):
        start = perf_counter()
        retained = operation()
        durations.append(perf_counter() - start)

    if retained is None:
        pass
    return median(durations), durations
~~~

The assignment to <code>retained</code> makes consumption visible in this Python-level example, although CPython does not generally remove arbitrary unused calls as an optimising compiler might. The meaningless conditional simply preserves a visible reference and should not be copied into a polished benchmark harness.

Median resists isolated long interruptions but does not describe variance or tail latency. Report raw observations or quantiles when tail behaviour matters. The minimum can estimate least-interrupted execution in microbenchmark practice, but it may understate user-visible latency. Select a statistic according to the question.

Avoid placing data generation, imports, logging, or validation inside the timed region unless they belong to the operation being measured. Conversely, excluding allocation or conversion that production must perform makes the measurement artificially narrow. Define the boundary first.

Algorithm scaling can be checked by measuring geometrically increasing sizes and considering ratios. If doubling \(n\) approximately doubles work, linear growth is plausible over that range; a factor near four is consistent with quadratic growth. This is empirical evidence, not proof, and cache thresholds or noise can obscure it.

### 13.19.5 Memory and I/O evidence

Wall time aggregates computation, waiting, scheduling, and system effects. Operation counters test a model more directly. Memory measurement needs distinguish:

- logical container length;
- shallow object size;
- recursively retained object graph;
- cumulative allocations;
- peak traced Python allocation;
- process resident set size;
- external buffers and memory-mapped pages.

Python’s <code>tracemalloc</code> traces many Python memory allocations and can compare snapshots or report traced peak. It does not equal complete process memory. <code>sys.getsizeof</code> gives shallow size for an object according to its implementation, not recursively reachable storage.

For external-memory work, count bytes, requests, block transfers, seek patterns, and cache state. An \(O(n)\) sequential scan can outperform \(O(\log n)\) random lookups when storage latency and batching dominate. Database indexes add update and storage cost while changing query I/O.

Profiling identifies where an observed program spends resources; it does not by itself explain asymptotic behaviour or correctness. A line profiler, sampling profiler, allocation tracer, and system I/O tracer answer different questions.

### 13.19.6 A disciplined selection record

An algorithm decision should be reviewable. Record:

| Field | Required content |
|---|---|
| problem contract | admitted inputs, required outputs, mutation and failure semantics |
| size variables | encoded measures and relationships |
| candidate methods | including standard-library or maintained-library options |
| correctness basis | invariant, reduction, exchange argument, or cited specification |
| theoretical resources | case qualifier, time, auxiliary/total space, output cost |
| representation | concrete structures and operation assumptions |
| risk boundaries | adversarial data, numeric behaviour, recursion, concurrency |
| empirical method | versions, machine, dataset, repetitions, statistics |
| decision | chosen method and why alternatives were rejected |
| revision trigger | scale, workload, or requirement change requiring reassessment |

This record prevents “fast” from becoming an untraceable judgement and makes later replacement rational rather than fashionable.

### 13.19.7 Claim ledger

Throughout this treatise, computational claims should be identifiable as one of the following:

- **definition:** fixes terminology, such as the meaning of \(\Theta\);
- **derivation:** follows mathematically from stated premises, such as a recurrence solution;
- **specification rule:** promised by a language or library contract, such as stable sorting;
- **implementation fact:** true of a named implementation and version, such as CPython’s current Timsort;
- **empirical observation:** measured under a recorded environment and workload;
- **modelling assumption:** deliberately abstracts details, such as unit-cost comparisons;
- **substantive judgement:** an engineering recommendation based on declared priorities.

Mixing categories produces false authority. “Dictionary lookup is always constant-time” presents a model-dependent expected performance statement as a specification guarantee. “This implementation was faster in one benchmark” does not establish an asymptotic theorem. “Timsort is adaptive” is an implementation-family fact; “use the built-in sort unless requirements defeat its contract” is an engineering judgement supported by maintenance and correctness considerations.

> **Common misconception 13.72 — “Benchmarks settle which algorithm is best.”**  
> A benchmark measures chosen implementations on chosen workloads. Correctness, worst-case exposure, memory, maintainability, and future scale remain independent evidence, and a changed workload can reverse the result.

### 13.19.8 Worked synthesis — the smallest missing positive

Consider a deliberately compact specification:

> Given a mutable list of integers, return the smallest positive integer absent from it. Mutation and loss of original order are permitted.

For \([3,4,-1,1]\), the answer is 2. For \([1,2,3]\), it is 4. If the input contains \(n\) elements, the answer lies in \(\{1,\ldots,n+1\}\): if every value 1 through \(n\) is present, the answer is \(n+1\); otherwise the first absent member of that range is the answer. Values outside 1 through \(n\) cannot change which of those cases holds.

A straightforward set implementation retains all positive values and scans upward:

~~~python
def smallest_missing_positive_set(values: list[int]) -> int:
    present = set(values)
    candidate = 1
    while candidate in present:
        candidate += 1
    return candidate
~~~

Under ordinary expected hash assumptions, this takes expected \(O(n)\) time and \(O(n)\) auxiliary references. Its advantage is that it leaves the list order unchanged. The permission to mutate enables a deterministic \(O(n)\)-time, \(O(1)\)-auxiliary-word alternative under the unit-cost array model.

Use index \(k-1\) as the canonical position for value \(k\). At each index, repeatedly place its current in-range positive value into that value’s canonical position. Stop when the current value is out of range or its destination already contains an equal value.

~~~python
def smallest_missing_positive(values: list[int]) -> int:
    length = len(values)

    for index in range(length):
        while (
            1 <= values[index] <= length
            and values[values[index] - 1] != values[index]
        ):
            destination = values[index] - 1
            values[index], values[destination] = (
                values[destination],
                values[index],
            )

    for index, value in enumerate(values):
        if value != index + 1:
            return index + 1
    return length + 1
~~~

The duplicate test is essential. With \([1,1]\), trying perpetually to place the second 1 into a slot already containing 1 would make no progress. The condition recognises that the relevant presence fact is already represented.

**Correctness.** After the placement loop completes, for every \(k\in\{1,\ldots,n\}\), if \(k\) occurred in the input then <code>values[k - 1] == k</code>. When an occurrence of \(k\) is examined outside its canonical position, either that position already contains \(k\), or the swap puts \(k\) there. Once placed, it cannot be displaced: another \(k\) sees equality and does not swap, while a different value targets a different canonical index. Swaps preserve the multiset of list values. Therefore the first index not containing its one-based canonical value identifies the first absent positive; if no such index exists, all 1 through \(n\) are present and \(n+1\) is minimal absent.

**Termination and time.** Every successful swap places at least one previously unplaced in-range value permanently into its canonical position. There are at most \(n\) canonical positions, so there are at most \(n\) successful swaps across all inner-loop executions. The outer loop performs \(n\) iterations and the final scan at most \(n\); total abstract work is \(\Theta(n)\). This is another case where syntactic nesting does not imply quadratic cost.

**Space and effects.** The algorithm uses a fixed number of local integer references beyond the input, conventionally \(O(1)\) auxiliary words. It may radically reorder the list, and if an unexpected exception occurred during a generalised comparison or indexing operation it would not restore prior order. Here built-in integer comparisons and indices make the operational domain narrower and clearer.

The two implementations illustrate a complete engineering decision. Both are linear under their respective qualifications. The set version is shorter, non-mutating, and commonly preferable when \(O(n)\) memory is acceptable. The placement version earns lower auxiliary space by relying on mutable random access, integer-domain structure, and a subtler invariant. “Optimal asymptotics” does not erase semantic and verification costs.
