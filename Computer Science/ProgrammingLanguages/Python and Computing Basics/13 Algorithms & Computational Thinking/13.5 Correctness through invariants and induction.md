# 13.5 Correctness through invariants and induction

Mathematical **induction** proves a claim for non-negative integers by establishing a base case and showing that truth for an arbitrary (k) implies truth for (k+1). A loop-invariant proof has the same structure across iterations: initialisation, maintenance, and termination.

For recursive algorithms, **structural induction** follows the constructors of the input structure. To prove a property for a binary tree, establish it for the empty tree and show that if it holds for left and right subtrees, it holds for a node combining them.

Correctness proof stages:

1. state precondition and postcondition;
2. choose an invariant strong enough to imply the postcondition;
3. prove it before the first iteration;
4. prove every body path preserves it;
5. prove termination separately;
6. combine exit condition and invariant.

An invariant can be true but useless. “The processed count is non-negative” is preserved by a maximum scan but does not imply the returned value is maximal.

### 13.5.1 Partial and total correctness

A program is **partially correct** with respect to precondition \(P\) and postcondition \(Q\) when: if execution begins in a state satisfying \(P\) and terminates, the final state satisfies \(Q\). **Total correctness** adds termination for every state satisfying \(P\).

This distinction prevents a non-terminating program from being called correct merely because it never returns a wrong answer. A proof of total correctness commonly contains:

1. a safety argument: an invariant and exit condition establish \(Q\);
2. a progress argument: a **variant** or **ranking function** takes values in a well-founded set and strictly decreases.

A relation is **well-founded** when it admits no infinite descending chain. Non-negative integers under \(>\) are the usual choice. Saying only that a numeric variant decreases is insufficient if it can descend without bound through negative integers or real values.

> **Common misconception 13.19 — “A loop invariant proves termination.”**  
> An invariant constrains reachable states. Termination requires a separate progress argument, usually a well-founded decreasing variant.

### Worked example 13.5A — Prove a maximum scan

~~~python
from collections.abc import Sequence
from typing import TypeVar

T = TypeVar("T")


def maximum(values: Sequence[T]) -> T:
    if not values:
        raise ValueError("maximum requires a non-empty sequence")

    best = values[0]
    index = 1
    while index < len(values):
        if values[index] > best:
            best = values[index]
        index += 1
    return best
~~~

The annotation does not statically express orderability; the semantic precondition is that comparisons used by the function form a suitable total preorder and do not fail. Let \(n=\lvert values\rvert\).

The loop invariant is:

\[
1\le index\le n
\quad\text{and}\quad
best\text{ is a maximum of }values[0:index].
\]

**Initialisation.** Before the loop, \(index=1\), and <code>best</code> is the sole element of the one-element prefix.

**Maintenance.** Assume the invariant at loop entry. Comparing \(values[index]\) with <code>best</code> and retaining the larger produces a maximum of the prefix ending at that position. Incrementing <code>index</code> makes that prefix precisely <code>values[0:index]</code> for the next entry.

**Termination.** The variant \(n-index\) is a non-negative integer at each loop entry and decreases by one. At exit \(index=n\). Combining this with the invariant proves that <code>best</code> is a maximum of the entire sequence.

The function performs exactly \(n-1\) greater-than comparisons for \(n>0\), regardless of value order. Its comparison complexity is therefore \(\Theta(n)\), and an adversary argument shows this is optimal in the comparison model for finding a maximum: every non-maximum candidate must lose at least one comparison.

### 13.5.2 Preconditions are part of the theorem

A proof does not establish correctness beyond its hypotheses. Binary search’s theorem requires sorted input; Dijkstra’s theorem requires non-negative edge weights; a hash table requires stable hashes while keys are stored. Code may enforce a precondition, document it, or rely on a type or constructor that makes violations unrepresentable.

A **postcondition** describes the result and relevant state after successful completion. For an in-place sort it must cover both order and preservation:

\[
\forall i<j:\ key(a_i)\le key(a_j)
\]

and the output must be a permutation of the input. Proving only order would permit replacing the entire list with repeated copies of its minimum.

A **frame condition** states what is not modified. If a procedure promises to rearrange one list without mutating its elements or external collections, that non-interference belongs to the specification.

Exceptions also require specification. “Returns the maximum” leaves undefined what happens on an empty input or failed comparison. The implementation above explicitly raises <code>ValueError</code> for emptiness but can propagate arbitrary comparison exceptions. Stronger contracts would need to specify mutation state on failure.

> **Common misconception 13.20 — “If tests pass, the algorithm is proven correct.”**  
> Tests establish observations for selected executions. A proof covers every instance satisfying stated preconditions, subject to the validity of its model and premises. Tests remain essential for implementation errors and premise violations.

### 13.5.3 Weakening, strengthening, and proof usefulness

A predicate \(A\) is **stronger** than \(B\) when \(A\Rightarrow B\). Strengthening an invariant makes more claims and may allow the postcondition to follow, but makes initialisation and preservation harder to prove. Weakening does the reverse.

For insertion sort, “the prefix is sorted” is not by itself sufficient to prove permutation preservation. A useful invariant states both:

1. the processed prefix is sorted;
2. it contains exactly the multiset of elements originally in that prefix.

The word **multiset** denotes a collection retaining multiplicity without order. Ordinary set equality would lose duplicates and could not establish that two equal-valued input records remain represented twice.

Proof discovery often proceeds backwards from the postcondition. Ask what must be true at loop exit, replace the final bound with the current loop index, and add the facts needed to preserve that statement. This is a design technique, not an automatic recipe.

> **Common misconception 13.21 — “The strongest possible invariant is always best.”**  
> An unnecessarily strong claim can be false or needlessly difficult. The goal is an inductive assertion strong enough, together with exit conditions, to imply the required postcondition.

### 13.5.4 Ordinary, strong, and structural induction

**Ordinary induction** assumes \(P(k)\) to prove \(P(k+1)\). **Strong induction** assumes every earlier case \(P(0),\ldots,P(k)\) to prove \(P(k+1)\). The two principles have equal logical power over natural numbers, but strong induction often matches algorithms with several possible subproblem sizes.

To prove merge sort correct for every list length \(n\), use strong induction:

- base: lengths 0 and 1 are already sorted;
- hypothesis: recursive calls correctly sort every list shorter than \(n\);
- step: both halves are shorter than \(n\), so each recursive result is sorted and a permutation of its half; the verified merge operation produces a sorted permutation of their concatenation.

Structural induction follows data constructors rather than a numeric counter. For the binary-tree definition “empty, or a node with two binary trees”, prove the empty case and then prove the node case assuming the claim for both children. This form aligns with recursive traversals.

A recursive implementation additionally needs a termination argument. Every recursive call must move to a smaller value under a well-founded measure. “Calls itself on something that looks simpler” is insufficient, especially when aliasing or cyclic structures are possible.

> **Common misconception 13.22 — “Recursion is correct because it eventually reaches the base case.”**  
> One must prove that every admitted call moves toward a base case and that combining correct subresults establishes the current result.

### 13.5.5 Counterexamples and minimal falsification

A universal algorithmic claim is disproved by one admitted counterexample. Constructing a **minimal counterexample**—one smallest under a chosen size measure—often reveals the broken invariant.

Suppose an attempted binary search updates <code>high = middle - 1</code> while maintaining a half-open interval <code>[low, high)</code>. A target at position <code>middle - 1</code> can be discarded because <code>high</code> itself is already excluded. Very small arrays expose the disagreement among interval convention, update, and exit condition.

Property-based testing operationalises counterexample search by generating many inputs and shrinking failures. It does not turn finite execution into a mathematical proof, but it complements proof: the proof identifies intended invariants; generated tests challenge the implementation and assumptions.

For optimisation algorithms, a counterexample must distinguish feasibility from optimality. A greedy schedule can produce a valid schedule yet select fewer intervals than possible. Showing only that its output violates no constraints does not test the optimality theorem.

> **Common misconception 13.23 — “A plausible explanation of the main idea is a correctness proof.”**  
> A proof must cover initial conditions, every transition, termination, preservation of required data, and all admitted boundary cases. An unexamined phrase such as “clearly optimal” often hides the disputed step.
