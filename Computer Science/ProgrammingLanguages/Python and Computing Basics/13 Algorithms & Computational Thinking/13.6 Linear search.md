# 13.6 Linear search

Linear search applies to an arbitrary iterable and makes no sortedness assumption.

```python
from collections.abc import Iterable
from typing import TypeVar

T = TypeVar("T")


def find_index(values: Iterable[T], target: T) -> int | None:
    for index, value in enumerate(values):
        if value == target:
            return index
    return None
```

Invariant: before each comparison at index (i), none of the prior produced values at indices (0\ldots i-1) equals target. If a match is returned, it is the first index. On finite exhaustion, no item equals target.

Time is (O(n)) equality operations in the worst case. The function supports one-pass iterables and does not retain them. A set or dictionary can make repeated membership queries expected (O(1)) after (O(n)) preprocessing and memory, but building one for a single query may add cost and discard order/duplicate information.

### 13.6.1 The search contract determines the answer

“Find \(x\)” can denote several problems:

- decide whether any equal value exists;
- return the first position in encounter order;
- return every matching position;
- return one matching object;
- count matches;
- find a value satisfying a predicate rather than equality;
- find the minimum-cost or nearest match.

These specifications have different outputs and sometimes different lower bounds. A Boolean membership test may terminate at the first match. Enumerating every match has an \(\Omega(z)\) output cost for \(z\) results. Returning the first position presupposes a defined encounter order; a mathematical set has none, although a concrete Python set produces some iteration sequence that is not a portable ordering contract.

For a general iterable, <code>find_index</code> consumes values. If the iterable is an iterator, a failed search exhausts it and a successful search leaves it positioned after the match:

~~~python
stream = iter([10, 20, 30, 40])
assert find_index(stream, 30) == 2
assert list(stream) == [40]
~~~

Consumption is an observable effect and belongs in the function’s contract. A sequence can be revisited; an iterator represents evolving traversal state.

Equality also has cost and semantics. Searching a list of length-\(m\) strings can require \(O(nm)\) character work in a worst-case model, even though it performs \(n\) equality operations. User-defined equality can raise an exception or mutate state. The algorithmic comparison count remains useful, but it is not a complete wall-clock model.

> **Common misconception 13.24 — “Linear search has no preconditions.”**  
> It avoids sortedness, but still depends on finite traversal when a no-match result is expected, meaningful equality or predicate behaviour, and an understood consumption policy.

### 13.6.2 Predicate search and retained witnesses

A **witness** is an object demonstrating that a condition holds. Returning a witness often carries more information than returning <code>True</code>:

~~~python
from collections.abc import Callable, Iterable
from typing import TypeVar

T = TypeVar("T")


def first_where(
    values: Iterable[T],
    predicate: Callable[[T], bool],
) -> T | None:
    for value in values:
        if predicate(value):
            return value
    return None
~~~

This interface is ambiguous when <code>None</code> can itself be an element satisfying the predicate. One remedy is to raise on absence; another returns an explicit tagged result. A sentinel object can distinguish the cases internally:

~~~python
_MISSING = object()


def first_where_or(
    values: Iterable[T],
    predicate: Callable[[T], bool],
    default: object = _MISSING,
) -> T | object:
    for value in values:
        if predicate(value):
            return value
    if default is _MISSING:
        raise LookupError("no matching value")
    return default
~~~

The sentinel is tested by identity because its purpose is to be one unique object, not a value equal to some input. This revisits Chapter 5’s distinction between identity and equality.

The invariant is: before each iteration, no previously encountered value satisfies <code>predicate</code>. If the call returns a value, that value satisfies the predicate and is the earliest such witness. If finite iteration ends, the invariant covers every element and justifies absence.

### 13.6.3 Sentinels as an algorithmic transformation

In low-level presentations, **sentinel linear search** temporarily places the target at the final position so that the loop needs no bounds check at each step. After finding a match, it determines whether the match was original or the sentinel. This can reduce a constant factor in a machine model, but it mutates storage and demands restoration even if comparison fails.

In ordinary Python, the transformation is rarely justified: interpreter dispatch and equality dominate the saved branch, mutation may violate caller expectations, and a one-pass iterable has no writable last cell. The example remains conceptually useful because it shows that algorithms trade preconditions and mutation for operation count.

~~~python
def sentinel_find(values: list[int], target: int) -> int | None:
    if not values:
        return None

    final = values[-1]
    values[-1] = target
    index = 0
    try:
        while values[index] != target:
            index += 1
    finally:
        values[-1] = final

    if index < len(values) - 1 or final == target:
        return index
    return None
~~~

The <code>finally</code> suite restores the final reference if equality raises. This supplies only a basic exception-safety guarantee: arbitrary equality code could mutate the list in other ways. The function is pedagogical, not a recommendation over a straightforward <code>for</code> loop.

> **Common misconception 13.25 — “Fewer source-level tests necessarily means faster Python.”**  
> An abstract operation saving must survive interpreter, method-dispatch, allocation, cache, and mutation costs. Measure a semantically equivalent implementation on representative workloads.

### 13.6.4 Preprocess when questions repeat

For one membership query over \(n\) unsorted values, a scan uses \(O(n)\) time and \(O(1)\) auxiliary storage. For \(q\) queries it uses \(O(qn)\) worst-case comparisons. Preprocessing changes the trade:

| Representation | Build | One query | Extra storage | Preserves multiplicity/order? |
|---|---:|---:|---:|---|
| original sequence | none | \(O(n)\) | \(O(1)\) | yes |
| sorted copy + binary search | \(O(n\log n)\) | \(O(\log n)\) | \(O(n)\) | yes, in sorted rather than original order |
| hash set | expected \(O(n)\) | expected \(O(1)\) | \(O(n)\) | no |
| key-to-indices dictionary | expected \(O(n)\) | expected \(O(1+z)\) | \(O(n)\) | yes, if indices are stored |

The break-even point depends on constants, key costs, mutation frequency, and required outputs. If the source changes, an index must be updated or rebuilt; stale derived data is a correctness fault, not merely a performance issue.

A maintained summary can answer specialised searches. Keeping a minimum makes minimum retrieval \(O(1)\), but updating after arbitrary deletion may require a heap, balanced tree, counts map, or full rescan. No representation accelerates every operation simultaneously.

> **Common misconception 13.26 — “A hash set makes searching \(O(1)\), so conversion is always an improvement.”**  
> It adds construction and memory, offers expected rather than unconditional constant lookup, requires hashable stable keys, and discards information unless that information is stored separately.
