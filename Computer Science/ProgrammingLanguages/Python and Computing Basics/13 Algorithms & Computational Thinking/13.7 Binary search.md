# 13.7 Binary search

Binary search requires a sorted random-access sequence under a coherent ordering. Maintain a half-open candidate interval `[low, high)`.

```python
from collections.abc import Sequence


def binary_search(values: Sequence[int], target: int) -> int | None:
    low = 0
    high = len(values)

    while low < high:
        middle = low + (high - low) // 2
        candidate = values[middle]

        if candidate < target:
            low = middle + 1
        elif candidate > target:
            high = middle
        else:
            return middle

    return None
```

Invariant:

- (0\leq low\leq high\leq n);
- if target occurs in the sequence, at least one occurrence remains in `[low, high)`.

When `candidate < target`, sortedness proves positions through `middle` cannot contain target, so `low = middle + 1` preserves the candidate claim. When greater, positions from `middle` onward cannot be target, so `high = middle` preserves it. Equality returns a valid occurrence.

Variant is interval length `high - low`. Every non-returning iteration strictly reduces it. On exit it is zero; by the invariant no occurrence exists.

Each iteration approximately halves the interval, yielding (Theta(\log n)) comparisons. Indexing must be sufficiently direct; binary search over a linked list does not gain the same time bound because finding the middle costs linear traversal.

### Bound variants

Finding the first insertion position uses a related invariant:

```python
def lower_bound(values: Sequence[int], target: int) -> int:
    low = 0
    high = len(values)
    while low < high:
        middle = low + (high - low) // 2
        if values[middle] < target:
            low = middle + 1
        else:
            high = middle
    return low
```

At exit, all positions before `low` contain values less than target; all at or after contain values at least target. This returns the first equal occurrence when present and insertion point otherwise.

Off-by-one errors arise when interval convention, midpoint, update, and exit condition do not agree. Copying individual lines between closed and half-open variants breaks the proof.

### 13.7.1 Partition points unify the variants

Binary search is more general than equality lookup. Let a finite random-access domain be divided by a monotone Boolean predicate:

\[
\underbrace{False,\ldots,False}_{\text{possibly empty}},
\underbrace{True,\ldots,True}_{\text{possibly empty}}.
\]

The **partition point** is the first position where the predicate is true, or \(n\) if it is never true. Maintain

- every index below <code>low</code> is known false;
- every index at or above <code>high</code> is known true;
- the unknown interval is <code>[low, high)</code>.

At initialisation the known regions are empty, so the invariant holds without inspecting an element.

~~~python
from collections.abc import Callable


def first_true(length: int, predicate: Callable[[int], bool]) -> int:
    low = 0
    high = length

    while low < high:
        middle = low + (high - low) // 2
        if predicate(middle):
            high = middle
        else:
            low = middle + 1

    return low
~~~

If the predicate is not monotone, the invariant’s inference is invalid: observing true at <code>middle</code> would not prove all later positions true. The function cannot detect arbitrary violations without sacrificing the logarithmic advantage by checking the domain.

Lower bound uses <code>predicate(i) = values[i] &gt;= target</code>. Upper bound—the first index strictly greater than target—uses <code>values[i] &gt; target</code>. Equal values then occupy the half-open interval <code>[lower_bound, upper_bound)</code>.

~~~python
from collections.abc import Sequence


def upper_bound(values: Sequence[int], target: int) -> int:
    return first_true(
        len(values),
        lambda index: values[index] > target,
    )


def equal_range(values: Sequence[int], target: int) -> range:
    left = first_true(
        len(values),
        lambda index: values[index] >= target,
    )
    right = first_true(
        len(values),
        lambda index: values[index] > target,
    )
    return range(left, right)
~~~

The two searches use at most \(O(\log n)\) key comparisons and return all matching positions symbolically as a range. Materialising the matching elements additionally costs \(\Theta(z)\) for \(z\) matches.

> **Common misconception 13.27 — “Binary search is fundamentally a search for equality.”**  
> Its core operation locates a boundary in a monotone partition. Equality lookup is derived by choosing an ordering predicate and interpreting the boundary.

### 13.7.2 Exact comparison count and information

Each unsuccessful iteration reduces unknown interval length \(s>0\) to at most \(\lfloor s/2\rfloor\). After \(k\) iterations its length is at most \(\lfloor n/2^k\rfloor\). It reaches zero once \(2^k>n\), giving at most \(\lfloor\log_2 n\rfloor+1\) predicate evaluations for \(n>0\).

There is a matching comparison lower bound for locating one among \(n+1\) insertion gaps with binary yes/no outcomes. A decision tree of height \(h\) distinguishes at most \(2^h\) outcomes, so \(2^h\ge n+1\) and

\[
h\ge\lceil\log_2(n+1)\rceil.
\]

Binary search is therefore asymptotically optimal for this task in the binary-comparison, random-access model. The qualification matters: interpolation search can exploit numeric distribution assumptions, and a maintained direct-address table can answer different key domains by indexing.

The familiar midpoint formula <code>(low + high) // 2</code> is safe for Python integers because they do not overflow at a fixed word boundary. The alternative <code>low + (high - low) // 2</code> remains valuable because it generalises to fixed-width languages and makes interval dependence explicit.

> **Common misconception 13.28 — “Python’s arbitrary-size integers remove binary-search boundary errors.”**  
> They remove one overflow hazard. Inconsistent interval conventions, non-shrinking updates, invalid sortedness, and incoherent comparisons remain.

### 13.7.3 The standard <code>bisect</code> operations

The standard-library <code>bisect</code> module supplies partition-point operations over sorted sequences:

~~~python
from bisect import bisect_left, bisect_right, insort_left

scores = [10, 20, 20, 20, 40]

first = bisect_left(scores, 20)
after = bisect_right(scores, 20)
assert (first, after) == (1, 4)
assert scores[first:after] == [20, 20, 20]

insort_left(scores, 30)
assert scores == [10, 20, 20, 20, 30, 40]
~~~

The search is \(O(\log n)\), but insertion into a Python list remains \(O(n)\) because later references must move. The module documentation explicitly notes that the linear insertion step dominates. A logarithmic insertion-point search does not turn a dynamic array into a logarithmic-update ordered structure.

Python 3.10 and later accept a <code>key</code> parameter for relevant bisect functions. The key is applied to sequence elements during search; for insertion functions it is also used to search for the new value but not to transform the value stored. Repeated calls may recompute keys. If key extraction is expensive, maintain a parallel key list or cache results, while preserving synchronisation with the records.

The module’s functions use less-than ordering rather than calling equality to find a value. This permits insertion boundaries even for types whose ordering notion is more useful than equality, but it still requires the sequence to be sorted consistently with the same key and ordering.

The official documentation also warns that the functions are not thread-safe for concurrent operations on the same sequence. Synchronisation and mutation discipline remain the caller’s responsibility.

> **Common misconception 13.29 — “Using <code>bisect.insort</code> gives \(O(\log n)\) insertion into a list.”**  
> Locating the position is logarithmic; shifting the list suffix is linear. The complete insertion is \(O(n)\).

### Worked example 13.7A — Search an implicit answer space

Suppose a production line can make a known number of units per hour for each machine. Find the minimum integer hours needed to make at least a target number of units. The answer predicate “capacity by \(h\) hours is at least target” is monotone.

~~~python
def minimum_hours(rates: list[int], target: int) -> int:
    if target < 0:
        raise ValueError("target must be non-negative")
    if target == 0:
        return 0
    if not rates or any(rate <= 0 for rate in rates):
        raise ValueError("rates must be positive")

    def sufficient(hours: int) -> bool:
        return sum(rate * hours for rate in rates) >= target

    low = 0
    high = 1
    while not sufficient(high):
        high *= 2

    while low < high:
        middle = low + (high - low) // 2
        if sufficient(middle):
            high = middle
        else:
            low = middle + 1
    return low
~~~

The first loop performs **exponential search** for an upper bound: doubling reaches an answer \(H\) after \(O(\log H)\) predicate calls. The second locates the first sufficient integer in \(O(\log H)\) calls. If summing over \(m\) rates costs \(\Theta(m)\), total time is \(O(m\log H)\).

This method searches a numeric answer domain without materialising a sorted array. Its correctness depends entirely on predicate monotonicity and on existence of a finite sufficient bound.

### 13.7.4 Discrete search and numerical bisection

Numerical **bisection** locates a root of a continuous real-valued function by maintaining endpoints with opposite signs and repeatedly halving an interval. It resembles binary search but has different foundations: continuity via the intermediate value theorem rather than discrete sorted order.

Floating-point bisection needs an accuracy or iteration stopping rule. Exact equality with zero may never occur, and <code>(low + high) / 2</code> can round to an endpoint when the interval is extremely narrow. A robust specification states whether error is bounded in the input coordinate, function value, or number of representable values.

~~~python
from collections.abc import Callable


def bisect_root(
    function: Callable[[float], float],
    low: float,
    high: float,
    *,
    iterations: int = 80,
) -> float:
    low_value = function(low)
    high_value = function(high)
    if low_value == 0.0:
        return low
    if high_value == 0.0:
        return high
    if (low_value < 0.0) == (high_value < 0.0):
        raise ValueError("endpoints must bracket a sign change")

    for _ in range(iterations):
        middle = low + (high - low) / 2.0
        middle_value = function(middle)
        if middle_value == 0.0:
            return middle
        if (middle_value < 0.0) == (low_value < 0.0):
            low = middle
            low_value = middle_value
        else:
            high = middle

    return low + (high - low) / 2.0
~~~

The code assumes finite meaningful function values; NaN breaks sign reasoning. Eighty iterations is a modelling choice, not a universally correct tolerance. Numerical analysis must account for representation and conditioning, subjects developed in the numerical-computing branch.

> **Common misconception 13.30 — “Binary search and floating-point bisection have the same correctness proof.”**  
> They share interval halving. Discrete binary search relies on a monotone partition; root bisection relies on analytic and floating-point assumptions that must be stated separately.

### 13.7.5 Subsequence and substring search

Binary search exploits order across candidate positions. Substring search instead exploits overlap among comparisons. Given a text \(T\) of length \(n\) and pattern \(P\) of length \(m\), the exact substring-search problem asks for an index \(s\) such that

\[
T[s:s+m]=P,
\]

or an absence result. A specification must say whether it returns the first match, every match, or overlapping matches, and what an empty pattern means.

A direct algorithm tests every feasible alignment:

~~~python
from collections.abc import Sequence
from typing import TypeVar

T = TypeVar("T")


def naive_find(
    text: Sequence[T],
    pattern: Sequence[T],
) -> int | None:
    if len(pattern) == 0:
        return 0

    final_start = len(text) - len(pattern)
    for start in range(final_start + 1):
        for offset, expected in enumerate(pattern):
            if text[start + offset] != expected:
                break
        else:
            return start
    return None
~~~

The <code>else</code> belongs to the inner <code>for</code> and runs only when that loop is not terminated by <code>break</code>. The algorithm performs at most

\[
(n-m+1)m
\]

equality comparisons when \(0<m\le n\), hence \(O(nm)\). On ordinary mismatching text it often rejects an alignment quickly, but an input such as many repeated <code>a</code> elements followed by a differing final pattern element approaches the worst case.

The code compares indexed elements rather than slices. Forming and comparing <code>text[start:start+m]</code> can allocate or copy a subsequence for types such as lists and strings, adding representation-level cost.

#### Prefix information in Knuth–Morris–Pratt search

Suppose a mismatch occurs after several pattern elements have already matched. Those matched elements may contain a suffix that is also a pattern prefix. Reusing that fact avoids moving the text position backwards.

For each pattern prefix ending at index \(i\), define \(prefix[i]\) as the length of its longest proper prefix that is also a suffix. A **proper prefix** is shorter than the entire sequence.

~~~python
def prefix_lengths(pattern: Sequence[T]) -> list[int]:
    prefix = [0] * len(pattern)
    border = 0

    for index in range(1, len(pattern)):
        while border > 0 and pattern[index] != pattern[border]:
            border = prefix[border - 1]
        if pattern[index] == pattern[border]:
            border += 1
        prefix[index] = border

    return prefix
~~~

For <code>pattern = "ababaca"</code>, the table is \([0,0,1,2,3,0,1]\). At the prefix <code>ababa</code>, length 3 records that <code>aba</code> is both prefix and suffix. At the following <code>c</code>, border candidates fall from length 3 to the longest border of that border, then to zero.

The nested loop remains linear. Every successful outer progression can increase <code>border</code> by at most one; each failure fallback strictly decreases it. Across the whole construction, total decreases cannot exceed prior increases plus the initial value. Thus at most \(O(m)\) equality tests and table transitions occur.

The search maintains the number <code>matched</code> of pattern elements matching a suffix of the text processed so far:

~~~python
def kmp_find(
    text: Sequence[T],
    pattern: Sequence[T],
) -> int | None:
    if len(pattern) == 0:
        return 0

    prefix = prefix_lengths(pattern)
    matched = 0

    for text_index, value in enumerate(text):
        while matched > 0 and value != pattern[matched]:
            matched = prefix[matched - 1]
        if value == pattern[matched]:
            matched += 1
        if matched == len(pattern):
            return text_index - len(pattern) + 1

    return None
~~~

At the end of each processed text position, <code>matched</code> is the length of the longest pattern prefix equal to a suffix ending there. A mismatch discards only border lengths proven impossible and never re-examines a text element at an earlier index. As in table construction, increases and decreases of <code>matched</code> give \(O(n)\) search transitions after \(O(m)\) preprocessing. Auxiliary storage is \(O(m)\).

If every match is required, after emitting a match reset <code>matched = prefix[matched - 1]</code> and continue; this preserves overlapping occurrences. The additional output cost is \(\Omega(z)\) for \(z\) match indices.

Knuth–Morris–Pratt’s theoretical benefit is worst-case \(O(n+m)\) equality work. It is not necessarily the fastest implementation for every concrete string. Python’s built-in <code>str.find</code> and membership operations may use highly optimised implementation-specific algorithms, native loops, specialised character widths, and platform-aware routines. Portable code should rely on their documented result semantics rather than asserting a particular internal search family.

#### Rolling hashes

Rabin–Karp search compares a numeric fingerprint for each length-\(m\) window with the pattern fingerprint. A **rolling hash** updates the next window from the previous one in constant modular-arithmetic steps rather than rehashing every element.

~~~python
def rabin_karp_find(text: bytes, pattern: bytes) -> int | None:
    if not pattern:
        return 0
    if len(pattern) > len(text):
        return None

    base = 257
    modulus = 1_000_000_007
    high_place = pow(base, len(pattern) - 1, modulus)

    pattern_hash = 0
    window_hash = 0
    for pattern_byte, text_byte in zip(
        pattern,
        text[: len(pattern)],
    ):
        pattern_hash = (
            pattern_hash * base + pattern_byte
        ) % modulus
        window_hash = (
            window_hash * base + text_byte
        ) % modulus

    for start in range(len(text) - len(pattern) + 1):
        if (
            window_hash == pattern_hash
            and text[start : start + len(pattern)] == pattern
        ):
            return start

        if start + len(pattern) < len(text):
            outgoing = text[start]
            incoming = text[start + len(pattern)]
            window_hash = (
                (window_hash - outgoing * high_place) * base
                + incoming
            ) % modulus

    return None
~~~

Equal substrings produce equal fingerprints, but distinct substrings may collide. The explicit byte comparison after a hash match preserves correctness. Under a suitable collision model, expected work is \(O(n+m)\) plus match verification; adversarial or unlucky collisions can cause \(O(nm)\) verification. The modulus and base here are pedagogical and are not a cryptographic authentication mechanism.

Rolling hashes are particularly useful when searching several patterns of one length or comparing many windows. KMP uses deterministic prefix structure for one pattern; Rabin–Karp uses fingerprints and accepts collision verification. Aho–Corasick extends trie structure with failure links to search many patterns in one text. These are distinct answers to distinct workload structures.

#### Text is not always a sequence of user-perceived characters

Python strings are sequences of Unicode code points at the language level. A user-perceived grapheme can contain several code points, and canonically equivalent text can have different code-point sequences. Exact substring algorithms operate on the representation supplied. Searching human text may first require a documented Unicode normalisation and case policy; security-sensitive identifiers may deliberately forbid such equivalence.

**Audit caution — “substring” is not self-defining.** Byte substring, code-point substring, normalised linguistic match, locale-aware case-insensitive match, token sequence, and regular-expression match are different problems. Algorithmic correctness begins only after choosing one.
