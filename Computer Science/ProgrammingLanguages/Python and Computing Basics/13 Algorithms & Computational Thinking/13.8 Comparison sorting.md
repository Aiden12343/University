# 13.8 Comparison sorting

A **sorting algorithm** rearranges elements into non-decreasing order under a comparator or key. Additional properties include:

- **stability:** equal keys preserve relative input order;
- **in-place:** uses bounded or sublinear additional element storage under a defined model;
- **adaptive:** exploits existing order;
- worst-, average-, and best-case time;
- comparison and movement costs.

### Insertion sort

```python
def insertion_sort(values: list[int]) -> None:
    for index in range(1, len(values)):
        item = values[index]
        position = index

        while position > 0 and values[position - 1] > item:
            values[position] = values[position - 1]
            position -= 1

        values[position] = item
```

Outer invariant: before iteration at `index`, prefix `values[:index]` is sorted and contains exactly the original prefix elements. The inner loop shifts larger prefix elements right until `item` belongs at `position`. It is stable because equal elements are not shifted past one another under strict `>`.

Worst-case reversed input causes approximately (n(n-1)/2) comparisons and shifts, (Theta(n^2)). Already sorted input makes one comparison per outer iteration, (Theta(n)), showing adaptivity. Insertion sort is effective for small arrays and nearly sorted runs and appears as a component in hybrid algorithms.

### Merge sort

Merge sort divides the sequence, recursively sorts halves, and merges two sorted sequences.

```python
def merge_sort(values: list[int]) -> list[int]:
    if len(values) < 2:
        return values.copy()

    middle = len(values) // 2
    left = merge_sort(values[:middle])
    right = merge_sort(values[middle:])
    return merge(left, right)


def merge(left: list[int], right: list[int]) -> list[int]:
    result: list[int] = []
    i = 0
    j = 0

    while i < len(left) and j < len(right):
        if left[i] <= right[j]:
            result.append(left[i])
            i += 1
        else:
            result.append(right[j])
            j += 1

    result.extend(left[i:])
    result.extend(right[j:])
    return result
```

Merge invariant: `result` is sorted and contains exactly the consumed prefixes; every unconsumed item is no smaller than the final result item. Selecting the smaller front preserves it. `<=` selects from the left on equality, preserving stability.

The recursion has (log n) levels and performs (Theta(n)) merge work per level, giving (Theta(n\log n)) time. This implementation allocates slices and result lists, using (Theta(n)) peak auxiliary element-reference space plus recursion overhead under a careful accounting.

### Lower bound

Any deterministic comparison sort distinguishing arbitrary orders needs (Omega(n\log n)) comparisons in the worst case. A decision-tree argument has at least (n!) leaves, one per permutation, and a binary comparison tree of height (h) has at most (2^h) leaves. Thus (2^h\geq n!), so (h\geq\log_2(n!)=\Omega(n\log n)).

Non-comparison algorithms such as counting sort can beat this bound by exploiting key structure and range; they do not contradict it because their operations reveal more than pairwise relative order.

### 13.8.1 Selection sort separates selection from placement

**Selection sort** repeatedly finds the minimum of the unsorted suffix and exchanges it with the suffix’s first position.

~~~python
def selection_sort(values: list[int]) -> None:
    for boundary in range(len(values) - 1):
        minimum = boundary
        for index in range(boundary + 1, len(values)):
            if values[index] < values[minimum]:
                minimum = index
        values[boundary], values[minimum] = (
            values[minimum],
            values[boundary],
        )
~~~

At the start of iteration <code>boundary</code>:

1. the prefix before <code>boundary</code> contains the globally smallest elements in sorted order;
2. the suffix contains exactly the remaining elements.

The inner invariant says <code>minimum</code> indexes a minimum of the suffix portion inspected so far. After the scan, swapping places a suffix minimum at the boundary and preserves the outer invariant.

For every input order, the number of less-than comparisons is

\[
(n-1)+(n-2)+\cdots+1=\frac{n(n-1)}2.
\]

At most \(n-1\) swaps occur. Selection sort can therefore be useful in an abstract setting where comparisons are cheap but writes are unusually expensive. The implementation is not stable: swapping a later minimum forward can move one equal-key record behind another. Stability can be engineered by shifting rather than swapping, but then movement cost rises.

Selection sort and insertion sort share \(\Theta(n^2)\) worst-case time yet behave differently. Insertion sort is adaptive and stable as written; selection sort performs its full comparison count regardless of presortedness. Complexity class alone does not describe an algorithm.

> **Common misconception 13.31 — “Algorithms in the same \(\Theta\) class are interchangeable.”**  
> Stability, adaptiveness, writes, auxiliary storage, comparison cost, locality, and failure behaviour can differ substantially within one asymptotic class.

### 13.8.2 Bubble sort and the value of a weak algorithm

Bubble sort repeatedly compares adjacent elements and swaps inverted pairs. A pass moves at least one maximal remaining element to its final suffix position.

~~~python
def bubble_sort(values: list[int]) -> None:
    unsorted_end = len(values)
    while unsorted_end > 1:
        last_swap = 0
        for index in range(1, unsorted_end):
            if values[index] < values[index - 1]:
                values[index - 1], values[index] = (
                    values[index],
                    values[index - 1],
                )
                last_swap = index
        unsorted_end = last_swap
~~~

If no swap occurs, <code>last_swap</code> remains zero and the algorithm terminates. More precisely, after a pass, every position from <code>last_swap</code> onward is already in final sorted relation to what follows, so the next pass can stop there.

Adjacent swaps under strict less-than preserve stability. The algorithm is \(\Theta(n)\) on sorted input with this early-exit rule and \(\Theta(n^2)\) in the worst case. It usually performs more movements than insertion sort and has no advantage over Python’s production sort. Its pedagogical value lies in inversion reasoning: each adjacent swap removes exactly one inversion, so any adjacent-swap-only sorting algorithm requires at least \(I\) swaps for an input with \(I\) inversions.

> **Common misconception 13.32 — “Bubble sort is a reasonable default because it is simple.”**  
> Simplicity is one engineering criterion, but Python already supplies a stable, extensively tested, adaptive \(O(n\log n)\)-worst-case sort. Bubble sort is primarily an object of analysis and specialised adjacent-exchange constraints.

### 13.8.3 Merging without recursive slices

The earlier merge-sort implementation is clear but allocates list slices at every recursive division. A bottom-up implementation alternates source and destination arrays and makes allocation explicit:

~~~python
from typing import TypeVar

T = TypeVar("T")


def bottom_up_merge_sort(values: list[T]) -> list[T]:
    source = values.copy()
    destination = source.copy()
    width = 1

    while width < len(source):
        for start in range(0, len(source), 2 * width):
            middle = min(start + width, len(source))
            end = min(start + 2 * width, len(source))
            merge_into(source, destination, start, middle, end)
        source, destination = destination, source
        width *= 2

    return source


def merge_into(
    source: list[T],
    destination: list[T],
    start: int,
    middle: int,
    end: int,
) -> None:
    left = start
    right = middle

    for output in range(start, end):
        if right >= end or (
            left < middle and not source[right] < source[left]
        ):
            destination[output] = source[left]
            left += 1
        else:
            destination[output] = source[right]
            right += 1
~~~

The two input runs <code>[start, middle)</code> and <code>[middle, end)</code> are sorted. The merge condition chooses the left item unless the right item is strictly smaller. Avoiding <code>&lt;=</code> means the generic type needs only less-than, matching Python sorting’s preference for that relation; choosing left on equivalence preserves stability.

After passes of widths \(1,2,4,\ldots\), all runs of the resulting doubled width are sorted. There are \(\lceil\log_2 n\rceil\) passes, each reading and writing \(\Theta(n)\) references, so time is \(\Theta(n\log n)\). Two full lists exist during the operation; auxiliary reference storage is \(\Theta(n)\). The implementation returns a new list and does not mutate the caller’s list, although references to mutable elements are shared.

External merge sort extends the same invariant to storage too large for memory. It creates sorted runs that fit in memory, writes them, and performs a multiway merge with buffered I/O. Its chief cost model counts block transfers and seeks rather than only comparisons. An algorithm’s decomposition can survive while its relevant resources change.

> **Common misconception 13.33 — “Merge sort necessarily copies each element object.”**  
> A Python list implementation normally copies or moves references. Element objects remain shared unless the algorithm explicitly clones them.

### 13.8.4 Quicksort and partition invariants

Quicksort selects a **pivot**, partitions elements around it, and recursively sorts the partitions. Its attraction is good locality and small auxiliary arrays in common in-place implementations. Its hazard is unbalanced partitioning.

A three-way functional version makes duplicate handling clear:

~~~python
from typing import TypeVar

T = TypeVar("T")


def quicksort(values: list[T]) -> list[T]:
    if len(values) < 2:
        return values.copy()

    pivot = values[len(values) // 2]
    lower: list[T] = []
    equal: list[T] = []
    upper: list[T] = []

    for value in values:
        if value < pivot:
            lower.append(value)
        elif pivot < value:
            upper.append(value)
        else:
            equal.append(value)

    return quicksort(lower) + equal + quicksort(upper)
~~~

This treats values as equivalent when neither is less than the other. It allocates partitions and is stable only under assumptions about equivalence and recursive concatenation; it is not the traditional in-place quicksort.

If partition sizes are \(k\) and \(n-k-1\), the recurrence is

\[
T(n)=T(k)+T(n-k-1)+\Theta(n).
\]

Balanced partitions yield \(\Theta(n\log n)\). Repeated \(0\) and \(n-1\) partitions yield

\[
T(n)=T(n-1)+\Theta(n)=\Theta(n^2)
\]

and \(\Theta(n)\) recursion depth. Selecting the first element as pivot makes already sorted input adversarial for a common two-way formulation.

A uniformly random pivot gives expected \(\Theta(n\log n)\) comparisons for every fixed input arrangement, assuming randomness independent of the input. Randomisation does not remove the quadratic worst case; it makes consistently bad partition sequences unlikely under the model. Median-of-three and introspective fallback policies offer different engineering protections.

**Introsort** begins with quicksort-like partitioning, switches to heapsort if recursion depth indicates persistent imbalance, and often uses insertion sort for small partitions. It demonstrates hybrid design: retain common-case locality while imposing an \(O(n\log n)\) worst-case bound.

> **Common misconception 13.34 — “Randomised quicksort is worst-case \(O(n\log n)\).”**  
> Its expected cost can be \(\Theta(n\log n)\) for each fixed input, while some random pivot sequences still produce \(\Theta(n^2)\) work.

### 13.8.5 Heap sort

A max-heap places a maximum at its root. Heap sort builds a max-heap, swaps the root with the final unsorted element, reduces the heap boundary, and restores the heap.

~~~python
def heap_sort(values: list[int]) -> None:
    length = len(values)

    for root in range(length // 2 - 1, -1, -1):
        sift_down(values, root, length)

    for end in range(length - 1, 0, -1):
        values[0], values[end] = values[end], values[0]
        sift_down(values, 0, end)


def sift_down(values: list[int], root: int, end: int) -> None:
    while True:
        left = 2 * root + 1
        if left >= end:
            return

        larger = left
        right = left + 1
        if right < end and values[larger] < values[right]:
            larger = right

        if not values[root] < values[larger]:
            return

        values[root], values[larger] = values[larger], values[root]
        root = larger
~~~

During extraction:

- <code>values[:end]</code> is a max-heap;
- <code>values[end:]</code> is sorted and contains the largest values;
- every heap value is no greater than every suffix value.

The swap places the heap maximum immediately before the sorted suffix. Sifting restores the heap over the reduced prefix.

One sift costs \(O(\log n)\). Repeating it \(n-1\) times costs \(O(n\log n)\). Bottom-up heap construction is \(O(n)\), not \(O(n\log n)\): most nodes lie near the leaves and travel only a few levels. If a node of height \(h\) costs \(O(h)\), summing heights over a complete binary tree is linear:

\[
\sum_{h\ge0} O\left(\frac{n}{2^{h+1}}h\right)=O(n).
\]

Heap sort is in-place under an \(O(1)\)-word auxiliary convention and has \(O(n\log n)\) worst-case time. It is not stable in this form and often has poorer locality than highly engineered alternatives.

> **Common misconception 13.35 — “Building a heap by repeated insertion and bottom-up heapify have the same cost.”**  
> Repeated insertion is \(O(n\log n)\) in the worst case. Bottom-up heapify is \(O(n)\) because few nodes can move far.

### 13.8.6 Sorting beyond the comparison model

If keys have exploitable structure, sorting need not learn order solely through comparisons. **Counting sort** handles integer keys in a bounded range:

~~~python
from collections.abc import Callable, Sequence
from typing import TypeVar

T = TypeVar("T")


def counting_sort(
    values: Sequence[T],
    *,
    key: Callable[[T], int],
) -> list[T]:
    if not values:
        return []

    keys = [key(value) for value in values]
    minimum = min(keys)
    maximum = max(keys)
    counts = [0] * (maximum - minimum + 1)

    for item_key in keys:
        counts[item_key - minimum] += 1

    for index in range(1, len(counts)):
        counts[index] += counts[index - 1]

    result = [values[0]] * len(values)
    for value, item_key in zip(reversed(values), reversed(keys)):
        bucket = item_key - minimum
        counts[bucket] -= 1
        result[counts[bucket]] = value

    return result
~~~

Let \(n\) be item count and \(k=maximum-minimum+1\) the key range. Time and auxiliary storage are \(\Theta(n+k)\), excluding key-function cost beyond one call per item. Reverse traversal during placement preserves stability: later equal-key items claim later positions.

When \(k\gg n\), the counts array can be prohibitive. A dictionary of counts reduces storage for sparse keys but recovering sorted key order then costs at least sorting distinct keys or using another ordered structure.

**Radix sort** processes key digits using a stable sub-sort. Least-significant-digit radix sorting \(d\) digits in radix \(b\) costs \(O(d(n+b))\) under a fixed digit-extraction model. It is linear in \(n\) only when \(d\) and \(b\) are treated as suitably bounded. For arbitrary-size integers, \(d\) grows with bit length.

**Bucket sort** distributes values among ranges and sorts within buckets. Its expected linear claims require distribution assumptions; an adversarial concentration in one bucket can recover the inner sort’s worst case.

These algorithms do not violate the comparison lower bound. Array indexing by an integer digit reveals information unavailable to a pure comparison decision tree and may allocate storage proportional to the key universe.

> **Common misconception 13.36 — “Counting or radix sort proves the \(\Omega(n\log n)\) sorting lower bound false.”**  
> The lower bound is for arbitrary keys in the comparison model. Structured-key algorithms use stronger operations and carry range, digit, or distribution costs.

### 13.8.7 Sorting properties and selection

The principal algorithms can be compared only after fixing implementations:

| Algorithm | Best time | Worst time | Typical auxiliary element storage | Stable as presented | Adaptive |
|---|---:|---:|---:|:---:|:---:|
| insertion | \(\Theta(n)\) | \(\Theta(n^2)\) | \(\Theta(1)\) | yes | yes |
| selection | \(\Theta(n^2)\) | \(\Theta(n^2)\) | \(\Theta(1)\) | no | no |
| bubble with boundary | \(\Theta(n)\) | \(\Theta(n^2)\) | \(\Theta(1)\) | yes | yes |
| merge, array-backed | \(\Theta(n\log n)\) | \(\Theta(n\log n)\) | \(\Theta(n)\) | yes | weakly without run detection |
| randomised quicksort | expected \(\Theta(n\log n)\) | \(\Theta(n^2)\) | recursion/partitions vary | varies | no |
| heap sort | \(\Theta(n\log n)\) | \(\Theta(n\log n)\) | \(\Theta(1)\) | no | no |
| counting | \(\Theta(n+k)\) | \(\Theta(n+k)\) | \(\Theta(n+k)\) | yes as presented | no |

Sorting is unnecessary when the problem asks only for the \(k\)-th order statistic. **Quickselect** partitions as quicksort does but recurses into only the partition containing the requested rank. It has expected linear time with suitable randomisation and quadratic worst case. Deterministic median-of-medians pivot selection guarantees linear worst-case time, with larger constants and a more involved proof.

For a tiny number \(k\) of extreme items, a heap can produce top-\(k\) results in \(O(n\log k)\) time and \(O(k)\) storage. If fully sorted output is required, an \(\Omega(n\log n)\) comparison cost returns. Solve the requested output problem rather than sorting by habit.

> **Common misconception 13.37 — “To find the minimum, median, or top ten, first sort everything.”**  
> Full sorting computes more order information than selection may require. A scan finds an extremum in \(\Theta(n)\); selection and bounded heaps offer other task-specific bounds.
