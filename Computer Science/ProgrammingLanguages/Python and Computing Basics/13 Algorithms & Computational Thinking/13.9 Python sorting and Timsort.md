# 13.9 Python sorting and Timsort

Python’s `list.sort` and `sorted` are stable and use Timsort, an adaptive hybrid algorithm exploiting existing ordered runs and merging under carefully engineered invariants. Worst-case comparison growth is (O(n\log n)), while ordered structure can reduce work substantially.

Use key functions rather than comparators when possible:

```python
ordered = sorted(records, key=lambda record: (record.surname.casefold(), record.identifier))
```

The key is computed once per element under the sorting contract, then cached for comparisons. A comparator adapter can be built with `functools.cmp_to_key` for legacy interfaces, but a comparator must define a coherent ordering and can run many times.

Sorting a list containing incomparable keys raises `TypeError`; partial mutation can occur before a `list.sort` failure under documented cautions. Validate and derive keys before mutating critical original order where failure atomicity matters.

### 13.9.1 Language guarantees and implementation facts

The Python language/library contract guarantees that <code>list.sort()</code> modifies a list in place and returns <code>None</code>, while <code>sorted()</code> consumes an iterable and returns a new list. Both accept keyword-only <code>key</code> and <code>reverse</code> arguments and guarantee stability.

The fact that CPython 3.12 implements these operations with Timsort is an implementation fact documented in the sorting HOWTO and CPython source material; alternative conforming Python implementations may use another algorithm while preserving specified behaviour. Even within CPython, tuning constants and merge policies are not stable application interfaces.

Timsort identifies naturally ascending or descending **runs**, extends short runs using insertion-like techniques, and merges runs while maintaining size invariants. Existing order can therefore reduce comparisons. Its “galloping” mode accelerates certain merges when consecutive selections repeatedly come from one run. A complete proof and engineering account resides in implementation literature; applications should depend on stability and ordering results, not internal run-stack thresholds.

The key function is evaluated once for each input element during a successful ordinary sort invocation. Key caching converts repeated potentially expensive derivation into one derivation plus comparisons of cached keys. It does not imply that the key is pure: calls can have side effects or fail, which makes such a key hard to reason about.

> **Common misconception 13.38 — “Python guarantees Timsort forever.”**  
> Python guarantees documented sorting semantics, including stability. Timsort is the current CPython implementation strategy, not a necessary part of every conforming implementation’s contract.

### 13.9.2 Stability as a composition tool

Stability means that if two elements have equal keys, their relative input order is retained. It enables multi-pass sorting from least significant criterion to most significant criterion:

~~~python
from dataclasses import dataclass


@dataclass(frozen=True)
class Student:
    name: str
    cohort: int
    mark: int


students = [
    Student("Ada", 2, 78),
    Student("Grace", 1, 91),
    Student("Edsger", 2, 91),
]

by_mark_then_cohort = sorted(students, key=lambda item: item.mark)
by_mark_then_cohort.sort(key=lambda item: item.cohort)
~~~

The second stable pass makes cohort primary while preserving mark order within each cohort. A tuple key expresses the same policy more directly:

~~~python
equivalent = sorted(
    students,
    key=lambda item: (item.cohort, item.mark),
)
assert equivalent == by_mark_then_cohort
~~~

Descending one field but ascending another requires care. Negating a numeric key works for ordinary finite numbers but not all types and interacts with NaN. A stable multi-pass approach can apply different <code>reverse</code> settings from the least significant field upward.

The historical **decorate–sort–undecorate** pattern constructs tuples containing derived keys, possibly an original index, and the value; sorts them; then removes decoration. Python’s built-in key support internalises the common key-caching need, but explicit decoration remains useful for mixed direction, audited key validation, or deterministic tie policies.

~~~python
decorated = [
    (student.cohort, -student.mark, index, student)
    for index, student in enumerate(students)
]
decorated.sort()
ordered_students = [entry[-1] for entry in decorated]
~~~

The index prevents Python from needing to compare <code>Student</code> objects when the preceding keys tie and makes original-order tie breaking explicit.

> **Common misconception 13.39 — “A stable sort leaves equal-valued objects at their original indices.”**  
> It preserves their relative order with respect to one another. Other elements can move around them, so absolute indices generally change.

### 13.9.3 Ordering must be coherent

Sorting algorithms assume a comparison relation with enough order structure. A **strict weak ordering**, the common algorithmic requirement, is irreflexive and transitive and induces transitive equivalence among values incomparable in either direction. Python does not dynamically prove these laws. A user-defined <code>__lt__</code> that changes over time or creates cycles can yield meaningless order.

Floating-point NaN is a prominent boundary: comparisons such as \(x&lt;\mathrm{NaN}\), \(\mathrm{NaN}&lt;x\), and \(\mathrm{NaN}==\mathrm{NaN}\) are false. A robust application defines a total placement policy:

~~~python
from math import isnan


def numeric_sort_key(value: float) -> tuple[bool, float]:
    if isnan(value):
        return (True, 0.0)
    return (False, value)


readings = [3.0, float("nan"), -1.0, 2.0]
ordered = sorted(readings, key=numeric_sort_key)
assert ordered[:3] == [-1.0, 2.0, 3.0]
assert isnan(ordered[-1])
~~~

Heterogeneous values such as integers and strings have no default cross-type numerical/text order in modern Python. Derive a tagged key only if the domain has a defensible policy:

~~~python
def mixed_key(value: int | str) -> tuple[int, int | str]:
    if isinstance(value, int):
        return (0, value)
    return (1, value.casefold())
~~~

Case folding can make distinct strings share a primary key; stability or an explicit secondary original string determines ties. Locale-aware collation is a separate policy and may require specialised facilities.

Mutation during <code>list.sort</code>, inconsistent comparisons, and exceptions from keys or comparison methods can expose partially transformed state or specified implementation restrictions. If preserving the original is essential, sort a copy or compute and validate decorations before committing:

~~~python
def safely_sorted_numbers(raw: list[str]) -> list[str]:
    decorated: list[tuple[int, int, str]] = []
    for index, text in enumerate(raw):
        parsed = int(text)
        decorated.append((parsed, index, text))
    decorated.sort()
    return [text for _, _, text in decorated]
~~~

All integer conversions finish before sorting begins. If conversion fails, <code>raw</code> remains unchanged. This is a transaction-like design choice, not a special guarantee supplied by sorting.

> **Common misconception 13.40 — “If <code>__lt__</code> returns a Boolean, the object is sortable correctly.”**  
> A comparator must obey order laws consistently over the operation. Returning Boolean values is syntactically sufficient but not semantically sufficient.
