# 14.1 Concurrency is a lifetime relation

Two tasks are **concurrent** when their lifetimes overlap and the system must reason about their possible interleavings. **Parallelism** is simultaneous execution of operations on multiple processing resources. One CPU core can support concurrency by switching among tasks; several cores can execute in parallel. A parallel program is concurrent, but a concurrent program need not run operations simultaneously.

**Latency** is time from one request to its result. **Throughput** is completed work per unit time. Parallelism can increase throughput without reducing one request’s latency; coordination overhead can even increase it. Concurrency can reduce idle time by allowing other work while one task waits.

Workloads are often described as:

- **CPU-bound:** progress is limited primarily by computation on processors;
- **I/O-bound:** progress is limited primarily by waiting for external transfers or devices;
- **memory-bound:** progress is limited by memory access bandwidth or latency;
- **contention-bound:** progress is limited by competition for shared resources or locks.

These are measured diagnoses, not permanent labels on functions. The same code can change category with input, cache state, hardware, or environment.

### 14.1.1 Activities, resources, and schedules

An **activity** is an execution with its own progress state: an operating-system thread, process, event-loop task, device command, or remote request may each be treated as an activity at the relevant level. A **scheduler** selects which eligible activity may advance. A **schedule** is one permitted ordering of their execution steps.

The word “step” again depends on a model. Source statements are not indivisible physical events. The expression <code>total += amount</code> conceptually reads a binding, performs addition, and writes a binding; operators can invoke user code. At another level, a processor instruction can itself interact with caches and other cores. Correct concurrent reasoning declares which transitions are atomic at the chosen interface.

An activity is **ready** when it could execute if assigned a processing resource, **running** while instructions are being executed for it, **blocked** while it awaits an event or resource, and **terminated** after normal or exceptional completion. These are conceptual states; operating systems and runtimes use richer state machines.

**Pre-emption** occurs when a scheduler suspends an activity without that activity explicitly yielding. Operating-system threads are ordinarily pre-emptively scheduled. <code>asyncio</code> tasks cooperate at suspension points, although signals, callbacks, native threads, and underlying I/O still introduce external concurrency.

> **Common misconception 14.1 — “Concurrency requires several CPU cores.”**  
> One core can interleave several activities whose lifetimes overlap. Additional cores permit physical parallelism but do not define concurrency.

### 14.1.2 Logical time and nondeterminism

In sequential code, program order supplies one dominant before–after relation. Concurrent activities introduce only a **partial order**: some events are constrained, while others may occur in either order. A relation is partial when not every pair must be comparable.

An execution is **deterministic** with respect to an observation when every admitted schedule and environmental input produces the same observation. A program can be correct yet nondeterministic: a server may accept either waiting connection first while still processing both exactly once. Conversely, repeatable output does not prove race freedom; a defective schedule may simply be rare on the tested machine.

An **interleaving model** represents concurrency as a sequence of atomic steps chosen from activities. It is useful for proofs even when hardware executes truly simultaneously, provided the specified atomic operations can be linearised into an equivalent order. Weak memory effects and lock-free algorithms require a more detailed model; this chapter first builds the lock-based discipline that Python application code most often needs.

> **Common misconception 14.2 — “Nondeterministic output means the program is incorrect.”**  
> Correctness is judged against a contract. A contract may admit several results, but invariants such as exactly-once ownership and valid structure must hold for every permitted schedule.

### 14.1.3 Concurrency does not create capacity

Concurrency can hide waiting and improve utilisation, but every resource remains finite:

- processor cores execute bounded work;
- memory holds bounded live state;
- file-descriptor and connection pools have limits;
- remote services accept bounded rates;
- storage and networks have finite throughput;
- locks and serial components admit one or a bounded number of users.

If requests arrive faster than they complete, unfinished work accumulates. Let arrival rate be \(\lambda\) requests per second, average number in the system be \(L\), and average time in the system be \(W\). Under stable long-run conditions, **Little’s law** states

\[
L=\lambda W.
\]

At 500 requests per second and 0.2 seconds mean residence time, approximately 100 requests are present on average. This is a conservation relation, not a guarantee about tail latency or a prescription for worker count.

Concurrency limits are therefore semantic control points. A semaphore of 50 does not make a downstream database faster; it prevents one caller from creating more than 50 simultaneous uses. A queue bound determines whether overload blocks, rejects, drops, or spills work.

> **Common misconception 14.3 — “More concurrent work increases throughput indefinitely.”**  
> Concurrency can expose available capacity. Beyond a bottleneck it adds queueing, context switching, memory, cache pressure, and contention, often increasing latency and reducing throughput.

### 14.1.4 Decompose elapsed time

For one operation, elapsed latency may contain:

\[
T_{\text{elapsed}}
=T_{\text{run}}
+T_{\text{ready-wait}}
+T_{\text{resource-wait}}
+T_{\text{coordination}}
+T_{\text{transfer}}.
\]

The terms overlap in a system-wide account: while one request waits for storage, another may use the CPU. CPU time measures execution consumed by a process or thread; wall-clock time measures elapsed duration. A speedup claim must identify which is improved.

**Utilisation** is the fraction of a resource’s capacity occupied during an interval. High utilisation is not automatically desirable. As a queueing resource approaches saturation, waiting time can rise sharply because small bursts have no spare capacity. A latency-sensitive service commonly operates below theoretical maximum throughput.

**Work** is total operation count across all parallel activities. **Span** or **critical-path length** is the longest dependency chain. On \(p\) ideal processors, execution time is bounded below by both \(W/p\) and span \(S\):

\[
T_p\ge\max(W/p,S).
\]

Parallelism cannot shorten dependencies on the critical path.

> **Common misconception 14.4 — “If four workers finish a batch four times faster, each item became faster.”**  
> Batch throughput and individual latency differ. Parallel workers can reduce batch makespan while leaving one item’s service time unchanged or larger.
