# 14.10 Structured concurrency with task groups

**Structured concurrency** requires child task lifetimes to remain inside an owning lexical or dynamic scope. Python’s `asyncio.TaskGroup` creates sibling tasks and waits for them when the context exits. If a child fails, remaining siblings are cancelled under the task-group contract and failures are combined appropriately.

```python
import asyncio


async def fetch(identifier: int) -> str:
    await asyncio.sleep(0.01)
    return f"item-{identifier}"


async def fetch_all(identifiers: list[int]) -> list[str]:
    tasks: list[asyncio.Task[str]] = []
    async with asyncio.TaskGroup() as group:
        for identifier in identifiers:
            tasks.append(group.create_task(fetch(identifier)))
    return [task.result() for task in tasks]
```

Leaving the `async with` normally establishes that every created task completed successfully. A failing child changes the exit path; successful results should not be consumed as though the group completed normally.

Creating a task and discarding its reference creates unclear ownership. Its exception may be reported late, cancellation may be unmanaged, and application shutdown may abandon it. Structured scopes make completion and failure obligations visible.

### 14.10.1 Lifetime nesting is the principal invariant

Structured concurrency treats a concurrent operation like a function call: it does not return normally while owned child work remains unresolved. The lexical task-group scope establishes:

- every child is awaited before exit;
- on ordinary exit, every child completed successfully;
- on qualifying child failure, siblings receive cancellation;
- the group waits for sibling termination and cleanup;
- non-cancellation failures are reported together.

This restores local reasoning. A caller inspecting the result after <code>fetch_all</code> returns need not search a global task registry for still-running children created by that call.

The group may receive new tasks while active, including from children given access to it. Once shutdown begins, admission rules change. Passing the group widely weakens ownership clarity even if the API permits it.

> **Common misconception 14.43 — “Structured concurrency means tasks execute in source-code order.”**  
> It constrains lifetime and failure ownership, not scheduling order. Siblings still interleave and may complete in any permitted order.

### 14.10.2 Failure aggregation

Several siblings can fail before cancellation reaches them or while cleaning up. Python 3.11 introduced exception groups and <code>except*</code> so multiple independent exceptions are not discarded.

~~~python
import asyncio


class DownloadError(Exception):
    pass


class ParseError(Exception):
    pass


async def download() -> None:
    await asyncio.sleep(0)
    raise DownloadError("network response invalid")


async def parse() -> None:
    await asyncio.sleep(0)
    raise ParseError("document malformed")


async def run_group() -> None:
    try:
        async with asyncio.TaskGroup() as group:
            group.create_task(download())
            group.create_task(parse())
    except* DownloadError as failures:
        for failure in failures.exceptions:
            print(f"download: {failure}")
    except* ParseError as failures:
        for failure in failures.exceptions:
            print(f"parse: {failure}")
~~~

The set of observed failures can depend on scheduling and cancellation timing; do not write a test demanding both children always reach their explicit raise. Each <code>except*</code> handles matching leaves while unmatched exceptions continue propagating.

<code>KeyboardInterrupt</code> and <code>SystemExit</code> receive special TaskGroup treatment in Python 3.12: siblings are still cancelled and awaited, then the original base exception is re-raised rather than wrapped as an ordinary exception group.

Cancellation exceptions are normally control signals and are not aggregated like ordinary failures. Code that catches and suppresses <code>CancelledError</code> can interfere with task-group shutdown and timeout mechanisms.

> **Common misconception 14.44 — “A task group reports whichever child failed first and discards the rest.”**  
> It can aggregate multiple non-cancellation failures after cancelling and awaiting siblings. Which failures occur remains schedule- and cleanup-dependent.

### 14.10.3 Results require successful scope exit

Task objects returned by <code>create_task</code> retain results. Read them after the context exits normally:

~~~python
import asyncio


async def square(value: int) -> int:
    await asyncio.sleep(0)
    return value * value


async def squares(values: list[int]) -> list[int]:
    tasks: list[asyncio.Task[int]] = []
    async with asyncio.TaskGroup() as group:
        for value in values:
            tasks.append(group.create_task(square(value)))
    return [task.result() for task in tasks]
~~~

If the group exits exceptionally, control does not reach the result comprehension unless the exception is caught. Some tasks may have succeeded, others failed, and others been cancelled. A partial-results contract requires explicit handling rather than pretending the all-or-fail group returned normally.

Nested groups form a failure tree. A component can catch and convert expected child failures into domain results while letting unexpected failures propagate to its owner. This is supervision with lexical boundaries.

TaskGroup is not a transaction. Cancelling siblings does not undo external writes already committed. Atomic business effects still require idempotency keys, database transactions, compensating operations, or staging followed by commit.

> **Common misconception 14.45 — “Cancelling sibling tasks rolls back their work.”**  
> Cancellation changes future execution. Effects completed before cancellation remain unless an explicit transactional or compensating protocol reverses them.
