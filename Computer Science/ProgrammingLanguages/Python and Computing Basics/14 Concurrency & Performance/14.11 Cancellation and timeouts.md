# 14.11 Cancellation and timeouts

**Cancellation** is a control request asking a task to stop at a cooperative suspension point. In `asyncio`, cancellation appears through `CancelledError`, which cleanup code should generally propagate after releasing resources.

```python
async def use_resource(resource) -> None:
    await resource.open()
    try:
        await resource.process()
    finally:
        await resource.close()
```

Suppressing cancellation without completing the intended operation can make an owner believe the task stopped when it continues. Cleanup must itself respect cancellation and timeout policy; sometimes limited shielding is needed to preserve an invariant, but it must not create unbounded shutdown.

A **timeout** is a policy limiting how long an operation may remain incomplete, not proof that the underlying work ceased. Network, thread, or external service activity can continue after the caller stops waiting. APIs must define cancellation propagation and resource cleanup.

```python
async def run_with_timeout(operation):
    async with asyncio.timeout(2.0):
        return await operation()
```

Timeout values are environmental policy and should be configurable at an owning boundary. Retrying after a timeout is safe only if the operation is idempotent or has a request-identity protocol preventing duplicate effects.

### 14.11.1 Cancellation is delivered, not imposed

Calling <code>task.cancel()</code> does not seize the processor and destroy a task. It arranges for <code>asyncio.CancelledError</code> to be raised in the task at a suitable opportunity, normally when the task next suspends. The task may already have completed; it may be running Python code without an await point; it may be awaiting another future to which cancellation is propagated; or it may catch the exception. Cancellation is therefore a protocol implemented by the task, its awaitables, and its owner.

In modern Python, <code>CancelledError</code> derives directly from <code>BaseException</code>, not <code>Exception</code>. A broad <code>except Exception</code> consequently does not suppress it, which protects cancellation from many accidental handlers. A bare <code>except:</code> or <code>except BaseException</code> still can. Code that catches cancellation to record state or perform special cleanup should ordinarily re-raise it:

~~~python
import asyncio
from collections.abc import Awaitable, Callable


async def cancellable_worker(
    acquire_resource: Callable[[], Awaitable[object]],
    process_one_unit: Callable[[object], Awaitable[None]],
    release_resource: Callable[[object], Awaitable[None]],
    record_cancellation: Callable[[], None],
) -> None:
    resource = await acquire_resource()
    try:
        while True:
            await process_one_unit(resource)
    except asyncio.CancelledError:
        record_cancellation()
        raise
    finally:
        await release_resource(resource)
~~~

The <code>finally</code> suite runs for normal return, ordinary failure, and cancellation. The explicit handler records cancellation but does not convert it into success. Whether <code>release_resource</code> may itself be interrupted is a separate contractual question addressed below.

Cancellation latency is the interval between request and actual completion. A coroutine that performs a long CPU loop without suspension can have unbounded cancellation latency from the event loop's point of view. Insert checkpoints only where state is consistent: an <code>await asyncio.sleep(0)</code> can voluntarily yield, but adding arbitrary yields inside half-completed invariants can expose invalid intermediate state.

> **Common misconception 14.46 — “Calling cancel stops a task immediately.”**  
> Cancellation is cooperatively delivered. The task must reach a cancellation-aware suspension point, unwind, and finish cleanup before its lifetime ends.

### 14.11.2 Cleanup itself is concurrent work

Cleanup can block, fail, be cancelled, or contend for the same resources as ordinary work. A cleanup contract should answer four questions:

1. Is cleanup **idempotent**, so a repeated attempt has the same relevant effect as one attempt?
2. Is it **bounded**, or can shutdown wait forever?
3. Can it run after partial acquisition, where only some fields or handles exist?
4. If both the body and cleanup fail, how are the two failures preserved?

An asynchronous context manager localises acquisition and release. The acquisition must finish before control is yielded; the release applies only to the successfully acquired resource:

~~~python
from contextlib import asynccontextmanager
from collections.abc import AsyncIterator, Awaitable, Callable
from typing import TypeVar


T = TypeVar("T")


@asynccontextmanager
async def opened_resource(
    open_resource: Callable[[], Awaitable[T]],
    close_resource: Callable[[T], Awaitable[None]],
) -> AsyncIterator[T]:
    resource = await open_resource()
    try:
        yield resource
    finally:
        await close_resource(resource)
~~~

This pattern does not magically guarantee release. A second cancellation can interrupt an await in the <code>finally</code> suite, and process termination can prevent Python cleanup altogether. Resource protocols should therefore combine local cleanup with external recovery: leases expire, temporary files are recognisable, database transactions roll back on lost connections, and supervisors reclaim abandoned work.

When cleanup must complete to preserve an invariant, a narrow shield and a separate deadline may be justified. Shielding the entire task is rarely justified because it defeats the owner's cancellation policy. A robust design shields only the commit or release action whose interruption would leave corrupt state, and it retains a reference to the inner task so its result cannot disappear.

> **Common misconception 14.47 — “A finally block guarantees cleanup.”**  
> It guarantees an attempt during ordinary stack unwinding. Abrupt process death, an indefinitely blocked release, or cancellation during asynchronous cleanup can still prevent completion.

### 14.11.3 Deadlines compose better than repeated relative timeouts

A **relative timeout** says how much longer one operation may take from the moment the timeout is established. A **deadline** identifies an absolute point on a monotonic clock. Deadlines compose because every nested operation can calculate the same remaining budget; repeated relative timeouts can accidentally multiply an end-to-end limit.

Suppose an operation performs three sequential remote calls. Giving each a five-second relative timeout admits approximately fifteen seconds, excluding local work. If the user-visible requirement is five seconds for the whole operation, establish one deadline and pass the remaining budget:

~~~python
import asyncio
from collections.abc import Awaitable
from time import monotonic
from typing import TypeVar


T = TypeVar("T")


async def with_deadline(operation: Awaitable[T], deadline: float) -> T:
    remaining = deadline - monotonic()
    if remaining <= 0:
        raise TimeoutError("deadline already expired")
    async with asyncio.timeout(remaining):
        return await operation
~~~

Use a monotonic clock for elapsed-time policy because wall clocks can jump under administrative correction or clock synchronisation. A deadline must also define its domain: a value from one machine's monotonic clock cannot generally be sent to another machine as a meaningful absolute instant. Distributed protocols commonly transmit a remaining budget or use a suitably defined wall-clock timestamp while accounting for skew.

The <code>asyncio</code> timeout interfaces differ deliberately. <code>asyncio.timeout()</code> cancels the current task when its context expires and translates that cancellation into <code>TimeoutError</code> outside the context. <code>asyncio.wait_for()</code> cancels the awaited object and waits for its cancellation to complete, so elapsed time may exceed the numerical timeout. <code>asyncio.wait()</code> returns pending objects at its timeout and does not cancel them. Selecting among them is a lifetime decision, not stylistic preference.

> **Common misconception 14.48 — “A five-second timeout means the function returns within five seconds.”**  
> Delivery, cleanup, scheduler delay, and the API's waiting semantics can extend elapsed time. The value is a policy trigger, not a hard real-time guarantee.

### 14.11.4 Shielding, abandonment, and idempotency

<code>asyncio.shield(awaitable)</code> prevents cancellation of the surrounding wait from automatically cancelling the shielded awaitable. The caller still receives cancellation; the inner operation may continue. This creates **abandoned work** unless another owner retains the task, observes its result, and bounds its lifetime. Shielding therefore transfers responsibility rather than eliminating cancellation.

External effects complicate timeouts. Imagine a client sends a payment command, the server commits it, and the response is lost. The client observes a timeout but cannot infer whether the effect occurred. Blind retry can charge twice. An **idempotency key** gives repeated logically identical requests a stable identity. The receiver atomically records the key and outcome so a retry returns the existing outcome instead of repeating the effect.

A complete retry policy classifies failures:

- a rejection known to occur before execution may be safely retried under capacity policy;
- an ambiguous transport failure requires idempotency or reconciliation;
- a validation failure should not be retried unchanged;
- an overload response may permit delayed retry with jitter;
- cancellation by the owner usually ends retries rather than becoming another transient error.

**Exponential backoff** increases delay across attempts; **jitter** randomises delay to avoid many clients resynchronising into repeated bursts. Backoff controls request timing but does not make a non-idempotent operation safe.

> **Common misconception 14.49 — “A timeout followed by retry is ordinary error recovery.”**  
> A timeout can leave the effect's outcome unknown. Safe retry requires idempotency, deduplication, or explicit reconciliation with the external system.
