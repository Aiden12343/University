# 14.12 Backpressure

**Backpressure** prevents producers from creating work faster than consumers and resources can absorb it. Without a bound, a service can retain an ever-growing queue until memory exhaustion, even though every individual task is correct.

An `asyncio.Queue(maxsize=n)` makes `put` await when full:

```python
queue: asyncio.Queue[bytes | None] = asyncio.Queue(maxsize=100)
```

The bound shifts waiting to producers. Its size should follow burst tolerance, memory per item, service rate, and latency requirements. Dropping, blocking, spilling, rejecting, or sampling are policy alternatives with distinct semantics.

Concurrency is therefore capacity design. “Use async for scale” is meaningless without admission limits, timeouts, cancellation, and downstream backpressure.

### 14.12.1 Bounds turn resource exhaustion into policy

An unbounded queue converts a rate mismatch into deferred memory failure. If producers emit \(\lambda\) items per second and consumers complete only \(\mu\), then, while \(\lambda>\mu\), expected backlog grows at approximately \((\lambda-\mu)t\). No choice of initial queue capacity makes that condition stable indefinitely. A bound makes overload visible early enough for the system to apply an explicit policy.

The principal overload policies are:

| Policy | What the producer observes | Appropriate when | Principal risk |
|:---|:---|:---|:---|
| block or await | slower admission | every accepted item must be retained | upstream resources may remain occupied |
| reject | immediate failure | callers can retry or shed work | retry storms without backoff |
| drop newest | apparent acceptance or explicit drop | fresh items are not more valuable than queued ones | silent loss if not measured |
| drop oldest | space for recent work | stale telemetry has declining value | breaks FIFO and may starve old work |
| coalesce | several updates become one | only latest state or aggregate matters | intermediate events disappear |
| spill to durable storage | slower persistent admission | work must survive process failure | storage can become the next unbounded queue |
| sample | retain a representative fraction | statistical observation tolerates loss | biased sampling if policy is careless |

No policy is universally correct. A financial command queue and a screen-refresh queue have different loss semantics. The interface must expose whether acceptance means merely “placed in volatile memory”, durably recorded, or fully completed.

A queue bound \(B\) is not a worker count. It limits waiting items, while worker or semaphore count \(C\) limits active items. If each waiting item retains \(m\) bytes, the queue alone may retain approximately \(Bm\), excluding object overhead, active tasks, response buffers, and duplicates in other stages. Measure retained size rather than multiplying payload length alone.

> **Common misconception 14.50 — “A bounded queue prevents overload.”**  
> It prevents one form of unbounded accumulation. Overload still exists and must be resolved by waiting, rejection, loss, degradation, or additional genuine capacity.

### 14.12.2 Queueing delay is part of latency

Let one worker complete on average \(\mu\) jobs per second and let \(c\) comparable workers serve a stable stream. Nominal service capacity is at most \(c\mu\), but coordination and shared bottlenecks reduce it. **Queue utilisation** is often written \(\rho=\lambda/(c\mu)\) in a simplified model. Stability requires \(\rho<1\); useful tail latency normally requires material headroom below one.

Little’s law relates averages but does not describe the distribution. Two systems can have the same mean residence time and radically different ninety-ninth-percentile latency. Service-time variability, bursty arrivals, priorities, correlated failures, and retry traffic all matter. A single exceptionally slow job at the front of a FIFO queue can cause **head-of-line blocking** for later jobs even when those jobs would be quick.

Queue capacity should follow a latency budget. If admitted work may wait at most \(W_q\) seconds and sustainable completion rate is \(r\), then \(rW_q\) is a first-order estimate of backlog consistent with that average budget. It is not a proof: bursts and tail behaviour require workload-specific simulation or measurement. A queue of ten thousand chosen merely because memory permits it can turn an overload that should fail quickly into minutes of stale work.

Instrument at least:

- arrival, admission, rejection, drop, and completion rates;
- current and high-water queue depth;
- age of the oldest item;
- queue-wait, service, and end-to-end latency distributions;
- number of active workers and their utilisation;
- retry counts and failure classes.

Queue depth without item age can conceal a stalled queue whose depth happens to be small. Mean latency without percentiles can conceal a minority of unusably slow requests. A metric should correspond to a decision: scale capacity, reduce admission, degrade optional work, or investigate a slow stage.

> **Common misconception 14.51 — “A larger queue makes a service more resilient.”**  
> A larger queue absorbs a larger finite burst, but it also consumes memory and permits longer waiting. Under sustained overload it postpones rejection while making admitted work staler.

### 14.12.3 A bounded asynchronous pipeline

The following pipeline has a finite number of producer and consumer tasks, bounded item retention, one sentinel for each consumer, explicit completion accounting, and structured ownership. The example transforms text rather than performing network I/O so that its lifecycle is visible without an external dependency.

~~~python
import asyncio
from collections.abc import AsyncIterable
from dataclasses import dataclass


@dataclass(frozen=True)
class WorkItem:
    sequence: int
    text: str


@dataclass(frozen=True)
class Result:
    sequence: int
    normalised: str


STOP = object()


async def source(count: int) -> AsyncIterable[WorkItem]:
    for sequence in range(count):
        await asyncio.sleep(0)
        yield WorkItem(sequence, f" item {sequence} ")


async def produce(
    destination: asyncio.Queue[WorkItem | object],
    consumer_count: int,
    count: int,
) -> None:
    async for item in source(count):
        await destination.put(item)
    for _ in range(consumer_count):
        await destination.put(STOP)


async def consume(
    source_queue: asyncio.Queue[WorkItem | object],
    destination: asyncio.Queue[Result | object],
) -> None:
    while True:
        item = await source_queue.get()
        try:
            if item is STOP:
                break
            assert isinstance(item, WorkItem)
            result = Result(item.sequence, item.text.strip().casefold())
            await destination.put(result)
        finally:
            source_queue.task_done()
    await destination.put(STOP)


async def collect_results(
    source_queue: asyncio.Queue[Result | object],
    producer_count: int,
) -> list[Result]:
    finished = 0
    collected: list[Result] = []
    while finished < producer_count:
        item = await source_queue.get()
        try:
            if item is STOP:
                finished += 1
            else:
                assert isinstance(item, Result)
                collected.append(item)
        finally:
            source_queue.task_done()
    return collected


async def run_pipeline(count: int, consumer_count: int = 4) -> list[Result]:
    if consumer_count < 1:
        raise ValueError("consumer_count must be positive")

    work: asyncio.Queue[WorkItem | object] = asyncio.Queue(maxsize=32)
    results: asyncio.Queue[Result | object] = asyncio.Queue(maxsize=32)

    async with asyncio.TaskGroup() as group:
        collector = group.create_task(collect_results(results, consumer_count))
        group.create_task(produce(work, consumer_count, count))
        for _ in range(consumer_count):
            group.create_task(consume(work, results))

        await work.join()

    collected = collector.result()
    return sorted(collected, key=lambda result: result.sequence)


async def main() -> None:
    results = await run_pipeline(100)
    assert len(results) == 100
    assert results[0] == Result(0, "item 0")


if __name__ == "__main__":
    asyncio.run(main())
~~~

The work queue bounds not-yet-consumed inputs. Its <code>put</code> suspends the producer when consumers fall behind. The result queue is also bounded, and the collector drains it concurrently with the workers. After normal input exhaustion, the producer places one stop marker per consumer. After normal stop, every consumer places one stop marker in the result queue, so the collector knows exactly how many producers have terminated. Stop markers are not sent from cancellation cleanup: if a stage fails, the task group cancels the other stages instead of risking a cleanup task blocking while placing control messages into an undrained full queue. The collector itself belongs to the same task group and cannot outlive the pipeline.

The call to <code>work.join()</code> is not what owns child lifetime; the task group does. It verifies queue completion accounting while the group waits for all children. If a child fails, TaskGroup cancels siblings. The owner must never wait outside that owning scope for a sentinel that a cancelled worker can no longer send. The protocol also assumes workers do not independently suppress or convert their own cancellation; such a policy would need an explicit abnormal-stop outcome. Completion protocols and failure protocols must be designed together.

### 14.12.4 Concurrency limits and rate limits are distinct

A **concurrency limit** bounds operations simultaneously in progress. A **rate limit** bounds starts or completions per interval. If a remote call lasts one second, ten simultaneous calls imply roughly ten completions per second in steady state; if latency rises to ten seconds, the same concurrency allows about one completion per second. Conversely, a rate of ten starts per second can yield one hundred in-flight calls when each lasts ten seconds.

A semaphore expresses concurrency:

~~~python
import asyncio
from collections.abc import Awaitable, Callable, Iterable
from typing import TypeVar


T = TypeVar("T")
R = TypeVar("R")


async def bounded_call(
    semaphore: asyncio.Semaphore,
    function: Callable[[T], Awaitable[R]],
    argument: T,
) -> R:
    async with semaphore:
        return await function(argument)


async def call_all_bounded(
    function: Callable[[T], Awaitable[R]],
    arguments: Iterable[T],
    limit: int,
) -> list[R]:
    semaphore = asyncio.Semaphore(limit)
    async with asyncio.TaskGroup() as group:
        tasks = [
            group.create_task(bounded_call(semaphore, function, argument))
            for argument in arguments
        ]
    return [task.result() for task in tasks]
~~~

This bounds active calls but eagerly creates one task per argument. For millions of arguments, task objects themselves become an unbounded backlog. A fixed worker pool consuming a bounded queue bounds both task count and active work.

A **token bucket** is a rate-control model. Tokens enter a bucket at a configured rate up to a burst capacity; starting an operation consumes a token. Accumulated tokens permit a bounded burst while the long-run rate remains constrained. A token bucket still needs a concurrency bound when operations can remain outstanding for a long time.

Distributed admission control introduces further questions: whose clock defines rate, whether clients share one quota, what happens during coordinator partition, and whether rejected work is retried. Local semaphores cannot protect a global service from many independent processes unless capacity is partitioned or coordinated.

> **Common misconception 14.52 — “Limiting requests to one hundred per second limits concurrency to one hundred.”**  
> Rate constrains events per time; concurrency constrains simultaneous lifetime. Variable latency makes either quantity insufficient to infer the other.

### 14.12.5 Load shedding and graceful degradation

**Load shedding** deliberately refuses or discards work to preserve service for admitted work. It is a correctness policy under finite capacity, not merely a performance trick. A system that accepts everything and then times out everything may deliver less useful work than one that rejects excess requests immediately.

Admission can be prioritised by contractual class, deadline, estimated cost, or dependency health. Priority queues require ageing or reservation policies if lower-priority work must eventually progress. Estimated-cost scheduling can reduce mean response time but can be unfair to large jobs and can be gamed if clients report cost.

**Graceful degradation** preserves a core result while omitting optional computation: serve a cached representation, reduce image resolution, skip recommendations, or return a partial report explicitly marked incomplete. The degraded result must remain semantically valid. Quietly substituting stale or partial data where freshness or completeness is contractual is corruption, not graceful degradation.

Feedback loops need damping. If every instance observes latency and simultaneously halves its own concurrency, capacity can oscillate. Control intervals, hysteresis, central quotas, and carefully chosen signals reduce instability. The appropriate controller depends on the service and must be tested under bursts, partial failures, and recovery—not merely steady load.
