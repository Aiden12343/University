# 14.13 Choosing a concurrency model

| Work/constraint | Initial candidate | Principal obligations |
|:---|:---|:---|
| many blocking I/O operations using synchronous libraries | threads | shared-state safety, worker bounds, shutdown |
| CPU-heavy pure Python on several cores | processes | serialisation, startup, partitioning, result ownership |
| many async-compatible network operations | `asyncio` | no loop blocking, task ownership, cancellation, backpressure |
| native numerical library releasing GIL | library-managed/thread parallelism | library thread controls, oversubscription, memory bandwidth |
| fault isolation or privilege separation | processes/services | protocol, validation, supervision |

Hybrid systems are common: an async server delegates CPU work to a bounded process pool; a process uses a native library with internal threads. Uncontrolled nesting can oversubscribe cores and memory. Count concurrency across every layer.

### 14.13.1 Diagnose the wait before choosing the mechanism

The useful first question is not “threads, processes, or async?” but “what prevents this workload from completing sooner?” A measurement can reveal one or several limiting resources:

- high CPU utilisation on one core with pure Python frames suggests exploitable process parallelism if independent work exists;
- low CPU utilisation and many blocked system calls suggest I/O concurrency;
- high CPU utilisation inside a native numerical library may already use several threads;
- high memory bandwidth with additional cores producing little speedup suggests a memory-bound kernel;
- long lock-wait time suggests contention or over-broad sharing;
- low local utilisation with high remote latency suggests a dependency bottleneck;
- a full connection pool or storage queue indicates a downstream capacity bound;
- high scheduler and context-switch cost suggests excessive runnable activities.

These observations must be connected to a goal. If the requirement is lower median latency for one intrinsically sequential request, a process pool serving many requests may increase throughput while doing nothing for that request. If the requirement is stable tail latency at high offered load, admission control can matter more than faster steady-state service.

Construct a **resource budget** before selecting a mechanism: cores, memory, file descriptors, connections, subprocesses, external quotas, and maximum outstanding work. Construct a **lifetime graph** showing which component creates, supervises, cancels, and joins every activity. Construct a **state-ownership map** showing which activity may mutate each resource. These three documents turn a concurrency mechanism from a slogan into an analysable design.

> **Common misconception 14.53 — “The workload’s label determines the API.”**  
> “I/O-bound” or “CPU-bound” is an initial diagnosis, not a complete design. Library interfaces, state ownership, failure isolation, latency goals, transfer costs, and deployment limits also determine the mechanism.

### 14.13.2 Threads, tasks, and processes change different boundaries

A thread changes the execution stream while retaining a common process address space. Communication can be cheap because objects are shared by reference, but mutation requires synchronisation and one memory corruption fault can damage the process. Threads integrate naturally with blocking synchronous APIs and operating-system facilities that associate state with a thread.

An event-loop task changes the logical execution stream within an event loop. Communication among tasks in the same thread can avoid data races between suspension points, but re-entrancy occurs whenever control is yielded. Tasks are comparatively cheap, yet creating an unbounded number is still an allocation and scheduling failure. Async code requires non-blocking operations throughout the call path or explicit offloading of blocking sections.

A process changes the failure and address-space boundary. Ordinary object references do not cross it; data is serialised, inherited under platform-specific start semantics, placed in explicitly shared memory, or stored externally. This boundary can use several cores for Python execution and can isolate crashes or privileges, but startup, transfer, duplicated state, supervision, and deployment are material costs.

The mechanisms are not semantic substitutes. Replacing a thread with a task can break a blocking library call; replacing a thread with a process can break shared object identity; replacing a process with a thread removes fault isolation. The program must state which properties it needs.

| Property | Thread | Async task | Process |
|:---|:---|:---|:---|
| ordinary Python heap | shared | shared in event-loop process | isolated by default |
| scheduling | pre-emptive OS scheduling | cooperative at awaits | pre-emptive OS scheduling |
| pure-Python multicore on conventional CPython | generally no | no, by itself | yes |
| communication | shared objects, queues | awaits, async queues | serialisation, pipes, shared memory |
| startup cost | moderate | low | comparatively high |
| fault isolation | weak | weak | stronger, not absolute |
| blocking API compatibility | direct | blocks loop unless offloaded | direct inside worker |
| cancellation | cooperative conventions | explicit task cancellation | protocol or termination |

The table describes defaults, not universal laws. Native code can release the GIL; a free-threaded build differs; process workers can share memory; threads can communicate purely through queues. State the exact implementation and protocol.

> **Common misconception 14.54 — “Processes are threads with more overhead.”**  
> Processes establish a different address-space, serialisation, startup, security, and failure model. Those semantics are often the reason to choose them.

### 14.13.3 Hybrid architectures require a global concurrency budget

Real systems compose layers. Consider four service processes. Each process starts an event loop, permits fifty requests, owns a process pool of eight workers, and calls a native library that starts eight threads per worker. The apparent “eight workers” can create as many as \(4\times8\times8=256\) native threads, in addition to event-loop and service threads. If the machine has sixteen cores, runnable work can greatly exceed useful capacity.

**Oversubscription** means that runnable computational activities exceed available processing resources by enough that scheduling, cache displacement, and contention become material. Some oversubscription is normal: blocked activities do not consume a core, and a scheduler needs alternatives when one blocks. CPU-heavy nested pools, however, often compete destructively.

Set budgets at the deployment level:

\[
C_{\text{effective}}
=
N_{\text{instances}}
\times N_{\text{workers per instance}}
\times N_{\text{native threads per worker}}.
\]

This multiplication is a warning model, not exact utilisation. Libraries can dynamically change thread count, processes may run on constrained CPU sets, and stages need not peak together. Inspect actual thread/process counts and runnable utilisation.

A common hybrid server design is:

1. one event loop per service process owns network connections and request lifetimes;
2. a semaphore limits admitted remote operations;
3. short blocking I/O calls use a bounded thread executor when no async API exists;
4. measured CPU-heavy pure-Python work uses a bounded process executor;
5. native libraries receive explicit internal thread limits;
6. queues or semaphores impose backpressure before every bounded downstream pool;
7. the request deadline propagates through every offload.

Offloading does not automatically propagate cancellation. Cancelling the await on a running thread does not forcibly stop the thread function. A process future may be cancellable before it starts but not after a worker begins it; terminating a worker has coarse consequences. Long computations need cooperative checkpoints, smaller independently safe chunks, or acceptance that abandoned work consumes capacity until completion.

> **Common misconception 14.55 — “Each pool can choose its worker count independently.”**  
> Nested pools multiply. Useful capacity must be budgeted across service instances, process workers, library threads, connections, and external limits.

### 14.13.4 State ownership is the decisive simplifier

Choose a **single writer** where possible. One task can own a mutable cache, one thread can own a device handle, or one process can own database batch commits. Other activities send commands and receive immutable results. This resembles an actor: an **actor** is an independently scheduled entity that owns state and processes messages sequentially. The term is introduced here in its minimal sense; actor frameworks add addressing, supervision, distribution, and delivery semantics.

Single ownership changes the proof. Instead of proving every reader and writer uses the same lock, prove that only the owner mutates the state and that messages preserve the required order and identity. The trade-off is that the owner can become a serial bottleneck. Batching commands, partitioning state among several owners, or using an external transactional store can increase capacity without returning to unrestricted sharing.

Partitioning requires a key. If all operations for one customer must be ordered, hash customer identity to one owner. Operations for different customers can proceed independently. Repartitioning while work is in flight requires a migration protocol; otherwise two owners can simultaneously believe they have authority.

Immutable messages need versioning and validation at process or network boundaries. A Python dataclass shared within one deployment is not a permanent wire format. Define fields, types, optionality, compatibility, maximum sizes, and how unknown fields are handled. Treat deserialised input as untrusted even when it came from another internal component.

> **Common misconception 14.56 — “Message passing eliminates concurrency errors.”**  
> It can eliminate shared-memory races, but introduces ordering, duplication, loss, backpressure, schema, ownership-transfer, and delivery-lifetime questions.

### 14.13.5 A disciplined selection procedure

For a new concurrent component, answer these questions in order:

1. **Contract:** What are the required effects, ordering, latency, throughput, and failure semantics?
2. **Decomposition:** Which activities can progress independently, and what dependencies define the critical path?
3. **Bottleneck:** Which measured resource currently limits the contract?
4. **Ownership:** Which activity owns each mutable resource and each child lifetime?
5. **Capacity:** What bounds apply to active work, queued work, memory, handles, and external requests?
6. **Mechanism:** Which thread, task, process, native, or distributed primitive preserves those properties?
7. **Cancellation:** How does the owner request stop, how quickly is it observed, and what effects may already exist?
8. **Failure:** Where is each exception, exit code, or partial result observed?
9. **Shutdown:** In what order is admission stopped, queued work resolved, workers joined, and resources closed?
10. **Evidence:** Which benchmark, profile, stress test, and invariant check would falsify the design?

The mechanism is intentionally seventh only in the explanatory sequence above, though sixth in the operational checklist after constraints are established. Familiarity with one library should not decide architecture before semantics are known.

### Worked example 14.3 — Selecting a model for thumbnail generation

Suppose a service receives image files, validates metadata, decodes pixels through a native imaging library, resizes to three resolutions, and stores results. Measurement shows network upload dominates at low load, native resizing uses several internal threads, and storage saturates at forty concurrent writes.

An appropriate design might use async request handling for many partially received uploads; a byte limit and temporary-file spool to avoid retaining complete images; validation before expensive decode; a semaphore below forty for writes; and a small process pool for decode isolation if malformed native inputs could crash a worker. It should not automatically use one process per image or add a thread pool around an already parallel native resize kernel.

The request owner records an idempotency key before storage, owns all subtasks in a task group, and returns success only after the required variants commit. Optional variants can be an explicitly separate asynchronous job if the API contract permits eventual completion. Benchmarks vary image dimensions and compression, not merely file byte size, because decompressed dimensions drive memory and work. This conclusion comes from resource and failure evidence; “image processing is CPU-bound” would have been too coarse.
