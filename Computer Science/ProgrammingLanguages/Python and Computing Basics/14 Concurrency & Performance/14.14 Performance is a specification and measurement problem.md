# 14.14 Performance is a specification and measurement problem

“Fast” is not measurable. A performance requirement names:

- operation and workload distribution;
- input sizes and data shape;
- latency percentile or throughput;
- warm/cold cache and startup conditions;
- hardware, OS, Python implementation/build, dependencies;
- concurrency level;
- memory and error constraints;
- measurement duration and confidence.

Optimisation cycle:

1. establish correctness and a representative benchmark;
2. measure a baseline distribution;
3. profile to locate dominant cost;
4. form a causal hypothesis;
5. change one relevant factor;
6. remeasure under identical conditions;
7. verify correctness and resource regressions;
8. retain the change only when benefit justifies complexity.

### 14.14.1 Performance is a vector, not one scalar

A system has several performance dimensions: response-time distribution, throughput, memory, CPU time, energy, startup, binary size, storage traffic, network traffic, and capacity under failure. Improving one can worsen another. Precomputing an index reduces query latency by consuming construction time, memory, and update work. Batching improves throughput and boundary amortisation while delaying the first item. Compression reduces transfer bytes but consumes processor time.

A **service-level indicator** (**SLI**) is a measured quantity such as the proportion of requests completed below 200 milliseconds. A **service-level objective** (**SLO**) is a target for that indicator over a stated interval. An SLO is not identical to a contractual service-level agreement, which can include legal remedies and broader terms.

Requirements need dimensions and scope. Compare:

- vague: “search must be fast”;
- measurable: “for the recorded 10-million-row corpus, under 200 concurrent clients on environment E, successful exact-match searches shall have p50 below 40 ms and p99 below 180 ms over a 30-minute steady interval, while process RSS remains below 4 GiB and error rate below 0.1 per cent.”

The second statement is still incomplete unless the query distribution, cache condition, update traffic, success definition, and measurement location are specified. Yet it can be tested and contested. Precision makes engineering disagreement productive.

Performance tests should retain correctness oracles. A fast algorithm returning incomplete search results is not an optimisation. When approximate answers are allowed, the error metric—precision, recall, relative error, or domain-specific loss—becomes another dimension of the contract.

> **Common misconception 14.57 — “An optimisation is a change that lowers elapsed time.”**  
> A change is an optimisation only relative to a stated objective and constraints. Lower elapsed time can be unacceptable if it corrupts results, increases tail latency, exceeds memory, or shifts cost to another component.

### 14.14.2 Distributions and tail latency

Let measured latencies sorted in non-decreasing order be \(x_1,\ldots,x_n\). The \(p\)-th percentile is a value at or below which approximately \(p\) per cent of observations fall, under a stated sample quantile convention. Libraries use several interpolation conventions, so reproduce the method when exact values matter.

The median, or fiftieth percentile, describes a central observation and resists a small number of extreme values better than the arithmetic mean. The mean remains important for Little’s law and total resource accounting. The ninety-fifth, ninety-ninth, and higher percentiles describe increasingly rare tails but require increasingly large samples. With only one hundred observations, a reported p99 is essentially determined by one of the largest observations and has high uncertainty.

Tail latency matters in **fan-out** systems. If one user request waits for all \(k\) independent subrequests and each subrequest has probability \(q\) of meeting a threshold, the probability all meet it is \(q^k\). If each has a 0.99 probability and \(k=100\), then \(0.99^{100}\approx0.366\). Independence is often false, but the calculation shows how apparently rare per-component slowness becomes common at aggregation boundaries.

Record the complete distribution or a sufficiently accurate histogram, not only averages. Associate latency with result status and workload class: failures rejected quickly can make an aggregate latency statistic look better during an outage. Separate queue wait, connection acquisition, remote service, computation, and response transfer so the tail can be attributed.

**Coordinated omission** is measurement bias caused when a load generator waits for one response before scheduling the next request and therefore fails to represent requests that would have arrived while the system was stalled. Suppose requests should arrive every 10 ms, but one response stalls for one second. A closed-loop generator records one one-second latency and sends nothing during the stall; an open-loop model would account for many scheduled arrivals and their queueing delay. The load model must match the intended population.

> **Common misconception 14.58 — “The average latency represents user experience.”**  
> Means can conceal long tails, workload mixtures, failures, and coordinated omission. Report distributions at the boundary users experience and decompose them at internal boundaries.

### 14.14.3 Throughput curves and saturation

Measure throughput while varying offered load. Below capacity, completed throughput may rise approximately with arrival rate and latency remain modest. Near saturation, queueing delay grows. Above sustainable capacity, completed throughput plateaus or falls while queue length, rejection, timeout, and memory pressure grow.

This **load curve** is more informative than one maximum-throughput number. It identifies:

- the low-load latency floor;
- the knee where queueing begins to dominate;
- sustainable capacity under the SLO;
- overload behaviour and recovery;
- whether adding concurrency exposes capacity or merely adds contention.

Use a ramp, hold each level long enough to reach relevant steady behaviour, and include burst and recovery experiments. A database cache warming over minutes or a garbage collector reacting to allocation cannot be understood from a two-second run. Conversely, steady-state testing alone omits startup, autoscaling, connection establishment, and cache-cold behaviour.

Open-loop load generation schedules arrivals independently of previous completions and is suited to a specified arrival process. Closed-loop generation maintains a number of clients, each issuing another request after completion, and models interactive populations with think time. Neither is inherently correct; the service contract determines the model.

Failures alter offered load. Clients often retry, so an overloaded server can receive more traffic because it is failing. The **retry amplification factor** is attempted calls divided by original logical operations. Report both. Apply capped attempts, deadline budgets, jitter, and server overload signals to prevent positive feedback.

### 14.14.4 Controlled experiments and uncertainty

A benchmark is an experiment. Its **independent variable** is the factor deliberately changed, such as algorithm or worker count. Its **dependent variables** are measured outcomes. **Confounders** are uncontrolled factors correlated with the change: input order, CPU frequency, competing workloads, interpreter build, allocator state, network path, or cache condition.

Use this protocol:

1. record source revision, environment, exact command, dependencies, and input identity;
2. define a warm-up or cold-start policy before observing results;
3. randomise or interleave treatment order where drift is possible;
4. perform independent repetitions rather than treating inner-loop iterations as independent;
5. retain raw observations;
6. visualise distributions and inspect anomalies;
7. report an effect size and uncertainty, not merely a winner;
8. rerun correctness and resource checks.

An **effect size** describes the magnitude of a difference: absolute milliseconds, ratio, throughput increase, or memory saved. A **confidence interval** is an interval produced by a procedure that, under its assumptions and repeated sampling, covers the target parameter at a stated long-run rate. It is not the probability that this already computed fixed interval contains the fixed parameter. The assumptions behind common parametric intervals can be poor for skewed latency samples; resampling and distribution plots may be more informative, though neither repairs a biased workload.

Statistical significance does not imply practical significance. With enough repetitions, a 0.2 per cent change can be statistically detectable but operationally worthless. Conversely, a large improvement with wide uncertainty can justify further measurement rather than immediate rejection. Define a minimum worthwhile effect based on system cost and engineering complexity.

> **Common misconception 14.59 — “Repeating an operation a million times creates a million independent measurements.”**  
> Iterations in one process share machine state, caches, thermal conditions, allocator history, and drift. Independence belongs to the experimental design, not the loop count.

### 14.14.5 Performance work is causal inquiry

A profile shows association between observed samples and locations; it does not alone prove which change will improve the user-visible objective. A function can dominate because callers invoke it unnecessarily, because input representation causes poor locality, or because it waits on another resource. Optimising its inner instructions may address none of these causes.

Write a hypothesis in causal form: “Building the same regular expression on every item accounts for approximately 25 per cent of CPU time; compiling it once per pattern should reduce CPU time without changing matching semantics.” State a prediction, make the smallest change that tests it, and remeasure. If the profile changes but end-to-end latency does not, another bottleneck may have become dominant or the component may not be on the critical path.

This is an application of **Amdahl’s law** to optimisation. If fraction \(f\) of elapsed time can be accelerated by factor \(s\), ideal speedup is

\[
S=\frac{1}{(1-f)+f/s}.
\]

If parsing is 20 per cent of latency and is made infinitely fast, maximum end-to-end speedup is \(1/(1-0.2)=1.25\). Measurement overhead, overlap among components, and workload changes complicate direct use, but the law disciplines expectations.

Optimisations carry **maintenance cost**: more branches, native build machinery, less familiar data structures, numerical approximations, or weakened observability. Record the rationale, benchmark, environment, and rejected alternatives. Add a regression benchmark only when it is stable enough to guide decisions; flaky thresholds teach teams to ignore evidence.

> **Common misconception 14.60 — “The hottest function is where optimisation must occur.”**  
> Hotness identifies attributed cost. The best intervention may remove calls, change data shape, batch work, move it off the critical path, or alter an upstream algorithm.

### Worked example 14.4 — A reproducible benchmark record

The standard library can capture useful context without pretending to control the entire machine:

~~~python
from __future__ import annotations

import json
import os
import platform
import statistics
import sys
from dataclasses import asdict, dataclass
from time import perf_counter_ns
from typing import Callable


@dataclass(frozen=True)
class BenchmarkRecord:
    name: str
    repetitions: int
    samples_ns: tuple[int, ...]
    python: str
    implementation: str
    platform: str
    processor_count: int | None

    @property
    def median_ns(self) -> float:
        return statistics.median(self.samples_ns)


def measure(name: str, operation: Callable[[], object], repetitions: int) -> BenchmarkRecord:
    if repetitions < 1:
        raise ValueError("repetitions must be positive")

    samples: list[int] = []
    for _ in range(repetitions):
        started = perf_counter_ns()
        operation()
        samples.append(perf_counter_ns() - started)

    return BenchmarkRecord(
        name=name,
        repetitions=repetitions,
        samples_ns=tuple(samples),
        python=sys.version,
        implementation=platform.python_implementation(),
        platform=platform.platform(),
        processor_count=os.cpu_count(),
    )


if __name__ == "__main__":
    record = measure("sum-10k", lambda: sum(range(10_000)), 101)
    print(json.dumps(asdict(record), indent=2))
~~~

<code>perf_counter_ns</code> supplies a high-resolution monotonic performance counter in integer nanoseconds; it does not guarantee nanosecond physical resolution. The callable return is ignored semantically but remains observable to Python, so the operation is executed. This harness includes each function-call overhead in every sample and performs no warm-up; those are declared properties, not hidden defects. A research-quality comparison would add treatments, randomised order, input identity, machine controls, and analysis outside the timed region.
