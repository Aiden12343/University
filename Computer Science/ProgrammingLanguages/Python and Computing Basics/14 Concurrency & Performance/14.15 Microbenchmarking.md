# 14.15 Microbenchmarking

A **microbenchmark** measures a small operation. Python’s `timeit` module repeats code while reducing some common timing mistakes.

```python
from timeit import repeat


measurements = repeat(
    "target in values",
    setup="values = list(range(10_000)); target = -1",
    number=1_000,
    repeat=7,
)
print(min(measurements))
```

The minimum can approximate least-interfered execution for deterministic micro-operations, while the full distribution reveals noise. This benchmark measures worst-case absent membership in one list size under one runtime. It does not prove application latency, set comparison, warm-up neutrality, or cross-machine results.

Common defects:

- measuring setup or I/O unintentionally;
- allowing results to be cached when cold behaviour matters;
- benchmarking constant-folded or dead work;
- using tiny durations dominated by timer noise;
- comparing algorithms on different inputs;
- reporting one run or unsupported precision;
- changing several factors simultaneously.

### 14.15.1 Clocks and the measured interval

A clock is an interface with a **resolution**, the smallest representable or distinguishable increment; **precision**, the repeatability of readings; **accuracy**, closeness to a reference; and **monotonicity**, whether readings are guaranteed not to move backwards. These properties differ.

Python exposes several clocks:

| Function | Principal meaning | Typical use |
|:---|:---|:---|
| <code>time.perf_counter()</code> | highest-resolution available monotonic elapsed-time clock | wall-time benchmarks |
| <code>time.perf_counter_ns()</code> | same conceptual clock in integer nanoseconds | avoid floating-point conversion and rounding |
| <code>time.monotonic()</code> | monotonic elapsed-time clock | deadlines and timeout budgets |
| <code>time.process_time()</code> | CPU time consumed by current process | distinguish execution from waiting |
| <code>time.thread_time()</code> | CPU time consumed by current thread where supported | thread-level CPU diagnosis |
| <code>time.time()</code> | seconds relative to civil-time epoch | timestamps, not interval policy |

Inspect <code>time.get_clock_info</code> to learn implementation properties on the current platform. The numerical unit does not reveal effective resolution: <code>perf_counter_ns()</code> returns nanoseconds as integers even if consecutive clock observations change in larger increments.

The measured interval should include costs relevant to the question and exclude irrelevant setup. To compare lookup data structures after construction, build them outside the timer. To compare end-to-end request handling including parsing and construction, include them. Neither choice is more honest without a stated question.

Very short intervals are dominated by timer calls, loop mechanics, function dispatch, and interrupts. Repeating the target in an inner loop amortises some fixed timing overhead but changes conditions: caches warm, branch predictors learn, allocations interact, and objects remain live. Select duration and repetition to make the desired operational regime—not merely the numerical timer—representative.

> **Common misconception 14.61 — “A nanosecond-valued timer measures to nanosecond accuracy.”**  
> The return unit, clock resolution, measurement overhead, scheduler noise, and experimental reproducibility are distinct properties.

### 14.15.2 What timeit does and does not do

<code>timeit</code> constructs a <code>Timer</code>, executes setup outside repeated timing, and runs the statement a chosen number of times. Its command-line and programmatic interfaces can choose a loop count automatically. By default it temporarily disables cyclic garbage collection during timings; this can improve comparability for small snippets but makes a benchmark unrepresentative when collection is part of the workload. Collection can be explicitly enabled in setup when required.

Passing callables avoids fragile string construction:

~~~python
from random import Random
from timeit import repeat


rng = Random(2026)
values = [rng.randrange(1_000_000) for _ in range(50_000)]
present = values[-1]
absent = -1


def present_lookup() -> bool:
    return present in values


def absent_lookup() -> bool:
    return absent in values


present_times = repeat(present_lookup, repeat=9, number=100)
absent_times = repeat(absent_lookup, repeat=9, number=100)
print(min(present_times), min(absent_times))
~~~

The seeded pseudo-random generator makes this input reproducible, not statistically representative of every list. The present target at the last position forces a full scan here; the absent target also scans the complete list. The two operations have comparable asymptotic work but may differ at the final comparison and branch outcome.

The minimum of repeated timings can estimate an operation’s best observed time when incidental delays only add positive noise. It is not always the right summary. Dynamic frequency changes, allocation state, adaptive interpreter specialisation, thermal throttling, background reclamation, and cache contention can change the underlying performance rather than merely add isolated pauses. End-user latency requires the full distribution, not the minimum.

Modern interpreters can adapt execution after observing types and operations. A warm repeated loop may measure specialised steady state rather than startup. That is appropriate for a hot service path and inappropriate for a command that runs once. Declare warm-up and preserve enough iteration-order data to see transitions.

> **Common misconception 14.62 — “timeit produces an objective speed for a Python expression.”**  
> It times a precisely constructed repeated experiment. Generalisation depends on setup, loop count, garbage collection, runtime state, inputs, hardware, and the application question.

### 14.15.3 Fair comparison requires equivalent semantics

Two snippets can differ in more than implementation technique. A set membership test and a list membership test have different construction cost, memory use, order, duplicate retention, hashability requirements, and worst-case behaviour. A fair benchmark might answer several separate questions:

1. lookup after both structures already exist;
2. construction plus one lookup;
3. construction amortised over \(q\) lookups;
4. memory footprint under the target data distribution;
5. adversarial or collision-heavy behaviour where relevant.

Let list construction cost be \(C_l\), set construction be \(C_s\), per-query costs be \(Q_l\) and \(Q_s\), and number of queries be \(q\). The set wins on this simplified time model when

\[
C_s+qQ_s < C_l+qQ_l.
\]

The break-even point is

\[
q > \frac{C_s-C_l}{Q_l-Q_s},
\]

provided \(Q_l>Q_s\). This calculation exposes why timing only lookup can recommend a structure that never amortises construction in a one-query application.

Generate common input once, then randomise treatment order to reduce drift:

~~~python
from __future__ import annotations

from collections.abc import Callable
from dataclasses import dataclass
from random import Random
from time import perf_counter_ns


@dataclass(frozen=True)
class Observation:
    treatment: str
    elapsed_ns: int


def interleaved_benchmark(
    treatments: dict[str, Callable[[], object]],
    rounds: int,
    *,
    seed: int = 0,
) -> list[Observation]:
    if rounds < 1:
        raise ValueError("rounds must be positive")

    rng = Random(seed)
    names = list(treatments)
    observations: list[Observation] = []

    for _ in range(rounds):
        rng.shuffle(names)
        for name in names:
            started = perf_counter_ns()
            treatments[name]()
            elapsed = perf_counter_ns() - started
            observations.append(Observation(name, elapsed))

    return observations
~~~

The dictionary preserves references to callables; each round shuffles a list of names. The random seed makes order reproducible. A stronger harness would calibrate batch duration, isolate process starts, monitor system state, and record raw data. This small design nevertheless prevents the entire A treatment from always running cold and the entire B treatment from always running later.

Inputs must have equal logical meaning. Comparing a function on sorted data with another on shuffled data confounds algorithm and distribution. Mutation is especially treacherous: if treatment A sorts a shared list in place, treatment B receives already sorted input. Reconstruct or copy outside each timed region according to the intended lifecycle.

> **Common misconception 14.63 — “The shorter snippet is the faster implementation.”**  
> Source length says nothing reliable about runtime work. Built-ins can perform extensive native work, while long setup can enable cheap repeated operations.

### 14.15.4 Noise, isolation, and honesty

Operating systems multiplex processors; frequency governors change clock rates; simultaneous multithreading shares execution resources; caches retain other programs’ data; virtual machines can be migrated; and network paths vary. Perfect isolation is rarely available, but conditions can be characterised.

For sensitive CPU benchmarks:

- use an otherwise quiet machine when possible;
- record power policy, processor model, logical CPU count, and container CPU quota;
- consider pinning the benchmark to a processor, while acknowledging that interrupts still occur;
- avoid comparing results from thermally different phases;
- run treatments in fresh processes if interpreter or allocator history matters;
- verify that the benchmark duration exceeds timer granularity by a comfortable margin;
- retain outliers and explain any principled exclusion rule;
- report versions and exact code.

Do not quote more significant digits than the experiment supports. A claim of 12.347812 per cent improvement from noisy millisecond observations implies false precision. Prefer raw distributions, robust summaries, and an effect interval.

### Worked example 14.5 — Measuring scaling rather than one size

Complexity claims concern growth. Measure several geometrically increasing input sizes and normalise by a hypothesised function:

~~~python
from time import perf_counter


def unique_preserving_order(values: list[int]) -> list[int]:
    return list(dict.fromkeys(values))


def scaling_observations() -> list[tuple[int, float, float]]:
    observations: list[tuple[int, float, float]] = []
    for size in (1_000, 2_000, 4_000, 8_000, 16_000, 32_000):
        values = list(range(size))
        started = perf_counter()
        unique_preserving_order(values)
        elapsed = perf_counter() - started
        observations.append((size, elapsed, elapsed / size))
    return observations
~~~

If expected time is linear, elapsed time divided by \(n\) should approach a roughly stable range after fixed overhead and noise cease to dominate. This does not prove an asymptotic bound, and hash-table assumptions must be stated. It is more informative than one size because it can reveal regime changes, cache boundaries, and unexpected superlinear growth.
