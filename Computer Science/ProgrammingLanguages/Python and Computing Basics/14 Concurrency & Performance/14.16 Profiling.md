# 14.16 Profiling

A **profiler** attributes resource use to program locations or call paths.

- Deterministic CPU profilers observe function calls and returns, adding overhead but supplying call counts and cumulative time.
- Statistical profilers sample execution with lower perturbation and estimate where time is spent.
- Line profilers attribute within selected functions.
- Allocation and memory profilers examine allocation sites, peaks, and retained objects.
- Tracing systems follow operations across process/service boundaries.

`cProfile` provides deterministic profiling in the standard library:

```text
python -m cProfile -o profile.dat -m ledger benchmark-input.csv
```

Analyse both **internal time**, attributed to the function body excluding callees, and **cumulative time**, including called functions. A frequently called cheap function can have large cumulative cost because of its descendants; a leaf can have high internal cost.

Profiling development input can optimise an unrepresentative path. Capture production-like distributions safely and preserve privacy.

### 14.16.1 Attribution has a measurement model

A deterministic call profiler observes events such as call, return, and exception. It can count calls and attribute elapsed or CPU time to functions, but the instrumentation changes execution cost. Code with many tiny function calls can be perturbed more than code with fewer large calls, so profiled ratios are not guaranteed to match uninstrumented ratios.

A sampling profiler periodically inspects the current instruction or stack. If a location appears in \(k\) of \(n\) unbiased time samples, \(k/n\) estimates its share of sampled time. Sampling misses sufficiently short events individually, but repeated short events contribute in proportion to the time they occupy. Higher frequency improves temporal resolution while increasing overhead. Pauses, native frames, kernel waits, and multiple threads require tool-specific support.

**Inclusive time** is time attributed to a function and its descendants; **exclusive time** excludes descendants. In <code>cProfile</code> reports these correspond broadly to cumulative and internal time. Consider function A, which calls B and C. High inclusive time in A can simply mean that A is an entry point to expensive descendants. High exclusive time indicates cost within A’s own observed body.

A **call graph** represents caller–callee relations. A **flame graph** aggregates sampled stacks: horizontal width represents sample proportion, vertical position represents stack depth, and adjacency does not imply chronological order. A flame graph is not a time-series trace. An **icicle graph** uses a related orientation. A **trace** instead records timestamped spans or events and can expose critical-path waiting across asynchronous and distributed boundaries.

> **Common misconception 14.64 — “A profiler reports the exact time each line consumed.”**  
> Every profiler observes through a model and perturbs execution. Its attribution, clock, sampling, native-code visibility, and concurrency support determine what the numbers mean.

### 14.16.2 Using cProfile and pstats programmatically

The standard library permits controlled profiling and reproducible report generation:

~~~python
from __future__ import annotations

import cProfile
import io
import pstats
from collections.abc import Callable
from typing import TypeVar


T = TypeVar("T")


def profile_call(operation: Callable[[], T], limit: int = 25) -> tuple[T, str]:
    profiler = cProfile.Profile()
    profiler.enable()
    try:
        result = operation()
    finally:
        profiler.disable()

    stream = io.StringIO()
    statistics = pstats.Stats(profiler, stream=stream)
    statistics.strip_dirs().sort_stats(pstats.SortKey.CUMULATIVE)
    statistics.print_stats(limit)
    return result, stream.getvalue()
~~~

The <code>finally</code> suite stops profiling even when the operation fails, though <code>result</code> is returned only after successful completion. <code>strip_dirs</code> shortens path display and can collapse otherwise distinguishable names; retain full paths in archival profiles when ambiguity matters. Sorting by cumulative time identifies expensive call subtrees. A second view sorted by internal time identifies expensive bodies. Call counts reveal whether a modest per-call cost is multiplied excessively.

A profile should be connected to an unprofiled benchmark. If unprofiled wall time is 100 ms and profiled wall time is 180 ms, absolute profiled times should not be presented as production latency. The call structure and relative concentration may remain useful, but the perturbation is material.

Recursion produces primitive-call and total-call counts. A recursive function can be entered many times while only one outer call originates independently. Read the report legend and inspect callers/callees before inferring invocation structure.

### 14.16.3 Waiting, running, and blocked time

CPU profiling alone can tell little about an I/O-bound service. A function may have high wall-clock latency and almost no CPU samples because it waits for a socket, lock, child process, or queue. Conversely, high process CPU does not identify which request experienced latency when many requests overlap.

Use complementary observations:

- wall latency at request and stage boundaries;
- process and thread CPU time;
- runnable and blocked thread state;
- event-loop lag;
- queue wait and resource-acquisition time;
- operating-system I/O counters;
- lock contention where tools support it;
- distributed trace spans carrying one request identity;
- dependency-side metrics.

**Event-loop lag** is delay between when a callback was eligible to run and when it actually ran. Sustained lag can indicate blocking code, long CPU sections, too many ready callbacks, or an overloaded host. Measuring only total coroutine duration cannot separate queueing in the event loop from remote waiting.

Instrument semaphores and pools at both acquisition and service:

~~~python
from __future__ import annotations

import asyncio
from collections.abc import Awaitable, Callable
from dataclasses import dataclass
from time import perf_counter
from typing import TypeVar


T = TypeVar("T")


@dataclass(frozen=True)
class TimedResult:
    value: T
    wait_seconds: float
    service_seconds: float


async def timed_with_limit(
    limit: asyncio.Semaphore,
    operation: Callable[[], Awaitable[T]],
) -> TimedResult:
    requested = perf_counter()
    async with limit:
        acquired = perf_counter()
        value = await operation()
        finished = perf_counter()
    return TimedResult(
        value=value,
        wait_seconds=acquired - requested,
        service_seconds=finished - acquired,
    )
~~~

If service time remains stable while wait time grows, capacity or admission is implicated. If service time itself grows with concurrency, downstream saturation or contention is implicated. The context manager releases the semaphore if the operation raises or the task is cancelled.

> **Common misconception 14.65 — “Low CPU utilisation means the application is efficient.”**  
> It can mean useful waiting, unavoidable dependency latency, lock contention, starvation, throttling, or insufficient parallelism. Utilisation must be interpreted with throughput and wait-state evidence.

### 14.16.4 Profiling concurrent programs

Concurrent profiles need identity and causality. Aggregate samples can show that JSON parsing consumes 30 per cent of process CPU, but not which request or queue stage caused it. Attach stable operation identifiers at admission and preserve them across task creation, executor submission, process messages, and remote calls.

Context variables propagate automatically when <code>asyncio.to_thread</code> is used, but general executor and process propagation depends on the interface and values. Never assume thread-local state identifies an async request: many tasks share one thread, and one task can resume after another.

For asynchronous code, call stacks are discontinuous across suspension. Awaiting code is dormant, not on the native running stack. Async-aware profilers or task introspection reconstruct logical await relationships. A snapshot of only the event-loop thread may overrepresent dispatch and underrepresent dormant request lifetime.

For processes, collect per-worker profiles rather than allowing several workers to overwrite one file. Record process identity, role, start method, and workload partition. Aggregate only compatible profiles. A straggling partition can dominate batch makespan even if aggregate CPU is balanced.

Distributed traces introduce **spans**, timed operations linked by parent and trace identity. Sampling policy can bias analysis: retaining every error trace but one per cent of successes is useful operationally, yet error proportion in the retained sample no longer estimates traffic proportion without weighting. Trace timestamps across machines depend on clock alignment; duration measured within one monotonic clock is usually more reliable than subtracting unsynchronised wall timestamps.

### 14.16.5 Profiles answer “where”; experiments answer “whether”

After finding an apparent hotspot:

1. inspect callers and input distributions;
2. determine whether it lies on the critical path or overlaps other work;
3. calculate an upper-bound speedup from its fraction;
4. propose a semantic or algorithmic change;
5. benchmark unprofiled before and after;
6. verify that cost did not merely move elsewhere;
7. inspect memory, tail latency, and failure behaviour.

A cache can remove CPU from a profile while causing memory growth and lock contention. Parallel parsing can reduce one worker’s CPU time while increasing end-to-end latency through serialisation. The profile guides a hypothesis, not a verdict.

> **Common misconception 14.66 — “If an optimisation removes a hotspot, the program is faster.”**  
> Cost can move to callers, allocation, synchronisation, memory, or another stage. Only the target end-to-end measurement establishes improvement.

### Worked example 14.6 — Call counts expose repeated work

~~~python
import re


def extract_identifiers_slow(lines: list[str]) -> list[str]:
    identifiers: list[str] = []
    for line in lines:
        pattern = re.compile(r"[A-Z]{2}-\d{6}")
        identifiers.extend(pattern.findall(line))
    return identifiers


IDENTIFIER_PATTERN = re.compile(r"[A-Z]{2}-\d{6}")


def extract_identifiers(lines: list[str]) -> list[str]:
    identifiers: list[str] = []
    for line in lines:
        identifiers.extend(IDENTIFIER_PATTERN.findall(line))
    return identifiers
~~~

A profile can reveal one <code>re.compile</code> call per input line. Hoisting construction changes lifetime: the compiled pattern becomes module state and is reused. Correctness requires that the pattern is invariant and that reuse is supported. Benchmarking then determines whether compilation was already internally cached and whether the effect matters for representative input. The example illustrates a causal question; it does not assert a fixed speedup.
