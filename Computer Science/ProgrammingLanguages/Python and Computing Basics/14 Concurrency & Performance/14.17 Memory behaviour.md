# 14.17 Memory behaviour

Memory questions include:

- allocation rate;
- live set;
- retained size and object graph;
- peak resident memory;
- fragmentation and allocator arenas;
- native buffers outside Python-object accounting;
- process copy-on-write changes;
- cache and queue bounds.

`tracemalloc` traces Python memory allocations:

```python
import tracemalloc

tracemalloc.start()
before = tracemalloc.take_snapshot()

values = [str(number) for number in range(100_000)]

after = tracemalloc.take_snapshot()
for statistic in after.compare_to(before, "lineno")[:10]:
    print(statistic)
```

It does not capture every native allocation or equal operating-system resident-set change. A snapshot comparison identifies Python allocation differences under one trace configuration.

A **memory leak** is unintended retained memory whose lifetime exceeds need, not merely high peak allocation. References in caches, registries, closures, callbacks, task collections, exception tracebacks, and global containers can retain object graphs. Identify the reference path keeping objects reachable.

### 14.17.1 Allocation, retention, and resident memory are different

An **allocation** obtains storage for an object or buffer. A value is **live** while future correct execution can still use it. It is **reachable** when a chain of references from roots—such as active frames, globals, tasks, or native extension state—leads to it. CPython can reclaim an unreachable ordinary object, subject to implementation details discussed in Chapter 15.

The **live set** is memory occupied by currently live data. **Peak allocated memory** is the greatest allocation total observed under a particular accounting system. **Resident set size** (**RSS**) is the operating system’s estimate of pages currently resident for a process; it includes much that <code>tracemalloc</code> does not trace and can include shared pages under accounting rules. **Virtual memory size** covers mapped address space, not necessarily physical residence.

Freeing Python objects need not cause RSS to fall immediately. An allocator can retain freed blocks and arenas for reuse; fragmentation can leave partially occupied pages; a native library can cache buffers; the operating system can defer reclamation. Therefore:

- falling Python allocation counts do not guarantee falling RSS;
- stable RSS does not prove a leak;
- rising RSS does not identify a Python allocation site;
- one endpoint measurement can miss a damaging peak.

Measure the layer implicated by the requirement. A memory-constrained container cares about cgroup or operating-system accounting and peak RSS. An allocation optimisation may use <code>tracemalloc</code>. A native-array application needs native allocator or library evidence. A forked process model needs proportional and private-memory measures to understand shared pages.

> **Common misconception 14.67 — “If memory is freed, the operating-system graph must fall.”**  
> Language-level object reclamation, allocator reuse, page fragmentation, native caches, and resident-set accounting are different layers.

### 14.17.2 Snapshot comparisons and tracing scope

Start tracing before the allocations of interest. Snapshot A establishes a baseline; execute a controlled phase; snapshot B; compare by traceback, filename, or line. Repeating a create–release cycle can distinguish bounded warm-up from continuing retention:

~~~python
from __future__ import annotations

import gc
import tracemalloc
from collections.abc import Callable


def allocation_differences(
    phase: Callable[[], None],
    *,
    frames: int = 10,
    limit: int = 20,
) -> list[tracemalloc.StatisticDiff]:
    tracemalloc.start(frames)
    try:
        gc.collect()
        before = tracemalloc.take_snapshot()
        phase()
        gc.collect()
        after = tracemalloc.take_snapshot()
        return after.compare_to(before, "traceback")[:limit]
    finally:
        tracemalloc.stop()
~~~

Explicit collection here reduces one source of variation and asks about objects retained after collection. It changes timing and is not representative of steady execution. Tracing itself consumes memory and time. The returned statistics describe traced Python allocation differences, not necessarily ownership: a library line may allocate on behalf of caller data retained elsewhere.

Use filters to exclude known harness allocations, but retain the unfiltered snapshot for audit. Compare equal lifecycle states—for example, after the same number of completed requests and after cleanup—rather than comparing an empty process with a deliberately populated cache unless cache population is the question.

### 14.17.3 Reference paths explain retention

Suppose completed tasks are kept for observability:

~~~python
import asyncio
from collections.abc import Awaitable
from typing import TypeVar


T = TypeVar("T")
completed: list[asyncio.Task[object]] = []


async def retain_task(awaitable: Awaitable[T]) -> T:
    task = asyncio.create_task(awaitable)
    completed.append(task)
    return await task
~~~

Each completed task can retain its result; failed tasks can retain exceptions and traceback frames; frames can retain local variables and large object graphs. Clearing only a local payload binding does not help while the global list retains the task. The repair follows the required observability policy: retain bounded summaries, remove tasks in a done callback, or store a capped ring buffer.

~~~python
import asyncio
from collections.abc import Awaitable
from typing import TypeVar


T = TypeVar("T")
background: set[asyncio.Task[object]] = set()


def start_owned_background(awaitable: Awaitable[object]) -> None:
    task = asyncio.create_task(awaitable)
    background.add(task)
    task.add_done_callback(background.discard)
~~~

This set retains tasks during execution and releases them after completion. It does not observe exceptions. A complete owner should add a callback that calls <code>task.exception()</code> for non-cancelled tasks or, preferably, use a structured scope that awaits them. Memory lifetime and failure ownership are the same architectural question.

Reference-finding tools can reveal a referrer, but inspection itself creates temporary references. Prefer a small reproducer, lifecycle counters, snapshot traces, and knowledge of roots. In a graph, **shallow size** is the immediate object’s storage; **retained size** is storage that would become reclaimable if that object and only its exclusive descendants became unreachable. Shared descendants make retained-size accounting non-additive.

### 14.17.4 Caches are explicit memory policies

A cache exchanges space and invalidation complexity for avoided work. Every cache needs:

- a key defining semantic identity;
- a value and ownership policy;
- a maximum size or other eviction bound;
- expiry or invalidation rules;
- concurrency control;
- failure policy for construction;
- metrics for hit, miss, eviction, and memory;
- a decision about whether entries survive deployment or process boundaries.

<code>functools.lru_cache</code> provides a threadsafe memoising wrapper in ordinary documented use, but duplicate concurrent computation can occur before a result is cached. Arguments and results remain strongly referenced until eviction or clearing. An unbounded cache on user-controlled keys is a memory-growth mechanism.

A **weak reference** refers to an object without keeping it alive. Weak-key or weak-value mappings are useful for ancillary metadata whose lifetime should follow another object, but weak references do not define deterministic eviction: collection timing is implementation-dependent, and many built-in values cannot be weakly referenced. Weakness is not a substitute for a capacity policy when memory must remain below a hard limit.

### 14.17.5 Concurrency multiplies transient memory

If one active request peaks at \(m\) bytes, concurrency \(c\) can create nearly \(cm\) transient memory before shared structures and fragmentation. Pipeline stages can hold the same logical item in encoded, decoded, transformed, and serialised forms simultaneously. A thirty-megabyte compressed image can decode into hundreds of megabytes depending on dimensions and pixel representation; file size alone is not a memory admission measure.

Bound memory by tokens representing estimated bytes rather than only item count when sizes vary materially. Estimation need not be perfect to prevent one thousand large items from being admitted under a queue bound chosen for small items. For strict safety, validate declared size, stream formats where possible, cap decompressed dimensions, and enforce process/container limits.

Fork-based process pools can initially share parent pages through copy-on-write. Refcount updates, allocator activity, or mutations can dirty pages and convert apparently shared memory into private copies. Measuring only the parent before workers become active underestimates steady-state memory. Spawn-based workers construct independent heaps from the outset.

> **Common misconception 14.68 — “A queue of one hundred items has predictable memory use.”**  
> Item representations, nested graphs, duplicate buffers, active-stage copies, allocator overhead, and process replication can vary by orders of magnitude.

### 14.17.6 Garbage collection is not general memory management

CPython’s reference counting often reclaims objects when their reference count reaches zero; a cyclic collector handles many unreachable reference cycles. Calling <code>gc.collect()</code> cannot reclaim reachable objects and cannot force every native allocator to return pages. Disabling cyclic collection can reduce pauses in a carefully proven workload but allows unreachable cycles to accumulate.

Collection work depends on allocation and object graph behaviour. Measure pause distribution and reclaimed counts before tuning thresholds. If cyclic collection dominates, first ask why so many tracked container objects or cycles are created and whether their lifetimes can be simplified. Chapter 15 develops the CPython-specific mechanism; the language-level rule remains that a program should release resources explicitly rather than depend on object finalisation timing.

### Worked example 14.7 — Streaming controls peak retention

~~~python
from collections.abc import Iterable, Iterator
from hashlib import sha256


def digests_materialised(chunks: Iterable[bytes]) -> list[str]:
    copied = list(chunks)
    return [sha256(chunk).hexdigest() for chunk in copied]


def digests_streamed(chunks: Iterable[bytes]) -> Iterator[str]:
    for chunk in chunks:
        yield sha256(chunk).hexdigest()
~~~

The first function deliberately retains every input chunk until the list and comprehension complete, then retains every digest. The generator holds a chunk and digest around each suspension, but the consumer determines ultimate retention. Calling <code>list(digests_streamed(chunks))</code> still retains all result strings, and a source may itself already be materialised. Streaming is an end-to-end lifetime property, not a keyword attached to one function.
