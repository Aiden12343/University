# 14.18 Algorithmic and representational optimisation

The largest improvements often change the amount of work:

- replace repeated linear membership with a set when preprocessing and memory are justified;
- stream instead of materialising when one pass suffices;
- use vectorised native array operations for dense numerical work;
- batch boundary crossings;
- cache only stable expensive results under a bounded invalidation policy;
- choose compact representations to improve locality;
- move filtering near data acquisition when semantics permit.

Avoid premature low-level rewriting. Replacing clear Python with complicated byte manipulation to save a fraction of a percent can increase defects and block later algorithmic improvements.

### 14.18.1 Reduce the growth rate before constant factors

For \(n\) records, an accidental nested scan can perform roughly \(n^2\) comparisons. Replacing one repeated scan with an index can reduce expected work to approximately linear construction plus linear lookups under ordinary hash-table assumptions.

~~~python
from dataclasses import dataclass


@dataclass(frozen=True)
class Customer:
    customer_id: int
    name: str


@dataclass(frozen=True)
class Order:
    order_id: int
    customer_id: int


def attach_customers_quadratic(
    orders: list[Order],
    customers: list[Customer],
) -> list[tuple[Order, Customer]]:
    attached: list[tuple[Order, Customer]] = []
    for order in orders:
        for customer in customers:
            if customer.customer_id == order.customer_id:
                attached.append((order, customer))
                break
        else:
            raise KeyError(order.customer_id)
    return attached


def attach_customers_indexed(
    orders: list[Order],
    customers: list[Customer],
) -> list[tuple[Order, Customer]]:
    by_id = {customer.customer_id: customer for customer in customers}
    if len(by_id) != len(customers):
        raise ValueError("customer identifiers must be unique")

    try:
        return [(order, by_id[order.customer_id]) for order in orders]
    except KeyError as error:
        raise KeyError(f"unknown customer {error.args[0]}") from error
~~~

For \(o\) orders and \(c\) customers, the first version is \(O(oc)\) in the worst case. The second has expected \(O(c+o)\) time and \(O(c)\) additional space, assuming ordinary dictionary behaviour. It also makes duplicate-customer semantics explicit. The transformation is not free: identifiers must be hashable, memory must fit, and adversarial collision guarantees differ from balanced-tree indexes.

Database systems perform analogous work through indexes and join algorithms. Pulling two complete tables into Python and joining them can discard a query optimiser’s ability to filter, index, batch disk access, and avoid transfer. Move work to the component with the appropriate representation and statistics when doing so preserves semantics.

### 14.18.2 Representation determines locality and overhead

A Python list of integers is principally a dynamic array of references to separate integer objects, subject to implementation details. A packed native array can store fixed-width values contiguously. The packed representation can:

- eliminate one pointer traversal per element;
- reduce per-value metadata;
- place more values in each cache line;
- enable vector processor instructions;
- transfer blocks efficiently to native libraries or devices.

The advantage comes from representation and specialised kernels, not from a mystical “vectorisation” incantation. A vectorised expression can allocate several full-size temporaries:

\[
y=(a+b)\times(c-d).
\]

One implementation may allocate arrays for \(a+b\), \(c-d\), and the product. Fused kernels, in-place operations, or chunking can reduce peak memory, but in-place mutation changes aliasing semantics. Measure both time and peak memory.

Object-rich structures remain correct when values have heterogeneous types, arbitrary precision, custom protocols, or independent identity. Compact structures impose a schema—element width, signedness, byte order, null representation, and shape. The schema is the source of both efficiency and constraint.

**Locality of reference** means that memory accessed near in time is also near in address or reused. Processor caches exploit locality. Big-O treats an array access and pointer-following lookup as constant-time operations, but their constants can differ substantially because a cache miss waits far longer than an arithmetic instruction. Complexity analysis and machine-level performance complement rather than replace each other.

### 14.18.3 Batch fixed boundary costs

Many interfaces have a fixed per-call cost plus a variable per-item cost. If a crossing costs \(b\) and per-item work costs \(w\), processing \(n\) items one at a time costs approximately

\[
n(b+w),
\]

whereas one batch costs approximately

\[
b+nw.
\]

The model omits latency, memory, maximum message size, partial failure, and parallelism but explains why batching database inserts, process-pool tasks, network frames, and native calls can improve throughput.

Batch size trades off:

- larger batches better amortise fixed costs;
- smaller batches reduce first-item waiting and peak memory;
- large batches create coarse cancellation and retry units;
- small batches permit load balancing across workers;
- external systems impose transaction, packet, and parameter limits.

Adaptive batching can collect up to \(k\) items or wait at most \(d\) time, whichever occurs first. This bounds both size and batching delay. It must flush during shutdown and specify whether cancellation discards or commits a partial batch.

~~~python
from __future__ import annotations

from collections.abc import Iterable, Iterator
from itertools import islice
from typing import TypeVar


T = TypeVar("T")


def batched_exactly(values: Iterable[T], size: int) -> Iterator[tuple[T, ...]]:
    if size < 1:
        raise ValueError("size must be positive")

    iterator = iter(values)
    while batch := tuple(islice(iterator, size)):
        yield batch
~~~

The iterator is consumed once, at most <code>size</code> elements per batch. The last batch may be shorter. Python 3.12 does not yet expose the later <code>strict</code> option of <code>itertools.batched</code>; this implementation states its own remainder semantics and uses only 3.12-compatible constructs.

### 14.18.4 Eliminate work through laziness, caching, and early reduction

**Laziness** delays work until its result is requested. It can avoid work entirely when consumers stop early:

~~~python
from collections.abc import Iterable


def first_even_square(values: Iterable[int]) -> int | None:
    squares = (value * value for value in values if value % 2 == 0)
    return next(squares, None)
~~~

Only enough input is consumed to find the first even value. Replacing the generator with a list comprehension calculates every matching square before <code>next</code>. Laziness also shifts failure and resource lifetime: errors occur during consumption, and a generator reading a file must not escape the file’s context unless it owns that lifetime.

Caching avoids repeated work when inputs repeat and results remain valid. The relevant ratio is not merely hit rate. A cache hit avoiding a one-hour computation is valuable even if rare; a high hit rate on a nanosecond operation can be harmful if locking and hashing cost more. Consider miss penalty, memory, concurrency, invalidation, and cold-start fill.

**Early reduction** filters, projects, or aggregates before an expensive boundary. Read only required database columns; reject oversized payloads before decode; combine duplicate keys before remote calls; and calculate streaming aggregates instead of storing raw observations when later questions permit it. Do not push a filter across an operation if doing so changes order, exceptions, floating-point rounding, or side effects.

### 14.18.5 Specialise the common case without breaking the general case

A **fast path** handles a frequent case with less work; a **slow path** preserves complete semantics. For example, a parser might detect ASCII input and apply an ASCII-specific scan, falling back to full Unicode processing. The fast-path predicate must be cheaper than the avoided work and must imply every assumption the specialised implementation makes.

Profile-guided specialisation can improve hot workloads but creates test obligations. Test both paths, boundary transitions, and equivalent results. If a rare path becomes unmaintained, an optimisation has silently narrowed the real contract.

Python itself and its libraries may specialise operations. Application code should not duplicate interpreter-level tricks without evidence. Prefer semantic improvements—better algorithms, fewer objects, less transfer, stronger batching—before syntax folklore such as binding a global to a local solely to save name-lookup cost.

> **Common misconception 14.69 — “Low-level code is the advanced form of optimisation.”**  
> The strongest improvements usually remove work, change asymptotic growth, improve representation, or move computation to a suitable bulk engine. Instruction-level tuning comes after profiling and may deliver less.

### Worked example 14.8 — One pass instead of several materialisations

Suppose the task is to compute count, sum, minimum, and maximum for valid measurements. Four separate traversals require a reusable materialised sequence and repeat dispatch. One traversal maintains a sufficient aggregate:

~~~python
from dataclasses import dataclass
from math import isfinite
from collections.abc import Iterable


@dataclass(frozen=True)
class Summary:
    count: int
    total: float
    minimum: float
    maximum: float


def summarise(values: Iterable[float]) -> Summary | None:
    count = 0
    total = 0.0
    minimum = float("inf")
    maximum = float("-inf")

    for value in values:
        if not isfinite(value):
            continue
        count += 1
        total += value
        minimum = min(minimum, value)
        maximum = max(maximum, value)

    if count == 0:
        return None
    return Summary(count, total, minimum, maximum)
~~~

The function consumes one-pass iterables and uses constant auxiliary state. It explicitly excludes infinities and NaNs and returns <code>None</code> for no valid measurements. Floating-point summation order affects rounding; <code>math.fsum</code> can improve accuracy but would require retaining or separately processing values. Performance design cannot silently decide numerical semantics.
