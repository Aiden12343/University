# 14.19 Why Python can be “slow”

The statement requires comparison. CPython executing dynamic Python operations may perform more work than compiled native code specialised in advance:

- objects carry type and lifetime metadata;
- operations dispatch according to runtime types and protocols;
- values may be separately allocated and reached through pointers;
- bytecode dispatch or tiered interpreter machinery mediates source operations;
- reference management and garbage collection consume work;
- generic semantics restrict some compiler assumptions;
- pointer-rich structures have weaker locality than packed arrays.

This does not mean every Python application is slow. I/O can dominate. Python can orchestrate highly optimised C, C++, Fortran, Rust, or accelerator kernels. Development time and correctness can outweigh execution time. PyPy and other implementations make different trade-offs. Modern CPython uses adaptive specialisation and evolving execution machinery; exact internals are version-specific.

Precise statement: “Under benchmark B on environment E, this CPython implementation takes X distribution of time and Y memory, with profile P attributing Z percent to these dynamic operations.”

### 14.19.1 The unit of comparison matters

Comparing “Python” with “C” confounds at least language, implementation, algorithm, compiler, optimisation flags, library, representation, and expertise. A Python call to a native sorting routine and a hand-written C insertion sort do not establish a language ranking. Compare implementations of the same semantic task under the same workload and constraints.

Distinguish:

- **interpreter overhead**, work performed to execute dynamic language operations;
- **algorithmic work**, operations required by the chosen method;
- **library work**, often executed in optimised native code;
- **system wait**, time blocked on I/O or resources;
- **coordination overhead**, serialisation, scheduling, locking, and copying;
- **startup work**, import, compilation, process creation, and cache population.

A command-line tool that processes one small file can be dominated by interpreter startup and imports. A long-running service amortises those costs. A numerical program can spend 99 per cent of its time in a native kernel, making Python orchestration overhead irrelevant. A tight loop over Python objects exposes it directly.

### 14.19.2 Dynamic semantics require work

For an expression such as <code>left + right</code>, Python’s data model supports more than fixed-width integer addition. The runtime must account for operand types, reflected operations, subclass relationships, possible arbitrary-precision integers, user-defined methods, exceptions, and result-object lifetime. A compiler for statically known machine integers can emit a small fixed instruction sequence because its contract is narrower.

Similarly, calling <code>operation(value)</code> can involve resolving a name, determining that the object is callable, selecting a call protocol, binding arguments, creating or reusing frame state, and handling an arbitrary return or exception. Implementations optimise common cases, but must preserve observable semantics when assumptions fail.

Python integers do not overflow at fixed 32- or 64-bit boundaries; they grow to represent larger mathematical integers until resource limits intervene. This is semantically valuable and computationally different from machine-integer arithmetic. Strings maintain Unicode semantics, lists hold heterogeneous object references, and dictionaries invoke hashing and equality protocols. Comparing them with packed fixed-type arrays changes the problem.

### 14.19.3 Dispatch and specialisation

**Forward-reference flag.** Chapter 15 formally introduces bytecode and the CPython evaluation machinery. For this section, a minimal definition suffices: **bytecode** is a compact instruction representation executed by the Python virtual machine, and **dispatch** is selection of the implementation for the next instruction or operation.

CPython compiles source to bytecode and executes it through an interpreter. Dispatch, object checks, reference management, and generic operation protocols add work relative to a native loop whose types and control flow were resolved ahead of time. Yet “one bytecode equals one source operation” is false, and bytecode counts alone do not predict time.

Contemporary CPython versions use adaptive techniques that observe runtime behaviour and specialise some operations for common types or shapes, falling back when assumptions cease to hold. These mechanisms reduce overhead without changing language semantics. Their exact opcodes, thresholds, and implementation are version-specific and must not become application correctness assumptions.

Use <code>dis</code> only as explanatory evidence:

~~~python
import dis


def total(values: list[int]) -> int:
    result = 0
    for value in values:
        result += value
    return result


dis.dis(total)
~~~

The output describes the current interpreter build’s instruction stream, not processor instructions or a portable performance contract. Running the function can alter adaptive internal state without requiring source-visible change. Profile real execution rather than optimising for remembered opcode folklore.

### 14.19.4 Allocation, indirection, and caches

Object-oriented uniformity has spatial cost. A container of references plus separately allocated objects causes more metadata and pointer traversal than a packed buffer of fixed-width values. A processor loads memory in cache-line units; scattered objects can cause more cache and translation-lookaside-buffer misses. Automatic reference management also updates lifetime metadata.

However, allocation cost is not constant across circumstances. CPython maintains specialised allocators and free lists for some objects; small integers and interned strings can be reused under implementation policies; operating-system allocation may be amortised by arenas. Microbenchmarks that repeatedly allocate one shape can measure allocator steady state unlike a diverse application.

Optimisation should select a representation whose constraints match the domain. The standard <code>array</code> module, <code>memoryview</code>, packed binary formats, and numerical libraries can reduce object overhead. They require explicit element types, shapes, and lifetime rules. A memory view can avoid copying but retains the underlying exporter and can prevent resizing.

### 14.19.5 The GIL is only one possible limit

In conventional CPython, one global interpreter lock per interpreter prevents several threads from simultaneously executing Python bytecode in that interpreter. This explains why adding threads to a tight pure-Python loop generally does not yield multicore execution and can add switching overhead. It does not explain single-thread dispatch cost, memory layout, algorithms, I/O, or native kernels.

Native extension code can release the GIL while operating without Python objects, allowing multiple native computations or I/O operations to proceed. A free-threaded CPython build can disable the traditional GIL, subject to extension compatibility and different internal synchronisation. Neither case guarantees scaling: memory bandwidth, locks, serial fractions, allocation contention, and workload partition remain.

Therefore, “the GIL makes Python slow” is both too broad and causally incomplete. State the measured workload, implementation mode, thread count, profile, and comparison.

### 14.19.6 Alternative implementations and execution strategies

Python is a language with multiple implementations. CPython prioritises compatibility with its ecosystem and C API while evolving its execution engine. PyPy commonly employs a tracing just-in-time compiler and a different garbage collector. GraalPy integrates Python into GraalVM. MicroPython targets constrained environments with different trade-offs. Compatibility with Python source does not imply identical extension support, startup, memory, timing, or finalisation.

A **just-in-time compiler** (**JIT**) compiles code during program execution, using observed information to specialise machine code. It can make long-running hot loops faster while adding warm-up, compilation time, memory, and performance variability. An **ahead-of-time compiler** performs translation before execution. Cython translates a Python-like language with optional static information into C extension code. These strategies overlap in purpose but differ in contracts and interoperability.

Benchmark the deployment candidate. Code tuned to CPython refcount timing or extension internals may perform differently or fail elsewhere. Portability is an engineering requirement, not an automatic virtue: a system may intentionally require one implementation, but that dependency should be explicit.

> **Common misconception 14.70 — “Python’s speed is a single property of the language.”**  
> Performance belongs to a program, implementation, workload, representation, environment, and metric. Language semantics influence cost, but no context-free speed number exists.

### Worked example 14.9 — Moving the loop, not translating the syntax

~~~python
from math import fsum
from collections.abc import Iterable


def mean_manual(values: list[float]) -> float:
    if not values:
        raise ValueError("mean requires data")
    total = 0.0
    for value in values:
        total += value
    return total / len(values)


def mean_with_fsum(values: Iterable[float]) -> float:
    materialised = list(values)
    if not materialised:
        raise ValueError("mean requires data")
    return fsum(materialised) / len(materialised)
~~~

This is not a clean speed comparison because <code>fsum</code> provides more accurate summation semantics and the second function materialises arbitrary iterables. It illustrates the obligation to compare equivalent contracts. For an existing list, using a suitable built-in or native library can move iteration into optimised implementation code, but different rounding, input types, and allocation can dominate. First define numerical semantics; then benchmark candidates that satisfy them.

Often the correct “Python optimisation” is not rewriting each loop iteration in cleverer Python. It is expressing the operation so a suitable library can process a batch, changing the algorithm, or removing the loop from the critical path. When those options are exhausted and evidence identifies interpreter overhead, native acceleration becomes rational.
