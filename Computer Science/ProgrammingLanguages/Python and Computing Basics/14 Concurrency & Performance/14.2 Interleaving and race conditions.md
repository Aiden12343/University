# 14.2 Interleaving and race conditions

A **race condition** occurs when correctness depends on uncontrolled relative timing among concurrent operations. The defect is not simply that results vary; controlled nondeterminism can be valid. A race violates an invariant under some permitted ordering.

Consider a shared balance initially 100 and two withdrawals of 80 and 30. Each operation performs:

1. read balance;
2. check sufficient funds;
3. calculate new balance;
4. write new balance.

Interleaving:

| Step | Task A | Task B | Shared balance |
|---:|:---|:---|---:|
| 1 | reads 100 | | 100 |
| 2 | checks 80 allowed | | 100 |
| 3 | | reads 100 | 100 |
| 4 | | checks 30 allowed | 100 |
| 5 | computes 20, writes | | 20 |
| 6 | | computes 70, writes | 70 |

Both withdrawals report success, yet only 30 is reflected and the total withdrawal exceeds the original funds. Each read and write can be individually valid; the compound check-and-update is not atomic.

A **critical section** is a region that accesses shared state under an invariant requiring controlled exclusion or ordering. A **lock** is a synchronisation object through which tasks acquire permission to enter such a region.

```python
from threading import Lock


class Account:
    def __init__(self, balance: int) -> None:
        self._balance = balance
        self._lock = Lock()

    def withdraw(self, amount: int) -> None:
        if amount <= 0:
            raise ValueError("amount must be positive")
        with self._lock:
            if amount > self._balance:
                raise ValueError("insufficient funds")
            self._balance -= amount
```

The lock owns the entire check-and-update transition. Protecting only the final assignment leaves the race. Every access participating in the invariant, including reads exposed elsewhere, needs a coherent policy.

### 14.2.1 Shared state and conflicting actions

Two activities **share state** when both can reach or affect the same logical resource. Shared state is broader than one Python object. Two processes writing the same file, two services updating one database row, and two threads using one socket all share state through an external system.

Actions **conflict** when their order can affect an allowed observation, typically because at least one writes. Two reads of immutable data need no mutual exclusion. A read concurrent with a write may require synchronisation even when the read itself is “harmless”.

A **data race** has a specialised meaning in languages with formal memory models: unsynchronised conflicting memory accesses under specified conditions. A **race condition** is the broader correctness defect caused by timing. Python documentation does not give ordinary programs a licence to infer a complete cross-implementation memory model from current CPython behaviour; application code should express ordering with documented synchronisation primitives.

The state protected by a lock is not physically inside the lock. Developers establish a protocol: every access capable of violating invariant \(I\) must acquire lock \(L\). One uncooperative access bypasses the theorem.

> **Common misconception 14.5 — “Only writers need the lock.”**  
> A reader can observe a transient or mutually inconsistent state. Reads participating in a compound invariant require the same synchronisation policy unless an immutable snapshot or documented atomic interface supplies safety.

### 14.2.2 Atomicity and linearisation

An operation is **atomic** at an interface when observers cannot detect it partially completed. A **linearizable** concurrent operation appears to take effect at one instant between invocation and response, while respecting real-time order between non-overlapping calls. That conceptual instant is the **linearisation point**.

Atomicity is scoped. A thread lock can make a multi-field Python update atomic to other participants using that lock; it does not make the change durable after power loss. A database transaction can provide atomic commit under its own failure model; it may not make an external email part of the same transaction.

~~~python
from threading import Lock


class Inventory:
    def __init__(self, available: int) -> None:
        if available < 0:
            raise ValueError("available must be non-negative")
        self._available = available
        self._reserved = 0
        self._lock = Lock()

    def reserve(self, quantity: int) -> bool:
        if quantity <= 0:
            raise ValueError("quantity must be positive")

        with self._lock:
            if quantity > self._available:
                return False
            self._available -= quantity
            self._reserved += quantity
            return True

    def snapshot(self) -> tuple[int, int]:
        with self._lock:
            return self._available, self._reserved
~~~

The invariant is that both counters are non-negative and their sum remains the initial stock unless another locked operation intentionally changes total stock. The successful reservation linearises at the protected state transition. The snapshot copies both values while holding the lock, so it cannot pair one counter from before a reservation with the other from after it.

Returning the tuple releases the lock before the caller uses the values. This is safe because integers and the tuple are immutable. Returning a mutable internal mapping would allow unprotected mutation after release.

> **Common misconception 14.6 — “One atomic assignment makes a compound operation atomic.”**  
> Atomicity of the final write does not join the preceding read, validation, computation, and related-field updates into one indivisible transition.

### 14.2.3 Check–then–act and time-of-check to time-of-use

A **check–then–act race** occurs when an activity tests a condition and later acts on the assumption that the condition still holds. The filesystem form is called **time-of-check to time-of-use** (**TOCTOU**):

~~~python
if not destination.exists():
    destination.write_bytes(payload)
~~~

Another process can create or replace the path between the calls. A lock inside this Python process does not coordinate unrelated processes unless they share that lock protocol. Use an operating-system or library operation that combines the required semantics, such as exclusive creation, and still account for symbolic links, permissions, and the exact threat model.

The cache example “if absent, build, then insert” has the same shape. A dictionary’s individual operations may retain internal integrity, yet the compound once-only construction can occur twice. Correct remedies include:

- protect check and insertion with one lock, perhaps building inside it;
- install a future/promise placeholder under the lock, then build outside while others await it;
- use an idempotent builder for which duplicate work is acceptable;
- delegate uniqueness to a transactional store.

Building inside a global lock is simple but can serialise expensive work and deadlock if the builder re-enters. Placeholder designs need failure propagation and removal or retention policy. Synchronisation design trades one risk for another.

> **Common misconception 14.7 — “Thread-safe containers make every expression using them thread-safe.”**  
> Container integrity and application-level transactionality differ. A sequence of safe method calls can violate a higher-level invariant between calls.

### 14.2.4 Ownership, confinement, and immutability

The most reliable shared-state synchronisation can be no shared mutation:

- **thread confinement:** mutable state is reachable by only one thread;
- **task confinement:** one event-loop task owns mutation and receives messages;
- **process isolation:** heaps are separate unless state is explicitly transferred or shared;
- **immutability:** values cannot change after publication;
- **copy-on-write:** updates construct a new version while readers retain old snapshots.

Ownership is a protocol, not an intrinsic flag on ordinary objects. Sending a list through a thread queue does not remove the producer’s reference. The producer must agree not to mutate after transfer, or the consumer must receive a copy or immutable representation.

~~~python
from dataclasses import dataclass
from queue import Queue


@dataclass(frozen=True)
class MeasurementBatch:
    source: str
    values: tuple[float, ...]


channel: Queue[MeasurementBatch] = Queue(maxsize=16)
channel.put(MeasurementBatch("sensor-7", (1.2, 1.4, 1.3)))
~~~

The frozen dataclass prevents ordinary field rebinding and the tuple prevents element replacement. This is shallow immutability: any mutable objects nested within fields would remain mutable.

Immutable snapshots increase allocation and can contain stale information. A reader must know whether “consistent as of version \(v\)” is acceptable or whether current state is required. Avoiding races does not decide freshness semantics.

> **Common misconception 14.8 — “Passing an object through a queue transfers ownership automatically.”**  
> A thread queue transfers a reference. Exclusive ownership exists only if producers stop using mutable aliases or the message representation enforces the intended isolation.

### 14.2.5 Lock granularity and composition

**Lock granularity** is the amount of state or work covered by one lock. A coarse lock makes invariants easier to state but limits parallel access. Fine-grained locks can reduce contention while increasing lock ordering, lifetime, and composition complexity.

Suppose accounts each own a lock. A transfer needs both accounts’ invariants and the system invariant that total funds are conserved. Acquiring only the source lock permits observers to see funds disappear before the destination update. Acquiring both locks in a global order preserves the compound transition.

Public methods that each acquire an internal non-reentrant lock do not necessarily compose:

~~~python
with account.lock:
    account.withdraw(10)
~~~

If <code>withdraw</code> tries to acquire the same ordinary lock, the thread blocks on itself. Exposing locks leaks representation policy. Prefer one higher-level operation implementing the complete transaction, or carefully document an external-locking interface.

A reentrant lock permits the owning thread to acquire repeatedly, tracking depth, but can conceal poor decomposition and does not solve cycles between different locks. Use it when re-entrant call structure is intentional, not as a universal deadlock cure.

> **Common misconception 14.9 — “Smaller critical sections are always better.”**  
> Reducing hold time may improve concurrency, but splitting an invariant across separately locked phases can make the operation incorrect. Correct atomic scope precedes contention optimisation.
