# 14.20 Native acceleration and boundary cost

Escape hatches include:

- call optimised standard-library or third-party native code;
- use NumPy-style packed arrays and vectorised kernels;
- compile selected modules with Cython;
- write extension modules using the CPython C API or a stable ABI strategy;
- use foreign-function interfaces;
- move a component to another language/process under a protocol.

**Cython** is a language and compiler that translates Python-like and C-extended source to C extension modules. Static type declarations can permit direct C operations in selected regions. It is not the same as CPython and does not make arbitrary Python source automatically native-speed.

Native boundaries have costs:

- conversion or copying of inputs and outputs;
- GIL acquisition/release and thread-state rules;
- reference ownership and error-indicator protocols;
- platform/compiler ABI compatibility;
- memory safety risk;
- debugging across languages;
- distribution of binary wheels.

Batch enough work per crossing to justify overhead. A native call per scalar in a Python loop can remain dominated by dispatch; a native kernel over a contiguous million-element array can amortise the boundary.

### 14.20.1 Choose the narrowest escape hatch

Native code expands the trusted computing base. Prefer, in order of increasing ownership burden:

1. a standard-library operation with the required semantics;
2. a mature maintained library exposing a bulk operation;
3. a subprocess or service with an explicit protocol;
4. generated or compiled code through a higher-level binding system;
5. a small foreign-function interface to an existing stable C ABI;
6. a custom extension using implementation APIs.

This ordering is not absolute. A process boundary adds transfer cost but isolates crashes and dependency conflicts. A direct extension gives low-latency object integration but can corrupt the interpreter if reference or memory rules are violated. The narrowest interface that meets the contract minimises long-term maintenance.

First isolate a kernel: a function with explicit inputs, outputs, error rules, and no incidental dependence on globals. Establish a correct Python reference implementation and property tests. Measure its fraction of end-to-end cost and calculate maximum possible benefit. Define representative small, medium, and large inputs because a native implementation can lose at small sizes through crossing overhead.

### 14.20.2 Copies, views, and ownership

Passing a Python list of arbitrary objects to a fixed-type native function can require conversion and allocation. Returning results may require conversion back. A **zero-copy** interface avoids copying a payload, but still performs validation and establishes shared lifetime. Zero-copy is not zero-cost.

The Python **buffer protocol** allows an exporter to expose a memory region with metadata such as format, shape, and strides. A <code>memoryview</code> is a Python view over such a buffer:

~~~python
from __future__ import annotations

import struct
from collections.abc import Iterable


def encode_unsigned(values: Iterable[int]) -> bytearray:
    materialised = list(values)
    if any(not 0 <= value <= 0xFFFFFFFF for value in materialised):
        raise ValueError("values must fit unsigned 32-bit representation")

    storage = bytearray(4 * len(materialised))
    view = memoryview(storage)
    for index, value in enumerate(materialised):
        struct.pack_into("<I", view, index * 4, value)
    return storage
~~~

This produces a little-endian 32-bit representation. A native function receiving the buffer can process contiguous bytes without converting each value into a Python integer, provided the binding validates format and lifetime. The view keeps the bytearray alive; resizing the exporter while views exist is restricted. Endianness and width are now protocol semantics.

Strided or non-contiguous views can require a native kernel capable of arbitrary strides or a contiguous copy. Alignment requirements may also force a copy. “Accepts a buffer” does not prove that no copy occurs.

### 14.20.3 Foreign-function interfaces and generated bindings

A **foreign-function interface** (**FFI**) calls code using another language’s binary calling convention. Python’s <code>ctypes</code> and third-party systems can describe function signatures and marshal values. Incorrect declarations can pass the wrong widths or pointers and cause memory corruption. Validate return codes, retain callback objects for as long as native code might call them, and never pass a pointer whose backing Python object can disappear.

Binding generators reduce boilerplate but do not decide ownership. Every native object needs answers:

- who allocates and who frees it;
- whether a returned pointer is borrowed or newly owned;
- how long input buffers remain valid;
- whether callbacks can occur after the initiating call;
- which thread invokes callbacks;
- how native errors become Python exceptions;
- whether calls may run concurrently;
- whether the library itself is re-entrant or thread-safe.

A wrapper should translate native failure into a precise Python exception before returning. In the CPython C API, an extension function that signals failure must follow the API’s return/error-indicator convention consistently. Returning an ordinary value while an exception remains set, or returning an error sentinel without an exception, is an extension defect.

### 14.20.4 Cython as selective static commitment

Cython accepts Python-like source plus optional declarations that permit selected values and loops to use C representations. A conceptual kernel might be written:

~~~cython
cpdef long sum_nonnegative(long[:] values):
    cdef Py_ssize_t index
    cdef long total = 0
    for index in range(values.shape[0]):
        if values[index] < 0:
            raise ValueError("negative value")
        total += values[index]
    return total
~~~

This is Cython source, not valid Python source, and requires a build step. The typed memory view commits to a compatible buffer representation. The <code>long</code> accumulator has platform-dependent width and can overflow unlike a Python integer; a production contract should choose an exact-width type or explicitly define overflow. Bounds checks, wraparound behaviour, and GIL use must be selected deliberately.

Releasing the GIL in Cython or C is valid only while code avoids Python objects and APIs requiring attached Python thread state, except through documented free-threading-safe mechanisms. A <code>nogil</code> region does not make the underlying native library thread-safe. If several threads mutate the same native buffer, ordinary memory races remain.

### 14.20.5 CPython API, stable ABI, and version reach

The CPython C API exposes Python objects, exceptions, reference ownership, modules, and interpreter services. Some names are public but tied to a CPython feature release; a limited subset participates in the **limited API**, from which extensions can target the **stable ABI** for compatibility across several Python 3 releases. Stable ABI can simplify wheel distribution but may omit newer or lower-level optimisation opportunities.

The **application binary interface** (**ABI**) specifies binary-level contracts such as calling conventions, object layouts made public, symbol availability, and data representation. Source compatibility does not imply binary compatibility. Operating system, processor architecture, compiler runtime, debug mode, and free-threaded versus conventional builds can affect artefacts.

Do not read or write private object fields merely because a header exposes an implementation layout. Accessor functions preserve abstraction and are increasingly important for free-threaded safety. In a free-threaded build, internal container locking does not make arbitrary borrowed-pointer use safe after another thread can mutate the container. Use the version-specific extension guidance and declare build support accurately.

Wheels encode compatibility tags. Producing binary distributions requires a matrix of Python versions, platforms, architectures, and ABI choices. Continuous integration should build, install into clean environments, import, test behaviour, and, where relevant, run memory and thread sanitisation in the native toolchain.

### 14.20.6 GIL transitions are correctness boundaries

In conventional CPython, a native extension normally begins execution with the GIL held when called from Python. It can release the lock around long native work that neither accesses Python objects nor invokes unsafe Python APIs, then reacquire before constructing results or raising Python exceptions. Releasing around a tiny operation can cost more than it saves.

When native code creates its own thread and later calls Python, that thread must establish the interpreter/thread state required by the documented C API. Multiple interpreters complicate association: a convenience API that assumes the main interpreter may be unsuitable for a subinterpreter. Free-threaded builds remove the global exclusion guarantee but still require thread state and object-specific synchronisation.

Reference ownership must survive the unlocked interval. If a borrowed reference points into a mutable container and another thread can remove the object while the GIL is released—or in a free-threaded build while operations overlap—the pointer can become invalid. Convert to owned references or copy stable data under the proper lock before releasing.

> **Common misconception 14.71 — “Native code is automatically fast and parallel.”**  
> Native code can be slower at small sizes, copy extensively, contend on its own locks, retain the GIL, saturate memory bandwidth, or change semantics. Its benefit and safety require measurement and a precise boundary contract.

### 14.20.7 Isolate failure and preserve a fallback

Native defects include buffer overrun, use-after-free, undefined signed overflow, ABI mismatch, deadlock, and process crash. Python exceptions cannot contain arbitrary memory corruption. Run risky parsers or rapidly evolving components in a worker process when fault isolation outweighs transfer cost. Apply operating-system resource and privilege limits appropriate to the threat model.

Keep the reference implementation executable in tests even if production dispatches to the accelerator:

~~~python
from __future__ import annotations

from collections.abc import Callable, Sequence


def dot_reference(left: Sequence[float], right: Sequence[float]) -> float:
    if len(left) != len(right):
        raise ValueError("vectors must have equal length")
    return sum(a * b for a, b in zip(left, right, strict=True))


def verify_accelerator(
    accelerated: Callable[[Sequence[float], Sequence[float]], float],
    cases: Sequence[tuple[Sequence[float], Sequence[float]]],
) -> None:
    for left, right in cases:
        expected = dot_reference(left, right)
        actual = accelerated(left, right)
        tolerance = 1e-12 * max(1.0, abs(expected))
        if abs(actual - expected) > tolerance:
            raise AssertionError((left, right, expected, actual))
~~~

The tolerance is an example policy, not universally valid numerical analysis. It combines relative scaling with an absolute floor but does not handle NaN or infinity. Tests should include empty values, mismatched lengths, extremes, non-contiguous buffers, aliases, concurrent calls, interruption, and allocation failure where interfaces permit simulation.

### 14.20.8 Benchmark the complete crossing curve

Measure total call time over input sizes \(n\), including validation and conversion. A simplified model is

\[
T_{\text{native}}(n)=b+c+n\,w_n,
\]

where \(b\) is dispatch/binding overhead, \(c\) is conversion cost that may itself depend on \(n\), and \(w_n\) is native per-item work. Python time might be

\[
T_{\text{Python}}(n)=p+n\,w_p.
\]

The accelerator is useful only where its curve lies below the reference under relevant constraints. A dispatcher can retain Python for tiny inputs and native code for larger inputs, but the branching threshold is environment-dependent and must not affect semantics.

Include concurrent scaling. A native kernel releasing the GIL may scale until memory bandwidth saturates. A kernel using internal threads can become slower when invoked concurrently by an outer thread pool. Record physical cores, affinity, library thread variables, and input layout. The boundary is part of the system, not an isolated function.
