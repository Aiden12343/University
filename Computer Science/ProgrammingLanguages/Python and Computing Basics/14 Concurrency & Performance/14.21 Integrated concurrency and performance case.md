# 14.21 Integrated concurrency and performance case

Requirement: download 1,000 independent documents, parse them, calculate hashes, and store results.

Design questions:

- Network I/O is concurrent and must have connection/time/admission bounds.
- Parsing may be Python CPU work or native-library work; profile it.
- Hash calculation may release the GIL for sufficiently large buffers under implementation rules, but do not assume without measurement/documentation.
- Storage writes need transaction and idempotency policy.
- Retaining all documents can exceed memory; stream or bound queues.
- Cancellation must close responses and stop child work.
- Retrying downloads must distinguish safe GET-like retrieval from non-idempotent effects.

Candidate architecture:

1. async producer fetches with bounded semaphore and timeouts;
2. bounded queue supplies parse work, applying backpressure;
3. CPU-heavy Python parsing uses bounded process workers if profiling justifies;
4. one transaction-owning consumer batches result writes;
5. task group owns every coroutine;
6. failures cancel siblings and preserve already committed batch semantics;
7. metrics record queue depth, request latency, parse time, error class, throughput, and memory.

Parallelism is an outcome of partitioning and runtime resources. Correctness begins with ownership, bounded capacity, idempotency, and transaction contracts.

### 14.21.1 State the contract before drawing the pipeline

Assume each input record contains a stable document identifier, an HTTPS URL, and an expected version. For each record the system must eventually record either:

- a committed result containing identifier, version, content digest, parsed metadata, and completion timestamp; or
- a terminal rejection describing a non-retryable validation failure.

Transient infrastructure failure can leave the item pending for a later run. The system must never commit metadata for bytes whose identifier/version does not match the result row. Reprocessing the same identifier and version must not create a second logical result. These are safety properties. Eventual completion while required dependencies recover and retry limits permit is a liveness property.

Define acceptance precisely. Reading a source line is not acceptance; enqueuing in volatile process memory is not durable acceptance. In this design, the source manifest remains the durable input, and a checkpoint records committed identifiers. A crashed process can therefore restart by scanning the manifest and skipping already committed identities.

The performance objective might state: for 100 KiB–10 MiB documents under the recorded workload distribution, complete at least 200 documents per second at steady state, with p99 end-to-end latency below 30 seconds, RSS below 4 GiB, no more than 64 network requests and 8 parser processes active, and no more than 256 downloaded-but-uncommitted documents resident. These values are illustrative; measurement must justify them.

### 14.21.2 Derive stages and ownership

The logical stages are:

| Stage | Input | Output | Owner and boundary |
|:---|:---|:---|:---|
| admission | manifest record | validated job | coordinator task |
| acquisition | job | bounded bytes or spool path | async fetch task |
| parsing | acquired document | parsed immutable result | process worker |
| commit | parsed result | durable outcome | single batching task/database |
| observation | stage events | metrics/logs | telemetry subsystem |

The coordinator owns all task lifetimes. A fetch task owns its response stream and temporary file until it transfers a closed spool path to parsing. A process worker receives serialisable values and returns an immutable result or a tagged failure. The commit task is the only writer to the checkpoint in this simplified design. Temporary files are named under a run-specific directory and removed after commit or terminal failure; startup recovery removes abandoned run directories only after proving no live process owns them.

Queue bounds establish a finite cut through the pipeline:

\[
M_{\text{pipeline}}
\lesssim
B_f m_f+B_p m_p+C_f a_f+C_p a_p+M_{\text{runtime}},
\]

where \(B_f,B_p\) are queue bounds, \(m_f,m_p\) mean retained item sizes, \(C_f,C_p\) active concurrency, \(a_f,a_p\) active per-operation storage, and \(M_{\text{runtime}}\) shared overhead. Means are insufficient for a hard memory proof; maximum validated document size and representation peaks supply conservative bounds.

### 14.21.3 Represent outcomes rather than transporting arbitrary exceptions

An exception object can be difficult to serialise and can retain traceback state. Across a process boundary, return a stable tagged outcome:

~~~python
from __future__ import annotations

import os
from dataclasses import dataclass
from hashlib import sha256
from typing import Literal


@dataclass(frozen=True)
class ParseSuccess:
    kind: Literal["success"]
    document_id: str
    version: str
    digest: str
    word_count: int


@dataclass(frozen=True)
class ParseFailure:
    kind: Literal["failure"]
    document_id: str
    version: str
    category: Literal["invalid-encoding", "invalid-format", "internal"]
    detail: str
    retryable: bool


ParseOutcome = ParseSuccess | ParseFailure


def parse_document(document_id: str, version: str, payload: bytes) -> ParseOutcome:
    try:
        text = payload.decode("utf-8")
    except UnicodeDecodeError as error:
        return ParseFailure(
            "failure",
            document_id,
            version,
            "invalid-encoding",
            f"byte offset {error.start}",
            False,
        )

    try:
        if "\x00" in text:
            raise ValueError("NUL character is forbidden")
        words = text.split()
        return ParseSuccess(
            "success",
            document_id,
            version,
            sha256(payload).hexdigest(),
            len(words),
        )
    except ValueError as error:
        return ParseFailure(
            "failure",
            document_id,
            version,
            "invalid-format",
            str(error),
            False,
        )
    except Exception as error:
        return ParseFailure(
            "failure",
            document_id,
            version,
            "internal",
            type(error).__name__,
            True,
        )
~~~

The parser does not return a traceback or confidential payload in <code>detail</code>. Expected invalid input becomes a non-retryable value. Unexpected defects are tagged retryable only as a placeholder; a real policy would cap retries and alert because deterministic software defects do not improve with repetition.

Hash the exact acquired bytes before any text normalisation. If content identity instead concerns canonical logical text, define normalisation—including Unicode form and newline rules—before hashing. A digest detects accidental mismatch; it does not authenticate an untrusted publisher without a key or trusted expected digest.

### 14.21.4 Acquisition needs size, time, and identity bounds

A production fetcher should:

- validate scheme and destination policy before connection;
- resolve and connect under a security policy that accounts for redirects and DNS changes;
- set connection, response-header, idle-read, and end-to-end deadlines;
- reject declared and observed sizes above the cap;
- stream to a bounded buffer or spool file rather than concatenate without limit;
- verify expected media and content identity where applicable;
- close the response under success, exception, and cancellation;
- classify status and transport failures for retry.

This chapter’s cybersecurity branch later develops hostile-input and server-side request-forgery concerns. The minimal definition here is that allowing arbitrary URLs can cause the service to access internal or otherwise forbidden resources; a URL string check alone is not a complete defence because name resolution and redirects affect the eventual destination.

Retry owns an end-to-end deadline. Each attempt receives the remaining budget, and the backoff is also charged to it. The operation is naturally idempotent if acquisition is a side-effect-free retrieval of an immutable version, but remote access logs and quotas are still effects. Store the expected version so a mutable URL cannot silently yield bytes from a later version.

### 14.21.5 Bounded orchestration without eager task explosion

The following executable core simulates asynchronous acquisition, offloads parsing through an executor interface, bounds queues, and commits through one owner. It uses a thread executor in the portable demonstration so the parser function remains importable in an interactive context; production placement must follow profiling and process-start constraints.

~~~python
from __future__ import annotations

import asyncio
from collections.abc import Awaitable, Callable, Iterable
from concurrent.futures import Executor, ThreadPoolExecutor
from dataclasses import dataclass


@dataclass(frozen=True)
class DocumentJob:
    document_id: str
    version: str
    url: str


@dataclass(frozen=True)
class Acquired:
    job: DocumentJob
    payload: bytes


PIPELINE_STOP = object()


async def simulated_fetch(job: DocumentJob, maximum_bytes: int) -> bytes:
    await asyncio.sleep(0.001)
    payload = f"{job.document_id} from {job.url}".encode()
    if len(payload) > maximum_bytes:
        raise ValueError("document exceeds maximum size")
    return payload


async def admit(
    jobs: Iterable[DocumentJob],
    destination: asyncio.Queue[DocumentJob | object],
    fetcher_count: int,
) -> None:
    for job in jobs:
        await destination.put(job)
    for _ in range(fetcher_count):
        await destination.put(PIPELINE_STOP)


async def fetch_worker(
    admitted: asyncio.Queue[DocumentJob | object],
    acquired: asyncio.Queue[Acquired | object],
    maximum_bytes: int,
) -> None:
    while True:
        item = await admitted.get()
        try:
            if item is PIPELINE_STOP:
                break
            assert isinstance(item, DocumentJob)
            async with asyncio.timeout(2.0):
                payload = await simulated_fetch(item, maximum_bytes)
            await acquired.put(Acquired(item, payload))
        finally:
            admitted.task_done()
    await acquired.put(PIPELINE_STOP)


async def parse_worker(
    acquired: asyncio.Queue[Acquired | object],
    parsed: asyncio.Queue[ParseOutcome | object],
    executor: Executor,
    fetcher_count: int,
) -> None:
    stopped_fetchers = 0
    loop = asyncio.get_running_loop()
    while stopped_fetchers < fetcher_count:
        item = await acquired.get()
        try:
            if item is PIPELINE_STOP:
                stopped_fetchers += 1
                continue
            assert isinstance(item, Acquired)
            outcome = await loop.run_in_executor(
                executor,
                parse_document,
                item.job.document_id,
                item.job.version,
                item.payload,
            )
            await parsed.put(outcome)
        finally:
            acquired.task_done()
    await parsed.put(PIPELINE_STOP)


async def commit_owner(
    parsed: asyncio.Queue[ParseOutcome | object],
) -> dict[tuple[str, str], ParseOutcome]:
    committed: dict[tuple[str, str], ParseOutcome] = {}
    while True:
        item = await parsed.get()
        try:
            if item is PIPELINE_STOP:
                return committed
            assert isinstance(item, (ParseSuccess, ParseFailure))
            key = (item.document_id, item.version)
            existing = committed.get(key)
            if existing is not None and existing != item:
                raise RuntimeError(f"conflicting result for {key!r}")
            committed[key] = item
        finally:
            parsed.task_done()


async def process_documents(
    jobs: Iterable[DocumentJob],
    *,
    fetcher_count: int = 8,
    maximum_bytes: int = 1_000_000,
) -> dict[tuple[str, str], ParseOutcome]:
    if fetcher_count < 1:
        raise ValueError("fetcher_count must be positive")

    admitted: asyncio.Queue[DocumentJob | object] = asyncio.Queue(maxsize=32)
    acquired: asyncio.Queue[Acquired | object] = asyncio.Queue(maxsize=16)
    parsed: asyncio.Queue[ParseOutcome | object] = asyncio.Queue(maxsize=32)

    with ThreadPoolExecutor(max_workers=4) as executor:
        async with asyncio.TaskGroup() as group:
            commit_task = group.create_task(commit_owner(parsed))
            group.create_task(admit(jobs, admitted, fetcher_count))
            for _ in range(fetcher_count):
                group.create_task(
                    fetch_worker(admitted, acquired, maximum_bytes)
                )
            group.create_task(
                parse_worker(acquired, parsed, executor, fetcher_count)
            )

        return commit_task.result()


async def pipeline_demo() -> None:
    jobs = [
        DocumentJob(f"doc-{number}", "v1", f"https://example.test/{number}")
        for number in range(100)
    ]
    outcomes = await process_documents(jobs)
    assert len(outcomes) == len(jobs)


if __name__ == "__main__":
    asyncio.run(pipeline_demo())
~~~

Line-by-line lifecycle analysis:

1. <code>admit</code> streams the iterable rather than creating one task per document. The admitted queue bounds pending records.
2. A fixed number of fetch workers creates the acquisition-concurrency limit. Each always calls <code>task_done</code> and sends one downstream stop marker on termination.
3. One parse coordinator counts all fetcher stop markers. It submits one item at a time in this compact example, so the executor’s four workers are not actually saturated. To exploit four-way parallelism, use four parse coordinator tasks and one stop per coordinator, or keep a bounded set of futures. This limitation is explicit rather than hidden.
4. <code>run_in_executor</code> does not forcibly stop a running function when the awaiting task is cancelled. The <code>with</code> statement shuts down the executor and waits by default; shutdown latency includes outstanding parse calls.
5. The commit owner is the sole mutator of its mapping. A real database operation would atomically enforce uniqueness on <code>(document_id, version)</code>.
6. Every task belongs to the task group. On ordinary completion, stop markers close downstream stages. On exceptional completion, sibling cancellation prevents orphan tasks.

The demonstration is pedagogical, not a production downloader. It sends stop markers only after normal completion. Exceptional failure is propagated by the task group and cancels sibling stages, avoiding stop-marker puts from cancellation cleanup that could themselves block on an undrained full queue. A hardened implementation also needs nested ownership scopes, explicit channel closing, or a supervisory shutdown path for independently cancelled workers and external shutdown. This subtlety is why graceful shutdown requires adversarial tests.

### 14.21.6 Scale the parse stage without losing bounds

To keep \(p\) parse submissions active without eagerly materialising all input, create exactly \(p\) parse workers. Each consumes the acquired queue and produces to the parsed queue. The acquisition stage then sends \(p\) parse stop markers after all fetchers finish; coordinating this requires one owner to count upstream completion. Each parse worker sends one downstream stop marker; the commit owner counts \(p\).

With a <code>ProcessPoolExecutor</code>, place construction under the main guard when the module is an executable entry point, ensure submitted callables and arguments are picklable, and measure serialisation. Sending complete multi-megabyte payloads copies data through process communication. Passing spool paths reduces message size but transfers filesystem lifetime and security obligations. Shared memory reduces copying but requires allocation, offset/length validation, ownership, and reclamation.

Partition size affects load balance. One document per process submission balances variable parsing but pays high overhead. Batches amortise serialisation but can make one slow batch a straggler. Measure duration against document shape and use moderate chunks with bounded in-flight count.

### 14.21.7 Commit semantics and exactly-once language

“Exactly once” is often an overstatement. A process can receive an outcome, commit it, and crash before acknowledging the worker. On restart the outcome is submitted again. What can be guaranteed is often **at-least-once delivery with idempotent effect**.

Use a database uniqueness constraint on the logical key. In one transaction:

1. insert the result if absent;
2. if present, compare immutable identity and return the existing result;
3. reject a conflicting result for the same key;
4. record any checkpoint whose advancement must be atomic with the result.

Do not update a separate checkpoint before committing the result; a crash between them can cause permanent omission. Do not acknowledge durable completion before the transaction commits. If external object storage and a database cannot share one transaction, stage content under a content-derived key, then commit a reference; orphan staging objects can be collected by a separate reconciliation policy.

### 14.21.8 Failure matrix

| Failure point | Observable uncertainty | Required response |
|:---|:---|:---|
| before request sent | no remote retrieval | retry within deadline |
| after request sent, before response | retrieval outcome unknown but assumed side-effect-free | retry immutable version |
| during spool write | partial local file | close and delete/recover by run identity |
| parser raises input error | bytes known, result terminal | commit rejection |
| parser process crashes | item outcome unknown | replace worker, retry under cap, inspect crash |
| result queue full | downstream slower | await; admission backpressure propagates |
| database commit times out | commit outcome ambiguous | query by idempotency key before retry |
| process receives shutdown | tasks may be at any stage | stop admission, drain/cancel by policy, close |
| host terminates abruptly | no Python cleanup guarantee | durable manifest/checkpoint and startup reconciliation |

Failures can combine. A dependency slowdown fills queues; cancellation then begins; cleanup tries to use the same exhausted connection pool; timeout retries increase load. Test compound failure rather than one exception at a time.

### 14.21.9 Shutdown protocol

For graceful service shutdown:

1. stop accepting new manifests or requests;
2. record which accepted work is durable;
3. allow admitted work to drain until a shutdown deadline;
4. cancel remaining owned tasks;
5. wait for cancellation cleanup within a smaller budget;
6. shut down thread/process executors under a declared wait policy;
7. close database and network pools after their users stop;
8. flush telemetry without making shutdown unbounded;
9. leave recoverable markers for work not completed.

Order matters. Closing the database before the commit owner stops converts clean drain into failure. Waiting for queues before stopping infinite producers never terminates. Cancelling workers before preserving their job identities can lose volatile accepted work.

Signals are notifications, not a full shutdown protocol. Repeated termination may shorten the grace interval; a forced kill can occur at any point. Correctness must not depend exclusively on <code>finally</code>.

### 14.21.10 Performance model and experiment

Measure each stage’s service demand \(D_i\), effective parallelism \(c_i\), and sustainable rate. A first-order pipeline capacity is bounded by the slowest stage:

\[
X\le\min_i \frac{c_i}{D_i},
\]

subject to serialisation, shared resources, and arrivals. If one commit transaction handles 500 results/s, raising fetch concurrency beyond the point that acquisition supplies 500/s increases queueing rather than throughput.

Design experiments:

- sweep fetch concurrency while parser and commit capacity are fixed;
- sweep process workers and batch size while controlling native library threads;
- vary document size, encoding, and structural complexity;
- inject response delay, partial reads, parser crashes, and database stalls;
- measure stage wait/service distributions, queue age/depth, throughput, errors, retries, CPU, RSS, disk, and network;
- include cold start, steady state, overload, recovery, and graceful shutdown;
- compare thread and process parsing only after including transfer and startup;
- verify output set and digest against the sequential reference after every run.

A concurrency setting is selected near the best SLO-compliant region with headroom, not at the noisiest maximum observed throughput point. Repeat on the deployment CPU and quota; a developer workstation is not the target environment.

> **Common misconception 14.72 — “Once a pipeline is bounded and uses structured concurrency, its design is complete.”**  
> Bounds and lifetime ownership are foundations. Correctness still depends on item identity, stage protocols, durable commit, compound failures, cleanup order, security, and measured capacity.

### 14.21.11 Proof obligations

The final design document should state and justify:

- **no duplication of logical results:** uniqueness constraint and idempotent commit key;
- **no mismatched bytes/result:** immutable job identity travels with payload and outcome;
- **bounded volatile backlog:** finite queues, fixed task counts, maximum input representation;
- **owned activity lifetime:** all tasks and executors close within an enclosing scope;
- **observable failure:** every task/future outcome reaches an owner;
- **deadlock freedom:** channel close order and downstream drain remain available under each failure path;
- **eventual recovery:** durable manifest plus checkpoint permits replay after abrupt exit;
- **deadline propagation:** every wait consumes one end-to-end budget;
- **resource cleanup:** response, file, process, and database lifetimes have explicit owners;
- **portable assumptions:** conventional/free-threaded CPython, start method, native thread use, and platform constraints are recorded.

Some obligations are demonstrated by construction, some by tests, and some require assumptions about libraries or external systems. A rigorous document labels the boundary. It does not claim to have proven a database’s implementation from Python code.
