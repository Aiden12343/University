# 14.3 Safety, liveness, and progress

A **safety property** states that something bad never occurs: balance never becomes negative; two tasks never mutate the protected structure simultaneously. A **liveness property** states that something good eventually occurs: a waiting task eventually proceeds; a submitted job eventually completes or reports cancellation.

Locks can establish safety while destroying liveness. A **deadlock** occurs when tasks wait in a cycle for conditions only another waiting task can satisfy. With locks A and B:

- Task 1 holds A and waits for B;
- Task 2 holds B and waits for A.

Neither can proceed.

Prevention strategies include a global lock-acquisition order, acquiring all required resources through one coordinator, avoiding hold-and-wait, time-bounded acquisition with recovery, or eliminating shared mutable state.

**Starvation** occurs when a task remains unable to progress because others repeatedly receive resources. **Livelock** occurs when tasks continue reacting and changing state but make no useful progress. **Fairness** describes which waiting tasks are eventually selected; many lock APIs do not promise strict ordering.

### Worked example 14.1 — Establish lock order

For transfers between accounts, assign each account a stable internal ordering key. Acquire the lower-key lock first and the higher-key lock second regardless of transfer direction. This removes cycles involving two such locks because every acquisition edge points in one global order.

The ordering key must be stable and unique enough for tie handling. Using user-visible account numbers may leak policy or permit collision; an internal monotonic identifier or ordered pair with identity fallback can be used under a precise lifecycle design.

### 14.3.1 Four conditions for resource deadlock

The Coffman analysis identifies four conditions jointly necessary for a classical resource deadlock:

1. **mutual exclusion:** some resource cannot be used by all contenders simultaneously;
2. **hold and wait:** an activity holds one resource while requesting another;
3. **no pre-emption:** resources are released voluntarily rather than forcibly reclaimed without violating semantics;
4. **circular wait:** a cycle exists in the waits-for relation.

Eliminating any one prevents this form of deadlock. Not every strategy is acceptable: forcibly taking a lock while its owner is halfway through a mutation destroys safety. Global resource ordering attacks circular wait while preserving mutual exclusion.

A **wait-for graph** has an activity vertex for each participant and edge \(A\to B\) when \(A\) waits for a resource held by \(B\). A cycle is necessary for deadlock in the single-instance resource model. Systems with multiple resource instances require more careful detection.

Deadlock can occur without two explicit <code>Lock</code> objects. A thread can hold a lock while waiting for a future whose worker needs the same lock; a bounded executor can have every worker waiting for subtasks queued to that executor; a subprocess can fill its output pipe while the parent waits for exit before reading. Dependencies, not API names, form the cycle.

> **Common misconception 14.10 — “Deadlock requires two threads acquiring two locks in opposite order.”**  
> That is the smallest familiar example. Futures, queues, processes, I/O buffers, callbacks, and capacity reservations can participate in the same cyclic-wait structure.

### 14.3.2 Prove a lock order

Assign every lock-bearing resource a unique rank from a strict total order. Require that an activity holding rank \(r\) may acquire only a lock of greater rank. If a wait cycle existed,

\[
r_1<r_2<\cdots<r_k<r_1,
\]

which contradicts transitivity and irreflexivity of strict order. Therefore no lock-acquisition cycle exists among participants obeying the policy.

~~~python
from contextlib import contextmanager
from threading import Lock
from typing import Iterator


class RankedResource:
    def __init__(self, rank: int) -> None:
        self.rank = rank
        self.lock = Lock()


@contextmanager
def acquire_ranked(
    *resources: RankedResource,
) -> Iterator[None]:
    ordered = sorted(resources, key=lambda item: item.rank)
    if len({item.rank for item in ordered}) != len(ordered):
        raise ValueError("resource ranks must be unique")

    for resource in ordered:
        resource.lock.acquire()
    try:
        yield
    finally:
        for resource in reversed(ordered):
            resource.lock.release()
~~~

Reverse release is conventional and maintains nesting discipline, although the cycle-prevention proof concerns acquisition. If acquisition itself could fail or time out partway, the context manager would need to release the already acquired prefix before propagating failure. With the blocking calls shown, interruption semantics depend on platform and runtime.

Rank uniqueness must be stable for each resource lifetime. Using <code>id</code> can order currently live objects within one process, but identities can be reused after destruction; retaining resources through the acquisition scope avoids that particular change. A monotonic internal rank is easier to audit.

> **Common misconception 14.11 — “Using timeouts proves a program cannot deadlock.”**  
> A timeout may break indefinite waiting, but recovery can livelock, leak partial reservations, duplicate effects, or violate invariants. Prevention and a proved rollback protocol are stronger.

### 14.3.3 Conditions separate state from notification

A **condition variable** lets activities wait for a predicate over protected state. Notification is not the state itself. The correct pattern is:

~~~python
from collections import deque
from threading import Condition
from typing import Generic, TypeVar

T = TypeVar("T")


class BoundedBuffer(Generic[T]):
    def __init__(self, capacity: int) -> None:
        if capacity < 1:
            raise ValueError("capacity must be positive")
        self._capacity = capacity
        self._items: deque[T] = deque()
        self._changed = Condition()
        self._closed = False

    def put(self, item: T) -> None:
        with self._changed:
            self._changed.wait_for(
                lambda: len(self._items) < self._capacity
                or self._closed
            )
            if self._closed:
                raise RuntimeError("buffer is closed")
            self._items.append(item)
            self._changed.notify_all()

    def get(self) -> T:
        with self._changed:
            self._changed.wait_for(
                lambda: bool(self._items) or self._closed
            )
            if not self._items:
                raise EOFError("buffer is closed and empty")
            item = self._items.popleft()
            self._changed.notify_all()
            return item

    def close(self) -> None:
        with self._changed:
            self._closed = True
            self._changed.notify_all()
~~~

The condition’s lock protects the deque and closed flag. Waiting releases the lock atomically with blocking and reacquires it before returning. The predicate is checked repeatedly because another awakened thread may consume the relevant item first, or a wait may return when the predicate is not yet usable. Python’s <code>wait_for</code> implements the repeated check.

Closing wakes both producers and consumers. Existing items remain consumable; once drained, consumers receive end-of-stream. This is one possible shutdown contract, not a universal condition-variable behaviour.

Using <code>notify_all</code> is simple but can wake activities whose predicates remain false, producing a **thundering herd**. Separate conditions for “not empty” and “not full” can target notifications. Optimisation must retain a proof that every newly satisfiable class is eventually notified.

> **Common misconception 14.12 — “A notification means the condition is true.”**  
> Notification says protected state may have changed. A waiter must recheck its predicate while holding the associated lock.

### 14.3.4 Starvation, fairness, and priority inversion

A system can be deadlock-free yet fail liveness. If one waiting thread repeatedly loses an unspecified lock-selection race, it may starve. Python’s primitive lock documentation does not define which waiter proceeds after release, so strict FIFO fairness must not be assumed.

**Priority inversion** occurs when a high-priority activity waits for a resource held by a low-priority activity, while medium-priority work prevents the low-priority holder from running and releasing it. Some operating systems provide priority inheritance for selected primitives; Python’s high-level lock contract does not promise a portable solution.

Fairness has several meanings:

- **weak fairness:** a continuously enabled action eventually runs;
- **strong fairness:** an action enabled infinitely often eventually runs;
- bounded waiting: a known bound exists on how many competitors proceed first;
- FIFO service: waiting order determines admission.

Throughput-oriented scheduling can conflict with fairness and tail latency. A short-job-first queue lowers mean completion time under assumptions but can starve long jobs without ageing. The scheduling contract is part of system semantics.

> **Common misconception 14.13 — “No deadlock implies every task eventually completes.”**  
> Starvation, livelock, failed workers, lost notifications, unbounded arrivals, and external dependency failure can prevent completion without a wait cycle.

### 14.3.5 Livelock and retry synchronisation

In livelock, participants remain active while preventing useful progress. Two polite activities may each observe conflict, release resources, wait the same fixed interval, and retry in phase forever. Randomised exponential backoff reduces repeated synchrony under a probabilistic model:

\[
delay_k\sim U(0,\min(cap,base\cdot2^k)).
\]

Backoff is not a correctness proof. It reduces collision probability and offered load; attempts still need a maximum, deadline, cancellation path, and idempotency policy. Random jitter should not be used for security without an appropriate generator, and tests should inject a deterministic source.

A **progress condition** classifies concurrent algorithms more formally. Informally:

- **wait-free:** every participating operation completes in a bounded number of its own steps;
- **lock-free:** system-wide some operation completes despite delays to others;
- **obstruction-free:** an operation completes if it eventually runs in isolation;
- **blocking:** a suspended or failed holder can prevent others.

These are strong technical terms from non-blocking algorithm theory, not synonyms for “uses no Python <code>Lock</code> object”. A program built from lock-free primitives can still block on I/O or application queues.

> **Common misconception 14.14 — “Lock-free means no waiting and therefore faster.”**  
> Lock-free is a system-wide progress guarantee under a model. Individual operations may starve, retries can be costly, and memory reclamation and contention can make a lock-based design superior.
