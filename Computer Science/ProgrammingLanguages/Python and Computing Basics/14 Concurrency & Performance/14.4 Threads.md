# 14.4 Threads

A **thread** is an execution sequence within a process. Threads share the process address space and ordinarily share module objects, heap objects, open resources, and process configuration. Each has its own call stack and scheduling state.

```python
from concurrent.futures import ThreadPoolExecutor


def fetch_label(identifier: int) -> str:
    return f"item-{identifier}"


with ThreadPoolExecutor(max_workers=4) as executor:
    labels = list(executor.map(fetch_label, range(10)))
```

An executor manages worker threads and future results. `map` preserves input order in its result iteration, not completion order. If one earlier result is slow, consuming ordered results can wait even when later tasks finished.

A **future** represents a result that may not yet be available. It can complete successfully, fail with an exception, or be cancelled under its state rules. Every future should have an owner that observes its outcome; discarded futures can hide failure.

Threads are effective when underlying operations release the GIL or spend time waiting, and when shared-memory communication simplifies the design. They impose race, lifecycle, and shutdown obligations.

`threading.Event`, `Condition`, `Semaphore`, `Barrier`, and thread-safe queues express different coordination protocols. A queue often provides clearer ownership than many threads mutating a shared collection directly.

### 14.4.1 Thread lifetime and ownership

Creating a <code>Thread</code> object does not start execution; <code>start()</code> may be called once and arranges for <code>run()</code> to execute in another thread. A thread is alive from just before its <code>run</code> begins until just after it returns or raises. <code>join()</code> waits for termination; it does not return the target function’s value and, for a raw thread, it does not re-raise that function’s exception.

~~~python
from dataclasses import dataclass
from threading import Thread
from typing import Callable, Generic, TypeVar

T = TypeVar("T")


@dataclass
class ThreadOutcome(Generic[T]):
    value: T | None = None
    error: BaseException | None = None


def start_observed_thread(
    function: Callable[[], T],
) -> tuple[Thread, ThreadOutcome[T]]:
    outcome: ThreadOutcome[T] = ThreadOutcome()

    def run() -> None:
        try:
            outcome.value = function()
        except BaseException as error:
            outcome.error = error

    thread = Thread(target=run)
    thread.start()
    return thread, outcome
~~~

The caller must join before reading the outcome as complete. A stronger interface would encode “pending” separately from a successful <code>None</code> result and provide a method that raises the captured error. <code>concurrent.futures.Future</code> already supplies that state machine and is usually preferable.

A **daemon thread** does not keep the interpreter alive once only daemon threads remain. CPython may stop daemon threads abruptly during shutdown, so they are inappropriate as the sole owners of buffered writes, transactions, or mandatory cleanup. Graceful service shutdown uses non-daemon workers, an explicit stop signal, and joins.

> **Common misconception 14.15 — “A daemon thread is a managed background service.”**  
> Daemon status mainly changes interpreter-exit behaviour. It can cause abrupt abandonment; it does not supervise, restart, cancel, or clean up the activity.

### 14.4.2 Futures and executor shutdown

An executor separates task submission from worker management. <code>submit</code> returns a future. Calling <code>future.result()</code> waits when necessary, returns the value, or re-raises the worker exception in the observer thread.

~~~python
from concurrent.futures import (
    Future,
    ThreadPoolExecutor,
    as_completed,
)


def reciprocal(value: float) -> float:
    return 1.0 / value


values = [2.0, 0.0, 4.0]
with ThreadPoolExecutor(max_workers=3) as executor:
    futures: dict[Future[float], float] = {
        executor.submit(reciprocal, value): value
        for value in values
    }
    for future in as_completed(futures):
        source = futures[future]
        try:
            result = future.result()
        except ZeroDivisionError:
            print(f"{source}: division by zero")
        else:
            print(f"{source}: {result}")
~~~

<code>as_completed</code> yields futures by completion rather than submission order. The mapping retains request context. The executor context manager calls shutdown and waits for pending work under its contract.

Cancelling a future succeeds only if it has not begun running. Python cannot safely and generally terminate an arbitrary running thread: it may hold locks, own borrowed resources, or be halfway through an invariant. Cooperative cancellation passes an event or deadline that the function checks at safe points.

Submitting tasks from workers to the same bounded pool and waiting synchronously for them can deadlock when all workers become parents awaiting queued children. A pool is capacity, not an infinitely recursive scheduler.

> **Common misconception 14.16 — “<code>Future.cancel()</code> stops the function.”**  
> It can prevent execution of a pending task. Once running, ordinary thread work requires a cooperative stop protocol; abandoning the future merely abandons observation.

### 14.4.3 Events, semaphores, and barriers

Synchronisation primitives express different state machines:

- an **event** is a level-triggered Boolean flag; waiters proceed while it is set;
- a **semaphore** stores permits; acquire consumes one and release adds one;
- a **bounded semaphore** detects releases beyond its initial bound;
- a **barrier** releases a fixed group only after the required number arrive;
- a **condition** waits for an application predicate while coordinating a lock.

An event is appropriate for a stop request:

~~~python
from threading import Event, Thread
from time import sleep


def poll_until_stopped(stop: Event) -> None:
    while not stop.wait(timeout=0.25):
        perform_one_poll()


stop = Event()
thread = Thread(target=poll_until_stopped, args=(stop,))
thread.start()
try:
    sleep(1.0)
finally:
    stop.set()
    thread.join()
~~~

The undefined <code>perform_one_poll</code> represents application work and is deliberately a forward dependency of the example rather than executable standalone code; its minimal definition is “perform one bounded-duration polling attempt”. The timed event wait combines delay and prompt stop response. If one poll can block forever, the join can still block forever.

A semaphore limits simultaneous entries but does not create resources. If a connection pool contains ten connections, a semaphore of ten can guard checkout; release must occur in <code>finally</code> or a context manager.

A barrier is reusable after all parties pass unless it becomes broken through timeout, reset, abort, or failed barrier action under its specific contract. Barrier counts must include exactly the participating threads; a worker that exits early can strand peers.

> **Common misconception 14.17 — “An event records how many signals occurred.”**  
> A basic event records a Boolean level. Several <code>set()</code> calls before <code>clear()</code> collapse into one set state; use a queue or counter when multiplicity matters.

### 14.4.4 Thread-local and context-local state

**Thread-local storage** gives each thread a separate attribute namespace through one shared <code>threading.local</code> object. It can hold per-thread caches or legacy request context, but values follow operating-system worker threads, not logical tasks.

Thread pools reuse workers. State left in a worker-local object by one submitted request can be observed by a later request on that worker unless explicitly reset. This makes thread-local state unsuitable for implicit security identity without a disciplined lifecycle.

**Context variables**, from <code>contextvars</code>, attach state to the current logical context and integrate with <code>asyncio</code> task context propagation. <code>asyncio.to_thread</code> propagates the current context to the worker call in Python 3.12. Ordinary manually created threads have version/build-dependent context inheritance rules in newer free-threaded configurations, so explicit context policy is preferable when behaviour matters.

~~~python
from contextvars import ContextVar

request_id: ContextVar[str | None] = ContextVar(
    "request_id",
    default=None,
)


def process_request(identifier: str) -> None:
    token = request_id.set(identifier)
    try:
        handle_request()
    finally:
        request_id.reset(token)
~~~

The undefined <code>handle_request</code> means “perform the request operation”. Resetting with the token restores the prior nested context rather than blindly assigning <code>None</code>.

> **Common misconception 14.18 — “Thread-local state is local to one request.”**  
> It is local to a worker thread, whose lifetime can span many requests. Logical request context needs explicit setup/reset or context-aware propagation.

### 14.4.5 Thread testing and observability

Sleep-based tests are fragile: delay does not prove another thread reached a desired state, and a duration sufficient on one machine may fail under load. Coordinate a test with events and barriers to place activities at meaningful protocol points.

~~~python
from threading import Barrier, Thread


def run_simultaneously(
    left_action: Callable[[], None],
    right_action: Callable[[], None],
) -> None:
    start = Barrier(3)

    def wrapped(action: Callable[[], None]) -> None:
        start.wait()
        action()

    left = Thread(target=wrapped, args=(left_action,))
    right = Thread(target=wrapped, args=(right_action,))
    left.start()
    right.start()
    start.wait()
    left.join()
    right.join()
~~~

This increases overlap opportunity but does not enumerate all schedules or prove race freedom. Deterministic model testing, repeated stress, build variants, and runtime race detectors in native components provide complementary evidence.

Thread names, native identifiers, queue depths, wait durations, and lock-contention metrics assist diagnosis. Logs must include causal identifiers without assuming print order equals semantic order; output buffering and logging locks can alter schedules.

> **Common misconception 14.19 — “A concurrency test that passes repeatedly proves the absence of races.”**  
> Testing samples schedules. Proof, synchronisation design, systematic schedule exploration, and specialised tooling are needed to cover behaviours rare or impossible to induce by sleeping.
