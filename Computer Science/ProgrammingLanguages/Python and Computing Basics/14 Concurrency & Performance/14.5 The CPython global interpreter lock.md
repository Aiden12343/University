# 14.5 The CPython global interpreter lock

In a conventional GIL-enabled CPython build, the **global interpreter lock** (**GIL**) permits only one thread at a time to execute Python bytecode within one interpreter. Threads still overlap, and native code or blocking I/O can release the GIL. The GIL simplifies parts of CPython’s internal memory management; it is not a language requirement and not a general program lock.

Consequences:

- CPU-bound pure Python threads usually do not execute Python bytecode in parallel within one conventional interpreter.
- I/O-bound threads can make progress while another waits and releases the GIL.
- native libraries can perform parallel work outside the GIL under their contracts.
- the GIL does not make compound Python operations transactionally safe.
- multiple processes have separate interpreters and can use separate cores.

Modern CPython also provides **free-threaded builds** in which the global lock can be disabled. These builds permit parallel execution of Python code but require thread-safe extension compatibility and introduce different performance trade-offs. Some extensions may cause the GIL to be enabled or may not support the configuration. Code must use proper synchronisation in both modes; relying on accidental serialisation in a GIL-enabled build is not a portable concurrency design.

Python language semantics define results and permitted behaviour, not one global-lock strategy. “Python has a GIL” is therefore too broad; conventional CPython builds have one, while other implementations and free-threaded configurations differ.

### Worked example 14.2 — Why the GIL does not protect a transaction

```python
if key not in cache:
    cache[key] = build_value(key)
```

Even in a GIL-enabled build, scheduling or GIL release can occur across operations, and `key` hashing/equality or `build_value` can execute arbitrary code. Two threads can both observe absence and both build, with one result replacing the other. If duplicate work or effects are invalid, protect the whole transition or use an interface designed for once-only initialisation.

Conversely, wrapping every dictionary read in a lock “because dictionaries are unsafe” may impose needless contention. State the compound invariant and consult the runtime/build contract for the exact operation.

### 14.5.1 What the conventional GIL serialises

A running CPython thread that executes Python code has an attached **thread state**. In the conventional build, it must hold the GIL to interact with most Python objects and execute interpreter instructions. The runtime periodically considers switching, and blocking native operations commonly detach thread state and release the GIL.

“One thread executes Python bytecode at a time” is an explanatory approximation, not a source-level atomicity contract. A single expression can span several interpreter instructions; one instruction can invoke arbitrary Python methods; native code can release the lock; signals and finalisation can run at defined checkpoints; implementation details evolve. Chapter 15 will replace the bytecode simplification with the evaluator and thread-state model.

The switching interval exposed by <code>sys.getswitchinterval()</code> is an implementation scheduling parameter measured in seconds. It is not a promise that a switch occurs at exactly that interval, and changing it is not a correctness mechanism.

~~~python
import sys

print(sys.implementation.name)
print(sys.version)
print(sys.getswitchinterval())
~~~

Concurrency documentation should record the complete implementation and build, not just “Python 3”. CPython, PyPy, Jython, and other implementations may have different execution and memory-management constraints.

> **Common misconception 14.20 — “The GIL locks my Python objects.”**  
> It coordinates conventional CPython interpreter execution. It neither identifies application invariants nor replaces locks around multi-operation transactions.

### 14.5.2 Operations that release the GIL

Native code may release the GIL while it performs blocking I/O or long computation that does not touch Python objects. This permits another Python thread to execute. Whether a particular library operation releases it, and for what input sizes, is a versioned implementation/library fact.

Hash functions, compression libraries, regular-expression engines, database drivers, and numerical kernels differ. A CPU-heavy function implemented in C can scale across Python threads if it releases the GIL, while another C function can monopolise it. “CPU-bound means use processes” is therefore an initial heuristic for pure Python, not a universal rule.

An extension typically surrounds a safe native region with thread-state/GIL release and restoration. It must not use Python C API objects in the detached region unless the relevant API explicitly permits it. Blocking while holding the GIL unnecessarily prevents other Python threads in that interpreter from advancing.

Oversubscription can arise when each Python worker calls a native library that starts its own thread pool. Four Python threads each requesting eight native threads can create 32 runnable threads on an eight-core host. Control both layers and measure CPU, memory bandwidth, and latency.

> **Common misconception 14.21 — “C extensions always bypass the GIL.”**  
> An extension can release it around selected safe work, retain it throughout, or manage its own threads. The extension’s documented and measured behaviour decides.

### 14.5.3 Free-threaded CPython

CPython 3.13 introduced an optional free-threaded build under PEP 703. PEP 779 moved the free-threaded build to an officially supported but still optional phase for Python 3.14; it is not the default build. The status and exact overhead are version-dependent.

Free-threaded execution permits Python threads to run on several cores, but removing one global lock requires other mechanisms:

- internal container locks and critical sections;
- biased, deferred, and per-thread reference-counting techniques;
- immortalisation of selected shared objects;
- safe memory reclamation;
- extension declarations and thread-safe C API use.

These are CPython implementation facts, not new language-level transaction guarantees. Official 3.14 guidance explicitly recommends application synchronisation instead of relying on built-in container internal locks and warns that concurrent modification behaviour has not historically been a stable Python guarantee.

A free-threaded build can run with the GIL enabled, and importing an extension that has not declared free-threading support can cause the GIL to be enabled with a warning. On current builds, configuration and runtime state can be inspected:

~~~python
import sys
import sysconfig


def concurrency_build_report() -> dict[str, object]:
    report: dict[str, object] = {
        "implementation": sys.implementation.name,
        "version": sys.version,
        "free_threaded_capable": (
            sysconfig.get_config_var("Py_GIL_DISABLED") == 1
        ),
    }
    checker = getattr(sys, "_is_gil_enabled", None)
    report["gil_enabled"] = (
        checker() if checker is not None else "not exposed"
    )
    return report
~~~

The underscored <code>sys._is_gil_enabled</code> name signals a non-public-style API surface despite being documented for this purpose in the free-threading HOWTO; version guards remain appropriate. <code>Py_GIL_DISABLED</code> describes build capability, while runtime GIL state answers a different question.

Free-threaded builds can impose single-thread overhead and different memory behaviour. Parallel speedup depends on sharing patterns, object allocation, container contention, native extensions, and hardware. A codebase must be correct under actual parallel interleavings before performance becomes relevant.

> **Common misconception 14.22 — “Installing free-threaded Python makes every threaded program faster.”**  
> It enables parallel interpreter execution. Serial workloads can pay overhead, contended programs can scale poorly, and incompatible extensions can re-enable the GIL.

### 14.5.4 Per-interpreter GIL and isolation

PEP 684 placed a GIL in each subinterpreter in CPython 3.12’s C API architecture. Separate interpreters in one process can therefore support parallel interpreter execution when isolation requirements are met. This is distinct from disabling the GIL in one interpreter.

Subinterpreters have separate runtime state but share a process and some low-level resources. Extension modules written around process-global mutable state may be unsafe or unable to load in isolated interpreters. Data crossing interpreters needs a supported shareable representation or communication mechanism.

The model occupies a middle ground:

- threads in one conventional interpreter share objects cheaply but contend on one GIL;
- isolated interpreters separate interpreter state within one process;
- processes supply operating-system address-space isolation at higher transfer/startup cost;
- free-threaded one-interpreter execution permits object sharing with explicit parallel safety obligations.

Select by semantics and ecosystem support, not solely by core count.

> **Common misconception 14.23 — “Per-interpreter GIL and no-GIL CPython are the same design.”**  
> One supplies separate locked interpreters; the other permits parallel threads within a free-threaded interpreter. Their sharing and extension constraints differ.

### 14.5.5 Portability rule

Treat every concurrency claim as one of:

- **language/library guarantee:** documented behaviour of a synchronisation API;
- **CPython conventional-build fact:** current GIL-enabled implementation behaviour;
- **CPython free-threaded fact:** current optional-build mechanism or limitation;
- **extension/library fact:** whether native work releases locks or uses internal parallelism;
- **empirical result:** scaling observed on a named build and machine.

Never use an implementation accident as the sole synchronisation protocol. Code that “works because list append is atomic” has no declared application invariant, no compound-operation guarantee, and no portability across evolving free-threaded semantics. Use a queue, lock, immutable snapshot, or documented atomic API that states the intended relation.

> **Common misconception 14.24 — “Code that is safe on today’s GIL-enabled CPython is thread-safe Python.”**  
> Thread safety is a contract over permitted executions. Accidental serialisation in one implementation/build is not a portable contract and may disappear when operations, extensions, or builds change.
