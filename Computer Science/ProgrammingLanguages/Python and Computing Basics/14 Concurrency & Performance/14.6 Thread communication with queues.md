# 14.6 Thread communication with queues

Message passing transfers ownership through a synchronised channel instead of permitting arbitrary shared mutation.

```python
from queue import Queue
from threading import Thread


def worker(tasks: Queue[int | None], results: Queue[int]) -> None:
    while True:
        task = tasks.get()
        try:
            if task is None:
                return
            results.put(task * task)
        finally:
            tasks.task_done()


tasks: Queue[int | None] = Queue()
results: Queue[int] = Queue()
thread = Thread(target=worker, args=(tasks, results))
thread.start()

for value in range(3):
    tasks.put(value)
tasks.put(None)
tasks.join()
thread.join()
```

`None` is a **sentinel message** requesting termination. It is safe only because ordinary tasks are integers and `None` is outside that domain. `task_done` must correspond to every successful `get`, including the sentinel, so queue completion accounting reaches zero.

This example still needs failure transport: an exception in the worker would terminate the thread and can leave the main thread waiting. Executors capture exceptions in futures; custom worker protocols should return tagged outcomes or otherwise notify the owner and ensure shutdown.

### 14.6.1 Queue state and completion accounting

Python’s synchronous <code>queue.Queue</code> coordinates threads and can bound buffered items. Its conceptual counters differ:

- queue size counts items currently awaiting <code>get</code>;
- unfinished-task count increases on each <code>put</code>;
- <code>task_done</code> decreases unfinished count;
- <code>join</code> waits until unfinished count reaches zero.

An item removed by <code>get</code> is no longer in queue size but remains unfinished until acknowledged. Calling <code>task_done</code> too many times raises; omitting it can make <code>join</code> wait indefinitely.

Approximate size methods such as <code>qsize</code>, <code>empty</code>, and <code>full</code> are observations that can become obsolete immediately. This is another check–then–act boundary:

~~~python
if not tasks.empty():
    task = tasks.get()
~~~

Another consumer can remove the final item between calls. Use blocking or non-blocking <code>get</code> and handle its documented result directly.

> **Common misconception 14.25 — “<code>Queue.join()</code> waits for worker threads to exit.”**  
> It waits for completion acknowledgements corresponding to queued items. Thread termination requires separate joins.

### 14.6.2 One sentinel per independent consumer

A single sentinel terminates one consumer. If \(w\) workers each independently remove messages and exit on a sentinel, enqueue \(w\) sentinels or implement a coordinated close protocol.

Re-enqueuing one sentinel after seeing it can eventually notify all workers but complicates unfinished-task accounting, ordering, and failure cases. Explicit multiplicity is easier to prove when worker count is fixed.

Use a unique object when the ordinary domain may contain <code>None</code>:

~~~python
from queue import Queue
from threading import Thread
from typing import Final

STOP: Final = object()


def consume(
    tasks: Queue[int | object],
    results: Queue[int],
) -> None:
    while True:
        message = tasks.get()
        try:
            if message is STOP:
                return
            assert isinstance(message, int)
            results.put(message * message)
        finally:
            tasks.task_done()


worker_count = 4
tasks: Queue[int | object] = Queue(maxsize=32)
results: Queue[int] = Queue()
workers = [
    Thread(target=consume, args=(tasks, results))
    for _ in range(worker_count)
]
for worker in workers:
    worker.start()

for value in range(100):
    tasks.put(value)
for _ in workers:
    tasks.put(STOP)

tasks.join()
for worker in workers:
    worker.join()
~~~

The <code>assert</code> narrows a dynamically broad queue annotation but is not an input-validation policy for hostile messages. A typed tagged union would represent work and stop variants more explicitly.

Sentinels placed after all tasks in a FIFO queue ensure earlier tasks are taken before shutdown messages. They do not ensure every result has been consumed or persisted. That is a separate pipeline stage.

> **Common misconception 14.26 — “One stop sentinel shuts down a worker pool.”**  
> One queue item is consumed once. Every independently blocking consumer needs a termination path, and sentinel acknowledgement must match completion accounting.

### 14.6.3 Failure must travel to an owner

The worker above still loses an exception after acknowledging its failed item. A tagged outcome preserves request identity and error:

~~~python
from dataclasses import dataclass


@dataclass(frozen=True)
class Work:
    identifier: int
    value: int


@dataclass(frozen=True)
class Success:
    identifier: int
    value: int


@dataclass(frozen=True)
class Failure:
    identifier: int
    error: BaseException


Outcome = Success | Failure


def calculate(work: Work) -> Success:
    if work.value < 0:
        raise ValueError("negative input")
    return Success(work.identifier, work.value * work.value)
~~~

A worker can catch <code>Exception</code>, construct <code>Failure</code>, and place it on a result queue. Catching <code>BaseException</code> indiscriminately would also capture process-exit and keyboard-interrupt classes whose policy differs. Transferring exception objects between processes may fail serialisation; an explicit error record is safer there.

The owner must decide whether one failure:

- fails only that item;
- stops admission but drains accepted work;
- cancels every remaining item;
- triggers retry under an idempotency key;
- terminates and reconstructs the whole batch.

Silently logging inside a worker and continuing is a policy, often a dangerous accidental one.

> **Common misconception 14.27 — “An exception in a background worker automatically fails the main operation.”**  
> Raw worker exceptions occur in that activity. They affect the owner only through a future, result channel, exception hook, supervision protocol, or explicit observation.

### 14.6.4 Shutdown is a protocol

Graceful shutdown normally has phases:

1. stop accepting new work;
2. signal or close producers;
3. decide whether queued work drains or is discarded;
4. request worker termination;
5. acknowledge every accepted item according to policy;
6. join workers;
7. flush or commit owned outputs;
8. report incomplete and failed work.

Order matters. Joining consumers before sending stop signals waits forever. Sending stops while producers remain able to enqueue can leave work behind the sentinels. Closing a result consumer before workers finish can block workers on a full results queue.

Python versions after 3.12 add evolving queue shutdown APIs, but this treatise’s Python 3.12 baseline uses explicit sentinels and state. When targeting a later version, consult that exact version’s queue contract rather than retrofitting newer methods into 3.12 examples.

> **Common misconception 14.28 — “Putting sentinels in <code>finally</code> makes shutdown correct.”**  
> Placement alone does not order producers, queued work, result drainage, acknowledgements, and joins. Shutdown needs an end-to-end state transition.
