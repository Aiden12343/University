# 14.7 Processes

A **process** has an isolated address space and operating-system-managed resources. The `multiprocessing` module and `ProcessPoolExecutor` create or manage worker processes. Processes can execute Python code on several CPU cores without sharing one interpreter GIL.

Isolation changes communication. Arguments and results are commonly serialised and transferred; large objects incur copying or inter-process communication cost. Shared memory is possible but restores synchronisation obligations. Process startup is more expensive than a function call or thread creation and varies by platform and start method.

```python
from concurrent.futures import ProcessPoolExecutor


def sum_squares(limit: int) -> int:
    return sum(number * number for number in range(limit))


def main() -> None:
    limits = [2_000_000] * 4
    with ProcessPoolExecutor() as executor:
        results = list(executor.map(sum_squares, limits))
    print(results)


if __name__ == "__main__":
    main()
```

The entry guard is essential for safe worker startup under methods that import the main module. Callable and argument transfer ordinarily requires picklable representations. Nested functions, open sockets, locks, and huge object graphs may not transfer as intended.

Process parallelism helps only when useful computation exceeds startup, serialisation, transfer, scheduling, and result-combination costs. Amdahl’s law bounds speedup when a fraction remains serial. If fraction (s) is inherently serial and the rest is perfectly parallel over (p) processors, ideal speedup is

\[
\frac{1}{s+(1-s)/p}.
\]

With (s=0.1), even unlimited processors approach speedup 10, before overhead.

### 14.7.1 Start methods are semantic choices

The principal multiprocessing start methods are:

- **spawn:** start a fresh interpreter process and import the main module;
- **fork:** clone the calling process through the operating system’s fork facility;
- **forkserver:** ask a dedicated, comparatively controlled server process to fork workers.

Availability and defaults vary by platform and Python version. Python 3.12 code should not infer one universal default; later releases have changed defaults on some platforms. Select an explicit context when correctness or reproducibility depends on it:

~~~python
from concurrent.futures import ProcessPoolExecutor
from multiprocessing import get_context


def cube(value: int) -> int:
    return value**3


def main() -> None:
    context = get_context("spawn")
    with ProcessPoolExecutor(mp_context=context) as executor:
        print(list(executor.map(cube, range(8))))


if __name__ == "__main__":
    main()
~~~

Spawn requires the main module to be safely importable and worker callables/arguments to be transferable. Top-level function definitions satisfy ordinary pickling/import lookup; a lambda or nested closure generally does not.

Fork inherits a snapshot of process memory and execution context, including locks and native-library state. If another thread held a lock at fork, the child may inherit the locked state without the owning thread. Forking a multi-threaded runtime is therefore hazardous unless every involved library documents safety. “It is faster” is not a semantic justification.

Forkserver and spawn reduce inherited-state hazards at the cost of startup and transfer. The correct choice depends on platform, libraries, worker lifetime, and data distribution.

> **Common misconception 14.29 — “Multiprocessing behaves the same on Linux, macOS, and Windows.”**  
> Start-method availability, defaults, inheritance, import, signal, and startup behaviour differ. Select and test the target context explicitly where semantics matter.

### 14.7.2 Serialisation defines the process boundary

Process-pool submissions commonly pickle a callable reference and arguments. Pickle reconstructs a representation in the worker; it does not transfer a live closure, file descriptor, lock ownership, database transaction, or arbitrary interpreter state as such.

Transfer cost can dominate:

\[
T_{\text{parallel}}
=T_{\text{start}}
+T_{\text{serialise}}
+T_{\text{copy/IPC}}
+T_{\text{compute}}
+T_{\text{return}}
+T_{\text{coordination}}.
\]

If a task computes for 10 microseconds but needs 1 millisecond of submission and transfer, distributing each item increases time. **Chunking** groups several logical items per submission:

~~~python
def sum_square_chunk(values: list[int]) -> int:
    return sum(value * value for value in values)
~~~

The owner partitions input, submits chunks, and combines partial sums. Larger chunks amortise transfer but reduce load balance and delay first results. Optimal granularity is empirical under a stated distribution.

Pickle is executable deserialisation and must not be used for untrusted bytes, as established in Chapter 11. Process-pool communication is ordinarily trusted within the application boundary, but compromised or multi-tenant peers change the threat model.

> **Common misconception 14.30 — “A process pool sends Python objects to workers.”**  
> It sends a serialised representation or supported shared handle from which workers reconstruct or access state. Identity, aliases, open resources, and custom reduction behaviour may change.

### 14.7.3 Amdahl, Gustafson, and overhead

Amdahl’s law fixes total problem size and asks how much a serial fraction limits speedup:

\[
S_p=\frac{1}{s+(1-s)/p}.
\]

Parallel efficiency is \(E_p=S_p/p\). With \(s=0.05\) and \(p=8\), ideal speedup is approximately 5.93 and efficiency about 0.74 before overhead.

Gustafson’s law asks a different question: if elapsed time is fixed while problem size grows with processor count, scaled speedup is

\[
S_p=p-s(p-1).
\]

The laws do not contradict one another; they hold different quantities fixed. Neither includes communication, imbalance, memory bandwidth, synchronisation, or scheduler overhead unless those are incorporated into \(s\) or an extended model.

**Strong scaling** measures time for a fixed problem as processors increase. **Weak scaling** increases problem size with processors, usually holding work per processor roughly constant. Report which experiment is performed.

> **Common misconception 14.31 — “Amdahl’s law says parallel computing is pointless.”**  
> It quantifies fixed-size serial limits. Larger problems, reduced serial work, pipeline overlap, and different scaling questions can still justify parallel systems.

### 14.7.4 Pool lifecycle and broken workers

A process future can fail because the function raised, argument/result serialisation failed, a worker terminated abruptly, or the pool itself became unusable. These causes have different retry safety.

<code>ProcessPoolExecutor</code> owns a finite worker set. Its context-manager exit waits for submitted work by default. Long-running services may recycle workers to limit accumulated state where supported, but recycling increases startup cost and interacts with start methods.

Workers should not recursively submit to and wait on the same process executor. The official contract warns that calling executor/future methods from a callable submitted to a <code>ProcessPoolExecutor</code> can deadlock. Keep orchestration with the owner unless a separately provisioned hierarchy is proved.

Abruptly terminating a process can leave:

- locks held in shared memory;
- queue pipes containing partial protocol data;
- temporary files;
- external transactions;
- duplicate side effects after retry.

Process isolation contains memory corruption better than threads but does not automatically roll back external effects.

> **Common misconception 14.32 — “If a worker process crashes, only its calculation is lost.”**  
> It may own shared synchronisation, IPC writes, files, or external effects. Supervision needs failure classification, cleanup, and idempotent replay boundaries.

### 14.7.5 CPU affinity, topology, and oversubscription

An operating system may schedule workers across logical CPUs. Logical CPU count can exceed physical core count through simultaneous multithreading; sockets and non-uniform memory access place memory at different distances from cores.

CPU affinity can reduce migration or isolate workloads, but it can also prevent load balancing and is platform-specific. Cache hierarchy and memory bandwidth often limit parallel numeric speedup before arithmetic units are saturated.

A process pool default worker count is an API policy, not knowledge of the application’s complete parallelism. Native libraries called inside each process may create threads. Containers and job schedulers may constrain usable CPUs differently from host-reported counts. Measure effective allocations and configure all layers.

> **Common misconception 14.33 — “Use one process per reported CPU.”**  
> Reported logical CPUs, allocated CPUs, physical cores, memory capacity, nested native threads, workload balance, and external bottlenecks all affect an appropriate worker bound.
