# 14.8 Inter-process state and consistency

Processes do not observe ordinary mutations to each other’s independent Python heaps. After a fork-like creation mechanism, memory may initially share physical pages through copy-on-write, but later writes produce process-private state. Other start methods construct workers through fresh interpreter startup.

Use explicit communication:

- pipes and queues for messages;
- sockets for local or network protocols;
- shared memory for array-like data under coordination;
- databases or files under transaction/locking protocols;
- manager proxies when their extra server/serialisation behaviour is appropriate.

Never infer a universal start method or inherited state across platforms and Python versions. Select or document one where semantics matter, place process creation behind the main guard, and test in the target environment.

### 14.8.1 Copy-on-write is neither copying nor ordinary sharing

After a fork on supporting systems, parent and child virtual address spaces may initially map the same physical pages read-only. On a write, the operating system copies an affected page for the writer. This **copy-on-write** mechanism can make startup appear memory-efficient when large state remains read-only.

The optimisation is page-granular. Reference-count updates, allocator metadata, garbage collection, or seemingly small object mutations can dirty pages and erode sharing. Operating-system resident-set figures can double-count shared pages depending on the metric. Spawn does not inherit the same address-space snapshot.

Treat inherited objects as logically private unless an explicit shared-memory or external coordination mechanism says otherwise. A child appending to an inherited list does not update the parent’s list.

> **Common misconception 14.34 — “Forked processes share Python objects until one changes the object.”**  
> They have separate virtual object states. Copy-on-write may share physical pages temporarily, and many runtime writes besides obvious application mutation can break that sharing.

### 14.8.2 Shared memory needs a representation and protocol

Shared memory exposes bytes or fixed representations to several processes without serialising a full copy on every access. It does not supply type invariants, exclusive ownership, visibility protocol, or lifetime cleanup by itself.

~~~python
from multiprocessing import get_context
from multiprocessing.shared_memory import SharedMemory


def fill(shared_name: str, size: int) -> None:
    segment = SharedMemory(name=shared_name)
    try:
        for index in range(size):
            segment.buf[index] = index % 256
    finally:
        segment.close()


def main() -> None:
    size = 1_000
    segment = SharedMemory(create=True, size=size)
    try:
        context = get_context("spawn")
        worker = context.Process(
            target=fill,
            args=(segment.name, size),
        )
        worker.start()
        worker.join()
        if worker.exitcode != 0:
            raise RuntimeError("worker failed")
        assert segment.buf[17] == 17
    finally:
        segment.close()
        segment.unlink()


if __name__ == "__main__":
    main()
~~~

The join establishes process completion before the parent reads in this simple protocol. <code>close</code> releases each process’s handle; <code>unlink</code> requests destruction of the named segment under platform rules. A crash can leak named resources, motivating a resource tracker or external cleanup.

If producer and consumer operate simultaneously, they need a readiness flag, lock, semaphore, atomic index, immutable slot ownership, or another protocol. Writing a multi-byte record can expose partial data. Packed arrays must agree on byte order, alignment, element width, shape, and bounds.

False sharing occurs when independent frequently written values occupy one cache line, causing cores to exchange coherence ownership despite no logical sharing. Padding or partitioning can improve performance, but hardware-specific measurement is required.

> **Common misconception 14.35 — “Shared memory removes inter-process communication.”**  
> It changes payload transfer into coordinated access to common bytes. Metadata, readiness, ownership, consistency, and cleanup still require communication.

### 14.8.3 Managers, files, and transactional stores

A multiprocessing manager commonly hosts objects in a server process and exposes proxies. A method call on a proxy may serialise a request, cross IPC, execute remotely, and serialise a response. Syntax resembling a local list does not imply local-operation cost or compound atomicity.

For durable state, a database can supply transactions, isolation levels, constraints, and crash recovery that memory locks do not. A unique constraint is stronger than “check absent, then insert” in each process. File locks vary by platform and advisory/mandatory semantics; atomic rename and exclusive creation solve narrower filesystem transitions.

Select the consistency model:

- **linearizable:** operations appear in real-time-consistent total order;
- **serializable:** transactions are equivalent to some serial order, not necessarily real-time order;
- **snapshot isolation:** reads observe a consistent snapshot with specified write-conflict rules;
- **eventual consistency:** replicas converge when updates cease, under stated conflict handling.

These terms belong to the external system contract. A Python <code>Lock</code> coordinates only participants sharing that lock object and does not create durable or distributed consensus.

> **Common misconception 14.36 — “A multiprocessing manager makes a normal container safely shared.”**  
> It supplies proxy-mediated operations. Each remote method has IPC cost, and sequences of methods still need a server-side transaction or explicit lock to preserve compound invariants.
