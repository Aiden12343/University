# 14.9 Asynchronous I/O

`asyncio` supports cooperative concurrency in an event loop. A **coroutine function** is defined with `async def`. Calling it creates a **coroutine object**; it does not execute the body to completion. An **awaitable** is an object that can be used with `await`. A **task** schedules a coroutine for event-loop execution and retains its outcome.

```python
import asyncio


async def pause_then(label: str, delay: float) -> str:
    await asyncio.sleep(delay)
    return label


async def main() -> None:
    first, second = await asyncio.gather(
        pause_then("A", 0.2),
        pause_then("B", 0.1),
    )
    print(first, second)


asyncio.run(main())
```

`asyncio.sleep` suspends the current task and lets the loop run other ready tasks. `gather` returns results in argument order, so output is `A B` even though B’s delay completes first.

Cooperative scheduling means a task runs until it awaits, returns, raises, or otherwise yields control through event-loop machinery. A blocking system call or CPU-heavy loop inside an async function blocks the event-loop thread and delays all other tasks.

> **Common misconception — “`async def` makes code run in the background.”**  
> Calling creates a coroutine object. It runs only when awaited or scheduled by an event loop. CPU work remains ordinary work and can block the loop.

### 14.9.1 Coroutine functions, objects, and suspension

Calling an ordinary function executes its body until it returns or raises. Calling a coroutine function creates a coroutine object; execution begins when an event loop drives it through awaiting or task scheduling. A coroutine retains suspended frame state across awaits.

<code>await expression</code> does not mean “the operating system performs this asynchronously”. The expression must produce an awaitable whose protocol eventually yields control. Awaiting a coroutine that performs a blocking socket call before its first genuine suspension still blocks the event-loop thread.

~~~python
import asyncio
import time


async def wrongly_blocking() -> None:
    time.sleep(1.0)


async def cooperatively_waiting() -> None:
    await asyncio.sleep(1.0)
~~~

Both functions have <code>async def</code> syntax. The first calls synchronous sleep and prevents the loop thread from servicing other tasks for approximately a second. The second registers a timer and suspends, allowing other ready callbacks to run.

An await is also a control-flow and failure boundary. By the time execution resumes:

- other tasks may have changed shared state;
- cancellation may have been injected;
- the awaited operation may return or raise;
- a deadline may have expired;
- context-local state follows its propagation rules.

Do not hold a thread lock across an await. The event-loop thread can block trying to reacquire it for another task while the owner is suspended waiting for work that now cannot run. <code>asyncio</code> synchronisation primitives suspend tasks instead of blocking the loop thread, but they are not thread-safe and solve event-loop task coordination rather than cross-thread locking.

> **Common misconception 14.37 — “Every <code>await</code> yields control immediately.”**  
> An awaitable may complete synchronously without suspension, and code before its first actual suspension runs in the current turn. Correctness must not depend on an await forcing a scheduling point.

### 14.9.2 Event-loop mechanics

An event loop maintains sources of future readiness:

- callbacks ready to run;
- timers ordered by deadline;
- operating-system I/O readiness registrations;
- completed futures and tasks;
- thread-safe notifications from other threads;
- signals on supporting platforms.

It repeatedly waits for external events when nothing is ready, marks callbacks ready, and executes ready callbacks. The precise ordering and batching policy is an implementation contract, not a fairness theorem.

Readiness is not completion. A readable socket means an attempted read can make progress; it does not guarantee the complete application message has arrived. Protocols need framing and partial-transfer handling. A writable socket means buffer space is available, not that the remote peer received durable data.

Timers use the loop’s monotonic clock, not wall-clock civil time. Wall time can jump because of synchronisation or administrative change; elapsed deadlines need a monotonic source.

~~~python
import asyncio


async def delay_until(deadline: float) -> None:
    loop = asyncio.get_running_loop()
    remaining = deadline - loop.time()
    if remaining > 0:
        await asyncio.sleep(remaining)
~~~

Even after the timer becomes eligible, overload can delay execution. A deadline is an earliest scheduling eligibility or cancellation policy, not an exact real-time execution guarantee.

> **Common misconception 14.38 — “The event loop constantly checks every socket.”**  
> Implementations normally ask operating-system readiness mechanisms to report relevant events. Polling details are platform-specific, and readiness still requires protocol processing.

### 14.9.3 Tasks give coroutines concurrent lifetime

Sequential awaits do not overlap:

~~~python
async def sequential_pauses() -> tuple[str, str]:
    first = await pause_then("A", 0.2)
    second = await pause_then("B", 0.1)
    return first, second
~~~

The second call is not begun until the first completes. Creating tasks gives both coroutine executions a lifetime before awaiting their results:

~~~python
async def concurrent_pauses() -> tuple[str, str]:
    first_task = asyncio.create_task(pause_then("A", 0.2))
    second_task = asyncio.create_task(pause_then("B", 0.1))
    first = await first_task
    second = await second_task
    return first, second
~~~

The result variables retain chosen order even though completion order differs. <code>asyncio.gather</code> is a concise aggregation primitive, but its default failure behaviour in Python 3.12 differs from <code>TaskGroup</code>: the first propagated exception does not automatically cancel all other gather members.

Tasks need ownership. The event loop retains only weak references in relevant cases; keep a strong reference to fire-and-monitor tasks and consume their outcomes:

~~~python
background: set[asyncio.Task[None]] = set()


def start_background(coroutine) -> None:
    task = asyncio.create_task(coroutine)
    background.add(task)
    task.add_done_callback(background.discard)
~~~

This set prevents premature loss and removes finished tasks, but it still lacks exception observation. A production callback should call <code>task.exception()</code> under cancellation handling or route outcomes to supervision. Prefer structured task scopes whenever lifetime permits.

> **Common misconception 14.39 — “Calling several coroutine functions before awaiting them starts them concurrently.”**  
> Calls create coroutine objects. They acquire scheduled lifetime only when wrapped in tasks or passed to an API that schedules them.

### 14.9.4 Result order, completion order, and bounded fan-out

Three common collection policies differ:

- await each coroutine sequentially: no overlap;
- <code>gather</code>: overlap and return results in argument order;
- <code>as_completed</code>: consume next completed result.

Starting one task per element in an enormous input can create excessive task, socket, buffer, and remote load even if results are consumed incrementally. Completion-order iteration is not admission control.

~~~python
from collections.abc import Awaitable, Callable, Iterable
from typing import TypeVar

T = TypeVar("T")
R = TypeVar("R")


async def bounded_map(
    function: Callable[[T], Awaitable[R]],
    values: Iterable[T],
    *,
    concurrency: int,
) -> list[R]:
    if concurrency < 1:
        raise ValueError("concurrency must be positive")

    semaphore = asyncio.Semaphore(concurrency)

    async def invoke(index: int, value: T) -> tuple[int, R]:
        async with semaphore:
            return index, await function(value)

    tasks = [
        asyncio.create_task(invoke(index, value))
        for index, value in enumerate(values)
    ]
    completed = await asyncio.gather(*tasks)
    completed.sort(key=lambda pair: pair[0])
    return [result for _, result in completed]
~~~

The semaphore bounds simultaneous calls to <code>function</code> but the code still materialises every input and task. For an unbounded stream, use a bounded worker queue or rolling task window. It also inherits <code>gather</code> failure semantics; a <code>TaskGroup</code> version can give sibling-failure containment.

> **Common misconception 14.40 — “A semaphore around the network call bounds memory.”**  
> It bounds entries into one region. Creating all tasks and retaining all arguments/results can still consume memory proportional to total input.

### 14.9.5 Offloading blocking functions

<code>asyncio.to_thread</code> runs a synchronous callable in a worker thread and returns an awaitable for its result. In Python 3.12 it propagates the current <code>contextvars.Context</code>.

~~~python
from pathlib import Path


async def read_file(path: Path) -> bytes:
    return await asyncio.to_thread(path.read_bytes)
~~~

This prevents the file operation from blocking the event-loop thread; it does not make filesystem I/O natively asynchronous, make the function cancellable, or guarantee parallel pure-Python CPU speed in conventional CPython. If the awaiting task is cancelled, an already running thread callable ordinarily continues unless the callable has its own cooperative protocol.

Use a bounded, owned executor when offload volume matters. The default executor’s size and lifetime are implementation/library policy. Offloading thousands of calls can merely move an unbounded queue from the event loop to an executor.

CPU-bound Python can be delegated with <code>loop.run_in_executor</code> to a process pool, but arguments/results cross the process boundary and cancellation still cannot retract arbitrary already running side effects.

> **Common misconception 14.41 — “<code>to_thread</code> converts a blocking API into a cancellable async API.”**  
> It moves the blocking call off the loop thread. Cancellation of the await does not safely terminate an arbitrary running thread function.

### 14.9.6 Async resource lifetime and streams

Asynchronous context managers permit suspension during acquisition and release:

~~~python
async def fetch_in_session(client, request):
    async with client.session() as session:
        return await session.fetch(request)
~~~

The concrete client is intentionally abstract. Its contract must state connection ownership, response-body drainage, cancellation behaviour, and whether leaving the context waits for closure.

Async iterators model streams:

~~~python
async def consume_chunks(response) -> None:
    async for chunk in response.chunks():
        process(chunk)
~~~

If <code>process</code> is CPU-heavy or blocking, it stalls further I/O. If it stores every chunk, streaming syntax does not bound memory. Flow control requires awaiting writes/drains or placing a bounded stage between producer and consumer.

Finalisation should not depend solely on garbage collection. Tasks and transports can retain resources in cycles or until loop shutdown. Lexical <code>async with</code>, explicit <code>aclose</code>, and owned task groups make lifetime visible.

> **Common misconception 14.42 — “Using <code>async for</code> means data is processed in constant memory.”**  
> Iteration can be incremental, but the body, buffering layers, queued tasks, and retained results determine live memory.
