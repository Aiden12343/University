# 15.1 The capstone changes explanatory level

Python-language semantics specify what valid programs mean. CPython supplies one implementation of those semantics. This chapter descends into CPython to explain mechanisms behind source compilation, frames, bytecode, object representation, reference counting, and cyclic collection. Every implementation claim is version-scoped; none silently becomes a requirement imposed on PyPy, GraalPy, MicroPython, or a future CPython revision.

The correct question is not “what does Python really do?”, as though the language account were false. The language contract and the implementation mechanism answer different questions. Assignment really does bind names to objects at the language level; a particular CPython build realises local bindings through frame storage and reference management. Neither description replaces the other.

### 15.1.1 An explanatory ladder

One execution can be described at several levels:

| Level | Representative question | Evidence |
|:---|:---|:---|
| language semantics | What result or exception is required? | language reference and accepted PEPs |
| public Python interface | What may portable Python inspect? | library and data-model documentation |
| public CPython API | What may an extension or embedding application call? | versioned C API documentation |
| CPython mechanism | How does this build implement the contract? | source, internal documentation, tests, generated files |
| machine execution | Which instructions, cache misses, and system calls occurred? | compiler output, debugger, profiler, operating-system traces |
| experiment | What happened in this run? | reproducible observation with environment record |

An explanation is valid only within its level and stated domain. “Assignment binds a name” is a language statement. “A fast local occupies a slot in an interpreter frame” is a CPython mechanism statement. “This local was held in register R14 at this instant” is a machine observation for a particular compiled build. A lower level supplies a mechanism for a higher-level contract; it does not make the higher-level statement false.

Abstractions permit substitution. Python implementations can represent frames, integers, or garbage collection differently while satisfying the language contract. Even CPython can replace an internal structure between minor releases. Code that depends on an internal field has chosen a narrower platform than code depending on a public interface. That choice can be rational, but it must be explicit.

> **Common misconception 15.1 — “CPython internals reveal what Python really is.”**  
> Python semantics and CPython mechanisms are simultaneously real descriptions at different interfaces. Internal structure explains one implementation; it does not supersede the language contract.

### 15.1.2 Four classes of claim

Every claim in this chapter belongs to one of four classes:

1. a **language guarantee**, intended to hold across conforming implementations;
2. a **documented CPython interface**, supported for a stated version or ABI;
3. a **private CPython mechanism**, free to change unless promoted to a contract;
4. an **empirical observation**, dependent on the measured executable and environment.

The distinction prevents common category errors. The language permits immutable equal values to share identity, but does not require it. CPython commonly caches certain integers; this mechanism does not authorise numeric identity tests. The <code>dis</code> module documents how to inspect CPython bytecode, while also warning that bytecode itself can change between releases. An observed opcode sequence is evidence about a build, not syntax semantics.

Source code alone does not automatically define a public promise. A private helper can change without compatibility process. A comment can be incomplete. A test can encode an intended invariant, an incidental current output, or merely one regression case. Establish the relevant authority: specification, documented API, accepted design, source implementation, or experiment.

> **Common misconception 15.2 — “If behaviour appears in CPython source, user programs may rely on it.”**  
> Source establishes what that revision implements. Reliance requires a language or documented interface guarantee, or an explicit decision to target that exact mechanism.

### 15.1.3 Version, build, and platform form part of the object of study

“CPython 3.12” still leaves material variables:

- maintenance release and source commit;
- release, debug, or trace-reference build;
- compiler, optimisation and link-time settings;
- conventional or free-threaded configuration in versions supporting it;
- 32- or 64-bit word size and byte order;
- operating system and processor architecture;
- allocator selection and environment switches;
- extension modules capable of changing execution or memory behaviour.

Record an observation envelope:

~~~python
from __future__ import annotations

import json
import platform
import sys
import sysconfig


def implementation_report() -> dict[str, object]:
    return {
        "implementation": platform.python_implementation(),
        "version": sys.version,
        "hexversion": hex(sys.hexversion),
        "cache_tag": sys.implementation.cache_tag,
        "platform": platform.platform(),
        "machine": platform.machine(),
        "pointer_bits": 8 * (sys.maxsize.bit_length() // 8 + 1),
        "debug_build": hasattr(sys, "gettotalrefcount"),
        "gil_disabled_build": sysconfig.get_config_var("Py_GIL_DISABLED"),
        "compiler": platform.python_compiler(),
    }


if __name__ == "__main__":
    print(json.dumps(implementation_report(), indent=2))
~~~

The pointer-width calculation rounds the maximum signed index width to bytes and is an observation, not an ABI query. <code>sysconfig</code> values depend on build configuration. The absence of <code>gettotalrefcount</code> is a useful but not universal description of debug instrumentation. A scientific record also includes executable path, source revision if known, command, environment variables, input digest, and extension versions.

> **Common misconception 15.3 — “All installations with the same Python version have identical internals.”**  
> Build flags, compiler, platform, allocator, optional GIL mode, and extensions can alter layout, instrumentation, and performance while retaining the same language version.

### 15.1.4 The capstone’s method

For each mechanism, proceed from observation to explanation:

1. construct the smallest source example that distinguishes the question;
2. state the language-level expected result;
3. inspect through a public interface such as <code>ast</code>, <code>symtable</code>, <code>dis</code>, <code>inspect</code>, <code>gc</code>, or <code>weakref</code>;
4. identify the versioned CPython implementation path only as deeply as necessary;
5. trace success, failure, and lifetime ownership;
6. perturb one feature and predict the resulting observation;
7. report what remains unknown.

This method avoids reverse-engineering folklore from one output. Internals become a connected causal account: source structure guides compilation; code metadata guides evaluation; type objects supply protocols; ownership determines lifetime; external I/O crosses operating-system boundaries. The final integrated trace will join these without pretending one source line maps to one opcode, C function, or machine instruction.
