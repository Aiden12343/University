# 15.10 CPython object representation

At the C level, every ordinary CPython object begins with header information sufficient to identify its type and manage lifetime under the build configuration. Variable-sized objects include size information. The exact fields, layout, alignment, and free-threading changes belong to the CPython ABI/API version.

A Python reference in CPython C code is typically a pointer to `PyObject` or a more specific structure whose initial layout is compatible under the API. Type objects contain slots implementing operations such as call, number protocols, sequence behaviour, deallocation, traversal, and representation.

This explains dynamic dispatch: the implementation examines type-provided slots or method structures rather than compiling every source operator to one fixed machine operation.

### Small immutable object reuse

CPython may reuse selected immutable objects, including a documented implementation range or strategically interned strings. Example observations:

```python
a = 5
b = 5
print(a is b)
```

may print `True` in CPython. This is not a licence to use identity for numeric equality. Optimisation, compilation unit, REPL mode, implementation, and version can influence reuse. The language requires `a == b`, not shared identity.

It is inaccurate to say “5 is mutable because the name can change”. Rebinding `a = 6` changes the name’s referent; it does not mutate the integer object representing 5. Internal memory can be altered through unsupported native attacks, but violating implementation invariants does not redefine Python’s object mutability contract.

### 15.10.1 The common object header supplies identity, type, and lifetime machinery

At the source-compatible C API level, <code>PyObject</code> is the common prefix through which code handles an arbitrary Python object. A conventional build’s conceptual header includes a type pointer and reference-count state; debug, trace-reference, free-threaded, or future builds can add fields or encode lifetime differently. Client code must use API macros/functions rather than copy a remembered structure diagram.

A **type pointer** identifies the object’s runtime type object. A **reference-count field or state** participates in CPython lifetime management. Variable-sized built-in representations extend the conceptual prefix with a signed size field through <code>PyVarObject</code>. “Variable-sized” means the representation has a logical item count associated with its allocation; it does not assert that the object can be resized in place under Python semantics.

For example, a tuple is immutable to Python code but variable-sized at allocation because different tuples contain different numbers of element-reference slots. An integer has a variable-length magnitude representation because arbitrarily large values require different numbers of internal digits, even though integer objects are immutable.

~~~python
import sys


objects = [
    (),
    (None,),
    tuple(range(20)),
    0,
    2**1_000,
]

for value in objects:
    print(type(value).__name__, len(value) if isinstance(value, tuple) else value.bit_length(), sys.getsizeof(value))
~~~

<code>sys.getsizeof</code> reports the implementation-defined shallow size of the object, including garbage-collector overhead where the object reports it, but excluding separately allocated referents. It is useful for comparisons within a recorded build, not for deriving a universal structure layout.

The macro <code>Py_TYPE</code> retrieves type under the documented C API. <code>Py_REFCNT</code> exposes a count-like value but is unsuitable for deciding uniqueness, especially with immortal objects and free-threaded changes. <code>Py_SIZE</code> is valid only for APIs/types whose contracts permit it; treating arbitrary object memory as a chosen C struct violates type and aliasing invariants.

> **Common misconception 15.38 — “Every CPython object consists of exactly a reference count, a type pointer, and its value.”**  
> The common header is only a prefix model. Layout varies by object type, build mode, ABI, alignment, GC tracking, and release; payloads can include pointers to separate allocations and caches.

### 15.10.2 The type object is executable metadata

A Python class is ordinarily an instance of a metaclass, usually <code>type</code>. At the C level, a <code>PyTypeObject</code> describes instances through metadata and operation slots. Slots include construction, deallocation, call, representation, attribute access, numeric operations, sequence/mapping operations, traversal, finalisation, iteration, and descriptor behaviour. Not every slot is populated directly; inheritance and type readiness establish effective behaviour.

This is why an operator is not a tag-based switch over a small closed set. The evaluator obtains the operand types, applies slot-resolution rules, and lets those types participate. User-defined classes ultimately install slot wrappers based on special methods in the class namespace.

~~~python
class Distance:
    def __init__(self, metres: float) -> None:
        self.metres = metres

    def __add__(self, other: object) -> "Distance":
        if not isinstance(other, Distance):
            return NotImplemented
        return Distance(self.metres + other.metres)


left = Distance(1.5)
right = Distance(2.25)
combined = left + right
assert combined.metres == 3.75
assert type(combined) is Distance
assert type(Distance) is type
~~~

Looking up <code>left.__add__</code> in Python is useful for learning but not a faithful description of every operator’s internal lookup. Special-method lookup commonly proceeds on the type and bypasses ordinary instance attribute lookup so that protocol invariants and implicit invocation remain controlled. The slot wrapper can then call the Python-defined method.

A metaclass creates and governs class objects. When a class statement executes, its metaclass selection, namespace preparation, body execution, class construction, descriptor <code>__set_name__</code>, base-class initialisation hook, and decorators form a protocol. The result’s own type pointer is the chosen metaclass. Section 9’s statement that classes are objects is therefore literal in CPython’s object graph, not analogy.

### Worked example 15.11 — Distinguish instance, class, and metaclass lookup

~~~python
class Meta(type):
    category = "metaclass attribute"


class Example(metaclass=Meta):
    category = "class attribute"


instance = Example()

assert instance.category == "class attribute"
assert Example.category == "class attribute"
assert type(Example).category == "metaclass attribute"
assert isinstance(Example, Meta)
assert isinstance(instance, Example)
~~~

The same spelling occurs in two different namespaces. Attribute lookup rules decide which relationship is relevant; memory adjacency does not. A metaclass is not a superclass of ordinary instances: <code>Meta</code> is the type of <code>Example</code>, while <code>Example</code> is the type of <code>instance</code>.

> **Common misconception 15.39 — “Dunder methods are found by ordinary lookup on the instance every time an operator executes.”**  
> Implicit special-method invocation generally uses type slots and special lookup rules. Assigning a same-named callable only to one instance often does not alter the operator protocol.

### 15.10.3 Integers use a signed, variable-length representation

Python integers have arbitrary precision subject to available memory. CPython represents a magnitude as a sequence of base-(2^k) digits, with (k) selected by build configuration, and encodes sign/size information in the integer object’s structural state. Python 3.12 reorganised parts of the internal long-object representation and introduced compact-value helpers; extensions must not inspect private digit fields unless deliberately tied to that release’s internal API.

The logical cost of arithmetic therefore depends on operand magnitude. Addition of two machine-small integers can take a fast path; addition of (n)-digit magnitudes requires work proportional to (n) in the general case and may allocate a result. Multiplication selects algorithms based on size in implementation-specific thresholds. “Integer addition is one CPU add” is true only for a narrow specialised case, not the Python semantic operation.

~~~python
import sys


values = [0, 1, 2**30 - 1, 2**30, 2**300, -(2**300)]

for value in values:
    print(value.bit_length(), sys.getsizeof(value))
~~~

Size transitions reveal implementation allocation steps but should not be used to infer the internal digit base without checking the build. Negative values share magnitude-scale behaviour while their mathematical bit operations follow the language’s infinite two’s-complement model, regardless of the sign-magnitude-like storage mechanism.

CPython reuses a set of small integer objects and may fold or share other integer constants. The range commonly documented for the internal cache is an implementation fact and can be expanded in specialised builds. Equality is numeric; identity remains an object-lifetime question.

> **Common misconception 15.40 — “Python integers are always machine words, so their operations have constant cost and overflow normally.”**  
> CPython integers grow across multiple internal digits and do not silently wrap. Time and storage scale with magnitude, and fixed-width behaviour requires an explicit representation such as an array or C integer type.

### 15.10.4 Unicode strings choose a representation compatible with their contents

PEP 393 introduced CPython’s flexible string representation. A string has one logical sequence of Unicode code points, while its internal storage can use one-, two-, or four-byte code units depending on the maximum code point and representation state. ASCII strings receive especially compact handling. Internal canonical data, cached hash, optional UTF-8/legacy views, and interning state are implementation mechanisms, not separate Python string values.

### Worked example 15.12 — Shallow sizes reflect representation thresholds

~~~python
import sys


samples = {
    "ascii": "a" * 20,
    "latin": "é" * 20,
    "bmp": "λ" * 20,
    "astral": "😀" * 20,
}

for label, text in samples.items():
    print(label, len(text), len(text.encode("utf-8")), sys.getsizeof(text))
~~~

<code>len</code> counts Unicode code points, not UTF-8 bytes or user-perceived grapheme clusters. The encoded byte length follows UTF-8. The shallow CPython size reflects headers, storage kind, terminators/alignment, and build policy. It should be recorded rather than predicted as a portable formula.

String hashes are cached after computation in conventional CPython. Hash randomisation means values can differ between processes; cache presence does not make hashes stable persistent identifiers. Interning can let selected equal strings share an object, improving lookup or comparison paths, but code must still use <code>==</code> for textual equality.

Concatenation produces a string value and can require allocation/copying proportional to lengths. CPython has narrow optimisations for selected temporary concatenations, but repeated construction should use <code>str.join</code> or streaming when the algorithmic contract demands predictable linear work. Internal width can widen if one high code point enters the result.

### 15.10.5 Lists separate logical length from allocated capacity

A CPython list owns a contiguous dynamic array of pointers to element objects. The list object records logical length and allocated capacity; the element objects reside separately. Appending can place a new strong reference in spare capacity or allocate a larger pointer array and copy pointers. Overallocation yields amortised (O(1)) append, while an individual resize is (O(n)).

~~~python
import sys


values: list[int] = []
previous = sys.getsizeof(values)

for number in range(100):
    values.append(number)
    current = sys.getsizeof(values)
    if current != previous:
        print(len(values), previous, current)
        previous = current
~~~

The observed growth points are implementation policy. They reveal capacity changes only indirectly and vary with pointer size and release. Removing elements can leave capacity; clearing or deletion does not promise immediate resident-memory return.

Shallow copying a list allocates a new pointer array and increments/retains references to the same elements. It does not recursively clone them:

~~~python
inner = [1]
first = [inner]
second = first.copy()

assert first is not second
assert first[0] is second[0]

second[0].append(2)
assert first == [[1, 2]]
~~~

The contiguous pointer array explains (O(1)) indexing and (O(n)) insertion near the front. It does not mean the element payloads are contiguous or unboxed; numerical arrays use a different contract.

> **Common misconception 15.41 — “A list stores all element values inline in one contiguous block.”**  
> A CPython list stores a contiguous array of object references. Referent payloads are separate objects, may be shared, and contribute memory and cache behaviour not reported by the list’s shallow size.

### 15.10.6 Dictionaries combine hashing with compact ordered storage

Modern CPython dictionaries use a compact hash-table design separating sparse index information from dense entries. Entries retain hashes/keys and values under layout choices; instance dictionaries can use **split-table** key sharing so many instances share a keys structure while storing their own values. The exact structures and thresholds are private and have changed.

A dictionary preserves insertion order as a language guarantee in current Python, but that guarantee does not specify the current compact-table implementation. Another implementation can preserve the same order by another mechanism. Updating an existing key does not move it; deleting and reinserting can place it at the end under documented semantics.

Hash lookup first narrows candidate locations, then equality confirms a key. Equal keys must have equal hashes. Collisions are expected and resolved; a collision does not overwrite an unrelated key. Mutation of data used in a key’s hash while the key is resident would make lookup inconsistent, which is why keys must be hashable under a stable equality/hash contract.

~~~python
class CollidingKey:
    def __init__(self, value: str) -> None:
        self.value = value

    def __hash__(self) -> int:
        return 1

    def __eq__(self, other: object) -> bool:
        return (
            isinstance(other, CollidingKey)
            and self.value == other.value
        )


mapping = {
    CollidingKey("left"): 1,
    CollidingKey("right"): 2,
}
assert mapping[CollidingKey("left")] == 1
assert len(mapping) == 2
~~~

This deliberately pathological hash forces candidates together but correctness remains. Performance can degrade toward linear work under severe collision patterns or expensive equality. CPython randomises hashes of selected built-in types to make predictable collision attacks harder; user-defined constant hashes defeat their own distribution.

Dictionary resizing allocates or rebuilds index structures and is amortised over operations. Iteration while structurally mutating generally raises a runtime error, but thread safety requires stronger reasoning: another thread and callbacks from <code>__hash__</code> or <code>__eq__</code> can interleave effects.

### Worked example 15.13 — Equal keys can preserve the original key object

~~~python
first_key = 1
equal_key = 1.0
mapping = {first_key: "integer"}
mapping[equal_key] = "float update"

stored_key = next(iter(mapping))
assert len(mapping) == 1
assert stored_key is first_key
assert mapping[1] == "float update"
~~~

Because <code>1 == 1.0</code> and their hashes agree, the second assignment updates the existing entry rather than necessarily replacing its stored key object. Mapping semantics are based on hash/equality equivalence, not representation type alone.

### 15.10.7 Identity is stable during lifetime, while addresses can be reused

The language requires <code>id(obj)</code> to be unique among simultaneously existing objects and stable during the object’s lifetime. CPython commonly implements it from the object’s memory address. After deallocation, the allocator can reuse that address, so an integer identity value can recur for a different object later.

~~~python
class Token:
    pass


token = Token()
identity = id(token)
assert identity == id(token)
del token

# No assertion about a future object's id is valid here.
print(identity)
~~~

Converting an address-like identity to an integer does not keep the object alive and is not a safe pointer. Native interfaces that need an object later must hold a proper strong reference under their API. Persistent systems need application-defined identifiers; process-local <code>id</code> values can be reused, vary across runs, and disclose address-layout information.

Objects tracked by the cyclic collector can have an additional GC header stored adjacent to the object allocation, but that header is not part of the public <code>PyObject</code> prefix and untracked objects need not have it. Allocator padding, alignment, and arena metadata further separate “object size” from total process footprint.

> **Common misconception 15.42 — “id is a permanent globally unique object number.”**  
> It is unique only among overlapping lifetimes in one execution. CPython address reuse makes persistence, pointer reconstruction, and cross-process comparison invalid.

Object representation describes where references and slots reside. Native code must additionally know who owns each reference and when ownership can be transferred, borrowed, or destroyed.
