# 15.11 Reference ownership in the C API

CPython extension programming distinguishes **strong references**, **borrowed references**, and, in modern APIs, explicit ownership conventions.

- A new/strong reference contributes ownership that must eventually be released.
- A borrowed reference does not transfer ownership; it remains valid only while another owner and API-specific conditions keep the object alive.
- Increment/decrement operations adjust reference ownership under the build’s thread-safety machinery.

Conceptual extension code:

```c
PyObject *item = PyList_GetItem(list, 0);  /* borrowed under this API */
if (item == NULL) {
    return NULL;
}
Py_INCREF(item);                          /* acquire own strong reference */
return item;                              /* transfer result ownership */
```

The exact API documentation governs each function. Treating a borrowed reference as owned can over-release and use freed memory; treating a new reference as borrowed leaks it. Memory safety depends on ownership proof along every return and error path.

Stable ABI and limited-API mechanisms reduce coupling to internal layouts for binary extensions, while the general C API exposes more version-specific surface. An extension distributed across platforms requires compatible wheels or source builds with toolchains.

### 15.11.1 Ownership is an obligation, not a pointer type

At the C type level, both an owned and a borrowed reference can have type <code>PyObject *</code>. Ownership is a proof obligation carried by API documentation and control flow. The compiler does not generally reject a missing decrement or an over-release. Reviewers therefore annotate each reference-producing operation and every exit.

The principal terms are:

- a **strong reference** keeps the object alive under the API’s lifetime rules;
- a **new reference** is a returned strong reference whose release obligation transfers to the caller;
- a **borrowed reference** can be used only while a specified owner and stability condition keep it valid;
- a **stolen reference** is one whose ownership an API takes from the caller, usually even on success under the exact documented rule;
- an **immortal object** has implementation lifetime state that prevents ordinary deallocation, but references to it must still follow API conventions.

“New” describes transfer, not that the object was newly allocated. An API can return a new reference to an old interned object by incrementing ownership. “Borrowed” describes no transfer, not weakness: a borrowed pointer is usable while its validity conditions hold, whereas a weak reference is a Python-level object that tolerates referent death and reports it.

> **Common misconception 15.43 — “PyObject pointers encode whether a reference is owned.”**  
> The C pointer type normally carries no ownership qualifier. New, borrowed, stolen, and strong status comes from the called API’s contract and the path by which the pointer was obtained.

### 15.11.2 Every exit path must balance owned references

A reliable native function writes an ownership ledger before implementation. For each local pointer: source API, initial ownership, possible aliases, stealing calls, and release site. Error paths deserve equal attention because allocation or protocol calls can fail at nearly every step.

~~~c
static PyObject *
make_pair(PyObject *first, PyObject *second)
{
    PyObject *pair = PyTuple_New(2);
    if (pair == NULL) {
        return NULL;
    }

    /* Valid only because pair is fresh and both indices are in range. */
    PyTuple_SET_ITEM(pair, 0, Py_NewRef(first));
    PyTuple_SET_ITEM(pair, 1, Py_NewRef(second));

    return pair;
}
~~~

Each <code>Py_NewRef</code> creates a strong ownership claim and <code>PyTuple_SET_ITEM</code> steals it. The unchecked macro is valid only because <code>pair</code> is newly allocated with exactly two empty positions and the indices are proved. It would leak a prior item if used as a general replacement operation and can corrupt memory when its preconditions fail. In real extension code, prefer <code>PyTuple_Pack</code> for this task:

~~~c
static PyObject *
make_pair_safely(PyObject *first, PyObject *second)
{
    return PyTuple_Pack(2, first, second);
}
~~~

The higher-level constructor owns the balancing logic and returns a new reference or <code>NULL</code>. The design principle is general: choose an API whose ownership contract matches the operation rather than assembling a fragile sequence of low-level transfers.

Where several owned temporaries are necessary, a single cleanup label can make balance auditable:

~~~c
static PyObject *
normalised_mapping(PyObject *input)
{
    PyObject *result = NULL;
    PyObject *items = PyMapping_Items(input);
    if (items == NULL) {
        goto done;
    }

    PyObject *sorted = PySequence_List(items);
    if (sorted == NULL) {
        goto done;
    }

    if (PyList_Sort(sorted) < 0) {
        Py_DECREF(sorted);
        goto done;
    }

    result = sorted;

done:
    Py_XDECREF(items);
    return result;
}
~~~

<code>Py_XDECREF</code> tolerates <code>NULL</code>; <code>Py_DECREF</code> requires a valid non-null reference. The result variable receives ownership only on success. This example is illustrative rather than a complete semantic “normalisation”: sorting arbitrary mapping items can invoke user comparison and can fail.

The safest modern style often uses helper APIs and ownership conventions available in the minimum supported CPython version, keeps owned lifetimes short, and tests forced allocation and protocol failures. C++ wrappers can encode RAII—resource acquisition is initialisation—but must interoperate correctly with Python exceptions and interpreter attachment.

> **Common misconception 15.44 — “Reference leaks matter only on the successful return path.”**  
> Any allocation, conversion, callback, comparison, or container operation can fail. Each early return must preserve the exception and release exactly those references still owned on that path.

### 15.11.3 Borrowed references require a stability argument

A borrowed reference is safe only while its owner remains alive and no permitted action invalidates the borrowed access. The dangerous interval is often hidden in a call that can execute arbitrary Python:

~~~c
/* Conceptual hazard: do not copy as production code. */
PyObject *item = PyList_GetItem(list, 0);  /* borrowed */
if (item == NULL) {
    return NULL;
}

if (PyObject_CallNoArgs(callback) == NULL) {
    return NULL;
}

/* callback may have mutated list and released its former item */
return PyObject_Repr(item);
~~~

Even in a conventional GIL build, the callback can mutate <code>list</code>, delete the element, and cause the object’s last strong reference to disappear. The GIL prevents simultaneous execution during portions of the C call; it does not preserve a container element across re-entrant Python code.

Acquire an owned reference before the re-entrancy boundary. On CPython versions offering APIs that return strong references directly, prefer them; otherwise increment while validity is established under the required synchronisation:

~~~c
PyObject *item = PyList_GetItem(list, 0);  /* borrowed */
if (item == NULL) {
    return NULL;
}
Py_INCREF(item);                          /* retain across callback */

PyObject *ignored = PyObject_CallNoArgs(callback);
if (ignored == NULL) {
    Py_DECREF(item);
    return NULL;
}
Py_DECREF(ignored);

PyObject *representation = PyObject_Repr(item);
Py_DECREF(item);
return representation;
~~~

Free-threaded builds strengthen the need for fetch-style APIs and explicit container locking where documented. A separate thread can mutate a shared container after a borrowed pointer is obtained. An increment performed after removal may already be too late. APIs introduced for strong-reference retrieval close this race within their contract.

> **Common misconception 15.45 — “A borrowed reference is safe as long as the GIL was held when it was obtained.”**  
> Re-entrant callbacks can invalidate it in a GIL build, and concurrent mutation can invalidate assumptions in a free-threaded build. Safety requires owner lifetime and stability across the entire use interval.

### 15.11.4 Stealing references moves rather than duplicates an obligation

When an API steals a reference, the caller must treat the reference as transferred according to the exact success/failure rule. It must not decrement the transferred ownership again, yet it may retain a separate owned reference if it incremented beforehand.

This is analogous to moving a resource in a language with explicit ownership, but C provides no automatic invalidation. A useful local convention sets a pointer to <code>NULL</code> immediately after an unconditional transfer, making accidental cleanup less likely:

~~~c
PyObject *value = PyLong_FromLong(42);
if (value == NULL) {
    return NULL;
}

/* Suppose documented_api_steals(value) always steals on this path. */
if (documented_api_steals(value) < 0) {
    value = NULL;
    return NULL;
}
value = NULL;
~~~

This pseudo-call intentionally has no real declaration: the reader must consult a real function’s documentation rather than assume a universal steal-on-failure pattern. Setting the local to <code>NULL</code> is a review convention, not reference-count machinery.

The C API provides helpers such as <code>Py_NewRef</code> and <code>Py_XNewRef</code> in supported versions to express “return this object while acquiring a new strong reference”. These improve expression clarity and reduce the split between increment and return:

~~~c
static PyObject *
return_selected(PyObject *selected)
{
    return Py_NewRef(selected);
}
~~~

For replacement of an owned field, APIs/macros such as <code>Py_SETREF</code> and <code>Py_XSETREF</code> can encode “replace then release the old object” with important null preconditions. Under free-threading or shared published state, atomicity and locks remain separate concerns; ownership helpers do not by themselves make a compound state transition thread-safe.

> **Common misconception 15.46 — “If an API steals a reference, it creates another owned reference internally while the caller keeps its own.”**  
> Stealing transfers an existing ownership obligation. Continued caller ownership requires a distinct strong reference acquired before the transfer.
