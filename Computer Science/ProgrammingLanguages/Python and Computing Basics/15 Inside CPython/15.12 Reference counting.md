# 15.12 Reference counting

In conventional CPython, each object participates in reference counting. When a strong reference is acquired, a count-like ownership state increases; when released, it decreases. Reaching zero ordinarily triggers immediate deallocation under that implementation context, recursively releasing contained references.

Advantages:

- many unreachable acyclic objects are reclaimed promptly;
- resource wrappers may appear to finalise promptly in CPython;
- lifetime follows explicit ownership operations in the C API.

Costs and complications:

- every reference transfer requires bookkeeping;
- deallocation pauses can occur where the final reference is released;
- long recursive container destruction can cascade;
- cycles do not reach zero through reference counting alone;
- free-threaded operation requires different synchronisation and biased/deferred strategies internally.

Python code should use `with` for deterministic external-resource release rather than relying on reference count timing. Other implementations can use tracing garbage collection and delay finalisation.

`sys.getrefcount(obj)` in CPython reports a value affected by the temporary reference supplied to the call and by interpreter/compiler details. It is a diagnostic observation, not a stable ownership API.

### 15.12.1 Counts approximate strong ownership, not all machine pointers

The conventional model associates each object with the number of strong references recognised by CPython ownership rules. A local binding, container element, function default, closure cell, module global, and temporary evaluation-stack entry can each contribute. A raw C pointer that has not acquired ownership contributes nothing. Conversely, an internal owner can contribute without an obvious Python-level name.

Reference counting maintains an invariant, not a census of every address-sized bit pattern. Increment when acquiring an independent strong ownership claim; decrement when releasing it. If the last claim is released, deallocation begins. Missing an increment can leave a dangling pointer; missing a decrement leaves an unreachable object artificially alive; an extra decrement can destroy a live object.

At Python level, rebinding demonstrates transfers:

~~~python
class Payload:
    pass


first = Payload()
second = first
container = [first]

del first
assert second is container[0]

container.clear()
# The object remains alive through second.
assert isinstance(second, Payload)
~~~

Deleting <code>first</code> removes one binding. Clearing the list releases its element reference. Neither operation “deletes the object” because <code>second</code> remains an owner. The language account is reachability and binding; the CPython mechanism includes corresponding reference transfers.

Not every runtime reference is strong. Weak references do not retain the referent. Borrowed C pointers rely on someone else’s strong ownership. Some internal temporary references can be protected by precise invariants. Immortal objects no longer behave like ordinary decrement-to-zero counts. The model remains useful when stated as ownership, not when reduced to one publicly meaningful integer.

> **Common misconception 15.47 — “The reference count equals the number of Python variable names pointing at an object.”**  
> Strong owners also include containers, frames, cells, defaults, interpreter structures, and native code; names can be absent or multiple, and weak/borrowed pointers do not count as independent owners.

### 15.12.2 The zero transition invokes type-specific destruction

When ordinary reference state reaches zero in conventional CPython, the object’s type-specific deallocator runs. It must place the object into a consistent state, release owned child references, clear weak references and finalisation state under applicable rules, and return memory through the matching allocator. Releasing children can make their counts reach zero, causing a cascade.

For a container chain, destruction depth and timing can be non-trivial:

~~~python
class Marker:
    def __init__(self, label: str, log: list[str]) -> None:
        self.label = label
        self.log = log

    def __del__(self) -> None:
        self.log.append(self.label)


events: list[str] = []
values = [Marker("first", events), Marker("second", events)]
values.clear()
print(events)
~~~

The observed order and promptness should not become application semantics. List clearing must release element ownership, but external aliases, cycles, interpreter implementation, and finaliser behaviour can change when hooks run. A <code>__del__</code> method can execute arbitrary code and even mutate structures involved in destruction.

This produces a central implementation rule: decrement operations can be re-entrant. Consider a native setter replacing an owned field. If it decrements the old value before publishing the new consistent state, the old value’s finaliser can inspect a half-updated owner. Safer patterns first retain the new value if needed, update the field, and then release the old value, using documented replacement helpers where suitable.

Errors during finalisation cannot propagate to the vanished caller. Python reports unraisable exceptions through <code>sys.unraisablehook</code>. Libraries can customise that hook for observation, but must not let the hook itself become a source of recursive failure or retained exception graphs.

### Worked example 15.14 — Observe an unraisable finaliser error safely

~~~python
import gc
import sys


records: list[tuple[type[BaseException], str]] = []


def capture_unraisable(event) -> None:
    records.append((type(event.exc_value), str(event.exc_value)))


class FaultyFinaliser:
    def __del__(self) -> None:
        raise RuntimeError("cleanup failed")


previous = sys.unraisablehook
sys.unraisablehook = capture_unraisable
try:
    value = FaultyFinaliser()
    del value
    gc.collect()
finally:
    sys.unraisablehook = previous

assert records and records[0][0] is RuntimeError
~~~

The explicit collection makes the example more tolerant of implementation timing but does not make finalisers a sound cleanup primitive. Modifying a process-wide hook requires isolation in concurrent programs.

> **Common misconception 15.48 — “Py_DECREF is always a tiny non-observable arithmetic operation.”**  
> It can trigger type deallocation, recursive child release, weak callbacks, finalisers, arbitrary Python execution, and memory return. Native code must establish consistent state before a potentially final decrement.

### 15.12.3 getrefcount is a perturbed observation

<code>sys.getrefcount</code> is a CPython diagnostic returning a reference-count value as observed while its argument is being passed. The call itself creates at least one temporary reference, and compiler/interpreter temporaries can add more. Immortal objects can report very large implementation values unrelated to an actionable owner count.

### Worked example 15.15 — Compare deltas, not mythical absolute counts

~~~python
import sys


class Sample:
    pass


value = Sample()
before = sys.getrefcount(value)
aliases = [value, value, value]
during = sys.getrefcount(value)
aliases.clear()
after = sys.getrefcount(value)

assert during >= before + 3
assert after == before
~~~

Even this controlled delta is CPython-specific. The <code>>=</code> acknowledges possible temporaries, while equality after clearing is expected for this simple compiled context but should not be used as a production invariant. A tracing tool, debugger, notebook display, or alternate compiler optimisation can retain another reference.

Reference counts cannot prove that an object is “unused”. A reachable cache entry can have one owner and still be a leak relative to the application’s intended lifetime. A borrowed pointer can be semantically in use while adding no count. Diagnose ownership paths and application roots instead.

The <code>gc.get_referrers</code> function can expose selected tracked containers referring to an object, but it omits untracked and non-GC references, can return partially constructed objects, and creates new references during inspection. It is a debugging aid, not a complete inverse pointer map.

> **Common misconception 15.49 — “sys.getrefcount reveals the exact stable number of program references.”**  
> Calling it perturbs the count; temporaries, tooling, immortality, and implementation strategies affect the value. At most it supports carefully controlled, version-scoped experiments.

### 15.12.4 Immortality removes hot shared objects from ordinary zero-count lifetime

PEP 683 introduced **immortal objects** as a CPython mechanism: selected objects are marked so their reference state never reaches ordinary deallocation during runtime. Common singletons and statically allocated objects are natural candidates. This reduces reference-count write traffic and supports later free-threading mechanisms.

Immortality is not a new Python semantic category. <code>None</code> is still a singleton because the language specifies its role; its internal immortal state is a CPython implementation technique. User code must not infer immortality from a large value returned by <code>getrefcount</code>, retain raw pointers without ownership discipline, or assume every interned object is immortal.

At the C API level, increment/decrement operations on an immortal object become harmless with respect to its lifetime under the documented implementation, but extensions should still perform them according to contract. Omitting correct ownership merely because a test object happened to be immortal makes the code fail when another object arrives.

### 15.12.5 Free-threaded reference counting is distributed and deferred

Removing one global lock makes a single shared counter a highly contended cache line and exposes races in ordinary increments. The free-threaded design accepted through PEP 703 combines mechanisms including biased reference counting, deferred reference counting for selected references, immortalisation, and stop-the-world coordination for cyclic collection. Exact fields and state transitions are implementation details of each supporting version.

**Biased reference counting** gives an object an owning-thread bias so that common local increments/decrements can avoid an atomic operation, while references from other threads update shared state. Ownership transfer or merging reconciles state. **Deferred reference counting** omits immediate updates for selected interpreter-stack references and later accounts for them during coordinated scanning. These meanings differ from “reference counting was removed”.

The observable consequences are important:

- a raw numeric reference count is even less suitable as a truth oracle;
- deallocation timing can differ from conventional builds;
- borrowed-reference patterns that depended on global exclusion need strong-reference fetch APIs or locks;
- container integrity locks do not make multi-step application operations atomic;
- extension modules must use public ownership and thread-state APIs rather than direct field arithmetic.

### Worked example 15.16 — State a lifetime contract without relying on prompt destruction

~~~python
from contextlib import contextmanager
from io import StringIO
from collections.abc import Iterator


@contextmanager
def output_buffer() -> Iterator[StringIO]:
    stream = StringIO()
    try:
        yield stream
    finally:
        stream.close()


with output_buffer() as output:
    output.write("complete")
    assert output.getvalue() == "complete"

assert output.closed
~~~

The context manager gives deterministic lexical release independent of whether a reference count falls immediately. It remains correct on a tracing collector, conventional CPython, or a free-threaded configuration. Prompt reclamation is an optimisation of object memory lifetime; external resource correctness belongs to explicit protocols.

> **Common misconception 15.50 — “Free-threaded CPython simply makes every reference increment atomic and otherwise preserves the old model exactly.”**  
> Its design combines biased, deferred, immortal, atomic, and coordinated mechanisms to control contention and lifetime. Extensions must follow the supported API rather than assume one counter field.

Reference counting efficiently handles acyclic ownership. It cannot by itself distinguish an isolated cycle from a still-useful strongly connected structure, because every member of either structure can have a positive count.
