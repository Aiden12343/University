# 15.13 Cyclic garbage collection

Reference counting cannot reclaim a cycle whose objects refer to each other after all external references disappear:

```python
left: list[object] = []
right: list[object] = [left]
left.append(right)

del left
del right
```

The two lists retain each other even though program roots no longer reach them. CPython’s cyclic garbage collector tracks selected container objects and periodically analyses groups to identify unreachable cycles.

The collector is **generational** in the broad sense that it uses generations or age-based policies whose exact count and scheduling have changed across versions. The empirical observation underlying generational collection is that many objects die young, so scanning younger candidates more often can reduce work. Consult the documentation for the target CPython version; do not hard-code historical generation counts.

The collector’s analysis conceptually distinguishes references internal to a candidate group from references arriving from outside. If subtracting internal support leaves no external reachability, the group is unreachable and can be cleared/finalised under applicable rules.

### Finalisation and resurrection

`__del__` is a finaliser hook, not a dependable resource manager. It can run at difficult times, during interpreter shutdown, on an arbitrary thread context under implementation rules, or not before abrupt termination. A finaliser can **resurrect** an object by creating a new reachable reference. Exceptions in `__del__` cannot propagate normally to a caller and are reported specially.

Use context managers for resources, `weakref.finalize` for selected fallback cleanup without embedding the same cycle hazards, and finalisers only with a complete lifecycle analysis.

### 15.13.1 The collector augments rather than replaces reference counting

The cyclic collector considers objects capable of participating in reference cycles, principally containers and user instances whose types support traversal. Such an object is **tracked** when registered with the collector’s tracking structures. Many atomic immutable objects need not be tracked because they cannot point into a cycle. CPython can also untrack containers such as selected dictionaries or tuples when their contents make cycle participation impossible, and later track them if contents change.

~~~python
import gc


observations = {
    "integer": gc.is_tracked(42),
    "list": gc.is_tracked([]),
    "atomic tuple": gc.is_tracked((1, 2, 3)),
    "nested tuple": gc.is_tracked(([],)),
    "dictionary": gc.is_tracked({"key": 1}),
}

for label, tracked in observations.items():
    print(label, tracked)
~~~

Only broad expectations should be asserted: a list capable of holding itself is normally tracked, while an integer is not a cycle-forming container. Tuple and dictionary tracking can change after a collection or mutation as an optimisation. “Untracked” does not mean unmanaged, immortal, outside reference counting, or invisible to all diagnostic tools. It means the cyclic collector need not include that object in the relevant traversal population at that moment.

The collector is not a moving/compacting collector in conventional CPython. It ordinarily leaves live object addresses stable and reclaims detected unreachable groups by clearing and reference-count consequences. That fact supports parts of the existing C API but also contributes to fragmentation; it is an implementation property, not a Python language guarantee.

> **Common misconception 15.51 — “Every CPython object is periodically traced by the cyclic garbage collector.”**  
> Reference counting manages all ordinary strong ownership, while cyclic collection tracks selected cycle-capable objects. Atomic and optimisably acyclic objects may be untracked.

### 15.13.2 Trial deletion identifies external support

Reference counts cannot distinguish a reachable cycle from an unreachable one using each count alone. The collector therefore performs a graph analysis over a candidate set. A useful conceptual account, sometimes called **trial deletion**, is:

1. copy each candidate’s reference-count support into temporary GC state;
2. traverse candidate-to-candidate strong references and subtract them from the target’s temporary support;
3. candidates with positive remaining support have references from outside the candidate graph or from roots represented outside the subtraction;
4. propagate reachability from those externally supported candidates through their outgoing edges;
5. the remaining candidates are unreachable cyclic trash, subject to finalisation and clearing rules.

This is conceptual, not a line-for-line specification of current internal functions or bit encodings. The key proof idea is that internal edges cancel. If a pair refers only to each other, both ordinary counts may be one; subtracting their mutual edges leaves zero. If a module global also points to one member, positive external support remains and reachability propagates to the other.

### Worked example 15.17 — Distinguish an unreachable cycle from a live cycle

~~~python
import gc
import weakref


class Node:
    def __init__(self, label: str) -> None:
        self.label = label
        self.next: Node | None = None


left = Node("left")
right = Node("right")
left.next = right
right.next = left

left_reference = weakref.ref(left)
right_reference = weakref.ref(right)

root = left
del left, right
gc.collect()
assert left_reference() is root
assert right_reference() is root.next

del root
gc.collect()
assert left_reference() is None
assert right_reference() is None
~~~

The local <code>root</code> is an external path during the first collection. After it is removed, only the internal cycle remains. Explicit <code>gc.collect</code> makes the observation deterministic enough for CPython tests but should not be inserted into normal hot paths as a substitute for lifecycle design.

An object graph can be unreachable from the program’s intended data model yet still reachable from the runtime—for example through a forgotten global cache, a trace function, a task registry, or a traceback. The collector correctly preserves it. Such a **logical leak** requires finding and removing the unwanted root, not changing cycle thresholds.

> **Common misconception 15.52 — “The collector frees every object the application no longer wants.”**  
> It can reclaim only objects unreachable under runtime roots and supported traversal. A stale cache or retained traceback is still reachable even if its lifetime violates the application design.

### 15.13.3 Generations trade collection frequency against survivor scanning

CPython 3.12 exposes three generations numbered 0, 1, and 2. Newly tracked objects enter the youngest generation. Survivors are promoted; younger generations are collected more often. Allocation-minus-deallocation counters and thresholds influence automatic collection. This exact three-generation policy must not be projected onto later releases: free-threaded and newer collector designs have revised generation counts and scheduling.

The public interface exposes configuration and statistics:

~~~python
import gc


print("thresholds", gc.get_threshold())
print("current counts", gc.get_count())

for generation, statistics in enumerate(gc.get_stats()):
    print(generation, statistics)
~~~

<code>get_count</code> values are scheduling counters, not numbers of live objects in each generation. <code>get_stats</code> reports cumulative collections, collected objects, and uncollectable objects for each exposed generation under the running interpreter. Allocation patterns in extensions or untracked types can escape a simplistic inference.

Calling <code>gc.collect(generation)</code> requests collection through a specified generation under that version’s semantics and returns the documented number of unreachable objects found. A full collection can clear certain built-in free lists as a side effect, changing subsequent memory and performance observations. Collection during another collection is undefined; callbacks must not recursively force it.

Applications sometimes disable automatic collection during a verified short phase that creates no cycles and then restore it. This is an advanced latency optimisation requiring measurement and exception-safe restoration:

~~~python
import gc


was_enabled = gc.isenabled()
if was_enabled:
    gc.disable()
try:
    records = [{"index": index} for index in range(10_000)]
finally:
    if was_enabled:
        gc.enable()

assert records[-1]["index"] == 9_999
~~~

The code does not prove no cycles were formed by surrounding hooks, subclasses, trace functions, or later mutations. Disabling automatic collection never disables reference counting. A server that forgets to re-enable it can accumulate cycles indefinitely.

> **Common misconception 15.53 — “Generation numbers and thresholds have one timeless meaning across CPython versions.”**  
> CPython 3.12’s three-generation policy is version-specific. Later collector and free-threaded designs alter generations, triggers, and scanning fractions; tools must interrogate and document their target runtime.

### 15.13.4 Extension containers must describe their outgoing graph

A native extension type that can participate in cycles must opt into GC support and implement traversal correctly. Its <code>tp_traverse</code> slot visits every owned Python reference that can lead to a cycle. Its <code>tp_clear</code> slot breaks such references safely. Allocation/initialisation tracks the object only after its traversable fields are in a state the collector can inspect, and deallocation untracks before invalidating them.

A conceptual skeleton is:

~~~c
typedef struct {
    PyObject_HEAD
    PyObject *peer;
} LinkObject;

static int
Link_traverse(LinkObject *self, visitproc visit, void *argument)
{
    Py_VISIT(self->peer);
    return 0;
}

static int
Link_clear(LinkObject *self)
{
    Py_CLEAR(self->peer);
    return 0;
}

static void
Link_dealloc(LinkObject *self)
{
    PyObject_GC_UnTrack(self);
    Link_clear(self);
    Py_TYPE(self)->tp_free((PyObject *)self);
}
~~~

The type definition must also set the documented GC flag and use a GC-compatible allocation/free path. <code>Py_VISIT</code> applies the visitor to a non-null child and propagates non-zero results. <code>Py_CLEAR</code> clears the field before decrementing the former value, helping make re-entrant finalisation observe a consistent owner.

Omitting an edge from <code>tp_traverse</code> can hide a cycle forever. Visiting a pointer that is not an owned Python reference can corrupt analysis. Clearing a mandatory invariant without making remaining methods tolerate the cleared state can cause use-after-clear errors during finalisation. GC support is therefore part of the type’s formal ownership design.

Inheritance adds requirements: a subtype’s traversal and clear logic may need to call the base implementation. The exact allocation helpers differ for fixed/variable-sized and limited-API use. Follow the C API documentation and model tests on each supported release.

> **Common misconception 15.54 — “The cyclic collector can discover native extension pointers by scanning raw memory.”**  
> CPython depends on each GC-aware type’s traversal contract. Hidden owned edges are invisible to graph analysis and can make cycles leak.

### 15.13.5 Finalisation, clearing, resurrection, and uncollectable state

PEP 442 established safe finalisation of cyclic isolates containing Python-level finalisers. Broadly, weak references are handled, finalisers are called under controlled ordering, the isolate is checked for resurrection, and cyclic links are cleared if it remains isolated. The exact implementation steps and distinctions among legacy C finalisers, modern finaliser slots, and weak callbacks require the target-version documentation.

**Resurrection** occurs when finalisation creates an externally reachable path to an object that was otherwise unreachable. A finaliser is normally called at most once under the modern protocol even if the resurrected object later becomes unreachable again.

### Worked example 15.18 — Demonstrate one-shot resurrection

~~~python
import gc
import weakref


resurrected: list[object] = []
events: list[str] = []


class Phoenix:
    def __del__(self) -> None:
        events.append("finalise")
        resurrected.append(self)


value = Phoenix()
reference = weakref.ref(value)
del value
gc.collect()

assert events == ["finalise"]
assert resurrected and reference() is resurrected[0]

resurrected.clear()
gc.collect()
assert events == ["finalise"]
~~~

Weak-reference timing around resurrection is subtle and version-specific; this example targets ordinary CPython behaviour and deliberately checks only after explicit collection. Resurrection makes reasoning difficult: state may have been partially torn down, external invariants may no longer hold, and ownership becomes global. It should almost never be an application technique.

<code>gc.garbage</code> stores objects the collector found uncollectable under the active policy, and <code>DEBUG_SAVEALL</code> deliberately appends all unreachable objects rather than freeing them. Turning on that flag creates retention by design:

~~~python
import gc


previous_flags = gc.get_debug()
try:
    gc.set_debug(previous_flags | gc.DEBUG_SAVEALL)
    cycle: list[object] = []
    cycle.append(cycle)
    del cycle
    gc.collect()
    saved = len(gc.garbage)
    gc.garbage.clear()
finally:
    gc.set_debug(previous_flags)

gc.collect()
assert saved >= 1
~~~

Global GC flags and <code>gc.garbage</code> affect the process. Diagnostic code must restore flags and clear intentionally saved state. The example should run in an isolated test process when other threads or tests may allocate cycles concurrently.

### 15.13.6 Collection callbacks enable measurement but can perturb it

<code>gc.callbacks</code> receives phase information at collection start and stop. A callback can measure duration and counts, but must remain fast, avoid retaining object graphs, and avoid causing nested collection.

~~~python
import gc
import time


starts: dict[int, int] = {}
durations: list[tuple[int, int]] = []


def observe_gc(phase: str, info: dict[str, int]) -> None:
    generation = info["generation"]
    if phase == "start":
        starts[generation] = time.perf_counter_ns()
    elif phase == "stop" and generation in starts:
        durations.append(
            (generation, time.perf_counter_ns() - starts.pop(generation))
        )


gc.callbacks.append(observe_gc)
try:
    gc.collect()
finally:
    gc.callbacks.remove(observe_gc)

assert durations
~~~

The measured interval includes callback overhead and whatever system scheduling occurs. It does not by itself identify pause attribution in a concurrent/free-threaded collector. Pair GC statistics with allocation traces, latency distributions, application phase, and runtime metadata.

> **Common misconception 15.55 — “Calling gc.collect is a general cure for high memory use.”**  
> It addresses eligible unreachable cycles. Reachable caches, native allocations, allocator retention, fragmentation, memory maps, and large still-live objects require different diagnoses; forced collection can only add cost when no cyclic trash exists.

Cyclic collection answers whether selected strongly connected objects remain externally reachable. Weak references answer a different design need: observing or indexing an object without becoming an external owner.
