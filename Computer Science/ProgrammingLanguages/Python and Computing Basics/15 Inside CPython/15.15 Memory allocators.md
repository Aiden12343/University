# 15.15 Memory allocators

CPython layers memory management. Object-specific free lists, small-object allocation, arenas/pools, and platform allocators may retain freed memory for reuse rather than returning it immediately to the operating system. Therefore:

- object deallocation does not imply resident process memory immediately falls;
- `sys.getsizeof` does not include allocator fragmentation or all referents;
- a stable high-water resident set is not alone proof of a live-object leak;
- native extensions can allocate outside Python-traced domains.

Diagnose in layers: count live objects or allocation traces, inspect reachability, compare resident memory, and include native profilers where relevant. Choose the measure corresponding to the claim.

### 15.15.1 Allocator domains encode distinct contracts

The CPython memory C API separates three allocator domains:

| Domain | Representative family | Intended use |
|:---|:---|:---|
| raw | <code>PyMem_RawMalloc</code>, <code>PyMem_RawRealloc</code>, <code>PyMem_RawFree</code> | general memory, callable without an attached Python thread state under documented rules |
| memory | <code>PyMem_Malloc</code>, <code>PyMem_Realloc</code>, <code>PyMem_Free</code> | buffers associated with interpreter-managed memory and requiring an attached thread state |
| object | <code>PyObject_Malloc</code>, <code>PyObject_Realloc</code>, <code>PyObject_Free</code> | Python-object storage and related private allocations under object-domain rules |

The three families can route to different allocator implementations or hooks. Memory obtained from a family must be resized and freed with its matching family. Mixing <code>malloc</code> with <code>PyMem_Free</code>, or <code>PyObject_Malloc</code> with <code>free</code>, is undefined and can corrupt heaps even if it appears to work in one release build.

~~~c
static int
copy_bytes(const char *source, Py_ssize_t length, char **output)
{
    if (length < 0) {
        PyErr_SetString(PyExc_ValueError, "negative length");
        return -1;
    }

    char *buffer = PyMem_Malloc((size_t)length + 1);
    if (buffer == NULL) {
        PyErr_NoMemory();
        return -1;
    }

    memcpy(buffer, source, (size_t)length);
    buffer[length] = '\0';
    *output = buffer;
    return 0;
}

/* The eventual owner must call PyMem_Free(*output). */
~~~

The calculation casts a non-negative <code>Py_ssize_t</code> before adding one; on supported models its maximum plus one is representable by <code>size_t</code>. More general element-count times element-size calculations still require explicit overflow checks or checked-size helpers. Allocator ownership and size arithmetic form one proof, not separate afterthoughts.

Since Python 3.12, custom allocators installed for all domains must be thread-safe under the documented requirement. After full runtime initialisation, replacement allocators generally need to wrap the existing allocator rather than substitute arbitrary nonconforming state. Debug hooks may need reinstalling. Embedder code must follow the preinitialisation/initialisation phase restrictions for that version.

> **Common misconception 15.58 — “All CPython allocation functions are interchangeable wrappers around C malloc.”**  
> Raw, memory, and object domains have distinct attachment and instrumentation contracts. Allocation, reallocation, and free must remain within the same documented family.

### 15.15.2 pymalloc organises small blocks into pools and arenas

In the default conventional build, the specialised allocator commonly called **pymalloc** serves object-domain requests up to 512 bytes. It groups equal-size blocks into pools and obtains pools from larger arenas. In CPython 3.12, an arena is 1 MiB on 64-bit platforms and 256 KiB on 32-bit platforms; pool and size-class details are version/build mechanisms. Larger requests go to underlying platform allocation paths.

This hierarchy reduces the cost of repeated small allocations and internal fragmentation between unlike sizes. A pool dedicated to one size class can recycle a freed block immediately. An arena can return to the platform only when all its pools are sufficiently free under allocator policy. One long-lived object can therefore pin a pool or arena containing mostly free capacity.

The following Python experiment observes shallow allocation patterns, not internal pools directly:

### Worked example 15.21 — Separate live size from resident high-water behaviour

~~~python
import gc
import os
import tracemalloc


tracemalloc.start()
before = tracemalloc.take_snapshot()

objects = [bytearray(400) for _ in range(50_000)]
during = tracemalloc.take_snapshot()
del objects
gc.collect()
after = tracemalloc.take_snapshot()

during_growth = sum(
    statistic.size_diff
    for statistic in during.compare_to(before, "lineno")
)
remaining_growth = sum(
    statistic.size_diff
    for statistic in after.compare_to(before, "lineno")
)

print(os.getpid(), during_growth, remaining_growth)
tracemalloc.stop()
~~~

The trace should show substantial allocation growth and later reduction, but exact numbers are deliberately not asserted. The process’s resident set may remain high because pools, arenas, the platform allocator, or operating-system page policy retain address space for reuse. <code>bytearray</code> can include a separately allocated buffer whose path is not reducible to the object header’s shallow size.

Three quantities answer different questions:

- **live traced allocation** estimates blocks currently attributed to traced Python allocator domains;
- **allocator reserved memory** includes free blocks kept in pools/arenas or platform heaps;
- **resident set size** counts pages currently resident according to operating-system accounting and can include code, shared libraries, mappings, native buffers, and allocator metadata.

A decline in the first need not immediately produce a decline in the third. Conversely, a native extension leak may grow resident memory without appearing in ordinary tracemalloc domains unless it integrates tracing.

> **Common misconception 15.59 — “If an object is deallocated, its bytes must immediately be returned to the operating system.”**  
> CPython and platform allocators commonly retain freed blocks, pools, or arenas for reuse. Object death, allocator availability, address-space release, and resident-page reduction are separate events.

### 15.15.3 Debug hooks expose family and boundary errors

CPython’s memory debug hooks can surround allocated blocks with forbidden-byte regions, fill newly allocated and freed memory with recognisable patterns, record requested size and API family, and use tracemalloc information to report allocation origin. A debug build enables substantial checks by default; the <code>PYTHONMALLOC=debug</code> environment setting can enable debug hooks in other supported builds.

These hooks help detect:

- writes before or after an allocated block;
- use of an inappropriate allocator family to free a block;
- selected calls without required thread-state attachment;
- use-after-free patterns when overwritten bytes retain debug markers.

They do not prove absence of all memory errors. An out-of-bounds write can corrupt unrelated data before a guard is checked; data races can evade deterministic detection; a pointer can target a still-allocated but semantically wrong object. AddressSanitizer, UndefinedBehaviorSanitizer, Valgrind-like tools, debug builds, and stress tests provide complementary evidence.

Allocator selection can be reported rather than guessed:

~~~python
import os
import sys


print("implementation", sys.implementation.name)
print("malloc setting", os.environ.get("PYTHONMALLOC", "<default>"))
print("tracemalloc setting", os.environ.get("PYTHONTRACEMALLOC", "<default>"))
~~~

Changing <code>PYTHONMALLOC</code> requires starting a new process; setting it after initialisation does not retroactively rebuild allocator state. Comparing default, system-malloc, and debug configurations can isolate allocator-retention effects, but each configuration changes overhead and timing.

> **Common misconception 15.60 — “A release build that passes tests proves a C extension has correct allocation boundaries.”**  
> Heap corruption can remain latent. Debug hooks and native memory sanitizers deliberately change layout and timing to expose family mismatches, overruns, use-after-free, and races.

### 15.15.4 tracemalloc attributes selected allocations to Python stacks

<code>tracemalloc</code> records traceback metadata for traced allocation blocks. It can compare snapshots by source line, filename, or traceback, filter domains/locations, and report current and peak traced size. Starting it early captures more of program startup; deeper traceback limits improve attribution at additional memory/time cost.

### Worked example 15.22 — Compare a bounded allocation phase

~~~python
import tracemalloc


def build_index(size: int) -> dict[int, str]:
    return {number: str(number) for number in range(size)}


tracemalloc.start(10)
baseline = tracemalloc.take_snapshot()

index = build_index(20_000)
populated = tracemalloc.take_snapshot()

statistics = populated.compare_to(baseline, "traceback")
for statistic in statistics[:3]:
    print(statistic)

del index
tracemalloc.stop()
~~~

Snapshot comparison is differential: unrelated concurrent activity appears too. Run controlled workloads repeatedly, use filters, and preserve the allocation stack rather than blaming whichever line happens to retain the final container. A positive difference can represent intended cache growth; a leak is growth that violates the required lifetime and remains unbounded under a representative workload.

Native extensions can register allocations in non-zero tracemalloc domains through the C API, enabling separation from default Python allocations. Tracking metadata itself consumes memory. The module does not trace arbitrary <code>malloc</code> calls without cooperation.

### 15.15.5 Free lists and caches complicate before-and-after tests

Object implementations can retain recently freed structures in type-specific free lists or caches. Integer/string interning, tuple/frame-related caches in selected versions, import caches, regular-expression caches, and application-level pools all change allocation reuse. A full generation-2 collection clears some built-in free lists, but not necessarily every retained block.

<code>sys.getallocatedblocks</code>, where available, reports the number of memory blocks allocated by the interpreter and can return zero or an approximate value when tracking is unavailable. It is not a byte count and includes activity caused by the measurement environment:

### Worked example 15.23 — Treat allocated-block counts statistically

~~~python
import gc
import statistics
import sys


def allocated_blocks() -> int | None:
    getter = getattr(sys, "getallocatedblocks", None)
    return None if getter is None else getter()


measurements: list[int] = []
for _ in range(7):
    gc.collect()
    value = allocated_blocks()
    if value is not None:
        measurements.append(value)

if measurements:
    print(statistics.median(measurements), min(measurements), max(measurements))
~~~

Variation is expected. The act of building the list creates blocks. A valid leak test repeats a representative create/use/release cycle, discards warm-up, checks the slope or plateau across many rounds, and corroborates with object/reachability evidence.

> **Common misconception 15.61 — “One memory metric can distinguish every leak, cache, fragmentation, and allocator effect.”**  
> Live object graphs, traced blocks, native allocations, reserved arenas, virtual memory, and resident pages are different quantities. Diagnosis requires several aligned measurements and a lifetime hypothesis.

Allocator and reference-count designs were historically protected by a process-wide execution lock. Free-threaded builds must preserve memory safety and ownership without making that lock the universal exclusion mechanism.
