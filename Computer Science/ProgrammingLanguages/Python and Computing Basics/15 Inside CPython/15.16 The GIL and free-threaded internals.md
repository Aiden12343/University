# 15.16 The GIL and free-threaded internals

In conventional builds, the GIL permits CPython object and interpreter internals to rely on broad mutual exclusion for many operations, though extensions release it around blocking work or independent native computation. Thread switching can occur between bytecodes and within operations that release the lock or invoke arbitrary code.

Free-threaded CPython builds remove that global exclusion and use finer-grained, deferred, atomic, biased, or immortal-object techniques as the version implements them. Built-in containers employ internal synchronisation sufficient to protect their own memory integrity under documented conditions, but application-level sequences remain non-atomic unless explicitly synchronised.

Extension modules must advertise and implement compatible thread behaviour. Importing an extension not marked safe can alter runtime mode under version-specific policy. Performance can improve for parallel Python work and regress for single-thread or contention-heavy work; measurement is required.

The language-level conclusion is stable: never use the GIL as the specification of a program invariant.

### 15.16.1 The conventional GIL serialises attached bytecode execution, not all process activity

In a conventional CPython build, a thread must hold the **global interpreter lock** while operating on most Python objects and executing Python bytecode. Broad mutual exclusion makes ordinary reference-count updates and many object invariants cheaper than if every field required separate synchronisation. The lock is associated with an interpreter/runtime arrangement, not with a source line, and its policy has evolved.

Only one thread holding that GIL executes Python interpreter work at an instant, but other activity can proceed:

- a thread can release the lock while blocking in operating-system I/O;
- extension code can release it around native computation that does not touch Python objects;
- subprocesses execute in distinct processes with distinct interpreters;
- devices, kernels, databases, and network peers continue independently;
- some extension libraries manage their own worker threads and release the GIL.

This explains why threading can improve throughput for I/O-bound workloads even though CPU-bound pure Python bytecode remains serialised in one conventional interpreter. It does not guarantee improvement: lock hand-offs, scheduling, cache pressure, oversubscription, and task granularity add overhead.

The GIL is not held forever by one thread. The evaluator responds to switching requests and blocking operations. A configurable switch interval influences how often the interpreter asks long-running Python execution to yield, but it is not a strict maximum latency, instruction count, or real-time scheduling guarantee.

~~~python
import sys


original = sys.getswitchinterval()
try:
    sys.setswitchinterval(0.01)
    assert sys.getswitchinterval() > 0
finally:
    sys.setswitchinterval(original)
~~~

Changing a process-wide scheduling hint to “fix” a race is invalid. A correct algorithm uses locks, queues, conditions, futures, immutable messages, or transactional storage. The interval can be varied in stress tests to expose accidental scheduling assumptions.

> **Common misconception 15.62 — “The GIL means a multithreaded CPython program has no concurrency.”**  
> It serialises much Python-object/bytecode execution in a conventional interpreter. Threads can overlap blocking I/O and GIL-releasing native work, while external systems and processes execute concurrently.

### 15.16.2 Detaching thread state permits blocking or independent native work

Native extension code commonly brackets a region that neither accesses Python objects nor calls most Python C APIs. The <code>Py_BEGIN_ALLOW_THREADS</code> and <code>Py_END_ALLOW_THREADS</code> macros save/detach the current thread state and later restore/attach it; in a GIL build this releases and reacquires the lock.

~~~c
static PyObject *
wait_for_device(PyObject *self, PyObject *arguments)
{
    int descriptor;
    if (!PyArg_ParseTuple(arguments, "i", &descriptor)) {
        return NULL;
    }

    int status;
    Py_BEGIN_ALLOW_THREADS
    status = blocking_device_wait(descriptor);
    Py_END_ALLOW_THREADS

    if (status < 0) {
        return PyErr_SetFromErrno(PyExc_OSError);
    }
    Py_RETURN_NONE;
}
~~~

The native function names the intended shape; a real implementation must handle EINTR, platform handles, cancellation, descriptor lifetime, and whether its external API is thread-safe. Inside the detached region, it must not manipulate Python objects, adjust ordinary Python ownership through non-permitted APIs, or raise a Python exception. It records native status and constructs the Python result after reattachment.

In free-threaded builds these macros still detach/attach thread state even though they do not release a global lock in the same sense. The thread-state invariant remains. A callback from a foreign native thread must use documented attachment APIs and target the intended interpreter; convenience APIs historically assume the main interpreter and can be unsuitable for subinterpreters.

Long C loops that retain the GIL can starve other Python threads and delay signal handling. Releasing it is safe only when all accessed data has a non-Python lifetime and appropriate native synchronisation. Holding a raw pointer into a mutable Python buffer across detachment requires a specific export/pinning contract; “I do not call the API” alone is insufficient.

> **Common misconception 15.63 — “Between ALLOW_THREADS macros, C code may keep using Python object fields as long as it does not create objects.”**  
> Detachment permits other execution or free-threaded mutation. The region must avoid Python C API/object access unless an explicit API guarantees safety and lifetime independently.

### 15.16.3 Per-interpreter GILs partition exclusion, not arbitrary objects

PEP 684 moved the GIL into interpreter state and enabled subinterpreters configured with their own GIL in supporting CPython versions. Two such interpreters can execute Python code in parallel while retaining a GIL within each interpreter. This requires isolation of runtime state that was historically process-global.

A subinterpreter is not a lightweight thread sharing one arbitrary Python heap. Module dictionaries, built-ins, imported module instances, and many stateful resources are interpreter-specific. Cross-interpreter communication must use objects/data supported by explicit channels, copying, serialisation, or carefully designed shareable representations. Passing a normal <code>PyObject *</code> from one interpreter to another violates ownership and allocator assumptions.

Extension modules are a central constraint. A traditional single-phase extension with mutable static globals can accidentally share state across interpreters, retain objects from the wrong interpreter, or assume one finalisation event. Multi-phase initialisation and per-module state let each module instance own its state and support traversal, clearing, and freeing under the correct interpreter.

Conceptually:

~~~c
typedef struct {
    PyObject *cache;
} module_state;

static module_state *
get_state(PyObject *module)
{
    return (module_state *)PyModule_GetState(module);
}
~~~

The complete module definition must specify state size and lifecycle slots, traverse/clear owned objects, and declare multi-interpreter/GIL support through APIs appropriate to the target version. A pointer returned from module state remains governed by the module instance’s lifetime.

Per-interpreter isolation also affects process facilities that cannot be duplicated cleanly: environment variables, file descriptors, locale, signal disposition, C library globals, and third-party library singletons remain process-wide unless mediated. “Separate interpreter” is a carefully bounded isolation unit, not an operating-system security sandbox.

> **Common misconception 15.64 — “A per-interpreter GIL makes every extension and global resource safely independent.”**  
> Parallel interpreters require per-interpreter module state and explicit treatment of process-global native resources. Ordinary Python objects cannot be shared across interpreter heaps by raw pointer.

### 15.16.4 Free-threaded CPython replaces broad exclusion with several mechanisms

PEP 703 specifies an optional build mode in which Python threads can execute bytecode in parallel without one process/interpreter-wide GIL. In the 3.13 experimental era and subsequent development, the implementation combines techniques rather than applying one lock to every object:

- biased and deferred reference counting reduce atomic update traffic;
- selected objects are immortalised;
- built-in containers use fine-grained internal locks for memory integrity;
- optimistic dictionary/list access paths attempt common reads with validation;
- stop-the-world phases coordinate selected garbage-collection work;
- allocator changes and page reuse constraints support safe lock-free/optimistic reads;
- critical-section APIs let extension operations follow container locking policy;
- borrowed-reference APIs gain strong-reference alternatives for concurrent safety.

Each item is implementation- and version-scoped. The stable application consequence is that two threads may truly execute Python operations simultaneously. Data races that the conventional GIL happened to mask can become visible. The language still does not promise that compound read-modify-write sequences are atomic.

### Worked example 15.24 — Protect a semantic invariant, not a container method

~~~python
from threading import Lock, Thread


class Account:
    def __init__(self, balance: int) -> None:
        self._balance = balance
        self._lock = Lock()

    def withdraw(self, amount: int) -> bool:
        if amount < 0:
            raise ValueError("amount must be non-negative")
        with self._lock:
            if amount > self._balance:
                return False
            self._balance -= amount
            return True

    @property
    def balance(self) -> int:
        with self._lock:
            return self._balance


account = Account(100)
threads = [
    Thread(target=account.withdraw, args=(60,))
    for _ in range(2)
]
for thread in threads:
    thread.start()
for thread in threads:
    thread.join()

assert account.balance == 40
~~~

An internal lock on the integer object or instance dictionary would not make “check then subtract” one transaction. The account lock covers the invariant. The example is correct under both conventional and free-threaded builds and under scheduling changes.

Built-in list/dictionary locks preserve internal memory safety and give operations behaviour consistent with their documented critical regions. They do not supply a durable transaction across two calls, prevent logical lost updates, or replace ordering between application objects. Iteration while another thread mutates still requires an application protocol.

### 15.16.5 Extension compatibility is an explicit declaration and audit

A binary extension targeting a free-threaded build must be compiled for the appropriate ABI/configuration and declare support through the version’s module initialisation mechanism. The declaration is a claim backed by an audit:

- all process-global and module state has defined locking/ownership;
- borrowed references cannot outlive stable protected sources;
- direct reference-count and object-layout access is replaced by supported APIs;
- container mutations follow critical-section rules;
- callbacks and thread-state attachment target the right interpreter;
- released-GIL/detached regions have independent memory lifetimes;
- third-party native libraries are themselves safe under parallel calls.

In early free-threaded releases, importing an extension that does not declare support can cause the runtime to enable the GIL under documented policy and emit a warning. Exact behaviour and command-line/environment controls vary; test the actual deployment executable.

### Worked example 15.25 — Record the execution configuration in a benchmark

~~~python
import json
import sys
import sysconfig


def concurrency_configuration() -> dict[str, object]:
    gil_enabled = getattr(sys, "_is_gil_enabled", None)
    return {
        "version": sys.version,
        "gil_disabled_build": bool(
            sysconfig.get_config_var("Py_GIL_DISABLED")
        ),
        "gil_currently_enabled": (
            gil_enabled() if gil_enabled is not None else None
        ),
    }


print(json.dumps(concurrency_configuration(), indent=2))
~~~

The runtime query is only available in versions that expose it; <code>None</code> means “not observable through this interface”, not “the GIL is disabled”. A benchmark record should also list imported native extensions because one can affect runtime mode or parallel scalability.

> **Common misconception 15.65 — “No-GIL mode makes every threaded workload faster.”**  
> Parallelism introduces synchronisation, atomic operations, cache coherence, allocation, scheduling, and contention costs. Speedup depends on workload, thread count, extensions, memory bandwidth, and single-thread overhead, and must be measured against a stated baseline.

Function-call overhead is one frequently executed part of this picture. Vectorcall reduces argument-container construction while preserving the language’s call and binding semantics.
