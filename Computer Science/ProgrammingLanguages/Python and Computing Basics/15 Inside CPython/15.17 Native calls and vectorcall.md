# 15.17 Native calls and vectorcall

Function calls are frequent, so modern CPython uses calling conventions such as **vectorcall** to reduce temporary tuple/dictionary construction when passing positional and keyword arguments internally. Exact structures and flags are C API details.

At Python level, call semantics remain:

- evaluate callable;
- evaluate arguments in order;
- perform signature binding or callable-specific processing;
- execute and return or raise.

An implementation optimisation may avoid allocating an argument tuple while preserving the observable call. Benchmarking a call must therefore target a CPython version and callable kind; built-ins, Python functions, bound methods, and extension callables have different fast paths.

### 15.17.1 Call semantics and call representation are separate contracts

Python call syntax first evaluates the primary expression naming the callable, then argument expressions in specified order, expands starred positional and double-starred keyword inputs under defined rules, rejects duplicate keywords, and invokes the object’s call protocol. A Python function then binds supplied arguments to positional-only, positional-or-keyword, variadic positional, keyword-only, and variadic keyword parameters, applying retained defaults where permitted.

Vectorcall changes how an already evaluated call is carried across an internal/API boundary. Instead of necessarily constructing a tuple of positional arguments and a dictionary of keywords, the caller supplies a contiguous vector of object pointers plus compact metadata. The callee consumes that representation directly when it supports the protocol.

The following language-level experiment proves evaluation order, not vectorcall internals:

~~~python
events: list[str] = []


def argument(label: str, value: int) -> int:
    events.append(label)
    return value


def combine(left: int, right: int, *, scale: int) -> int:
    events.append("body")
    return (left + right) * scale


result = combine(
    argument("left", 2),
    argument("right", 3),
    scale=argument("scale", 4),
)

assert result == 20
assert events == ["left", "right", "scale", "body"]
~~~

An optimised calling convention cannot reorder these visible effects. It begins after or participates consistently in evaluation while retaining the specified sequence. Nor may it omit duplicate-key detection, positional-only restrictions, or descriptor binding.

> **Common misconception 15.66 — “Vectorcall is a different kind of Python function with different argument rules.”**  
> It is a CPython calling representation and protocol. Python-level evaluation, expansion, binding, defaults, and error semantics remain the governing contract.

### 15.17.2 nargsf and kwnames describe a packed argument vector

At the C API level, a vectorcall function receives a callable, an array of <code>PyObject *</code> arguments, a <code>size_t nargsf</code>, and a keyword-name tuple. Masking <code>nargsf</code> with the documented operation obtains the positional count; a flag can indicate that a writable scratch slot exists immediately before the argument vector. The keyword tuple contains names only, while corresponding values follow the positional values in the same vector.

Conceptually, a call such as <code>function(10, 20, scale=3, mode="fast")</code> is represented as:

| Vector index | Object role |
|:---:|:---|
| 0 | positional value 10 |
| 1 | positional value 20 |
| 2 | value 3 for keyword <code>scale</code> |
| 3 | value <code>fast</code> for keyword <code>mode</code> |

and <code>kwnames</code> is a tuple equivalent to <code>("scale", "mode")</code>. It is not a dictionary and need not allocate one unless callee semantics require a <code>**kwargs</code> object. Keywords in <code>kwnames</code> must satisfy the protocol’s string/name requirements; callers must not mutate argument arrays in violation of flags.

A simplified custom type slot has this form:

~~~c
static PyObject *
Example_vectorcall(PyObject *callable,
                   PyObject *const *arguments,
                   size_t nargsf,
                   PyObject *keyword_names)
{
    Py_ssize_t positional = PyVectorcall_NARGS(nargsf);
    /* Parse without retaining borrowed array entries across callbacks. */
    return parse_and_execute(
        callable,
        arguments,
        positional,
        keyword_names
    );
}
~~~

The placeholder helper would need a complete parsing, ownership, error, recursion, and thread-safety implementation. C extensions should normally use maintained parsing helpers or generated Argument Clinic code instead of hand-parsing every vector. Vector entries are not automatically new owned references.

The <code>PY_VECTORCALL_ARGUMENTS_OFFSET</code> flag permits selected callers to let a callee temporarily use <code>arguments[-1]</code>, enabling efficient insertion of a bound receiver. It does not authorise arbitrary out-of-bounds access. The callee must restore any temporarily changed value before return.

> **Common misconception 15.67 — “kwnames contains the keyword values or is an ordinary keyword dictionary.”**  
> It contains keyword-name objects. Their values occupy the argument vector after positional values, allowing a call to avoid constructing a dictionary when the callee does not need one.

### 15.17.3 Descriptors and method calls motivate allocation avoidance

Ordinary attribute access to a function stored on a class produces a bound method object whose receiver is recorded as <code>__self__</code>. If code immediately calls that method, allocating a transient bound-method object is often avoidable. CPython’s method-load/call paths can carry callable and receiver separately into vectorcall.

### Worked example 15.26 — Bound-method semantics survive an optimised call

~~~python
class Counter:
    def __init__(self) -> None:
        self.value = 0

    def add(self, amount: int) -> int:
        self.value += amount
        return self.value


counter = Counter()

bound = counter.add
assert bound.__self__ is counter
assert bound.__func__ is Counter.add
assert counter.add(3) == 3
assert bound(4) == 7
~~~

The explicit <code>bound</code> access materialises a method object observable through identity and attributes. The immediate <code>counter.add(3)</code> expression can use an optimised path while producing the same receiver binding. A custom descriptor may implement arbitrary <code>__get__</code>, so the optimiser must preserve descriptor semantics and guard fast paths.

Callable categories differ. A Python function parses against its code/signature metadata. A built-in C function can implement method flags or vectorcall directly. A class call passes through metaclass/type construction machinery. A callable instance uses the type’s call slot. <code>functools.partial</code> and bound methods prepend stored arguments. Benchmarking “the cost of a Python call” without identifying the category conflates distinct paths.

### Worked example 15.27 — inspect semantic signatures rather than native flags

~~~python
import inspect
from functools import partial


def affine(value: float, scale: float, offset: float) -> float:
    return value * scale + offset


shifted = partial(affine, scale=2.0, offset=1.0)

signature = inspect.signature(affine)
assert tuple(signature.parameters) == ("value", "scale", "offset")
print(inspect.signature(shifted))
assert shifted(3.0) == 7.0
~~~

The structural assertion avoids coupling the test to whether annotations are stored as objects or postponed strings and to formatted spelling. The point is that <code>inspect.signature</code> provides callable binding semantics while vectorcall flags describe a native transport.

Argument Clinic is a CPython source-generation system that turns declarative signatures into C parsing wrappers, documentation signatures, and method definitions. It reduces repetitive error-prone conversion code and lets maintainers evolve calling conventions centrally. It is a CPython development mechanism, not a Python packaging dependency every extension must use.

> **Common misconception 15.68 — “Avoiding a temporary tuple means a call performs no allocations or argument processing.”**  
> The callee may create locals, <code>*args</code>, <code>**kwargs</code>, defaults, conversion results, a frame, or returned objects. Vectorcall removes selected transport overhead, not the semantic work of calling.

Calls cross module boundaries through name and attribute resolution. Import creates those module objects through a protocol whose early caching and failure behaviour are essential to circular-import reasoning.
