# 15.18 Import internals and module objects

Import uses `sys.meta_path` finders to produce module specifications, loaders to create/execute modules, and `sys.modules` to cache them. Import locks coordinate concurrent loading. Package path entries and hooks permit filesystem, archive, frozen, and custom sources.

During import, the module is inserted in `sys.modules` before execution completes to manage recursion. If execution fails, cleanup rules remove or retain related entries according to the import path, and already imported side-effect modules can remain. Import is not a transaction rolling back every effect.

Instrumenting import time can expose expensive top-level code:

```text
python -X importtime -c "import ledger"
```

`-X` options are implementation-specific. The output describes one environment and cache state.

### 15.18.1 Import is a protocol with an early cache entry

An import first checks <code>sys.modules</code> for the fully qualified name. If no usable entry exists, finders on <code>sys.meta_path</code> are asked for a <code>ModuleSpec</code>. The chosen loader can create a module or allow default creation; import-related attributes are initialised; the module is placed in <code>sys.modules</code>; and the loader executes its code. The early insertion is what lets a recursive import encounter the same partially initialised module instead of creating an infinite series of copies.

The protocol separates discovery, module creation, and execution. A spec records name, loader, origin, package/submodule information, and optional loader state. It is not necessarily a filesystem record: built-in, frozen, namespace-package, zip, database, remote, or application-defined finders can participate.

### Worked example 15.28 — Observe a module specification without re-executing it

~~~python
import importlib.util
import json


for name in ("json", "sys"):
    specification = importlib.util.find_spec(name)
    if specification is None:
        raise RuntimeError(f"no specification for {name}")
    print(
        name,
        type(specification.loader).__name__,
        specification.origin,
        specification.submodule_search_locations,
    )

assert json.__spec__ is not None
assert json.__spec__.name == "json"
~~~

<code>find_spec</code> can import a parent package while locating a submodule, so it is not universally side-effect-free. Printing a custom loader can execute its representation. Inspection tools should work within a controlled finder environment.

During a circular import, a module can be present but incomplete. Suppose <code>alpha</code> imports <code>beta</code> before binding <code>alpha.ready</code>, while <code>beta</code> immediately reads that attribute. The cache correctly returns <code>alpha</code>; the attribute is absent because execution has not reached its assignment. Reordering imports sometimes hides the cycle but does not improve architecture. Extract shared declarations into a lower-level module, import modules rather than eager attributes where suitable, or delay a dependency explicitly.

If execution of a newly loaded module fails, import removes the failing module’s cache entry under the standard protocol, while modules successfully loaded as side effects can remain cached. Mutations, files written, network requests, thread creation, and registrations performed before failure are not rolled back. Retrying the import can repeat them.

Import locks prevent duplicate concurrent execution of the same module under ordinary protocol and coordinate deadlock-sensitive module loading. They do not make module top-level effects into a transaction or make all custom finders/loaders thread-safe. Import hooks must honour protocol and lock expectations.

> **Common misconception 15.69 — “A module enters sys.modules only after all of its top-level code succeeds.”**  
> It is inserted before execution to support recursion. Circular importers can therefore observe a partially initialised namespace, and failure does not undo every transitive side effect.

### 15.18.2 Module objects are ordinary namespaces with import metadata

A module object has a dictionary namespace and attributes such as <code>__name__</code>, <code>__spec__</code>, <code>__loader__</code>, <code>__package__</code>, and sometimes <code>__file__</code>, <code>__cached__</code>, and <code>__path__</code>. Not every module has a filesystem location; built-in/frozen modules and namespace packages require conditional handling.

~~~python
import math


metadata = {
    name: getattr(math, name, None)
    for name in (
        "__name__",
        "__package__",
        "__file__",
        "__cached__",
        "__loader__",
        "__spec__",
    )
}
for name, value in metadata.items():
    print(name, value)
~~~

Module attribute access can be customised with module-level <code>__getattr__</code> and <code>__dir__</code>. Replacing the module object’s class with a <code>ModuleType</code> subclass supports still more behaviour in CPython. Thus a module namespace is usually dictionary-backed but should not be treated as a passive immutable map.

<code>importlib.reload</code> re-executes module code in the existing module object’s retained dictionary under documented rules. Names absent from the new source can remain from the prior execution unless overwritten or cleared. External references to old classes/functions are not rebound. Reload is therefore unsuitable as a universal live-upgrade mechanism.

### 15.18.3 Bytecode caches accelerate compilation, not module effects

For eligible source modules, CPython can store compiled code in a <code>__pycache__</code> file named with an implementation/version cache tag and possibly optimisation level. PEP 3147 standardised cache directories; PEP 488 refined optimisation tags; PEP 552 added hash-based invalidation modes.

A cache begins with versioned header information including a magic number and invalidation data, followed by a <code>marshal</code>-encoded code object graph. Timestamp-based caches compare source metadata; hash-based caches can validate a source hash according to checked/unchecked policy. Exact header widths and flags must be read from the target version’s import implementation or documented helpers.

~~~python
import importlib.util
import sys


source_path = "package/example.py"
cache_path = importlib.util.cache_from_source(
    source_path,
    optimization=sys.flags.optimize,
)
restored_source = importlib.util.source_from_cache(cache_path)

print(cache_path)
assert restored_source.endswith(source_path)
~~~

The example computes conventional paths without creating files. Cache use avoids parsing/compilation when validation succeeds; the module code still executes on the first import in that interpreter. <code>sys.modules</code>, not the <code>.pyc</code> file, normally prevents repeat execution on subsequent imports.

The <code>marshal</code> format is private to Python/CPython versions and not secure against malformed or malicious data. Code objects deserialised from it are executable. Never accept an untrusted bytecode cache as harmless data. Signed packages, filesystem permissions, reproducible builds, and source-distribution verification address different parts of the supply-chain problem.

### Worked example 15.29 — Compile a checked cache in an isolated temporary directory

~~~python
import importlib.util
import py_compile
from pathlib import Path
from tempfile import TemporaryDirectory


with TemporaryDirectory() as directory:
    root = Path(directory)
    source = root / "example.py"
    source.write_text("answer = 42\n", encoding="utf-8")

    cache = Path(
        importlib.util.cache_from_source(str(source))
    )
    py_compile.compile(
        str(source),
        cfile=str(cache),
        doraise=True,
        invalidation_mode=py_compile.PycInvalidationMode.CHECKED_HASH,
    )

    assert cache.is_file()
    assert cache.read_bytes()[:4] == importlib.util.MAGIC_NUMBER
~~~

The temporary directory makes the filesystem mutation bounded and automatically removable. Matching the leading magic bytes identifies compatibility with the running interpreter, not authenticity or safety.

### 15.18.4 Native modules need interpreter-aware initialisation

PEP 489 defines multi-phase initialisation for extension modules. A creation phase establishes the module object; execution slots initialise state. Per-module memory declared in the module definition can hold references separately for each module instance/interpreter. Traversal, clearing, and free callbacks integrate that state with lifetime management.

The design supports reload-like execution, subinterpreters, and module specifications more reliably than a legacy function returning one process-global module. It does not automatically make underlying third-party libraries multi-interpreter-safe. Extensions must declare whether they support multiple interpreters and whether they require the GIL using mechanisms available in the target release.

> **Common misconception 15.70 — “A pyc file is portable, trusted machine code that prevents the module from executing.”**  
> It is a version-specific cache of marshalled code objects. It accelerates compilation; import still executes code, validation is not authentication, and the physical CPU still runs the interpreter’s native code.
