# 15.2 From source bytes to an abstract syntax tree

CPython reads source bytes under encoding rules, tokenises decoded text, parses tokens according to the Python grammar, and constructs internal syntax representations. Public standard-library interfaces expose parts of this pipeline.

```python
import ast
import tokenize
from io import BytesIO


source = b"answer = left + right\n"

for token in tokenize.tokenize(BytesIO(source).readline):
    print(token.type, token.string)

tree = ast.parse(source, filename="example.py", mode="exec")
print(ast.dump(tree, indent=2))
```

`tokenize` exposes token records useful to tools while retaining lexical details such as comments and physical positions. `ast.parse` exposes an **abstract syntax tree** in which grammar structure is represented without every source punctuation detail.

The AST for the assignment contains a module node, assignment node, name target in store context, binary operation, two name operands in load context, and addition operator node. `Load` and `Store` are not machine reads/writes; they classify the role of a name or target in the syntax tree.

### Worked example 15.1 — Same value, different syntax trees

```python
import ast


ast.dump(ast.parse("result = 2 + 3 * 4"), indent=2)
ast.dump(ast.parse("result = (2 + 3) * 4"), indent=2)
```

The first tree nests multiplication as the right operand of addition. The second nests addition as the left operand of multiplication. Parentheses need not survive as a dedicated semantic node because their work was to change grouping during parsing.

Parsing establishes syntactic structure, not successful runtime name lookup or operand compatibility. Both `left + right` and `4 + "5"` form valid ASTs.

### 15.2.1 Source begins as bytes

A source file is a byte sequence. Before grammar can apply, the implementation determines an encoding and decodes bytes to Unicode source text. Python source defaults to UTF-8; an encoding declaration, when permitted and correctly placed, can name another codec. A UTF-8 byte-order mark is also recognised under the language’s encoding rules. Decoding failure occurs before tokenisation.

The <code>tokenize.detect_encoding</code> interface exposes this initial decision:

~~~python
from io import BytesIO
from tokenize import detect_encoding


examples = (
    b"answer = 42\n",
    b"# -*- coding: latin-1 -*-\nword = 'caf\xe9'\n",
    b"\xef\xbb\xbfanswer = 42\n",
)

for source in examples:
    encoding, consumed = detect_encoding(BytesIO(source).readline)
    print(encoding, consumed)
~~~

The returned consumed lines must be supplied again to a tokenizer using this low-level interface; detection has already read them. An editor displaying text successfully does not prove the interpreter selected the same codec. Source control should normally standardise UTF-8 and avoid visually confusable characters.

Line-ending recognition, indentation tabs, form feeds, and Unicode identifiers then enter lexical rules. The tokenizer is not merely splitting on spaces. It distinguishes indentation levels, line continuation, strings, numbers, names, operators, comments, and physical versus logical lines.

> **Common misconception 15.4 — “Python parses characters directly from the file.”**  
> A file supplies bytes. Encoding detection and Unicode decoding precede lexical and grammatical analysis, and either layer can fail independently.

### 15.2.2 Tokens retain lexical distinctions

Tokens classify source spans. Compare operator punctuation, names, indentation, and end markers:

~~~python
from io import BytesIO
from token import tok_name
from tokenize import tokenize


source = b"if amount >= 10:\n    total += amount  # account\n"

for item in tokenize(BytesIO(source).readline):
    print(
        tok_name[item.type],
        repr(item.string),
        item.start,
        item.end,
    )
~~~

The comment is available to <code>tokenize</code> but ordinarily absent from the semantic AST. Whitespace separating tokens is mostly not represented after parsing, whereas indentation is semantically significant and becomes <code>INDENT</code>/<code>DEDENT</code> structure. The tokenizer emits an encoding token for byte input and an end marker.

The standard <code>tokenize</code> module is designed principally for Python token streams and tools; exact error recovery differs from a full editor parser. Its <code>untokenize</code> operation guarantees that re-tokenising reproduces token type and string pairs, not original spacing.

> **Common misconception 15.5 — “The AST contains every detail in the source file.”**  
> Comments, most whitespace, quote style, redundant parentheses, and some lexical distinctions are discarded or normalised. Tools requiring exact formatting need a concrete-syntax representation or token preservation.

### 15.2.3 Grammar constructs structure

CPython 3.12’s parser is generated from a Parsing Expression Grammar (**PEG**) grammar, a mechanism adopted through PEP 617. Grammar productions recognise valid arrangements of tokens and construct internal syntax values leading to AST nodes. This is a versioned CPython implementation of Python grammar; the language reference defines syntax at a different authority level.

A **concrete syntax tree** preserves grammar and punctuation structure closely. An **abstract syntax tree** discards details that do not affect the later semantic representation and labels meaningful roles. In the expression \(result=(2+3)\times4\), parentheses determine grouping but need not remain as a node. The resulting multiplication node contains an addition node as its left operand.

Parsing establishes syntactic well-formedness, not successful execution. A parsed name can be unbound later. A call can target a non-callable object. An addition can receive incompatible operands. Conversely, some constraints described as syntax errors are detected in later compiler validation rather than token recognition alone; “syntax error” names the user-facing category, not necessarily one internal phase.

### 15.2.4 AST contexts identify roles

Names and compound targets carry context nodes such as <code>Load</code>, <code>Store</code>, and <code>Del</code>:

~~~python
import ast


tree = ast.parse(
    """
value = source
items[index] = value
del obsolete
"""
)

for node in ast.walk(tree):
    if isinstance(node, ast.Name):
        print(node.id, type(node.ctx).__name__)
~~~

The context expresses syntactic use. It is not a direct instruction to read or write a physical memory address. <code>items[index] = value</code> gives <code>items</code> and <code>index</code> load roles while the subscription target has store context; runtime assignment invokes the subscription protocol.

Assignment targets can be patterns of names, starred targets, attributes, and subscriptions. Their evaluation ordering and failure semantics belong to language rules. AST structure allows a compiler or static analyser to distinguish these roles before any objects exist.

> **Common misconception 15.6 — “An AST Store node is the location where a value is stored.”**  
> It labels a target’s syntactic role. Symbol analysis and runtime object protocols later decide local binding, global binding, attribute assignment, or subscription mutation.

### 15.2.5 Source locations are ranges, not decorations

AST statement and expression nodes expose line and column location fields when available. In CPython, column offsets are UTF-8 byte offsets in the parser’s internal source representation, not necessarily Unicode character indices. PEP 657 added end locations and fine-grained expression positions used in richer tracebacks.

~~~python
import ast


source = "résultat = price + tax\n"
tree = ast.parse(source)
assignment = tree.body[0]
assert isinstance(assignment, ast.Assign)
expression = assignment.value

segment = ast.get_source_segment(source, expression)
print(expression.lineno, expression.col_offset)
print(expression.end_lineno, expression.end_col_offset)
print(segment)
~~~

Consumers should use <code>ast.get_source_segment</code> or documented position handling rather than slicing Unicode strings with byte offsets. Location data can be absent on constructed nodes. <code>ast.fix_missing_locations</code> propagates necessary positions when compiling transformed trees, but it cannot reconstruct exact original spans that never existed.

### 15.2.6 Parse modes define the expected root

<code>ast.parse</code> and <code>compile</code> accept modes:

- <code>exec</code> expects a suite of statements and produces a module-like root;
- <code>eval</code> expects one expression;
- <code>single</code> supports interactive statement behaviour;
- <code>func_type</code> exists for legacy function type-comment syntax in the AST interface.

~~~python
import ast


module_tree = ast.parse("x = 1", mode="exec")
expression_tree = ast.parse("x + 1", mode="eval")
interactive_tree = ast.parse("x + 1", mode="single")

print(type(module_tree).__name__)
print(type(expression_tree).__name__)
print(type(interactive_tree).__name__)
~~~

Mode changes structure and later code-generation behaviour. It is not a request to reinterpret arbitrary invalid input. An assignment is invalid in <code>eval</code> because it is a statement, while an assignment expression has its own grammar.

### 15.2.7 Transforming ASTs preserves obligations

An <code>ast.NodeTransformer</code> can return replacement nodes. The result must satisfy the compiler’s structural invariants, contain appropriate contexts, and carry acceptable locations:

~~~python
import ast


class ReplaceName(ast.NodeTransformer):
    def __init__(self, old: str, new: str) -> None:
        self.old = old
        self.new = new

    def visit_Name(self, node: ast.Name) -> ast.AST:
        if node.id != self.old:
            return node
        replacement = ast.Name(id=self.new, ctx=node.ctx)
        return ast.copy_location(replacement, node)


tree = ast.parse("result = source + 1")
transformed = ReplaceName("source", "input_value").visit(tree)
transformed = ast.fix_missing_locations(transformed)
code = compile(transformed, "<transformed>", "exec")

namespace = {"input_value": 9}
exec(code, namespace)
assert namespace["result"] == 10
~~~

Copying <code>ctx</code> preserves load/store role. Copying location preserves diagnostics. Executing transformed untrusted input is still arbitrary code execution; AST filtering is not automatically a secure sandbox because Python’s object model offers many indirect capabilities.

> **Common misconception 15.7 — “If source has been converted to an AST, it is safe data.”**  
> An AST can represent imports, calls, attribute access, resource exhaustion, and arbitrary program effects. Structural representation does not remove authority.
