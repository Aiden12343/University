# 15.20 Reading CPython source responsibly

When investigating implementation:

1. identify exact CPython version, commit, build flags, and platform;
2. begin from a language-visible experiment and disassembly;
3. locate the public C API or internal function reached in that version;
4. distinguish generated code, macros, stable API, limited API, and private internals;
5. trace ownership and exception paths, not only success;
6. verify hypotheses with debug builds, tests, or instrumentation;
7. report findings as implementation-scoped.

Source comments can be outdated or local; tests and behaviour add evidence. One opcode name does not explain user-visible semantics without following specialisation and fallback paths.

### 15.20.1 Start with a falsifiable language-visible question

“Understand <code>dict</code>” is not a bounded investigation. “In CPython 3.12.13, which paths execute when an exact string key already exists in a combined-table dictionary, and which user-visible operations can run?” is answerable. It identifies version, operand class, state, and observables. Before opening the source, write competing predictions and the experiment that distinguishes them.

A useful research record begins with:

- executable version, commit if available, build flags, compiler, and platform;
- minimal source reproducer and exact command;
- expected language semantics from the reference;
- public observations from <code>ast</code>, <code>symtable</code>, <code>dis</code>, <code>inspect</code>, <code>gc</code>, or a profiler;
- the unresolved mechanism question;
- success, error, re-entrancy, and ownership paths to trace.

This ordering prevents a source function’s evocative name from determining the hypothesis. It also detects when no internal research is necessary because a documented public contract already answers the engineering question.

### Worked example 15.31 — Build a reproducible inspection dossier

~~~python
from __future__ import annotations

import ast
import dis
import hashlib
import json
import platform
import symtable
import sys
from collections.abc import Callable


def inspect_source(source: str, function_name: str) -> dict[str, object]:
    tree = ast.parse(source, filename="<dossier>")
    symbols = symtable.symtable(source, "<dossier>", "exec")
    namespace: dict[str, object] = {}
    exec(compile(tree, "<dossier>", "exec"), namespace)

    candidate = namespace[function_name]
    if not callable(candidate):
        raise TypeError(f"{function_name!r} is not callable")
    function: Callable[..., object] = candidate

    return {
        "sha256": hashlib.sha256(source.encode()).hexdigest(),
        "python": sys.version,
        "implementation": platform.python_implementation(),
        "ast": ast.dump(tree, include_attributes=True),
        "symbols": [
            {
                "name": child.get_name(),
                "identifiers": list(child.get_identifiers()),
            }
            for child in symbols.get_children()
        ],
        "instructions": [
            {
                "offset": item.offset,
                "opname": item.opname,
                "argrepr": item.argrepr,
                "positions": tuple(item.positions),
            }
            for item in dis.get_instructions(function)
        ],
    }


if __name__ == "__main__":
    report = inspect_source(
        "def add(left, right):\n    return left + right\n",
        "add",
    )
    print(json.dumps(report, indent=2))
~~~

This tool executes the supplied source and therefore accepts only trusted input. It records a digest, environment, syntax tree, high-level symbols, and structured disassembly. A fuller dossier records optimisation flags, cache/adaptive settings, executable path, environment variables, source commit, and workload. JSON serialisation of resolved <code>argval</code> is intentionally avoided because it can contain code objects or other non-JSON values.

### 15.20.2 Navigate the repository by subsystem and symbol flow

In a CPython 3.12 source tree, common starting regions include:

| Region | Typical subject |
|:---|:---|
| <code>Grammar/</code>, <code>Parser/</code> | grammar inputs, PEG parser, tokenisation, AST construction |
| <code>Python/</code> | compiler, symbol table, evaluator, imports, errors, interpreter lifecycle |
| <code>Objects/</code> | built-in object representations and protocol implementations |
| <code>Include/</code> | public, cpython-specific, and internal declarations |
| <code>Modules/</code> | built-in/extension modules, including GC implementation in selected versions |
| <code>Lib/</code> | Python standard-library code and tests’ dependencies |
| <code>Lib/test/</code> | regression and semantic tests |
| <code>Tools/</code> | generators, analysis, build, and maintenance tools |
| <code>Doc/</code> | language, library, C API, how-to, and development documentation sources |

Exact file placement changes. Search the checked-out version with <code>rg</code>, beginning from a public symbol, opcode name, slot, error text fragment, or test name. Follow declarations to callers and callees. For generated interpreter code, identify both the generated artefact compiled by the build and the definition/generator that owns the change.

A disciplined path for an operation is:

1. disassemble the minimal example and identify the version-specific opcode;
2. locate its semantic definition or generated case;
3. follow the fast-path guard and every fallback;
4. identify helper calls that can execute user code or fail;
5. annotate ownership of every consumed/produced reference;
6. locate tests for exact types, subclasses, errors, tracing, and concurrency;
7. change one condition and verify the predicted path in an instrumented build.

Reading only the successful exact-type branch produces dangerously incomplete explanations. The fallback is often where the language’s extensibility lives.

### 15.20.3 Headers encode stability boundaries

CPython headers distinguish stable/limited API declarations, normal public C API, CPython-specific API, and private internal declarations. A leading underscore often signals privacy but is not the only indicator. Documentation and preprocessor guards establish the supported boundary.

The **limited API** lets an extension compile against a deliberately restricted surface; the **stable ABI** permits compatible binaries across multiple Python 3 releases for supported platforms and ABI versions. Neither promises identical performance or availability of every new feature. Extensions using internal structures gain flexibility/performance at the cost of rebuilding and auditing per CPython release.

Macros can evaluate arguments more than once, omit checks, or expose layout in full-API builds. Stable-ABI forms may be actual function calls. Never infer ownership or error behaviour from capitalization. Consult the specific declaration and C API documentation, then inspect implementation only to answer mechanism questions.

### 15.20.4 Build configurations are experimental instruments

A debug build enables assertions and reference/memory diagnostics that release builds omit. Sanitizer builds expose invalid memory, undefined behaviour, and races. Profile-guided and link-time-optimised release builds answer performance questions closer to production. One configuration cannot answer all three.

A typical source investigation maintains at least:

- an unmodified release build for baseline behaviour;
- a debug build for assertions and allocator diagnostics;
- a minimally instrumented build with counters/logging at the hypothesised path;
- where relevant, AddressSanitizer, UndefinedBehaviorSanitizer, or ThreadSanitizer builds;
- conventional-GIL and free-threaded builds for concurrency claims.

Instrumentation must avoid recursion. Printing from allocation, reference-count, signal, or import internals can itself allocate, acquire locks, or import encodings. Prefer fixed-size counters, debugger breakpoints, low-level writes under safe conditions, and existing tracing facilities. Verify that the instrumentation did not select a different path.

Tests should run narrowly first and broadly before drawing a conclusion. A local CPython change can pass the one reproducer yet violate stable ABI, debug-reference, subinterpreter, platform, endianness, or free-threaded tests. Build-generated files must be regenerated with repository tooling rather than hand-edited alone.

### 15.20.5 History explains decisions but does not itself specify current behaviour

Version control supplies the commit introducing a line, its review discussion, linked issue, benchmarks, and prior designs. <code>git blame</code> is an index into history, not a judgement assigning fault and not proof that the last editor designed the surrounding invariant. Refactors can move lines without preserving useful attribution; search commits and surrounding tests.

PEPs vary in status and role. A final accepted PEP explains a design, but implementation details can evolve after acceptance. A rejected or deferred PEP is valuable historical argument, not a contract. The current language/C API documentation and tests establish supported behaviour more directly; source establishes current mechanism.

Academic papers and books contribute general concepts—abstract machines, compiler data flow, garbage collection, inline caching, memory allocation—but cannot be presumed to describe the current code. Use them to formulate mechanisms and asymptotic expectations, then verify CPython’s actual adaptation.

### 15.20.6 Report negative knowledge explicitly

A rigorous internal report states what it did not establish. Examples:

- the exact native instruction path was not measured;
- the specialised form appeared only for exact integers;
- the allocator experiment did not include extension allocations;
- the debug build changed timing;
- the result was not tested on Windows or a 32-bit target;
- no claim is made for CPython 3.13 or PyPy;
- a source comment suggests an invariant, but no public guarantee was found.

This is not rhetorical caution; it delineates the proposition. Reproducibility means another researcher can recreate the observation envelope and discover the same boundary, including disagreement.

> **Common misconception 15.72 — “Reading the current implementation file is sufficient to establish a complete CPython fact.”**  
> Generated inputs, headers, callers, fallbacks, error paths, ownership, tests, build flags, history, and experiment all contribute. A source line without its version and contract boundary is incomplete evidence.

### 15.20.7 Capstone checklist

Before relying on an internal claim, answer:

1. Which language-visible behaviour is being explained?
2. Is the statement language, public interface, private implementation, or observation?
3. Which exact version, commit, build, platform, and runtime mode?
4. What are the minimal success and failure reproducers?
5. Which compiler metadata and instruction sites are involved?
6. Which types, slots, guards, caches, and fallbacks participate?
7. Where can arbitrary Python code re-enter?
8. Who owns every reference at each boundary?
9. How are exceptions indicated, propagated, and cleared?
10. Which frames, tracebacks, cells, or caches extend lifetime?
11. Which allocator and memory metric support the memory claim?
12. What synchronisation protects the semantic invariant?
13. Which public documentation and tests support the boundary?
14. Which alternative implementation could satisfy the same semantics differently?
15. What observation would falsify the proposed mechanism?
