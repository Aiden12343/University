# 15.3 Symbol-table analysis and scope classification

Before code execution, the compiler determines how names are scoped within code blocks. Assignment, parameter declarations, `global`, `nonlocal`, comprehensions, and nested function references contribute to this analysis.

```python
import symtable


source = """
rate = 2

def outer(offset):
    def inner(value):
        return value * rate + offset
    return inner
"""

table = symtable.symtable(source, "example.py", "exec")
```

The symbol table classifies `rate` as module-global; `offset` as local to `outer` and free in `inner`; `value` as local to `inner`. A variable referenced by nested code may require **cell** storage so closures can retain its binding after the defining frame returns. In the nested code it is a **free variable**.

This compile-time classification explains `UnboundLocalError`: a name assigned in a function is classified local unless declared otherwise, so an earlier read does not dynamically fall back to global state.

### 15.3.1 Blocks are compiler units, not merely indented regions

A **code block** is a region whose name bindings are analysed together. A module is a block; a function body is a block; a class body is a block; the implicit function-like scopes created for comprehensions and generator expressions are blocks; code passed to <code>eval</code> or <code>exec</code> is compiled as a block appropriate to its mode. An indented suite is not necessarily a new block. The body of an <code>if</code>, <code>for</code>, <code>while</code>, <code>with</code>, or <code>try</code> statement remains in the surrounding block.

This distinction explains why a loop target remains available after an ordinary loop but a comprehension target does not leak into its surrounding function in modern Python:

~~~python
def compare_blocks() -> tuple[int, bool]:
    for ordinary in range(3):
        pass

    squares = [hidden * hidden for hidden in range(3)]
    return ordinary, "hidden" in locals()


assert compare_blocks() == (2, False)
~~~

The list-comprehension machinery has its own implicit execution scope. The name <code>hidden</code> is local to that scope. The ordinary loop introduces no scope, so <code>ordinary</code> remains a local binding of <code>compare_blocks</code>. A block is therefore a compiler and namespace concept, not a visual indentation concept.

Exception-handler targets have another rule. After an <code>except ... as error</code> suite, the target is cleared so the exception, traceback, frame, and locals are less likely to remain in a cycle. Clearing a target is not creation of a separate block:

~~~python
def handler_target() -> bool:
    try:
        raise ValueError("invalid")
    except ValueError as problem:
        assert str(problem) == "invalid"

    return "problem" in locals()


assert handler_target() is False
~~~

Structural pattern matching likewise does not create a scope. Names captured by a successful pattern belong to the surrounding block. Programs should not depend on bindings left by a failed partial match because the language permits implementation variation in that case.

> **Common misconception 15.8 — “Every indented suite creates a scope.”**  
> Indentation groups statements syntactically. Only specified constructs create code blocks and corresponding scope analysis; ordinary conditional, loop, context-manager, and exception suites do not.

### 15.3.2 Classification is static within a block

The compiler determines a name’s binding class from the entire block before the block executes. It does not choose local or global lookup according to which branch happens to run. Assignment targets, parameters, imports, function and class definitions, exception targets, pattern captures, and assignment expressions can all establish local bindings. A <code>del</code> target also participates in classification because deleting a local still addresses that block’s binding.

Consider:

~~~python
status = "module"


def read_then_assign(flag: bool) -> str:
    if flag:
        status = "local"
    return status
~~~

The presence of the assignment classifies <code>status</code> as local throughout <code>read_then_assign</code>. Calling <code>read_then_assign(True)</code> returns the local string. Calling it with <code>False</code> reaches a local read before any value was assigned and raises <code>UnboundLocalError</code>. Runtime control flow does not cause the read to fall back to the module binding.

The exception is a subclass of <code>NameError</code>, but the distinction is informative: the compiler selected local access, and that local slot currently has no value. A plain unresolved global or built-in lookup ordinarily produces <code>NameError</code> instead.

The public <code>symtable</code> module exposes compiler symbol analysis without executing the source:

~~~python
import symtable


source = """
status = 'module'

def read_then_assign(flag):
    if flag:
        status = 'local'
    return status
"""

root = symtable.symtable(source, "scope_demo.py", "exec")
function_table = next(
    child for child in root.get_children()
    if child.get_name() == "read_then_assign"
)

for identifier in function_table.get_identifiers():
    symbol = function_table.lookup(identifier)
    print(
        identifier,
        "parameter=" + str(symbol.is_parameter()),
        "local=" + str(symbol.is_local()),
        "global=" + str(symbol.is_global()),
        "free=" + str(symbol.is_free()),
    )
~~~

The interface reports compiler decisions such as parameter, imported, assigned, referenced, local, global, nonlocal, and free status. The exact table classes and newly exposed flags can evolve, so an analysis tool should state its supported Python versions. The public interface is preferable to reverse-engineering private compiler structures.

> **Common misconception 15.9 — “Python decides whether a variable is local when execution reaches an assignment.”**  
> Scope classification is performed for the complete block during compilation. A conditional assignment can therefore make every use in that block local even on paths where the assignment never executes.

### 15.3.3 Local, global, free, and cell are relational categories

A parameter or binding introduced in a function is ordinarily **local** to that function. A name resolved in the module namespace is **global** from a function’s point of view; this includes a name explicitly declared <code>global</code> and a referenced name for which no enclosing function binding is found. A name used by a nested function and supplied by an enclosing function scope is **free** in the nested function. The corresponding enclosing binding must be made available through a **cell**.

Cell and free therefore describe the same lexical relationship from opposite sides:

~~~python
def make_accumulator(start: int):
    total = start

    def add(amount: int) -> int:
        nonlocal total
        total += amount
        return total

    return add


accumulate = make_accumulator(10)
assert accumulate(4) == 14
assert accumulate(3) == 17

outer_code = make_accumulator.__code__
inner_code = accumulate.__code__
print(outer_code.co_cellvars)
print(inner_code.co_freevars)
print(accumulate.__closure__)
~~~

In a typical CPython 3.12 build, <code>total</code> occurs in the outer code object’s <code>co_cellvars</code> and the inner code object’s <code>co_freevars</code>. The function object’s <code>__closure__</code> tuple contains cell objects corresponding positionally to <code>co_freevars</code>. The closure does not contain a frozen copy of the integer. It carries access to a binding cell; augmented assignment replaces the cell’s referenced integer.

The initial parameter <code>start</code> need not become a cell because the nested function does not reference it. A compiler can store an ordinary local and a captured local differently while the source-level rule remains lexical binding.

The <code>global</code> declaration directs bindings in the current block to the module namespace. The <code>nonlocal</code> declaration directs them to an already existing binding in a lexically enclosing function scope:

~~~python
counter = 0


def install_counter():
    counter = 100

    def use_nonlocal() -> int:
        nonlocal counter
        counter += 1
        return counter

    def use_global() -> int:
        global counter
        counter += 10
        return counter

    return use_nonlocal, use_global


nearby, module_level = install_counter()
assert nearby() == 101
assert module_level() == 10
~~~

The declarations are compile-time directives for a block, not runtime lookup functions. They must appear under syntax restrictions before conflicting uses or bindings in that block. <code>nonlocal</code> cannot invent a binding and cannot target the module scope; a matching enclosing function binding must exist.

The LEGB mnemonic from Chapter 8 remains useful—local, enclosing, global, built-ins—but must not be mistaken for four dictionaries searched identically for every name. Compilation chooses specialised access categories. Locals may occupy indexed frame storage; free names use cells; globals and built-ins follow namespace lookup machinery. The mnemonic describes resolution order at the language level, while bytecode and storage explain CPython’s mechanism.

> **Common misconception 15.10 — “A closure captures the current value of each outer variable.”**  
> A CPython closure normally retains cells representing lexical bindings. Later rebinding through <code>nonlocal</code> is visible to every closure sharing the cell; this is the mechanism beneath late-binding behaviour.

### 15.3.4 Several closures can share one cell

One invocation of an outer function creates one family of captured cells. Sibling closures returned from that invocation can share them; a second invocation creates an independent family:

~~~python
from collections.abc import Callable


def make_pair() -> tuple[Callable[[], int], Callable[[], int]]:
    state = 0

    def increment() -> int:
        nonlocal state
        state += 1
        return state

    def read() -> int:
        return state

    return increment, read


increment_a, read_a = make_pair()
increment_b, read_b = make_pair()

assert increment_a() == 1
assert read_a() == 1
assert read_b() == 0

cell_from_increment = increment_a.__closure__[0]
cell_from_read = read_a.__closure__[0]
assert cell_from_increment is cell_from_read
~~~

The positional index used in the last lines is an observation tied to <code>co_freevars</code>; robust introspection pairs the names and cells rather than assuming index zero:

~~~python
def make_reader(value: object):
    def read() -> object:
        return value

    return read


def closure_bindings(function) -> dict[str, object]:
    cells = function.__closure__ or ()
    return {
        name: cell.cell_contents
        for name, cell in zip(function.__code__.co_freevars, cells, strict=True)
    }


reader = make_reader(1)
assert closure_bindings(reader) == {"value": 1}
~~~

Reading <code>cell_contents</code> can invoke representations later if printed, and cells can be empty during unusual construction or after deletion of a nonlocal binding. Introspection observes live state and can retain it.

### 15.3.5 Class bodies deliberately differ from enclosing function scopes

A class statement executes its body to populate a namespace, but that namespace is not an enclosing lexical function scope for methods. An unqualified name in a method does not normally resolve through the class dictionary. Attribute access through the instance or class performs that operation at runtime:

~~~python
unit = "module"


class Measurement:
    unit = "millisecond"

    def misleading(self) -> str:
        return unit

    def explicit(self) -> str:
        return self.unit


sample = Measurement()
assert sample.misleading() == "module"
assert sample.explicit() == "millisecond"
~~~

The class body has special compiler behaviour for the implicit <code>__class__</code> cell when a method requires it, as with zero-argument <code>super()</code> or direct <code>__class__</code> use. This special case does not turn arbitrary class attributes into closure variables.

Comprehensions inside class bodies expose another consequence. Their implicit scope does not ordinarily treat the class namespace as an enclosing function scope. Code that tries to refer to a class-local name from the comprehension can therefore fail even though a sequential statement in the class body can read it. Prefer computing such values before the class statement, after class creation, or with an explicit construction whose resolution is unambiguous.

Annotation scopes and lazy annotation evaluation have evolved in Python 3.12 and later. A tool that classifies names in type aliases, generic parameter lists, or annotations must target the appropriate language version rather than extrapolating ordinary function rules. This chapter’s central principle applies: the language reference defines each scope category; <code>symtable</code> exposes the selected compiler’s analysis.

> **Common misconception 15.11 — “A class namespace encloses the lexical scope of every method and comprehension written inside it.”**  
> Methods normally resolve unqualified free names through enclosing function scopes, then the module and built-ins—not through the class dictionary. Class attributes are reached through attribute lookup, subject to a few explicitly specified compiler mechanisms such as <code>__class__</code> cells.

### 15.3.6 Dynamic execution cannot retroactively change compiled access

The built-ins <code>exec</code> and <code>eval</code> compile new source under documented namespace arguments. They do not rewrite the containing function’s already compiled local-access plan. Consequently, attempting to inject an optimised local with <code>exec</code> and then reading it through precompiled local bytecode is not a sound technique:

~~~python
def dynamic_namespace() -> tuple[bool, object]:
    namespace: dict[str, object] = {}
    exec("created = 41 + 1", {}, namespace)
    return "created" in namespace, namespace["created"]


assert dynamic_namespace() == (True, 42)
~~~

An explicit dictionary makes the data flow and authority boundary visible. Executing untrusted source remains arbitrary code execution even when globals and locals mappings are supplied; built-ins, object capabilities, denial of service, and implementation escape routes make ad hoc namespace restriction an inadequate security boundary.

Symbol analysis completes a crucial transition. The AST says where a name syntactically loads or stores. The symbol table decides what kind of binding that use denotes within each block. Code generation can then select instructions and metadata appropriate to locals, cells, globals, attributes, and subscriptions. None of these phases needs the eventual runtime values.
