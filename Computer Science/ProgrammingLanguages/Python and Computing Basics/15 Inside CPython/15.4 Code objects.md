# 15.4 Code objects

CPython compilation produces **code objects**, immutable objects containing executable bytecode and metadata. A function object combines a code object with globals, defaults, annotations, closure cells, and other runtime attributes.

```python
def add(left: int, right: int = 1) -> int:
    result = left + right
    return result


code_object = add.__code__
print(code_object.co_name)
print(code_object.co_argcount)
print(code_object.co_varnames)
print(code_object.co_consts)
print(add.__defaults__)
```

Distinctions:

- `co_varnames` contains names associated with local variables and parameters under CPython’s code-object layout.
- `co_consts` contains literal and compiler-created constant objects referenced by the code.
- parameter default object `1` is stored on the function object in `__defaults__`, because defaults are evaluated when the function definition executes, not on every function-body call.
- annotations are associated with the function under the active annotation semantics, not simply elements of `co_varnames`.

The order and inclusion details of `co_consts` are compiler implementation details. A common compiler may include `None` for an implicit return path and arrange constants in discovery or compiler-determined order, but portable code must not interpret tuple position as a source-level guarantee. Constant folding can add, remove, or replace entries between versions.

### Worked example 15.2 — Constant versus local name

```python
def demonstrate() -> int:
    x = 5
    y = x + 3
    return y
```

Literal objects such as 5 and 3 are candidates for `co_consts`. Names `x` and `y` belong to local-variable metadata. `y` is not “stored in `co_consts`” because `co_consts` is not the function’s runtime variable storage; it is immutable metadata listing constants referenced by the compiled code. On each call, the frame provides storage for current local bindings.

The expression `x + 3` cannot generally be folded to 8 because `x` is a runtime local binding, even though this source appears to assign 5 immediately before. Optimisation must preserve tracing, exception, dynamic execution, and compiler-policy semantics and is not required to perform arbitrary data-flow proof. By contrast, `5 + 3` may be folded because both operands are compile-time constants under applicable rules.

The word **constant** here means a value embedded in compiled code metadata, not a promise that the same mathematical value can never appear elsewhere or that a referenced object is recursively immutable in every context. Code-object constants themselves must be suitable for the compiler’s immutable code representation.

### 15.4.1 Code, function, and frame answer different lifetime questions

Three objects that beginners often conflate have distinct roles:

| Object | Represents | Usually exists when |
|:---|:---|:---|
| code object | compiled instructions and metadata for a block | compilation completes and an enclosing code object retains it |
| function object | a callable binding of code to globals, defaults, closure, and attributes | a function definition or construction executes |
| frame or interpreter-frame state | one active or suspended execution of code | the callable is invoked or execution is suspended |

One code object can be shared by many function objects, and one function can generate many frames through repeated or recursive calls. The following deliberately constructs two functions over one code object but different global namespaces:

~~~python
from types import FunctionType


def template() -> str:
    return greeting


english = FunctionType(
    template.__code__,
    {"greeting": "hello"},
    "english",
)
french = FunctionType(
    template.__code__,
    {"greeting": "bonjour"},
    "french",
)

assert english.__code__ is french.__code__
assert english() == "hello"
assert french() == "bonjour"
~~~

The code object classifies <code>greeting</code> as a global name but does not contain the namespace value selected for each function. The function carries a reference to its globals mapping. Each call supplies a separate execution state. Direct <code>FunctionType</code> construction is useful for study but ordinary programs should prefer definitions, closures, modules, and documented callable abstractions.

A nested function’s code object exists as a constant in the enclosing code object before a nested function object exists. Repeated execution of the <code>def</code> statement can therefore create new function objects sharing compiled code:

~~~python
def factory(offset: int):
    def shift(value: int) -> int:
        return value + offset

    return shift


shift_one = factory(1)
shift_two = factory(2)

assert shift_one.__code__ is shift_two.__code__
assert shift_one.__closure__ != shift_two.__closure__
assert shift_one(10) == 11
assert shift_two(10) == 12
~~~

The functions share instructions but have distinct cells containing distinct outer bindings. This separation is essential to understanding defaults, decorators, recursion, and closure state.

> **Common misconception 15.12 — “A function and its code object are the same thing.”**  
> A code object is context-free compiled metadata. A function adds a globals namespace, defaults, closure cells, annotations, name information, and mutable attributes; a call creates separate execution state.

### 15.4.2 Code objects are immutable but refer to other objects

Code objects are immutable in the sense that their exposed attributes cannot be reassigned in place and their instruction representation is fixed after construction. Immutability permits sharing and reasoning about compiled blocks. It does not imply that every object reachable from every metadata field is a mathematically primitive scalar, nor does it make arbitrary manually constructed code safe.

The documented <code>code.replace</code> method creates a new code object with specified fields changed, rather than mutating the original. Field names, invariants, and bytecode encodings remain version-sensitive:

~~~python
def labelled() -> int:
    return 7


original = labelled.__code__
renamed = original.replace(co_name="renamed_body")

assert original.co_name == "labelled"
assert renamed.co_name == "renamed_body"
assert original is not renamed
assert original.co_code == renamed.co_code
~~~

Changing the diagnostic name alone leaves the byte sequence unchanged, but indiscriminate replacement of constants, local counts, stack size, exception tables, or line tables can violate interpreter invariants or crash unsupported consumers. A code object is executable authority. Deserialising or installing one from an untrusted source is equivalent in risk to accepting code.

The <code>types.CodeType</code> constructor has changed repeatedly as metadata evolved. Positional construction tightly couples code to an exact interpreter version. AST transformation followed by <code>compile</code> lets the compiler re-establish its own invariants and is usually the correct level for program transformation.

> **Common misconception 15.13 — “Because code objects are immutable, editing their bytes through reconstruction is a safe public metaprogramming interface.”**  
> Immutability prevents in-place alteration; it does not stabilise bytecode formats or validate arbitrary field combinations. Reconstructed code remains version-coupled executable data.

### 15.4.3 Metadata partitions names by intended mechanism

Several tuples make compiler decisions observable:

- <code>co_varnames</code> identifies parameters and local-variable names in compiler-defined order;
- <code>co_cellvars</code> identifies locals represented through cells for nested access;
- <code>co_freevars</code> identifies enclosing cells expected by the code;
- <code>co_names</code> lists names used by operations such as global, attribute, method, and import access;
- <code>co_consts</code> lists embedded constants, including nested code objects where applicable;
- <code>co_filename</code>, <code>co_name</code>, <code>co_qualname</code>, and first-line/position data support diagnostics and introspection.

These are tables addressed by encoded operands in the instruction stream. They do not all correspond one-to-one with source spelling, and identical names or constants can be deduplicated. Inspect them by meaning, not by relying on a remembered tuple index:

~~~python
from types import CodeType


RATE = 4


def build(prefix: str):
    suffix = "!"

    def format_value(value: int) -> str:
        scaled = value * RATE
        return prefix + str(scaled) + suffix

    return format_value


function = build("value=")
code = function.__code__

print("locals", code.co_varnames)
print("free", code.co_freevars)
print("cells", code.co_cellvars)
print("other names", code.co_names)
print("constants", code.co_consts)

nested_codes = tuple(
    constant
    for constant in build.__code__.co_consts
    if isinstance(constant, CodeType)
)
assert function.__code__ in nested_codes
~~~

In the inner block, <code>value</code> and <code>scaled</code> are locals; <code>prefix</code> and <code>suffix</code> are free variables; <code>RATE</code> and <code>str</code> require global/built-in lookup; the attribute tables do not themselves hold the eventual objects. The outer code has cells because it supplies captured bindings.

<code>co_nlocals</code> counts ordinary local-variable entries represented in corresponding local metadata. CPython 3.12 internally uses a broader locals-plus layout that can include local, cell, and free entries, but private index calculations should not be inferred solely from these public tuples. The frame section will separate public observability from internal storage.

Names in <code>co_names</code> include more than module globals. The same table can index attribute names and other name-bearing operations. Thus membership in <code>co_names</code> does not prove which namespace will be consulted; disassembly supplies the instruction context.

### 15.4.4 Constants record compiler output, not a source ledger

The compiler may intern, deduplicate, canonicalise, or fold literal expressions according to version-specific rules. It also emits implicit constants, commonly <code>None</code> for a fall-through return, and nested code objects. A function docstring, when retained, is commonly represented as the first constant under documented introspection conventions; optimisation settings can remove assertion or docstring information.

Compare compilation levels without assuming a particular tuple layout:

~~~python
source = '''
"""Module documentation."""
assert 2 + 2 == 4
answer = 10 * 20
'''

normal = compile(source, "example.py", "exec", optimize=0)
without_asserts = compile(source, "example.py", "exec", optimize=1)
without_docstrings = compile(source, "example.py", "exec", optimize=2)

for code in (normal, without_asserts, without_docstrings):
    print(code.co_consts)
~~~

The precise output is an experiment for the selected build. The semantic guarantees are narrower: optimisation level can affect assertions and docstrings as documented; constant folding must not change required ordinary behaviour. An analysis must distinguish absence from <code>co_consts</code> due to folding from absence because a value is produced at runtime.

Mutable literals are not stored as one reusable mutable object in <code>co_consts</code>. A list display must create a new list at runtime where the language requires a fresh object. Immutable container constants can be represented in implementation-selected ways when observable semantics permit it.

~~~python
def new_list() -> list[int]:
    return [1, 2, 3]


first = new_list()
second = new_list()
assert first == second
assert first is not second
~~~

If a compiler reused one mutable list here, mutation through <code>first</code> would incorrectly alter <code>second</code>. The compiled constants may supply element values while an instruction builds the list during each call.

> **Common misconception 15.14 — “Every source literal appears unchanged and once in co_consts.”**  
> Constants are compiler products. Folding, deduplication, nested code, implicit returns, optimisation levels, and runtime construction can all change what appears and how often.

### 15.4.5 Flags and structural requirements

<code>co_flags</code> is a bit field: individual bits describe properties such as optimised locals, creation of a new locals namespace, variable positional or keyword parameters, generator/coroutine status, and selected future features. Interpret named bits through documented constants rather than unexplained decimal masks:

~~~python
import inspect


def ordinary(value: int) -> int:
    return value


def generated():
    yield 1


async def coroutine() -> int:
    return 1


for function in (ordinary, generated, coroutine):
    flags = function.__code__.co_flags
    labels = [
        name
        for name, bit in inspect.__dict__.items()
        if name.startswith("CO_")
        and isinstance(bit, int)
        and flags & bit
    ]
    print(function.__name__, sorted(labels))
~~~

Some flag bits are CPython-facing documentation rather than cross-implementation semantics. A generator remains a generator by language behaviour regardless of whether another implementation exposes an identical bit mask.

The compiler also computes <code>co_stacksize</code>, the maximum evaluation-stack space required under its control-flow analysis. This is not the number of Python call frames, native stack bytes, local variables, or objects allocated. Exception handling and branch joins contribute to valid stack-depth analysis.

Argument-count fields require careful interpretation. <code>co_argcount</code> includes positional-only and positional-or-keyword parameters; <code>co_posonlyargcount</code> identifies the positional-only prefix; <code>co_kwonlyargcount</code> counts keyword-only parameters. Variadic parameters are identified by flags and positions within local-name metadata. The <code>inspect.signature</code> interface usually provides the correct semantic view for call binding:

~~~python
import inspect


def signature_case(
    first: int,
    /,
    second: int = 2,
    *values: int,
    scale: int = 1,
    **options: object,
) -> int:
    return (first + second + sum(values)) * scale


print(inspect.signature(signature_case))
print(signature_case.__code__.co_argcount)
print(signature_case.__code__.co_posonlyargcount)
print(signature_case.__code__.co_kwonlyargcount)
~~~

### 15.4.6 Source positions and exception regions are executable metadata

Modern code objects encode fine-grained source positions and zero-cost exception-table regions. “Zero-cost” means that entering a protected <code>try</code> region need not push the older explicit block-management setup on the normal path; it does not mean exceptions are computationally free.

The documented <code>co_positions</code> iterator associates code units with line and column ranges when available. Position information can be suppressed by an implementation option, and some artificial instructions have no source span:

~~~python
def divide(total: float, count: int) -> float:
    return total / count


positions = list(divide.__code__.co_positions())
for position in positions[:8]:
    print(position)
~~~

The tuple elements describe start line, end line, start column, and end column, with possible <code>None</code> values. Consumers should prefer <code>dis.Instruction.positions</code> when correlating instructions and spans rather than manually assuming a fixed byte-to-position ratio.

The private encoding of <code>co_exceptiontable</code> is not a general serialisation protocol. The disassembler can render exception-table relationships; debuggers and bytecode tools should use maintained libraries and explicit version gates. Replacing <code>co_code</code> without a corresponding valid exception table and position table can produce profoundly incorrect behaviour.

> **Common misconception 15.15 — “A code object is just a byte string of opcodes.”**  
> Correct evaluation also depends on constants, names, local and closure layout, flags, stack size, source-position data, exception regions, and the function/frame context that supplies runtime state.

Code objects close the static half of compilation. The next section examines their instruction representation, while retaining a disciplined distinction: disassembly is a view of a CPython build’s compiler output, not a second Python language specification.
