# 15.5 Disassembly and bytecode

The `dis` module presents version-specific CPython bytecode in a readable form.

```python
import dis


def add(left: int, right: int) -> int:
    return left + right


dis.dis(add)
```

Modern CPython bytecode changes between minor versions and can include adaptive or specialised execution details, inline caches, source positions, and exception tables. Opcode names and offsets are not stable application APIs. Disassembly is evidence about the selected interpreter build.

A conceptual disassembly loads two fast-local references, performs a binary operation, and returns the result. “Fast local” names a CPython access strategy, not a different semantic category of variable. The binary operation can dispatch to Python’s numeric/special-method protocol; it is not necessarily one hardware addition.

### Stack-machine model

CPython bytecode is commonly explained using an evaluation stack within a frame. Instructions push and pop object references. For `left + right`:

1. push object bound to local `left`;
2. push object bound to local `right`;
3. pop operands and perform addition protocol;
4. push result object;
5. return the top result.

This is an interpreter-level operand stack, distinct from the native thread call stack and distinct from the abstract call stack of Python frames, though implementations connect them.

Do not mutate bytecode or construct code objects by positional fields unless the project explicitly targets a CPython version and accepts fragility. Use `ast`, supported compilation interfaces, decorators, or tracing APIs at the highest suitable level.

### 15.5.1 An instruction stream is a compact intermediate representation

**Bytecode** is a compact instruction representation consumed by CPython’s interpreter. It is **intermediate** because it lies between source/AST structures and the native machine instructions that implement the interpreter. In CPython 3.12 the public disassembly view treats instructions as opcodes with optional integer operands, positions, jump targets, and cache information. The physical encoding uses fixed-size code units plus additional units for extended arguments and inline caches, but clients should obtain offsets from <code>dis</code> rather than decode <code>co_code</code> by assumption.

An **opcode** identifies an operation category. An **operand argument**, often abbreviated <code>oparg</code> in implementation discussion, supplies a small integer interpreted according to that opcode: perhaps an index into <code>co_consts</code>, a local slot, a packed name/flag value, a relative jump distance, or a count. The same integer has no independent meaning outside its opcode.

~~~python
import dis


def area(width: float, height: float) -> float:
    scale = 0.5
    return width * height * scale


for instruction in dis.get_instructions(area, show_caches=True):
    print(
        instruction.offset,
        instruction.opname,
        instruction.arg,
        instruction.argval,
        instruction.argrepr,
    )
~~~

<code>arg</code> exposes an encoded argument where one exists. <code>argval</code> supplies a resolved value interpreted by the disassembler—for example a constant, name, or target offset. <code>argrepr</code> is display text, useful to a human but unsuitable as a stable parser interface. An instruction with no argument reports <code>None</code> for corresponding fields.

The raw byte at a numeric offset is not enough to reconstruct semantics. Extended arguments can contribute higher bits. Cache entries occupy instruction-stream space but are hidden by ordinary disassembly. Jump interpretation changed between versions; in 3.12 relative jump arguments account for directions and cache layout under the documented version rules. Exception regions reside in separate metadata. Treating an offset as “source character number” or “the nth operation” is consequently false.

> **Common misconception 15.16 — “Python bytecode is a stable portable binary language.”**  
> CPython bytecode is a private, version-specific interpreter representation. Opcode sets, operands, cache units, jump encodings, and exception machinery can change even when source semantics remain stable.

### 15.5.2 Disassembly is structured observation

The most useful disassembly object is not formatted terminal text but a sequence of <code>dis.Instruction</code> records. These supply the opcode name, numeric opcode, argument, interpreted value, offset, source position, line-start status, jump-target status, and cache details documented for that version.

~~~python
import dis


def choose(flag: bool, left: int, right: int) -> int:
    if flag:
        return left + 1
    return right - 1


instructions = tuple(dis.get_instructions(choose))
for item in instructions:
    print(
        f"{item.offset:>3}",
        item.opname,
        "target" if item.is_jump_target else "",
        item.positions,
    )
~~~

The source position can cover a subexpression rather than a whole physical line. A compiler-generated instruction may have no position. Several instructions can share one span, and one source expression can require several instructions. PEP 626 strengthened accurate line-event behaviour, while PEP 657 added finer-grained positions; neither establishes a one-to-one source/instruction map.

A disassembler consumer should work from fields rather than columns of <code>dis.dis</code> output. Formatted output is intended for people and changes as information evolves. A robust analysis records:

- <code>sys.version</code> and implementation;
- the source and compilation flags;
- whether caches and adaptive forms were requested;
- the code object’s qualified name;
- structured instruction fields;
- whether execution had warmed or tracing was active.

Disassembling is normally observational, but retrieving descriptors or representations around a function can execute user code if an analysis traverses arbitrary objects carelessly. Limit inspection to explicit code/function objects and avoid printing hostile object representations.

### 15.5.3 The evaluation stack is verified across control flow

Most instructions communicate temporary values through a frame’s **evaluation stack**. A stack is last-in, first-out: a push adds a reference at the top; a pop removes the most recently pushed reference. Local and closure storage are not the evaluation stack, although instructions transfer references between them.

For an expression with nested calls, stack occupancy changes throughout evaluation:

~~~python
def combine(a: int, b: int, c: int) -> int:
    return max(a + b, c * 2)
~~~

Conceptually, the interpreter must resolve the callable, evaluate arguments left to right, retain intermediate results, perform the call, and return its result. The exact 3.12 instruction forms include call-protocol details that may differ from earlier or later versions. A valid compiler ensures that every control-flow path reaching an instruction has a compatible stack state and that the maximum depth fits <code>co_stacksize</code>.

The public <code>dis.stack_effect</code> function gives the net stack change of an opcode for a supplied argument and, where relevant, a selected jump outcome:

~~~python
import dis


def combine(a: int, b: int, c: int) -> int:
    return max(a + b, c * 2)


def effects(function) -> list[tuple[int, str, int]]:
    result: list[tuple[int, str, int]] = []
    for instruction in dis.get_instructions(function):
        if instruction.arg is None:
            effect = dis.stack_effect(instruction.opcode)
        else:
            effect = dis.stack_effect(
                instruction.opcode,
                instruction.arg,
            )
        result.append((instruction.offset, instruction.opname, effect))
    return result


print(effects(combine))
~~~

Net effect alone does not determine whether an instruction temporarily requires operands below the top, can raise, or has different effects on taken and untaken branches. For a conditional jump, ask separately with <code>jump=True</code> and <code>jump=False</code> when the opcode supports those outcomes. A complete **control-flow graph** has nodes representing basic blocks and edges representing possible transfers. Stack-depth analysis propagates depths over these edges and rejects incompatible joins.

A **basic block** is a maximal straight-line instruction sequence entered only at its first instruction and left only at its end. Jumps, targets, returns, raises, and exception edges divide blocks. Exception tables introduce edges that formatted linear disassembly does not communicate merely by indentation.

~~~python
import dis


def guarded_divide(total: float, count: float) -> float | None:
    try:
        return total / count
    except ZeroDivisionError:
        return None


dis.dis(guarded_divide)
~~~

On the successful path, no exception handler executes. If division signals <code>ZeroDivisionError</code>, the interpreter consults protected-region metadata, unwinds the evaluation stack to the encoded depth, establishes handler state, and transfers control. This hidden edge is part of the program’s control flow even though no source <code>goto</code> exists.

> **Common misconception 15.17 — “Adding each instruction’s stack effect in printed order reconstructs execution.”**  
> Branches, loops, exceptions, and calls create multiple paths. Stack analysis must follow a control-flow graph and respect path-specific effects and exception edges.

### 15.5.4 Generic instructions can specialise under guarded evidence

CPython 3.11 introduced the specialising adaptive interpreter described by PEP 659, and subsequent releases have revised the details. A generic operation initially supports the full language protocol. Runtime counters and inline data can observe recurring operand shapes or types. When profitable, the interpreter selects a **specialised** operation guarded by assumptions, such as exact built-in types and stable structural versions. If a guard fails, execution returns to a general path and can later adapt again.

This technique is an instance of **speculative optimisation**: optimise for an observed case, attach a test that proves the case still applies, and preserve a correct fallback. It cannot skip user-visible semantics merely because a common case is faster.

The <code>dis</code> API can show the adaptive instruction stream for a warmed function on supporting CPython versions:

~~~python
import dis


def total_lengths(items: list[str]) -> int:
    total = 0
    for item in items:
        total += len(item)
    return total


sample = ["alpha", "beta", "gamma"]

print("before")
dis.dis(total_lengths, adaptive=True, show_caches=True)

for _ in range(20_000):
    total_lengths(sample)

print("after")
dis.dis(total_lengths, adaptive=True, show_caches=True)
~~~

The threshold, resulting instruction names, cache fields, and even whether a particular site specialises are empirical. Debugging, tracing, build options, input diversity, and interpreter changes can influence them. The valid conclusion is conditional: this code site in this recorded build displayed this adaptive state after this workload.

An **inline cache** stores data adjacent to or associated with an instruction site: perhaps type versions, dictionary keys versions, indices, counters, or callable information. “Inline” describes locality to the operation site, not a Python <code>dict</code> accessible as an ordinary object. Cache entries in 3.12 occupy code-unit positions that the disassembler hides unless <code>show_caches=True</code>.

Specialisation is not memoisation of an operation result. An integer-add fast path still computes a new result for current operands. It caches evidence about how to perform the operation, not that <code>x + y</code> always has one value.

> **Common misconception 15.18 — “After warm-up, CPython permanently replaces Python semantics with type-specific semantics.”**  
> Specialised instructions are guarded implementations of the same operation. Guard failure, invalidation, tracing, or workload change can deoptimise the site and invoke the generic protocol.

### 15.5.5 One instruction can conceal an open-ended computation

An opcode named for addition, attribute load, iteration, containment, call, or comparison can execute user-defined methods, allocate objects, acquire locks, perform I/O through extension code, mutate global state, release the GIL, or raise an exception. Opcode granularity is not semantic atomicity.

~~~python
class NoisyNumber:
    def __init__(self, value: int) -> None:
        self.value = value

    def __add__(self, other: object) -> "NoisyNumber":
        print("addition protocol executed")
        if not isinstance(other, NoisyNumber):
            return NotImplemented
        return NoisyNumber(self.value + other.value)


left = NoisyNumber(2)
right = NoisyNumber(3)
result = left + right
assert result.value == 5
~~~

The source addition may correspond to a compact binary-operation instruction, yet its generic path invokes <code>__add__</code>. Returning <code>NotImplemented</code> is a protocol signal allowing reflected-operation handling, not the same as raising <code>NotImplementedError</code>. The method body can run many more instructions and arbitrary effects.

Likewise, attribute access is not merely a structure offset. Descriptors, <code>__getattribute__</code>, <code>__getattr__</code>, metaclass rules, and module hooks can participate. Iteration can call arbitrary iterator methods. Equality can be user code. The interpreter often optimises exact built-in cases, but it must prove those cases with guards.

Thread-safety reasoning must therefore operate on explicit synchronisation and semantic transactions. A single bytecode can invoke code that switches threads; a multi-bytecode update can be accidentally indivisible in one build and cease to be so after specialisation or free-threading changes.

> **Common misconception 15.19 — “One bytecode instruction is atomic and therefore thread-safe.”**  
> An instruction can invoke arbitrary Python or native code and may release or operate without the GIL. Application invariants require documented synchronisation, not opcode counting.

### 15.5.6 Bytecode is not native machine code

The CPU executes native instructions generated when the CPython executable and extension libraries were compiled. Those native instructions implement dispatch, object checks, arithmetic helpers, allocation, reference management, and system calls. CPython bytecode is data examined by that native interpreter.

A useful three-level trace for <code>left + right</code> is:

1. Python semantics request binary addition with its dispatch protocol.
2. CPython bytecode encodes a generic or specialised binary-operation site and metadata.
3. Native CPython code tests types, invokes a fast path or protocol helpers, adjusts ownership, and returns to dispatch; the hardware executes the compiled machine instructions underlying those actions.

The number of native instructions varies with types, caches, compiler optimisation, processor architecture, branch prediction, allocation, and error path. It cannot be inferred by multiplying the number of bytecodes by a constant.

Alternative Python implementations may interpret a different bytecode, compile to another virtual-machine representation, or generate native code dynamically. Even within CPython, experimental tiers can change execution beneath the same Python contract. For performance work, choose a measure appropriate to the layer: <code>dis</code> for compiler/interpreter structure, a Python profiler for call attribution, hardware counters for microarchitectural events, and a native profiler for interpreter hot paths.

> **Common misconception 15.20 — “Disassembly shows the instructions executed by the physical processor.”**  
> <code>dis</code> shows CPython’s interpreter instructions. A native disassembler or hardware-aware profiler is required to study the processor instructions implementing them.

The static stream still does not explain when defaults are evaluated or how closure cells, decorators, and globals become attached. Those events occur when the enclosing block executes a function definition.
