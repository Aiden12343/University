# 15.6 Function creation and defaults

When a module containing a function definition executes, the body’s code object already exists among the enclosing code’s compiled constants. Runtime instructions evaluate decorators, defaults, keyword defaults, and relevant annotation expressions or representations; assemble a function object; attach closure cells; apply decorators; and bind the final result.

This resolves an apparent contradiction:

- function body source is compiled before the function is called;
- default expressions execute when the `def` statement runs;
- body instructions execute only on later calls.

### Worked example 15.3 — Observe the three times

```python
def announce(label: str) -> int:
    print(label)
    return 3


def decorate(function):
    print("decorate")
    return function


@decorate
def operation(value: int = announce("default")) -> int:
    print("body")
    return value


print("defined")
operation()
```

At module execution, `announce("default")` prints `default`; the function is created; `decorate` prints `decorate`; the final function is bound. Then `defined` prints. The later call prints `body`. Compilation preceded all of these runtime observations.

### 15.6.1 A definition statement is executable construction

The compiler emits a code object for a function body while compiling the enclosing block. It also emits instructions in that enclosing block for the runtime work of the <code>def</code> statement. Thus source has at least three relevant times:

- **compilation time**, when syntax, symbols, code, position, and exception metadata are produced;
- **definition-execution time**, when the enclosing frame evaluates defaults, annotations under the active semantics, and decorators and creates/binds a function;
- **call time**, when argument binding and body evaluation occur.

Repeated execution of one definition statement creates distinct function objects:

~~~python
from collections.abc import Callable


def make_functions() -> tuple[Callable[[], int], Callable[[], int]]:
    def produce() -> int:
        return 9

    first = produce

    def produce() -> int:
        return 9

    second = produce
    return first, second


first, second = make_functions()
assert first is not second
assert first() == second() == 9
~~~

The two syntactically separate bodies may or may not yield equal byte strings, but their code objects are compiler constants at different source locations. More importantly, each definition execution creates a function object and rebinds the local name <code>produce</code>. A loop executing one definition statement similarly creates a function on each iteration while normally reusing the one nested code object.

The function object exposes mutable metadata—<code>__name__</code>, <code>__qualname__</code>, documentation, annotations, and an attribute dictionary—as well as read-only associations such as <code>__code__</code> assignment subject to compatibility checks. Mutating metadata does not recompile source. Replacing <code>__code__</code> deliberately changes what later calls execute and requires closure/free-variable compatibility.

> **Common misconception 15.21 — “A def statement runs the function body to create the function.”**  
> Compilation creates body code; executing <code>def</code> constructs a function around that code and evaluates surrounding definition-time expressions. The body runs only when the resulting callable is invoked.

### 15.6.2 Defaults are retained objects, not expression recipes

Positional defaults are stored in the function’s <code>__defaults__</code> tuple; keyword-only defaults are stored in <code>__kwdefaults__</code>. The values are results of definition-time evaluation. They are not AST fragments evaluated afresh for a missing argument.

~~~python
def make_default() -> list[str]:
    print("creating default")
    return []


def append_event(
    event: str,
    history: list[str] = make_default(),
) -> tuple[str, ...]:
    history.append(event)
    return tuple(history)


assert append_event("opened") == ("opened",)
assert append_event("closed") == ("opened", "closed")
print(append_event.__defaults__)
~~~

The diagnostic message appears once when the definition executes. Both omitted-argument calls bind <code>history</code> to the same list. Passing an explicit list bypasses that default but does not replace <code>__defaults__</code>.

The usual sentinel design asks call time to construct state deliberately:

~~~python
def append_event_safely(
    event: str,
    history: list[str] | None = None,
) -> tuple[str, ...]:
    active_history = [] if history is None else history
    active_history.append(event)
    return tuple(active_history)


assert append_event_safely("opened") == ("opened",)
assert append_event_safely("closed") == ("closed",)
~~~

This is correct only if <code>None</code> is not a meaningful explicit argument. Otherwise use a private unique sentinel:

~~~python
_MISSING = object()


def collect(
    value: int,
    destination: list[int] | object = _MISSING,
) -> list[int]:
    if destination is _MISSING:
        active: list[int] = []
    elif isinstance(destination, list):
        active = destination
    else:
        raise TypeError("destination must be a list")
    active.append(value)
    return active
~~~

Shared defaults are sometimes intentional—for a precomputed immutable value or consciously shared cache—but the ownership contract must be explicit and concurrency-safe. Altering <code>function.__defaults__</code> is possible, because defaults belong to the function object; doing so changes later omitted-argument calls and should be reserved for controlled metaprogramming or tests.

> **Common misconception 15.22 — “A default expression is evaluated whenever the caller omits the argument.”**  
> The expression is ordinarily evaluated when the definition statement executes, and the resulting object is retained on the function. Mutation therefore persists across omitted-argument calls.

### 15.6.3 Closures are assembled when the definition executes

If the nested code has free variables, the enclosing frame supplies corresponding cells when constructing the function. The code object names required cells through <code>co_freevars</code>; the function stores them in <code>__closure__</code>. A mismatch is not a valid callable construction.

~~~python
def make_multiplier(factor: int):
    def multiply(value: int) -> int:
        return value * factor

    return multiply


triple = make_multiplier(3)

for name, cell in zip(
    triple.__code__.co_freevars,
    triple.__closure__ or (),
    strict=True,
):
    print(name, cell.cell_contents)
~~~

The function does not retain the completed outer frame merely because it has a closure. It retains the required cells. Other objects, such as tracebacks or explicit frame references, can retain the frame separately. Cells let captured bindings outlive the activation that created them without preserving every temporary local.

Loop-created closures expose the binding nature of capture:

~~~python
from collections.abc import Callable


def late_bound() -> list[Callable[[], int]]:
    functions: list[Callable[[], int]] = []
    for number in range(3):
        functions.append(lambda: number)
    return functions


assert [function() for function in late_bound()] == [2, 2, 2]
~~~

All lambdas made during one invocation share the loop variable’s cell. The loop finishes with the cell bound to 2. A definition-time default can intentionally snapshot the value into an ordinary parameter default:

~~~python
def captured_values():
    return [
        (lambda number=number: number)
        for number in range(3)
    ]


assert [function() for function in captured_values()] == [0, 1, 2]
~~~

This technique works because each lambda definition evaluates its default while that comprehension iteration’s <code>number</code> is current. It is not a change to closure semantics; it avoids a free-variable dependency by creating a parameter with a retained default.

### 15.6.4 Decorator application replaces the bound result

Decorators are evaluated when the definition statement executes. Decorator expressions are evaluated in source order from top to bottom, while the resulting decorator callables are applied to the newly created function from bottom to top. The final returned object is bound to the defined name.

~~~python
from collections.abc import Callable


events: list[str] = []


def decorator_named(name: str):
    events.append(f"evaluate {name}")

    def apply(function: Callable[[int], int]):
        events.append(f"apply {name}")

        def wrapper(value: int) -> int:
            events.append(f"call {name}")
            return function(value)

        return wrapper

    return apply


@decorator_named("outer")
@decorator_named("inner")
def double(value: int) -> int:
    return value * 2


assert events[:4] == [
    "evaluate outer",
    "evaluate inner",
    "apply inner",
    "apply outer",
]
assert double(5) == 10
~~~

The name <code>double</code> refers to the object returned by the outer application, not necessarily the original function. A decorator can return a descriptor, class instance, unrelated function, or non-callable object. <code>functools.wraps</code> copies selected metadata and sets <code>__wrapped__</code>; it does not make the wrapper identical to the wrapped callable or automatically preserve an exact runtime signature.

Annotation evaluation depends on the language version and active future statements. In a conventional 3.12 module without postponed evaluation, many annotation expressions are evaluated during definition execution and stored in <code>__annotations__</code>. A future import can store string forms instead. Later Python versions introduce additional lazy annotation machinery. Libraries should retrieve annotations through documented facilities such as <code>inspect.get_annotations</code> with an explicit evaluation policy, rather than assuming values or strings universally.

> **Common misconception 15.23 — “The name introduced by def must remain bound to the original function object.”**  
> Decorators can replace the function with any returned object. The definition binds the result of successive decorator applications; preservation of callability, metadata, and signature is a decorator contract.

Definition execution is now accounted for. Calling the resulting function requires a fresh execution state, whose public and private representations have deliberately diverged in modern CPython.
