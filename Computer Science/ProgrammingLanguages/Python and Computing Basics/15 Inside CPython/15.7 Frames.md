# 15.7 Frames

A CPython **frame** represents execution state for code: code object, globals, builtins, local/stack storage, instruction position, exception state, and links or ownership required by the version’s interpreter design. Frame implementation was substantially refactored across modern CPython releases, so internal structure names must be version-scoped.

Python exposes frame objects through tracebacks, `inspect`, and `sys._getframe`, but retaining them can retain complete local object graphs and create cycles.

```python
import inspect


def inspect_call(value: int) -> tuple[str, tuple[str, ...]]:
    frame = inspect.currentframe()
    if frame is None:
        raise RuntimeError("frame inspection unavailable")
    try:
        return frame.f_code.co_name, tuple(frame.f_locals)
    finally:
        del frame
```

Deleting the local frame reference helps break a cycle in which the frame’s locals contain a reference to the frame. Introspection has lifetime and performance effects.

`f_locals` is a mapping view/snapshot under documented semantics that have evolved; writing it should not be treated as a portable way to change optimised local bindings. Debugger and tracing behaviour follows specific version APIs.

### 15.7.1 A logical frame need not always be a materialised Python object

At the language level, each active call has execution state: current instruction, local bindings, access to globals and built-ins, an evaluation stack, and exception context. CPython 3.12 represents the efficient internal state with an interpreter-frame structure and exposes a <code>PyFrameObject</code> only when a Python-level frame object is required. This **materialisation** avoids allocating and maintaining the full introspection wrapper for every ordinary call.

The distinction matters when reading source. “Frame” can mean:

1. the abstract activation record required to evaluate one code invocation;
2. CPython’s private interpreter-frame storage;
3. the public Python frame object exposed through <code>sys._getframe</code>, tracebacks, generators, or tracing;
4. the native C stack state executing the evaluator.

These entities are related but not interchangeable. A source statement that “pushes a Python frame” is too imprecise to establish whether native recursion, an internal frame record, or a heap-visible <code>PyFrameObject</code> is involved.

~~~python
import sys


def public_frame_summary(value: int) -> tuple[str, str, int]:
    frame = sys._getframe()
    return (
        frame.f_code.co_name,
        frame.f_code.co_filename,
        frame.f_lineno,
    )


name, filename, line = public_frame_summary(3)
assert name == "public_frame_summary"
assert filename.endswith(".py") or filename.startswith("<")
assert line > 0
~~~

<code>sys._getframe</code> is a CPython-oriented introspection interface and can be unavailable on other implementations. Requesting the object itself changes lifetime and may affect optimisation. A profiler should not assume that the state it observes had already existed in identical materialised form.

> **Common misconception 15.24 — “Every Python call immediately allocates one ordinary frame object.”**  
> A call requires logical execution state, but modern CPython can use an internal interpreter frame and materialise a public frame object only when introspection or traceback behaviour requires it.

### 15.7.2 Locals-plus storage is indexed, while f_locals is a mapping interface

Function compilation assigns indices for parameters, ordinary locals, cells, and free variables in a version-specific combined layout often discussed as **locals plus**. Load/store instructions can address indices directly, avoiding a dictionary lookup for ordinary optimised locals. This is one reason the box metaphor for variables is misleading: a local binding is represented by an entry or slot holding an object reference under frame invariants, not by a Python object named “the variable box”.

The public <code>frame.f_locals</code> interface presents a mapping-oriented view. In Python 3.12, interactions between optimised fast locals and that mapping have context-dependent synchronisation rules; writes must not be treated as a portable reliable way to alter active local variables. PEP 667 defines revised semantics in later Python versions. A debugger must target and test the exact version it supports.

### Worked example 15.4 — Observe, do not mutate, an active local namespace

~~~python
import inspect


def snapshot_locals(left: int, right: int) -> dict[str, object]:
    total = left + right
    frame = inspect.currentframe()
    if frame is None:
        raise RuntimeError("frame inspection unavailable")
    try:
        return dict(frame.f_locals)
    finally:
        del frame


snapshot = snapshot_locals(2, 5)
assert snapshot["left"] == 2
assert snapshot["right"] == 5
assert snapshot["total"] == 7
~~~

Copying makes the returned object a normal dictionary snapshot, although its values still reference the same objects. The mapping also contains the local <code>frame</code> at the moment it is copied, so careless storage can preserve a frame through a value graph. The <code>finally</code> deletion removes the direct local cycle before return, but the snapshot constructed earlier can itself contain the frame; a production helper should filter that entry:

~~~python
import sys


def safe_local_snapshot() -> dict[str, object]:
    amount = 12
    frame = sys._getframe()
    try:
        return {
            name: value
            for name, value in frame.f_locals.items()
            if name != "frame"
        }
    finally:
        del frame


assert safe_local_snapshot()["amount"] == 12
~~~

Even the filtered result can retain large or sensitive objects. Introspection is an ownership operation, not a free textual glance.

> **Common misconception 15.25 — “f_locals is the dictionary in which CPython stores every active function local.”**  
> Optimised locals use indexed internal storage. <code>f_locals</code> is a documented mapping interface whose synchronisation and write-through semantics depend on version and execution context.

### 15.7.3 Calls form a dynamic chain, distinct from lexical scope

The **call chain** records which invocation called which other invocation at runtime. Lexical scope records where blocks were nested in source. These relations can differ completely. A globally defined helper can be called from a nested function without becoming its lexical parent.

Frame objects expose <code>f_back</code> to the caller’s frame when available. This supports traceback and inspection but does not govern name resolution:

~~~python
import sys


def report_chain(limit: int = 5) -> list[str]:
    names: list[str] = []
    frame = sys._getframe()
    try:
        while frame is not None and len(names) < limit:
            names.append(frame.f_code.co_name)
            frame = frame.f_back
        return names
    finally:
        del frame


def caller() -> list[str]:
    return report_chain()


chain = caller()
assert chain[:2] == ["report_chain", "caller"]
~~~

The chain can expose test runners, notebook machinery, or server internals after these entries; never assert an entire external call chain without controlling the environment. Retaining one frame can retain its caller through <code>f_back</code>, its locals, globals, code, trace function, and objects reachable from them.

Python recursion creates a sequence of logical frames. CPython checks recursion depth to prevent uncontrolled exhaustion, but the configured limit is not a promise that every depth below it is safe. Native extensions, platform stack size, trace functions, and interpreter implementation affect the physical resource limit. Raising <code>sys.setrecursionlimit</code> without measuring stack safety can terminate the process rather than merely raising a Python exception.

~~~python
def triangular(number: int) -> int:
    if number == 0:
        return 0
    return number + triangular(number - 1)


assert triangular(5) == 15
~~~

CPython does not promise tail-call elimination. Rewriting a tail-recursive algorithm as iteration can make space use explicit and preserve tracebacks showing actual calls. Mathematical induction can prove either version; an implementation optimisation is not required for correctness.

> **Common misconception 15.26 — “The caller chain is the same thing as the enclosing-scope chain.”**  
> Call relationships are dynamic and represented by active frames; enclosing scopes are lexical and compiled through cells/global rules. A callee does not gain access to its caller’s locals merely because the caller’s frame exists.

### 15.7.4 Suspension preserves execution state

A generator call initially returns a generator object without running its body. Iteration resumes its stored frame state until <code>yield</code>, normal return, or exception. A coroutine has analogous suspension machinery under its protocol. Locals and pending evaluation state can therefore outlive an individual resume operation.

### Worked example 15.5 — Inspect a suspended generator

~~~python
import inspect


def staged(limit: int):
    current = 0
    while current < limit:
        yield current
        current += 1


generator = staged(2)
assert inspect.getgeneratorstate(generator) == "GEN_CREATED"
assert next(generator) == 0
assert inspect.getgeneratorstate(generator) == "GEN_SUSPENDED"

frame = generator.gi_frame
assert frame is not None
assert frame.f_locals["current"] == 0

assert list(generator) == [1]
assert inspect.getgeneratorstate(generator) == "GEN_CLOSED"
assert generator.gi_frame is None
~~~

After the first yield, <code>current</code> remains bound and the instruction position identifies the suspension point. Exhaustion clears the generator’s frame reference in ordinary operation, releasing retained locals subject to other references. Calling <code>close</code> injects <code>GeneratorExit</code>; a <code>finally</code> suite can then release resources, but external resources should still be wrapped in clear context-management ownership.

Generator delegation through <code>yield from</code>, coroutine awaiting, and asynchronous-generator hooks add chains of suspended state. An apparently idle task can therefore own files, locks, network buffers, contexts, or large arrays. Lifecycle design must include cancellation, close, and exception paths.

### 15.7.5 Tracebacks turn transient frames into retained graphs

When an exception propagates, traceback objects identify frames and instruction locations along the path. Keeping the exception can keep its traceback; keeping the traceback can keep frames; frames keep local references. A monitoring system that stores exceptions indefinitely can become a memory leak even after the logical request has finished.

~~~python
import traceback


def fail_with_payload() -> None:
    payload = bytearray(1_000_000)
    raise RuntimeError(f"payload length {len(payload)}")


try:
    fail_with_payload()
except RuntimeError as error:
    formatted = "".join(
        traceback.format_exception(type(error), error, error.__traceback__)
    )
    traceback.clear_frames(error.__traceback__)

assert "payload length" in formatted
~~~

<code>traceback.clear_frames</code> clears locals in completed frames where permitted; it does not erase every reference held elsewhere or alter the already formatted string. Whether clearing is appropriate depends on debugging requirements. Structured logging commonly extracts a bounded representation and then releases the live exception graph.

Assigning <code>error = None</code> after an <code>except</code> is usually unnecessary because the language clears the handler target at suite completion. Storing the exception in another container defeats that cleanup. Calling <code>frame.clear()</code> on an executing frame raises; suspended generators and coroutines require careful protocol-aware cleanup.

> **Common misconception 15.27 — “After an exception has been caught, all frames on its path are automatically freed.”**  
> An exception, traceback, debugger, logger, generator, or explicit frame reference can retain those frames and their locals. Reachability—not whether the handler has printed—determines lifetime.
