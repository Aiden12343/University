# 15.8 The evaluation loop

CPython’s interpreter repeatedly obtains an opcode from the current instruction stream, dispatches to implementation code, manipulates frame state, and continues or transfers control. Contemporary versions use generated and specialised interpreter machinery rather than one eternally stable hand-written `switch` loop. “The eval loop” remains a conceptual label for bytecode evaluation.

For a binary addition instruction, implementation work can include:

1. obtain operand references from frame stack/local storage;
2. inspect operand types or specialised cache state;
3. take a fast path for a frequent type pairing when guards hold;
4. otherwise invoke generic numeric dispatch, including reflected methods;
5. propagate an exception indicator if no operation succeeds;
6. manage ownership/reference counts of consumed and produced references;
7. place the result for later instructions;
8. update instruction position and monitoring/tracing state.

Adaptive specialisation can replace a generic operation with a version-specific specialised form after observing stable types. Guards preserve semantic correctness and deoptimise or respecialise when assumptions fail. These mechanisms explain performance, not language behaviour: user-defined addition must still receive its specified opportunity.

### 15.8.1 Dispatch connects encoded operations to native implementation cases

The evaluator maintains a current instruction position and frame stack pointer. It obtains an opcode, advances or adjusts the instruction position, and dispatches to the native implementation case for that opcode. A case reads operands from frame storage, performs guarded or generic operations, updates ownership, pushes a result or selects an error path, and transfers to the next case or another frame.

Historical explanations often reproduce a large C <code>switch</code>. That is a useful abstract machine but an unreliable map of current source. CPython 3.12 defines much instruction semantics in generated descriptions from which interpreter cases and related metadata are produced. A build can use computed-goto dispatch where supported, while another compiler/platform can choose a switch-like strategy. Generated files may contain the code actually compiled even though their authoritative inputs lie elsewhere.

The following miniature interpreter is not CPython. It isolates the dispatch idea with integers rather than Python objects:

~~~python
from enum import IntEnum


class Operation(IntEnum):
    CONSTANT = 1
    ADD = 2
    RETURN = 3


def evaluate(
    program: list[tuple[Operation, int | None]],
    constants: tuple[int, ...],
) -> int:
    stack: list[int] = []
    instruction = 0

    while True:
        opcode, argument = program[instruction]
        instruction += 1

        if opcode is Operation.CONSTANT:
            assert argument is not None
            stack.append(constants[argument])
        elif opcode is Operation.ADD:
            right = stack.pop()
            left = stack.pop()
            stack.append(left + right)
        elif opcode is Operation.RETURN:
            return stack.pop()
        else:
            raise RuntimeError(f"unknown opcode {opcode}")


program = [
    (Operation.CONSTANT, 0),
    (Operation.CONSTANT, 1),
    (Operation.ADD, None),
    (Operation.RETURN, None),
]
assert evaluate(program, (20, 22)) == 42
~~~

Real CPython differs at every detailed edge. Its stack entries are object references; addition follows type protocols and may raise; instructions can jump, call, yield, import, monitor, and enter exception handlers; reference ownership must remain correct; specialisation mutates execution-side state; and thread/interpreter state participates. The model’s value lies only in separating program counter, dispatch, operands, and effects.

> **Common misconception 15.28 — “The CPython evaluator is permanently one giant switch statement in ceval.c.”**  
> Dispatch remains the conceptual operation, but current cases and metadata are substantially generated and reorganised. Source navigation must begin from the target release’s build inputs and generated outputs.

### 15.8.2 Stack ownership is part of every instruction’s correctness

An interpreter instruction does not merely compute values; it transfers ownership of object references. A stack entry represents a strong reference under internal conventions. An operation that consumes two entries must ensure they are eventually released even if user code raises. A produced result must be owned before it becomes visible to later operations. Borrowed references obtained from containers may require promotion when their source can change.

Conceptually, a binary operation follows a shape such as:

1. fetch owned references to right and left operands from stack positions;
2. invoke a helper that returns a new reference or signals failure;
3. release the consumed operands according to ownership rules;
4. on success, place the result in the surviving stack position;
5. on failure, establish the correct stack depth and enter common exception dispatch.

The order of decrements matters because releasing a final reference can execute <code>__del__</code>, weak-reference callbacks, descriptor cleanup, or container destruction. That re-entrant work can run Python and observe state. CPython source frequently arranges a structure into a consistent state before a decrement capable of invoking arbitrary code.

At Python level, this can be demonstrated with deterministic explicit deletion on a conventional CPython build, but the language does not promise immediate finalisation:

~~~python
events: list[str] = []


class ObserveFinalisation:
    def __del__(self) -> None:
        events.append("finalised")


def release_local() -> None:
    value = ObserveFinalisation()
    del value


release_local()
print(events)
~~~

On ordinary conventional CPython, <code>events</code> commonly contains the message immediately. Another implementation or a cycle can delay it. The internal lesson is narrower: every operation that may release a last reference must be treated as a possible re-entrancy boundary, not as an inert counter decrement.

> **Common misconception 15.29 — “Once an opcode has computed its mathematical result, the rest is bookkeeping without semantic consequences.”**  
> Reference transfers, decrements, allocation failures, finalisers, and callbacks can execute observable work or raise. Ownership ordering is part of interpreter correctness.

### 15.8.3 Runtime, interpreter, thread, and frame states form a hierarchy

A process running CPython has process-wide runtime state. It can contain one or more interpreter states. Each interpreter has modules, built-ins, import state, codecs, allocator-related state, pending work, and other version-dependent resources. A thread executing Python is associated with a **thread state** for an interpreter. The thread state carries current exception and evaluation context, recursion information, tracing/monitoring fields, and links needed by the build. Frames represent individual code activations under that thread state.

The hierarchy is not a simple ownership tree in every field, but it disciplines questions:

| Question | Principal level |
|:---|:---|
| Which module cache resolves an import? | interpreter state |
| Which exception indicator is currently set in C API execution? | attached thread state |
| Which local binding does an instruction read? | current frame |
| Which allocator hooks or initialisation phase applies? | runtime/interpreter configuration |
| Which OS thread is running native extension code? | operating-system thread plus attached/detached thread state |

A thread state must be attached before most Python C API work. In a conventional GIL build, attachment and GIL ownership are closely coupled; in a free-threaded build, attachment remains necessary even though one global interpreter lock is absent. The older phrase “acquire the GIL before using the API” is therefore an incomplete general model. The stable requirement is to follow documented thread-state and API rules for the chosen build.

Subinterpreters complicate global assumptions. Objects generally belong to the interpreter context in which they were created, and most arbitrary Python objects cannot simply be passed between interpreters as shared pointers. Extension modules with process-global mutable C state can break isolation. Later sections connect per-interpreter locking and multi-phase module state.

> **Common misconception 15.30 — “An operating-system thread is itself a Python frame or a Python interpreter.”**  
> An OS thread can attach a CPython thread state to an interpreter and evaluate a chain of frames. These are distinct state layers with different lifetimes and sharing rules.

### 15.8.4 Calls can switch frames without mirroring every step in native recursion

When a call targets a Python function, argument binding populates the new activation’s local entries, closure cells are made available, and evaluation continues in that frame. Modern CPython can transfer between interpreter frames through evaluator control flow rather than requiring one fresh recursive C invocation for every ordinary Python-to-Python call. Native stack use still exists and particular calls, extensions, callbacks, tracing, or recursion paths can re-enter evaluation.

The distinction helps explain why three “stacks” must not be collapsed:

- the evaluation stack of temporary Python object references within a frame;
- the chain/stack of Python activations;
- the native machine stack used by compiled CPython and extension functions.

An evaluator can push a logical Python activation while reusing a native evaluation loop. Conversely, a native helper can recurse in C without creating an additional Python frame. Resource analysis must identify which stack is at risk.

### Worked example 15.6 — Calls create independent locals over shared code

~~~python
import inspect


def depth_record(number: int) -> list[tuple[int, int]]:
    frame = inspect.currentframe()
    if frame is None:
        raise RuntimeError("frame unavailable")
    try:
        record = [(number, id(frame))]
    finally:
        del frame

    if number == 0:
        return record
    return record + depth_record(number - 1)


records = depth_record(3)
assert [number for number, _ in records] == [3, 2, 1, 0]
assert len({identity for _, identity in records}) == 4
~~~

The <code>id</code> values demonstrate distinct simultaneously live materialised frames in this run. Their code objects are the same, and after return their memory addresses can later be reused. The experiment does not reveal whether every transition required another native evaluator call.

### 15.8.5 The eval breaker coordinates infrequent obligations

Checking every possible asynchronous condition through a large general routine after every instruction would be expensive. CPython uses an **evaluation breaker** concept: a compact condition indicates that the evaluator should take a slower path to process pending obligations. Exact bits and checkpoints are private and version-specific.

Such obligations can include:

- a request to handle a signal in the main Python thread;
- pending calls scheduled through implementation APIs;
- thread scheduling or lock-drop requests in GIL builds;
- asynchronous exception delivery under narrowly defined APIs;
- cyclic-collector or other runtime coordination in versions where routed there;
- instrumentation changes requiring deoptimisation or checks.

Signals illustrate the separation between operating-system delivery and Python handler execution. A low-level handler records that work is pending; the Python signal handler normally runs later at a safe interpreter checkpoint in the main thread. Long native computations that neither return to the evaluator nor explicitly check signals can delay handler execution.

### Worked example 15.7 — A signal handler runs in interpreter context

~~~python
import os
import signal


received: list[int] = []


def record_signal(number: int, frame: object) -> None:
    del frame
    received.append(number)


if hasattr(signal, "SIGUSR1"):
    previous = signal.signal(signal.SIGUSR1, record_signal)
    try:
        os.kill(os.getpid(), signal.SIGUSR1)
        for _ in range(100_000):
            if received:
                break
        assert received == [signal.SIGUSR1]
    finally:
        signal.signal(signal.SIGUSR1, previous)
~~~

The platform guard is essential because <code>SIGUSR1</code> is not universal. The loop merely lets normal Python evaluation reach checking points; it is not a portable timing guarantee. Production signal handlers should do minimal, re-entrant-safe coordination and must account for the main-thread rule.

> **Common misconception 15.31 — “Python signal handlers execute immediately inside the operating system’s low-level signal handler.”**  
> CPython ordinarily defers Python-level handler execution until the main interpreter thread reaches a checking point. Native code can therefore delay it.

### 15.8.6 Tracing, profiling, and monitoring are semantic observers with costs

<code>sys.settrace</code> installs a tracing function receiving events such as calls, lines, returns, exceptions, and optionally opcodes. <code>sys.setprofile</code> provides a lower-volume call-oriented interface including native call events. Python 3.12 introduces the <code>sys.monitoring</code> interface from PEP 669 for lower-impact event monitoring with tool identifiers and selective events.

### Worked example 15.8 — Collect bounded call and return events

~~~python
import sys
from types import FrameType


events: list[tuple[str, str]] = []


def trace(
    frame: FrameType,
    event: str,
    argument: object,
):
    del argument
    if frame.f_code.co_filename == __file__:
        events.append((frame.f_code.co_name, event))
    return trace


def square(value: int) -> int:
    return value * value


previous = sys.gettrace()
sys.settrace(trace)
try:
    assert square(6) == 36
finally:
    sys.settrace(previous)

assert ("square", "call") in events
assert ("square", "return") in events
~~~

The <code>finally</code> restoration is mandatory in shared processes. A trace callback is itself code and can retain frames, perturb scheduling, suppress or replace tracing through errors, and substantially change performance. CPython disables tracing recursively while invoking the trace function under documented rules to avoid unlimited self-tracing, but callbacks remain part of program behaviour.

Low-impact monitoring reduces costs by allowing specific events and tools, but “low” does not mean zero. Instrumentation can inhibit specialisation, require instruction patching or counters, materialise frames, and allocate records. Benchmark the instrumented system and define whether the quantity of interest is instrumented or uninstrumented execution.

> **Common misconception 15.32 — “A profiler or tracer passively observes execution without changing it.”**  
> Observation consumes time, can alter specialisation and frame materialisation, retains objects if implemented carelessly, and can change thread interleavings. Its overhead and perturbation require measurement.

### 15.8.7 Specialisation remains subordinate to generic dispatch

An adaptive instruction site is a small state machine. It begins generic or adaptive, counts useful observations, attempts specialisation, tests guards on later executions, records misses, and can return to a less specialised state. Cache invalidation can be driven by type or dictionary version changes and other watched structure.

The following workload changes the operand family deliberately:

~~~python
import dis


def combine(left, right):
    return left + right


for _ in range(20_000):
    combine(1, 2)

dis.dis(combine, adaptive=True, show_caches=True)

for _ in range(1_000):
    combine("a", "b")

dis.dis(combine, adaptive=True, show_caches=True)
~~~

The observed transitions are intentionally not asserted. A particular release can retain, replace, or decline a specialisation based on thresholds and cache policy. What must hold is semantic: integer calls return integer sums and string calls return concatenations. If a user-defined operand arrives, its protocol must receive the specified dispatch.

Specialisation also changes how source-level timing should be interpreted. Faster lookup may reduce lock-holding time or expose a different interleaving, but it does not turn a compound operation into a transaction. Benchmark distributions can be multimodal while sites warm, deoptimise, or encounter heterogeneous data.

> **Common misconception 15.33 — “Adaptive state is part of the function’s permanent source-independent type.”**  
> Adaptive state belongs to version-specific execution sites and workload history. It can be reset, invalidated, suppressed, or represented outside the immutable code bytes while leaving the function’s language meaning unchanged.

Normal dispatch produces a result or a structured transfer. When an operation cannot complete, the interpreter must carry both a failure signal and an exception object graph without confusing failure sentinels with ordinary values.
