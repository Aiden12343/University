# 15.9 Exception machinery

At the C implementation boundary, many CPython API functions indicate failure through a sentinel return—often `NULL` for pointer-returning functions or `-1` for selected integer-returning functions—while storing exception state in the current thread state. Native extension code must check according to each API contract and propagate or handle the error without returning an ordinary result while an exception remains set.

At Python level, raising creates or normalises an exception instance and transfers control according to compiled exception-handling tables and frame state. Traceback objects connect frames representing the propagation path. Catching an exception binds it temporarily; Python clears the handler target at suite end to reduce cycles among exception, traceback, frame, and locals.

Exception messages are not stable machine interfaces unless explicitly documented. Tests should normally assert exception type and structured attributes or stable semantic fragments rather than entire version-specific wording.

### 15.9.1 C-level failure uses two coordinated channels

Python can return <code>None</code>, <code>-1</code>, or any other ordinary object/value successfully, so a native API cannot use one universal payload to mean failure. CPython C APIs document a **sentinel** return and require an exception indicator to be set in the attached thread state. For a pointer-returning function, <code>NULL</code> often signals failure. For an integer-returning function, <code>-1</code> may signal failure either unconditionally or only when an exception is also set. The contract of the specific function controls interpretation.

Conceptual C extension code must test both according to that contract:

~~~c
static PyObject *
item_as_index(PyObject *sequence, Py_ssize_t position)
{
    PyObject *item = PySequence_GetItem(sequence, position);
    if (item == NULL) {
        return NULL;
    }

    Py_ssize_t value = PyNumber_AsSsize_t(item, PyExc_OverflowError);
    Py_DECREF(item);
    if (value == -1 && PyErr_Occurred()) {
        return NULL;
    }

    return PyLong_FromSsize_t(value);
}
~~~

<code>PySequence_GetItem</code> returns a new reference or <code>NULL</code>. <code>PyNumber_AsSsize_t</code> can legitimately return -1, so the exception indicator disambiguates. The item reference is released before either later return. <code>PyLong_FromSsize_t</code> can itself fail and return <code>NULL</code>, already setting an exception.

Returning a non-<code>NULL</code> result while an exception remains set violates the extension-call contract and commonly produces a <code>SystemError</code> reported against the extension. Returning <code>NULL</code> without setting an exception also violates it. Native code that handles an error must fetch/clear or otherwise transform the exception using documented APIs; code that propagates should preserve it and return the required sentinel.

The error indicator belongs to the current thread state, not to a process-global C variable and not directly to the returned Python exception object. Modern exception APIs have evolved from three-part type/value/traceback manipulation towards normalised exception instances. Extension code should use the API family documented for its minimum supported Python release.

> **Common misconception 15.34 — “A C function’s NULL or -1 return is itself the Python exception.”**  
> The sentinel signals that no ordinary result was produced; exception state is carried separately in the current thread state. Both channels must agree under the function’s contract.

### 15.9.2 Raising creates relationships among type, instance, cause, context, and traceback

A <code>raise</code> statement can receive an exception class or instance. The runtime ensures an instance is available and associates propagation information. When an exception arises while another is being handled, implicit **exception context** records the earlier exception in <code>__context__</code>. Explicit <code>raise new from cause</code> records <code>__cause__</code> and controls display. <code>raise new from None</code> suppresses context display but does not deny that diagnostic state may exist.

### Worked example 15.9 — Translate an exception without erasing causality

~~~python
class ConfigurationError(Exception):
    pass


def read_count(text: str) -> int:
    try:
        value = int(text)
    except ValueError as error:
        raise ConfigurationError("count must be an integer") from error

    if value < 0:
        raise ConfigurationError("count must be non-negative")
    return value


try:
    read_count("many")
except ConfigurationError as error:
    assert isinstance(error.__cause__, ValueError)
    assert error.__suppress_context__ is True
~~~

The translated exception gives callers a domain-specific type while preserving the conversion failure as its explicit cause. A bare <code>raise</code> inside an active handler re-raises the currently handled exception with its propagation semantics; <code>raise error</code> is not identical because it introduces a new raise site in the traceback.

Exception instances are mutable objects. Adding notes through <code>add_note</code>, attaching domain fields, or preserving causes can improve diagnostics, but can also retain sensitive input or large graphs. Logging should apply an explicit redaction policy.

<code>SystemExit</code>, <code>KeyboardInterrupt</code>, and <code>GeneratorExit</code> derive directly from <code>BaseException</code>, not <code>Exception</code>, so routine <code>except Exception</code> handling does not swallow them. Catching <code>BaseException</code> is justified mainly for cleanup followed by re-raising or at a process boundary with a deliberate policy.

> **Common misconception 15.35 — “raise ... from None deletes the original exception.”**  
> It suppresses display of implicit context in the usual traceback rendering. It is a presentation/causality choice, not secure erasure of every reference or diagnostic fact.

### 15.9.3 Exception tables encode protected regions and handlers

CPython 3.12 code objects carry an encoded exception table identifying instruction ranges, handler targets, stack restoration depths, and flags required for propagation. The ordinary path through a <code>try</code> suite need not execute explicit setup/pop-block opcodes used by older designs. When an operation reports failure, evaluator exception dispatch uses the current instruction location to find a matching protected region.

A conceptual unwind performs these obligations:

1. recognise that the operation returned its error sentinel with exception state set;
2. release or discard evaluation-stack entries beyond the handler’s required depth;
3. find the innermost applicable exception-table entry for the failing instruction;
4. arrange exception information required by the handler protocol;
5. transfer the instruction pointer to handler bytecode; or, if no entry applies, finish the frame exceptionally and propagate to its caller.

<code>finally</code> and <code>with</code> cleanup can run during this transfer and can themselves raise. A new exception then gains the previous exception as context unless suppressed. A <code>return</code>, <code>break</code>, or <code>continue</code> leaving protected source can also require cleanup even without a current error.

~~~python
events: list[str] = []


def nested_failure() -> None:
    try:
        events.append("body")
        raise LookupError("missing")
    finally:
        events.append("cleanup")


try:
    nested_failure()
except LookupError:
    events.append("caught")

assert events == ["body", "cleanup", "caught"]
~~~

The exception table is compiler metadata, not a table of exception classes that might ever arise. Type matching occurs when handler code runs. Nearly any Python operation can raise <code>MemoryError</code>, invoke user code, or propagate an unexpected extension exception, so a static list of “possible exceptions” is generally an approximation.

Disassembly can display an exception table for study:

~~~python
import dis


def parse_or_default(text: str) -> int:
    try:
        return int(text)
    except ValueError:
        return 0


dis.dis(parse_or_default)
~~~

Do not parse the formatted table as a stable format or synthesize its bytes manually. Compiler invariants connect instruction offsets, cache units, stack depth, and handler conventions.

> **Common misconception 15.36 — “Zero-cost exceptions mean raising an exception has no cost.”**  
> The term describes reduced normal-path setup. Raising still constructs or updates exception state, searches handlers, unwinds stacks, runs cleanup, and commonly builds traceback information.

### 15.9.4 Tracebacks are linked execution records

A traceback object records a frame, a last-instruction indication, a line, and a link to the next traceback in the propagation sequence. Rich rendering combines traceback/code positions with source text. It is not merely a preformatted string.

### Worked example 15.10 — Extract bounded structured traceback data

~~~python
import traceback


def denominator(value: int) -> float:
    return 10 / value


def calculate() -> float:
    return denominator(0)


try:
    calculate()
except ZeroDivisionError as error:
    summary = traceback.TracebackException.from_exception(
        error,
        capture_locals=False,
    )
    locations = [
        (frame.name, frame.filename, frame.lineno)
        for frame in summary.stack
    ]

assert locations[-2][0] == "calculate"
assert locations[-1][0] == "denominator"
~~~

<code>TracebackException</code> can represent formatted diagnostic information without indefinitely preserving all live frames. Setting <code>capture_locals=True</code> obtains representations of locals and can execute hostile <code>repr</code> methods, leak secrets, allocate substantially, or itself fail in surrounding tooling. Production error collection needs bounds and redaction.

Exception groups permit several unrelated exceptions to propagate as one tree and allow <code>except*</code> clauses to handle matching subgroups. The group retains structure rather than flattening every leaf into one message:

~~~python
def grouped() -> None:
    raise ExceptionGroup(
        "parallel failures",
        [ValueError("bad value"), OSError("unavailable")],
    )


handled: list[str] = []
try:
    grouped()
except* ValueError as group:
    handled.extend(type(item).__name__ for item in group.exceptions)
except* OSError as group:
    handled.extend(type(item).__name__ for item in group.exceptions)

assert handled == ["ValueError", "OSError"]
~~~

Multiple <code>except*</code> clauses can act during one propagation operation; this differs from ordinary <code>except</code>, where the first matching clause consumes the selected exception. Derived subgroups preserve metadata and nesting according to group operations.

An exception handler target is cleared at suite completion because the instance points to its traceback and the traceback points to a frame whose locals would otherwise include the instance. This language-level cleanup reduces a common cycle; it does not guarantee immediate reclamation if another reference remains.

> **Common misconception 15.37 — “A traceback is harmless text that cannot affect memory lifetime.”**  
> It is an object graph containing frame references. Retaining it can retain locals, callers, modules, resources, and sensitive data until those references are cleared or released.

Exception machinery depends on every value being represented as an object with a type and lifetime policy. That common header and the type’s slots form the next layer.
