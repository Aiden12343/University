A **branch** is optional relative to the trunk, not intellectually independent. The reader may skip this chapter without impairing another branch. A reader who enters it must nevertheless preserve every earlier distinction: a name is a binding, an object has identity and type, an interface is not its implementation, and an empirical measurement does not become a universal guarantee.

**Data science** is the disciplined construction of claims from data by computational and statistical means. **Data** are recorded representations treated as evidence about some subject. A measurement table is not the measured world. It is the result of instruments, definitions, sampling decisions, encoding rules, omissions, and transformations. Numerical software can calculate exactly according to its implemented rules while supporting a false conclusion because the records do not answer the stated question. Computational correctness, statistical validity, and substantive validity are separate obligations.

This chapter introduces three connected layers:

1. NumPy represents homogeneous multidimensional arrays and delegates regular numerical work to compiled kernels.
2. pandas represents labelled, heterogeneous tabular data and supplies alignment, grouping, joining, and missing-data operations.
3. Statistical reasoning determines what a calculated quantity does and does not justify.

The libraries are examples of durable models, not substitutes for their official versioned documentation. APIs evolve. Every reproducible analysis therefore records environment versions and treats undocumented behaviour as unstable.

### 16.1.1 Four independent standards of adequacy

An analytical result can succeed under one standard and fail under another:

| Standard | Governing question | Representative failure |
|:---|:---|:---|
| computational correctness | Did the program implement its stated transformation? | wrong axis or join key |
| statistical validity | Does the inferential procedure have its claimed properties under defensible assumptions? | treating dependent observations as independent |
| measurement validity | Do recorded fields represent the intended concepts? | using login count as a proxy for learning |
| substantive validity | Does the conclusion answer the real domain question and support the proposed action? | optimising average latency while tail latency causes harm |

The standards are conjunctive for a defensible conclusion: passing three does not compensate for failing the fourth. A perfectly computed confidence interval around a systematically mismeasured quantity remains a precise answer to the wrong question. A well-designed sample can be destroyed by a many-to-many join. A statistically detectable difference can be too small to matter operationally.

This separation extends Chapter 12’s testing model. Unit tests can prove that a function returns an agreed calculation for selected inputs. They cannot, without additional evidence, prove that a sensor was calibrated, participants were sampled without bias, or an estimand corresponds to a policy objective. Those are nevertheless testable claims in the wider scientific sense: calibration studies, sampling audits, sensitivity analyses, and decision evaluation supply different evidence.

> **Common misconception 16.1 — “If the code is correct, the analysis is correct.”**  
> Correct code establishes only that the specified computation was performed. Measurement, sampling, statistical assumptions, causal interpretation, and decision relevance require independent justification.

### 16.1.2 Data work is a chain of lossy representations

A physical or social process produces events. An instrument or administrative procedure selects aspects of them; an encoding converts observations into records; storage formats impose schemas; cleaning changes or rejects values; aggregation discards detail; modelling reduces data to fitted structure; visualisation maps selected quantities to marks; prose turns those marks into claims. Each arrow can lose information or introduce assumptions.

The term **raw data** is therefore relative. A CSV supplied by a laboratory may be raw relative to the analyst’s transformations, but it already incorporates sensor electronics, calibration, filtering, unit conversion, sampling intervals, firmware decisions, and export logic. Preserve the received input unchanged because it is the earliest available evidence, not because it is epistemically untouched.

A useful analytical record assigns each artefact a role:

- **source artefact:** immutable bytes received or retrieved, with provenance and digest;
- **staging representation:** parsed data close to source form, retaining rejected rows and parse diagnostics;
- **validated canonical table:** records satisfying an explicit schema and unit contract;
- **derived table:** deterministic transformation with lineage to inputs and code revision;
- **model artefact:** fitted parameters plus training data identity, procedure and environment;
- **presentation artefact:** chart, table or prose generated from a pinned derived result.

This structure permits correction. If a unit conversion changes, rebuild descendants from the source rather than manually patching a chart. If licensing prohibits retaining source rows, record the lawful provenance and transformation while designing an approved retention policy; reproducibility never overrides law, consent, confidentiality, or ethics.

### 16.1.3 Library versions are part of the method

This edition distinguishes stable conceptual models from versioned interfaces. The numerical examples target NumPy 2.x semantics unless a narrower release is named. Tabular examples use interfaces common to pandas 2.2 and 3.0, while explicitly flagging the pandas 3.0 default Copy-on-Write and string-dtype transitions where relevant. Statistical examples state the procedure rather than treating a library function name as a method description.

Record versions through code rather than memory:

~~~python
from importlib.metadata import PackageNotFoundError, version
import platform
import sys


def environment_versions(names: tuple[str, ...]) -> dict[str, str]:
    result = {
        "python": sys.version.split()[0],
        "implementation": platform.python_implementation(),
        "platform": platform.platform(),
    }
    for name in names:
        try:
            result[name] = version(name)
        except PackageNotFoundError:
            result[name] = "not installed"
    return result


print(environment_versions(("numpy", "pandas", "scipy", "matplotlib")))
~~~

A version report is necessary but insufficient. Linked BLAS/LAPACK libraries, CPU dispatch, thread-pool settings, locale, time-zone database, and optional dtype backends can alter behaviour or performance. Capture variables only when relevant to the claim; exhaustive environment dumps can expose secrets and hinder review.

> **Common misconception 16.2 — “A notebook and its package names fully specify the computational environment.”**  
> Versions, platform libraries, backends, configuration, input identity, execution order, and external state can all affect results. Reproducibility requires a bounded environment contract.

The branch now begins at the point before arrays or tables: deciding what one record means and which collection of possible records the question concerns.
