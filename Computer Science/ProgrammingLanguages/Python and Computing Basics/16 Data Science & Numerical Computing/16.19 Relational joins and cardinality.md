# 16.19 Relational joins and cardinality

A **relation** in the relational model is a set of tuples under named attributes. A practical DataFrame resembles a relation but has ordering, an index, dtypes, and duplicate-row behaviour beyond the pure mathematical model. A **key** is an attribute or combination that uniquely identifies a record under a stated domain. A **foreign key** refers from one relation to a key in another.

A **join** combines records whose key values satisfy a condition. Common equality joins include:

- inner join: retain matched keys;
- left join: retain every left row and attach matching right data;
- right join: symmetrical retention of every right row;
- full outer join: retain keys from either side.

### Worked example 16.12 — Validate join cardinality

~~~python
import pandas as pd

devices = pd.DataFrame(
    {
        "device_id": ["A17", "A18", "A19"],
        "site_id": ["N", "S", "N"],
    }
)
sites = pd.DataFrame(
    {
        "site_id": ["N", "S"],
        "site_name": ["North", "South"],
    }
)

enriched = devices.merge(
    sites,
    on="site_id",
    how="left",
    validate="many_to_one",
    indicator=True,
)

assert enriched["_merge"].eq("both").all()
~~~

<code>validate="many_to_one"</code> states that many device rows may share a site key but the right table must have at most one row per site key. Without it, an accidental duplicate in <code>sites</code> multiplies device rows. This **row explosion** can inflate sums while leaving the program syntactically successful. The indicator exposes unmatched records; the assertion converts their unexpected presence into failure.

Join cardinality must be reasoned about before code:

| Left key multiplicity | Right key multiplicity | Possible matches per key |
|:---:|:---:|:---:|
| one | one | one |
| many | one | many |
| one | many | many |
| many | many | Cartesian multiplication within the key |

A many-to-many join can be intentional. It is dangerous only when the analyst assumes a different relationship.

### 16.19.1 Keys, multiplicities, and conservation checks

A candidate key is not established by a small sample’s apparent uniqueness. It follows from a domain rule and should be verified on every relevant boundary. Composite keys require tuple uniqueness: checking each component separately is too strong when, for example, one device legitimately has many timestamps, and too weak if only one component is inspected.

Before a join, calculate expected cardinalities and identify which quantities should be conserved. A many-to-one enrichment should normally preserve left row count and any left-row measure summed exactly once. A one-to-many expansion should increase rows in an explainable manner; totals may need allocation rather than repetition.

~~~python
import pandas as pd

orders = pd.DataFrame(
    {
        "order_id": [101, 102, 103],
        "customer_id": ["C1", "C2", "C1"],
        "amount": [12.0, 8.0, 5.0],
    }
)
customers = pd.DataFrame(
    {"customer_id": ["C1", "C2"], "segment": ["retail", "trade"]}
)

before_rows = len(orders)
before_total = orders["amount"].sum()

joined = orders.merge(
    customers,
    on="customer_id",
    how="left",
    validate="many_to_one",
    indicator=True,
)

assert len(joined) == before_rows
assert joined["amount"].sum() == before_total
assert joined["_merge"].eq("both").all()
~~~

The total equality is exact here because the same stored floating values are added in the same effective order; general floating computations may require a justified tolerance. These assertions do not prove segment values are correct, but they defend cardinality and coverage invariants.

Column-name collisions produce suffixes unless addressed. A robust join selects only needed right-hand columns, renames ambiguous fields according to provenance, and checks that generated suffixes have not silently propagated. Index-based joins obey the same cardinality reasoning even when key columns are less visible.

> **Common misconception 16.53 — “A successful merge preserves the meaning of totals.”**  
> A merge can duplicate or omit measure-bearing rows while remaining syntactically valid. Declare cardinality, inspect unmatched cases, and test row-count and measure-conservation properties appropriate to the relationship.

### 16.19.2 Null keys and equality semantics

Missing keys require exceptional care. pandas equality merges can match rows whose key values are null-like to other null-key rows, unlike conventional SQL joins in which null does not compare equal to null. Multiple missing keys on both sides can therefore create an unexpected many-to-many product. The behaviour is documented, but it rarely represents a genuine shared entity.

~~~python
import pandas as pd

left = pd.DataFrame({"key": ["A", None, None], "left_value": [1, 2, 3]})
right = pd.DataFrame({"key": ["A", None], "right_value": [10, 20]})

joined = left.merge(right, on="key", how="inner")
assert len(joined) == 3  # one A match and two null-to-null matches
~~~

If missing means “identity unknown”, those two null-left rows must not both be declared the same entity as the null-right row. Reject null keys before joining, assign domain-valid surrogate identifiers, or separate unmatched missing-key rows under an explicit policy. Replacing all nulls with one sentinel string merely reproduces equality and can collide with genuine data.

Canonicalisation of keys is another substantive operation. Trimming whitespace, changing case, removing punctuation, transliterating scripts, or rounding coordinates can increase matches while creating false equivalences. Preserve raw keys, document normalisation, measure match ambiguity, and retain an audit trail. **Record linkage** under uncertain identifiers is a statistical/data-quality task, not an ordinary deterministic join.

> **Common misconception 16.54 — “Missing join keys simply remain unmatched.”**  
> pandas can match null keys to null keys, unlike usual SQL null semantics. Filter, reject, or model missing identities explicitly before a merge, especially when either side contains several null-key rows.

### 16.19.3 Semi-joins, anti-joins, ordered joins, and interval questions

A **semi-join** retains left rows whose keys have at least one right match without adding right columns. An **anti-join** retains left rows without a right match. They can be expressed with a validated indicator merge, while avoiding many-to-many multiplication by first establishing the right key set:

~~~python
import pandas as pd

requests = pd.DataFrame({"request_id": [1, 2, 3], "site": ["N", "X", "S"]})
valid_sites = pd.DataFrame({"site": ["N", "S"]})

membership = requests.merge(
    valid_sites.drop_duplicates("site"),
    on="site",
    how="left",
    validate="many_to_one",
    indicator=True,
)
semi = membership.loc[membership["_merge"].eq("both"), requests.columns]
anti = membership.loc[membership["_merge"].eq("left_only"), requests.columns]

assert semi["request_id"].tolist() == [1, 3]
assert anti["request_id"].tolist() == [2]
~~~

An exact equality join is wrong when the question is temporal proximity. <code>merge_asof</code> performs an ordered nearest, backward, or forward match, optionally within groups and a tolerance. Both inputs must satisfy sorting requirements. A backward as-of join can attach the most recent configuration known at event time; a nearest join might attach a future record and leak information.

~~~python
import pandas as pd

events = pd.DataFrame(
    {
        "time": pd.to_datetime(["2026-01-01 10:04", "2026-01-01 10:11"], utc=True),
        "reading": [7.0, 9.0],
    }
).sort_values("time")
settings = pd.DataFrame(
    {
        "time": pd.to_datetime(["2026-01-01 10:00", "2026-01-01 10:10"], utc=True),
        "mode": ["safe", "fast"],
    }
).sort_values("time")

annotated = pd.merge_asof(
    events,
    settings,
    on="time",
    direction="backward",
    tolerance=pd.Timedelta("15min"),
)
assert annotated["mode"].tolist() == ["safe", "fast"]
~~~

Interval overlap joins, spatial joins, fuzzy linkage, and range containment require specialised predicates or libraries. Converting them into rounded equality keys can introduce boundary artefacts. In every case, report unmatched, multiply matched, and ambiguity counts before using the enriched data.

> **Common misconception 16.55 — “Every data combination problem is an equality merge on cleaned keys.”**  
> Membership, non-membership, temporal precedence, nearest-neighbour, interval overlap, and uncertain linkage are different relations. Choose the operation that encodes the question and audit ambiguity and direction.
