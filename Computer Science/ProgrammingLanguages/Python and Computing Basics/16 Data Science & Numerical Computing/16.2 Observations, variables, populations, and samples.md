# 16.2 Observations, variables, populations, and samples

An **observation** is a recorded unit of analysis, such as one patient visit, one manufactured component, or one transaction. A **variable** in statistics is a characteristic recorded or conceptually defined for observations. This use differs from the programming use criticised in Chapter 5: in Python, a name is a binding, whereas in statistics a variable is a quantity whose observed values differ across units or possible outcomes. Context resolves the term.

A **population** is the complete collection about which a question is posed. A **sample** is the subset actually observed. The population need not be all humans or all objects; it is defined by the research question. “All temperature readings produced by this calibrated sensor under the specified operating regime during September” is a possible population. Changing the regime changes the population.

A **parameter** is a numerical property of a population, such as its mean. A **statistic** is a numerical function of a sample, such as the sample mean. Statistics are observable once the sample is known; population parameters are commonly unknown and estimated through statistics. The distinction prevents an observed average from being mistaken for an exact property of an unseen population.

Data values have a **measurement scale**, which constrains meaningful operations.

- **Nominal** values identify categories without an intrinsic order: blood type or region code.
- **Ordinal** values have an order but not necessarily equal intervals: a rank or ordered response category.
- **Interval** values have meaningful differences but no ratio-preserving zero: temperature in degrees Celsius is the standard example.
- **Ratio** values have meaningful differences and ratios relative to a substantive zero: elapsed time or mass under an appropriate convention.

Storing a category as the integer 3 does not make addition meaningful. Representation type and substantive scale must not be conflated.

### Worked example 16.1 — A table does not define its own semantics

Consider:

| device_id | elapsed_ms | status |
|:---|---:|:---|
| A17 | 83 | ok |
| A18 | 107 | retry |
| A19 | 91 | ok |

The string column <code>device_id</code> is nominal. Lexicographic order is available computationally but carries no necessary scientific meaning. <code>elapsed_ms</code> is a ratio-scale measurement if zero milliseconds means zero elapsed duration under the measurement procedure. <code>status</code> is nominal even if encoded as 0 and 1. A mean of status codes would be interpretable only after an explicit indicator convention, for example 1 for retry and 0 otherwise; it would then estimate a retry proportion, not an “average status.”

The table still leaves questions unanswered. Were failed devices omitted? Was elapsed time rounded? Does each row represent an independent device, or could one physical device appear repeatedly under different identifiers? Which clock produced the measurements? These are schema and provenance questions, not syntactic details.

### 16.2.1 The unit of analysis determines permissible counting

The **unit of analysis** is the entity about which a row-level or model-level conclusion is drawn. A table can contain one row per request while the scientific unit is a user, one row per laboratory reading while the unit is a specimen, or one row per examination while the unit is a student. Treating rows as independent units inflates apparent sample size whenever several rows arise from one unit.

Suppose 1,000 requests came from ten users. The row count is 1,000; the number of users is ten. A confidence calculation that assumes 1,000 independently sampled users is not repaired by correct arithmetic. Dependence within user can make the effective information much closer to ten clusters than 1,000 independent units.

An **identifier** is a value intended to distinguish units under a scope. An identifier is not automatically a key: duplicates, reuse across dates, missing values, and source-system changes can violate uniqueness. A **composite key** uses several fields, such as <code>(site_id, device_id, observed_at)</code>, when no single field uniquely identifies a record.

Represent key expectations before analysis:

~~~python
from collections import Counter


records = [
    {"user_id": "U1", "request_id": "R1"},
    {"user_id": "U1", "request_id": "R2"},
    {"user_id": "U2", "request_id": "R3"},
]

request_counts = Counter(row["request_id"] for row in records)
user_counts = Counter(row["user_id"] for row in records)

assert max(request_counts.values()) == 1
assert user_counts == {"U1": 2, "U2": 1}
~~~

The request identifier is unique in this toy scope; the user identifier is deliberately repeated. Neither dictionary syntax nor a later DataFrame can infer which is the analytical unit.

> **Common misconception 16.3 — “Each row is automatically one independent observation.”**  
> A row is a storage unit. Scientific independence and the unit of analysis follow the data-generating and sampling process, including repeated and clustered measurements.

### 16.2.2 Variables have roles as well as stored types

A **conceptual variable** names a property of interest, such as household income or response latency. An **operational definition** specifies how it is measured: source, instrument, unit, timing, inclusion rule and transformation. Two columns named <code>income</code> can represent gross annual household income, monthly personal take-home pay, an imputed bracket midpoint, or an administrative benefit assessment; they are not interchangeable.

Useful variable roles include:

- **identifier:** distinguishes entities but is not ordinarily treated as magnitude;
- **outcome:** quantity whose variation is to be described or explained;
- **exposure or treatment:** condition whose association or effect is under study;
- **covariate:** additional measured characteristic used for description, adjustment or prediction;
- **weight:** quantity determining how an observation contributes under a sampling or aggregation design;
- **time index:** orders events or associates them with calendar/elapsed time;
- **censoring/selection indicator:** records whether an outcome is fully observed or why inclusion ended.

These are analytical roles, not immutable properties. Age may be an outcome in one study and a covariate in another. A database identifier must rarely be converted to a numerical predictor merely because it contains digits.

A **proxy** is an observed variable used in place of a target concept that is difficult to measure. Proxy validity requires evidence about the relationship and can vary among subgroups. “Clicks” may proxy engagement, but interface design, bots, accessibility needs and repeated accidental activation also affect clicks.

**Measurement error** is the difference between recorded and target quantity under a defined model. **Systematic error** has a directional or structurally patterned component; **random error** varies unpredictably under repeated measurement. Averaging can reduce selected zero-centred random error but does not remove systematic bias.

~~~python
from dataclasses import dataclass


@dataclass(frozen=True)
class FieldDefinition:
    name: str
    concept: str
    operational_definition: str
    unit: str | None
    role: str
    nullable: bool


latency = FieldDefinition(
    name="latency_ms",
    concept="request completion latency",
    operational_definition=(
        "monotonic-clock difference from accepted request to final byte"
    ),
    unit="millisecond",
    role="outcome",
    nullable=False,
)

assert latency.unit == "millisecond"
~~~

The dataclass is a documentation structure, not enforcement that source clocks are monotonic or final-byte events are recorded. Validation must connect declarations to acquisition and tests.

> **Common misconception 16.4 — “A numeric storage type makes a variable quantitative.”**  
> Codes, identifiers and ordered categories can be stored as numbers without supporting arithmetic differences or ratios. Meaning comes from the measurement contract.

### 16.2.3 A target population, sampling frame and realised sample differ

The **target population** is the collection to which the desired conclusion refers. The **sampling frame** is the operational list or mechanism from which units can actually be selected. The **realised sample** contains units that were selected, available, consented, recorded and survived quality rules. Gaps between these sets create **coverage**, **non-response** and **selection** mechanisms.

A **census** attempts to observe every member of a defined population. It does not eliminate measurement error, missing values, frame omissions, duplication or changes over time. Administrative “complete data” can be complete only for people using a service, not for all people eligible for it.

A **probability sample** uses a design giving units known non-zero selection probabilities. A **simple random sample** of fixed size gives each equal-sized subset equal probability. Stratified, clustered and unequal-probability designs require corresponding weights and variance methods. A convenience sample has unknown selection probabilities and cannot inherit probability-sampling claims by growing large.

Selection can be represented with inclusion indicators. Let (S=1) mean a unit enters the observed sample and (Y) be an outcome. If the chance of (S=1) depends on (Y) or its causes, the observed distribution (Y\mid S=1) can differ systematically from the target population distribution.

Consider an uptime survey sent only through the service being evaluated. Users unable to connect cannot receive the survey, so severe failures are structurally under-covered. Ten million responses would estimate the responding reachable population extremely precisely while missing the primary failure mode.

### 16.2.4 Longitudinal and cross-sectional structures answer different questions

**Cross-sectional data** observe units at one time or over a short reference period. **Longitudinal data** observe the same units repeatedly. **Panel data** combine unit and time dimensions; **cohort data** follow units sharing an entry condition. Repeated observations support change analysis but introduce within-unit dependence, attrition and time-varying measurement.

Wide and long storage forms, introduced later, do not determine study design. A longitudinal study can be stored wide with one column per occasion or long with one row per unit-occasion. The unit-time key and acquisition process establish structure.

> **Common misconception 16.5 — “A very large sample is necessarily representative.”**  
> Size reduces selected random error under a design; it does not repair coverage, non-response, measurement, survivorship or selection bias and can make a biased estimate deceptively precise.

Having defined what the values represent, description can summarise their observed distribution without yet making a claim about an unseen population.
