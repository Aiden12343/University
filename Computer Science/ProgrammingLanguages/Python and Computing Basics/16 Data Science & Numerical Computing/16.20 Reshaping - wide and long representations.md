# 16.20 Reshaping: wide and long representations

A **wide** table commonly gives repeated measurements separate columns, while a **long** table gives one measurement per row with variables identifying kind and occasion. Neither is universally canonical. An operation may be clearer in one form.

~~~python
import pandas as pd

wide = pd.DataFrame(
    {
        "device_id": ["A17", "A18"],
        "morning": [83, 107],
        "evening": [88, 101],
    }
)

long = wide.melt(
    id_vars="device_id",
    var_name="period",
    value_name="latency_ms",
)

restored = long.pivot(
    index="device_id",
    columns="period",
    values="latency_ms",
)
~~~

<code>melt</code> turns measurement-column names into values of <code>period</code>. <code>pivot</code> requires each index/column pair to identify at most one value; duplicates make the intended result ambiguous. <code>pivot_table</code> can aggregate duplicates, but doing so silently changes the question unless an aggregation rule was specified in advance.

### 16.20.1 Tidy structure and observational grain

In **tidy data**, each variable forms a column, each observation forms a row, and each observational unit type forms a table. The principle is useful because many operations then map predictably to columns and groups. It is not a command that every exported report must be long, nor does it decide what counts as one observation. That decision follows from the domain and estimand.

Consider a table with columns <code>height_2025</code> and <code>height_2026</code>. If year is a variable, those names encode values inside schema. Melting them can expose <code>year</code> as data. By contrast, columns <code>height_cm</code> and <code>mass_kg</code> are different variables and should not be melted into one untyped “measurement” column unless another column preserves measure kind and units.

Normalisation separates repeated entity attributes from repeated events. A customer name copied into every transaction is convenient for reading but risks inconsistency; a customer table keyed by customer identifier and a transaction table carrying a foreign key represent different grains. Analytical tables may deliberately denormalise for computation, provided the join and snapshot provenance are recorded.

Reshape operations should preserve an identifiable key. Before melting, determine which columns uniquely identify a source row and whether generated variable labels can collide. After pivoting back, compare values, dtypes, label names, column order, and missingness—not only row count.

~~~python
import pandas as pd

wide = pd.DataFrame(
    {
        "device": ["A", "B"],
        "latency_morning": [10.0, 20.0],
        "latency_evening": [12.0, 18.0],
    }
)

long = wide.melt(
    id_vars="device",
    var_name="measure_period",
    value_name="latency_ms",
)
long[["measure", "period"]] = long["measure_period"].str.rsplit(
    "_", n=1, expand=True
)

assert long.duplicated(["device", "measure", "period"]).sum() == 0
~~~

Encoding two fields in one column-name convention is itself a schema. Splitting on an underscore assumes measure names do not make the boundary ambiguous. A more robust source format supplies measure and period explicitly.

> **Common misconception 16.56 — “Long format is always tidy and wide format is always untidy.”**  
> Tidiness depends on what constitutes a variable, observation, and observational unit. Wide matrices are natural for some algorithms; long event tables are natural for others. Preserve grain, identifiers, and units during conversion.

### 16.20.2 Invertibility, aggregation, and nested values

A transformation is **invertible** when the original can be recovered uniquely from its result under a stated equivalence. <code>melt</code> followed by <code>pivot</code> can be invertible if identifier and variable columns uniquely identify every value and if metadata/coercion losses are controlled. <code>pivot_table</code> usually performs an aggregation, so it is many-to-one and cannot generally be inverted.

~~~python
import pandas as pd

long = pd.DataFrame(
    {
        "student": ["A", "A", "A", "B"],
        "subject": ["maths", "maths", "history", "maths"],
        "score": [70, 80, 75, 90],
    }
)

duplicates = long.duplicated(["student", "subject"], keep=False)
assert duplicates.sum() == 2

mean_table = long.pivot_table(
    index="student",
    columns="subject",
    values="score",
    aggfunc="mean",
)
assert mean_table.loc["A", "maths"] == 75
~~~

The two mathematics records have been collapsed. Whether they are repeated attempts, duplicate ingestion, or separate assessors determines the correct response. An aggregation must not be selected merely to silence <code>pivot</code>’s duplicate error.

<code>stack</code> moves column-index levels into the row index; <code>unstack</code> moves row-index levels into columns. Missing combinations, sorting, and categorical levels affect results, and implementation details have evolved. Index names are critical: unnamed MultiIndex levels make later code depend on numeric level positions.

<code>explode</code> converts each list-like cell into multiple rows. It changes grain and duplicates values from other columns:

~~~python
import pandas as pd

articles = pd.DataFrame(
    {
        "article_id": [1, 2],
        "tags": [["python", "arrays"], []],
    }
)
exploded = articles.explode("tags", ignore_index=True)
print(exploded)
~~~

The empty list produces a missing-like tag row under current semantics. Exploding several columns together requires matching element counts row by row. Summing an article-level measure after tag explosion duplicates it once per tag; one must either aggregate at article grain first or allocate the measure according to a justified rule.

Reshaping can also change dtype because several source columns must share one value column, or because missing combinations are introduced. A round-trip test should include adversarial cases: duplicate keys, empty lists, missing labels, categorical levels, mixed dtypes, and identifiers whose text resembles missing tokens.

> **Common misconception 16.57 — “Reshaping changes only presentation.”**  
> A reshape can change observational grain, introduce or remove missing combinations, coerce dtypes, aggregate duplicates, and duplicate measures. Treat it as a semantic transformation with preconditions and invariants.
