# 16.21 Time data, ordering, and time zones

A date-time value combines a calendar system, a clock reading, precision, and possibly a relation to a time zone. A **time zone** is a rule set mapping local civil times to offsets from a universal timeline; it is not merely a fixed number of hours. Daylight-saving transitions and political changes make named-zone rules date-dependent.

A **naive datetime** lacks time-zone interpretation. An **aware datetime** has sufficient offset or zone information for timeline reasoning under library rules. Data from distributed systems should commonly be normalised to a stable timeline representation such as UTC while retaining original zone information where civil-time interpretation matters.

~~~python
import pandas as pd

events = pd.DataFrame(
    {
        "occurred_at": [
            "2026-03-29T00:30:00Z",
            "2026-03-29T01:30:00Z",
        ]
    }
)

events["occurred_at"] = pd.to_datetime(
    events["occurred_at"],
    utc=True,
)
events["london_time"] = events["occurred_at"].dt.tz_convert(
    "Europe/London"
)
~~~

Parsing with <code>utc=True</code> creates a consistent aware timeline. Conversion uses time-zone rules for the specified dates. Replacing the time-zone label without conversion is a different operation: it changes or supplies interpretation rather than preserving the instant. Tests must include clock changes, ambiguous local times, nonexistent local times, leap years, and interval boundaries.

Time-series resampling groups values into calendar or duration bins. The analyst must specify closed side, label side, origin, time zone, and handling of missing intervals. “Daily average” is incomplete when observations have irregular frequency, unequal coverage, or local-day transitions.

### 16.21.1 Instants, civil labels, durations, and periods

An **instant** is a point on a timeline. A **local civil time** is a calendar-and-clock label interpreted under a jurisdiction’s zone rules. A **duration** is an elapsed amount of time. A **calendar period** is a labelled interval such as February 2028 or financial quarter 2026-Q3. These are related but not substitutable.

Adding 24 elapsed hours to an instant need not yield the same local clock time on the next civil day across a daylight-saving transition. Adding one calendar month has no fixed duration because months differ in length. Dividing a financial quarter into seconds answers a different question from advancing one quarter. pandas represents these concepts through timestamp-like, Timedelta-like, Period-like, DateOffset, and time-zone-aware dtypes and objects.

Time-zone-aware storage normally records instants in a uniform underlying timeline while associating a zone for display and civil operations. Two differently displayed aware timestamps can represent the same instant:

~~~python
import pandas as pd

utc = pd.Timestamp("2026-07-01 12:00:00", tz="UTC")
new_york = utc.tz_convert("America/New_York")

assert utc == new_york
assert utc.hour == 12
assert new_york.hour == 8
~~~

The equality concerns the instant; the hour fields concern different civil representations. Removing a zone with <code>tz_localize(None)</code> retains displayed wall-clock fields and discards timeline interpretation, whereas conversion to UTC followed by removal yields a naive UTC clock label. Both may be useful, but neither should be implicit.

Localising naive times encounters **ambiguous times** when clocks move backward and one wall-clock label occurs twice, and **nonexistent times** when clocks move forward and a range of labels is skipped. pandas requires or offers policies such as raising, inferring, selecting a fold, shifting, or marking missing. A bulk inference based on order can fail when records are absent or unsorted.

~~~python
import pandas as pd

naive = pd.DatetimeIndex(["2026-10-25 00:30", "2026-10-25 01:30"])
aware = naive.tz_localize(
    "Europe/London",
    ambiguous=[False, True],
    nonexistent="raise",
)
print(aware)
~~~

The supplied Boolean choices disambiguate local times according to pandas’ daylight-saving interpretation. Domain data should preferably include an offset, UTC instant, or source-system fold indicator so that analysts do not guess later.

> **Common misconception 16.58 — “A time zone is a fixed UTC offset attached to a clock reading.”**  
> A named zone is a history and rule set whose offset can vary by date and policy. Instants, local civil labels, elapsed durations, and calendar advances require distinct operations.

### 16.21.2 Precision, range, parsing, and clock quality

A timestamp’s visible decimal places do not prove measurement accuracy. **Resolution** is the smallest representable increment; **precision** describes repeatability or granularity; **accuracy** describes closeness to the relevant true time. A system can store nanoseconds for a clock synchronised only to tens of milliseconds. Ordering events with equal or uncertain timestamps may require a sequence number or causal identifier.

NumPy and pandas date-time representations use fixed-width integer counts relative to an epoch at a unit. Finer units cover a smaller representable calendar range. Library releases have expanded or altered resolution support, so code should not hard-code one historical nanosecond range as a universal property. Parse required bounds and units in tests.

Parsing should reject ambiguity rather than rely on locale inference:

~~~python
import pandas as pd

raw = pd.Series(["2026-09-01T13:45:30Z", "2026-09-02T07:05:00Z"])
parsed = pd.to_datetime(
    raw,
    format="%Y-%m-%dT%H:%M:%SZ",
    utc=True,
    errors="raise",
)
assert str(parsed.dtype).startswith("datetime64")
~~~

Unix-like numeric timestamps need an explicit unit and origin. Interpreting milliseconds as seconds can move a date far outside range or, worse, produce a plausible but wrong instant. Spreadsheet serial dates and GPS times have different epochs and leap-second conventions. Record the source clock, unit, epoch, zone, and synchronisation method.

Most civil software does not represent leap seconds as ordinary 60-valued seconds. UTC, TAI, GPS time, monotonic process clocks, and operating-system wall clocks have different purposes. Measuring elapsed program duration should use a monotonic clock rather than subtracting wall-clock readings that an administrator or synchronisation service can adjust. Chapter 14 introduced <code>perf_counter</code> for this reason.

Time ordering is also not necessarily causal ordering. Distributed messages can arrive late; device clocks can drift; database commit time differs from event occurrence; ingestion time differs from both. A robust event schema may carry <code>occurred_at</code>, <code>received_at</code>, and <code>processed_at</code> separately.

> **Common misconception 16.59 — “More timestamp digits mean more accurate temporal data.”**  
> Representation resolution can exceed clock accuracy by orders of magnitude. Preserve source, unit, epoch, zone, uncertainty, and ordering semantics; do not manufacture certainty by formatting.

### 16.21.3 Resampling, exposure, and information boundaries

Resampling maps observations onto bins. For event counts, summing events in each half-open interval may be appropriate. For a state variable observed irregularly, taking the arithmetic mean of recorded values weights observation occasions, not elapsed time. A time-weighted mean requires a model of the value between observations and an exposure interval.

Suppose a sensor reports 10 at 00:00, 20 at 00:01, and 20 at 00:59. The mean of records is (50/3), but under a step-function assumption that each value persists until the next observation, the hour is near 20 because the initial value persists for only one minute. Neither answer is correct until the observation process is specified.

~~~python
import pandas as pd

events = pd.Series(
    [1, 1, 1],
    index=pd.to_datetime(
        ["2026-01-01 00:59", "2026-01-01 01:00", "2026-01-01 01:59"],
        utc=True,
    ),
)

hourly = events.resample(
    "1h",
    closed="left",
    label="left",
    origin="start_day",
).sum()
assert hourly.iloc[0] == 1
assert hourly.iloc[1] == 2
~~~

The event exactly at 01:00 belongs to the second interval because bins are closed on the left. Changing closure changes boundary attribution. Calendar-frequency resampling in a local zone can create days with 23 or 25 elapsed hours; converting to UTC before duration-based analysis and converting labels back for reporting often clarifies the distinction.

Time series also distinguish:

- **event time**, when the represented phenomenon occurred;
- **availability time**, when its value could have been used by the decision system;
- **processing time**, when the current pipeline handled it;
- **revision time**, when a corrected value became known.

Backtests must join on availability, not merely on the date a statistic describes. A monthly economic indicator labelled January but published and revised in February was not available during January. Selecting the latest revised historical table introduces **look-ahead bias**.

Lagged and rolling features should be derived after sorting and within the evaluation boundary. A centred rolling mean uses later rows; backward fill uses a future observation; interpolation can span the train/test boundary; resampling the full dataset can expose future bin composition. A safe forecasting pipeline specifies a prediction cutoff and proves that every input has an availability timestamp no later than that cutoff.

Regularity must be tested rather than inferred from a DateTimeIndex. Duplicate timestamps, gaps, variable sampling rates, and late events affect frequency methods. A row shift means “previous row”; a one-day time shift means “same label one day away”; they coincide only under strict regularity.

> **Common misconception 16.60 — “Sorting by timestamp prevents temporal leakage.”**  
> Sorting establishes an order but not an information boundary. Revised values, delayed labels, centred windows, future-filled gaps, entity crossover, and publication lag can all expose information unavailable at prediction time.
