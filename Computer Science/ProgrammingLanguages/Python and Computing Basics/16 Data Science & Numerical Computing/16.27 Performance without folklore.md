# 16.27 Performance without folklore

Array and table performance depends on:

- algorithmic work;
- element representation and width;
- memory layout and access order;
- allocation and copying;
- cache and memory bandwidth;
- native library implementation;
- thread-pool configuration;
- data size and distribution;
- conversion across Python/native or host/device boundaries.

“Vectorise everything” is not an adequate rule. A built-in pandas string operation can still create Python objects or expensive temporaries. A carefully written compiled kernel may dominate; a small Python loop can be clearer and fast enough. Measure the operation that matters with representative data.

Memory profiling is as important as elapsed time. If four intermediate float64 arrays each contain 100 million elements, their raw element storage alone is approximately \(4\times100{,}000{,}000\times8\) bytes, or 3.2 billion bytes, before other objects and allocator effects. Peak memory can terminate a computation even when the final result is small.

Chunking processes bounded partitions:

~~~python
from io import StringIO

import pandas as pd

source = StringIO("latency_ms\n10\n20\n\n30\n")
total = 0.0
count = 0

for chunk in pd.read_csv(
    source,
    usecols=["latency_ms"],
    chunksize=100_000,
):
    values = chunk["latency_ms"].dropna()
    total += float(values.sum())
    count += int(values.size)

mean = total / count if count else float("nan")
~~~

The algorithm avoids holding the full file in memory, but only because sum and count compose across chunks. A median cannot be computed exactly from chunk medians. Streaming algorithms require algebraic reasoning about sufficient state.

### 16.27.1 A performance model precedes optimisation

Elapsed time can be decomposed conceptually into computation, memory movement, allocation, interpreter overhead, I/O, synchronisation, and waiting on other systems. The dominant component determines which optimisation can matter. A faster arithmetic kernel cannot accelerate a job waiting on a remote object store; parallel reads cannot repair an (O(n^2)) pairwise algorithm at scale.

**Operational intensity** is the amount of useful arithmetic per byte transferred through a level of the memory hierarchy. Low-intensity operations such as adding two large arrays are often limited by memory bandwidth: each element requires reads and a write for very little arithmetic. High-intensity matrix multiplication can reuse cached blocks and exploit vector units, approaching compute limits. This explains why “NumPy is fast” varies by operation and layout.

Construct a benchmark that specifies:

- representative shapes, dtypes, contiguity, missingness, and value distribution;
- cold versus warm caches and whether one-time compilation or parsing is included;
- setup separated from the operation unless setup belongs to production latency;
- repeated measurements with distribution, not only the minimum;
- synchronisation for asynchronous/device operations;
- software versions, hardware, power mode, and thread settings where material;
- correctness and memory checks for every candidate.

The smallest timing is sometimes used to estimate uncontended execution because pauses only lengthen runs, but production tail latency may be the quantity that matters. A benchmark must reflect the service objective.

~~~python
from time import perf_counter

import numpy as np

rng = np.random.default_rng(42)
values = rng.standard_normal(2_000_000)

# Warm the relevant implementation path.
np.square(values, out=np.empty_like(values))

durations = []
output = np.empty_like(values)
for _ in range(7):
    start = perf_counter()
    np.square(values, out=output)
    durations.append(perf_counter() - start)

print(f"median seconds: {np.median(durations):.6f}")
assert np.all(output >= 0.0)
~~~

The preallocated output excludes repeated destination allocation from the measured region. That is appropriate only if the real application can reuse storage. The assertion is a weak sanity check; numerical equivalence to a trusted calculation should be tested outside the timing loop.

### 16.27.2 Vectorisation trades interpreter work for kernels and temporaries

Vectorisation has two meanings often conflated: expressing an operation over whole arrays, and executing machine instructions that operate on several scalar lanes. A NumPy expression can achieve the first without a particular CPU SIMD strategy; a compiled loop can use SIMD without exposing array syntax to Python.

Whole-array operations reduce per-element Python dispatch and enable optimised native loops. They can also allocate full-sized temporaries. For

\[
z=(a-b)^2+(c-d)^2,
\]

a direct expression may allocate each difference and square before the sum. Using <code>out</code>, controlled in-place updates, expression compilers, or a fused native kernel can reduce memory traffic. Mutation is safe only when aliases and later uses are understood.

Algorithmic reformulation dominates micro-optimisation. Computing every pairwise distance between (n) points needs (O(n^2)) outputs if all distances are materialised, regardless of broadcasting elegance. Blocking bounds peak intermediates but not output size. If only nearest neighbours or aggregate statistics are needed, spatial indices, streaming top-k selection, or domain structure may avoid materialising the matrix.

pandas performance depends heavily on dtype. Object-dtype strings invoke Python object machinery and pointer chasing; extension or Arrow-backed representations may be denser and dispatch to different kernels, but support and semantics vary. A row-wise <code>apply(axis=1)</code> constructs Python-level row objects and is often expensive. Vectorised column expressions, joins, categorical encodings, or a compiled specialised kernel may help after profiling. Converting to NumPy can lose missing and label semantics, so performance gains must be weighed against boundary complexity.

### 16.27.3 Threads, native libraries, and oversubscription

NumPy, SciPy, pandas, compression libraries, and file readers may release the GIL or create native threads. BLAS implementations can use a thread pool for linear algebra. If a multiprocessing job starts eight processes and each native library starts eight threads, 64 runnable workers can contend for fewer cores, memory bandwidth, and caches. This **oversubscription** can make parallel code slower and less predictable.

Thread-count environment settings must ordinarily be configured before importing the relevant native libraries, and their exact names depend on the runtime. Record them in benchmark and production manifests. More threads do not guarantee speedup: small matrices cannot amortise scheduling, low-intensity operations saturate bandwidth, and virtualised/container CPU quotas can differ from visible logical processors.

Parallel reductions can change addition order, producing small floating differences. Bitwise reproducibility may require fixed algorithms and thread counts, at a performance cost, and still may not transfer across instruction sets or library builds. Most scientific contracts should define numerical tolerances and statistical reproducibility rather than assume identical final bits, while cryptographic and exact-integer applications require different guarantees.

### 16.27.4 Memory, chunking, and external representations

Peak memory includes input buffers, parsed columns, indices, masks, temporary arrays, output, allocator fragmentation, and copies created at interoperability boundaries. Object arrays include only pointer storage in <code>nbytes</code>; pointed-to Python objects consume additional memory. A DataFrame’s reported deep memory usage is an estimate and can count shared objects imperfectly.

Chunking works when a computation has mergeable state. Mean can be formed from count and a stable running sum; variance can use mergeable count, mean, and second-moment state; approximate quantile sketches trade accuracy for bounded state. Exact global sorting, arbitrary joins, and exact median generally require external algorithms, partitioning, or storage proportional to data.

A chunked CSV loop is not automatically out-of-core if each transformed chunk is accumulated in a list and concatenated. Stream results to a durable typed format or reduce them. Column projection, predicate pushdown, partition pruning, and compressed columnar formats can avoid reading irrelevant bytes when the storage engine supports them. These optimisations require schema and partition design upstream.

Optimisation should end with a documented comparison: same accepted result under defined tolerances and invariants, lower relevant resource cost on representative inputs, no unacceptable loss of clarity or portability, and monitoring for distribution changes. A locally faster expression that changes missing-value handling is not an optimisation; it is another algorithm.

> **Common misconception 16.72 — “Vectorised or parallel code is necessarily the fastest correct solution.”**  
> Performance depends on algorithm, representation, memory traffic, allocation, kernel implementation, threading, I/O, and scale. Measure end-to-end resource use while preserving an explicit semantic and numerical contract.
