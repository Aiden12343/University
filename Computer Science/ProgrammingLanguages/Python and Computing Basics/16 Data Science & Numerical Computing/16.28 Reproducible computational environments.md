# 16.28 Reproducible computational environments

A reproducible project records:

- source code revision;
- Python implementation and version;
- direct and transitive dependency versions;
- platform and architecture where relevant;
- input data identity and retrieval date;
- configuration;
- random generator state or seed strategy;
- commands that rebuild outputs;
- expected tests and checksums.

A notebook is a document containing executable cells and outputs. Its interactive state can violate visible top-to-bottom order: a cell may have been run after a later cell, and deleted code may still have affected memory. Before publication, restart the kernel and execute all cells in order. Production transformations are often more testable as importable functions called by the notebook than as stateful cells containing all logic.

Reproducibility is not identical to correctness. A biased analysis can be reproduced perfectly. Reproducibility makes the process inspectable and the error repeatable; validation determines whether the process answers its question.

### 16.28.1 Levels of reproducibility

Terminology varies across disciplines, so define the intended guarantee. A useful hierarchy is:

- **repeatability**: the same team, code, data, and environment can rerun the computation;
- **computational reproducibility**: another investigator can obtain materially consistent results from the supplied artefacts;
- **replicability**: an independent study or implementation obtains compatible evidence under a comparable design;
- **robustness**: conclusions survive plausible alternative specifications, assumptions, and perturbations.

These levels are not automatic implications. A container can repeat an implementation defect. An independently collected study can fail to reproduce an effect because the population differs rather than because either study was fraudulent. State what was repeated, by whom, under which equivalence criterion.

Exact byte-for-byte reproduction is appropriate for source archives, checksums, and some deterministic transformations. Numerical reproduction may instead require tolerances because parallel reductions, BLAS libraries, CPUs, and floating implementations can vary. Statistical reproduction can require agreement of distributions or inferential conclusions rather than identical random draws. Define the equivalence relation before comparing outputs.

### 16.28.2 Project organisation and executable entry points

A compact analytical project can use the following conceptual layout:

~~~text
project/
├── pyproject.toml
├── README.md
├── LICENSE
├── src/
│   └── analysis_package/
│       ├── __init__.py
│       ├── ingest.py
│       ├── transform.py
│       └── report.py
├── tests/
│   ├── data/
│   └── test_transform.py
├── notebooks/
│   └── exploratory.ipynb
├── config/
│   └── published-analysis.toml
├── data/
│   ├── README.md
│   └── checksums.sha256
└── outputs/
    └── README.md
~~~

The directory tree is illustrative, not a standard imposed by Python. Importable code in <code>src</code> avoids relying on the notebook’s working directory. Tests own small lawful fixtures. Configuration is versioned separately from code. Data and outputs include governance notes; large or restricted data may be referenced by immutable identifiers rather than committed.

There should be one documented command that builds each principal result from declared inputs. A task runner, workflow engine, or ordinary Python entry point can encode dependencies. File modification times alone are unreliable provenance across downloads and clock changes; content hashes and explicit manifests are stronger. A workflow should write outputs atomically so interruption cannot leave a partial file masquerading as complete.

Exploration and production serve different purposes. A notebook is valuable for inspecting distributions and developing hypotheses. Stable transformations should migrate into functions or modules with tests, while the notebook calls those interfaces. Parameterised notebook execution can produce reports, but only if a clean kernel runs cells in declared order and failures stop publication.

### 16.28.3 Environments, lock files, and containers

A dependency declaration states acceptable version ranges for development or distribution. A **lock file** records a resolved dependency graph, commonly including hashes and platform markers, so an application environment can be reconstructed more closely. A virtual environment isolates Python packages but not the operating-system kernel, C library, drivers, CPU, locale, time-zone database, external services, or data.

A container image packages user-space files and configuration atop a host kernel. It improves portability but is not a complete virtual machine or eternal archive. Image tags such as <code>latest</code> are mutable; use content digests for identity. Base images, package indices, and build steps can disappear. Preserve build recipes and, for important work, archive resolved artefacts in a governed repository.

Native dependencies matter. NumPy may link against different BLAS implementations; compression and time-zone databases change behaviour; compiler flags can select CPU instructions. Capture diagnostic output programmatically where needed, but avoid leaking credentials, hostnames, or personal paths into public manifests.

An environment report should distinguish direct requirements from the full resolved inventory. Listing every installed package from a cluttered workstation may include irrelevant tools and still omit system libraries. Build the project in a clean environment, run tests, then record the resolution used.

### 16.28.4 Randomness and deterministic execution

Reproducible stochastic work records:

- bit-generator algorithm and relevant library version;
- root entropy or a securely stored state when disclosure is inappropriate;
- stream-spawn hierarchy and mapping to tasks;
- number, order, and shapes of stochastic operations when stream identity must be exact;
- deterministic preprocessing and row ordering before random splitting;
- policy for native-library nondeterminism and hardware accelerators.

Seeding a model does not necessarily make a whole pipeline deterministic. Hash iteration, parallel scheduling, non-associative reductions, GPU kernels, data-loader order, and external services can vary. Deterministic modes may be slower or unsupported for some operations. Report residual nondeterminism and evaluate whether it changes substantive results.

Where exact reruns are required for audit, preserve realised split identifiers and sampled indices in addition to the seed. This guards against later changes in row ordering or random algorithms. Do not publish secrets or identifiers that compromise privacy; store sensitive manifests under access control.

### 16.28.5 Data lineage, immutable identity, and permissible archiving

**Data lineage** records how an artefact derives from sources through transformations. A useful lineage record names source owner, acquisition method and time, licence or consent basis, version/snapshot, byte-level hash where stable, schema, filters, and transformations. A URL and retrieval date may be the only available identity for a changing public source, but it is weaker than an immutable snapshot.

Raw data should be treated as immutable within the analytical process. Corrections arrive as new versions or append-only change records, not silent edits. The “raw” file may already be a constructed export; provenance should not imply unmediated reality. Canonicalisation can change byte hashes while preserving logical values, so retain both original-byte and canonical-table identities when needed.

The FAIR principles—findable, accessible, interoperable, and reusable—guide stewardship, but “accessible” permits authenticated and governed access. Personal, confidential, copyrighted, culturally sensitive, or security-relevant data must not be made public merely for reproducibility. A reproducibility package can include metadata, code, schema, synthetic fixtures, aggregate checks, and a controlled-access procedure.

Retention has costs and legal limits. A reproducibility plan should state who may access data, for how long, where encryption keys reside, and how deletion obligations interact with archives and backups. De-identification is not a simple removal of names: linkage and rare combinations can re-identify individuals.

### 16.28.6 Reports as claims with traceable evidence

Every reported number or figure should be traceable to a machine-readable result and an execution manifest. Tables need units, denominators, missing counts, rounding rules, and definitions. Figures need captions with population, period, exclusions, transformations, uncertainty, and source. Model outputs need evaluation design and comparison baseline.

A **computational narrative** explains why transformations and models answer the question, not merely what commands were run. It distinguishes decisions fixed before outcome inspection from exploratory choices, records abandoned analyses when they affect selection, and exposes limitations. References should identify software and methods at stable versioned sources rather than cite only a package home page.

Long-lived reproduction should be tested by a clean-room exercise: another person follows the documented entry point on a fresh environment with only authorised artefacts. Record failures as missing requirements and improve the package. Continuous integration can repeatedly test code and small fixtures, while periodic archival drills verify that external data and registries remain available.
