# 16.5 Why an array abstraction exists

A Python list can hold references to arbitrary objects. That generality is useful but costly for regular numerical work. A list of one million Python integers ordinarily involves a dynamic array of references plus separately represented integer objects. Adding corresponding elements through a Python loop repeatedly performs bytecode dispatch, iteration protocol operations, type checks, numeric protocol dispatch, reference management, and result-object allocation.

A **homogeneous array** represents many elements under one declared element format. Homogeneous means that each logical element obeys the same representation rule. NumPy’s central type, <code>numpy.ndarray</code>, is a multidimensional array object with:

- a data region or reference to one;
- a **shape**, giving the length of each dimension;
- a **dtype**, describing the element representation and operations;
- **strides**, giving byte offsets needed to advance one step along each dimension;
- flags and ownership relationships governing layout and mutability.

A **dimension**, also called an axis in array contexts, is one independent index direction. An array with shape <code>(3, 4)</code> has two axes: three positions along axis 0 and four along axis 1. It contains \(3\times4=12\) logical elements. Its **rank** in this sense is the number of axes, although NumPy documentation commonly uses <code>ndim</code> to avoid conflict with matrix rank.

Because metadata separates logical indexing from physical layout, the same data buffer can support multiple views. Because one dtype governs a region, compiled loops can process elements with fewer dynamic decisions. This is the reason for arrays; shorter syntax is secondary.

### Worked example 16.4 — Shape, dtype, and axis

~~~python
import numpy as np

temperatures = np.array(
    [
        [18.5, 20.0, 19.25],
        [17.75, 21.5, 20.25],
    ],
    dtype=np.float64,
)

print(temperatures.shape)       # (2, 3)
print(temperatures.ndim)        # 2
print(temperatures.dtype)       # commonly float64
print(temperatures[1, 2])       # 20.25
print(temperatures.mean(axis=0))
~~~

The outer two rows may represent days and the three columns sensors. The shape records two days by three sensors. <code>float64</code> requests a binary floating-point format ordinarily occupying 64 bits per element. The subscription <code>[1, 2]</code> selects zero-based day 1 and sensor 2. <code>mean(axis=0)</code> reduces the day axis, producing one mean for each sensor. Reducing an axis means consuming positions along it; the unreduced axes remain.

The program imports a third-party library, so a project must declare and lock an acceptable NumPy version rather than assuming its presence.

### 16.5.1 An ndarray is metadata plus an accessible storage region

An <code>ndarray</code> does not require one unique ownership layout, but its logical indexing is described by a compact set of properties:

- <code>ndim</code>: number of axes;
- <code>shape</code>: length of each axis;
- <code>size</code>: product of shape entries, with the scalar-array convention handled explicitly;
- <code>dtype</code>: interpretation of one logical element;
- <code>itemsize</code>: nominal bytes occupied by one fixed-size element;
- <code>strides</code>: signed byte displacement for advancing one position along each axis;
- <code>data</code>/<code>base</code>/flags: implementation-facing access and ownership/layout information.

For ordinary non-object fixed-width arrays, <code>nbytes = size * itemsize</code> reports raw logical element storage. It excludes the array header, an owning base object, allocator metadata, and separately allocated objects referenced by object dtype.

~~~python
import numpy as np


cube = np.arange(24, dtype=np.int32).reshape(2, 3, 4)

assert cube.ndim == 3
assert cube.shape == (2, 3, 4)
assert cube.size == 24
assert cube.itemsize == 4
assert cube.nbytes == 96
print(cube.strides, cube.flags.c_contiguous)
~~~

The three axes acquire meaning only from a data contract—perhaps experiment, sensor and time. Shape <code>(2, 3, 4)</code> alone does not declare those labels. Code that silently assumes an axis order can return a correctly shaped but scientifically incorrect result.

A zero-dimensional array has shape <code>()</code> and one element; an empty axis yields size zero. These cases differ:

~~~python
import numpy as np


scalar_array = np.array(7.0)
empty_matrix = np.empty((0, 3), dtype=np.float64)

assert scalar_array.shape == ()
assert scalar_array.ndim == 0
assert scalar_array.size == 1
assert empty_matrix.shape == (0, 3)
assert empty_matrix.size == 0
~~~

A NumPy scalar such as <code>np.float64(7)</code>, a zero-dimensional ndarray, and a Python <code>float</code> are different object categories even when numeric comparison succeeds. Interfaces should state whether scalar arrays are accepted and whether outputs preserve NumPy scalar dtypes.

> **Common misconception 16.13 — “The shape tuple completely defines what an array means.”**  
> Shape defines axis lengths. Axis semantics, units, coordinate labels, missingness and provenance belong to an external contract and can be wrong despite valid dimensions.

### 16.5.2 Array creation chooses conversion and ownership policies

<code>np.array</code> constructs an array and ordinarily copies input data unless documented options permit otherwise; <code>np.asarray</code> converts to an ndarray while avoiding a copy when dtype/order and input representation already suffice. NumPy 2.x makes copy policies increasingly explicit. A caller requiring independence should request or perform an explicit copy and test the contract.

~~~python
import numpy as np


original = np.arange(6, dtype=np.int64)
same_when_possible = np.asarray(original)
independent = np.array(original, copy=True)

assert same_when_possible is original
assert not np.shares_memory(original, independent)

independent[0] = 99
assert original[0] == 0
~~~

Conversion from nested Python sequences requires a rectangular compatible shape for an ordinary multidimensional numeric array. Ragged nesting is not silently padded; represent variable-length collections explicitly as separate arrays, an object array chosen consciously, or a tabular/list-column model.

~~~python
import numpy as np


rows = [[1, 2], [3, 4]]
matrix = np.asarray(rows, dtype=np.int64)
assert matrix.shape == (2, 2)

try:
    np.asarray([[1, 2], [3]], dtype=np.int64)
except ValueError:
    ragged_rejected = True
else:
    ragged_rejected = False

assert ragged_rejected
~~~

Functions such as <code>zeros</code>, <code>ones</code>, <code>full</code> and <code>empty</code> allocate by shape/dtype. <code>empty</code> means “do not initialise element bytes to a promised value”; reading before fully assigning is a correctness and possibly confidentiality defect. It is safe only when every element is overwritten before observation.

> **Common misconception 16.14 — “np.empty creates an array containing zeros or harmless blank values.”**  
> It allocates without value initialisation guarantees. Prior memory contents can appear as arbitrary representable values until every element is written.

### 16.5.3 Homogeneity enables regular kernels but does not eliminate abstraction

A fixed-width dtype lets one loop calculate element addresses and invoke one family of operations without dereferencing an arbitrary Python object for each element. This improves locality and amortises interpreter dispatch. The ndarray still performs checks, manages ownership, selects loops, handles broadcasting, allocates outputs and reports floating exceptions according to configuration.

Object-dtype arrays store Python object references:

~~~python
import numpy as np


objects = np.array([1, "two", [3]], dtype=object)
assert objects.dtype == np.dtype(object)
assert isinstance(objects[2], list)

alias = objects.copy()
alias[2].append(4)
assert objects[2] == [3, 4]
~~~

The array copy duplicates the reference buffer, not the referenced list. Arithmetic over object dtype invokes Python protocols element by element and can raise arbitrary exceptions. It can be useful for integration, but it is rarely a substitute for a well-chosen numerical or string representation.

NumPy’s array protocols and the Array API standard permit other libraries/devices to expose array-like behaviour. Code requiring NumPy-specific strides, views or functions should say so; code written to an array standard can be more portable but must remain within that smaller contract.

> **Common misconception 16.15 — “Any ndarray operation is automatically a fast native numerical operation.”**  
> Object dtype, callbacks, conversions, non-contiguous layout, unsupported kernels and small inputs can retain Python overhead or require copies. Representation and operation determine the path.

The dtype is the pivotal representation decision. It constrains range, precision, promotion, casting, missing-value strategy and interoperability.
