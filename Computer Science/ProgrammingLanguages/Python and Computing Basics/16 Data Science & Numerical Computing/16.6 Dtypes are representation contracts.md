# 16.6 Dtypes are representation contracts

A NumPy **dtype** is an object describing how fixed-size memory regions are interpreted: kind, size, byte order, and possibly fields or subarrays. Typical kinds include signed and unsigned integers, binary floating-point values, complex values, Boolean values, fixed-width byte or Unicode strings, date/time units, and references to arbitrary Python objects.

An integer dtype such as signed 8-bit integer has a finite range, conventionally \(-128\) through \(127\). Arithmetic can overflow according to array rules rather than expanding into an arbitrary-precision Python integer. A floating dtype approximates real numbers with finite binary significand and exponent fields. Many decimal fractions, including 0.1, have no finite binary expansion and are rounded to a nearby representable value. Chapter 5’s warning about floating-point equality therefore applies more strongly to bulk computation, where rounding accumulates through an algorithm’s operation order.

An **object dtype** stores references to Python objects. It restores heterogeneity but forfeits many benefits of compact native representation and compiled homogeneous arithmetic. It is not a neutral “accept anything” setting for numerical data.

### Worked example 16.5 — Representation range is part of the contract

~~~python
import numpy as np

values = np.array([126, 127], dtype=np.int8)
print(values.dtype)
print(np.iinfo(values.dtype).min, np.iinfo(values.dtype).max)
~~~

The query establishes the supported range rather than discovering it after a failure. Adding one to the second element asks for a mathematical value outside that range. NumPy’s result depends on documented operation, casting, overflow, and promotion rules for the installed version. The academically correct practice is not to memorise one observed wraparound result as universal. Select a dtype whose range covers legitimate values, test boundary cases, and state overflow policy.

For financial quantities denominated in decimal currency, binary floating point may be inappropriate where exact minor-unit arithmetic is required. Integer minor units or <code>decimal.Decimal</code> under an explicit rounding context can better encode the contract. NumPy’s fast native numeric model and Python’s decimal model solve different problems.

### 16.6.1 Integer arithmetic is finite-width under array dtypes

A signed (b)-bit two’s-complement integer represents values from (-2^{b-1}) through (2^{b-1}-1); an unsigned (b)-bit integer represents 0 through (2^b-1). NumPy exposes actual limits with <code>np.iinfo</code>. Operations remain governed by NumPy’s dtype-resolution and overflow rules, not Python’s arbitrary-precision integer semantics.

~~~python
import numpy as np


dtype = np.dtype(np.int16)
limits = np.iinfo(dtype)
values = np.array([limits.min, 0, limits.max], dtype=dtype)

assert limits.min == -(2**15)
assert limits.max == 2**15 - 1
assert values.dtype == dtype
~~~

Overflow in integer scalar/array operations can wrap under fixed-width arithmetic, and conversions can warn or fail depending on the API and version. Do not use overflow as an accidental modulus. If modular arithmetic is intended, state the modulus and use an unsigned dtype or explicit operation whose contract matches it. If overflow is invalid, widen before computing and validate input bounds.

~~~python
import numpy as np


small = np.array([30_000, 30_000], dtype=np.int16)
widened = small.astype(np.int64)
total = widened.sum()

assert total == 60_000
assert total.dtype == np.dtype(np.int64)
~~~

Reductions sometimes choose a wider accumulator by default—for example, small platform integers may sum in a native-width integer—but this is operation- and dtype-specific. An explicit <code>dtype</code> on the reduction documents the required accumulator range.

> **Common misconception 16.16 — “NumPy integers behave like Python int objects with unlimited precision.”**  
> Array integer dtypes have finite ranges and operation-specific promotion/accumulation. Overflow policy must be designed and boundary-tested.

### 16.6.2 Promotion decides a common computation dtype

When operands have different dtypes, NumPy resolves a loop and result dtype according to **promotion** rules. NumPy 2.0 adopted the NEP 50 model in which a Python scalar’s value ordinarily does not change promotion merely because it happens to fit a narrower dtype; scalar kind and array precision govern the result more predictably.

Inspect rather than guess:

~~~python
import numpy as np


pairs = [
    (np.dtype("int16"), np.dtype("int64")),
    (np.dtype("int32"), np.dtype("float32")),
    (np.dtype("float32"), np.dtype("complex64")),
]

for left, right in pairs:
    print(left, right, "->", np.result_type(left, right))

values = np.array([1, 2], dtype=np.float32)
result = values + 3.0
assert result.dtype == np.dtype(np.float32)
~~~

The last assertion reflects NumPy 2.x weak Python-scalar promotion. Older versions or different array standards can behave differently. Values outside the chosen dtype’s representable range can raise rather than silently force a wider array.

<code>np.can_cast</code> classifies casting under policies such as <code>safe</code>, <code>same_kind</code>, <code>unsafe</code> and stricter equivalence/no-cast modes:

~~~python
import numpy as np


assert np.can_cast(np.int16, np.int64, casting="safe")
assert not np.can_cast(np.float64, np.int32, casting="safe")
assert np.can_cast(np.float64, np.int32, casting="unsafe")
~~~

“Safe” means every value representable in the source dtype can be represented by the destination under NumPy’s casting taxonomy; it does not prove a scientifically valid unit conversion or exact preservation of a computed real quantity.

> **Common misconception 16.17 — “Mixed-dtype arithmetic always chooses the widest-looking operand.”**  
> Promotion follows a versioned type-resolution system involving kinds, precision and scalar rules. Use <code>result_type</code>, documented ufunc resolution and tests.

### 16.6.3 Floating point represents a finite lattice with exceptional values

IEEE 754 binary floating formats encode sign, exponent and significand with special representations for positive/negative infinity and **NaN** (“not a number”). The representable values are unevenly spaced: precision is relative to magnitude. <code>np.finfo</code> reports format properties.

~~~python
import numpy as np


info = np.finfo(np.float64)
print(info.eps, info.tiny, info.max)

one = np.float64(1.0)
next_after_one = np.nextafter(one, np.float64(2.0))
assert next_after_one - one == info.eps
~~~

<code>eps</code> is the distance from 1 to the next larger representable value for the format, not a universal comparison tolerance. At magnitude (10^{12}), adjacent spacing is much larger; near zero, subnormal behaviour matters. Tolerances should combine an absolute component for values near zero with a relative component for scale, justified by error analysis.

NaN comparisons follow IEEE-style unordered semantics: NaN is not equal to itself. Use <code>np.isnan</code>. Infinity is a numeric extended value, not missingness; use <code>np.isfinite</code> when an algorithm requires finite data.

~~~python
import numpy as np


values = np.array([1.0, np.nan, np.inf, -np.inf])
assert np.isnan(values).tolist() == [False, True, False, False]
assert np.isfinite(values).tolist() == [True, False, False, False]
~~~

Floating operations can emit warnings and produce NaN/infinity rather than raise Python exceptions. <code>np.errstate</code> establishes a lexical policy:

~~~python
import numpy as np


values = np.array([1.0, 0.0, -1.0])
with np.errstate(divide="raise", invalid="raise"):
    try:
        np.log(values)
    except FloatingPointError:
        invalid_input_detected = True
    else:
        invalid_input_detected = False

assert invalid_input_detected
~~~

The operation may have written part of an output before raising; do not assume transactional rollback. Global error settings should not be mutated without restoration.

> **Common misconception 16.18 — “Machine epsilon is the correct tolerance for every floating comparison.”**  
> Error depends on magnitude, operation count, conditioning and algorithm. Epsilon describes spacing near one for a format; tolerance is a problem-specific error budget.

### 16.6.4 Byte order, time units, structured and object dtypes widen the contract

A dtype can specify byte order. Data exchanged between machines/files can require byteswapping; native-endian interpretation of foreign bytes corrupts values while preserving plausible shapes. Use format metadata and explicit dtype strings, not platform guesswork.

Date/time dtypes store integer counts in a declared unit relative to an epoch under NumPy’s model. Months and years are not fixed-length durations and require special conversion policies. Time zones are not stored in ordinary <code>datetime64</code>; pandas or domain structures supply zone-aware semantics.

A **structured dtype** divides each item into named fields at specified offsets and types. It can map binary records efficiently but is not a full relational table: fields share one record buffer, nested/variable data are limited, and alignment must match the external binary specification.

~~~python
import numpy as np


packet_dtype = np.dtype(
    [("sensor", "<u2"), ("status", "u1"), ("reading", "<f4")]
)
packets = np.zeros(3, dtype=packet_dtype)
packets["sensor"] = [1, 2, 3]
packets["reading"] = [1.5, 2.5, 3.5]

assert packets.dtype.names == ("sensor", "status", "reading")
assert packets["reading"].shape == (3,)
~~~

The explicit little-endian fields describe byte interpretation, but actual network/file records may include alignment, padding, checksums and version tags. Validate <code>itemsize</code> and offsets against the format specification.

Physical traversal follows shape and strides rather than dtype alone.
