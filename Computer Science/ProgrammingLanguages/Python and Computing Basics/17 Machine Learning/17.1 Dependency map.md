### 17.1.1 The branch-local mathematical bridge

An **array** is a finite multidimensional collection of values described by a shape and element representation. In supervised tabular learning, a two-dimensional array commonly places cases along axis 0 and represented input features along axis 1. A table may additionally have labels and heterogeneous columns; conversion from a table to a numerical array is a semantic boundary because labels, missing-value conventions, and per-column dtypes can be lost.

A **population** is the collection about which a question is asked. A **sample** is the realised collection used for fitting or evaluation. A **random variable** assigns a possible value to each outcome in a probability model. An **expectation** is a probability-weighted average under that model. These terms do not claim that a dataset was randomly sampled: they state the objects needed to make uncertainty claims. If observation was selective, evaluation inherits that selection unless design or modelling addresses it.

For events (A) and (B) with (P(B)>0), conditional probability is

\[
P(A\mid B)=\frac{P(A\cap B)}{P(B)}.
\]

A probabilistic classifier estimates a conditional quantity such as (P(Y=1\mid X=x)) under a fitted representation and data-generating regime. It does not estimate (P(X=x\mid Y=1)), the probability that the model is correct, or the probability of a causal effect. These are different conditionals or different kinds of claims.

An **estimator** is a rule that maps possible samples to fitted state or an estimate. In machine-learning libraries the same word also names an object implementing a fitting interface. The statistical and software meanings are compatible but not identical: the Python object contains configuration and learned state, while the mathematical estimator is the procedure across hypothetical samples.

> **Common misconception 17.1 — “Machine learning begins where statistics ends.”**  
> Learning algorithms are estimators operating on measured samples. Their predictive, probabilistic, and uncertainty claims remain governed by sampling, measurement, dependence, and distributional assumptions.

### 17.1.2 What is fixed, learned, selected, and evaluated

A machine-learning experiment contains several layers of choice:

| Layer | Examples | Chosen using |
|---|---|---|
| problem | unit, target, horizon, decision | domain purpose and governance |
| representation | features, encodings, missingness | training data and prior design, within evaluation boundaries |
| model class | linear map, tree ensemble, neural network | development evidence and constraints |
| parameters | coefficients, split thresholds, weights | fitting algorithm on training data |
| hyperparameters | penalty, depth, architecture, learning rate | validation procedure |
| decision policy | threshold, ranking capacity, abstention | consequences, capacity, validation evidence |
| final assessment | declared metrics and slices | untouched test or prospective data |

Moving information upward from final assessment into earlier choices contaminates the meaning of the reported result. Even an apparently innocent decision—choosing which subgroup plot looks most interesting after inspecting the test set—uses test information. A rigorous record therefore tracks not only fitted parameters but the complete adaptive path that selected the reported system.

The branch uses scikit-learn to expose estimator composition and PyTorch terminology to explain contemporary differentiable models. Library names are examples of interfaces, not definitions of machine learning. Stable concepts are separated from versioned behaviour; production work records exact releases and consults their official documentation.

> **Common misconception 17.2 — “The model is the only learned part of a machine-learning system.”**  
> Feature definitions, preprocessing statistics, hyperparameters, thresholds, stopping rules, and even the chosen metric can be selected from data. Evaluation must encompass the whole adaptive procedure.

### 17.1.3 The epistemic contract of a learning study

An **epistemic contract** states what evidence would justify a claim and what remains unknown. Machine-learning reports often collapse several propositions:

1. the implementation optimises its stated objective;
2. the fitted system performs on held-out cases from a specified sampling regime;
3. the system will perform in a deployment environment;
4. the resulting decisions improve an outcome;
5. the use is ethically and legally justified.

Each proposition needs additional evidence. Unit tests and optimisation traces support the first. A non-leaking evaluation supports the second. Temporal, geographic, institutional, or prospective validation strengthens the third. Randomised or causally identified evidence may be required for the fourth. The fifth requires normative governance that cannot be derived from predictive accuracy.

The central objects of this chapter can be arranged as

\[
\text{raw event}
\xrightarrow{\text{measurement}}
\text{record}
\xrightarrow{\text{representation}}
x
\xrightarrow{\text{fitted model}}
s
\xrightarrow{\text{decision policy}}
a
\xrightarrow{\text{environment}}
y.
\]

Here \(x\) is a feature representation, \(s\) a score or prediction, \(a\) an action, and \(y\) a later outcome. Every arrow can fail independently. Measurement can encode bias; representation can discard information; a model can misgeneralise; a threshold can misuse a calibrated score; an action can alter the outcome; delayed outcome collection can be selective.

This decomposition also identifies ownership. Data producers own source meaning and quality; model developers own fitting and evaluation; service engineers own availability and versioned execution; decision owners own policy and consequence; governance functions own permitted use, appeal, and retirement. Shared ownership does not mean diffuse accountability.

A rigorous study records at least four kinds of uncertainty:

- **aleatoric uncertainty**, variation treated as inherent in outcomes under the model;
- **epistemic uncertainty**, uncertainty due to limited knowledge, samples, or model specification;
- **distributional uncertainty**, doubt about whether future conditions match evaluated conditions;
- **normative uncertainty**, disagreement about values, harms, rights, and acceptable trade-offs.

These categories overlap in practice and cannot always be cleanly estimated. Calling one model output “the uncertainty” without naming the category is inadequate. Predictive entropy, ensemble spread, a confidence interval, and stakeholder disagreement are not interchangeable quantities.

Examples throughout use synthetic or library datasets so that mechanisms are reproducible and no external download is silently required. Synthetic evidence demonstrates computation, not domain validity. A real study must replace convenient generated data with governed provenance, measurement analysis, and population-specific validation.

The chapter’s order follows the dependency of a defensible system: formulate the task; represent and partition data; choose loss and evaluation; fit classical models; derive gradient computation; construct neural models; select without contaminating assessment; then confront shift, fairness, explanation, security, production, and reproducibility. Later machinery never cancels earlier obligations.
