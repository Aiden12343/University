# 17.26 A complete training loop

~~~python
import torch
from torch import nn
from torch.utils.data import DataLoader, TensorDataset

torch.manual_seed(42)

features = torch.randn(1_000, 10)
targets = (
    features[:, :1] * 2.0
    - features[:, 1:2] * 0.5
    + 0.1 * torch.randn(1_000, 1)
)

dataset = TensorDataset(features, targets)
loader = DataLoader(
    dataset,
    batch_size=64,
    shuffle=True,
)

network = nn.Sequential(
    nn.Linear(10, 32),
    nn.ReLU(),
    nn.Linear(32, 1),
)
optimiser = torch.optim.Adam(network.parameters(), lr=1e-3)

for epoch in range(20):
    network.train()
    total_loss = 0.0

    for batch_features, batch_targets in loader:
        optimiser.zero_grad()
        predictions = network(batch_features)
        loss = nn.functional.mse_loss(
            predictions,
            batch_targets,
        )
        loss.backward()
        optimiser.step()
        total_loss += float(loss.detach()) * len(batch_features)

    mean_loss = total_loss / len(dataset)
    print(epoch, mean_loss)
~~~

Line-by-line state:

1. A seed makes supported random operations repeatable under the documented environment; it does not guarantee identical results across every device and version.
2. Synthetic targets encode a known relation plus noise.
3. The data loader forms shuffled mini-batches.
4. The network constructor creates parameter tensors.
5. Adam retains optimiser state associated with those parameters.
6. <code>network.train()</code> selects training behaviour for modules whose behaviour differs between training and evaluation.
7. <code>zero_grad</code> clears accumulated gradients. Frameworks often accumulate by default because accumulation is useful for some algorithms.
8. The forward call creates predictions and a graph.
9. The loss compares predictions and targets.
10. <code>backward</code> computes parameter gradients.
11. <code>step</code> mutates parameters using gradients and optimiser state.
12. <code>detach</code> obtains a value excluded from gradient history for reporting.

This loop evaluates training loss only. A legitimate experiment adds validation, checkpoints, early-stopping policy, environment recording, and a final held-out assessment.

### 17.26.1 Phase separation and evaluation semantics

A defensible experiment separates at least four roles:

1. the training partition supplies parameter updates;
2. the validation partition selects hyperparameters, epochs, thresholds, and checkpoints;
3. the test partition estimates the fully selected procedure once;
4. deployment data support prospective monitoring and, only under a declared retraining process, later development.

Validation must run without gradient construction and without parameter updates. Modules are placed into evaluation mode so dropout and stateful normalisation use inference behaviour. Evaluation losses are aggregated by the number of represented examples or loss elements, not by naively averaging unequal batch means.

~~~python
from __future__ import annotations

from collections.abc import Iterable
from typing import Any


def evaluate_batches(
    model: Any,
    batches: Iterable[tuple[Any, Any]],
    *,
    torch_module: Any,
) -> float:
    model.eval()
    total_loss = 0.0
    total_items = 0

    with torch_module.no_grad():
        for features, targets in batches:
            predictions = model(features)
            batch_loss = torch_module.nn.functional.mse_loss(
                predictions,
                targets,
                reduction="sum",
            )
            total_loss += float(batch_loss)
            total_items += targets.numel()

    if total_items == 0:
        raise ValueError("evaluation loader is empty")
    return total_loss / total_items
~~~

Passing the framework module explicitly makes this helper importable in an environment without the optional dependency; in actual PyTorch code, ordinary module-level import is clearer. The reduction counts target elements. For per-example structured losses, the desired denominator must be specified rather than copied mechanically.

Metrics that require the whole evaluation set, such as ROC AUC, should accumulate predictions and targets or use a mathematically correct streaming implementation. Averaging per-batch AUC values does not equal dataset AUC and can fail when a batch contains one class.

### 17.26.2 Checkpointing and exact resumption

A checkpoint selected by minimum validation loss stores more than model weights:

- architecture and preprocessing configuration;
- model parameter and buffer state;
- optimiser and scheduler state;
- current epoch and update count;
- random-generator states;
- data-sampler or iterator progress where exact continuation matters;
- mixed-precision scaling state;
- best validation value and stopping-policy state;
- software, hardware, dataset, and code identities.

Writing checkpoints atomically prevents an interruption from replacing a valid artifact with a partial file. Retain a last-known-good checkpoint independently of the newest one. Loading a general Python pickle can execute code, so artifact provenance and restricted formats matter.

**Early stopping** selects an update index. A patience of ten means that training stops after a stated number of qualifying validation checks without sufficient improvement; it does not mean ten epochs universally, because evaluation frequency can differ. The minimum improvement, tie rule, missing-metric policy, and restored checkpoint must be defined.

The same validation trajectory should not be inspected indefinitely while architecture decisions accumulate. Repeated human adaptation overfits the validation set even if no program reads it during backpropagation. Nested evaluation or a fresh confirmation set is needed when the search process itself becomes extensive.

> **Common misconception 17.58 — “Calling evaluation mode turns off gradient calculation.”**  
> Module mode changes behaviours such as dropout and batch normalisation. A separate no-gradient context controls graph recording; both are ordinarily needed for evaluation.

### 17.26.3 Gradient accumulation, clipping, and mixed precision

When a desired effective batch exceeds device memory, several mini-batch losses can be backpropagated before one optimiser step. If each loss is a mean, dividing by the number of accumulation steps usually preserves the gradient scale for equal-sized batches. Unequal final batches, distributed reduction, regularisation, and stateful layers require additional care. The optimiser’s step counter and schedule advance on parameter updates, not necessarily every loader iteration.

**Gradient clipping** limits a gradient norm or individual values. It can prevent a rare unstable update, particularly in recurrent systems, but changes the optimisation rule. Frequent clipping indicates that scale, objective, data, initialisation, or learning rate may need diagnosis. Log the unclipped norm when possible.

Mixed-precision training chooses lower-precision arithmetic for suitable operations while retaining selected state in wider precision. Dynamic loss scaling multiplies a loss before backpropagation to prevent small half-precision gradients underflowing, then unscales before clipping and updating. Non-finite gradients cause a skipped update and adjusted scale. Correct operation order is material.

Training loops should fail loudly on non-finite losses, empty partitions, schema changes, impossible labels, and absent checkpoints. Silently continuing after a NaN can poison optimiser state and make all later values non-finite.

> **Common misconception 17.59 — “A complete training loop is just forward, backward, and step inside an epoch loop.”**  
> Those operations form the update kernel. A complete experiment also specifies data state, validation, mode changes, selection, failure handling, checkpoint state, reproducibility, and final evaluation.
