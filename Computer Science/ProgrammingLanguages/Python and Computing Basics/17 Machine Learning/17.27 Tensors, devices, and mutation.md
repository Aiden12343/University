# 17.27 Tensors, devices, and mutation

A framework **tensor** is a multidimensional array with dtype, shape, strides or layout, device placement, and optional automatic-differentiation metadata. A **device** is an execution and storage location such as CPU or accelerator. Moving a tensor can copy data and synchronise execution.

Accelerators gain throughput from large regular operations and parallelism. Sending many tiny operations across a host/device boundary can be slower than CPU execution. Timings must account for asynchronous execution by synchronising at measurement boundaries according to framework documentation.

In-place mutation can invalidate values needed for gradient computation. Frameworks track versioning or reject some unsafe mutations. Python aliasing remains relevant: two tensor objects or views may share storage, and a detached tensor can still share storage even though it no longer participates in gradient tracking.

Mixed-precision training uses narrower formats for selected operations to increase throughput and reduce memory while retaining wider representations where needed. It can overflow, underflow, or lose accuracy. Loss scaling and hardware-specific kernels manage some risks; numerical verification remains necessary.

### 17.27.1 Shape, dtype, strides, and views

A dense tensor’s logical index is mapped to storage through strides. For a two-dimensional tensor, an element at \((i,j)\) can be located conceptually at

\[
\text{offset}+i\,s_0+j\,s_1,
\]

where \(s_0,s_1\) are strides measured in storage elements. Transposition can create a view with exchanged strides without moving data. A reshape can be a view when layout permits or a copy otherwise. Code should not infer aliasing solely from an operation’s familiar name.

A **contiguous** layout stores elements in the order expected by a designated convention, but libraries can support several memory formats. Kernels may require or run faster on particular layouts and insert copies when necessary. A shape-correct model can therefore suffer unexpected memory traffic.

The dtype controls range, precision, storage, and supported operations. Integer tensors do not ordinarily carry gradients because infinitesimal variation of discrete values is undefined. Float16, bfloat16, float32, and float64 have different exponent and significand ranges; bfloat16 retains a float32-like exponent range with less precision, while IEEE float16 has more significand bits but a narrower exponent range.

Broadcasting aligns dimensions under library rules. It avoids material copies in many operations but can accidentally expand a comparison from \((n,1)\) and \((n,)\) to \((n,n)\). Assert semantic shapes at boundaries.

> **Common misconception 17.60 — “A tensor reshape always rearranges or copies its numbers.”**  
> It may return a view over the same storage, return a copy, or reject the operation depending on layout and API. Shape describes logical indexing, not ownership.

### 17.27.2 Device execution and truthful measurement

A host program enqueues accelerator kernels and may continue before they finish. A wall-clock timer around enqueue operations measures dispatch rather than completed computation unless the framework synchronises. Data transfers can likewise be asynchronous when memory and API conditions permit.

Benchmarking requires:

- warm-up to trigger compilation, allocation, and cache population;
- synchronisation immediately outside the measured region;
- repeated measurements and distribution summaries;
- fixed shapes, dtype, modes, and grad settings;
- disclosure of hardware, library, driver, and algorithm settings;
- separation of transfer, input pipeline, forward, backward, and update time.

Peak throughput requires sufficient parallel work. A tiny batch can be latency-bound; a large batch can exhaust memory or alter statistical behaviour. Faster examples per second do not necessarily mean less time to a selected validation quality.

Device transfer also establishes ownership and lifetime concerns. A non-blocking transfer does not permit unsafe mutation or release of source memory. Distributed training adds collective communication; one failed or slow worker can stall peers, and floating reductions can depend on topology and order.

### 17.27.3 Numerical equivalence is tolerance-relative

Floating addition is not associative:

\[
(a+b)+c
\]

can round differently from

\[
a+(b+c).
\]

Parallel kernels change reduction order, and hardware may fuse multiply-add operations or select algorithms with different accuracy. Results can be mathematically equivalent without bitwise identity.

Tolerance-based comparison combines an absolute tolerance near zero and relative tolerance at larger scale. A tolerance must follow application consequences, not merely make a test pass. Gradient-scale and probability-tail errors can matter even when aggregate loss changes little.

NaN and infinity checks should cover inputs, activations where practical, loss, gradients, parameters, and optimiser state during diagnosis. Clipping an infinite value after it has entered an exponential average may be too late. Anomaly-detection modes are expensive but can locate the operation that first produced an invalid gradient.

> **Common misconception 17.61 — “Moving the same model to an accelerator should produce identical numbers, only faster.”**  
> Dtypes, kernels, reduction order, fused operations, and determinism guarantees can differ. Accuracy and performance must both be measured under the actual environment.
