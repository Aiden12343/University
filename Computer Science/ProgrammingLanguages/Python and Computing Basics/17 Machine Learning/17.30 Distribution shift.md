# 17.30 Distribution shift

Training and deployment data need not share a distribution. **Covariate shift** changes the input distribution. **Label shift** changes target prevalence under specified conditional stability. **Concept drift** changes the relation between inputs and target. Terminology varies, so a report should describe the concrete change rather than rely on labels alone.

Sources include changing user behaviour, policy, sensors, economic conditions, feedback from the model’s own decisions, and upstream software revisions. Random cross-validation within historical data can miss all of them.

Monitoring input statistics can detect some changes but cannot determine target performance before delayed labels arrive. A stable marginal feature distribution can conceal changed conditional relationships, and a changed distribution need not reduce performance. Monitoring therefore combines data quality, drift indicators, delayed outcomes, calibration, slice metrics, service health, and human reports.

### 17.30.1 Factorising shift

The joint distribution can be factorised as

\[
p(x,y)=p(y\mid x)p(x)
\]

or

\[
p(x,y)=p(x\mid y)p(y).
\]

**Covariate shift** commonly denotes a change in \(p(x)\) while \(p(y\mid x)\) remains stable. Under support overlap and correct density ratios, importance weighting can reweight source risk toward a target input distribution:

\[
R_{\text{target}}(f)
=
\mathbb{E}_{\text{source}}
\left[
\frac{p_{\text{target}}(X)}
{p_{\text{source}}(X)}
\ell(f(X),Y)
\right].
\]

Large ratios create high variance, and absent source support makes target behaviour unidentifiable from source labels.

**Label shift** conventionally assumes \(p(x\mid y)\) is stable while \(p(y)\) changes. **Concept drift** is used for changes in the predictive relation, often \(p(y\mid x)\). Real changes need not fit one pure category. A new sensor can alter representation and error at once; a policy can alter who receives a label; a model can alter behaviour and therefore future data.

**Domain generalisation** attempts to learn across observed environments so performance extends to another, whereas **domain adaptation** uses some information from the target environment. Both require assumptions connecting environments. No algorithm can infer arbitrary unseen changes.

> **Common misconception 17.66 — “A statistically significant feature-distribution change proves that the model must be retrained.”**  
> Drift tests detect a chosen distributional difference, often with sample-size-dependent sensitivity. They do not by themselves measure performance harm or establish that retraining on available labels will help.

### 17.30.2 Monitoring, delayed labels, and feedback

Monitoring begins with service invariants: schema versions, missingness, category cardinality, numeric ranges, latency, error rates, and prediction volume. Statistical monitors can then compare feature, score, and embedding distributions. Univariate tests miss changed dependence; multivariate tests can be difficult to diagnose and scale.

When outcomes arrive later, join them to historical predictions using stable event identifiers and the feature/model version used at decision time. Reconstructing predictions with current features creates hindsight leakage. Some outcomes never become observable because an action prevented or censored them. This is a missing-data and causal problem, not merely an engineering delay.

A model creates **feedback** when its output affects future inputs or labels. Recommending popular items increases their exposure; denying credit hides repayment outcomes for rejected applicants; predictive policing changes recorded incidents through patrol allocation. Training on resulting observations can amplify a policy while conventional test metrics appear stable.

A retraining trigger needs:

- a condition, persistence window, and uncertainty rule;
- label-availability and data-quality requirements;
- a candidate-training and validation protocol;
- comparison against the incumbent on current and protected historical slices;
- approval, staged rollout, rollback, and audit retention;
- a rule for emergencies when outcomes are unavailable.

Automatically retraining whenever a divergence threshold fires can turn noise or an upstream defect into a new model. Sometimes the correct response is to repair the data source, adjust policy, or suspend automation.

> **Common misconception 17.67 — “Periodic retraining makes a model current.”**  
> Retraining can reproduce stale labels, absorb feedback bias, or degrade protected cases. Currency requires valid recent evidence, controlled comparison, and a deployment decision—not a calendar alone.

### 17.30.3 Out-of-distribution detection and robustness

An input is **out of distribution** only relative to a reference distribution and purpose. A rare but valid case, corrupt record, new population, adversarial input, and ordinary tail event require different responses. No scalar detector can identify every departure that matters.

Predictive confidence is not an out-of-distribution certificate. Softmax can assign extreme confidence far from training support because logits extrapolate. Ensembles, density estimates, distance in a learned representation, conformal scores, and specialised detectors expose different signals, each with blind spots. A detector selected on known anomalies can overfit that anomaly taxonomy.

**Robustness** must name a perturbation set or environmental range. Adversarial robustness studies worst-case changes within a defined norm or transformation set:

\[
\max_{\delta\in\Delta}\ell(f(x+\delta),y).
\]

An \(L_p\) ball is mathematically convenient but may not represent semantically plausible change. Conversely, spelling variation, sensor replacement, code revision, strategic user adaptation, and physical attacks may lie outside small numeric norms.

Stress testing constructs plausible challenging slices and transformations before deployment. It should cover:

- corrupted, missing, extreme, and boundary inputs;
- subgroup and intersectional cases;
- temporal and institutional shifts;
- plausible manipulation by an informed user;
- dependency, feature-service, and partial-data failures;
- batch-size, latency, and resource extremes.

Robust optimisation and augmentation can trade ordinary accuracy for performance under the modelled perturbations. The trade-off is a policy decision informed by incident severity. A benchmark attack success rate does not establish security against an adaptive adversary with another objective.

When a detector signals uncertainty, the system needs a response: abstain, request more information, route to expert review, use a conservative fallback, or halt. If all cases must receive an action, an “uncertainty score” without decision integration is merely telemetry.
