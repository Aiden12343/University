# 17.33 From experiment to production system

A model artifact is only one component:

1. input collection and schema enforcement;
2. feature computation with training-serving consistency;
3. model version and runtime;
4. decision threshold and business rules;
5. output delivery;
6. logging and privacy controls;
7. monitoring and rollback;
8. human workflow and exception handling.

**Training-serving skew** occurs when production features differ from training features because code, timing, defaults, or data sources diverge. Reusing a versioned transformation pipeline reduces but does not eliminate this risk.

Serialised model files can execute code or depend tightly on library versions. Treat untrusted model artifacts as untrusted software. Record training code, dependency versions, schema, dataset identity, metrics, and cryptographic digest. Load only approved artifacts in restricted environments.

### Worked example 17.9 — A prediction boundary

~~~python
from dataclasses import dataclass
from typing import Any

import pandas as pd


@dataclass(frozen=True)
class Prediction:
    probability: float
    model_version: str


def predict_one(
    raw: dict[str, Any],
    *,
    pipeline: Any,
    model_version: str,
) -> Prediction:
    required = {"age", "monthly_usage", "plan"}
    missing = required.difference(raw)
    if missing:
        raise ValueError(f"missing fields: {sorted(missing)}")

    row = pd.DataFrame([raw])
    probability = float(pipeline.predict_proba(row)[0, 1])

    if not 0.0 <= probability <= 1.0:
        raise RuntimeError("model returned an invalid probability")

    return Prediction(
        probability=probability,
        model_version=model_version,
    )
~~~

The function validates field presence, constructs the expected tabular boundary, extracts one probability, checks its numeric range, and attaches model identity. A complete service must also validate types, ranges, unexpected fields, missing values, resource limits, logging policy, latency, concurrency, and failures. The function returns a probability rather than embedding an institutional action; threshold policy can therefore be versioned separately.

### 17.33.1 Contracts, registries, and lineage

A production input contract specifies field name, type, units, valid ranges, missingness, category vocabulary, time semantics, and version. A JSON schema can validate representation but not every semantic condition: a timestamp can be syntactically valid yet lie after the decision time. Feature pipelines need point-in-time-correct joins so historical training uses only values that would have been known then.

A **feature store** is an infrastructure pattern for defining, computing, and serving reusable features with lineage and training-serving consistency. It does not automatically prevent leakage; point-in-time retrieval, source quality, ownership, and transformation versions remain necessary.

A **model registry** records candidate artifacts, versions, approvals, evaluation evidence, lineage, and lifecycle stage. An artifact digest proves byte identity, not quality or safety. The registry should bind:

- source revision and build recipe;
- immutable training-data or snapshot identifiers;
- dependency and runtime environment;
- preprocessing and model artifact;
- schema and output semantics;
- validation reports and known limitations;
- owner, approval, expiry, and rollback predecessor.

Serialization formats make different security and portability trade-offs. Pickle-family formats can invoke arbitrary constructors and must never be loaded from untrusted provenance. Safer graph or tensor formats restrict executable behaviour but can still exhaust resources or exploit vulnerable runtimes. Signatures, digests, access control, isolation, dependency scanning, and size limits form a layered defence.

### 17.33.2 Serving patterns and staged release

**Online serving** produces a response per request under a latency budget. **Batch inference** scores a bounded dataset on a schedule. **Streaming inference** reacts to an event flow. The same model can have different correctness conditions in each: late events, duplicates, retries, ordering, and partial failure must be addressed.

A release can progress through:

1. offline replay against recorded eligible inputs;
2. **shadow deployment**, where the candidate receives live inputs but does not control action;
3. a **canary**, where a small eligible fraction receives candidate decisions;
4. controlled expansion with guardrails;
5. full release while retaining rollback.

Shadow outputs can be compared with the incumbent and eventual labels, but shadow execution may omit downstream feedback and load effects. Canary assignment should support causal comparison and protect high-risk groups; naive routing by geography or customer tier can confound results.

Rollback includes model, preprocessing, schema, threshold, dependencies, and state. Rolling weights back while retaining an incompatible feature version is not rollback. Exercise the procedure before an incident and define who can invoke it.

### 17.33.3 Observability and incident response

Technical service measures include request volume, latency quantiles, saturation, error codes, timeouts, and resource use. Model measures include schema failures, missingness, score distribution, abstention, decision rate, calibration, error metrics when labels mature, and slice-specific harms. Business outcomes are not substitutes for model metrics because policy and demand can move them independently.

Logs should identify request, model, feature version, decision-policy version, and event time without collecting unnecessary personal or secret data. Sampling policies must retain rare critical events. Access, encryption, retention, erasure, and purpose limitations belong in the design.

An incident runbook defines detection, severity, containment, rollback or shutdown, stakeholder communication, evidence preservation, correction, and post-incident learning. A kill switch must bypass the same failing dependency it is intended to disable. High-stakes systems need a safe manual or degraded mode.

> **Common misconception 17.71 — “Deploying a model means exposing its prediction function through an API.”**  
> Deployment is a versioned socio-technical control loop comprising contracts, features, policy, security, serving, observation, human operations, and reversible change.

### 17.33.4 Security and privacy are model properties and system properties

A machine-learning threat model identifies assets, adversaries, access, capabilities, and acceptable residual risk. Distinct attacks include:

- **poisoning**, which changes training data or labels to alter the learned model;
- **backdoors**, which make a trigger induce attacker-chosen behaviour while ordinary evaluation appears normal;
- **evasion**, which modifies an input at prediction time to avoid or induce a decision;
- **model extraction**, which uses queries or artifact access to approximate parameters or behaviour;
- **membership inference**, which attempts to determine whether a record participated in training;
- **model inversion**, which infers sensitive attributes or representative training information;
- **availability attacks**, which exhaust expensive preprocessing, batching, memory, or downstream review capacity.

Input validation blocks malformed representations, not semantic attacks. Rate limits and authentication constrain query access but do not eliminate extraction. Robust training defends against a specified attack model, not every manipulation. Security evaluation should use an independent adversarial perspective and be repeated when interfaces, data, or model versions change.

Training-data provenance requires signed or access-controlled sources, append and correction logs, anomaly checks, reviewer separation, and the ability to trace a model back to accepted records. Public or user-generated data are untrusted input even when collected at scale. A poisoned pre-trained model or dependency can bypass local data controls.

Privacy is not equivalent to removing names. High-dimensional features can re-identify people; predictions can disclose sensitive inferences; logs can recreate an input history. Data minimisation reduces both exposure and spurious modelling opportunities. Define purpose, lawful basis, retention, access, deletion, and subject rights before collection.

**Differential privacy** supplies a formal bound on how much an output distribution can change when one protected unit’s data are added or removed. A randomised mechanism \(M\) is \((\varepsilon,\delta)\)-differentially private when, for adjacent datasets \(D,D'\) and every measurable output set \(S\),

\[
P(M(D)\in S)
\leq
e^\varepsilon P(M(D')\in S)+\delta.
\]

The adjacency unit—row, person, household, or event—determines the protection. Smaller \(\varepsilon\) is stronger under a fixed definition, but privacy loss composes across repeated analyses. Clipping and noise in differentially private gradient methods trade utility against a quantified budget. Differential privacy does not prevent biased modelling, authorised misuse, or disclosure already present in model inputs.

Federated learning keeps some raw data on participating devices or sites while aggregating updates, but updates can leak information and the coordinator can be malicious. Secure aggregation, differential privacy, device trust, poisoning defences, and participation analysis remain necessary. “Data never leaves the device” is not a complete privacy proof.

Secrets, credentials, internal URLs, and personal data must not be embedded in features, prompts, model artifacts, exception traces, or experiment trackers. Redaction after logging is weaker than not collecting. Incident response must treat a compromised artifact as a software and data breach, rotate affected credentials, assess exposed training information, and preserve forensic lineage.
