# 17.34 Reproducibility beyond a seed

Sources of variation include:

- data order and split;
- parameter initialisation;
- stochastic augmentation;
- multi-thread reduction order;
- accelerator kernels;
- library and driver versions;
- hardware;
- non-deterministic algorithms;
- distributed scheduling.

A seed controls only operations connected to its generator. Frameworks may expose deterministic modes with performance costs and incomplete coverage. Exact bitwise reproduction is stronger than statistical reproducibility; a scientific conclusion can be robust without identical low bits, while identical bits can reproduce a flawed experiment.

Record seeds, configurations, commits, dependency lock, hardware, dataset digest, and commands. Repeat across several seeds when optimisation variability matters, and report the distribution rather than selecting the best run.

### 17.34.1 Levels of reproducibility

Several distinct goals are often collapsed:

- **repeatability**: the same team reruns the same artifacts and environment;
- **computational reproducibility**: another party obtains materially consistent results from supplied code, data, and environment;
- **replicability**: an independent implementation or study supports the substantive result;
- **robustness**: the conclusion survives reasonable changes in assumptions, samples, and implementation.

Terminology varies across disciplines, so define the intended level. A container image can preserve software while leaving remote data mutable. A random seed can reproduce a split while an unpinned upstream query changes rows. A fully preserved run can faithfully repeat leakage.

Randomness has several sources: Python’s generator, NumPy generator objects, framework CPU and device generators, data-loader workers, augmentation libraries, and external systems. Prefer explicit generator objects where APIs permit. Record seed derivation for distributed workers so streams are reproducible without being identical.

Deterministic algorithm modes can reject unsupported kernels or select slower alternatives. Cross-version and cross-platform bitwise identity is rarely guaranteed. When exact replay matters—for forensic or regulated contexts—archive the executable environment and representative outputs, and test replay before relying on it.

### 17.34.2 Experiment identity and provenance

An experiment record should make the following relation reconstructable:

\[
\text{code}+\text{configuration}+\text{data}
+\text{environment}+\text{random state}
\longrightarrow
\text{artifacts}+\text{metrics}.
\]

Configuration includes defaults after resolution, not only user overrides. Data identity may require source query, extraction time, schema, row-selection policy, content digest, and immutable snapshot. Secrets should be referenced through managed identities, never copied into manifests.

Metrics need context: split identifiers, denominators, confidence intervals, threshold, aggregation, and code version. Storing a bare scalar such as <code>accuracy=0.91</code> is insufficient. Preserve failed and superseded runs when they influenced selection; deleting them creates survivorship bias.

A **datasheet** or data card documents collection, composition, preprocessing, uses, limitations, maintenance, and governance of a dataset. A **model card** documents intended use, evaluated populations, metrics, limitations, ethics, and maintenance of a model. These are living evidence, not compliance decoration; claims must be linked to executable evaluations and owners.

### 17.34.3 Reproduction as a test

Build the project in a clean environment, acquire data through the documented path, run training, recreate evaluation tables, load the artifact in the serving runtime, and replay representative boundary cases. Automate this process where cost permits. A lockfile that has never been rebuilt is an untested assertion.

Statistical reproduction should state acceptable equivalence: exact bytes, metric tolerance, confidence-interval overlap, rank stability, or decision invariants. Repeating several seeds quantifies algorithmic variability, while resampling or new sites address sampling and environmental variability. Do not use seed repetitions as if they were independent new datasets.

Archive enough information to explain a past decision after current systems and staff have changed. Retention must be reconciled with privacy, licensing, erasure, and security obligations; sometimes reproducibility requires a governed recomputation process rather than indefinite raw-data retention.

> **Common misconception 17.72 — “Setting every random seed makes an experiment reproducible.”**  
> Seeds control specified pseudorandom streams. Data, code, dependencies, hardware, algorithms, concurrency, configuration, and procedural decisions must also be identified, and some environments do not promise bitwise determinism.
