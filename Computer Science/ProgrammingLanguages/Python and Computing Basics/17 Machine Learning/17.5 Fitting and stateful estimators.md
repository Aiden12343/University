# 17.5 Fitting and stateful estimators

In scikit-learn, an **estimator** is an object following a documented interface. A supervised estimator commonly provides <code>fit(X, y)</code> and <code>predict(X)</code>. Fitting mutates estimator state by learning attributes, conventionally named with a trailing underscore.

~~~python
import numpy as np
from sklearn.linear_model import LinearRegression

X = np.array(
    [
        [0.0],
        [1.0],
        [2.0],
        [3.0],
    ]
)
y = np.array([1.0, 3.0, 5.0, 7.0])

model = LinearRegression()
model.fit(X, y)

print(model.coef_)       # approximately [2.]
print(model.intercept_)  # approximately 1.
print(model.predict(np.array([[4.0]])))  # approximately [9.]
~~~

The capital \(X\) is two-dimensional because estimators conventionally accept rows by features even when there is one feature. The target is one-dimensional. Before fitting, the estimator object stores configuration. After fitting, it also stores learned coefficient and intercept attributes. <code>predict</code> applies the fitted mapping.

This example was constructed from the exact relation \(y=2x+1\). Real data include measurement noise, omitted causes, changing regimes, and finite samples. A numerical coefficient is not automatically a causal effect.

### 17.5.1 Configuration, learned state, and cloning

A scikit-learn estimator’s constructor arguments are configuration. Calling <code>fit</code> validates data and creates learned attributes, conventionally ending in an underscore. The convention supports inspection and composition: <code>coef_</code>, <code>classes_</code>, and <code>n_features_in_</code> are fitted state; <code>alpha</code> or <code>max_depth</code> are parameters of the Python estimator configuration, often called hyperparameters in statistical discussion.

<code>get_params</code> recursively exposes constructor configuration for search and cloning. A **clone** creates an unfitted estimator with the same configuration rather than copying learned state.

~~~python
import numpy as np
from sklearn.base import clone
from sklearn.linear_model import Ridge
from sklearn.utils.validation import check_is_fitted

X = np.array([[0.0], [1.0], [2.0], [3.0]])
y = np.array([1.0, 2.8, 5.2, 7.1])

fitted = Ridge(alpha=2.0).fit(X, y)
fresh = clone(fitted)

assert fresh.get_params()["alpha"] == 2.0
check_is_fitted(fitted)
try:
    check_is_fitted(fresh)
except Exception as error:
    print(type(error).__name__)
~~~

Cross-validation relies on this distinction: each fold must receive a fresh estimator so learned state from another fold cannot persist. Copying a fitted pipeline into a fold would contaminate its validation data.

Estimator methods have different purposes. <code>predict</code> returns point or class predictions; <code>predict_proba</code> returns class probabilities where supported; <code>decision_function</code> can return uncalibrated scores; <code>transform</code> returns a representation; <code>fit_transform</code> may have specialised training-set semantics. One must not infer probability merely because values lie between zero and one.

> **Common misconception 17.11 — “An estimator object is just a mathematical function.”**  
> It is a stateful program with configuration, learned arrays, schemas, randomness, version-coupled code, and method-specific contracts. Fitting mutates its state.

### 17.5.2 Random state, repeated fitting, and incremental interfaces

An estimator parameter named <code>random_state</code> may accept an integer, a generator-like object, or <code>None</code>, with semantics documented per estimator. An integer commonly requests reproducible reinitialisation for each independent fit in scikit-learn workflows; sharing a mutable random-state object can couple fits through consumed state. Reproducibility also depends on data order, parallel implementation, native libraries, and version.

<code>warm_start=True</code> asks some estimators to reuse fitted state across subsequent calls to <code>fit</code>. <code>partial_fit</code> asks supported estimators to update incrementally on batches. They solve different problems and impose estimator-specific rules. Repeatedly calling ordinary <code>fit</code> generally replaces fitted state; assuming accumulation can silently discard earlier data.

Incremental learning needs a stream protocol:

- category and feature spaces must remain compatible or have an explicit evolution rule;
- the first classification update may need the complete class set;
- batch order can affect the result;
- preprocessing state must update consistently without using future batches;
- concept drift requires forgetting, weighting, windows, or monitoring rather than indefinite accumulation;
- checkpoints must include optimiser or sufficient-statistic state, not merely final coefficients.

The estimator API provides structural interoperability, not semantic interchangeability. Two objects exposing <code>fit</code> and <code>predict</code> can target different losses, probabilities, class order, missingness, and thread behaviour.

> **Common misconception 17.12 — “Calling fit twice continues training.”**  
> Ordinary fitting commonly starts a new fit and overwrites learned state. Continuation requires a documented incremental or warm-start contract and compatible data semantics.
