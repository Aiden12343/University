# 17.7 Data leakage

**Data leakage** occurs when model development uses information that would be unavailable at the claimed prediction point or that improperly crosses evaluation boundaries. Leakage creates optimistic estimates without necessarily producing any exception.

Forms include:

- **target leakage:** a feature directly or indirectly contains the outcome;
- **train–test contamination:** preprocessing learns from evaluation data;
- **entity leakage:** correlated records for one entity occur in both sets;
- **temporal leakage:** future observations inform past predictions;
- **selection leakage:** inclusion or labelling depends on post-outcome information.

### Worked example 17.4 — Scaling before splitting leaks

Incorrect:

~~~python
from sklearn.datasets import make_classification
from sklearn.model_selection import train_test_split
from sklearn.preprocessing import StandardScaler

X, y = make_classification(
    n_samples=500,
    n_features=10,
    random_state=7,
)
scaled = StandardScaler().fit_transform(X)
X_train, X_test, y_train, y_test = train_test_split(
    scaled,
    y,
    random_state=42,
)
~~~

The scaler’s means and standard deviations were estimated from all rows, including test rows. Although no test target was used, the test feature distribution influenced training representation.

Correct boundary:

~~~python
from sklearn.datasets import make_classification
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import train_test_split

X, y = make_classification(
    n_samples=500,
    n_features=10,
    random_state=7,
)
X_train, X_test, y_train, y_test = train_test_split(
    X,
    y,
    stratify=y,
    random_state=42,
)

pipeline = make_pipeline(
    StandardScaler(),
    LogisticRegression(),
)
pipeline.fit(X_train, y_train)
predictions = pipeline.predict(X_test)
~~~

The pipeline fits the scaler on training data during <code>fit</code> and reuses those learned transformation parameters during <code>predict</code>. The object composes state transitions so the boundary is harder to violate accidentally.

> **Common misconception 17.16 — “Leakage means putting the target column into X.”**  
> That is one obvious form. Leakage includes any illicit information path across time, entities, preprocessing, selection, labelling, feature engineering, or repeated evaluation.

### 17.7.1 Leakage follows information, not column names

A feature can leak without containing the literal target. A discharge code can reveal an outcome assigned after treatment; a record count can reveal how long a case stayed open; a missing-value marker can encode that a clinician ordered a test after seeing deterioration. Conversely, a variable strongly associated with the target is not leakage if it is genuinely and lawfully available at prediction time.

Audit each feature with an **availability contract**:

1. Which source event creates the raw value?
2. At what timestamp can the prediction service first observe it?
3. Can later corrections overwrite the historical value?
4. Does its presence, absence, or update frequency reveal a later action?
5. Was any statistic used to construct it learned from validation or test cases?

Feature stores require point-in-time joins. Selecting the latest current record for a historical event can attach a future revision. A backfill job can make offline features more complete than production features were. Reproducing values “as known then” requires versioned event and availability time.

Selection leakage arises before feature construction. If the dataset includes only people who received a diagnostic test, the model is conditioned on the historical decision to test. It may not generalise to all people being considered for testing, and the label may be unavailable for those not tested.

> **Common misconception 17.17 — “Unsupervised preprocessing cannot leak because it never sees y.”**  
> Scaling, imputation, vocabulary construction, PCA, outlier removal, and feature filtering learn the evaluation input distribution. That information can make evaluation optimistically unrepresentative even without labels.

### 17.7.2 Target-dependent encodings require cross-fitting

A target encoding replaces a category with a statistic of training targets in that category. If each training row’s own target contributes to its encoded feature, rare categories can nearly reveal their labels. A safe training representation uses out-of-fold encodings: fit the encoding on other folds and transform the held-out fold. After validation design is fixed, a final encoder may fit all development data for deployment.

Feature selection also leaks when it searches correlations with the target before cross-validation. The entire selection operation belongs inside each training fold. The same applies to learned missingness policies, dimensionality reduction chosen by supervised criteria, and threshold selection.

An audit should test the pipeline against deliberately permuted targets. Performance far above chance after permutation is a strong warning of leakage or evaluation defects, though chance-level performance does not prove absence. Temporal “time travel” tests can assert that feature queries return identical values when future records are withheld.

~~~python
import numpy as np
from sklearn.feature_selection import SelectKBest, f_classif
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import StratifiedKFold, cross_val_score
from sklearn.pipeline import make_pipeline

rng = np.random.default_rng(12)
X = rng.normal(size=(300, 2_000))
y = rng.integers(0, 2, size=300)

pipeline = make_pipeline(
    SelectKBest(score_func=f_classif, k=20),
    LogisticRegression(max_iter=1_000),
)
folds = StratifiedKFold(n_splits=5, shuffle=True, random_state=12)
scores = cross_val_score(pipeline, X, y, cv=folds, scoring="accuracy")
print(scores.mean())
~~~

Because selection is refitted inside each fold and targets are random, performance should fluctuate around chance rather than inherit the best correlations from the full dataset. One realisation can still deviate; the example is a diagnostic design, not a probabilistic guarantee.

> **Common misconception 17.18 — “A pipeline eliminates leakage automatically.”**  
> It protects only operations placed inside it and metadata routed correctly. Leakage can remain in upstream table construction, feature availability, split choice, target definition, repeated evaluation, or custom code.
