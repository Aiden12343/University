The web is not a Python facility. It is a distributed system of independently administered machines communicating through layered protocols. Python participates by constructing, parsing, and reacting to protocol messages. A framework hides repetitive mechanics but cannot repeal the network, security, concurrency, or data semantics beneath it.

### 18.1.1 The end-to-end object of study

A web application is not the function decorated with a route. It is an end-to-end path through independently failing components:

\[
\text{user agent}
\rightarrow
\text{name resolution}
\rightarrow
\text{transport security}
\rightarrow
\text{HTTP intermediaries}
\rightarrow
\text{application process}
\rightarrow
\text{stateful dependencies}.
\]

A **user agent** is software acting on behalf of a user, commonly a browser but also a command-line client, mobile application, crawler, or another service. An **origin server** is the authoritative HTTP endpoint for a resource, even when reverse proxies or content-delivery networks stand between it and the client. An **intermediary** is a component that forwards, transforms, caches, filters, or observes protocol messages.

Correctness is a composition of contracts. A route can return the right JSON while the proxy caches one user’s response for another. A transaction can preserve database invariants while a client repeats a timed-out payment. TLS can authenticate a server while application authorisation exposes another person’s record. The unit of reasoning is therefore the whole request and its side effects, not one library call.

Three timescales matter:

- **request time**, from receipt to response or timeout;
- **deployment time**, during which old and new versions coexist;
- **lifecycle time**, during which data, credentials, schemas, clients, and threats evolve.

Designs that work in one process at request time can fail during rolling deployment or later revocation. This chapter treats time and partial failure as first-class properties.

> **Common misconception 18.1 — “Web development begins with choosing a framework.”**  
> It begins with distributed protocol, state, trust, and failure models. A framework implements part of those contracts but cannot choose the application’s semantics or risk policy.

### 18.1.2 A disciplined boundary vocabulary

A **trust boundary** is a point at which data or control crosses between parties, privilege levels, processes, networks, or administrative domains with different assumptions. Every inbound byte is untrusted until validated for its intended use; data remain untrusted after storage if an attacker could have supplied or altered them.

An **application boundary** converts one representation or authority into another: URL text into a route value, bytes into JSON, a session identifier into a principal, input fields into a domain command, or a database row into a response. Boundary code should be small, explicit, limited, and tested because ambiguity compounds across layers.

The chapter separates four concerns often collapsed into “the backend”:

| Concern | Governing question |
|:---|:---|
| protocol | what messages and effects are valid? |
| domain | what state transitions preserve business invariants? |
| persistence | how are concurrent durable changes represented? |
| operations | how is the system deployed, observed, limited, and recovered? |

This separation is conceptual rather than a demand for four services. One well-structured process can maintain these boundaries; many services can still entangle them.

> **Common misconception 18.2 — “Backend code is trusted because users cannot see it.”**  
> Clients control requests, timing, repetition, ordering, and often stored content. Server-side location hides implementation, not attack surface or protocol behaviour.
