# 18.10 Representations and content negotiation

A resource is a conceptual target; a **representation** is a sequence of bytes plus metadata describing one state of that resource. The same resource can have JSON, HTML, image, or language-specific representations. **Content negotiation** selects a representation using request fields and server policy.

JSON numbers do not distinguish every Python numeric type and cannot exactly carry every arbitrary Python integer through all consumers. JSON objects require string names; JSON has no tuple, set, bytes, date-time, decimal, or object identity. API schemas must define encodings for these concepts.

~~~python
from datetime import datetime, timezone

payload = {
    "device_id": "A17",
    "recorded_at": datetime.now(timezone.utc).isoformat(),
    "latency_ms": 83,
}
~~~

The date-time becomes text under ISO 8601-like formatting. A consumer still needs rules for permitted precision, UTC marker, offsets, leap seconds, and required fields. “It is JSON” specifies syntax, not application semantics.

### 18.10.1 Media types and representation metadata

A **media type** identifies representation format and parameters, such as <code>application/json</code> or <code>text/html; charset=utf-8</code>. The <code>Content-Type</code> field describes content actually sent. A client posting JSON with <code>text/plain</code> has not met a JSON endpoint’s contract even if the bytes happen to parse.

Text must have a character-encoding rule. JSON exchanged over HTTP is encoded in UTF-8 under its media-type specification; arbitrary <code>charset</code> variation should not be invented. Binary formats need their own schema and evolution rules.

Content codings such as gzip compress a representation for transfer. <code>Content-Encoding</code> names that transformation; it is not the media type. Servers must limit decompressed size because a small compressed request can expand enormously. Signatures and digests must specify whether they cover encoded transfer bytes or decoded representation bytes.

Language, profile, and API-version information can be represented through media-type parameters, fields, or resource identifiers. Each approach affects caches, links, deprecation, and client implementation. “Versionless” APIs still evolve; compatibility rules simply move elsewhere.

> **Common misconception 18.22 — “<code>Content-Type</code> tells the server what response the client wants.”**  
> It describes enclosed request or response content. <code>Accept</code> and related negotiation fields describe acceptable response representations.

### 18.10.2 Negotiation and the <code>Vary</code> contract

An <code>Accept</code> value can list media ranges with quality weights. The server combines client preferences, representation availability, and policy. A missing <code>Accept</code> commonly means broad acceptance, not specifically JSON. A 406 can report that no acceptable representation exists, though APIs often define one fixed representation instead.

If response selection depends on <code>Accept-Encoding</code>, <code>Accept-Language</code>, or another request field, a shared cache needs that field in <code>Vary</code>. Otherwise it can reuse a compressed, language-specific, or otherwise incompatible representation for another request. Excessive <code>Vary</code> dimensions fragment cache effectiveness.

~~~python
from __future__ import annotations

from dataclasses import dataclass


@dataclass(frozen=True)
class Representation:
    media_type: str
    body: bytes


def choose_representation(accept: str | None) -> Representation:
    html = Representation(
        "text/html; charset=utf-8",
        b"<p>device A17</p>",
    )
    json = Representation(
        "application/json",
        b'{"device_id":"A17"}',
    )
    if accept is None or "*/*" in accept:
        return json
    if "application/json" in accept:
        return json
    if "text/html" in accept:
        return html
    raise LookupError("no acceptable representation")


assert choose_representation("application/json").media_type == (
    "application/json"
)
~~~

This deliberately incomplete parser cannot implement quality weights, specificity, parameters, or quoted syntax. It exposes why applications should use maintained negotiation utilities or define a narrow documented contract.

Streaming JSON as one giant array delays valid closure and complicates recovery. Newline-delimited JSON, server-sent events, or format-specific streaming can define incremental records, but each needs framing, per-record limits, cancellation, and partial-delivery semantics.

> **Common misconception 18.23 — “Content negotiation is just checking whether a header contains the word JSON.”**  
> It is selection under typed syntax, weights, specificity, availability, and cache variation. Substring tests misparse valid fields.

### 18.10.3 HTML is a semantic document language

HTML represents a document tree with elements whose names carry structure and behaviour. A browser parses bytes under the response encoding and HTML parsing algorithm, repairs some malformed structures, constructs a Document Object Model (DOM), loads referenced resources, and exposes interactive semantics.

Elements are not chosen only for appearance. A heading establishes document hierarchy; a button is keyboard-focusable and activates under platform input conventions; a label associates text with a form control; navigation and main landmarks support assistive technology. Replacing them with generic <code>div</code> elements plus click handlers discards behaviour that then has to be reconstructed incompletely.

An **accessible name** identifies a control to assistive technologies. It can derive from text, a label, or defined ARIA relationships. ARIA can express states and relations absent from native elements, but it does not add keyboard behaviour automatically. Prefer native semantic controls, then use ARIA to fill genuine gaps.

Forms serialise named successful controls under an encoding. A checkbox can be absent when unchecked; repeated names can yield several values; file controls use multipart encoding; submit buttons can contribute different names. Server code must parse a multimap rather than assume one scalar per name.

Client-side validation improves feedback but is not an authority boundary. Requests can bypass the browser, constraints can be altered, and concurrent state can change. The server repeats all material validation and authorisation. Return errors associated with fields and a summary usable without colour alone.

HTML responses can support **progressive enhancement**: links and forms perform core navigation and mutation, while JavaScript improves interactivity. This reduces dependency on a successful client bundle and often creates cleaner HTTP semantics. It is an architectural option, not a requirement that every interface avoid rich client state.

### 18.10.4 CSS, JavaScript, and the rendering pipeline

CSS selects elements and applies a cascade of declarations. The final value depends on origin, importance, cascade layer, specificity, scoping, source order, inheritance, and computed-value rules. “The last rule wins” is an incomplete summary.

Layout algorithms—block, inline, flex, grid, table, positioned layout—solve different constraint systems. Responsive design lets layout respond to available space and user preferences rather than a list of device names. Logical properties support writing directions; relative units and content-driven sizing support zoom and text enlargement.

A browser combines the DOM and style information, performs layout, paints pixels, and composites layers. DOM or style changes can require new style calculation, layout, paint, or compositing work. Repeatedly reading layout after writes can force synchronous recalculation. Measure with browser profiling rather than guessing from framework component count.

JavaScript runs tasks on an event loop. Promise callbacks run as microtasks at defined checkpoints; rendering and user input compete with long tasks. An <code>async</code> function yields only at awaits whose operations genuinely settle later. CPU-heavy parsing or rendering on the main thread blocks input and accessibility.

Modules provide lexical scope and dependency graphs. Bundlers can transform modules, split chunks, minify code, and rewrite asset references; source maps connect generated failures to source but can disclose source if published indiscriminately. A content hash supports immutable caching.

Hydration attaches interactive behaviour to server-rendered markup. If the client renders a structurally different tree, frameworks can discard or repair DOM, lose input state, and report mismatch. Time, randomness, locale, authentication, and browser-only values must be controlled across server and client rendering.

Browser performance includes:

- navigation and server response;
- render-blocking styles and scripts;
- image/font transfer and decoding;
- main-thread long tasks;
- layout stability;
- interaction latency;
- memory and detached DOM;
- third-party scripts.

Optimisation follows measured user-facing metrics and representative devices. A tiny compressed bundle can execute expensively; a large image can be harmless below the fold with correct lazy loading; premature memoisation can increase complexity without reducing work.
