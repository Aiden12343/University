# 18.11 Caching and conditional requests

A **cache** stores a representation or result for reuse. HTTP caching can reduce latency and load, but stale or private content creates correctness and security risks. Response fields define freshness and reuse policy. An **entity tag**, or ETag, is a validator associated with a selected representation. A client can send a conditional request and the server can respond that the existing cached representation remains valid.

Caches exist in browsers, service workers, proxies, content-delivery networks, gateways, application processes, and databases. Clearing one cache does not clear all. Cache keys must include every request property that changes the selected representation; otherwise one user or encoding can receive another’s result.

**Cache invalidation** means ensuring reused state ceases to be used when its validity ends. Versioned immutable resource names avoid invalidation for static assets: a changed content hash yields a new URL, while old content can remain cached safely.

### 18.11.1 Freshness and reuse policy

A stored response can be **fresh**, reusable without contacting the origin, or **stale**, requiring validation or permitted stale reuse. <code>Cache-Control</code> directives communicate policy. Examples include:

- <code>max-age</code>: freshness lifetime for relevant caches;
- <code>s-maxage</code>: shared-cache freshness overriding ordinary maximum age;
- <code>private</code>: prevent storage by shared caches;
- <code>no-store</code>: request that caches not store the message;
- <code>no-cache</code>: allow storage but require validation before reuse;
- <code>must-revalidate</code>: constrain stale reuse after freshness;
- <code>immutable</code>: representation is not expected to change during freshness.

<code>no-cache</code> does not mean “do not cache.” <code>no-store</code> is stronger but cannot erase copies already logged or retained outside compliant caches. Sensitive responses need authentication, appropriate cache fields, minimal content, and intermediary configuration.

A cache computes age from response timing and fields; clocks, transit, and revalidation matter. Application-level caches often invent simpler TTL rules and thereby omit HTTP variation or authorisation. Cache design must define key, value, freshness, invalidation, ownership, and failure behaviour.

> **Common misconception 18.24 — “<code>Cache-Control: no-cache</code> disables caching.”**  
> It ordinarily permits storage but requires successful validation before reuse. <code>no-store</code> asks caches not to store, though broader data handling still matters.

### 18.11.2 Validators and conditional requests

A strong ETag identifies byte-equivalent selected representations under strong comparison. A weak ETag, marked <code>W/</code>, can identify semantically equivalent representations unsuitable for byte-range combination. ETag generation must include every representation variation, including encoding when applicable.

A client sends <code>If-None-Match</code> on retrieval; a match allows 304 with fields updating cached metadata and no representation body. <code>If-Match</code> on mutation requires a current match and supports lost-update prevention. Date validators are coarser and vulnerable to timestamp precision; when both apply, defined precedence matters.

~~~python
from hashlib import sha256


def strong_etag(body: bytes) -> str:
    digest = sha256(body).hexdigest()
    return f'"{digest}"'


body = b'{"device_id":"A17","status":"ok"}'
validator = strong_etag(body)
assert validator.startswith('"') and validator.endswith('"')
assert strong_etag(body) == validator
~~~

A content hash is a convenient strong validator only if the bytes hashed are exactly the selected representation and collision resistance satisfies the application. Computing it repeatedly for a large dynamic body can cost more than the saved transfer; version columns or stored digests may be preferable.

Cache invalidation strategies include short freshness, explicit purge, versioned keys, write-through updates, tag invalidation, and event-driven eviction. Every strategy has a race. Design which stale values are tolerable and for how long; “eventual consistency” needs a bound and consequence analysis.

Cache stampedes occur when many requests miss or revalidate one popular key simultaneously. Request coalescing, probabilistic early refresh, bounded locks, and serving permitted stale content can protect the origin. Locks themselves need expiry and failure handling.

> **Common misconception 18.25 — “Adding Redis makes an endpoint faster.”**  
> A cache adds network, serialisation, consistency, invalidation, and failure costs. It helps only when reuse probability and saved work exceed those costs under a correct key and policy.
