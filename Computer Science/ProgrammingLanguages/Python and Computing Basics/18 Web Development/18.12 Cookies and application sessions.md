# 18.12 Cookies and application sessions

A **cookie** is a small piece of state a server asks a user agent to store and return under domain, path, lifetime, and security rules. Cookies are automatically attached to matching requests, which is convenient for sessions and central to cross-site request forgery risk.

A **session** associates a sequence of requests with server-recognised state. A common design stores an opaque random session identifier in a cookie and session data on the server. A signed client-side session stores data in the cookie with integrity protection but not necessarily confidentiality. Users can read data that are merely signed.

Cookie attributes include:

- <code>Secure</code>: send only over secure transport under browser rules;
- <code>HttpOnly</code>: deny ordinary script access, reducing some token theft;
- <code>SameSite</code>: constrain cross-site attachment;
- <code>Path</code> and <code>Domain</code>: define scope;
- expiry or maximum age.

Session identifiers must be unpredictable, rotated after privilege changes, invalidated on logout according to policy, and protected from logging. Cookie flags mitigate classes of attack but do not replace output encoding, CSRF controls, or TLS.

### 18.12.1 Cookie selection and scope

A user agent can store several same-named cookies with different paths or domains. Servers should not assume a simple dictionary with one authoritative value. Narrow scope reduces accidental exposure, but <code>Path</code> is a sending rule rather than a robust confidentiality boundary between applications on one host.

A host-only cookie omits <code>Domain</code> and returns only to the setting host. A domain cookie can reach matching subdomains, increasing exposure if any subdomain is less trusted. Cookie-name prefixes such as <code>__Host-</code> let supporting browsers enforce secure, host-only, root-path properties.

<code>SameSite=Strict</code> most strongly restricts cross-site attachment but can disrupt legitimate entry flows. <code>Lax</code> permits selected top-level navigations; <code>None</code> permits cross-site use and requires <code>Secure</code> in modern browsers. “Same-site” is not identical to “same-origin,” so SameSite is defence in depth rather than a complete request-authorisation mechanism.

Cookies have practical size and count limits. Large signed session payloads consume bandwidth on every matching request and can be evicted unpredictably. Do not store secrets merely because the value is opaque-looking or base64 encoded.

> **Common misconception 18.26 — “<code>HttpOnly</code> prevents XSS.”**  
> It blocks ordinary script access to that cookie. Injected script can still act as the user, read page data, issue requests, and alter the interface.

### 18.12.2 Session lifecycle and fixation

A session identifier needs high entropy from a cryptographically secure generator. Store only a verifier or carefully protect the store where risk demands. Bind session state to a principal, creation and activity times, authentication strength, and revocation status.

**Session fixation** occurs when an attacker arranges for a victim to authenticate while retaining an identifier known to the attacker. Rotate the identifier after login, privilege elevation, account recovery, and other trust changes. Preserve only explicitly safe pre-authentication state during rotation.

Timeout policy includes absolute lifetime, idle lifetime, and sometimes renewal. Short lifetimes reduce exposure but can harm usability and create unsafe workarounds. “Remember me” should create a separately revocable long-lived credential that establishes a new session, not make the ordinary session immortal.

Logout should invalidate server-side state and expire the browser cookie. In distributed stores, revocation propagation has latency. Stateless signed tokens cannot be forcibly revoked before expiry without a denylist, key rotation, version check, or introspection, each reintroducing state or broad invalidation.

> **Common misconception 18.27 — “A signed session cookie is encrypted.”**  
> A signature ordinarily protects integrity and authenticity, not confidentiality. The client can read its payload unless it is separately encrypted.

### 18.12.3 Server-side and token-based state

Server-side sessions make revocation and mutable session state straightforward but require a shared durable or replicated store across application instances. Failure policy matters: if the session store is unavailable, failing closed protects authorisation while reducing availability.

Self-contained access tokens carry claims such as issuer, audience, subject, scope, and expiry. A resource server must validate signature, allowed algorithm, issuer, intended audience, time bounds, and application-specific claims. Merely decoding a token is not validation. A token for one service must not be accepted by another because it has a valid signature.

Bearer tokens grant authority to whoever possesses them. Keep them out of URLs, logs, browser local storage where threat models prohibit script access, and referrer-bearing pages. Proof-of-possession mechanisms can bind a token to a key but add protocol and key-management complexity.

~~~python
from secrets import token_urlsafe


def new_session_identifier() -> str:
    return token_urlsafe(32)


first = new_session_identifier()
second = new_session_identifier()
assert first != second
assert len(first) >= 40
~~~

Length is not itself the security proof; <code>secrets</code> uses an operating-system cryptographic source, and 32 random bytes provide ample entropy before URL-safe encoding. The identifier still needs secure transport, storage, rotation, and invalidation.

> **Common misconception 18.28 — “Stateless tokens eliminate session management.”**  
> They move state into signed claims while retaining issuance, expiry, key rotation, audience, revocation, theft, scope, and logout problems.

### 18.12.4 Browser origins, storage, and cross-context communication

The **same-origin policy** limits how a document or script from one origin can inspect another origin’s resources. It is not one rule but a family governing DOM access, network response reading, storage, canvas data, and other capabilities. Cross-origin writes and embeds are sometimes allowed even when reads are blocked.

CORS lets a server opt into selected cross-origin script access. For a non-simple request, the browser sends a preflight <code>OPTIONS</code> request describing intended method and fields. A successful preflight authorises the browser to proceed under the response policy; it does not authenticate the requesting user or constrain direct non-browser clients.

Origins sent in <code>Origin</code> must be compared as parsed exact allowed origins. Reflecting an arbitrary value together with credential permission grants any requesting site access under the victim’s browser credentials. Cache responses varying by origin with an appropriate <code>Vary</code> rule.

Browser storage includes cookies, local storage, session storage, IndexedDB, cache storage, and service-worker state. Their capacity, lifetime, synchronous/asynchronous API, origin partitioning, eviction, and script accessibility differ. Local storage is synchronously accessible to same-origin script and therefore unsuitable for secrets under an XSS threat model.

A service worker can intercept requests and serve cached responses, enabling offline behaviour and creating another cache/deployment layer. An old service worker can continue controlling pages after a server deployment. Version caches, define update and activation policy, and provide a recovery path from a broken worker.

Cross-window <code>postMessage</code> permits explicit communication. The sender should specify an exact target origin, not <code>*</code>, when data are sensitive. The receiver checks <code>event.origin</code>, expected source window, message schema, and authorisation before acting. Message data are untrusted even when the origin is allowed because another application component on that origin may be compromised.

Third-party iframes can be constrained with <code>sandbox</code>, Permissions Policy, CSP, and narrow messaging. Granting both script and same-origin capabilities to untrusted same-origin content can undermine sandboxing. Isolation is a capability design, not a visual border.
