# 18.13 From a request to a Python callable

A web server accepts network connections, parses HTTP, enforces protocol limits, and invokes application code through an interface. The application should not reimplement HTTP framing for ordinary work. In Python, two principal server–application interfaces are WSGI and ASGI.

**Web Server Gateway Interface**, or WSGI, defines a synchronous callable contract for Python web applications. A simplified application receives an environment mapping and a callback used to start the response:

~~~python
from collections.abc import Callable, Iterable
from typing import Any


def application(
    environ: dict[str, Any],
    start_response: Callable[..., Any],
) -> Iterable[bytes]:
    body = b"Hello, web\n"
    start_response(
        "200 OK",
        [
            ("Content-Type", "text/plain; charset=utf-8"),
            ("Content-Length", str(len(body))),
        ],
    )
    return [body]
~~~

The body is bytes. The content length uses byte length. This minimal example omits error handling, streaming close hooks, header validation, and server deployment. WSGI represents one request/response exchange through a synchronous call and does not natively model WebSocket or long-lived bidirectional asynchronous events.

**Asynchronous Server Gateway Interface**, or ASGI, defines an asynchronous event interface. An application receives a scope describing the connection plus <code>receive</code> and <code>send</code> awaitable callables:

~~~python
from typing import Any


async def application(
    scope: dict[str, Any],
    receive: Any,
    send: Any,
) -> None:
    if scope["type"] != "http":
        raise ValueError("this application accepts HTTP only")

    await send(
        {
            "type": "http.response.start",
            "status": 200,
            "headers": [
                (b"content-type", b"text/plain; charset=utf-8"),
            ],
        }
    )
    await send(
        {
            "type": "http.response.body",
            "body": b"Hello, ASGI\n",
            "more_body": False,
        }
    )
~~~

ASGI represents HTTP, WebSocket, and lifespan events through typed messages. An <code>async def</code> application is not automatically faster. It improves concurrency for operations that genuinely await non-blocking interfaces. CPU-bound work still occupies an event-loop thread unless moved or redesigned.

### 18.13.1 WSGI’s exact synchronous boundary

WSGI specifies how a server presents one HTTP request to a Python callable and how that callable begins and returns a response. The <code>environ</code> mapping contains CGI-derived strings, server metadata, and extension values. The request body is a file-like byte stream under <code>wsgi.input</code>; reading without respecting content length or server limits can block or consume excessive data.

The application calls <code>start_response(status, headers)</code> before yielding non-empty body bytes. Headers are native strings constrained by the specification’s encoding model; bodies are bytes. If the returned iterable has <code>close</code>, the server must call it, enabling generator cleanup. An application must not depend on the server consuming the entire iterable after a client disconnect.

**WSGI middleware** is both an application to the outer server and a server-like caller of the inner application. It can add correlation identifiers, enforce authentication, alter paths, compress output, or catch exceptions. Order matters: exception middleware outside authentication observes different state from middleware inside it.

~~~python
from __future__ import annotations

from collections.abc import Callable, Iterable
from typing import Any
from uuid import uuid4

StartResponse = Callable[..., Any]
WSGIApp = Callable[
    [dict[str, Any], StartResponse],
    Iterable[bytes],
]


class CorrelationMiddleware:
    def __init__(self, application: WSGIApp) -> None:
        self.application = application

    def __call__(
        self,
        environ: dict[str, Any],
        start_response: StartResponse,
    ) -> Iterable[bytes]:
        request_id = environ.get(
            "HTTP_X_REQUEST_ID",
            str(uuid4()),
        )
        environ["application.request_id"] = request_id

        def wrapped_start(
            status: str,
            headers: list[tuple[str, str]],
            exc_info: object = None,
        ) -> Any:
            headers.append(("X-Request-ID", request_id))
            return start_response(status, headers, exc_info)

        return self.application(environ, wrapped_start)
~~~

The example trusts an inbound identifier for correlation only; a production system validates length and characters and distinguishes externally supplied from internally generated identity. Middleware must not append a second conflicting response field if the inner application already set one under the chosen policy.

> **Common misconception 18.29 — “WSGI is a web server.”**  
> It is an interface specification between servers and applications. A server implementation manages sockets, workers, timeouts, and protocol parsing; a framework or application implements the callable side.

### 18.13.2 ASGI scopes, events, and connection lifetime

ASGI separates a connection **scope** from a sequence of events. An HTTP scope ordinarily covers one request; a WebSocket scope covers the connection. <code>receive</code> yields request-body chunks, disconnects, WebSocket messages, or lifespan events according to scope type. <code>send</code> emits response and protocol events.

Request bodies can arrive in several <code>http.request</code> events with <code>more_body=True</code>. Reading only the first truncates content. Buffering every chunk without a maximum invites memory exhaustion. A streaming consumer processes bounded chunks and responds to disconnect or cancellation.

ASGI lifespan events let a server ask the application to initialise and shut down resources. Connection pools should be created within process/event-loop lifecycle, not arbitrarily at module import, and closed during shutdown. Multiple worker processes each run their own lifespan and own pools.

ASGI middleware wraps the three-callable interface. It must keep request-local state inside the call or scope, not on a shared middleware instance where concurrent connections race. Context variables can propagate request metadata across awaits but require care when spawning tasks.

> **Common misconception 18.30 — “Replacing <code>def</code> with <code>async def</code> converts a WSGI application into an ASGI application.”**  
> The interfaces have different call signatures, event models, lifetimes, and concurrency contracts. An adapter can bridge subsets but cannot invent native streaming or WebSocket semantics.

### 18.13.3 Backpressure, cancellation, and sync/async boundaries

**Backpressure** prevents a fast producer from overwhelming a slower consumer. Awaiting <code>send</code> can allow the server to regulate output; placing generated chunks into an unbounded in-process queue defeats that benefit. Streaming database rows while a client reads slowly can hold a transaction and connection for an unacceptable time.

Client disconnect is a cancellation signal, not proof that server work should always stop. A read-only report can be cancelled; a payment already committed must complete its durable response record even if the socket vanished. Cancellation policy follows side-effect boundaries.

Calling blocking database or HTTP clients directly in an event-loop thread stalls every coroutine on that loop. A thread offload protects the loop but remains bounded by threads and does not make the dependency asynchronous. Conversely, calling an async library from synchronous WSGI requires an event-loop bridge whose lifecycle and cancellation semantics are non-trivial.

CPU-bound Python work should be bounded and usually moved to a process, native implementation that releases the GIL, or background system. Spawning an unbounded task per request only relocates overload.

> **Common misconception 18.31 — “ASGI applications can handle unlimited concurrent requests because waiting is non-blocking.”**  
> Each connection consumes memory, descriptors, task state, dependency capacity, and scheduling work. Concurrency must remain bounded end to end.

### 18.13.4 Server-sent events and WebSockets

Ordinary HTTP is client-initiated request/response. Some applications need continuing server updates or bidirectional messages.

**Server-Sent Events** (SSE) keep an HTTP response open with media type <code>text/event-stream</code>. The server emits UTF-8 text events separated by blank lines. Browsers can reconnect and send a last-event identifier, permitting resumable streams if the application retains a bounded event history. SSE is server-to-client; client-to-server actions use ordinary requests.

A **WebSocket** begins with an HTTP upgrade or extended connection procedure and then exchanges framed messages bidirectionally. Message boundaries are preserved at the WebSocket layer, unlike raw TCP application writes. Frames can fragment a message; maintained libraries reassemble or stream according to their API.

Opening a WebSocket does not supply authentication. Browser cookies can accompany the handshake, creating cross-site WebSocket hijacking risk if the server neglects origin and CSRF-like validation. Tokens passed in query strings leak through logs; subprotocol or first-message authentication has its own exposure and timeout rules.

After connection, authorisation applies to every subscribed resource and command, and may need re-evaluation when roles change. Define:

- maximum connections per principal and globally;
- maximum message size and rate;
- accepted message schema and version;
- heartbeat and idle timeout;
- outbound queue bound for slow consumers;
- ordering and duplicate semantics;
- reconnect and resume behaviour;
- server restart and deployment draining;
- observability without logging sensitive payloads.

A slow client can cause an unbounded outbound buffer unless the server blocks producers, drops defined ephemeral events, coalesces state updates, or disconnects it. Each policy changes semantics.

~~~python
from dataclasses import dataclass, field


@dataclass
class BoundedMailbox:
    capacity: int
    _items: list[bytes] = field(default_factory=list)

    def offer(self, message: bytes) -> bool:
        if len(self._items) >= self.capacity:
            return False
        self._items.append(message)
        return True

    def take(self) -> bytes:
        if not self._items:
            raise LookupError("mailbox is empty")
        return self._items.pop(0)


mailbox = BoundedMailbox(capacity=2)
assert mailbox.offer(b"one")
assert mailbox.offer(b"two")
assert not mailbox.offer(b"three")
~~~

The list has \(O(n)\) removal and is only pedagogical; <code>collections.deque</code> or an asynchronous bounded queue is appropriate. The important contract is that overload becomes an explicit result rather than invisible memory growth.

WebSockets are not a message broker. A disconnected client misses messages unless the application stores and resumes them. Sticky routing can keep a connection at one process, but broadcasts across processes need a shared event system and delivery policy.
