# 18.15 Django as an integrated framework

Django supplies an integrated set of facilities: URL routing, request and response abstractions, templates, forms, authentication, administration, database migrations, and an object-relational mapper. Its purpose is not that every project needs more machinery. It encodes coherent defaults for applications that need these concerns together.

A **project** is the configured site-level application. A Django **app** is a reusable or bounded feature component within a project. The word “app” here is framework terminology and does not necessarily indicate a separately deployed service.

Conceptual model:

~~~python
from django.db import models


class Device(models.Model):
    device_id = models.CharField(
        max_length=64,
        unique=True,
    )
    status = models.CharField(max_length=32)
    created_at = models.DateTimeField(auto_now_add=True)

    def __str__(self) -> str:
        return self.device_id
~~~

The class declares fields that Django uses to build Python descriptors, validation facilities, queries, and migration state. <code>unique=True</code> requests a database uniqueness constraint through migrations. Application checks alone cannot enforce uniqueness against concurrent transactions; the database constraint is authoritative.

A **migration** is a versioned transformation of database schema or related state. It is executable history, not a snapshot to regenerate casually. Deployments must sequence schema and application versions so both old and new processes remain compatible during a rolling transition.

### 18.15.1 Requests through Django’s architecture

Django resolves a URL pattern to a view after request middleware runs. A view can be a function or class-based callable and returns an <code>HttpResponse</code> or raises an exception handled by the framework. Response middleware then runs in the reverse direction under the configured chain.

Middleware order affects security and semantics: sessions must exist before authentication middleware uses them; security headers must apply to error responses; transaction middleware changes the duration of database transactions. Installing a component without understanding its order can silently weaken a guarantee.

Forms and model forms combine input parsing, validation, error representation, and controlled model construction. They do not replace object-level authorisation. Excluding an <code>owner</code> field from a form prevents direct binding, but the view must still assign and check ownership correctly.

Django’s administration interface is powerful operational software, not a public application UI. Restrict access, use strong authentication, limit model actions, log material changes, and avoid registering sensitive models casually. Staff status is broad authority under configuration, not a decorative flag.

> **Common misconception 18.34 — “Django is secure by default, so application security is automatic.”**  
> Secure defaults mitigate common classes when used correctly. Domain authorisation, deployment, secrets, dependency updates, unsafe template overrides, raw SQL, and custom code remain application responsibilities.

### 18.15.2 Models, managers, and async boundaries

A model class declares persistence mapping and some invariants. Custom managers and query sets can centralise common selection and tenant scoping, but hidden filters can surprise maintenance code. Database constraints remain necessary because model validation is not automatically invoked for every bulk update or external writer.

~~~python
from django.db import models


class ActiveDeviceQuerySet(models.QuerySet):
    def active(self):
        return self.exclude(status="retired")

    def for_site(self, site_id: int):
        return self.filter(site_id=site_id)


class ManagedDevice(models.Model):
    device_id = models.CharField(max_length=64, unique=True)
    site_id = models.PositiveBigIntegerField()
    status = models.CharField(max_length=32)

    objects = ActiveDeviceQuerySet.as_manager()

    class Meta:
        constraints = [
            models.CheckConstraint(
                condition=models.Q(
                    status__in=["new", "ok", "retired"]
                ),
                name="managed_device_valid_status",
            )
        ]
~~~

The query-set methods are composable and lazy. The check constraint protects the status domain for every database writer using a supporting backend. The example uses an integer rather than a foreign key only to isolate query-set structure; a real relation ordinarily deserves a foreign key.

Django supports asynchronous views and parts of its stack, but synchronous middleware or database operations can force thread adaptation. Long-lived streaming and WebSockets usually use ASGI-oriented infrastructure and, for WebSockets, an additional protocol framework. Measure the actual call chain rather than infer concurrency from one <code>async</code> keyword.

Framework upgrades can change defaults, deprecate APIs, and close security vulnerabilities. Pin compatible versions, read release and deployment checklists, run system checks and tests, and deploy migrations deliberately. Long-term-support releases reduce upgrade frequency but do not eliminate maintenance.

> **Common misconception 18.35 — “A larger integrated framework removes architectural decisions.”**  
> It supplies coherent defaults and facilities. The application still decides domain boundaries, data ownership, authorisation, consistency, deployment, and failure policy.
