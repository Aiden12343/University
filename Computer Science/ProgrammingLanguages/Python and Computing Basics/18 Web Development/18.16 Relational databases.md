# 18.16 Relational databases

A **database management system**, or DBMS, stores and retrieves structured state under concurrency, durability, and query semantics. In a relational database, a **table** has named columns and rows. A **primary key** identifies a row; a **foreign key** enforces references between tables under configured actions.

SQL, the Structured Query Language, declares desired relational results. A simplified schema:

~~~sql
CREATE TABLE site (
    site_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL UNIQUE
);

CREATE TABLE device (
    device_id TEXT PRIMARY KEY,
    site_id BIGINT NOT NULL REFERENCES site(site_id),
    status TEXT NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL
);
~~~

The database, not Python type hints, enforces non-null and key constraints for every writer using the database. A check constraint could restrict status to a domain, although a reference table or application evolution may better suit some cases.

SQL query:

~~~sql
SELECT
    s.name,
    COUNT(*) AS device_count
FROM device AS d
JOIN site AS s ON s.site_id = d.site_id
GROUP BY s.site_id, s.name
ORDER BY device_count DESC;
~~~

The DBMS planner chooses an execution strategy using indexes and statistics. An **index** is an auxiliary structure accelerating selected lookups and orderings at storage and write cost. Creating an index on every column can slow writes and consume space without improving actual queries.

### 18.16.1 Relations, keys, and normalisation

The relational model represents data as relations of tuples over named attributes. SQL tables approximate this model with types, nullability, duplicates unless constrained, ordering only when requested, and vendor-specific behaviour. Row order without <code>ORDER BY</code> is undefined even if a test repeatedly returns insertion order.

A **candidate key** is a minimal set of attributes uniquely identifying a tuple. A primary key is the candidate selected as the table’s principal identifier. A **surrogate key** is introduced for identification rather than derived from domain meaning; it does not remove the need for unique constraints on natural invariants such as an external device identifier within a tenant.

Normalisation decomposes data to reduce redundancy and update anomalies. If a site name is copied onto every device row, renaming the site requires many consistent writes. A separate site relation referenced by a foreign key represents the dependency once. Denormalisation can be justified for measured read paths, but it creates a synchronisation rule that must be owned.

NULL represents missing or inapplicable information under SQL’s three-valued logic. Comparisons with NULL yield unknown rather than true or false; use <code>IS NULL</code>. <code>NOT IN</code> with a nullable subquery can therefore behave unexpectedly. Nullability is a domain decision, not merely a convenience during coding.

> **Common misconception 18.36 — “A primary key makes every domain entity unique.”**  
> It makes stored rows unique by that key. Duplicate real-world entities remain possible unless domain identity and additional constraints are defined.

### 18.16.2 Constraints and indexes are executable invariants

Database constraints reject invalid state under concurrent writers:

- <code>NOT NULL</code> requires a value;
- <code>CHECK</code> enforces a row-level predicate supported by the DBMS;
- <code>UNIQUE</code> enforces candidate-key-like uniqueness;
- <code>FOREIGN KEY</code> enforces referential existence and configured update/delete action;
- exclusion or trigger-based constraints can protect more complex relations in supporting systems.

Application validation improves error messages but races: two processes can both observe “name unused” before inserting. The database unique constraint serialises the invariant; the application catches and maps the resulting conflict.

B-tree indexes support equality, range, and ordering patterns over leading columns. A composite index on <code>(site_id, created_at)</code> can serve filtering by site and ordering/ranging by creation time; it is not equivalent to independent indexes for every query. Partial indexes cover rows satisfying a predicate; expression indexes cover computed keys.

Query planners estimate row counts from statistics and choose scans, joins, and sorts. A plan appropriate for ten rows can fail at ten million. Use <code>EXPLAIN</code> and measured execution under representative data, but do not force a plan from one observation without understanding parameter distributions and cache state.

~~~python
import sqlite3

connection = sqlite3.connect(":memory:")
connection.execute(
    """
    CREATE TABLE device (
        device_id TEXT PRIMARY KEY,
        site_id INTEGER NOT NULL,
        status TEXT NOT NULL
            CHECK (status IN ('new', 'ok', 'retired')),
        UNIQUE (site_id, device_id)
    )
    """
)
connection.execute(
    "CREATE INDEX device_site_status "
    "ON device(site_id, status)"
)
connection.execute(
    "INSERT INTO device VALUES (?, ?, ?)",
    ("A17", 4, "ok"),
)
try:
    connection.execute(
        "INSERT INTO device VALUES (?, ?, ?)",
        ("B20", 4, "impossible"),
    )
except sqlite3.IntegrityError:
    pass
else:
    raise AssertionError("CHECK constraint should reject status")
~~~

SQLite is useful for this self-contained demonstration; its concurrency, types, DDL, and query planner differ from server DBMSs. Production-dependent behaviour must be tested against the selected production family.

> **Common misconception 18.37 — “Indexes are copies that make all database access faster.”**  
> Each index supports particular predicates and orderings while consuming storage, cache, and write work. Unused or redundant indexes reduce performance.

### 18.16.3 Time, money, identity, and tenant boundaries

Time values need a clock and meaning. An **instant** identifies one point on a time line and can be stored in a UTC-capable timestamp type. A civil time such as “09:30 Europe/London” combines local date/time with a named time zone whose political rules can change. An offset such as <code>+01:00</code> is not a time-zone rule set.

Store instants for occurred events and retain the named zone where future civil schedules must follow local rules. Daylight-saving transitions create nonexistent and repeated local times. Database and Python libraries need an explicit policy for ambiguity rather than silent guessing.

Durations use monotonic clocks for in-process deadlines because wall clocks can jump. Database expiry based on authoritative database time avoids disagreement among application hosts, while clients should not control security expiry.

Money uses an integer minor unit or exact decimal with declared currency and rounding. Binary floating point cannot exactly represent many decimal fractions. Currency determines scale only imperfectly: some currencies have no minor unit, and financial instruments can require more precision. A monetary amount without currency is incomplete.

Identifiers have scope. An account number can be unique within a tenant but not globally; an external provider ID needs provider identity; a user-facing slug can change while an internal key remains. Composite unique constraints should encode the actual scope.

Multi-tenant systems choose among shared tables with tenant keys, separate schemas, separate databases, or hybrid partitioning. Every model affects isolation, operations, migrations, backup/restore, noisy neighbours, and cross-tenant analytics. In a shared-table design:

- every tenant-owned table carries a non-null tenant key;
- unique constraints include tenant scope where appropriate;
- foreign keys prevent cross-tenant references, sometimes through composite keys;
- repository queries require tenant context;
- caches and object storage keys include tenant identity;
- background jobs and logs carry tenant scope without exposing it as unchecked client input.

Database row-level security can enforce tenant predicates below the application, but only if session context is set safely for every transaction and privileged bypass roles are constrained. Connection pooling can leak session variables between requests unless reset.

Deletion is a workflow, not one SQL statement. Foreign keys, audit duties, legal holds, derived indexes, caches, search systems, object storage, backups, and downstream processors can retain data. Define erasure scope and communicate residual backup retention accurately.
