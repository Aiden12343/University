# 18.17 Parameterised queries and injection

**Injection** occurs when untrusted data alters the structure of code or a command rather than remaining data. SQL injection commonly arises from constructing SQL with string concatenation.

Unsafe:

~~~python
query = (
    "SELECT * FROM device "
    f"WHERE device_id = '{device_id}'"
)
cursor.execute(query)
~~~

An attacker-supplied quote can terminate the intended literal and introduce SQL syntax. Escaping manually is error-prone and database-specific.

Safe structural separation:

~~~python
cursor.execute(
    "SELECT device_id, status "
    "FROM device WHERE device_id = %s",
    (device_id,),
)
~~~

The placeholder syntax depends on the database driver. The driver transmits or encodes the value as a parameter under protocol rules rather than interpreting it as query structure. Parameters ordinarily cannot substitute identifiers or keywords; dynamic table or column selection requires an allowlist and driver-supported identifier composition.

An ORM reduces direct SQL construction but does not make all expressions safe. Raw fragments, dynamic ordering, template rendering, shell calls, and URL construction each have their own injection boundaries.

### 18.17.1 Values are not identifiers or syntax

Database parameters represent literal values. They cannot ordinarily choose a table name, column, operator, sort direction, or SQL keyword because those positions belong to grammar. Dynamic syntax needs a mapping from an external choice to developer-authored fragments:

~~~python
from typing import Literal

SortChoice = Literal["created", "status"]


def ordering_sql(choice: SortChoice) -> str:
    allowed = {
        "created": "created_at DESC, device_id ASC",
        "status": "status ASC, device_id ASC",
    }
    try:
        return allowed[choice]
    except KeyError as error:
        raise ValueError("unsupported ordering") from error


assert ordering_sql("created").startswith("created_at")
~~~

The returned fragment comes entirely from code. The client selects among capabilities rather than supplying SQL. Driver identifier-composition APIs can quote a validated identifier, but an unrestricted user-selected table is usually also an authorisation and data-exposure defect.

Parameter placeholders differ: DB-API drivers use styles such as <code>?</code>, <code>%s</code>, or named markers. Do not interpolate before passing to the driver. Logging a rendered query should avoid reconstructing secrets and must not become the execution path.

> **Common misconception 18.38 — “Prepared statements sanitise an entire SQL string after interpolation.”**  
> Parameters keep values separate from parsed query structure. Interpolating first has already lost the distinction; dynamic syntax requires controlled composition.

### 18.17.2 Injection is a family of parser-boundary failures

The same structure appears in shell injection, template injection, LDAP filters, regular expressions, email headers, log forging, and code evaluation. Defence follows the target grammar:

1. avoid exposing a programmable grammar where a fixed operation suffices;
2. use structured APIs that separate data from syntax;
3. allowlist the small unavoidable syntax choices;
4. encode output for the exact destination context;
5. run with least authority so a defect has bounded effect.

Input validation alone is insufficient. An apostrophe is a legitimate surname; rejecting it damages data while clever encodings bypass naive filters. Parameterisation permits the full value domain without treating it as structure.

Database accounts should have only required privileges. A read endpoint should not connect as a superuser capable of dropping schemas. Separate migration authority from application runtime authority. Row-level security can add database enforcement for tenant policy, but application context propagation and policy testing remain essential.

Error messages should not reveal query text or schema. Timing and row-count differences can still disclose existence, so authorisation should occur before sensitive query distinctions where feasible.

> **Common misconception 18.39 — “Escaping dangerous characters is a universal injection defence.”**  
> Escaping is grammar- and context-specific and often incomplete. Structural APIs and fixed syntax are preferable; least privilege limits residual damage.
