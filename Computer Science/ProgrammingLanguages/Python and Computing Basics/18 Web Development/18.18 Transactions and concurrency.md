# 18.18 Transactions and concurrency

A **transaction** groups database operations under an all-or-nothing unit and an isolation model. The traditional ACID properties are:

- **atomicity:** a transaction’s changes commit as a unit or are rolled back;
- **consistency:** defined invariants hold across successful transactions, assuming constraints and correct operations;
- **isolation:** concurrent transactions interact as if governed by the selected isolation guarantees;
- **durability:** committed changes survive failures covered by the system’s guarantee.

“Consistency” does not mean the database understands every business rule. It enforces declared constraints and transaction logic.

### Worked example 18.4 — Transfer as one transaction

~~~python
from decimal import Decimal


def transfer(
    connection,
    *,
    source_id: int,
    destination_id: int,
    amount: Decimal,
) -> None:
    if amount <= 0:
        raise ValueError("amount must be positive")
    if source_id == destination_id:
        raise ValueError("accounts must differ")

    with connection:
        with connection.cursor() as cursor:
            cursor.execute(
                "SELECT balance FROM account "
                "WHERE account_id = %s FOR UPDATE",
                (source_id,),
            )
            row = cursor.fetchone()
            if row is None:
                raise LookupError("source account does not exist")
            if row[0] < amount:
                raise ValueError("insufficient funds")

            cursor.execute(
                "UPDATE account SET balance = balance - %s "
                "WHERE account_id = %s",
                (amount, source_id),
            )
            cursor.execute(
                "UPDATE account SET balance = balance + %s "
                "WHERE account_id = %s",
                (amount, destination_id),
            )
            if cursor.rowcount != 1:
                raise LookupError(
                    "destination account does not exist"
                )
~~~

The exact context-manager and placeholder behaviour depends on the driver. The row lock prevents specified concurrent modifications under supported transaction semantics. Both updates commit together or an exception triggers rollback. A database check constraint should additionally forbid negative balances where the domain demands it.

Isolation levels permit or prevent different anomalies. A **lost update** occurs when concurrent operations overwrite one another. A **write skew** can occur when transactions read overlapping state and write disjoint rows while jointly violating an invariant under some isolation levels. “Using a transaction” is incomplete; the invariant, reads, writes, locks, and database isolation must be analysed.

Long transactions retain locks or old versions, increase contention, and complicate retries. Network calls should ordinarily not occur while holding a database transaction open unless the protocol explicitly requires it.

### 18.18.1 Isolation phenomena and serialisability

Isolation levels are named categories with DBMS-specific implementations. Common anomalies include:

- **dirty read**: observing another transaction’s uncommitted write;
- **non-repeatable read**: rereading a row and obtaining a committed change;
- **phantom**: repeating a predicate query and obtaining a changed row set;
- **lost update**: one write overwrites another without incorporating it;
- **write skew**: transactions read shared constraints and write disjoint rows, jointly violating an invariant.

**Serialisable** execution provides outcomes equivalent to some serial order of committed transactions, not necessarily the order they began. Implementations use locks, predicate locks, multiversion checks, or serialisation-failure detection. Applications must be prepared to retry transactions rejected to preserve serialisability.

Snapshot isolation provides a consistent snapshot but can permit write skew. “Repeatable read” means different things across databases. Correct design cites the actual DBMS documentation and tests the invariant with concurrent sessions.

> **Common misconception 18.40 — “ACID transactions execute one at a time.”**  
> Databases interleave concurrent work while providing an isolation contract. The selected level and access pattern determine which observations and anomalies are possible.

### 18.18.2 Locks, deadlocks, and retryable transactions

Pessimistic locking acquires database locks before a conflicting action; optimistic control performs work and rejects a conflicting commit or conditional write. Pessimistic methods can block and deadlock. Optimistic methods can waste work and repeatedly conflict under contention.

A **deadlock** is a cycle of waits: transaction A holds a resource B needs while B holds one A needs. Databases detect a cycle and abort a participant. Acquire resources in a consistent order to reduce deadlocks, keep transactions short, and retry the whole transaction after rollback with a bound and jitter.

~~~python
from __future__ import annotations

from collections.abc import Callable
from typing import TypeVar

T = TypeVar("T")


class SerializationFailure(Exception):
    pass


def run_transaction(
    operation: Callable[[], T],
    *,
    maximum_attempts: int = 3,
) -> T:
    for attempt in range(maximum_attempts):
        try:
            return operation()
        except SerializationFailure:
            if attempt + 1 == maximum_attempts:
                raise
    raise AssertionError("loop must return or raise")
~~~

The operation must begin a fresh transaction on every attempt. Side effects outside the database—emails, HTTP calls, file writes—must not be repeated casually. Record an outbox event within the transaction and perform external delivery later.

Savepoints provide partial rollback within a transaction but do not create independent durability. Nested library transaction blocks may join one outer transaction rather than commit separately; know the framework contract.

> **Common misconception 18.41 — “A deadlock means the database is broken.”**  
> Deadlocks are an expected possibility under locking concurrency. The database resolves them by aborting work; applications must minimise cycles and retry safe transaction units.

### 18.18.3 Transactions do not cross systems automatically

A local database transaction cannot atomically commit an email provider, message broker, payment processor, and another database unless a distributed protocol and every participant support it. Two-phase commit can coordinate prepared participants but introduces availability, blocking, and operational costs and is uncommon across public services.

A **saga** represents a multi-step process as local transactions plus compensating actions. Compensation is not time travel: refunding a payment does not make a sent parcel or disclosed email unseen. The process needs explicit states, idempotent commands, retry rules, deadlines, and manual resolution for irrecoverable cases.

The transactional outbox solves one common boundary by committing domain state and an event record together. A relay may publish the event more than once, so consumers deduplicate or make effects idempotent. An inbox table can record consumed event identifiers transactionally with local changes.

> **Common misconception 18.42 — “Wrapping code in one Python <code>with</code> block makes every side effect atomic.”**  
> The database connection controls its own transaction. External services, files, caches, and queues need explicit coordination and recovery semantics.
