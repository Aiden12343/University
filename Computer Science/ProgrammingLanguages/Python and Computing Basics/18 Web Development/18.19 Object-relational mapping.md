# 18.19 Object-relational mapping

An **object-relational mapper**, or ORM, maps Python-level classes and expressions to database tables and queries. It solves repetitive mapping, composable query construction, identity handling, and schema integration. It does not make the relational model object-shaped.

~~~python
device = (
    Device.objects
    .select_related("site")
    .get(device_id="A17")
)
print(device.site.name)
~~~

<code>select_related</code> requests a join for a single-valued relation, avoiding a later query when <code>site</code> is accessed. Without deliberate loading, iterating devices and accessing each related site can cause the **N+1 query problem**: one initial query plus one query per row. Query count grows linearly and network/database latency dominates.

ORM query sets are often lazy. Construction does not necessarily execute SQL; iteration, conversion, length, or related operations can trigger evaluation. Debugging performance requires inspecting generated SQL, query plans, row counts, and indexes.

The ORM object identity map, database row identity, and Python object identity are distinct. Two Python objects can represent the same database row at different times and hold stale values.

### 18.19.1 Object graphs and relational sets have different semantics

Objects expose navigation and behaviour; relational queries transform sets or bags of rows. An ORM translates a useful subset, but translation has costs:

- attribute access can trigger I/O;
- a Python loop can become hundreds of SQL statements;
- object creation can dominate bulk processing;
- implicit flushing can issue writes before an apparent commit point;
- equality and identity can differ across sessions;
- database NULL and SQL collation differ from Python values and comparison.

Query expressions should remain in the ORM’s translatable language until execution. Pulling rows into Python to filter wastes indexes and bandwidth; calling a Python-only function inside a query is usually impossible or evaluated in an unexpected place.

An **identity map** returns one in-memory object per database identity within a unit of work in some ORMs. It improves relationship consistency but creates stale caches and memory growth. Django does not provide one general long-lived identity map; other ORMs do. Never assume the pattern from the generic term “ORM.”

> **Common misconception 18.43 — “ORM attributes behave like ordinary in-memory attributes.”**  
> Access can execute queries, lazy relations can fail outside a session, and values can be stale relative to concurrent database state.

### 18.19.2 Query shape is part of correctness

The N+1 problem is one instance of uncontrolled query shape. Joining several one-to-many relations can instead create a Cartesian multiplication, returning enormous duplicate row combinations. Select-in prefetch can use several bounded queries and assemble relations without multiplication. The right strategy depends on cardinality.

Pagination should happen in SQL under a deterministic order. Fetching every row and slicing in Python is not pagination. Counting an enormous filtered set can itself be expensive; APIs should decide whether exact totals justify cost.

Bulk updates bypass per-object hooks, validation, and sometimes timestamp behaviour. They are valuable precisely because they avoid object-by-object machinery. Database constraints and explicit audit logic protect invariants that must survive every write path.

~~~python
# Conceptual Django query: inspect rather than execute here.
query = (
    Device.objects
    .filter(site_id=4, status="ok")
    .select_related("site")
    .order_by("device_id")
)
sql, parameters = query.query.sql_with_params()
~~~

Inspecting generated SQL and parameters helps verify joins and filtering without interpolating values. Actual performance requires the database execution plan and representative data.

Repository or service layers can isolate persistence choices, but mechanically wrapping every ORM method often adds indirection without a semantic boundary. Introduce an abstraction around domain operations and transaction units, not because a pattern catalogue demands one.

> **Common misconception 18.44 — “Fewer SQL queries always means better performance.”**  
> One explosive join can be worse than several selective queries. Measure row cardinality, transferred bytes, plan, latency, memory, and lock duration.
