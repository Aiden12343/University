# 18.20 Schema evolution

Changing a live schema is a distributed compatibility problem. Suppose a required column is added. If the database first rejects rows lacking it while old application instances still write the old form, deployment fails.

An **expand–migrate–contract** strategy:

1. add a nullable or defaulted field compatible with old code;
2. deploy code that writes both old and new representations;
3. backfill existing rows in bounded batches;
4. verify completeness;
5. deploy code reading only the new representation;
6. enforce the new constraint;
7. remove the old representation after no supported reader needs it.

Each step is reversible or observable. Large table rewrites can lock or saturate a database; version-specific database facilities determine operational strategy.

### 18.20.1 Schema and application versions coexist

During rolling deployment, old and new processes execute concurrently. A safe migration establishes a compatibility window. Renaming a column directly can break the old version; adding a new column, dual-writing, backfilling, switching reads, and later removing the old one permits coexistence.

Defaults have several meanings: a database default for omitted writes, an ORM default applied in Python, and a backfill for existing rows. They are not interchangeable. A volatile or computed default can rewrite a table in some database versions; consult the selected engine.

Migration files belong in version control and are reviewed like production code. Editing an already-applied migration creates divergent histories. A corrective migration advances from known state. Squashing history is a deliberate maintenance operation that preserves compatibility for supported installations.

> **Common misconception 18.45 — “A migration is just the difference between current model classes and the database.”**  
> It is ordered executable history with dependencies, data assumptions, locking behaviour, and compatibility obligations.

### 18.20.2 Online change, backfill, and rollback

A large backfill should process deterministic bounded batches, commit progress, respect replication and load, and be restartable. Record a high-water mark or select rows still missing the new value. An update without a stable order can revisit or starve rows under concurrent changes.

Creating an index can block writes or consume substantial I/O unless the DBMS provides an online/concurrent form. Adding a constraint can be staged: create it without validating historical rows where supported, repair data, validate, then make application assumptions. Each engine has different syntax and guarantees.

Data migration code must use historical model/schema state rather than importing today’s application class, which may change before a fresh installation replays history. Time zones, locale, external APIs, and nondeterministic defaults make historical replay fragile.

Rollback has limits. Dropping a column destroys data; reversing after new code wrote values unavailable to old code can be lossy. Prefer roll-forward correction and backups tested through restoration. Application rollback must remain compatible with the already-applied schema.

A migration runbook states:

- expected locks and duration;
- compatible application versions;
- preconditions and free-space requirements;
- monitoring and abort thresholds;
- backfill progress and validation queries;
- rollback or roll-forward procedure;
- ownership and communication.

~~~python
def batches(
    identifiers: list[int],
    *,
    size: int,
) -> list[list[int]]:
    if size <= 0:
        raise ValueError("size must be positive")
    return [
        identifiers[start : start + size]
        for start in range(0, len(identifiers), size)
    ]


assert batches([1, 2, 3, 4, 5], size=2) == [
    [1, 2],
    [3, 4],
    [5],
]
~~~

Real backfills should not first load all identifiers as this demonstration does. They page through an indexed stable key and persist progress, with rate control and idempotent updates.

> **Common misconception 18.46 — “Database migrations should always run automatically when an application process starts.”**  
> Concurrent starters, long locks, privilege separation, and failure recovery make migration a controlled deployment operation in many systems.
