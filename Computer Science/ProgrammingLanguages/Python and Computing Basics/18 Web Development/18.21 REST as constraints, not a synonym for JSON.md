# 18.21 REST as constraints, not a synonym for JSON

**Representational State Transfer**, or REST, is an architectural style defined through constraints including client–server separation, stateless interaction, cacheability, uniform interface, layered systems, and optional code transfer. In everyday speech, “REST API” often means an HTTP API exposing resources with JSON. The looser usage should not erase HTTP semantics.

Resource-oriented design gives nouns stable URLs and uses methods for operations:

| Operation | Method and target |
|:---|:---|
| list devices | <code>GET /devices</code> |
| retrieve A17 | <code>GET /devices/A17</code> |
| create under collection | <code>POST /devices</code> |
| replace A17 | <code>PUT /devices/A17</code> |
| partially modify A17 | <code>PATCH /devices/A17</code> |
| remove A17 | <code>DELETE /devices/A17</code> |

This is a convention, not automatic correctness. Actions that do not map cleanly to resource replacement can be represented as subordinate resources, commands, or documented POST operations. A clear domain protocol is better than forced noun grammar.

Collection endpoints need filtering, ordering, pagination, and limits. Offset pagination is simple but can duplicate or skip rows as concurrent changes shift positions. Cursor pagination uses a stable ordering key and opaque continuation value. It still requires a deterministic total order and policy for mutations.

### 18.21.1 Uniform interfaces and hypermedia

REST’s **uniform interface** constrains components to shared resource-identification, representation, message, and hypermedia semantics. It enables generic intermediaries and evolvable clients at the cost of application-specific efficiency. Merely using JSON over HTTP does not satisfy every REST constraint.

A resource is conceptual: “the current device A17” can have representations that change while its identifier remains stable. Representations carry state and links. A client applies methods to resource identifiers rather than invoking an in-process object method.

**Hypermedia as the engine of application state** means a response supplies links or controls indicating available transitions. A client need not construct every URI from undocumented templates. In practice many JSON APIs instead publish out-of-band schemas and fixed path conventions. That can be a valid HTTP API, but the distinction should be named accurately.

Links can have relation types such as <code>self</code>, <code>next</code>, <code>collection</code>, or domain-specific registered/documented relations. A URL is opaque to a client unless the protocol defines its structure. Parsing a database identifier from the last path segment couples the client to current routing.

> **Common misconception 18.47 — “REST means mapping CRUD operations to four HTTP methods.”**  
> CRUD mapping is one design technique. REST is an architectural style involving statelessness, cacheability, uniform interface, layers, resources, representations, and hypermedia constraints.

### 18.21.2 Collection protocols and evolution

A collection endpoint should define:

- filter vocabulary and combination rules;
- stable sort fields and tie-breakers;
- default and maximum page size;
- cursor opacity, lifetime, and tenant binding;
- treatment of insertions, deletions, and updates during traversal;
- field selection or expansion;
- total-count semantics and cost;
- error behaviour for invalid or expired cursors.

Keyset pagination asks for rows after the last ordering tuple. For descending creation time with a unique identifier tie-breaker:

~~~sql
SELECT device_id, created_at, status
FROM device
WHERE
    (created_at, device_id) < (%s, %s)
ORDER BY created_at DESC, device_id DESC
LIMIT %s;
~~~

The cursor can encode the last tuple plus version and scope, then be authenticated to prevent tampering. It should not expose a capability the caller is not authorised to use. Changing sort/filter parameters invalidates the cursor.

API evolution prefers additive compatible changes where possible: clients must ignore documented unknown response fields, while servers can reject unknown request fields under a stricter contract. Removing or changing meaning needs deprecation, telemetry, consumer communication, and a version boundary.

Versioning can use media types, fields, paths, or host names. None removes the need to maintain semantics within a version. Dates such as <code>2026-09-22</code> can label a compatibility profile but should not imply that clients automatically understand later fields.

Generated OpenAPI descriptions can document paths, schemas, authentication, and responses, and can drive clients or validation. They do not prove business invariants, authorisation, concurrency safety, or implementation conformance. Contract tests should exercise the description against running behaviour.

> **Common misconception 18.48 — “Once an API is versioned, breaking changes are harmless.”**  
> Clients still need migration time, old versions need security maintenance and retirement, and shared state must support coexistence. Versioning labels incompatibility; it does not remove its cost.

### 18.21.3 Webhooks are outbound APIs under failure

A **webhook** asks one system to deliver event notifications to an HTTP endpoint controlled by another. Delivery crosses administrative domains and must assume timeout, duplication, reordering, endpoint compromise, and long outages.

The event should have an immutable identifier, type, occurrence time, schema version, producing account, and data or a reference to fetch current state. Consumers deduplicate by event identifier. Events describe facts—<code>invoice.paid</code>—rather than demand implementation-specific actions—<code>send_green_email</code>.

The sender signs a canonical byte representation with a per-consumer secret or asymmetric key. Include a timestamp and reject signatures outside a bounded window to reduce replay. Verify the signature over the raw body before parsing or transforming it. Compare through a constant-time library function.

~~~python
import hashlib
import hmac


def sign_webhook(
    secret: bytes,
    timestamp: int,
    body: bytes,
) -> str:
    message = str(timestamp).encode("ascii") + b"." + body
    return hmac.new(
        secret,
        message,
        hashlib.sha256,
    ).hexdigest()


secret = b"pedagogical-secret-not-for-production"
body = b'{"event_id":"evt_17"}'
signature = sign_webhook(secret, 1_800_000_000, body)
assert hmac.compare_digest(
    signature,
    sign_webhook(secret, 1_800_000_000, body),
)
~~~

Production secrets come from managed random generation and support overlap during rotation. Signature verification establishes possession of a secret and body integrity, not that the event should be accepted for this account; validate tenant and event semantics too.

Return success quickly after durably recording the event, then process asynchronously. If processing completes before acknowledgement and the response is lost, the sender retries. If acknowledgement occurs before durable storage, the event can be lost.

Retry with increasing delay and a finite retention window. Expose delivery logs and manual redelivery without changing event identity. Disable endpoints after sustained failures under a communicated policy. SSRF controls apply when customers configure webhook destinations; do not let a webhook feature become an internal network fetcher.
