# 18.22 GraphQL

GraphQL defines a typed schema and query language through which a client requests a shaped result. A **field resolver** supplies a field value. The client can obtain related data in one protocol request, but the server may execute many underlying database queries unless resolvers batch and prefetch.

~~~graphql
query DeviceWithSite($id: ID!) {
  device(id: $id) {
    id
    status
    site {
      name
    }
  }
}
~~~

The operation declares a variable and requested fields. The response can contain both data and errors for different field paths. HTTP status alone therefore may not encode every application failure.

GraphQL shifts complexity rather than erasing it. Servers need query-depth or complexity limits, authorisation at appropriate field/resource boundaries, batching, caching policy, persisted-query controls, and protection against introspection or error leakage according to threat model. A flexible query language is an execution interface exposed to untrusted clients.

### 18.22.1 Schema and execution

A GraphQL schema defines object, scalar, enum, interface, union, and input types plus root operations. A non-null marker constrains whether a field may return null; if a non-null field fails, null propagates to the nearest nullable parent, potentially removing a larger result subtree.

Execution validates an operation against the schema, coerces variables, selects the operation, and invokes resolvers. Resolvers can return values synchronously or asynchronously under the implementation. Field execution order and mutation serialisation follow specification rules, but a database transaction spanning a mutation must be designed explicitly.

A resolver receives parent value, arguments, execution context, and field information under common implementations. The context can carry the authenticated principal and request-scoped loaders. It must not become a mutable process-global container.

The N+1 problem appears when resolving <code>site</code> for each device performs one query. A request-scoped **data loader** batches keys and caches within that request:

\[
\{1,4,9\}
\longrightarrow
\texttt{SELECT ... WHERE site\_id IN (1,4,9)}.
\]

Results must be returned in the same order as keys, including missing values. Cross-request caching needs separate authorisation and invalidation semantics; a request-local loader is not a general cache.

> **Common misconception 18.49 — “GraphQL executes one database query because the client sends one request.”**  
> Protocol request count and persistence query count are independent. Resolver design can issue one query per field occurrence unless batching and prefetching control it.

### 18.22.2 Authorisation, cost, caching, and subscriptions

Schema visibility does not equal field authority. Authorisation can apply at operation, object, field, and returned-record levels. A resolver for <code>device(id:)</code> must enforce that the principal may access that device, not merely that the field exists. Filtering unauthorised records and rejecting access have different disclosure semantics.

Depth alone poorly estimates cost: a shallow field can request 100,000 records, while a deep lookup can be cheap. Cost analysis includes list bounds, fan-out, resolver weights, fragments, aliases, and recursion. Persisted operations let trusted clients use pre-approved documents, but public clients may still need flexible query support.

HTTP caches struggle when every operation uses POST to one URL. GET for side-effect-free queries, persisted-query hashes, response caches keyed by operation/variables/principal, and resolver caches can help. Every cache must include authorisation context and invalidation.

Subscriptions model server-initiated result updates, commonly over WebSocket or server-sent transport. They require authentication at connection and operation time, reauthorisation when privileges change, bounded per-client subscriptions, disconnect cleanup, event filtering, and delivery semantics. A database event and a pushed notification are not one atomic action.

The errors array can coexist with partial data. Production errors should include stable safe codes while internal logs retain diagnostic causes. Returning exception messages can expose schema, SQL, paths, or secrets.

> **Common misconception 18.50 — “A typed GraphQL schema validates that every requested operation is safe.”**  
> It validates shape and type compatibility. Authorisation, cost limits, side effects, data sensitivity, resolver batching, and error disclosure are separate controls.
