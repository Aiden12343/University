# 18.23 Authentication and authorisation

**Authentication** establishes which principal is making a request under a confidence level. **Authorisation** decides whether that principal may perform an action on a resource. Performing authentication without resource-level authorisation produces insecure direct object access.

A **principal** is an identity recognised by the system: user, service, device, or process. A **credential** is evidence used to authenticate, such as a password, cryptographic key, or token. An **access token** represents delegated authority under scope and lifetime.

Passwords must be stored through a password-hashing function designed to be slow and salted, using an established library and current parameters. General cryptographic hashes such as plain SHA-256 are too fast for password storage. A **salt** is a unique non-secret value combined with each password so identical passwords do not share stored verifiers and precomputed attacks are impeded.

Authentication sessions should consider:

- credential enrolment and recovery;
- multi-factor methods;
- rate limiting and abuse detection;
- session rotation;
- logout and revocation;
- device and risk signals;
- audit trails;
- phishing resistance;
- secret exposure in logs and URLs.

Authorisation should be deny-by-default and checked server-side at the object and operation. Hiding a button in a browser is interface behaviour, not enforcement.

### 18.23.1 Identity proofing, authenticators, and recovery

Authentication is a lifecycle:

1. enrol or proof an identity;
2. bind one or more authenticators;
3. verify an authenticator during login;
4. establish a session at an authentication strength;
5. rotate, revoke, recover, and audit.

A password is one authenticator, not an identity. Password hashing functions such as Argon2id, scrypt, bcrypt, or PBKDF2 deliberately consume time and often memory. Parameters should follow maintained guidance and be upgraded on successful login. A per-password salt is stored with the verifier; an optional server-held **pepper** introduces separate secret management and rotation problems.

Compare verifiers with library functions designed for the format. Apply rate controls by account and broader source signals without creating an easy account-lockout denial of service. Error messages can avoid confirming account existence, while monitoring retains internal distinctions.

Multi-factor authentication combines independent factor categories—knowledge, possession, inherence—not merely two passwords. Phishing-resistant public-key authenticators bind assertions to an origin. WebAuthn/passkeys can reduce password and phishing risk, but account recovery can become the weakest authenticator and must meet comparable assurance.

Recovery tokens are single-use, short-lived, securely generated, and stored as verifiers where practical. Changing credentials should revoke or review active sessions, notify the user through an independent channel, and protect against session theft.

> **Common misconception 18.51 — “A password hash can be encrypted later if stronger protection is needed.”**  
> Password verification should use a purpose-built slow salted derivation from the start. Encryption is reversible and creates a decryption-key target; parameter upgrades usually occur on subsequent successful authentication.

### 18.23.2 OAuth 2.0 and OpenID Connect roles

OAuth 2.0 is an authorisation framework for delegated access. Roles include resource owner, client, authorisation server, and resource server. An access token is presented to a resource server; its exact format can be opaque or self-contained.

OpenID Connect adds an identity layer. An **ID token** communicates authentication claims to the client and is not a generic API access token. Accepting an ID token at an unrelated resource server confuses audience and purpose.

The authorisation-code flow with Proof Key for Code Exchange (PKCE) protects public clients from intercepted codes. The client creates a high-entropy verifier, sends a derived challenge in the authorisation request, and proves possession during token exchange. Redirect URIs require exact registered comparison under protocol rules; loose prefix matching enables token theft.

State and nonce values address different correlations and replay threats. Tokens require validation of issuer, audience, signature/algorithm, expiry, not-before rules, and protocol-specific nonce or authorised-party claims. Fetch current keys from authenticated issuer metadata under bounded caching and rotation policy.

Scopes describe delegated authority coarsely; possession of <code>devices:read</code> does not prove access to every device. The resource server still enforces tenant and object policy. Refresh tokens are high-value long-lived credentials and need rotation, sender constraint where appropriate, revocation, and secure client storage.

> **Common misconception 18.52 — “OAuth authenticates users and JWT is the protocol.”**  
> OAuth delegates access, OpenID Connect adds authentication, and JWT is one token representation. Each token must be validated for its specified issuer, audience, purpose, and flow.

### 18.23.3 Authorisation models and object checks

Role-based access control (RBAC) assigns permissions through roles. Attribute-based control (ABAC) evaluates principal, resource, action, and environment attributes. Relationship-based control (ReBAC) reasons over relations such as owner, member, or parent organisation. Real systems combine them.

A policy can be expressed as

\[
\operatorname{allow}(p,a,r,c)
\]

for principal \(p\), action \(a\), resource \(r\), and context \(c\). The decision must use authoritative current attributes and fail closed when dependencies are unavailable under the risk policy.

Object-level authorisation is easiest when incorporated into the query:

~~~sql
SELECT device_id, status
FROM device
WHERE device_id = %s
  AND tenant_id = %s;
~~~

Returning no row can map to 404 without disclosing existence outside the tenant. Loading by identifier first and checking later creates opportunities for accidental use, logging, timing differences, or a forgotten check.

Central policy engines improve consistency but add availability, caching, versioning, and explanation concerns. Cached allow decisions can outlive revocation. Policy tests should cover every operation, relationship, tenant boundary, administrator exception, and default.

Administrative and support impersonation need explicit purpose, approval, short duration, visible indication, immutable audit, and prohibited actions—not a hidden “login as anyone” endpoint.

> **Common misconception 18.53 — “Authorisation is complete once a route checks the user’s role.”**  
> Permission depends on action and resource, often tenant, relationship, state, and context. Route-level roles rarely express object ownership or field-level disclosure.

### 18.23.4 Secrets and cryptographic key management

Applications use database passwords, API keys, session-signing keys, TLS private keys, webhook secrets, and data-encryption keys. Their value lies in authority, so secret management covers generation, distribution, in-memory exposure, use, rotation, revocation, audit, and destruction.

Do not commit secrets to source control. Removing the line from the latest commit does not remove history or clones; revoke the credential and rewrite history only as an additional containment step. Secret-scanning hooks and repository scanning reduce accidental inclusion but do not replace review.

Workload identity can let a platform issue short-lived credentials to an authenticated service instance, avoiding static cloud keys. The service exchanges identity for scoped authority under policy. Compromise remains possible during the credential lifetime, so minimise scope and log use.

Envelope encryption uses a data-encryption key for content and wraps that key under a key-encryption key managed by a dedicated service. Rotating the wrapping key can rewrap data keys without re-encrypting every data object; rotating compromised data keys may require re-encryption. Key identifiers and algorithms travel with ciphertext under an authenticated format.

Cryptographic messages need version, algorithm policy, key identifier, nonce, ciphertext, and authentication tag as appropriate. Never select an algorithm directly from untrusted input without an allowlist. Authenticated encryption rejects modified ciphertext before plaintext is used.

Key rotation requires an overlap:

1. publish or deploy the new verification/decryption key;
2. begin issuing or encrypting with the new primary;
3. continue accepting old material for its maximum legitimate lifetime;
4. stop accepting the old key;
5. destroy or archive it under recovery policy.

Immediate removal can invalidate every session or webhook in flight; endless retention makes revocation meaningless. Emergency compromise rotation follows a shorter and more disruptive plan.

Application logs should record key identifiers and operation outcomes, never secret values or plaintext. Error messages must not distinguish cryptographic failure modes in ways that create an oracle. Use maintained high-level libraries; custom cryptographic protocols require specialist review.
