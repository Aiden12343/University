# 18.24 Cross-site scripting and output contexts

**Cross-site scripting**, or XSS, occurs when attacker-controlled content is interpreted as executable active content in another user’s browser. The primary defence is context-appropriate output encoding through a trusted template system. HTML text, HTML attribute, JavaScript, CSS, and URL contexts have different grammars; one escaping function cannot safely serve all.

~~~html
<p>{{ display_name }}</p>
~~~

In a template engine with automatic HTML escaping, text such as <code>&lt;script&gt;</code> is represented as text rather than parsed as an element. Marking untrusted content “safe” disables this boundary. Rich user-authored HTML requires a maintained allowlist sanitizer, not regular expressions.

A **Content Security Policy**, or CSP, can restrict permitted script and resource origins and reduce impact. It is a defence in depth, not a substitute for correct encoding. DOM APIs that parse strings as HTML must not receive untrusted text where text-only APIs suffice.

### 18.24.1 Stored, reflected, and DOM-based execution

In **stored XSS**, attacker content is persisted and later rendered to victims. In **reflected XSS**, request content is returned in an unsafe response. **DOM-based XSS** arises when client-side code moves attacker-controlled data into an executable browser sink without necessarily involving unsafe server rendering.

Sources include URL fragments, query parameters, cross-window messages, storage, API responses, and element attributes. Sinks include <code>innerHTML</code>, script construction, unsafe URL assignment, event-handler attributes, and dynamic code evaluation. Data that was safe as JSON becomes unsafe when inserted into HTML without context handling.

Output encoding transforms data for one grammar:

| Context | Required strategy |
|:---|:---|
| HTML text | HTML entity encoding by a trusted template engine |
| quoted HTML attribute | attribute encoding plus controlled attribute name |
| URL component | component percent-encoding plus scheme/origin policy |
| JavaScript data | safe JSON serialisation in a supported embedding pattern |
| CSS | avoid dynamic untrusted syntax; use constrained properties/APIs |
| rich HTML | maintained allowlist sanitisation |

Encoding too early creates double encoding and loses context. Store canonical content; encode at the final output boundary. Sanitised rich HTML needs re-sanitisation when policy/library changes if old stored output remains trusted.

> **Common misconception 18.54 — “Escaping angle brackets prevents XSS.”**  
> Browser execution can arise in attributes, URLs, scripts, styles, SVG, and DOM sinks. Encoding must match the exact parser context, and rich markup requires sanitisation.

### 18.24.2 CSP, nonces, and safer DOM construction

A strict CSP can permit scripts carrying a per-response unpredictable nonce and disallow inline event handlers and unapproved origins. Every legitimate script element receives the nonce from the server; attacker-injected markup lacks it. Reusing a fixed nonce destroys the distinction.

Hashes can authorise fixed inline script content. <code>strict-dynamic</code> changes how trust propagates from authorised scripts in supporting browsers. Report-only policy collects violations before enforcement, but reports contain URLs and can be noisy or attacker-controlled.

<code>script-src 'self'</code> is weak if the same origin serves attacker-uploaded JavaScript, JSONP, or vulnerable script gadgets. CSP source lists are capabilities, not a branding statement about trusted companies.

Client code should prefer <code>textContent</code>, <code>createElement</code>, property assignment, and framework text interpolation. Trusted Types in supporting browsers can require sensitive DOM sinks to receive values created by approved policies, reducing accidental string injection. It is a guardrail, not automatic sanitisation.

Cookies marked HttpOnly can remain unreadable to injected script, but the script can issue same-origin actions and read DOM/API responses under the active session. XSS frequently subsumes CSRF.

> **Common misconception 18.55 — “A strong CSP makes output encoding optional.”**  
> CSP limits execution pathways and impact. Correct context encoding and safe DOM APIs prevent attacker data from becoming executable in the first place.
