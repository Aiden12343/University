# 18.25 Cross-site request forgery

**Cross-site request forgery**, or CSRF, exploits automatic browser credential attachment. An attacker causes a victim’s browser to send a state-changing request to a site where the victim is authenticated. The server sees a valid session cookie unless it verifies that the request originated from an authorised interaction.

Defences include:

- unpredictable CSRF tokens bound to session or request context;
- <code>SameSite</code> cookie policy;
- origin or referer validation where appropriate;
- requiring non-simple custom headers for APIs under a controlled origin;
- never using safe methods for state change.

CORS, the browser’s **Cross-Origin Resource Sharing** mechanism, is not a general CSRF defence. It governs whether browser scripts may read or issue certain cross-origin requests; some requests can still be sent without readable responses.

### 18.25.1 Why the browser sends the credential

Browsers attach matching cookies according to domain, path, security, SameSite, and request context. A malicious origin can submit an HTML form or trigger certain requests without reading the response. The target server sees the victim’s cookie unless it requires evidence unavailable to the attacker.

A synchroniser-token pattern stores an unpredictable token in the server session and embeds it in legitimate forms. The submitted value must match the session. A double-submit pattern sends a token in both cookie and request value and validates their relation, preferably with cryptographic binding to session context. Token values must not enter URLs where history and referrers expose them.

Origin checking validates the <code>Origin</code> field for state-changing requests and can fall back under a documented policy when absent. Referer checking can help but carries privacy and intermediary considerations. Host and forwarded-host validation prevents comparison against an attacker-injected expected origin.

SameSite substantially reduces common CSRF paths, but browser compatibility, subdomain trust, same-site cross-origin requests, top-level navigation exceptions, and required cross-site integrations remain. Sensitive operations can require recent reauthentication or transaction-specific confirmation.

> **Common misconception 18.56 — “POST requests are protected from CSRF because links use GET.”**  
> Attackers can submit cross-origin forms and trigger other credentialed requests. Method choice preserves semantics but is not proof of legitimate origin.

### 18.25.2 APIs, CORS, and login CSRF

An API using an <code>Authorization</code> bearer token that malicious origins cannot obtain or cause the browser to attach automatically has a different CSRF exposure from cookie authentication. If the token is in a cookie, or the client also accepts cookies, CSRF returns.

A custom request field often forces a CORS preflight, letting the server allow only trusted origins. The server must not reflect arbitrary origins while permitting credentials. <code>Access-Control-Allow-Origin: *</code> cannot be combined with credentialed browser access under ordinary rules, and CORS never authenticates non-browser clients.

**Login CSRF** forces a victim’s browser into a session controlled by the attacker. The victim may then enter private data into the attacker’s account. Login endpoints therefore need request-origin protection and new session identifiers, not only post-login forms.

CSRF tokens should be scoped and compared in constant-time where secrets are involved through library support. Rotate at suitable lifecycle points without invalidating every concurrent form unnecessarily. Error responses should not echo tokens.

> **Common misconception 18.57 — “CORS is a server firewall that blocks requests from unapproved origins.”**  
> CORS instructs supporting browsers which cross-origin responses scripts may read and which non-simple requests may proceed. Direct clients and many simple requests are outside that promise.
