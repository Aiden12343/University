# 18.26 Server-side request forgery

**Server-side request forgery**, or SSRF, occurs when an attacker influences a server to make requests to unintended destinations, potentially reaching internal services, cloud metadata, or privileged networks.

Validating that a URL begins with an allowed string is inadequate. Parsing, redirects, DNS changes, alternative address forms, user information, and scheme confusion can bypass textual checks. A robust design avoids arbitrary destinations, uses explicit allowlists, resolves and validates every connection target under policy, limits schemes and ports, revalidates redirects, constrains egress at the network layer, and applies time/size limits.

This problem demonstrates why URL parsing is not authorisation. A syntactically valid URL can designate a forbidden capability.

### 18.26.1 Resolution, redirects, and rebinding

An SSRF defence that validates a hostname and then lets another component resolve it can suffer **time-of-check/time-of-use** change. DNS rebinding can return a permitted public address during validation and an internal address during connection. Resolve under controlled policy, validate every returned candidate, and ensure the connection uses a validated address while preserving correct TLS host verification.

Blocked ranges include loopback, link-local, private, multicast, unspecified, documentation, and environment-specific service networks for both IPv4 and IPv6. IPv4-mapped IPv6 and unusual textual forms must normalise through an IP-address library rather than a regular expression.

Every redirect is a new destination decision. Disable redirects or validate scheme, host, port, and resolved addresses at each hop with a low maximum. Authentication fields and sensitive headers should not be forwarded to a different origin.

Cloud instance metadata services are high-value internal targets. Provider-specific protections such as session-oriented metadata tokens reduce exposure but do not authorise arbitrary server fetches. Network egress rules should prevent workloads from reaching capabilities they do not need.

> **Common misconception 18.58 — “Blocking <code>127.0.0.1</code> prevents SSRF to local services.”**  
> Loopback has many textual and IPv6 forms, and internal targets include private, link-local, metadata, service-discovery, and redirected addresses. Normalised resolution and egress policy are required.

### 18.26.2 Capability-oriented outbound design

The safest fetcher does not accept an arbitrary URL. It accepts a constrained identifier—such as an image ID—and the server constructs a destination from controlled configuration. If user-selected hosts are essential, onboard and verify them separately rather than accept them per request.

An outbound proxy can enforce DNS, address, scheme, port, identity, and logging policy centrally. Network namespaces and firewall rules provide another boundary if application validation fails. The fetcher should:

- use GET or another fixed method;
- omit ambient internal credentials;
- set an independent connect timeout and total deadline;
- cap redirect count and response bytes;
- restrict decompression expansion;
- restrict media types where applicable;
- stream to bounded storage;
- avoid returning internal error detail;
- limit concurrency and per-principal rate.

Blind SSRF may return no body but still perform state-changing internal requests or reveal reachability through timing. Do not assume response suppression removes impact.

~~~python
import ipaddress


def public_unicast(address: str) -> bool:
    value = ipaddress.ip_address(address)
    return value.is_global


assert not public_unicast("127.0.0.1")
assert not public_unicast("169.254.169.254")
assert not public_unicast("::1")
~~~

<code>is_global</code> follows Python’s address classification and can change as registries and standards evolve. Production policy may be stricter and should be tested against all supported Python versions; classification alone still does not bind validation to the connection.

> **Common misconception 18.59 — “SSRF matters only when the response body is returned to the attacker.”**  
> A server can perform privileged state changes, scan reachability, trigger side effects, or leak information through timing without returning content.
