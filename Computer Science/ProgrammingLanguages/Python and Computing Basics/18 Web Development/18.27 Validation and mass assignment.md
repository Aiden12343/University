# 18.27 Validation and mass assignment

Request validation has levels:

1. framing and size;
2. media type and decoding;
3. syntactic structure;
4. field types and ranges;
5. cross-field invariants;
6. authorisation for requested state transition;
7. database constraints.

A **mass-assignment** vulnerability occurs when a framework binds every supplied field to an object, including fields the client must not control, such as <code>is_admin</code> or <code>owner_id</code>. Define an explicit input schema and construct authorised fields individually.

Unknown fields require policy. Rejecting them catches mistakes and reduces attack surface. Ignoring them supports some forward compatibility but can conceal a misspelled security-relevant field. Document the choice per endpoint.

### 18.27.1 Validation does not grant authority

Syntactic validation answers whether input has an accepted form. Semantic validation answers whether values satisfy domain rules. Authorisation answers whether this principal may request this transition. A valid positive integer <code>owner_id</code> is still forbidden if ownership is server-assigned.

Use separate input, domain, persistence, and output models where their fields differ. Reusing an ORM model as a request schema tends to expose internal flags and server-managed columns. Reusing a response model as input can let clients set computed or confidential fields.

Patch semantics need special care. Missing can mean “leave unchanged”; explicit null can mean “clear”; a value can mean “replace.” Truthiness checks collapse zero, false, empty text, and absence. Use a sentinel or schema representation that preserves the distinction.

~~~python
from dataclasses import dataclass
from typing import Final

MISSING: Final = object()


@dataclass(frozen=True)
class DevicePatch:
    status: object = MISSING
    label: object = MISSING


patch = DevicePatch(status="retired")
assert patch.status == "retired"
assert patch.label is MISSING
~~~

A production schema would narrow types after parsing and reject unknown fields. The sentinel demonstrates three-state logic without confusing absent with <code>None</code>.

> **Common misconception 18.60 — “If a field passes schema validation, it is safe to write.”**  
> Validation establishes form and selected invariants. Authority, current state, concurrency, and server-managed ownership still govern whether the transition is allowed.

### 18.27.2 Files, parsers, and resource limits

File uploads are hostile byte streams. A client-provided filename is display metadata, not a path. Generate storage names, retain the original only after normalisation for presentation, and prevent traversal. Check:

- total and per-file size before and during streaming;
- file count and multipart field limits;
- actual format through a maintained parser, not extension alone;
- decompressed and decoded dimensions;
- archive entry count, paths, expansion ratio, and nested depth;
- malware or content policy under the threat model;
- storage quota and lifecycle;
- authorisation on later retrieval.

Image and document parsers are complex native attack surfaces; isolate processing with reduced privilege and resource limits. Re-encoding through a trusted library can remove active metadata but is not proof against library vulnerabilities.

Deserialising pickle from a request can execute code and is never a data-validation problem. Use constrained formats and explicit schemas. XML, YAML, template, and archive libraries need safe modes that disable external entities, arbitrary object construction, or path extraction.

Regular expressions can exhibit catastrophic backtracking on adversarial input. JSON nesting, integer length, Unicode normalisation, and collection counts can also consume disproportionate CPU or memory. Validation must impose structural limits before expensive work.

Mass assignment appears beyond ORM objects: configuration updates, cloud SDK calls, serializer model binding, and dataclass unpacking can expose new fields automatically after an application upgrade. Explicit allowlists keep the external contract stable.

> **Common misconception 18.61 — “Checking a file extension and MIME header validates an upload.”**  
> Both are attacker-controlled declarations. Safe handling requires bounded parsing, format verification, generated storage paths, isolation, and authorised retrieval.
