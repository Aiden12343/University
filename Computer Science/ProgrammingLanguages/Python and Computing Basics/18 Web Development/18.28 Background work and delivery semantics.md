# 18.28 Background work and delivery semantics

HTTP request handlers should not hold a connection open for every long operation. A **job queue** stores work descriptions for background workers. Enqueuing and processing occur in separate failure domains.

Delivery is commonly **at least once**: a job can be delivered again if a worker completes the side effect but fails before acknowledging. Handlers must be **idempotent** or deduplicate by operation identity. “Exactly once” requires a defined boundary and coordination; it is not obtained by naming a queue option.

Suppose creating an order must enqueue an email. Committing the database row and publishing a queue message separately permits two failures: row committed but no message, or message published but row rolled back. The **transactional outbox** pattern writes the domain change and an outbox record in one database transaction; a relay later publishes unprocessed outbox records with idempotent handling.

Background jobs carry authorisation context carefully. A worker should receive the minimum identifiers and re-evaluate relevant current authority rather than trust a mutable client-supplied role.

### 18.28.1 Job state and acknowledgement

A queue message is not the job’s complete state. A robust job record can contain:

- immutable job identifier and operation key;
- principal or tenant scope;
- payload schema and version;
- creation, availability, start, and completion times;
- attempt count and maximum;
- current state and lease owner;
- result or safe error code;
- trace and causation identifiers.

A broker may hide a delivered message for a **visibility timeout**. If the worker does not acknowledge before expiry, another worker can receive it. The timeout must exceed ordinary processing or be renewed through a lease; a crashed worker must eventually release it.

Acknowledging before the side effect risks lost work. Acknowledging after the side effect risks duplicate work. At-least-once delivery chooses the latter and requires idempotency. At-most-once delivery can lose work. “Exactly once” is meaningful only for a named state transition under one coordination boundary.

> **Common misconception 18.62 — “A queue guarantees that each job runs exactly once.”**  
> Brokers coordinate delivery and acknowledgement under failure. Workers can crash at any boundary, so durable effects need idempotency, deduplication, or transactional integration.

### 18.28.2 Outbox, inbox, retries, and dead letters

An outbox table can be written in the same transaction as domain state:

~~~sql
INSERT INTO purchase (purchase_id, status)
VALUES (%s, 'accepted');

INSERT INTO outbox (
    event_id,
    event_type,
    aggregate_id,
    payload,
    created_at
)
VALUES (%s, 'purchase.accepted', %s, %s, CURRENT_TIMESTAMP);
~~~

A relay claims unpublished rows in bounded batches, publishes, and marks progress. If marking fails after publish, it publishes again. Consumers use the immutable <code>event_id</code> in an inbox or idempotent state transition.

Retry classification distinguishes transient dependency failure, rate policy, permanent invalid input, cancelled work, and unknown defects. Immediate repeated attempts against a permanent error waste capacity. Exponential delay with jitter and a maximum attempt/deadline moves exhausted jobs to a **dead-letter** state for inspection or controlled replay.

Dead letters are not a rubbish bin. They require alerts, ownership, data-retention rules, privacy controls, replay tooling, and an explanation of whether the domain operation remains pending. Replaying after code changes must preserve the original payload schema or migrate it explicitly.

Scheduled work needs a time-zone and misfire policy. “Every day at 02:30 Europe/London” encounters daylight-saving gaps and repetitions; “every 24 hours after completion” has different semantics. A scheduler firing twice must not duplicate the logical action.

Long workflows should persist state transitions rather than hold one worker or database transaction. A state machine makes waiting, compensation, timeout, and manual intervention observable.

> **Common misconception 18.63 — “Moving work to a background queue removes it from the user-facing reliability contract.”**  
> It changes when and where work occurs. Users still need acknowledgement semantics, status, deadlines, cancellation, failure recovery, and durable results.
