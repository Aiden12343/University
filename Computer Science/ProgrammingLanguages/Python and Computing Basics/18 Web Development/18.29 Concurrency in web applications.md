# 18.29 Concurrency in web applications

A server can use:

- multiple processes for isolation and CPU parallelism;
- threads for concurrent blocking work;
- an event loop for many awaiting operations;
- combinations of these.

Global mutable Python objects are not a reliable shared state store. Threads can race within one process; processes do not ordinarily share heaps; hosts do not share memory. Durable or coordinated state belongs in a system designed for it, such as a transactional database, cache with explicit semantics, or message broker.

Every outbound dependency needs deadlines. A **timeout** bounds one operation or phase; a **deadline** bounds remaining time for the whole request. Nested services that each wait their full timeout can amplify latency. Propagating a deadline lets deeper calls decline work that can no longer complete usefully.

Unbounded concurrency converts slow dependencies into resource exhaustion. Servers impose connection limits, queue bounds, body-size limits, worker counts, and load shedding. Backpressure tells producers to slow or refuses excess work rather than accumulating an unlimited queue.

### 18.29.1 Worker models and the GIL

A pre-fork server runs several worker processes. Process isolation contains crashes and uses multiple CPU cores, but each process has its own heap, connection pools, caches, and startup cost. Too many workers multiply database connections and memory.

Threaded workers share a process heap. Blocking I/O can overlap, while Python bytecode execution is constrained by the CPython GIL described in Chapter 14. Native code can release the GIL. Shared mutable state requires synchronisation even if a single bytecode operation appears atomic, because application invariants span operations and interpreter details change.

Async workers multiplex tasks on an event loop. They excel when handlers spend substantial time awaiting non-blocking dependencies. One blocking call or CPU loop stalls the loop. Per-request task creation must be structured so child tasks are cancelled and awaited rather than leaked after a response.

Worker count follows measured service time, memory, CPU, downstream connection limits, and latency objectives. The database may be the bottleneck long before application CPU. A connection pool of 20 in each of 20 processes demands up to 400 database sessions.

> **Common misconception 18.64 — “More application workers always increase throughput.”**  
> Workers compete for CPU, memory, locks, database connections, and downstream capacity. Beyond saturation they increase queues, context switching, and tail latency.

### 18.29.2 Deadlines, overload, and fairness

Each request starts with a finite budget. Outbound calls should receive the remaining deadline, not an independent large timeout. Distinguish:

- connection timeout;
- TLS handshake timeout;
- response-header timeout;
- idle read/write timeout;
- total call deadline;
- application request deadline.

A timeout releases the caller’s wait but may not cancel remote work. Retrying can leave several copies executing. Cancellation propagation and idempotency reduce waste, while servers should stop expensive work when the result can no longer be delivered if safe.

At saturation, an unbounded queue converts overload into enormous latency and memory use. A bounded queue rejects excess work promptly, allowing clients or upstream systems to shed or retry under policy. Admission can reserve capacity by operation or tenant so cheap health checks and critical actions are not starved by expensive reports.

Concurrency limits should exist per process, per dependency, per principal, and globally where appropriate. A semaphore around an outbound service creates a bulkhead, but waiting for the semaphore consumes request budget. Return overload before the deadline is exhausted.

Rate limits govern arrivals over time; concurrency limits govern simultaneous work; quotas govern cumulative consumption. Token-bucket and leaky-bucket algorithms express bursts differently. Distributed exact counters can become a bottleneck, so approximate or partitioned enforcement requires a stated overshoot policy.

> **Common misconception 18.65 — “A timeout makes a slow operation safe.”**  
> It bounds one wait. The remote operation, retries, partial side effects, occupied workers, and accumulated queues require cancellation, deadlines, idempotency, and capacity controls.
