# 18.3 Addresses, ports, and names

An **IP address** identifies a network interface or endpoint under Internet Protocol routing. IPv4 addresses contain 32 bits; IPv6 addresses contain 128 bits. Human-readable forms are representations of those bits. Addresses can change, be shared through translation, or identify an intermediary rather than one enduring machine.

A **port number** is a transport-layer integer used with an address and protocol to direct traffic to an application endpoint. A server **listens** on a local address and port; the operating-system kernel associates incoming connection traffic with a socket.

A **socket** is an operating-system abstraction for a communication endpoint. Python socket objects wrap kernel resources and must be closed. A TCP connection is identified by endpoint information at both sides, so many clients can connect to one listening server port.

The **Domain Name System**, or DNS, is a distributed naming system. A domain name such as <code>example.org</code> can be resolved through records to addresses and other information. DNS is not a universal permanent map from one name to one machine. Responses can contain multiple addresses, be cached for a time-to-live, differ by location, or change during operation.

### Worked example 18.1 — Resolve without assuming one address

~~~python
import socket

results = socket.getaddrinfo(
    "example.org",
    443,
    type=socket.SOCK_STREAM,
)

for family, socket_type, protocol, canonical_name, address in results:
    print(family, socket_type, protocol, address)
~~~

<code>getaddrinfo</code> asks the platform resolver for usable endpoint candidates. Each result includes address family, socket type, protocol, and an address structure. Code that selects only the first result without fallback can fail on a multi-address service. The call can block and can fail through DNS, local configuration, or network conditions; production code needs timeouts at the layer that performs it.

### 18.3.1 Address scope, binding, and translation

IPv4 and IPv6 addresses have scope. Loopback addresses refer to the local host; link-local addresses are valid only on a link; private IPv4 ranges are not globally routed; globally scoped addresses can be routed according to network policy. None of these properties is an authentication decision. A request appearing to originate from a private address can have traversed a proxy, and an attacker who reaches an internal network remains an attacker.

When a server binds to <code>127.0.0.1</code>, only local IPv4 connections ordinarily reach it. Binding to <code>0.0.0.0</code> means all configured IPv4 interfaces; it is not a destination clients should use. IPv6 <code>::</code> is the corresponding unspecified bind address, with dual-stack behaviour dependent on operating-system configuration.

Network address translation, or **NAT**, rewrites addressing information at a boundary and maintains mapping state. Many private clients can share one public address. Consequently, an IP address is neither a durable user identifier nor proof that requests come from one device. Rate limits based only on source address can punish shared networks and remain bypassable.

The kernel identifies a TCP connection by protocol plus local and remote address/port pairs. A listening socket can accept many connections on one local port because each accepted connection has a different peer tuple. The server process receives a new connected socket; the listening socket remains available for subsequent arrivals.

> **Common misconception 18.5 — “An IP address identifies one computer or user.”**  
> Addresses can be shared, translated, reassigned, proxied, multihomed, or privacy-rotated. They identify routing endpoints under a time and network context, not enduring persons.

### 18.3.2 DNS is a cached distributed database

DNS stores typed records in a hierarchy of zones. Important record types include:

| Record | Purpose |
|:---|:---|
| A | maps a name to an IPv4 address |
| AAAA | maps a name to an IPv6 address |
| CNAME | aliases one name to another canonical name under restrictions |
| MX | identifies mail exchangers |
| TXT | carries application-defined text, including verification and mail policy |
| NS | delegates a zone to authoritative name servers |
| SOA | carries zone authority and timing metadata |
| CAA | constrains certificate-authority issuance policy |

A recursive resolver follows referrals and caches answers. An authoritative server answers for a zone. A stub resolver in the application or operating system asks a recursive resolver. These roles can be combined by software but have distinct trust and caching semantics.

A record’s **time to live** (TTL) tells caches how long it may ordinarily be reused. TTL does not guarantee that every client observes a change after exactly that period: earlier caches, local policy, connection reuse, application caching, and clock behaviour intervene. Negative answers can also be cached.

Clients should attempt suitable address candidates with bounded fallback rather than assume IPv4, IPv6, or answer order. “Happy Eyeballs” algorithms stagger connection attempts to avoid waiting on a broken family while preferring modern connectivity. Application code should usually rely on maintained connection libraries rather than reimplement that scheduling.

DNS Security Extensions authenticate signed DNS data under a chain of trust; they do not encrypt ordinary DNS queries and do not replace TLS identity validation. Encrypted DNS transports protect a query on part of its path but move trust to the selected resolver.

> **Common misconception 18.6 — “Changing a DNS record immediately moves all traffic.”**  
> Cached answers, connection pools, resolver policy, negative caching, and gradual client behaviour create an interval of coexistence. Migrations must support both old and new destinations.
