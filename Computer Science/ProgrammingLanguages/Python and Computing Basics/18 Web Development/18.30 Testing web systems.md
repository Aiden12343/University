# 18.30 Testing web systems

Tests occupy layers:

- pure domain-function unit tests;
- request tests through framework test clients;
- database integration tests against the supported engine;
- contract tests between services;
- browser tests for critical user journeys;
- load and fault tests;
- security tests derived from a threat model.

### Worked example 18.5 — Flask request tests

~~~python
import pytest

from application import create_app


@pytest.fixture
def client():
    app = create_app({"TESTING": True})
    return app.test_client()


def test_unknown_device_returns_structured_404(client):
    response = client.get("/devices/missing")

    assert response.status_code == 404
    assert response.content_type == "application/json"
    assert response.get_json()["error"]["code"] == (
        "device_not_found"
    )


def test_create_rejects_empty_identifier(client):
    response = client.post(
        "/devices",
        json={"device_id": ""},
    )

    assert response.status_code == 422
~~~

The tests assert protocol contract, not internal function calls. They still run in process and do not test the production server, TLS termination, proxy headers, network timeouts, or database engine. Integration tests add those boundaries selectively.

Database tests must isolate transactions without creating a false environment. SQLite can differ from PostgreSQL in typing, locking, SQL, constraints, and concurrency. Use the production database family for behaviours on which correctness depends.

### 18.30.1 Test contracts rather than implementation accidents

A unit test exercises a small deterministic rule without network or database. An integration test crosses real boundaries. A contract test verifies the assumptions between independently changing components. An end-to-end test exercises a user-visible path through deployed-like infrastructure. These categories describe evidence, not prestige; a healthy suite uses each where its information exceeds its cost.

Request tests should assert:

- method and path behaviour;
- status and representation media type;
- schema including required, optional, and unknown fields;
- authentication and object authorisation;
- cache and precondition fields;
- idempotency and repeated requests;
- limits and malformed bodies;
- transactional rollback;
- safe error disclosure.

Avoid assertions on unstable incidental text, database-generated identifiers, or field order unless they are contractual. Snapshot tests can reveal broad changes but require review; blindly accepting a new snapshot converts a test into stored output.

Property-based tests generate cases from invariants. A URL normaliser might be tested for idempotence, a pagination cursor for authenticated round trip, and a transfer for preservation of total balance. Stateful property tests can explore sequences that example tests miss.

~~~python
from dataclasses import dataclass


@dataclass
class Account:
    balance: int


def move(source: Account, destination: Account, amount: int) -> None:
    if amount <= 0 or source.balance < amount:
        raise ValueError
    source.balance -= amount
    destination.balance += amount


left = Account(80)
right = Account(20)
before = left.balance + right.balance
move(left, right, 30)
assert left.balance + right.balance == before
assert min(left.balance, right.balance) >= 0
~~~

The property holds in one process but says nothing about concurrent database transactions. Integration tests must reproduce overlapping schedules against the supported DBMS.

> **Common misconception 18.66 — “A high line-coverage percentage means a web service is well tested.”**  
> Coverage records execution, not assertion quality, concurrency schedules, protocol boundaries, security cases, failure modes, or production correspondence.

### 18.30.2 Deterministic dependencies, faults, and performance

Mocks isolate code but can faithfully reproduce the developer’s misunderstanding. Prefer small fakes implementing an explicit contract and integration tests against the real dependency. Consumer-driven contracts can detect incompatible provider changes but do not replace provider correctness or end-to-end authorisation tests.

Time, randomness, and identifiers should enter through controllable interfaces. Freezing wall time without modelling monotonic deadlines can conceal bugs. Test clock jumps, expiry boundaries, daylight-saving transitions, and token rotation overlap.

Fault injection should cover:

- connection refusal and DNS failure;
- timeout before and after a committed side effect;
- truncated and malformed upstream responses;
- database deadlock and serialisation retry;
- queue redelivery;
- disk or quota exhaustion;
- process termination during graceful shutdown;
- stale cache and partial deployment.

Load tests need a realistic arrival process, data cardinality, think time, connection reuse, payload sizes, and warmed/cold states. Coordinated omission occurs when a generator waits during a slow response and therefore fails to send requests that would have arrived; latency looks better than the real open system.

Security testing derives from the threat model: dependency scanning, static analysis, dynamic tests, fuzzing parsers, authorisation matrices, secret scanning, and manual review. A scanner finding nothing is not proof of absence.

> **Common misconception 18.67 — “Mocking every dependency makes tests reliable.”**  
> It makes them deterministic relative to mock behaviour. Real protocol, database, encoding, concurrency, and deployment mismatches require integration and system evidence.
