# 18.31 Deployment topology

A typical deployment can contain:

1. DNS naming;
2. a load balancer or reverse proxy terminating TLS;
3. multiple application instances;
4. a database and cache;
5. a job broker and workers;
6. object storage;
7. telemetry collectors.

A **reverse proxy** accepts client requests and forwards them to upstream services. It can terminate TLS, enforce limits, normalise forwarding information, buffer bodies, and balance load. The application must trust forwarded client-address and scheme headers only from configured proxies; otherwise a client can spoof them.

Application instances should be replaceable. Configuration enters through a controlled mechanism; secrets do not belong in source control or container images. Startup should validate essential configuration. A **health check** should distinguish whether a process is alive from whether it is ready to receive traffic. Readiness can fail during startup or controlled draining without forcing a destructive restart.

Graceful shutdown stops accepting new requests, allows bounded in-flight work to complete, and closes resources. Deployment systems must allow enough termination time.

### 18.31.1 Processes, images, and immutable releases

A production server binds sockets or receives them from a supervisor, starts bounded workers, imports an application factory, and manages signals. Running a framework development server omits hardened limits, worker supervision, and controlled lifecycle.

A container packages a filesystem and process configuration; it does not provide a virtual machine security boundary by itself. Run as a non-root user, use a minimal maintained base, remove build credentials and tools from the runtime image, set a read-only filesystem where possible, and declare writable temporary locations.

Build one immutable artifact and promote it through environments. Rebuilding for production can resolve different dependencies despite the same source revision. Configuration selects environment-specific endpoints and policy without modifying bytes. Record source commit, dependency lock, image digest, migration set, and build provenance.

Secrets enter through a dedicated mechanism with access control, audit, rotation, and short lifetime. Environment variables are convenient but can leak through process inspection, crash reports, or diagnostics; mounted secret files and workload identity have different trade-offs. Never bake secrets into images.

Static assets are fingerprinted by content, served with long immutable caching, and referenced by the corresponding application release. Upload assets before code that references them and retain older assets while old pages remain cached. A CDN is an untrusted or semi-trusted intermediary under the data model and needs purge, origin authentication, and cache-key policy.

> **Common misconception 18.68 — “A container makes an application production-ready and isolated.”**  
> It packages processes and namespaces under a runtime. Reliability, privilege, kernel exposure, secrets, networking, persistence, limits, and orchestration remain.

### 18.31.2 Rollout, health, and rollback

A liveness check asks whether a process should be restarted. A readiness check asks whether it should receive new traffic. Including a temporarily unavailable database in liveness can restart every application instance during a database outage, amplifying failure. Readiness can decline while liveness remains healthy.

Startup checks prevent traffic until migrations/configuration and essential pools are ready. During shutdown, readiness turns false, routing drains, the server stops accepting new work, and in-flight requests receive a bounded grace interval. Background tasks need their own lease and shutdown protocol.

A **rolling deployment** replaces instances gradually. A **blue–green deployment** prepares a parallel environment then switches traffic. A **canary** exposes a controlled subset and evaluates guardrails. All require schema compatibility and a decision about sticky sessions, caches, long-lived connections, and workers.

Rollback should use a known artifact and documented compatible schema, not an emergency source rebuild. If a new version emitted events or wrote state old code cannot understand, binary rollback is unsafe; feature flags or roll-forward correction can separate activation from deployment.

Traffic splitting must produce comparable populations if metrics decide promotion. Routing 1% of users from one geography is not a random canary. Automated rollback rules need persistence windows and protection against telemetry failure.

> **Common misconception 18.69 — “Zero-downtime deployment means replacing all instances quickly.”**  
> It requires overlapping compatible versions, readiness and draining, stable routing, migration sequencing, retained assets, and reversible activation.

### 18.31.3 Infrastructure, configuration, and capacity as reviewed code

Infrastructure-as-code records desired networks, identities, load balancers, databases, queues, and policies in versioned declarative definitions. It enables review and repeatable environments but can reproducibly deploy a dangerous configuration. Plans contain sensitive topology and sometimes secret-derived values; protect state storage and review output.

Apply changes through a controlled pipeline using least-privileged deployment identity, peer review, policy checks, and drift detection. Manual emergency changes should be recorded and reconciled rather than silently overwritten later. Production access is exceptional, time-limited, audited, and separated from ordinary development accounts.

Configuration has schema and lifecycle. Validate types, required values, URL origins, trusted proxy counts, timeouts, pool sizes, and mutually dependent options at startup. A default development secret or wildcard CORS origin must not allow production to start.

Feature flags need owners, purpose, default, targeting, expiry, and removal. Evaluation failure should follow a safe policy. A stale flag creates permanent branches that double testing combinations; flags are temporary operational state, not a substitute for versioned configuration design.

Capacity planning connects arrival rate, service time, concurrency, worker resources, and dependency limits. A deployment request can state:

| Quantity | Example contract |
|:---|:---|
| peak eligible arrival | 800 requests/s |
| p99 application time | below 300 ms |
| maximum in-flight | 400 per region |
| database connections | 120 total per primary |
| queue backlog objective | below 60 s of work |
| failure reserve | survive loss of one zone |

Autoscaling reacts after measuring load and starting capacity. Scaling on CPU alone misses blocked I/O and queue growth; scaling on raw request count ignores operation cost. New instances can stampede migrations, caches, and connection establishment. Minimum warm capacity protects sudden bursts.

Regional design accounts for data residency, latency, identity, encryption keys, DNS, and failover. Active–active writes require a conflict and consistency model; active–passive requires a promotion authority and tested routing. Spreading stateless instances globally while retaining one distant database can worsen latency and create the appearance rather than substance of resilience.

Cost is a system property. Unbounded logs, egress, per-request serverless invocations, idle overprovisioning, inefficient queries, and forgotten environments can dominate. Cost limits must not silently drop security logs or backups; budgets and anomaly alerts route decisions to owners.
