# 18.32 Observability

**Observability** is the ability to infer a system’s internal state from emitted evidence. Three common signal forms are:

- **logs:** discrete event records;
- **metrics:** numerical measurements aggregated over labels and time;
- **traces:** causal timing paths across operations and services.

Structured logs encode named fields rather than prose alone. Each request can carry a correlation identifier. Sensitive fields, credentials, session tokens, personal data, and full request bodies require minimisation or redaction. Logs are a data system with access, retention, and integrity requirements.

Service measures include:

- request rate;
- error rate by meaningful class;
- latency distribution, including tail percentiles;
- saturation of workers, queues, connections, CPU, and memory;
- dependency health;
- domain outcomes.

An average latency can remain low while a small but important group experiences severe delay. Percentiles require sufficient volume and careful aggregation; averaging percentiles across instances is generally invalid.

A trace span records one timed operation with parent relation and attributes. Sampling reduces cost but can miss rare events; tail-based policies can retain slow or failed traces at additional complexity.

### 18.32.1 Signals, context, and cardinality

Logs answer discrete questions when fields are consistent: event name, time, severity, request/trace identifiers, service and release, principal class, operation, outcome, and safe error code. Free-form prose remains useful for humans but should not be the only structure.

Metrics aggregate efficiently. A counter increases; a gauge represents a current value; a histogram records a distribution in buckets. Label values create time series. Using user ID, URL query, exception message, or request ID as a label creates unbounded **cardinality**, exhausting monitoring storage. Put high-cardinality identifiers in logs or traces.

Distributed trace context propagates across trusted calls and queue messages. Accept external trace identifiers under validation but create new internal span identities and avoid treating trace baggage as trusted authorisation. Sampling decisions and context size propagate cost.

Exemplars can connect a metric bucket to representative traces. Correlation lets an operator move from an SLO alert to a slow trace and then to structured logs without storing every request body.

> **Common misconception 18.70 — “Adding more telemetry always improves observability.”**  
> Excess volume, cardinality, sensitive data, inconsistent fields, and unactionable alerts can obscure failures and destabilise the system meant to be observed.

### 18.32.2 SLIs, SLOs, and actionable alerts

A **service-level indicator** (SLI) is a measured property such as successful request proportion or latency below a threshold. A **service-level objective** (SLO) is a target over a window. A service-level agreement can attach contractual consequences and is not synonymous with an internal SLO.

For an availability SLI:

\[
\text{availability}
=
\frac{\text{good eligible events}}
{\text{all eligible events}}.
\]

“Good” and “eligible” need exact definitions. A fast 500 is not good; a 404 caused by an invalid client may be excluded from server availability; a request cancelled after the server committed needs a policy.

An **error budget** is the permitted amount of not-good service under the SLO. Burn-rate alerts detect consumption faster than allowed across short and long windows. This connects alerts to user impact rather than every CPU fluctuation.

Tail latency should be measured at the user-facing boundary and sliced by operation and meaningful population. Percentiles cannot generally be averaged; histograms with compatible buckets can aggregate. An endpoint with one request per hour needs different alert statistics from one with millions.

Alerts should be actionable, owned, deduplicated, and connected to a runbook. Page on symptoms requiring urgent human action; ticket persistent low-risk issues; record informational events without waking someone. Test that the alert path works.

> **Common misconception 18.71 — “A service is healthy when CPU and memory are below thresholds.”**  
> Resource signals explain causes. User-oriented correctness, availability, and latency indicators define whether the service is meeting its objective.
