# 18.33 Reliability and partial failure

Distributed systems fail partially: an application can run while its database is unreachable; a client can time out while the server commits; one availability zone can fail while another works. Error handling must classify operations by recoverability and ambiguity.

Protective patterns include:

- bounded retry with backoff and jitter;
- circuit breakers that temporarily stop calls to a failing dependency;
- bulkheads that isolate resource pools;
- idempotency and deduplication;
- queues with dead-letter policy;
- graceful degradation;
- load shedding;
- rollback.

Retries increase load and can turn a small outage into a collapse. They belong under a total deadline and retry budget. A circuit breaker is not a cure for correctness errors; it trades some calls for faster failures while a dependency appears unhealthy.

### 18.33.1 Stability patterns and their trade-offs

A circuit breaker observes selected failures and opens temporarily, rejecting calls without contacting the dependency. A half-open state probes recovery. Thresholds must distinguish overload, caller errors, and local cancellation; a breaker shared across unrelated tenants or operations can spread failure.

A **bulkhead** reserves independent capacity so one dependency or workload cannot consume every worker. Separate pools reduce utilisation efficiency in return for isolation. Load shedding rejects low-priority or excess work before saturation; graceful degradation serves a cheaper or older representation when correctness permits.

Fallbacks are production code and can fail. A stale price, permissive authorisation cache, or empty recommendation is not universally safe. State the maximum staleness and prohibited fallbacks. Never fall back from failed authentication to anonymous privileged behaviour.

Retries should ordinarily occur at one layer. If three nested services each perform three attempts, one request can produce \(3^3=27\) deepest calls. Centralise policy, propagate attempt metadata, and cap total work.

### 18.33.2 Recovery, backups, and disaster objectives

High availability during ordinary component failure differs from disaster recovery after loss or corruption. A replica can reproduce accidental deletion immediately; it is not a backup. Backups need independent protection, encryption, retention, access control, integrity checking, and tested restoration.

The **recovery point objective** (RPO) states the maximum tolerable data loss measured in time or another unit. The **recovery time objective** (RTO) states the target time to restore service. Near-zero values cost substantially and require architecture, rehearsal, and organisational readiness.

A recovery exercise restores into an isolated environment, verifies schema and application compatibility, checks record counts and domain invariants, rotates compromised secrets if relevant, and measures elapsed time. A green “backup completed” message does not test restore.

Multi-region designs must choose consistency, failover authority, DNS/routing behaviour, data replication, conflict handling, and failback. Automatic failover can promote a lagging replica and lose acknowledged writes. Manual failover can exceed RTO. The trade-off must be explicit.

### 18.33.3 Failover authority, fencing, and split brain

Redundancy creates a second problem: deciding which replica may act. During a network partition, two healthy processes can each be unable to observe the other. If both infer that absence means failure and accept writes, the system has **split brain**: more than one participant exercises authority that was intended to be exclusive. Reconnecting the network does not automatically reconcile two externally visible histories. Money charged, mail sent, stock allocated, or names assigned cannot in general be merged by choosing the row with the latest timestamp.

A lease grants authority for a bounded interval, but its safety depends on the time source, renewal protocol, storage semantics, and behaviour of a paused former holder. A process may stop long enough for its lease to expire, resume without realising that a successor now owns the role, and issue a stale write. A **fencing token** prevents this class of error by attaching a monotonically increasing authority number to each grant. The protected resource rejects operations bearing a number lower than the greatest one it has already observed. The check must occur at the resource that could be damaged; testing a lease in application memory and then issuing an unfenced write leaves a time-of-check/time-of-use interval.

A quorum is a threshold of participants whose responses are required for an operation. Intersecting read and write quorums can establish useful guarantees under a stated replica model, but the word *quorum* is not itself proof of linearizability, durability, or availability. Membership changes, correlated failures, stale leaders, asynchronous replication, and acknowledgement policy remain material. Likewise, a consensus algorithm can order commands among participating nodes; it cannot make an unavailable external payment processor transactional, repair a faulty domain invariant, or guarantee progress when its required participants cannot communicate.

Wall clocks are evidence, not an authority oracle. They can jump, drift, repeat local times, or disagree across hosts. Use monotonic clocks for elapsed deadlines within one process, protocol-defined expiries for credentials, and database or consensus ordering where state transitions require a shared sequence. When human time has domain meaning, preserve the time zone and the rule used to interpret daylight-saving gaps and repetitions.

The practical design method is to name every exclusive authority: migration runner, scheduler, queue partition consumer, primary database, certificate issuer, inventory allocator, or deployment controller. For each one, specify how authority is acquired, how a successor proves precedence, where stale actors are fenced, what happens during lost communication, and how an operator recovers from ambiguity. “Only one instance normally runs” is an observation about a healthy deployment, not a concurrency invariant.

### 18.33.4 Incidents and learning

An incident process establishes command, technical investigation, communications, evidence preservation, mitigation, and recovery. Runbooks accelerate known actions but cannot replace judgement. Audit changes made under emergency access.

After recovery, a blameless technical review reconstructs contributing conditions rather than stopping at the person who triggered the event. Corrective actions should address detection, containment, architecture, tests, process, and documentation, with owners and deadlines. “Be more careful” is not a system control.

Chaos experiments deliberately introduce bounded failure to verify hypotheses: terminate an instance, add dependency latency, drop a zone, expire a certificate in staging, or replay queue messages. Define steady-state measures, blast radius, abort controls, and approvals. Experiments on production require mature safeguards.

> **Common misconception 18.72 — “Redundancy guarantees reliability.”**  
> Correlated dependencies, shared configuration, bad deployments, replicated corruption, failover defects, and overload can defeat replicas. Reliability requires independent failure domains and exercised recovery.
