# 18.34 Synthesis: designing a reservation service from first principles

This section composes the chapter’s layers into one system. The purpose is not to prescribe a universal architecture but to show how protocol, domain, persistence, security, concurrency, and operations constrain one another.

The service reserves a time slot for a registered patient at a clinic. A reservation can be held briefly, confirmed, cancelled, or expire. Duplicate client retries must not create duplicate reservations. A patient may access only their own reservations; clinic staff have separately governed authority. Confirmation sends a notification without making database commit depend on the notification provider.

### 18.34.1 State, invariants, and threat boundaries

Define states:

\[
\text{held}
\rightarrow
\text{confirmed}
\rightarrow
\text{cancelled}
\]

and

\[
\text{held}
\rightarrow
\text{expired}.
\]

Not every arrow is permitted. Confirming an expired hold is a conflict, not a new implicit booking. Cancelling can be idempotent under a protocol that returns the current cancelled representation. Expiration is driven by server time, never a client-supplied timestamp.

Core invariants:

1. one clinic slot has at most one active held or confirmed reservation;
2. a reservation belongs to exactly one patient and clinic;
3. hold expiry is later than creation and bounded by policy;
4. only the owning patient or an authorised staff principal can view or mutate it;
5. one idempotency key under one patient and operation identifies one logical creation;
6. a committed confirmation produces at least one durable notification event;
7. every privileged staff mutation produces an immutable audit event.

The uniqueness invariant is concurrent and belongs in the database. Authorisation belongs at both request policy and tenant-scoped query boundaries. Notification delivery is cross-system and uses an outbox. Audit data need tamper resistance, minimised sensitive content, retention, and access controls.

Trust boundaries include the browser, public load balancer, application workload, identity provider, database, queue/relay, notification provider, and telemetry system. A trace crossing them must not carry medical detail or bearer credentials.

### 18.34.2 Resource and HTTP contract

Resources:

| Resource | Example identifier | Principal operations |
|:---|:---|:---|
| available slot | <code>/clinics/C4/slots/2026-10-03T09:30Z</code> | retrieve availability |
| reservation collection | <code>/reservations</code> | create under an idempotency key; list authorised reservations |
| reservation | <code>/reservations/R82</code> | retrieve and conditionally mutate |
| confirmation | <code>/reservations/R82/confirmation</code> | create the confirmation transition |

Creating a hold:

~~~http
POST /reservations HTTP/1.1
Content-Type: application/json
Accept: application/json
Idempotency-Key: 675e2b9c-0f3b-4cf7-a43a-946196b9e2b3

{
  "slot_id": "S19"
}
~~~

A successful first response is 201 with <code>Location</code>, representation, ETag, and private/no-store cache policy. Repetition of the same key and request fingerprint returns the stored logical result. Reuse of the key for another slot returns a conflict. A currently occupied slot returns 409 without revealing another patient.

Confirmation can be expressed as creation of a subordinate resource:

~~~http
PUT /reservations/R82/confirmation HTTP/1.1
If-Match: "reservation-version-3"
~~~

The complete representation and method contract must specify whether an already confirmed reservation returns 200/204 or the original result. The ETag prevents a stale page from confirming after cancellation or expiry. A 412 reports a failed representation precondition; a 409 can report a current domain state that cannot transition.

Collection pagination uses a cursor bound to patient, filter, and stable ordering <code>(created_at, reservation_id)</code>. Staff queries require explicit clinic scope and audited permission. Neither patient nor staff client may provide an arbitrary <code>patient_id</code> to override the server-derived subject without a separately authorised staff operation.

### 18.34.3 Relational state and one atomic creation

A simplified PostgreSQL-oriented schema:

~~~sql
CREATE TABLE reservation (
    reservation_id UUID PRIMARY KEY,
    patient_id UUID NOT NULL REFERENCES patient(patient_id),
    slot_id UUID NOT NULL REFERENCES clinic_slot(slot_id),
    status TEXT NOT NULL
        CHECK (status IN ('held', 'confirmed', 'cancelled', 'expired')),
    hold_expires_at TIMESTAMP WITH TIME ZONE NOT NULL,
    version BIGINT NOT NULL CHECK (version > 0),
    created_at TIMESTAMP WITH TIME ZONE NOT NULL,
    updated_at TIMESTAMP WITH TIME ZONE NOT NULL
);

CREATE UNIQUE INDEX one_active_reservation_per_slot
ON reservation(slot_id)
WHERE status IN ('held', 'confirmed');

CREATE TABLE idempotent_request (
    patient_id UUID NOT NULL,
    operation TEXT NOT NULL,
    idempotency_key TEXT NOT NULL,
    request_digest BYTEA NOT NULL,
    response_status INTEGER,
    response_body JSONB,
    reservation_id UUID REFERENCES reservation(reservation_id),
    PRIMARY KEY (patient_id, operation, idempotency_key)
);

CREATE TABLE outbox (
    event_id UUID PRIMARY KEY,
    event_type TEXT NOT NULL,
    aggregate_id UUID NOT NULL,
    payload JSONB NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL,
    published_at TIMESTAMP WITH TIME ZONE
);
~~~

The partial unique index makes active occupancy authoritative under concurrency. The idempotency table scopes keys to patient and operation and retains a request digest so conflicting reuse is detectable. The outbox shares the reservation transaction.

Creation transaction:

1. authenticate the principal before beginning expensive work;
2. validate the request schema and slot identifier;
3. begin a transaction;
4. insert or lock the idempotency record;
5. if a completed matching request exists, return its stored result;
6. reject a digest mismatch;
7. verify the slot belongs to the requested clinic and remains reservable;
8. insert the held reservation, relying on the unique index to resolve races;
9. store the stable response and commit;
10. return only after commit.

If two patients race, one insert succeeds and one receives a uniqueness violation mapped to 409. An earlier “check available” query improves messaging but is not the invariant. If the response is lost after commit, the retry finds the idempotency record.

The hold expiry worker updates only rows still held and past expiry:

~~~sql
UPDATE reservation
SET status = 'expired',
    version = version + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE reservation_id = %s
  AND status = 'held'
  AND hold_expires_at <= CURRENT_TIMESTAMP;
~~~

Affected-row count distinguishes an applied transition from a reservation already confirmed or cancelled. Several workers can attempt expiration safely because the predicate makes the transition idempotent.

### Worked example 18.6 — Domain transition independent of HTTP

~~~python
from __future__ import annotations

from dataclasses import dataclass, replace
from datetime import datetime
from enum import StrEnum


class ReservationStatus(StrEnum):
    HELD = "held"
    CONFIRMED = "confirmed"
    CANCELLED = "cancelled"
    EXPIRED = "expired"


@dataclass(frozen=True)
class Reservation:
    reservation_id: str
    patient_id: str
    status: ReservationStatus
    hold_expires_at: datetime
    version: int

    def confirm(self, *, now: datetime) -> "Reservation":
        if self.status is not ReservationStatus.HELD:
            raise ValueError("only a held reservation can confirm")
        if now >= self.hold_expires_at:
            raise ValueError("hold has expired")
        return replace(
            self,
            status=ReservationStatus.CONFIRMED,
            version=self.version + 1,
        )
~~~

The domain object exposes an explicit legal transition and returns a new value. It does not claim atomicity: persistence must condition its update on current status and version. It does not send email: an outbox event is created in the transaction. It does not authorise: the application service establishes the acting principal first.

### 18.34.4 Authentication, privacy, and abuse

Patient sessions use origin-bound phishing-resistant authentication where feasible, short ordinary sessions, secure host-only cookies, CSRF defence, session rotation after authentication, and recovery of comparable assurance. Staff access can require stronger multifactor authentication, managed devices, narrow clinic roles, and step-up for exceptional actions.

Every reservation query includes patient or authorised clinic scope. A random UUID reduces guessing but is not authorisation. Error responses avoid disclosing that another patient holds a slot beyond the availability information the product intentionally exposes.

Medical and contact data are minimised. Notification events reference the reservation rather than copy every detail; the worker fetches only what the selected template needs. Logs record reservation identifiers under restricted access but exclude symptoms, token values, cookies, and message bodies. Retention and deletion policy must account for clinical, audit, legal, and user rights rather than apply one TTL blindly.

Abuse controls include per-principal and per-clinic creation rates, a cap on simultaneous holds, proof or friction for automated bulk reservation, and fairness review so controls do not exclude legitimate accessibility needs. Rate limiting by source IP alone harms shared networks and is easily distributed.

The public availability endpoint can leak clinic capacity or patient activity through timing. Threat modelling decides acceptable granularity, cacheability, and whether slots are shown before authentication. Audit access itself is privileged and monitored.

### 18.34.5 Delivery, observation, and recovery

The application artifact, schema migration, static assets, and worker version are compatible during rollout. A new event field is additive; old workers ignore documented unknown fields. Removing a field waits until telemetry shows no supported consumer depends on it.

SLIs include:

- proportion of eligible reservation requests receiving a correct terminal response;
- p95 and p99 creation latency by clinic/region without personal labels;
- slot-conflict rate;
- idempotency replay and mismatch counts;
- hold-expiry delay;
- outbox age and notification delivery delay;
- authorisation denials and suspicious enumeration patterns.

The notification SLO is separate from reservation correctness. A provider outage must not undo confirmed reservations. Workers retry within a deadline, expose delivery status, and route exhausted events for controlled resolution. Duplicate provider submissions use a stable provider idempotency key.

A canary deployment monitors schema errors, conflict rates, latency, session failures, and outbox delay. Rollback retains compatibility with the migrated schema. Feature activation can be disabled independently if a new confirmation workflow fails.

Fault tests include:

- client timeout immediately after reservation commit;
- two concurrent holds for one slot;
- confirmation racing expiration;
- database deadlock during confirmation;
- notification publish followed by relay crash;
- revoked staff authority during an open session;
- stale ETag mutation;
- queue redelivery;
- unavailable identity provider for an existing session;
- loss and restore of the primary database under declared RPO/RTO.

The design is defensible only after implementation and tests show these properties. Diagrams, framework choices, and nominal status codes are hypotheses until exercised under concurrent and failed execution.
