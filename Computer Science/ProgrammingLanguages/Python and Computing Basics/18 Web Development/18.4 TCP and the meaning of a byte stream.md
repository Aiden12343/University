# 18.4 TCP and the meaning of a byte stream

The **Transmission Control Protocol**, or TCP, provides an ordered reliable byte stream between endpoints, subject to connection failure. “Reliable” means it detects loss and reorders or retransmits within its protocol; it does not guarantee that the peer application processed a message or committed a transaction.

TCP presents bytes, not application messages. If one side sends 100 bytes once, the other can receive them as 40 then 60, as 100, or through other positive chunk sizes. Conversely, bytes from several sends can be returned together. An application protocol must delimit or length-prefix messages.

TCP uses flow control so a sender does not overrun a receiver’s advertised capacity and congestion control so traffic responds to network conditions. Establishing a connection and recovering from loss add latency. Closing one direction, resetting a connection, and idling through intermediary timeouts have distinct meanings.

### Worked example 18.2 — Read until a protocol delimiter

~~~python
from __future__ import annotations

import socket


def receive_until(
    connection: socket.socket,
    delimiter: bytes,
    *,
    limit: int,
) -> bytes:
    if not delimiter:
        raise ValueError("delimiter must be non-empty")
    if limit <= 0:
        raise ValueError("limit must be positive")

    buffer = bytearray()

    while delimiter not in buffer:
        chunk = connection.recv(4_096)
        if not chunk:
            raise EOFError("connection ended before delimiter")
        buffer.extend(chunk)
        if len(buffer) > limit:
            raise ValueError("message exceeds limit")

    message, _, remainder = buffer.partition(delimiter)
    if remainder:
        raise ValueError(
            "example function cannot preserve trailing bytes"
        )
    return bytes(message)
~~~

The loop does not equate one <code>recv</code> with one message. It checks end-of-stream and imposes a resource limit. The deliberate rejection of trailing bytes reveals an incomplete design: a real buffered parser must retain bytes belonging to the next message. Making the defect explicit is superior to silently discarding data.

### 18.4.1 Connection establishment and sequence space

TCP establishes shared connection state through a handshake. Each direction has a sequence number space. Acknowledgements describe bytes received, while retransmission recovers from inferred loss. The protocol delivers accepted bytes to the application in order, so a missing earlier segment can delay later bytes even if they arrived. This is transport-layer **head-of-line blocking**.

Reliability has limits. A local successful <code>send</code> generally means bytes entered an operating-system buffer, not that the peer application read them. A successful HTTP response means the server generated a response, not necessarily that the user saw it. After a connection breaks, either endpoint can be uncertain about how much application work occurred.

A graceful close sends an end-of-stream indication after queued bytes. A reset aborts the connection and can discard unread buffered data. TCP is bidirectional: one endpoint can **half-close** its sending direction while continuing to receive. Many application libraries abstract these states, but error diagnosis requires distinguishing EOF, timeout, reset, and local cancellation.

> **Common misconception 18.7 — “If <code>send</code> succeeds, the remote operation succeeded.”**  
> It ordinarily confirms local buffering of bytes. Remote receipt, parsing, authorisation, transaction commit, and response are later independent events.

### 18.4.2 Buffering and framing without data loss

A delimiter protocol must retain bytes after the delimiter for the next message. A length-prefixed protocol first reads a fixed-size or delimited length header, validates it against a maximum, then reads exactly that many payload bytes. An attacker can announce an enormous length and never send it, so limits and deadlines apply before allocation and throughout receipt.

~~~python
from __future__ import annotations

from dataclasses import dataclass, field


@dataclass
class LengthPrefixedDecoder:
    maximum_body: int
    _buffer: bytearray = field(default_factory=bytearray)

    def feed(self, data: bytes) -> list[bytes]:
        self._buffer.extend(data)
        messages: list[bytes] = []

        while len(self._buffer) >= 4:
            size = int.from_bytes(self._buffer[:4], "big")
            if size > self.maximum_body:
                raise ValueError("announced body exceeds limit")
            end = 4 + size
            if len(self._buffer) < end:
                break
            messages.append(bytes(self._buffer[4:end]))
            del self._buffer[:end]

        return messages


decoder = LengthPrefixedDecoder(maximum_body=1_024)
packet = (5).to_bytes(4, "big") + b"hello"
assert decoder.feed(packet[:3]) == []
assert decoder.feed(packet[3:] + (0).to_bytes(4, "big")) == [
    b"hello",
    b"",
]
~~~

The decoder is independent of socket chunk sizes and preserves an incomplete suffix. A production protocol must also define whether zero-length messages are valid, how connection EOF with buffered data is treated, and how long an incomplete frame may occupy resources.

### 18.4.3 Congestion, connection reuse, and QUIC

TCP congestion control discovers available path capacity and reduces sending after signs of congestion. A new connection begins without full knowledge of the path. Reusing connections avoids repeated handshakes and can preserve learned capacity, but long-lived pools require idle expiry, health checks, maximum lifetime, and bounded size.

The Nagle algorithm can coalesce small writes while delayed acknowledgements postpone responses, historically creating latency interactions for chatty protocols. Applications should write coherent buffers and use protocol/server settings deliberately rather than assume every small <code>send</code> is transmitted immediately.

HTTP/2 multiplexes streams over one TCP connection, eliminating HTTP/1.1 application-level ordering between responses but retaining TCP head-of-line blocking when a packet is lost. HTTP/3 maps HTTP semantics over QUIC, which runs over UDP and provides encrypted multiplexed streams so loss in one stream need not block bytes in another. QUIC remains reliable where the stream requires it; “uses UDP” does not mean “unreliable HTTP.”

> **Common misconception 18.8 — “UDP is fast and unreliable, while TCP is slow and reliable.”**  
> UDP supplies datagrams with little transport machinery; applications can build reliability and congestion control over it, as QUIC does. Performance follows the complete protocol and workload.

> **Common misconception 18.9 — “Keeping unlimited connections open improves performance.”**  
> Connections consume descriptors, buffers, memory, ports, and peer capacity. Pools need bounds, expiry, fairness, and behaviour for failed or stale connections.
