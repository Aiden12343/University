# 18.5 TLS: authenticated protected transport

**Transport Layer Security**, or TLS, is a protocol for establishing protected communication. It can provide:

- confidentiality against observers lacking session keys;
- integrity against undetected modification;
- server authentication through certificates and trust validation;
- optional client authentication.

A **certificate** binds identity information, commonly a DNS name, to a public key under signatures and a trust system. Validation includes a chain to a trusted authority, name matching, validity period, constraints, and revocation-related policy. Encryption without correct authentication can create a private channel to an attacker.

HTTPS is HTTP carried through TLS. TLS does not make the application trustworthy, prevent it logging secrets, validate user input, or ensure a response is true. It protects a transport relation under stated assumptions.

Python clients should use library defaults that validate certificates and hostnames. Disabling verification to “fix” a certificate error destroys the property the error protects. Resolve the certificate, clock, trust-store, proxy, or name problem instead.

### 18.5.1 Handshake, identity, and key establishment

During a TLS handshake, peers negotiate a protocol version and cryptographic parameters, establish shared traffic secrets, authenticate the transcript, and ordinarily authenticate the server with a certificate chain. Modern ephemeral key exchange provides **forward secrecy**: later compromise of a long-term server key need not reveal previously recorded sessions, assuming ephemeral secrets were destroyed.

Public-key cryptography establishes identity and keys; efficient symmetric cryptography protects application records after the handshake. An authenticated-encryption algorithm supplies confidentiality and integrity together. Nonces and sequence state prevent safe reuse of the same key stream; implementations, not application code, manage record cryptography.

A public certificate contains names in its subject alternative name extension and a public key. A certification path links it through intermediate authorities to a trust anchor configured by the client. Validation asks at least whether:

- signatures and constraints form an acceptable chain;
- the requested host name matches;
- the certificate is within its validity period;
- intended key use is permitted;
- algorithms and key sizes satisfy policy;
- revocation information is handled under client policy.

Server Name Indication communicates the intended host during the handshake so one address can serve multiple certificates. Application-Layer Protocol Negotiation chooses a protocol such as HTTP/2. These fields occur before ordinary HTTP routing; a certificate mismatch cannot be repaired by a Flask route.

> **Common misconception 18.10 — “TLS encrypts a request with the website’s public key.”**  
> The handshake uses asymmetric mechanisms to authenticate and establish shared secrets; bulk records are protected with symmetric authenticated encryption derived from those secrets.

### 18.5.2 Termination, mutual TLS, and operational trust

TLS may terminate at a load balancer, reverse proxy, service mesh sidecar, or the application process. After termination, traffic can be re-encrypted to the next hop or travel over a protected internal channel under another trust model. The application must know which proxy may assert scheme, host, and client-certificate information.

In **mutual TLS** (mTLS), the client also presents a certificate. This can authenticate service or managed-device identities, but issuance, rotation, revocation, key storage, and authorisation remain. A valid certificate says that a trusted issuer bound a key to an identity under a policy; it does not grant every action.

Certificate automation should renew well before expiry and alert on failure. Private keys belong in restricted secret storage, not source repositories or container layers. Rotating a certificate may require supporting old and new trust chains during rollout. Certificate pinning can narrow trust but creates recovery risk when keys or issuers change.

TLS does not hide all metadata. Observers can often see IP addresses, traffic timing, sizes, and some handshake information. Server logs and terminating proxies see plaintext. End-to-end privacy claims must name endpoints and retained metadata.

~~~python
import ssl

context = ssl.create_default_context()
context.minimum_version = ssl.TLSVersion.TLSv1_2
context.check_hostname = True
context.verify_mode = ssl.CERT_REQUIRED

assert context.check_hostname
assert context.verify_mode == ssl.CERT_REQUIRED
~~~

The default context loads platform trust configuration and secure defaults appropriate to a client. Pinning cipher lists or protocol details without a compatibility and maintenance reason can age worse than maintained defaults.

> **Common misconception 18.11 — “Traffic is safe after TLS termination because it is inside the network.”**  
> Internal networks contain compromised hosts, misconfiguration, and unintended routes. Every hop needs an explicit trust, identity, confidentiality, and integrity model.
