# 18.6 URLs and resource identifiers

A **Uniform Resource Identifier**, or URI, identifies a resource according to a syntax. A **Uniform Resource Locator**, or URL, is a URI that indicates a means of locating or accessing a resource. A typical HTTP URL contains:

\[
\text{scheme}://\text{authority}/\text{path}?\text{query}\#\text{fragment}.
\]

For

<code>https://shop.example:8443/products/17?currency=GBP#reviews</code>:

- scheme: <code>https</code>;
- host: <code>shop.example</code>;
- explicit port: <code>8443</code>;
- path: <code>/products/17</code>;
- query: <code>currency=GBP</code>;
- fragment: <code>reviews</code>.

The fragment is interpreted by the client and ordinarily is not sent in an HTTP request. Percent-encoding represents bytes in URI components, but decoding and interpretation depend on the component. A plus sign can have special form-encoding meaning in a query while remaining a literal plus elsewhere. String concatenation is therefore an unsafe general URL constructor.

~~~python
from urllib.parse import urlencode, urljoin

base = "https://api.example/v1/"
path = urljoin(base, "devices")
query = urlencode({"site": "north & west", "limit": 20})
url = f"{path}?{query}"
print(url)
~~~

Even <code>urljoin</code> requires care with untrusted second arguments: an absolute input can replace the origin. Component-aware construction does not decide which destinations are authorised.

### 18.6.1 Authority, origin, normalisation, and resolution

The URL **authority** can contain user information, host, and port. User information is not a safe place for credentials: URLs appear in logs, history, referrers, monitoring, and screenshots. A host can be a registered name, IPv4 literal, or bracketed IPv6 literal.

A web **origin** is conventionally the tuple of scheme, host, and effective port. Two paths on one origin share browser-origin authority; identical hosts under HTTP and HTTPS are different origins; omitted ports resolve to scheme defaults. Origin is central to browser security, whereas a **site** is a related but different registrable-domain concept used by mechanisms such as <code>SameSite</code>.

Relative-reference resolution follows URI rules. A leading slash replaces the path from the authority root; no leading slash resolves relative to the base directory; <code>..</code> removes a path segment under the algorithm. String concatenation does not implement these rules.

Normalisation is purpose-specific. Scheme and DNS host names are case-insensitive, while path case can be significant. Percent-encoded forms, default ports, dot segments, Unicode host names, and trailing slashes can identify equivalent or distinct resources depending on layer. Security code must parse once with a defined parser and compare canonical components under an explicit policy.

Internationalised domain names are represented to DNS through an ASCII-compatible encoding. Visually confusable Unicode characters can create deceptive names. User interfaces should display identity-sensitive host names carefully and retain the parsed ASCII form for policy.

> **Common misconception 18.12 — “Two URLs that look alike designate the same resource.”**  
> Case, encoding, origin, port, Unicode, path normalisation, query ordering, fragments, and server policy can make visually similar forms equivalent or distinct.

### 18.6.2 Parsing is not destination authorisation

Suppose a service accepts a callback URL. It must first parse syntax, then separately decide:

- permitted schemes;
- exact hosts or controlled suffixes;
- permitted effective ports;
- whether credentials and fragments are forbidden;
- resolved address ranges;
- redirect policy;
- DNS re-resolution policy;
- request method, headers, body, time, and response limits.

~~~python
from urllib.parse import urlsplit


def validated_https_origin(
    value: str,
    *,
    allowed_hosts: frozenset[str],
) -> tuple[str, int]:
    parsed = urlsplit(value)
    if parsed.scheme != "https":
        raise ValueError("HTTPS is required")
    if parsed.username is not None or parsed.password is not None:
        raise ValueError("user information is forbidden")
    host = parsed.hostname
    if host is None or host.lower() not in allowed_hosts:
        raise ValueError("host is not allowlisted")
    try:
        port = parsed.port or 443
    except ValueError as error:
        raise ValueError("invalid port") from error
    if port != 443:
        raise ValueError("non-default port is forbidden")
    return host.lower(), port


assert validated_https_origin(
    "https://api.example/callback?x=1",
    allowed_hosts=frozenset({"api.example"}),
) == ("api.example", 443)
~~~

This function validates only textual origin policy. It does not connect, validate resolved addresses, control redirects, or establish that the destination is entitled to receive data. Those are additional boundaries.

A suffix check such as <code>host.endswith("example.com")</code> accepts <code>notexample.com</code>. If subdomains are allowed, require either exact equality or a dot-delimited suffix and still account for DNS ownership. Prefer an explicit allowlist when the destination set is small.

> **Common misconception 18.13 — “If a URL parser accepts a URL, it is safe to fetch.”**  
> Parsing establishes structure. Authorisation must constrain destination, resolution, redirects, capabilities, resource use, and data disclosure.
