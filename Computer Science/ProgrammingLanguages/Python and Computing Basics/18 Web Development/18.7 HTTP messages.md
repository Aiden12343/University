# 18.7 HTTP messages

The **Hypertext Transfer Protocol**, or HTTP, is a stateless application protocol whose semantics are expressed through requests and responses. Stateless means each request carries enough protocol context for interpretation; servers can still maintain application state in databases or sessions.

An HTTP request has a method, target, protocol version under a wire representation, header fields, and an optional content body. A response has a status code, header fields, and optional content.

A conceptual request:

~~~http
GET /devices/A17 HTTP/1.1
Host: api.example
Accept: application/json
~~~

A conceptual response:

~~~http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Length: 32

{"device_id":"A17","status":"ok"}
~~~

Headers are named fields conveying metadata and control information. <code>Content-Type</code> identifies the representation format of enclosed content. <code>Accept</code> describes response media types acceptable to the client. <code>Content-Length</code> counts body bytes under applicable framing, not Unicode characters.

HTTP/2 and HTTP/3 use binary framing and multiplexed streams rather than the textual HTTP/1.1 wire form shown. The application semantics of methods, statuses, and fields are substantially shared, but intermediaries and version-specific mechanisms matter. Framework code ordinarily handles framing; developers must still understand semantics.

### 18.7.1 Fields, framing, and message boundaries

An HTTP field has a case-insensitive field name and a value whose grammar is defined by that field’s specification. Treating every field as an arbitrary comma-separated list is unsafe: some fields permit lists, some carry dates containing commas, and some have structured-field syntax. Maintained protocol libraries should parse them.

HTTP/1.1 serialises a start line, fields, an empty line, and an optional body. Body length can be determined by method/status semantics, <code>Content-Length</code>, transfer coding, or connection close under defined rules. Conflicting length signals are security-critical because two intermediaries that disagree about the boundary can interpret one byte stream as different requests. This class underlies **HTTP request smuggling**.

HTTP/2 and HTTP/3 use frames with explicit lengths and stream identifiers. Header compression reduces repeated metadata. Binary framing removes some HTTP/1.1 ambiguities but creates version-specific limits and state machines. Converting between protocol versions at a proxy must preserve semantics and reject ambiguous messages.

Fields such as <code>Connection</code> govern one transport hop and must not be forwarded as end-to-end metadata. Other fields describe the selected representation or request across intermediaries. A reverse proxy that copies every inbound field blindly can forward hop-by-hop controls, forged client identity, or internal routing hints.

Servers bound field count, total field bytes, individual line or value length, request-target length, and body size. Limits should fail early and consistently across proxy and application; if the proxy permits 100 MiB but the application buffers only 5 MiB safely, the outer limit should reflect the lower boundary.

> **Common misconception 18.14 — “HTTP headers are an unstructured dictionary of strings.”**  
> Field names are case-insensitive, repeated values have field-specific combination rules, and each field has defined syntax, scope, and forwarding semantics.

### 18.7.2 Hosts, proxies, and effective request identity

The authority identifies the intended origin. HTTP/1.1 uses the <code>Host</code> field; later versions carry equivalent pseudo-header information. Servers must validate accepted host names rather than use any supplied host to construct password-reset links or absolute redirects. A **Host header injection** can otherwise make a trusted application emit attacker-controlled origins.

Behind a proxy, the application’s direct peer is the proxy, not the user agent. Forwarded fields can communicate original scheme, host, and client address, but clients can forge the same field names. The application or server must discard untrusted incoming forwarding fields and accept assertions only from a configured proxy chain with a known hop count.

The request target has several forms in HTTP/1.1: origin form for ordinary origin requests, absolute form for some proxy requests, authority form for <code>CONNECT</code>, and asterisk form for server-wide <code>OPTIONS</code>. Frameworks ordinarily expose a normalised path and query, which may no longer reveal raw encoding distinctions. Security controls must know which form and normalisation stage they inspect.

> **Common misconception 18.15 — “The application can trust <code>X-Forwarded-For</code> because the load balancer sets it.”**  
> It is trustworthy only after a configured trusted proxy removes or normalises client-supplied values and the application interprets the declared proxy chain correctly.

### 18.7.3 Multiplexing, prioritisation, and streaming

HTTP/1.1 persistent connections reuse transport state, but ordinary pipelining had head-of-line and deployment difficulties. HTTP/2 multiplexes independent request streams over one connection and compresses fields; HTTP/3 maps streams to QUIC. Multiplexing reduces some connection overhead but does not make server work free: one client can open many streams and consume memory or scheduling attention.

A response body can be generated incrementally. **Streaming** reduces time to first byte and peak buffering, but after response fields are committed the application can no longer replace the status cleanly when a generator fails. Proxies may buffer despite application streaming, and compression can delay small chunks. A streaming contract needs cancellation handling, maximum duration, backpressure, and partial-response semantics.

Trailers carry fields after a streamed body under protocol rules, but intermediary and client support varies. They are not a portable substitute for an ordinary status or upfront metadata unless the whole path supports them.

> **Common misconception 18.16 — “HTTP/2 makes every request faster.”**  
> It reduces particular connection and multiplexing costs. Server processing, congestion, prioritisation, field compression state, loss, dependency latency, and workload determine actual performance.

### 18.7.4 Security response fields constrain browser capabilities

HTTP response fields can instruct browsers to reduce attack surface:

- <code>Strict-Transport-Security</code> tells a browser to use HTTPS for a host for a period, optionally including subdomains;
- <code>Content-Security-Policy</code> restricts resource and script execution capabilities;
- <code>X-Content-Type-Options: nosniff</code> reduces content-type guessing in relevant contexts;
- <code>Referrer-Policy</code> controls referrer information sent on navigation and subresource requests;
- <code>Permissions-Policy</code> controls browser features delegated to documents and frames;
- framing policy through CSP <code>frame-ancestors</code> restricts which ancestors may embed a page.

HSTS is effective only after the browser has learned the policy unless the domain is preloaded. Setting <code>includeSubDomains</code> requires every present and future subdomain to support HTTPS; otherwise it creates outages. Removing the field does not immediately erase a cached long lifetime.

MIME sniffing can cause a response to be interpreted as executable content contrary to a mistaken media type. Serve user uploads from a distinct non-privileged origin, set accurate types and download disposition where intended, and avoid allowing an uploaded HTML or SVG document to inherit application origin authority.

Clickjacking places a target page in a deceptive frame so a user interacts with concealed controls. Frame restrictions reduce embedding; sensitive actions still need clear confirmation and authorisation. A JavaScript “frame buster” is weaker than enforced browser policy and can be bypassed.

Referrer data can expose path and query information to linked origins. Secrets never belong in URLs regardless of policy because URLs also enter browser history, server logs, proxy logs, analytics, screenshots, and copied links.

Security fields need coverage on errors, redirects, and framework-generated responses, not only successful views. Test the final proxy-delivered response because outer infrastructure can add, remove, or duplicate fields. Duplicate CSP fields combine restrictively under browser rules; duplicate incompatible CORS fields can make access fail.

Fields cannot repair an application that emits attacker-controlled active content, authorises the wrong principal, or exposes secrets in the body. They establish browser constraints around otherwise correct application semantics.
