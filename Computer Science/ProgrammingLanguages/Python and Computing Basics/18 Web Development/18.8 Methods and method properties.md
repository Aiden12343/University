# 18.8 Methods and method properties

An HTTP **method** describes the request’s intended semantics.

| Method | Conventional purpose | Safe | Idempotent |
|:---|:---|:---:|:---:|
| GET | retrieve a representation | yes | yes |
| HEAD | retrieve response metadata without response content | yes | yes |
| POST | submit data for resource-specific processing | no | no general guarantee |
| PUT | create or replace state at a target | no | yes |
| PATCH | apply a partial modification under a patch format | no | no general guarantee |
| DELETE | request removal of a target resource | no | yes |
| OPTIONS | describe communication options | yes | yes |

A **safe** method is intended to be read-only from the client’s requested semantics, although logging and accounting can still change server state. An **idempotent** method has the same intended effect when repeated as when performed once. The repeated responses need not be identical. Deleting an already deleted resource can return a different status while the intended final state remains deleted.

Network clients cannot always know whether a timed-out request reached the server. Retrying an idempotent operation is usually more tractable. Non-idempotent operations such as payments require application mechanisms such as an **idempotency key**, a client-generated operation identifier whose repeated submission maps to one logical operation under a server contract.

### Worked example 18.3 — Retry only under a policy

~~~python
from __future__ import annotations

import time
from collections.abc import Callable
from typing import TypeVar

T = TypeVar("T")


def retry(
    operation: Callable[[], T],
    *,
    attempts: int,
    initial_delay: float,
    retryable: Callable[[Exception], bool],
) -> T:
    if attempts < 1:
        raise ValueError("attempts must be at least one")

    delay = initial_delay
    for attempt in range(attempts):
        try:
            return operation()
        except Exception as error:
            final_attempt = attempt == attempts - 1
            if final_attempt or not retryable(error):
                raise
            time.sleep(delay)
            delay *= 2

    raise AssertionError("loop must return or raise")
~~~

The function exposes rather than guesses which failures are retryable. Real HTTP retry policy must consider method semantics, idempotency keys, status codes, <code>Retry-After</code>, timeouts, exponential backoff, random jitter, total deadline, and load amplification. Catching <code>Exception</code> is acceptable only because the predicate must classify and unclassified exceptions are re-raised.

### 18.8.1 Safety, idempotency, and cacheability are separate

Safety expresses requested semantics: a client does not ask a safe method to change server state. Logging, billing a provider for bandwidth, cache population, and counters can still occur as incidental effects. Crawlers, link previewers, browser prefetchers, and caches may issue GET requests without a user explicitly pressing a button. Encoding “delete” in a GET target is therefore dangerous.

Idempotency concerns the intended effect of repeated identical requests. <code>PUT</code> of the same complete representation can be idempotent even if audit rows and response timestamps differ. <code>POST</code> has no general idempotency guarantee, though a particular POST protocol can define one. A PATCH document can be idempotent—“set status to closed”—or non-idempotent—“increment count.”

Cacheability is a third property. GET and HEAD responses are commonly cacheable under controls; other method responses may be cacheable only under explicit conditions and limited support. A method being safe does not guarantee a response will be cached, and idempotency does not imply cacheability.

> **Common misconception 18.17 — “Safe, idempotent, and cacheable mean the same thing.”**  
> Safety concerns requested side effects, idempotency concerns repeated effect, and cacheability concerns reuse of a response under caching rules.

### 18.8.2 Preconditions prevent lost updates

A client that reads version A, edits it, and writes later can overwrite another client’s intervening version B. HTTP preconditions make the write conditional. The server returns an ETag with the representation; the client sends <code>If-Match</code> on PUT or PATCH. If the current selected representation no longer matches, the server returns 412 rather than silently overwriting.

This is **optimistic concurrency control**: operations proceed without holding a lock during user thought time and detect conflict at commit. A version number or last-modified timestamp can play a similar role if its comparison semantics are sufficiently precise. The check and state change must be atomic in the authoritative store.

<code>If-None-Match: *</code> can make creation conditional on absence. It is stronger than “GET then POST,” which races between requests. HTTP conditions must map to database constraints or conditional updates rather than remain an application-only check.

~~~python
from dataclasses import dataclass


@dataclass
class Document:
    body: str
    version: int


def replace_if_current(
    document: Document,
    *,
    expected_version: int,
    new_body: str,
) -> Document:
    if document.version != expected_version:
        raise RuntimeError("precondition failed")
    return Document(
        body=new_body,
        version=document.version + 1,
    )


current = Document("first", version=7)
updated = replace_if_current(
    current,
    expected_version=7,
    new_body="second",
)
assert updated.version == 8
~~~

This in-memory function illustrates the state transition but is not concurrency-safe across threads or processes. A database conditional update such as <code>... WHERE id = ? AND version = ?</code>, followed by an affected-row check, establishes the atomic boundary.

> **Common misconception 18.18 — “PUT automatically prevents concurrent overwrites because it is idempotent.”**  
> Idempotency governs repetition of one request, not conflicts between different representations. Preconditions or transactional concurrency control are required.

### 18.8.3 Retrying ambiguous operations

A timeout can occur before connection, during request upload, while the server works, after commit but before the response arrives, or while the client reads the response. Only the first case proves the server did nothing. The client frequently faces an **ambiguous outcome**.

An idempotency key names one logical operation. The server stores the key, a fingerprint of material request fields, operation state, and resulting response in a transactional relation. Reuse with the same fingerprint returns the stored result; reuse with different content is rejected. Keys need scope, entropy, retention, and protection against cross-principal collision.

Retry delay should usually grow and include **jitter**, random variation that prevents synchronised clients from retrying simultaneously. A retry budget caps additional load, and a total deadline prevents attempts after the result is no longer useful. <code>Retry-After</code> can communicate service policy but does not force client compliance.

> **Common misconception 18.19 — “Retrying a POST is always unsafe.”**  
> POST has no generic idempotency guarantee, but an application can define deduplicated semantics with an idempotency key. Safety depends on the complete server protocol and ambiguity handling.
