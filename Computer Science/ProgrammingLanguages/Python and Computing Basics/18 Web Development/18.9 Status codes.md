# 18.9 Status codes

HTTP status codes are three-digit results grouped by first digit:

- 1xx: interim information;
- 2xx: successful handling;
- 3xx: redirection;
- 4xx: the request cannot be fulfilled in its present client-associated form;
- 5xx: the server failed to fulfil an apparently valid request.

Important examples:

| Code | Meaning in context |
|---:|:---|
| 200 | successful response with representation or result |
| 201 | resource created; commonly accompanied by its location |
| 204 | successful response with no content |
| 304 | selected cached representation remains usable under conditional request |
| 400 | malformed or invalid request at the HTTP/application boundary |
| 401 | authentication credentials are required or invalid under challenge semantics |
| 403 | server understood identity/context but refuses authorisation |
| 404 | target resource not found or intentionally undisclosed |
| 409 | request conflicts with current resource state |
| 412 | a supplied precondition failed |
| 422 | content understood but application instructions are semantically invalid |
| 429 | request rate exceeds a policy; response may communicate retry timing |
| 500 | unexpected server failure |
| 502 | gateway received an invalid upstream response |
| 503 | service temporarily unable to handle the request |
| 504 | gateway did not receive an upstream response in time |

A status is part of a protocol contract, not an exception taxonomy copied mechanically from Python. A database uniqueness conflict may become 409; malformed JSON may become 400; a valid JSON document violating a domain rule may become 422 under a chosen API convention. Document the mapping.

### 18.9.1 Selecting a status by protocol outcome

A status code describes the response to this request, not the moral character of the caller. A 404 can deliberately conceal whether a resource exists when the principal lacks permission. A 401 uses HTTP authentication challenge semantics and is commonly returned for missing or invalid authentication; despite its historical reason phrase, 403 better expresses an authenticated or otherwise understood request that is refused.

Redirection status codes differ in method-preservation semantics. A 303 directs retrieval, conventionally with GET, of another resource after a POST. A 307 or 308 preserves method and content; 301 and 302 have historical user-agent behaviour that can rewrite POST to GET. Choose deliberately rather than return “redirect” generically.

For asynchronous work, 202 means the request was accepted for processing, not completed. The response should identify status or result resources and cancellation semantics where applicable. A 204 response has no content body; returning JSON with it creates disagreement among clients and intermediaries.

Client cancellation can leave the server working; no universal status retroactively means “nothing happened.” Status codes describe messages that are actually delivered. Internal logs should distinguish client disconnect, application rejection, dependency failure, and successful work whose response was lost.

> **Common misconception 18.20 — “Every application error maps to one obvious HTTP status.”**  
> Mapping depends on resource and protocol semantics. The API must define stable distinctions among syntax, authentication, authorisation, absence, conflict, validation, rate policy, and server failure.

### 18.9.2 Machine-readable errors and disclosure

An error representation should have a stable media type and machine code independent of translated prose. Useful fields can include:

- a stable application error code;
- a human-readable summary safe for the caller;
- per-field validation details;
- a correlation identifier;
- a documentation URI;
- retry or remediation information.

Do not expose stack traces, SQL text, secret values, internal host names, or existence information prohibited by policy. Log internal diagnostic detail under access controls and connect it through a correlation identifier, not by sending it to the client.

Batch and GraphQL-like operations can have partial results. One outer status may not describe every item, so the representation needs per-item outcomes and atomicity rules. Avoid returning 200 for every failure merely because the body contains an error: generic clients, caches, monitors, and retry policies use status semantics.

Rate limiting can return 429, but limits have identity and scope: per credential, user, origin, tenant, operation, or resource. Responses should avoid revealing another tenant’s activity. A gateway 502/503/504 distinction can support operations, but clients should follow documented retry policy rather than guess from all 5xx codes.

> **Common misconception 18.21 — “Returning HTTP 200 with an <code>error</code> field is equivalent to an error status.”**  
> Status participates in generic caching, monitoring, client, and intermediary behaviour. The body supplies application detail; it does not replace protocol semantics.
