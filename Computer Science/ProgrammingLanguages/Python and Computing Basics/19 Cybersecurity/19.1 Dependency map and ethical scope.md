All reconnaissance, testing, monitoring, and automation in this chapter is limited to systems the practitioner owns or is explicitly authorised to assess. **Authorisation** is permission from a competent owner specifying targets, techniques, time, data handling, and reporting. Technical ability does not create permission. A written rules-of-engagement document prevents a legitimate assessment from becoming an uncontrolled intrusion.

The chapter teaches defensive analysis: how vulnerabilities arise from violated contracts, how to reduce attack surface, how to use cryptographic libraries correctly, and how to detect and respond to failure. Examples use local data or illustrative endpoints. They do not authorise use against third parties.

### 19.1.1 Authority, scope, and proportionality

An assessment is authorised only to the extent of its grant. Ownership of one account does not imply permission to test the service hosting it; employment does not imply authority over every employer system; public reachability does not imply consent. A valid scope names assets and also the identities through which tests may act, the data that may be observed, prohibited techniques, rate and concurrency limits, time zone, emergency contacts, and the person empowered to stop the work. Third-party infrastructure—cloud services, payment processors, content-delivery networks, and upstream networks—can remain outside scope even when it supports an in-scope application.

A **rules of engagement** document converts authority into operational constraints. It should distinguish observation, benign validation, controlled exploitation, persistence, social engineering, physical access, denial-of-service testing, and destructive action because these have radically different consequences. It should state evidence retention, encryption, reporting, notification, restoration, and deletion duties. When reality diverges from the plan—an unexpected production host, personal data, a medical device, or evidence of an unrelated intrusion—the correct action is to stop, preserve minimal evidence, and contact the authorised owner.

Proportionality means using the least intrusive method that answers the security question. Configuration review can establish that anonymous storage access is enabled without downloading every object. A single controlled request can prove an object-level authorisation defect without enumerating other users’ records. The evidential objective is reproducibility, not spectacle.

### 19.1.2 Laboratories and dual-use knowledge

Security mechanisms and vulnerabilities are dual-use: the same knowledge can harden an application or damage one. The academically sound response is not to conceal mechanisms, because defenders must understand them, but to couple technical study to controlled environments and explicit objectives. A **security laboratory** is an isolated environment containing deliberately vulnerable or disposable systems, synthetic identities and data, bounded network routes, snapshots, and observable reset procedures.

Laboratory isolation must be tested rather than assumed. A virtual machine can reach a production network through its host; a container ordinarily shares its host kernel; a sample credential can accidentally match a real credential; malware can escape an intended directory through mounted volumes. Use non-routable or host-only networking where appropriate, separate accounts, no production secrets, minimal shared folders, resource limits, and a documented teardown. Record software versions because a security result is often version-specific.

The defensive practitioner also has duties to subjects whose data appear in evidence. Collect the minimum, restrict access, distinguish technical findings from personal attribution, and delete according to agreement. A vulnerability report should communicate affected versions, prerequisites, impact, evidence, and remediation without publishing secrets or unnecessary exploit automation.

> **Common misconception 19.1 — “If a system is publicly reachable, testing it is permitted.”**  
> Reachability is a technical fact, not consent. Authorisation must cover the target, identity, technique, time, data handling, and foreseeable effects.

> **Common misconception 19.2 — “A virtual machine makes any security experiment safe.”**  
> Isolation depends on networking, shared devices, host integration, credentials, hypervisor behaviour, and resource controls. A laboratory is a designed boundary, not a product label.
