# 19.12 Injection as a general grammar failure

SQL injection, shell injection, template injection, LDAP injection, expression injection, and log injection share a structure:

1. a language has code/structure and data;
2. a program constructs a language document using untrusted text;
3. the consumer parses the combined text;
4. untrusted text changes syntax.

The primary defence is to preserve structure/data separation using parameterised interfaces, typed builders, or context-specific encoders. An allowlist restricts cases where the user selects among structural alternatives. “Sanitise the string” is too vague to constitute a defence.

Log injection illustrates integrity rather than code execution. If a newline from input is embedded in line-oriented logs, an attacker can forge apparent records. Structured logging serialises fields under one format; viewers must still escape control characters and active content.

### 19.12.1 Context determines the defence

An encoder valid for one grammar can be dangerous in another. HTML text, an HTML attribute, a URL component, JavaScript source, CSS, SQL literals, SQL identifiers, shell arguments, LDAP filters, regular expressions, CSV formula cells, and log viewers all have different syntax. Data can cross several contexts: a database value enters JSON, becomes JavaScript data, and is inserted into the DOM. Protection must be applied at each output boundary for the next interpreter.

The strongest interface makes structure unrepresentable as data. A SQL driver sends a prepared statement and separately typed parameters. A DOM API assigns `textContent` rather than concatenating HTML. A template engine auto-escapes according to a known HTML context. A structured logger serialises named fields. When structural choice is genuinely user-controlled—such as selecting an ordering column—map an external enum to a fixed internal fragment.

Template injection differs from cross-site scripting. If untrusted text becomes template source, it can invoke the server-side template language before any HTML escaping occurs. Treat templates, regular expressions, queries, and policies as code or configuration with controlled authorship. A “sandboxed” template engine still needs a threat model for introspection, object access, computation, and resource exhaustion.

### 19.12.2 Secondary and stored interpretation

Injection can be delayed. An attacker stores a newline, spreadsheet formula, template expression, or shell fragment that appears inert until an export, administrative viewer, migration, or incident tool interprets it. This **second-order injection** defeats reviews focused only on the original input endpoint. Data provenance does not become trustworthy merely because bytes passed through a database.

CSV illustrates the distinction. Quoting commas and newlines creates valid CSV, yet spreadsheet software can interpret a cell beginning with `=`, `+`, `-`, or `@` as a formula under its policy. If a spreadsheet is the intended consumer, export design must address that behaviour without corrupting legitimate data, and recipients need a documented trust model.

Header injection similarly arises when untrusted values create line breaks or delimiter structure in mail or HTTP fields. Use APIs that validate field grammar and reject control characters. Normalise neither by silent deletion nor by repeated decoding, because changing a value can merge distinct identities or hide evidence.

> **Common misconception 19.31 — “Escaped input is safe wherever it is later used.”**  
> Escaping has meaning only for a specified output grammar and position. Stored data must be encoded again for each new consumer context.

> **Common misconception 19.32 — “Injection requires obvious punctuation such as quotes.”**  
> Typed objects, options, encodings, delimiters, duplicate fields, expressions, and secondary interpreters can alter structure without one universal special character.
