# 19.14 Dependency and supply-chain risk

Software depends on interpreters, libraries, build backends, package indexes, source repositories, compilers, operating-system packages, container bases, and deployment systems. A **software supply chain** is this path from source and dependencies to executing artifact.

Threats include:

- malicious or compromised package releases;
- dependency confusion between internal and public names;
- typo-squatted names;
- compromised maintainer credentials;
- vulnerable transitive dependencies;
- mutable tags or unpinned downloads;
- malicious build-time code;
- stolen signing keys;
- CI credential exfiltration.

Controls include:

- minimise dependencies and privileges;
- use isolated environments;
- lock resolved versions and verify hashes where supported;
- separate public and internal package namespaces;
- review provenance and maintainers;
- scan known vulnerabilities while recognising database limitations;
- generate a software bill of materials;
- use reproducible or attestable builds;
- sign and verify artifacts under a managed trust policy;
- restrict build-network and secret access;
- patch through a tested release process.

A **software bill of materials**, or SBOM, inventories components and versions. It aids response but does not prove absence of malicious code or unknown vulnerabilities. A scanner’s “zero findings” means no matching findings under its database and configuration.

### 19.14.1 Resolution is code selection

A dependency declaration usually describes a set of acceptable distributions, not one artifact. A resolver considers version constraints, environment markers, Python version, platform tags, optional extras, index contents, yanked releases, and transitive metadata. The resulting environment can change when an index publishes a newer eligible version even though application source is unchanged. Reproducible deployment therefore requires recording the resolved artifact set for each target environment, not merely broad direct requirements.

Names are part of the trust boundary. **Typosquatting** publishes a confusingly similar name. **Dependency confusion** causes a public distribution to satisfy a name intended for an internal source. Controls include a single governed resolution configuration, reserved internal names or separate namespaces, explicit indexes, no unreviewed fallback, and tests showing which repository supplied every artifact. `--extra-index-url` can create ambiguity when the same project name exists in multiple indexes; repository priority must be understood rather than assumed.

A wheel is an installable archive and can contain native code. A source distribution causes a build backend and its dependencies to execute during build. Build isolation separates an environment; it does not make build code harmless. Treat installation and build as code execution: run them in a restricted environment with no production secret, minimal network access, bounded authority, and retained provenance.

### 19.14.2 Locking, hashing, and artifact verification

A lock records selected versions and preferably exact artifacts or secure hashes. Version pinning alone does not prove that the bytes later downloaded are the bytes reviewed. Hash verification binds an expected digest to bytes, provided the lock itself is trusted and each permitted platform artifact is represented deliberately.

### Worked example 19.5 — Verify a staged distribution against approved metadata

~~~python
from __future__ import annotations

from hashlib import file_digest
from pathlib import Path


def verify_sha256(path: Path, approved_hex: str) -> None:
    if len(approved_hex) != 64:
        raise ValueError("invalid SHA-256 representation")
    with path.open("rb") as stream:
        actual = file_digest(stream, "sha256").hexdigest()
    if actual != approved_hex.lower():
        raise ValueError("artifact digest does not match approved metadata")
~~~

The comparison detects a byte mismatch with approved metadata; it does not establish who approved the digest or whether the matching artifact is benign. Trusted repository metadata, signed attestations, independent review, and controlled lock changes address different links. Use a constant-time comparison only where digest secrecy or a remotely measurable oracle belongs to the threat model; these public fixed-length artifact hashes are not secrets.

Python’s standardised `pylock.toml` format can describe reproducible installation inputs, and index-hosted attestations can associate distributions with signing identities. An attestation is a signed statement about an artifact and build subject. Its value depends on verification policy: accepted identity, issuer, workflow, repository, source revision, predicate type, freshness, transparency evidence, and revocation or compromise response. “Signed” without a trust policy is incomplete.

### 19.14.3 Build provenance and continuous trust

**Build provenance** records how an artifact was produced: source identity and revision, builder identity, invocation, dependencies, parameters, and outputs. Higher-assurance pipelines isolate builds, minimise mutable inputs, use short-lived workload identity, retain tamper-evident evidence, and separate approval from execution. Reproducible builds allow independent parties to compare outputs from the same declared inputs, but nondeterminism, compiler trust, and dependency bootstrapping still require analysis.

CI systems are production systems with unusually powerful authority. Pull requests can modify workflow code; build logs and caches can leak secrets; self-hosted runners can retain state; artifacts can be replaced after tests; broad repository tokens can publish or rewrite source. Separate untrusted change testing from privileged release, pin reusable actions by immutable identity, restrict outbound access, protect environments, require reviewed promotion, and make release identity short-lived.

An SBOM should identify components, versions, suppliers, hashes, relationships, and the artifact to which the inventory applies. Generate it from the actual build where possible and retain it with provenance. It is an index for questions—“where is this component deployed?”—not a verdict. Dynamically loaded plugins, vendored code, operating-system libraries, build tools, and generated assets can be missed.

Vulnerability response needs supported update windows, compatibility tests, rollback, and emergency change paths. A permanently frozen lock accumulates known flaws; unrestricted automatic updates admit unreviewed change. Automated proposals plus evidence and staged deployment separate discovery from promotion.

> **Common misconception 19.35 — “Pinning versions secures dependencies.”**  
> Pins improve repeatability but do not authenticate artifacts, inspect code, constrain build execution, or keep a vulnerable version safe indefinitely.

> **Common misconception 19.36 — “A wheel is only data because it is an archive.”**  
> Installation places importable Python and may include native binaries. Importing or executing the installed project grants process authority.

> **Common misconception 19.37 — “An attestation proves an artifact is safe.”**  
> It proves that an accepted identity made a particular statement. Policy must decide whether the identity, builder, source, predicate, and process are sufficient.

> **Common misconception 19.38 — “An SBOM is a vulnerability report.”**  
> It inventories components and relationships. Vulnerability matching, exploitability, configuration, reachability, unknown flaws, and remediation remain separate analyses.
