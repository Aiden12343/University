# 19.15 Secrets

A **secret** is information whose disclosure grants authority or defeats a security property: passwords, private keys, API tokens, session identifiers, and encryption keys. A secret must have an owner, purpose, scope, creation process, storage location, delivery path, rotation policy, revocation mechanism, and audit trail.

Source repositories, container images, command-line arguments, crash dumps, chat messages, and logs are poor secret stores. Environment variables are a common delivery mechanism but can be inherited or exposed through diagnostics; they are not encrypted merely because they are environmental.

Code should receive the narrow secret it needs through a configured secret-management interface and avoid retaining or copying it unnecessarily. Redaction must occur before logs leave the process.

~~~python
from dataclasses import dataclass


@dataclass(frozen=True, repr=False)
class ApiCredential:
    value: str

    def __repr__(self) -> str:
        return "ApiCredential(<redacted>)"
~~~

Suppressing representation reduces accidental display but strings remain immutable objects whose memory cannot be reliably erased from Python. If that threat matters, use purpose-built native facilities and minimise lifetime; do not promise secure erasure the runtime cannot guarantee.

### 19.15.1 Secret inventories and delivery

Secret management begins with inventory. For each secret record issuer, subject, audience, capabilities, storage, consumers, delivery route, lifetime, rotation, revocation, owner, and evidence of use. A forgotten credential cannot be rotated reliably. A credential with no audience or scope boundary often becomes an organisation-wide skeleton key.

Prefer short-lived credentials obtained from a workload identity over long-lived copied tokens. A workload proves its platform identity to a credential service, which issues authority for a narrow audience and interval. This reduces stored secret material but shifts trust to workload identity, metadata endpoints, time, and the issuer. Protect those paths against SSRF and confused-deputy use.

A secret manager protects storage and mediates retrieval; it cannot protect plaintext after release to an authorised process. Cache only when availability and rate justify it, bind access to one workload, audit retrieval, and avoid placing values in general configuration objects likely to be printed. Command-line arguments can appear in process inspection and shell history. Environment variables can propagate to children and diagnostics. Mounted files need permissions, update semantics, and deletion behaviour. Choose a delivery channel from the platform threat model.

### 19.15.2 Rotation, revocation, and compromise

Rotation is a protocol, not replacement of one string. A safe sequence commonly introduces a new credential, updates verifiers or consumers to accept both versions, migrates producers, observes old-key use, disables the old version, and verifies rejection. Signing and encryption keys require key identifiers so historical data can select the correct key during overlap. Rotation cadence should reflect exposure and system capability; frequent manual rotation that causes outages can be worse than automated short-lived credentials.

Revocation asks how quickly authority must stop. Stateless self-contained tokens can remain valid until expiry unless verifiers consult state or rotate a key affecting many tokens. Server-side session references permit immediate central revocation but create an online dependency. Document the maximum revocation delay as a security property.

After suspected disclosure, rotation alone can miss derived sessions, cached credentials, replicas, logs, backups, downstream copies, and persistence established by the attacker. Determine the credential’s capabilities and use evidence, contain dependent authority, preserve forensic data, and rebuild trust from a known point. A new secret issued through a compromised pipeline is already suspect.

~~~python
from __future__ import annotations

import logging
from collections.abc import Mapping


SENSITIVE_FIELDS = frozenset({"authorization", "cookie", "password", "secret", "token"})


def redacted(fields: Mapping[str, object]) -> dict[str, object]:
    return {
        key: "<redacted>" if key.casefold() in SENSITIVE_FIELDS else value
        for key, value in fields.items()
    }


logging.info("request metadata %r", redacted({"token": "not-for-logs", "route": "/v1"}))
~~~

This allowlist-by-name example is deliberately limited. Secrets can occur in URLs, exception messages, nested bodies, arbitrary headers, filenames, subprocess output, or fields with unanticipated names. Prefer logging schemas that admit only approved fields rather than trying to discover every secret after construction. Test redaction with representative failure paths.

Secret scanning should cover current source, history, build artifacts, issue systems, and logs, but pattern matching cannot determine whether a value is live or find every encoding. On discovery, revoke or rotate first under an incident plan; deleting the visible occurrence does not invalidate copies.

> **Common misconception 19.39 — “A secret manager means applications no longer handle secrets.”**  
> It governs storage and retrieval. An authorised application still receives or uses authority and can leak plaintext, misuse it, or be induced to act as a deputy.

> **Common misconception 19.40 — “Deleting a committed secret repairs the leak.”**  
> Clones, caches, build logs, artifacts, mirrors, and observers may retain it. Revoke or rotate the authority and investigate use.

> **Common misconception 19.41 — “Frequent rotation automatically reduces risk.”**  
> Rotation helps only when distribution, overlap, revocation, observation, and failure recovery are reliable. A brittle manual ritual can create outages and bypasses.
