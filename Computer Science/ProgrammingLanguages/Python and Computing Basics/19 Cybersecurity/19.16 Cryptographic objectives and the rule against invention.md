# 19.16 Cryptographic objectives and the rule against invention

**Cryptography** studies techniques for protecting information under adversarial conditions. Modern cryptographic security is conditional on algorithms, parameters, key secrecy, nonce discipline, implementations, protocols, endpoints, and threat assumptions. Applying an encryption function does not secure a system whose keys are public or whose decrypted data are exposed.

Do not design cryptographic algorithms or protocols for production. Use current, reviewed, high-level constructions from maintained libraries and follow their key, nonce, and version guidance. “Clever” combinations of primitives commonly fail because security properties do not compose by intuition.

Principal constructions include:

- cryptographic hash functions;
- message authentication codes;
- symmetric authenticated encryption;
- public-key encryption or key agreement;
- digital signatures;
- password-hashing or key-derivation functions;
- cryptographically secure random generation.

Each has a different key and objective. Substituting one for another is a category error.

### 19.16.1 Security definitions and protocol context

A cryptographic primitive is analysed against a defined game or adversary capability: collision resistance, chosen-message forgery, indistinguishability under chosen-plaintext attack, or authenticated-encryption security, for example. These are more precise than “strong encryption”. Parameters translate the definition into an intended security level, subject to algorithmic advances and implementation quality.

Kerckhoffs’s principle states that a cryptosystem should remain secure when everything except the key is known. Hiding an algorithm or binary can add friction but must not be the foundation. Public scrutiny permits analysis; secrecy of design prevents defenders from knowing whether obscurity is all that holds.

Protocols require **domain separation**: a value authenticated for one purpose should not be accepted for another. Bind a protocol identifier, version, message type, sender/receiver roles, algorithm or key identifier, and contextual resource to an unambiguous byte encoding. The same key should not be reused across unrelated algorithms or environments unless a reviewed construction explicitly derives separated subkeys.

~~~python
def frame_fields(*fields: bytes) -> bytes:
    framed = bytearray(b"SECURITY-TREATISE\x00v1\x00")
    for field in fields:
        framed.extend(len(field).to_bytes(8, "big"))
        framed.extend(field)
    return bytes(framed)


assert frame_fields(b"ab", b"c") != frame_fields(b"a", b"bc")
~~~

Length-prefixing prevents the concatenation ambiguity in the assertion. The encoder still needs maximum lengths, a stable integer representation, and a specification shared by every implementation. Canonical JSON is not obtained merely by removing whitespace; numbers, key order, Unicode, duplicates, and implementation behaviour must be defined.

### 19.16.2 Side channels and implementation reality

A mathematically secure construction can leak through timing, cache access, power, electromagnetic emanation, error messages, branch behaviour, memory access, compression ratios, packet length, or repeated failure. Python cannot promise constant-time execution for arbitrary code because interpreter dispatch, allocation, garbage collection, big integers, and libraries vary. Use maintained native implementations that state side-channel properties, and avoid exposing fine-grained decryption or signature errors to remote adversaries.

Constant-time comparison is relevant only to one leakage mechanism. It does not conceal input length, whether an account exists, database time, rate-limit state, or subsequent branching. Equalising every response with arbitrary sleeps adds load and noise without a proof. First remove the secret-dependent operation or use a reviewed protocol; then measure the complete observable path.

Algorithm agility is the capacity to migrate under a versioned policy, not permission for clients to choose any algorithm. Negotiation can enable downgrade unless authenticated and constrained. Store algorithm and parameter identifiers with ciphertext or verifiers, maintain an allowed set, reject unknown or retired suites, and rehearse migration. “Encrypt everything again immediately” can be operationally dangerous without tested recovery and backups.

Post-quantum migration illustrates lifecycle reasoning. The concern is not only future decryption at the day a capable computer exists; adversaries can store encrypted traffic now and attack it later. Systems with long confidentiality horizons must inventory cryptographic uses, data lifetimes, protocols, libraries, key infrastructure, and interoperability before replacing primitives. Use standardised, reviewed schemes through maintained protocols rather than experimental combinations.

> **Common misconception 19.42 — “A standard algorithm makes a custom protocol secure.”**  
> Security also depends on encoding, key separation, nonce rules, replay handling, identities, errors, downgrade resistance, endpoints, and lifecycle.

> **Common misconception 19.43 — “Constant-time comparison removes timing attacks.”**  
> It reduces one comparison leak. Length, lookup, parsing, rate limits, errors, allocation, and surrounding control flow can remain observable.
