# 19.18 Message authentication codes

A **message authentication code**, or MAC, uses a secret key to produce a tag providing integrity and source authentication among key holders. HMAC is a standard construction combining a cryptographic hash with a key.

~~~python
import hashlib
import hmac


def sign_message(key: bytes, message: bytes) -> bytes:
    return hmac.digest(key, message, "sha256")


def verify_message(
    key: bytes,
    message: bytes,
    supplied_tag: bytes,
) -> bool:
    expected = sign_message(key, message)
    return hmac.compare_digest(expected, supplied_tag)
~~~

<code>compare_digest</code> reduces timing information associated with ordinary early-exit comparison. It does not hide message length or repair weak keys. Every verifier holding the shared key can also generate tags, so an HMAC cannot provide public non-repudiation.

A MAC does not provide confidentiality: the message remains visible. It also requires replay protection where repetition matters. Include a protocol version, context, operation identity, and freshness data in an unambiguous authenticated structure, then maintain state or expiry rules.

### 19.18.1 Tag verification and key separation

Verification must authenticate exactly the bytes whose meaning is acted upon. If a proxy normalises a path, a JSON parser ignores duplicate fields, or a timestamp is parsed differently by signer and verifier, a valid tag can protect one interpretation while the application uses another. Define the canonical byte representation and reject representations outside it.

Tag truncation reduces forgery resistance. An attacker allowed (q) independent online attempts against a uniformly distributed (t)-bit tag has success probability approaching (q/2^t) while probabilities remain small. Rate limits and key lifetime therefore interact with tag length. Never accept a variable-length prefix supplied by the caller; verify the protocol’s one required length.

Keys need context separation. Derive independent subkeys for webhook authentication, database field protection, session tokens, and other purposes through an approved key-derivation function with explicit labels. If one key is shared by many tenants or environments, compromise and forgery blast radius expand.

~~~python
from __future__ import annotations

import hashlib
import hmac
import time


def webhook_payload(timestamp: int, body: bytes) -> bytes:
    return frame_fields(b"webhook", str(timestamp).encode("ascii"), body)


def verify_webhook(
    key: bytes,
    *,
    timestamp: int,
    body: bytes,
    tag: bytes,
    now: int | None = None,
    tolerance: int = 300,
) -> bool:
    current = int(time.time()) if now is None else now
    if tolerance < 0 or abs(current - timestamp) > tolerance:
        return False
    expected = hmac.digest(key, webhook_payload(timestamp, body), hashlib.sha256)
    return len(tag) == len(expected) and hmac.compare_digest(expected, tag)
~~~

The timestamp constrains replay duration but does not prevent multiple replays inside the window. For non-idempotent effects, persist an authenticated event identifier and reject duplicates transactionally. Clock tolerance, delayed delivery, rotation, and failure responses belong to the protocol.

### 19.18.2 Symmetric authenticity and attribution limits

Every party holding a MAC key can forge tags indistinguishable from every other holder’s. MAC evidence can establish “someone within this key-sharing group generated the tag”, not public attribution to one member. If two organisations may later dispute which originated a record, a shared MAC key cannot resolve the dispute cryptographically.

Key compromise affects past evidence unless keys were isolated by period and securely destroyed. Audit systems should record key versions and verification context, and must not accept retired keys indefinitely merely to keep old messages operational. Archive verification and live command authorisation can have different policies.

> **Common misconception 19.46 — “A valid MAC proves which server sent a message.”**  
> It proves generation by some holder of the shared key. Any verifier holding that key can also forge the same evidence.

> **Common misconception 19.47 — “Adding a timestamp prevents replay.”**  
> It limits an acceptance window. Repetition within that window still requires idempotency or persistent nonce/event tracking where effects matter.
