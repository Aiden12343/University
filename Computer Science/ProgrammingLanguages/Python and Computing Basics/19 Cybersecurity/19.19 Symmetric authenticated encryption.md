# 19.19 Symmetric authenticated encryption

**Symmetric encryption** uses secret key material shared by encrypting and decrypting parties. Modern applications generally require **authenticated encryption with associated data**, abbreviated AEAD. An AEAD construction encrypts plaintext and authenticates both ciphertext and optional associated data.

Associated data can bind visible protocol fields—such as version or record identifier—to the ciphertext. Modification causes verification failure. Decryption must not release unauthenticated plaintext.

Many AEAD schemes require a **nonce**, a number used once under a key according to scheme rules. A nonce need not be secret. Reuse can catastrophically break confidentiality or authenticity. Random nonce generation is safe only when size and collision probability satisfy the construction; counter-based nonces require durable uniqueness.

Conceptual use with a high-level library:

~~~python
import os
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

key = AESGCM.generate_key(bit_length=256)
cipher = AESGCM(key)

nonce = os.urandom(12)
associated_data = b"record:v1:A17"
plaintext = b"confidential reading"

ciphertext = cipher.encrypt(
    nonce,
    plaintext,
    associated_data,
)
recovered = cipher.decrypt(
    nonce,
    ciphertext,
    associated_data,
)
assert recovered == plaintext
~~~

The example exposes mechanics, not a complete key-management design. The application must store or transmit the nonce with the ciphertext, protect the key separately, preserve associated data exactly, handle authentication failure without oracle leakage, rotate keys under a versioned envelope, and never copy this illustrative key handling into production unexamined.

### 19.19.1 Nonce discipline and construction limits

AES-GCM commonly uses a 96-bit nonce and requires uniqueness for every encryption under one key. Reusing a nonce can reveal relationships between plaintexts and enable authentication forgeries. Random selection makes collisions probabilistic; counters make uniqueness an allocation and durability problem. After process rollback, backup restoration, concurrent allocation, or key reuse across hosts, a naïve counter can repeat. A library cannot infer the distributed lifecycle of an application key.

ChaCha20-Poly1305 also requires nonce uniqueness under a key and can perform well without hardware AES acceleration. AES-GCM and ChaCha20-Poly1305 are constructions with usage limits; very large message counts or volumes under one key raise forgery or collision bounds. Current library and protocol guidance determines rekey thresholds.

Do not split one logical plaintext into independently encrypted chunks without authenticating sequence, total structure, record identity, and finality. Otherwise an attacker may reorder, duplicate, omit, or splice valid chunks. A streaming authenticated-encryption protocol needs explicit record numbers and a truncation signal, or a reviewed construction designed for streams.

### 19.19.2 Versioned encrypted envelopes

An encrypted record needs enough visible metadata to select the decryption policy without trusting that metadata unauthenticated. A typical envelope includes format version, algorithm suite fixed by that version, key identifier, nonce, ciphertext/tag, and associated context. The key identifier chooses a key; it is not secret and must be authenticated as associated data so substitution cannot redirect interpretation.

~~~python
from __future__ import annotations

import os
from dataclasses import dataclass

from cryptography.hazmat.primitives.ciphers.aead import AESGCM


@dataclass(frozen=True)
class SealedRecord:
    version: int
    key_id: str
    nonce: bytes
    ciphertext: bytes


def seal_record(key: bytes, key_id: str, record_id: str, plaintext: bytes) -> SealedRecord:
    nonce = os.urandom(12)
    context = frame_fields(b"sealed-record", key_id.encode(), record_id.encode())
    ciphertext = AESGCM(key).encrypt(nonce, plaintext, context)
    return SealedRecord(1, key_id, nonce, ciphertext)


def open_record(key: bytes, record_id: str, sealed: SealedRecord) -> bytes:
    if sealed.version != 1 or len(sealed.nonce) != 12:
        raise ValueError("unsupported encrypted record")
    context = frame_fields(b"sealed-record", sealed.key_id.encode(), record_id.encode())
    return AESGCM(key).decrypt(sealed.nonce, sealed.ciphertext, context)
~~~

The example assumes the caller has securely mapped `key_id` to the supplied key and has a nonce strategy appropriate to the key’s scope. It binds a database record identity so ciphertext copied to another record fails verification. Production code must bound every field, collapse authentication failures to a safe interface, and use a maintained envelope policy.

Authentication failure is ordinary adversarial input and must produce no plaintext or detailed oracle. Do not retry decryption under arbitrary old algorithms or keys until something succeeds; that creates algorithm-confusion and cost problems. Select one suite from trusted version metadata, authenticate all relevant context, and fail closed.

Encryption does not erase metadata. Ciphertext length, access time, key identifier, record count, communication peers, and update pattern may remain visible. Padding and traffic shaping can reduce selected leakage but add complexity and cost; state the metadata threat before claiming confidentiality.

> **Common misconception 19.48 — “A random nonce cannot repeat.”**  
> It has a collision probability that grows with the number of encryptions. Whether that probability is acceptable depends on nonce size, construction, key scope, and usage.

> **Common misconception 19.49 — “AEAD protects every property of an encrypted record.”**  
> It protects plaintext confidentiality and authenticated bytes under its model. Length, timing, access pattern, key use, endpoint compromise, and replay can remain.

> **Common misconception 19.50 — “Each encrypted chunk being authentic makes a file authentic.”**  
> Valid chunks can still be reordered, omitted, duplicated, or spliced unless position, identity, sequence, and finality are authenticated.
