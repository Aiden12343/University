# 19.2 Security is a property relative to a threat model

**Cybersecurity** is the discipline of managing risks to information systems and the people and institutions dependent on them. “Secure” is not an absolute adjective. A paper archive can resist remote attackers and fail against fire. An encrypted database can resist stolen-disk inspection and disclose records through an over-authorised application. Security claims require a **threat model**.

A threat model identifies:

1. **assets**—what has value or requires protection;
2. **actors**—users, administrators, services, outsiders, insiders, and operators;
3. **adversary capabilities**—access, resources, knowledge, persistence, and constraints;
4. **trust boundaries**—places where authority or validation assumptions change;
5. **attack surface**—reachable interfaces through which behaviour can be influenced;
6. **security objectives**—properties to preserve;
7. **controls**—measures reducing likelihood or impact;
8. **residual risk**—risk remaining after controls.

An **asset** can be data, money, availability, safety, reputation, legal compliance, cryptographic keys, or a person’s autonomy. An **adversary** is an actor intentionally attempting to violate an objective. A **threat** is a potential cause of harm. A **vulnerability** is a weakness that permits a threat to violate an objective. An **exploit** is a method that uses a vulnerability. **Risk** combines uncertainty about occurrence with consequence; multiplying one guessed probability by one guessed monetary loss is only one simplified model.

### Worked example 19.1 — Threat-model a file-upload feature

Suppose employees upload PDF invoices for later review.

Assets include invoice confidentiality, reviewer workstation integrity, storage availability, correct association with accounts, and an audit trail. Actors include employee, reviewer, web service, scanning service, storage service, administrator, and external attacker. Trust boundaries occur at the browser/service interface, service/storage identity, scanner execution environment, and reviewer download.

Threats include:

- unauthorised employee reads another account’s invoice;
- oversized uploads exhaust memory or storage;
- a non-PDF file exploits a parser;
- a filename traverses out of the intended directory;
- malicious active content harms a reviewer;
- duplicate submissions cause duplicate payment;
- logs disclose invoice contents;
- retention exceeds policy.

Controls include authenticated object-level authorisation, generated storage names, content and size limits, isolated parsing, asynchronous scanning, idempotency keys, encryption, restricted storage identities, audit records, quarantine, retention deletion, and reviewer-safe rendering. No single “file type check” solves the problem.

### 19.2.1 From system model to security invariants

A threat model begins with a system model: components, principals, stores, communications, administrative owners, external dependencies, and lifecycle transitions. A **data-flow diagram** represents processes, stores, external entities, and flows. Its value is not graphical notation itself but the questions forced at each crossing: which principal sends these bytes, what authenticates it, what parser interprets them, which authority receives them, what persists, and which failure is visible to whom?

A **security invariant** is a property required to hold across every permitted transition. “Only the account owner or a delegated reviewer can read an invoice” is stronger than “the download endpoint checks a role”, because it applies to previews, exports, search, backups, support tools, and future endpoints. “Every released artifact is attributable to a reviewed source revision and approved build identity” similarly spans repository, CI, registry, and deployment.

Write invariants before enumerating attacks. They provide test oracles and prevent a checklist from becoming the objective. For each invariant, record assumptions: identity provider honest, kernel isolation functioning, cryptographic keys undisclosed, clocks within bounds, administrator actions audited, or dependencies returning schema-conforming data. An assumption is not a control; it is a condition under which the claim remains valid.

~~~python
from dataclasses import dataclass
from enum import StrEnum


class Objective(StrEnum):
    CONFIDENTIALITY = "confidentiality"
    INTEGRITY = "integrity"
    AVAILABILITY = "availability"


@dataclass(frozen=True)
class ThreatCase:
    asset: str
    action: str
    objective: Objective
    preconditions: tuple[str, ...]
    controls: tuple[str, ...]
    residual_uncertainty: str


invoice_read = ThreatCase(
    asset="invoice A17",
    action="read through another account's identifier",
    objective=Objective.CONFIDENTIALITY,
    preconditions=("attacker has an ordinary account",),
    controls=("object-level authorisation", "non-disclosing errors"),
    residual_uncertainty="support and export paths need separate evidence",
)
~~~

The data class does not calculate risk. It forces one threat statement to name the asset, attempted violation, prerequisites, controls, and uncertainty. A model represented in data can be reviewed for missing owners and tested against evidence, but its completeness still depends on human inquiry.

### 19.2.2 Abuse cases, attack trees, and taxonomies

An **abuse case** describes an undesired interaction from an actor’s perspective: “as a contractor whose access has expired, I obtain a retained export”. An **attack tree** refines an adversary goal into alternative and conjunctive subgoals. If the root is “publish an unauthorised package”, children may include compromise a maintainer, compromise CI, seize the package name, substitute an artifact in storage, or persuade a consumer to use another index. Tree structure exposes shared controls and alternative paths.

Taxonomies such as STRIDE—spoofing, tampering, repudiation, information disclosure, denial of service, and elevation of privilege—are prompts, not proofs. They can stimulate questions at a boundary but do not establish likelihood, domain impact, privacy harm, safety effects, or the completeness of the system model. Likewise, a catalogue of common weaknesses helps classify known defect patterns but does not replace reasoning about the particular system.

Threat models require maintenance. New features add flows, dependencies change ownership, attackers gain techniques, mitigations decay, and deployment topology changes. Revisit the model at architectural changes, new sensitive data, identity changes, incident findings, and scheduled review points. Store decisions beside the system’s design history so later engineers can distinguish an accepted risk from an unnoticed omission.

### 19.2.3 Risk without false precision

Qualitative risk assessment orders attention using defined scales for likelihood and consequence. Quantitative assessment estimates frequency and loss distributions. Both can be useful; both can mislead. Ordinal labels such as “high” are not numbers that support arbitrary multiplication, while a numerical model built from unsupported point estimates creates precision without knowledge.

Separate at least four questions: how reachable the condition is, whether an adversary can exploit it, what technical privilege or state change follows, and what harm that consequence produces in this organisation. Record uncertainty and evidence. A remotely reachable flaw in a retired test system and a local flaw in an administrator tool can reverse priority when actual exposure, privilege, or safety is considered.

A **risk treatment** can avoid the activity, reduce likelihood or impact, transfer specified financial consequences, or accept residual risk. Acceptance is an accountable, time-bounded decision with monitoring and review—not the absence of remediation. Controls can introduce new risks: account lockout creates availability loss; detailed telemetry creates privacy exposure; automatic blocking can be manipulated against victims.

> **Common misconception 19.3 — “A threat model is a list of famous attacks.”**  
> It is an argument relating a particular system, assets, actors, boundaries, objectives, assumptions, controls, and remaining uncertainty. Attack names are prompts within that argument.

> **Common misconception 19.4 — “A high severity score determines remediation priority.”**  
> Generic technical severity omits deployment exposure, exploit activity, asset value, compensating controls, blast radius, and operational consequence. Priority is contextual.

> **Common misconception 19.5 — “Once written, a threat model is complete.”**  
> Models age as code, dependencies, topology, data, identities, and adversaries change. A stale model can legitimise assumptions that no longer hold.
