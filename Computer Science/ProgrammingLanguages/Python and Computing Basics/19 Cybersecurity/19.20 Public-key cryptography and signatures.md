# 19.20 Public-key cryptography and signatures

In **public-key cryptography**, a key pair has a private key kept secret and a public key intended for distribution. Uses include:

- encryption to a public-key holder;
- agreement on shared key material;
- digital signatures verifiable with a public key.

A **digital signature** binds a private key to a message under an algorithm; holders of the public key can verify. This supports authenticity and integrity if public-key identity is trusted and private-key custody holds. It does not prove that a human understood, intended, or was legally bound by the message.

Signing raw ambiguous concatenations is unsafe. Sign a versioned canonical representation including domain context so a signature for one protocol cannot be transplanted into another. Key compromise requires revocation and incident handling; signatures made before or after compromise have different evidential status according to timestamps and policy.

Hybrid encryption uses public-key operations to establish or wrap symmetric key material, then AEAD for data. High-level protocols such as TLS implement carefully designed variants; applications should not reconstruct them from primitives.

### 19.20.1 Key agreement, encryption, and forward secrecy

Public-key encryption and key agreement are different constructions. In key agreement, parties contribute key material and derive a shared secret; authentication must bind the exchanged ephemeral keys to identities or an active adversary can interpose. A key-derivation function then turns the shared secret plus transcript context into separated traffic keys. Raw group elements or shared secrets are not normally used directly as encryption keys.

**Forward secrecy** means compromise of a long-term authentication key does not by itself reveal past session keys, assuming ephemeral private values were destroyed and the protocol was correct. It does not protect a session compromised while active, plaintext logged by endpoints, or encrypted archives made under a long-term data key. TLS 1.3 obtains forward-secret key agreement in its ordinary ephemeral modes; applications should use the protocol rather than rebuilding its handshake.

Hybrid encryption generates a random data-encryption key, encrypts data with AEAD, and encapsulates or wraps the data key for each authorised recipient. Recipient identity, algorithm suite, wrapped-key list, and ciphertext context must be authenticated. Removing one recipient’s wrapped key prevents future access only if that recipient did not retain the data key or plaintext.

### 19.20.2 Signatures, encodings, and identity

Signature algorithms accept bytes, not abstract documents. JSON object order, duplicate names, Unicode, whitespace, numbers, and line endings make naïve “sign the JSON” schemes ambiguous. Define a canonical representation or sign a protocol-defined binary structure. Include domain, version, role, resource, expiry, and algorithm policy in the signed content.

Some signature representations admit more than one encoding of related mathematical values; verification libraries and protocols must enforce their specified canonical rules. Never compare signature bytes to establish that two parties signed “the same thing” unless the scheme and encoding guarantee determinism. Verify through the library’s algorithm-specific API.

A public key becomes meaningful only through a trust mechanism: direct provisioning, a certificate chain to an accepted root, a transparency log, a web of endorsements, or a pinned identity. X.509 certificate validation checks name, chain, time, usage, constraints, algorithms, and revocation policy under a trust store. A cryptographically valid self-signed certificate establishes an internally consistent key binding, not that the presented identity should be trusted.

~~~python
from cryptography.exceptions import InvalidSignature
from cryptography.hazmat.primitives.asymmetric.ed25519 import Ed25519PublicKey


def verify_release_signature(
    public_key: Ed25519PublicKey,
    *,
    project: str,
    version: str,
    artifact_digest: bytes,
    signature: bytes,
) -> bool:
    message = frame_fields(
        b"release-signature",
        project.encode("utf-8"),
        version.encode("ascii"),
        artifact_digest,
    )
    try:
        public_key.verify(signature, message)
    except InvalidSignature:
        return False
    return True
~~~

The function verifies possession of the private key corresponding to an already trusted public key and binds project, version, and digest. It does not establish how the public key was enrolled, whether the signer was authorised to publish that version, whether the artifact is safe, or whether the signature is fresh rather than replayed.

### 19.20.3 Certificates, transparency, and compromise

Certificate expiry limits ordinary acceptance but does not revoke a still-valid certificate immediately. Revocation mechanisms have availability and privacy trade-offs and are not uniformly enforced. Short-lived certificates reduce exposure and encourage automated renewal, while renewal authority becomes critical infrastructure. Certificate Transparency makes issued web certificates publicly auditable; it helps discover misissuance but does not block every attack by itself.

Private signing keys deserve stronger separation than verification keys because compromise enables forgery. Use hardware-backed or managed signing where the risk warrants it, require reviewed release subjects, limit identities and algorithms, and log operations. Following compromise, determine when it began, revoke or distrust affected keys, re-establish identity through an independent path, and reassess every signature in the uncertainty window.

> **Common misconception 19.51 — “Public-key encryption removes the need to trust key distribution.”**  
> Encryption to the wrong public key protects data for the attacker. Identity binding and trust establishment are fundamental.

> **Common misconception 19.52 — “A certificate is trustworthy because its signature validates.”**  
> Validation also requires an accepted trust anchor, name, time, usage, constraints, algorithms, and policy. A self-signed attacker certificate can be internally valid.

> **Common misconception 19.53 — “Forward secrecy protects stored encrypted data.”**  
> It concerns past session keys after later long-term-key compromise. Data encrypted under retained storage keys has a different lifecycle.
