# 19.21 Password storage

A password has low and uneven entropy because humans choose memorable strings. Fast general hashes let an attacker test guesses rapidly after database theft. A **password-hashing function** is deliberately expensive and salted. Current choices include Argon2id, scrypt, bcrypt under appropriate limits, and PBKDF2 in compatibility environments, with parameters selected from current authoritative guidance.

A **salt** is a unique non-secret value generated for each password. It defeats precomputed tables and ensures identical passwords ordinarily yield different stored verifiers. A server-side **pepper** is an optional additional secret stored separately; it complicates rotation and does not replace strong password hashing.

Use a framework or maintained password library:

~~~python
from argon2 import PasswordHasher
from argon2.exceptions import VerifyMismatchError

hasher = PasswordHasher()
stored = hasher.hash("correct horse battery staple")

try:
    valid = hasher.verify(stored, "candidate password")
except VerifyMismatchError:
    valid = False

if valid and hasher.check_needs_rehash(stored):
    replacement = hasher.hash("candidate password")
~~~

The encoded verifier includes salt and parameters. Successful login is an opportunity to upgrade outdated parameters. The literal passwords are pedagogical only; real credentials arrive through protected input and must not be logged.

Password policy should favour sufficient length, reject known-compromised choices where lawful and possible, permit password managers and paste, rate-limit online guesses, and provide phishing-resistant multi-factor options. Frequent arbitrary forced changes can produce predictable variants and are not a substitute for breach response.

### 19.21.1 Online and offline guessing

Online guessing passes through the live verifier and can be rate-limited, monitored, challenged, and blocked. Offline guessing begins after an attacker obtains stored verifiers and can proceed without the service. Password hashing primarily raises the cost of the offline attack; account lockout cannot help once the database is stolen.

The relevant entropy is the distribution from which people actually choose passwords, not the maximum combinations permitted by a character policy. Composition rules often cause predictable substitutions. Long passwords generated by a manager can carry high entropy; multiword user-chosen phrases may be memorable but still follow biased choices. Screening against compromised-password corpora addresses known choices without prescribing arbitrary symbol rituals.

Argon2id combines memory and computation cost to impede massively parallel specialised guessing. Parameters include memory, passes, and parallelism, and should be benchmarked on the actual authentication tier under expected concurrency. A per-verification setting that is tolerable alone can become a denial-of-service vector at login volume. Maintain a concurrency budget and upgrade parameters on successful authentication when the stored encoding indicates older policy.

### 19.21.2 Input handling and verifier lifecycle

Password length should be measured consistently and bounded generously enough for password-manager output while preventing resource abuse. Do not silently truncate unless a legacy algorithm’s limitation is explicitly handled before enrolment. Unicode normalisation is a policy choice: changing it later can make existing credentials unverifiable, while invisible or confusable characters create usability hazards. The safest operational rule is to preserve exact input under one documented encoding and let the password-hashing library consume bytes consistently.

Use a generic remote error for unknown account and wrong password, but recognise that timing, recovery, rate-limit, and registration paths can still enumerate accounts. Equalise major code paths where practical, monitor abuse, and avoid elaborate sleeps that create easy denial of service.

A pepper is a server-held secret incorporated through a supported construction and stored separately from the verifier database. It can raise the value of a database-only theft but creates rotation and availability obligations. If compromise requires resetting every password, rehearse that event. Do not improvise a pepper by concatenating a global string around a password hash whose security proof assumes another interface.

### 19.21.3 Authentication beyond passwords

Password reset is an alternative authentication protocol and often the easiest route into an account. Reset tokens need high entropy, narrow purpose, short lifetime, one-time transactional use, safe delivery, and invalidation policy. Recovery that relies on public biographical questions is weak. Support staff need constrained workflows resistant to social engineering and insider abuse.

Passkeys and WebAuthn credentials use scoped public-key operations and can provide phishing resistance. Their security and usability depend on authenticator enrolment, device or synchronisation model, recovery, related origins, user verification, and revocation. Maintain an authenticator inventory and notify users of changes through an independent channel where risk warrants it.

> **Common misconception 19.54 — “Account lockout protects stolen password hashes.”**  
> Offline attackers test guesses locally. Deliberately expensive salted hashing is the control for verifier theft; lockout affects online attempts.

> **Common misconception 19.55 — “Complexity rules measure password strength.”**  
> Human choice distributions remain predictable under many rules. Length, compromised-choice screening, password managers, rate controls, and strong hashing address different risks.

> **Common misconception 19.56 — “Password reset is merely an account convenience.”**  
> It is an authentication path that can override the primary credential. Its identity proofing, tokens, support process, notifications, and abuse controls require equal scrutiny.
