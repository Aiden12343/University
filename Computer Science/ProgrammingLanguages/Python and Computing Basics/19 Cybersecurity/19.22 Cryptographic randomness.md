# 19.22 Cryptographic randomness

Security tokens need unpredictability against an adversary who knows the algorithm and observes other outputs. Python’s <code>random</code> module is designed for simulation, not security. The <code>secrets</code> module uses the operating system’s cryptographic source.

~~~python
import secrets

session_id = secrets.token_urlsafe(32)
reset_token = secrets.token_bytes(32)
choice = secrets.choice(
    "ABCDEFGHJKLMNPQRSTUVWXYZ23456789"
)
~~~

Token length should be based on entropy and online/offline guessing conditions, not character count alone. URL-safe encoding expands random bytes into text; 32 random bytes contain 256 bits before encoding. Token databases can store a keyed or cryptographic digest rather than the bearer token, limiting disclosure from a read-only database compromise, provided verification and lookup are designed correctly.

Randomness does not grant authorisation. A bearer token conveys whatever authority the server associates with it; scope and expiry reduce consequence of theft.

### 19.22.1 Entropy sources, DRBGs, and process lifecycle

An operating system gathers uncertainty from hardware and runtime events, maintains internal state, and exposes a cryptographic random interface. A deterministic random bit generator expands secret state into output and is reseeded under its design. Application code should use the operating-system-backed interface through `secrets` or maintained cryptographic libraries, not estimate environmental entropy from time, process identifiers, network addresses, or user names.

Boot-time entropy and cloned machine images historically caused repeated keys or tokens when systems began from identical state. Modern platforms address these risks, but appliances and constrained devices need particular validation. Forking can duplicate userspace generator state; a cryptographic library must reseed or use an operating-system interface with appropriate fork behaviour. The standard `random` module deliberately permits deterministic seeding for simulation and therefore cannot serve adversarial unpredictability.

Health tests should follow the random source’s design. Applying ad hoc statistical tests to a small output sample cannot prove cryptographic unpredictability; a deterministic encrypted counter can look statistically random while being entirely predictable to a key holder. Conversely, ordinary clusters in random output are not evidence of failure.

### 19.22.2 Token entropy and storage

If a token contains (b) independent random bits and an attacker can make (q) guesses, the elementary success bound is about (q/2^b), absent leakage or bias. The effective security can be much lower when generation is biased, logs disclose values, comparisons leak, endpoints permit unlimited attempts, or tokens remain valid indefinitely. Choose entropy from the attack budget and consequence, then apply expiry and attempt controls.

Encoding does not add entropy. Hex uses two characters per byte; URL-safe base64 encodes approximately six bits per character with details of padding and alphabet. A 32-character human alphabet token carries (32 \log_2(|A|)) bits only when every character is independently uniform over alphabet (A). `secrets.choice` supports such generation; `%` reduction over random bytes can introduce bias when the alphabet size does not divide 256.

Store a reset or API bearer token as a digest or keyed digest when the server only needs equality verification. On presentation, hash the candidate under the same versioned scheme, look up or compare, check purpose and expiry, and consume atomically. Database readers then do not immediately obtain live bearer values, although online guessing and application compromise remain.

~~~python
import hashlib
import secrets


def issue_bearer_token() -> tuple[str, bytes]:
    token = secrets.token_urlsafe(32)
    verifier = hashlib.sha256(token.encode("ascii")).digest()
    return token, verifier


def matches_bearer_token(candidate: str, verifier: bytes) -> bool:
    actual = hashlib.sha256(candidate.encode("ascii")).digest()
    return secrets.compare_digest(actual, verifier)
~~~

The high-entropy token makes a fast digest appropriate for database-at-rest protection; this is not password storage. Production records also need an identifier, purpose, subject, scope, creation and expiry, use count, and transactional one-time consumption where relevant.

> **Common misconception 19.57 — “A random-looking string is unpredictable.”**  
> Appearance says nothing about generator state, entropy, bias, repetition, leakage, or an adversary’s knowledge. Use an operating-system cryptographic source.

> **Common misconception 19.58 — “Base64 makes a token stronger.”**  
> It represents existing bytes in text. Security comes from the entropy and lifecycle of those bytes, not the encoding alphabet.
