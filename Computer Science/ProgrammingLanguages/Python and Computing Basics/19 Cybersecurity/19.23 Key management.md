# 19.23 Key management

Cryptographic keys require lifecycle management:

1. generation from an approved source;
2. identity and purpose labelling;
3. protected storage;
4. controlled use;
5. rotation;
6. revocation;
7. destruction under realistic media semantics;
8. audit and recovery.

Encryption keys and signing keys should be separated by purpose. Development and production keys should differ. Keys should not be embedded in source code or ordinary configuration files. Hardware security modules and managed key services can restrict extraction and record operations, but applications authorised to request decryption can still leak plaintext.

**Envelope encryption** encrypts data with a data-encryption key and wraps that key with a key-encryption key managed separately. Rotation of the wrapping key can rewrap small keys without re-encrypting all data, subject to service and threat model.

Backups need key recovery; otherwise encryption can turn an operational failure into permanent data loss. Conversely, retaining every old key defeats deletion policies. Availability and confidentiality must be designed together.

### 19.23.1 Hierarchies, envelopes, and cryptoperiods

A key hierarchy limits the amount of data and authority under one key. A root or master key protects key-encryption keys; those wrap data-encryption keys; derived subkeys serve one protocol context. Compromise at a higher level has wider consequence, so higher-level keys receive stronger isolation, less frequent direct use, dual control where appropriate, and more rigorous recovery.

A **cryptoperiod** is the interval during which a key is authorised for a use. It is not necessarily the interval during which old ciphertext remains decryptable. A key can stop encrypting new data yet remain available for decryption until records are migrated or expire. Track states such as pending, active, decrypt-only, revoked, compromised, and destroyed. Applications should reject a decrypt-only key for new encryption.

Envelope encryption permits frequent data keys while a managed key service controls wrapping. Associated data should bind tenant, resource, purpose, and envelope version. The key service’s access policy must prevent one workload from unwrapping another tenant’s key; ciphertext is not self-authorising. Rate and anomaly monitoring on decrypt operations can reveal compromise and also create an availability dependency.

~~~python
from dataclasses import dataclass
from enum import StrEnum


class KeyState(StrEnum):
    ACTIVE = "active"
    DECRYPT_ONLY = "decrypt-only"
    REVOKED = "revoked"


@dataclass(frozen=True)
class KeyMetadata:
    key_id: str
    purpose: str
    state: KeyState
    algorithm: str


def permits_operation(metadata: KeyMetadata, operation: str) -> bool:
    if metadata.state is KeyState.REVOKED:
        return False
    if operation == "encrypt":
        return metadata.state is KeyState.ACTIVE
    if operation == "decrypt":
        return metadata.state in {KeyState.ACTIVE, KeyState.DECRYPT_ONLY}
    return False
~~~

This is policy metadata, not key storage. Real policy also checks tenant, caller, time, algorithm suite, compromise status, and approval. Keeping states explicit prevents a migration tool from accidentally using an old key for new data.

### 19.23.2 Hardware and managed key boundaries

A hardware security module or managed key service can keep keys non-exportable and perform cryptographic operations behind an authenticated interface. “Non-exportable” constrains direct key extraction, but an authorised or compromised client may still request signatures or decryptions. Command authorisation, quotas, approval, audit, and context binding remain essential.

Availability planning includes regional failure, service quotas, credential bootstrap, network partitions, and disaster recovery. Caching an unwrapped key locally improves availability while weakening central control. Make this trade-off explicit, minimise cache lifetime, protect process memory, and ensure a restarted instance cannot silently fall back to a plaintext key file.

Dual control requires two independent authorised parties or mechanisms for selected high-impact operations. Split knowledge means no one party possesses the whole secret. They solve different problems and can be undermined when both approvals occur through one compromised workstation or organisation.

### 19.23.3 Deletion, escrow, and recovery

Cryptographic erasure destroys all usable copies of a key so retained ciphertext becomes infeasible to decrypt. Its claim depends on complete key inventory: backups, replicas, memory, logs, escrow, wrapped copies, snapshots, and derived keys. Storage remanence no longer matters only if no key survives and the algorithm remains secure.

Key escrow or recovery protects availability but creates a concentrated confidentiality target. Define who can recover, under which approvals, with what evidence and notification, how often recovery is tested, and how abuse is detected. An untested sealed envelope is not a recovery plan; a frequently exercised universal key can become ordinary ambient authority.

Compromise response distinguishes suspected exposure, confirmed extraction, and unauthorised use. Stop new use, preserve evidence, identify dependent keys and data, rotate or re-encrypt under a clean trust path, revoke verification trust where relevant, and communicate consequences. Merely marking a key “revoked” does not undo plaintext already disclosed or signatures already accepted.

> **Common misconception 19.59 — “A cloud key service prevents key misuse.”**  
> It can prevent extraction and centralise policy, but authorised clients can still request harmful operations. Identity, context, quotas, audit, and application compromise matter.

> **Common misconception 19.60 — “Key rotation means re-encrypting all data immediately.”**  
> Rotation can stop new encryption, retain decrypt-only versions, rewrap data keys, or migrate records gradually. The correct transition follows the compromise and availability model.

> **Common misconception 19.61 — “Deleting one master key guarantees cryptographic erasure.”**  
> The claim holds only if every usable copy, backup, cache, escrow share, derived key, and alternative plaintext representation is gone.
