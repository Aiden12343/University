# 19.24 Race conditions as security defects

A **time-of-check/time-of-use** flaw occurs when a program checks a condition and later acts while an adversary can change the referenced state between operations. Path validation followed by opening is one example. Authorisation checked against mutable ownership before a delayed write is another.

Atomic operating-system or database operations narrow the window:

- create with exclusive flags rather than “check absent, then create”;
- update with a version precondition rather than “read, decide, write”;
- perform authorisation and mutation in one transaction where the data model permits;
- use directory-relative descriptors rather than re-resolving a pathname.

Locks within one Python process do not coordinate independent processes or external actors unless they share the same lock service and failure model. The security boundary determines the synchronisation mechanism.

### 19.24.1 Security invariants under concurrency

Many security checks are predicates over mutable state: account active, token unused, balance sufficient, membership current, object owned, quota available. A correct sequential check can fail under interleaving. Two workers each observe an unused reset token, both pass, and both consume it; two transfers each observe sufficient balance and jointly overdraw; authorisation changes after a read but before a write.

Express the invariant in the storage system that serialises the competing operation. A unique constraint can enforce one redemption record. A conditional update can consume a token only while `used_at IS NULL` and report whether exactly one row changed. Row locks or serialisable transactions can protect multi-row invariants, with complete transaction retry on serialisation failure. Application locks are advisory unless every actor participates and lock failure is handled.

~~~python
def consume_reset_token(connection, token_digest: bytes, used_at: str) -> bool:
    with connection:
        cursor = connection.execute(
            """
            UPDATE reset_tokens
               SET used_at = ?
             WHERE digest = ?
               AND used_at IS NULL
               AND expires_at > ?
            """,
            (used_at, token_digest, used_at),
        )
        return cursor.rowcount == 1
~~~

The conditional write combines validation and state change at one database boundary. A production design should use a proper timestamp type and transaction semantics, bind the token to purpose and subject, invalidate related sessions as policy requires, and avoid revealing which predicate failed.

### 19.24.2 Distributed authority and stale actors

A distributed lock can expire while its holder is paused. The holder later resumes and writes after another process acquired the lock. A **fencing token** is a monotonically increasing authority number attached to each grant; the protected resource rejects operations older than the greatest number seen. Without enforcement at the resource, a lease merely informs well-behaved clients.

Optimistic concurrency uses a version in a conditional update: change this object only if version 7 still holds. HTTP entity tags and database compare-and-swap operations express the same shape. On conflict, recompute authorisation and domain decisions from current state; blindly retrying a stale mutation can reinstate the race.

Python’s GIL does not make a security invariant atomic. Bytecode can switch around I/O, C extensions can release the GIL, multiple processes and hosts do not share it, and free-threaded builds change assumptions. Choose synchronisation from the state owner, not from interpreter folklore.

> **Common misconception 19.62 — “Checking immediately before use closes the race.”**  
> Another actor can change state between separate operations. Use an atomic primitive or transaction that owns both predicate and state transition.

> **Common misconception 19.63 — “A distributed lock guarantees exclusive writes.”**  
> Expiry, pauses, partitions, failover, and stale holders can violate exclusivity unless the resource enforces fencing or equivalent ordering.
