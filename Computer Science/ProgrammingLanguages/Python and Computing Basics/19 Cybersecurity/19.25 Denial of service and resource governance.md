# 19.25 Denial of service and resource governance

**Denial of service** is degradation or prevention of authorised availability. An attacker need not crash a program; consuming disproportionate CPU, memory, disk, descriptors, locks, network capacity, queue slots, or expensive third-party calls can suffice.

Controls include:

- input and output size limits;
- timeouts and deadlines;
- bounded queues and concurrency;
- rate limits per appropriate identity and global budgets;
- pagination and query cost limits;
- streaming;
- computationally bounded parsers;
- quotas;
- isolation;
- caching under correct keys;
- graceful degradation.

Rate limiting by IP address alone can punish users behind shared translation and can be bypassed through distributed sources. Account identifiers can be attacker-created. A layered abuse policy combines network, account, device, cost, behaviour, and global capacity while avoiding discriminatory or privacy-invasive inference.

Regular expressions can exhibit catastrophic backtracking for crafted inputs under some engines and patterns. Prefer linear-time constructions, bound input length, and test adversarial cases. Algorithmic complexity is a security property.

### 19.25.1 Cost asymmetry and admission control

A denial-of-service path often amplifies cheap attacker work into expensive defender work: a small compressed body expands, one query fans out, an unauthenticated request invokes password hashing, a cache miss triggers many upstream calls, or a tiny datagram induces a large reflected response. Model cost at every stage—bytes, CPU, memory, descriptors, locks, database rows, third-party fees, human attention—and identify who can cause it.

Admission control should happen before scarce work. Bound request headers and body while reading, not after buffering. Apply connection and concurrency limits before expensive parsing. Authenticate only after cheap protocol validation, yet ensure authentication itself has a separate budget. Reserve capacity for health, administration, and critical operations so overload of one class does not consume all workers.

Rate, concurrency, and quota are different. A token bucket permits a long-run rate with bounded burst; a concurrency limit constrains in-flight work; a quota limits cumulative consumption over a period or account lifecycle. A caller can obey a request-rate limit while holding every connection on slow operations. Apply the control matching the scarce resource.

~~~python
from dataclasses import dataclass


@dataclass
class TokenBucket:
    capacity: float
    refill_per_second: float
    tokens: float
    updated_at: float

    def admit(self, now: float, cost: float = 1.0) -> bool:
        if cost <= 0:
            raise ValueError("cost must be positive")
        elapsed = max(0.0, now - self.updated_at)
        self.tokens = min(self.capacity, self.tokens + elapsed * self.refill_per_second)
        self.updated_at = now
        if self.tokens < cost:
            return False
        self.tokens -= cost
        return True
~~~

This local model explains token-bucket arithmetic. A distributed limiter needs atomic shared state or a deliberately approximate allocation, a trusted monotonic time model, bounded key cardinality, eviction policy, and failure behaviour. It does not replace a concurrency bulkhead or global overload limit.

### 19.25.2 Algorithmic and storage exhaustion

Worst-case complexity matters when an adversary controls shape. Hash-table collision attacks, deeply nested syntax, quadratic duplicate detection, regular-expression backtracking, graph explosion, and pathological database plans can turn small inputs into large work. Benchmark adversarial generators and enforce structural limits derived from capacity, not arbitrary constants copied from another system.

Disk exhaustion can arise from uploads, logs, temporary files, caches, dead letters, crash dumps, and failed cleanup. Reserve space for recovery and audit, isolate quotas by tenant and workload, cap retention, and monitor growth rate. Deleting evidence automatically during an attack can destroy incident data; define priority and protected retention.

Timeouts should be deadlines propagated through dependencies. If each layer independently spends 30 seconds, a request can occupy resources far beyond the caller’s patience. Cancellation must release database queries, child processes, locks, temporary objects, and queue leases. A timeout response without cleanup is resource leakage.

Abuse controls can harm legitimate users. IP-based limits aggregate households and carrier networks; identity-based limits can be evaded through account creation; device fingerprinting affects privacy and can discriminate. Use layered signals, appeal and recovery mechanisms, and measure false positives. Security is not achieved by transferring denial of service from the attacker to users.

> **Common misconception 19.64 — “Rate limiting solves denial of service.”**  
> Rate is one dimension. Slow concurrency, expensive requests, distributed identities, storage growth, dependency amplification, and global capacity need separate controls.

> **Common misconception 19.65 — “Returning a timeout frees the consumed resources.”**  
> Work may continue in databases, child processes, threads, queues, or remote services. Cancellation and cleanup must propagate to the actual resource owners.
