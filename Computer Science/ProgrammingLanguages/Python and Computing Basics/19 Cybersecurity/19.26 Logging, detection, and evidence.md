# 19.26 Logging, detection, and evidence

Preventive controls fail. **Detection** identifies conditions suggesting policy violation or compromise. Security telemetry should answer who performed what action, on which resource, through which service, with what result and correlation context—without recording unnecessary secret content.

An **audit log** is an append-oriented record designed to support accountability. It requires access controls, retention, time synchronisation, integrity protection, and documented event semantics. Logging an unauthenticated user-supplied name as “actor” does not establish attribution.

Useful events include:

- authentication success and failure under privacy-aware aggregation;
- credential or privilege change;
- sensitive data access;
- authorisation denial;
- administrative action;
- key-management operation;
- unusual resource exhaustion;
- security-control failure;
- deployment and configuration change.

Alerts need an owner, severity, runbook, evidence links, and false-positive management. An alert no one can investigate is accumulated noise. Attackers may deliberately trigger alerts to hide activity or exhaust responders.

Logs are untrusted input when they contain attacker-controlled fields. Store structured values, escape at display, and guard analysis systems against query or template injection.

### 19.26.1 Event semantics and trustworthy context

An event schema should distinguish observed subject, authenticated principal, delegated actor, network peer, claimed client address, action, object, decision, result, reason category, policy version, assurance level, request identifier, and trace correlation. A reverse proxy field is not trustworthy until the application knows which proxy inserted it. A user-supplied account name is a claim, not an authenticated actor.

Timestamps need a declared clock and precision. Wall-clock synchronisation supports cross-system timelines but can step or drift; monotonic time measures durations within a process. Retain ingestion time as well as producer event time when delayed or compromised sources are possible. Normalise time zones without discarding the original context required for legal or operational interpretation.

Logs need access control because they concentrate identifiers, topology, failures, and sometimes content. Minimise sensitive fields, tokenise where correlation rather than identity is needed, define retention by purpose, and audit queries. Development debugging levels must not silently become permanent production collection.

### 19.26.2 Integrity, availability, and tamper evidence

Append-only interfaces, restricted writers, remote collection, immutable retention, and cryptographic commitments can raise confidence in evidence. A local attacker controlling a process can often suppress events before they are emitted, so tamper-evident storage does not prove completeness. Loss counters, heartbeat events, independent network or identity-provider evidence, and alerting on silence help expose gaps.

Hash chaining can reveal deletion or reordering relative to a trusted checkpoint: each record commits to the previous digest and current canonical event. If an attacker can rewrite the whole chain and its starting point, it offers no protection. Periodically anchor a signed checkpoint under independently controlled authority, and version the canonical encoding.

~~~python
from hashlib import sha256


def chain_event(previous: bytes, canonical_event: bytes) -> bytes:
    if len(previous) != 32:
        raise ValueError("previous SHA-256 digest required")
    return sha256(frame_fields(b"audit-chain", previous, canonical_event)).digest()
~~~

This primitive is only one component of an audit design. Sequence numbers, canonical event encoding, durable checkpoint publication, writer identity, missing-event detection, privacy, retention, and recovery determine whether the chain is useful.

### 19.26.3 Detection engineering

A detection is an executable hypothesis about observable behaviour. It states data sources, selection, exclusions, aggregation window, threshold or model, severity, owner, response, test cases, and expected false positives. Map it to the threat behaviour it intends to reveal, but do not confuse a taxonomy mapping with effectiveness.

Evaluate **precision**—the proportion of alerts that represent the target condition—and **recall**—the proportion of target conditions detected—under available ground truth. Security operations rarely possess complete ground truth, so use simulations, incident backtesting, purple-team exercises, and data-quality monitors. An alert can fail because the rule is wrong, the source is absent, fields changed, clocks drifted, or routing broke.

Attackers can poison logs, create high-cardinality fields, induce alert floods, or mimic benign automation. Bound and validate telemetry at ingestion, isolate the monitoring plane, and rate-limit notifications without suppressing evidence. Detection latency and investigation capacity are security resources.

> **Common misconception 19.66 — “An immutable log proves every action was recorded.”**  
> Immutability protects retained entries. Compromised producers can omit, delay, mislabel, or prevent events before storage unless independent evidence detects gaps.

> **Common misconception 19.67 — “More alerts increase detection coverage.”**  
> Low-quality volume consumes analyst attention and can hide real incidents. Coverage requires reliable data, tested hypotheses, ownership, and response capacity.
