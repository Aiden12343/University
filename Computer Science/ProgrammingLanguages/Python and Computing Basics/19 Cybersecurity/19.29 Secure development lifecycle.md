# 19.29 Secure development lifecycle

A **secure development lifecycle** integrates security into ordinary engineering:

1. define security and privacy requirements;
2. threat-model designs and major changes;
3. choose maintained dependencies and minimal authority;
4. implement through safe abstractions;
5. review sensitive changes;
6. run tests, static analysis, dependency checks, and secret detection;
7. build through controlled provenance;
8. deploy with hardened configuration;
9. monitor and respond;
10. learn from incidents and retire unsupported components.

Code review looks for violated trust boundaries and invariants, not merely suspicious function names. A parameterised query can still be authorised incorrectly. A cryptographic library can be used with nonce reuse. A memory-safe parser can permit unbounded allocation.

**Fuzz testing** generates or mutates inputs to explore unexpected behaviour. Coverage-guided fuzzers use execution feedback to reach new paths. Properties—no crash, bounded memory, parse/serialise round trip, rejection of invalid forms—supply oracles. Fuzzing finds examples, not proof of absence.

Static analysis approximates program behaviour without executing every path. It can find tainted data flows, dangerous calls, and type errors. Dynamic analysis observes execution under selected inputs. Both have false positives and false negatives; tools augment reasoning.

### 19.29.1 Secure by design and secure by default

**Secure by design** places security requirements and trust boundaries in architecture before implementation. **Secure by default** means the installed or newly created state provides appropriate protection without requiring every operator to discover and enable it. A secure option hidden behind undocumented configuration does not protect ordinary deployments.

Defaults include listening interfaces, authentication, initial credentials, debug mode, telemetry, permissions, encryption policy, CORS, session cookies, administrative routes, and failure behaviour. Default-deny is appropriate for authority but needs usable enrolment and recovery; a default that operators routinely disable to function is not successful security design.

Security requirements should be testable: “an invoice is readable only by its uploader and current reviewers”; “no build triggered by an untrusted pull request can access release identity”; “a parser consumes no more than 64 MiB and 2 CPU seconds for a 10 MiB input”. Link each requirement to threat, design control, implementation location, evidence, monitoring, and owner.

### 19.29.2 Review and change control

Security-sensitive code review traces data and authority across boundaries. Reviewers ask: What principal is established? Which object is authorised? Which parser runs first? Is structure separated from data? Can state change between check and use? Which key and context protect the message? What happens under retry, cancellation, old versions, and partial deployment? Which logs or errors disclose values?

High-risk changes benefit from independent approval and small diffs. Generated lock files, workflow definitions, authentication policy, migrations, infrastructure, and key configuration deserve the same review as application code. Branch protection is ineffective if an administrator or automation can rewrite protected history without independent evidence.

Threat models and security tests should change with the code. A new export route may bypass object-level checks even if the original download endpoint remains correct. A new cache changes confidentiality and revocation timing. Treat security documentation as executable design history: review it in the same change, and retire assumptions explicitly.

### 19.29.3 Release, disclosure, and end of life

A release should have attributable source, reviewed changes, reproducible or attestable build evidence, dependency inventory, security test results, signed immutable artifacts, controlled promotion, rollback, and supported upgrade instructions. Separate building from deploying: the environment that compiles untrusted source should not directly control production.

A vulnerability-response process receives reports, triages privately, develops and tests fixes, coordinates affected parties, assigns identifiers where appropriate, publishes clear advisories, and monitors update adoption. Silence and legal threat suppress evidence; indiscriminate disclosure can expose users before mitigation. Policy should balance both under accountable timelines.

Unsupported software is a security state. Define support periods, notify owners, prevent new deployments, remove public exposure, migrate data, revoke credentials, archive necessary evidence, and eventually destroy systems and keys. An abandoned service remains an attack path even when no team considers it active.

The NIST Secure Software Development Framework groups practices around preparing the organisation, protecting software, producing well-secured software, and responding to vulnerabilities. A framework supplies outcomes and vocabulary; each project still needs concrete controls and evidence.

### 19.29.4 Security economics and organisational incentives

Security work consumes engineering time, operational capacity, money, and user attention; insecurity externalises costs onto customers, responders, and society. Rational local decisions can therefore produce poor collective outcomes. A feature team measured only on delivery speed may postpone hardening whose benefits appear in another team’s incident budget. A supplier may stop updates before customers can replace embedded equipment. An operator may suppress noisy alerts to meet service metrics while losing detection.

Governance must align decision rights with consequences. Name owners for assets and controls, fund maintenance and end-of-life work, include security outcomes in release criteria, and make accepted risk visible to an authority able to bear it. Security teams should provide paved paths—maintained authentication, secret delivery, logging, build provenance, and sandbox services—so the protected method is less costly than improvisation. Central platforms still need product-specific threat models and escape routes for justified exceptions.

Metrics shape behaviour. Counting vulnerabilities found can reward insecure production or discourage reporting; counting vulnerabilities closed can encourage superficial status changes; demanding zero incidents encourages reclassification. Prefer a balanced set: time to revoke exposed credentials, supported-version coverage, verified restoration, critical authority reduction, detection data quality, exception age, patch deployment evidence, and recurrence of weakness classes. Interpret trends with changes in discovery effort.

Security debt resembles technical debt but includes latent adversarial consequence. Record deferred controls with threat, affected assets, compensating measures, owner, review date, and retirement plan. Interest appears as slower changes, fragile incident response, unsupported dependencies, and widening privilege. A risk register that never expires decisions becomes an archive of abandoned responsibility.

Procurement is part of the lifecycle. Customers can require vulnerability-disclosure policy, support duration, secure defaults, SBOMs, provenance, incident notification, data deletion, export, and migration. Requirements should be verifiable and proportional; a supplier questionnaire answered once is not continuing assurance. Contracts allocate duties but do not technically enforce them.

Security work must also preserve learning. Near misses, failed deployments, false alerts, and rejected threat hypotheses contain evidence. Review them without waiting for a major incident. An organisation that only studies public breaches will repeatedly rediscover its own local conditions.

> **Common misconception 19.70 — “Security review happens after implementation so it can inspect real code.”**  
> Code review is necessary, but architectural trust, authority, data collection, protocol, and recovery choices become expensive or impossible to repair late. Review spans the lifecycle.
