# 19.30 Security testing as hypothesis testing

A security test should state:

- threat and prerequisite;
- protected property;
- test environment and authorisation;
- input or action;
- expected secure result;
- evidence collected;
- cleanup;
- residual uncertainty.

“Run a scanner” is an activity, not a test specification. For object-level authorisation, construct two principals and two resources, then verify every operation rejects cross-principal access without disclosing existence beyond policy. For path confinement, generate parent segments, absolute paths, links, Unicode variants, reserved names, and concurrent changes.

Property-based testing is valuable:

~~~python
from pathlib import Path

from hypothesis import given, strategies as st


@given(st.text())
def test_confined_path_never_escapes(name: str) -> None:
    root = Path("/tmp/authorised-test-root").resolve()
    try:
        candidate = confined_path(root, name)
    except (ValueError, OSError):
        return
    assert candidate.is_relative_to(root)
~~~

The test checks the function’s ancestry property over generated strings. It does not simulate mutable symlinks or prove operating-system race safety. The test root must exist in a disposable controlled environment; a production path must never appear in such a test.

### 19.30.1 Complementary assurance methods

Unit tests examine local invariants; integration tests exercise real parsers, databases, operating-system permissions, identity providers, and cryptographic libraries; system tests cross deployed boundaries; configuration tests inspect hardened state. Contract tests ensure independently changing components agree on security-relevant fields and failure semantics. None subsumes the others.

Static application security testing reasons from source or intermediate representation. Dynamic testing sends inputs to a running application. Interactive analysis combines runtime observation with code context. Composition analysis maps dependencies to advisories. Infrastructure scanners compare configuration with policy. Secret scanners seek credential-like material. Each sees a different projection and inherits modelling, coverage, and database limits.

Fuzzing is particularly effective at parser and native boundaries. A harness should be deterministic, reset state, bound resources, expose deep code, and define oracles beyond crashes: excessive allocation, timeout, inconsistent acceptance, invariant violation, or divergent parsers. Preserve minimised counterexamples as regression cases. A billion executions of a shallow harness can provide less evidence than one well-targeted property.

Penetration testing explores how weaknesses compose in a deployed scope using human judgement. A red team emulates defined adversary objectives while testing organisational detection and response; a blue team defends; a purple exercise collaborates to improve both. These are not substitutes for continuous engineering, and a point-in-time “no findings” result expires as the system changes.

### 19.30.2 Negative, differential, and metamorphic properties

Negative tests assert prohibited transitions: one tenant cannot read another’s object; an expired authenticator cannot create a session; an unsigned artifact cannot deploy; a malformed envelope yields no plaintext. They should also verify absence of side effects, information leakage, and audit gaps.

Differential testing feeds identical inputs to independent implementations or versions and flags disagreement. This exposes parser and canonicalisation differences but cannot tell which result is correct; the specification supplies the oracle. **Metamorphic testing** transforms an input under a relation whose output should be predictable—for example, reordering semantically unordered fields should not change a canonical domain value, while changing authenticated associated data must make decryption fail.

Security regression tests must include the vulnerable path and its nearest variants without embedding dangerous live credentials or production data. Name the weakness and invariant so a future refactor does not “fix” the test by changing an incidental status code while restoring the defect.

### 19.30.3 Safe test operations and evidence

Run intrusive tests in disposable environments with synthetic data. Where production validation is necessary, use explicit approval, minimal requests, identifiable sources, rollback, monitoring, and stop conditions. Test accounts should have realistic policy but no access to unrelated real records. Clean up created tokens, files, users, and telemetry while retaining agreed evidence.

A finding report distinguishes observation from inference and includes affected component/version, prerequisite, exact security property, minimal reproduction, evidence, impact, likelihood factors, remediation options, and uncertainty. Severity should be justified, not copied blindly from a scanner. Retest the fix and check adjacent paths.

False positives consume engineering trust; false negatives create unwarranted assurance. Calibrate tools against seeded known cases, track rule versions, measure suppressions, require expiry on exceptions, and monitor whether the analysed code and deployed artifact match. Coverage is a claim about the assessment boundary, not the system as a whole.

> **Common misconception 19.71 — “Passing a penetration test certifies a system as secure.”**  
> It supplies evidence about selected objectives, scope, techniques, versions, and time. Unexamined paths, future changes, unknown weaknesses, and operational failure remain.
