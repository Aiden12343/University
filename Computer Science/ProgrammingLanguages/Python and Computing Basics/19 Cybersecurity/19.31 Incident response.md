# 19.31 Incident response

An **incident** is an event or series of events that violates or threatens policy and requires coordinated response. An incident-response lifecycle commonly includes preparation, detection, triage, containment, eradication, recovery, and learning. These phases overlap; premature eradication can destroy evidence, while delayed containment can increase harm.

Preparation establishes:

- roles and decision authority;
- contact paths independent of compromised systems;
- evidence and privacy procedures;
- logging and time synchronisation;
- backups and restoration tests;
- credential and key rotation mechanisms;
- isolation and rollback tools;
- legal, regulatory, and communications processes.

During response, maintain a timestamped decision log. Preserve original evidence with hashes and controlled custody where forensic standards apply. Do not run arbitrary exploratory commands on a compromised host without understanding how they alter state.

Containment can isolate accounts, hosts, tokens, network paths, or features. Rotating one password is insufficient if session tokens, API keys, signing keys, or persistence mechanisms remain. Recovery restores known-good artifacts, verifies integrity, monitors recurrence, and reintroduces service gradually.

A **post-incident review** reconstructs technical and organisational conditions without reducing the event to one person’s mistake. Corrective actions should be specific, owned, prioritised, and verified. “Be more careful” is not a control.

### 19.31.1 Triage, severity, and decision structure

An event becomes a security incident when evidence indicates or credibly threatens policy violation requiring coordination. Triage establishes what is known, confidence, affected assets and identities, current adversary activity, safety or legal urgency, data at risk, and immediate containment options. Preserve uncertainty: an alert is neither automatically false nor confirmed compromise.

Severity combines impact and response urgency. A low-volume signing-key compromise can outrank a noisy malware outbreak; a safety-critical outage can require restoration before forensic completeness. Predefined criteria assist escalation, but an incident commander must adapt as evidence changes. Separate command, technical investigation, operations, communications, legal/privacy, and executive decision roles so one investigator is not also expected to coordinate every stakeholder.

Maintain an incident record with UTC timestamps, source, actor, decision, rationale, evidence reference, and next review. Use communications independent of potentially compromised identity or messaging systems. Restrict the incident channel because it contains attacker knowledge, personal data, and defensive plans, yet avoid secrecy that prevents affected operators from acting.

### 19.31.2 Containment, eradication, and recovery are hypotheses

Containment can revoke sessions, disable credentials, isolate hosts, block network paths, suspend a feature, remove public routes, or freeze releases. Each action has blast radius and can alert an adversary or destroy volatile evidence. State the hypothesis—“this identity is the only path to the registry”—and seek disconfirming evidence.

Eradication removes malicious artifacts and closes entry and persistence mechanisms. Reimaging from trusted media is often more defensible than attempting to clean an unknown compromised host, but the new host can be reinfected through compromised identity, automation, firmware, or source. Re-establish the chain of trust from an independent root.

Recovery restores service progressively, validates integrity and security invariants, rotates affected authority, observes for recurrence, and communicates user actions. A backup may contain dormant persistence or vulnerable configuration. Restore into isolation, scan and validate, identify its time relative to compromise, and apply clean updates before promotion.

### 19.31.3 Evidence and forensic limits

Digital evidence is mutable. Acquire it through documented tools and procedures, record who handled it, retain original bytes where possible, hash acquisitions, use write protection when appropriate, and perform analysis on copies. A hash demonstrates later byte consistency with the acquired image; it does not prove the acquisition was complete or the source truthful.

~~~python
from __future__ import annotations

from dataclasses import dataclass
from datetime import datetime, timezone
from hashlib import file_digest
from pathlib import Path


@dataclass(frozen=True)
class EvidenceRecord:
    path: str
    sha256: str
    size: int
    acquired_at: str


def describe_evidence(path: Path) -> EvidenceRecord:
    with path.open("rb") as stream:
        digest = file_digest(stream, "sha256").hexdigest()
    stat = path.stat()
    return EvidenceRecord(
        path=str(path),
        sha256=digest,
        size=stat.st_size,
        acquired_at=datetime.now(timezone.utc).isoformat(),
    )
~~~

This records a local file after acquisition. It does not safely acquire a live disk, preserve filesystem metadata, establish custody, or prevent the path from changing between hashing and `stat`. Forensic work requiring legal reliability needs trained personnel, validated tooling, jurisdiction-appropriate procedure, and an explicit privacy basis.

Cloud evidence can include control-plane audit, snapshots, identity-provider events, object versions, CI provenance, and provider logs. Retention may be short and clocks heterogeneous; preparation must enable and test collection before an incident. Endpoint telemetry controlled by an attacker needs corroboration.

### 19.31.4 Learning and organisational repair

A useful review constructs a timeline, impact, detection path, contributing technical and organisational conditions, what worked, what impeded response, and corrective actions. “Root cause” can be misleading when many conditions were jointly necessary. Ask why one mistake reached production, why detection lagged, why authority was broad, and why recovery was difficult.

Actions should change systems: enforce an invariant in code, shorten credentials, add a tested detection, remove a dangerous feature, clarify ownership, exercise recovery, or alter approval. Each needs an owner, deadline, verification method, and review. Count completed risk reduction, not the number of action items opened.

NIST SP 800-61 Revision 3 integrates incident response with the Govern, Identify, Protect, Detect, Respond, and Recover functions of Cybersecurity Framework 2.0. This emphasises that preparation and lessons are ordinary risk management, not a separate emergency discipline activated only after compromise.

> **Common misconception 19.72 — “Incident response begins when an alert fires and ends when service returns.”**  
> Preparation, evidence readiness, governance, recovery validation, notification, learning, and corrective-action verification extend before and after the visible event.
