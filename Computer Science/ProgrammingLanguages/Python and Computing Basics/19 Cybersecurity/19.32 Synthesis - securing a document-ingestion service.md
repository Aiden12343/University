# 19.32 Synthesis: securing a document-ingestion service

The branch’s concepts become meaningful when composed. Consider a Python service that accepts business documents from authenticated organisations, extracts text through native tools, lets authorised reviewers inspect results, and exports approved records. The service is deliberately similar to common production systems: it combines identity, untrusted files, native parsers, durable state, background work, cryptography, supply-chain dependencies, and operational response.

### 19.32.1 Assets, principals, and invariants

Assets include original documents, extracted text, organisation membership, reviewer decisions, cryptographic keys, processing availability, release artifacts, audit evidence, and the safety of worker infrastructure. Principals include uploader, reviewer, organisation administrator, support operator, web service, parser worker, database role, object-storage identity, build workload, and incident responder. External dependencies include identity provider, key service, package index, image registry, malware intelligence, and notification provider.

The primary invariants are:

1. an organisation can learn neither content nor existence of another organisation’s documents except through an explicit audited delegation;
2. only current reviewers can approve, and an uploader cannot approve the same document where separation of duties applies;
3. untrusted document bytes never execute with web-service, database, cloud-control, or outbound-network authority;
4. one accepted upload consumes bounded storage and processing resources;
5. every externally visible state transition is attributable to authenticated policy input and a versioned application decision;
6. only artifacts produced by the approved release workflow can run;
7. compromise of one parser worker does not reveal other documents, production secrets, or a reusable release identity;
8. document deletion follows retention policy across primary data, derived data, queues, caches, and recoverable backups under the stated window.

These invariants expose conflicts. Malware analysis may require retaining a sample after a user requests deletion; legal hold can override ordinary retention; debugging extraction failures may tempt engineers to download sensitive documents. Policy must name these exceptions, authorities, notifications, and audit evidence rather than leaving them to ad hoc operator judgement.

### 19.32.2 Boundary architecture

The network-facing application accepts metadata and streams bytes directly into a newly allocated quarantine object under a generated identifier. It does not use the client filename as a storage key. The upload path enforces authenticated tenant, content-length policy where available, actual streamed byte count, deadline, per-tenant quota, global capacity, and idempotency. A database transaction creates the document record and an outbox job only after storage confirms the quarantined object identity and digest.

The parser worker receives a one-job capability: read one quarantined object and write one result location. It has no general bucket listing, database credential, production signing key, instance metadata access, or unrestricted egress. A supervisor launches the native parser in a separate restricted process or virtual-machine boundary with read-only input, empty writable scratch space, CPU/memory/file/process limits, bounded output, and whole-process-group termination. The original is never opened by a reviewer workstation.

Parser output is still untrusted. The worker validates encoding, text size, page count, embedded resource count, and result schema before publishing. A safe renderer produces a representation without active content. Malware-scanner status is evidence, not proof: “no detection” does not make a file trusted. Policy decides whether inconclusive or failed scanning blocks review.

The reviewer application retrieves by opaque document identifier, loads the authoritative organisation and membership in the same transaction or consistent policy snapshot, and authorises the object-level action. A signed URL, if used, is a short-lived scoped bearer capability generated only after authorisation; it is excluded from logs and third-party resources. Approval uses optimistic versioning and a uniqueness or state-transition constraint so concurrent requests cannot bypass separation of duties.

### 19.32.3 Threat analysis and control evidence

For path traversal, the system avoids user-selected storage paths, validates archive entries inside the parser sandbox, and publishes only generated object keys. Evidence includes property tests over path variants, integration tests with links and collisions on supported filesystems, and a sandbox test proving the worker cannot write outside scratch.

For command injection, the worker invokes a pinned absolute parser binary with a fixed argument vector, controlled environment, option terminator, closed standard input, streamed output limit, and external deadline. The binary and native libraries are identified in the SBOM. Tests use filenames beginning with options, control characters, invalid encodings, huge output, spawned descendants, and signals.

For cross-tenant access, tests construct two organisations, users with changing roles, delegated review, archived membership, guessed identifiers, exports, search, thumbnails, audit views, and support workflows. The invariant is evaluated at every object-producing path. Logs record policy version and authenticated subject without revealing another tenant’s document identifier in a denial response.

For supply-chain compromise, source changes require review; untrusted pull requests cannot access release credentials; dependencies resolve from governed indexes into a lock with artifact hashes; builds run without production authority; provenance binds source revision and builder; the registry admits immutable signed artifacts; deployment verifies the expected identity and predicate; and the running image exposes its digest. An emergency dependency update follows the same trust chain with accelerated approval, not an untracked workstation build.

For denial of service, limits cover concurrent uploads, bytes, declared and actual expanded size, page count, parser time, parser memory, output, queue depth, database connections, and per-tenant plus global work. Admission occurs before parser allocation. The service rejects excess work promptly and preserves capacity for cancellation, health, administration, and incident response.

### Worked example 19.6 — One-time worker capability

~~~python
from __future__ import annotations

import hashlib
import secrets
from dataclasses import dataclass
from datetime import datetime, timedelta, timezone


@dataclass(frozen=True)
class WorkerGrant:
    grant_id: str
    document_id: str
    input_object: str
    output_object: str
    expires_at: datetime
    verifier_digest: bytes


def issue_worker_grant(document_id: str, input_object: str, output_object: str) -> tuple[str, WorkerGrant]:
    bearer = secrets.token_urlsafe(32)
    grant = WorkerGrant(
        grant_id=secrets.token_hex(16),
        document_id=document_id,
        input_object=input_object,
        output_object=output_object,
        expires_at=datetime.now(timezone.utc) + timedelta(minutes=10),
        verifier_digest=hashlib.sha256(bearer.encode("ascii")).digest(),
    )
    return bearer, grant


def grant_matches(grant: WorkerGrant, bearer: str, now: datetime) -> bool:
    supplied = hashlib.sha256(bearer.encode("ascii")).digest()
    return now < grant.expires_at and secrets.compare_digest(supplied, grant.verifier_digest)
~~~

The bearer proves possession but does not itself enforce one-time use or object operations. The job service must atomically transition the grant from pending to claimed, issue storage operations restricted to the two named objects, expire the grant, and reject reuse. A digest protects the database from immediately yielding the bearer token, while a compromised job service can still misuse grants. The example makes scope and lifetime explicit so that remaining authority is reviewable.

### 19.32.4 Secrets, keys, and privacy

The web and worker identities obtain short-lived platform credentials. Database roles separate request reads/writes, migrations, analytics, and incident access. The document-encryption envelope binds tenant, document identifier, schema version, and key identifier as associated data. Per-tenant or per-domain data keys limit blast radius; a managed key-encryption key wraps them. Rotation distinguishes active from decrypt-only keys and is exercised against backups.

Audit records exclude document content, bearer URLs, session identifiers, parser output, and raw client filenames where unnecessary. They include authenticated subject, tenant, document opaque identifier, action, decision, policy version, result, request correlation, and trusted service identity. Access to audit data is itself audited and retained by purpose. Product analytics do not inherit security logs wholesale.

Privacy review maps every derived artifact: OCR text, thumbnails, search indexes, malware samples, temporary scratch files, queue payloads, caches, exports, logs, support tickets, and backups. Deletion is a state machine with observable completion and documented backup expiry, not a single database `DELETE`. Legal hold and incident preservation are explicit exceptional states.

### 19.32.5 Verification, deployment, and incident exercise

The evidence plan contains unit tests for parsers and policy functions; property tests for identifiers, frames, and object isolation; integration tests on the production database and filesystems; sandbox escape assertions; native fuzzing under sanitisers; dependency and provenance verification; adversarial file corpus tests; load tests for expansion and slow input; and a scoped penetration test of the deployed environment. Every limit is observed at the actual resource owner.

Deployment is immutable and progressive. Schema changes remain compatible with old and new application versions. Readiness is withdrawn before shutdown; parser workers stop claiming jobs and release or let leases expire; one-time grants cannot be duplicated through retry. Rollback restores a previously trusted artifact without reverting security-critical schema or key state blindly.

The incident exercise assumes a parser dependency has a remotely exploitable memory flaw and one worker made an unexpected metadata-service request. Responders preserve worker and control-plane evidence, block worker egress, suspend new parsing, determine whether credentials were exposed, revoke and rotate affected workload identity, identify documents processed by vulnerable versions, rebuild from reviewed source and patched dependencies, verify provenance, stage recovery, notify according to data impact, and add a regression plus detection. Restoration is not declared complete until cross-tenant and key-use evidence supports the invariants again.

This synthesis demonstrates the chapter’s central claim: security is not an isolated validation function or cryptographic primitive. It is a maintained argument that the composition of identities, parsers, operating-system authority, state transitions, dependencies, keys, telemetry, and response preserves explicit properties under stated adversaries and failures.
