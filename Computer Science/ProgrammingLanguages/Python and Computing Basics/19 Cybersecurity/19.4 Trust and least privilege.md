# 19.4 Trust and least privilege

**Trust** is acceptance of a component’s behaviour for a purpose. Trust is not affection or certainty. If an application can read a secret, the design trusts it not to disclose that secret whether or not documentation says so.

The **principle of least privilege** grants each principal only the capabilities needed for its task, for only the required duration and scope. A reporting process needing SELECT access should not receive database schema-alteration rights. An image processor should not have cloud-account administrator credentials.

**Privilege separation** distributes operations among components with different authority. A network-facing parser can run in a restricted process and pass validated results to a more privileged service. Compromise of the parser then encounters a smaller capability set.

**Defence in depth** places independent or partially independent controls across layers. Input validation, parameterised queries, database constraints, least-privilege credentials, and monitoring can jointly protect a data operation. Repeating the same flawed string check in three functions is not meaningful depth.

### 19.4.1 Identity, authentication, authorisation, and accounting

An **identity** is a set of attributes by which a system distinguishes a principal in context. **Identification** presents a claimed identity; **authentication** establishes evidence that the claimant controls an authenticator associated with it; **authorisation** decides whether that principal may perform an action on a resource under current policy. **Accounting** records relevant actions and decisions. The four stages must not be collapsed. Knowing who requested an operation does not determine whether it is allowed.

Authentication strength depends on the entire lifecycle: enrolment, binding, storage, use, recovery, revocation, reauthentication, and support. A strong authenticator with a weak recovery channel inherits the recovery channel’s weakness. Multi-factor authentication combines factors from different categories only when their compromise is sufficiently independent. Two memorised secrets are not two independent factors; approving a prompt on the compromised device that initiated it may add little resistance.

Phishing-resistant authentication binds a cryptographic operation to the legitimate verifier context so a lookalike site cannot simply relay a reusable secret. It reduces a major attack class but does not prevent session theft, malicious browser code, coerced approval, compromised recovery, or authorised misuse. Sensitive actions may require fresh authentication and transaction details bound into the approval.

### 19.4.2 Access-control models and policy location

**Discretionary access control** lets an owner or authorised subject grant access. **Mandatory access control** enforces centrally defined labels and dominance rules. **Role-based access control** associates permissions with organisational roles. **Attribute-based access control** evaluates subject, resource, action, and environmental attributes. **Relationship-based access control** uses graph relationships such as owner, member, reviewer, or parent organisation. Real systems combine models.

The authorisation decision needs authoritative, current inputs and must occur for every protected operation. Hiding a button is user-interface behaviour, not enforcement. Route-level role checks can still miss which individual object is addressed. Caches require an invalidation and staleness policy when membership or revocation changes.

~~~python
from dataclasses import dataclass
from enum import StrEnum


class Action(StrEnum):
    READ = "read"
    APPROVE = "approve"


@dataclass(frozen=True)
class Principal:
    subject_id: str
    organisation_id: str
    roles: frozenset[str]


@dataclass(frozen=True)
class Invoice:
    organisation_id: str
    uploader_id: str
    status: str


def permitted(actor: Principal, action: Action, invoice: Invoice) -> bool:
    if actor.organisation_id != invoice.organisation_id:
        return False
    if action is Action.READ:
        return actor.subject_id == invoice.uploader_id or "reviewer" in actor.roles
    if action is Action.APPROVE:
        return "approver" in actor.roles and invoice.status == "reviewed"
    return False
~~~

The function makes the default denial explicit and accepts only already authenticated domain values. A production decision may also depend on delegation, assurance level, conflict-of-interest rules, resource sensitivity, time, or legal hold. Centralising pure policy logic helps systematic testing, but enforcement must still wrap every path and mutation.

### 19.4.3 Confused deputies and delegated authority

A **confused deputy** is a component with authority that an unprivileged caller induces it to misuse. A compiler allowed to write billing files, a cloud function holding broad storage credentials, or a URL-fetching service with internal network access can become deputies. Authenticating the caller is insufficient when the request fails to bind the intended resource and authority.

Capability-oriented designs pass a reference that already embodies the permitted object and operation, reducing ambient lookup. Delegation tokens should bind audience, scope, resource, lifetime, and where possible the presenting party. Broad bearer credentials are transferable authority: anyone who obtains them can act until expiry or revocation.

“Zero trust” is best read as an architectural instruction to make access decisions from explicit identity, device, resource, and context signals rather than network location. It does not mean trusting nothing—which would make operation impossible—or continuously prompting users. Every design retains a trusted computing base.

### 19.4.4 Classical security models

Formal security models isolate selected properties so policy can be reasoned about precisely. They are deliberately narrower than a complete production threat model. Their value lies in exposing information flows and state transitions that informal permission lists can obscure.

The Bell–LaPadula model addresses confidentiality through ordered security levels. Its familiar rules prohibit a subject from reading information above its clearance (“no read up”) and from writing information to a lower classification (“no write down”), subject to the model’s exact variants. The latter blocks a cleared process from copying secret content into a public object. It does not establish data correctness, application safety, covert-channel absence, or usable declassification. Real systems need trusted mechanisms that deliberately transform or release information under policy.

The Biba family addresses integrity with an order that is often presented as the dual: do not read lower-integrity data when it could contaminate trusted computation, and do not write to higher-integrity objects from a lower-integrity subject. Strict application can be impractical because services must ingest untrusted input. The useful lesson is to mediate promotion: parse, validate, corroborate, and record provenance before low-trust data influences high-integrity state.

Clark–Wilson integrity centres on **well-formed transactions**, constrained data items, transformation procedures, integrity verification, certification, and separation of duties. A user does not arbitrarily edit a ledger; an authorised transformation preserves declared invariants and an independent role certifies relevant procedures. This maps closely to database constraints, domain commands, dual approval, immutable journal entries, and reconciliation.

The Brewer–Nash or “Chinese Wall” model constrains access dynamically to avoid conflicts of interest: after accessing confidential data for one company in a conflict class, a consultant is restricted from competitors in that class. Authority therefore depends on access history, not only a static role. This illustrates why caches and replicas of policy state can be security-critical.

Information-flow control associates labels with data and computations and restricts flows between them. Explicit flows copy a value; implicit flows disclose through control structure, such as setting a public bit depending on a secret condition. Timing, resource use, termination, and other covert channels complicate complete enforcement. Language- or operating-system-level information-flow systems can provide strong scoped guarantees, but ordinary Python type hints do not enforce confidentiality labels at runtime.

These models should not be mixed into one slogan. Bell–LaPadula can preserve secrecy while accepting false high-level data; Biba can preserve integrity while denying useful low-trust observations; Clark–Wilson depends on certified transformations; history-based policy needs reliable history. Select the property, state, transitions, and trusted subjects explicitly.

### 19.4.5 Human factors, social engineering, and insider risk

People are participants in a security system, not external noise. A control that requires users to distinguish visually identical domains, reject every urgent request, memorise many unique secrets, or navigate an inaccessible recovery flow transfers design failure to the user. Attackers exploit authority, urgency, fear, helpfulness, routine, and organisational hierarchy because those are legitimate mechanisms of cooperation.

**Social engineering** manipulates people or processes to obtain information, action, or access. Phishing uses deceptive messages or sites; pretexting constructs a plausible role or situation; vishing uses voice; physical tailgating abuses access courtesy; consent phishing persuades a user to grant a malicious application legitimate delegated authority. Training can improve recognition, but technical design should reduce what a successful deception can accomplish through phishing-resistant authenticators, transaction binding, scoped approval, independent confirmation, and least privilege.

Security prompts need comprehensible choices at the decision moment. Repeated low-value warnings condition automatic approval. Display the relying party, action, resource, consequence, and whether the request was user-initiated. For high-impact changes, use an independent channel or second person whose evidence does not originate from the same potentially compromised workflow. “Contact the requester” is weak when contact details came from the suspicious message; use an independently maintained directory.

An **insider threat** arises from a person or service with legitimate access who acts maliciously, negligently, under coercion, or through compromise. Treating every insider as malicious destroys collaboration and privacy; treating employment as unlimited trust creates catastrophic concentration. Separation of duties, just-in-time privilege, peer approval, data minimisation, behavioural detection with due process, and well-designed offboarding reduce opportunity while respecting legitimate work.

Offboarding must revoke sessions, physical access, devices, service accounts, delegated roles, recovery contacts, signing authority, cached credentials, and third-party access. Role changes require the same discipline; privilege accumulation over years can exceed any current job need. Periodic access review should ask resource owners to justify concrete permissions rather than approve an unreadable list.

Security culture affects reporting. Staff who expect punishment for mistakes hide suspicious clicks or accidental disclosures, increasing harm. A just culture distinguishes ordinary error, risky shortcuts encouraged by system conditions, and reckless or malicious action. Fast, blame-aware reporting channels, rehearsed response, and visible correction create better evidence than demands for perfect behaviour.

Human safeguards themselves can harm. Intensive monitoring can violate privacy and employment rights, accessibility barriers can exclude users, and opaque fraud models can discriminate. Define lawful purpose, proportionality, contestability, retention, and human review. Security objectives do not suspend ethical governance.

> **Common misconception 19.8 — “Authentication proves authorisation.”**  
> Authentication establishes an identity claim to some assurance. Authorisation is a separate decision about one action, resource, and context.

> **Common misconception 19.9 — “Multi-factor authentication means any two checks.”**  
> Factors must represent sufficiently independent authenticator categories and lifecycles. Two passwords or two prompts on one compromised device need not resist the same failure.

> **Common misconception 19.10 — “Administrators should receive broad permanent access because emergencies happen.”**  
> Emergency access can be time-bounded, approved, strongly authenticated, recorded, and reviewed. Permanent ambient authority increases both accident and compromise impact.

> **Common misconception 19.11 — “Zero trust means no component is trusted.”**  
> Systems necessarily trust some hardware, software, identities, and operators. The principle is to minimise and continuously justify trust rather than infer it from network location.
