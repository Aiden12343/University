# 19.5 The operating-system security boundary

Chapter 2 established the kernel/user-space boundary. The kernel mediates address spaces, files, processes, devices, credentials, and network operations. A process ordinarily cannot read arbitrary memory from another process because virtual-memory mappings and processor privilege enforce separation. It can nevertheless receive authority through inherited file descriptors, environment variables, command-line arguments, filesystem permissions, inter-process channels, or shared credentials.

A **security principal** at operating-system level can be a user identifier, group, service identity, container identity, or access token depending on the system. Permissions determine operations on resources. Ownership and mode bits on Unix-like systems are one model; access-control lists provide finer entries. Windows uses access tokens and security descriptors. Portable Python code cannot assume identical semantics.

### Worked example 19.2 — Create a private file deliberately

~~~python
from pathlib import Path
import os


def write_private(path: Path, data: bytes) -> None:
    descriptor = os.open(
        path,
        os.O_WRONLY | os.O_CREAT | os.O_EXCL,
        0o600,
    )
    try:
        with os.fdopen(descriptor, "wb") as stream:
            descriptor = -1
            stream.write(data)
    finally:
        if descriptor != -1:
            os.close(descriptor)
~~~

<code>O_EXCL</code> with <code>O_CREAT</code> asks that creation fail if the path already exists, reducing overwrite and some race risks. Mode <code>0o600</code> requests owner read/write permission on a Unix-like system, subject to platform semantics and access-control mechanisms. The descriptor is converted into a managed stream; the sentinel prevents double close.

This function does not make the bytes globally secret. Parent-directory access, backups, privileged accounts, malware in the process, logs, storage snapshots, and platform differences remain. Filesystem permissions implement one boundary.

### 19.5.1 Process credentials and inherited authority

At process creation, authority arrives through more than a user name. On a Unix-like system it can include real and effective user and group identifiers, supplementary groups, capabilities, open descriptors, current and root directories, resource limits, namespaces, environment variables, signal disposition, and controlling terminal. On Windows it can include an access token, integrity level, privileges, restricted security identifiers, inherited handles, job-object constraints, and desktop/session context. Python exposes only parts portably.

Inheritance is a frequent leak. A child that needs one pipe can accidentally inherit a database socket, log file, secret-bearing environment, or administrative handle. Modern APIs try to make file descriptors non-inheritable by default, yet subprocess code must still state the exact environment, working directory, standard streams, and handles it intends to convey. Clearing an environment wholesale can break library behaviour; copying it wholesale can disclose credentials. Construct a minimal reviewed environment from required values.

Privilege should be acquired as late as possible and discarded as early as possible. Dropping an identifier is not sufficient if powerful descriptors, groups, capabilities, writable configuration, or reacquirable tokens remain. Starting unprivileged is usually simpler than trying to shed authority correctly after initialisation.

### 19.5.2 Filesystem permissions and namespace semantics

Directory permissions govern name creation, removal, and traversal; file permissions govern access to file content. A file’s apparent mode is also affected by creation mask, access-control lists, ownership, mount options, inherited policy, and platform rules. Deleting a read-only file can be possible when the containing directory permits name removal. Conversely, a readable file is inaccessible if a parent directory cannot be traversed.

Path names are mutable references through a namespace, while an open descriptor names a kernel object already resolved. This distinction explains both descriptor-relative security and unlink semantics: a name can disappear while an open file remains usable. Security-sensitive code should prefer opening once, validating descriptor metadata where necessary, and operating through that descriptor rather than repeatedly resolving attacker-influenced names.

Temporary files illustrate the rule. A predictable name followed by ordinary creation permits another process to pre-create or redirect it. `tempfile.NamedTemporaryFile`, `TemporaryFile`, and `mkstemp` use exclusive creation; the obsolete pattern of asking for a name and opening it later reintroduces the race. The temporary directory itself must be appropriate to the secrecy and sharing model.

### 19.5.3 Isolation mechanisms are layered controls

Containers, virtual machines, language sandboxes, mandatory access-control policies, seccomp-style syscall filters, Windows job objects, and restricted tokens constrain different boundaries. A container commonly isolates namespaces and resource views while sharing the host kernel. A virtual machine adds a hypervisor boundary but can retain shared clipboard, folders, devices, management agents, and network routes. A Python virtual environment isolates package resolution, not operating-system authority.

A sandbox policy starts from required operations: read these immutable inputs, write this output directory, allocate this much memory, run for this long, make no network connections, create no children, and expose no production credential. Controls must fail closed when unavailable and must be tested from inside the sandbox. Application-level timeouts alone cannot stop native code that ignores cancellation; an external supervisor needs authority to terminate and clean up the worker.

> **Common misconception 19.12 — “Running as a non-administrator makes a process harmless.”**  
> Ordinary accounts may read valuable data, use inherited credentials, reach internal services, consume resources, or alter user-executed code. Privilege is resource-specific.

> **Common misconception 19.13 — “A Python virtual environment is a security sandbox.”**  
> It changes interpreter and package selection. Code inside ordinarily retains the process’s filesystem, network, subprocess, and native-extension authority.

> **Common misconception 19.14 — “Dropping the user identifier removes privileged authority.”**  
> Open descriptors, supplementary groups, capabilities, tokens, writable loaders, and inherited services can preserve or restore authority. The whole credential set matters.
