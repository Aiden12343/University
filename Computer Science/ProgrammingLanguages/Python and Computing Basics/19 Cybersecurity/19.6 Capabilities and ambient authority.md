# 19.6 Capabilities and ambient authority

A **capability** is an unforgeable reference or token granting authority to perform operations on a resource. An open file descriptor is capability-like: code holding it can act on the already opened file without resolving its path again. An object exposing only <code>read</code> can embody less authority than a path string passed to code able to open arbitrary files.

**Ambient authority** is authority implicitly available from the execution environment, such as all files accessible to the process identity or credentials discovered from environment configuration. Passing a narrow file-like object to a parser is safer than passing a root directory and expecting self-restraint.

API design can express least authority:

~~~python
from collections.abc import Iterable
from typing import TextIO


def count_nonempty_lines(stream: TextIO) -> int:
    return sum(1 for line in stream if line.strip())
~~~

The function can read only what the supplied stream provides. It has no path-opening logic, network client, or credential lookup. Smaller authority also makes testing easier.

### 19.6.1 Designation, authority, and attenuation

An ordinary path string designates a resource but conveys no proof that its holder may open it; access is resolved against ambient process credentials. A capability combines designation with authority. Capabilities can be **attenuated**: a read–write handle can produce a read-only view, a database connection can be wrapped to expose one stored operation, or a token can be limited to one object and expiry. Attenuation should be monotonic—the derived capability grants no authority absent from its source.

Revocation is not automatic. Destroying one Python reference does not invalidate copies held elsewhere. A capability can be made revocable through an indirection checked on every use, a short expiry, a version or generation number, or destruction of the underlying resource. Each choice trades availability and state. Offline signed capabilities are easy to verify but difficult to revoke immediately; centrally looked-up references support revocation but add a dependency.

High-entropy capability URLs are bearer credentials when possession is sufficient. They must not enter referrers, analytics, browser history, screenshots, logs, or third-party requests. Entropy resists guessing; it does not protect a leaked URL or prevent an authorised holder from forwarding it.

### 19.6.2 Authority visible in Python interfaces

Function signatures can reveal and restrict effects. Passing a `TextIO`, clock callable, random-source protocol, or narrowly typed repository is preferable to letting domain code discover global configuration and open arbitrary resources. This is not merely testability technique: explicit dependencies make authority reviewable.

~~~python
from collections.abc import Callable
from dataclasses import dataclass
from datetime import datetime
from typing import Protocol


@dataclass(frozen=True)
class Report:
    report_id: str
    text: str


class ReportSink(Protocol):
    def store(self, report: Report) -> None: ...


def publish_report(
    report: Report,
    *,
    sink: ReportSink,
    now: Callable[[], datetime],
) -> str:
    sink.store(report)
    return f"{report.report_id}:{now().isoformat()}"
~~~

The function receives authority to store reports through one interface and to obtain time through one callable. It has no implicit filesystem root, network client, or credential resolver. Python’s dynamic nature cannot prevent a malicious object from doing more internally, but the design narrows what honest code needs and what review must trace.

Plugin systems are a sharper boundary. Importing a plugin executes Python with the importer’s process authority; a manifest promising limited permissions does not enforce them. Untrusted plugins require process or virtual-machine isolation, a narrow message protocol, resource governance, authenticated provenance, and a plan for compromise. Restricted built-ins and source filtering are not complete Python sandboxes.

> **Common misconception 19.15 — “A random unguessable URL is not a credential.”**  
> If possession authorises access, the URL is a bearer capability and requires secrecy, scope, expiry, revocation, and leak prevention.

> **Common misconception 19.16 — “Removing dangerous built-ins safely sandboxes untrusted Python.”**  
> Python objects, imports, native code, introspection, resource exhaustion, and implementation details create many paths to ambient authority. Strong isolation belongs outside the interpreter process.
