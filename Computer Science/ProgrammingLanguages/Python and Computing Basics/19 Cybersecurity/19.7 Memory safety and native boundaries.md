# 19.7 Memory safety and native boundaries

A **memory-safety violation** occurs when a program reads, writes, uses, or frees memory outside the rules governing valid objects and lifetimes. Classes include buffer overflow, out-of-bounds access, use-after-free, double free, and use of uninitialised memory. Such defects can corrupt data, crash a process, or permit code execution.

Ordinary Python indexing and object lifetime rules prevent many direct memory-safety errors: an out-of-range list index raises <code>IndexError</code>, and managed references retain objects. This is memory safety at the Python language/interface level, not proof that the complete Python process is safe. CPython, extension modules, native libraries, parsers, drivers, and the interpreter itself contain native code. <code>ctypes</code>, buffer interfaces, C extensions, and unsafe deserialisers cross boundaries.

A memory-safe application can still have security defects: SQL injection, broken authorisation, unsafe file access, secret disclosure, race conditions, and denial of service require no invalid pointer.

Native extension review follows Chapter 15’s ownership discipline:

- validate lengths before allocation and indexing;
- distinguish signed and unsigned conversions;
- check integer overflow in size products;
- preserve reference ownership on every error path;
- release resources exactly once;
- avoid retaining borrowed pointers beyond their valid lifetime;
- account for GIL and free-threaded builds;
- fuzz parsers with sanitiser-enabled builds.

### 19.7.1 From corrupted memory to security consequence

A buffer overflow is not synonymous with arbitrary code execution. Exploitability depends on what is overwritten, memory layout, attacker control, compiler and operating-system mitigations, process authority, and available code paths. Consequences range from deterministic rejection to denial of service, data disclosure, state corruption, control-flow diversion, and escape from a higher-level safety guarantee.

Stack canaries attempt to detect selected stack corruption before returning. Non-executable memory prevents direct execution from designated data pages. Address-space layout randomisation makes useful addresses less predictable. Control-flow integrity restricts indirect branches. Memory tagging and hardware protections can detect or prevent further classes. These are defence in depth: none repairs undefined behaviour, and information disclosure can weaken address randomisation.

Integer arithmetic often precedes the memory defect. If a native extension calculates `count * element_size` in a bounded machine integer and the product wraps, it may allocate a small buffer and then copy the large logical count. Validate domain bounds and check multiplication before conversion to the native allocation type.

~~~python
import sys


def checked_allocation_size(count: int, item_size: int) -> int:
    if count < 0 or item_size <= 0:
        raise ValueError("invalid dimensions")
    if count > sys.maxsize // item_size:
        raise OverflowError("allocation size exceeds platform limit")
    return count * item_size


assert checked_allocation_size(10, 8) == 80
~~~

The Python integer itself does not overflow, but the check models conversion to a platform-sized native length. A real extension must also honour allocator, object, protocol, and application limits far below `sys.maxsize`.

### 19.7.2 Python’s native attack surface

Every wheel containing compiled code extends the trusted computing base. Image, compression, database, cryptographic, numerical, regular-expression, and XML libraries may process adversarial bytes beneath Python-level checks. Buffer-exporting objects allow zero-copy access with lifetime and mutability constraints. `ctypes` and foreign-function interfaces can fabricate pointers or call a function with a mismatched signature. A segmentation fault bypasses Python exceptions.

Version and provenance therefore matter at the native boundary. Compile high-risk code with address, undefined-behaviour, and thread sanitisers in testing where supported. Fuzz the native entry point, not merely a Python wrapper that rejects most inputs first. Treat crashes, leaks, excessive allocation, hangs, and inconsistent parsing as findings. Minimise the wrapper’s conversions so lengths, ownership, error codes, and thread-state transitions are explicit.

Subinterpreters and a global interpreter lock are not security isolation. Objects and extensions can retain process-global state; native memory and descriptors share a process; a crash affects all interpreters. Separate processes under separate credentials are the minimum ordinary isolation unit for hostile native parsing.

> **Common misconception 19.17 — “A buffer overflow always yields code execution.”**  
> It yields memory-safety violation. Exploitability and consequence depend on overwritten state, attacker control, mitigations, layout, and process authority.

> **Common misconception 19.18 — “Python bounds checks protect data passed to a C extension.”**  
> They protect Python operations before the boundary. Native code must independently honour lengths, ownership, lifetime, concurrency, and integer-conversion rules.

> **Common misconception 19.19 — “The GIL is a security boundary between Python tasks.”**  
> It is an implementation synchronisation mechanism. Tasks share process memory, modules, descriptors, credentials, and failure fate.
