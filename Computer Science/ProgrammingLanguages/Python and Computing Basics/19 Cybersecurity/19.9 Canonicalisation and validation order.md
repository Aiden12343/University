# 19.9 Canonicalisation and validation order

**Canonicalisation** maps multiple equivalent representations to a chosen standard form. Security comparisons fail when validation occurs on one representation and use occurs after another decoding or normalisation.

Examples:

- percent-encoded path separators decoded after a filter;
- Unicode visually confusable identifiers;
- case-insensitive filesystem names;
- relative path segments;
- alternative IP-address representations;
- archive entries with platform-specific separators.

A sound order is domain-specific: parse once with the same semantics as the eventual consumer, canonicalise where a unique form exists, validate the canonical structure, and use structured APIs without a second incompatible interpretation. Repeated decode-until-stable loops can create new ambiguity and denial-of-service risk.

### 19.9.1 Parse, canonicalise, validate, authorise, act

These verbs denote different operations. **Parsing** establishes structure under a grammar. Canonicalisation chooses a comparison representation where the domain defines equivalence. **Syntactic validation** checks shape; **semantic validation** checks meaning and cross-field rules. Authorisation relates a principal and operation to a resource. Action changes or discloses state. Reordering them can change security.

For example, an API receives an account identifier encoded in a URL path. The HTTP server parses and percent-decodes according to its URL rules. Application code validates one identifier grammar and looks up a canonical database key. It then authorises the authenticated principal against the retrieved account and performs the operation inside a transaction. A filter applied to raw path text before the server’s decoding does not protect the value actually used.

Validation should normally be an allowlist of domain forms, not a blacklist of anticipated attacks. A device identifier grammar such as ASCII uppercase letters and digits with a fixed length is reviewable. “Reject quotes, semicolons, and `<script>`” neither defines a device identifier nor covers every downstream grammar. An allowlist does not replace parameterisation: even valid user text remains data at a SQL or shell boundary.

~~~python
import re


DEVICE_ID = re.compile(r"[A-Z2-9]{8,20}\Z", re.ASCII)


def parse_device_id(raw: str) -> str:
    candidate = raw.strip().upper()
    if not DEVICE_ID.fullmatch(candidate):
        raise ValueError("invalid device identifier")
    return candidate


assert parse_device_id(" abcd2345 ") == "ABCD2345"
~~~

The canonicalisation is part of the identifier definition; it would be wrong for a case-sensitive credential. The excluded characters `0`, `1`, `I`, and `O` may reduce human transcription confusion, but such a choice must be compatible with existing identifiers.

### 19.9.2 Equivalence must match the consumer

Filesystems, databases, URLs, host names, email addresses, Unicode strings, and cryptographic encodings have different equivalence rules. A database collation may treat strings equal that Python does not. Some filesystems preserve case but compare without it. IPv6 has many textual forms for one address; an IPv4 address can appear within IPv6 syntax. URL user-information and backslashes can surprise ad hoc host parsers.

When a security decision concerns a destination, parse it with the same standards-conforming implementation used to connect, resolve all candidates under policy, revalidate after redirects, and constrain actual egress. Textual normalisation alone cannot freeze DNS or routing. When a decision concerns a filesystem object, use descriptor-relative operations and protect mutable directories rather than relying on a resolved string.

Canonical forms can become signing contracts. If producers and verifiers serialise maps, numbers, or Unicode differently, signatures fail—or worse, one signature is interpreted over different meanings. Specify bytes, not an informal object, and version the canonicalisation algorithm.

> **Common misconception 19.23 — “Sanitising before decoding is safer because dangerous characters are removed early.”**  
> A later decoder can create characters or structure the filter never examined. Security checks must apply to the representation the consumer will use.

> **Common misconception 19.24 — “Canonicalisation has one universal correct result.”**  
> Equivalence is domain- and consumer-specific. A transformation correct for host names may corrupt credentials, paths, signatures, or user text.
