**Systems engineering** designs and operates collections of software, hardware, networks, people, and procedures as coherent services. **Development and operations**, commonly abbreviated **DevOps**, names organisational and technical practices that reduce the separation between creating software and operating it. It is not a job title, cloud product, container file, or instruction to give every developer production administrator access.

The central problem is controlled change. Software must move from source to a running environment while preserving provenance, configuration, security, availability, observability, and rollback. Automation is valuable because it makes repeated operations explicit and reviewable. Automated error is also repeatable and fast; tests, staged authority, and feedback remain necessary.

### 20.1.1 Services as socio-technical systems

A **service** is a capability delivered continuously or on demand through a defined interface. The interface may be a network protocol, a queue, a file exchange, a command, or a human procedure. A service is broader than its principal executable. Its behaviour depends on people, deployment machinery, credentials, networks, clocks, data stores, vendors, documentation, and recovery arrangements. A **socio-technical system** is one whose properties arise from interaction between technical components and human organisations. Reliability and security therefore cannot be inferred from source code alone.

**Production** is the environment in which real obligations are discharged: users rely on results, business state changes, money or safety may be affected, and errors have consequences beyond the engineering exercise. The term does not necessarily mean a large public cloud. A laptop controlling a laboratory instrument can be production. A large staging cluster is not production if nobody depends on its outcomes.

Operations has two intertwined forms:

- **control-plane work** changes, schedules, configures, or observes resources;
- **data-plane work** performs the service's intended user or business operations.

The distinction is relative. A deployment API is control plane for an application, but its own request handling is data plane for the deployment service. A sound design prevents ordinary data-plane inputs from acquiring control-plane authority and ensures the control plane remains recoverable when the data plane is overloaded.

### 20.1.2 Feedback, learning, and toil

Delivery is a feedback system. A change is proposed, transformed into an artifact, tested, released to a bounded population, observed, compared with expectations, and either advanced, corrected, or withdrawn. Short feedback latency matters only when the signal is trustworthy. A test that completes in one minute while failing to exercise the built artifact is faster but less informative than a ten-minute test of the object actually deployed.

**Toil** is recurring operational work that is substantially manual, repetitive, automatable, tactical, and proportional to service growth. Not every manual task is toil: an unfamiliar investigation can generate new knowledge. Not every automated task is valuable: a complicated controller that saves one annual command can impose more maintenance than it removes. Automation should be judged by total lifecycle cost, failure modes, auditability, and the human attention it frees for engineering.

The governing loop is:

1. state an intended service property;
2. encode the change and its authority;
3. predict observable consequences;
4. expose the change gradually;
5. measure user-relevant and resource outcomes;
6. compare observation with the prediction;
7. preserve evidence and revise the system model.

This loop connects software engineering, systems theory, security, and organisational learning. “DevOps maturity” is not the number of named tools installed. It is the degree to which the organisation can make small, attributable, reversible changes; detect their consequences; and learn without concealing uncertainty.

> **Common misconception 20.1 — “Operations begins after development finishes.”**  
> Operational properties are created by architecture, interfaces, state models, dependencies, tests, deployment design, and organisational ownership from the first design decision. Handover cannot add recoverability to an intrinsically irreversible system.

> **Common misconception 20.2 — “Automation removes humans from the system.”**  
> Automation relocates human decisions into code, policy, defaults, credentials, review, and exception handling. It changes when and where judgement occurs; it does not eliminate judgement or accountability.
