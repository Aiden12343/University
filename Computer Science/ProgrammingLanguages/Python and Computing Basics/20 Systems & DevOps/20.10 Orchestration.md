# 20.10 Orchestration

A **container orchestrator** schedules and manages containers across hosts. It reconciles desired state—such as three replicas of an image—with observed state. Functions include placement, restart, service discovery, rolling replacement, health evaluation, configuration, secrets, and volume attachment.

A **declarative configuration** states a desired outcome. A **controller** repeatedly observes and acts to reduce difference from that desired state. This **reconciliation loop** is eventually convergent, not one atomic transaction across a cluster.

Desired replica count 3 does not mean exactly three processes exist at every instant. During rollout or failure there can be fewer or more according to policy. Applications must tolerate overlap between versions, duplicate job execution, changing addresses, and partial readiness.

Readiness and liveness have distinct purposes:

- **liveness** asks whether restart may recover a stuck process;
- **readiness** asks whether traffic should be sent now;
- **startup** can grant slow initialisation a separate window.

A liveness check that fails whenever the database is briefly unavailable can restart every application replica, intensifying the outage. Dependency failure commonly affects readiness or endpoint responses rather than proof the process itself is unrecoverably dead.

### 20.10.1 Workload and service abstractions

Kubernetes is used here as a concrete example, not as a definition of orchestration. Its smallest scheduled unit, a **Pod**, contains one or more containers sharing selected network and storage namespaces and a lifecycle. A Pod is ordinarily disposable. Higher-level controllers create replacements:

- a **Deployment** manages interchangeable stateless replicas through ReplicaSets;
- a **StatefulSet** gives replicas stable ordinal identity and volume relationships;
- a **DaemonSet** places eligible Pods across nodes, often for node-local agents;
- a **Job** seeks a finite number of successful completions;
- a **CronJob** creates Jobs according to a schedule whose missed and duplicate execution semantics must be understood.

A **Service** supplies a stable logical endpoint over a changing backend set. ConfigMaps and Secrets distribute configuration-shaped data, but they do not determine application reload semantics and a Secret object is not automatically protected against every cluster reader. PersistentVolume abstractions connect workload claims to storage whose topology, access modes, snapshots, and failure guarantees depend on the provider.

The API server stores declared objects and their versioned state. Controllers watch and reconcile independently. There is no global transaction making a Deployment, Service, policy, volume, and external database update simultaneous. Operators must expect intermediate combinations and design compatibility accordingly.

### Worked example 20.2 — A bounded deployment contract

~~~yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: report-api
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  selector:
    matchLabels:
      app: report-api
  template:
    metadata:
      labels:
        app: report-api
    spec:
      terminationGracePeriodSeconds: 45
      containers:
        - name: service
          image: registry.example/report-api@sha256:APPROVED_DIGEST
          ports:
            - name: http
              containerPort: 8080
          readinessProbe:
            httpGet:
              path: /ready
              port: http
            periodSeconds: 5
          livenessProbe:
            httpGet:
              path: /live
              port: http
            periodSeconds: 10
          resources:
            requests:
              cpu: 250m
              memory: 256Mi
            limits:
              cpu: "1"
              memory: 512Mi
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            runAsNonRoot: true
            capabilities:
              drop: ["ALL"]
~~~

The document makes several policies visible but proves none of their values suitable. The placeholder digest must be replaced by an approved real digest. `maxUnavailable: 0` preserves nominal replica count only if the cluster has capacity for a surge Pod and the readiness probe represents useful readiness. Three replicas can still share one node, zone, dependency, or defect unless placement and failure domains are controlled. The example omits volumes, egress policy, disruption budget, service account, topology spread, and observability because each requires system-specific decisions.

### 20.10.2 Scheduling, disruption, and rollout mathematics

Schedulers choose nodes satisfying hard constraints and optimise soft preferences from an imperfect snapshot. Resource requests, affinity, anti-affinity, topology spread, taints, tolerations, volumes, devices, and policy all affect placement. A Pod pending for lack of capacity is not repaired by a liveness probe. A workload whose replicas all fit only in one zone has not gained zonal resilience from a replica count of three.

Disruption can be involuntary—node failure—or voluntary—upgrade, drain, or autoscaler action. A **Pod disruption budget** limits certain voluntary concurrent disruptions; it cannot prevent hardware failure and does not create spare capacity. Maintenance design must combine budget, replica topology, surge room, termination grace, and dependency capacity.

During a rolling update, `maxSurge` bounds replicas above desired count and `maxUnavailable` bounds unavailable desired replicas according to controller semantics. These are availability and capacity parameters, not percentages of user traffic. Long-lived connections, client caching, readiness delay, and uneven load can expose a new version to a different fraction. Progressive delivery needs measurement at the traffic layer as well as object counts.

### 20.10.3 Probe semantics

Probe endpoints should be cheap, bounded, authenticated or network-restricted as appropriate, and free of sensitive diagnostics. Liveness asks whether local restart is a justified remedy. Readiness asks whether this instance should receive new work. Startup suppresses premature liveness judgement during known initialisation. A single `/health` endpoint often conflates all three.

Use thresholds and periods to account for transient scheduling and network delay. Probe execution itself consumes resources; a short timeout against an overloaded application can synchronise failures. Readiness should normally fail before graceful shutdown begins, but terminating endpoints can remain in client caches or connection pools, so drain time must reflect the real routing path.

> **Common misconception 20.20 — “A Pod is a durable machine.”**  
> It is a replaceable scheduled object. Durable identity and data require explicit controller, volume, database, and recovery semantics.

> **Common misconception 20.21 — “Three replicas tolerate any two failures.”**  
> Tolerance depends on failure independence, placement, quorum, state, shared dependencies, capacity, and whether remaining replicas can serve the workload.

> **Common misconception 20.22 — “A green rollout status proves the service is healthy.”**  
> It proves controller conditions under configured probes. User correctness, latency, hidden workflows, background work, and downstream effects require separate evidence.
