# 20.11 Continuous integration

**Continuous integration**, or CI, is the practice of integrating changes frequently and automatically verifying them. A **pipeline** is an ordered or dependency-structured collection of automated jobs. Typical stages:

1. source and provenance checkout;
2. dependency resolution under lock;
3. formatting/lint/type checks;
4. unit tests;
5. integration tests;
6. security and licence policy;
7. artifact build;
8. artifact test;
9. signing and publication.

The artifact should be built once after prerequisite verification and then promoted. Tests running against a source directory can pass while the built wheel omits a package or data file. Install and test the artifact itself in a clean environment.

### Worked example 20.3 — A local CI-equivalent script

~~~python
from __future__ import annotations

import subprocess
import sys
from collections.abc import Sequence


def run(command: Sequence[str]) -> None:
    print("+", *command, flush=True)
    subprocess.run(
        command,
        check=True,
    )


def main() -> int:
    run([sys.executable, "-m", "ruff", "check", "."])
    run([sys.executable, "-m", "mypy", "src"])
    run([sys.executable, "-m", "pytest", "-q"])
    run([sys.executable, "-m", "build"])
    return 0


if __name__ == "__main__":
    raise SystemExit(main())
~~~

Argument lists preserve command structure. <code>sys.executable</code> selects the interpreter running the script. Fail-fast <code>check=True</code> prevents publication after a failed stage. A hosted CI definition must additionally pin action/plugin versions, minimise token permissions, isolate untrusted contributions, retain test reports, and publish only from protected conditions.

CI executes code from the proposed change. A pull request can alter tests, build scripts, or package metadata to exfiltrate credentials. Workflows for untrusted changes must not expose publication tokens or production secrets.

### 20.11.1 The pipeline is a trust graph

A CI pipeline is more accurately modelled as a directed acyclic graph than as a list. Nodes consume source, dependencies, credentials, caches, earlier artifacts, and environment state; edges convey artifacts and authority. A job that depends on tests should consume their authenticated result for the same source and artifact, not merely run later by convention.

The pipeline's trust boundaries include:

- the source-hosting identity and protected-reference policy;
- workflow definitions and reusable actions;
- runner images, hypervisors, networks, and administrators;
- dependency registries and mirrors;
- caches and artifact stores;
- signing or attestation identities;
- deployment targets and approval systems.

Pinning a third-party action by a mutable major-version tag permits its bytes to change between runs. Pin by immutable revision under an update process, minimise third-party execution, and record resolved identity in provenance. A reusable pipeline component is executable dependency code even when its syntax looks declarative.

An **ephemeral runner** is created for a bounded job and discarded afterwards. This reduces persistence between mutually untrusted builds, but the base image, attached network, instance metadata, cache, and controller remain shared trust. Self-hosted runners that process public contributions should be assumed compromiseable and isolated from internal networks and durable credentials.

### 20.11.2 Caches and artifact flow

A cache accelerates recomputation and is permitted to miss. An artifact is an intended output whose identity and retention form part of the release record. Confusing them can make a cache eviction destroy evidence or let an untrusted cache entry enter a release.

Cache keys must bind every input whose mismatch affects correctness or security: operating system, architecture, interpreter, lock digest, tool version, and perhaps compiler flags. A restore-prefix fallback can deliberately accept a less-specific entry for performance, but its content must remain untrusted input to a verified build. Never cache credentials. Protect cache writes so an untrusted branch cannot poison keys later consumed by a privileged release.

Pass artifacts between jobs by digest through the CI artifact facility rather than rebuilding or relying on a mutable workspace. Test reports, coverage, static-analysis findings, SBOMs, and provenance should state source revision and artifact identity. A green test result for digest (a) cannot approve digest (b), even if both display the same release version.

### 20.11.3 Credentials and untrusted changes

Modern CI systems can exchange a short-lived workload identity assertion for a narrowly scoped cloud or registry credential. This **federated workload identity** removes a reusable secret from repository settings, but its policy becomes critical. Bind trust to repository, protected reference, workflow identity, environment, audience, and where supported the exact reusable workflow. A policy trusting every branch or every repository in an organisation recreates a broad static secret in another form.

Separate validation from publication. Untrusted changes receive no release authority and run with read-only source access, restricted network, bounded compute, and isolated caches. A later trusted workflow may consume a reviewed source revision or attested artifact, but it must not blindly execute mutable outputs produced by the untrusted job. Manual approval is meaningful only if the approver can see exactly which immutable subject and policy the approval authorises.

Flaky tests are not harmless noise. Retrying until green changes a test from an assertion into a probabilistic filter whose false-acceptance rate increases with attempts. Quarantine may preserve delivery while ownership and a deadline remain explicit, but the affected property has lost evidence. Measure flake rate, retain failed attempts, and repair or remove nondeterminism rather than concealing it.

> **Common misconception 20.23 — “A CI job is safe because it runs before merge.”**  
> It executes attacker-influenced code against runner, network, cache, metadata, and platform interfaces. Pre-merge placement does not remove authority.

> **Common misconception 20.24 — “Caches are trusted because CI created them.”**  
> Their writers, keys, fallback rules, and retention determine trust. Treat restored content as untrusted acceleration and verify release inputs independently.

> **Common misconception 20.25 — “A manual approval secures deployment.”**  
> Approval without an immutable subject, intelligible evidence, bounded authority, and enforced post-approval immutability is a ceremonial click, not a control.
