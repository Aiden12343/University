# 20.12 Continuous delivery and deployment

**Continuous delivery** keeps software in a releasable state and automates movement toward production while a human or policy can approve release. **Continuous deployment** automatically releases every change satisfying the pipeline. Organisations use the terms inconsistently, so state actual controls.

A deployment changes running state. Strategies include:

- **recreate:** stop old version, start new; simple but introduces downtime;
- **rolling:** replace subsets gradually;
- **blue–green:** prepare a complete parallel environment, then switch traffic;
- **canary:** send a small selected traffic fraction to the new version, evaluate, and expand;
- **feature flag:** deploy code separately from enabling behaviour.

A strategy must cover database schema, background workers, queues, caches, scheduled jobs, and external contracts, not only request-serving containers.

Feature flags create runtime branches and operational state. Each needs owner, purpose, default, audit, expiry, and cleanup. Long-lived flags multiply test combinations and can become an unaudited configuration system.

### 20.12.1 Release, deployment, and exposure

A **release** makes a capability available for intended use; a **deployment** changes installed or running artifacts. The two can be decoupled. Code may be deployed dark behind a flag, or a previously deployed capability may be released to a selected population. This separation reduces simultaneous change only when flag state and targeting are themselves governed and observable.

Model delivery as a state machine whose subject is an artifact digest plus configuration and schema versions:

\[
\text{built}\rightarrow\text{verified}\rightarrow\text{staged}
\rightarrow\text{canary}\rightarrow\text{general}\rightarrow\text{retired}.
\]

Transitions require evidence and authority. Skipping a state during an emergency should be an explicit exceptional transition, not an undocumented manual path. An environment is not merely a name; it is a set of identities, data classes, quotas, networks, regions, dependencies, and policy. Staging can demonstrate mechanism but cannot prove production-scale behaviour when these differ.

Progressive exposure limits **blast radius**, the maximum affected population or resource scope before evaluation. Useful dimensions include replica count, traffic percentage, tenants, regions, operations, data classes, and time. Five per cent of traffic can still include the largest customer or all write operations. Select the dimension that bounds actual harm.

### 20.12.2 Canary inference

A canary comparison asks whether evidence under the new version is compatible with an acceptable effect, not merely whether its graph “looks normal”. Define before rollout:

- primary user and safety indicators;
- guardrail resource and dependency indicators;
- baseline and canary populations;
- minimum event count and observation duration;
- acceptable effect size, not only statistical significance;
- automatic stop and rollback conditions;
- handling for low traffic, delayed effects, seasonality, and multiple comparisons.

Random assignment improves comparability when feasible. Instance-based canaries can be biased by geography, cache warmth, tenant mix, or connection routing. A very large sample can make a trivial difference statistically significant; a small sample can miss a harmful difference. Engineering judgement therefore combines confidence intervals, practical thresholds, and known worst-case consequences.

### 20.12.3 Stateful evolution: expand, migrate, contract

Mixed versions make one-step breaking schema changes unsafe. An **expand–migrate–contract** sequence separates them:

1. expand the schema or protocol so old and new code can coexist;
2. deploy code capable of the old and new representation;
3. migrate or backfill data through a restartable, observable process;
4. switch reads or writers under measured control;
5. prove no supported process depends on the old representation;
6. contract by removing it in a later release.

Dual writing can bridge representations but creates consistency questions when one write succeeds and the other fails. Prefer a transactional outbox, change stream, or authoritative single write plus derived migration where the data system supports it. A backfill must be rate-limited, checkpointed, idempotent, and distinguish its load in telemetry. It competes with user traffic for database, cache, and network capacity.

Background workers need rollout coordination. If new producers emit messages old consumers cannot parse, a rolling application deployment can poison the queue. Version envelopes, tolerant readers, staged producers, and dead-letter policy make the transition explicit. Scheduled jobs may execute once under each version during overlap; leases and idempotent operations must cover that case.

> **Common misconception 20.26 — “A canary is safe because only one replica runs the new version.”**  
> Traffic distribution, request cost, tenant concentration, shared writes, and asynchronous effects determine exposure. Replica fraction is not harm fraction.

> **Common misconception 20.27 — “Database migrations occur before or after deployment.”**  
> In continuously available systems they are often a sequence spanning multiple compatible releases, backfills, verification gates, and delayed contraction.
