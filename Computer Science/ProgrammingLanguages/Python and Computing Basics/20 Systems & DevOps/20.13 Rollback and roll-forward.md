# 20.13 Rollback and roll-forward

A **rollback** restores a previously known application artifact or configuration. It is only safe if state remains compatible. A destructive database migration, emitted message format, or external side effect cannot necessarily be reversed by starting old code.

Plan rollback before deployment:

- previous artifact digest is retained;
- configuration versions are recorded;
- schema is backward compatible;
- queue messages are understood by both versions;
- feature flags can disable new behaviour;
- rollback permissions and commands are tested;
- evidence defines when to trigger it.

Sometimes a **roll-forward** patch is safer than rollback because new state has already been written. Disaster recovery is not an improvised deployment reversal; backups require restoration testing, point-in-time objectives, key availability, and dependency reconstruction.

### 20.13.1 Reversibility is a property of the transition

An artifact may be perfectly preserved while the deployment remains irreversible. Classify every change by the state it can affect:

| State class | Typical rollback concern |
|:---|:---|
| stateless code | old process may not accept new configuration or protocol |
| database schema | removed or transformed data may not be reconstructable |
| database contents | new writes may violate old invariants |
| messages | old consumers may reject new envelopes or semantics |
| caches and indexes | stale entries or new key format may survive artifact change |
| external effects | email, payment, deletion, or partner call cannot be “un-sent” |
| identity and policy | revoked or broadened authority may have continuing consequences |

A **reversible migration** supplies a defined inverse under stated preconditions. Many transformations are only compensatable: one can create a new business action that offsets the old one, while preserving both in the audit record. Refund is not rollback of a payment; it is a second financial event.

Rollback testing must begin after the new version has written representative state, not merely immediately after start. Validate old readers, queued messages, leases, configuration schema, and dashboards. Preserve the exact old artifact and its dependency availability. A rollback path that requires rebuilding an unsupported image during an incident is not a tested rollback.

### 20.13.2 Decision rules and forward repair

Predefine conditions favouring rollback: recent attributable change, compatible state, fast safe restoration, and no security reason to prohibit the old version. Conditions favouring roll-forward include irreversible data transition, severe known vulnerability in the old release, or a small well-understood defect with a tested patch.

Mitigation can be neither: disable one feature, shed expensive traffic, isolate a tenant, increase capacity temporarily, stop a producer, or switch to a safe degraded mode. The incident objective is restoration of acceptable service, not ritual return to a previous version.

Record the decision with artifact, schema, configuration, time, evidence, authority, expected result, and abort condition. This turns rollback into an observable experiment and prevents repeated oscillation between versions when the suspected cause is wrong.

> **Common misconception 20.28 — “Rollback reverses a deployment.”**  
> It replaces selected executable or configuration state. Data mutations, messages, external effects, security exposure, and learned client behaviour can remain.

> **Common misconception 20.29 — “Roll-forward is merely accepting more risk.”**  
> When state is incompatible with old code, a narrowly scoped forward repair can be the lower-risk and more reversible path.
