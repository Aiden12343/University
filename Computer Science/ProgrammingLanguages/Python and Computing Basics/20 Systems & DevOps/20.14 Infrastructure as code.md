# 20.14 Infrastructure as code

**Infrastructure as code**, or IaC, represents infrastructure configuration in version-controlled machine-readable definitions executed by tools. It supplies review, repeatability, dependency planning, and change history. It does not make infrastructure ordinary pure code: providers are remote stateful systems with asynchronous operations, quotas, defaults, and manual drift.

An IaC resource declares desired properties:

~~~hcl
resource "example_object_store" "reports" {
  name               = "reports-production"
  versioning_enabled = true
  public_access      = false

  retention_days = 90
}
~~~

The syntax is illustrative. The provider translates it into API operations and records identity in **state**, a mapping between declared resources and remote objects. State can contain sensitive values and must be protected, locked during updates, backed up, and access-controlled.

A **plan** compares configuration, recorded state, and refreshed remote observations to propose actions. Reviewers should inspect replacements, permission expansions, deletions, and unknown values. The actual apply can differ if remote state changes after planning; high-risk systems use saved plans, locks, policy, and staged environments.

### 20.14.1 Resource graphs and provider semantics

IaC tools infer or accept a dependency graph. A reference from resource (B) to an attribute of (A) creates an edge (A\rightarrow B); a topological walk orders operations where possible. Independent nodes may be changed concurrently. An explicit dependency is needed when the remote relationship is real but no data reference expresses it. Adding unnecessary dependencies serialises work and can create cycles.

The graph does not make remote operations transactional. If nodes (A) and (B) succeed and (C) fails, the provider may leave (A) and (B) changed. A subsequent plan should converge from observed state. Modules must therefore tolerate partial application and avoid assuming “apply failed” means “nothing happened”.

A **provider** translates declared resources into API reads and mutations. Provider versions change schemas, defaults, import behaviour, diff suppression, and upgrade logic. Lock provider versions and checksums; review upgrades like library changes. The cloud service can change independently, so a pinned provider does not freeze remote semantics.

Values can be unknown during planning because an identifier or endpoint will exist only after creation. A policy or reviewer must distinguish “known safe” from “not yet known”; rendering unknown as an empty string or ignoring it can approve a property never inspected. Prefer designs whose security-critical scope is known before apply.

### 20.14.2 State, locking, and separation

IaC state maps logical addresses to remote identities and stores attributes used for planning. Even values marked sensitive may exist in state; the marking commonly controls display, not storage. Protect state with encryption, access control, versioning, audit, backup, and a locking mechanism suited to concurrent operations. Do not grant every plan reader all production secrets merely for convenience.

Divide state by lifecycle and authority boundary rather than putting an organisation into one global file. Excessive fragmentation creates dependencies and coordination cost; insufficient separation grants broad read/write access and creates a large failure domain. Publish narrow non-secret outputs through a dedicated interface rather than allowing consumers to read a producer's entire state snapshot.

Import brings an existing remote object under a declared address. It does not generate a correct desired configuration or prove the object matches policy. After import, plan until the intended no-change baseline is understood, and protect against accidental replacement. Moving a resource address within state changes management identity; it must preserve the same remote object deliberately.

### Worked example 20.4 — Classify dangerous plan actions

~~~python
from dataclasses import dataclass
from enum import StrEnum


class PlanAction(StrEnum):
    CREATE = "create"
    UPDATE = "update"
    REPLACE = "replace"
    DELETE = "delete"


@dataclass(frozen=True)
class PlannedResource:
    address: str
    action: PlanAction
    contains_unknown_security_scope: bool = False


def requires_explicit_approval(resource: PlannedResource) -> bool:
    return (
        resource.action in {PlanAction.REPLACE, PlanAction.DELETE}
        or resource.contains_unknown_security_scope
    )
~~~

The classifier is deliberately a small policy component, not an IaC parser. Production tooling consumes the tool's versioned machine-readable plan, authenticates its origin, checks sensitive resource types and permission expansions, and binds approval to the saved plan digest. Text scraping is too brittle for an enforcement boundary.

### 20.14.3 Module interfaces and policy

An infrastructure module is an abstraction with inputs, outputs, invariants, upgrade rules, and ownership. Expose intent—retention class, service identity, or availability tier—rather than every provider option. Overly thin wrappers add naming without policy; overly rigid modules force callers to escape and create unmanaged resources.

Validate inputs, constrain versions, document destructive transitions, and test upgrades from supported prior versions. Policy as code can reject public storage, unencrypted state, wildcard permissions, or unapproved regions, but policy inherits the completeness limits of plan data and schemas. Maintain exception identity, owner, expiry, rationale, and compensating controls.

> **Common misconception 20.30 — “A no-change plan proves infrastructure is correct.”**  
> It shows agreement among configuration, state, observations, provider semantics, and ignored attributes. All can agree on an insecure or unavailable design.

> **Common misconception 20.31 — “IaC apply is a transaction.”**  
> Remote mutations can partially succeed, time out ambiguously, or be changed concurrently. State refresh and reconciliation are fundamental, not merely recovery from tool defects.
