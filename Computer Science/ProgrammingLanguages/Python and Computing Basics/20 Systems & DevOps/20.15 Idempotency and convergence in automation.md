# 20.15 Idempotency and convergence in automation

Operational automation should commonly be idempotent: repeated execution drives the system to the same desired state. “Install package if missing” is more robust than “append installation command output and hope.”

Idempotency does not mean no work. A reconciliation loop can query state every time and make no mutation when compliant. Some operations—key rotation, database migration, certificate issuance—are inherently versioned transitions and need recorded identity rather than naive repetition.

### Worked example 20.5 — Idempotent directory state

~~~python
from dataclasses import dataclass
from pathlib import Path
import os


@dataclass(frozen=True)
class DirectoryResult:
    path: Path
    created: bool


def ensure_private_directory(path: Path) -> DirectoryResult:
    try:
        path.mkdir(mode=0o700, parents=True)
        created = True
    except FileExistsError:
        created = False

    if not path.is_dir():
        raise RuntimeError(f"{path} is not a directory")

    os.chmod(path, 0o700)
    return DirectoryResult(path=path, created=created)
~~~

The function converges a path toward a directory and permission mode on a Unix-like platform. It distinguishes creation from preexistence and rejects a non-directory. It remains vulnerable to races and symbolic-link semantics in an adversarial writable parent; infrastructure automation must operate under a trusted ownership boundary or use lower-level descriptor controls.

### 20.15.1 State idempotency and request idempotency

For a state transformation (f), mathematical idempotency means

\[
f(f(s))=f(s).
\]

“Ensure the directory exists with mode 0700” can approximate this property. “Add one worker” does not; repeated application increases count. State-oriented interfaces declare the desired worker count, while transition-oriented interfaces need an operation identity or precondition.

**Request idempotency** means retries of the same logical request have the same intended effect as one execution. It is not established merely because an HTTP method is conventionally idempotent. A poorly implemented `PUT` can append audit rows, send repeated notifications, or generate a new resource each time.

An idempotency-key protocol commonly:

1. chooses an unpredictable or collision-resistant key scoped to caller and operation;
2. stores the key, a canonical request digest, status, and result atomically with or before the effect;
3. rejects reuse with a different request;
4. returns the recorded result for a completed duplicate;
5. defines behaviour for an in-progress duplicate;
6. retains the record longer than every legitimate retry horizon.

If the effect occurs in an external system that does not share the transaction, exactly-once semantics are generally unavailable. Use the external system's idempotency key, a transactional outbox, reconciliation, or compensating action. “Exactly once” is an end-to-end claim about observation and effect, not a queue setting.

### 20.15.2 Convergence and monotonic progress

A controller observes current state (o_t), compares it with desired state (d_t), and selects an action (a_t). Convergence requires that repeated actions under stable (d) tend to reduce a meaningful distance from desired state. External controllers, delays, rate limits, and non-monotonic dependencies can produce oscillation.

Prefer **monotonic** transitions where information or completed work accumulates in one direction: an artifact moves from unverified to verified for a fixed digest; a migration checkpoint advances; a deletion tombstone prevents resurrection. Monotonic design reduces coordination because old observations cannot legitimately reverse completed facts without an explicit new version.

Controllers need ownership boundaries. Two controllers writing the same field from different desired sources can fight indefinitely. Server-side field ownership, version preconditions, leases, or a single authoritative reconciler make conflict observable. A last-write-wins update can converge while silently discarding intent.

> **Common misconception 20.32 — “Retrying an idempotent operation is free.”**  
> Repeated requests still consume bandwidth, CPU, locks, logs, and quota, and may repeat secondary effects not covered by the idempotency contract.

> **Common misconception 20.33 — “Convergence means the system moves smoothly toward desired state.”**  
> Reconciliation can overshoot, oscillate, stall on quotas, or conflict with another controller. Stability requires ownership, feedback timing, bounded actions, and observability.
