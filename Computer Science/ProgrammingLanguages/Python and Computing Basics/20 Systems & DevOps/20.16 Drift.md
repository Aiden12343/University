# 20.16 Drift

**Configuration drift** is divergence between intended and actual system state. It arises from emergency manual changes, provider defaults, automated controllers, failed partial operations, or undocumented dependencies.

Drift detection refreshes observations and compares them with declared state. Automatic correction is not always safe: an incident responder may have intentionally blocked traffic. Systems need a break-glass process that records manual changes, duration, owner, reason, and reconciliation plan.

Immutable replacement reduces in-place drift for application hosts: construct a new image, test it, replace instances, and discard old ones. Databases and durable services still evolve in place and need separate control.

### 20.16.1 Sources and classes of drift

Distinguish at least four classes:

- **declared drift:** the configuration repository changed but has not been applied;
- **remote drift:** a person, controller, or provider changed the remote object outside the declaration;
- **semantic drift:** provider defaults or service behaviour changed while visible fields appear equal;
- **inventory drift:** a resource exists but is absent from the system's declared ownership and state.

The last class is easy to miss because a plan tool compares only resources it knows. Cloud inventory, billing, DNS, certificate, and identity scans can reveal orphans. Tags and ownership metadata help but are mutable claims; correlate with account, audit, state, and creation identity.

Drift can be desirable temporarily. Incident responders may block traffic, raise capacity, or revoke an identity faster than the normal pipeline. A break-glass change should create a durable record containing target, before and after state, actor, reason, expiry, and intended reconciliation. The regular controller must either pause or recognise the override; otherwise it may immediately undo the mitigation.

### 20.16.2 Detection and reconciliation policy

Run read-only refresh under a schedule and after significant incidents. Classify differences by consequence rather than volume. A changed description is not equivalent to a public-access rule, deleted backup policy, or provider-forced replacement. Alert only when an owner can act; retain lower-severity evidence for trend and audit.

Possible treatments are:

1. **revert remote state** to the declaration;
2. **adopt the remote change** by reviewed configuration and state update;
3. **replace the resource** from a known artifact;
4. **preserve an exception** with scope and expiry;
5. **investigate semantic mismatch** when the diff is empty but behaviour changed.

Automatic reconciliation is appropriate only where the declared source is authoritative and reversal is safe. Identity revocation, firewall containment, and human emergency changes often require a precedence model rather than blind correction.

> **Common misconception 20.34 — “Drift is any difference from the repository.”**  
> Repository, state, remote observations, provider semantics, and authorised overrides are distinct sources. The difference must be classified before deciding which source is wrong.

> **Common misconception 20.35 — “Automatic drift correction is always safer.”**  
> It can undo incident containment, recreate deliberately deleted resources, or repeat a destructive declaration. Authority and exception semantics must precede automation.
