# 20.17 Cloud APIs and SDKs

A cloud **software development kit**, or SDK, wraps remote provider APIs. A Python method call can cross a network, authenticate, encounter rate limits, partially succeed, or return eventually consistent state. It is not an ordinary local object method despite similar syntax.

~~~python
from __future__ import annotations

from dataclasses import dataclass
from typing import Protocol


class ObjectStore(Protocol):
    def put_object(
        self,
        *,
        bucket: str,
        key: str,
        body: bytes,
        metadata: dict[str, str],
    ) -> object:
        ...


@dataclass(frozen=True)
class StoredReport:
    bucket: str
    key: str
    digest: str


def store_report(
    client: ObjectStore,
    *,
    bucket: str,
    key: str,
    body: bytes,
    digest: str,
) -> StoredReport:
    client.put_object(
        bucket=bucket,
        key=key,
        body=body,
        metadata={"sha256": digest},
    )
    return StoredReport(bucket, key, digest)
~~~

The protocol narrows the client capability and permits a test double. The function still cannot know from an interrupted call whether the provider committed the object. A deterministic key and digest make retries converge if overwrite semantics are acceptable. For create-once semantics, use provider preconditions or an operation record.

SDK defaults for retry, timeout, region, credential discovery, and endpoint must be understood. A default credential chain can accidentally use a developer’s broad personal credentials. Production supplies a workload identity with least privilege.

### 20.17.1 A remote call has ambiguous outcomes

Consider a client that sends a create request, the server commits it, and the response is lost. The client observes a timeout, which does not reveal whether the effect occurred. Retrying with a different identity can duplicate the resource; refusing to retry can leave a successful but undiscovered object. This is the **two-generals-shaped** uncertainty of acknowledgement across a failing channel, although practical systems mitigate rather than solve it absolutely.

Design the API interaction around one of:

- a client-chosen stable resource name with create-if-absent precondition;
- a provider-supported idempotency token;
- a request record queried after ambiguity;
- a deterministic reconciliation that lists and matches intended identity;
- a compensating cleanup whose own authority and ambiguity are controlled.

HTTP status and SDK exception taxonomies are inputs, not sufficient retry policy. Retry only failures classified transient for that operation, and respect server guidance. Authentication failure, validation error, exhausted quota, and conflict usually require different action. A 500 response after a committed operation can still be ambiguous.

### Worked example 20.6 — Bounded retry with injected time and randomness

~~~python
from __future__ import annotations

import random
import time
from collections.abc import Callable
from typing import TypeVar


T = TypeVar("T")


class TransientRemoteError(Exception):
    pass


def retry_transient(
    operation: Callable[[], T],
    *,
    attempts: int = 4,
    base_delay: float = 0.1,
    maximum_delay: float = 2.0,
    sleep: Callable[[float], None] = time.sleep,
    uniform: Callable[[float, float], float] = random.uniform,
) -> T:
    if attempts < 1 or base_delay < 0 or maximum_delay < 0:
        raise ValueError("invalid retry policy")

    for attempt in range(attempts):
        try:
            return operation()
        except TransientRemoteError:
            if attempt + 1 == attempts:
                raise
            ceiling = min(maximum_delay, base_delay * (2**attempt))
            sleep(uniform(0.0, ceiling))

    raise AssertionError("unreachable")
~~~

Injected `sleep` and `uniform` make timing policy deterministically testable. The function deliberately does not guess which provider exceptions are transient, enforce a total wall-clock deadline, consume a shared retry budget, or make `operation` idempotent. A production adapter supplies those semantics and emits attempt, cause, delay, and final outcome without logging sensitive request bodies.

### 20.17.2 Pagination, consistency, and concurrency

List APIs commonly paginate. A page token may represent continuation over a changing collection rather than a stable snapshot. Objects can be missed or repeated while creation and deletion occur. Consumers should deduplicate by stable identity, follow tokens exactly, bound total work, and decide whether they require snapshot semantics. Never assume a missing object after one eventually consistent read proves deletion.

Optimistic concurrency uses an observed version, entity tag, or generation as a precondition: update only if the remote object still has version (v). A conflict forces reread and policy-level merge, preventing silent lost update. Retrying the same unconditional whole-object write can erase another actor's fields.

SDK clients often pool connections and may be safe for concurrent requests while paginators, response streams, or transaction objects are not. Read the versioned SDK contract. Create expensive clients at an appropriate scope, close them at shutdown, set connection and operation timeouts, and limit in-flight calls so the local process does not become the source of provider throttling.

Test adapters with scripted outcomes: success, transient failure, permanent failure, throttling with retry guidance, timeout after commit, pagination duplication, stale read, version conflict, and credential expiry. A mock that always returns immediate success verifies only Python call syntax.

> **Common misconception 20.36 — “A timeout means the cloud operation failed.”**  
> It means the client did not receive a qualifying completion in time. The remote effect may be absent, pending, or committed.

> **Common misconception 20.37 — “The SDK's default retries make a program resilient.”**  
> Defaults may amplify load, exceed the caller's deadline, repeat unsafe effects, or differ by version. End-to-end policy must bound and observe them.
