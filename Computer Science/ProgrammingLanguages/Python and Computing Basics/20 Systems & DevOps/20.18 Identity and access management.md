# 20.18 Identity and access management

Cloud **identity and access management**, or IAM, maps principals to permitted actions on resources under conditions. A policy is executable authority. Wildcards such as every action on every resource are not harmless conveniences; they define blast radius.

Workloads should receive short-lived credentials from their runtime identity rather than static keys embedded in files. Human administration should use individual identities, strong authentication, role assumption, approval for exceptional authority, and audit.

Policy design starts from operations:

| Component | Required operations | Explicit exclusions |
|:---|:---|:---|
| report writer | create objects under one prefix | read other prefixes, delete, change policy |
| report reader | read approved objects | write, list secrets, administer bucket |
| deployment job | update one service to signed image | create administrators, read customer data |
| backup process | read database snapshot stream and write backup | serve application traffic |

Permission simulation tools help but do not model every service condition or data path. Test both allowed and denied operations in a staging account.

An emergency **break-glass** role has powerful authority protected by strong controls, alerting, short sessions, and post-use review. It must be tested; a sealed credential nobody can access during an outage does not provide availability.

### 20.18.1 Policy evaluation and resource scope

An IAM decision evaluates principal, action, resource, and context under provider-specific policy combination rules. Context can include time, network, device, authentication strength, session tags, source workload, and requested attributes. An explicit deny commonly overrides allows, but inheritance, organisation boundaries, resource policies, permission boundaries, and service-control policies vary. Never infer one provider's evaluation model from another's vocabulary.

Resource scope should follow data and control boundaries. “Read objects in bucket X” may permit every tenant unless a prefix or object attribute is constrained. “Update service Y” may permit replacement with an arbitrary image, effectively granting code execution under the service identity. Analyse the transitive authority of an action, not only its name.

Privilege escalation paths include:

- modifying a policy or role trust relationship;
- attaching a stronger role to a workload;
- passing a service role to a compute job;
- changing code executed by a privileged pipeline;
- writing a configuration, startup script, or image consumed by a stronger principal;
- reading credentials or state that convey another authority.

A least-privilege review therefore constructs an authority graph. Direct permissions are only its first edge.

### 20.18.2 Federation and workload identity

**Federation** allows one identity system to accept assertions from another under a trust policy. Human users can authenticate centrally and assume time-bounded roles; workloads can present platform identity instead of storing long-lived keys. The receiving system must validate issuer, audience, signature, time, subject, and policy-specific claims. A signed token for the wrong audience is not a credential for this service.

Short-lived credentials reduce exposure duration but do not fix excessive scope. Renewal paths must remain available, clocks must be sufficiently synchronised, and software must refresh before expiry without creating a request storm. Cache credentials only in process memory or protected platform facilities according to the threat model, never in build layers or broad shared volumes.

Separate deployment authority from application data authority. A pipeline able to update code can often cause the new code to use the application's identity, so it has indirect data authority even if it cannot call the database directly. That is an architectural fact to govern, audit, and constrain through review, signed artifacts, admission, and narrow runtime identity.

### 20.18.3 Lifecycle and review

Every principal needs an owner, purpose, credential method, policy source, creation time, last use, review interval, and retirement condition. Service accounts without ownership become permanent invisible administrators. Access reviews should examine observed use and transitive escalation, but unused does not automatically mean unnecessary: disaster-recovery roles are intentionally rare and must be tested separately.

Break-glass access should require strong phishing-resistant authentication where feasible, independent notification, short session, reason, command or action audit, and retrospective review. Avoid a circular dependency in which the same failed identity provider is required to obtain emergency identity-provider administration.

> **Common misconception 20.38 — “A read-only role cannot cause change.”**  
> Read access to secrets, state, private source, customer data, or signed artifacts can convey authority or enable consequential external action.

> **Common misconception 20.39 — “Short-lived credentials are low privilege.”**  
> Lifetime limits duration, not action or resource scope. A five-minute organisation-administrator credential can have catastrophic blast radius.
