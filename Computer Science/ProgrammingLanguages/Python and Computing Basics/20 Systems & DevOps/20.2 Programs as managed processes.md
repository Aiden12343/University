# 20.2 Programs as managed processes

A long-running service is still a process under Chapter 2’s model. It has:

- an executable and arguments;
- an environment;
- a current directory;
- open file descriptors or handles;
- an operating-system identity and privileges;
- memory and CPU use;
- parent and child relationships;
- signals or control events;
- an exit status.

An **init system** or **service manager** starts, stops, supervises, and restarts services according to configuration. A **daemon** is a background service process, historically detached from an interactive terminal. Modern service managers often prefer a foreground process whose standard streams and lifecycle they supervise directly.

Do not implement daemonisation, log rotation, crash restart, and privilege management inside every Python application when the platform provides a service manager. Application code should expose a clear process contract.

### Worked example 20.1 — A signal-aware worker

~~~python
from __future__ import annotations

import signal
import time
from threading import Event

stopping = Event()


def request_stop(
    signum: int,
    frame: object,
) -> None:
    stopping.set()


signal.signal(signal.SIGTERM, request_stop)
signal.signal(signal.SIGINT, request_stop)

while not stopping.is_set():
    perform_one_bounded_unit_of_work()
    stopping.wait(timeout=1.0)

close_resources()
~~~

The signal handler performs only a simple safe state change. The main loop observes that state between bounded work units. <code>Event.wait</code> permits early wake-up and avoids a fixed uninterruptible sleep. Cleanup occurs in ordinary control flow.

Production code defines what happens to in-progress work: complete, return to a queue, roll back, checkpoint, or abandon. It also imposes a maximum shutdown grace period. A forced process termination can occur, so durable correctness cannot rely exclusively on cleanup code executing.

### 20.2.1 The process contract

A **process contract** describes what a supervisor may assume and what the program requires. At minimum it specifies:

| Concern | Contract question |
|:---|:---|
| start | Which executable, arguments, directory, environment, identity, and resource limits are required? |
| readiness | What observable event proves the process can accept its assigned work? |
| health | Which internal failures are recoverable without restart, and which require termination? |
| shutdown | Which notification is sent, how is new work refused, and how long may draining take? |
| state | Which paths, sockets, queues, and remote systems contain durable or recoverable state? |
| output | Which streams and structured events are emitted, and what must never be logged? |
| failure | Which exit statuses and termination signals distinguish configuration, transient, and software defects? |

Unix-like processes inherit open file descriptors, environment, credentials, signal dispositions, resource limits, and working directory from their parent unless the creation operation changes them. Inheritance is convenient but creates **ambient state**: behaviour depends on resources not visible in the function or command line. Supervisors should close unintended descriptors, construct a minimal environment, set a deterministic working directory, and grant a narrow operating-system identity.

The process with identifier 1 inside a Linux PID namespace has special lifecycle responsibilities. It adopts orphaned descendants and must reap exited children; signal behaviour can also differ from that of an ordinary process. An application placed directly at container PID 1 should either manage these duties correctly or use a small reviewed init process. A shell wrapper that fails to replace itself with the application can intercept signals and make graceful shutdown unreliable.

### 20.2.2 Admission, draining, and termination

Graceful shutdown is a protocol, not a signal handler. A request-serving process usually moves through states such as starting, ready, draining, and stopped. On termination it should first become unready, then stop accepting new work, allow bounded in-flight work to reach a defined safe point, flush only telemetry whose loss policy permits delay, release leases, and exit before the supervisor's deadline. The ordering prevents a load balancer from sending new requests while old requests drain.

A worker pulling durable jobs must coordinate claim and acknowledgement. If it acknowledges before the side effect, a crash can lose work. If it performs the side effect before acknowledgement, a crash can cause redelivery and duplicate effect. The standard resolution is not “shut down more carefully”; it is an idempotent operation, transactional coupling, or a deduplication record that makes at-least-once delivery safe under interruption.

A service manager can express dependencies, restart policy, credentials, filesystem protections, resource limits, and environment without adding them to application code. The following abbreviated systemd unit is illustrative rather than portable:

~~~ini
[Unit]
Description=Report ingestion worker
After=network-online.target

[Service]
Type=notify
ExecStart=/opt/report-worker/venv/bin/python -m report_worker
WorkingDirectory=/var/lib/report-worker
User=report-worker
Group=report-worker
Restart=on-failure
RestartSec=5s
TimeoutStopSec=45s
NoNewPrivileges=yes
PrivateTmp=yes
ProtectSystem=strict
ReadWritePaths=/var/lib/report-worker

[Install]
WantedBy=multi-user.target
~~~

`Type=notify` requires the process to tell the manager when initialisation is complete; printing “started” is not an equivalent machine-readable readiness protocol. Hardening directives narrow filesystem and privilege access, but each must be tested against actual runtime requirements. A setting copied from a checklist without understanding may either break recovery or leave an unstated path writable.

> **Common misconception 20.3 — “Handling SIGTERM makes shutdown graceful.”**  
> The handler merely begins a state transition. Grace requires admission closure, bounded draining, durable job semantics, dependency deadlines, supervisor coordination, and correctness under forced termination.

> **Common misconception 20.4 — “A container has only one process.”**  
> A container can contain a process tree. The one-process convention encourages focused lifecycle ownership; it is not a kernel rule, and helper or child processes still require signal propagation and reaping.
