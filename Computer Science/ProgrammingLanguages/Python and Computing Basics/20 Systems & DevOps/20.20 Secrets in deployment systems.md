# 20.20 Secrets in deployment systems

Deployment platforms often inject secrets as environment variables, mounted files, or service API responses. The mechanism should preserve:

- encryption at rest and in transit;
- workload identity;
- least-privilege retrieval;
- versioning and rotation;
- audit;
- revocation;
- redaction;
- no inclusion in build artifacts.

Mounted secret files can be updated independently of a process, but the application must define reload behaviour. Environment variables normally require process replacement to change. Rotation plans account for overlap: a database may temporarily accept old and new credentials while clients roll.

Secrets should not be passed as build arguments, embedded in IaC state as plaintext, printed in debug output, or returned by health endpoints. CI masking based on exact text can fail for encoded, split, or transformed values; avoid exposing the value in the first place.

### 20.20.1 The secret-zero problem

A workload needs some initial basis for obtaining further secrets. This **secret zero** should preferably be a platform-established identity—such as a signed workload assertion, hardware-rooted identity, or orchestrator-bound service account—rather than a reusable key baked into the artifact. The secret store authenticates that identity and returns a scoped, short-lived credential or performs the sensitive operation on the workload's behalf.

Bootstrapping merely relocates trust. If any Pod in a namespace can assume the same service account, or any process on a host can query unrestricted instance metadata, the platform identity is too broad. Bind identity to workload, namespace, image or deployment policy where supported, audience, and requested secret path. Protect the agent or metadata channel from server-side request forgery.

Secrets have states: generated, distributed, active, rotating, retired, revoked, archived where policy requires, and destroyed. Inventory every copy and derivative. A database password can appear in process memory, connection pools, crash dumps, shell history, IaC state, CI logs, telemetry, support bundles, backups, and developer machines. Rotation that changes only the central record leaves those copies and sessions valid.

### 20.20.2 Rotation without outage

Rotation is a compatibility transition. For a shared credential:

1. create a new version under authorised generation;
2. permit new and old versions for a bounded overlap if the system supports it;
3. distribute or make the new version discoverable;
4. cause clients to establish new sessions with it;
5. verify adoption from server-side evidence;
6. revoke the old version and terminate or expire sessions where necessary;
7. investigate clients still presenting the retired identity.

Single-secret systems may require coordinated restart or proxy indirection. Rotation frequency should reflect compromise risk and operational capability; automatic frequent rotation that is never tested under dependency failure can create repeated outages. Emergency revocation needs a faster path than routine scheduled rotation.

Applications reading a mounted file should reopen it rather than assume an existing descriptor sees replacement. Atomic symbolic-link or directory updates can change a path target while the old inode remains open. Environment variables ordinarily remain fixed for the process. Define reload signal, polling interval, validation, fallback, and failure behaviour.

### 20.20.3 CI and deployment secrets

Prefer identity federation for registry, signing, and cloud deployment so CI receives narrowly scoped ephemeral authority. A release workflow should not expose production credentials to tests or arbitrary scripts. Isolate credential-bearing steps, restrict command and network surface, and attest the subject they publish.

Secret scanning detects known patterns after a value reaches a repository or artifact; it does not prove absence and can miss encoded or format-valid custom credentials. Treat a committed secret as compromised even if history is rewritten. Revoke first, then remove copies and investigate use. Masking output reduces accidental display but should never be the primary containment control.

> **Common misconception 20.42 — “A managed secret store removes secrets from applications.”**  
> The application still receives a value or operation capability, and the identity used to obtain it becomes security-critical. The store centralises lifecycle; it does not abolish endpoint compromise.

> **Common misconception 20.43 — “Rotation is complete when the new value is issued.”**  
> Completion requires verified adoption, invalidation of old copies and sessions, monitoring for residual use, and a tested recovery path.
