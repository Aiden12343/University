# 20.21 Service discovery and naming

**Service discovery** maps a logical service identity to reachable endpoints. DNS is a common mechanism; registries and orchestrator APIs provide others. Endpoint membership changes during scaling and failure.

Clients should:

- resolve according to platform caching rules;
- attempt multiple healthy endpoints where appropriate;
- impose connection and operation deadlines;
- discard failed pooled connections;
- avoid assuming one address is permanent;
- authenticate the logical service identity, not merely an IP address.

Hard-coded instance addresses turn replaceable infrastructure into pets: individually maintained machines whose identity matters. **Cattle** is the imperfect historical metaphor for replaceable instances managed as a group; neutral terms such as replaceable instance are preferable because systems, not living beings, are being described.

### 20.21.1 Logical identity and endpoint sets

A discovery name should denote a logical service, not one current process. Resolution returns an endpoint set plus metadata and lifetime. The client then chooses or is directed to an endpoint and authenticates that it is speaking to the intended logical service. These are separate steps: discovery answers “where might it be?”, while authentication answers “who is there?”.

DNS A and AAAA records map a name to IPv4 and IPv6 addresses. SRV records can additionally express service, protocol, target, port, priority, and weight, although client support varies. Modern platform registries may return richer health, zone, version, or shard metadata. Do not encode critical semantics into a record type the actual client library ignores.

A DNS **time to live** (TTL) tells caches how long a record may be reused, subject to resolver implementation and local policy. It does not cause every client to refresh at the same instant or close existing connections. A process can cache forever, a proxy can obey a different maximum, and a connection pool can continue using an address after the DNS entry changes. Migration therefore needs overlap and endpoint draining, not an assumption that one TTL makes an old address disappear.

Negative answers are cached too. Creating a name immediately after clients received “does not exist” can leave an outage until negative cache expiry. Split-horizon DNS, in which the same name resolves differently by network context, can be useful but complicates diagnosis and certificate identity. Record resolver path, response, TTL, and network context when debugging.

### 20.21.2 Client-side and proxy-side discovery

In **client-side discovery**, the client obtains endpoints and performs selection. It can use zone affinity, observed latency, or consistent hashing, but every language client must implement updates, balancing, retries, and health correctly. In **proxy-side discovery**, a stable local or remote proxy resolves and selects endpoints. This centralises policy but adds a hop and a new control/data-plane dependency.

Service meshes commonly place a proxy near each workload and distribute routing policy through a control plane. Loss of the control plane should have a defined data-plane behaviour: continue with last-known-good endpoints for a bounded period, reject unsafe new policy, or fail closed for selected routes. A mesh can standardise mTLS and telemetry; it cannot understand application idempotency, tenant authorisation, or whether a retry is semantically safe.

Discovery must handle empty sets. Immediate tight re-resolution amplifies control-plane load. Use bounded backoff, preserve last-known-good endpoints only while their safety and validity permit, surface the condition, and respect a caller deadline. Stale discovery can be better than no service for a read replica and dangerous for a decommissioned privileged endpoint; policy is service-specific.

> **Common misconception 20.44 — “DNS changes take effect after the TTL.”**  
> TTL bounds standards-conforming cache reuse of a record, not connection lifetime, every resolver implementation, negative cache, application cache, or traffic drain.

> **Common misconception 20.45 — “A service mesh provides application reliability.”**  
> It can standardise transport policy and selected retries, but it cannot infer business correctness, idempotency, data consistency, or safe degradation from network metadata.
