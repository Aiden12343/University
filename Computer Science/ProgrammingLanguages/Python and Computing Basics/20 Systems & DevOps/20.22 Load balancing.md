# 20.22 Load balancing

A **load balancer** distributes requests among eligible backends. Algorithms include round robin, least outstanding work, hashing, and latency-aware choices. Distribution is not necessarily even because request costs differ and connections persist.

**Session affinity** directs related requests to one backend. It can simplify local state but causes imbalance and impedes replacement. Shared durable session state or stateless signed claims often improve flexibility, while introducing database/cache or revocation trade-offs.

Health checks remove a backend only after detection thresholds; transient failures and flapping require hysteresis. A healthy process can still be overloaded or semantically failing. Load balancers need connection limits, timeouts, draining, and protection against slow clients.

Consistent hashing can reduce key movement when cache nodes change, but hot keys remain hot. Replication and request coalescing may be needed.

### 20.22.1 Layer, algorithm, and information

A layer-4 load balancer distributes transport connections using network and transport fields. A layer-7 balancer parses an application protocol such as HTTP and can route by host, path, headers, method, or authenticated metadata. Greater semantic information permits finer policy and also increases parser, configuration, privacy, and computational surface.

Algorithms operate on imperfect information:

- **round robin** ignores current cost and long-lived connection imbalance;
- **weighted round robin** represents expected capacity but needs maintained weights;
- **least connections** uses connection count, which may not track concurrent work;
- **least outstanding requests** better tracks request concurrency but not request cost;
- **power of two choices** samples two or more backends and chooses the less loaded, often gaining much of global least-load performance with lower coordination;
- **consistent hashing** keeps a key on a relatively stable subset as membership changes, useful for caches or affinity but vulnerable to skew and hot keys.

Choice should match protocol and workload. HTTP/2 and HTTP/3 multiplex many requests over one connection, weakening connection-count heuristics. Streaming requests can occupy capacity for minutes. GPU inference can have batching and memory constraints unlike web request CPU. Export the load signal the algorithm actually uses and test skew.

### 20.22.2 Health, draining, and overload

Health is sampled and delayed. A backend usually fails several checks before removal and passes several before readmission to prevent flapping. During this interval clients can receive failures. Active checks also differ from passive observation of real traffic. A probe path can succeed while a tenant-specific query fails, or fail because the checker lacks a dependency available to users.

Connection draining stops assignment of new work and permits existing connections or requests to finish for a bound. Long-lived connections need an explicit maximum or protocol signal; otherwise a deployment can wait indefinitely. Clients may reconnect simultaneously when a backend closes all connections, creating a **reconnection storm**. Staggered draining and jitter reduce it.

At overload, balancing cannot manufacture capacity. **Load shedding** rejects selected work early so admitted work can complete. Priority, tenant quota, request cost, and deadline can guide admission. Queueing every request behind an exhausted backend converts clear rejection into timeouts and retry amplification. The balancer should expose rejected and queued work distinctly from backend errors.

Retries at multiple layers multiply. If a client attempts three times, a proxy three times, and a service SDK three times, one logical operation can cause up to (3^3=27) downstream attempts. Establish one primary retry owner per boundary and propagate attempt count and deadline where protocols allow.

> **Common misconception 20.46 — “Round robin distributes equal load.”**  
> It distributes assignments under its own unit. Variable request cost, persistent connections, retries, and backend capacity can produce highly unequal work.

> **Common misconception 20.47 — “Removing an unhealthy backend ends its traffic immediately.”**  
> Detection, propagation, client caches, existing connections, and in-flight requests create a drain interval whose semantics must be designed.
