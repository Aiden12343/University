# 20.23 Observability as an operational model

Operations require evidence about external behaviour and internal resource state. A service should emit:

- structured events with stable schemas;
- metrics with controlled label cardinality;
- traces with causal context;
- deployment and configuration annotations;
- domain-level correctness indicators.

**Label cardinality** is the number of distinct label combinations in a metric. Using user identifiers or raw URLs as labels can create millions of series and overwhelm a monitoring system. High-cardinality identifiers belong in sampled traces or logs under privacy controls, not unbounded metric labels.

Instrumentation must have bounded overhead. Blocking application requests on telemetry delivery makes monitoring failure become service failure. Buffering without a bound turns it into memory exhaustion. Clients batch, sample, drop under policy, and report dropped telemetry counts.

### 20.23.1 From telemetry to claims

**Monitoring** evaluates known conditions against collected signals. **Observability**, in its systems-theoretic sense, concerns what internal state can be inferred from external outputs; in software practice it denotes the instrumentation and investigative capability supporting that inference. Installing a telemetry backend does not make an uninstrumented or semantically opaque service observable.

The major signals answer different questions:

| Signal | Basic unit | Strong use | Structural limitation |
|:---|:---|:---|:---|
| metric | numeric observations over labelled dimensions | rates, distributions, saturation, alerting | loses per-event detail; cardinality must be bounded |
| log | timestamped event with fields | discrete facts, diagnostics, audit under stronger controls | expensive to search; schemas and completeness vary |
| trace | causally related spans for an operation | cross-service path, phase latency, dependency attribution | sampling can omit rare events; instrumentation changes context |
| profile | samples or measurements of resource use by code location | CPU, allocation, lock, or wall-time hotspots | overhead and symbol/privacy constraints; not business correctness |

A useful event begins from a domain fact—“invoice approval rejected by policy version 12”—rather than a prose debugging sentence. Stable schema, event name, timestamp source, service and instance identity, artifact digest, configuration version, trace context, outcome, duration, and bounded error class make evidence joinable. User and tenant identifiers require minimisation, access policy, and retention; they are not free labels.

### Worked example 20.7 — Emit a bounded structured event

~~~python
from __future__ import annotations

import json
from dataclasses import asdict, dataclass
from datetime import datetime, timezone


@dataclass(frozen=True)
class OperationEvent:
    event: str
    occurred_at: str
    operation_id: str
    outcome: str
    duration_ms: float
    artifact_digest: str


def encode_event(event: OperationEvent) -> str:
    if event.outcome not in {"success", "rejected", "failed"}:
        raise ValueError("unknown outcome")
    if event.duration_ms < 0:
        raise ValueError("negative duration")
    return json.dumps(asdict(event), separators=(",", ":"), sort_keys=True)


example_event = OperationEvent(
    event="report.ingest.completed",
    occurred_at=datetime.now(timezone.utc).isoformat(),
    operation_id="01J-EXAMPLE",
    outcome="success",
    duration_ms=18.4,
    artifact_digest="sha256:example",
)
~~~

The operation identifier supports correlation but should not encode personal or secret data. Real schemas constrain identifier length, use an approved clock source, record schema version, and send through a logger that prevents newline ambiguity and accidental field interpolation. The illustrative digest is not an authentic artifact identity.

### 20.23.2 Metrics, histograms, and cardinality

A **counter** is cumulative and normally non-decreasing except reset; derive event rates over intervals rather than treating one sample as work per second. A **gauge** can rise or fall and represents a sampled state such as queue depth. A **histogram** assigns observations to cumulative or disjoint buckets plus count and sum, enabling aggregation when bucket boundaries match the question.

Metric labels create a Cartesian product. If `route` has 100 values, `status` 6, `region` 8, and `tenant` 100,000, the theoretical series count is 480 million. Even sparse creation can overwhelm ingestion and query. Replace raw path with route template, group errors into bounded classes, and keep tenant detail in controlled event stores or sampled traces when justified.

### 20.23.3 Trace context and sampling

Distributed tracing propagates a trace identifier and parent relationship across process boundaries. Treat incoming context as untrusted syntax: validate it, avoid using it for authorisation, and start a fresh context when policy requires. **Baggage** propagates application-defined values and can leak sensitive data or inflate every request; allowlist small values and do not treat them as authenticated claims.

Head sampling decides near trace start and is operationally cheap but can miss rare failures not yet known. Tail sampling decides after observing more spans and can retain errors or high latency, at the cost of buffering and a more complex collector. Sampling probabilities must be recorded or otherwise accounted for before estimating rates. Audit events and billing facts should not depend on probabilistic trace sampling.

The telemetry pipeline needs its own health: accepted, dropped, retried, queued, sampled, transformed, and exported counts; configuration version; backpressure; and storage delay. Alerting on absent application events without checking exporter failure confuses service silence with instrumentation blindness.

> **Common misconception 20.48 — “If it is logged, it is observable.”**  
> The event may be dropped, delayed, unschematized, uncorrelated, inaccessible, or incapable of distinguishing the hypotheses under investigation.

> **Common misconception 20.49 — “High-cardinality labels merely cost more storage.”**  
> They also increase ingestion memory, index work, query latency, alert evaluation cost, and failure risk in the monitoring system itself.
