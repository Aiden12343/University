# 20.24 Service-level indicators and objectives

A **service-level indicator**, or SLI, is a quantitative measure of service behaviour relevant to users. A **service-level objective**, or SLO, is a target range or proportion for an SLI over a period. A **service-level agreement**, or SLA, is a formal agreement that may include consequences; it is not a synonym for an internal objective.

Availability SLI:

\[
\text{availability}
=
\frac{\text{good eligible events}}
{\text{total eligible events}}.
\]

Every word requires definition. Does a client cancellation count? Is a 500 followed by successful retry good? Are planned maintenance events eligible? Does a response under 200 ms count as good while a slower successful response counts bad? The SLI specification is an executable classification rule.

An SLO of 99.9% good events over 30 days permits an **error budget** of 0.1% bad eligible events. Error budgets coordinate reliability and change: rapid consumption can pause risky rollout and prioritise stabilisation. They are not permission to cause avoidable failures.

### Worked example 20.8 — Compute an event-based SLI

~~~python
from dataclasses import dataclass


@dataclass(frozen=True)
class RequestEvent:
    status_code: int
    latency_ms: float
    eligible: bool = True


def availability_sli(
    events: list[RequestEvent],
) -> float:
    eligible = [event for event in events if event.eligible]
    if not eligible:
        raise ValueError("SLI undefined without eligible events")

    good = sum(
        1
        for event in eligible
        if event.status_code < 500
        and event.latency_ms <= 250.0
    )
    return good / len(eligible)
~~~

The code makes one policy explicit: all statuses below 500 and latency no more than 250 ms are good. That classifies 429 and 404 as good, which may or may not match responsibility and user experience. The exercise is to expose the policy, then refine it—not to adopt the example universally.

### 20.24.1 The SLI specification

An SLI requires more than a formula. A complete specification records:

- the user journey or service capability represented;
- event source and measurement point;
- eligible-population rule;
- good-event classifier or numeric statistic;
- window and aggregation;
- late, duplicate, missing, retried, and cancelled event treatment;
- segmentation needed to expose unequal experience;
- data quality, delay, ownership, and revision process.

Server-side request logs can report success even when a response never reaches the client. Client-side measurement better represents experience but can be sampled, blocked, delayed, or absent during total outage. Synthetic probes cover a controlled path continuously but do not reproduce every user. Mature SLI design triangulates sources and states precisely which failure classes each misses.

Time-based availability samples whether a service is good at intervals; event-based availability classifies operations. The former weights quiet and busy periods similarly, while the latter weights busy periods more. Neither is universally superior. A service that must always accept emergency calls may need time-based and event-based objectives plus a maximum continuous outage constraint.

### 20.24.2 Error-budget arithmetic and burn rate

For target (S), the budget fraction is (B=1-S). If an observed interval has bad-event fraction (b), its **burn rate** is

\[
R=\frac{b}{B}.
\]

At burn rate 1, failures consume budget exactly at the rate allowed over a comparable window. At rate 10, sustained behaviour consumes it ten times too fast. For a 99.9% target, (B=0.001); a 1% bad fraction gives (R=10).

~~~python
from math import isclose


def burn_rate(*, bad: int, total: int, objective: float) -> float:
    if bad < 0 or total <= 0 or bad > total:
        raise ValueError("invalid event counts")
    if not 0.0 < objective < 1.0:
        raise ValueError("objective must lie strictly between zero and one")
    return (bad / total) / (1.0 - objective)


assert isclose(
    burn_rate(bad=100, total=10_000, objective=0.999),
    10.0,
)
~~~

Floating-point representation makes exact equality brittle, so the assertion uses an approximate comparison. More importantly, the function assumes counts refer to the same eligible population and interval.

Multi-window, multi-burn-rate alerts combine a short window for rapid severe failure with a longer window confirming material budget consumption. This reduces paging on brief noise while detecting sustained harm. Ticket-level alerts can use slower burn. Alert thresholds should be derived from budget and response capacity, then tested against historical incidents and synthetic data.

### 20.24.3 Objectives as policy

An SLO should reflect user need and the cost of reliability, not the best number the system recently achieved. Setting the target at 100% leaves no budget for necessary change and is rarely a truthful engineering commitment. Setting it below ordinary performance does not automatically create useful risk capacity if users expect better.

Dependencies can have their own SLOs, but multiplying advertised percentages assumes independence and identical eligibility that rarely hold. Measure the composed user journey. Segment by region, tenant class, operation, or accessibility need where aggregate success can conceal a harmed population, while keeping metric cardinality controlled.

An SLA is contractual and may define credits, exclusions, reporting, and legal responsibilities differently from the engineering SLI. An internal SLO is often stricter, providing reaction room before an SLA breach. Do not infer one from the other without reading the precise populations and periods.

> **Common misconception 20.50 — “99.9% availability means 43.2 minutes of permitted monthly downtime.”**  
> That conversion assumes a time-based thirty-day denominator and binary full outage. Event-based, partial, segmented, and rolling-window definitions yield different budgets.

> **Common misconception 20.51 — “Remaining error budget should always be spent.”**  
> It is a risk-control signal, not a quota for deliberate harm. Change decisions still consider consequence, uncertainty, safety, security, and future demand.
