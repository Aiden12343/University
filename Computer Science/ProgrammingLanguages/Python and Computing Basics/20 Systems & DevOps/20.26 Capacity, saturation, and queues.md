# 20.26 Capacity, saturation, and queues

**Capacity** is the sustainable workload a system can serve under defined performance and reliability constraints. **Saturation** occurs when a constrained resource approaches or reaches its usable limit. CPU, memory, disk throughput, network, database connections, locks, worker threads, and queue depth can each saturate.

Little’s Law for a stable system relates long-run average number in system \(L\), arrival rate \(\lambda\), and average time \(W\):

\[
L=\lambda W.
\]

If 100 requests arrive per second and average time in system is 0.2 seconds, the average concurrent population is 20 under the law’s conditions. The law does not prescribe a worker count and does not guarantee stability. As utilisation approaches one for a bottleneck, queueing delay can rise sharply.

Unbounded queues hide overload temporarily while latency and memory grow. A bounded queue forces a policy: reject, shed low-priority work, apply backpressure, or spill durably. “No errors” during an overload is meaningless if responses arrive after they are useful.

Capacity planning combines representative load tests, production measurements, demand forecasts, headroom, failure scenarios, scaling delay, quotas, and cost. Benchmarks must include dependency limits and realistic data distribution.

### 20.26.1 Units, bottlenecks, and utilisation

Workload is multidimensional: requests per second, bytes, records, concurrent sessions, fan-out, write ratio, cache hit rate, and per-request computational complexity. “The service handles 10,000 requests per second” is meaningless without request mix, latency objective, data state, failure mode, and hardware or allocation.

For resource (j), a simple utilisation estimate is

\[
U_j=\lambda D_j,
\]

where (lambda) is completed operations per unit time and (D_j) is average demand on the resource per operation, expressed in compatible units. The bottleneck is the resource whose usable capacity is reached first, but bottlenecks move after optimisation. CPU relief can expose database lock or network limits.

For the idealised M/M/1 queue—Poisson arrivals, exponential service, one server, infinite buffer, first-come service—the mean time in system is

\[
W=\frac{1}{\mu-\lambda},\qquad \lambda<\mu,
\]

where (mu) is service rate. If (mu=100) per second, increasing (lambda) from 50 to 90 raises predicted (W) from 20 ms to 100 ms; at 99 it becomes one second. Real services violate these assumptions, yet the model correctly warns that queueing grows nonlinearly near saturation.

~~~python
def mm1_mean_time(*, arrival_rate: float, service_rate: float) -> float:
    if arrival_rate < 0 or service_rate <= 0:
        raise ValueError("rates must be non-negative and service positive")
    if arrival_rate >= service_rate:
        raise ValueError("no finite steady-state mean under this model")
    return 1.0 / (service_rate - arrival_rate)


assert mm1_mean_time(arrival_rate=90.0, service_rate=100.0) == 0.1
~~~

This is an explanatory model, not a capacity calculator. Bursty arrivals, several workers, service-time variance, priorities, finite queues, timeouts, abandonment, batching, and feedback change the distribution.

### 20.26.2 Load-test design

A valid load test states a hypothesis: for example, “under 800 representative operations per second with one zone unavailable, at least 99% of eligible writes complete within 400 ms for 30 minutes without queue growth”. It then specifies data volume and skew, cache warmth, arrival process, connection model, think time, dependency behaviour, resource limits, telemetry, ramp, steady duration, and stop conditions.

Test the saturation knee rather than only one expected point. Observe throughput, latency distribution, errors, queues, retries, CPU throttling, memory, garbage collection, database waits, and downstream quotas. A plateau in throughput with growing latency indicates queueing; rising throughput with rising error can indicate overload rejection or dependency exhaustion.

Production capacity includes failure headroom. If a region must survive loss of one of three zones without violating SLO, ordinary load cannot consume all three zones' capacity. Reserve room for failover, deployment surge, traffic forecast error, and autoscaling delay. Headroom is an explicit reliability cost, not “waste” removable by average utilisation optimisation.

### 20.26.3 Backpressure and admission

**Backpressure** propagates inability to accept work towards producers so queues remain bounded. In synchronous protocols this can be rejection or reduced advertised window; in streams it can pause demand; in queues it can be quota or producer delay. If producers cannot slow, shed according to priority and preserve evidence about rejected work.

Admission should occur before expensive parsing, authentication backends, fan-out, or allocation where possible, while retaining enough identity to apply fair quotas. Per-tenant limits prevent one customer consuming all capacity; global limits preserve the service as a whole. Reserved emergency capacity must be protected from normal spillover if it is to exist during an incident.

> **Common misconception 20.54 — “Fifty per cent average CPU means fifty per cent spare capacity.”**  
> Peaks, per-core imbalance, throttling, non-CPU bottlenecks, failure headroom, and latency objectives determine usable capacity.

> **Common misconception 20.55 — “A longer queue increases resilience.”**  
> It can absorb a bounded burst, but during sustained overload it hides failure while increasing latency, memory, stale work, and recovery time.
