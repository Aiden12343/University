# 20.27 Autoscaling

**Autoscaling** changes allocated capacity based on observed signals. CPU-based scaling works when CPU tracks load and new instances arrive before queues become harmful. It fails for I/O-bound services, long startup, or metrics delayed by the scaling system.

Queue-depth scaling estimates workers required to drain work within a target. Predictive scaling uses anticipated schedules. Minimum capacity handles sudden load while new instances start. Maximum capacity limits cost and protects dependencies.

Scaling one tier can overload another. Adding application workers increases database connections and request rate. A global capacity model must account for downstream bottlenecks and provider quotas.

Scale-down risks terminating useful work. Draining, job leases, checkpointing, and termination grace periods define safe removal. Flapping between sizes wastes resources; cooldown and hysteresis stabilise control.

### 20.27.1 Autoscaling as feedback control

An autoscaler samples a signal, computes desired capacity, changes resources, and waits for the system to respond. Sampling interval, metric delay, startup time, readiness, cooldown, and workload dynamics create a feedback loop. An aggressive controller acting on delayed measurements can overshoot and oscillate.

For a utilisation target (u_t), a proportional horizontal policy often resembles

\[
n_{desired}=\left\lceil n_{current}\frac{u_{observed}}{u_t}\right\rceil.
\]

If four replicas observe 90% utilisation against a 60% target, the raw recommendation is six. Missing metrics, not-ready replicas, stabilisation windows, minimum/maximum bounds, and scaling policies modify the real decision. The formula assumes utilisation falls roughly inversely with replicas, which fails for serial bottlenecks and sticky load.

Scale on a signal causally close to demand and available before harm. CPU is useful when per-request CPU is stable. Queue age can be more meaningful than depth when job costs vary. Concurrency can guide event-driven services. A business metric arriving minutes late may be valuable for prediction but unsafe as the only reactive signal.

### 20.27.2 Horizontal, vertical, and infrastructure scaling

Horizontal scaling changes replica count. Vertical scaling changes resource requests or limits for existing or replaced replicas. Cluster scaling changes underlying nodes. Each loop has different delay and can interact: an application scaler creates pending Pods; a cluster scaler adds nodes; a vertical recommender changes requests and alters placement. Bound responsibilities and observe the combined control system.

Vertical changes may require restart and can reduce replica density. Memory cannot always be compressed safely, so a vertical recommendation based on recent use needs peak and failure reasoning. Serverless scale-to-zero reduces idle cost but introduces cold-start latency and a dependency on the platform's admission queue. Retain minimum warm capacity when the SLO cannot tolerate startup.

Predictive scaling uses schedules or forecasts to allocate before demand. It helps for periodic known events and fails under novelty. Combine prediction with reactive bounds, validate forecast error, and include provider quotas: a desired count above account or subnet capacity is not capacity.

### 20.27.3 Safe scale-down

Scale-down should select instances with the least disruption, mark them unavailable, drain connections, stop new job claims, release leases, and terminate after a bound. Local caches and recently warmed replicas create hysteresis: removing them too quickly can lower hit rate and increase backend load, causing scale-up again.

For queue workers, desired replicas should consider arrival rate, service rate distribution, backlog age, and target drain time. A huge old backlog may justify temporary scale, but if the database is saturated, adding workers lengthens transactions and reduces throughput. Place a dependency-aware maximum and shed or defer low-priority work.

> **Common misconception 20.56 — “Autoscaling follows traffic.”**  
> It follows a delayed measured proxy through a controller and resource startup path. The proxy can diverge from demand and the response can arrive too late.

> **Common misconception 20.57 — “Scaling out always increases capacity.”**  
> Shared locks, databases, quotas, cache churn, network, and coordination can make additional replicas neutral or harmful.
