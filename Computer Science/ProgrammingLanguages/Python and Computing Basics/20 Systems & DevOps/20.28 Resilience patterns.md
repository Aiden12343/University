# 20.28 Resilience patterns

A **timeout** prevents indefinite waiting. Configure connection, read, write, pool-acquisition, and total deadlines where libraries distinguish them. One large undifferentiated timeout obscures the failed phase.

A **retry** repeats an operation after selected transient failure. Use:

- idempotent semantics or operation identifiers;
- bounded attempts;
- exponential backoff;
- random jitter;
- a total deadline;
- server retry guidance;
- a retry budget.

A **circuit breaker** rejects calls temporarily after failures cross a threshold, allowing recovery and preserving caller resources. Half-open probes test whether service has recovered. Distributed clients each maintain partial observations, so breakers can oscillate.

A **bulkhead** gives workloads separate resource pools so one cannot consume all capacity. A **fallback** returns degraded behaviour, but stale or default data must be safe and visibly classified. Serving an incorrect bank balance is not an acceptable fallback for availability.

### 20.28.1 Begin with a failure model

**Resilience** is preservation or timely restoration of specified service properties under specified disturbances. It is not the absence of failure. Name faults: process crash, zone loss, delayed packets, corrupted response, stale discovery, expired credential, throttling, dependency slowdown, operator error, or regional control-plane loss. Then state which property and load must survive.

A deadline is an absolute or propagated latest useful completion time. If a caller has 800 ms remaining and allocates 700 ms to one dependency, downstream processing and network return cannot fit. Divide budget among attempts and phases, and cancel work after the result is no longer useful. Cancellation is cooperative: the server may continue an external effect, so it does not replace idempotency.

Nested retries amplify load precisely when capacity is scarce. A **retry budget** limits retries as a fraction or token pool relative to original requests. Once exhausted, fail promptly so the dependency can recover. Retry only operations whose semantic duplication is safe and errors likely transient; use server-provided delay where trustworthy and still cap it by the caller deadline.

### Worked example 20.9 — A local retry-budget gate

~~~python
from dataclasses import dataclass


@dataclass
class RetryBudget:
    maximum_tokens: int
    tokens: int

    def record_original_success(self) -> None:
        self.tokens = min(self.maximum_tokens, self.tokens + 1)

    def admit_retry(self) -> bool:
        if self.tokens <= 0:
            return False
        self.tokens -= 1
        return True
~~~

The example shows the mechanism but not a universal replenishment policy. A process-local budget is not a fleet-wide bound, disappears on restart, and can unfairly mix tenants. Production policy defines scope, initial tokens, replenishment, metrics, and how it combines with rate limiting and deadlines.

### 20.28.2 Circuit breakers, bulkheads, and shedding

A circuit breaker is a state machine. Closed permits calls and observes selected failures; open rejects for a bounded interval; half-open admits controlled probes. Thresholds based on tiny samples flap, while long windows react slowly. Count timeouts and resource failures according to whether another attempt would add harm. Expose state and rejected calls, and provide a safe operator override with expiry.

Bulkheads partition capacity by workload, dependency, tenant, or priority. Separate thread or connection pools prevent one slow dependency consuming every caller worker. The partition size is policy: rigid equal pools waste capacity under skew, while unlimited borrowing destroys isolation. A controlled shared reserve can balance efficiency and protection.

Load shedding should reject before work becomes expensive and return a signal clients will not retry blindly. Preserve high-priority control and recovery paths. Administrative status endpoints that share the exhausted request pool cannot help during overload; dedicate bounded capacity while authenticating it strongly.

### 20.28.3 Redundancy and graceful degradation

Redundancy improves availability only when replicas do not share the relevant failure and the system can select a correct survivor. Two databases replicating corrupted writes are redundant against disk failure, not logical corruption. Multi-region systems add network partitions, replication lag, data sovereignty, consistency decisions, duplicate processing, and failback complexity.

Graceful degradation removes optional work while preserving explicit semantics: omit recommendations, serve a labelled stale catalogue, reduce image quality, or queue non-urgent exports. It must not silently weaken authorisation, integrity, or financial correctness. Test degraded mode continuously enough that its dormant dependencies do not rot.

Hedging sends a duplicate after a delay and uses the first acceptable response. It can reduce tail latency for idempotent reads when slow requests are independent, but increases load and may correlate at the same bottleneck. Cap hedge rate, choose diverse endpoints where appropriate, cancel losers, and measure extra work.

> **Common misconception 20.58 — “Retries increase availability.”**  
> They can mask independent transient faults; under overload or persistent failure they increase demand and delay recovery.

> **Common misconception 20.59 — “Redundancy means duplication.”**  
> Useful redundancy requires independence, correct failure detection, sufficient survivor capacity, state semantics, and a tested selection or failover mechanism.

> **Common misconception 20.60 — “Degraded mode may relax controls because it is temporary.”**  
> Incidents are when attackers and mistakes exploit ambiguity. Degradation may reduce features or freshness, not silently abandon essential security or integrity invariants.
