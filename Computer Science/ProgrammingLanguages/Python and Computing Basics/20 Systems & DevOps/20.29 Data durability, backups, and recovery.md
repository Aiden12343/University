# 20.29 Data durability, backups, and recovery

A **backup** is a recoverable copy of data and the information required to interpret it. Replication is not backup: deletion, corruption, or ransomware can replicate. Snapshots can be crash-consistent without being application-consistent across systems.

The **recovery point objective**, or RPO, is the maximum targeted period of data loss measured backward from disruption. The **recovery time objective**, or RTO, is the targeted time to restore service. These are business objectives, not guarantees supplied merely by selecting a backup interval.

A recovery plan includes:

- data and metadata;
- schema and application versions;
- encryption keys;
- identity configuration;
- infrastructure definitions;
- dependency artifacts;
- restoration ordering;
- integrity verification;
- failover/failback;
- regular restoration exercises.

Backups must be isolated from ordinary administrative credentials, encrypted, retained under policy, and tested. A successful backup job proves data were written somewhere; only restoration and validation establish recoverability.

### Worked example 20.10 — Verify a backup artifact

~~~python
from dataclasses import dataclass
from hashlib import sha256
from pathlib import Path


@dataclass(frozen=True)
class BackupManifest:
    path: Path
    size: int
    sha256_hex: str


def manifest(path: Path) -> BackupManifest:
    digest = sha256()
    size = 0

    with path.open("rb") as stream:
        while chunk := stream.read(1024 * 1024):
            size += len(chunk)
            digest.update(chunk)

    return BackupManifest(
        path=path,
        size=size,
        sha256_hex=digest.hexdigest(),
    )
~~~

The manifest detects later byte differences if itself is trusted. It does not prove the backup contains a transactionally valid database, can be decrypted, matches the intended time, or can be restored within RTO. A restoration test must exercise those properties.

### 20.29.1 Copies, logs, and consistency points

A full backup captures the selected dataset at a consistency point. An incremental backup captures changes since a prior backup; a differential captures changes since a full base. A storage snapshot records blocks or objects under provider semantics. A transaction log or write-ahead log can support point-in-time recovery when combined with a valid base and an unbroken log sequence.

Crash consistency approximates state after abrupt machine loss: individual storage structures may recover through logs, but relationships across databases, object stores, and queues may not align. Application consistency coordinates or records a recoverable boundary across components. For a report system, database metadata pointing to an object not yet backed up can make both individually valid copies jointly unusable.

The backup **dependency closure** includes:

- data and schemas;
- encryption and wrapping keys, certificates, and trust roots;
- identity and access policy;
- application and migration artifacts;
- infrastructure and network definitions;
- provider account, region, quotas, and DNS authority;
- instructions and human authority to perform restoration.

A perfectly preserved encrypted backup without recoverable keys is durable ciphertext, not recoverable service state. Conversely, storing data and keys under the same routinely compromised administrator defeats isolation.

### 20.29.2 RPO, RTO, and recovery sequencing

If snapshots occur every 24 hours, that schedule alone does not guarantee a 24-hour RPO: failed jobs, replication delay, corruption detection time, and restore-point validation matter. Continuous logs can lower RPO but add chain dependencies. Measure the newest verified recoverable point, not the newest file timestamp.

RTO includes declaration, access, infrastructure allocation, artifact retrieval, key recovery, data transfer, restore, replay, validation, traffic switch, and operational stabilisation. A laboratory restore of a small sample measures only a subset. Test representative size and constrained bandwidth.

Recovery priorities follow business dependencies. Identity, DNS, key management, and control-plane services may precede applications, while their own recovery can depend on the application platform. Identify and break cycles through independent emergency access, offline material, or separate recovery infrastructure.

### 20.29.3 Immutability, deletion, and exercises

Use separate credentials and, where supported, write-once retention or delayed deletion to resist ransomware and administrator error. Immutability creates obligations: personal data deletion, legal holds, vulnerable secrets, and storage cost require a designed retention schedule. A retention lock applied incorrectly can make prohibited data undeletable.

A restoration exercise starts in an isolated clean environment. Verify manifest and provenance, recover keys through the documented path, restore in order, replay to the selected point, run structural and domain invariants, scan for compromised persistence if the source incident involved intrusion, reconcile external systems, and measure actual RPO/RTO. Do not connect restored writers to production until split-brain and duplicate-effect controls are established.

Failback is another migration. Writes accepted in the recovery site must be reconciled before returning. DNS, clients, queues, caches, and long-lived connections can continue using the recovery path. A plan that ends at “traffic restored” omits the riskiest transition back to sustainable normal operation.

> **Common misconception 20.61 — “Point-in-time recovery can restore any desired instant.”**  
> It is bounded by valid base backups, complete compatible logs, retention, clock and transaction semantics, keys, and tested tooling.

> **Common misconception 20.62 — “Immutable backups solve ransomware.”**  
> They protect selected copies from modification under defined authority. Attackers may corrupt data before capture, steal keys, destroy other dependencies, or remain present after restoration.
