# 20.3 Exit status and supervision

A process **exit status** is a small integer communicated to its parent. By convention, zero means success and nonzero means failure, but meanings beyond that are program-defined. A supervisor can distinguish:

- clean requested termination;
- configuration error that restart cannot fix;
- temporary dependency failure;
- unexpected software failure;
- external resource exhaustion.

Restarting every failure indefinitely creates a crash loop, consumes resources, and hides persistent misconfiguration. Supervisors use backoff, restart limits, and operator-visible state.

Python command:

~~~python
from __future__ import annotations

import argparse
import sys


def main(argv: list[str] | None = None) -> int:
    parser = argparse.ArgumentParser()
    parser.add_argument("--check-config", action="store_true")
    options = parser.parse_args(argv)

    try:
        configuration = load_configuration()
        validate_configuration(configuration)
    except ConfigurationError as error:
        print(f"configuration error: {error}", file=sys.stderr)
        return 2

    if options.check_config:
        return 0

    return run_service(configuration)


if __name__ == "__main__":
    raise SystemExit(main())
~~~

The entry function returns status rather than terminating from deep code. A configuration-check mode enables deployment systems to reject invalid configuration before replacing a healthy instance. Standard error carries human diagnostics; structured operational logging can begin after configuration is valid.

### 20.3.1 Failure classification and restart control

Exit status is a narrow channel, so diagnostics belong in bounded structured events and retained crash evidence. Status values should be stable enough for automation but not so numerous that the supervisor embeds application business logic. A useful distinction is whether immediate restart can plausibly change the outcome:

- a transient network interruption may justify delayed retry;
- an invalid configuration will ordinarily repeat until configuration changes;
- a corrupted local state store may require quarantine and operator action;
- an invariant failure should preserve evidence and prevent an endless high-rate loop.

If attempt (k) waits (b2^k) seconds, capped at (m), identical replicas that fail together will still restart together. **Jitter** randomises the wait to reduce synchronised load. One full-jitter policy samples

\[
d_k \sim U\!\left(0,\min(m,b2^k)\right),
\]

where (U(0,x)) is a uniform distribution from zero to (x). A restart policy also needs a maximum attempt rate or start-limit interval. Backoff prevents a tight loop; it does not repair the cause or establish that repeated work is safe.

Supervision should distinguish process failure from service failure. A process can be alive while returning incorrect answers. Conversely, a process can exit intentionally after completing a finite job. The supervisor observes lifecycle; service-level monitoring observes outcomes. Treating one as the other produces false recovery and misleading availability.

### 20.3.2 Watchdogs and stuck processes

A **watchdog** expects periodic evidence that a process or subsystem remains able to make progress. A heartbeat generated by a dedicated thread can continue while the main request loop is deadlocked; therefore the heartbeat must exercise the property it claims. A useful watchdog might require the event loop to schedule work, a queue consumer to advance an offset, or a controller to complete a bounded reconciliation.

External watchdogs can act when in-process logic is unable to. Their action must be conservative: terminating a process holding an external lease, mid-migration, or writing non-transactional state can intensify damage. Record last progress, blocked phase, and relevant identifiers before restart where possible, and cap retained crash data to avoid converting repeated failure into storage exhaustion.

> **Common misconception 20.5 — “Nonzero exit status tells the supervisor what went wrong.”**  
> It indicates a program-defined failure class at most. Root cause requires versioned configuration, logs, traces, resource state, crash evidence, and the conditions preceding exit.

> **Common misconception 20.6 — “Exponential backoff guarantees recovery.”**  
> Backoff spaces attempts and jitter decorrelates clients. Neither supplies capacity, fixes permanent faults, makes a side effect idempotent, nor defines when attempts must stop.
