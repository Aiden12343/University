# 20.33 Runbooks and automation

A **runbook** is an executable or human procedure for a recurring operational condition. It includes prerequisites, authority, commands or actions, expected evidence, branches, stop conditions, rollback, and escalation.

Good automation makes safe state transitions repeatable. It supports dry-run or plan modes, uses explicit targets, validates preconditions, logs changes, limits concurrency, and is idempotent where possible.

Dangerous pattern:

~~~python
for resource in list_everything():
    delete(resource)
~~~

Safer design separates discovery, immutable plan, approval, and execution:

~~~python
from dataclasses import dataclass


@dataclass(frozen=True)
class DeletionCandidate:
    resource_id: str
    reason: str
    observed_version: str


def execute_candidate(
    client,
    candidate: DeletionCandidate,
) -> None:
    client.delete_if_version(
        resource_id=candidate.resource_id,
        expected_version=candidate.observed_version,
    )
~~~

The executor receives a resolved identity and observed version. A conditional delete rejects state changed after planning. The missing pieces—scope generation, retention rule, approval, audit, and recovery—remain explicit instead of being buried inside a broad loop.

### 20.33.1 Runbook structure and human factors

A runbook begins with trigger and scope, not commands. It states the symptom or request for which it is valid, prerequisites, required authority, affected systems, estimated duration, risk, and conditions that prohibit use. Every destructive or high-blast-radius action names an exact target-selection method and a verification step.

Structure actions as small numbered transitions with expected output and branches. Screenshots decay and conceal text; include copyable commands with placeholders clearly distinguished from literals. Commands should display resolved targets before mutation and use non-interactive flags only when their consequences are understood. Avoid shell globs, ambient current account, implicit region, and “delete all matching” in emergency procedures.

Human readers under stress skip dense prose. Put stop conditions beside the dangerous step, not in an appendix. State whether a command is safe to repeat, how long it may run, what partial completion looks like, and how to cancel. Use independent confirmation for actions whose erroneous scope is catastrophic.

### 20.33.2 From runbook to automation

Automate when the procedure is frequent, time-critical, error-prone, or requires consistent evidence. Preserve the runbook's safeguards in the program:

- typed required inputs and explicit environment;
- read-only discovery followed by an immutable plan;
- current-version or generation preconditions;
- scope and count limits;
- least-privilege identity;
- bounded concurrency, deadlines, and rate limits;
- idempotency and resumable checkpoints;
- structured audit and a summary of actual effects;
- dry-run semantics that execute the same discovery and validation path;
- recovery or compensating operation.

A dry run that skips authentication, provider reads, template expansion, or target selection gives false confidence. It should stop immediately before mutation while producing the exact plan subject to approval. If state can change before execution, apply must recheck preconditions.

Automation has a **kill switch** only if operators can invoke it through an independent available path and the stopped state is safe. Terminating a migration halfway can violate invariants; pause at checkpoints rather than arbitrary instruction boundaries. Test the switch and access route.

### 20.33.3 Ownership and decay

Every runbook has an owner, last verified date, supported versions, and test cadence. Link it from the alert or service catalogue so responders do not search during crisis. Executing it in a game day tests both instructions and permissions. Record deviations: repeated manual improvisation indicates the model is incomplete.

Generated documentation can preserve flag and schema accuracy, while human rationale explains choice and risk. Treat runbooks as versioned code with review, but do not assume repository review alone proves operational usability. New responders should be able to follow them in an isolated environment without oral folklore.

> **Common misconception 20.70 — “A runbook is accurate because an expert wrote it.”**  
> Platforms, permissions, interfaces, and failure modes change. Accuracy requires versioning, execution tests, ownership, and feedback from actual use.

> **Common misconception 20.71 — “Automation is the runbook with commands joined together.”**  
> Safe automation must encode targets, preconditions, concurrency, retries, evidence, partial failure, approval, and recovery that a human previously supplied implicitly.
