# 20.34 Testing infrastructure and deployments

Infrastructure tests include:

- static schema and policy validation;
- unit tests of modules and templates;
- plan assertions;
- deployment into an isolated ephemeral environment;
- connectivity and authorisation tests;
- artifact provenance and signature verification;
- failure injection;
- backup restoration;
- load tests under actual limits;
- rollback rehearsal.

A **smoke test** checks a small set of critical behaviours after deployment. It should use dedicated test data and avoid irreversible production side effects. A synthetic transaction can exercise a path continuously, but monitoring accounts must not receive broad exemptions that make their success unrepresentative.

**Chaos engineering** performs controlled experiments on failure hypotheses, such as loss of one instance or added network latency. It requires steady-state measures, limited blast radius, abort conditions, and informed ownership. Randomly killing production resources without a hypothesis is vandalism, not engineering.

### 20.34.1 Layered infrastructure assurance

Static validation catches syntax, schema, forbidden policy, dependency cycles, and some unsafe defaults without provisioning. Unit tests exercise module transformations and policy functions. Plan tests inspect proposed resources and changes. Integration tests provision real or faithful sandbox resources and verify provider behaviour. Production verification observes the actual deployed system. Each layer covers different failures; none subsumes the rest.

Test the module interface, not only one example. Vary optional inputs, region, account, naming, empty collections, maximum sizes, upgrade from supported versions, import, and destroy. Destruction deserves explicit testing in an isolated environment because dependency and retention rules differ from creation. Confirm that protected state and backups survive intended teardown.

Ephemeral environments improve isolation but can differ from production in data scale, quotas, identity hierarchy, network, and managed-service tier. Record those differences. A shared long-lived staging environment better exposes coexistence and integration but accumulates drift and test interference. A mature strategy uses both under defined purposes.

### 20.34.2 Policy, connectivity, and recovery tests

Policy tests include positive and negative cases from representative principals. Verify that deployment can update only the intended service, application can access only its own data, backup can write but not erase retention, and an unrelated workload cannot reach private endpoints. A configuration object showing a deny rule is weaker evidence than an attempted forbidden operation from the relevant identity.

Connectivity tests should originate from actual network positions and exercise DNS, routes, security rules, TLS identity, proxy, and application authentication. A control-plane query saying a rule exists does not prove packets traverse the intended path. Retain test identities without granting broad monitoring exemptions.

Recovery tests restore infrastructure and data from declared artifacts into a clean account or project, then validate domain invariants and RPO/RTO. Test loss of the normal control plane and primary administrator. A recovery plan depending on the failed region's secrets service or unavailable single sign-on contains a circular dependency.

### 20.34.3 Failure experiments and game days

A chaos experiment states a steady-state hypothesis, injected disturbance, scope, duration, abort threshold, observation, and expected recovery. Begin in a low-consequence environment, then increase realism only when evidence and organisational authority justify it. Inject one discriminating condition at a time before combining failures.

Useful experiments include process termination, node drain, zone unreachability, DNS delay, expired credential, dependency throttling, full queue, clock skew, telemetry loss, and corrupted configuration rejected before rollout. Do not inject unrecoverable data corruption into production merely to appear realistic; use a laboratory copy and test restore.

A **game day** exercises people, procedures, communications, access, and technology under a scenario. It can reveal that the backup works but no responder can assume the recovery role, or that the failover succeeds while status communication fails. Capture observations without punishing participants for exposing weaknesses; concealment is the enemy of resilience.

Production tests need a blast-radius budget, named commander, live monitoring, stop mechanism, customer and regulatory consideration, and cleanup verification. Experiments are successful when they produce trustworthy evidence, including evidence that the hypothesis was false—not only when the system survives.

> **Common misconception 20.72 — “Chaos engineering proves a system is resilient.”**  
> One bounded experiment supplies evidence about one disturbance, version, load, and observation window. Resilience remains a scoped, continuously revised claim.
