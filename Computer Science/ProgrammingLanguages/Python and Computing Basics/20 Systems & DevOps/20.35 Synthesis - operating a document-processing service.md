# 20.35 Synthesis: operating a document-processing service

Consider the secure document-ingestion service from §19.32 as an operational system. Users upload documents; an API stores immutable input objects and a metadata record; a queue delivers work to isolated parser workers; outputs enter quarantine; a policy service approves promotion; authorised readers obtain results. The system spans synchronous requests, asynchronous jobs, object storage, a database, secrets, artifacts, identities, networks, and human response.

### 20.35.1 Service objectives and boundaries

Begin with three user journeys:

1. an authorised upload is durably accepted and receives an operation identifier;
2. processing completes or reaches a visible terminal failure within a target time;
3. an authorised reader retrieves only a promoted result belonging to the correct tenant.

Define separate SLIs. Upload availability counts eligible accepted requests whose database record and input object satisfy the durable acceptance invariant. Processing timeliness measures operation creation to terminal state, including queue time. Retrieval correctness cannot be reduced to HTTP status; synthetic and audit checks validate tenant and promotion policy, while security tests seek cross-tenant denial.

The control plane includes deployment, worker policy, parser allowlists, key and secret lifecycle, queue configuration, quarantine promotion, and incident overrides. The data plane includes upload, processing, and retrieval. No document field may select a control-plane image, network destination, secret path, or policy version.

### 20.35.2 Artifacts, infrastructure, and identity

Build the API and worker as separate immutable artifacts because their privileges differ. Each release binds source revision, locked dependencies, platform manifest, SBOM, provenance, tests, and signature to a digest. The parser worker uses a stronger sandbox runtime, no general egress, read-only root, bounded temporary storage, CPU, memory, process and wall-time limits. The API has database and object-write authority but cannot promote output. The promotion service can mark a verified output visible but cannot parse arbitrary documents.

IaC separates production state into network/identity foundation, durable data, and replaceable compute so a routine service update cannot destroy storage. State backends use independent restricted identity and retention. Plans reject public object access, wildcard IAM, unapproved images, deletion of protected stores, unknown security scope, and loss of multi-zone placement.

Workload federation supplies short-lived credentials. Queue messages carry document and operation identifiers, not storage secrets. Workers receive a one-time scoped capability for one input and one output, expire it after the job window, and cannot list tenant buckets. CI validation of untrusted pull requests has no registry write or cloud authority; protected release exchanges its workflow identity for signing and publication scopes.

### 20.35.3 Delivery and state evolution

The deployment record fixes API digest, worker digest, configuration snapshot, database schema interval, message version, and policy bundle. A release first reaches a synthetic environment with representative hostile files, then an internal canary tenant, then a small random production population. Guardrails include upload error and latency, queue age, parser resource terminations, quarantine rejection rate, cross-tenant policy tests, object-store errors, and cost per completed document.

Schema evolution follows expand–migrate–contract. If a new worker emits result envelope version 2, readers learn both versions before producers emit version 2. Backfill is idempotent, checkpointed, and rate-limited below storage and database headroom. Old consumers remain until queue and dead-letter evidence proves no version-1-only work remains. Contract occurs in a later release.

Rollback is tested after new-format records exist. If the old API cannot read them, rollback is prohibited and the plan selects flag disablement or forward repair. External notifications use operation identifiers and a transactional outbox so retry cannot send duplicate completion notices.

### 20.35.4 Capacity and resilience

Capacity modelling separates upload bytes per second, documents per second, parser CPU-seconds, peak memory by file type, temporary expansion, object requests, queue age, and database writes. Admission limits compressed and expanded size before scarce parser execution. Per-tenant quotas prevent monopolisation. The queue is bounded through storage quota and maximum age; expired work reaches an explicit terminal state rather than processing obsolete documents indefinitely.

Workers scale from backlog age and measured service rate, capped by database, object-store, sandbox-host, and budget constraints. Minimum warm capacity covers sudden demand and incident reprocessing. Scale-down stops claims, renews or releases leases, and permits bounded completion. A visibility timeout alone is not correctness: the result write and job completion are idempotent by operation identifier.

Retries belong at one layer for each dependency, obey the end-to-end deadline, and use full jitter plus a shared budget. Parser failures due to invalid input are permanent, not retried. Object-store timeouts after upload are reconciled by deterministic object key and digest. Circuit breakers protect storage and policy dependencies; degraded mode may pause new upload or return already promoted results, but never bypass scanning or tenant authorisation.

### 20.35.5 Observability, recovery, and cost

Every operation carries a generated correlation identifier through API, queue, worker, quarantine, and promotion. Metrics bound labels to route templates, result classes, file-type groups, and region. Document names, tenant identifiers, object keys, and parser text do not enter metric labels. Restricted structured events retain exact operation and tenant identity for audit. Traces are sampled with error and high-latency tail retention, but accounting and security events are unsampled durable records.

Backups combine database snapshots and transaction logs, versioned immutable object input/output, configuration and policy bundles, artifacts, and recoverable key hierarchy. A consistency ledger records the object digest referenced by each database version. Clean-room exercises restore to a point, validate referential and tenant invariants, reprocess a sample through current isolated workers, and prove the recovery identity path works without the primary control plane.

Cost is measured per durably completed document and segmented by file class. It includes parser compute, temporary and retained storage, scanning, object operations, telemetry, network transfer, retries, and quarantine retention. A decompression bomb rejected after bounded inspection is counted as defence cost, not successful work. Budgets shed free experimental reprocessing before contractual uploads and never delete retained evidence automatically.

### 20.35.6 Incident exercise

The capstone incident combines a worker release with rising memory terminations and delayed processing. The incident commander pauses rollout and preserves the new digest. Operations removes unhealthy workers from admission, increases only verified host headroom, and prevents retry storms. Investigation compares file-type distribution, old and new artifacts, cgroup events, queue age, parser phase spans, and deployment timing. It discovers that one newly supported format expands a shared native library's memory use beyond the tested limit.

Rollback is evaluated against message and output compatibility. If safe, traffic returns to the old worker while affected format jobs enter a visible deferred state; otherwise a flag disables that format and the new worker continues for others. Users receive accurate impact and next-update time. Recovery is verified by falling queue age, stable memory, successful representative documents, and absence of cross-tenant or quarantine bypass.

The review does not end with “increase memory”. It adds format-specific expansion measurement, a corpus representing large valid inputs, admission estimates, a sandbox limit test, canary segmentation by file type, a queue-age burn alert, and a release requirement connecting supported formats to capacity evidence. Memory may still be raised if the valid workload requires it, but the decision becomes a measured service policy rather than an unexplained patch.
