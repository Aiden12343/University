# 20.4 Configuration

**Configuration** is externally selected information that changes program behaviour without modifying its source. Examples include network addresses, feature policies, timeouts, resource limits, and service endpoints. A secret is not merely configuration; it requires confidentiality and lifecycle controls.

Configuration sources can include:

- command-line arguments;
- environment variables;
- versioned files;
- service-discovery systems;
- configuration services;
- platform metadata.

Precedence must be explicit. Otherwise an environment variable silently overrides a file or a default masks a missing production value.

~~~python
from dataclasses import dataclass
import os


@dataclass(frozen=True)
class ServiceConfig:
    database_url: str
    request_timeout_seconds: float
    worker_count: int


def config_from_environment() -> ServiceConfig:
    try:
        database_url = os.environ["SERVICE_DATABASE_URL"]
    except KeyError as error:
        raise ValueError(
            "SERVICE_DATABASE_URL is required"
        ) from error

    timeout = float(
        os.environ.get(
            "SERVICE_REQUEST_TIMEOUT_SECONDS",
            "5.0",
        )
    )
    workers = int(
        os.environ.get("SERVICE_WORKER_COUNT", "4")
    )

    if timeout <= 0:
        raise ValueError("timeout must be positive")
    if workers < 1 or workers > 128:
        raise ValueError("worker count outside 1..128")

    return ServiceConfig(
        database_url=database_url,
        request_timeout_seconds=timeout,
        worker_count=workers,
    )
~~~

The function parses text because environment values are strings. It validates ranges and returns immutable typed configuration. It does not print the database URL, which can contain credentials. A production parser should classify invalid numeric syntax with configuration-specific errors and redact secret components.

Configuration should be validated completely at startup where possible. Discovering a misspelled endpoint only when a rare request path executes converts a deployment defect into an intermittent outage.

### 20.4.1 A configuration value has provenance

The effective value alone is insufficient for diagnosis. A configuration system should be able to explain the **provenance** of each non-secret value: default, file, environment, command line, remote policy, or emergency override; the source version; the parser version; and the time at which it became effective. This makes “why is this replica different?” answerable without dumping secrets.

Layered configuration requires a deterministic precedence relation. Suppose defaults (D), file values (F), environment (E), and command-line values (C) are maps. A common merge is

\[
C \triangleright E \triangleright F \triangleright D,
\]

where the leftmost defined value wins. That notation does not settle deletion, nested maps, empty strings, lists, or unknown keys. Those semantics must be specified. Silently ignoring an unknown production key turns a spelling error into a default; strict schema validation is generally safer.

Configuration has at least four validation layers:

1. **lexical:** can text be decoded as the intended primitive, such as an integer or URL?
2. **structural:** are required fields present and unknown fields rejected or handled deliberately?
3. **semantic:** are ranges, relationships, and mutually exclusive options valid?
4. **environmental:** are named files, credentials, regions, and endpoints actually available to this workload?

Environmental validation may be expensive or transient, so it should distinguish “configuration is impossible” from “dependency is presently unavailable”. A deployment preflight can test authority without making an irreversible business change.

### 20.4.2 Static and dynamic configuration

**Static configuration** takes effect only when a process starts or is replaced. **Dynamic configuration** can change while the process runs. Dynamic control shortens mitigation time but introduces distributed-state problems: replicas may observe versions at different times, invalid changes can spread rapidly, and rollback must identify the previous state precisely.

Treat a dynamic configuration as an immutable versioned snapshot. Validate it before publication, sign or authorise the publisher, distribute a monotonically identified version, retain last-known-good state, expose the active version in telemetry, and define what happens when the source is unreachable. A change affecting protocol compatibility may require coordinated rollout rather than arbitrary live reload.

Feature flags are dynamic configuration specialised for behaviour selection. A flag record needs type, owner, rationale, default, targeting rule, creation time, expiry, audit history, and removal condition. Evaluation must have a deterministic fallback. If the flag service times out during every request, a mechanism intended to reduce risk has become a synchronous availability dependency.

> **Common misconception 20.7 — “Keeping configuration outside code makes every change safe.”**  
> Externalisation improves separability, but a configuration change can alter authority, data interpretation, capacity, and protocol behaviour as profoundly as a code change. It requires validation, review, staged exposure, and attribution.

> **Common misconception 20.8 — “Dynamic configuration is preferable because it avoids deployment.”**  
> It trades deployment delay for distributed consistency, validation, audit, and emergency-control complexity. Values whose transition cannot be made safe across mixed replicas should remain tied to an artifact rollout.
