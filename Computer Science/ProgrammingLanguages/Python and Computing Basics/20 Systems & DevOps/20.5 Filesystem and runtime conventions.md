# 20.5 Filesystem and runtime conventions

A service needs deliberate locations for:

- immutable application code;
- configuration;
- writable state;
- temporary files;
- caches;
- logs where the platform does not collect streams;
- runtime sockets and process identifiers.

Writing beside imported package code fails in read-only images, conflicts across deployments, and confuses state with artifact. Temporary directories can be cleared and can be shared with untrusted processes under platform rules. Use secure temporary-file APIs and atomic replacement where appropriate.

An **atomic rename** can make a newly completed file appear at its final path in one filesystem operation under supported conditions:

~~~python
from pathlib import Path
import os
import tempfile


def replace_text_atomically(
    destination: Path,
    text: str,
) -> None:
    destination.parent.mkdir(
        parents=True,
        exist_ok=True,
    )

    descriptor, temporary_name = tempfile.mkstemp(
        dir=destination.parent,
        prefix=f".{destination.name}.",
    )
    temporary = Path(temporary_name)

    try:
        with os.fdopen(
            descriptor,
            "w",
            encoding="utf-8",
            newline="\n",
        ) as stream:
            stream.write(text)
            stream.flush()
            os.fsync(stream.fileno())

        os.replace(temporary, destination)
    except BaseException:
        temporary.unlink(missing_ok=True)
        raise
~~~

The temporary file resides in the destination directory so replacement need not cross filesystems. Flushing Python buffers and requesting <code>fsync</code> improves persistence of file content, but complete crash-durability may also require syncing the directory and depends on filesystem and hardware guarantees. Atomic visibility is not identical to durable storage.

### 20.5.1 Namespaces of state

Filesystem layout expresses lifecycle. On a conventional Unix-like host, executable or shareable application content is distinct from host configuration, variable durable state, volatile runtime state, caches, and temporary data. The Filesystem Hierarchy Standard supplies common locations, but containers, user-scoped applications, macOS, and Windows have different conventions. The invariant is more important than one pathname: code is replaceable and preferably read-only; durable state has an owner and backup policy; caches may be discarded; temporary data has bounded lifetime; runtime sockets disappear safely after reboot.

Every writable path should answer:

- which identity may create, read, rename, link, and delete entries;
- whether names can be influenced by another principal;
- whether the filesystem is local, networked, layered, or ephemeral;
- which atomicity and durability guarantees apply;
- how quotas and exhaustion are handled;
- whether content survives process, container, host, or regional replacement;
- how backup, retention, encryption, and deletion are governed.

An application that writes uploads, caches, database files, and generated reports under one directory makes these policies inseparable. Separate paths and mounts allow different permissions, quotas, backup schedules, and no-execute or read-only controls.

### 20.5.2 Atomicity, durability, and concurrency

An operation is **atomic** with respect to observers when they see either the state before it or the state after it, not an intermediate state. **Durability** concerns whether acknowledged state survives specified failures. **Consistency** describes which relationships among states remain valid. These properties are independent.

For a local file replacement, a stronger Unix-oriented protocol is:

1. create a new file securely in the destination directory;
2. write all bytes and validate the write result;
3. flush language and operating-system buffers for the file;
4. set final ownership and metadata under controlled semantics;
5. rename over the destination atomically where supported;
6. synchronise the containing directory if the required failure model demands persistent directory entry change.

This protocol still depends on the filesystem, mount options, storage device, kernel, and power-loss model. Network filesystems can differ. Applications should not invent a durability guarantee stronger than the documented stack provides.

File locks are advisory on many systems and have platform-specific behaviour across processes, threads, fork, descriptor duplication, and network mounts. A lock file created by “check then create” is vulnerable to a race unless creation is atomic. A stale lock after crash requires an ownership and fencing policy; merely deleting it based on an old process identifier can conflict with PID reuse.

> **Common misconception 20.9 — “A path under `/tmp` is private to the process.”**  
> The directory may be shared, names may be observable, cleanup may occur independently, and space may be limited. Secure creation, permissions, lifecycle, and namespace configuration are still required.

> **Common misconception 20.10 — “Calling `fsync` once makes an update crash-proof.”**  
> Persistence depends on which file and directory objects were synchronised, the order of operations, filesystem and device guarantees, and the failure considered. `fsync` is a primitive within a protocol, not a universal proof.
