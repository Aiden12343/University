# 20.6 Immutable artifacts

A deployable **artifact** is a versioned output of a build process: wheel, archive, executable, container image, or package. An artifact should be immutable after publication. Promotion moves the same identified bytes from test to production; rebuilding separately for production can introduce dependency or tool differences.

A **content digest** identifies artifact bytes through a cryptographic hash. A human-friendly version points to a release; a digest establishes exact identity. Mutable tags such as <code>latest</code> are convenient references, not durable evidence.

Artifact metadata includes:

- source revision;
- build definition;
- dependency lock;
- compiler/interpreter and tool versions;
- build time under reproducibility policy;
- tests performed;
- SBOM and provenance attestation;
- signature;
- compatibility and migration requirements.

Reproducible builds aim for identical outputs from identical declared inputs. Timestamps, unordered file traversal, locale, network downloads, and embedded paths can defeat them. Reproducibility supports comparison; it does not prove the source is benign.

### 20.6.1 Build closure and hermeticity

The **build closure** is the complete transitive set of inputs affecting artifact bytes: source, dependencies, build backend, compiler, interpreter, operating-system libraries, environment, locale, clocks, random seeds, filesystem ordering, and invoked tools. A **hermetic build** is isolated so it can read only declared inputs and produce declared outputs. Hermeticity improves repeatability and provenance; it does not imply determinism if a declared input such as time or randomness varies.

Build systems commonly represent actions as a directed acyclic graph. A node may be reused from cache only if its action identity commits to every relevant input and tool. A cache key based only on source revision can return an artifact built with a different compiler or dependency. Conversely, embedding the current directory or build time can destroy cache reuse without adding meaningful identity.

Artifact identity should be content based at every promotion boundary. A release record can be represented explicitly:

~~~python
from dataclasses import dataclass


@dataclass(frozen=True)
class ReleaseIdentity:
    source_revision: str
    artifact_sha256: str
    provenance_sha256: str
    sbom_sha256: str
    configuration_schema: int


def same_artifact(left: ReleaseIdentity, right: ReleaseIdentity) -> bool:
    return left.artifact_sha256 == right.artifact_sha256
~~~

The other fields describe evidence and compatibility, but only the artifact digest answers whether the deployed bytes are identical. A release version can be reassigned accidentally or maliciously; an immutable registry policy and admission verification prevent silent substitution.

### 20.6.2 Promotion and compatibility

**Promotion** changes an artifact's approved use without changing its bytes. The development environment, staging environment, and production environment may supply different configuration and data, but they should execute the same identified artifact when the purpose is to carry test evidence forward. Rebuilding from the same source for each environment breaks that evidence chain.

Compatibility forms part of artifact metadata. The artifact should state supported configuration schema, database schema interval, message versions, CPU architecture, operating-system ABI, Python implementation and version, and required external protocol capabilities. Compatibility is usually an interval rather than one point because rolling deployment creates overlap.

An artifact store needs retention policy. Keeping every build forever may be expensive and retain vulnerable material; deleting the last known-good production artifact makes rollback impossible. Retain releases according to recovery and audit requirements, protect active and rollback digests from collection, and ensure that their dependencies and decryption or signature trust material remain available.

> **Common misconception 20.11 — “An artifact version uniquely identifies its bytes.”**  
> Only an enforced immutable mapping or content digest establishes byte identity. A mutable tag or version label is a name whose referent can change.

> **Common misconception 20.12 — “Hermetic and reproducible mean trustworthy.”**  
> Hermeticity constrains inputs and reproducibility permits independent comparison. Both can faithfully reproduce malicious source, compromised tools, or an authorised but unsafe dependency.
