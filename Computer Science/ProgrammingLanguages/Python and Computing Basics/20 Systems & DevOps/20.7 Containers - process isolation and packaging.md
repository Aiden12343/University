# 20.7 Containers: process isolation and packaging

A **container** is a set of processes executed with operating-system isolation and resource controls, conventionally packaged with a filesystem image and metadata. On Linux, common mechanisms include:

- **namespaces**, which give processes restricted views of identifiers and resources;
- **control groups**, or cgroups, which account for and limit resources;
- filesystem layers and mount controls;
- capabilities and security modules;
- ordinary user and permission mechanisms.

A container usually shares the host kernel. It is not a miniature physical machine and not by itself a security boundary equivalent to a strongly isolated virtual machine. Kernel vulnerabilities, excessive capabilities, mounted host sockets, privileged mode, and shared devices can cross isolation.

A **container image** is an immutable content-addressed collection of filesystem layers plus configuration. A **container** is a runtime instance of an image with writable state and process configuration. Deleting a container should not delete durable business data; persistent state belongs in managed volumes or external services under explicit backup semantics.

### 20.7.1 What Linux isolation actually composes

Linux containers combine mechanisms rather than invoking one “container” system call. Namespace types can isolate process identifiers, mounts, networks, inter-process communication, host names, cgroup views, time, and user identifiers. A namespace changes what a process can name or observe; it does not necessarily limit how much of a resource the process consumes. Cgroups account for and constrain CPU, memory, process count, and I/O. Capability sets split portions of traditional superuser privilege. Seccomp can restrict system calls, while Linux Security Modules such as SELinux or AppArmor apply mandatory policy.

These controls are orthogonal and incomplete in isolation. A process in a network namespace can still exhaust host memory without a memory cgroup. A non-root process can retain dangerous capabilities. A read-only root filesystem does not make a writable host socket safe. A restrictive system-call filter does not repair excessive file permissions. Defence arises from a reviewed composition under a stated kernel and runtime version.

**Rootless containers** arrange runtime operation without host-root authority, often using user namespaces that map container identifiers to unprivileged host identifiers. They reduce the consequence of runtime compromise, but feature availability and mapping rules vary. “Root inside” may not be host root, yet a process still has broad power over its container filesystem and peers; application least privilege remains valuable.

### 20.7.2 Images, layers, and the writable view

An OCI image manifest identifies a configuration object and an ordered sequence of compressed filesystem layer descriptors. Applying layer changes constructs a root filesystem view. Runtime overlay or union filesystems commonly add a writable layer for the container instance. Writing a large existing file may trigger a **copy-up**, consuming time and storage unexpectedly. Deleting a file from a later image layer records a whiteout; bytes can remain in an earlier layer and registry storage.

Therefore:

- a secret copied in one layer remains compromised even if a later command deletes it;
- package-manager caches removed within the same build instruction need not survive in a committed intermediate layer;
- log files written into the container layer consume ephemeral storage and disappear on replacement;
- image size is the sum of relevant compressed layers, not the apparent size of the final directory tree;
- identical layers can be shared, so one vulnerable base layer can affect many images.

The OCI runtime specification describes a bundle and lifecycle, whereas the image specification describes content. A higher-level engine resolves, unpacks, configures networking and storage, and invokes a low-level runtime. Distinguishing these layers helps locate policy: registry admission is not runtime sandboxing, and a secure runtime cannot authenticate bytes it was never asked to verify.

### 20.7.3 Containers, virtual machines, and trust boundaries

A virtual machine presents virtual hardware and ordinarily runs a guest kernel; a process container ordinarily shares the host kernel. Virtual machines usually provide a stronger isolation boundary at greater startup and resource cost. Sandbox runtimes can interpose a user-space kernel or lightweight virtual machine beneath a container interface. Choice depends on multi-tenancy, kernel attack surface, workload trust, device access, performance, and operational maturity.

Do not group mutually hostile workloads solely because both are “containers”. Define the trusted computing base, the host and orchestrator administrators, permitted device and kernel interfaces, and the consequence of escape. High-risk parsing, untrusted customer code, and ordinary trusted microservices may require different runtime classes.

> **Common misconception 20.13 — “Namespaces limit resource consumption.”**  
> Namespaces primarily isolate views and identifiers. Cgroups and quotas constrain resource use; both kinds of control are normally required.

> **Common misconception 20.14 — “Deleting a file in a later image layer removes its secret.”**  
> Layer history can retain the original bytes. Once committed or pushed, the secret must be treated as disclosed and rotated.

> **Common misconception 20.15 — “Rootless makes untrusted code harmless.”**  
> It narrows host authority but leaves kernel, runtime, network, resource-exhaustion, data, and same-container risks. The residual boundary must still be modelled and tested.
