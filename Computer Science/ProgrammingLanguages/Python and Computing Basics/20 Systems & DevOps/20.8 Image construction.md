# 20.8 Image construction

A container build definition records steps producing an image. A minimal Python example:

~~~dockerfile
FROM python:3.12-slim

ENV PYTHONDONTWRITEBYTECODE=1
ENV PYTHONUNBUFFERED=1

RUN groupadd --system app \
    && useradd --system --gid app --create-home app

WORKDIR /app

COPY pyproject.toml README.md ./
COPY src/ ./src/

RUN python -m pip install \
    --no-cache-dir \
    --disable-pip-version-check \
    .

USER app

CMD ["python", "-m", "service"]
~~~

Interpretation:

1. The base image supplies a specific Python family and operating-system userland; production should pin an approved immutable digest.
2. Bytecode files are suppressed in this layout, and Python output is unbuffered for stream collection.
3. A non-root operating-system identity is created.
4. Source and project metadata are copied.
5. The project is installed as a package.
6. Runtime privileges drop to the application user.
7. The exec-form command starts Python without a shell.

The example is not a complete hardened build. It lacks a lock with verified hashes, multi-stage separation, SBOM generation, signature, vulnerability policy, read-only runtime filesystem, explicit health behaviour, resource limits, and base-image update process. A small image reduces transfer and some surface but is not automatically trustworthy.

Layer order affects caching and disclosure. Removing a secret in a later layer does not remove it from earlier layer content. Build secrets require a facility that does not commit them into layers.

### 20.8.1 Deterministic, minimal build contexts

The **build context** is the tree of files visible to image-building instructions. Sending the repository indiscriminately can include credentials, version-control metadata, test corpora, editor files, and gigabytes of irrelevant data. An exclusion file reduces context, but an allowlisted generated context is stronger for sensitive repositories. The builder cannot prevent a copied secret from leaking if the secret was intentionally included in its readable context.

Pinning `FROM python:3.12-slim` selects a mutable tag. For reproducible promotion, record and preferably use a manifest digest while retaining a readable annotation for maintainers. A digest also pins defects; update automation must regularly resolve, test, and approve a newer base rather than assuming immutability and patch currency are the same objective.

A **multi-stage build** uses one stage with compilers and headers to produce a wheel or executable and copies only the product into a smaller runtime stage. The boundary reduces runtime tools and files but is not automatically hermetic: both stages may download mutable inputs. Verify dependency hashes, restrict network access after acquisition, and preserve build provenance.

~~~dockerfile
# The digest is illustrative; production records an approved real digest.
FROM python:3.14-slim@sha256:APPROVED_BUILD_DIGEST AS build
WORKDIR /build
COPY pyproject.toml pylock.toml ./
COPY src/ ./src/
RUN --mount=type=cache,target=/root/.cache/pip \
    python -m build --wheel --outdir /out

FROM python:3.14-slim@sha256:APPROVED_RUNTIME_DIGEST AS runtime
RUN useradd --system --uid 10001 --no-create-home app
COPY --from=build /out/*.whl /tmp/package.whl
RUN python -m pip install --no-cache-dir /tmp/package.whl \
    && rm /tmp/package.whl
USER 10001:10001
WORKDIR /app
ENTRYPOINT ["python", "-m", "service"]
~~~

The placeholder digests deliberately make the fragment non-buildable until approved values are supplied; invented digests would teach a dangerous copying practice. A real pipeline builds the wheel separately where possible, verifies it, and copies the exact artifact rather than using an unrestricted wildcard when several outputs may exist.

### 20.8.2 Architecture, metadata, and time

A multi-platform image index can associate different manifests with CPU architecture and operating system. The tag therefore does not identify one executable byte sequence. Test each target architecture; emulation can hide performance or instruction-set defects, while native extensions may differ. Admission and provenance should bind the platform-specific manifest selected at deployment.

Image metadata such as labels, default environment, user, working directory, entrypoint, command, stop signal, and exposed ports forms part of the runtime contract. Defaults are overrideable, so security must not rely on a label or `EXPOSE` statement enforcing a network rule. Avoid embedding secrets or unnecessary build timestamps in labels. When time is required for traceability, source revision and signed provenance provide stronger identity than a mutable wall-clock string.

> **Common misconception 20.16 — “The smallest image is the most secure image.”**  
> Size can reduce packages and transfer, but security depends on provenance, patchability, configuration, runtime authority, and application behaviour. An opaque tiny binary may be harder to inspect and recover than a slightly larger maintained base.

> **Common misconception 20.17 — “Pinning a base digest solves updates.”**  
> Pinning gives repeatability. A separate monitored process must discover, assess, rebuild, test, and promote patched base images.
