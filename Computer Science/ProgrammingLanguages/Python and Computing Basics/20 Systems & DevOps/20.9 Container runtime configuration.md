# 20.9 Container runtime configuration

Secure and operable runtime defaults include:

- non-root user;
- read-only root filesystem where possible;
- explicit writable mounts;
- dropped Linux capabilities;
- no privileged mode;
- restricted system calls and mandatory access controls;
- CPU and memory requests/limits;
- bounded process count;
- no host namespace or control socket mount;
- restricted network policy;
- secret injection through a managed mechanism;
- immutable image digest;
- health and shutdown settings.

Memory limits interact with Python and native allocators. A process exceeding a hard cgroup limit can be killed without a Python <code>MemoryError</code> it can handle. Capacity tests must run under actual limits.

CPU limits can throttle an application. A machine reports many logical CPUs while the container is granted a fraction or quota; worker-count heuristics based only on host CPU discovery can oversubscribe.

### 20.9.1 Requests, limits, and quality of service

A resource **request** expresses the capacity a scheduler should reserve or use for placement; a **limit** constrains consumption. Semantics vary by orchestrator and resource. CPU is commonly compressible: exceeding quota leads to throttling and latency. Memory is incompressible: when reclamation cannot satisfy demand, a process or container may be terminated. Storage, process identifiers, file descriptors, sockets, and network bandwidth also need budgets even when the platform does not expose identical request/limit pairs.

Set requests from measured working sets and load, not from arbitrary fractions of node size. Requests far below reality overcommit the node and make eviction correlated. Requests far above reality waste placement capacity. A memory limit too close to median use ignores peaks, allocator fragmentation, page cache, native extensions, and workload variation. A limit so high that every replica can consume node memory defeats isolation.

The kernel's out-of-memory decision may kill the process without allowing `finally` blocks or Python exception handling. Durable protocols must already tolerate abrupt loss. The restart evidence should distinguish an OOM termination from an application exception and relate it to working set, limit, node pressure, and deployment version.

### 20.9.2 Runtime contract and hardening

Runtime configuration should be reviewed as one contract:

| Domain | Examples of explicit state |
|:---|:---|
| identity | numeric user/group, supplementary groups, service account, token audience |
| filesystem | read-only root, volume types, ownership, mount flags, ephemeral quota |
| kernel | capabilities, seccomp profile, security module, sysctls, privilege escalation |
| network | namespace, listeners, ingress/egress policy, DNS, proxy variables |
| resources | CPU, memory, process count, files, storage, accelerators |
| lifecycle | entrypoint, probes, stop signal, grace period, restart policy |
| evidence | stream collection, runtime events, image digest, configuration version |

Run as a stable numeric identity where ownership crosses image or volume boundaries; a username in one image can map differently in another. Dropping every capability and adding back only demonstrated needs is safer than inheriting a broad default set. `no-new-privileges` prevents selected execution paths from gaining additional privilege but does not remove authority already held.

Read-only root filesystems reveal accidental writes during testing. Supply explicit writable temporary, cache, and state locations with quotas. An application that implicitly writes bytecode, font caches, or a home directory should be configured rather than granted a writable root. This makes the artifact/state boundary executable.

> **Common misconception 20.18 — “CPU and memory limits behave alike.”**  
> CPU quota usually delays work through throttling; memory pressure can terminate work abruptly. Their capacity tests, alerts, and failure semantics differ.

> **Common misconception 20.19 — “Running as a non-root user is complete container hardening.”**  
> It is one control among filesystem, capabilities, system calls, mandatory policy, namespaces, cgroups, devices, networking, provenance, and application permissions.
