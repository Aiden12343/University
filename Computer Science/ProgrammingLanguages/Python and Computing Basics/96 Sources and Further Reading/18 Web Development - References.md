# 18.38 References and further study

The references below are not a substitute for the semantic distinctions developed in this chapter. They are the normative specifications, primary research, framework documentation, and operational studies against which those distinctions should be checked. Protocol specifications change through errata, updates, and replacement documents; living standards and framework manuals change in place. A production design must therefore record the exact revision against which it was reviewed. URLs were last verified on 22 September 2026.

### 18.38.1 Naming, transport, and HTTP

1. Mockapetris, P. (1987), *Domain Names—Concepts and Facilities*, RFC 1034. [RFC Editor](https://www.rfc-editor.org/rfc/rfc1034). This is the conceptual foundation for DNS: its distributed name space, zones, delegation, resolvers, caching, and negative knowledge. Read it with RFC 1035 and later operational updates rather than treating a DNS lookup as a single database query.

2. Mockapetris, P. (1987), *Domain Names—Implementation and Specification*, RFC 1035. [RFC Editor](https://www.rfc-editor.org/rfc/rfc1035). The document specifies DNS message layout, resource-record representation, transport behaviour, and resolver/name-server interaction. Its wire-level detail explains why record type, class, TTL, truncation, recursion, and authoritative status are semantically distinct.

3. Deering, S. and Hinden, R. (2017), *Internet Protocol, Version 6 (IPv6) Specification*, RFC 8200. [RFC Editor](https://www.rfc-editor.org/rfc/rfc8200). This specification establishes IPv6 addressing, packet structure, extension-header processing, fragmentation, and upper-layer delivery. It is particularly useful when testing address classification and avoiding IPv4-only assumptions in allowlists, logs, parsers, and SSRF defences.

4. Eddy, W. (ed.) (2022), *Transmission Control Protocol (TCP)*, RFC 9293. [RFC Editor](https://www.rfc-editor.org/rfc/rfc9293). The consolidated TCP specification defines the reliable ordered byte stream, connection state machine, sequence and acknowledgement rules, retransmission, flow control, and reset behaviour. It supplies the precise substrate beneath HTTP/1.1 and TLS without pretending that a stream preserves application-message boundaries.

5. Iyengar, J. and Thomson, M. (2021), *QUIC: A UDP-Based Multiplexed and Secure Transport*, RFC 9000. [RFC Editor](https://www.rfc-editor.org/rfc/rfc9000). QUIC integrates secure connection establishment, independent multiplexed streams, connection migration, and loss recovery above UDP. Comparing it with TCP clarifies why HTTP/3 changes transport failure coupling while leaving the higher-level semantics of HTTP substantially intact.

6. Rescorla, E. (2018), *The Transport Layer Security (TLS) Protocol Version 1.3*, RFC 8446. [RFC Editor](https://www.rfc-editor.org/rfc/rfc8446). This is the normative account of TLS 1.3 handshakes, key schedule, authentication, record protection, resumption, and early data. Its explicit threat assumptions are essential when reasoning about certificate validation, termination proxies, replayable 0-RTT requests, and mutual authentication.

7. Cooper, D. et al. (2008), *Internet X.509 Public Key Infrastructure Certificate and Certificate Revocation List (CRL) Profile*, RFC 5280. [RFC Editor](https://www.rfc-editor.org/rfc/rfc5280). The certificate path-validation algorithm, name constraints, key usages, extensions, and revocation model explain what certificate acceptance actually asserts. A TLS library’s successful handshake is the result of this policy machinery, not proof of an endpoint’s application-level trustworthiness.

8. Berners-Lee, T., Fielding, R. and Masinter, L. (2005), *Uniform Resource Identifier (URI): Generic Syntax*, RFC 3986. [RFC Editor](https://www.rfc-editor.org/rfc/rfc3986). The generic syntax separates scheme, authority, path, query, and fragment and defines reference resolution and permitted normalisations. It should be read before implementing URL comparison, signing, redirect policy, cache keys, or security checks on user-supplied destinations.

9. Barth, A. (2011), *The Web Origin Concept*, RFC 6454. [RFC Editor](https://www.rfc-editor.org/rfc/rfc6454). This document formalises origin calculation and serialisation for browser security policy. It makes clear why origin is not equivalent to site, host name, registrable domain, or URL prefix, distinctions on which CORS, messaging, cookies, and embedded-content security depend.

10. Fielding, R., Nottingham, M. and Reschke, J. (2022), *HTTP Semantics*, RFC 9110. [RFC Editor](https://www.rfc-editor.org/rfc/rfc9110). The central HTTP reference defines resources, representations, methods, status codes, fields, content negotiation, validators, preconditions, authentication, intermediaries, and connection-independent semantics. Application code should derive retry, caching, redirection, and conditional-update behaviour from these semantics rather than from framework conventions.

11. Fielding, R., Nottingham, M. and Reschke, J. (2022), *HTTP Caching*, RFC 9111. [RFC Editor](https://www.rfc-editor.org/rfc/rfc9111). This specification defines cache keys, freshness, validation, invalidation, request and response directives, authenticated responses, and shared-cache constraints. It is the necessary reference for deciding whether reused content is semantically permissible, not merely technically available.

12. Thomson, M. and Benfield, C. (2022), *HTTP/1.1*, RFC 9112. [RFC Editor](https://www.rfc-editor.org/rfc/rfc9112). The document specifies textual message syntax, field parsing, content length, transfer coding, connection management, and ambiguity handling. Its message-framing rules are indispensable for understanding desynchronisation and request-smuggling defects between components that disagree about where one message ends.

13. Thomson, M. and Benfield, C. (2022), *HTTP/2*, RFC 9113. [RFC Editor](https://www.rfc-editor.org/rfc/rfc9113). HTTP/2 maps HTTP semantics onto binary frames, multiplexed streams, flow control, prioritisation, and compressed fields. It explains why multiplexing reduces some connection costs yet introduces stream-level limits, state exhaustion, head-of-line effects below the HTTP layer, and new operational observables.

14. Bishop, M. (2022), *HTTP/3*, RFC 9114. [RFC Editor](https://www.rfc-editor.org/rfc/rfc9114). This specification maps HTTP onto QUIC streams and QPACK field compression. It permits a disciplined comparison of application semantics, stream cancellation, connection migration, loss isolation, and intermediary support without the inaccurate claim that HTTP/3 is a different application model.

15. Nottingham, M. (2022), *Building Protocols with HTTP*, RFC 9205. [RFC Editor](https://www.rfc-editor.org/rfc/rfc9205). The guidance addresses method selection, status codes, URIs, fields, redirects, caching, versioning, extensibility, security, and use of HTTP’s existing machinery. It is a corrective to API designs that tunnel an unrelated protocol through a nominal HTTP endpoint.

16. IETF HTTP Working Group (2026), *Cookies: HTTP State Management Mechanism*, RFC 10025. [RFC Editor](https://www.rfc-editor.org/rfc/rfc10025). This successor to RFC 6265 specifies contemporary `Cookie` and `Set-Cookie` processing, scope, expiry, prefixes, and attributes. Server policy must nevertheless account for browser deployment behaviour and recognise that cookie transport does not by itself provide session rotation, revocation, or CSRF protection.

17. Fette, I. and Melnikov, A. (2011), *The WebSocket Protocol*, RFC 6455. [RFC Editor](https://www.rfc-editor.org/rfc/rfc6455). The reference defines the HTTP opening handshake, origin field, masking, fragmentation, control frames, close handshake, and status codes. It exposes WebSocket as a stateful framed protocol requiring explicit authentication lifetime, message limits, backpressure, liveness, and deployment-drain policy.

18. Bray, T. (ed.) (2017), *The JavaScript Object Notation (JSON) Data Interchange Format*, RFC 8259. [RFC Editor](https://www.rfc-editor.org/rfc/rfc8259). JSON’s deliberately small data model conceals interoperability hazards involving duplicate names, number range and precision, Unicode, ordering, and parser limits. Application schemas must add the domain types and constraints that JSON itself does not express.

19. Freed, N., Klensin, J. and Hansen, T. (2013), *Media Type Specifications and Registration Procedures*, RFC 6838. [RFC Editor](https://www.rfc-editor.org/rfc/rfc6838). Media types identify representation formats and processing expectations; they are not decorative filename labels. The registration rules and structured suffix conventions support precise content negotiation, safe parser selection, and evolution of application-specific formats.

20. Nottingham, M., Wilde, E. and Dalal, S. (2023), *Problem Details for HTTP APIs*, RFC 9457. [RFC Editor](https://www.rfc-editor.org/rfc/rfc9457). The standard supplies interoperable fields for machine-readable HTTP error details while preserving the status code’s protocol meaning. It is a useful base vocabulary, but applications must still specify stable problem types, disclosure policy, field validation, and retry implications.

21. Hodges, J., Jackson, C. and Barth, A. (2012), *HTTP Strict Transport Security (HSTS)*, RFC 6797. [RFC Editor](https://www.rfc-editor.org/rfc/rfc6797). HSTS lets a host instruct user agents to require secure transport for a period, reducing downgrade and insecure-navigation exposure. Deployment requires care over subdomains, preload commitments, certificate failure, bootstrap requests, and the inability to repair an inaccessible host over HTTP.

22. Nottingham, M. and Fielding, R. (2012), *Additional HTTP Status Codes*, RFC 6585. [RFC Editor](https://www.rfc-editor.org/rfc/rfc6585). The definitions of 428, 429, 431, and 511 sharpen application handling of preconditions, rate limits, oversized fields, and captive portals. In particular, 429 communicates a refusal policy; it does not replace concurrency control, fair accounting, or overload protection.

### 18.38.2 Python interfaces and the browser platform

23. Eby, P. (2010), *Python Web Server Gateway Interface v1.0.1*, PEP 3333. [Python Enhancement Proposals](https://peps.python.org/pep-3333/). The PEP is the exact WSGI contract: a synchronous callable, an environment mapping, a response-start callback, and an iterable of bytes. Its rules about iteration, closing, errors, and header commitment explain both middleware composition and WSGI’s streaming limitations.

24. ASGI project (2026), *ASGI HTTP and WebSocket Protocol Specification*. [ASGI documentation](https://asgi.readthedocs.io/en/latest/specs/www.html). ASGI represents connections as scopes and protocol traffic as asynchronous receive/send events. The specification should be consulted for disconnects, response start, trailers, WebSocket acceptance and closure, subprotocols, and version negotiation rather than inferring behaviour from one server.

25. Pallets (2026), *Flask 3.1 Documentation*. [Flask documentation](https://flask.palletsprojects.com/en/stable/). The manual covers application and request contexts, routing, blueprints, factories, error handling, testing, security considerations, and deployment boundaries. Its small core makes framework mechanics visible, but extensions remain independently versioned components whose contracts must be reviewed separately.

26. Pallets (2026), *Werkzeug Documentation*. [Werkzeug documentation](https://werkzeug.palletsprojects.com/en/stable/). Werkzeug implements much of Flask’s WSGI request, response, routing, serving, and test infrastructure. Studying it distinguishes protocol adaptation from domain logic and exposes details such as trusted hosts, proxy metadata, multipart parsing, secure filenames, and response conditionality.

27. Pallets (2026), *Jinja Documentation*. [Jinja documentation](https://jinja.palletsprojects.com/en/stable/). Jinja’s template inheritance, escaping, undefined values, loaders, filters, bytecode caching, and sandbox qualifications are central to server-rendered Python applications. Automatic HTML escaping is contextual protection, not a general licence to place untrusted values in scripts, styles, URLs, or already-marked markup.

28. Django Software Foundation (2026), *Django 6.0 Documentation*. [Django documentation](https://docs.djangoproject.com/en/6.0/). This is the authoritative guide to Django’s request pipeline, models, query sets, migrations, transactions, forms, templates, middleware, authentication, security controls, asynchronous support, testing, and deployment. The versioned manual should be paired with the deployment checklist and release-specific security notes.

29. WHATWG (living standard), *HTML*. [HTML Standard](https://html.spec.whatwg.org/multipage/). HTML defines parsing, document semantics, forms, navigation, script integration, events, embedded content, storage hooks, and many security-relevant browser behaviours. Semantic elements and native controls should be understood as interoperability and accessibility contracts, not merely default presentation choices.

30. WHATWG (living standard), *Fetch Standard*. [Fetch Standard](https://fetch.spec.whatwg.org/). Fetch unifies requests, responses, redirects, credentials, referrers, CORS, mixed content interaction, service workers, and network errors across browser APIs. It is the normative place to understand why a request can be transmitted yet its response remain unreadable to script.

31. WHATWG (living standard), *URL Standard*. [URL Standard](https://url.spec.whatwg.org/). Browser URL parsing is a state machine designed for compatibility with deployed content and is not identical to a naive RFC 3986 parser. Security-sensitive comparison, origin calculation, IDNA handling, percent encoding, and relative resolution must use one explicit parser model end to end.

32. Ecma International, TC39 (living specification), *ECMAScript Language Specification*. [ECMA-262](https://tc39.es/ecma262/). The specification defines JavaScript values, objects, execution contexts, promises, modules, jobs, and language semantics. Its job-queue model is necessary for reasoning precisely about microtasks, asynchronous callbacks, rendering opportunities, error propagation, and browser application responsiveness.

33. W3C CSS Working Group (2021–), *CSS Cascading and Inheritance Level 5*. [W3C specification](https://www.w3.org/TR/css-cascade-5/). This module formalises origins, importance, layers, specificity, scoping, inheritance, and computed values. It replaces folklore about “the last rule wins” with the actual ordered cascade that governs maintainability and component isolation.

34. W3C Web Accessibility Initiative (2023), *Web Content Accessibility Guidelines (WCAG) 2.2*. [W3C Recommendation](https://www.w3.org/TR/WCAG22/). WCAG organises testable success criteria under perceivable, operable, understandable, and robust principles. Conformance is a floor for evaluation, not a substitute for semantic HTML, assistive-technology testing, representative users, or attention to complete task flows.

35. W3C Web Application Security Working Group (2025–), *Content Security Policy Level 3*. [W3C specification](https://www.w3.org/TR/CSP3/). CSP defines source lists, nonces, hashes, navigation and embedding restrictions, reporting, and enforcement algorithms. It is a defence-in-depth constraint on content execution and loading, not a repair for unsafe interpolation or a replacement for context-correct output handling.

36. W3C Web Applications Working Group (2026), *Service Workers*. [W3C specification](https://www.w3.org/TR/service-workers/). The event-driven worker and registration lifecycle enable programmable request interception, offline behaviour, and background events. The specification reveals why activation, update races, cache versioning, storage eviction, and stale clients require explicit compatibility and recovery design.

### 18.38.3 Relational data and transactions

37. Codd, E. F. (1970), ‘A Relational Model of Data for Large Shared Data Banks’, *Communications of the ACM*, 13(6), pp. 377–387. [ACM Digital Library](https://doi.org/10.1145/362384.362685). Codd separates logical relations from physical storage and develops normalisation around dependencies. The paper remains the conceptual antidote to treating a relational database as a collection of serialised objects.

38. Gray, J. and Reuter, A. (1992), *Transaction Processing: Concepts and Techniques*. San Mateo, CA: Morgan Kaufmann. [Publisher record](https://www.elsevier.com/books/transaction-processing/gray/978-1-55860-190-1). This comprehensive treatment connects transaction models, logging, recovery, locking, distributed commit, queues, performance, and operational failure. Its terminology remains foundational even where contemporary systems implement different algorithms.

39. Adya, A. (1999), *Weak Consistency: A Generalized Theory and Optimistic Implementations for Distributed Transactions*. PhD thesis, Massachusetts Institute of Technology. [MIT repository](https://hdl.handle.net/1721.1/9333). Adya supplies a dependency-graph account of isolation phenomena broader than the original ANSI anomaly list. It supports precise reasoning about what weaker isolation permits and which application invariants can consequently fail.

40. PostgreSQL Global Development Group (2026), *PostgreSQL 18: The SQL Language*. [PostgreSQL documentation](https://www.postgresql.org/docs/18/sql.html). The manual provides a concrete, production-grade account of SQL syntax, data types, queries, definition, manipulation, concurrency, performance, and extensions. Product-specific behaviour must be distinguished from both the relational model and portable SQL assumptions.

41. PostgreSQL Global Development Group (2026), ‘Transaction Isolation’, in *PostgreSQL 18 Documentation*. [PostgreSQL documentation](https://www.postgresql.org/docs/18/transaction-iso.html). The section states the visibility guarantees and anomalies of each implemented level, including serialisation failures. It directly motivates transaction-wide retry rather than retrying only the statement that happened to receive an error.

42. PostgreSQL Global Development Group (2026), ‘Constraints’, in *PostgreSQL 18 Documentation*. [PostgreSQL documentation](https://www.postgresql.org/docs/18/ddl-constraints.html). Primary, unique, foreign, check, not-null, exclusion, and generated constraints turn invariants into concurrency-safe database rules. Their treatment of nulls, references, actions, and deferral matters to both schema design and migration order.

43. PostgreSQL Global Development Group (2026), ‘Indexes’, in *PostgreSQL 18 Documentation*. [PostgreSQL documentation](https://www.postgresql.org/docs/18/indexes.html). The index chapters cover B-tree and specialised access methods, multicolumn order, partial and expression indexes, index-only scans, combination, and maintenance. An index is a measured access-path hypothesis with write and storage cost, not a generic performance flag.

44. PostgreSQL Global Development Group (2026), ‘Using `EXPLAIN`’, in *PostgreSQL 18 Documentation*. [PostgreSQL documentation](https://www.postgresql.org/docs/18/using-explain.html). Execution plans expose estimated and observed scans, joins, row counts, costs, buffers, and timing. Comparing estimates with `ANALYZE` evidence is the disciplined route from a slow request to statistics, query-shape, or indexing changes.

45. SQLAlchemy authors (2026), *SQLAlchemy 2.0 Documentation*. [SQLAlchemy documentation](https://docs.sqlalchemy.org/en/20/). The documentation makes explicit the separation among SQL expression construction, connection and transaction management, identity maps, unit-of-work persistence, relationships, and loading strategies. It is particularly valuable for detecting hidden queries and understanding that ORM object operations compile into relational work.

### 18.38.4 Architecture, interfaces, identity, and application security

46. Fielding, R. T. (2000), *Architectural Styles and the Design of Network-based Software Architectures*. PhD dissertation, University of California, Irvine. [Authoritative text](https://www.ics.uci.edu/~fielding/pubs/dissertation/top.htm). Chapters 5 and 6 define REST as a constraint-derived architectural style and evaluate the Web against it. The dissertation, not contemporary endpoint aesthetics, is the source for statelessness, uniform interface, cacheability, layering, and hypermedia.

47. OpenAPI Initiative (2026), *OpenAPI Specification 3.2.1*. [Authoritative specification](https://spec.openapis.org/oas/v3.2.1.html). OpenAPI describes HTTP interfaces, operations, parameters, representations, schemas, callbacks, webhooks, and security schemes in a language-neutral document. Generated code and documentation inherit every omission and ambiguity in that contract; schema validation alone cannot prove full conformance.

48. GraphQL Foundation (2025), *GraphQL Specification, September 2025 Edition*. [GraphQL specification](https://spec.graphql.org/September2025/). The specification defines documents, type systems, validation, variable and result coercion, execution, errors, introspection, and subscriptions. It deliberately does not solve transport, authorisation, query cost, batching, cache invalidation, or database access patterns for an application.

49. Hardt, D. (ed.) (2012), *The OAuth 2.0 Authorization Framework*, RFC 6749. [RFC Editor](https://www.rfc-editor.org/rfc/rfc6749). OAuth defines delegated authorisation roles, endpoints, grants, tokens, scope, and client classes. It does not make an access token an identity proof; security deployments must apply later best-current-practice updates and a profile appropriate to the client environment.

50. Jones, M. and Hardt, D. (2012), *The OAuth 2.0 Authorization Framework: Bearer Token Usage*, RFC 6750. [RFC Editor](https://www.rfc-editor.org/rfc/rfc6750). A bearer token grants authority to whoever possesses it, so transport, storage, audience, scope, expiry, leakage prevention, and logging discipline determine its safety. The specification defines request methods and error signalling, not an application’s authorisation model.

51. Sakimura, N. et al. (2015), *Proof Key for Code Exchange by OAuth Public Clients*, RFC 7636. [RFC Editor](https://www.rfc-editor.org/rfc/rfc7636). PKCE binds an intercepted authorisation code to a per-transaction verifier. Correctness depends on high-entropy verifiers, an approved transformation, exact transaction binding, and validation at the token endpoint; it does not replace redirect-URI checks or stateful request correlation.

52. Lodderstedt, T. et al. (2025), *Best Current Practice for OAuth 2.0 Security*, RFC 9700, BCP 240. [RFC Editor](https://www.rfc-editor.org/rfc/rfc9700). This consensus document updates the original OAuth threat guidance, deprecates unsafe modes, and addresses code injection, redirectors, mix-up, token replay, and sender constraint. Contemporary implementations should treat it as part of the baseline, not optional commentary.

53. Parecki, A. et al. (2026), *OAuth 2.0 for Browser-Based Applications*, RFC 10017. [RFC Editor](https://www.rfc-editor.org/rfc/rfc10017). The BCP analyses browser execution and storage threats and compares architectural patterns for public clients. Its recommendations refine the simplistic choice between storing tokens in a single-page application and placing every responsibility in an opaque backend.

54. Sakimura, N. et al. (2014, incorporating Errata Set 2), *OpenID Connect Core 1.0*. [OpenID Foundation](https://openid.net/specs/openid-connect-core-1_0.html). OpenID Connect adds authentication, ID tokens, claims, discovery relationships, nonce handling, and user-information exchange to OAuth. Secure relying parties must validate issuer, audience, signature, time claims, nonce, and flow-specific hashes rather than merely decode a JWT.

55. W3C Web Authentication Working Group (2026), *Web Authentication: An API for Accessing Public Key Credentials—Level 3*. [W3C Recommendation](https://www.w3.org/TR/webauthn-3/). WebAuthn binds public-key credentials to relying-party scope and authenticators, enabling phishing-resistant authentication. Server implementations must preserve challenge freshness, origin and RP-ID checks, credential ownership, signature counters or equivalent risk signals, and recovery policy.

56. Temoshok, D. et al. (2025), *Digital Identity Guidelines: Authentication and Authenticator Management*, NIST SP 800-63B-4. [NIST](https://doi.org/10.6028/NIST.SP.800-63B-4). The guideline defines authenticator assurance levels and requirements for passwords, cryptographic authenticators, phishing resistance, recovery, lifecycle, rate limiting, and reauthentication. Its risk-scoped requirements are more defensible than inherited password folklore.

57. OWASP Foundation (2025), *Application Security Verification Standard 5.0.0*. [OWASP ASVS](https://owasp.org/projects/asvs). ASVS is a versioned catalogue of testable technical security requirements organised by verification level. It can turn a threat model into acceptance evidence, provided requirement identifiers include the ASVS version and project-specific exclusions are documented rather than silently ignored.

58. OWASP Foundation (continuously maintained), *Authentication Cheat Sheet*. [OWASP Cheat Sheet Series](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html). This operational reference covers account identifiers, password handling, multifactor authentication, responses, reauthentication, adaptive controls, and protocol choices. It should be reconciled with NIST SP 800-63B-4 and the application’s concrete account-recovery and abuse model.

59. OWASP Foundation (continuously maintained), *Session Management Cheat Sheet*. [OWASP Cheat Sheet Series](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html). The guide treats entropy, cookie properties, identifier exchange, renewal, expiration, logout, fixation, concurrent sessions, storage, and monitoring as one lifecycle. This reinforces the chapter’s distinction between a secure cookie transport envelope and secure server-side session semantics.

60. OWASP Foundation (continuously maintained), *Cross Site Scripting Prevention Cheat Sheet*. [OWASP Cheat Sheet Series](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html). The guide maps output encoding to HTML, attribute, JavaScript, CSS, and URL contexts and distinguishes encoding from HTML sanitisation. Its central lesson is that one universal escaping function cannot be correct for every parser context.

61. OWASP Foundation (continuously maintained), *Cross-Site Request Forgery Prevention Cheat Sheet*. [OWASP Cheat Sheet Series](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html). Synchroniser tokens, signed double-submit patterns, origin evidence, SameSite cookies, and interaction requirements are compared with their limits. The guidance is relevant specifically where ambient credentials accompany attacker-triggerable requests.

62. OWASP Foundation (continuously maintained), *Server-Side Request Forgery Prevention Cheat Sheet*. [OWASP Cheat Sheet Series](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html). The document covers allowlists, scheme and address validation, DNS hazards, network controls, cloud metadata, and application-layer cases. Robust defences must bind validation to the actual destination across resolution and redirects rather than validate one spelling of a host.

63. OWASP Foundation (continuously maintained), *SQL Injection Prevention Cheat Sheet*. [OWASP Cheat Sheet Series](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html). Parameterised statements separate literal values from SQL grammar, while allowlisting is required for structural choices such as identifiers and order direction. Escaping and stored procedures are not automatically safe merely because they move string construction elsewhere.

64. OWASP Foundation (continuously maintained), *File Upload Cheat Sheet*. [OWASP Cheat Sheet Series](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html). File names, size, type, parser behaviour, archives, storage, retrieval authorisation, malware handling, and denial of service form one boundary. Content-Type and filename extensions are untrusted claims, while successful parsing can itself consume hostile resources.

65. OWASP Foundation (continuously maintained), *WebSocket Security Cheat Sheet*. [OWASP Cheat Sheet Series](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html). The guide extends ordinary web controls to long-lived bidirectional channels: handshake origin, session expiry, per-message authorisation, input validation, limits, logging, and shutdown. Connection establishment must not be mistaken for permanent authority over every later message.

### 18.38.5 Delivery, observability, and reliability

66. OpenTelemetry project (2026), *OpenTelemetry Specification 1.57.0*. [OpenTelemetry specification](https://opentelemetry.io/docs/specs/otel/). The cross-language specification defines traces, metrics, logs, resources, context propagation, sampling, SDK behaviour, and export. It supplies interoperable telemetry mechanics, while applications remain responsible for semantic conventions, cardinality budgets, privacy, retention, and meaningful service indicators.

67. W3C Distributed Tracing Working Group (2021), *Trace Context, Level 1*. [W3C Recommendation](https://www.w3.org/TR/trace-context/). `traceparent` and `tracestate` standardise trace identity and vendor state across process boundaries. Propagation permits correlation; it does not authenticate callers, make baggage trustworthy, guarantee sampling, or justify recording sensitive payloads.

68. Souppaya, M., Scarfone, K. and Dodson, D. (2022), *Secure Software Development Framework (SSDF) Version 1.1*, NIST SP 800-218. [NIST](https://doi.org/10.6028/NIST.SP.800-218). SSDF groups organisational preparation, software protection, secure production, and vulnerability response into outcome-oriented practices. It connects code-level controls to provenance, dependencies, build systems, release integrity, remediation, and evidence across the lifecycle.

69. Open Container Initiative (2025), *OCI Image Format Specification 1.1.1*. [OCI specification](https://specs.opencontainers.org/image-spec/?v=v1.1.1). The specification defines content-addressed descriptors, manifests, indexes, configurations, and filesystem layers for interoperable container images. Image format standardisation does not itself provide runtime confinement, minimal contents, provenance, signature policy, secret safety, or vulnerability management.

70. Beyer, B., Jones, C., Petoff, J. and Murphy, N. R. (eds) (2016), *Site Reliability Engineering: How Google Runs Production Systems*. Sebastopol, CA: O’Reilly. [Full text](https://sre.google/sre-book/table-of-contents/). The collection systematises service-level objectives, error budgets, monitoring, automation, capacity, overload, incident response, and eliminating toil. Its practices should be adapted to risk and scale rather than copied as organisational ritual.

71. Beyer, B., Murphy, N. R., Rensin, D. K., Kawahara, K. and Thorne, S. (eds) (2018), *The Site Reliability Workbook*. Sebastopol, CA: O’Reilly. [Full text](https://sre.google/workbook/table-of-contents/). Worked chapters translate SRE principles into SLO construction, burn-rate alerting, incident practice, canarying, configuration, and organisational adoption. The examples clarify the difference between collecting telemetry and operating from explicit reliability policy.

72. Dean, J. and Barroso, L. A. (2013), ‘The Tail at Scale’, *Communications of the ACM*, 56(2), pp. 74–80. [DOI](https://doi.org/10.1145/2408776.2408794). The paper explains how variable component latency becomes dominant in fan-out services and analyses hedging, tied requests, micro-partitioning, and load balancing. Tail mitigation must be weighed against extra work and correlated overload.

73. Yuan, D. et al. (2014), ‘Simple Testing Can Prevent Most Critical Failures: An Analysis of Production Failures in Distributed Data-Intensive Systems’, in *Proceedings of OSDI 2014*. [USENIX](https://www.usenix.org/conference/osdi14/technical-sessions/presentation/yuan). The empirical study traces severe failures to error-handling paths and shows the value of explicit fault injection and assertions. It supports testing adverse events as first-class behaviour rather than relying only on nominal-path coverage.

74. Kleppmann, M. (2017), *Designing Data-Intensive Applications*. Sebastopol, CA: O’Reilly. [Author’s book page](https://martin.kleppmann.com/2017/03/27/designing-data-intensive-applications.html). The synthesis connects storage engines, replication, partitioning, transactions, batch and stream processing, consistency, and derived data. It is a rigorous bridge from a single web service to distributed systems whose failures cannot be hidden behind a framework.

75. Wiggins, A. (2017 revision), *The Twelve-Factor App*. [Canonical text](https://12factor.net/). The concise methodology treats codebase, dependencies, configuration, backing services, build–release–run separation, stateless processes, port binding, concurrency, disposability, environment parity, logs, and administrative processes. Several principles require qualification for stateful, regulated, or highly distributed systems, which makes the text useful for critical comparison rather than dogma.
