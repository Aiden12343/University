## Introduction

In [[1.1 Counting and Number Sense]] through [[1.12 Ratio Proportion and Units]], you learned to count, add, subtract, multiply, divide, use fractions and decimals, work with percentages and ratios, and handle negative numbers. This topic brings all of those skills together — not to learn new operations, but to check that your answers make sense.

Estimation and error checking help you decide whether an answer is reasonable.

You do not estimate because exact answers are unimportant. You estimate because **exact-looking answers can still be wrong**.

```text
398 + 602
```

Estimate: `400 + 600 = 1000`. So if your exact answer is `10,000`, you know something went wrong.

This topic introduces:
- [[rounding]] — replacing a number with a nearby simpler number
- [[upper and lower estimates]] — rough values above and below the true answer
- [[mental checks]] — quick reasoning checks without full written calculation
- [[inverse checks]] — using the opposite operation to check a calculation
- [[units checks]] — checking that the answer has the correct unit and scale

> [!example] Everyday idea
> If you calculate a restaurant tip and the total is larger than the entire meal, you know you made a mistake — even without recalculating.

## Breadcrumbs

### Breadcrumb 1: Estimation Before Exact Calculation

**Builds on:** [[1.6 Breadcrumb 6|Comparing Fractions]] (compare estimate to exact), [[1.7 Breadcrumb 6|Finding a Percentage of an Amount]] (estimating percentages)

An estimate is a close, simple answer.

Question:

```text
49 x 21
```

Estimate:

```text
50 x 20 = 1000
```

So the exact answer should be near 1000.

Exact:

```text
49 x 21 = 1029
```

That is reasonable.

> [!important] Estimate first
> If you estimate after seeing your answer, you may accidentally force the estimate to fit. Estimate before exact calculation.

---

### Breadcrumb 2: Rounding

**Builds on:** [[1.2 Breadcrumb 6|Rounding to Landmarks]] (rounding to the nearest 10, 100, 1000), [[1.13 Breadcrumb 1|Estimation Before Exact Calculation]] (rounding makes estimation practical)

[[rounding]] makes numbers easier to work with.

Examples:

```text
398 rounds to 400
61 rounds to 60
19.8 rounds to 20
```

Rounding is useful when you want an approximate size.

#### Chunked Example
Question: Estimate `198 + 403`.

Step 1: Round each number.

```text
198 -> 200
403 -> 400
```

Step 2: Add rounded numbers.

```text
200 + 400 = 600
```

Answer: The estimate is **about 600**.

---

### Breadcrumb 3: Upper and Lower Estimates

**Builds on:** [[1.13 Breadcrumb 2|Rounding]] (rounding both up and down gives a range)

[[upper and lower estimates]] give a range.

Example:

```text
48 x 31
```

Lower estimate:

```text
40 x 30 = 1200
```

Upper estimate:

```text
50 x 40 = 2000
```

The true answer should be between 1200 and 2000.

Exact:

```text
48 x 31 = 1488
```

This fits the range.

> [!note] Bounds can be rough
> Early in the course, upper and lower estimates do not need to be perfect. They need to catch answers that are wildly impossible.

### Breadcrumb 4: Mental Checks

**Builds on:** [[1.3 Breadcrumb 3|Subtraction as Difference]] (mental checks use the meaning of operations), [[1.1 Breadcrumb 4|Bigger, Smaller, and Equal]] (direction of change)

[[mental checks]] are quick checks that use common sense and simple maths.

Examples:

- Adding positive numbers should make the result larger.
- Subtracting a positive number should make the result smaller.
- Multiplying by a number greater than 1 should increase a positive amount.
- Dividing by a number greater than 1 should reduce a positive amount.
- A percentage over 100% should be more than the whole.
- A percentage under 100% should be less than the whole.

#### Chunked Example
Question: A learner says `75% of 80 = 120`. Is that reasonable?

Step 1: 75% is less than 100%.

Step 2: 75% of 80 must be less than 80.

Step 3: 120 is greater than 80.

Answer: The answer is not reasonable.

---

### Breadcrumb 5: Inverse Checks

**Builds on:** [[1.3 Breadcrumb 10|Checking with Inverse Operations]] (addition/subtraction check each other), [[1.5 Breadcrumb 5|Checking Division with Multiplication]] (multiplication/division check each other)

[[inverse checks]] use opposite operations.

Addition and subtraction check each other.

```text
47 + 28 = 75
75 - 28 = 47
```

Multiplication and division check each other.

```text
8 x 7 = 56
56 / 7 = 8
```

Fractions can also be checked by reversing the operation or using equivalent forms.

#### Chunked Example
Question: Check `91 - 37 = 54`.

Step 1: Use addition to reverse subtraction.

```text
54 + 37
```

Step 2: Calculate.

```text
54 + 37 = 91
```

Answer: The check works, so the subtraction is likely correct.

---

### Breadcrumb 6: Units Checks

**Builds on:** [[1.12 Breadcrumb 8|Units in Computer Science]] (units carry meaning), [[1.12 Breadcrumb 5|Unit Rates]] (rate answers must include "per [unit]")

[[units checks]] ask whether the answer uses the correct unit.

Example:

Question: A server handles 600 requests in 10 seconds. What is the rate?

Correct setup:

```text
600 requests / 10 seconds = 60 requests/second
```

The answer is not just:

```text
60
```

It is:

```text
60 requests/second
```

> [!warning] Unit mismatch
> You cannot fairly compare `60 requests/second` with `300 requests/minute` until the units match.

---

### Breadcrumb 7: Magnitude Checks

**Builds on:** [[1.2 Breadcrumb 4|Comparing Large Numbers]] (magnitude means digit count), [[1.13 Breadcrumb 2|Rounding]] (estimate size by rounding)

Magnitude means rough size.

Example:

```text
997 x 102
```

Estimate:

```text
1000 x 100 = 100,000
```

So the answer should have about six digits.

If a calculator or program gives:

```text
10,169,400
```

something is probably wrong because the magnitude is too large.

---

### Breadcrumb 8: Error Checking in Programs

**Builds on:** [[1.13 Breadcrumb 5|Inverse Checks]] (inverse operations catch formula errors), [[1.13 Breadcrumb 6|Units Checks]] (unit bugs are common in code)

Programs can produce wrong numerical output because of:

- wrong formula
- wrong units
- off-by-one counting
- integer division
- rounding too early
- decimal precision
- swapped numerator and denominator
- using milliseconds where seconds were expected

> [!example] CS connection
> If a program reports a download speed of 8000 MB/s on a normal home connection, a unit conversion bug may have confused megabits and megabytes or seconds and milliseconds.

---

### Breadcrumb 9: A Practical Checking Routine

**Builds on:** [[1.13 Breadcrumb 1]] through [[1.13 Breadcrumb 8]] (combine all checks into one workflow)

Use this routine for every serious calculation:

1. Name the quantity you are finding.
2. Write the units.
3. Estimate the rough size.
4. Calculate exactly.
5. Check with an inverse operation if possible.
6. Check units.
7. Ask whether the magnitude is reasonable.

This is the arithmetic version of debugging.

---

## Why This Works

Errors often change the size, direction, or unit of an answer.

Estimation catches size errors.

Inverse checks catch operation errors.

Unit checks catch meaning errors.

Together, they stop mistakes from spreading into later algebra, statistics, algorithms, and code.

## Worked Examples

For fully worked solutions, use [[1.13 Estimation and Error Checking - Worked Examples]].

### Example 1 — Estimate

Question: Estimate `302 + 699` and check whether the exact answer is reasonable.

Step 1: Round each number to the nearest hundred.

```text
302 -> 300
699 -> 700
```

Step 2: Add the rounded numbers.

```text
300 + 700 = 1000
```

Step 3: Calculate exactly.

```text
302 + 699 = 1001
```

Answer: **The estimate is 1000; the exact answer 1001 is close, so it is reasonable**.

### Example 2 — Inverse Check

Question: Check whether `63 - 28 = 35` is correct using an inverse operation.

Step 1: Use addition to reverse the subtraction.

```text
35 + 28
```

Step 2: Calculate.

```text
35 + 28 = 63
```

Answer: **The check works, so the calculation is correct**.

### Example 3 — Unit Check

Question: A program processes 1200 records in 20 seconds. State the rate with its correct unit.

Step 1: Divide the quantity by the time.

```text
1200 / 20 = 60
```

Step 2: Attach the correct unit.

```text
60 records/second
```

Answer: **60 records/second**.

## Common Mistakes

- Treating estimation as a replacement for exact calculation.
- Rounding too aggressively and losing the meaning.
- Estimating only after calculating.
- Ignoring units.
- Checking with the same mistaken operation instead of the inverse.
- Accepting calculator or program output without a reasonableness check.
- Comparing rates with different units.

## Where This Shows Up in CS

Estimation and error checking appear in:

- debugging numerical code
- checking benchmark results
- validating API outputs
- interpreting logs
- checking memory and storage calculations
- spotting unit conversion bugs
- numerical methods
- floating-point error analysis
- machine learning metrics

Example:

```text
records = 120000
time = 2 seconds
rate = 60000 records/second
```

If a program instead reports:

```text
60 records/second
```

you should suspect a units or division error.
