## Introduction

**Type theory** studies the classification of values and expressions in programming languages. From [[5.5 Propositional Logic]], you understand logical propositions and implications. From [[5.9 Predicate Logic]], you understand quantifiers. From [[5.10 Proof Techniques]], you know how to construct proofs.

The **Curry-Howard correspondence** reveals a deep connection: types correspond to logical propositions, and programs correspond to proofs.

```
Proposition      →  Type
Proof            →  Program
Implication P→Q  →  Function type P→Q
Conjunction P∧Q  →  Product type P×Q (pair)
Disjunction P∨Q  →  Sum type P+Q (either)
True             →  Unit type ()
False            →  Empty type ⊥
```

This means: if a program type-checks, it is a correct proof. A well-typed program cannot "go wrong" at runtime (for a sound type system). This is why types catch bugs before the program runs.

## New Words

- **[[type system]]** — set of rules assigning types to program expressions to prevent runtime errors.
- **[[Curry-Howard correspondence]]** — types are propositions, programs are proofs.
- **[[simply typed lambda calculus]]** — core language with functions (→), variables, and base types.
- **[[polymorphism]]** — ability to write code that works with multiple types (parametric: List<T>, ad-hoc: overloading).
- **[[type inference]]** — compiler automatically deducing types (Hindley-Milner in ML, Haskell, Rust).

## Breadcrumbs

### Breadcrumb 1: Simply Typed Lambda Calculus

**Builds on:** [[5.5 Propositional Logic]] (implication, variables)

The **lambda calculus** is the mathematical foundation of functional programming. Terms:
- Variable: x
- Abstraction: λx:T.e (function: takes x of type T, returns expression e).
- Application: e₁ e₂ (apply function e₁ to argument e₂).

Types:
- T → U: function from type T to type U.
- Base types: Int, Bool, etc.

#### Chunked Example

Question: What is the type of λx:Int. x+1?

Step 1: Parameter x has type Int. The body x+1 returns Int.

Step 2: The function takes Int and returns Int.

Step 3: Type: Int → Int.

Answer: **Type: Int → Int**.

#### Chunked Example

Question: What is the type of λf:Bool→Int. λx:Bool. f(x)?

Step 1: f has type Bool → Int. x has type Bool. f(x) has type Int.

Step 2: The inner λx function has type Bool → Int. The outer λf has type (Bool→Int) → (Bool→Int).

Answer: **Type: (Bool→Int) → (Bool→Int)**.

### Breadcrumb 2: Curry-Howard Correspondence

**Builds on:** Breadcrumb 1, [[5.5 Propositional Logic]] (connectives)

The correspondence maps logical connectives to type constructors. A proof of P→Q is a function that takes a proof of P and returns a proof of Q.

#### Chunked Example

Question: What type corresponds to "if P then Q"? What is a proof of P→Q?

Step 1: Implication P→Q corresponds to function type P→Q.

Step 2: A proof of P→Q is a function that, given a proof of P, produces a proof of Q.

```haskell
-- In Haskell: f :: P -> Q  means f is a proof that P implies Q
```

Answer: **Function type P→Q. Proof = function from P to Q**.

### Breadcrumb 3: Algebraic Data Types — Sums and Products

**Builds on:** Breadcrumb 2

Product types (pairs, records) correspond to logical AND. Sum types (tagged unions, Either) correspond to logical OR.

**Product** (P∧Q): a value of type P×Q contains BOTH a P and a Q.
**Sum** (P+Q): a value of type P+Q contains EITHER a P or a Q (tagged with which).

#### Chunked Example — Maybe/Option Type

Question: What does Haskell's `Maybe a` type represent logically?

Step 1: `data Maybe a = Nothing | Just a` means Maybe a = () + a (Unit + a = True ∨ a).

Step 2: Nothing represents failure or absence (logically: True). Just a represents success with a value.

```haskell
safeDiv :: Int -> Int -> Maybe Int
safeDiv _ 0 = Nothing  -- division by zero → failure
safeDiv x y = Just (x `div` y)  -- success
```

Step 3: The type system forces you to handle both cases — no null pointer exceptions.

Answer: **Maybe a = () + a (Unit + a). Sum type eliminating null by forcing both cases**.

### Breadcrumb 4: Type Inference

**Builds on:** Breadcrumb 1

**Type inference** lets the compiler deduce the type of every expression without explicit annotations. The Hindley-Milner algorithm (used in ML, Haskell, Rust) is the most common.

#### Chunked Example

Question: What type does Haskell infer for `f x = x + 1`?

Step 1: (+) has type Num a ⇒ a → a → a (for any numeric type a).

Step 2: x must be Num a. The + operator applied to x and 1 returns the same type.

Step 3: Inferred type: f :: Num a ⇒ a → a (works for any numeric type — polymorphic).

Answer: **f :: Num a ⇒ a → a** (polymorphic over numeric types).

## Worked Examples

### Example 1 — Function Composition Types

Question: f: A → B, g: B → C. What is the type of g ∘ f (compose g after f)?

Step 1: g ∘ f = λx:A. g(f(x)).

Step 2: x:A, f(x):B, g(f(x)):C.

Step 3: The composition takes A and returns C.

Answer: **Type: A → C**.

### Example 2 — Type of a Lambda Expression with Pairs

Question: What is the type of λx:Int. λy:Bool. (x, y) in the simply typed lambda calculus?

Step 1: x has type Int. y has type Bool. The pair (x, y) has product type Int × Bool.

Step 2: The inner function λy:Bool. (x, y) takes Bool and returns Int × Bool. Its type: Bool → (Int × Bool).

Step 3: The outer function λx:Int. ... takes Int and returns (Bool → (Int × Bool)).

Answer: **Int → Bool → (Int × Bool)**.

### Example 3 — Curry-Howard: Finding a Proof Term

Question: Under the Curry-Howard correspondence, give a λ-term that is a proof of the proposition A → (B → A). Explain how the term corresponds to a proof.

Step 1: A → (B → A) means: given a proof of A, return a function that, given a proof of B, returns a proof of A.

Step 2: The λ-term λx:A. λy:B. x satisfies this: x is a proof of A, y is a proof of B, and the body x returns the proof of A, discarding y.

Step 3: This corresponds to the logical tautology "if A is true, then B implies A" — which is always true regardless of B.

Step 4: In combinatory logic, this term is the K combinator, a foundational building block.

Answer: **λx:A. λy:B. x (the K combinator)**.

### Example 4 — Haskell Type Inference

Question: What type does Haskell infer for the function f defined as `f g x y = g (x y)`? Show your reasoning.

Step 1: x y means x is applied to y, so x must be a function type a → b and y : a. Then x y : b.

Step 2: g (x y) means g is applied to the result of x y, so g must be a function type b → c. Then g (x y) : c.

Step 3: f takes three arguments g, x, y and produces result c. So f :: (b → c) → (a → b) → a → c.

Step 4: This is the type of function composition (though the arguments are in a different order than the standard . operator).

Answer: **f :: (b → c) → (a → b) → a → c**.

## Why This Works

The Curry-Howard correspondence shows that type checking and proof checking are the same thing. A type system is a theorem prover: it verifies that your program satisfies its specification (as encoded in types).

This is not coincidental. The simply typed lambda calculus was designed as a system for constructing functions. Church's original formulation of the lambda calculus was an attempt to formalise logic. The types-as-propositions connection was discovered by Curry (1934) and extended by Howard (1969).

A practical consequence: in a language like Rust or Haskell, if your program compiles, certain entire classes of bugs (type errors, memory errors, null pointer dereferences) are provably absent.

## Common Mistakes

> [!failure] Mistake pattern: Confusing static and dynamic typing
> Static: types checked at compile time (Java, Rust, Haskell). Dynamic: types checked at runtime (Python, JS). Static catches more errors early.

> [!failure] Mistake pattern: Thinking more types = more safety
> Very strict type systems (dependent types) can prove complex properties but are harder to use. There is a trade-off between expressiveness and usability.

> [!failure] Mistake pattern: Ignoring type inference
> Languages like Haskell and Rust infer most types — you only annotate function signatures. The compiler checks consistency for free.

## Where This Shows Up in CS

### Practical Type Systems
```text
- Haskell: full Hindley-Milner type inference, algebraic data types, type classes
- Rust: ownership types, trait system, lifetime inference
- TypeScript: gradual typing on top of JavaScript
- Java/C#: nominal typing, generics, interfaces
- Python: optional type hints (mypy checks them)
```

### Verification
```text
- Formal verification: Coq, Lean — types encode full program specifications
- Correct by construction: well-typed programs satisfy their specification
- Smart contracts: formal verification prevents exploits
```

### Language Design
```text
- Algebraic effects: typed effect handlers
- Dependent types: types depend on values (Idris, Agda)
- Linear types: resources used exactly once (Rust borrows are a form)
```
