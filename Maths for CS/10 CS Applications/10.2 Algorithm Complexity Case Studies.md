## Introduction

From [[10.1 Big O Theta and Omega]], you know what O, Ω, and Θ mean. Now we apply them to real algorithms and data structures.

The core skill: look at code (or a description of an algorithm), count how many times each line executes as a function of input size n, and simplify to the dominant term.

This analysis is not theoretical — it predicts whether your program finishes in milliseconds or hours. A naive O(n²) algorithm on a million inputs takes ~10¹² operations (~17 minutes at 1 GHz). An O(n log n) algorithm takes ~20 million operations (~0.02 seconds). The same task, two different algorithms, a 50,000× difference.

## New Words

- **[[worst-case complexity]]** — maximum steps over all inputs of size n.
- **[[average-case complexity]]** — expected steps over all inputs of size n (requires probabilistic assumptions).
- **[[amortised analysis]]** — averaging cost over a sequence of operations, giving per-operation bound.
- **[[space complexity]]** — memory used as a function of input size.
- **[[NP-complete]]** — class of problems where no polynomial-time algorithm is known, and all NP-complete problems reduce to each other.

> [!important] You pass this topic only when you can define all five terms without looking.

## Breadcrumbs

### Breadcrumb 1: Constant Time O(1) and Logarithmic Time O(log n)

**Builds on:** [[10.1 Big O Theta and Omega]] (growth rates, Big O definition)

**O(1)**: Time does not depend on input size. Examples: array indexing, hash table lookup (average case), arithmetic operations.

Why is arr[i] O(1)? Array elements are stored contiguously. The address is computed as: base_address + i × element_size. This is a single arithmetic operation regardless of array length.

**O(log n)**: Time grows logarithmically. Doubling n adds a constant amount of work. Examples: binary search, balanced BST operations, heap insert/extract.

#### Chunked Example — Binary Search Comparison Count

Question: Binary search on a sorted array of n = 1024 elements. How many comparisons in the worst case?

Step 1: Each comparison halves the search range. Range sizes: 1024 → 512 → 256 → 128 → 64 → 32 → 16 → 8 → 4 → 2 → 1.

Step 2: The number of halvings to reach 1 is log₂(1024) = 10.

Step 3: Each halving requires one comparison. Worst case: 10 comparisons + 1 final check = 11.

Answer: **≤ 11 comparisons for n=1024**.

### Breadcrumb 2: Linear Time O(n) and Linearithmic Time O(n log n)

**Builds on:** Breadcrumb 1

**O(n)**: Time grows linearly with input size. Examples: scanning a list, finding the max, linear search.

**O(n log n)**: Faster than quadratic, slower than linear. Examples: merge sort, heapsort, quick sort (average case).

#### Chunked Example — Counting Operations in a Loop

Question: What is the runtime of this code?

```python
total = 0
for i in range(n):
    total += arr[i]
```

Step 1: The loop runs n times. Each iteration does O(1) work (one addition, one array access).

Step 2: Total: n × O(1) = O(n).

Answer: **O(n)**.

### Breadcrumb 3: Quadratic and Cubic Time — O(n²) and O(n³)

**Builds on:** Breadcrumb 2

**O(n²)**: Nested loops where each runs n times. Examples: bubble sort, insertion sort worst case, naive matrix addition.

#### Chunked Example — Nested Loop Analysis

Question: What is the runtime of bubble sort on an array of n elements?

```python
for i in range(n):
    for j in range(n-1-i):
        if arr[j] > arr[j+1]:
            arr[j], arr[j+1] = arr[j+1], arr[j]
```

Step 1: Outer loop: n iterations. Inner loop: n-1-i iterations.

Step 2: Total comparisons = (n-1) + (n-2) + ... + 1 + 0 = n(n-1)/2.

Step 3: n(n-1)/2 = (n²-n)/2. Dominant term: n²/2. After dropping constants: O(n²).

Answer: **O(n²) worst case**.

### Breadcrumb 4: Exponential O(2ⁿ) and Factorial O(n!) — The Intractable Zone

**Builds on:** [[6.1 Combinatorics Basics]] (factorials, power sets)

**O(2ⁿ)**: Time doubles with each additional input element. Examples: subset generation, naive Fibonacci.

**O(n!)**: Worst of all common growth rates. Example: generating all permutations, travelling salesman (naive).

#### Chunked Example — Why O(2ⁿ) Is Intractable

Question: n=50. An O(2ⁿ) algorithm runs at 10⁹ ops/sec. How long?

Step 1: 2⁵⁰ ≈ 1.13×10¹⁵ operations.

Step 2: At 10⁹ ops/sec: 1.13×10¹⁵ / 10⁹ = 1.13×10⁶ seconds.

Step 3: 1.13×10⁶ seconds / (86400 sec/day) ≈ 13 days.

Step 4: For n=60: 2⁶⁰ ≈ 1.15×10¹⁸ → 1.15×10⁹ seconds ≈ 36 years.

Answer: **n=50: ~13 days. n=60: ~36 years. Adding 10 inputs makes it 1000× slower**.

### Breadcrumb 5: Amortised Analysis — The Average Over Many Operations

**Builds on:** Breadcrumb 1

Amortised analysis bounds the average cost per operation over a sequence, even if individual operations are expensive.

#### Chunked Example — Dynamic Array (e.g., Python list)

Question: Python list append is O(1) amortised. How?

Step 1: Start with capacity = 1. When full, allocate 2× capacity and copy all elements.

Step 2: For n insertions: copying costs 1 + 2 + 4 + ... + n/2 = n-1 total elements copied.

Step 3: Total cost for n inserts = n (insertions) + (n-1) (copies) = 2n-1.

Step 4: Amortised per insert: (2n-1)/n ≈ 2 = O(1).

Answer: **Amortised O(1): occasional O(n) resize, averaged over all inserts**.

## Sorting Algorithm Comparison

| Algorithm | Best | Average | Worst | Space | Stable |
|---|---|---|---|---|---|
| Insertion | O(n) | O(n²) | O(n²) | O(1) | Yes |
| Merge | O(n log n) | O(n log n) | O(n log n) | O(n) | Yes |
| Quick | O(n log n) | O(n log n) | O(n²) | O(log n) | No |
| Heap | O(n log n) | O(n log n) | O(n log n) | O(1) | No |

#### Chunked Example — Why Quick Sort Is Used Despite O(n²) Worst Case

Question: Quick sort worst case O(n²) but used in practice. Why?

Step 1: Worst case occurs only when pivot is always min/max element (sorted or reverse-sorted input with bad pivot choice).

Step 2: Random pivot makes worst-case probability ≈ 2/n! — essentially zero.

Step 3: Average case O(n log n) with low constant factors, in-place O(log n) space.

Answer: **Low constants + O(log n) space + extremely unlikely worst case**.

## Worked Examples

### Example 1 — Recurrence for Fibonacci

Question: Compute T(n) for naive recursive Fibonacci: F(n) = F(n-1) + F(n-2).

Step 1: T(n) = T(n-1) + T(n-2) + 1. This is the same recurrence as Fibonacci itself.

Step 2: This recurrence solves to T(n) = O(2ⁿ) — exponential.

Step 3: With memoisation: each F(k) computed once → T(n) = O(n) — linear.

```python
# Naive: O(2ⁿ)
def fib(n):
    if n <= 1: return n
    return fib(n-1) + fib(n-2)

# Memoised: O(n)
def fib_memo(n, memo={}):
    if n in memo: return memo[n]
    if n <= 1: return n
    memo[n] = fib_memo(n-1, memo) + fib_memo(n-2, memo)
    return memo[n]
```

Answer: **Naive: O(2ⁿ). Memoised: O(n).**

### Example 2 — Space Complexity of Recursion

Question: Recursive binary search on n elements. Space complexity?

Step 1: Each recursive call uses a stack frame (return address, parameters, local variables).

Step 2: Recursion depth = O(log n) (each call halves the range).

Step 3: Space = O(log n) (not counting the input array).

Step 4: Iterative version: O(1) space (no recursion, no stack frames).

Answer: **Recursive binary search: O(log n) stack space. Iterative: O(1).**

### Example 3 — Quickselect (Median Finding)

Question: Find kth smallest element in O(n) average time.

Step 1: Partition the array (like quick sort), placing the pivot element in its correct position.

Step 2: The pivot's index tells you if the kth element is to the left, right, or at the pivot.

Step 3: Recurse on only one side — not both.

Step 4: T(n) = T(n/2) + O(n) → T(n) = O(n) average case.

```python
def quickselect(arr, k, lo=0, hi=None):
    if hi is None: hi = len(arr)-1
    pivot = partition(arr, lo, hi)
    if k == pivot: return arr[pivot]
    elif k < pivot: return quickselect(arr, k, lo, pivot-1)
    else: return quickselect(arr, k, pivot+1, hi)
```

Answer: **Quickselect: O(n) average, O(n²) worst case**.

### Example 4 — CS Application: Database Join Analysis

Question: Why do databases use hash joins instead of nested loop joins?

Step 1: Nested loop join: for each row in table A, scan table B. If |A|=m, |B|=n: O(m×n).

Step 2: Hash join: build hash table on smaller table (O(m)), then probe with larger table rows (O(n)). Total: O(m+n) average.

Step 3: For m=10⁶, n=10⁶: O(n²) ≈ 10¹² (hours). O(m+n) ≈ 2×10⁶ (milliseconds).

Answer: **Hash join: O(m+n) vs nested loop: O(m×n). 10⁶× speedup for equal-sized tables**.

## Why This Works

Counting operations as a function of input size gives a machine-independent measure of efficiency. By focusing on the dominant term, we filter out hardware differences (CPU speed, memory latency) and language overhead.

Amortised analysis is important because it captures the true cost of data structures where occasional operations are expensive but rare. Without amortised analysis, a dynamic array would appear to have O(n) append (because of the occasional resize). With amortised analysis, we see the true O(1) average cost.

## Common Mistakes

> [!failure] Mistake pattern: Confusing average-case with worst-case
> Quick sort has O(n²) worst case but O(n log n) average. Never claim quick sort is O(n log n) without qualifying "average case."

> [!failure] Mistake pattern: Forgetting space complexity
> Many algorithms trade space for time (memoisation, hash tables, Bloom filters). Always consider both.

> [!failure] Mistake pattern: Assuming O(1) means fast
> O(1) with huge constant (e.g., 10⁹ ops) is worse than O(n) with small constant (n=100: 100 ops). Constants matter at small n.

> [!failure] Mistake pattern: Overlooking the recursive stack space
> A function that calls itself recursively uses O(depth) stack space. The iterative version may use O(1).

### Database Query Optimisation
```text
- Sequential scan: O(n)
- Indexed lookup: O(log n)
- Join types: O(n²) naive, O(n log n) hash/merge join
- Query planner chooses based on complexity estimates
```

### Operating Systems — Scheduler Analysis
```text
- Round-robin: O(1) per context switch
- O(n) scheduler degrades with many processes
- Linux CFS: O(log n) using red-black tree
```

### Networking — Routing Algorithm Complexity
```text
- OSPF: Dijkstra O(E log V)
- BGP: path-vector, complexity depends on path count
- SDN: centralised controller updates flow tables
```
