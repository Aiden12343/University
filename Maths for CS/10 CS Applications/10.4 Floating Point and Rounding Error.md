## Introduction

Computers cannot represent most real numbers exactly. Just as 1/3 = 0.33333... cannot be written exactly in decimal, 0.1 cannot be written exactly in binary — it is a repeating fraction.

**Floating point** stores: (-1)^s × mantissa × 2^exponent. This is like scientific notation (1.23×10⁴) but in binary.

From [[10.3 Binary Hexadecimal and Number Bases]], you know about binary representation. Floating point extends this to real numbers, trading exactness for range — double precision can represent values from ≈10⁻³⁰⁸ to ≈10³⁰⁸, but with only about 15-17 significant decimal digits.

This has practical consequences:
- 0.1 + 0.2 ≠ 0.3 (error ≈ 4.4×10⁻¹⁶).
- Associativity fails: (a+b)+c ≠ a+(b+c) in general.
- Large + small = large (the small number gets lost).
- Subtracting nearly equal numbers loses precision catastrophically.

## New Words

- **[[floating point]]** — representation: (-1)^s × m × 2^e, where s = sign, m = mantissa (significand), e = exponent.
- **[[IEEE 754]]** — standard for floating point arithmetic (single: 32-bit, double: 64-bit).
- **[[rounding error]]** — difference between exact value and floating point representation.
- **[[catastrophic cancellation]]** — loss of precision when subtracting nearly equal numbers.
- **[[machine epsilon]]** — upper bound on relative rounding error (≈2⁻²³ for single, ≈2⁻⁵² for double).

> [!important] You pass this topic only when you can define all five terms without looking.

## Breadcrumbs

### Breadcrumb 1: IEEE 754 Structure

**Builds on:** [[10.3 Binary Hexadecimal and Number Bases]] (binary representation, bits)

**Double precision (64-bit)**:
- 1 sign bit (bit 63).
- 11 exponent bits (bits 52-62), biased by 1023.
- 52 mantissa bits (bits 0-51). An implicit leading 1 gives 53 bits of precision.

```
Value = (-1)^s × (1.mantissa) × 2^(exponent - 1023)
```

**Single precision (32-bit)**:
- 1 sign + 8 exponent + 23 mantissa → about 7 decimal digits.

#### Chunked Example — Machine Epsilon

Question: What is machine epsilon for double precision?

Step 1: Mantissa has 52 bits (plus implicit 1). Epsilon is the smallest value such that 1+ε ≠ 1.

Step 2: Since only 52 bits of mantissa: ε ≈ 2⁻⁵².

Step 3: 2⁻⁵² ≈ 2.22×10⁻¹⁶. This is the relative error per operation.

Answer: **ε_double ≈ 2⁻⁵² ≈ 2.22×10⁻¹⁶**.

### Breadcrumb 2: Rounding Error — Why 0.1 + 0.2 ≠ 0.3

**Builds on:** Breadcrumb 1

#### Chunked Example

Question: Compute 0.1 + 0.2 in double precision. Why is it not exactly 0.3?

Step 1: 0.1₁₀ in binary: 0.000110011001100110011...₂ (repeating — like 1/3 in decimal).

Step 2: IEEE 754 can only store 53 bits of mantissa. The repeating pattern is truncated/rounded.

Step 3: 0.2 is also not exact (it is 2×0.1, same repeating pattern).

Step 4: Adding two approximations and rounding: 0.1+0.2 ≈ 0.30000000000000004.

Step 5: Error: |0.30000000000000004 - 0.3| ≈ 4.4×10⁻¹⁶ ≈ 2×ε.

Answer: **0.1+0.2 = 0.30000000000000004 (rounding error ≈ 4.4×10⁻¹⁶)**.

### Breadcrumb 3: Catastrophic Cancellation

**Builds on:** Breadcrumb 2

When you subtract two nearly equal numbers, the result has far fewer significant digits because the leading digits cancel. If both numbers are accurate to 15 digits but they agree on the first 12, the result only has 3 significant digits.

#### Chunked Example

Question: Compute √(x+1) - √x for x = 10¹⁵. Compare direct vs rearranged.

Step 1: Direct: √(10¹⁵+1) - √(10¹⁵). Both square roots are ≈ 3.16227766×10⁷, differing only in the last few digits.

Step 2: Subtracting loses ~8 digits of precision. Result is inaccurate.

Step 3: Rearranged: multiply numerator and denominator by (√(x+1)+√(x)):
```
√(x+1)-√x = (x+1-x)/(√(x+1)+√x) = 1/(√(x+1)+√x)
```

Step 4: ≈ 1/(2×3.16227766×10⁷) ≈ 1.581×10⁻⁸ (much more accurate).

Answer: **Use 1/(√(x+1)+√x) instead of direct subtraction to avoid catastrophic cancellation**.

### Breadcrumb 4: Associativity and Distributivity Fail

**Builds on:** Breadcrumb 2

Floating point arithmetic does NOT satisfy:
- Associativity: (a+b)+c ≠ a+(b+c).
- Distributivity: a(b+c) ≠ ab+ac.

#### Chunked Example

Question: In double precision, compare (a+b)+c vs a+(b+c) where a=10³⁰, b=-10³⁰, c=1.

Step 1: (a+b)+c = (10³⁰-10³⁰)+1 = 0+1 = 1. ✓ Correct.

Step 2: a+(b+c) = 10³⁰+(-10³⁰+1). But -10³⁰+1 ≈ -10³⁰ (1 is too small to add — it disappears due to the limited mantissa).

Step 3: 10³⁰+(-10³⁰) = 0. ✗ Wrong! The answer should be 1.

Answer: **Floating point addition is NOT associative: (a+b)+c = 1, a+(b+c) = 0**.

## Worked Examples

### Example 1 — Kahan Summation

Question: Summing 10⁷ numbers each ≈ 1. How much error for naive sum? How does Kahan summation help?

Step 1: Naive: sum ≈ n+O(nε). For n=10⁷, ε≈2×10⁻¹⁶: error ≈ 10⁷×2×10⁻¹⁶ = 2×10⁻⁹.

Step 2: Kahan summation: tracks a running compensation term. Error ≈ O(ε) + O(nε²) ≈ 2×10⁻¹⁶.

```python
def kahan_sum(values):
    s = 0.0  # running sum
    c = 0.0  # compensation
    for v in values:
        y = v - c
        t = s + y
        c = (t - s) - y  # algebraically zero, but captures rounding
        s = t
    return s
```

Answer: **Naive: error ≈ 2×10⁻⁹. Kahan: error ≈ 2×10⁻¹⁶ (essentially exact).**

### Example 2 — ML Loss NaN from Exploding Gradients

Question: Why might loss become NaN during neural network training? How to prevent it?

Step 1: Double precision max ≈ 1.8×10³⁰⁸. If gradient elements exceed this, they overflow to infinity.

Step 2: Any operation involving infinity produces NaN (0×∞, ∞-∞, etc.).

Step 3: Loss becomes NaN, training fails.

```python
# Solution: gradient clipping
grad_norm = torch.norm(grad)
if grad_norm > max_norm:
    grad = grad * max_norm / grad_norm  # scale down
```

Answer: **Gradient overflow causes NaN. Fix: gradient clipping, smaller learning rate, or mixed precision training.**

### Example 3 — Comparing Floats Safely

```python
# NEVER do this:
if x == 0.1:  # WRONG — floating point is inexact

# Do this instead:
epsilon = 1e-12
if abs(x - 0.1) < epsilon:  # CORRECT — check within tolerance
```

### Example 4 — CS Application: Numerical Stability in ML

```python
# Log-sum-exp trick: avoid overflow in softmax
# Instead of computing exp(large), subtract max first:
def softmax(logits):
    max_val = np.max(logits)
    stable = logits - max_val  # shift so max = 0
    exp_vals = np.exp(stable)
    return exp_vals / np.sum(exp_vals)
```

## Why This Works

Floating point is a trade-off: finite precision for wide range. Every operation rounds the result to the nearest representable number. The relative error of each operation is bounded by machine epsilon.

Catastrophic cancellation occurs because the subtraction reveals the rounding errors that were previously hidden in the trailing digits. When the leading digits cancel, those hidden errors become the entire result.

Kahan summation works because the compensation term captures the rounding error from each addition. The expression (t-s)-y is algebraically zero, but in floating point it equals -rounding_error(y). By subtracting this from the next value, the error is corrected.

## Common Mistakes

> [!failure] Mistake pattern: Comparing floats with ==
> Never write `if x == 0.1`. Use `abs(x - 0.1) < epsilon` instead.

> [!failure] Mistake pattern: Ignoring precision in iterative algorithms
> In gradient descent, loss might stop decreasing due to precision limits, not convergence. Use double precision.

> [!failure] Mistake pattern: Assuming associativity and distributivity
> a(b+c) may not equal ab+ac in floating point due to rounding. Order of operations matters.

> [!failure] Mistake pattern: Confusing decimal and binary fractions
> 0.1, 0.2, 0.3 are repeating fractions in binary. Only fractions with denominator = power of 2 (0.5, 0.25, 0.125, 0.0625) are exact.
