## Introduction

**Hashing** takes any input and produces a fixed-size "fingerprint." The same input always gives the same output, but even a tiny change completely changes the output.

From [[6.2 Modular Arithmetic]], you know about mod operations. The simplest hash is h(k) = k mod m. From [[10.3 Binary Hexadecimal and Number Bases]], you understand binary representation — hash functions operate on binary data.

Hashing serves three fundamental purposes:
1. **Hash tables**: O(1) average lookup for key-value storage.
2. **Data integrity**: checksums verify files were not corrupted.
3. **Cryptography**: secure hashes provide tamper evidence.

The core tension: hash functions map an infinite domain (all possible inputs) to a finite range (fixed-size output). By the pigeonhole principle, collisions are inevitable. A good hash minimises them and makes them unpredictable.

## New Words

- **[[hash function]]** — maps arbitrary data to fixed-size output (hash/digest).
- **[[collision]]** — when two different inputs produce the same hash.
- **[[hash table]]** — data structure storing key-value pairs indexed by hash of the key.
- **[[cryptographic hash]]** — hash that is one-way (preimage resistant) and collision resistant.
- **[[checksum]]** — small hash for error detection (e.g., CRC32, MD5, SHA-256).

> [!important] You pass this topic only when you can define all five terms without looking.

## Breadcrumbs

### Breadcrumb 1: Simple Integer Hash — Modulo

**Builds on:** [[6.2 Modular Arithmetic]] (mod operator, modular arithmetic), [[10.3 Binary Hexadecimal]]

The simplest hash function for integer keys: h(k) = k mod m, where m is the table size.

#### Chunked Example

Question: Hash keys 15, 27, 42, 35 into a table of size m = 10.

Step 1: h(15) = 15 mod 10 = 5. h(27) = 27 mod 10 = 7.

Step 2: h(42) = 42 mod 10 = 2. h(35) = 35 mod 10 = 5.

Step 3: Keys 15 and 35 both map to slot 5 → collision!

Answer: **Slots: 15→5, 27→7, 42→2, 35→5. Collision at slot 5**.

### Breadcrumb 2: Collision Resolution — Chaining

**Builds on:** Breadcrumb 1

**Chaining**: each slot stores a linked list (or another data structure) of all keys that hash to that slot.

If keys are uniformly distributed, each slot has ~λ = n/m keys on average (load factor). Expected search time: O(1+λ/2).

#### Chunked Example

Question: m = 5, insert keys 12, 17, 22, 7 using h(k) = k mod 5.

Step 1: h(12)=2, h(17)=2, h(22)=2, h(7)=2.

Step 2: All hash to slot 2 → chain of 4 elements.

Step 3: Load factor λ = 4/5 = 0.8.

Step 4: Lookup: follow chain of length 4 → O(4) = O(1+λ).

Answer: **All at slot 2, chain length 4, λ=0.8**.

### Breadcrumb 3: Cryptographic Hashes

**Builds on:** Breadcrumb 1

A **cryptographic hash** must satisfy:
- **Preimage resistance**: given y, cannot find x such that H(x) = y (one-way).
- **Collision resistance**: cannot find x ≠ y such that H(x) = H(y).
- **Avalanche effect**: changing 1 input bit flips ~50% of output bits.

#### Chunked Example — SHA-256

Question: What are the properties of SHA-256?

Step 1: SHA-256 outputs 256 bits (32 bytes, 64 hex digits).

Step 2: Preimage resistance: finding x from H(x) requires ≈ 2²⁵⁶ attempts (brute force).

Step 3: Collision resistance: finding any x≠y with same hash requires ≈ 2¹²⁸ attempts (birthday bound).

Step 4: Avalanche effect: changing "hello" to "Hello" (capital H) completely changes the hash.

```
SHA-256("hello") = 2cf24dba5fb0a30e26e83b2ac5b9e29e...
SHA-256("Hello") = 185f8db32271fe25f561a6fc938b2e26...
```

Answer: **SHA-256: 256-bit, preimage resistant, collision resistant, avalanche effect**.

### Breadcrumb 4: Hash Tables — O(1) Average Lookup

**Builds on:** [[10.1 Big O Theta and Omega]] (amortised analysis), Breadcrumb 2

Hash tables achieve O(1) average lookup by using the hash to directly index into an array.

#### Chunked Example — Python Dict

Question: How do Python dicts achieve O(1) average lookup?

Step 1: hash(key) produces an integer. This integer modulo table size gives the slot.

Step 2: Python uses **open addressing** (not chaining) — if a slot is taken, it probes the next slot.

Step 3: When load factor λ > 2/3, the table is resized (amortised O(1)).

```python
d = {"name": "Alice", "age": 30}
# hash("name") → slot, store ("name", "Alice") there
# d["name"] → compute hash, go to slot, retrieve value
```

Answer: **Hash table with open addressing, resize at λ>2/3, amortised O(1) average**.

## Worked Examples

### Example 1 — Load Factor and Performance

Question: Hash table has m = 1000 slots, n = 750 entries. Average chain length? Average successful search time?

Step 1: λ = n/m = 750/1000 = 0.75.

Step 2: Average successful search (chaining): 1 + λ/2 = 1 + 0.375 = 1.375 comparisons.

Step 3: Average unsuccessful search: λ = 0.75 comparisons (all chains).

Answer: **Average 1.375 comparisons per successful lookup**.

### Example 2 — Bloom Filter

Question: How does a Bloom filter test set membership with controllable false positive rate?

Step 1: Use k independent hash functions. Bit array of size m, initially all 0.

Step 2: Insert x: set bits at h₁(x), h₂(x), ..., hₖ(x) to 1.

Step 3: Check y: if any of h₁(y), ..., hₖ(y) is 0 → y is definitely NOT in the set.

Step 4: If all are 1 → y is probably in the set (false positive possible, false negative impossible).

```python
# Used in: databases (avoid disk lookups), spell checkers, network routers
```

Answer: **Bloom filter: set membership with tunable false positive rate. No false negatives.**

### Example 3 — CS Application: Git Content-Addressable Storage

Question: How does Git identify files and commits?

Step 1: Every file stored as a blob, keyed by SHA-1 hash of its contents.

Step 2: Same file content → same hash → deduplication.

Step 3: Every commit stores hash of parent commit → chain guaranteeing integrity.

```text
.git/objects/ab/cdef1234...  # stored by hash prefix
```

Answer: **Git uses SHA-1 as content-addressable keys. Same content = same hash = no duplicates.**

### Example 4 — CS Application: Hash Table in a Database Index

```python
# Database hash index: O(1) equality lookups
# But NOT useful for range queries (use B-tree for that)
CREATE INDEX idx_user_id ON users USING HASH (user_id);
# SELECT * FROM users WHERE user_id = 42  → O(1)
# SELECT * FROM users WHERE user_id > 42  → cannot use hash index
```

## Why This Works

If the hash function distributes keys uniformly, each slot has ~n/m keys on average. With m ≈ n, average lookup is O(1). This makes hash tables one of the most useful data structures in CS.

Cryptographic hashes rely on the difficulty of inverting a many-to-one function. The avalanche effect ensures that similar inputs produce completely different outputs, preventing attackers from guessing the input from the hash.

The birthday paradox governs collision resistance: finding any collision requires only ≈ √N attempts for an N-bit hash (2^(n/2)), not N attempts (2^n). This is why SHA-256 needs 256 bits for 128 bits of collision resistance.

## Common Mistakes

> [!failure] Mistake pattern: Using a bad hash function
> h(k)=k mod m with m=2^k (power of 2) discards bits. Choose prime m for better distribution.

> [!failure] Mistake pattern: Confusing cryptographic hash with checksum
> MD5 is broken for security (collision found) but still used as checksum. SHA-256 is standard for security.

> [!failure] Mistake pattern: Ignoring hash table worst case
> With a terrible hash function (all keys same slot), lookup is O(n). Python's hash randomisation mitigates this.

> [!failure] Mistake pattern: Thinking cryptographic hashes can be reversed
> Preimage resistance means given a hash, you cannot find the input. Passwords hashed with SHA-256 cannot be "decrypted."

## Where This Shows Up in CS

### Data Structures
```python
# Python: set, dict, frozenset all use hash tables
s = {1, 2, 3}           # hash set
d = {"key": "value"}    # hash map
```

### Git
```text
- Every commit identified by SHA-1 hash
- Content-addressable: file hash = blob ID
- Integrity: verify history via hash chain
```

### Cryptography
```text
- Password storage: hash (not plaintext)
- Digital signatures: hash then sign
- Blockchain: hash chain of blocks
- TLS/SSL: hash in certificate verification
```

### Databases
```text
- Hash indexes: O(1) point lookups
- Hash joins: O(m+n) join (vs O(m×n) nested loop)
- Partitioning: hash to distribute across servers
```
